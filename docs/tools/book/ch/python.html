1The big picture: what runs when you type python app.py

Python is the language the wider industry reaches for when the important thing is how quickly people can build and change something: web backends, data pipelines, machine-learning code, test harnesses and glue scripts. It pays for that with a slow interpreter, and it gets away with it because the heavy work usually happens in C, C++ or Rust underneath. Understanding where that boundary lies is the single most useful thing to know about Python performance.

1.1Python is a language; CPython is the program that runs it

"Python" names a language specification, and several programs implement it. CPython, the reference implementation written in C, is what you get from python.org, from your Linux distribution, from uv python install and inside nearly every Docker image. PyPy is an alternative with a tracing JIT compiler that runs pure-Python loops several times faster, MicroPython runs on microcontrollers, and GraalPy runs on the JVM's Graal compiler. When people say "Python does X", they almost always mean "CPython does X", and many things that look like language rules (reference counting, the GIL, the size of an int) are really CPython implementation details.

CPython dominates for one practical reason: its C API. NumPy, pandas, PyTorch, OpenCV's Python bindings, cryptography, lxml and thousands of other packages are compiled extensions that talk directly to CPython's internal object structures. An alternative interpreter must either emulate that API (slowly) or lose the ecosystem. That is also why CPython changes carefully: removing the GIL took years largely because extensions had silently relied on it.

This chapter follows one interpreter version as its reference, CPython 3.14 (October 2025), and says when a behaviour is new. The annual release cycle matters in practice: 3.11 made the interpreter about 25 % faster on average, 3.12 made some objects immortal, 3.13 shipped an experimental free-threaded build, and 3.14 made that build officially supported. A team on 3.9 is running a noticeably different machine from a team on 3.14.

1.2From source text to a running program

CPython is often called an interpreter, but it does not interpret your source text line by line. When a module is imported (or run as the main script), CPython first compiles it. The tokenizer splits the text into tokens; the parser, a PEG parser since 3.9, builds an abstract syntax tree (AST); the compiler turns the AST into a code object per function, class body and module: a compact array of bytecode instructions plus tables of constants, local variable names and line numbers. Only then does the evaluation loop (the function _PyEval_EvalFrameDefault in ceval.c, usually just called "ceval") execute the bytecode one instruction at a time.

Compilation is cached. The marshalled code object is written to __pycache__/app.cpython-314.pyc, keyed by the source file's modification time and size (or by a hash, if you ask for reproducible builds), so the next import skips straight to execution. The main script itself is compiled every time, which is one reason tools keep the entry script tiny and put the code in an importable package. Once imported, a module object is stored in sys.modules; a second import of the same name is just a dictionary lookup. You can watch each stage yourself: ast.dump(ast.parse(src)) prints the tree, dis.dis(fn) prints the bytecode, and python -X importtime app.py prints how long each import took, which is often the first thing to look at when a command-line tool feels sluggish to start.

Interesting detail

Because import executes the module's top-level code, "import" in Python is a run-time action, not a compile-time declaration as in C++. Class and function definitions are statements that create objects when they execute. That is what makes decorators, metaclasses and plugin registries possible, and also why a slow or side-effecting import (connecting to a database at module level) is a design smell. Python 3.15 adds explicit lazy imports (PEP 810) precisely because eager import time became a real cost for large command-line tools.

1.3Why Python is slow, and why that is usually fine

Take the smallest possible loop: adding up a list of a million integers. In C++ the compiler knows the type of every value, keeps them in registers and may vectorise the loop into a handful of SIMD instructions per eight elements. In CPython each iteration executes about six bytecode instructions; each instruction is a trip through the dispatch loop; the integers are separate heap objects with a type pointer and a reference count; the addition must check the types, allocate a new int object for the result and adjust reference counts on the old ones. Measured on CPython 3.14, a plain for loop takes 20.4 ms for a million integers, about 20 ns per element. The builtin sum() does the same thing in a C loop and takes 3.6 ms. NumPy's arr.sum() over a contiguous array of machine integers takes 0.26 ms, eighty times faster than the Python loop.

The industry's answer is not to make Python fast but to keep Python as the orchestration layer and push the inner loops down. A FastAPI service spends its time waiting for the database and in Pydantic's validation core, written in Rust. A pandas or Polars pipeline spends its time in C, C++ or Rust kernels over columnar buffers. A PyTorch training script spends its time in CUDA kernels; Python just decides which ones to launch. The skill that separates a strong Python engineer is knowing which side of that boundary each line of code is on. A loop over a million rows written in Python is a bug in a data pipeline, but a loop over ten HTTP handlers is not worth a second thought.

Numbers

Measured on CPython 3.14.6, x86-64 cloud VM: one attribute load o.x ≈ 8 ns, one int addition ≈ 9 ns, one call into a pybind11 function ≈ 0.6 µs, awaiting a trivial coroutine ≈ 58 ns, one event-loop round trip ≈ 1.6 µs, starting and joining a thread ≈ 80–100 µs. A useful mental unit: CPython executes on the order of 50–100 million simple bytecode instructions per second per core, a C++ loop on the order of billions of operations.

Talk track

"Python is slow per operation, roughly fifty times slower than C++ on a tight loop, because every value is a heap object and every operation is dynamically dispatched. We use it anyway because the expensive work runs in compiled libraries: NumPy, Polars, PyTorch, the database. Our job is to keep the hot loops inside those libraries and to measure before we optimise."

2Objects, names and references

Almost every surprise a C++ programmer has with Python, and many that Python programmers have too, comes from one fact: variables do not hold values, they hold references to objects on the heap. Once you see the objects and the arrows, mutability, aliasing, argument passing and the cost of a list of numbers all follow.

2.1Everything is a PyObject

Every value in CPython, from the integer 1 to a function, a class or a module, is a C struct allocated on the heap that begins with the same two fields: ob_refcnt, a reference count, and ob_type, a pointer to the object's type. The type object is itself a PyObject (of type type) and holds a table of function pointers: how to add, compare, hash, iterate, get attributes, and how to free an instance. When the interpreter executes a + b, it does not know at compile time what a is; it follows a's type pointer and calls whatever the type supplies for addition. This is the dynamic dispatch that a C++ virtual call does through a vtable, except that it happens for every operation, including arithmetic on numbers.

The sizes explain why a list of numbers is expensive. An int is a variable-length object holding its value in 30-bit "digits" (Python ints have unlimited precision, so 2**64 simply needs more digits: 36 bytes). A float is a boxed C double: 24 bytes for 8 bytes of payload. A tuple stores its item pointers inline after a header; a list stores them in a separately allocated, over-allocated array so that append is amortised O(1). Container objects that can take part in reference cycles (lists, dicts, tuples, instances) carry an extra 16-byte header for the cycle collector, which is why an empty tuple is 48 bytes and an empty list 56. Measured with sys.getsizeof: object() 16 bytes, 1.0 24, "abc" 44, an empty dict 64, a three-key dict 184, an empty set 216.

CPython's integer objects for −5 to 256 are created at start-up and shared. int("256") is 256 is True; int("257") is 257 is False, because 257 is built fresh each time. Short strings that look like identifiers are similarly interned (one shared copy), which makes attribute and dictionary lookups with them faster because equal strings are then usually the same object and compare by pointer first.

Pitfall

is compares identity (the same object), == compares values. x is 257 may be true in one place and false in another depending on how the value was produced; CPython even emits a SyntaxWarning for is with a literal. Use is only for singletons: None, True, False, sentinel objects and enum members.

2.2Names are labels, assignment binds

A Python variable is a name in a namespace (a function's local slots, a module's dictionary, an object's attribute dictionary) that refers to an object. Assignment b = a never copies anything: it makes the name b refer to the same object as a and increments that object's reference count. Whether a later change through b is visible through a depends only on whether the operation mutates the object or rebinds the name. Step through the figure to see the difference.

Function arguments work the same way, which is sometimes called call by sharing: the parameter name is bound to the caller's object. A function that appends to a list parameter changes the caller's list; a function that assigns a new list to the parameter changes nothing outside. This is neither C++ pass-by-value (no copy is made) nor pass-by-reference (rebinding the parameter does not rebind the caller's variable). The closest C++ picture is that every Python variable is a std::shared_ptr<Object> passed by value: the pointer is copied, the object is shared, and the reference count tracks the owners (the C++ chapter shows what that costs in C++).

2.3Mutability, hashing and the mistakes that follow from them

Some types are immutable: int, float, str, bytes, tuple, frozenset, and by convention frozen dataclasses. Every operation on them produces a new object. Others are mutable: list, dict, set, bytearray and ordinary class instances. The split exists for hashing. A dictionary finds a key by its hash; if the key could change after insertion, its hash would change and the entry would be lost in the wrong slot. So only hashable objects (whose hash never changes during their lifetime) can be dict keys or set members, and the built-in mutable containers deliberately define __hash__ = None. A tuple is hashable only if everything inside it is.

Three classic mistakes come straight from this model. The mutable default argument: def add(item, bucket=[]) evaluates [] once, when the def statement runs, so every call that omits bucket shares the same list and it grows across calls. The fix is bucket=None and creating the list inside. The shallow copy: grid = [[0] * 3] * 3 creates one inner list and three references to it, so setting grid[0][0] changes all three rows; [[0] * 3 for _ in range(3)] creates three lists. And aliasing across layers: a service caches a dict and returns it to callers, one caller mutates it, and every later request sees the change. copy.copy copies the outer container, copy.deepcopy recursively copies everything it can reach (and is slow); returning immutable objects (tuples, frozen dataclasses, Pydantic models with frozen=True) avoids the question.

def add(item, bucket=[]):        # the [] is created once, at def time
    bucket.append(item)
    return bucket

add(1); add(2)                   # -> [1, 2]: the default list is shared between calls

def add(item, bucket=None):      # the idiom
    if bucket is None:
        bucket = []
    bucket.append(item)
    return bucket
Why it matters

In a backend service, a module-level dict or list is shared by every request that the process handles, across threads and, with asyncio, across interleaved coroutines. Most "it works in tests, corrupts data under load" bugs in Python services are shared mutable state that nobody meant to share.

2.4Inside the containers: list, tuple, dict and set

A list is a dynamic array of pointers. When it runs out of space, CPython grows it by about one-eighth plus a constant, which gives the capacities measured in 3.14: 4, 8, 16, 24, 32, 40 for the first 40 appends. Appending and popping at the end are amortised O(1); inserting or deleting at the front shifts every pointer, which is O(n) (use collections.deque for queues). Indexing is O(1), membership x in lst is a linear scan. A tuple is a fixed-size array stored inline, slightly smaller and faster to create than a list; CPython 3.14 also caches a tuple's hash inside it.

A dict is a hash table, and since Python 3.6 it is a compact one. It keeps two arrays: a small, sparse indices table (one byte per slot while the dict has fewer than 128 entries) and a dense entries array of (hash, key, value) triples in insertion order. A lookup hashes the key, uses the low bits to pick a slot, follows the slot's index to the entry, and confirms the match by comparing the stored hash and then the key. Collisions are resolved by probing other slots in a pseudo-random sequence that mixes in the higher bits of the hash. Because iteration walks the dense entries array, dicts preserve insertion order, a CPython detail in 3.6 that became a language guarantee in 3.7.

A set is a hash table of keys without values (and without the compact layout, which is why an empty set is larger than an empty dict). Hash tables in CPython resize before they are two-thirds full, so the expected number of probes stays close to one. String hashes are randomised per process (PYTHONHASHSEED), which defends web services against attackers who send many keys with colliding hashes to turn O(1) lookups into O(n). The algorithms chapter explains why such cache-friendly layouts beat theoretically equivalent pointer-based structures.

2.5Classes and instances

A class is an object too, created at run time when the class statement executes, and an instance stores its attributes in a per-instance namespace. Historically that was a full dict per instance; recent CPython versions create the dict lazily and store attribute values inline in the instance when all instances of a class share the same attribute names (the "shared keys" layout), so the memory gap between a plain instance and a __slots__ instance is much smaller than it was before 3.11 (memory advice written for Python 2 often overstates it). __slots__ = ("x", "y") still has its uses: it forbids any other attribute (a typo like p.xx = 1 raises instead of silently creating a new attribute), removes the dict entirely, and makes attribute access a fixed-offset load. @dataclass(slots=True) generates it for you.

Method calls follow the method resolution order (MRO), a linearisation of the class and its bases computed by the C3 algorithm, visible as Cls.__mro__. super() does not mean "my parent"; it means "the next class after me in the MRO of the object's actual type", which is what makes cooperative multiple inheritance (mixins) work. Chapter 6 shows the exact attribute lookup rules, including why a property beats an instance attribute but an instance attribute beats a method.

In practice

Coming from C++: there is no "private" in Python, only conventions (_internal, and __mangled names that get the class name prefixed). There are no overloads by type (use functools.singledispatch or default arguments), no const, and no destructors you can rely on for anything but memory (use context managers, Chapter 6). Interfaces are expressed with abstract base classes or, more idiomatically today, structural Protocol types (Chapter 9).

Talk track

"In Python every value is a heap object with a reference count and a type pointer, and variables are just names bound to those objects. Assignment and argument passing copy the reference, never the object, so a mutation is visible to everyone holding the same object and a rebinding is visible to nobody. That is why mutable defaults and shared module-level state cause bugs, and why only immutable things can be dictionary keys."

3Memory management: reference counting, the cycle collector and the allocator

C++ makes you decide who frees each object; Python decides for you. CPython does it with two mechanisms that work together: reference counting frees most objects the instant they become unused, and a cycle collector periodically finds groups of objects that only reference each other. Knowing both explains when memory is released, why it sometimes is not, and why the GIL existed in the first place.

3.1Reference counting: deterministic and cheap per step, but everywhere

Every time a reference to an object is created (bound to a name, stored in a list, pushed on the value stack, passed as an argument), CPython increments the object's ob_refcnt; every time a reference disappears, it decrements it. When the count reaches zero, the object's type's deallocation function runs immediately: it decrements the counts of everything the object refers to (which may free them in turn) and returns the memory to the allocator. You can see the count with sys.getrefcount(x), which reports one more than you expect because the argument itself is a temporary reference: a fresh list measured 2, and after y = x and z = [x, x] it measured 5.

The great property of reference counting is determinism. A file object closes its file descriptor the moment the last reference goes away, a large NumPy array's buffer is freed when the last view of it dies, and memory use follows the program's actual working set instead of waiting for a collector. The costs are a write to memory on nearly every operation (even reading a value from a list increments and later decrements its count), and the fact that those writes must not race. Two threads incrementing the same count without synchronisation could lose an update and free an object that is still in use. The simplest protection is one lock around the whole interpreter: the GIL (Chapter 7).

Since Python 3.12 some objects are immortal (PEP 683): None, True, small integers, interned strings and other objects that live for the whole process have their reference count set to a huge sentinel (measured: 3,221,225,472 for both None and 1) and increments and decrements on them are skipped. That removes millions of useless writes and, importantly for servers that fork worker processes, stops those writes from dirtying shared memory pages that would otherwise be copied by the operating system's copy-on-write.

3.2Cycles and the cycle collector

Reference counting alone cannot free a cycle. A parent node holding a list of children, where each child holds a reference back to its parent, keeps every count at one or more even when nothing outside refers to the structure. CPython therefore runs a second mechanism, the cycle collector (the gc module), which considers only container objects (those that can refer to other objects) and finds groups that are unreachable from outside. The algorithm is clever because it never needs to know the program's roots (stack variables, C globals): it works purely from reference counts.

Scanning every container on every allocation would be far too expensive, so the collector is generational: new containers start in the young generation, and a collection of the young generation is triggered when allocations minus deallocations of containers exceed a threshold (2,000 on 3.14, from gc.get_threshold() = (2000, 10, 10)). Objects that survive are promoted to older generations that are collected less often, on the observation that most objects die young. Recent releases have experimented with making the old-generation collection incremental to reduce pause times on very large heaps, so treat the thresholds as tunables of your version rather than constants of the language.

In practice

Large services sometimes tune the collector rather than leave it alone. Instagram famously ran Django with the cycle collector disabled and later used gc.freeze() (3.7+): call it in the parent process just before forking workers, and every object that exists at that moment is moved to a permanent generation that is never scanned, so the collector's writes do not trigger copy-on-write copies of shared pages in every worker. If a batch job allocates millions of long-lived objects, temporarily disabling the collector with gc.disable() during the build phase can also save seconds of repeated scans.

Pitfall

Reference cycles that include big objects delay their release until the next collection, which matters for GPU tensors, large arrays and open sockets. A classic source is an exception stored in a variable: the traceback references the frame, the frame references the variable, and the variable references the exception. Python deletes the name bound by except E as e: at the end of the block for exactly this reason. Use weakref for back-pointers (child → parent, observer lists, caches with WeakValueDictionary) when you design structures with natural cycles.

3.3The allocator, and why memory does not go back to the operating system

Allocating many small objects with malloc would be slow and fragment the heap, so CPython has its own small-object allocator, pymalloc. Requests up to 512 bytes are rounded up to one of 32 size classes (multiples of 16 bytes) and served from 16 KiB pools, each pool holding blocks of one size class; pools are carved out of 1 MiB arenas obtained from the operating system with mmap (sizes from sys._debugmallocstats() on 3.14). Larger requests go to the system malloc. The free-threaded build replaces pymalloc with Microsoft's mimalloc, which is thread-safe without a global lock.

An arena is returned to the operating system only when every block in it is free. A long-running service that briefly builds a million small objects and then frees most of them can therefore keep its resident memory high: a few survivors pin many arenas. This is fragmentation, not a leak, and it is why the standard production answer is worker recycling: Gunicorn's max_requests, Celery's worker_max_tasks_per_child or a Kubernetes memory limit with a restart policy replace worker processes after a while. To find a real leak, compare two tracemalloc snapshots, which attribute live allocations to source lines, or use Bloomberg's memray, which also tracks allocations made by C extensions.

import tracemalloc
tracemalloc.start(25)                       # keep 25 frames of traceback per allocation
before = tracemalloc.take_snapshot()
handle_many_requests()
after = tracemalloc.take_snapshot()
for stat in after.compare_to(before, "lineno")[:5]:
    print(stat)                             # e.g. cache.py:41: size=48.2 MiB (+48.2 MiB), count=401234 (+401234)
Talk track

"CPython frees most objects immediately by reference counting, which is deterministic but needs every count update to be protected, historically by the GIL. Cycles are found by a generational collector that subtracts internal references and frees what is left. 4Executing code: bytecode, frames and the adaptive interpreter

To reason about Python performance you need a picture of what the interpreter does per line. That picture is a stack machine executing bytecode on frames, and since 3.11 a machine that rewrites its own instructions to specialise for the types it actually sees.

4.1Code objects, frames and the value stack

Each function is compiled into a code object: its bytecode, constants, variable names and some flags. Calling the function creates a frame: an activation record holding the local variables in fixed slots (an array, not a dictionary, which is why local variables are faster than globals), the value stack, the instruction pointer and a link to the calling frame. Since 3.11 frames live in a contiguous per-thread stack of memory and are only turned into full Python objects when something asks for them, such as a traceback or sys._getframe().

CPython's bytecode is for a stack machine: instructions push operands onto the frame's value stack and pop them off. Here is the real output of dis.dis on CPython 3.14 for the summing loop from Section 1.3, with the loop body highlighted in the stepper below.

Names that are not local are looked up differently. A global is found in the module's dict and then the builtins dict (LOAD_GLOBAL), an attribute through the attribute protocol (LOAD_ATTR, Section 6.4), and a variable from an enclosing function through a cell object (Section 6.1). The old advice to copy globals into locals for speed (append = out.append before a loop) matters much less since 3.11, because of what the next section describes.

4.2The specialising adaptive interpreter

Python code is dynamically typed, but most code is not dynamically used: a given + in a given line adds ints almost every time it runs, and a given obj.x almost always sees the same class. CPython 3.11 introduced the specialising adaptive interpreter (PEP 659), the main reason 3.11 was about 25 % faster than 3.10. Each instruction that can benefit has a small inline cache next to it in the bytecode. After the instruction has executed a few times, the interpreter looks at the operands it saw and rewrites the instruction in place to a specialised form: BINARY_OP becomes BINARY_OP_ADD_INT, LOAD_ATTR becomes LOAD_ATTR_INSTANCE_VALUE with the attribute's offset cached, LOAD_GLOBAL becomes LOAD_GLOBAL_MODULE with the dict's version number cached. The specialised form starts with a cheap guard (is it really an int? is the type version unchanged?) and takes the fast path. If the guard keeps failing, the instruction is de-specialised and tried again later.

You can watch it happen. Running add_all 2,000 times and calling dis.dis(add_all, adaptive=True) on 3.14 shows FOR_ITER_LIST, BINARY_OP_ADD_INT and RESUME_CHECK where the plain disassembly showed the generic forms. The specialised code is the input to the next step, a JIT compiler: 3.13 added an experimental "copy-and-patch" JIT that stitches together precompiled machine-code templates for hot sequences of specialised instructions. It is off by default (enabled with PYTHON_JIT=1 on builds that include it), its gains so far are modest, and the build used here was compiled without it, which is why the loop's jump shows up as JUMP_BACKWARD_NO_JIT. CPython 3.14 also gained an alternative interpreter loop built on tail calls between instruction handlers when compiled with a recent Clang, worth a few percent.

Interesting detail

Exceptions became "zero-cost" in 3.11: entering a try block no longer executes any instruction. Instead the compiler emits an exception table mapping instruction ranges to handlers, consulted only when an exception is actually raised. Raising and catching is still not free (it creates an exception object and a traceback), so "ask forgiveness, not permission" (try: d[k] except KeyError) is the right style when the exception is rare and the wrong one in a hot loop where it is common.

4.3Faster Python: the options in order of effort

When profiling shows that Python itself, not I/O or a library, is the bottleneck, the options form a ladder. First, use a better algorithm or a builtin: sum, sorted, collections.Counter, set membership instead of list scans, str.join instead of repeated +=. Second, vectorise with NumPy, pandas or Polars so that the loop runs in compiled code (Chapter 10). Third, upgrade the interpreter: moving from 3.10 to 3.14 is a free speedup for most code. Fourth, compile the hot function: Numba JIT-compiles numerical functions over NumPy arrays from a decorator; Cython and mypyc compile annotated Python to C extensions. Fifth, write the kernel in C++ or Rust and bind it (Chapter 11). A different interpreter such as PyPy is attractive for pure-Python workloads but is usually ruled out by C extensions.

Pitfall

Micro-optimising Python code that is not the bottleneck is the most common waste of time in Python performance work. A web endpoint that spends 40 ms in a database query and 0.2 ms in Python gains nothing from local-variable tricks. Measure with a profiler first (Section 14.1), then decide which rung of the ladder to climb.

4.4The import system

An import x statement first checks sys.modules. On a miss it asks each finder on sys.meta_path whether it can locate x; the default path finder walks sys.path entries in order (Figure 12.1) and returns a spec naming a loader. The loader creates an empty module object, inserts it into sys.modules before running its code (so circular imports see a partially initialised module rather than recursing forever), and executes the module's code object in the module's namespace. A package is a module with a __path__: a directory with an __init__.py, or, without one, a namespace package that can be spread over several directories.

The model explains the classic import errors. A circular import fails with "cannot import name X (most likely due to a circular import)" when module A does from b import f while b, half-initialised, is importing A: the name does not exist yet. A local file named json.py or random.py next to your script shadows the standard library because the script's directory is the first entry on sys.path. And a module-level import of a heavy library (pandas takes several hundred milliseconds to import) is paid by every command of a CLI, which is why tools import heavy modules inside the function that needs them.

5Protocols, iteration and generators

Python's flexibility comes from a small number of protocols: special methods with double-underscore names that the interpreter calls on your behalf. Iteration is the most important of them, and generators make it possible to process data that does not fit in memory with code that reads like a simple loop.

5.1The data model: operators are method calls

Every piece of syntax maps to a special method on the operand's type. len(x) calls type(x).__len__(x), x[i] calls __getitem__, x == y calls __eq__, with calls __enter__ and __exit__, for calls __iter__ and __next__. For binary operators the left operand gets the first try: a + b calls a.__add__(b), and if that returns the special value NotImplemented, Python tries b.__radd__(a). That two-sided rule is how 2 * np.array([1, 2]) works although the int type knows nothing about NumPy. Lookups of special methods go to the type, not the instance, which is both faster and why you cannot make one object iterable by assigning obj.__iter__ = ....

The practical consequence is duck typing: a function that iterates over its argument works with a list, a generator, a file, a database cursor or your own class, as long as it implements the protocol. Libraries lean on this heavily. A Polars DataFrame, a FastAPI request body and a PyTorch tensor all feel native because they implement the same handful of protocols as built-in types.

5.2Iterables and iterators

An iterable is anything with __iter__ that returns an iterator; an iterator is an object with __next__, which returns the next item or raises StopIteration, and an __iter__ that returns itself. A for loop is shorthand for exactly that:

for row in rows:          # is executed as:
    use(row)

it = iter(rows)           # rows.__iter__()
while True:
    try:
        row = next(it)    # it.__next__()
    except StopIteration:
        break
    use(row)

The distinction matters because an iterator is consumed. A list is an iterable you can loop over many times; a generator, a file object or zip(...) is an iterator you can loop over once, and a second loop silently sees nothing. Functions that need two passes over their input should either accept a sequence or materialise it with list(...) knowingly.

5.3Generators: functions that can pause

A function containing yield is a generator function. Calling it does not run its body; it returns a generator object that holds a suspended frame. Each next() resumes the frame until the next yield, which hands a value to the caller and suspends the frame again, keeping all its local variables, its position and even an open file. When the function returns, the generator raises StopIteration. Mechanically, a generator is a frame that lives on the heap instead of the C stack, which is why suspending and resuming costs about as much as a function call.

Generators turn data processing into a pipeline of small, composable stages that stream in constant memory. The first stage of the sales pipeline could read a large CSV file like this:

import csv
from collections.abc import Iterator

def read_rows(path: str) -> Iterator[dict[str, str]]:
    with open(path, newline="") as f:          # the file stays open while the generator is suspended
        yield from csv.DictReader(f)

def valid(rows):
    for r in rows:
        if r["qty"].isdigit() and int(r["qty"]) >= 3:
            yield r

def revenue(rows):
    for r in rows:
        yield r["city"], int(r["qty"]) * float(r["price"])

totals: dict[str, float] = {}
for city, amount in revenue(valid(read_rows("orders.csv"))):   # one row in memory at a time
    totals[city] = totals.get(city, 0.0) + amount

yield from delegates to a sub-iterator, passing values through in both directions. Generators can also receive values (gen.send(v) makes the paused yield expression evaluate to v), be told to raise an exception at the pause point (throw) or be closed (close). Those three methods were the original building blocks of coroutines, and Chapter 8 shows that async def coroutines are a direct descendant: the same suspended-frame machinery, driven by an event loop instead of a for loop.

Pitfall

A generator's finally blocks and with exits run only when the generator finishes or is closed. If a consumer stops early (a break, an exception) and keeps a reference to the generator, the file stays open until the generator is garbage-collected. For resources that must be released promptly, close the generator explicitly or wrap it in contextlib.closing.

5.4Comprehensions and functional techniques

List, dict and set comprehensions ([f(x) for x in xs if p(x)]) are the idiomatic replacement for map-and-filter loops; a generator expression with round brackets is the lazy version and can be passed straight to sum, any, max or "".join. Since 3.12 comprehensions are inlined into the enclosing function (PEP 709) instead of creating a hidden function call, which made them up to twice as fast.

Python supports a functional style without being a functional language. Functions are first-class values; functools.partial fixes some arguments; functools.reduce folds; functools.cache and lru_cache memoise pure functions; functools.singledispatch gives open-ended dispatch on the type of the first argument; operator.itemgetter and attrgetter make fast key functions for sorting. The itertools module is the toolkit for lazy streams: chain, islice, groupby (which groups only consecutive equal keys, so sort first), accumulate, product, pairwise and batched (3.12), which cuts a stream into chunks, for example to insert rows into a database in batches of 1,000. What Python does not have is tail-call elimination (recursion is limited to about 1,000 frames by default) or cheap immutable collections, so deep recursion and persistent data structures are not idiomatic.

Talk track

"A for loop calls iter() once and next() until StopIteration. A generator is a function whose frame can be suspended at yield and resumed by next(), so a pipeline of generators processes one item at a time in constant memory, however big the input. async/await is built on the same suspended-frame mechanism."

6Functions, decorators, context managers, descriptors and metaclasses

Frameworks look like magic until you know the five mechanisms they are built from. @app.get("/orders") is a decorator, with session: is a context manager, @property and every method call are descriptors, and a Pydantic model or a Django model class is assembled by a metaclass. Each one is a small, well-defined hook into code that runs when Python executes a definition or looks up an attribute.

6.1Functions are objects, and closures capture variables

Executing a def statement creates a function object: the code object plus the module's globals, the default argument values (evaluated once, at that moment, hence the mutable-default trap of Section 2.3), and a tuple of cells for variables captured from enclosing functions. A function that refers to a variable of an enclosing function is a closure: the compiler stores that variable in a cell object shared by both functions, so the inner function sees the variable itself, not a snapshot of its value. nonlocal lets the inner function rebind it.

def make_counter():
    count = 0                     # lives in a cell, shared with inc
    def inc():
        nonlocal count
        count += 1
        return count
    return inc

handlers = [lambda: i for i in range(3)]
[h() for h in handlers]           # [2, 2, 2]: all three closures share one variable i
handlers = [lambda i=i: i for i in range(3)]
[h() for h in handlers]           # [0, 1, 2]: the default captures the value at def time

The second example is the late-binding pitfall: closures capture variables, not values, so callbacks created in a loop all see the loop variable's final value. A default argument or functools.partial captures the value instead. C++ programmers can map this directly: a Python closure always captures by reference, like [&], except that the cell keeps the variable alive as long as any closure needs it.

6.2Decorators: functions that transform functions

A decorator is any callable that takes a function (or class) and returns a replacement. The syntax is pure shorthand: @timed above def f means f = timed(f), executed once, when the definition runs. A decorator with arguments, such as @retry(times=3), is a function that returns a decorator. The idiomatic shape wraps the original in a closure and copies its name, docstring and signature with functools.wraps, so that tracebacks, documentation tools and frameworks that inspect signatures (FastAPI, pytest, Typer) still see the original.

import functools, time, logging
from collections.abc import Callable

def retry[**P, R](times: int = 3, delay: float = 0.1) -> Callable[[Callable[P, R]], Callable[P, R]]:
    def decorate(fn: Callable[P, R]) -> Callable[P, R]:
        @functools.wraps(fn)
        def wrapper(*args: P.args, **kwargs: P.kwargs) -> R:
            for attempt in range(1, times + 1):
                try:
                    return fn(*args, **kwargs)
                except ConnectionError:
                    if attempt == times:
                        raise
                    logging.warning("retry %s (%d/%d)", fn.__name__, attempt, times)
                    time.sleep(delay * 2 ** attempt)      # exponential backoff
            raise AssertionError("unreachable")
        return wrapper
    return decorate

@retry(times=5)
def fetch_rates(currency: str) -> dict[str, float]: ...

Decorators are how frameworks register things without configuration files. FastAPI's @app.post("/orders") stores the function and its signature in the application's route table and returns the function unchanged; pytest's @pytest.fixture marks a function for the fixture system; @functools.cache wraps a function with a dictionary lookup; @dataclass is a class decorator that reads the class's annotations and generates __init__, __repr__ and __eq__. The typing in the example uses ParamSpec with the 3.12 type-parameter syntax so that type checkers know the wrapper accepts exactly the wrapped function's arguments.

6.3Context managers: Python's answer to RAII

C++ releases resources in destructors, which run at a precisely known point. Python's reference counting often frees objects promptly too, but the language does not promise it (other implementations, cycles and stored tracebacks all delay it), so resource release needs an explicit construct: the with statement. with mgr as x: calls mgr.__enter__(), binds its result to x, runs the block, and then always calls mgr.__exit__(exc_type, exc, tb), whether the block finished normally, returned, or raised. If __exit__ returns true, the exception is suppressed. Files, locks, database transactions, temporary directories, HTTP sessions and decimal precision settings are all context managers.

from contextlib import contextmanager
import time

@contextmanager
def timer(label: str):
    t0 = time.perf_counter()
    try:
        yield                          # the with-block runs here
    finally:
        print(f"{label}: {(time.perf_counter() - t0) * 1e3:.1f} ms")

with timer("aggregate"), db.transaction():   # several managers, exited in reverse order
    aggregate()

contextlib.contextmanager turns a generator into a context manager: code before the yield is the enter part, code after it is the exit part, and an exception in the block is re-raised at the yield. contextlib.ExitStack handles a dynamic number of resources, suppress ignores chosen exceptions, and async with calls __aenter__ and __aexit__, which may await, for asynchronous resources such as connection pools.

Why it matters

Relying on reference counting to close things is a latent bug: it works in CPython until an exception's traceback keeps the frame alive, or until someone runs the code under PyPy. Linters flag open() without with for this reason (ruff rule SIM115).

6.4Descriptors and attribute lookup

Attribute access is a protocol too, and the descriptor protocol is the piece that makes methods, properties, classmethod, staticmethod, __slots__ and ORM fields work. A descriptor is an object stored on a class that defines __get__, and optionally __set__ or __delete__. When you read obj.attr, object.__getattribute__ follows a fixed order that decides between the class's descriptor and the instance's own dictionary.

Two everyday facts fall out of this order. First, methods are descriptors: a function stored on a class has a __get__ that returns a bound method, an object that remembers self. That is the whole implementation of self; there is no special method dispatch in the language. (The interpreter avoids creating the bound-method object for the common obj.method(...) pattern by loading the function and self together.) Second, a property is a data descriptor, so it cannot be shadowed by an instance attribute, while functools.cached_property is deliberately a non-data descriptor: on first access it computes the value and stores it in the instance dict, and every later access finds the dict entry first and never calls the descriptor again.

class Positive:
    """A reusable validated field: a data descriptor."""
    def __set_name__(self, owner, name):          # called when the class is created
        self.name = "_" + name
    def __get__(self, obj, objtype=None):
        return self if obj is None else getattr(obj, self.name)
    def __set__(self, obj, value):
        if value <= 0:
            raise ValueError(f"{self.name[1:]} must be positive, got {value}")
        setattr(obj, self.name, value)

class OrderLine:
    quantity = Positive()
    price = Positive()
    def __init__(self, quantity, price):
        self.quantity, self.price = quantity, price   # goes through Positive.__set__

This is, in miniature, how Django model fields, SQLAlchemy columns and attrs validators work. When you want a fallback for missing attributes (a proxy, a lazy loader), define __getattr__, which is called only after the normal lookup fails; overriding __getattribute__ intercepts every access and is rarely the right tool.

6.5Classes are created by metaclasses

Because a class is an object, something must create it, and that something is its metaclass, by default type. Executing a class statement runs five steps: determine the metaclass from the bases; call its __prepare__ to get a namespace (normally a dict); execute the class body in that namespace, so every def and assignment becomes an entry; call metaclass(name, bases, namespace), which creates the class object, calls __set_name__ on descriptors such as Positive above and then __init_subclass__ on the parent class; finally apply any class decorators. type("Point", (), {"x": 0}) does the same thing as a one-line class statement.

A custom metaclass can intervene in any of those steps, which is how enum.Enum turns class attributes into singleton members, abc.ABCMeta refuses to instantiate classes with abstract methods, Django's ModelBase turns field declarations into database columns, and Pydantic's model metaclass reads annotations and builds a validator in Rust for the whole class. For your own code, two lighter hooks cover nearly every need: __init_subclass__ on a base class runs for every subclass (perfect for plugin registries), and class decorators post-process one class. The usual rule of thumb is that if you are not sure you need a metaclass, you do not.

class Exporter:
    registry: dict[str, type["Exporter"]] = {}
    def __init_subclass__(cls, *, fmt: str, **kw):
        super().__init_subclass__(**kw)
        Exporter.registry[fmt] = cls             # runs when each subclass is defined

class CsvExporter(Exporter, fmt="csv"): ...
class ParquetExporter(Exporter, fmt="parquet"): ...
Exporter.registry["parquet"]                     # -> ParquetExporter
Talk track

"A decorator is a function applied to a function at definition time; frameworks use it to register routes and fixtures. A context manager guarantees cleanup through __enter__ and __exit__, Python's RAII. Methods and properties are descriptors: class attributes with __get__, and data descriptors take priority over the instance dict. Classes are built by a metaclass when the class statement runs, which is how ORMs and Pydantic turn declarations into behaviour; __init_subclass__ covers most uses without a metaclass."

7Parallelism: the GIL, threads, processes and free-threaded Python

"Python can't do threads" is a half-truth worth taking apart. Python threads are real operating-system threads; what the global interpreter lock prevents is two of them executing Python bytecode at the same time. This chapter explains what the lock protects, how it is handed over, when threads help anyway, and how the free-threaded build in 3.13 and 3.14 removes it.

7.1What the GIL is, and what it protects

The global interpreter lock is a mutex inside each interpreter that a thread must hold to touch Python objects. It exists because CPython's internals were written assuming a single thread at a time: reference counts are plain integers updated without atomic instructions, and dicts, lists and the allocator have no locks of their own. One lock around everything made the interpreter simple and fast for single-threaded code and, just as important, made C extensions easy to write, since extension code holding the GIL can assume no Python object changes under it.

The GIL protects the interpreter's integrity, not your program's logic. Each bytecode instruction runs atomically, but a statement like counter += 1 is four instructions (load, load, add, store), and the GIL can pass to another thread between any two of them. Two threads incrementing a shared counter can lose updates even with the GIL; the fix is the same as in any language, a threading.Lock or a design without shared mutable state. Operations implemented as a single C call, such as list.append or dict[key] = value, happen to be atomic under the GIL, and a lot of existing code quietly relies on that.

7.2How the GIL is handed over

The current GIL design dates from Python 3.2. A thread that wants the GIL waits on a condition variable with a timeout equal to the switch interval, 5 ms by default (sys.getswitchinterval()). If the timeout expires and the holder has not released the lock in the meantime, the waiter sets a drop request flag in the eval breaker. The holder checks the eval breaker at backward jumps and function entries (Figure 4.1, step 6), sees the request, releases the GIL, signals the waiter, and then waits until the other thread has actually taken it, so that it cannot immediately grab it back.

Crucially, a thread also releases the GIL voluntarily whenever it is about to block: every blocking system call in the standard library (socket reads, file I/O, time.sleep, waiting on a lock or a subprocess) is wrapped in "release GIL, call, reacquire GIL". Well-written C extensions do the same around long computations: NumPy releases it inside most array operations, hashlib for large inputs, zlib and image libraries during compression, and our pybind11 binding in Chapter 11 with gil_scoped_release. So the GIL serialises Python bytecode, not waiting and not compiled computation. The simulator below makes the consequences visible.

The simulation reproduces what the real measurements in Section 7.3 show. With pure-Python work under the GIL, throughput stays at 1.0× one thread however many threads you add. With I/O-bound requests that spend 1 ms in Python and 6 ms waiting, eight threads achieve about 6.9× (the GIL becomes the limit only when the Python parts add up to a full core). With C code that releases the GIL, four threads reach 4× on four cores. In the free-threaded build, pure Python scales to the number of cores too.

Arguments and results are pickled and sent through a pipe, so passing a 1 GB DataFrame to a worker costs a serialisation and a copy each way. Each worker is a full interpreter with its own imported modules and memory. And workers must be started: Linux used to fork the parent, which is fast but copies the state of every thread's locks at that instant and can deadlock a child if another thread held a lock; Python 3.14 switched the Linux default to forkserver, which forks children from a clean single-threaded server process (macOS and Windows use spawn, which starts a fresh interpreter and re-imports your main module, hence the mandatory if __name__ == "__main__": guard). multiprocessing.shared_memory and memory-mapped NumPy arrays avoid copying large inputs.

In practice

Data-processing libraries mostly make this decision for you: Polars, DuckDB and PyArrow run their kernels on all cores in native threads, NumPy's linear algebra calls a multithreaded BLAS, and PyTorch has its own thread pools. Reach for processes when the hot loop is genuinely Python, threads (or asyncio) when the program waits on networks and disks, and check whether your library is already parallel before adding either.

7.4Free-threaded Python: how CPython removed the GIL

PEP 703 describes a CPython build without the GIL. It shipped as an experimental option in 3.13 and became officially supported, though still not the default, in 3.14 (PEP 779). The free-threaded interpreter is a separate binary, conventionally python3.14t, and extensions must be compiled for it (wheel tag cp314t). Removing the lock meant solving every problem the lock had solved, without making single-threaded code much slower:

Biased reference counting. Most objects are only ever touched by the thread that created them. Each object therefore has two counts: a local one that the owning thread updates with ordinary, non-atomic instructions, and a shared one that other threads update atomically. The true count is their sum. Deferred and immortal reference counts handle objects that all threads hammer, such as functions, modules, code objects and type objects, so that they do not become cache-line ping-pong between cores. Per-object locks ("critical sections") protect the internal state of lists, dicts and sets, so that list.append from two threads stays safe; a scheme called quiescent-state-based reclamation lets readers access a dict or list without taking its lock while making sure that storage being replaced is freed only when no thread can still be reading it. mimalloc replaces pymalloc as a thread-safe allocator. And the specialising interpreter was made thread-safe, which is why 3.13t ran single-threaded code much slower and 3.14t only modestly slower (a single-thread overhead in the range of 5–10 % is the commonly reported figure for 3.14t; in this chapter's small benchmark the difference was within noise).

Pitfall

Free-threading removes the accidental serialisation that hid race conditions. Code that was "safe because of the GIL" (check-then-act on a shared dict, lazily initialised globals, non-thread-safe C libraries) can now fail. When a free-threaded interpreter imports an extension that has not declared itself safe (via the Py_mod_gil slot), it re-enables the GIL for the whole process and prints a warning, so a single old dependency silently brings back serial execution. Check sys._is_gil_enabled() in your service's start-up log.

There is a third model between threads and processes: subinterpreters. Since 3.12 each subinterpreter can have its own GIL (PEP 684), and 3.14 exposes them in the standard library as concurrent.interpreters and the InterpreterPoolExecutor in concurrent.futures (PEP 734). Interpreters in one process run Python in parallel but share no objects; they communicate by passing data through queues, much like processes but with lower start-up and memory cost.

8asyncio: one thread, thousands of connections

A web service that keeps ten thousand mostly idle connections open cannot afford ten thousand threads of a few megabytes of stack each, plus the scheduler cost of switching between them. asyncio runs all of them on one thread: each connection's logic is a coroutine that gives the thread back whenever it would wait. The concurrency chapter explains event loops and coroutines in general; this chapter is about how Python implements them and how Python services go wrong with them.

8.1The event loop

An asyncio event loop is a plain Python object running a plain loop on one thread. Each iteration runs every callback in its ready queue, computes how long it may sleep (zero if more callbacks are ready, otherwise until the earliest timer in a heap), calls the operating system's readiness API through the selectors module (epoll on Linux, kqueue on macOS; the Linux chapter shows why epoll scales), and then schedules the callbacks of sockets that became readable or writable and of timers that expired. The one-sentence contract is that while a callback runs, nothing else in that loop runs.

8.2Coroutines, tasks and what await really does

Calling an async def function does not run it; it returns a coroutine object, a suspended frame built on the same machinery as a generator (Section 5.3). A coroutine makes progress only when something drives it with send(). That driver is a Task: asyncio.create_task(coro) wraps the coroutine and schedules a step in the ready queue. A step calls coro.send(None); the coroutine runs until it awaits something that is not ready yet. At the bottom of every chain of awaits there is a Future, an object that will hold a result later (for example "data arrived on this socket"). The task registers itself as a done-callback on that future and returns control to the loop. When the selector reports the socket readable, the loop resolves the future, which puts the task's next step into the ready queue, and the coroutine resumes after its await with the result.

So await means "suspend this coroutine until that awaitable has a result, and let the loop run other things meanwhile". Awaiting a coroutine that never actually waits does not yield to the loop at all; it is just a function call costing about 58 ns on 3.14. One full trip through the loop (await asyncio.sleep(0)) measured 1.6 µs. That is what makes asyncio efficient for I/O: switching between ten thousand connections costs microseconds, not the tens of microseconds of a thread context switch plus the memory of ten thousand stacks. Measured: 1,000 concurrent requests that each await 0.2 s complete in 0.21 s on one thread.

import asyncio, httpx

async def fetch_price(client: httpx.AsyncClient, sku: str) -> float:
    r = await client.get(f"https://prices.example.com/{sku}", timeout=2.0)
    r.raise_for_status()
    return r.json()["price"]

async def total(skus: list[str]) -> float:
    async with httpx.AsyncClient() as client:
        async with asyncio.TaskGroup() as tg:            # 3.11+: structured concurrency
            tasks = [tg.create_task(fetch_price(client, s)) for s in skus]
        return sum(t.result() for t in tasks)            # all done (or all cancelled) here

asyncio.run(total(["ABC-1234", "XYZ-0001"]))

8.3Structured concurrency, cancellation and timeouts

Early asyncio code started tasks with create_task and hoped someone would await them; errors in forgotten tasks vanished into a log message, and an exception in one of several gathered tasks left the others running. Python 3.11 added TaskGroup: tasks created in an async with TaskGroup() block cannot outlive the block, and if one fails, the others are cancelled and all errors are raised together as an ExceptionGroup (handled with except*). This is the same structured-concurrency idea as Trio's nurseries and Kotlin's coroutine scopes, and it should be the default for new code.

Cancellation is cooperative: task.cancel() makes the coroutine's current await raise CancelledError, which unwinds its finally blocks and async with exits. A coroutine that catches CancelledError and does not re-raise it breaks timeouts and shutdown for everything above it. Timeouts are built on cancellation: async with asyncio.timeout(2.0): (3.11) cancels the block after two seconds and converts the cancellation into TimeoutError at the boundary. Every network call in a service should sit inside some timeout; a missing one is how a slow dependency turns into exhausted connection pools.

Pitfall

The event loop keeps only weak references to tasks. A fire-and-forget asyncio.create_task(send_email()) whose result you do not store can be garbage-collected in the middle of its execution. Keep a reference (a set of background tasks, discarding each one in a done-callback), use a TaskGroup, or hand the work to a real job queue.

8.4The blocking-call problem

The contract that nothing else runs while a callback runs has a harsh consequence: one synchronous call that takes 200 ms freezes every connection on that loop for 200 ms. The usual culprits are innocent-looking: the requests library instead of httpx or aiohttp, a synchronous database driver, time.sleep instead of asyncio.sleep, reading a large file, or a CPU-heavy function such as parsing a big JSON document or resizing an image. Measured: five coroutines that each call time.sleep(0.2) take 1.00 s together, exactly as if there were no concurrency; the same five using asyncio.to_thread(time.sleep, 0.2) take 0.20 s.

The remedies, in order of preference: use async libraries for I/O (httpx, asyncpg, aiofiles, the async interfaces of SQLAlchemy and Redis clients); push unavoidable blocking calls to a thread with asyncio.to_thread or loop.run_in_executor; push CPU-heavy work to a process pool or a job queue. To find offenders, run with PYTHONASYNCIODEBUG=1 (or asyncio.run(main(), debug=True)), which logs every callback that holds the loop longer than 100 ms. Since 3.14, python -m asyncio ps PID and pstree PID show the tasks of a running process and what each is awaiting.

Interesting detail

Async is "contagious" (the function-colouring problem): only an async def can await, so making one deep function asynchronous forces every caller up the chain to become asynchronous too. That is why mature libraries ship both a sync and an async API, and why FastAPI accepts both def and async def endpoints, running the former in a thread pool (Section 13.2). uvloop, a drop-in event loop built on libuv, makes the loop's own overhead two to four times smaller and is the default in many production servers.

Talk track

"asyncio runs many coroutines on one thread. A coroutine is a suspendable frame; a Task drives it, and when it awaits something not ready, the task parks on a future and the loop runs other tasks until epoll says the data is there. It's great for many concurrent I/O waits and useless for CPU work, and a single blocking call freezes every request on the loop, so we use async drivers, to_thread for the leftovers and TaskGroup plus timeouts for structure."

9Type hints, data classes and protocols

Type hints arrived in Python 3.5 and are now standard in every serious codebase. They do not make Python statically typed: the interpreter ignores them when running code. Their value comes from tools that read them, type checkers before the code runs and libraries such as Pydantic and FastAPI while it runs.

9.1Gradual typing: what annotations are and are not

An annotation such as def total(rows: list[Order]) -> float is metadata stored on the function. CPython does not check it; total("oops") runs and fails (or worse, does not fail) somewhere inside. A type checker such as mypy or pyright reads the source, infers types and reports mismatches before the code runs, the way a C++ compiler would. Typing is gradual: unannotated code is treated as Any, compatible with everything, so a codebase can be annotated module by module. In 3.14 annotations are evaluated lazily (PEP 649/749): the expressions are stored as code and only evaluated when something asks for them through annotationlib or __annotations__, which removed the need for quoted forward references and for from __future__ import annotations in most code.

The vocabulary worth knowing: built-in generics (list[int], dict[str, float]), unions with | (int | None), Literal["csv", "parquet"], TypedDict for dicts with fixed keys (JSON payloads), Callable, Iterator, @overload for functions whose return type depends on argument types, Self, @override (3.12), TypeIs (3.13) for user-defined narrowing, and the 3.12 syntax for generics: def first[T](xs: Sequence[T]) -> T and type Matrix = list[list[float]]. In configuration, the important switch is strictness: mypy's --strict or pyright's "strict" mode forbids implicit Any and catches far more, and new code should start strict because retrofitting it is expensive.

9.2Protocols: structural interfaces for duck typing

Python has two ways to express an interface. An abstract base class (abc.ABC with @abstractmethod) is nominal: a class satisfies it only by inheriting from it, as in C++ or Java. A Protocol (PEP 544, 3.8) is structural: any class that has the right methods satisfies it, without knowing the protocol exists. Protocols are how you type duck typing, and they are usually the better choice for parameters, because callers can pass objects from libraries that you do not control. The C++ analogue is a concept rather than a base class.

from typing import Protocol

class Storage(Protocol):
    def put(self, key: str, data: bytes) -> None: ...
    def get(self, key: str) -> bytes: ...

class S3Storage:                       # no inheritance from Storage
    def put(self, key: str, data: bytes) -> None: ...
    def get(self, key: str) -> bytes: ...

class InMemoryStorage:                 # a test double that also fits
    def __init__(self) -> None: self.d: dict[str, bytes] = {}
    def put(self, key: str, data: bytes) -> None: self.d[key] = data
    def get(self, key: str) -> bytes: return self.d[key]

def archive(store: Storage, report: bytes) -> None:   # accepts both, checked statically
    store.put("reports/latest", report)

9.3Data classes, attrs and Pydantic: three kinds of record

Most programs need small record types. @dataclass (3.7) generates __init__, __repr__ and __eq__ from annotated fields and, with options, ordering, hashing, immutability (frozen=True), keyword-only fields and __slots__ (slots=True). It does no validation: Order(quantity="many") is accepted. attrs is the older, richer library the standard dataclass was modelled on, with validators and converters. Pydantic is different in kind: it parses and validates data at run time from annotations, converting "7" to 7 where allowed, rejecting values that do not fit, and serialising to and from JSON. Its core, pydantic-core, is written in Rust, which is why Pydantic v2 is many times faster than v1.

10NumPy and the data stack: memory layout, views and vectorisation

Every serious numerical, data or ML library in Python is built on one idea: keep the numbers in a contiguous block of machine values and describe how to walk it, so that loops can run in compiled code. Knowing NumPy's model of buffer, dtype, shape and strides explains why vectorised code is fast, when a slice shares memory and when it copies, and what Polars and pandas do differently.

10.1Why a list of numbers is the wrong data structure

Chapter 2 showed that a Python list holds pointers to boxed objects. For a million floats that means 8.4 MB of pointers plus a million 24-byte float objects scattered over the heap: 32.4 MB measured, for 8 MB of actual data. A NumPy float64 array of the same million values is one 8,000,000-byte buffer plus a small header. Beyond memory, the layout decides speed: a loop over the array reads consecutive addresses that the CPU prefetches and can process with SIMD instructions, while a loop over the list chases a pointer, checks a type and touches a reference count per element.

10.2An ndarray is a buffer plus a description of how to walk it

An ndarray object has a pointer to a data buffer, a dtype (the element type: int32, float64, a structured record), a shape (the size of each axis) and strides: for each axis, how many bytes to move in the buffer to get to the next element along that axis. Element [i, j] of a 2-D array lives at byte offset + i·strides[0] + j·strides[1]. For a = np.arange(12, dtype=np.int32).reshape(3, 4) the strides are (16, 4): four bytes to the next column, sixteen bytes (one row of four int32 values) to the next row. That is C order (row-major), NumPy's default. Fortran order (column-major, order="F") has the strides the other way round and is what LAPACK, MATLAB and Eigen use by default.

Because the description is separate from the data, many operations only write a new header. Transposing swaps the strides; slicing with a step multiplies one; selecting a row adds an offset; reversing uses a negative stride; broadcasting uses a stride of zero, so that one row is read again for every row of the result. Pick an expression below and watch which bytes of the original buffer it uses.

10.3Views versus copies

The rule follows from the model. Basic indexing (integers, slices, ..., np.newaxis) always returns a view: a new array object sharing the original buffer, whose strides and offset express the selection. Advanced indexing (an integer array or list like a[[0, 2]], or a boolean mask like a[a > 5]) selects an arbitrary set of elements that no single set of strides can describe, so it always returns a copy. reshape returns a view when the new shape can be expressed with strides over the existing layout and copies otherwise (a.T.reshape(12) must copy, because the transposed order is not a constant step through memory). np.shares_memory(x, y) tells you which case you are in; .copy() makes the decision explicit.

a = np.arange(12, dtype=np.int32).reshape(3, 4)
col = a[:, 1]            # a view: shape (3,), strides (16,), offset 4
col[:] = -1              # writes into a's buffer
a[0]                     # -> [ 0, -1,  2,  3]
big = a[a > 5]           # a copy: modifying big never changes a
a[a > 5] = 0             # but assignment through a mask writes into a (it is __setitem__, not a copy)

Views make NumPy fast and memory-efficient, and they are also its classic trap. A function that receives a slice and modifies it in place changes the caller's array; a small view keeps a huge buffer alive (a 10-element slice of a 1 GB array pins the whole gigabyte); and a non-contiguous view handed to C code may be copied silently (Section 11.2). pandas used to add its own layer of confusion with the "SettingWithCopy" warning; pandas 3.0 made Copy-on-Write the only behaviour, so any derived DataFrame or Series behaves as a copy, and data is actually copied only when one of them is modified.

10.4Vectorisation and memory traffic

Vectorisation means expressing a computation as whole-array operations so that the loop runs inside NumPy's compiled code. Computing 2x + 1 over a million floats measured 54 ms as a Python loop over a list and 2.06 ms as x * 2.0 + 1.0 on an array, a factor of 26. A Python loop over the NumPy array itself was the slowest variant at 126 ms, because every element access creates a new NumPy scalar object: mixing the two worlds element by element gets the worst of both. Broadcasting extends vectorisation to arrays of different shapes by aligning shapes from the right and stretching axes of size 1 (with stride 0), so image - mean_per_channel works without a loop or a copy of the mean.

Once code is vectorised, the bottleneck usually becomes memory traffic. x * 2.0 + 1.0 creates a temporary array for x * 2.0, then another for the result: three passes over memory where one would do. In-place operations (x *= 2; x += 1), the out= argument, numexpr or a Numba-compiled loop avoid the temporaries. Layout matters too, as the C++ chapter on cache lines explains: on a 4000×4000 float64 array (128 MB), copying it took 25 ms but copying its transpose into a new contiguous array took 48 ms, and summing each of the 4,000 rows separately took 17 ms against 30 ms for the 4,000 strided columns.

Numbers

Measured on NumPy 2.5.4 / CPython 3.14: list of 10⁶ floats 32.4 MB vs array 8.0 MB; 2x+1 over 10⁶ elements: Python list loop 54 ms, NumPy 2.06 ms, Python loop over the NumPy array 126 ms; 4000×4000 copy 25 ms, transpose copy 48 ms; row sums 17 ms vs column sums 30 ms.

10.5The data-processing pipeline: pandas and Polars

The sales pipeline filters two million synthetic orders to those with quantity ≥ 3 and sums revenue per city. Written three ways, with the same result:

def py_agg(rows):                                   # rows: list of (city, qty, price) tuples
    tot = {}
    for city, q, p in rows:
        if q >= 3:
            tot[city] = tot.get(city, 0.0) + q * p
    return tot

def pd_agg(df):                                     # pandas 3.1
    d = df[df.qty >= 3]
    return (d.qty * d.price).groupby(d.city).sum()

def pl_agg(df):                                     # Polars 2.1, lazy API
    return (df.lazy()
              .filter(pl.col("qty") >= 3)
              .group_by("city")
              .agg((pl.col("qty") * pl.col("price")).sum().alias("rev"))
              .collect())

Measured: pure Python 122 ms, pandas 72 ms, Polars 7 ms. pandas is built on NumPy arrays, one per column, with a rich and sometimes inconsistent API that grew over fifteen years; its operations are vectorised but mostly single-threaded and eager, so each step materialises a full intermediate result. Polars is written in Rust on the Apache Arrow columnar format, runs its kernels on all cores, and in the lazy API builds a query plan that an optimiser rewrites before running it: the plan Polars printed for this pipeline reads only the needed columns (projection pushdown) and applies the filter before the aggregation (predicate pushdown), the same optimisations a database performs. The memory picture differs too: 61 MB in pandas against 45 MB in Polars for the same table.

The industry trend is towards Arrow as the shared in-memory format: Polars, DuckDB, PyArrow, Spark and pandas (optionally, and by default for strings since pandas 3.0) can exchange columns without copying. For a new pipeline, Polars or DuckDB (SQL over the same Arrow data) is the performant default, and pandas remains the lingua franca for exploration, plotting and the huge existing codebase.

Talk track

"A NumPy array is a contiguous buffer plus dtype, shape and strides. Slicing changes only the strides and offset, so it returns a view that shares memory; fancy and boolean indexing copy. Vectorised code is fast because the loop runs in C over unboxed values, and after that, memory traffic and layout are what matter. For tabular pipelines, Polars' lazy, multithreaded, Arrow-based engine was ten times faster than pandas on our aggregation."

11Bridging to C and C++: pybind11, nanobind, Cython and the C API

Python's success depends on calling compiled code cheaply. Sometimes you bind an existing C++ library so that Python users can script it; sometimes you move one hot loop out of Python. Either way the questions are the same: how arguments cross the boundary, who owns the memory, when the GIL is held, and how the result is built and shipped as a wheel.

11.1The options, from lowest level to highest

The CPython C API is the foundation: an extension module is a shared library that exports PyInit_<name> and manipulates PyObject* directly. You must get reference ownership right by hand (a "new reference" returned by a function must be released with Py_DECREF; a "borrowed reference" must not), translate errors into exceptions, and hold the GIL whenever you touch objects. Few people write it directly today, but every tool below generates it. ctypes (standard library) and cffi call functions in an existing C shared library without compiling anything, at a higher cost per call. Cython compiles a Python superset (or annotated pure Python) to C; it is ideal for speeding up a Python loop gradually and for wrapping C libraries, and it powers parts of pandas, scikit-learn and lxml. pybind11 is a header-only C++ library that uses templates to generate bindings from C++ signatures: classes, overloads, STL containers, exceptions and NumPy arrays map naturally. nanobind, by pybind11's author, keeps the same style with much smaller binaries, faster compilation and lower call overhead, and supports the stable ABI. For Rust, PyO3 fills the same role and underlies Polars, pydantic-core and many new libraries.

11.2The running example: a C++ blur bound with pybind11

imglib is a tiny "C++ image library": a 3×3 box blur on 8-bit greyscale images, written as plain C++ that knows nothing about Python. The binding takes a NumPy array through the buffer protocol, which gives C++ a raw pointer, shape and strides without copying; requests C-contiguous uint8 data; releases the GIL for the duration of the C++ call; and returns a new NumPy array that Python owns.

#include <pybind11/pybind11.h>
#include <pybind11/numpy.h>
namespace py = pybind11;

void box_blur_fast(const uint8_t* src, uint8_t* dst, int h, int w, long stride);  // plain C++

py::array_t<uint8_t> blur(py::array_t<uint8_t, py::array::c_style | py::array::forcecast> img) {
    auto in = img.unchecked<2>();                     // checks ndim == 2
    int h = int(in.shape(0)), w = int(in.shape(1));
    py::array_t<uint8_t> out({h, w});                 // owned by Python when returned
    const uint8_t* src = img.data();
    uint8_t* dst = out.mutable_data();
    {
        py::gil_scoped_release nogil;                  // other Python threads may run now
        box_blur_fast(src, dst, h, w, w);              // must not touch any Python object here
    }
    return out;
}

PYBIND11_MODULE(imglib, m) {
    m.def("blur", &blur, py::arg("img"), "3x3 box blur of a 2-D uint8 array");
}

Measured on a 1080p image: the first, naive C++ version (a bounds check for every one of the nine neighbours of every pixel) took 18.5 ms, slower than a vectorised NumPy version built from nine shifted slices (4.8 ms). A tuned version that sums three rows into a column buffer and handles the borders separately, so that the compiler can vectorise the interior loop, took 2.3 ms. Pure Python would need about 2 s. The lesson is the one Figure 1.2 hinted at: crossing into C++ removes interpreter overhead, but it does not write a fast kernel for you, and NumPy's kernels are already good compiled code. Bind C++ when you have a real algorithm or an existing library, not to replace one NumPy expression.

The fixed cost of a call measured about 0.6 µs. That is negligible against 2.3 ms of work but adds up quickly for a function called once per pixel or per row from Python, so good binding APIs are coarse-grained: pass whole images, batches or arrays, never single values in a loop. When the input is not C-contiguous uint8 (a strided slice like img[:, ::2], or a float image), forcecast makes the binding accept it by copying into a temporary, which is correct but hides an O(n) cost; dropping forcecast makes such calls fail loudly instead.

Pitfall

Lifetime bugs are the dangerous ones. A C++ object that keeps a raw pointer into a NumPy buffer after the call returns will crash when Python frees that array; returning a reference to a C++ member without the right return_value_policy or py::keep_alive lets Python outlive the owner. Touching any Python object (even logging through Python) inside a gil_scoped_release block is undefined behaviour. And C++ exceptions must not escape across the boundary unconverted; pybind11 translates the standard ones to Python exceptions automatically.

11.3Building and shipping extensions

An extension is only useful if users can pip install it without a compiler. The modern build uses scikit-build-core (CMake under a PEP 517 backend; see Build systems 5.5 for CMake itself) or meson-python, declared in pyproject.toml. CI then builds one binary wheel per platform and Python version, typically with cibuildwheel, and uploads them to PyPI. Linux wheels must follow the manylinux policy: built against an old glibc in a reference container (for example manylinux_2_28), so that they run on any distribution with that glibc or newer; auditwheel verifies the policy and vendors needed shared libraries into the wheel.

The number of wheels grows with every Python version, which is why the stable ABI matters: an extension restricted to the "limited API" can be built once as an abi3 wheel (e.g. cp312-abi3) that loads on every later CPython version. nanobind and PyO3 support it and Cython can target it; pybind11 has historically not supported it, so check the current release if this matters. Free-threaded Python adds another axis: cp314t wheels, which must be compiled separately and should declare that they are thread-safe. The C++ chapter's ABI section explains why binary compatibility is such a delicate contract.

Talk track

"To use C++ from Python we bind it with pybind11 or nanobind: NumPy arrays come in through the buffer protocol without copying, we release the GIL around the C++ work, and we keep the API coarse-grained because each call costs around half a microsecond. We build with scikit-build-core and ship manylinux wheels from cibuildwheel. And we measure, because a naive C++ loop can lose to NumPy."

12Packaging, environments and dependency management

"It works on my machine" is the oldest Python complaint, and it comes from a simple fact: an import finds whatever happens to be installed on the interpreter's path. Modern Python packaging is a set of standards and tools that make that set of installed packages declared, isolated and reproducible.

12.1Virtual environments: what they actually isolate

A virtual environment is a directory with its own site-packages folder and a pyvenv.cfg file. Its bin/python is just a symlink to the base interpreter; at start-up, CPython notices pyvenv.cfg next to its executable and puts the environment's site-packages on sys.path instead of the system one. "Activating" the environment only prepends its bin directory to PATH. So a venv isolates installed Python packages and nothing else: not the interpreter version, not system libraries, not environment variables. Creating one with uv and installing a package from a warm cache took 0.10 s for this chapter, and the result was a 7.9 MB directory.

Never install packages into the operating system's Python: distribution tools depend on it, and since PEP 668 Debian, Ubuntu and Homebrew mark it as "externally managed", so pip refuses with an error unless forced. One environment per project, created from a lock file and recreated freely, is the norm. When packages need non-Python dependencies that wheels do not cover (specific CUDA, MKL or GDAL builds), conda or its faster successor pixi manage those binary dependencies alongside Python; for containers, the base image plays that role (Build systems 9.7).

12.2pyproject.toml, build backends and wheels

A Python project is described by pyproject.toml. The [project] table (PEP 621) holds the name, version, supported Python versions, dependencies and entry points; the [build-system] table (PEP 517/518) names the build backend, the library that turns the source tree into installable artifacts: hatchling, setuptools, poetry-core, flit-core, uv_build, or scikit-build-core and meson-python for compiled extensions. Tools such as pip and uv are frontends: they create an isolated build environment, install the backend into it and ask it to build. This split is why the old setup.py install is gone and any frontend can build any project.

Two artifacts come out. An sdist (.tar.gz) is the source plus metadata and needs a build step on the installing machine. A wheel (.whl) is a zip file laid out ready to be unpacked into site-packages: installing it runs no project code. Its file name carries compatibility tags: csvstat-0.1.0-py3-none-any.whl is pure Python for any Python 3 on any platform, while numpy-2.5.4-cp314-cp314-manylinux_2_28_x86_64.whl is compiled for CPython 3.14's ABI on x86-64 Linux with glibc 2.28 or newer. When no wheel matches, pip falls back to building the sdist, which is how a pip install on an unusual platform suddenly needs a C++ compiler.

The running example, csvstat, is a command-line tool created with uv init --package. Its whole pyproject.toml:

[project]
name = "csvstat"
version = "0.1.0"
requires-python = ">=3.14"
dependencies = ["typer>=0.12"]

[project.scripts]
csvstat = "csvstat:app"            # creates a csvstat executable in the environment's bin/

[build-system]
requires = ["uv_build>=0.11.32,<0.12.0"]
build-backend = "uv_build"
uv add 'typer>=0.12'       # edits pyproject.toml, resolves, writes uv.lock, syncs .venv
uv run csvstat d.csv x     # -> n=3 mean=4.33 median=2.00
uv build                   # -> dist/csvstat-0.1.0.tar.gz, dist/csvstat-0.1.0-py3-none-any.whl
uv tool install .          # install it as an isolated command for the user (like pipx)

12.3Dependency resolution and lock files

Dependencies in pyproject.toml are ranges (typer>=0.12) because a library must coexist with other libraries' requirements. An application, by contrast, needs exact, reproducible versions of everything, including dependencies of dependencies. A resolver searches for one version of each package that satisfies every constraint (an NP-hard problem in general, solved in practice by backtracking with good heuristics), and a lock file records the result with hashes of every artifact. csvstat's uv.lock pins nine packages for one direct dependency. The build systems chapter covers the same lock-file logic for C++ with Conan.

The tools differ mainly in how much of this workflow they own. pip installs and resolves but has no project lock file of its own; teams combined it with pip-tools (pip-compile writes a pinned requirements.txt). Poetry was the first popular all-in-one project manager with its own lock file. uv, written in Rust by Astral, replaced most of these in 2024–2026 by doing all of it, much faster: it resolves and installs packages from a global cache using hard links or copy-on-write clones instead of re-extracting files, manages Python versions themselves (uv python install 3.14t fetched the free-threaded interpreter used in Chapter 7 in under three seconds), runs single-file scripts with inline dependencies, and installs tools. PEP 751 (2025) standardised a tool-neutral lock file, pylock.toml, which pip and uv can export and install.

In practice

A typical 2026 service repository: pyproject.toml with dependency ranges and dev dependency groups (pytest, ruff, mypy), a committed uv.lock, CI that runs uv sync --locked (fail if the lock is out of date) and then the checks, and a Dockerfile that copies pyproject.toml and uv.lock first, runs uv sync --frozen --no-dev in one cached layer and copies the source afterwards, so that code changes do not reinstall dependencies. Dependabot or Renovate opens pull requests to bump the lock, and the SBOM and vulnerability scanning described in Build systems 11.5 read the same lock.

Pitfall

Upper bounds on library dependencies (requests<3) look prudent but cause unsolvable conflicts for everyone downstream when two libraries cap the same package differently. The accepted practice is to put exact pins only in applications' lock files and to keep libraries' ranges as open as testing allows.

13Python in backend services: WSGI, ASGI, FastAPI and Django

A large share of production Python is web backends: APIs for mobile and web apps, internal services, ML model serving. They are built on a standard interface between the server that speaks HTTP and the application that handles requests, and the choice between the synchronous and asynchronous versions of that interface shapes everything from performance to which database driver you can use.

13.1WSGI and ASGI: the contract between server and application

WSGI (PEP 3333, 2003) defines an application as a callable app(environ, start_response) that receives a dict describing one HTTP request and returns an iterable of body bytes. A WSGI server such as Gunicorn or uWSGI handles sockets and HTTP parsing and calls the application once per request, in a worker process or thread that is blocked until the response is complete. Flask and classic Django are WSGI applications. The model is simple and robust, but one request occupies one worker for its whole duration, including every database round trip, and it cannot express WebSockets or long-lived streaming.

ASGI is the asynchronous successor: an application is async def app(scope, receive, send), a coroutine that receives events (request body chunks, WebSocket messages) and sends events (response start, body chunks). Because the application is a coroutine, one worker process with one event loop can serve thousands of concurrent requests, as long as they spend their time awaiting I/O. Uvicorn, Hypercorn and Granian are ASGI servers; Starlette, FastAPI, Litestar and modern Django are ASGI applications.

In production a reverse proxy or load balancer terminates TLS and buffers slow clients, and the ASGI server runs several worker processes, commonly one per core, either with uvicorn --workers N or with Gunicorn managing Uvicorn workers. In Kubernetes the usual pattern is fewer workers per pod and more pods, letting the orchestrator handle restarts and scaling. Each worker is a separate interpreter with its own GIL, so a CPU-heavy endpoint only blocks the worker it runs in, but it does block every other request on that worker's loop (Section 8.4).

13.2The running example: the order service in FastAPI

FastAPI builds on Starlette (routing, the ASGI plumbing) and Pydantic (data validation). Its central idea is that the endpoint's signature is the specification: path and query parameters, the request body model and the return type are all read from type hints, used to parse and validate requests, to serialise responses, and to generate an OpenAPI schema and interactive documentation at /docs. The whole service:

from typing import Annotated
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel, Field

app = FastAPI(title="orders")

class OrderIn(BaseModel):
    sku: Annotated[str, Field(pattern=r"^[A-Z]{3}-\d{4}$")]
    quantity: Annotated[int, Field(gt=0, le=100)]
    note: str | None = None

class OrderOut(OrderIn):
    id: int

DB: dict[int, OrderOut] = {}                  # stands in for a database

@app.post("/orders", status_code=201)
async def create_order(order: OrderIn) -> OrderOut:   # body parsed and validated before we run
    out = OrderOut(id=len(DB) + 1, **order.model_dump())
    DB[out.id] = out
    return out

@app.get("/orders/{order_id}")
async def get_order(order_id: int) -> OrderOut:      # path parameter converted to int
    if order_id not in DB:
        raise HTTPException(status_code=404, detail="order not found")
    return DB[order_id]

What happens when a request arrives: Uvicorn parses the HTTP bytes and calls the app with an ASGI scope; Starlette's router matches POST /orders; FastAPI reads the JSON body and validates it against OrderIn (a malformed body never reaches your code, the client gets a 422 response listing every error); it calls create_order; it validates the return value against OrderOut and serialises it to JSON. Dependency injection with Depends() supplies database sessions, the authenticated user or settings to endpoints, and lets tests replace them (app.dependency_overrides).

The async def versus def choice matters. An async def endpoint runs on the event loop and must only await non-blocking I/O. A plain def endpoint is run in a thread pool (40 threads by default, through AnyIO) so that blocking code does not freeze the loop. Writing async def and then calling a synchronous database driver inside is the most common FastAPI performance bug: it is exactly the blocking-call problem of Figure 8.2.

13.3Pydantic: validation as parsing

Pydantic treats validation as parsing into a typed object. In the default lax mode it coerces where the intent is unambiguous: OrderIn.model_validate({"sku": "ABC-1234", "quantity": "7"}) returns a model with quantity=7. Invalid data raises one ValidationError that lists every problem with its location and a machine-readable type, which FastAPI forwards to the client. The real output for {"sku": "abc", "quantity": 0}:

('sku',) string_pattern_mismatch - String should match pattern '^[A-Z]{3}-\d{4}$'
('quantity',) greater_than - Input should be greater than 0

Pydantic v2 compiles each model into a validator tree in pydantic-core (Rust) when the class is created, by the metaclass mechanism of Section 6.5. That is why validation is fast and why defining thousands of models costs start-up time. Strict mode (model_config = ConfigDict(strict=True), or per field) disables coercion where it would hide client bugs; pydantic-settings applies the same validation to environment variables and configuration files, which turns a misconfigured deployment into a clear error at start-up instead of a crash at the first request.

13.4Django, Flask and choosing a framework

Django is the "batteries included" framework: an ORM with migrations, an admin interface generated from the models, authentication, forms, templates, sessions and a strong security baseline (CSRF protection, escaping, safe password hashing) out of the box. It has supported ASGI since 3.0, async views since 3.1 and an async ORM interface since 4.1, though much of its ecosystem is still synchronous. Flask is a minimal WSGI framework to which you add pieces. FastAPI is API-first, typed and async-first, and has become the default for new JSON APIs and ML model serving.

14Profiling, testing and automation

Python's dynamism cuts both ways: it makes code quick to write and quick to break. The engineering practices around it, measuring before optimising, testing with pytest, static checks in CI and disciplined scripting, are what make Python codebases maintainable at scale.

14.1Profiling: find the hot spot before you touch anything

There are two kinds of profiler. A deterministic profiler such as the standard library's cProfile hooks every function call and return, so it counts calls exactly but adds overhead to each one, which inflates the apparent cost of small, frequently called functions. A sampling profiler interrupts the program many times per second and records the stack, which gives a statistically accurate picture with little overhead and can attach to a running production process. py-spy (written in Rust, reads the interpreter's memory from outside the process) and Scalene (which also separates time spent in Python from time in native code and reports memory) are the common choices; Linux perf can see Python function names since 3.12 when the interpreter runs with -X perf, and Python 3.15 adds a sampling profiler to the standard library (PEP 799).

python -m cProfile -s cumulative pipeline.py | head -15      # deterministic, whole run
py-spy record -o profile.svg --pid 4711                       # flame graph of a running service
py-spy dump --pid 4711                                        # where is every thread right now?
python -X importtime -c "import pandas" 2>&1 | sort -t'|' -k2 -n | tail   # slow imports

The cProfile output for the pure-Python aggregation in Section 10.5 showed 233,351 calls to dict.get accounting for 28 ms of the function's 74 ms: a hint that a defaultdict or, better, a vectorised group-by is the fix. Memory has its own tools: tracemalloc in the standard library (Section 3.3), memray for native allocations and flame graphs of memory, and sys.getsizeof only for single objects, since it does not follow references.

Why it matters

Intuition about Python performance is unreliable because the costs are invisible in the source: an innocent-looking attribute access may be a property that queries a database, and an innocent-looking in may scan a list of 100,000 items. Ten minutes with a sampling profiler on a realistic workload routinely beats a day of guessing.

14.2Testing with pytest

pytest is the de facto standard test runner. Tests are plain functions whose names start with test_, and checks are plain assert statements: pytest installs an import hook that rewrites the assert statements in test modules so that a failure reports the values of both sides and the intermediate expressions, without special assertion methods. Fixtures provide setup and teardown by dependency injection: a test names a fixture as a parameter and pytest builds it (and its own fixtures) before the test, with a chosen scope (function, module, session) and cleanup after a yield. Parametrisation runs one test body over many inputs. The order service's tests:

import pytest
from fastapi.testclient import TestClient
from app import app, DB

@pytest.fixture
def client():
    DB.clear()                                   # each test starts from an empty store
    return TestClient(app)                       # calls the ASGI app in-process, no network

def test_create_and_get(client):
    r = client.post("/orders", json={"sku": "ABC-1234", "quantity": 3})
    assert r.status_code == 201
    assert client.get(f"/orders/{r.json()['id']}").json()["quantity"] == 3

@pytest.mark.parametrize("payload", [
    {"sku": "abc-1234", "quantity": 3},          # pattern
    {"sku": "ABC-1234", "quantity": 0},          # gt=0
    {"sku": "ABC-1234", "quantity": "many"},     # not an int
])
def test_rejects_bad_input(client, payload):
    assert client.post("/orders", json=payload).status_code == 422

def test_missing(client):
    assert client.get("/orders/99").status_code == 404

Running pytest -q reported 5 passed in 1.29s: the parametrised test counts as three. Shared fixtures go into conftest.py, which pytest discovers automatically. monkeypatch replaces attributes, environment variables and dictionary entries for one test and restores them afterwards; unittest.mock creates stand-in objects that record how they were called; tmp_path gives each test a fresh directory. Plugins add what the core lacks: pytest-asyncio or AnyIO's plugin for async def tests, pytest-cov for coverage, pytest-xdist to spread tests over cores, and Hypothesis for property-based tests (described in the software quality chapter).

Pitfall

Mocking where a name is defined instead of where it is looked up is the classic unittest.mock error. If orders.py does from payments import charge, the test must patch orders.charge, because orders holds its own reference to the function (Section 2.2: names are bindings). Heavy mocking is also a design signal: if a test needs ten patches, the code under test probably needs a parameter or a Protocol-typed dependency instead.

14.3Static checks and code quality

Because nothing is checked until a line runs, Python teams lean on static tools that run in seconds. ruff (Rust, by the uv authors) replaced flake8, isort, pyupgrade and black-style formatting with one fast tool and hundreds of lint rules, from unused imports to open() without with. A type checker (Section 9.3) catches the wrong-type and maybe-None errors that cause most production exceptions. pre-commit runs these on each commit; CI runs them again, plus the tests on every supported Python version (with nox or tox, or a CI matrix calling uv run --python 3.12 pytest). Security scanners such as bandit and pip-audit look for risky calls and known-vulnerable dependencies.

14.4Scripting and automation done well

Python is the default language for automation: build and release scripts, data migrations, log analysis, test harnesses and glue between tools. A few habits separate scripts that survive from scripts that become a liability. Use pathlib.Path rather than string concatenation for paths. Call other programs with subprocess.run([...], check=True, capture_output=True, text=True, timeout=60), passing arguments as a list and never building a shell string from input (shell=True plus user data is a command-injection hole). Parse arguments with argparse or Typer, log with logging rather than print, exit with a non-zero status on failure, and put the logic in functions behind if __name__ == "__main__": so that tests can import them.

For single-file scripts, PEP 723 inline script metadata removes the need for a project or a manually created environment: dependencies are declared in a comment block, and uv run script.py creates a cached environment with them on first use.

# /// script
# requires-python = ">=3.12"
# dependencies = ["httpx", "rich"]
# ///
import httpx, rich
rich.print(httpx.get("https://api.github.com/rate_limit", timeout=5).json()["rate"])
In automotive

In automotive and embedded teams Python is rarely in the product but everywhere around it: code generators that turn ARXML or DBC files into C sources, test benches that drive CAN and diagnostic traffic (python-can, cantools, udsoncan), HIL test automation, log converters and the data pipelines that select and label recorded drive data. The same practices apply, with one extra rule: tools whose output ends up in a safety-relevant build must be versioned and reproducible like any other build tool, which in practice means pinned environments and lock files from Chapter 12.

QSelf-check questions

Q.1Core questions

What is the difference between a list and a tuple?Basic

A list is mutable and stores its item pointers in a separate, over-allocated array so that appends are amortised O(1); a tuple is immutable, stores its pointers inline, is slightly smaller and faster to create, and is hashable if its items are, so it can be a dict key. Use tuples for fixed records and lists for collections that grow.

What is the difference between is and ==?Basic

is tests identity (same object), == calls __eq__ to compare values. Use is only for singletons such as None. Small-int caching (−5 to 256) and string interning make is on numbers or strings appear to work sometimes, which is exactly why it must not be relied on.

How are arguments passed in Python?Basic

By sharing: the parameter name is bound to the same object the caller passed. Mutating that object is visible to the caller; rebinding the parameter is not. It is neither copy semantics nor C++ reference semantics; think of copying a shared_ptr.

Why is a mutable default argument a bug?Basic

Defaults are evaluated once, when the def statement executes, and stored on the function object. A list default is therefore shared by every call that omits the argument and accumulates state. Use None and create the object inside the function.

How does Python manage memory?Intermediate

CPython uses reference counting, which frees an object as soon as its count reaches zero, plus a generational cycle collector for reference cycles that counting cannot free. Small objects come from the pymalloc allocator (pools in 1 MiB arenas), larger ones from malloc. Memory is returned to the OS only when whole arenas become empty, so RSS can stay high after a spike.

What is the GIL and why does it exist?Intermediate

A per-interpreter mutex that a thread must hold to execute Python bytecode. It exists because reference counts and the built-in containers are not thread-safe, and one lock made the interpreter and C extensions simple and single-threaded code fast. It is released during blocking I/O and by C code that opts to, so threads help with I/O but not with pure-Python computation.

When would you use threads, processes or asyncio?Intermediate

Threads for I/O-bound work with blocking libraries; asyncio for very many concurrent I/O operations with async libraries; processes for CPU-bound pure-Python work (each has its own GIL, at the cost of pickling and memory); and on the free-threaded 3.14t build, threads for CPU-bound work too if all extensions support it. Numeric work belongs in libraries that parallelise internally.

What is a generator, and why use one?Basic

A function containing yield; calling it returns an iterator whose frame suspends at each yield and resumes on next(). Generators produce values lazily, so a pipeline of them processes arbitrarily large inputs in constant memory and can represent infinite sequences.

How does a decorator work? Write one that times a function.Basic

@timed above def f is f = timed(f). A timer: def timed(fn): @functools.wraps(fn) def w(*a, **k): t = time.perf_counter(); try: return fn(*a, **k) finally: log(fn.__name__, time.perf_counter() - t); return w. wraps preserves the name, docstring and signature for tracebacks and frameworks.

What does the with statement do?Basic

It calls __enter__, runs the block, and always calls __exit__ with the exception information (or Nones), which may suppress the exception by returning true. It is the guaranteed-cleanup mechanism for files, locks and transactions, equivalent to RAII in C++.

What is a descriptor? Give examples.Advanced

An object stored on a class that defines __get__ (and maybe __set__/__delete__) and so controls attribute access on instances. Functions (which produce bound methods), property, classmethod, staticmethod, __slots__ members and ORM fields are all descriptors. Data descriptors take priority over the instance dict; non-data descriptors lose to it.

What is a metaclass, and when would you write one?Advanced

The class of a class (default type), which constructs the class object when the class statement runs. Frameworks use them to turn declarations into behaviour (Enum, ABCMeta, Django models, Pydantic). In application code, __init_subclass__ or a class decorator almost always suffices.

What is the MRO and how does super() use it?Intermediate

The method resolution order is the C3 linearisation of a class and its bases (Cls.__mro__). super() returns a proxy that looks up the next class after the current one in the MRO of the instance's actual type, which is what makes cooperative multiple inheritance and mixins work.

Explain async/await.Intermediate

async def creates coroutine functions whose calls return suspended coroutine objects. A Task drives a coroutine on the event loop; when it awaits something not yet ready, the task parks on a future and the loop runs other tasks, resuming it when the selector or a timer resolves the future. It is concurrency on one thread, not parallelism.

What is the difference between a view and a copy in NumPy?Intermediate

A view is a new array header (shape, strides, offset) over the same buffer; basic slicing returns views, so writes are shared. Advanced indexing with integer arrays or boolean masks returns a copy because no strides can describe an arbitrary selection. np.shares_memory tells you which you have.

Why is vectorised NumPy code faster than a Python loop?Basic

The loop runs in compiled C over a contiguous buffer of unboxed values: no bytecode dispatch, no type checks or reference counts per element, cache-friendly access and often SIMD. Measured: 2.06 ms versus 54 ms for 2x+1 over a million elements.

How would you expose a C++ library to Python?Intermediate

With pybind11 or nanobind: bind functions and classes, accept NumPy arrays through the buffer protocol to avoid copies, release the GIL around long C++ work, keep the API coarse-grained, manage lifetimes with return-value policies, build with scikit-build-core and CMake, and ship manylinux and macOS/Windows wheels from cibuildwheel (abi3 wheels with nanobind where possible).

What is a virtual environment, and what does it not isolate?Basic

A directory with its own site-packages and a pyvenv.cfg; the interpreter uses it when started from the venv's bin/python. It isolates installed Python packages only: the interpreter, the standard library, system libraries and environment variables are shared with the base installation.

What is the difference between a wheel and an sdist?Basic

A wheel is a built, ready-to-unpack archive tagged for Python version, ABI and platform; installing it runs no code. An sdist is source plus metadata that must be built on the installing machine, possibly needing a compiler. Pip falls back to the sdist when no wheel matches.

Why do applications need lock files if pyproject.toml lists dependencies?Intermediate

pyproject.toml lists ranges of direct dependencies; a lock file records the exact resolved version and hash of every direct and transitive package, so every developer, CI run and container installs the identical set. Without one, a new release of a transitive dependency can break a deployment that changed nothing.

What is the difference between WSGI and ASGI?Intermediate

WSGI is a synchronous callable per request, so a worker is occupied for the request's whole duration. ASGI makes the application a coroutine receiving and sending events, so one worker's event loop can serve many concurrent requests and handle WebSockets and streaming.

In FastAPI, when do you write def and when async def endpoints?Intermediate

async def when everything inside awaits non-blocking I/O; plain def when the code uses blocking libraries, because FastAPI runs def endpoints in a thread pool. A blocking call inside an async def endpoint freezes the event loop for all requests on that worker.

What does Pydantic do that a dataclass does not?Basic

It validates and parses input at run time from the type hints: coerces compatible values, enforces constraints, collects all errors with locations, serialises to and from JSON and produces JSON Schema. A dataclass only generates boilerplate methods and checks nothing at run time.

How do you profile a slow Python service in production?Intermediate

Attach a sampling profiler such as py-spy to the running process (py-spy record for a flame graph, py-spy dump for current stacks), confirm whether time is in Python, in native code or waiting, and only then optimise. Use cProfile for exact call counts in reproductions and tracemalloc or memray for memory growth.

How do pytest fixtures work?Basic

A fixture is a function decorated with @pytest.fixture; tests request it by naming it as a parameter, and pytest builds it (and the fixtures it depends on) before the test, caching it according to its scope and running code after its yield as teardown. Shared fixtures live in conftest.py.

What changed in the free-threaded build to make it safe without the GIL?Advanced

Biased reference counting (non-atomic counts for the owning thread, atomic shared counts for others), deferred and immortal counts for heavily shared objects, per-object locks for lists, dicts and sets with lock-free reads protected by quiescent-state reclamation, mimalloc as the allocator, and a thread-safe specialising interpreter. Extensions must be rebuilt (cp314t) and declare support, or the GIL is re-enabled.

Q.2Why and what if

Why can counter += 1 lose updates between threads even with the GIL?Why

The statement compiles to separate load, add and store instructions, and the GIL can be handed to another thread between them. Both threads can load the same old value. The GIL makes single instructions atomic, not statements; use a lock or avoid sharing.

Why does sys.getrefcount(x) return one more than you expect?Why

Passing x as the argument creates a temporary reference for the duration of the call, which is counted too.

Why does a service's memory not drop after a large request finishes?Why

pymalloc returns an arena to the OS only when all its blocks are free; a few surviving objects pin arenas, so freed memory stays in the process for reuse. That is fragmentation, not a leak; compare tracemalloc snapshots to check, and recycle workers if needed.

Why are local variables faster than globals in CPython?Why

Locals live in a fixed-size array in the frame and are accessed by index (LOAD_FAST); globals require dict lookups in the module and then builtins. Specialisation with cached dict versions has narrowed the gap since 3.11, but locals remain the cheapest.

What if a dict key object were mutated after insertion?What if

Its hash would change but the entry would stay in the slot chosen by the old hash, so lookups with the mutated key would probe the wrong slots and fail, while the entry stayed unreachable. This is why the built-in mutable containers are unhashable.

What if two objects reference each other and one defines __del__?What if

Since Python 3.4 (PEP 442) the cycle collector can still collect them: it calls the finalizers once and then frees the cycle if nothing was resurrected. Before 3.4 such cycles went to gc.garbage uncollected. Finalizer order within a cycle is unspecified, so __del__ should not rely on other objects in the cycle.

What if you call an async def function without await?What if

You get a coroutine object and the body never runs; when the object is garbage-collected Python warns "coroutine ... was never awaited". To run it concurrently you must wrap it in a task (create_task or a TaskGroup) and keep a reference.

What if one endpoint in an async service does 300 ms of CPU-bound JSON processing?What if

Every other request on that worker's event loop is frozen for 300 ms, so tail latency rises for unrelated endpoints. Move the work to a process pool or a job queue, or to a plain def endpoint if it releases the GIL (otherwise threads still contend for the GIL), and add more worker processes.

Why does a[[0, 2]] return a copy but a[0:3:2] a view?Why

A slice is a regular pattern expressible as an offset and a stride per axis, so NumPy writes a new header over the same buffer. An index list can select any elements in any order, which no single stride can describe, so the values must be gathered into a new buffer.

What if you pass a transposed array to a C++ binding that requires C-contiguous input?What if

With forcecast pybind11 silently copies it into a temporary C-contiguous array (correct, but an extra O(n) cost and memory per call); without it the call raises a TypeError. Either convert once with np.ascontiguousarray or make the C++ code accept strides.

Why can a naive C++ loop be slower than NumPy?Why

NumPy's kernels are compiled, vectorised code over contiguous data. A naive C++ loop with per-element bounds checks and branches prevents SIMD and does more work per pixel, so it can lose (18.5 ms versus 4.8 ms in the blur example). Removing the branches from the interior made it 2.3 ms.

What if a free-threaded 3.14t process imports an old C extension?What if

If the extension does not declare free-threading support, CPython re-enables the GIL for the whole process and warns, so the program runs correctly but serially. Check sys._is_gil_enabled() after imports.

Why does cached_property not slow down repeated access, while property runs every time?Why

cached_property is a non-data descriptor that stores the computed value in the instance dict, and the instance dict wins over non-data descriptors on later lookups. property is a data descriptor, which always wins over the instance dict, so its getter runs on every access.

What if your package's tests import a local file called random.py?What if

The script directory (or test root) is first on sys.path, so import random anywhere, including in the standard library, gets your file instead, often failing with confusing attribute errors. Rename it and avoid stdlib module names.

Why do processes, not threads, speed up CPU-bound Python on the default build, and what do they cost?Why

Each process has its own interpreter and GIL, so they run bytecode in parallel. The costs are pickling arguments and results through pipes, duplicated memory and imports per worker, and start-up time; the measured speedup was 3.2× on 4 cores, below the ideal 4×.

What if you mock payments.charge but the code under test did from payments import charge?What if

The test has no effect: the module under test holds its own name bound to the original function. Patch orders.charge, the name where it is looked up.

  • The Python documentation: "Data model", "Execution model", "The import system", and the "What's New" pages for 3.11 to 3.14, which explain each interpreter change in detail.
  • CPython's internals documentation, InternalDocs/ in the CPython repository (interpreter, frames, garbage collector, exception handling).
  • PEP 659 (specialising adaptive interpreter), PEP 683 (immortal objects), PEP 703 and PEP 779 (free-threading), PEP 734 (multiple interpreters), PEP 649 (deferred annotations), PEP 544 (protocols), PEP 517/621/751 (build interface, project metadata, lock files), PEP 723 (inline script metadata).
  • The free-threading guide at py-free-threading.github.io: compatibility status of popular packages and porting advice for extensions.
  • Luciano Ramalho, Fluent Python, 2nd edition (O'Reilly): the data model, descriptors, metaclasses, generators and asyncio in depth.
  • Anthony Shaw, CPython Internals (Real Python): a guided tour of the interpreter's source.
  • NumPy documentation, "The N-dimensional array" and "Copies and views"; the Polars user guide on the lazy API and query optimisation.
  • pybind11 and nanobind documentation (buffer protocol, return value policies, GIL); scikit-build-core and cibuildwheel documentation.
  • The Python Packaging User Guide (packaging.python.org) and the uv documentation.
  • FastAPI documentation ("Concurrency and async / await", "Dependencies"), Pydantic documentation, the Django documentation on async support.
  • pytest documentation (fixtures, parametrisation, monkeypatch) and the py-spy, Scalene and memray READMEs.
