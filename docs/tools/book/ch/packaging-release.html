Packaging, CI/CD and release engineering

How software gets from a commit to running on someone else's machine: Linux packages (deb, rpm), application formats (AppImage, Flatpak, Snap), linking choices for distribution, CI pipeline design, caches and artifacts, versions and releases, signing, deployment strategies for services, and over-the-air updates for embedded Linux and vehicles. One running example, the camera tool framegrab, is built, packaged, signed and shipped to desktops, a cluster and a fleet of camera boxes, and most numbers come from real tools run on it.

1The big picture: from a commit to running software

Building software produces a binary on one machine. Shipping it means that binary has to install, start and keep working on thousands of machines you will never see, get replaced safely when a fix comes, and be traceable back to the exact source it came from. That second problem has its own tools and its own failure modes, and this chapter is about them.

1.1Shipping is a separate problem from building

A compiler and a build system answer one question: given this source, produce a correct binary. The build chapter covers that path, from preprocessing through linking to a container image. Once the binary exists, four new questions appear, and each has grown its own discipline.

Packaging asks how the binary, its data files and its configuration get onto another machine in a form that machine can install, upgrade and remove, and how the package states what it needs from that machine. A package is a contract: "I contain these files, I need these libraries in at least these versions, and these scripts must run when I am installed." Continuous integration asks how every change is built and tested automatically, quickly enough that people actually wait for the answer, and how the outputs of that run are kept. Release engineering asks which of those outputs becomes a release, what it is called, how users can trust it came from you, and how you will reproduce it in five years. Deployment and delivery ask how a release replaces the previous one on running systems without taking them down, and how to undo it when it is wrong.

These questions look administrative until one goes wrong. A package that depends on a glibc newer than the customer's distribution refuses to start with an error the customer cannot interpret. A pipeline that takes ninety minutes teaches engineers to merge without waiting for it. A release key kept as a CI secret is stolen along with the CI system. A rolling deployment of a version that never becomes ready stalls with a fifth of the capacity gone. An update to a camera box that loses power at the wrong moment turns the box into a brick in a car on the other side of the world. Each of these is a property of the shipping path, not of the code, and each is avoided by design decisions made long before the incident.

Why it matters

Users never see your source code; they see what arrives on their machine and what happens when it changes. A strong team can be undone by a weak shipping path: the bug fix exists for weeks before anyone receives it, or the fix arrives and breaks something else. The quality of the shipping path sets how fast every other improvement reaches people.

1.2The running example: framegrab and its three destinations

framegrab is a small C program that grabs frames from a camera, compresses them with zlib and can upload them to a server. The source used in the experiments is about forty lines, which is enough, because what interests us is everything around it. It is shipped three ways, and the three ways are deliberately different.

Engineers on Linux desktops install the framegrab tool to inspect and record camera output. They run Ubuntu, Debian, Fedora and the occasional Arch Linux, of different ages, and the tool must install with the package manager they already use or as a single file they download. The uploaded frames go to framegrab-ingest, a service that runs as a container on a Kubernetes cluster. The team deploys it several times a week and controls the machines completely. Finally, the same capture code runs on a camera box, an embedded Linux device fitted to test vehicles and later to production trucks. Nobody logs into it, power can disappear at any moment, and it is updated over the air.

The three destinations differ in exactly the properties that drive design. On desktops you do not control the environment, so the package must describe its needs or bring them along. On the cluster you control everything, so the hard part is changing a running system while it serves traffic. On the device you control the software completely but not the conditions, so the hard part is never leaving the device in a state from which it cannot recover. Keep these three in mind; nearly every choice in the chapter is "which of these problems are you solving?"

2What a package is: deb and rpm from the inside

Before package managers, installing software meant unpacking a tarball and running its install script as root, then hoping nothing else had overwritten the same files. Packages exist so that a machine knows which files belong to which software, what that software needs, and how to remove or upgrade it cleanly.

2.1Why packages exist: files, metadata, scripts and a contract

Every package format, whether deb, rpm, apk on Alpine or pacman's tar archives, carries the same three things. The files to install, with their paths, permissions and owners. The metadata: the name, the version, the architecture, a description, and above all the dependency relations, which say what else must be present. And scripts that run as root at install, upgrade and removal time, for the things that are not just files: creating a system user, enabling a service, rebuilding a cache.

The package manager keeps a database of every installed package and every file it owns. That database is what makes removal and upgrade possible: when framegrab 1.4.1 replaces 1.4.0, dpkg knows exactly which files 1.4.0 put there, which of them the new version still has, and which to delete. It is also what prevents conflicts. If another package tries to install /usr/bin/framegrab, dpkg refuses unless the second package declares that it replaces the first. Without a database, the machine's file system is the only record, and the record is ambiguous.

The dependency relations are the contract with the rest of the system. framegrab needs libc.so.6 and libz.so.1; the package says which packages provide them and in which minimum versions. The package manager can then install what is missing, refuse what would break, and upgrade libraries knowing who depends on them. This is the distribution model's great strength: zlib is installed once, and a security fix to zlib reaches every program that uses it with one package update.

Interesting detail

The distribution model assumes one version of each library for the whole system. That is what makes shared security fixes work, and it is also the root of "dependency hell": if application X needs libfoo 2 and application Y needs libfoo 3, and the two are not co-installable, one of them cannot be installed. Sonames (build 4.2) let distributions ship several major versions side by side as libfoo2 and libfoo3; the application formats of Chapter 4 take a different route and bring their own copies.

2.2Inside a .deb

A .deb is a remarkably plain file. The outer container is an ar archive, the same format as a static library, with exactly three members in a fixed order. The experiment in this chapter builds framegrab 1.4.0 as a deb by hand with dpkg-deb and opens it again:

$ ar t framegrab_1.4.0-1_amd64.deb
debian-binary
control.tar.xz
data.tar.xz
$ dpkg-deb -I framegrab_1.4.0-1_amd64.deb
 new Debian package, version 2.0.
 size 3484 bytes: control archive=512 bytes.
     266 bytes,     9 lines      control
     135 bytes,     3 lines   *  postinst             #!/bin/sh
 Package: framegrab
 Version: 1.4.0-1
 Architecture: amd64
 Depends: libc6 (>= 2.34), zlib1g (>= 1:1.2.0)
 ...

debian-binary holds the string "2.0", the format version. control.tar.xz holds the control file with the metadata, the maintainer scripts (preinst, postinst, prerm, postrm), a list of checksums of the payload (md5sums) and the list of configuration files (conffiles). data.tar.xz is the payload: a tar archive of the files exactly as they will appear under /. Compression can be gzip, xz or zstd; Ubuntu switched its archive to zstd in 21.10 for faster installs.

The interesting line is Depends, and nobody typed it. The build ran dpkg-shlibdeps on the binary, which read its ELF dynamic section (NEEDED libz.so.1, NEEDED libc.so.6), looked up which installed package provides each library, and then consulted that library's symbols file, a list that maps each exported symbol version to the first package version that provided it. framegrab uses __libc_start_main@GLIBC_2.34, so it needs libc6 at least 2.34; the minimum is computed, not guessed. In a normal Debian package build, debhelper runs this automatically and fills in a ${shlibs:Depends} substitution variable.

Conffiles deserve a sentence. A file under /etc listed as a conffile is treated specially on upgrade: if the administrator has edited it and the new package also changes it, dpkg stops and asks (or, unattended, keeps the local version and writes the new one as .dpkg-dist). This is why a package must never generate its configuration file in a maintainer script and then also ship it; the two mechanisms fight.

2.3Inside an .rpm: the spec file and generated requirements

An rpm is built from a spec file, a recipe with a preamble of metadata and sections for each stage: %prep unpacks sources, %build compiles, %install copies files into a staging root, %files lists what belongs to the package, and %pre, %post, %preun, %postun hold the scriptlets. The experiment's spec is twenty lines; rpmbuild turned it into a 14.6 KB package. The file itself is a 96-byte legacy lead, a signature header, a header with every piece of metadata, and a compressed cpio archive as payload.

The header is where rpm differs most from deb. Its requirements are generated at a finer grain:

$ rpm -qp --requires framegrab-1.4.0-1.x86_64.rpm
/bin/sh
libc.so.6()(64bit)
libc.so.6(GLIBC_2.2.5)(64bit)
libc.so.6(GLIBC_2.34)(64bit)
libz.so.1()(64bit)
libz.so.1(ZLIB_1.2.0)(64bit)
rtld(GNU_HASH)
...
$ rpm -qp --provides framegrab-1.4.0-1.x86_64.rpm
application()
application(framegrab.desktop)
framegrab = 1.4.0-1
framegrab(x86-64) = 1.4.0-1

rpm does not say "I need the package glibc"; it says "I need something that provides the symbol version GLIBC_2.34 of libc.so.6", and the glibc package declares that it provides exactly that. The resolver matches capabilities, not package names, which makes renaming and splitting packages painless. The /bin/sh requirement appeared because the spec has a %post scriptlet: rpm noticed that a shell will be needed to run it. Even the desktop file produced a capability, application(framegrab.desktop), which software centres use to find installable applications.

Pitfall

rpm runs an upgrade in an order that surprises people: the new package's %pre and %post run first, and only then the old package's %preun and %postun. Each scriptlet receives a count of how many versions will remain installed: 1 or more means upgrade, 0 means removal. A %postun that deletes the service user without checking $1 -eq 0 deletes it on every upgrade, right after the new version created it.

2.4Repositories and dependency resolution

Nobody installs packages one file at a time. A repository is a directory tree of packages plus index files that list every package with its metadata and checksum. An apt repository has a dists/<suite>/ tree with a Release file (signed as InRelease) and one Packages index per component and architecture; packages live under pool/. A dnf repository has repodata/repomd.xml pointing to compressed XML or SQLite metadata. apt update and dnf makecache download these indexes, and from then on the package manager works out what to do locally.

Working out what to do is harder than it looks. Installing one package may require others, which may conflict with something installed, which may be resolvable by upgrading a third package, which itself has requirements. Deciding whether a set of package versions satisfies all Depends, Conflicts and Breaks relations is NP-complete in general, which is why dnf and zypper use libsolv, a SAT solver, and why apt's resolver, which uses heuristics, occasionally proposes to remove half the desktop to install one package. In practice the problem stays tractable because distributions keep the repository consistent: every package in a release was built and tested against the others.

That consistency is the reason to publish your own packages in your own repository rather than as loose files. With a repository, users add one line to their sources, and from then on apt upgrade brings new framegrab versions along with their security updates. Several repositories can be combined, and pinning (/etc/apt/preferences.d, dnf's priority=) decides which wins when two offer the same package. Ubuntu adds one more field worth knowing: Phased-Update-Percentage in the index makes apt offer an update to only that share of machines at first, chosen deterministically per machine. That is a staged rollout built into the package manager, the same idea as the fleet rollouts of Section 10.6.

2.5Maintainer scripts, upgrades and services

Maintainer scripts are the most dangerous part of a package, because they are arbitrary shell run as root on someone else's machine, at a moment when the system is half way between two states. The order dpkg follows on an upgrade is fixed by Debian Policy, and knowing it explains most rules about writing the scripts.

The rules follow from the sequence. Scripts must be idempotent, because a failed upgrade is retried and the same postinst configure may run twice. They must work without interaction, because packages are installed by automation; questions belong in debconf, which can be pre-seeded. They should do as little as possible: enabling and restarting a systemd unit, creating a system user with systemd-sysusers or adduser --system, triggering a cache rebuild. Anything that can be a file should be a file, and caches should be rebuilt by triggers, which let many packages request one rebuild of the icon cache instead of each rebuilding it.

Services add a second lifecycle on top. On Debian and Ubuntu, debhelper's dh_installsystemd generates the script fragments that stop the service in prerm, reload systemd, and start or restart it in postinst. Fedora uses the %systemd_post family of macros, and by default does not start new services at install time; a preset policy decides. Doing this by hand is where packages go wrong: a service restarted before its new configuration file is unpacked, or never restarted after an upgrade, so the machine keeps running the old binary from a deleted inode until the next reboot.

In practice

For framegrab-ingest's on-premises edition, the team's rule is that the postinst does three things only: create the system user, call deb-systemd-invoke restart on the unit, and print nothing. Schema migrations run in the service at start time, guarded by a version table, not in the package script, so they also run when someone deploys the same version as a container.

2.6Building packages properly

The experiment built its deb with dpkg-deb directly and its rpm from a hand-written spec, which is fine for seeing the formats but not how packages are normally made. Debian packages are built from a debian/ directory (control, rules, changelog, copyright) by dpkg-buildpackage, with debhelper's dh sequencer doing nearly all the work: configuring CMake or Meson, installing, stripping and splitting debug symbols into a -dbgsym package, computing dependencies, generating service script fragments. rpm packages come from a spec file built with rpmbuild, with macros playing the same role.

Two habits separate reliable packages from fragile ones. First, build in a clean, minimal environment: sbuild or pbuilder on Debian and mock on Fedora create a fresh chroot with only the declared build dependencies, so a missing Build-Depends fails the build instead of silently working on the developer's well-stocked laptop. A CI container image does the same job if it starts from the target distribution's base image. Second, run the linters: lintian for debs and rpmlint for rpms know hundreds of policy rules, from missing copyright files to binaries with an insecure RPATH.

Software that ships outside a distribution's archive, as framegrab does, often uses a simpler route. CMake's CPack has DEB and RPM generators; nfpm builds deb, rpm, apk and Arch packages from one YAML file listing files, dependencies and scripts, with no distribution tooling needed. These produce perfectly valid packages; what they do not do is compute dependencies from the binary, so the dependency lines must be maintained by hand and checked by a test that installs the package on a clean image of every supported distribution. That install test is the single most useful packaging check in CI.

Talk track

"Our packages are built in a clean container of each target distribution, linted, and then installed, upgraded from the previous release and removed again on fresh images in CI. If a dependency is missing or a script is not idempotent, the pipeline fails before a user sees it."

3One binary, many Linux systems: linking as a distribution decision

A distribution package is built for one release of one distribution. Software that wants to run on many of them with one download has to decide what it brings along and what it takes from the host, and the decision is mostly about glibc.

3.1Why a binary from one distribution fails on another

Build framegrab on Ubuntu 24.04 and copy it to a machine running Debian 11 or RHEL 8, and it does not start:

./framegrab: /lib/x86_64-linux-gnu/libc.so.6: version `GLIBC_2.34' not found (required by ./framegrab)

The reason is symbol versioning (build 4.4). glibc tags every exported symbol with the version in which its current behaviour appeared, and the linker records in the binary the exact version of each symbol it bound to. The experiment shows what the Ubuntu 24.04 build of framegrab asks for:

host: ldd (Ubuntu GLIBC 2.39-0ubuntu8.9) 2.39
$ objdump -T framegrab | grep -o 'GLIBC_[0-9.]*' | sort -uV
GLIBC_2.2.5 GLIBC_2.3.4 GLIBC_2.4 GLIBC_2.34
$ objdump -T framegrab | grep GLIBC_2.34
... __libc_start_main

One symbol pins the whole binary to glibc 2.34 or newer, and it is not even one the program calls: it is __libc_start_main, the function the C start-up code uses to reach main. glibc 2.34 (2021) merged libpthread, libdl and libutil into libc and gave this function a new version, so every binary linked against 2.34 or later requires 2.34. Debian 11 and Ubuntu 20.04 ship glibc 2.31, RHEL 8 ships 2.28. The binary itself is fine; it simply promises to use functions that the older library does not have.

The key property is that glibc is backward compatible but not forward compatible. A binary linked against glibc 2.17 runs on 2.39, because 2.39 still provides every old symbol version alongside the new ones. A binary linked against 2.39 does not run on 2.17. Every strategy in this chapter follows from that asymmetry.

3.2Build on the oldest baseline you support

The cheapest fix is to build on the oldest system you want to support. A binary built against glibc 2.28 binds to symbol versions no newer than 2.28 and therefore runs on RHEL 8, Debian 11, Ubuntu 20.04 and everything newer. The build environment becomes a container image of the oldest supported distribution, or a sysroot from it (build 7.3) combined with a modern compiler.

Python's binary wheels formalised this idea. A manylinux wheel promises to run on any Linux with at least a stated glibc: manylinux2014 means glibc 2.17 (CentOS 7), manylinux_2_28 means glibc 2.28, following PEP 600's manylinux_x_y naming. The numpy wheels downloaded for this chapter's delta experiment are tagged manylinux_2_17_x86_64: built on an old baseline with a newer compiler toolchain, and installed on the Ubuntu 24.04 container without complaint. The auditwheel tool checks that a wheel uses no newer symbols than its tag allows and copies any other shared libraries into it, which is bundling (Section 3.4) done automatically. The Python chapter covers wheels from the Python side.

The cost is that the oldest baseline also limits the C++ standard library. libstdc++ uses symbol versions too (GLIBCXX_3.4.30 and so on), so a binary built with a new GCC needs a new libstdc++ at run time. The usual answers are to link libstdc++ statically (-static-libstdc++, permitted by its runtime library exception) while keeping glibc dynamic, or to use a toolchain such as Red Hat's devtoolset, which links the newer parts of libstdc++ statically into the binary and uses the system's old libstdc++ for the rest.

3.3Static linking: musl, glibc and what you give up

The opposite extreme links everything into the executable, so the only thing it needs from the host is the kernel's system-call interface, which Linux keeps stable. The experiment linked framegrab three ways:

BuildStripped sizeNeeds from the host
dynamic, glibc14 472 byteslibc.so.6 (≥ 2.34), libz.so.1
static, glibc1 001 536 byteskernel; and the same glibc for name lookups (warning below)
static, musl (no zlib)71 328 byteskernel only

The static glibc build compiled, but the linker printed a warning worth reading:

warning: Using 'getaddrinfo' in statically linked applications requires at runtime the shared
libraries from the glibc version used for linking

glibc's name lookup goes through NSS, the Name Service Switch, which reads /etc/nsswitch.conf and loads plug-in libraries such as libnss_files.so or libnss_systemd.so with dlopen at run time. A static binary still has to load those plug-ins, and they must match the glibc it was linked against. The same applies to iconv character conversions and some locale data. So "static glibc" is not really self-contained, and glibc's maintainers discourage it. On the test machine the lookup worked only because the host's glibc was the same one.

musl, the C library behind Alpine Linux, was designed for static linking. It has no NSS: it reads /etc/hosts and talks DNS directly, so the static musl build of framegrab resolved names on its own. It is also small: 71 KB against a megabyte. The trade-offs are behavioural differences (no NSS means no LDAP or systemd user lookups, a different DNS implementation, a simpler malloc that can be noticeably slower in heavily threaded programs) and the need to build every dependency against musl too; the experiment had to drop zlib from the musl build because the system's static zlib was built against glibc. Go programs built with CGO_ENABLED=0 and Rust programs for the x86_64-unknown-linux-musl target are static this way, which is a large part of why they are easy to ship.

Static linking has two costs beyond the technical ones. Security fixes: when zlib has a vulnerability, a distribution fixes it once for every dynamically linked program, but every statically linked program must be rebuilt and re-shipped by its vendor. Your SBOM (build 11.5) is the only way to know which of your binaries contain the vulnerable code. Licensing: glibc is LGPL, which allows linking from proprietary programs on the condition that users can relink the program against a modified library; with dynamic linking that is automatic, with static linking you must provide your object files. Permissively licensed libraries such as musl (MIT) and zlib do not impose that condition.

Pitfall

Some libraries cannot be meaningfully linked statically because they are the interface to hardware the host owns. The OpenGL, EGL and Vulkan libraries come with the GPU driver and must match the kernel driver's version; a GUI program always loads them from the host. A fully static framegrab is fine as a command-line tool and impossible as an application that draws with the GPU.

3.4Bundling shared libraries with $ORIGIN

Between the two extremes sits bundling: keep the program dynamically linked, but ship its non-system libraries next to it and tell the dynamic loader to look there first. The loader expands the token $ORIGIN in a binary's RUNPATH to the directory containing the binary, so the search path moves with the installation. The experiment copied framegrab and libz into an application directory and set the path with patchelf:

$ patchelf --set-rpath '$ORIGIN/../lib' AppDir/usr/bin/framegrab
$ readelf -d AppDir/usr/bin/framegrab | grep RUNPATH
 0x000000000000001d (RUNPATH)            Library runpath: [$ORIGIN/../lib]
$ LD_DEBUG=libs AppDir/usr/bin/framegrab --version
calling init: AppDir/usr/bin/../lib/libz.so.1
framegrab 0.0.0-dev (zlib 1.3)

The loader found the bundled libz before the system's. This is what AppImage tools such as linuxdeploy do, what auditwheel does for Python wheels, and what vendors of large applications have done for decades under /opt. The single set of rules that makes it work is about what not to bundle. glibc and the dynamic loader must come from the host, because the loader is named by absolute path in the binary and the kernel loads it. GPU driver libraries must come from the host, for the reason above. Libraries that talk to system services whose protocols change (D-Bus, PulseAudio or PipeWire client libraries, fontconfig with its cache format) are usually better taken from the host. The AppImage project maintains an excludelist of such libraries that its tools refuse to bundle.

Bundling moves the security responsibility to you, exactly as static linking does, and adds a subtle failure: if a host library that you did not bundle (a GPU driver, say) itself depends on a newer libstdc++ than the one you bundled, the process now contains two expectations and only one libstdc++. The usual rule is to bundle libstdc++ only if the host's is older than yours, which some AppImage runtimes check at start.

3.5Choosing

The choice follows from the destination. For distribution packages, link dynamically against the distribution's libraries and build once per distribution release; the package manager handles the rest. For a downloadable binary that must run on any Linux, build on an old baseline and either bundle (for applications with a GUI, which cannot be static) or link statically against musl (for command-line tools and services). For containers and embedded images, the question disappears: the image contains the whole user space, so the binary is built against exactly the libraries it will meet. That is one of the main reasons containers spread, and the reason the camera box never has a glibc problem.

Numbers

glibc versions of common baselines: RHEL 8 2.28, Debian 11 and Ubuntu 20.04 2.31, RHEL 9 2.34, Ubuntu 22.04 2.35, Debian 12 2.36, Ubuntu 24.04 2.39. A binary built on RHEL 8 or AlmaLinux 8 runs on all of them; one built on Ubuntu 24.04 runs only on the last.

4AppImage, Flatpak and Snap

Distribution packages tie an application's release to the distribution's: Debian stable ships the framegrab version that existed when it froze, for two years. Application formats exist to separate the two, so that one build reaches every distribution and users get new versions when the developer releases them.

4.1Why application formats exist

The distribution model works beautifully for the operating system and its libraries and poorly for applications whose users want the newest version. A developer who wants framegrab on Ubuntu 22.04, 24.04, Debian 12, Fedora 41 and Arch must otherwise build and test five packages, maintain five repositories, and still cannot help users on a distribution they did not target. Each distribution, in turn, repackages popular applications, with its own patches, its own delays, and bug reports that reach the upstream developer for problems the developer never created.

Three answers grew up on Linux in the 2010s, and they made different trade-offs. AppImage (2004 as klik, renamed in 2013) packs the application and its bundled libraries into one executable file and asks nothing of the system beyond FUSE. Flatpak (2015, originally xdg-app) runs applications on shared, versioned runtimes inside a sandbox, distributed through repositories such as Flathub. Snap (2016, from Canonical) mounts compressed application images managed by a system daemon, confined by AppArmor and updated automatically from the Snap Store. All three solve the "one build for all distributions" problem; they differ on sandboxing, on how much is shared, and on who controls distribution.

4.2AppImage: one file you can run

An AppImage is an ELF executable with a compressed file system glued to its end. The experiment opened the official appimagetool, which is itself an AppImage, without running it:

$ file -b appimagetool-x86_64.AppImage
ELF 64-bit LSB pie executable, x86-64, version 1 (SYSV), static-pie linked
runtime ELF ends at offset 944632 of 15133176 bytes
magic at that offset:  h s q s           (squashfs, little-endian "sqsh")
ELF sections the AppImage spec adds: .digest_md5 .sha256_sig .sig_key .upd_info
bytes 8-10 of the ELF header: A I 002    (AppImage type 2 magic)

The first 945 KB are the runtime, a small static program; the rest is a squashfs image. The experiment then built framegrab as an AppImage by concatenating the same runtime with a squashfs of the bundled application directory from Section 3.4:

runtime 944632 + squashfs 61440 = AppImage 1006072 bytes
/AppRun
/framegrab.desktop
/framegrab.png
/usr/bin/framegrab
/usr/lib/libz.so.1

When a user runs the file, the runtime finds its own end, mounts the squashfs read-only with FUSE at a temporary directory such as /tmp/.mount_framegXXXXXX, and executes AppRun inside it, which sets up paths and starts the real program. Nothing is installed; deleting the file uninstalls the application. The runtime also answers to options of its own: --appimage-extract unpacks the image (useful where FUSE is unavailable, such as in containers and CI), --appimage-offset prints where the image starts.

That design explains AppImage's strengths and weaknesses. It is the simplest possible user experience, needs no root and no daemon, and runs on almost any distribution newer than the build baseline. It has no sandbox: the application runs with the user's full rights. It shares nothing, so ten AppImages bundle ten copies of the same libraries. It depends on FUSE; older type 2 runtimes needed the host's libfuse2, which Ubuntu 22.04 no longer installs by default and which produced a wave of "AppImage does not start" reports, while newer runtimes link libfuse statically and need only the kernel module and fusermount. Updates are optional: the .upd_info section can hold a URL to a .zsync file, and a tool such as AppImageUpdate then downloads only the changed blocks. Signatures are optional too (.sha256_sig, .sig_key) and almost nothing checks them, so in practice users trust the HTTPS site they downloaded from.

4.3Flatpak: shared runtimes and a sandbox

Flatpak separates an application from a runtime, a versioned set of base libraries maintained by someone else: org.freedesktop.Platform for the common base, org.gnome.Platform and org.kde.Platform for the two big desktops. An application declares which runtime and version it needs and bundles only what the runtime lacks. Many applications share one runtime, and both applications and runtimes are stored in an OSTree repository, a content-addressed store in which identical files are kept once and hard-linked, so twenty applications on the same runtime cost little extra disk. Updates arrive as deltas between OSTree commits.

The application is described by a manifest that flatpak-builder executes in a clean SDK environment:

id: org.example.Framegrab
runtime: org.freedesktop.Platform
runtime-version: '24.08'
sdk: org.freedesktop.Sdk
command: framegrab
finish-args:
  - --share=network          # upload frames
  - --device=all             # camera nodes under /dev (coarse; the camera portal is finer)
  - --filesystem=xdg-pictures
modules:
  - name: framegrab
    buildsystem: cmake-ninja
    sources:
      - type: archive
        url: https://example.org/framegrab-1.4.0.tar.gz
        sha256: 5f0c…

At run time, bubblewrap starts the application in new namespaces (build 9.3) with the runtime mounted at /usr, the application at /app, a seccomp filter, and only the access listed in finish-args. Everything else goes through portals, D-Bus services on the host that mediate access: the file-chooser portal lets the user pick a file, and the application receives only that file, not the home directory; a camera portal grants access to a camera through PipeWire after the user agrees. GPU drivers come as runtime extensions that match the host's driver, which solves the problem from Section 3.3. Flathub is the de facto central repository, but anyone can host a Flatpak repository, and organisations do.

Interesting detail

The sandbox is only as strong as the permissions an application asks for. Many applications on Flathub request --filesystem=home or --socket=x11, and an X11 client can read every keystroke on the display, so the sandbox does little for them. The model works best for applications written for portals and Wayland.

4.4Snap: mounted images, confinement and a store

A snap is a squashfs image, like an AppImage's payload, but it is installed and managed by snapd, a system daemon. snapd mounts each installed revision read-only at /snap/<name>/<revision> through a systemd mount unit, keeps the previous revision for rollback, and gives each snap writable data directories. An application snap runs on a base snap (core22, core24: a minimal Ubuntu LTS user space), which plays the role of Flatpak's runtime. It is described by a snapcraft.yaml with parts to build, apps to expose, and the interfaces each app plugs into: network, camera, home.

Confinement comes in three levels. Strict confinement uses AppArmor profiles, seccomp filters and device cgroups generated from the declared interfaces; some interfaces connect automatically, others only after the user or a store decision allows them. Classic confinement is no confinement, granted by the store for tools such as editors and compilers that need the whole system. Devmode is for development. Full strict confinement needs AppArmor in the host kernel, which Ubuntu has and some other distributions do not, so on those snaps run with weaker isolation.

Distribution is centralised: snaps come from the Snap Store, run by Canonical, which is the only store snapd talks to (organisations can buy a proxy or dedicated store). Each snap has channels made of a track and a risk level (stable, candidate, beta, edge), so 1.4/stable and latest/edge can exist side by side. snapd refreshes installed snaps automatically, several times a day by default; users can postpone or hold refreshes, and enterprises can gate them. Automatic updates are the feature Canonical intended and the one users argue about most. Ubuntu Core takes the model further: the whole operating system, kernel and gadget configuration included, is a set of snaps with transactional updates and automatic rollback, which makes it one of the embedded update systems of Chapter 10.

5Designing a CI pipeline

Continuous integration is a practice: everyone integrates into the main line at least daily, and every integration is checked automatically (software quality 10.1). The pipeline is the machine that does the checking, and its design decides whether people trust it, wait for it, or route around it.

5.1A pipeline is a dependency graph triggered by events

Strip away the vendor vocabulary and every CI system has the same parts. An event starts a run: a push, a pull request, a tag, a schedule, a manual button. The run is a directed acyclic graph of jobs; an edge from job A to job B means B needs A's result. Each job runs on a runner, a machine or container that executes its steps in a fresh workspace. Jobs pass files to each other as artifacts and speed themselves up with caches (Chapter 6). The definition lives in the repository next to the code, so a change to the pipeline is reviewed and versioned like any other change, and an old commit can be rebuilt with the pipeline it had.

The build chapter's Section 11.2 follows one job of this kind from commit to artifact for an automotive application: toolchain images pinned by digest, a build matrix, packaging and promotion. This chapter takes the next step up and asks how to design the whole graph: what runs on which event, in which order, on which runners, and with which permissions.

Three events deserve different pipelines. A pull request run answers "may this change be merged?" and must be fast, because a person is waiting; it builds, runs the tests that matter for the change and reports. A main branch run answers "is main still good?" and produces the artifacts that may become a release, so it builds every target and runs the slower tests. A tag run answers "make this a release": it does not rebuild anything that the main run already built and tested, it names, signs and publishes those artifacts (Chapter 7). Scheduled nightly runs take the jobs nobody can wait for: long soak tests, hardware-in-the-loop benches, fuzzing, dependency updates.

5.2Anatomy: GitHub Actions and GitLab CI

The two most common hosted systems describe the same graph in slightly different YAML. Here is framegrab's pull request and main pipeline in GitHub Actions, shortened:

  pull_request:
  push:
    branches: [main]

GitLab CI expresses the same graph with stages for a coarse order and needs: for real dependencies, parallel: matrix: for the legs, rules: for which events trigger which jobs, cache: key: files: [conan.lock] for cache keys and artifacts: paths: with expire_in: for outputs. Jenkins pipelines are Groovy (Jenkinsfile) and run on agents the team operates. The vocabulary differs; the graph, the events, the runners, the caches and the artifacts are the same, and a pipeline designed well in one moves to another without being redesigned.

Pitfall

A matrix multiplies quickly. Four compilers times three build types times three distributions is 36 jobs per push. Run the full product only on main or nightly; on pull requests run the legs that catch most failures (one fast compiler, the sanitizer build, the most different architecture), and use include: to list the combinations you actually want instead of excluding the ones you do not.

5.3The critical path, parallelism and waiting for runners

The wall-clock time of a pipeline is not the sum of its jobs; it is the length of its critical path, the longest chain of dependent jobs, as long as there are enough runners to run everything else beside it. framegrab's graph makes this concrete.

Two consequences follow, and both are routinely ignored. First, optimise the critical path, not the average job. Shaving five minutes off three x86 legs saves nothing; moving the aarch64 tests to native Arm runners, or caching its build, saves minutes for every engineer on every push. Second, parallelism needs runners. A graph with eight independent jobs finishes in the time of the longest only if eight runners are free; with two runners the jobs queue, and the queue becomes the critical path. The model also shows the cost side. Six legs on two runners take 58.5 minutes and 108 runner-minutes, with jobs spending more than two and a half hours waiting in total. Hosted CI is billed per runner-minute, self-hosted CI by the machines you keep, and both are finite, so the matrix width is a budget decision as much as a quality decision. Two cheap rules help: cancel superseded runs (the concurrency block above), and put fast, likely-to-fail jobs such as formatting and lint at the front so a doomed run stops in one minute instead of thirty.

Numbers

A common target is ten to fifteen minutes for the pull-request path (software quality 13.2). Beyond about twenty minutes, people stop waiting and switch to other work, which makes each failure cost a context switch, and they start batching changes, which makes each failure harder to attribute.

5.4Keeping main green: required checks and merge queues

A green pull request proves that the change works on the commit it was tested against, not on the main branch it will land on. When main has moved since, two individually correct changes can combine into a broken one. This is a semantic conflict: git merges the text without complaint, and the build fails.

Both pull requests branch from commit M. PR A renames foo() to bar() and updates every caller. PR B adds a new call to foo(). Each pipeline runs on its branch, which contains M plus its own change, and both pass.

A is merged. Main is now M+A, which builds: A updated every caller that existed when it was written.

B is merged next. Its check is still green, because it ran on M, and git sees no textual conflict. Main is now M+A+B, which calls a function that no longer exists: the build is red for everyone until somebody notices and fixes it.

A merge queue does not merge B directly. It creates the commit main would become, M+A+B, runs the required checks on that, and merges only if they pass. Here the build fails in the queue, B is removed from it with a message, and main stays green. Queues test several waiting pull requests together in speculative batches, so the extra runs cost less than one per change.

The idea is old. Graydon Hoare described it in 2014 as the "not rocket science rule of software engineering": automatically maintain a repository of code that always passes all the tests. The bors bot built for the Rust project implemented it; GitHub's merge queue and GitLab's merge trains are the hosted versions. A cheaper half-measure is a branch protection rule that requires pull requests to be up to date with main before merging, which works for small teams and becomes a race for large ones, because each merge invalidates every other pull request's check.

Whatever the mechanism, required checks must be few, fast and reliable. A required check that is flaky blocks merges at random and teaches everyone to retry until green, which is worse than not requiring it. Flaky tests are quarantined and fixed (software quality 4.6), not retried into submission.

5.5Monorepos and selective pipelines

When one repository holds framegrab, its ingest service, the camera-box image and shared libraries, building everything on every change wastes most of the pipeline. Two techniques limit the work. Path filters (on: pull_request: paths: in GitHub Actions, rules: changes: in GitLab) start a pipeline only when files under certain directories change. They are simple and slightly wrong: a change to a shared header must trigger every consumer, and path lists drift out of date.

The robust technique is to ask the build system which targets are affected. A build graph with declared dependencies, such as Bazel's, can answer "which test targets depend, directly or transitively, on these changed files?", and CI runs exactly those. Bazel combined with a remote cache goes further: unchanged targets are not even rebuilt on the runner, their outputs are downloaded from the cache by content hash. Tools in other ecosystems (Nx and Turborepo for JavaScript, Pants for Python) do the same. The cost is that the build graph must be complete and honest; any undeclared dependency becomes a test that silently does not run.

5.6Runners: hosted, self-hosted, ephemeral and hardware

Hosted runners are virtual machines the CI provider starts for each job and destroys afterwards. They need no maintenance and give every job a clean machine, which is exactly the isolation CI wants. Their limits are the hardware on offer, network access to internal systems, and cost at scale. Self-hosted runners are machines the team operates: big build servers, Arm boards, GPU machines, or a bench with a camera box attached for hardware-in-the-loop tests. They are fast and can reach internal networks, and they carry a new risk: a runner that persists between jobs carries state, caches, credentials and possibly malware from one job to the next.

The answer is ephemeral self-hosted runners: each job gets a fresh container or virtual machine that is destroyed afterwards, typically scaled by a controller on Kubernetes (actions-runner-controller for GitHub, the Kubernetes executor for GitLab). Hardware is the exception that cannot be ephemeral, so hardware runners get extra care: they run only jobs from trusted branches, never from forks; they reflash the device under test to a known image at the start of every job; and they are reserved through a lock so two pipelines do not drive the same bench.

Pitfall

Never attach a persistent self-hosted runner to a public repository. Anyone can open a pull request, and the pull request's code runs on the runner. GitHub's documentation says the same, and attackers scan for exactly this configuration.

5.7Pipeline security

A CI system holds the keys to everything it publishes: registry credentials, signing keys, cloud accounts. It also runs code from every pull request. That combination makes it one of the most attractive targets in a software organisation, and the supply-chain incidents in build 11.6 are the proof. Five rules cover most of the risk.

Least privilege for tokens. Every job gets a token for the repository. Set the default to read-only (permissions: contents: read) and grant write access per job, only where needed: the release job may create a release, the lint job may not.

Untrusted code never meets secrets. Pull requests from forks run without secrets by default, and that default must not be undone. GitHub's pull_request_target event runs in the context of the base repository, with secrets, so that bots can label pull requests; a workflow that uses it and then checks out and builds the pull request's code hands the secrets to whoever opened it. GitHub's security team called this a "pwn request" in 2021, and it remains one of the most common real CI vulnerabilities. Values such as pull request titles are also attacker-controlled and must not be pasted into shell commands through ${{ }} expressions.

Pin third-party actions by commit SHA. A reference such as @v4 is a git tag, and tags can be moved. In March 2025 the popular tj-actions/changed-files action was compromised and its version tags were pointed at a commit that printed the runner's secrets into the build log (CVE-2025-30066); thousands of repositories ran it. Workflows that referenced the action by a full commit SHA kept running the old, clean code. That is why the workflow in Section 5.2 pins every action by SHA with the version in a comment; Dependabot or Renovate update those pins through reviewed pull requests.

Short-lived credentials instead of stored secrets. A cloud key stored as a CI secret is valid until someone rotates it, and can be read by any job that can read the secret. With OpenID Connect, the CI platform issues each job a signed identity token that states which repository, branch, tag, workflow and environment the job belongs to. The cloud's token service checks those claims against a trust policy and returns a credential that expires within the hour.

Protect the release path separately. Signing keys and production credentials belong to an environment that only runs for tags from protected branches, optionally after a person approves; the job that builds pull requests should not be able to reach them at all. The strongest form keeps the private key in a hardware security module or a cloud key-management service that signs on request and never releases the key, so even a compromised job can at most sign something during its own run, and leaves a log entry when it does.

Talk track

"Our CI follows least privilege. The default token is read-only; third-party actions are pinned by SHA and updated through reviewed pull requests; fork builds have no secrets; the release job gets cloud and signing access through OIDC from a protected environment, and the signing key never leaves the KMS."

6Caches and artifacts

Both caches and artifacts are files that outlive a job, and they are constantly confused. They make opposite promises: a cache may disappear at any time and the job must still be correct; an artifact is an output with an identity that must be kept exactly as it was produced.

6.1Cache versus artifact: two different promises

A cache is an optimisation. It holds things that can be recomputed from the job's inputs, such as compiler outputs, downloaded dependencies or Docker layers, keyed by a description of those inputs. A job that finds the cache is faster; a job that does not must produce the same result, only slower. Caches can be evicted, shared between branches under rules, and rebuilt at any time. If deleting all caches changes a build's result, the build has a bug.

An artifact is a product. It is a file the pipeline made and others will use: the deb, the AppImage, the container image, the OTA bundle, the test report, the debug symbols. It has an identity (name, version, digest), a retention period, and a chain back to the commit and pipeline run that produced it. Artifacts move between jobs in a run (the package job downloads the build job's output), and the ones that matter move on to a registry (build 11.4), where they become immutable.

The confusion causes two classic bugs. Using a cache to pass a build output from one job to the next works until the cache is evicted or a parallel run writes the same key, and then the package job ships the binary from somebody else's run. Using artifacts as a cache, uploading the whole build tree so that the next run can reuse it, fills the artifact storage and still misses whenever anything changes. Use each for its own job.

6.2Designing cache keys

A cache key is a name that should change exactly when the cached content would change. For framegrab's compiler cache, the content depends on the runner's operating system, the compiler and its version, the dependencies (fixed by the lockfile), and the source. A good key encodes the first three directly and the source loosely.

The pattern in the figure is the standard one for incremental caches such as ccache: an exact key that ends with the commit, so each run saves its own entry, and restore-keys that match by prefix, so a run on a new commit restores the closest older cache and the compiler cache itself sorts out which objects are still valid. For caches that are pure functions of a lockfile, such as downloaded packages, the key is simply the lockfile's hash and no fallback is needed: a new lockfile should start fresh.

Two rules prevent most cache bugs. Put everything that changes the output into the key: a cache shared between GCC 13 and GCC 14 serves wrong objects unless the tool itself checks the compiler (ccache does, by hashing the compiler binary's content or mtime). Keep everything else out: a date, a run number or a random value in the key makes every lookup a miss. And respect the platform's limits. GitHub Actions gives each repository 10 GB of cache by default, evicts the least recently used entries beyond that, and deletes entries not used for seven days; a matrix of twelve legs each saving a 2 GB cache evicts itself continuously and hits nothing. Caches are also scoped: a run can restore caches from its own branch and the default branch, never from an unrelated pull request, which is a security boundary as much as an organisational one.

In practice

Restoring a cache costs a download. A 2 GB ccache directory takes tens of seconds to restore and save on a hosted runner, which can exceed what it saves for a small project. Shared remote caches avoid the round trip: ccache's remote storage (HTTP or Redis), sccache with an object store, and Bazel's remote cache fetch only the entries a build actually needs.

6.4Cache poisoning and other ways caches go wrong

Because a cache is reused without being rebuilt, whoever can write to it can change what later builds contain. This is cache poisoning. The scoping rules exist to stop it: a pull request from a fork writes only to its own scope, and the main branch never restores it. The protection fails when untrusted code runs in a trusted scope, which brings back the pull_request_target problem of Section 5.7: published research in 2024 showed that a job able to run code in the default branch's context could fill the cache with entries that release workflows later restored. The defensive rule is simple: release builds start without caches, or only with caches written by trusted jobs, and their outputs are verified by reproducing them (Section 7.6).

The everyday failures are less dramatic. A stale cache serves results for inputs that changed but were not in the key, for example a system header that came with a new runner image; the build passes in CI and fails on a clean machine. A corrupted cache from a job that was cancelled while saving restores half a directory. The cure for both is the same discipline: keys that name all inputs, tools that verify their own entries (ccache checks, a raw directory copy does not), and a scheduled job that builds main from an empty cache so the clean path is always tested.

6.5Artifacts: between jobs, for people, and for later

Artifacts serve three audiences. Later jobs in the same run need build outputs: framegrab's package job downloads the four build legs' binaries instead of building again. These artifacts can expire within days. People need reports: test results in JUnit XML, which CI systems render as a list of failures; coverage; sanitizer reports; the logs of a failed integration test. They are kept for weeks. The future needs release artifacts and everything required to support them: the packages, the SBOM, the provenance, and the debug symbols. These are kept for as long as the release is supported, which for a vehicle can be fifteen years.

Debug symbols deserve their own plan, because they are needed exactly when something has gone wrong in the field. Release binaries are shipped stripped; the symbols are split off with objcopy --only-keep-debug (debhelper does this automatically into -dbgsym packages) and stored, indexed by the binary's build ID, a hash the linker writes into a .note.gnu.build-id section. A crash report or core dump names the build ID, and the symbols are found without guessing which build it was. debuginfod servers serve symbols and sources by build ID over HTTP; Debian, Ubuntu and Fedora run public ones, and debuggers fetch from them automatically. For the camera box, the team keeps its own symbol server, fed by the release pipeline, because a minidump from a truck a year later is useless without the symbols of that exact build.

Pitfall

Artifacts from a pull request run are built from unreviewed code. Never let a release job download them, and never let anyone install them on shared systems as if they were releases. Only artifacts from the protected main or tag pipeline are candidates for promotion.

7Versions and releases

A release turns one pipeline output into something with a name that people and machines can refer to, compare, trust and reproduce. Most of the craft is in making that name unambiguous and the process boring.

7.1What a version number has to do

A version string has three jobs, and different schemes weight them differently. It must order: a package manager has to decide whether 1.10.0 is newer than 1.9.0 (it is, numerically, though not as text). It may communicate compatibility: SemVer promises that a minor bump does not break users. And it must identify one build exactly, so that a bug report, a crash dump and a registry entry all point at the same bits. The first job is done by machines, which means the ordering rules of every system that will compare your versions matter, and they are not the same.

7.2SemVer, CalVer and the distributions' rules

Semantic Versioning 2.0.0 defines MAJOR.MINOR.PATCH, an optional pre-release after a hyphen (1.0.0-rc.1) that sorts before the release, and optional build metadata after a plus (1.0.0+build.5) that is ignored for ordering. Its compatibility promise and its limits for C++ ABIs are in build 6.4. Calendar versioning uses the date instead (24.04 for Ubuntu, 2025.2 for JetBrains products, 25.1 for pip): it says how old a release is and makes no compatibility promise, which is honest for applications and operating systems that break something in every release anyway.

The trouble starts when a version moves between ecosystems. The experiment compared the same strings with dpkg's, rpm's and Python's (PEP 440) own comparison functions and with a direct implementation of SemVer's precedence rules:

Pitfall

Pick one canonical version per release and derive each ecosystem's spelling from it with tested code: SemVer 1.4.0-rc.1 becomes deb 1.4.0~rc.1-1, rpm 1.4.0~rc.1, PEP 440 1.4.0rc1. Then add a test that sorts a list of past versions in each spelling and checks the order.

7.3Versions from git

A version written by hand in a source file drifts from reality: someone tags v1.4.1 and forgets the file, or edits the file in a branch that is never released. The robust pattern is that the git tag is the version and the build derives everything from it. git describe --tags prints the nearest tag and how far the commit is from it, for example v1.4.0-12-g3f2a9c1: twelve commits after v1.4.0, at commit 3f2a9c1. A release build on the tag gets exactly 1.4.0; a main-branch build gets a development version such as 1.4.1-dev.12+g3f2a9c1 that sorts after 1.4.0, before 1.4.1, and identifies the commit. Tools exist in most ecosystems to do this (setuptools-scm for Python, CMake reading git describe at configure time, Go embedding version-control information in every binary since Go 1.18).

The binary should then report its identity: framegrab --version prints the version, the commit and, for packages, the build ID. The camera box goes further and reports the version of every component in a signed manifest at each start, which is the inventory Uptane relies on (Section 10.5).

Two refinements matter at scale. A CI pipeline usually clones shallowly, and git describe on a shallow clone without tags fails or lies, so the release job fetches tags explicitly. And release tags should be annotated and signed (git tag -s), so that the tag itself is evidence of who declared this commit a release; lightweight tags are just pointers anyone with push access can move, and protected-tag rules on the server should forbid moving release tags at all.

7.4Changelogs, release notes and conventional commits

A changelog is for people who use the software and want to know what changed and whether they need to act. It is not the git log, which is for people who change the software. The "Keep a Changelog" convention groups entries under Added, Changed, Deprecated, Removed, Fixed and Security, with the newest release first and an Unreleased section on top. Release notes add context for one release: what to watch for when upgrading, known issues, migration steps.

Two families of tools generate changelogs. Conventional commits give commit messages a machine-readable prefix (feat:, fix:, feat!: or a BREAKING CHANGE: footer), and tools such as semantic-release and release-please derive both the next SemVer number and the changelog from the commits since the last tag. This works when every commit is a meaningful user-facing change, which trunk-based teams with squash merges come close to. Changelog fragments (towncrier in Python, changesets in JavaScript) instead ask each pull request to add a small file describing its user-visible change; the release collects them. Fragments produce better text, because they are written for users, at the cost of one more thing to review.

Talk track

"Every release has notes written for the people who install it: what changed, what they must do, and what we know is still wrong. They are generated from fragments that each pull request adds, so the notes are ready when the tag is, not written from memory on release day."

7.5Release engineering: cadence, trains and hotfixes

Release management on a branch level, with release branches, cherry-picks from main and the choice between GitFlow and trunk-based development, is in software quality 2.4. The release engineer's question is one level up: when do releases happen, and what decides what is in them?

There are two answers. Feature-driven releases ship when a set of features is done. They feel natural and work badly: the release waits for its slowest feature, the batch grows while it waits, a larger batch has more risk, and more risk makes everyone want to add one more fix before the release, which delays it further. Time-driven releases ship on a calendar, and whatever is ready goes. The extreme is a release train: on a fixed date a release branch is cut from main and stabilised while main moves on; features not ready by the cut wait for the next train, which is never far away.

Trains work because they make releases boring. Chrome and Firefox both ship a major release every four weeks; the Linux kernel releases every nine to ten weeks after a two-week merge window and seven or eight release candidates; Ubuntu ships every six months with a long-term-support release every two years. None of them waits for a feature. Unfinished work is merged dark behind feature flags (software quality 10.3), so main is releasable on any day and the cut is a non-event.

Hotfixes are where processes are tested. The rule that keeps them safe is that a hotfix is a normal change made quickly, not an exception to the process: it is merged to main with review and tests, cherry-picked to the release branch, built by the same pipeline, and released as a patch version. The shortcut of building a hotfix on someone's laptop is how unreproducible, unsigned or untested binaries reach customers, and the shortcut is most tempting exactly when the pressure is highest.

Why it matters

The cost of a release is mostly fixed: notes, signatures, approvals, rollout monitoring. If releases are rare, each one carries many changes and much risk, so the process grows heavier, so releases become rarer. Frequent small releases break that cycle; it is the same argument that makes small pull requests easier to review than large ones.

7.6Reproducible release builds

A build is reproducible when the same source, build environment and instructions produce bit-for-bit identical output; why that matters and the general techniques are in build 6.6. The release-level point is that reproducibility turns "trust our build server" into "check it yourself". If two independent builders produce the same hash, a compromised build server would have had to compromise both.

The experiment shows the most common source of differences and its standard fix. Building the same framegrab deb twice, two seconds apart, gives two different files, because the tar archive inside records each file's modification time. Setting SOURCE_DATE_EPOCH, the convention from reproducible-builds.org, makes dpkg-deb clamp every timestamp to that value:

naive:               f6ccfc64c21a29cd  ba5fdff8f39c830c
SOURCE_DATE_EPOCH:   d202fbb77bfa23c9  d202fbb77bfa23c9
  entry mtime: 2025-11-13 16:00

In a pipeline, SOURCE_DATE_EPOCH is set to the commit time (git log -1 --format=%ct), so it is a property of the source, not of the moment of building. Timestamps are only the first of the usual suspects; the others are file ordering in archives, absolute build paths embedded in debug information (-ffile-prefix-map fixes them), locale and time zone, and parallel build output order. A release pipeline checks reproducibility by building twice in different environments and comparing hashes; Debian runs this check for its whole archive and the large majority of its packages reproduce.

8Signing and trust

A user who installs framegrab is trusting that the file came from the framegrab team and was not changed on the way. Signatures make that checkable. What they prove is narrower than it looks, and how keys are kept and updates are described decides whether the signatures mean anything.

8.1What a signature proves, and what it does not

A signature proves that whoever held a particular private key signed exactly these bytes. Combined with a way to know which key belongs to whom, it gives integrity (the bytes were not changed) and origin (the key holder approved them). It does not prove that the software is correct, safe or even built from the source the user thinks: SolarWinds' malicious update in 2020 was properly signed, because the malware was inserted inside the build before signing (build 11.6). Signing protects the path from the signer to the user; reproducible builds and provenance protect the path from source to signer.

A signature is also only as good as the answer to three questions. Which key should be trusted for this? A key trusted for everything is a key whose theft compromises everything. Is the signed thing current? An old, validly signed version with a known vulnerability is a perfect attack payload. What happens when a key is lost? If there is no plan, the answer is a manual re-installation on every machine. The rest of this chapter is about those three questions.

8.2Signing packages versus signing repositories

Debian and Ubuntu do not normally check signatures on individual .deb files. They sign the repository's index and chain hashes from there, which the experiment reproduced with a local repository, a throw-away key and apt itself:

== link 1: InRelease is signed (gpg --verify) ==
Good signature from "Example Repo Signing <repo@example.org>"
== link 2: InRelease lists the hash of Packages ==
  48e762ef845aaa24781f30391239e34551602f725bb7840c1fde7ec8a15ed84b   main/binary-amd64/Packages
  actual: 48e762ef845aaa24781f30391239e34551602f725bb7840c1fde7ec8a15ed84b
== link 3: Packages lists the hash of each .deb ==
Filename: pool/framegrab_1.4.0-1_amd64.deb
SHA256: 690c22f6d5b54e8b878bb3d5df087f4d1a4791c26f7a2d4e253692548de6ca6e
  actual: 690c22f6d5b54e8b878bb3d5df087f4d1a4791c26f7a2d4e253692548de6ca6e

The design has an elegant property: one signature operation per repository update covers thousands of packages, and the signing key is used rarely. It also has a weakness the next sections address: a captured but validly signed old InRelease could be replayed to hide newer security updates. apt defends with the Valid-Until field, which makes a Release file expire, so a mirror cannot freeze clients on old metadata forever.

The rpm world signs both. Each package carries an OpenPGP signature in its signature header (added by rpmsign), and dnf verifies it before installing when gpgcheck=1; repository metadata can be signed as well (repo_gpgcheck). Per-package signatures let a single .rpm be verified anywhere, for example when copied onto an air-gapped machine. Flatpak signs OSTree commits and the repository summary; snaps are covered by assertions that the store signs; AppImages can embed a signature that almost no one checks.

Pitfall

The old way to add a vendor's key on Debian and Ubuntu, apt-key add, put it into a global keyring trusted for every repository, so the framegrab vendor's key could sign a fake glibc for the Ubuntu archive. apt-key has been deprecated for years. The current practice is a keyring file per repository, referenced by signed-by= in that repository's source entry, so the key is trusted only for that repository, as in the experiment.

8.3Keys: where they live and how they rotate

The private key is the release. Anyone who has it can publish a framegrab that every user's machine will accept, so where it lives matters more than any algorithm choice. Three layers are common. A root or primary key is generated offline, kept offline (on a hardware token in a safe, or split between several people), and used only to certify other keys. Signing keys or subkeys do the daily work and are certified by the root; they live in a hardware security module (HSM) or a cloud key-management service (KMS) that performs signatures on request and never exports the key, and the release job reaches them through OIDC (Section 5.7). Every signature request is logged, so an unexpected signature is at least visible.

Keys should expire, because expiry forces rotation to be practised while it is not an emergency. Debian rotates its archive signing keys with each release; OpenPGP keys carry expiry dates that can be extended by the offline root. The rotation itself needs a plan: clients must learn the new key before the old one stops being used, which for a package repository means shipping the new key in a keyring package signed with the old one, well in advance. For devices the plan must exist before the first device ships, because a camera box that only knows one key can never be told about another if that key is lost. This is the problem TUF's root role solves (Section 8.5).

In practice

Desktop operating systems have their own signing regimes. Windows checks Authenticode signatures from certificates issued by a public CA, and SmartScreen builds reputation per publisher. macOS requires Developer ID signatures and, since macOS 10.15, notarization: the developer uploads the build to Apple, which scans it and issues a ticket that Gatekeeper checks, optionally stapled to the application for offline verification. Both put a certificate authority between the publisher and the user, the same structure as the Web PKI (networking 9.4).

8.4Sigstore: keyless signing and transparency logs

Long-lived signing keys are hard to keep safe, and most open-source projects never managed it: keys sat on laptops, were shared, or were simply absent. Sigstore, an OpenSSF project launched in 2021, removes the long-lived key. The signer proves an identity instead, using the same OIDC tokens as Section 5.7, and every signature is recorded in a public append-only log.

The steps, as in the figure: the release job generates an ephemeral key pair; it sends the public key and its OIDC token to Fulcio, a certificate authority that issues a short-lived X.509 certificate whose subject is the identity from the token (for a CI job, the workflow path and ref); it signs the artifact; and it uploads the signature, certificate and artifact hash to Rekor, a transparency log built on a Merkle tree, receiving a signed proof of inclusion. The private key is then discarded. A verifier runs, for example:

cosign verify \
  --certificate-identity https://github.com/org/framegrab/.github/workflows/release.yml@refs/tags/v1.4.0 \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  registry.example.org/framegrab-ingest@sha256:…

This checks the certificate chain to Fulcio's root, the identity and issuer, the log inclusion, and the signature.

Two properties make this better than it sounds. There is no key to steal, only an identity to impersonate, and impersonating a CI workflow means compromising the repository's release path, which leaves traces. And the log makes every signature public, so a project can monitor Rekor for signatures made with its identity that it did not make, the same idea as Certificate Transparency for TLS certificates. Sigstore now underpins npm package provenance, PyPI's attestations, Kubernetes release signing and GitHub's artifact attestations. Its limit is that it proves which workflow signed, not that the workflow was benign, which is why it is combined with build provenance (SLSA) that records how the artifact was built.

8.5TUF: securing the update process itself

A signed package is not yet a secure update system. An attacker who controls a mirror, or the network, can do much without forging a signature: serve an old, validly signed version with a known hole (a rollback attack); keep serving the same old metadata so the client never learns about the fix (a freeze); combine metadata from different moments into a set that never existed (mix-and-match); or send an endless file. And if the one signing key is stolen, nothing limits the damage. The Update Framework (TUF), from Justin Cappos's group and described in a 2010 paper on surviving key compromise, is a specification of metadata and client rules that defeats these attacks. It is a CNCF graduated project and the basis of Uptane.

The ideas behind the roles are general and worth carrying to any update design. Separate keys by job and risk: the key that must be online to sign fresh timestamps every day is not the key that says which files are valid. Use thresholds for the most important role, so one stolen key is not enough. Make metadata expire, so a frozen client notices. Version everything and never go backwards: the client stores the highest version it has seen of each role and rejects anything lower. Pin hashes and lengths, so a download can be stopped as soon as it exceeds the expected size. And plan key rotation in-band: a new root is signed by the old root's threshold and by its own, so clients can follow a chain of roots instead of being reinstalled.

Interesting detail

TUF also supports delegations: the targets role can hand responsibility for a path pattern to another role with its own keys, for example camera-box/* to the camera team's key. A compromise of that key affects only those files. Python's PyPI has worked on adopting TUF for years; the metadata model is simple, but retrofitting it onto a running ecosystem with existing clients is not.

9Deploying services

A deployment replaces software that is serving users while it serves them. The strategies differ in how many instances change at once, how traffic moves between versions, and how much evidence you collect before the new version reaches everyone.

9.1A deployment changes a running system

For framegrab-ingest the release is a container image, digest-pinned, that already passed the pipeline. Deploying it means that, for some period, the cluster runs old and new instances, load balancers decide which one each request reaches, and the system must keep working the whole time. Four things go wrong in practice. The new version is broken in a way tests did not catch. It is slow to start, so capacity dips while new instances warm up. Old and new versions disagree about data formats or protocols while both are running. And the deployment cannot be undone cleanly because something irreversible happened, usually a database change.

The ideas around deployment as a practice are covered elsewhere: deploy is not release, feature flags separate the two, and canary size is a statistical question (software quality 10.3 and 10.4). This chapter covers the mechanics of the strategies and the failure modes above.

9.2Five strategies

Recreate stops all old instances, then starts new ones. It is the only strategy in which the two versions never run together, which makes it the right choice when they cannot (an exclusive lock on a device, a schema change the old code cannot survive). The price is downtime for as long as start-up takes.

Rolling replaces instances a few at a time and is the default of Kubernetes Deployments. It needs no extra infrastructure and little extra capacity, and it mixes versions for the duration: a user's consecutive requests can reach different versions. Its parameters and failure modes are the subject of Section 9.3.

Blue/green runs a complete second environment (green) beside the live one (blue), tests green with production configuration but no users, then switches all traffic at once, at the load balancer or by changing a Kubernetes Service selector. Rollback is the same switch in reverse, which takes seconds as long as blue is kept running. The cost is double capacity during the switch, and the switch is all-or-nothing: if green is wrong, every user sees it at the same moment.

Canary sends a small share of traffic (one to five percent is common) to the new version and compares its error rates and latencies with the old one before widening, in steps. It gives the strongest evidence with the least exposure, and it needs traffic splitting by weight (a service mesh, an ingress controller, or a controller such as Argo Rollouts or Flagger that automates the steps and the analysis) and good per-version metrics. Shadow or mirroring sends a copy of live traffic to the new version and throws its responses away. No user is exposed at all, which makes it ideal for comparing a rewrite's results or performance with the original; it only works for requests without side effects, or with side effects suppressed, because otherwise the shadow charges the customer a second time.

9.3Rolling updates: surge, unavailability and readiness

A Kubernetes rolling update is controlled by two numbers. maxSurge is how many pods above the desired count may exist during the update; maxUnavailable is how many below the desired count may be not ready. Both default to 25 %. The controller creates new pods while it is under the surge limit, and deletes old pods while the number of ready pods stays at or above the desired count minus maxUnavailable. The word "ready" does the real work: a pod is ready when its readiness probe passes, and until then it receives no traffic and does not count toward availability. A readiness probe that says ready before the application can serve, for example before its caches are loaded, defeats the whole mechanism.

The interactive shows the three-way trade-off. More surge makes the rollout faster at the cost of extra pods, which a cluster without spare capacity cannot schedule. More unavailability also speeds it up, at the cost of serving capacity during the rollout. Slow start-up stretches everything. And the bad-release case shows the rolling update's built-in safety and its limit: because old pods are deleted only when new ones are ready, a version that never becomes ready stops the rollout with at most maxUnavailable pods lost. Kubernetes marks it as failed after progressDeadlineSeconds (600 s by default), but it does not roll back by itself; something or someone must run kubectl rollout undo. A version that becomes ready and then returns errors is not stopped at all, which is what canary analysis is for.

The other end of each pod's life matters as much. When a pod is deleted, it is removed from the Service's endpoints and sent SIGTERM at roughly the same time, and the two travel through different parts of the system. A process that exits immediately on SIGTERM drops requests that load balancers are still sending it. The fix is graceful shutdown: stop accepting new connections, finish in-flight requests, then exit, within terminationGracePeriodSeconds (30 s by default), often with a short preStop sleep so that endpoint removal propagates first.

9.4Two versions at once: skew, schemas and sessions

Every strategy except recreate runs two versions side by side, so version N and version N+1 must be able to coexist. That constrains three things. Interfaces between services must accept both old and new message formats for one release (add fields, never repurpose them; make readers tolerant of unknown fields). Shared state must be readable by both: if 1.5.0 writes a new field into a cache entry, 1.4.0 must not crash when it reads one. And users with sessions may bounce between versions, so session data must be compatible too, or the load balancer must pin sessions for the duration.

Database schemas are the hard case, because a schema change is shared and often irreversible. The standard answer is expand, migrate, contract (software quality 6.3) spread over several releases. Release 1 adds the new column and writes to both old and new (expand); a background job copies old data (migrate); release 2 reads the new column; release 3, after nobody can roll back to release 1, drops the old column (contract). Each step is compatible with the release before it, so every deployment can be rolled back.

9.5Rollback, roll forward and GitOps

When a release is bad, there are two ways out. Rollback redeploys the previous version, which is fast and well-tested, as long as nothing irreversible happened in between; the expand-contract discipline exists to keep that true. Roll forward deploys a new fix instead. It is the only option when rollback is impossible, and it is slower and riskier under pressure, because the fix has had less testing than the version you would roll back to. A good default is: roll back first, then fix calmly.

GitOps turns deployment itself into a version-controlled change. The desired state of the cluster (which image digest runs where, with which configuration) lives in a git repository; a controller in the cluster, such as Argo CD or Flux, continuously compares the cluster with the repository and corrects any difference. Deploying is a merge to that repository; rolling back is a revert; the audit log is the git history; and a manual change to the cluster is undone automatically, which removes a whole class of "someone changed it by hand" incidents. The OpenGitOps principles summarise it as declarative, versioned and immutable, pulled automatically, and continuously reconciled. The release pipeline's last step is then a pull request that bumps an image digest, not a command that touches the cluster, and the CI system never needs credentials for production.

Talk track

"Deployment to production is a merge into the environment repository. Argo CD applies it, Argo Rollouts sends 5 % of traffic to the new version and compares error rate and p99 latency with the old one for fifteen minutes before each step, and aborts automatically if either is worse. Rollback is a revert of the same pull request."

10Over-the-air updates for embedded Linux and vehicles

On a device, the update system is the one piece of software that must never fail, because it is how every other failure gets fixed. Everything in this chapter serves one property: whatever happens during an update, the device ends up running a complete, verified version, old or new.

10.1Why devices are different

Compare the camera box with framegrab-ingest. Nobody can log in to fix a failed update; the next opportunity may be a workshop visit months later, at a cost of tens to hundreds of euros. Power can disappear at any moment, when the ignition is switched off or a battery is changed. The connection is a cellular link that is slow, metered, and drops in tunnels. The fleet is large and diverse: thousands of boxes on several hardware revisions, each with some version history. And in a vehicle, updates are regulated: UN R156 requires a certified software update management system, traceable software identification and safe update conditions (production integration 7.1).

The ECU-level mechanisms are covered in that chapter: flashing microcontrollers over UDS, secure boot with dm-verity, the A/B sequence with boot counters and health checks, and the vehicle-level flow from back end to ECU. This chapter adds what sits around a Linux-based ECU such as the camera box: how its update is packaged, which frameworks implement it, how to make it small enough to send over cellular, how to secure the metadata with Uptane, and how to roll it out to a fleet.

10.2Three ways to update a Linux device

Package-based updates, running apt upgrade or opkg upgrade on the device, are how desktops and servers are updated, and they are a poor fit for unattended devices. Each package's scripts run on the device; a power cut leaves some packages new and some old; and over years, each device becomes a combination of package versions that nobody ever tested together. Image-based updates replace the whole root file system with an image built and tested as one unit, usually into an inactive A/B slot, so the device runs either exactly the old tested image or exactly the new one. That property, "the device runs what we tested", is why image-based updates dominate embedded Linux despite costing twice the storage.

File-tree updates with OSTree sit between the two. OSTree stores files in a content-addressed object repository, much like git, and a deployment is a tree of hard links into that repository. An update downloads only the objects that changed, builds the new deployment beside the old one, and switches the boot entry atomically; the previous deployment stays as a rollback target. It gives image-like atomicity with one partition and file-level deduplication, at the cost of weaker isolation than two physical slots: both deployments share one file system and one object store. Fedora CoreOS and IoT, Endless OS, Toradex's Torizon and Automotive Grade Linux use it, and so does Flatpak (Section 4.3).

10.3Update frameworks and what a bundle contains

Nobody should write the A/B logic, signature checks and boot-counter handling from scratch; several mature open-source frameworks exist and they integrate with Yocto (Linux 8.5), which builds the images.

SWUpdate reads a .swu file, a cpio archive whose first member, sw-description, describes what to install where: images for partitions, files, scripts, bootloader variables, with hardware compatibility checks. It supports A/B and single-copy-plus-rescue layouts, signed and encrypted updates, and delta updates based on zchunk. RAUC (Robust Auto-Update Controller) installs bundles: a squashfs containing the images and a manifest, with a CMS signature appended. Its newer "verity" bundle format protects the squashfs with a dm-verity hash tree, which lets the device stream a bundle over HTTP and verify each block as it arrives instead of downloading the whole bundle first, and supports adaptive updates that fetch only blocks the device does not already have. Both leave rollout and fleet management to a separate server (hawkBit is a common open-source choice). Mender combines a device client for A/B updates with a server for device inventory, deployments and phased rollouts. OSTree-based systems use rpm-ostree, Torizon's update client and similar front ends. Android, the largest embedded Linux fleet, uses its own update_engine with A/B and, since Android 11, virtual A/B with copy-on-write snapshots to avoid doubling storage.

Whatever the framework, the bundle for the camera box has the same parts: the root file system image (squashfs, read-only, with a dm-verity hash tree so secure boot extends to every block read at run time), optionally a kernel and device tree, a manifest naming the target hardware and version, and a signature over all of it. The signature is checked before anything is written, the written slot is read back and hashed, and the bootloader switches only after both checks pass.

Pitfall

An update is complete only when the new version has confirmed itself healthy, not when it has booted. If the health check runs before the application has actually opened the camera and produced frames, an image that boots fine and then fails will be committed, and the fallback slot will be overwritten by the next update. The health criterion must be the service the device exists for.

10.4Delta updates: sending only what changed

A full image for a small embedded system is easily tens of megabytes, and for an infotainment unit gigabytes. Over a metered cellular link to a large fleet that is a real cost and a real delay. Most updates change a small part of the image, so the obvious idea is to send the difference. The experiment measured how much difference "a small part" is, on a 69 MB root file system of 832 files where one release changes 19 files: a patch release of one large library (the numpy wheel from 2.1.0 to 2.1.1, whose 10.5 MB shared object changed) and a rebuilt application binary.

The numbers carry three lessons. A delta between versions of the same code is tiny: bsdiff described the change in 53 KB, about 370 times smaller than the full compressed image, because a patch release of a library changes few instructions and bsdiff is designed for shifted but similar binaries. Even the 14 KB application binary, rebuilt with a new version string, needed only 201 bytes. Second, compression destroys similarity: a small change in the input changes every compressed byte after it within the block, so a diff of two compressed images is more than fifty times larger than a diff of the uncompressed ones. Delta systems therefore diff the uncompressed content and compress the patch, or diff block by block with knowledge of the format. Third, a file-level delta (send the changed files, compressed) is a simple middle ground at 2.5 MB: no binary diffing, but every changed file is sent whole.

Deltas have costs that the numbers hide. A delta applies only to one exact source version, so a fleet spread over five versions needs five deltas or a fallback to the full image. Applying a binary delta needs memory and CPU on the device, and the result must be verified against the expected hash of the full target image, because a delta applied to a slightly different base produces a wrong image. Chunk-based schemes avoid exact-version deltas altogether: casync and desync split images into content-defined chunks and fetch only chunks the device lacks, from whatever version it has; RAUC's adaptive updates and OSTree's object fetching work on the same principle.

Interesting detail

Executables are a hard case for naive diffing because inserting a few instructions shifts every address after them, and every instruction that refers to a shifted address changes. bsdiff (Colin Percival, 2003) copes by encoding "this region is like that region, plus small byte differences". Google went further for Chrome: Courgette and its successor Zucchini disassemble the executable, diff it at the level of instructions and references, and reassemble it on the client, which made Chrome's updates several times smaller.

10.5Uptane: TUF for vehicles

A vehicle is not one device but dozens of ECUs, most of them unable to reach the internet, some too small to check a modern signature, all of them updated through a central telematics or gateway unit. Uptane adapts TUF (Section 8.5) to that structure. It began as a research project of NYU, the University of Michigan Transportation Research Institute and the Southwest Research Institute, was first published as a standard in 2019 through IEEE-ISTO, and is maintained by the Uptane project under the Linux Foundation's Joint Development Foundation.

The central idea is to split the decision in two. The image repository holds TUF metadata for every image the OEM has approved, signed with offline keys; it says what is valid for which hardware. The director repository decides which images a particular vehicle should install, based on the vehicle's reported inventory; it must be online to do this, so its keys are online and more exposed. The primary ECU downloads both sets of metadata and checks that the director's instructions name images that the image repository also lists, with matching hashes and lengths; it then distributes the images to secondary ECUs. Secondaries that can afford it repeat the full verification themselves; small ones perform partial verification, checking only the director's targets metadata, which still detects an image that the primary altered. Each ECU signs a report of what it runs, and the primary sends the collected vehicle version manifest back, which is how the director knows the fleet's real state.

The design keeps TUF's properties (expiring, versioned metadata, rollback protection, threshold signatures and in-band key rotation) and adds two that vehicles need: per-vehicle targeting without trusting the online system completely, and verification on ECUs that cannot do everything themselves. Open-source implementations exist (aktualizr, used by Automotive Grade Linux and Toradex Torizon), and several OEMs and suppliers use Uptane-based systems; it fits naturally into the software update management system that R156 asks for.

10.6Rolling out to a fleet

The canary idea of Section 9.2 applies to fleets with longer time scales and higher stakes, because a bad update cannot be undone in minutes. A phased rollout widens in steps, with a health gate before each one.

The gates compare the updated group with the rest, not with an absolute threshold: install success rate, number of automatic rollbacks, boot time, application crashes and resets, diagnostic trouble codes, and the function's own health signal (for the camera box, frames delivered per hour). Comparing against vehicles still on the old version removes effects of season, weather and usage that would otherwise look like regressions. The selection of each phase matters too: it should cover every hardware revision and region early, and avoid putting all of one customer's vehicles in the first phase. Updates are also gated by vehicle state, the conditions R156 requires: parked, ignition in the right state, enough battery charge for the worst-case install time, and the driver informed where needed.

When a gate fails, the rollout is halted, not reversed: vehicles already on 1.4.1 stay there unless their own health check rolled them back, and the rest stay on 1.4.0 until a fixed 1.4.2 starts a new rollout. Rolling the fleet back deliberately is itself an update, with all its cost and risk, and anti-rollback counters may forbid it for security fixes (production integration 7.5). This is the deepest difference from services: on a cluster, rollback is the cheap default; on a fleet, the cheap default is to stop.

Why it matters

The whole chain of this chapter meets here. A camera-box release is built once by the pipeline, versioned from its tag, reproducible, signed through a KMS key the release job reaches by OIDC, described by Uptane metadata, packaged as a verity bundle with a delta for each common source version, installed into the inactive slot, confirmed by the device's own health check, and widened across the fleet only as the evidence comes in. Each link can be explained on its own; the value is that no link is missing.

QSelf-check questions

Q.1Core questions

What three things does every package format carry, and why is a package database needed?Basic

Files with their paths and permissions, metadata including dependency relations, and scripts that run at install, upgrade and removal. The package manager records which package owns each file; that record is what makes clean removal, upgrade (knowing which old files to delete) and conflict detection possible. Without it, the file system is the only record, and it cannot tell whose file is whose.

What are the three members of a .deb, and where does its Depends line usually come from?Basic

An ar archive with debian-binary (the format version "2.0"), control.tar (metadata, maintainer scripts, checksums, conffiles) and data.tar (the payload). The library dependencies are computed by dpkg-shlibdeps from the binary's NEEDED entries and the libraries' symbols files, which map each used symbol version to a minimum package version; for framegrab that gave libc6 (>= 2.34) and zlib1g (>= 1:1.2.0).

How do rpm requirements differ from deb dependencies?Intermediate

rpm generates requirements on capabilities rather than package names, at the granularity of symbol versions: libc.so.6(GLIBC_2.34)(64bit), libz.so.1(ZLIB_1.2.0)(64bit), /bin/sh for scriptlets. Packages declare what they provide, and the resolver matches capabilities, so packages can be renamed or split without breaking dependants. Debian expresses library needs as package names with minimum versions.

In which order does rpm run scriptlets during an upgrade, and what bug does it cause?Intermediate

The new package's %pre and %post run first, then the old package's %preun and %postun. Each receives the number of versions that will remain: 1 or more on upgrade, 0 on removal. A %postun that removes a user, a directory or a service without checking that the count is 0 does so on every upgrade, right after the new version set it up.

Why must maintainer scripts be idempotent and non-interactive?Basic

A failed upgrade is retried, so the same configure step can run twice and must give the same result. Packages are installed by automation and unattended upgrades with nobody at a terminal, so questions block or fail; configuration choices go through debconf, which can be pre-seeded.

Why does a binary built on Ubuntu 24.04 fail on Debian 11, and how do you fix it?Basic

The linker records glibc symbol versions, and the 24.04 build binds __libc_start_main@GLIBC_2.34; Debian 11 has glibc 2.31, so the loader reports "version GLIBC_2.34 not found". glibc is backward but not forward compatible, so build on the oldest system you support (or a sysroot from it), link statically against musl, or ship a container or image that contains the user space.

Why is a statically linked glibc binary not fully self-contained?Intermediate

Name lookups (getaddrinfo, getpwnam) go through NSS, which loads plug-in libraries with dlopen at run time according to nsswitch.conf; those must come from the same glibc version used for linking. iconv and some locale handling behave similarly. The linker warns about it. musl avoids the problem by having no NSS and its own DNS resolver.

What does $ORIGIN do in a RUNPATH, and what must never be bundled?Intermediate

The loader replaces $ORIGIN with the directory of the binary, so RUNPATH=$ORIGIN/../lib finds libraries shipped next to the program wherever it is installed. glibc and the dynamic loader must come from the host (the loader path is absolute and kernel-loaded), and so must GPU driver libraries (libGL, EGL, Vulkan), which must match the kernel driver; libraries that speak changing system protocols are usually better taken from the host too.

How does an AppImage start, and what does it require from the host?Basic

It is an ELF runtime followed by a squashfs image. The runtime finds the offset where the image starts, mounts it read-only with FUSE under /tmp/.mount_*, and runs AppRun, which starts the program with its bundled libraries. The host must provide a glibc at least as new as the build baseline, FUSE (libfuse2 for old runtimes, only the kernel module and fusermount for static ones), GPU drivers and desktop services. There is no sandbox.

What is a Flatpak runtime, and how does a Flatpak application get access to a user's file?Intermediate

A runtime is a versioned, shared set of base libraries (org.freedesktop.Platform, GNOME, KDE) mounted at /usr in the sandbox; applications bundle only what it lacks, and OSTree deduplicates identical files. File access goes through the file-chooser portal on the host: the user picks a file, and only that file is made available to the sandbox, instead of granting the whole home directory.

What are snap channels and confinement levels?Basic

A channel is a track plus a risk level (stable, candidate, beta, edge), such as 1.4/stable; users follow a channel and snapd refreshes automatically. Strict confinement uses AppArmor, seccomp and device cgroups generated from declared interfaces; classic means no confinement, granted by the store for tools that need the whole system; devmode is for development.

What determines the wall-clock time of a pipeline?Basic

The critical path, the longest chain of dependent jobs, provided enough runners are free to run everything else in parallel. With too few runners, jobs queue and the queue lengthens the run: the chapter's model goes from 28.5 to 42 minutes when eight runners become two, with the same 75 runner-minutes of work.

What problem does a merge queue solve that required checks alone do not?Intermediate

Semantic conflicts between pull requests that were each tested against an older main: A renames a function, B adds a call to the old name, both are green, together they do not build. A merge queue tests the exact commit main would become, including changes queued ahead, and merges only if it passes, keeping main green.

What is the difference between a cache and an artifact?Basic

A cache is an optimisation keyed by inputs; it may be evicted and the job must still produce the same result without it. An artifact is a product with an identity, a retention period and provenance, passed between jobs or published. Passing build outputs through caches, or using artifacts as caches, causes wrong or wasteful builds.

How do you design a cache key for a compiler cache?Intermediate

Encode everything that changes the output except the fine-grained source: operating system, compiler and version, a hash of the lockfile, then the commit, so each run saves a new entry. Add restore keys that drop the commit, then the lockfile hash, so a new commit restores the newest compatible cache. Leave out timestamps and run numbers, and set the cache's base directory so paths do not differ between runners.

Why does 1.0.0-rc.1 sort after 1.0.0 in dpkg, and what is the fix?Intermediate

In a Debian version the last hyphen separates the upstream version from the Debian revision, so 1.0.0-rc.1 is upstream 1.0.0 with revision "rc.1", which is greater than 1.0.0 with no revision. The tilde sorts before everything, including the end of the string, so 1.0.0~rc.1 < 1.0.0 in both dpkg and rpm (since 4.10).

How does apt protect thousands of packages with one signature?Intermediate

The repository's InRelease file is signed; it lists the hash of each Packages index; each Packages index lists the hash of each .deb. apt verifies the signature with the key named by signed-by, then checks each hash in the chain. In the experiment, one changed byte in a .deb gave "Hash Sum mismatch" and one changed byte in InRelease gave BADSIG.

What does Sigstore's keyless signing replace, and what does a verifier check?Advanced

It replaces a long-lived signing key with an ephemeral key bound to an OIDC identity by a Fulcio certificate valid for about ten minutes, and records the signature in the Rekor transparency log. A verifier checks that the certificate chains to Fulcio, names the expected identity (for CI, the workflow and ref) and issuer, that the log contains the entry, and that the signature was made while the certificate was valid.

Name the four TUF roles and what each protects against.Advanced

Root (offline, threshold) names the keys of all roles and allows key rotation and recovery from compromise. Timestamp (online, short expiry) names the current snapshot and prevents freeze attacks. Snapshot names the current version of every targets file and prevents mix-and-match. Targets lists hashes and lengths of files and prevents tampered or endless downloads; delegations limit how far a key reaches. Monotonic version numbers prevent rollback.

Compare recreate, rolling, blue/green, canary and shadow deployments in one sentence each.Basic

Recreate stops old then starts new: simple, never mixes versions, has downtime. Rolling replaces instances in batches: little extra capacity, versions mixed during rollout. Blue/green switches all traffic to a fully prepared second environment: instant rollback, double capacity, all users switch at once. Canary sends a small share to the new version and widens on evidence: least exposure, needs traffic splitting and metrics. Shadow mirrors traffic to the new version and discards its responses: no user exposure, only for side-effect-free requests.

What do maxSurge and maxUnavailable control in a rolling update?Intermediate

maxSurge is how many pods above the desired count may exist, maxUnavailable how many below it may be not ready. The controller creates new pods within the surge and deletes old pods only while ready pods stay at or above desired minus maxUnavailable. More surge is faster but needs spare capacity; more unavailability is faster but reduces serving capacity; with surge 1 and unavailability 0, capacity never drops.

Why are image-based updates preferred for embedded Linux over package upgrades?Basic

An image is built and tested as one unit and written to an inactive slot, so after any interruption the device runs exactly the old or exactly the new tested image. In-place package upgrades run scripts on the device, can be interrupted half way, and over time leave each device with a combination of versions nobody tested.

What is in a RAUC verity bundle, and why does the verity format matter?Advanced

A squashfs with the images and a manifest, protected by a dm-verity hash tree, plus an appended CMS signature over the manifest and hash tree root. Because every block can be verified on its own against the signed root hash, the device can stream the bundle over HTTP and check each block as it arrives, and adaptive updates can fetch only the blocks it lacks.

Explain Uptane's director and image repositories.Advanced

The image repository, signed with offline keys, lists every approved image with hashes and target hardware. The director repository, with online keys, tells a specific vehicle which images each ECU should install. The primary ECU installs only images named by the director that the image repository also lists with matching hashes, so compromising either repository alone cannot install arbitrary software. Secondaries verify fully or, if small, partially (director metadata only).

Q.2Why and what if

Why do distributions want one version of each library, and what does that cost?Why

One copy means one place to fix a vulnerability: a zlib update reaches every program at once, and disk and memory are shared. The cost is that applications needing different incompatible versions conflict, and applications are tied to the distribution's release cycle, which is what application formats and containers work around.

Why is static linking attractive for Go and Rust tools but awkward for C++ GUI applications?Why

Go (without cgo) and Rust on musl link their whole world statically and need only the kernel, so one binary runs on any Linux. A GUI application must load GPU driver libraries and talk to desktop services from the host, glibc's NSS does not work statically, and the vendor must rebuild and re-ship for every vulnerability in any bundled library.

What if your AppImage bundles an old libstdc++ and the host's GPU driver needs a newer one?What if

The driver's libraries are loaded into the same process and need symbol versions your bundled libstdc++ lacks, so loading fails or the process aborts. That is why bundling libstdc++ is conditional: some AppImage runtimes compare versions at start and use the host's if it is newer, and tools exclude it unless needed.

Why optimise the critical path rather than the average job time?Why

Jobs off the critical path finish while the critical chain is still running, so making them faster does not change when the pipeline finishes. Only shortening the longest dependent chain (caching it, splitting it, moving it to faster runners) shortens the wait, assuming enough runners; if jobs queue, adding runners is the fix instead.

What if a workflow triggered by pull_request_target checks out and builds the pull request's code?What if

The workflow runs with the base repository's secrets and write token, and the pull request's build scripts are arbitrary code from whoever opened it, so that person can read the secrets or push to the repository. Builds of untrusted code must use the pull_request event without secrets; pull_request_target is for metadata tasks that never execute the pull request's content.

Why pin CI actions by commit SHA rather than by version tag?Why

A tag is a movable pointer; an attacker who compromises the action's repository can move v4 to malicious code, as happened with tj-actions/changed-files in March 2025, and every workflow using the tag runs it at once. A full commit SHA names immutable content, and updates arrive as reviewable pull requests from Dependabot or Renovate.

What if a release build restores a cache written by an untrusted job?What if

Whatever the untrusted job put in the cache can end up in the release: a poisoned object file or dependency is reused without being rebuilt, and the release is signed with your key. Release builds should start without caches or only with caches from trusted scopes, and reproducing the build independently detects the difference.

Why are time-based release trains usually better than feature-based releases?Why

A feature-based release waits for its slowest feature, grows while it waits, and becomes riskier, which invites more delay. A train has a fixed date and takes whatever is ready; a missed feature waits a few weeks for the next train. Releases become small, frequent and routine, and unfinished work stays dark behind flags.

What does a valid signature not tell you, and what covers that gap?Why

It does not say that the signed code is what the source repository contains or that it is benign: a compromised build machine produces properly signed malware, as in SolarWinds. Reproducible builds let independent parties confirm the binary matches the source, and build provenance (SLSA attestations) records which source, builder and steps produced it.

What if your only signing key for a device fleet is lost or stolen?What if

If devices trust only that key, a stolen key lets an attacker sign updates they will accept, and a lost key means you can never update them again; either way the fix is a workshop visit per device. The design answer, before shipping, is a root of trust that can rotate other keys in-band (TUF/Uptane root role with thresholds and offline keys) and several provisioned keys.

What if a rolling update deploys a version whose pods become ready but return errors?What if

The rolling update sees ready pods and completes, replacing every old pod; all users get errors. Readiness only checks the probe. Protection comes from canary analysis that compares the new version's error rate and latency with the old one and aborts, and from making readiness probes check real dependencies.

Why must version N and N+1 of a service be compatible, and how do you change a database column safely?Why

Every strategy except recreate runs both versions together, and rollback runs the old version against whatever the new one wrote. A column change is done with expand, migrate, contract across releases: add the new column and write both, backfill, switch reads, and drop the old column only when no deployable version uses it.

Why is a diff of two compressed images so much larger than a diff of the uncompressed content?Why

Compression makes each output byte depend on preceding input, so a small change alters the rest of the compressed block or stream and similar inputs produce dissimilar outputs. In the experiment bsdiff gave 3 MB for compressed squashfs images and 53 KB for uncompressed tar images. Delta systems diff uncompressed content or work block by block.

What if the device's health check runs before the application has done its real job?What if

An image that boots but cannot, for example, open the camera is committed as good, the boot counter is reset, and the previous slot becomes the target of the next update, losing the fallback. The health criterion should be the function the device exists for, with a time window long enough to observe it.

Why does a fleet rollout halt instead of rolling back when a gate fails?Why

A rollback across a fleet is itself an update with all its cost, time and risk, may be forbidden by anti-rollback counters for security fixes, and takes days to reach every vehicle. Halting limits damage to the vehicles already updated, whose own health checks roll back individually if needed, and a fixed version then starts a new rollout.

When would you choose OSTree over two-slot A/B for a device?Why

When storage is tight and updates are frequent: OSTree keeps both versions in one partition with file-level deduplication and fetches only changed objects, giving atomic switches and rollback without doubling storage. Two physical slots give stronger isolation (a corrupted file system cannot affect the other slot) and suit devices where that matters more than space.
