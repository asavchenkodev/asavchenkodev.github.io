Game engines and real-time game programming

How a game engine turns a while-loop into a world that updates sixty times a second: the game loop and fixed timesteps, entity component systems and data-oriented design, physics and collision, transform hierarchies and animation, the engine side of rendering, input, events and assets, memory pools, and determinism and networking for multiplayer. The chapter builds a tiny engine step by step, a small top-down arena game with four players and a few thousand projectiles, and compares each decision with Unreal, Unity, Godot and Bevy. Measurements come from small C++ and Python experiments run for this chapter.

1The big picture: what a game engine is for

A game is a simulation that has to produce a new, consistent picture of its world every 16.7 milliseconds, react to a player within a few frames, and never stutter. A game engine is the reusable machinery that makes this possible, so that a game team can spend its time on the game and not on the loop, the memory, the physics and the renderer.

1.1A game is a real-time simulation with a frame deadline

Most software is judged by throughput or by average response time. A game is judged by its worst frame. At 60 frames per second the whole world, every character, projectile, sound and particle, must be advanced and drawn in 16.7 ms; at 120 Hz in 8.3 ms; a virtual-reality headset at 90 Hz gives 11.1 ms and makes people feel ill when frames are missed. A frame that takes 40 ms instead of 16 is not "a bit slower on average", it is a visible hitch that players notice and reviewers write about. Game programming is therefore soft real-time programming: nobody dies when a deadline is missed, but the product is measured by how rarely it happens.

The second property is that the world is a simulation with state. The arena game of this chapter holds four players, a few hundred enemies and up to a few thousand projectiles, each with a position, a velocity, a health value, an animation state and a sound. Every frame the engine reads input, advances that state by a small step of time, resolves collisions, and then turns the state into a picture. The same state is shared by many subsystems that each want it in a different shape: physics wants bodies and shapes, the renderer wants meshes and materials sorted by state, the audio mixer wants emitters with positions, the network wants a compact snapshot. Much of engine architecture is the question of who owns which part of that state and how it flows between subsystems within one frame.

The third property is scale of content. A modern game ships gigabytes of meshes, textures, animations and sounds made by artists in other tools. The engine must import them, convert them into formats the target device can load quickly, stream them in and out while the player moves, and let designers change them without a programmer. That is why the editor and the asset pipeline are a large part of every engine, often more code than the runtime itself.

Why it matters

The patterns that make games run at a stable frame rate, fixed-rate loops, frame budgets, no allocation inside the frame, data laid out for the cache, work split into jobs with explicit dependencies, deterministic replay, are the same patterns that make any latency-bound system predictable: trading engines, robotics, camera pipelines, audio processing. Games are simply the field where they were pushed hardest and documented most openly.

1.2Building an engine from a while-loop

The clearest way to understand an engine is to start with the smallest program that could be a game and watch each subsystem appear because something breaks without it. The smallest game is a loop that reads input, updates the world and draws it:

while (running) {
    pollInput();          // keyboard, mouse, gamepad
    update();             // move the player, the enemies, the bullets
    render();             // draw everything
}

This loop runs as fast as the machine allows, so the game is twice as fast on a computer that is twice as fast. The first fix is to measure the time each frame took and scale every movement by it, which brings in a timer and the idea of a timestep (Section 2). Moving by "speed times elapsed time" makes physics depend on the frame rate, so the next fix is a fixed timestep for the simulation with interpolation for drawing. As the number of objects grows, a class hierarchy of game objects becomes rigid and slow, and the world is reorganised into components and eventually an entity component system with data stored by type (Section 3, Section 4).

Bullets must hit things, so a collision system appears, and because testing every pair is quadratic it needs a broad phase that finds candidate pairs quickly; stacked crates must rest on each other, which needs a constraint solver (Section 5). Characters have arms and legs that move together, which needs a transform hierarchy and skeletal animation (Section 6). Drawing ten thousand objects one by one is too slow, so the renderer gets culling, sorting and batching, and moves to its own thread (Section 7). Loading a level from disk freezes the game, so asynchronous loading and a resource system with handles appear; allocating and freeing memory every frame causes stalls and fragmentation, so pools and frame arenas appear; one core is not enough, so a job system appears (Section 8). Finally a second player wants to join over the internet, which needs replication, prediction and, for some genres, a deterministic simulation (Section 9).

Each of these subsystems is an answer to a concrete failure of the simple loop. Engines differ mainly in how they answer, and the comparison in Section 10 follows the same order.

1.3The layers of an engine runtime

Once all these pieces exist, they settle into layers, shown in Figure 1.1. At the bottom, the platform layer hides the operating system: windows and the swap chain, files, threads, the high-resolution clock, input devices and the GPU device. Porting an engine to a new console or phone mostly means rewriting this layer. Above it, the core provides what every other part uses: allocators, containers, vector and quaternion math, logging, profiling markers and the job system. Engines usually write their own containers and allocators rather than using the standard library, mainly to control allocation and memory layout precisely.

The resource layer knows every asset by a stable identifier, loads it asynchronously and hands out handles. The world layer holds the game state: entities and components (or a tree of objects), the transform hierarchy, events and the gameplay code. Above the world sit the simulation subsystems, physics, animation, AI and navigation, audio and networking, each reading and writing parts of the world. At the top, the presentation subsystems turn state into output: the renderer, the user interface and the audio output. Beside all of this stands the tools side: the editor, importers, per-platform cookers, profilers and the build pipeline. A shipped game contains only the runtime column; the studio works mostly in the tools column.

Interesting detail

The split between "engine" and "game" is not where most people expect. In Unreal, Unity and Godot the gameplay framework itself, player controllers, cameras, game modes, input mapping, is part of the engine, and a typical game adds its own systems on top. Large studios often keep a proprietary engine (Frostbite at EA, Decima at Guerrilla, id Tech at id Software) because the tools and the content pipeline, not the renderer, are what lets hundreds of artists work in parallel.

Talk track

"An engine is a fixed-rate simulation loop plus the machinery around it: memory and jobs at the bottom, a resource system for assets, a world of entities and components in the middle, physics, animation, audio and networking on top of the world, and a renderer that turns the world into a frame. Most of the engineering is about keeping every frame inside its budget and about moving data efficiently between those subsystems."

1.4Four engines that frame the comparison

The chapter compares each subsystem with four engines that represent four different philosophies. Unreal Engine (Epic Games, C++ with the Blueprint visual language) is the high-end engine with the most complete feature set: a deferred renderer with virtualised geometry (Nanite) and dynamic global illumination (Lumen), its own Chaos physics, a mature networking layer, and source code available to licensees. Unity (C# gameplay code on a C++ core) became the most widely used engine for mobile and independent games because of its fast iteration and broad platform support; it has a classic GameObject model and, since 2023, a production data-oriented stack called Entities (part of DOTS). Godot (C++ core, its own GDScript language plus C# and native extensions, MIT licence) is the open-source engine with a tree of nodes as its object model and a deliberately small, readable code base. Bevy (Rust, MIT/Apache licence) is a younger, pre-1.0 engine in which everything, including the renderer and the user interface, is built on an entity component system.

The comparison is not a ranking. Each engine made coherent choices for its audience, and seeing the same problem solved four ways is the fastest route to understanding why the problem is hard.

2The game loop and time

The loop decides when the world advances and by how much. Getting this wrong makes a game run at different speeds on different machines, makes jumps higher at low frame rates, and makes physics explode; getting it right is a dozen lines of code that every engine contains in some form.

2.1Variable timestep: scale everything by the frame time

The first fix to the naive loop is to measure how long the last frame took, call it dt, and advance everything by that much time: position += velocity * dt. The game now runs at the same speed on fast and slow machines, which is why many simple games and many gameplay scripts still work this way. Unity's Update() receives Time.deltaTime, Godot's _process(delta) and Unreal's Tick(DeltaSeconds) do the same.

The problem is that numerical integration is only approximately right, and the error depends on the step. The experiment in integrators.py simulates a jump with an upward speed of 5 m/s under gravity, whose exact apex is 1.274 m. With the integration order many beginners write, position first and then velocity (explicit Euler), the apex is 1.359 m at 30 Hz, 1.316 m at 60 Hz, 1.292 m at 144 Hz and 1.285 m at 240 Hz. A player on a 30 Hz machine jumps 6.6 % higher than the true value and 5.8 % higher than a player at 240 Hz, enough to reach a ledge the level designer meant to be out of reach. With the order engines use, velocity first and then position (semi-implicit Euler), the error has the opposite sign, −6.5 % at 30 Hz, but it still depends on the frame rate.

Frame-rate dependence is the mild problem. The serious one is stability: stiff springs, stacked bodies and fast collisions need a small step, and a single long frame, a disk stall or a window being dragged, can produce a step of 200 ms in which objects pass through walls or springs gain energy and explode. Variable steps also make the simulation impossible to reproduce, because two runs never see the same sequence of dt values.

2.2Fixed timestep with an accumulator

The standard answer, popularised by Glenn Fiedler's article "Fix Your Timestep!" (2004), separates simulation time from wall-clock time. The simulation always advances in steps of exactly dt, for example 1/60 s. The loop measures how much real time has passed, adds it to an accumulator, and runs as many fixed steps as the accumulator allows. Whatever is left over, less than one step, stays in the accumulator for the next frame:

constexpr double dt = 1.0 / 60.0;        // simulation step, never changes
double acc = 0.0;
State previous = world, current = world;
auto last = Clock::now();
while (running) {
    auto now = Clock::now();
    double frame = std::min(seconds(now - last), 0.25);   // clamp after a long stall
    last = now;
    acc += frame;
    pollInput();
    while (acc >= dt) {                   // zero, one or several steps per frame
        previous = current;
        simulate(current, dt);
        acc -= dt;
    }
    double alpha = acc / dt;              // how far we are between two steps
    render(interpolate(previous, current, alpha));
}

Three things happen here. First, physics and gameplay now behave identically on every machine and every run with the same inputs, because they only ever see the same dt. Second, a frame can contain zero steps (a 144 Hz display with a 60 Hz simulation draws more frames than it simulates) or several steps (a 30 Hz frame needs two). Third, because the rendered frame usually falls between two simulation steps, the renderer interpolates between the previous and the current state using alpha. Without interpolation, objects visibly stutter: on a 144 Hz display some frames would show the same simulation state twice and others would jump ahead.

Interpolation costs one step of latency, because the renderer shows a state between the last two steps rather than the newest one. The alternative, extrapolating forward from the current state, has no extra latency but shows wrong positions when something collides or changes direction. Most engines interpolate rigid bodies and let the camera and the player's own character use the latest state.

Numbers

Default fixed steps: Unity's FixedUpdate runs at 50 Hz (0.02 s), Godot's physics at 60 ticks per second with at most 8 steps per frame, Bevy's FixedUpdate schedule at 64 Hz. Unreal ticks physics with the frame by default and offers optional substepping and, in Unreal Engine 5, an asynchronous fixed-rate physics mode.

2.3The spiral of death, and why the accumulator is clamped

The fixed-step loop has one dangerous failure. If one simulation step costs more real time than the time it simulates, for example a step that simulates 16.7 ms takes 18 ms of CPU, then each frame owes more steps than the previous one, takes even longer, and owes still more. The game freezes within a second. This is the spiral of death, and every fixed-step loop has a guard against it: a cap on the number of steps per frame, or a clamp on the time added to the accumulator, as in the std::min(…, 0.25) above. When the cap is hit the leftover time is thrown away and the game runs in slow motion instead of freezing, which is the lesser evil.

Figure 2.1 runs the loop above in a model. Each grey box is a frame on the wall clock; inside it, teal blocks are fixed steps and the amber block is rendering. The middle lane shows how many steps each frame ran, and the red line is the time owed at the start of each frame.

The model (experiments/check_interactive.js) shows the numbers behind the picture. With a 60 Hz simulation, a 60 fps display and ±30 % frame-time jitter, 48 of 60 frames run exactly one step, six run none and six run two; interpolation is what hides that unevenness. At 144 fps, 35 of 60 frames run no step at all. At 30 fps most frames run two steps. When a step costs 18 ms and there is no cap, the 17th frame already lasts more than 100 ms and the 60th lasts 3.5 s and needs 196 steps. With a cap of four steps the frames stay below 75 ms and the game runs at 90 % of real speed.

Pitfall

Putting gameplay logic in the variable-rate update and physics forces in the fixed one, then reading input only in the variable one, loses inputs: a button pressed and released within one frame that ran zero fixed steps never reaches the physics. Engines document this (Unity: read input in Update, apply forces in FixedUpdate); the robust fix is to buffer input events and consume them in the fixed step.

2.4The frame as a pipeline: game thread, render thread, GPU, display

On a single thread a frame would run input, simulation, render preparation and GPU submission in sequence, and the GPU would sit idle while the CPU simulates. Engines therefore pipeline frames, as in Figure 2.2. While the game thread simulates frame N+1, a render thread turns frame N into GPU commands, the GPU executes frame N−1, and the display scans out an even older frame. Unreal has a game thread, a render thread and an RHI thread that talks to the graphics API; Bevy extracts the render-relevant data into a separate render world at the end of each update and renders it in parallel with the next update; Unity runs its render loop on a render thread when the platform supports it.

Pipelining buys throughput with latency. In the figure an input sampled at the start of frame N appears on screen about 57 ms later, between three and four refresh intervals. For a strategy game that is fine; for a fighting game or a competitive shooter it is not, and engines and drivers add low-latency modes that delay the start of the game frame so that input is sampled as late as possible, or limit how many frames the CPU may queue ahead of the GPU. The same trade-off, throughput through buffering against latency through short queues, appears in camera pipelines; the vsync and frame-pacing side is covered in GPU programming for surround view 14.4.

In practice

Teams measure frame time, not frames per second, because frame time adds up and FPS does not: going from 16 ms to 20 ms costs 4 ms, while "60 to 50 FPS" hides that. They track the 99th-percentile frame time and count hitches over a threshold, and they budget the frame per subsystem (for example 4 ms gameplay, 3 ms physics, 2 ms animation, 5 ms render thread at 60 Hz). Frame profilers such as Tracy, Unreal Insights, the Unity Profiler, PIX, Superluminal or RenderDoc for the GPU show each frame as a timeline of named scopes on every thread.

Talk track

"The simulation runs in fixed steps from an accumulator so that physics is stable and reproducible; the renderer interpolates between the last two steps so motion stays smooth at any display rate. The accumulator is capped to avoid the spiral of death. Frames are pipelined across the game thread, render thread and GPU for throughput, which costs two to three frames of input latency that low-latency modes try to win back."

3Game objects: from inheritance to components to ECS

Every engine must decide what a "thing in the world" is in code. The answer has moved over twenty years from class hierarchies to components attached to objects to entity component systems, and each step was driven by the same two pressures: designers need to combine behaviours freely, and the CPU needs data it can stream through its caches.

3.1Why the inheritance tree broke

The first instinct of an object-oriented programmer is a class hierarchy: a GameObject base class, a Movable subclass, Character and Vehicle below it, Player and Enemy below Character, as in panel A of Figure 3.1. It works for the first prototype. Then a designer asks for an enemy that can drive a vehicle, a turret that is static but shoots like a character, a projectile that can be picked up. Each request either duplicates code in another branch or moves shared code upward until the base class becomes a "blob" with hundreds of fields and virtual functions that most objects do not use. Single inheritance forces one classification on things that have many independent aspects; multiple inheritance brings diamond problems instead.

The hierarchy is also slow, which matters as soon as there are thousands of objects. Each object is a separate heap allocation in an unpredictable place, each update is a virtual call through a pointer, and the hot data (position and velocity) is mixed with cold data (names, configuration) in the same cache lines. Section 4 measures what that costs.

3.2Composition: objects made of components

The first fix, widely adopted in the 2000s and still the default model of Unity, Unreal and Godot, is composition. A game object is a container, and behaviour comes from the components attached to it: a transform, a mesh renderer, a rigid body, a health component, an AI script (panel B). An enemy that drives a vehicle is simply an object with both sets of components. Designers can build new kinds of objects in the editor without new classes, which is the main reason the model won.

The engines spell it differently. In Unity a GameObject holds Components, and gameplay code is written as MonoBehaviour components with Update, FixedUpdate and LateUpdate methods the engine calls every frame. In Unreal an AActor holds UActorComponents, scene components form the actor's transform hierarchy, and both actors and components can tick, in tick groups ordered around physics. Godot takes composition further: there are only nodes, a node's children are its components, and a scene is a saved tree of nodes that can be instanced inside other scenes, so a "player" is a small tree with a body, a sprite, a collision shape and a script.

Composition solves the flexibility problem but not the performance one. Each component is still an individual object on the heap with its own virtual update, so iterating all rigid bodies still chases pointers across memory. For a few hundred objects this is irrelevant; for tens of thousands of projectiles, crowd agents or particles it dominates the frame.

3.3Entity Component System: ids, data, and systems

An entity component system (ECS) separates the three roles that an object combines. An entity is only an identifier, a number with no data and no behaviour. A component is plain data, a struct such as Position{x, y} or Health{hp}, with no methods beyond trivial helpers. A system is a function that runs over every entity that has a given set of components: the movement system asks for all entities with Position and Velocity and updates them in one loop. Behaviour therefore lives in systems, data lives in component storage, and an entity is "a player" only because of which components it currently has.

struct Position { float x, y; };
struct Velocity { float x, y; };
struct Lifetime { float seconds; };

void movement(World& w, float dt) {                  // a system
    for (auto [e, p, v] : w.query<Position, Velocity>())
        { p.x += v.x * dt; p.y += v.y * dt; }
}
void expire(World& w, Commands& cmd, float dt) {     // structural changes are deferred
    for (auto [e, life] : w.query<Lifetime>())
        if ((life.seconds -= dt) <= 0) cmd.despawn(e);
}

Entity bullet = w.spawn(Position{0, 0}, Velocity{30, 0}, Lifetime{2.0f});

The model gives three things at once. Flexibility, because adding a Burning component to any entity makes the burning system process it, with no class changes. Performance, because a system walks arrays of exactly the data it needs. And parallelism, because each system declares which component types it reads and writes, so a scheduler can run systems that do not conflict on different cores (Section 3.6). The well-known public example is Blizzard's description of the Overwatch architecture (GDC 2017), where gameplay and netcode were built as systems over components; Unity's Entities package, Unreal's Mass framework for crowds, Bevy, and the C++ libraries EnTT and flecs are current implementations.

Pitfall

ECS does not remove the need to think about order. Systems that run in an unspecified order produce one-frame delays (the camera follows the player's position from the previous frame) or flicker. Real ECS engines let you order systems explicitly, group them into stages or sets, and run some in a fixed-step schedule; the work moves from "which class owns this method" to "which system runs when".

3.4How components are stored: archetypes and sparse sets

The interesting engineering in an ECS is the storage, and two designs dominate, shown in Figure 3.2.

Archetype storage groups entities by their exact set of component types. All entities that have exactly {Position, Velocity} live in one table, those with {Position, Velocity, Health} in another. Inside a table each component type is a column, a contiguous array, and each entity is a row. A query for (Position, Velocity) finds all matching tables once (and caches the list), then walks their columns front to back, which is the ideal access pattern for caches, prefetchers and SIMD. An entity index maps each entity to its table and row. Unity's Entities stores tables in 16 KB chunks; Bevy's default table storage, flecs and Unreal's Mass work the same way.

Sparse-set storage gives each component type its own pool. A pool holds a dense array of components, a parallel dense array of the entity ids that own them, and a sparse array indexed by entity id that points into the dense array. Adding or removing a component is O(1) and touches only that pool. A query over several components iterates the smallest pool and looks the others up through their sparse arrays, which is a random access per entity unless the pools are kept sorted in the same order. EnTT is the best-known sparse-set ECS; Bevy offers sparse-set storage as an opt-in per component type.

The choice is a trade-off between iteration speed and structural-change speed. Archetypes win when the component set of an entity rarely changes and the same queries run every frame, which is the common case for movement, rendering and physics synchronisation. Sparse sets win for components that come and go often, such as a Stunned tag that lasts half a second, or a Selected marker. Engines that use archetypes therefore often support "tag" components without data, enable/disable bits instead of add/remove (Unity's enableable components), or a sparse-set option for volatile components.

3.5Structural changes, command buffers and handles

Adding a component to an entity in an archetype ECS moves the entity: its row is copied into the table for the new component set, and the hole it leaves is filled by moving the last row of the old table into it (swap-remove), so the table stays dense. Figure 3.3 steps through it. The move is cheap for one entity but has a consequence that every ECS user meets: a system that is iterating the old table while the move happens would skip the moved row or read a stale pointer. ECS engines therefore defer structural changes. Systems record "add this component", "spawn", "despawn" into a command buffer, and the buffer is applied at a sync point between systems. Bevy calls these Commands, Unity EntityCommandBuffer; flecs has a deferred mode.

Entities are referred to by handles, not pointers, because entities die and their slots are reused. A handle stores the slot index and a generation counter; destroying an entity increments the generation of its slot, so an old handle no longer matches and a lookup returns "gone" instead of silently reaching whichever entity reused the slot (Figure 3.4). Unity's Entity is {Index, Version}, Bevy's Entity is an index with a generation, and EnTT packs both into one integer. The same generational-index idea is used for textures, meshes, sound voices and network objects throughout engines, and it is worth knowing outside games: it is the standard safe replacement for raw pointers into pooled storage.

3.6Scheduling systems in parallel

Because every system declares what it reads and writes, the engine can compute which systems may run at the same time: two systems conflict only if one writes a component type that the other reads or writes. Figure 3.5 shows a small schedule for the arena game. Input and AI run in parallel because they write different components; steering must wait for both; movement and animation both only read velocity and write different things, so they run together; audio and collision both only read positions. Bevy builds such a schedule automatically from the parameter types of each system function and runs it on a thread pool; Unity's Entities schedules jobs with explicit dependency handles; Unreal's Mass and task graph work similarly.

Two lessons carry over to any task-graph design. Parallelism is limited by the longest dependency chain, so adding cores helps only until the critical path dominates. And conflicts are judged per component type, which is coarse: two systems that write Velocity for disjoint sets of entities (players and AI) still serialise unless they are expressed as one system or the engine supports finer-grained access. The general theory of thread pools and task scheduling is in Concurrency 6.2.

3.7When ECS is the wrong tool

ECS is not free. Logic that naturally belongs to one unique object, the game mode, the menu, the camera rig, a boss with a hand-scripted sequence, becomes awkward when it must be expressed as a system over a query that matches one entity. Relationships such as "parent of", "inventory contains", or "is targeting" are graph-shaped, and tables of components are not graphs; engines add relationship features (flecs pairs, Bevy's parent and child components, Unity's linked entity groups) or keep such data outside the ECS. Debugging is also different: there is no object to inspect, only rows spread across tables, so ECS engines need good entity inspectors.

This is why Godot's lead developer argued publicly (2021) that Godot should not be an ECS engine: most game objects are few and unique, the node tree is easier for designers, and the hot paths (physics, rendering, particles) are already implemented in optimised servers below the nodes. Unity and Unreal take a hybrid route: the familiar object model for most of the game, and an ECS (Entities, Mass) for the parts that have tens of thousands of similar things. Bevy uses ECS for everything and accepts the awkwardness for the uniformity.

Talk track

"In an ECS an entity is just an id, components are plain data stored in arrays by type, and systems are functions over every entity with a given set of components. Archetype storage keeps entities with the same component set in one table with a column per component, so iteration is a linear walk; the price is that adding or removing a component moves the entity, so those changes go through command buffers. Because systems declare reads and writes, the scheduler can run non-conflicting systems in parallel. It shines for many similar things; for unique objects the classic object model is often simpler."

4Data-oriented design, memory and the cache

Data-oriented design is the discipline behind ECS: start from the data each part of the program transforms and how it moves through memory, not from a model of real-world objects. On current CPUs a cache miss costs as much as a hundred arithmetic instructions, so the layout of data decides performance more often than the algorithm does.

4.1The problem is moving data, not computing

Mike Acton's talk "Data-Oriented Design and C++" (CppCon 2014) put the idea bluntly: the purpose of every program is to transform data from one form to another, and if you do not understand the data you do not understand the problem. The practical reason is the memory hierarchy. A core reads its L1 cache in about 1 ns, L2 in about 4 ns, shared L3 in 10–40 ns and DRAM in 80–120 ns, and memory moves in 64-byte cache lines; the details are in Algorithms 1.6 and C++: cache lines and locality. A loop that uses every byte of every line it loads, in order, runs at memory bandwidth with the prefetcher hiding latency. A loop that follows pointers to scattered objects and uses 12 bytes of each 64-byte line pays for the whole line and often for the full latency.

Data-oriented design therefore asks three questions of each hot loop. Which fields does it actually read and write? Are those fields contiguous, in the order the loop visits them? And how many items are processed together, so that the work per item can be vectorised and the per-call overhead amortised? The usual answers are to split hot from cold data, to store hot fields as arrays (structure of arrays, SoA) or as small structs (array of structs, AoS, with only hot fields), to process items in batches rather than one virtual call at a time, and to avoid pointers inside the hot data. Programming languages 10.5 covers the same idea from the paradigm side, and C++: AoS versus SoA from the language side.

4.2Measured: the same update in four layouts

The experiment dod_bench.cpp moves two million entities by x += v·dt in three dimensions, the simplest system any engine has, in four layouts, and takes the best of twenty runs on a 4-core Xeon VM (Figure 4.1). In the classic object version each entity is a 112-byte heap object with a virtual Update(), allocated among other allocations and visited through a shuffled array of pointers, as happens in a long-running game where objects are created and destroyed in no particular order. That costs 24.4 ns per entity, 48.8 ms for the frame, three frames' worth of budget for one trivial system.

Putting the same 104-byte structs contiguously in an array, still mixing hot and cold fields, cuts the cost to 10.6 ns: no pointer chase, no virtual call, and the prefetcher can follow the array. Keeping only the six hot floats in a 24-byte struct cuts it to 1.68 ns, because the loop now loads 24 bytes per entity instead of 104, a ratio of 4.3 in memory traffic that becomes a factor of 6.3 in time. Storing the six fields as six separate float arrays (SoA) gives 1.32 ns, because the compiler can now use full-width SIMD loads and stores. From the object version to SoA the same code gets 18 times faster, without any algorithmic change.

Interesting detail

The gap between the hot-only AoS struct and SoA is small here because the loop touches all six fields. SoA wins clearly when a loop reads only some fields (a culling pass that reads only bounding spheres) or when the computation vectorises better across entities than within one. Many engines use a hybrid, "AoSoA": small blocks of, say, eight entities stored as SoA, so one block fills a SIMD register and the whole block sits in a few cache lines. Unity's Entities chunks and ISPC-style code are built this way.

Pitfall

Micro-benchmarks like this flatter whatever fits in cache. With 2 million entities and a 260 MB L3 on this VM, part of the data may stay in L3, so the absolute numbers are optimistic for a console or phone; the ratios are the transferable part. Always measure in the real frame, with the profiler, after the rest of the frame has evicted your data.

4.3Allocators inside a frame: arenas, pools and stacks

A general-purpose heap (malloc, new) must handle any size in any order from any thread, so it uses locks or per-thread caches, keeps metadata, and fragments over time. A game frame has much more structure than that: most temporary data lives exactly one frame, many objects come in a few fixed sizes, and the program knows when a level is unloaded. Engines exploit that structure with a small set of special allocators, shown in Figure 4.2.

A frame arena (linear or bump allocator) is a large block and an offset. Allocating rounds the offset up for alignment and advances it; freeing does nothing; at the end of the frame the offset is reset to zero, which frees everything at once. It is the cheapest allocator possible and ideal for per-frame scratch: visible-object lists, temporary strings, command lists. If the render thread reads data produced by the game thread one frame later, the engine keeps two arenas and alternates them (double buffering), so each allocation lives exactly two frames. A stack allocator is an arena with markers: a level load pushes a marker, and unloading the level pops back to it. A pool serves objects of one size from an array of slots, keeping the free slots in a linked list stored inside the free slots themselves, so allocation pops the head of the list and freeing pushes it, both O(1), with no fragmentation and with neighbouring objects near each other in memory.

class FrameArena {
    std::byte* base; size_t cap, off = 0;
public:
    FrameArena(std::byte* mem, size_t n) : base(mem), cap(n) {}
    void* alloc(size_t n, size_t align = alignof(std::max_align_t)) {
        size_t p = (off + align - 1) & ~(align - 1);
        if (p + n > cap) return nullptr;      // budget exceeded: report, never fall back silently
        off = p + n; return base + p;
    }
    void reset() { off = 0; }                 // called once per frame
};

In the bullet experiment of Figure 4.1, 300 of 2,000 live bullets die and are replaced every frame for 10,000 frames. Using new and delete for each costs 15.6 ns per spawn and despawn; a pool with a free list costs 3.8 ns, four times less. With glibc's per-thread caches the heap is fast in this benchmark; the stronger reasons to avoid it in the frame are predictability (an occasional slow path that takes the global lock or asks the OS for memory), fragmentation over hours of play, and memory budgets that must be enforced per subsystem on a console with a fixed amount of RAM. C++17's polymorphic memory resources (std::pmr) package these allocators for standard containers; see C++: custom allocators and PMR.

4.4Object reuse, budgets, and the rest of the cache playbook

Object pooling at the gameplay level is the same idea one layer up: instead of destroying a bullet entity and creating a new one, the game deactivates it and reuses it, which also avoids re-running initialisation, re-registering with physics and re-creating render state. Unity documents an ObjectPool<T> class for exactly this, and Unreal's Niagara particle system pools its components. The cost is that a reused object must be fully reset; a stale timer or a leftover status effect on a recycled enemy is a classic bug.

Several other cache techniques recur across engines. Hot/cold splitting moves rarely used fields into a separate array, so the hot struct stays small. Sorting by access order (for example sorting draw calls or particles by material or by spatial cell) makes neighbouring iterations touch neighbouring memory. Indices instead of pointers (32-bit indices into arrays) halve the size of references, survive relocation and serialise directly. Avoiding false sharing keeps data written by different threads in different cache lines (Concurrency 5.4). And memory budgets give each subsystem a fixed amount of memory that is checked continuously in development builds, because on a console or phone running out of memory is a crash, not a slowdown.

Talk track

"Data-oriented design means laying data out for how it is processed: hot fields contiguous, cold fields elsewhere, many items per call, indices instead of pointers. In a quick benchmark moving two million entities went from 24 ns per entity with heap objects and virtual calls to 1.3 ns with structure-of-arrays, 18 times faster with the same arithmetic. Inside the frame we avoid the general heap entirely: frame arenas for scratch, pools for same-size objects, level heaps for long-lived data, each with a budget."

5Physics, collision and spatial partitioning

A game physics engine is not a scientific simulator. Its job is to make bodies fall, collide, stack and slide plausibly, stably and within two or three milliseconds per frame, for hundreds or thousands of bodies. Almost every design decision trades accuracy for stability and speed.

5.1What happens in one physics step

Rigid-body engines such as Box2D, PhysX, Havok, Jolt, Bullet and Unreal's Chaos all run roughly the same sequence each fixed step, shown in Figure 5.1. First, external forces such as gravity are applied and velocities are updated. Then the broad phase finds pairs of bodies whose simple bounding volumes, usually axis-aligned bounding boxes (AABBs), overlap; this reduces thousands of bodies to a short list of candidate pairs. The narrow phase tests each candidate pair with the exact shapes and produces contact manifolds: contact points, a normal and a penetration depth. Bodies connected by contacts or joints are grouped into islands, so that a pile of crates in one corner is solved independently of a pile in another, and islands at rest can sleep.

The solver then computes impulses that stop bodies from moving into each other, apply friction and keep joints together. Finally positions are integrated with the corrected velocities, contact events ("began touching", "stopped touching") are reported to gameplay code, and bodies that have been almost motionless for a while are put to sleep so they cost nothing until something wakes them.

5.2Integration: why engines use semi-implicit Euler

Integration turns accelerations into velocities and velocities into positions over one step. The textbook explicit Euler method updates the position with the old velocity and the velocity with the old acceleration. It is unconditionally unstable for oscillating systems: every step adds a little energy. The phase portrait in Figure 5.2 shows a mass on a stiff spring (100 N/m, 1 kg) stepped at 30 Hz; explicit Euler spirals outward and after 10 s has multiplied the energy by 5 × 1013; at 120 Hz it still gains a factor of 4,000.

Swapping the order, updating velocity first and then moving with the new velocity, gives semi-implicit (or symplectic) Euler. It costs exactly the same, but it preserves the geometric structure of the motion: energy oscillates around the true value (within 2–6 % in the experiment) instead of drifting. That is why almost every game physics engine uses it. Velocity Verlet is more accurate (energy within 0.1 %) at the cost of a second force evaluation, and is common in particle and cloth systems. Semi-implicit Euler is stable for a spring as long as the step is below 2/ω, here 200 ms, which is why stiff springs, high mass ratios and fast rotations are the cases where game physics still struggles.

x += v * dt;                                      v += (F / m) * dt;
v += (F / m) * dt;                                x += v * dt;

5.3Broad phase: avoiding the N² pair test

With N bodies there are N(N−1)/2 pairs. For 10,000 bodies that is 50 million tests per step, which no frame can afford, while the number of pairs that actually touch is usually proportional to N. The broad phase exists to find the few real candidates without looking at all pairs, and three families of structures are used, shown in Figure 5.3.

A uniform grid or spatial hash divides space into cells of fixed size; each object is inserted into the cells its bounding box overlaps, and only objects sharing a cell are tested. A spatial hash is the same grid stored in a hash table, so it works in unbounded worlds. It is excellent for many similar-sized objects (particles, bullets, crowds) and poor when sizes vary widely. Sort and sweep (also called sweep and prune) sorts the bounding intervals along one axis and reports pairs whose intervals overlap; because objects move little between steps, the sorted order changes little and insertion sort repairs it in nearly linear time. It degrades when many objects line up on the chosen axis. A dynamic AABB tree, a bounding volume hierarchy whose leaves are the bodies' boxes, slightly enlarged so that small movements do not require updates, handles mixed sizes and static geometry well; Box2D, Bullet and Jolt use variants of it, and the same tree answers ray casts and area queries for gameplay.

The experiment broadphase.cpp places circles at constant density and finds overlapping pairs three ways; all three find exactly the same pairs. For 10,000 circles, brute force performs 50 million tests in 39.8 ms, a grid with cells twice the radius performs 4,342 tests in 0.89 ms, and sort and sweep 316,000 tests in 1.23 ms. For 50,000 circles brute force needs 1.09 s, the grid 3.6 ms and sort and sweep 9.2 ms. The grid wins here because every object has the same size and the cell size was chosen for it.

The cell size is the grid's one parameter, and Figure 5.4 lets you change it. Too small, and each object spans many cells, so insertions multiply and the same pair is found in several cells. Too large, and each cell holds many objects, so the in-cell tests approach brute force.

5.4Narrow phase: exact shapes and contact manifolds

The narrow phase decides whether two shapes really intersect and, if they do, where and how deeply. Spheres, capsules and boxes have dedicated tests. For general convex shapes two algorithms dominate. The separating axis theorem (SAT) states that two convex polyhedra do not intersect if and only if there is an axis on which their projections do not overlap, and for polyhedra the candidate axes are the face normals and the cross products of edge pairs; it is fast for boxes and simple hulls. The Gilbert–Johnson–Keerthi algorithm (GJK, 1988) works on any convex shape that can report its furthest point in a direction (a "support function") and computes the distance between shapes by searching the Minkowski difference; when the shapes overlap, the expanding polytope algorithm (EPA) finds the penetration depth and normal. Non-convex objects are decomposed into convex pieces or represented as triangle meshes, which are usually allowed only for static geometry.

A single contact point is not enough for a box resting on the floor; it would rock. The narrow phase therefore produces a manifold of up to four points per pair, and keeps manifolds from step to step so that the solver can reuse the previous impulses as a starting guess (warm starting), which is a large part of why stacks are stable.

5.5Solving contacts: sequential impulses

Each contact is a constraint: the relative velocity along the normal must not bring the bodies closer, friction must stay within the friction cone, joints must keep their anchor points together. Solving all constraints exactly is a large linear complementarity problem; games instead use iterative methods. The most widely used is sequential impulses, described by Erin Catto for Box2D (GDC 2006): visit each constraint in turn, compute the impulse that would fix its velocity error, clamp it (contacts can push but not pull, friction is bounded by the normal impulse), apply it to both bodies, and repeat over all constraints a fixed number of times. This is a projected Gauss–Seidel iteration. Box2D version 2 used 8 velocity and 3 position iterations by default; Box2D version 3 (2024) uses a "soft step" solver with several substeps per step instead.

Iteration count is the engine's accuracy dial. Few iterations leave stacks slightly springy and let tall stacks sink; more iterations cost time linearly. Penetration that remains is corrected gently over several steps (Baumgarte stabilisation or a separate position pass) rather than at once, because full correction in one step injects energy and makes objects jitter or explode apart. Sleeping islands, warm starting and solver iteration counts per body are the main tuning tools.

Pitfall

Large mass ratios break iterative solvers. A 1 kg crate under a 1,000 kg crate converges very slowly, and the stack sinks or jitters. Designers learn to keep ratios below about 1:10 for stacked bodies, or the engine increases iterations for those islands.

5.6Tunnelling and continuous collision detection

Discrete collision detection only looks at positions at the end of each step. A bullet at 600 m/s moves 10 m per step at 60 Hz, so a 20 cm wall is simply never overlapped and the bullet passes through (Figure 5.5). Three remedies are common. Gameplay bullets are usually not physics bodies at all but ray casts or short shape casts along the path travelled in the step. For physics bodies, continuous collision detection (CCD) sweeps the shape from its old to its new position and computes the time of impact, then advances the body only to that time. Speculative contacts create a contact as soon as the swept bounding boxes are close, and let the solver allow only the velocity that would close the remaining gap; this is cheaper than full CCD and is used by Box2D v3 and others, at the cost of occasional "ghost" collisions with objects that would have been missed.

5.7Which physics engine where

Unity uses NVIDIA PhysX for 3D and Box2D for 2D, and offers Unity Physics and Havok Physics for its Entities stack. Unreal Engine 5 replaced PhysX with its own Chaos physics, which also handles destruction. Godot ships its own physics engine and, since Godot 4.4 (March 2025), Jolt as a built-in option for 3D. Jolt, written by Jorrit Rouwe and used in Guerrilla's Horizon Forbidden West, is open source and designed for multi-core scaling. Bevy has no built-in physics; the community crates Avian and bevy_rapier (built on the Rust engine Rapier) fill the gap. Spatial queries such as ray casts, overlap tests and sweeps, used by gameplay for line of sight, bullets, AI perception and character controllers, run on the same broad-phase structures, which is why they are part of the physics API in every engine.

Talk track

"A physics step is integrate forces, broad phase to get candidate pairs from AABBs in a grid, sweep or tree, narrow phase with SAT or GJK to get contact manifolds, an iterative sequential-impulse solver for contacts and joints, then integrate positions with semi-implicit Euler and put still bodies to sleep. It runs at a fixed rate because the solver's stability depends on the step. Fast objects need ray casts or continuous collision detection, otherwise they tunnel."

6Scenes, transforms and animation

Things in a game are attached to other things: a sword to a hand, a hand to an arm, a camera to a car. The transform hierarchy expresses that, and skeletal animation is the same hierarchy applied to the bones of a character, evaluated tens of thousands of times per frame.

6.1The transform hierarchy and dirty flags

Each node in the hierarchy stores a local transform, position, rotation and scale relative to its parent, because that is what designers and animators edit: the sword is 10 cm from the palm, whatever the player is doing. The renderer and physics need the world transform, which is the product of all local transforms from the root down: world = parent.world × local. Rotations are stored as unit quaternions because they interpolate well and do not suffer gimbal lock (Mathematics: quaternions); world transforms are cached as 4×4 or 3×4 matrices.

Recomputing every world matrix every frame is wasteful when most objects do not move, and recomputing it on every edit is wasteful when one object is edited ten times per frame. Engines therefore mark a node and its subtree dirty when a local transform changes and recompute world matrices once, parents before children, when they are needed (Figure 6.1). Bevy makes this explicit with two components, Transform (local) and GlobalTransform (world), and a propagation system that runs once per frame; Unity and Godot update world transforms lazily when they are read; Unreal's scene components update their children when they move.

The hierarchy is for attachment, not for everything. Early engines used a single scene graph for transforms, rendering order, visibility culling and state changes at once, and found that each of these wants a different structure: culling wants a spatial tree or grid, rendering wants objects sorted by material, and logic wants whatever grouping the designer chose. Modern engines keep the transform hierarchy shallow and separate from the spatial acceleration structures and from the render lists, which are rebuilt every frame (Section 7). Godot's scene tree is the visible exception, but even there the rendering server keeps its own flat data.

Pitfall

Deep hierarchies are slow in data-oriented engines because propagation is inherently sequential down each chain and moves between memory locations. Thousands of small objects parented under one moving object (all the bolts of a ship) force thousands of matrix updates per frame. Static content should be un-parented or merged at build time.

6.2Skeletal animation, from clip to skinned vertex

A character is a mesh bound to a skeleton of 50 to 150 bones. Each vertex is attached to up to four bones with weights, captured in the bind pose when the artist rigged the mesh. Animations are clips: for each bone, keyframed curves of rotation, translation and sometimes scale over time. Every frame, for every visible character, the engine runs the pipeline in Figure 6.2.

It samples each active clip at the current time, interpolating between keyframes: linear interpolation for translations, spherical linear interpolation (slerp) or normalised linear interpolation (nlerp, cheaper and good enough for small angles) for rotations. It blends several sampled poses: a walk and a run weighted by speed, an aim layer on the upper body only (a bone mask), a hit reaction added on top (additive blending). A state machine decides which clips play and how transitions cross-fade; blend trees or blend spaces map parameters such as speed and direction to weights. The result is a local pose, one transform per bone relative to its parent. Procedural steps follow: inverse kinematics plants the feet on uneven ground and points the head at a target; a ragdoll may blend in after a hit.

The local pose is then converted to model space by walking the skeleton from the root, the same parent-times-local product as the transform hierarchy. Multiplying each bone's model matrix by the inverse of its bind-pose matrix gives the skinning palette, the transform that moves a vertex from the bind pose to the current pose. Finally the vertex shader computes each vertex as the weighted sum of the vertex transformed by its bones' palette matrices; this is linear blend skinning.

Interesting detail

Linear blend skinning averages matrices, and an average of rotations is not a rotation. Twisting a forearm by 180° makes the wrist collapse into a thin "candy wrapper". Dual-quaternion skinning (Kavan et al., 2007) blends rotations properly and avoids it at a small extra cost, and rigs add twist bones so that no single joint has to twist far. Animation data is also large; engines compress curves aggressively (the open-source Animation Compression Library is used in Unreal as a plugin), because memory, not CPU, is often the limit for a game with thousands of clips.

Numbers

A crowd of 200 characters with 70 bones each needs 14,000 bone transforms sampled, blended and multiplied per frame, before skinning. This is why animation is one of the first systems moved to jobs, why distant characters update at a lower rate (animation level of detail), and why crowds often bake animations into textures that the GPU samples directly.

Root motion is a further decision: whether the character's movement through the world comes from gameplay code (the capsule moves at a set speed and the animation plays on top) or from the animation itself (the root bone's motion in the clip moves the capsule). Root motion avoids sliding feet but gives control to animators, and in multiplayer games it must be reproduced on the server.

7The engine side of rendering

The GPU API draws triangles; the engine decides which objects to draw, in which order, into which intermediate images, and how to prepare all that without stalling the simulation. This section covers that engine layer and leaves shaders and GPU APIs to the graphics chapters.

7.1From world to draw calls: extract, cull, sort, submit

The renderer of the arena game cannot read the world while the game thread is changing it for the next frame, so the first step of every frame is extraction: copying exactly what rendering needs (world matrices, mesh and material handles, light parameters, camera) into renderer-owned data. Unreal keeps "render proxies" of each component on the render thread and sends updates to them; Bevy runs an explicit extract schedule that copies data into a separate render world; Unity's scriptable render pipelines collect renderers through a culling step. After extraction the game thread is free to simulate the next frame (Figure 2.2).

Visibility comes next. Frustum culling discards objects outside the camera's view volume using the bounding volumes and a spatial structure; occlusion culling discards objects hidden behind others, using precomputed visibility, a low-resolution depth buffer rendered on the CPU, or the previous frame's depth on the GPU; level of detail (LOD) selects a simpler mesh for distant objects. In a typical scene this removes most objects before any draw is issued.

The surviving objects become draw lists, one per pass. Each draw gets a sort key, a single integer whose bit fields encode, from most to least significant, the layer, the pass, whether it is translucent, the shader and material, and the depth (Figure 7.1). Sorting the integers groups draws that share GPU state, so state changes are minimal, and orders opaque objects front to back (so the depth test rejects hidden pixels early) and translucent objects back to front (so blending is correct). Draws with the same mesh and material are merged into instanced draws. Finally the lists are recorded into command buffers, increasingly on several threads in parallel, and submitted.

Why it matters

A draw call is cheap on the GPU but not on the CPU: the driver validates state, binds resources and records commands, traditionally tens of microseconds per draw on older APIs. Ten thousand individual draws can take the whole frame on the render thread while the GPU idles. Batching, instancing, sorting by state and, in recent engines, GPU-driven rendering (the GPU culls and generates its own indirect draws) exist to keep that cost down. What a draw call is at the API level is explained in GPU programming for surround view 1.2.

7.2Render graphs: passes declare what they read and write

A modern frame is not one pass but twenty or more: shadow maps, a depth pre-pass, a G-buffer pass in a deferred renderer, lighting, screen-space effects, translucency, post-processing (tone mapping, bloom, anti-aliasing), and the user interface. Each pass reads some textures and writes others. Writing that sequence by hand, with every memory barrier, resource transition and texture allocation, becomes unmanageable, especially with explicit APIs such as Vulkan and Direct3D 12 that make the engine responsible for synchronisation.

The render graph (or frame graph) answers this the same way the ECS scheduler does for systems. Each pass declares its inputs and outputs; the engine builds a graph for the frame, removes passes whose outputs nobody uses, orders the rest, inserts barriers automatically, and allocates transient textures from a pool, letting two textures whose lifetimes do not overlap share the same memory (aliasing). The idea was presented publicly by Frostbite as "FrameGraph" (GDC 2017); Unreal's Render Dependency Graph (RDG), Unity's Render Graph in its scriptable pipelines and Bevy's render graph follow it. The forward-versus-deferred choice, G-buffers and the rasterisation pipeline itself are in Rasterization versus path tracing 3.3.

Interesting detail

Unreal Engine 5's Nanite takes GPU-driven rendering to its end point: meshes are split into small clusters arranged in a hierarchy, and the GPU selects, per frame and per screen region, the clusters whose detail matches the pixel size, rasterising tiny triangles in a compute shader. Artists can import film-quality meshes without making LODs. Lumen, its global illumination system, traces rays against simplified scene representations. Both trade fixed GPU cost for removing manual content work, which is the same trade the engine layer makes everywhere.

Talk track

"Each frame the renderer extracts what it needs from the game world so simulation can continue, culls by frustum, occlusion and LOD, builds per-pass draw lists sorted by a packed integer key to minimise state changes and get the right depth order, and executes a render graph where passes declare their inputs and outputs so barriers and transient memory are handled automatically."

8Input, events, resources and jobs

Around the simulation sit the systems that connect it to the outside world and to the hardware: input from players, events between systems, assets from disk, and work spread across cores. Each looks simple and each has a classic failure.

8.1Input: from device events to game actions

The operating system delivers input as events (key down, key up, mouse moved, gamepad axis changed) or as device state that can be polled. Engines usually do both: they drain the event queue once at the start of the frame, update a per-frame device state (which keys are down, which were pressed this frame), and let gameplay poll that state. Polling inside gameplay code avoids callbacks that fire in the middle of a system; recording events keeps short presses that would otherwise fall between two polls.

Gameplay should not depend on physical keys, so modern engines add an action mapping layer: "Jump" is bound to the space bar, the A button and a touch gesture; "Move" is a 2D axis from WASD or the left stick, with dead zones and response curves applied. Unreal's Enhanced Input system and Unity's Input System package work this way, and Godot has an input map of named actions. The mapping layer also handles contexts (driving and walking use different bindings) and rebinding by the player.

Two details matter for game feel. Input should be sampled as late as possible before the simulation step that uses it, since every millisecond between sampling and display adds to latency (Section 2.4). And actions often need buffering: a jump pressed 80 ms before landing should still happen on landing, and fighting games keep a buffer of recent inputs to recognise motion commands. With a fixed timestep, buffered input events must be consumed by the fixed step, not by the variable-rate update (Section 2.3).

8.2Events and messaging between systems

Systems need to tell each other things: a bullet hit an enemy, the player picked up a key, a door opened. The direct way, a callback or observer list (Unreal's delegates, Godot's signals, C# events in Unity), runs the listener immediately inside the sender's code. That is simple, but the listener may modify the world while the sender is iterating it, the order of side effects becomes hard to reason about, and long chains of callbacks hide the cost of an innocent-looking call.

An event queue decouples time as well as code: senders append events, and listeners process them at a defined point in the frame. Bevy's buffered events are an example: a writer system appends, reader systems read later in the frame or in the next frame, and each event is kept for two updates so that readers scheduled before the writer still see it. The cost is a frame of delay and the need to decide how long events live. Many engines use both: immediate callbacks for local, synchronous notifications (a UI button), queues for gameplay events that cross systems or threads.

8.3Resources: import, cook, load, stream

Artists produce assets in formats meant for editing: FBX or glTF meshes, PNG or EXR textures, WAV audio. These are slow to parse and often unsuitable for the target device. The asset pipeline in Figure 8.1 converts them in two stages. Import, in the editor, converts a source file into the engine's own format and gives it a stable identifier that survives renames: Unity stores a GUID in a .meta file next to every asset, Godot 4 writes .import files and uses uid:// identifiers, Unreal keeps everything in .uasset packages. Cooking, at build time, produces platform-specific data: textures compressed to GPU formats (BC on PC and consoles, ASTC on mobile), meshes with generated LODs, shaders compiled for the target API, unused data stripped. The cooked results are packed into large archive files ordered for streaming.

At run time, gameplay asks for an asset by identifier and receives a handle immediately, not the asset. A loader thread reads, decompresses and uploads the data; the handle reports "loading" until then, and code must cope with that, for example by showing a placeholder. A resource cache maps identifiers to loaded objects with reference counts, so ten enemies share one mesh and the mesh is unloaded when the last one goes. Open-world games add streaming: the world is divided into cells, and cells and texture mip levels are loaded and evicted continuously according to the player's position and the memory budget. Bevy's AssetServer returning Handle<T>, Unity's Addressables and Unreal's World Partition are three current shapes of the same idea. In the editor, hot reload re-imports an asset when its source file is saved and swaps it in the running game, which is a large part of what makes iteration fast.

Pitfall

Synchronous loading "just this once" is the most common source of hitches: a sound file loaded the first time an explosion happens, a shader compiled the first time a material is seen. The fixes are preloading by level or by asset dependency, asynchronous loading everywhere, and caching or precompiling shaders, which is why PC games increasingly compile shaders at start-up.

8.4Jobs, fibers and the main thread

For years engines ran one thread for the game, one for rendering and a few for audio and loading, which used four cores at most. Current engines split the frame into many small jobs with dependencies, executed by one worker thread per core: animation per character, physics islands, culling per view, command recording per pass, particle updates. Naughty Dog described a fiber-based job system (GDC 2015) in which jobs can wait for other jobs by switching fibers instead of blocking a thread, so that even the frame's own control flow is a set of jobs. Unity's C# Job System with the Burst compiler, Unreal's task graph and UE5 Tasks, and Bevy's executor over its task pools are the mainstream versions. The general mechanics, work stealing and why queues need care, are in Concurrency 6.2.

Engines keep one rule from the single-threaded era: there is a main thread (Unreal's game thread) on which gameplay code and most engine objects are touched, and parallel jobs work on data handed to them explicitly. That rule is why ECS and data-oriented design fit so well with jobs: a job over a component column has clearly defined inputs and outputs, while a job that calls virtual methods on arbitrary game objects does not.

8.5The gameplay layer and scripting

Most game code is gameplay, written by people who are not engine programmers and changed daily. Engines therefore offer a faster, safer layer above C++: Unreal's Blueprints (visual scripting compiled to bytecode) next to C++, Unity's C# (run by Mono in the editor and usually compiled ahead of time with IL2CPP for shipping), Godot's GDScript (a Python-like language designed for the engine) plus C# and native GDExtension libraries. Bevy is the exception: gameplay is ordinary Rust systems, so there is one language and full performance, at the cost of compile times and a steeper learning curve for designers.

The layer brings its own costs: garbage-collected languages produce allocation spikes and collection pauses unless code avoids allocating per frame (Unity's incremental collector spreads the work), reflection-heavy object systems such as Unreal's UObject have their own garbage collector and memory overhead, and every call across the language boundary costs time. The standard advice in all engines is the same: keep per-frame scripts small, move heavy loops into native systems, and profile.

9Determinism, networking and multiplayer

Multiplayer turns one simulation into several copies that must agree while they are separated by 20 to 150 ms of network latency, lose packets, and are run by players who may cheat. There are two basic answers: make every copy compute exactly the same thing from the same inputs, or make one copy the authority and let the others predict and correct.

9.1Two models: lockstep and authoritative server

In deterministic lockstep (Figure 9.1, left) every machine runs the complete simulation, and only player inputs are sent. Turn N is simulated when the inputs of every player for turn N have arrived. Bandwidth is tiny and independent of the number of units, which is why real-time strategy games with thousands of units use it; the classic account is "1500 Archers on a 28.8" about Age of Empires (Bettner and Terrano, GDC 2001), and Factorio uses lockstep today. The prices are that every player waits for the slowest connection, a new player must receive the entire state to join, and the simulation must be bit-for-bit deterministic on every machine, or the copies drift apart (a desync).

In the authoritative server model (right) one machine, a dedicated server or a hosting player, runs the true simulation. Clients send inputs and receive snapshots of the state they need. Because the server's state is the truth, small numerical differences on clients are corrected automatically and determinism is not required; because clients never decide outcomes, cheating is harder. The price is bandwidth that grows with the amount of visible state, and latency: a client that waited for the server before showing the effect of its own input would feel 100 ms of lag on every action. Shooters, action games and most online games use this model, with the techniques in Section 9.3.

9.2What makes a simulation deterministic, and what breaks it

Determinism means that the same initial state and the same sequence of inputs produce exactly the same state, bit for bit, every time and on every machine. Integer arithmetic is deterministic. Floating-point arithmetic is deterministic for one binary on one CPU, since IEEE 754 defines each basic operation exactly, but the program around it often is not, as the experiment determinism.cpp shows.

First, floating-point addition is not associative. Summing the same 100,000 numbers forward, backward and in four interleaved lanes gives 91,323,888, 91,325,232 and 91,325,152 in the same binary. Any change in iteration order, for example iterating a hash map whose layout depends on pointer addresses, or a parallel reduction whose split depends on the thread count, changes results. Second, compiler flags change the arithmetic. With -ffp-contract=fast on a CPU with fused multiply-add, a*b+c is computed with one rounding instead of two and the last bits differ; in the experiment the FMA build even generated different "random" inputs from the same seed, because the compiler fused the multiply-add inside std::uniform_real_distribution. With -ffast-math the compiler vectorises the forward sum, which reorders it, and the result changes again. Third, library functions such as sin, exp and pow are not required to be correctly rounded and differ between C libraries and platforms.

Small differences matter because games are chaotic. In the experiment 100 balls bounce in a box at 60 Hz; changing one ball's x coordinate by one unit in the last place (about 10−6 m) produces a difference of more than 1 cm after 85 steps (1.4 s) and more than 1 m after 90 steps. In lockstep that is a desync within two seconds.

Deterministic engines therefore control every source: they compile the simulation with strict floating-point settings and identical binaries for all platforms (or use fixed-point arithmetic), implement their own transcendental functions, iterate in a defined order (sorted ids, never pointer order), keep the random-number generator and its seed inside the simulation state, keep the simulation on one thread or make parallel parts order-independent, and never let rendering or frame time leak into the simulation. They also compute a checksum of the state every few turns and compare it across machines, so a desync is detected at the step where it happens. The same requirements apply to replays, rollback netcode and automated tests that compare recorded runs; the simulation chapter discusses them for driving simulators in Simulation 9.3, and numerical reproducibility in general is in Mathematics: determinism and reproducibility.

Pitfall

"It is deterministic on my machine" proves little: the same binary on the same CPU hides most problems. Desyncs appear between compilers, between x86 and ARM, between a debug and a release build, or when a new platform's math library rounds atan2 differently. Lockstep games run continuous cross-platform determinism tests that replay recorded matches and compare checksums.

9.3Client-side prediction, reconciliation and interpolation

The authoritative-server model becomes playable through three techniques, stepped through in Figure 9.2. Client-side prediction: the client applies its own inputs to its own character immediately, running the same movement code as the server, so the player feels no delay. Each input carries a sequence number. Server reconciliation: the server processes the input when it arrives and returns the authoritative state together with the number of the last input it applied. The client then resets its character to that state and re-applies all inputs it has sent since. If the prediction was right nothing visible changes; if it was wrong (another player blocked the way) the character is corrected, ideally smoothed over a few frames.

Entity interpolation: other players cannot be predicted, since their inputs are unknown. The client therefore buffers snapshots and draws other entities between two snapshots it has already received, typically about 100 ms in the past (the Source engine's default interpolation delay). Motion is smooth, but everything the player sees of others is late by the interpolation delay plus half the round trip. Hence lag compensation: when a client fires, the server rewinds the other players' hit boxes to where that client saw them, using the client's latency and interpolation delay, and judges the hit there. It favours the shooter, which is why players sometimes feel they were hit after reaching cover.

The rest of a networking layer is bandwidth engineering. Snapshots are delta-compressed against the last snapshot the client acknowledged, values are quantised (a position to millimetres, an angle to 16 bits), and entities are prioritised by relevance, so distant or invisible objects are updated rarely or not at all. Unreal's replication system is built around per-actor relevancy, update frequencies and remote procedure calls, with the newer Iris system in Unreal Engine 5; Unity has Netcode for GameObjects and Netcode for Entities; Godot provides multiplayer synchronizer and spawner nodes; Bevy relies on community crates. Transport is almost always UDP with the engine's own reliability and ordering for the messages that need it, because TCP's in-order delivery would stall all game data behind one lost packet. Server tick rates range from 20–30 Hz for large battle-royale games to 64 or 128 Hz for competitive shooters (Valorant's servers run at 128 Hz).

9.4Rollback netcode

Fighting games need both determinism and responsiveness: two players, frame-exact timing, no server. Rollback combines lockstep's input exchange with prediction. Each machine simulates immediately using its local input and a guess for the remote input (usually "the same as last frame"), and saves the game state every frame. When the real remote input for an earlier frame arrives and differs from the guess, the game restores the saved state of that frame and re-simulates all frames since, within a single display frame (Figure 9.3). GGPO, the library that popularised it, was released as open source in 2019, and most current fighting games ship rollback netcode.

Rollback has two hard requirements: the simulation must be deterministic, and saving, restoring and re-simulating several frames must fit in one frame's budget. A small, flat game state, which data-oriented design produces naturally, makes snapshotting a memcpy; this is one more reason ECS engines are attractive for networked games. Visual effects and sounds triggered during mispredicted frames must be handled carefully so they are not played twice or left orphaned.

10.2Choosing an engine, or none

For a team the choice is rarely about the runtime alone. It is about the editor and content pipeline the artists will live in, the platforms (consoles require licensed engines or a lot of porting work), the language the team knows, source access when something breaks, and the cost model. Unreal suits high-fidelity 3D with a team that can handle C++ and a large engine; Unity suits mobile, cross-platform and teams that want C#; Godot suits smaller teams that value an open, lightweight engine; Bevy suits programmers who want Rust and ECS and accept a young ecosystem without a full editor.

Writing your own engine is reasonable when the game needs something no general engine does well (a voxel world, a simulation-heavy strategy game, a deterministic lockstep model across thousands of units) or when the target is unusual, for example an embedded device without a full operating system. The tiny engine of this chapter shows how small the core loop is; the years of work are in tools, content pipelines and platform support.

11Relevance to automotive visualisation, simulation and embedded software

Game engines reach the car in two direct ways, as the renderer of in-car displays and as the core of driving simulators, and in a third, indirect way: the techniques games use to meet frame deadlines are the techniques embedded perception software needs.

11.1In-car displays: game engines in the cockpit

Instrument clusters and infotainment screens increasingly show 3D content: a model of the car with the surroundings, animated driver-assistance visualisations, navigation in 3D. Several manufacturers render this with game engines. GM's GMC Hummer EV (2021) uses Unreal Engine for its displays, and Volvo Cars announced in 2022 that its next-generation cars, starting with the EX90, would use Unreal Engine for real-time visualisation in the cockpit; Unity also offers its runtime for automotive HMI, alongside specialised HMI tools such as Kanzi and Qt. The engine brings the editor, materials, lighting and animation tools that design teams know, and fast iteration between designers and the car.

The automotive context changes the constraints. The target is an embedded SoC with a fixed GPU budget shared with surround-view and other displays, so frame budgets, memory budgets and shader compile times dominate; start-up time matters (the rear-view camera image must appear within regulated limits after reverse is engaged, see GPU programming for surround view for frame pacing on such systems); and safety-relevant content such as warning indicators is usually not left to a general game engine but rendered by a separate, qualified path. The engine's job is the experience layer on top of that.

11.2Driving simulators are game engines with sensors

CARLA is built on Unreal Engine; NVIDIA's simulators build on Omniverse with USD scene descriptions; many commercial simulators use Unity or Unreal for rendering (Simulation 3.2). Everything in this chapter appears there with a different emphasis. The fixed timestep becomes a hard requirement: CARLA's synchronous mode with a fixed delta time makes the simulation advance one step per client tick, so the system under test, not the wall clock, drives time, which is the accumulator idea taken to its end. Ray casts against the physics broad phase become lidar models (Simulation 5.3). The renderer becomes a camera model whose exposure, noise and lens distortion matter more than its beauty. And determinism, a convenience in games, becomes the basis of regression testing: the same scenario and seed must give the same verdict (Simulation 9.3), with the same traps as in Section 9.2: thread timing, floating-point order and asynchronous loading.

11.3What embedded perception software can borrow

A camera perception pipeline on an ECU is a soft real-time loop with a frame deadline, as a game is: every 33 ms a frame arrives, must be processed through several stages, and must produce output before the next one. The game-engine toolbox transfers almost directly. A fixed-rate loop with explicit budgets per stage and a 99th-percentile view of frame time, instead of averages. No general-purpose allocation inside the frame: pools for detections and tracks, frame arenas for scratch data, everything sized at start-up, which is also what automotive coding rules demand (C++: deterministic allocation). Data-oriented layouts for point clouds, feature lists and tensors, processed in batches. Generational handles instead of pointers into pooled storage. Jobs with declared inputs and outputs scheduled as a graph rather than threads that lock shared objects. Pipelining across CPU, GPU and accelerators with bounded queues, and an honest accounting of the latency that pipelining adds. And deterministic replay: recording the inputs of a drive and replaying them through the same code to reproduce a bug is the lockstep idea applied to debugging.

QSelf-check questions

Q.1Core questions

Describe a game loop with a fixed timestep.Basic

Each frame measures the elapsed wall-clock time, clamps it, and adds it to an accumulator. While the accumulator holds at least one step dt, the simulation runs one step with exactly dt and the accumulator is reduced. The remainder divided by dt is alpha, and the renderer draws the state interpolated between the previous and the current step. Input is polled before stepping. This makes physics stable and reproducible regardless of frame rate, and interpolation keeps motion smooth on any display.

Why not just multiply everything by delta time?Basic

Because integration error depends on the step: a jump with explicit Euler is 6.6 % too high at 30 Hz and 0.8 % at 240 Hz, so gameplay differs by machine. Long frames produce huge steps that make stiff systems unstable and let objects pass through walls, and variable steps make runs impossible to reproduce. Variable dt is acceptable for visual-only effects and simple movement; physics and anything that must be reproducible need a fixed step.

What is the spiral of death and how do you prevent it?Intermediate

If a simulation step takes longer in real time than the time it simulates, each frame accumulates more owed time than it can pay, needs more steps, takes longer, and the game freezes. Prevention: cap the steps per frame or clamp the time added to the accumulator, accepting slow motion; and keep the step cost well below dt through budgets and profiling. In the chapter's model an 18 ms step at 60 Hz led to a 3.5 s frame within 60 frames without a cap, and to 90 % game speed with a cap of four.

What is an Entity Component System and why do engines use it?Basic

An architecture where entities are plain ids, components are plain data, and systems are functions that process all entities with a given component set. It gives composition without class hierarchies, contiguous data for cache-friendly iteration, and declared read/write sets that let a scheduler run systems in parallel. Engines use it where there are many similar things: crowds, projectiles, particles, networked state.

Compare archetype and sparse-set ECS storage.Intermediate

Archetype storage keeps one table per exact component set, with a column per component; queries walk matching tables linearly, which is the fastest iteration, but adding or removing a component copies the entity's row to another table. Sparse sets keep one pool per component with a dense array and an id-indexed sparse array; adding and removing are O(1) and local, but multi-component queries look up the other pools per entity. Choose archetypes for stable component sets iterated every frame and sparse sets for components that toggle often; many engines offer both.

Why are structural changes deferred with command buffers?Intermediate

Adding or removing a component moves the entity between tables and swap-removes the old row, which shifts another entity. During iteration that would make the iterator skip or repeat entities and invalidate references, and with parallel systems it would be a data race. Recording changes in a command buffer and applying them at a sync point keeps iteration safe and makes the moment of change explicit.

What is data-oriented design?Basic

Designing code around the data it transforms and how that data moves through the memory hierarchy: hot fields contiguous and separate from cold fields, arrays processed in batches, indices instead of pointers, and layouts matched to the access pattern (SoA, AoS, AoSoA). The motivation is that a cache miss costs about 100 ns while an arithmetic operation costs under 1 ns. In the chapter's benchmark the same movement update was 18 times faster in SoA than with heap objects and virtual calls.

Which allocators would you use in a game frame and why?Intermediate

A frame arena (bump allocator reset each frame, double-buffered if the render thread reads it one frame later) for temporary data; pools with free lists for many same-size objects such as bullets, particles and contacts; stack or level heaps with markers for data that lives for a level; and the general heap only at load time. They are O(1), do not fragment, keep related data together, and allow per-subsystem budgets. The measured pool was four times faster than new/delete for bullet churn, but predictability and fragmentation are the stronger arguments.

Walk through one step of a rigid-body physics engine.Intermediate

Apply forces and integrate velocities; broad phase on AABBs (grid, sort and sweep or dynamic AABB tree) to get candidate pairs; narrow phase with exact shapes (SAT, GJK and EPA) to produce contact manifolds; group bodies into islands and skip sleeping ones; solve contacts, friction and joints with an iterative sequential-impulse solver, warm-started from the previous step; integrate positions with semi-implicit Euler; report contact events and put still bodies to sleep.

How do you avoid testing every pair of objects for collision?Basic

Use a broad phase. A uniform grid or spatial hash with cells about the size of the objects tests only objects in the same or neighbouring cells; sort and sweep along an axis tests only overlapping intervals and benefits from temporal coherence; a dynamic AABB tree handles mixed sizes and also serves ray casts. For 10,000 circles the chapter measured 50 million brute-force tests in 39.8 ms against 4,342 grid tests in 0.89 ms.

What is tunnelling and how is it handled?Intermediate

A fast, small object moves farther than the thickness of an obstacle in one step and is never seen overlapping it. Bullets are usually ray or shape casts along the path of the step. Physics bodies use continuous collision detection (sweep the shape and stop at the time of impact) or speculative contacts (create a contact early and limit the closing velocity). A smaller step also helps but costs every body.

Why do engines store rotations as quaternions?Basic

Four numbers instead of nine, no gimbal lock, cheap composition, easy renormalisation, and smooth interpolation with slerp or nlerp, which animation blending needs constantly. Matrices are still used for the cached world transforms and skinning palettes because the GPU consumes matrices.

Explain skeletal animation and skinning.Intermediate

A mesh is bound to a skeleton in a bind pose, with each vertex weighted to up to four bones. Each frame the engine samples clips, blends poses (state machines, blend trees, layers, additive), applies IK, converts the local pose to model space by walking the hierarchy, and multiplies each bone's model matrix by its inverse bind matrix to get the skinning palette. The vertex shader transforms each vertex by its bones' palette matrices and sums them with the weights (linear blend skinning).

What does the renderer do before it issues draw calls?Intermediate

It extracts render data from the world so the game thread can continue, culls by frustum and occlusion, selects LODs, builds draw lists per pass, assigns each draw a packed integer sort key (layer, pass, translucency, material, depth), sorts, merges into instanced draws, and records command buffers, often on several threads. A render graph orders the passes and manages barriers and transient textures.

What is a render graph?Advanced

A per-frame graph of render passes, each declaring which resources it reads and writes. The engine culls passes whose outputs are unused, orders the rest, inserts the synchronisation barriers and layout transitions that explicit APIs require, and allocates transient textures from a pool with memory aliasing between resources whose lifetimes do not overlap. Frostbite's FrameGraph, Unreal's RDG and Unity's Render Graph are examples.

Lockstep versus client-server: when do you use which?Intermediate

Lockstep sends only inputs, so bandwidth does not depend on the number of units: ideal for RTS and simulation games with thousands of units and few players, but it needs bit-exact determinism, waits for the slowest player and makes late joining hard. An authoritative server sends state, tolerates non-determinism, resists cheating and suits action games and many players, at the price of bandwidth and the need for prediction and interpolation.

Explain client-side prediction and server reconciliation.Intermediate

The client applies its own inputs immediately with the same movement code the server uses, tagging each input with a sequence number. The server returns authoritative states with the last processed input number. The client resets to that state and replays the unacknowledged inputs; if the prediction was right nothing changes, otherwise the error is corrected, usually smoothed over a few frames.

What is lag compensation?Advanced

Clients see other players interpolated in the past, by the interpolation delay plus network latency. When a client fires, the server rewinds the other players' hit boxes to the time the shooter saw, judges the hit there, and then restores the present. It makes aiming fair for the shooter at the cost of occasional "shot behind cover" for the target, and it needs a bounded history of positions on the server.

How would you make a simulation deterministic across machines?Advanced

Use identical binaries or fixed-point arithmetic; compile the simulation with strict floating-point settings (no fast-math, no FMA contraction); avoid platform math libraries for transcendental functions; iterate in a defined order and never by pointer or hash layout; keep the RNG and its seed in the simulation state; keep wall-clock time and rendering out of the simulation; keep parallel parts order-independent; and checksum the state periodically to detect desyncs at once.

What is rollback netcode?Advanced

Each peer simulates immediately with its local input and a predicted remote input, saving state every frame. When the true remote input for an earlier frame arrives and differs, it restores that frame's state and re-simulates up to the present within one frame. It gives lockstep consistency with near-zero perceived input delay, provided the simulation is deterministic and small enough to save, restore and re-run several times per frame.

How do engines use multiple cores?Intermediate

A main or game thread runs gameplay; the frame is broken into jobs (animation per character, physics islands, culling per view, command recording per pass, particle updates) with explicit dependencies, executed by one worker per core with work stealing; the render thread and RHI thread run a frame behind. ECS schedulers derive parallelism from systems' declared reads and writes. The speed-up is bounded by the critical path, so restructuring dependencies often matters more than adding workers.

Why do engines use handles instead of pointers for assets and entities?Basic

Objects are destroyed, reloaded, streamed out and relocated. A handle (index plus generation, or an asset id) survives relocation, can be checked for staleness, can refer to something still loading, serialises and replicates over the network, and is smaller than a pointer when 32-bit indices suffice.

How do Unreal, Unity, Godot and Bevy differ in their object models?Basic

Unreal: Actors with components, a reflected UObject system with garbage collection, Blueprints on top of C++, Mass for ECS-style crowds. Unity: GameObjects with C# MonoBehaviour components, and the separate Entities stack for data-oriented code. Godot: a tree of nodes where scenes are reusable subtrees, scripted in GDScript, deliberately not ECS. Bevy: ECS throughout, with gameplay as Rust systems.

Q.2Why and what if

Why does the renderer interpolate between the last two simulation states instead of drawing the latest one?Why

Because display frames and simulation steps do not line up: a frame may come after zero, one or two steps. Drawing the latest state would show repeated and skipped positions, which looks like stutter. Interpolating with alpha places every frame at the right fraction between two steps, at the cost of one step of latency. Extrapolating avoids the latency but is wrong whenever something changes direction.

What if the display runs at 144 Hz and the simulation at 60 Hz without interpolation?What if

About 35 of 60 frames contain no simulation step in the chapter's model, so many consecutive frames show the same state and then a jump. Motion judders even though the frame rate is high; the extra frames buy nothing until interpolation is added.

Why does semi-implicit Euler keep energy bounded when explicit Euler does not, at the same cost?Why

Explicit Euler moves with the old velocity, which systematically overshoots outward on an oscillation and adds energy every step. Semi-implicit Euler moves with the updated velocity; the resulting map is symplectic, it preserves phase-space area, so energy oscillates around the true value instead of drifting. It remains stable while the step is below 2/ω for a spring.

What if the grid cell is much smaller than the objects?What if

Each object overlaps many cells, so insertions multiply and the same pair is found in several cells and must be deduplicated. In the interactive, halving the cell from one diameter to one radius raised insertions from 1,200 to 2,700. Too large a cell has the opposite problem: at 60 radii the grid did 43,282 tests, almost the 44,850 of brute force.

Why was the fat array-of-structs layout six times slower than the hot-only struct when both are contiguous?Why

The loop is bound by memory traffic, not arithmetic. With 104-byte structs every entity brings 104 bytes into the cache to use 24; with 24-byte structs the cache lines contain only useful data, a 4.3 times reduction in bytes, and the simpler layout lets the compiler vectorise. The cost tracks the bytes moved.

What if two systems both write Velocity, one for players and one for AI enemies?What if

A scheduler that tracks access per component type sees a write-write conflict and runs them one after the other, even though they touch disjoint entities. Options are to merge them into one system, to split the data into different component types (PlayerIntent and AiIntent, then one steering system), or to use an engine feature that proves the queries disjoint (for example by filters on marker components).

Why do structural changes in archetype storage cost more for entities with many components?Why

The move copies every column of the entity's row into the new table and swap-removes it from the old one, so the cost is proportional to the total size of all its components, not just the one being added. Volatile flags on component-rich entities are better expressed as enable bits, tags in sparse sets, or values inside an existing component.

What if a lockstep game iterates an unordered hash map of units keyed by pointer?What if

Iteration order depends on memory addresses, which differ between machines and runs, so units are processed in different orders; with floating-point sums and order-dependent gameplay (who attacks first) the states differ. The chaos experiment shows such a difference grows to metres within two seconds: a desync. Iterate by stable ids instead.

Why can an authoritative server tolerate non-deterministic clients?Why

Clients only predict and display; the server's snapshots are the truth and overwrite client state continuously. Any drift from floating-point differences is corrected at the next snapshot. Determinism only matters for the prediction to usually match, so that corrections are rare and small.

What if the server's interpolation delay is set to zero?What if

The client would draw other players at the newest snapshot and have nothing to interpolate towards until the next one arrives, so any late or lost packet makes them freeze and jump. The delay is usually set to about two snapshot intervals so one packet can be lost without visible stutter.

Why is the pipelined frame both faster and laggier than a sequential one?Why

Throughput is set by the slowest stage instead of the sum of all stages, because the game thread, render thread and GPU work on different frames concurrently. But each frame still passes through every stage plus queues, so the time from input to display grows to several frame intervals. Low-latency modes shorten the queues or start the frame later.

What if gameplay code loads an asset synchronously the first time an explosion happens?What if

The frame blocks on disk I/O and decompression, possibly shader compilation, and the player sees a hitch exactly at the dramatic moment. Assets should be preloaded by level or dependency, loaded asynchronously behind handles with placeholders, and shaders compiled or cached ahead of time.

Why do modern engines keep the transform hierarchy separate from culling and render order?Why

Each needs a different organisation: attachment is a parent-child tree chosen by designers, culling needs a spatial structure balanced by position and size, and rendering needs objects sorted by pass and material. One scene graph serving all three makes each worse; separate, rebuilt-per-frame structures are faster and simpler.

What if a perception pipeline on an ECU allocates its detection objects with new every frame?What if

Average cost may be fine, but allocation time becomes unpredictable, memory fragments over hours of operation, and it violates the usual automotive rule of no dynamic allocation after start-up. The game-engine answer applies directly: a pool sized for the maximum number of detections, a frame arena for scratch data, and handles instead of pointers.

Why does rollback need a small game state?Why

The game saves the state every frame and may restore it and re-simulate several frames within a single 16.7 ms frame. If the state is large or scattered over the heap, saving and restoring cost too much; a compact, flat state, typical of data-oriented designs, makes it a memory copy.

Command buffer (ECS)
Recorded spawns, despawns and component changes applied later at a sync point.
Cooking
Converting imported assets into platform-specific runtime formats at build time.
Desync
Divergence of supposedly identical simulations in a lockstep or replay system.
Dirty flag
Marker that a cached value, such as a world transform, must be recomputed before use.
Data-oriented design
Organising code and data around access patterns and memory movement rather than object models.
ECS
Entity Component System: ids, plain-data components stored by type, and systems over component queries.
Entity interpolation
Drawing remote entities between buffered snapshots, slightly in the past, for smooth motion.
Extraction
Copying render-relevant state from the game world into renderer-owned data each frame.
Fixed timestep
Simulating with a constant dt independent of the frame rate.
Frame arena
Linear allocator whose memory is released all at once at the end of the frame.
Generational handle
Index plus generation counter that detects use after a slot was freed and reused.
GJK
Gilbert–Johnson–Keerthi algorithm for distance and intersection of convex shapes via support functions.
Island
Group of bodies connected by contacts or joints, solved and put to sleep together.
Lag compensation
Server rewinding other players to the time a shooter saw them to judge a hit.
Linear blend skinning
Vertex position as the weighted sum of the vertex transformed by each influencing bone.
Deterministic lockstep
Network model where peers exchange only inputs and each runs an identical simulation.
Contact manifold
Set of contact points with a normal and depth describing how two shapes touch.
Narrow phase
Exact shape tests that turn candidate pairs into contacts.
Pool allocator
Allocator of equal-size slots with an intrusive free list; O(1) and without fragmentation.
Client-side prediction
Applying one's own inputs locally before the server confirms them.
Server reconciliation
Resetting to the server's state and replaying unacknowledged inputs.
Render graph
Per-frame graph of passes with declared resource use, from which order, barriers and memory aliasing are derived.
Rollback
Restoring a saved state and re-simulating when a predicted remote input turns out wrong.
Semi-implicit Euler
Integrator that updates velocity first and moves with the new velocity; stable and cheap.
Sequential impulses
Iterative constraint solver applying clamped impulses per contact or joint (projected Gauss–Seidel).
Skinning palette
Per-bone matrices (model pose times inverse bind pose) used to skin vertices.
Snapshot
Server-sent state of the relevant entities at one tick, usually delta-compressed.
Sort key
Packed integer per draw call whose bit fields order draws by pass, state and depth.
Sparse set
Component pool with dense data plus an id-indexed sparse array for O(1) lookup, add and remove.
Spiral of death
Runaway in a fixed-step loop when one step costs more real time than it simulates.
Tunnelling
A fast object passing through a thin obstacle between two discrete steps.
