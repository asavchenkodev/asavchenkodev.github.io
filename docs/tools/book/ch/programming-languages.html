Programming languages and paradigms

Why C, C++, Rust, Go, Java, Kotlin, C#, Python, JavaScript, TypeScript and Lisp look the way they do, studied through the problems each one solves and the price it pays: how source becomes running code, who frees memory, what a type system checks, how concurrency is organised, and what functional, declarative, reactive and data-oriented programming actually change. Rust gets extra depth. One small backend task, counting server errors per endpoint in an access log, is implemented and measured in eight languages so that every claim about speed, memory and start-up has a number behind it.

1The big picture: a language is a bundle of trade-offs

There is no best programming language, only languages that made different bets about who should pay for safety, speed and convenience, and when. Once you can name those bets, any new language becomes easy to place, and arguments about languages turn into arguments about trade-offs, which can actually be settled.

1.1Every language decides who pays, and when

Every program has to answer the same questions. Where does this piece of memory come from, and who gives it back? Is this value a number or a string, and what happens if someone treats it as the wrong one? What happens when two threads touch the same data? How does the text a person wrote become instructions a processor executes? A programming language is, more than anything else, a fixed set of answers to these questions. The syntax, the braces and keywords that people argue about online, is the least important part.

Each answer moves a cost somewhere. It can be paid by the programmer, who has to think about it and can get it wrong (C makes you free memory yourself). It can be paid by the compiler at build time, which rejects programs that might be wrong and makes builds slower (Rust's borrow checker, C++ templates). Or it can be paid by the runtime while the program runs, in CPU time and memory (a garbage collector in Java or Go, dynamic type checks in Python). Nothing makes the cost disappear. When a language looks effortless, look for where it moved the cost; when it looks strict, look at which mistakes it no longer lets you make.

This is also why one company runs many languages at once. A typical web company writes its browser front end in TypeScript, its business services in Java, Kotlin or Go, its data pipelines and machine learning in Python, its performance-critical infrastructure in C++ or Rust, and its glue in shell scripts. Each part has a different answer to "what is expensive here": developer time, latency, memory, safety, or the size of the hiring pool.

Why it matters

A senior engineer is expected to explain why a team should or should not use a language, not just which one they like. The useful vocabulary is the one in this chapter: memory model, type system, execution model, concurrency model, ecosystem. "Rust is fast and safe" is a slogan; "Rust moves memory-safety checks from run time and code review to compile time, at the price of a steeper learning curve and longer builds" is an argument.

1.2Five axes for comparing any language

Five properties explain most of the practical difference between languages. They are largely independent: knowing that a language is compiled tells you little about whether it has a garbage collector (Go is compiled and collected; Swift is compiled and reference-counted; Python is interpreted and reference-counted).

Memory management answers who frees memory: the programmer (C), the compiler at the end of a scope (C++ destructors, Rust), a reference counter (Python, Swift), or a tracing garbage collector (Java, C#, Go, JavaScript). The type system answers when types are checked (compile time or run time), how much the compiler infers, and which mistakes it can rule out, such as null pointers or data races. The execution model answers how source becomes machine code: compiled ahead of time to a native binary, interpreted from bytecode, or compiled just in time while the program runs. The concurrency model answers how a program does several things at once: operating-system threads with locks, lightweight green threads (goroutines, virtual threads), a single-threaded event loop with callbacks and async, or actors sending messages. The ecosystem covers the package manager, build tool, libraries, platforms, tooling, community and hiring pool, and it often decides more than the other four together.

1.3Where languages came from: a short family tree

Languages are easier to understand once you see what they reacted against. Almost every idea in a "modern" language is decades old; what changes is which ideas become affordable and which problems hurt most at the time.

Lisp (1958) introduced garbage collection, closures, and the idea that programs are data that other programs can manipulate. Simula (1967) and Smalltalk (1972) introduced classes, objects and message passing. C (1972) was designed to write Unix portably, close enough to the machine that the compiler output was predictable. ML (1973) brought type inference and algebraic data types; Haskell (1990) pushed purity and laziness as far as they go. C++ (1985) put Simula's classes on top of C without giving up C's performance, which became its defining principle: you do not pay for what you do not use.

The 1990s were about productivity and the internet. Python (1991) optimised for readable code and fast iteration. Java (1995) offered "write once, run anywhere" through a virtual machine and made garbage collection mainstream in enterprise software. JavaScript (1995) was built in about ten days to make web pages interactive and became, by accident of history, the only language every browser runs. C# (2000) was Microsoft's answer to Java.

The 2000s and 2010s reacted to multicore processors, cloud services and security failures. Go (released 2009, version 1.0 in 2012) was written at Google for large networked services, favouring fast builds and simple concurrency over expressiveness. Rust (1.0 in 2015, started at Mozilla) set out to give C++ performance with memory safety checked by the compiler. Kotlin (2016) modernised Java without leaving the JVM, Swift (2014) did the same for Objective-C on Apple platforms, and TypeScript (2012) added a static type system on top of JavaScript without changing what runs in the browser.

Interesting detail

Many "new" features are old ideas becoming cheap. Garbage collection existed in 1958 but was too slow for most systems software until the 1990s; closures existed in Scheme in 1975 and arrived in Java in 2014 (Java 8) and in C++ in 2011. Rust's ownership rules descend from research on linear and affine types and on region-based memory management (the Cyclone language, early 2000s).

1.4Paradigms: ways of organising a program

A paradigm is a way of structuring a program, a set of habits about what the main building blocks are. In imperative programming the program is a sequence of statements that change state: assign this, loop over that, update a counter. Procedural programming organises those statements into functions. Object-oriented programming bundles state with the functions that may change it, and uses polymorphism so that the caller does not need to know which concrete type it has. Functional programming builds programs from functions that return new values instead of changing old ones. Declarative programming describes the result you want (an SQL query, an HTML page, a Kubernetes manifest) and leaves the steps to an engine. Event-driven and reactive programming organise a program around things that happen: messages, clicks, data arriving over time.

Real languages mix paradigms, and good code in any language mixes them too. A modern Java service uses classes for its domain objects, streams and lambdas (functional) for collection processing, annotations and SQL (declarative) for persistence, and an event bus for integration. Rust has no inheritance but has traits, closures, iterators and pattern matching. The useful question is not "which paradigm is best" but "which paradigm makes this particular part of the program easiest to reason about". Chapters 9 and 10 answer that for each paradigm.

Pitfall

Treating a paradigm as an identity. "We are an OOP shop" leads to class hierarchies for data that only needed a function; "we are functional" leads to monad stacks for code that only needed a loop. Paradigms are tools; the cost of each shows up in how hard the code is to change later.

2From source text to running program

A processor only executes machine code. Every language has to get from the text a person wrote to those instructions, and the moment it does so (before shipping, at start-up, or while the program is running) shapes start-up time, peak speed, memory use, portability and how a program is deployed.

2.1Ahead-of-time compilation: decide everything before running

An ahead-of-time (AOT) compiler translates the whole program into machine code for a specific processor and operating system before it ever runs. C, C++, Rust, Go, Swift and Zig work this way. The compiler parses the source into a syntax tree, checks types, lowers the program into an intermediate representation, optimises it (inlining small functions, removing dead code, keeping values in registers, vectorising loops) and finally generates machine code. A linker joins the object files and libraries into an executable that the operating system can load directly. The steps are described in Build systems 2.2.

The advantage is that nothing remains to be done at run time: the first instruction executes at full speed, there is no compiler in memory, and the binary's behaviour is fixed and inspectable. In the running example the C, Rust and Go versions start in about one millisecond on an empty input. The price is that the compiler must decide everything without seeing real data. It does not know which branch is usually taken or which concrete type a function receives most often, unless you give it a profile (profile-guided optimisation, PGO), and the binary only runs on the platform it was compiled for. Cross-compiling for ARM servers, phones and x86 laptops means one build per target.

Go and Rust differ in a way that matters for deployment. Go links everything, including its runtime and garbage collector, into one static binary by default: copy one file into a minimal container image and it runs. Rust also links its own libraries statically but usually depends on the system C library; both produce binaries of a few megabytes (in the running example, 2.2 MB for Go and 4.3 MB for Rust before stripping symbols, 1.5 MB and 0.4 MB after). C and C++ binaries are smallest (20 to 40 KB) because they rely on shared system libraries that are already on the machine.

2.2Interpreters and bytecode: ship the source, pay per operation

An interpreter is a program that reads another program and carries out its operations one by one. Modern interpreters do not walk the source text; CPython, Ruby and Guile first compile the source into bytecode, a compact list of instructions for a virtual machine (CPython caches it in .pyc files), and then run a loop: fetch the next opcode, jump to the code that implements it, repeat.

Every operation pays for that dispatch, and in a dynamically typed language also for checking types at run time. When CPython executes total += v, it looks up the type of total, finds its addition method, checks the type of v, allocates or reuses an integer object for the result, and adjusts reference counts. A C compiler turns the same statement into one machine instruction. That is why the same loop takes 46 ms per million elements in CPython and 2.9 ms in C (Figure 2.2): roughly a factor of 15, which grows to 50 or more for arithmetic-heavy code.

Interpreters are still popular because the costs are often irrelevant and the benefits are large. There is no build step, so the edit-run cycle is instant; programs can inspect and modify themselves at run time; the same file runs on any machine with the interpreter. And much of the work in a real Python program is not done by the interpreter at all: in the running example the per-line split() and dictionary update are implemented in C inside CPython, which is why the Python version (0.75 s) is only about four times slower than C there, not fifteen. NumPy, PyTorch and pandas push this further: Python orchestrates, compiled code does the heavy work.

2.3JIT compilers: speculate, compile, and be ready to back out

A just-in-time (JIT) compiler combines the two approaches. The JVM (Java, Kotlin, Scala), .NET (C#, F#) and JavaScript engines (V8 in Chrome and Node, JavaScriptCore in Safari) start by interpreting bytecode, count how often each method and loop runs, and compile only the hot parts to machine code while the program is running. Because compilation happens late, the JIT knows things an AOT compiler can only guess: which class actually arrives at a virtual call site, which branch is never taken, that an array always holds small integers. It compiles speculatively for what it has seen, inlines aggressively, and inserts cheap guards that check the assumptions still hold.

When a guard fails, for example a JavaScript function that always received integers is suddenly called with a string, the engine deoptimises: it throws the optimised code away, reconstructs the interpreter's view of the stack frame, continues in the interpreter, and may recompile later with the new knowledge. This is what makes dynamic languages fast in practice. JavaScript has no static types, yet V8 runs the numeric loop at 4.3 ms because after a few iterations it has seen nothing but small integers and compiles accordingly.

Tiers exist because compiling costs time. An optimising compiler may spend milliseconds on one method, which is only worth it for code that runs millions of times. HotSpot (the standard JVM) therefore starts every method in the interpreter, compiles it with the fast C1 compiler after a few thousand calls, and with the optimising C2 compiler once it is clearly hot. -XX:+PrintCompilation on the warm-up experiment shows the loop being compiled by C2 (tier 4) about 40 ms after the JVM started, while the first iteration was still running: the JIT replaced the running loop with compiled code in the middle of the loop, called on-stack replacement.

Pitfall

Benchmarking a JIT language without warm-up. The first iteration of the Java loop takes 14 ms, later ones 2.9 ms. A microbenchmark that times one call measures the interpreter and the compiler, not your code. Use a harness that warms up (JMH for Java, Benchmark.js or mitata for JavaScript) and report steady-state and cold numbers separately; both matter, for different users.

In practice

Warm-up has real operational consequences. A freshly started Java service handles its first thousands of requests slowly, so deployments route traffic to new instances gradually, send synthetic warm-up requests, or use a Class Data Sharing archive and tiered compilation settings to shorten start-up. Serverless functions, which may start for a single request, are where JIT warm-up hurts most and where AOT languages (Go, Rust) or AOT-compiled Java (GraalVM Native Image) are preferred.

2.5The lines are blurring: AOT for managed languages, WebAssembly

The neat split of Figure 2.1 is less neat today. Java can be compiled ahead of time to a native executable with GraalVM Native Image, and .NET has Native AOT; both start in milliseconds and use far less memory, at the price of giving up some dynamic features (unrestricted reflection, loading classes at run time) and the JIT's profile-driven peak performance. WebAssembly (Wasm) is a portable bytecode designed to be compiled to fast machine code safely inside a sandbox. Browsers run it next to JavaScript, which lets C++, Rust or Go code run in a web page (Figma and Photoshop on the web are well-known examples), and server-side runtimes such as Wasmtime use it to run untrusted plug-ins with near-native speed and strong isolation. For a language designer it is simply one more back-end target, like x86 or ARM.

3Memory: who frees it, and when

Every object a program creates occupies memory that must eventually be given back. Freeing too late wastes memory; freeing too early or twice corrupts it. The four strategies languages use, manual freeing, scope-based ownership, reference counting and tracing garbage collection, differ in who decides when that moment has come, and each pays for the decision differently.

3.1Manual memory management: the programmer decides

In C, memory on the heap is requested with malloc and returned with free, and nothing in the language connects the two. The compiler does not know who owns a pointer, how long the memory behind it is needed, or whether some other part of the program still holds a copy of the address. The running example shows the everyday version of this problem: the C program copies each new path into the hash table with strdup, and the comment next to it asks "who frees this?". The honest answer is "nobody, the process exits", which is fine for a tool that runs for half a second and a leak in a server that runs for a month.

Getting it wrong produces three families of bugs. A leak frees too late or never; the process grows until it is killed. A use after free keeps using a pointer after the memory was returned; by then the allocator may have handed the same bytes to someone else, so a read returns another object's data and a write corrupts it. A double free returns the same block twice and corrupts the allocator's own bookkeeping. Add buffer overflows (writing past the end of an array, a spatial error rather than a temporal one) and you have the bug classes behind most serious security vulnerabilities in C and C++ software (Section 3.7).

Manual management survives because it gives complete control. An embedded system can allocate everything at start-up and never again; a game engine can allocate a frame's temporary data from an arena (one large block handed out by moving a pointer) and release the whole arena at the end of the frame in one operation. That control is exactly what C programmers mean when they call the language predictable.

3.2Scope-based ownership: the compiler decides, at the end of a scope

C++ answered the problem with RAII (resource acquisition is initialisation): tie each resource to an object whose destructor releases it, and let the compiler call the destructor when the object goes out of scope. A std::string or std::vector frees its buffer when the variable that owns it ends; a std::unique_ptr deletes what it points to; a lock guard unlocks. The free is inserted by the compiler at a point you can see in the source, so it is deterministic and costs nothing beyond the free itself. The C++ details are in C and modern C++, owners and borrowers.

RAII solves leaks and double frees for code that follows the rules, but it cannot stop a non-owning pointer or reference from outliving its owner. A reference into a vector, an iterator, a std::string_view or a raw pointer from get() can all dangle, and the compiler will not complain. Rust keeps RAII (it calls the destructor drop) and adds the missing piece: the compiler tracks every borrow and rejects programs where a reference could outlive the value it points to or coexist with a mutation. Chapter 5 shows how. The result is the same run-time behaviour as C++ (no collector, deterministic frees) with the dangling-pointer class of bugs ruled out at compile time.

3.3Reference counting: the last owner turns out the light

Reference counting keeps a counter in every object: how many references point to it. Copying a reference increments the counter, dropping one decrements it, and when it reaches zero the object is freed immediately. CPython uses it for every object (Python 3.1), Swift and Objective-C use it under the name ARC (automatic reference counting, with the compiler inserting the increments and decrements), and C++ offers it explicitly as std::shared_ptr, Rust as Rc and Arc.

Its attraction is that memory comes back as soon as it is unused, without pauses and without a background collector, so resources such as files and sockets are released at predictable moments. Its costs are less obvious. Every copy of a reference writes to memory, even when the program only reads the object; when references are shared between threads, the counter must be updated with atomic instructions, which are several times slower than ordinary ones and contend between cores (this is one reason Python had a global interpreter lock for decades). Freeing the head of a long linked list frees the whole list at once, which is a pause after all. And reference counting cannot free cycles: a parent that points to its child and a child that points back keep each other's counts above zero forever. Swift asks programmers to break cycles with weak references; CPython runs an additional cycle-detecting collector periodically; C++ and Rust offer weak_ptr and Weak.

Pitfall

Using shared_ptr or Arc everywhere "to be safe". Shared ownership hides the question of who is responsible for an object's lifetime, adds atomic traffic on every copy and makes cycles likely. Default to a single owner and borrowed references; reach for shared ownership only when several parties genuinely need to keep an object alive and you cannot say which one ends last.

3.4Tracing garbage collection: find what is still reachable

A tracing garbage collector turns the question around. Instead of tracking when each object stops being referenced, it periodically finds every object that can still be reached and frees everything else. The starting points, called roots, are the places the program can access directly: local variables on every thread's stack, global variables, and CPU registers. Anything reachable by following pointers from a root might still be used; anything else cannot be, because the program has no way to get to it. Java, C#, Go, JavaScript, Lisp, Haskell and most other managed languages use tracing collection.

At the start of a cycle every object is white. The collector knows the roots: the pointers in stack frames, globals and registers.

Objects referenced directly by roots become black once scanned, and each object they reference becomes grey: known to be live, but its own pointers are not yet followed. The grey set is the collector's work list.

The collector takes grey objects one by one, follows their pointers and shades what it finds grey, until no grey object is left. Every reachable object is now black. The work is proportional to the number of live objects and pointers, not to the garbage.

Everything still white is garbage, including the cycle F ⇄ G and the isolated H, and its memory is returned. Some collectors do not sweep at all: they copy live objects elsewhere and reuse the whole old area (Section 3.5).

Two properties follow. First, the program never frees anything explicitly, so use-after-free and double free cannot happen, and cycles are not a problem. Second, garbage is not freed when it becomes garbage but at the next collection, so a collected program needs headroom: more memory than its live data, to hold the garbage that accumulates between collections. How much headroom, and how much CPU the collector uses, is the main tuning question of every garbage-collected service, and it is a direct trade-off (Section 3.6).

Interesting detail

The collector must know exactly which words in memory are pointers. Java, Go and C# compilers emit maps for every stack frame and object layout; this is called precise collection. Collectors added to languages without such maps (the Boehm collector for C) are conservative: any word that looks like an address into the heap is treated as a pointer, which occasionally keeps garbage alive but never frees live data.

3.5Generational, compacting and concurrent collectors

A naive mark and sweep stops the whole program ("stop the world") while it marks, which on a heap of several gigabytes can take seconds. Modern collectors use three ideas to avoid that.

Generations. Most objects die young: the strings created while parsing a request are garbage before the response is sent. A generational collector allocates new objects in a small young generation (the nursery) and collects it often. Because almost everything there is dead, a young collection only has to touch the few survivors, copying them to an older area; objects that survive several collections are promoted to the old generation, which is collected rarely. The JVM's collectors and .NET's are generational; ZGC became generational in Java 21.

Compaction and bump allocation. A collector that copies survivors leaves the nursery completely empty afterwards, so the next allocation can simply hand out the next free address and move a pointer forward. Allocation in Java or C# is therefore often faster than malloc in C: a few instructions, no search for a free block, and no fragmentation, because objects are packed together when they are copied. The price is that objects move, so the collector must update every pointer to them.

Concurrency. Marking can run on other cores while the program continues, if the program and the collector cooperate. The difficulty is that the program keeps changing pointers during marking; if it stores a pointer to a white object into an already black object, the collector would never see it and would free a live object. A write barrier, a few instructions the compiler adds to every pointer store, reports such stores to the collector. With barriers, the remaining stop-the-world pauses only scan stacks and switch phases. Go's collector is concurrent, non-generational and non-moving, tuned for low pauses; Java's ZGC and Shenandoah are concurrent and compacting, with pauses typically below a millisecond regardless of heap size; G1, Java's default since version 9, aims for a configurable pause target such as 200 ms.

In practice

Pauses are no longer the main cost of a modern collector; CPU and memory are. In the Go experiment of Section 3.6 the longest pause in any configuration was 2.1 ms and the total pause time over a full second of heavy allocation was 1 to 12 ms, while the collector used between 2 % and 29 % of four CPU cores. Discord's well-known 2020 move of one service from Go to Rust was about latency spikes caused by a collection that Go then forced every two minutes on a large, mostly idle heap; the general lesson is to measure GC CPU and tail latency of your own workload before rewriting anything.

3.6The garbage-collection trade-off: memory against CPU

Every tracing collector has to decide when to start a cycle. Go exposes the decision as one number, GOGC: a new cycle starts when the heap has grown by GOGC percent over the live data left after the previous cycle. With the default of 100 and 60 MB of live data, the heap may grow to 120 MB before the next collection. A cycle costs roughly the same CPU however much garbage it frees, because marking only touches live objects. So the more headroom you allow, the fewer cycles run, and the cheaper collection becomes per byte allocated.

This gives a strikingly simple first-order model. Between two cycles the program allocates live × GOGC/100 megabytes, so at an allocation rate of R MB/s the collector runs R / (live × GOGC/100) times per second, each time scanning the live heap. The CPU spent is therefore proportional to R / GOGC: the live heap size cancels out. Doubling GOGC halves the GC CPU and costs one more live heap's worth of memory. A bigger live heap costs memory, not CPU, as long as GOGC stays the same.

3.7Memory safety: the industry's largest bug class

A language is memory safe if a program written in it cannot read or write memory it is not entitled to: no out-of-bounds access (spatial safety), no use of freed memory (temporal safety), no reading uninitialised memory, and in a concurrent program no data races on that memory. Java, C#, Go, Python, JavaScript and safe Rust are memory safe; C and C++ are not, because their pointers carry no bounds or lifetime information and their compilers are allowed to assume such errors never happen (they are undefined behaviour, see C and modern C++, how the optimiser uses undefined behaviour).

The consequences are measurable. Microsoft reported in 2019 that about 70 % of the security vulnerabilities it fixed each year were memory-safety issues; the Chromium project reported the same share for its serious security bugs in 2020. Google's Android team has published the most convincing counter-experiment: from 2019 Android wrote new system code in memory-safe languages (Rust, Kotlin, Java) while leaving most existing C and C++ in place, and the share of memory-safety vulnerabilities fell from about three quarters to below 20 % in 2025, because vulnerabilities concentrate in new code. Google estimates its Rust code at about 0.2 memory-safety vulnerabilities per million lines against roughly 1,000 for its historical C and C++, and reports that Rust changes are rolled back about four times less often and spend about 25 % less time in code review.

Governments followed. The US National Security Agency and CISA have published guidance since 2022 urging software makers to adopt memory-safe languages for new code and to publish memory-safety roadmaps for existing products, most recently the joint information sheet Memory Safe Languages: Reducing Vulnerabilities in Modern Software Development (June 2025). Nobody expects billions of lines of C and C++ to be rewritten; the realistic strategy is the one Android used: write new components in memory-safe languages, harden the old code (bounds-checked standard libraries, sanitizers in testing, fuzzing, see Software quality 5.2), and put the most exposed parts, such as parsers of untrusted input, behind a memory-safe boundary.

Why it matters

For a C++ engineer this is the single biggest change in the language landscape of the last decade. Memory safety used to be argued as a matter of taste; it is now a procurement and regulatory topic. C++ is responding with hardened standard library modes and safety profiles (C++26), but the comparison point customers and security teams use is Rust.

4Type systems: what the compiler can promise

A type system is a way of proving, before or while the program runs, that certain mistakes cannot happen: adding a string to a number, calling a method that does not exist, forgetting that a lookup can fail. Languages differ in which mistakes they rule out, when they check, and how much they make you write down to get there.

4.1Static or dynamic, strong or weak: two separate questions

Two questions are often mixed up. The first is when types are checked. A statically typed language (C, C++, Rust, Go, Java, Kotlin, C#, Haskell, TypeScript) checks types at compile time; a program with a type error does not build. A dynamically typed language (Python, Ruby, JavaScript, Lisp) attaches the type to the value at run time and checks it when an operation happens; a type error is an exception raised in production, possibly months after the code was written, on the one path no test covered.

The second question is how strictly types are enforced, usually called strong versus weak typing. Python is dynamic but strong: '1' + 1 raises a TypeError. JavaScript is dynamic and weak: '1' + 1 is the string '11' and '1' * 2 is the number 2, because the language converts silently. C is static but weak in a different way: int x = 3.9; compiles and quietly truncates, and any pointer can be cast to any other. Rust and Haskell are static and strong: they convert nothing implicitly, not even an i32 to an i64.

Static typing pays off in proportion to the size of the code base and the number of people changing it. The compiler finds every caller that breaks when a function's signature changes, editors can complete and navigate code reliably, and types document intent where comments would go stale. Dynamic typing pays off in small programs, exploratory work and code that manipulates data whose shape is not known in advance. Large organisations that started dynamic tend to add static checking later rather than rewrite: Microsoft created TypeScript for large JavaScript code bases, Facebook built the Hack language on PHP and Flow for JavaScript, Dropbox and Instagram adopted type hints and mypy for millions of lines of Python.

Interesting detail

A type system is sound if a well-typed program can never hit a type error at run time. Java's and Rust's (safe subset) are designed to be sound; TypeScript's is deliberately unsound, trading guarantees for compatibility with existing JavaScript (array covariance, any, unchecked index access). That is a reasonable engineering choice, but it means a TypeScript type is a strong hint, not a proof.

4.2Nominal and structural typing: by name or by shape

When is a value of type A acceptable where type B is expected? In a nominal type system the answer depends on declared names: a Java class is a Comparable only if it says implements Comparable. In a structural system it depends on shape: anything with the right fields or methods fits. Go interfaces are structural: a type satisfies io.Reader simply by having a Read method with the right signature, without ever mentioning io.Reader, which lets you define an interface after the fact for types you do not own. TypeScript is structural throughout, which suits JavaScript, where objects are usually built ad hoc from JSON.

The type experiment in experiments/types/structural.ts shows both the convenience and the checks. An object literal with an extra latencyMs field is accepted where a Hit is expected because it has the required shape. The other three calls are rejected by tsc --strict:

structural.ts(11,9): error TS2345: Argument of type 'Hit | undefined' is not assignable to parameter of type 'Hit'.
  Type 'undefined' is not assignable to type 'Hit'.
structural.ts(17,9): error TS2345: Argument of type 'unknown' is not assignable to parameter of type 'Hit'.
structural.ts(19,23): error TS2322: Type 'string' is not assignable to type 'number'.

The first error is the important one: Map.get returns Hit | undefined, and the compiler will not let you pass it on until you have handled the missing case. The second shows the difference between TypeScript's two escape hatches: a value typed any (line 14) is accepted anywhere and silently switches checking off, while unknown must be narrowed by a check before use. Nominal typing's advantage is the reverse of structural typing's: two types with the same shape but different meanings, such as UserId and OrderId both holding a string, cannot be mixed up. Structural languages simulate this with "branded" types.

4.3Generics: three ways to write code once for many types

Generic code works for any type that meets some requirement: a sorted list of anything comparable, a cache of anything hashable. Languages implement it in three fundamentally different ways, and the choice explains several otherwise puzzling differences between them.

Monomorphisation (C++ templates, Rust generics) generates a separate copy of the function for every type it is used with, each optimised as if written by hand for that type. That is why std::sort on integers is as fast as hand-written C, and why heavily generic C++ and Rust code compiles slowly and produces large binaries. Type erasure (Java, Kotlin, Scala on the JVM) compiles one copy that works on Object references and inserts casts at call sites. A List<Integer> therefore holds pointers to individually allocated Integer objects, and at run time a List<String> and a List<Integer> are the same class, which is why Java cannot write new T() or overload on List<String> versus List<Integer>. Erasure was chosen in 2004 so that generic code would run on existing JVMs; C#, designed later, keeps generic types at run time and specialises them for value types. Dictionary passing (Haskell type classes, Swift, Go since 1.18) compiles shared code and passes a table of the type's operations as a hidden argument. Go uses a hybrid it calls GC-shape stenciling: one copy per memory layout (all pointer types share one), plus a dictionary.

Talk track

"Rust and C++ generics are zero-cost at run time because the compiler stamps out a specialised copy per type, and you pay in compile time and binary size. Java's generics are erased, so there is one copy and boxing; that's why Java collections of primitives are slow and why Project Valhalla exists. Go chose a middle path to keep builds fast."

4.4Null, Option and algebraic data types

Tony Hoare introduced the null reference in ALGOL W in 1965 and in 2009 called it his "billion-dollar mistake". The problem is that in Java, C# (before nullable reference types), C, C++ and Go, every reference type silently includes one extra value that is not a valid object, and the type system does not track which references might be null. Every NullPointerException is a type error the compiler could not see.

Newer languages make absence explicit. Rust has no null; a value that might be missing has type Option<T>, which is either Some(value) or None, and you cannot use the value without handling both cases. Kotlin, Swift, TypeScript with strictNullChecks, and C# with nullable reference types distinguish String from String? and force a check before the nullable one is used, which is exactly the TypeScript error shown in Section 4.2.

Option is one example of an algebraic data type, specifically a sum type: a value that is exactly one of several variants, each with its own data. Combined with pattern matching that the compiler checks for exhaustiveness, sum types let you model a domain so that illegal states cannot be represented. A payment is Pending, Captured { amount } or Refunded { amount, reason }; there is no combination of nullable fields and boolean flags where a refunded payment has no reason. When someone adds a fourth variant, every match that does not handle it stops compiling, so the compiler lists the places to change. Rust's enum, Kotlin's and Java's sealed types with switch patterns (Java 21), Swift's enum, TypeScript's discriminated unions and C++'s std::variant all provide this, with different degrees of convenience.

enum Payment {
    Pending,
    Captured { amount_cents: u64 },
    Refunded { amount_cents: u64, reason: String },
}

fn balance(p: &Payment) -> i64 {
    match p {                          // must cover every variant, or it does not compile
        Payment::Pending => 0,
        Payment::Captured { amount_cents } => *amount_cents as i64,
        Payment::Refunded { .. } => 0,
    }
}

4.5Gradual typing: adding types to dynamic languages

Gradual typing lets a dynamically typed code base acquire static types one file or one function at a time. TypeScript does this for JavaScript and Python's type hints (with checkers such as mypy and pyright) for Python. Unannotated code is treated as any and keeps working; annotated code is checked; the boundary moves as the team adds types.

Two facts about gradual typing are often misunderstood. First, the types are erased: TypeScript compiles to plain JavaScript, and Python ignores annotations at run time, so a type says nothing about data that arrives from the network. A JSON response typed as Hit is a Hit only because someone said so; services validate untrusted input at the boundary with a schema library (Zod in TypeScript, Pydantic in Python) that checks the data and produces a typed value. Second, the guarantee is only as good as the number of anys. A strict configuration (strict: true, no implicit any, unknown for external data) is what makes the investment pay off.

Numbers

TypeScript's compiler was itself rewritten for speed: TypeScript 7 replaces the JavaScript implementation with a native one written in Go, which Microsoft reports as about ten times faster on large projects; the 7.0 release candidate was published in June 2026, with 6.0 as the last JavaScript-based version. The container used for this chapter has tsc 6.0.2.

4.6Type inference: static types without writing them everywhere

Static typing used to mean writing std::map<std::string, std::vector<int>>::iterator. Type inference lets the compiler work types out from context. Local inference (auto in C++, var in Java and C#, := in Go, let in Rust, Kotlin, Swift and TypeScript) infers a variable's type from its initialiser. The ML family goes further with Hindley–Milner inference, which can infer the types of whole functions, including their generic parameters, without a single annotation; Haskell and OCaml programs often contain no types except at module boundaries.

Rust deliberately stops in between: types are inferred inside a function body (even from later uses, as in let mut errors = HashMap::new(); whose key and value types come from the first insert), but every function signature must be written out. The reasoning is that signatures are the contract other people read and depend on, and inferring them would let an internal change silently alter a public interface. Most modern languages land on the same compromise.

Pitfall

Inference hiding the type a reader needs. auto x = compute(); is fine when compute obviously returns a count; it is a trap when the type decides behaviour, such as an integer type that may overflow, an iterator that may be invalidated, or a proxy object such as std::vector<bool>::reference.

5Rust in depth: memory safety without a garbage collector

Rust's claim is that you can have C++-level control and performance and still rule out use-after-free, double free, dangling references and data races, by having the compiler check a small set of ownership rules. This chapter explains those rules from the mechanism up, shows what the compiler actually says when you break them, and is honest about what Rust costs.

5.1Why Rust exists

Until Rust, a language designer had to choose. Garbage-collected languages are memory safe but need a runtime, extra memory and some unpredictability, which rules them out for operating-system kernels, browsers' rendering engines, embedded firmware, databases and latency-critical infrastructure. C and C++ give the control those systems need but leave memory safety to the programmer, and decades of experience (Section 3.7) show that even excellent programmers with code review, sanitizers and fuzzing do not achieve it at scale.

Rust started as a personal project of Graydon Hoare in 2006, was sponsored by Mozilla from 2009 to build a safer browser engine, and reached 1.0 in 2015. Its key observation is that most memory bugs come from one pattern: aliasing combined with mutation. A use-after-free is a pointer (an alias) that survives while the owner frees the memory (a mutation); iterator invalidation is an iterator that survives while the container reallocates; a data race is two threads holding aliases where at least one writes. If the compiler can guarantee that at any moment a piece of data has either any number of readers or exactly one writer, and that no reference outlives its data, all of these bugs become impossible. Ownership, borrowing and lifetimes are the rules that let the compiler check exactly that, without any run-time machinery.

Talk track

"Rust's core rule is 'shared XOR mutable': many readers or one writer, never both. Combine it with single ownership and compile-time lifetime checks and you rule out use-after-free and data races without a garbage collector. The cost moves to compile time and to the programmer's learning curve."

5.2Ownership and moves: every value has exactly one owner

The first rule is that each value has exactly one owning variable, and the value is dropped (its destructor runs and its memory is freed) when the owner goes out of scope. So far this is C++'s RAII. The difference is what assignment means. In C++, b = a for a string copies the characters unless you write std::move, and after a move a is still a valid, unspecified object you may accidentally use. In Rust, assigning or passing a value that owns resources moves it: ownership transfers, and the compiler forbids any further use of the old variable. There is nothing to accidentally use.

String::from allocates four bytes on the heap and stores pointer, length and capacity in a. a is the owner: when it goes out of scope, the bytes will be freed.

let b = a; copies the three words into b and marks a as moved. No heap copy happens, and any later use of a is a compile error (E0382). Only one variable will ever free these bytes.

let r = &b; creates a reference: a plain pointer at run time, but the compiler records that b is borrowed. While r is in use, b cannot be modified, moved or dropped.

At the closing brace b is dropped and the heap bytes are freed. The compiler inserted that call; it knows a was moved, so it does not drop it again.

Here is the error from experiments/borrow/e1_move.rs, where a vector of paths is passed to a function by value and then used again:

error[E0382]: borrow of moved value: `paths`
 --> e1_move.rs:5:24
  |
3 |     let paths = vec![String::from("/api/orders")];
  |         ----- move occurs because `paths` has type `Vec<String>`, which does not implement the `Copy` trait
4 |     let n = consume(paths);          // ownership moves into consume
  |                     ----- value moved here
5 |     println!("{n} {}", paths[0]);    // use after move
  |                        ^^^^^ value borrowed here after move
help: consider cloning the value if the performance cost is acceptable

The compiler also suggests the two real fixes: let consume borrow (&[String]) instead of taking ownership, or clone if a copy is really wanted. Small plain values such as integers, floats and booleans implement the Copy trait, so assigning them copies, as in C. Everything that owns a resource moves.

5.3Borrowing: many readers or one writer

Moving ownership everywhere would be impractical, so Rust lets you borrow a value: &T is a shared reference that allows reading, &mut T a mutable reference that allows writing. The borrow rules are the core of the language: at any point, a value may have any number of shared references or exactly one mutable reference, but not both; and no reference may outlive the value. Both are checked at compile time by the borrow checker; at run time a reference is just a pointer.

The classic bug these rules catch is invalidation. A reference to the first element of a vector points into the vector's heap buffer; pushing another element may need a bigger buffer, so the vector allocates a new one, moves the elements and frees the old buffer, and the reference now points to freed memory. In C++ that compiles without a warning. The C++ twin in experiments/borrow/alias.cpp, built with g++ -Wall -Wextra, produces no diagnostics and prints 1688350891 instead of 12 (a different garbage number each run, at -O0 and -O2 alike); only AddressSanitizer catches it, and only when the bad path actually runs in a test:

==3183==ERROR: AddressSanitizer: heap-use-after-free on address 0x… at pc 0x… bp 0x… sp 0x…
READ of size 4 at 0x… thread T0
    #0 0x… in main alias.cpp:8
freed by thread T0 here:
    #0 0x… in operator delete(void*, unsigned long)
    #1 0x… in std::__new_allocator<int>::deallocate(int*, unsigned long)

The Rust version does not compile:

error[E0502]: cannot borrow `latencies` as mutable because it is also borrowed as immutable
 --> e2_alias.rs:4:5
  |
3 |     let first = &latencies[0];       // shared borrow into the vector's buffer
  |                  --------- immutable borrow occurs here
4 |     latencies.push(40);              // may reallocate the buffer
  |     ^^^^^^^^^^^^^^^^^^ mutable borrow occurs here
5 |     println!("{first}");
  |                ----- immutable borrow later used here

The compiler does not reason about reallocation at all. It only sees that push takes &mut self while a shared borrow is still alive, which the rule forbids. That is the strength of the design: one simple, local rule covers a whole family of bugs, including ones the language designers never listed.

Interesting detail

The string version of the C++ bug, alias_string.cpp, printed garbage at -O2 but was not reported by AddressSanitizer. The reads of the dangling std::string happen inside libstdc++'s precompiled code, which was not built with ASan instrumentation. Sanitizers see only what was compiled with them, one more reason dynamic tools complement rather than replace a compile-time guarantee.

Why it matters

"Shared XOR mutable" is also what makes optimisation easier. A Rust compiler knows that while you hold a &mut, nobody else can see the data, which is the information C's restrict keyword tries to give and that C++ compilers usually cannot assume. It is also exactly the condition for the absence of data races, which is why the same rules make concurrency safe (Section 5.5).

5.4Lifetimes: how long a reference is valid

A lifetime is the region of the program during which a reference is valid. Inside one function the compiler works lifetimes out by itself. They appear in the source only at function boundaries, when a function returns a reference and the compiler needs to know which input it borrows from. The function in e3_dangling.rs returns a reference to a local String that is freed when the function returns, the textbook dangling pointer:

error[E0106]: missing lifetime specifier
 --> e3_dangling.rs:1:22
  |
1 | fn longest_path() -> &str {
  |                      ^ expected named lifetime parameter
  = help: this function's return type contains a borrowed value, but there is no value for it to be borrowed from
help: instead, you are more likely to want to return an owned value
1 + fn longest_path() -> String {

A function that does borrow from its inputs declares the relationship with a lifetime parameter: fn longer<'a>(x: &'a str, y: &'a str) -> &'a str says "the result is valid as long as both inputs are". Callers are then checked against that contract without looking at the function's body, which keeps checking local and fast. Most signatures need no annotation because of elision rules: with one reference input, or a &self method, the output is assumed to borrow from it.

Lifetimes are where Rust's learning curve is steepest, mostly because they reveal designs that were fragile all along. A struct that stores references to data owned elsewhere, a graph with parent pointers, a callback that captures a reference to its caller: all of these need either a clear owner (store indices into a vector instead of pointers, use an arena) or explicit shared ownership (Rc, Arc). Experienced Rust programmers say the borrow checker changed how they design C++ too.

Pitfall

Fighting the borrow checker with .clone() and Rc<RefCell<T>> everywhere. It compiles, but it moves checks to run time (RefCell panics on a conflicting borrow) and hides the ownership design that the compiler was asking for. When the checker objects, the first question is "who should own this data?", not "how do I silence this error?".

5.5Fearless concurrency: Send and Sync

A data race is two threads accessing the same memory at the same time, at least one of them writing, without synchronisation. In C++ it is undefined behaviour (Concurrency 2.3) and finding one may take weeks. Rust prevents data races at compile time with the same borrow rules plus two marker traits that the compiler derives automatically for every type. A type is Send if a value of it may be moved to another thread, and Sync if references to it may be shared between threads. thread::spawn requires its closure to be Send and to own everything it captures (the 'static bound), and that is enough.

Trying to increment a local counter from four threads (e4_race.rs) fails because the closures would borrow count mutably, four times, while it might go out of scope before the threads end (E0597 and E0502). Trying to share a reference-counted vector with Rc (e5_rc.rs) fails because Rc's counter is a plain integer and two threads updating it would race:

error[E0277]: `Rc<Vec<i32>>` cannot be sent between threads safely
 --> e5_rc.rs:6:19
  |
6 |     thread::spawn(move || println!("{}", s2.len())).join().unwrap();
  |     ------------- -------^^^^^^^^^^^^^^^^^^^^^^^^^
  |     |             `Rc<Vec<i32>>` cannot be sent between threads safely
  = help: within `{closure@e5_rc.rs:6:19}`, the trait `Send` is not implemented for `Rc<Vec<i32>>`

The fix is to use the thread-safe tools, and the compiler accepts them because their types say they are safe. Arc is Rc with an atomic counter, so it is Send and Sync; Mutex<T> owns the data it protects, and the only way to reach the data is through lock(), which returns a guard that unlocks when dropped. ok_arc.rs increments a shared counter 100,000 times from each of four threads and always prints 400000.

let count = Arc::new(Mutex::new(0u64));
let handles: Vec<_> = (0..4).map(|_| {
    let count = Arc::clone(&count);           // each thread owns a handle
    thread::spawn(move || {
        for _ in 0..100_000 { *count.lock().unwrap() += 1; }   // guard unlocks at end of statement
    })
}).collect();
for h in handles { h.join().unwrap(); }
println!("{}", *count.lock().unwrap());       // 400000
Pitfall

"Fearless" covers data races, not every concurrency bug. Rust still lets you write deadlocks (two mutexes locked in opposite orders), race conditions at a higher level (check-then-act across two separate lock acquisitions), and starvation. The compiler guarantees memory stays consistent; it cannot know your protocol.

5.6unsafe: the escape hatch, and how it is contained

Some correct programs cannot be expressed within the borrow rules: a doubly linked list, a lock-free queue, a call into a C library, a memory-mapped hardware register. For these Rust has unsafe blocks, inside which five extra operations are allowed, the important ones being dereferencing raw pointers and calling functions marked unsafe (including all foreign C functions). Everything else is still checked: unsafe does not switch off the borrow checker for references, it adds raw pointers that it does not check.

The idea is containment. The standard library's Vec, HashMap, Mutex and Arc are written with unsafe inside, but they expose a safe interface whose correctness is argued once, carefully, by experts, and then relied upon by everyone. An application typically has no unsafe at all, or a few dozen lines in one module that wraps a C library; a reviewer or auditor knows exactly where to look, and tools such as Miri (an interpreter that detects undefined behaviour in unsafe code) and cargo-geiger (which counts unsafe in dependencies) help. Compare C++, where every line is potentially unsafe.

In practice

Interfacing with C is the most common reason for unsafe. Tools generate the declarations (bindgen from C headers; cbindgen the other way), and the cxx crate generates a safe bridge between Rust and C++ for both sides. A typical migration wraps a C or C++ library behind a small, safe Rust API and writes new code against that API.

5.7Errors as values: Result and the ? operator

Rust has no exceptions. A function that can fail returns Result<T, E>, a sum type that is either Ok(value) or Err(error). The caller cannot get at the value without deciding what to do about the error, and the ? operator makes the common decision, "pass it up to my caller", one character long. The running example's main returns std::io::Result<()>, and File::open(path)? returns early with the I/O error if the file cannot be opened.

The effect is that every place an error can arise is visible in the code, as a ?, and every function's signature says whether it can fail. Go makes the same choice with its value, err := convention, but without the type system forcing you to look at err; Java's checked exceptions tried to make failure part of the signature and became unpopular because they did not compose with lambdas and generic code. For bugs that should never happen (an index out of bounds, a violated invariant) Rust has panic!, which unwinds the thread or aborts the process; panics are not for expected failures such as a missing file.

5.8Traits and zero-cost abstractions

Rust has no classes and no inheritance. Behaviour is described by traits, sets of methods a type can implement, similar to Java interfaces or C++20 concepts, and closer still to Haskell's type classes. Generic functions are constrained by traits (fn top<T: Ord>(items: &mut [T])) and monomorphised (Section 4.3), so a call through a trait bound is as fast as a direct call and can be inlined. When you do want run-time polymorphism, for example a list of different handler types, you ask for it explicitly with dyn Trait, which uses a vtable exactly like a C++ virtual call.

The same principle runs through the language: high-level code should compile to what you would have written by hand. Iterator chains such as lines().filter(...).map(...).sum() compile to a plain loop with no intermediate collections; Option<&T> takes no more space than a raw pointer because the compiler uses the null value, which a reference can never have, to represent None.

Numbers

Zero-cost abstraction does not mean zero-cost code. The idiomatic Rust version of the running example takes 0.38 s; a tuned version (errcount_fast.rs) that reuses one line buffer and does not build a vector per line takes 0.14 s, faster than the C version (0.17 s). Neither change is about the language: the idiomatic code allocates a String and a Vec for each of two million lines. The same is true in every language in Chapter 8.

5.9Rust in industry

Rust has moved from enthusiast language to infrastructure in under a decade, mostly in places where C and C++ used to be the only option. The Linux kernel accepted Rust as a second language for drivers in version 6.1 (December 2022), and at the 2025 Maintainers Summit the "Rust experiment" was declared concluded: Rust is a permanent part of the kernel. Android has supported Rust for platform code since 2021 and writes a growing share of its new native code in it, with the vulnerability results described in Section 3.7. Microsoft ships Rust inside the Windows kernel (parts of the graphics subsystem); Cloudflare replaced NGINX in much of its edge with Pingora, its own Rust proxy; AWS built Firecracker, the micro-VM monitor behind Lambda and Fargate, in Rust; and Rust is the default choice for new command-line tools, databases' storage engines, WebAssembly components and blockchain systems.

The common thread is that these are places where memory-safety bugs are expensive (they become security vulnerabilities) and where a garbage collector is unwelcome (kernels, proxies with tight latency budgets, embedded devices). Where neither is true, for a typical business service, Rust competes on reliability and performance against Go, Java and C#, and the case is weaker because those languages are memory safe too and easier to hire for.

In automotive

Safety standards such as ISO 26262 require a qualified toolchain. Ferrocene, a Rust compiler distribution by Ferrous Systems, has been qualified since 2023 for ISO 26262 up to ASIL D and IEC 61508 up to SIL 4, which makes Rust usable for safety-related ECU software in principle; certified libraries and process guidance (the equivalent of MISRA) are still maturing, so adoption is mostly in new, non-safety or QM components for now.

5.10What Rust costs

The honest list is short but real. The learning curve is steep for the first months: ownership and lifetimes force design decisions earlier than other languages do, and experienced C++ programmers often need to unlearn patterns such as long-lived pointers into shared mutable structures. Compile times are long, for the same reasons as C++ (monomorphisation, heavy optimisation through LLVM) plus the borrow checker; incremental builds help, but large Rust projects invest in build caching just like C++ ones. Interop with C++ works but is not seamless: templates, exceptions and inheritance do not cross the boundary, so a mixed code base needs a deliberate C-style or cxx bridge. The ecosystem is excellent for networking, command-line and systems work but thinner than C++ for GUIs, game engines, scientific computing and safety-certified libraries. And hiring: there are far fewer experienced Rust developers than C++, Java or Python developers, although developers are often keen to learn it.

Talk track

"I'd choose Rust where a memory-safety bug is a security incident and a garbage collector is not acceptable: network-facing parsers, agents, infrastructure, new low-level components. I would not rewrite a working C++ code base wholesale; I'd add Rust at the edges where untrusted data comes in, behind a narrow interface, and grow it from there. The main costs are ramp-up time and build times, not run-time performance."

6Concurrency models across languages

A backend service spends most of its time waiting: for the network, the database, another service. How a language lets thousands of such waits overlap, with operating-system threads, lightweight threads managed by the runtime, an event loop, or actors that exchange messages, shapes how its code looks, how it fails and how far it scales on one machine.

6.1Threads and locks: the baseline

The oldest model maps each concurrent activity to an operating-system thread and protects shared data with locks. C, C++, Java (before version 21), C# and Rust all start here. It is a direct model: the code reads sequentially, a blocking call blocks only its own thread, and the kernel schedules threads across cores. Its details, the memory model, atomics, mutexes and condition variables, are in Concurrency 1.2 and the chapters after it.

The limit is cost per thread. Each OS thread has a kernel structure, a kernel stack and a user stack (8 MB of reserved address space by default on Linux, of which only touched pages consume memory), and creating, destroying and switching between threads takes microseconds and a trip into the kernel. A server that gives every connection its own thread works for hundreds or a few thousand connections and degrades beyond that. Measured in experiments/threads, starting 10,000 threads that each wait on a barrier took 334 ms and 98 MB resident memory in Rust (with stacks reduced to 64 KB), and 2.5 s and 486 MB as Java platform threads. A busy web service may have 100,000 concurrent requests, most of them waiting on I/O; one thread each does not fit.

The three alternatives below all decouple "a concurrent activity" from "an OS thread". The runtime multiplexes many cheap activities onto a few threads, and when an activity waits for I/O, its thread runs another one instead of blocking.

6.2Goroutines and channels: cheap threads managed by the runtime

Go's answer is to make threads cheap enough to use one per request. A goroutine starts with a 2 KB stack that the runtime grows and shrinks as needed (by copying it to a larger block), and goroutines are scheduled by the Go runtime, not the kernel. The scheduler, often called G-M-P, has three kinds of objects: G is a goroutine, M is an OS thread, and P is a logical processor holding a queue of runnable goroutines; there are GOMAXPROCS Ps, by default one per core.

When a goroutine reads from a socket that has no data, the runtime registers the socket with the operating system's event mechanism (epoll on Linux, kqueue on macOS), parks the goroutine, and switches the thread to another goroutine; when data arrives, the goroutine becomes runnable again. The programmer writes plain blocking code, n, err := conn.Read(buf), and gets the scalability of an event loop. Measured: starting 100,000 goroutines took 178 ms and 265 MB (about 2.6 KB each), one million took 1.9 s and 2.6 GB.

Go's motto for coordinating goroutines comes from Tony Hoare's CSP (communicating sequential processes, 1978): "do not communicate by sharing memory; share memory by communicating". A channel is a typed, optionally buffered queue between goroutines, and select waits on several channels at once. A worker pool for the running example would send lines to a channel, run eight goroutines that parse and count, and merge their results:

lines := make(chan string, 1024)
results := make(chan map[string]int)
for w := 0; w < 8; w++ {
	go func() {                       // each worker owns its own map: no locks needed
		local := map[string]int{}
		for l := range lines {
			if f := strings.Fields(l); len(f) > 3 && f[3][0] == '5' {
				local[f[2]]++
			}
		}
		results <- local
	}()
}

Go also has mutexes and atomics, and the standard advice is pragmatic: use channels to pass ownership of data and to structure pipelines, a mutex to protect a shared cache. What Go does not have is Rust's compile-time race checking; two goroutines can still write the same map, and Go's race detector (go test -race) finds it only when a test exercises the race.

In practice

This model is why Go dominates cloud infrastructure: Docker, Kubernetes, etcd, Prometheus, Terraform and most cloud-provider command-line tools are written in Go. A network service that handles each connection in its own goroutine with straightforward blocking code, compiled to one static binary that starts in milliseconds, is exactly what infrastructure teams want.

6.3The event loop and async/await

JavaScript took the opposite route: one thread, and nothing ever blocks. The runtime (V8 plus libuv in Node, the browser's own loop in a web page) runs an event loop. Your code runs until it returns; anything that would wait, a timer, a network request, a file read, is handed to the runtime together with a callback, and the loop calls the callback when the result is ready. Because only one piece of JavaScript runs at a time, there are no data races between callbacks and no locks in application code.

The script starts on the call stack. console.log('A') prints immediately.

setTimeout registers a timer with the runtime and returns at once; the callback is not called now even with a 0 ms delay.

The timer expires and its callback is queued as a task. .then on an already resolved promise queues the callback as a microtask.

console.log('D') prints. The script returns and the call stack is empty for the first time.

The loop drains the whole microtask queue first: C is printed. Microtasks queued by microtasks would also run now, before any task.

Only now does the loop take one task: the timer callback prints B. Then microtasks again, then the next task, forever.

The weakness is the mirror of the strength: if one callback computes for 200 ms, nothing else runs for 200 ms. experiments/eventloop/blocking.js runs a 10 ms heartbeat timer as a stand-in for other users' requests. With an idle loop the worst lateness is 1 ms; while one handler runs a 200 ms synchronous loop, the heartbeat is 199 ms late and only 29 of 49 expected ticks fire; with the same work moved to a worker thread, the worst lateness is 2 ms. In a Node server that 199 ms is added to every other request in flight.

Callbacks nest badly, so languages added async/await. An async function returns a promise (or future) immediately; await suspends the function until the promise resolves and lets the loop run other work meanwhile. The compiler turns the function into a state machine whose states are the points between awaits, so the code reads sequentially but executes as callbacks. C#, Python (asyncio, Python 8), JavaScript, Kotlin (coroutines), Swift and C++20 (coroutines, Concurrency 6.5) all have a version of it. Rust's is the most explicit: an async fn compiles to a state machine that does nothing until an executor such as Tokio polls it, which keeps it free of hidden allocation and makes it usable on microcontrollers.

Pitfall

Blocking inside async code. A synchronous file read, a CPU-heavy JSON parse, a call to a blocking database driver or a time.sleep inside an async def stalls every other task on that loop, exactly like the 199 ms above. Move such work to a thread or process pool (worker_threads, asyncio.to_thread, Tokio's spawn_blocking).

6.4Virtual threads on the JVM

Java spent a decade with two unattractive options for high-concurrency services: one platform thread per request (simple code, limited scale) or reactive frameworks with callback chains (scalable, but hard to read and debug). Java 21 (2023) added virtual threads, the same idea as goroutines: Thread.ofVirtual().start(...) creates a thread object managed by the JVM, scheduled onto a small pool of carrier OS threads, and unmounted from its carrier whenever it blocks on I/O, a lock or a sleep. Existing blocking code, JDBC calls and all, scales without being rewritten.

Measured on the same test: 100,000 virtual threads started in 220 ms with 181 MB peak memory, one million in 1.0 s with 1.1 GB, against 2.5 s and 486 MB for only 10,000 platform threads. The main pitfall in Java 21 was pinning: a virtual thread that blocked while inside a synchronized block could not unmount and held its carrier thread, which could starve the pool; JDK 24 removed most of that restriction. Frameworks such as Spring Boot can now run each request on its own virtual thread with a configuration switch.

Talk track

"Go, Java 21 and Erlang all make threads cheap enough to use one per request, so you write blocking code and the runtime does the multiplexing. JavaScript, Python's asyncio, C# and Rust make waiting explicit with async/await on top of an event loop, which costs a second 'colour' of function but gives fine control. Both beat one OS thread per connection by orders of magnitude in concurrent connections."

6.5Actors: share nothing, send messages

The actor model goes further than CSP: there is no shared memory at all. An actor is an isolated unit with private state and a mailbox; it reacts to one message at a time and can send messages, create actors, and change its own state. Erlang (1986, built at Ericsson for telephone switches) and Elixir on the same BEAM virtual machine implement actors as processes even lighter than goroutines, each with its own small heap and its own garbage collection, so collecting one process never pauses another.

Erlang's most influential idea is about failure. Instead of defending against every error, a process that hits an unexpected state simply crashes, and a supervisor process that watches it restarts it in a known good state ("let it crash"). Supervisors form trees, so failures are contained and recovered at the right level. This is why Erlang systems are famous for availability, and why WhatsApp could serve hundreds of millions of users with a small team. The JVM has the same model in Akka and the .NET world in Orleans; the model also maps naturally onto distributed systems, where messages between machines are all you have anyway.

Pitfall

Actors trade data races for protocol problems. Mailboxes can grow without bound when a producer is faster than an actor, two actors waiting for each other's replies deadlock, and message ordering between more than two actors is not guaranteed. Bounded mailboxes, timeouts on every request and backpressure (Concurrency 8.2) are part of the design, not an afterthought.

6.6Function colouring, and choosing a model

Async/await has a well-known cost, named by Bob Nystrom's 2015 essay "What color is your function?": functions come in two colours. An async function can call ordinary functions, but an ordinary function cannot simply wait for an async one; it has to become async itself, and so must its callers, all the way up. Libraries end up with two versions of every API, and a blocking call buried deep in a synchronous library can stall an event loop. Goroutines and virtual threads avoid colouring entirely, since every function can block; that is the main argument for them. Async/await, in exchange, makes every suspension point visible in the code and needs no runtime scheduler, which is why Rust and C++ chose it.

7The languages, one problem at a time

Each mainstream language was created to fix something specific that hurt at the time, and its strengths and weaknesses follow from that original problem. Knowing the problem is the fastest way to predict where a language fits today.

7.1C: a portable assembler for writing an operating system

C was created at Bell Labs around 1972 so that Unix could be written in something more portable than assembly. Its design follows from that: a small language whose constructs map almost one-to-one onto machine operations, pointers as plain addresses, arrays as pointers to their first element, manual memory, no run-time support beyond a tiny library. A C programmer can predict the generated code and the memory layout of every structure, which is why C remains the language of operating-system kernels, embedded firmware, device drivers and the C ABI that every other language uses to talk to the operating system and to each other.

The same minimalism is its cost. There are no strings, no generic containers, no namespaces, no error-handling mechanism and no help with memory safety, so C code is long, and every buffer and pointer is a potential vulnerability. The running example in C is 36 lines, with a hand-written hash table, against 10 in Python. Modern C (C23) adds nullptr, constexpr objects and checked integer arithmetic, but its role is settled: the lowest common denominator, not the language for new application logic.

7.2C++: abstraction without paying for it

C++ started in 1979 as "C with classes": Bjarne Stroustrup wanted Simula's ability to model a problem with classes, with C's speed. Its guiding principle is zero overhead: an abstraction should cost nothing when unused and no more than hand-written code when used. Templates, RAII, move semantics, constexpr evaluation, ranges and coroutines all follow from it (C and modern C++). In the running example, the C++ version is shorter than the C version (24 lines) and the fastest of all eight at 0.10 s, using the standard unordered_map, ranges::sort and views::take.

C++ is the language of game engines, browsers, databases, trading systems, high-performance computing, automotive and robotics software, and of the internals of almost every other language runtime (V8, the JVM's HotSpot, CPython's extension modules, TensorFlow and PyTorch). Its costs are complexity, a large surface of undefined behaviour inherited from C and extended by its own features, slow builds, and a fragmented tooling ecosystem without a standard package manager. Its future is shaped by the memory-safety debate (Section 3.7): hardened library modes, profiles and contracts in C++26 aim to make the safe subset easier to enforce.

7.3Go: simple code for large teams and networked services

Go was designed at Google in 2007 by Robert Griesemer, Rob Pike and Ken Thompson, reportedly while waiting for a large C++ build. Its target was the problem Google had: large numbers of engineers writing networked servers, with slow builds, complicated languages and code that was hard to read for the next person. The answer was deliberate simplicity: a small language with one loop construct, no inheritance, no exceptions (errors are returned values), generics only since 2022, a single formatting style enforced by gofmt, very fast compilation, a garbage collector tuned for low pauses, goroutines, and a standard library that includes an HTTP server, TLS and JSON.

The result is code that looks the same whoever wrote it, compiles in seconds and deploys as a single static binary, which is why Go became the language of cloud-native infrastructure (Section 6.2) and a popular choice for backend services at companies such as Uber, Cloudflare and Twitch. Its critics point to verbosity (the if err != nil after every call), a type system less expressive than Rust's or Kotlin's, and the absence of sum types and null safety. Go's designers consider that a fair price for code that a new team member can read on day one.

7.4Java, Kotlin and C#: managed runtimes for large business systems

Java (1995) was designed to run the same compiled program on any machine, safely, which in practice meant a virtual machine, bytecode, a garbage collector, no pointer arithmetic, bounds-checked arrays and a large standard library. Over three decades the JVM became one of the most sophisticated runtimes in existence, with the JIT compilers of Section 2.3 and the collectors of Section 3.5, and Java became the default language of enterprise backends, banking, insurance, e-commerce, big-data systems (Hadoop, Kafka, Spark, Elasticsearch) and Android apps. Its strengths are the ecosystem (Maven Central, Spring, mature profilers and debuggers), excellent long-running performance, strong backward compatibility and the largest hiring pool after JavaScript and Python. Its traditional weaknesses, verbosity and slow start-up, have been reduced by records, pattern matching, var, virtual threads and AOT options.

Kotlin (JetBrains, 1.0 in 2016) runs on the same JVM and calls Java code directly, but adds null safety in the type system, data classes, extension functions, concise lambdas and coroutines. Google declared Android development "Kotlin-first" in 2019, and Kotlin is now the default for Android apps and increasingly for Spring backends. C# (Microsoft, 2000) began as Microsoft's Java and then often led it: generics that keep their types, async/await (2012, later copied by JavaScript, Python and Rust), LINQ and value types. Since .NET became open source and cross-platform (2016), C# runs Linux backends as well as Windows applications and the Unity game engine.

Why it matters

The JVM and .NET show that "managed" no longer means "slow". In the running example Java (0.61 s) is behind C++, Rust and Go only because of start-up and stream overhead on a short run; in a service that runs for days, JIT-compiled Java routinely matches C++ on throughput. What a managed runtime really costs is memory (Section 2.4) and warm-up.

7.5Python: optimise for the programmer's time

Guido van Rossum released Python in 1991 with the goal of a language that is easy to read and quick to write. Everything is an object, types are checked at run time, the syntax uses indentation and few symbols, and the standard library is large. The interpreter is slow at raw computation (Section 2.2), and for decades a global interpreter lock (GIL) let only one thread execute Python bytecode at a time, so CPU-bound work needed multiple processes.

Python won anyway, because in its main domains the interpreter is not where the time goes. In data science and machine learning, Python is the control language for libraries written in C, C++, Fortran and CUDA: NumPy, pandas, PyTorch, TensorFlow, scikit-learn. In automation, tooling, scripting and back-office services, developer time dominates machine time. Python is the most taught language in universities and the default language of AI work. The free-threaded build without the GIL (experimental in 3.13, officially supported but optional since 3.14) and the experimental JIT are changing the performance picture; the details are in Python 7.4. In the running example Python needs 10 lines and 0.75 s, within a factor of five of C.

7.6JavaScript and TypeScript: the language of the web

JavaScript was written in about ten days in 1995 by Brendan Eich at Netscape to make web pages interactive, borrowing syntax from Java, first-class functions from Scheme and prototypes from Self. It became important by accident: it is the only language every browser runs, so every web front end uses it, and Node.js (2009) brought it to servers with the event-loop model of Section 6.3. Its quirks (implicit conversions, this binding rules, two kinds of null, == versus ===) are the price of an early design that could never be changed without breaking the web.

TypeScript (Microsoft, 2012) is JavaScript plus a static type system that is erased at compile time. It was created because large JavaScript code bases were becoming unmaintainable, and it became the default for professional front-end work and much of Node backend work: types make refactoring safe and editors helpful, and adoption can be gradual (Section 4.5). Companies choose TypeScript on the backend mostly for one language across the whole web stack: shared types between client and server, one toolchain, and engineers who move between front end and back end. The running example in TypeScript on Node takes 1.07 s, the slowest of the compiled-or-JIT languages, because its idiomatic line reader is an asynchronous stream with per-line promise overhead.

7.7Lisp and Scheme: code is data

Lisp (John McCarthy, 1958) is the second-oldest high-level language still in use, and many ideas later taken for granted came from it: garbage collection, conditionals as expressions, closures, the read-eval-print loop (REPL), dynamic typing. Scheme (1975) is a small, clean dialect used for decades to teach programming (the textbook Structure and Interpretation of Computer Programs); Clojure (2007) is a modern Lisp on the JVM with immutable data structures; Emacs is largely written in Lisp.

Lisp's distinctive idea is that programs are written as the language's own basic data structure, nested lists. (+ 1 (* 2 3)) is both an expression and a list whose first element is the symbol +. Because code is data, a macro is just a function that receives code as a list and returns new code, which the compiler then compiles. Lisp programmers extend the language itself, adding control structures, domain-specific syntax or code generation, without waiting for the language designers. experiments/types/macros.scm defines a timed macro in a few lines and shows what the compiler sees after expansion:

(define-syntax timed
  (syntax-rules ()
    ((_ label body ...)
     (let ((t0 (get-internal-real-time)))
       (let ((result (begin body ...)))
         (format #t "~a took ~a ms~%" label
                 (quotient (* 1000 (- (get-internal-real-time) t0)) internal-time-units-per-second))
         result)))))

(timed "fib 25" (fib 25))     ; prints "fib 25 took 26 ms" and returns 75025

Scheme's macros are hygienic: the t0 introduced by the macro cannot collide with a variable called t0 in the caller's code, a problem C preprocessor macros have never solved. The influence is everywhere: Rust's macro_rules! and procedural macros, Elixir macros, Julia macros and C++26 reflection are all ways of letting programs generate programs. The cost is the same in every language: macro-heavy code is harder for tools and humans to follow. In the running example Guile Scheme is by far the slowest at 6.74 s, because its string splitting and generic hash tables are not tuned for this workload; Lisp's strengths are expressiveness and interactive development, not this kind of throughput.

7.8Other languages worth recognising

Swift (Apple, 2014) replaced Objective-C for iOS and macOS apps: compiled, reference-counted (ARC), with optionals, value types and protocols. Haskell, OCaml and F# are the main typed functional languages; they are used where correctness matters more than familiarity, for example compilers, financial contracts and verification tools, and they are the source of most ideas that mainstream languages adopt ten years later. Elixir brings a modern syntax to the Erlang VM for real-time web services (Section 6.5). Zig is a newer systems language that aims to be a better C: no hidden allocations, compile-time code execution, and a C compiler built into its toolchain, without Rust's ownership system. Scala combines functional and object-oriented programming on the JVM and powers Spark. SQL, finally, is the most widely used declarative language of all (Section 10.2), and arguably the most valuable second language for any backend engineer.

Claims about languages are cheap; the same program in each of them is not. This chapter puts the running example, the top three paths by server errors in a 90 MB access log, side by side in eight languages, then measures run time, start-up, memory and size, and asks what the numbers do and do not show.

8.1The code side by side

Each version is written the way an experienced developer in that language would write it on a normal day: standard library only, idiomatic constructs, no tuning. All eight produce the same output (/api/payments 2706, /api/search 2647, /api/recommendations 2296). Read them for what each language makes you say explicitly.

Some differences jump out. C has no hash map, so a quarter of the program is a hand-written open-addressing table with a fixed size of 1,024 slots; it would loop forever if the log contained more than 1,024 distinct paths, and the strduped keys are never freed. C++ gets the map, sorting and a lazy take(3) from the standard library, but its parsing uses find and substr on raw positions and would misparse or throw on a malformed line. Rust forces every failure to be handled or explicitly ignored: the file open returns a Result passed up with ?, the status parse is a Result mapped to false, and the slice pattern [_, _, path, status, ..] silently skips lines with too few fields. Go handles the open error explicitly and is the longest after C because sorting with a custom order needs a comparison closure and an explicit slice of keys. Java expresses the whole computation as a stream pipeline with groupingBy and counting, a functional style inside an object-oriented language. Python is the shortest at 10 lines: tuple unpacking doubles as validation (a line with the wrong number of fields raises an error), and Counter does the counting. TypeScript reads the file as an asynchronous stream with for await, the idiomatic Node way that never blocks the event loop. Scheme replaces the loop with a tail-recursive function, which the language guarantees runs in constant stack space.

8.3What the numbers say, and what they do not

The first lesson is that idiom matters as much as language. The idiomatic Rust program is slower than C++ and on a par with Go, because lines() allocates a new String for every line and the program collects each line's fields into a new Vec: four million allocations for two million lines. Reusing one buffer and splitting lazily (errcount_fast.rs) cuts the time to 0.14 s, faster than the C version. The C++ version is fast because find and substr on one reused std::string avoid most allocation; C's strtok_r and atoi are slower than you might expect. Go's strings.Fields allocates a slice per line, just like the idiomatic Rust. When performance matters, the question is rarely "which language" first; it is "how many allocations per item".

The second lesson is that Python is closer than its reputation for this kind of work, at 4.4 times C. The hot operations, reading lines, split(), the dictionary update, are C code inside CPython; the interpreter itself only executes a handful of bytecode operations per line. A loop doing arithmetic in Python (Section 2.2) is 15 times slower than C, not 4. Know which kind of loop you have.

The third lesson is about runtimes, not languages. Java's 62 ms start-up and 228 MB footprint come from the JVM booting, loading classes and sizing its heap for a machine with 15 GB; on a long-running service both are paid once and are mostly a configuration question. Node's 81 MB is V8's heap plus the cost of an asynchronous line reader that creates a promise per line. These costs matter enormously for command-line tools and serverless functions and hardly at all for a service that runs for weeks.

What the table does not show is just as important. It says nothing about how long each version took to write and debug (the Python version took minutes, the C hash table longer), how each behaves on malformed input (C and C++ would misbehave silently or throw; Rust and Python fail or skip explicitly), how easy each is to change when the log format changes, or what happens at a hundred times the data, when parallelism and I/O dominate. A benchmark of one program is a sample, not a ranking.

Pitfall

Choosing a language from a microbenchmark. Most backend services spend their time waiting on databases and other services; a 3× difference in CPU per request is invisible when 95 % of latency is I/O. Measure your own workload, look at where time actually goes (profilers exist for every language), and weigh run-time cost against developer time, hiring and safety.

9Functional programming

Functional programming builds programs from functions that compute new values instead of changing existing ones. Its ideas, immutability, pure functions, higher-order functions, algebraic data types and composable error handling, have moved from academic languages into Java, C#, C++, Rust, JavaScript and Python, because they make code easier to test, to reason about and to run concurrently.

9.1Pure functions and immutability

A pure function's result depends only on its arguments, and calling it has no effect other than producing that result: it does not modify its inputs, write to a global, log, read the clock or touch the network. is_error(status) = status >= 500 is pure; a function that increments a shared counter is not. Pure functions are easy to test (no set-up, no mocks: give inputs, check outputs), easy to reason about (you can replace a call with its result, which is called referential transparency), safe to cache, and safe to run in parallel, because there is nothing shared to race on.

Immutability is the data-side counterpart: values never change after they are created; an "update" creates a new value. If a list cannot change, anyone may hold a reference to it without defensive copies, and no thread can see it half-modified. Most mainstream code is not purely functional, nor should it be, since a program that never changes anything never writes a file or sends a response. The practical style is a functional core with an imperative shell: compute decisions with pure functions on immutable data, and confine effects (I/O, database writes, logging) to a thin outer layer that is simple enough to test with a few integration tests.

Why it matters

Most hard bugs involve state that changed when someone did not expect it: a shared object modified by another thread, a cache entry mutated by a caller, a configuration changed mid-request. Immutability removes that whole class. It is why Java added records, why C# added record and init, why Kotlin separates val from var and List from MutableList, and why Rust makes variables immutable unless declared mut.

9.2Higher-order functions and closures

A higher-order function takes functions as arguments or returns them. map applies a function to every element, filter keeps the elements a predicate accepts, reduce (or fold) combines them into one value. With these three, most loops over collections become a description of what is computed rather than how to iterate. The Java version of the running example is exactly this: split each line, map it to a Hit, filter errors, group and count. The Rust equivalent of the counting step reads the same way:

let errors: HashMap<String, usize> = log
    .lines()
    .filter_map(|l| {
        let mut f = l.split(' ').skip(2);                 // ts method | path status latency
        Some((f.next()?, f.next()?.parse::<u16>().ok()?))
    })
    .filter(|&(_, status)| status >= 500)
    .fold(HashMap::new(), |mut m, (path, _)| { *m.entry(path.to_owned()).or_insert(0) += 1; m });

A closure is a function together with the variables it captured from its surroundings; |&(_, status)| status >= threshold would capture threshold. Closures are what make higher-order functions practical, and they are also where languages differ in subtle ways: C++ lambdas capture by value or by reference as you specify (and a captured reference can dangle), Rust closures borrow or move according to the same ownership rules as everything else, Java lambdas may only capture effectively final variables, and JavaScript and Python closures capture variables, not values, which surprises everyone once in a loop.

Interesting detail

The functional pipeline is not necessarily slower than the loop. Rust iterator chains and C++ ranges compile to the same machine code as the hand-written loop, because each adapter is a small struct that the compiler inlines. Java streams and JavaScript array methods do pay for allocation and indirect calls, which the JIT removes only partly; in hot code in those languages a plain loop is still often faster.

9.3Persistent data structures: immutability without copying everything

If values never change, adding one entry to a map with a million entries must produce a new map. Copying a million entries for every update would make immutability unusable. Persistent data structures solve this by sharing structure: the new version reuses everything that did not change from the old one.

Clojure's vectors and maps, Scala's immutable collections, Immutable.js and Haskell's containers are trees with high branching factors (typically 32), so even large collections are only a few levels deep and an update copies a handful of small nodes. Reads cost a few pointer hops more than a flat array, and the extra allocation creates work for the garbage collector, so persistent structures are the right default where many readers share data that changes occasionally, and the wrong one inside a tight numeric loop.

In practice

Front-end frameworks rely on this. React decides whether to re-render a component by comparing old and new state by reference; that is only correct if state is never mutated in place, which is why Redux and React's own useState require creating new objects for every update (and libraries such as Immer make that convenient). The same idea, an immutable log of changes plus snapshots, appears in databases (multi-version concurrency control), in Git's object store and in event sourcing.

9.4Algebraic data types, pattern matching and recursion

Functional languages model data as algebraic data types: product types (records, structs, tuples: a path and a status) and sum types (a payment is pending or captured or refunded), taken apart with pattern matching that the compiler checks for completeness. Section 4.4 showed why this is the most valuable functional idea for everyday code: it lets the type system rule out impossible states. Java 21's sealed interfaces with record patterns, C#'s switch expressions, Kotlin's sealed classes and TypeScript's discriminated unions all bring it to mainstream languages.

Purely functional code has no loops that update a counter, so repetition is written as recursion, as in the Scheme version of the running example. Scheme guarantees tail-call optimisation: when a function's last action is a call, the call reuses the current stack frame, so a recursion over two million lines runs in constant stack space, like a loop. Java, Python and JavaScript engines (except Safari's) do not guarantee this, so deep recursion there overflows the stack; in practice functional code in those languages uses higher-order functions instead of explicit recursion.

9.5Monads without the mystery

"Monad" sounds abstract, but the idea is a pattern every developer has already used: chaining steps where each step may produce a value wrapped in some context (it might be missing, it might have failed, it might not have arrived yet), without writing the unwrapping logic between every pair of steps. A monad is a wrapper type with two operations: put a plain value into the wrapper, and flatMap (also called bind or and_then), which takes a function from a plain value to a new wrapped value and handles the context.

Three examples cover most of practice. Option/Optional: find_user(id).and_then(|u| u.manager).map(|m| m.email) returns None as soon as any step finds nothing, with no null checks. Result/Either: each step may fail with an error, and the first error short-circuits the rest, which Rust's ? operator writes as one character per step. Promise/Future: fetch(url).then(parse).then(save) runs each step when the previous one's value arrives, and async/await is syntax that hides the thens. Java's Optional and CompletableFuture, C#'s LINQ and Task, and Kotlin's nullable chain ?. are the same idea.

Haskell makes this pattern central because it is how a pure language sequences effects: an IO action is a value describing an effect, and do notation chains such values just as await chains promises. For a mainstream developer the useful takeaway is narrower: when you see repeated "if it is missing / failed / pending, stop; otherwise continue with the value" code, a monadic chain (and_then, flatMap, ?, await) usually expresses it more clearly.

Talk track

"A monad is a wrapper with a way to chain functions that return the same wrapper. Optional chaining, Result with the question-mark operator, and promises with then or await are all monads; they let you write the happy path in sequence while the wrapper handles absence, errors or asynchrony in one place."

9.6Functional ideas in mainstream code

The most successful functional ideas are the ones that slipped into mainstream languages and frameworks without the label. Collection pipelines (Java streams, C# LINQ, C++ ranges, Rust iterators, Python comprehensions) are map/filter/reduce. MapReduce, Spark and Apache Beam built large-scale data processing on the observation that pure functions over immutable partitions can be distributed and retried safely. React models a user interface as a pure function from state to a description of the screen. Serverless functions, stateless microservices and idempotent message handlers apply purity at the architecture level: a handler that does not depend on hidden state can be scaled out, retried and replaced freely.

The limits are just as real. Pure functional code can allocate heavily, which is a problem in latency-critical or embedded code; deep chains of higher-order functions can be harder to debug than a loop; and teams unfamiliar with the style may find heavily abstracted functional code (monad transformers, point-free style) harder to maintain than plain imperative code. Use functional ideas where they remove state and bugs, not as a goal in themselves.

10Other paradigms: objects, declarations, events, streams and data

Beyond imperative and functional programming, a few more paradigms shape how most software is actually organised: object-oriented design for modelling domains, declarative descriptions for configuration and queries, event-driven and reactive designs for systems that respond to things happening, and data-oriented design for performance. Each answers a different question about where complexity should live.

10.1Object-oriented programming, and what it became

Object-oriented programming bundles data with the operations allowed on it (encapsulation), lets callers use different implementations through one interface (polymorphism, usually through a vtable, see C and modern C++, virtual dispatch), and lets classes reuse other classes' code (inheritance). Its success in the 1990s came from a real problem: large programs with shared global data became impossible to change, and encapsulation gave each piece of state an owner with a small, controlled interface.

Three decades of practice have refined it. Composition over inheritance: deep class hierarchies couple subclasses to their parents' internals (the fragile base class problem), so modern designs implement interfaces and delegate to contained objects instead. Go and Rust have no implementation inheritance at all, only interfaces or traits. Interfaces over classes: depending on an interface rather than a concrete class is what makes dependency injection, mocking in tests and swapping implementations possible (the SOLID principles' dependency inversion). Data as data: not everything needs to be an object with behaviour; records, data classes and plain structs carry values between components, and logic that spans several types often reads better as a function than as a method forced onto one of them.

Pitfall

Modelling the real world's taxonomy instead of the program's needs. Square extends Rectangle looks natural and breaks the moment a caller sets the width of a rectangle and expects the height to stay the same (the Liskov substitution principle). Inherit only when every use of the parent is valid for the child; otherwise compose.

10.2Declarative programming: say what, not how

A declarative program describes the desired result and leaves the steps to an engine. SQL is the most successful example: SELECT path, count(*) FROM requests WHERE status >= 500 GROUP BY path ORDER BY 2 DESC LIMIT 3 is the running example in one line, and the database's query planner decides whether to scan, use an index, or parallelise, based on statistics the programmer never sees. HTML and CSS declare a page's structure and appearance; regular expressions declare a pattern; build files declare dependencies; Terraform declares the cloud resources that should exist.

The power of the declarative style is that the same description can be executed in many ways, optimised by the engine, and re-applied safely: applying "three replicas" twice still gives three replicas (it is idempotent), whereas running "start one replica" twice gives two too many. Its costs are a loss of control and harder debugging when the engine chooses badly: a slow SQL query is debugged by reading the planner's EXPLAIN output, a Terraform surprise by reading its plan. Declarative systems therefore always need a way to inspect what the engine decided.

Talk track

"Imperative code says how; declarative code says what, and an engine works out how. SQL, Kubernetes manifests, Terraform and React are all declarative, and the nice property is idempotence: you can re-apply the description and converge to the same state, which is exactly what you want for infrastructure and UIs."

10.3Event-driven programming: react to things that happen

In event-driven programming, the flow of the program is determined by events: a click, a message, a file change, a payment completed. Code registers handlers and the runtime calls them; nobody writes the main loop. User interfaces have always worked this way, as have the event loops of Section 6.3. At the architecture level, event-driven systems communicate by publishing events to a broker such as Kafka, RabbitMQ or a cloud pub/sub service, and any number of services subscribe: when an order is placed, billing, shipping, email and analytics each react independently, and the order service does not need to know they exist.

The benefit is decoupling: services can be added, scaled and deployed independently, and a slow consumer does not slow the producer. The cost is that the flow of control is no longer visible in any one place. To answer "what happens when an order is placed?" you have to find every subscriber, events may arrive twice or out of order, and a failure in one consumer is noticed late. Event-driven systems therefore need idempotent handlers, correlation IDs for tracing, and dead-letter queues, as described in Software architecture 8.5.

10.4Reactive programming: values that change over time

Reactive programming treats a sequence of events over time as a value you can transform, the way a spreadsheet cell defined as =A1+B1 updates itself whenever A1 or B1 changes. Libraries such as RxJS, Reactor (Spring WebFlux), RxJava and Kotlin Flow represent event streams as objects with operators: map, filter, merge, debounceTime, switchMap, retry. Each operator returns a new stream, so complex timing logic becomes a short declarative pipeline.

The search box above takes four lines in RxJS and would take dozens of lines of timers, flags and request bookkeeping with callbacks, with a race condition hiding in them. Reactive streams also carry backpressure: the Reactive Streams specification (adopted in Java 9 as java.util.concurrent.Flow) lets a slow subscriber tell the producer how many items it can take, which prevents unbounded buffering. User-interface frameworks have taken a lighter version of the idea, signals (Solid, Angular, Vue's reactivity, Svelte), where the framework tracks which values a piece of UI reads and updates only that piece when they change.

Pitfall

Reactive code is hard to debug: stack traces show the library's internals rather than your pipeline, errors terminate a stream unless explicitly handled, and a forgotten subscription leaks memory and keeps work running. On the backend, Java virtual threads (Section 6.4) have removed much of the reason to write request handling reactively; keep reactive streams for problems that are genuinely about streams and timing.

10.5Data-oriented design: organise code around memory access

Object-oriented design groups data by concept: a Particle object holds its position, velocity, colour and lifetime. Data-oriented design groups data by how it is processed, because on modern hardware the cost of a program is dominated by memory access, not instructions. If the physics update reads only positions and velocities, storing all positions in one contiguous array and all velocities in another (structure of arrays, SoA) lets every cache line fetched from memory carry only useful data, and lets the compiler use SIMD instructions. The array-of-objects layout drags colour and lifetime through the cache for nothing. C and modern C++, AoS versus SoA shows the mechanism and the measured difference.

Game engines took this furthest with the entity-component-system architecture, which the planned game-engines chapter covers. The same thinking appears in columnar databases and data formats (Parquet, Arrow, ClickHouse), which store each column contiguously because analytical queries read a few columns of many rows; in NumPy and pandas; and in GPU programming, where memory coalescing is the first optimisation (GPU computing). The lesson for any language: when performance matters, design the data layout first and the code second.

10.6Logic programming and other paradigms

A few more paradigms are worth recognising. Logic programming (Prolog, 1972) states facts and rules and lets the engine search for answers: given parent(a, b) and a rule for ancestor, the query ancestor(a, X) finds all X. Its descendant Datalog is widely used today for static analysis (GitHub's CodeQL queries code as a database), authorisation policies and network verification. Constraint programming and SAT/SMT solvers (Z3) state constraints and let a solver find a solution; schedulers, package-version resolvers and program verifiers use them. Array programming (APL, NumPy, MATLAB) operates on whole arrays at once. Dataflow and stream processing (Apache Flink, Beam, LabVIEW, Simulink in engineering) wire operators into graphs through which data flows. None is a general-purpose replacement for the mainstream paradigms; each is a powerful tool for a specific class of problems, often embedded inside a program written in a mainstream language.

In practice

Most large companies are polyglot by design: a small number of supported "paved road" languages (often Java or Kotlin, Go, TypeScript and Python, with C++ or Rust for specialists), each with an internal platform team that maintains its libraries, templates, build rules and security tooling. Adding a language means funding that support, which is why such decisions are made at the organisation level rather than by individual teams.

11.3Mixing languages: interop boundaries and migrations

Languages meet at boundaries, and the boundary determines how hard mixing is. Inside one process, the universal boundary is the C ABI: Python extension modules, Java's JNI and the newer Foreign Function and Memory API, Go's cgo, Rust's extern "C" and Node's N-API all call C functions. Calls across it are cheap but unsafe and awkward: no exceptions, no generics, ownership agreed by convention. Between processes, the boundary is a network protocol (HTTP/JSON, gRPC with Protocol Buffers, a message broker), which costs serialisation and latency but lets each side use any language and be deployed independently. Microservice architectures make this the default, which is one reason polyglot companies became common.

Migrations from one language to another succeed when they are incremental. The pattern that works is the strangler fig: put a stable interface in front of the old system, implement new functionality and then one existing piece at a time in the new language behind that interface, and retire old code only when the new code carries production traffic. Android's move to Rust, Kotlin's adoption inside Java apps, and TypeScript's adoption inside JavaScript code bases all followed this pattern; big-bang rewrites, which stop feature work for a year and rediscover every forgotten requirement, have a much worse record.

11.4A checklist for deciding

For a technical manager, a language decision is a risk decision. The questions below, roughly in order of how often they decide the outcome, turn a debate about taste into one about costs.

Platform and ecosystem: does the target platform dictate a language, and do the libraries we need (protocols, drivers, SDKs, ML frameworks) exist and are they maintained? People: who will write and maintain this for the next five years, how long will ramp-up take, and can we hire? Failure cost: what is the worst failure here, a security breach, a missed latency target, a crash in the field, slow delivery, and which language makes it least likely? Memory-unsafe languages for network-facing code are now a security argument that customers and regulators raise. Run-time constraints: latency budget and tail latency, memory limit, start-up time (serverless, CLI), deployment target (container, device, browser). Integration: how does it talk to the existing system, in-process through a C ABI or over the network? Longevity: who governs the language, how stable is it, is there a long-term-support policy, and for regulated products, a qualified toolchain? Total cost: developer time is usually more expensive than CPU time, until the service runs on thousands of machines.

In automotive

Vehicle software shows the same logic under stricter constraints. Safety-related ECU code is C and C++ under MISRA guidelines (MISRA C++:2023) with qualified compilers; Rust enters through qualified toolchains such as Ferrocene (Section 5.9), first in new components. Infotainment on Android Automotive is Kotlin and Java; tooling, test automation and data pipelines are Python; vehicle back-end services in the cloud use the mainstream backend languages above.

Talk track

"I'd decide on four things: what the platform and ecosystem force, who maintains it for five years, what the most expensive failure is, and the run-time constraints. Language features come after those. If the answers point to a new language, adopt it at a well-defined boundary, with platform support funded, and migrate incrementally."

QSelf-check questions

Q.1Core questions

What is the difference between a compiled and an interpreted language?Basic

Strictly, it is a property of the implementation, not the language: Python has interpreters and a JIT (PyPy), Java is compiled to bytecode and then JIT-compiled. An AOT compiler translates the whole program to machine code before it runs, so it starts fast and needs no runtime compiler. An interpreter executes bytecode one operation at a time, paying dispatch and dynamic checks on every operation (10–50× slower on tight loops) but allowing instant iteration. A JIT combines both: it interprets first and compiles hot code at run time using profile information.

What is garbage collection, and what does it cost?Basic

A tracing collector periodically finds every object reachable from the roots (stacks, globals, registers) and frees the rest, so the program never frees memory explicitly and cannot use freed memory. It costs CPU for marking, extra memory because garbage accumulates between collections (Go's default lets the heap reach about twice the live data), and some pauses, which modern concurrent collectors keep at or below a millisecond. More headroom means fewer collections and less CPU.

What is the difference between static and dynamic typing, and between strong and weak typing?Basic

Static versus dynamic is about when types are checked: at compile time (Java, Rust, Go) or at run time when an operation executes (Python, JavaScript). Strong versus weak is about implicit conversions: Python refuses '1' + 1, JavaScript returns '11', C silently truncates 3.9 to an int. Python is dynamic and strong; C is static and fairly weak.

Explain Rust's ownership and borrowing rules.Intermediate

Every value has one owner and is dropped when the owner goes out of scope. Assigning or passing a non-Copy value moves ownership and makes the old variable unusable. You can borrow instead: any number of shared references &T or exactly one mutable reference &mut T, never both at once, and no reference may outlive the value. The borrow checker enforces this at compile time, which rules out use-after-free, double free, iterator invalidation and data races with no run-time cost.

How does Rust prevent data races?Intermediate

A data race needs shared access with at least one writer and no synchronisation. The borrow rules already forbid shared and mutable access at the same time; across threads, thread::spawn requires captured values to be Send and owned, and shared references require Sync. Types with unsynchronised interior state such as Rc or RefCell are not Send/Sync, so they cannot cross threads. To share mutable data you use Arc<Mutex<T>> or atomics, and the mutex owns the data, so it cannot be reached without locking. Deadlocks and logical races remain possible.

What is a closure, and what can go wrong with captures?Intermediate

A closure is a function plus the variables it captured from where it was created. Capture semantics differ: C++ captures by value or reference as written, and a captured reference can dangle if the closure outlives the scope; Rust applies ownership rules, so a closure that outlives its scope must move its captures; Java allows only effectively final captures; JavaScript and Python capture variables, not values, so closures created in a loop may all see the final value of the loop variable.

What are goroutines and how do they differ from OS threads?Intermediate

Goroutines are threads managed by the Go runtime: they start with a 2 KB growable stack and are multiplexed onto a few OS threads (one per core by default) by the G-M-P scheduler. A goroutine waiting on the network is parked in the poller and costs no thread. Measured, 100,000 blocked goroutines cost about 265 MB and started in under 0.2 s, while 10,000 OS threads took 0.33–2.5 s. The code still looks blocking and sequential, which is the main appeal.

Explain the JavaScript event loop. What does a zero-delay setTimeout really do?Intermediate

JavaScript runs on one thread. Synchronous code runs to completion; operations that wait are handed to the runtime with a callback. When the stack is empty, the loop first drains all microtasks (promise callbacks), then runs one task (timers, I/O callbacks), then microtasks again. setTimeout(f, 0) queues f as a task after the current script and after all microtasks, so a resolved promise's then callback runs before it. Long synchronous work blocks everything; in the experiment, 200 ms of work delayed a timer by 199 ms.

What are virtual threads in Java 21 and when do they help?Intermediate

Virtual threads are JVM-managed threads multiplexed onto a small pool of carrier OS threads; when a virtual thread blocks on I/O it unmounts and the carrier runs another. They let thread-per-request code with blocking JDBC or HTTP clients scale to hundreds of thousands of concurrent requests (1 M started in about 1 s in the experiment). They help I/O-bound concurrency, not CPU-bound work; pitfalls are pinning (blocking inside synchronized in Java 21) and unbounded creation overwhelming a downstream database.

What is the difference between Java generics and C++ templates?Intermediate

C++ templates are monomorphised: the compiler generates a specialised copy per type, optimised like hand-written code, at the cost of compile time and binary size. Java generics use erasure: one compiled copy works on Object references with casts inserted, so List<Integer> holds boxed objects, generic types are unknown at run time, and you cannot write new T(). Erasure kept compatibility with pre-2004 JVMs.

What is a monad, in practical terms?Advanced

A wrapper type with a way to put a value in and a flatMap/and_then that chains functions returning the same wrapper, so the logic for the wrapper's context is written once. Option chains stop at the first missing value, Result chains at the first error (Rust's ?), promises chain asynchronous steps (then, await). The value is writing the happy path linearly while absence, failure or asynchrony is handled in one place.

What does "zero-cost abstraction" mean, and is it true?Advanced

That using an abstraction costs no more at run time than the hand-written equivalent, and unused features cost nothing: C++ templates and Rust iterators compile to the same loop you would write. It is true for the mechanism, not for the program: the abstraction can hide costs such as allocations. The idiomatic Rust log parser took 0.38 s because it allocated per line; removing those allocations gave 0.14 s. The costs also move to compile time and binary size.

Why would a company choose Go over Java for a new service, or the other way round?Advanced

Go: single static binary, millisecond start-up, small memory footprint, fast builds, simple language that large teams read uniformly, goroutines for I/O concurrency; a good fit for infrastructure and network services and container-heavy deployment. Java/Kotlin: the richest ecosystem for business systems, mature frameworks and tooling, excellent long-running throughput through the JIT, virtual threads since 21, and a very large hiring pool. In practice the existing platform and team usually decide.

When would you not use Rust?Advanced

When the team has no Rust experience and the deadline leaves no room for ramp-up; when the domain's ecosystem is elsewhere (ML research in Python, GUI or game engines in C++, enterprise integration in Java); when a garbage-collected language already gives memory safety and the performance is sufficient; when a certified toolchain or certified libraries are needed and not yet available; or for quick scripts and prototypes. Rust shines where memory safety and no-GC performance are both required.

What is memory safety and why are governments talking about it?Basic

Memory safety means a program cannot access memory out of bounds, after free, uninitialised, or under a data race. About 70 % of serious vulnerabilities in large C/C++ code bases (Microsoft, Chromium) are memory-safety bugs. Android cut its share of memory-safety vulnerabilities to under 20 % by writing new code in Rust, Kotlin and Java. NSA and CISA therefore urge memory-safe languages for new code and memory-safety roadmaps for existing products.

What is the difference between declarative and imperative programming? Give examples.Basic

Imperative code says how: a sequence of steps that change state (a loop that counts errors). Declarative code says what result is wanted and leaves the steps to an engine: SQL's GROUP BY, a Kubernetes manifest with replicas: 3, React's render function, HTML and CSS, Terraform. Declarative descriptions can be optimised by the engine and re-applied idempotently; the cost is less control and debugging through the engine's plan.

Composition or inheritance? Why?Intermediate

Prefer composition: build objects from smaller parts and depend on interfaces. Implementation inheritance couples a subclass to its parent's internals (fragile base class), forces "is-a" relationships that often break substitutability (Square/Rectangle), and makes hierarchies hard to change. Use inheritance for genuine substitutable specialisation or framework extension points; Go and Rust omit implementation inheritance entirely.

What is reactive programming and when is it the right tool?Advanced

Treating events over time as streams with composable operators (map, filter, debounce, switchMap, retry) and backpressure, as in RxJS, Reactor or Kotlin Flow. It fits problems that are about timing and streams: user input, live data feeds, combining several asynchronous sources, cancellation of stale requests. For ordinary request handling, plain blocking code on virtual threads or async/await is easier to read and debug.

How does a JIT make a dynamically typed language fast?Advanced

It profiles the running program, sees which types actually occur at each operation (for example always small integers, always the same object shape), and compiles specialised machine code for those types with cheap guards. Hidden classes and inline caches make property access as fast as a struct field. If a guard fails, the code is deoptimised back to the interpreter and possibly recompiled. In the experiment, Node ran a numeric loop at 4.3 ms versus 35 ms without the JIT.

What is function colouring?Advanced

With async/await, async functions can only be awaited from other async functions, so making one low-level function asynchronous forces all its callers to become async: functions have two "colours" that do not mix freely, and libraries need sync and async variants. Green-thread models (Go, Java virtual threads) have no colouring because any function may block; async/await in exchange makes suspension points explicit and needs no runtime scheduler.

Q.2Why and what if

Why does doubling GOGC roughly halve GC CPU, and why doesn't the live heap size change it?Why

A cycle starts after the program has allocated live × GOGC/100 bytes, so cycles per second = allocation rate / (live × GOGC/100). Each cycle's cost is proportional to the live heap it marks. Multiplying the two, the live heap cancels and GC CPU ∝ allocation rate / GOGC. A bigger live heap means fewer but more expensive cycles; it changes memory, not CPU. Measured: GOGC 50 → 21 %, 100 → 11.7 %, 200 → 6.3 %.

Why can reference counting not free a cycle, but a tracing collector can?Why

Reference counting frees an object only when its count reaches zero; two objects pointing at each other keep each other's counts at one or more even when nothing else references them. A tracing collector does not look at counts; it asks what is reachable from the roots, and an unreachable cycle is simply never marked, so it is swept like any other garbage.

Why does C++ accept a push_back while a reference to the first element is alive, and Rust not?Why

C++'s type system does not track the relationship between a reference and the container it points into, so the compiler cannot know the reference becomes invalid when the vector reallocates. Rust records that first is a shared borrow of latencies live until its last use; push needs &mut latencies, and shared plus mutable at the same time violates the borrow rule. Rust never reasons about reallocation; the general rule covers it.

Why is the Python log parser only 4× slower than C when a Python loop is 15× slower?Why

In the log parser, the work per line is mostly done by C code inside CPython: reading and decoding lines, str.split, integer parsing and dictionary updates. The interpreter only dispatches a few operations per line. In the arithmetic loop every addition and comparison goes through the interpreter's dispatch, type checks and integer objects. The ratio depends on how much time is spent in interpreted bytecode versus native library code.

Why is allocation in Java often faster than malloc in C?Why

A copying generational collector leaves the young generation completely empty after each collection, so allocation is a bump of a thread-local pointer plus a bounds check: a few instructions. malloc must find a suitably sized free block in a fragmented heap and maintain free lists. The JVM pays later, during collection, but for short-lived objects that die before the collection the cost is close to zero.

Why do Rust and Go both return errors as values, yet feel different?Why

Both make failure explicit in signatures. Rust's Result is a sum type: you cannot reach the value without handling the error, and ? propagates it concisely. Go returns (value, err) as two independent values: the compiler does not force you to check err, and propagation is an explicit if err != nil { return err }. Rust trades a richer type system for safety and brevity; Go trades it for simplicity.

Why did TypeScript choose an unsound type system?Why

Its goal is to type existing JavaScript patterns without changing run-time behaviour. A sound system would reject huge amounts of correct, idiomatic JavaScript (covariant arrays, dynamic object building, libraries without types). Accepting a few unsound corners (any, unchecked indexing, bivariant method parameters) made gradual adoption possible; strict settings and unknown recover much of the safety.

What if a Node.js handler parses a 50 MB JSON body synchronously?What if

The event loop is blocked for the whole parse, possibly hundreds of milliseconds, and every other request on that process waits: latency spikes for all users, health checks may time out and the instance may be restarted. Options: limit body size, stream-parse, move parsing to a worker thread, or scale with more processes. This is the same effect as the 199 ms timer lateness in the experiment.

What if you set GOGC very low to save memory in a container?What if

The collector runs far more often and its CPU use rises inversely (GOGC 25 used 29 % of four cores and made the program 2.4× slower than GOGC 100), while memory falls only to about 1.25 × live. A better tool for a container limit is GOMEMLIMIT, which keeps the normal GOGC behaviour until the heap approaches the limit and only then collects harder.

What if a Rust program wraps everything in Rc and RefCell to satisfy the borrow checker?What if

It compiles, but borrow checking moves to run time: a conflicting borrow_mut panics instead of failing compilation, reference counts add overhead, cycles can leak, and the types cannot cross threads. The underlying ownership design problem remains. Better: find the real owner, pass references down, use indices into a vector or an arena for graphs, and keep shared mutable state small and explicit.

What if a Java 21 virtual thread blocks on I/O inside a synchronized block?What if

In Java 21 it is pinned: it cannot unmount from its carrier OS thread while holding a monitor, so the carrier is blocked too. With many such threads, all carriers can be pinned and the application stalls although CPU is idle. Fixes: use ReentrantLock instead of synchronized around blocking calls, or upgrade to JDK 24+, which removed most pinning on monitors.

What if a JIT's speculation is wrong, for example a function that always got integers receives a string?What if

The guard in the optimised code fails, the engine deoptimises: it discards that compiled code, rebuilds the interpreter's frame from metadata, continues in the interpreter, and later may recompile a more general version. The result is still correct but temporarily slower; code whose types keep changing (megamorphic call sites) never gets the fastest code. This is why consistent object shapes and argument types matter for JavaScript performance.

What if two microservices in different languages must share a data model?What if

Define the model once in a language-neutral schema (Protocol Buffers for gRPC, OpenAPI or JSON Schema for HTTP, Avro for Kafka) and generate types for each language. Versioning rules (add optional fields, never reuse field numbers) keep old and new services compatible. Hand-maintained parallel definitions drift; validation at the boundary catches what types cannot, because types are erased in transit.

What if your team proposes rewriting a stable 500k-line C++ service in Rust?What if

Ask what failure it fixes: if security bugs in input handling, rewrite those components first behind a narrow interface (strangler pattern) and measure. A full rewrite stops feature work, rediscovers forgotten requirements and adds new bugs; Android's evidence shows most memory-safety benefit comes from writing new code in a safe language while old, battle-tested code ages. Fund interop, build and training costs explicitly.

What if an event-driven system processes the same "order placed" event twice?What if

Most brokers guarantee at-least-once delivery, so duplicates are normal, not exceptional. A handler that charges a card or sends an email on every delivery double-charges. Handlers must be idempotent: record processed event IDs, use idempotency keys with external APIs, or make the effect naturally idempotent (set state to "shipped" rather than increment a counter).

Why are persistent data structures popular in UI frameworks but rare in high-performance numeric code?Why

In UIs, state changes rarely and many readers compare versions; structural sharing makes "did it change?" a pointer comparison and gives cheap snapshots for undo and time travel. Numeric code updates millions of values per second in tight loops, where the extra allocation, pointer chasing and cache misses of tree-shaped persistent structures cost far more than a contiguous mutable array.
