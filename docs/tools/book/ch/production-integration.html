Production integration, diagnostics and the ECU lifecycle

The life of one software release, from the integration lab to a workshop years later: how applications, middleware, basic software, operating system, drivers and hardware are put together and started; what a release contains and how it is identified; how an ECU is flashed over UDS, how secure boot decides what may run, and how over-the-air updates install, activate and roll back; diagnostics one level below the services, with DoIP, Dcm and Dem; logging with DLT, health supervision and crash data; benches, CANoe and HIL; debugging real hardware with JTAG, trace and dumps; endurance testing; and the path from a development build through the plant to after-sales support.

1The life of one release

Most engineering books stop when the code works. In a vehicle, that is where the second half of the work begins: the code has to be combined with dozens of other components, started in the right order on real hardware, identified, signed and flashed, observed and diagnosed in millions of cars, updated without bricking anything, and supported in a workshop fifteen years later by a technician who has never heard of your team. This chapter follows one release of a camera ECU's software through all of it.

1.1Why integration is a discipline of its own

Every component of an ECU can pass its own tests and the ECU can still fail. The camera service works on the developer's bench, but on the integrated ECU it starts 300 ms later because it now waits for a logging daemon; the diagnostic service that reads a calibration value works, but only in the extended session, which the OEM's tester never enters at that point; the new perception model is faster, but it needs a newer GPU driver that conflicts with the display stack. None of these failures belongs to one component. They live in the interfaces: between software layers, between the ECU and the vehicle, between the supplier and the OEM, and between today's release and the one already in the field.

Integration is the work of making those interfaces explicit and checking them continuously. It has a technical side (build systems, start-up graphs, configuration, test benches) and an organisational side (who delivers what by when, who owns which configuration, what may change after a freeze). Both matter equally, which is why integration engineers, system engineers and engineering managers need the same mental model. This chapter gives it to them by following one release from start to end.

Why it matters

The expensive problems of an automotive software project are rarely algorithmic. They are a release that cannot be flashed in the plant because a bootloader rejects it, a fault memory full of entries that send good parts back as warranty returns, an update that bricks a few hundred cars, or a field issue that cannot be analysed because nothing was logged. Each of them is decided by choices made during integration, long before the problem appears.

1.2The running example: release 4.12 of a camera ECU

The example is the camera ECU of the earlier chapters: a system-on-chip that processes four surround cameras and a front camera, and a safety microcontroller that talks to the vehicle buses (Camera ECU 8). Its software version 4.12 starts as a set of component deliveries in an integration lab. It is built nightly, tested on benches and on hardware-in-the-loop racks, driven in test vehicles, frozen, signed and released. In the plant it is flashed into every new ECU at the end of the line, together with keys, coding and calibration. In the field it runs for years, produces logs and fault codes, and is replaced over the air by 4.13, or rolled back when 4.13 misbehaves. Years later a car arrives at a workshop with a black rear-view screen, and a technician with a diagnostic tester has to find out whether the camera, the cable, the ECU or the software is at fault.

The point of telling it as one story is that every station depends on decisions made at the earlier ones. The plant can only flash quickly if the release was split into sensible logical blocks and the bootloader supports a fast transport. The workshop can only diagnose the black screen if the release records the right fault codes and snapshot data. A rollback in the field is only possible if the update scheme kept the old version and the data format stayed compatible. Integration decisions are lifecycle decisions.

2The integrated stack: what fits together and who owns it

An ECU's software is not one program but a stack of layers from a dozen sources, each with its own release cycle. Integration starts with knowing the stack, the contract at each boundary, and who is allowed to change which part of the configuration.

2.1From hardware to application

Seen from the bottom, the camera ECU has two computers. The system-on-chip starts with a boot chain from the silicon vendor (boot ROM, secondary bootloaders, firmware for the DSPs, the image signal processor and the power-management controller), optionally a hypervisor that splits the chip into partitions, an operating system with its board support package (the drivers for this board: camera deserialiser, display, Ethernet, PCIe, storage), then a vision runtime (ISP tuning, an inference engine, the GPU stack), middleware (Adaptive AUTOSAR or a similar framework with SOME/IP, logging and persistency), and finally the applications: perception, surround view, the diagnostic and update clients. The safety microcontroller runs a Classic AUTOSAR stack: flash bootloader and security firmware at the bottom, the MCAL drivers, the AUTOSAR OS, basic software for communication, diagnostics, memory and watchdog management, the generated RTE and the vehicle-facing software components on top.

The colours in Figure 2.1 are the important part. Each colour is a different organisation with its own schedule: the silicon vendor releases a new board support package every quarter, the OS vendor issues safety-certified versions once a year, the AUTOSAR basic software comes from a stack vendor, open-source libraries have their own versions and security advisories, and the OEM changes the communication matrix every few weeks during development. The integrated ECU is a snapshot of all of them at compatible versions. Keeping that snapshot consistent is the integrator's main job.

2.2Interfaces are contracts

Between every pair of layers and every pair of teams there is an interface: a C++ API, a SOME/IP service, a shared-memory frame format, a configuration file, a DID that the tester reads. A working integration treats each one as a contract with a written definition, a version and an owner. In practice that means an interface control document or an interface description in a machine-readable form (ARXML for AUTOSAR ports and services, IDL or protobuf for middleware messages, header files with a version macro for C APIs, the ODX description for diagnostics), a versioning rule (incompatible changes increment the major version and need a migration plan; compatible additions increment the minor version), and a compatibility matrix that says which versions of which parts are known to work together.

The compatibility matrix deserves particular attention because it crosses the boundary of one ECU. The SoC software 4.12 may require MCU software 2.7 or later (a new message on the SPI link), calibration data in format version 3, a neural-network model trained for the new ISP tuning, and, on the vehicle side, a gateway that routes a new diagnostic address. If an update changes one of these without the others, the vehicle ends up in a combination nobody tested. Update systems therefore check the matrix before installing (Section 7.5), and the flash bootloader checks it in the "check programming dependencies" routine (Section 5.2).

Pitfall

The most common contract violation is an implicit one: a component starts to rely on behaviour that was never specified. A consumer assumes that frames arrive in order because they always did on the bench; a service assumes the time is synchronised when it starts; a diagnostic routine assumes the vehicle is stationary. The integration then breaks when another component changes something it was allowed to change. Writing down timing, ordering and preconditions as part of the interface, and testing them with contract tests at the boundary, is cheaper than finding them in a vehicle.

2.3Who owns which configuration

An ECU is shaped as much by configuration as by code: thousands of parameters for the basic software, the communication matrix, the diagnostic description, partition sizes, process start-up rules, logging levels, variant coding and per-unit calibration. Configuration is where integration conflicts hide, because it is often edited by several parties in tools that do not show who changed what. The rule that prevents most trouble is that every configuration item has exactly one owner, and that each kind of configuration is bound at a defined time.

2.4How a component drop becomes an integrated build

Day to day, integration is a pipeline. Component teams deliver "drops": a tagged version of their component with release notes, either as source on an integration branch or as a binary package with headers and a manifest. The integration team pins all versions in a build manifest (a repo manifest, a Yocto layer configuration, a Conan or similar lock file, or a list of package versions), builds the complete ECU image in a reproducible container (Build and containers 11.2), runs smoke tests on a bench (does it boot, do all processes start, do the cameras stream, does diagnostics answer), and then hands the build to the nightly regression on the HIL farm. When something breaks, the manifest makes it possible to bisect: build with the previous version of one component at a time until the culprit is found.

Two practices separate a calm integration from a chaotic one. The first is integrating continuously in small steps: a drop that changes one interface can be checked in a day, a "big bang" with twenty changed components takes weeks to untangle. The second is that the integration build is always releasable in principle: it carries a real version number, real signing (with development keys), the real diagnostic description and the real update package format, so that flashing, diagnostics and updates are tested every night rather than discovered at the release candidate.

Interesting detail

Many suppliers distinguish an "integration" build from a "release" build only by the signing key and the build flag that disables debug features, so that the binary that is tested is the binary that ships. Builds that differ in compiler options or include extra test hooks are the classic source of "it passed all tests, but the released version crashes", because the timing and memory layout changed.

3Boot, start-up dependencies and the service lifecycle

A camera ECU has a hard deadline at start: the rear view must be on the screen within about two seconds. Whether it is depends less on how fast each component starts than on what waits for what. Start-up is a dependency graph, and its critical path is an integration result.

3.1The boot chain in brief

The boot chain has been described three times in this book, each from a different angle: the generic Linux chain from boot ROM through U-Boot and the kernel to systemd (Linux 8.1, 8.4), the Qualcomm and QNX chain with its image file system and early camera (Camera ECU 8.2 to 8.5), and the reason the rear camera can start before the operating system (Embedded compute 6.8). The microcontroller side, with EcuM and BswM, and the Adaptive side, where Execution Management starts processes by function-group state, are in AUTOSAR 6.4 and 8.3. The summary: on power-up the boot ROM verifies and starts a first bootloader, which trains DDR memory and loads the next stages; each stage verifies the next (Chapter 6); the operating system starts its drivers and its first user process, which starts the rest according to a configuration. In parallel the microcontroller boots in a few hundred milliseconds and is the first to be on the vehicle bus.

3.2Start-up as a dependency graph

Every service in the stack needs something before it can start: the camera service needs the deserialiser driver and the link to the cameras; the rear-view application needs camera frames, the calibration, the display and the gear signal; the calibration needs the file system it lives on. Drawn as a graph with a duration on each node, the earliest start of each service is the latest finish among its dependencies, and the time to the first frame is the length of the longest chain, the critical path. Shortening anything off the critical path gains nothing; adding one dependency to a service on the path delays everything after it.

In the default configuration the first frame appears after 1.65 s and the critical path runs through the kernel and the camera link (serialiser lock and sensor initialisation take 400 ms). Three lessons come out of playing with the figure. First, an innocent-looking dependency is expensive: if the rear-view application waits for the logging daemon because a developer wanted its start-up messages logged, the first frame moves to 2.05 s and misses the requirement, although no component became slower. Second, verifying the whole 2 GB root file system before mounting it pushes the first frame to 2.69 s; that is why systems verify block by block on demand with dm-verity (Section 6.2), or, as the third option shows, pack what the rear view needs (here the calibration) into the boot image so that it does not wait for the file system at all. Third, moving work earlier in the chain helps only if it is on the critical path: starting the camera link from the bootloader saves 150 ms, and then the display pipeline becomes the critical path.

Numbers

Rear-view regulations such as FMVSS 111 in the United States require the image within 2.0 s of selecting reverse. Because a driver can open the door, start and shift within a few seconds, ECU budgets are usually set from power-on or wake-up: microcontroller on the bus within 100 to 300 ms, first camera image within about 1 to 2 s, full surround view and perception within 5 to 10 s. Network management often wakes the ECU when the door is unlocked, which buys the extra seconds (Networks 12.4).

Pitfall

Start-up dependencies are often implicit: a service polls for a file, retries a connection until it works, or blocks in a library call that waits for time synchronisation. Such waits do not appear in the start-up configuration, so the graph that the integrator draws is wrong. Measure instead: log a timestamped "ready" event from every service (Section 9.2), plot the real start-up timeline from hundreds of boots, and look at the slowest percentile, not the average.

3.3The service lifecycle: ready, degraded, failed, restarted

Once started, a service has a lifecycle that the platform must manage. It is starting until it reports that it is ready, which is not the same as "the process exists"; a camera service is ready when its streams deliver frames. It is running while it works, degraded when it works with reduced capability (one camera lost, a fallback model), stopping on a shutdown request, and failed when it crashed, missed a deadline or did not become ready in time. The platform decides what to do on failure: restart the process, switch the function group to a degraded state, or escalate to a reset of the ECU.

On Linux this is systemd's job: Type=notify services report readiness with sd_notify("READY=1"), WatchdogSec= expects periodic "WATCHDOG=1" messages, Restart=on-failure with StartLimitBurst= and StartLimitIntervalSec= defines the restart budget, and FailureAction= escalates (Linux 8.4). QNX has its system launch and monitor, and Adaptive AUTOSAR splits the job between Execution Management, which starts processes and receives their kRunning report, State Management, which decides function-group states, and Platform Health Management, which supervises checkpoints (AUTOSAR 8.4, 8.5). The mechanisms differ; the design questions are the same: what does ready mean for this service, what is a failure, how often may it restart, and what is the safe reaction when it cannot recover.

Pitfall

Unlimited restarts hide faults. A service that crashes every minute and is restarted every time looks healthy in a short test, fills the logs, consumes CPU and, if it crashes while holding a resource, degrades other services. A restart budget with escalation, and a diagnostic event when the budget is used, turns a hidden fault into a visible one.

3.4Shutdown and sleep: the forgotten half

Start-up gets attention because it has a visible deadline. Shutdown causes more field problems, because it has invisible ones. When the ignition goes off, the ECU has a limited time before network management lets it sleep or the power supply is cut: typically a few seconds, held up by a power latch the microcontroller controls. In that time it must write the fault memory and counters to non-volatile memory (the Dem and NvM of the Classic side, persistency on the SoC), flush logs, finish or abort any flash write in a consistent state, stop the cameras and tell the vehicle it is ready to sleep. An interrupted write can corrupt a calibration block or the fault memory; a missed sleep keeps the ECU awake and drains the battery (Networks 12.4).

Robust designs make every persistent write atomic (write a new copy, verify it, then switch a pointer, the same idea as A/B slots in Chapter 7), keep two copies of critical blocks, give the most important data immediate storage instead of waiting for shutdown, and test shutdown with power cuts at random moments thousands of times (Section 12.2).

Talk track

"Start-up is a dependency graph, and the time to the first rear-view frame is its critical path. I measure the real graph from ready events, remove accidental dependencies, and move what the first frame needs, such as calibration, out of the slow path. After start-up every service has a defined ready condition, failure detection, a restart budget and an escalation, and shutdown is designed just as carefully, because interrupted writes and missed sleeps are classic field issues."

4What a release is: content, identity and memory layout

A release is not a binary. It is a set of signed images, data, descriptions for the tools that will handle it, and evidence of how it was made and tested, all under one identifier that must still mean something in fifteen years.

4.1What one release contains

Release 4.12 of the camera ECU contains four kinds of things. The binaries are the boot chain images, the operating system and root file system, application packages, the microcontroller application and the neural-network models, each signed. The data are calibration defaults, parameter sets per vehicle variant, coding defaults and the catalogue that turns non-verbose log messages back into text. The descriptions are what the tools of other people need: the ODX or PDX file that tells the OEM's tester how to talk to this version, the flash container that the plant and workshop use, the A2L file for calibration tools, ARXML extracts and manifests, and the compatibility matrix. The evidence is the release note with known issues, test reports, the software bill of materials with licences, and the build record: commits, toolchain versions and the container digest that make the build reproducible.

The descriptions are the part that is most often forgotten and causes the most expensive delays. If the ODX for 4.12 does not contain the new DID that the plant's end-of-line test reads, the plant cannot produce cars with 4.12, whatever the quality of the software. Releasing descriptions together with binaries, generated from the same source (Section 8.4), is the cure.

4.2Version numbers, part numbers and what the ECU says about itself

An ECU must be able to say exactly what it is running, because the plant, the workshop, the update backend and the warranty department all ask. ISO 14229-1 reserves a range of data identifiers for identification, and every OEM specifies which of them its ECUs must support. Pitfall

Two different binaries with the same version number are an integration disaster that surfaces only in the field: the workshop believes the car runs 4.12, the backend offers an update that assumes 4.12's data format, and the car actually runs an engineering build that a test fleet forgot to reflash. Build systems should make it impossible: the version is assigned once by the release process, embedded in the image and in its signature, and every non-release build carries a version that cannot be confused with one.

4.3Memory layout and logical blocks

How the memory is divided decides what can be updated, what survives an update and what happens when an update fails. On the microcontroller, the flash typically holds the flash bootloader, which is never or almost never updated in the field; an application header with version, checksum or signature and a "valid" marker; the application code; one or more separately flashable calibration or parameter blocks; an area that emulates EEPROM for NvM data such as fault memory, counters and coding, which must survive reprogramming; and an area reserved for the hardware security module. Each separately programmable region is a logical block with its own identifier, version and signature, which lets a workshop update only the parameters without touching the code.

On the SoC, the storage (UFS or eMMC, tens of gigabytes) is divided into partitions: boot partitions with two copies of the bootloaders, two slots (A and B) for the kernel and the read-only root file system, partitions or package areas for applications and models that are updated individually, a persistent data partition for calibration, logs and crash dumps that survives updates, and a small replay-protected memory block (RPMB) where the security firmware keeps rollback counters. Section 7.3 shows why two slots make updates safe; the price is that half of the system storage holds an inactive copy.

Interesting detail

Many microcontrollers now offer dual-bank flash ("A/B swap"): the application exists twice, the new version is written into the inactive bank while the old one runs, and a hardware register selects which bank appears at the boot address. This gives a microcontroller the same safe update as a SoC, at the price of twice the code flash. Where flash is scarce, the application is updated in place by the bootloader, and the bootloader's job is to make sure an interrupted update leaves the ECU in the bootloader, not in a half-written application (Section 5.5).

4.4Reproducible builds and signing

Every image in a release is signed with a private key that never leaves a hardware security module in the OEM's or supplier's signing service. The build system sends a hash of the image to the signing service, which returns a signature after checking that the request comes from an authorised release pipeline; developers never have the production key. Development builds are signed with separate development keys, which only development ECUs (with development key hashes in their fuses, or in an unlocked state) accept. This separation is what stops an engineering build from ever running on a customer vehicle.

Reproducibility is the other half. Fifteen years after SOP, someone may have to build 4.12 again with one fix. That requires the exact sources, the exact toolchain and libraries (archived as a container image with a digest, Build and containers 11.4), the generator and configuration tool versions, the licences for commercial tools, and the debug information for every released binary, kept by build ID so that crash dumps from the field can be decoded (8.2). A practical test is to rebuild a release from the archive every year and compare the result bit for bit.

Talk track

"A release is signed binaries, data, the descriptions that testers and the plant need, and evidence. It is identified by version and part numbers the ECU reports in standard DIDs, plus the RXSWIN for type-approved functions. The memory layout decides what can be updated separately and what survives an update. Images are signed by a signing service with keys in an HSM, development and production keys are separate, and the build is archived so that it can be reproduced and its crash dumps decoded for the life of the vehicle."

5Flashing over UDS

Flashing is the moment when an ECU is most vulnerable: its own code is being replaced, the vehicle around it is in an unusual state, and a power cut can leave it without a working program. The flash sequence that OEMs specify is a careful answer to all three problems. Knowing it byte by byte makes plant, workshop and update issues easy to read.

5.1Why a separate bootloader

A program cannot safely erase and rewrite the flash it is executing from. A microcontroller's application is therefore reprogrammed by a separate flash bootloader (FBL): a small program in its own flash region that runs after every reset, checks whether a valid application is present (the "valid" marker and the checksum or signature in the application header), and either jumps to it or stays active and waits for a tester. The bootloader implements only the diagnostic services needed for programming, its own small communication stack and the flash driver, often copied to RAM at run time because the flash cannot be read while it is being written in the same bank. It is never updated in normal field updates, because a failed bootloader update would leave nothing to recover with; when it must change, a bootloader updater is flashed as an application that replaces the bootloader in a guarded procedure.

On a SoC the picture is similar with more layers: the boot ROM and the first bootloaders play the role of the FBL, and updates are written by the running system into an inactive slot (Chapter 7). Many camera ECUs therefore have two update mechanisms: UDS flashing through the microcontroller's bootloader for the MCU and as a recovery path, and an A/B update for the SoC, triggered either over UDS by a tester or by the vehicle's update master.

5.2The flash sequence step by step

OEM flash specifications differ in details, but almost all follow the same three phases built from ISO 14229 services: a pre-programming phase that prepares the vehicle, a programming phase in the bootloader, and a post-programming phase that restores normal operation. The sequence diagram below shows them; step through it to see what each step protects against.

The tester opens the extended session (10 03) and asks the ECU whether programming is possible now (31 01 02 03, check programming preconditions): the vehicle is stationary, the engine is off, the voltage is in range. Then it switches off fault storage (85 02, ControlDTCSetting off) and normal communication (28 03 01, CommunicationControl: disable receive and transmit of normal messages), usually as functional requests to all ECUs. Otherwise every other ECU would store "lost communication" fault codes while this one is silent, and the programming traffic would compete with normal traffic for the bus.

10 02 requests the programming session. The application does not implement programming; it writes a flag into a RAM area or the NvM that survives a reset ("programming requested"), resets the microcontroller, and the bootloader starts, sees the flag and stays active. Many bootloaders send the positive response 50 02 themselves after the reset, so the tester sees one response although the program that answers has changed. The response carries the P2 and P2* timing values the tester must use.

Only an authorised tester may program. With seed and key (27 11, then 27 12 <key>), the bootloader sends a random seed, the tester computes a key with a secret algorithm and key, and the bootloader compares. Failed attempts are counted and trigger a delay, so keys cannot be guessed quickly (negative responses 0x35 invalid key, 0x36 exceeded number of attempts, 0x37 required time delay not expired). Newer ECUs use service 0x29 with certificates instead, so that the secret is not shared by every tester in the world (Camera ECU 10.4).

Before changing anything, the tester writes who is programming and when, here the tester's identifier into DID 0xF198 (2E F1 98 …) and the date into 0xF199; some OEMs use one combined fingerprint DID. The bootloader stores it with the logical block, so the history of reprogramming can be read later (0xF183 to 0xF185). It is the first thing a field engineer looks at when a module behaves differently from its siblings.

The erase routine (31 01 FF 00 with the address and length format byte 0x44 and the 4-byte address and size of the logical block) erases the region. Erasing takes seconds on a microcontroller, longer than the normal response time P2 (typically 50 ms), so the bootloader immediately answers 7F 31 78, "request correctly received, response pending", and repeats it before each P2* (typically 5 s) expires until the erase is done and it sends 71 01 FF 00 00. From this moment the old application is gone; the "valid" marker was cleared first.

34 RequestDownload announces address and size (and in the data format byte whether the data are compressed or encrypted). The positive response 74 20 01 02 says: the following length field is 2 bytes long, and the maximum block length is 0x0102 = 258 bytes, including the service identifier and the block sequence counter, so 256 data bytes per block. The tester then sends 36 01 <256 bytes>, 36 02 … and so on; the counter wraps from 0xFF to 0x00, and a repeated block (after a lost response) is recognised by its counter and not written twice. 37 ends the transfer.

The tester starts the check-memory routine with the expected checksum, or the bootloader verifies the signature of the block over its whole content. Only if it matches does the bootloader write the "valid" marker. A modern bootloader checks a signature with the OEM's public key here (or lets its HSM do it), so that only images signed by the OEM can become valid, whatever a tester sends (Chapter 6).

If the release consists of several logical blocks (application, calibration, a second processor's image), each is downloaded and checked in turn. Then 31 01 FF 01 asks the bootloader to confirm that all blocks are present, valid and compatible with each other and with the hardware. A new application with an old calibration block of an incompatible format is refused here, instead of crashing after the reset.

11 01 (hard reset) restarts the ECU. The bootloader finds a valid application and jumps to it; the new software starts for the first time. If anything is still wrong, the bootloader stays active and the ECU still answers the tester, which is what keeps a failed flash recoverable.

The tester switches normal communication and fault storage on again, functionally for all ECUs (28 00 01, 85 01), clears the fault codes that other ECUs may still have stored during programming (14 FF FF FF), returns to the default session, and reads the version DIDs to confirm. In a vehicle, coding and calibration are restored or rewritten now if the new software needs them (Section 13.4).

Interesting detail

The first byte of every frame is the ISO-TP protocol control information. 0x is a single frame with x data bytes, 1x xx a first frame with a 12-bit total length, 2n a consecutive frame with a 4-bit sequence number that wraps from 2F to 20, and 30 BS ST a flow control frame (continue, with block size and minimum separation time). In the trace above, the ECU asks for a flow control after every 8 consecutive frames (BS = 8). With classic CAN a single ISO-TP message is limited to 4095 bytes, which is why maximum block lengths on CAN are at most 0xFFF; CAN FD frames carry 63 data bytes per consecutive frame and long messages use an escape with a 32-bit length.

5.3Where the time goes

Flashing time matters in the plant, where every second at the end-of-line station costs money and is multiplied by a million cars, and in the workshop, where a customer waits. The time is the sum of fixed steps (session changes, security access, two resets), the erase, the transfer of the data, the programming of the flash, and the final verification. Which of them dominates depends on the bus, the transport parameters and the memory.

A few numbers from the model (they are checked in experiments/check_interactive.js). A 4 MB microcontroller application over classic CAN at 500 kbit/s needs about 2.6 minutes when the ECU allows back-to-back frames (STmin 0): the link carries only about 29 KB/s of payload, because each 8-byte frame carries 7 data bytes and costs about 115 bit times. If the ECU's flow control asks for STmin = 1 ms, which slow bootloaders do to keep up, the same flash takes over 10 minutes: one parameter in the bootloader configuration quadruples the time. CAN FD at 2 Mbit/s brings it to about 41 s, and DoIP over 100BASE-T1 to about 17 s, where the link is no longer the limit: erasing and programming the flash take 12 of those seconds. For a 2 GB SoC image over DoIP the transfer at 100 Mbit/s takes about 3 minutes; at 1 Gbit/s the storage write dominates, and programming one block while the next arrives saves another 18 s.

Why it matters

The flash time is a negotiated requirement in the OEM's specification, because it determines the end-of-line cycle time and the workshop time per car. Typical levers, in order of effect: a faster transport (CAN FD or DoIP instead of CAN), STmin 0 and large blocks, compression of the data in the download request, pipelining in the bootloader (program from a double buffer while receiving the next block), erasing sector by sector during the download instead of up front, and splitting the release so that a workshop updates only the logical blocks that changed.

Pitfall

Small blocks over a fast link waste most of the time in round trips. With DoIP, a 4 KB block moves in under half a millisecond, but each block still waits for the tester to see the previous positive response, so a 2 GB image in 4 KB blocks takes over 13 minutes in the model instead of 4. Block length is announced by the ECU in the 0x74 response; on Ethernet it should be tens of kilobytes or more.

5.4Flash containers, ODX and the tools that run the sequence

The plant, the workshop and the developer's bench all run the same sequence, but with different tools: a development flash tool on the bench, the OEM's end-of-line system in the plant, and the OEM's workshop tester in the field. To make that possible, a release is delivered as a flash container: the binary data of each logical block (often as Intel HEX or Motorola S-record files, or a binary with an address map), their signatures, and a description of how to program them. The standard description format is ODX (ISO 22901-1, ASAM MCD-2D), whose ODX-F part describes flash data and sessions; ODX files and the flash data are packaged together as a PDX file. Some OEMs use their own container formats with the same content. The tester also needs the diagnostic description of the ECU (the ODX-D part), the security algorithm (a seed-key library or, with 0x29, certificates from the OEM's public key infrastructure), and the flash sequence itself, which is either coded in the tool, written as a script, or described in OTX (Open Test sequence eXchange, ISO 13209).

For the supplier, the practical consequence is that the flash container is a release deliverable that must be tested like code: flash every release candidate on a bench with the OEM's own tool or a faithful simulation of it, from the previous released version and from the oldest version still in the field, with the plant's sequence and with the workshop's.

5.5When flashing fails

A flash can fail at any step: the battery voltage drops, a cable is pulled, the tester crashes, a block arrives corrupted. The design goal is simple: whatever happens, the ECU must remain flashable. The bootloader achieves it with the "valid" marker. The marker is cleared before the erase and written only after the check-memory and dependency routines have succeeded, so any interruption leaves an ECU without a valid application, which stays in the bootloader after the next power-on and answers the tester. The workshop then simply repeats the flash. What must never be interrupted is a bootloader update, which is why bootloaders are updated only by a guarded procedure with a copy.

The negative responses tell what went wrong. The most common are 0x22 conditionsNotCorrect (preconditions not met, for example vehicle moving), 0x24 requestSequenceError (steps out of order, such as a download without erase), 0x31 requestOutOfRange (address or routine not allowed), 0x33 securityAccessDenied, 0x35 invalidKey, 0x36 exceededNumberOfAttempts, 0x37 requiredTimeDelayNotExpired, 0x70 uploadDownloadNotAccepted, 0x72 generalProgrammingFailure (the flash driver reported an error), 0x73 wrongBlockSequenceCounter, and 0x7F serviceNotSupportedInActiveSession. A tester log with the NRC is usually enough to find the cause.

Pitfall

A classic plant problem is a flash that works in the lab and fails on the line, because the line powers the ECU from a different supply, the cable to the vehicle connector is longer, or the end-of-line computer flashes several ECUs at once over one gateway. Test the sequence with the real fixture, at the minimum allowed voltage, and with the parallel load the plant will generate. Another is the ECU-specific programming counter: some bootloaders allow only a limited number of programming attempts (counted in the fingerprint area) and then refuse, which surprises test teams that reflash prototypes hundreds of times.

Talk track

"Flashing runs in the bootloader, because code cannot replace itself. The tester prepares the vehicle: extended session, check preconditions, fault storage and normal communication off. Then programming session, security access or authentication, fingerprint, erase with response pending, RequestDownload, TransferData blocks with a sequence counter, TransferExit, a check-memory routine that verifies checksum or signature, and a dependency check. Only then is the application marked valid, so any interruption leaves the ECU in the bootloader and recoverable. Time is dominated by the bus on CAN and by the flash memory on DoIP; STmin and the block length are the parameters to watch."

6Secure boot and the chain of trust

Signing an image is useless if the ECU does not check the signature every time it starts. Secure boot is that check, done by each stage on the next one, starting from a piece of code and a key that cannot be changed.

6.1Why secure boot exists

An attacker who can run their own code on an ECU owns everything that ECU can do: send brake requests if it is on the chassis bus, manipulate what the camera reports, read keys, or disable the function. The cheapest way to run one's own code is not a clever exploit but simply reflashing the device, through the diagnostic port, a debug interface, or by desoldering the flash chip. Secure boot closes that path: at every power-on, every piece of code is checked against a signature made with a key the attacker does not have, and code that fails the check is not run. It also protects against accidents: a corrupted image is detected, not executed. In the TARA of the functional safety chapter, secure boot is one of the standard controls (Functional safety 9.6); this section explains how it works.

6.2How each stage verifies the next

The chain starts in the boot ROM, code written into the chip at manufacture that cannot be changed. During production of the ECU, the hash of the OEM's (or supplier's) public root key is burned into one-time-programmable fuses, and a fuse that enables secure boot is blown. From then on the boot ROM loads the first bootloader, computes its hash, verifies its signature with a public key whose hash must match the fuses, and runs it only if both checks pass. The first bootloader does the same for the next stage with a key it carries in its signed image, and so on through the hypervisor and the kernel. Because each stage's code and keys were themselves verified, trust extends from the fuses to the last stage: a chain of trust.

The root file system is too large to hash at every boot (seconds for gigabytes, as Figure 3.1 showed). Linux's dm-verity solves this with a hash tree: the file system is divided into 4 KB blocks, their hashes are hashed again in levels, and only the root hash is stored, inside the signed kernel command line or a signed table. Each block is checked when it is first read; a modified block causes an I/O error instead of returning tampered data. QNX and other systems have equivalent mechanisms. Applications, models and calibration data that live outside the verified file system are signed packages, verified at installation and again when loaded.

The cost of verification is mostly hashing. On the cloud server used for this book, OpenSSL hashes about 1.6 GB/s with SHA-256 using the CPU's SHA instructions, and verifies an ECDSA P-256 signature in about 70 µs and an RSA-2048 signature in under 20 µs (experiments/out/crypto_speed.txt). An automotive application core with the Armv8 crypto extensions is in the same order of magnitude, so verifying a 64 MB kernel and initial file system costs some tens of milliseconds; boot ROM stages that run before caches and DDR are fully set up are slower, which is one reason early stages are kept small.

Interesting detail

Microcontrollers do it differently. Their hardware security module (HSM), a separate small core with its own memory and the keys, checks the bootloader and application flash before it releases the host cores from reset ("secure boot"), or lets the host start and checks in parallel ("authenticated boot"), withholding keys if the check fails. Because the MCU must be on the bus within a few hundred milliseconds, checking several megabytes with a symmetric MAC (AES-CMAC with a key in the HSM) is common; the MAC values are computed and stored during the first verified flash, after the signature was checked once.

6.3Keys: generation, provisioning and the plant

Secure boot is only as strong as its key handling. The private root keys are generated and stored in hardware security modules of the OEM's or supplier's signing service and used through an audited process; there are separate key pairs for development and production, and often per ECU family. The public key hashes reach the chips in the ECU plant: a provisioning station blows the fuses (or writes the HSM's key store) and enables secure boot; that step is irreversible. Symmetric keys for SecOC, diagnostic authentication and the individual ECU identity are injected at end of line from the OEM's key management system, encrypted for the specific ECU so that they never appear in clear text on the production line. A good design also plans revocation: if a signing key is ever compromised, the chips must be able to accept a new one, for example through several key slots in the fuses of which one can be revoked.

Pitfall

Prototype ECUs with development keys and production ECUs with production keys look identical. If a development-signed image reaches the plant, or a prototype with secure boot disabled reaches a customer car, the result is either a line stop or an unprotected vehicle. Plants check the key state of each ECU at end of line, and the release process makes sure only production-signed containers can be loaded into plant and workshop tools.

6.4Rollback protection and locked debug ports

A valid signature proves that the OEM signed an image, not that the image is current. An attacker who has the old, legitimately signed version 4.03 with a known vulnerability could flash it back. Anti-rollback prevents this: each image carries a security version number, and the device stores the minimum version it accepts in fuses (one fuse burned per increment) or in replay-protected storage (RPMB). Images below the minimum are rejected. The minimum is raised only when a release fixes a security problem, not with every release, because it also prevents legitimate rollbacks (Section 7.5).

Finally, secure boot decides what code starts; it does nothing against someone attaching a debugger to a running system. Production ECUs therefore lock their debug interfaces: JTAG and trace are disabled by fuses, or opened only after a challenge-response with a signed debug certificate for a specific device (Section 11.6). Diagnostic services that write memory or calibration are protected by security access or authentication, and the update path verifies signatures again before installation.

Talk track

"Secure boot is a chain of trust rooted in immutable boot ROM and a key hash in fuses: each stage verifies the signature of the next before running it, the kernel holds the root hash of a dm-verity file system checked block by block, and applications and models are signed packages. On microcontrollers the HSM checks the flash. Keys stay in HSMs, development and production keys are separate, keys are injected at end of line, anti-rollback counters stop downgrades to vulnerable versions, and debug ports are locked, because secure boot alone does not protect a running system."

7Over-the-air updates, A/B slots and rollback

Flashing in a workshop costs an appointment, an hour and a technician. Updating over the air costs a download. But an update that fails in a workshop is fixed on the spot, while an update that fails over the air fails in thousands of cars at once, far from any tester. OTA update design is mostly about making failure harmless.

7.1Why over-the-air updates, and what the regulation asks

Vehicles are now expected to receive fixes, security patches and new functions during their life, and a recall that needs a workshop visit for a software fix costs the OEM tens to hundreds of euros per car. Over-the-air (OTA) updates make that cheap, but they turn the update process itself into a safety- and security-relevant function. UN Regulation 156, mandatory for new vehicle types in the EU and other UNECE markets since 2022 and for all new vehicles since July 2024, requires the OEM to run a certified software update management system: every update is assessed for its impact on type-approved functions and safety, the RXSWIN is updated when relevant, the vehicle's software versions are recorded, updates are protected against manipulation, the vehicle is in a safe state during installation, the driver is informed, and a failed update must not leave the vehicle unsafe (Standards and regulations 5). The camera ECU's update design is the supplier's part of that system.

7.2The vehicle-level flow

An OTA update starts in the OEM's backend as a campaign: a set of vehicles, selected by type, VIN range and installed software versions, and a package for each ECU that needs to change. The telematics unit downloads the package in the background, resuming after interruptions, and hands it to the vehicle's update master (an Adaptive Vehicle UCM or an OEM-specific client on a central computer), which verifies signatures, checks the dependencies between ECUs, and waits for the preconditions: vehicle parked, sufficient battery charge, and the driver's consent on the screen for updates that make the car unavailable. It then distributes the packages: to SoC-based ECUs, which install in the background into their inactive slot, and to microcontroller ECUs, which the master flashes with the same UDS sequence a workshop would use (Section 5.2). Activation is coordinated so that all ECUs switch to the new versions together, then each verifies itself, and the master reports success or failure to the backend.

The AUTOSAR chapter shows the Adaptive side of this with UCM, software packages and V-UCM (AUTOSAR 10.5). Many OEMs use their own update clients with the same structure. Packages are often delta updates: only the binary differences between the installed version and the new one, which can shrink a 2 GB image to tens of megabytes, at the price that the delta only applies to an exactly known installed version, another reason why the version identification of Section 4.2 must be precise.

7.3A/B updates with health check and rollback

The robust update scheme for a SoC keeps two complete copies of the system: slot A, which is running, and slot B, which receives the update. Installation writes into B while A keeps working, so it can take as long as it needs and can be interrupted at any time. Activation is a reboot into B, but only on trial: the bootloader is told to try B, counts how often it has done so, and falls back to A if B does not boot successfully within a limit. Once B is running, a health check decides whether to keep it; only then is the update committed and B becomes the good slot. A remains as a fallback until the next update overwrites it.

Two mechanisms make the scheme safe. The boot counter in the bootloader handles software that does not even start: each boot of a trial slot increments the counter before starting it, a successful commit clears it, and when the counter reaches the limit the bootloader boots the other slot. U-Boot implements exactly this with its bootcount, bootlimit, upgrade_available and altbootcmd variables; open-source update frameworks such as RAUC, SWUpdate and Mender, Android's A/B updates and the vendor bootloaders of automotive SoCs use the same idea under other names. The health check handles software that starts but does not work: within a window after boot, the supervised services must report that they are running correctly (cameras stream, diagnostics answer, the microcontroller link is up), otherwise the update client rolls back. Going through the failures shows what each mechanism contributes. A bad signature is caught before anything is written. A power loss during installation is harmless because the boot target was never changed. A version that does not boot is caught by the boot counter: three attempts, then the bootloader returns to A. A version that boots but does not work is caught by the health check. And a power loss after a successful boot but before the commit simply leads to another trial boot, because the counter is still below the limit; this is why the limit is three rather than one, and why the counter is incremented by the bootloader and cleared only by a positive decision.

Pitfall

A health check that is too weak commits broken software: "the process started" is not "the function works". A health check that is too strict rolls back good software when a camera is unplugged in a workshop. The criteria should be the ones the function needs (frames from each connected camera, communication with the microcontroller, diagnostics reachable) and should distinguish faults of the new software from faults of the vehicle, which an update cannot fix.

7.4Other update schemes and where each fits

A/B is the most robust scheme but doubles the storage. The alternatives trade storage for risk. A recovery partition scheme has one main system and a small recovery system that can download and install a full image; an update overwrites the main system in place, and a failure leaves the device in recovery, functional only for updating. That is acceptable for an infotainment unit, not for a camera that must show the rear view. Package-level updates replace individual applications or software clusters (Adaptive UCM installs a new version alongside the old one, activates it and can roll back), which is fast and fine-grained but relies on the base system being compatible. Dual-bank microcontroller flash gives a microcontroller A/B behaviour (Section 4.3); without it, the microcontroller is updated in place by its bootloader, and the recoverability argument of Section 5.5 applies. Container-based deployment of applications on top of a fixed base image is used in some central computers and development fleets, with the same commit-or-rollback logic per container.

In a real camera ECU these are combined: the SoC's operating system and root file system in A/B slots, perception models and some applications as packages with their own versions, the microcontroller flashed by the update master over UDS, and its bootloader never updated in the field.

7.5Compatibility, data migration, and rollback versus anti-rollback

Rolling back the code is easy; rolling back the data is not. If 4.12 converts the calibration or the persistent configuration to a new format on its first start and 4.11 cannot read the new format, a rollback to 4.11 leaves a working program with unreadable data. The rule is that a new version must not change persistent data irreversibly until it is committed, either by keeping the old format until commit or by writing the new format alongside the old. The same reasoning applies across ECUs: if 4.12 on the SoC needs a new SPI message from the microcontroller, the update master must update and activate both together and roll both back together, which the compatibility matrix from Section 2.2 makes checkable.

Rollback also meets anti-rollback (Section 6.4). The security version in fuses or RPMB must not be raised when 4.12 is installed, only when it is committed, otherwise a failed 4.12 could no longer fall back to 4.11. And when a release fixes a security vulnerability, raising the minimum version deliberately makes rollback to the vulnerable versions impossible; that decision belongs to the security team, not to the update client.

Talk track

"An OTA campaign goes from the backend through the telematics unit to an update master that checks dependencies, preconditions and consent, installs on each ECU, activates them together and reports. On the SoC I use A/B slots: install into the inactive slot while the old one runs, boot it on trial with a boot counter in the bootloader, run a health check, and commit or roll back. The counter catches software that does not boot, the health check catches software that does not work, and a power loss at any point leaves a working slot. Rollback only works if persistent data are not converted irreversibly before the commit and the anti-rollback counter is raised only on commit."

8Diagnostics beyond the basics

The camera ECU chapter explains what diagnostics is for and which services exist. This chapter looks one level down: how a request travels on CAN and Ethernet, what the diagnostic stack inside the ECU does with it, where the descriptions come from, and how to read a fault memory like an engineer.

8.1A short recap

Diagnostics is the standard way for a tester (plant, workshop, developer, or the vehicle's own update master) to talk to an ECU. UDS (ISO 14229) defines the services: sessions (default, extended, programming) with timeouts, security access and authentication, reading and writing data identifiers (DIDs), starting routines (RIDs), controlling inputs and outputs, reading and clearing fault codes, and the programming services of Chapter 5 (Camera ECU 10.3 to 10.7). A fault code (DTC) is stored when a monitor's event is qualified after debouncing, with a status byte of eight flags, snapshot data and extended data (Camera ECU 11.2 to 11.6). What follows assumes those basics.

8.2On the wire: ISO-TP on CAN and DoIP on Ethernet

On CAN, UDS messages longer than one frame are carried by ISO-TP (ISO 15765-2), seen in the flash trace of Section 5.2: single frames, first frame, consecutive frames and flow control. Each ECU has a physical request and response identifier pair, and there is a functional request identifier that all ECUs listen to (on OBD the well-known 0x7DF; OEM-specific otherwise). Timing is supervised on both levels: ISO-TP has its own timeouts (typically 1000 ms for a missing flow control or consecutive frame), and UDS has P2 (the ECU must answer within typically 50 ms or send 0x78 response pending) and P2* (after response pending, typically 5000 ms).

On Ethernet, UDS is carried by DoIP, diagnostics over IP (ISO 13400-2), on port 13400 (Networks 7.7). A DoIP exchange has more structure than ISO-TP because the tester must first find the vehicle on a network and be allowed in. It sends a vehicle identification request over UDP and receives an announcement with the VIN, the logical address of the DoIP entity (usually the central gateway) and its entity identifier. It opens a TCP connection and sends a routing activation request with its own logical address (external testers use addresses 0x0E00 to 0x0FFF); the gateway answers with response code 0x10 when routing is activated. Only then can diagnostic messages flow: each carries a source and a target logical address and the UDS bytes, and the gateway first acknowledges the message (0x8002) and then delivers the ECU's response (0x8001). For ECUs behind the gateway on CAN, the gateway translates between DoIP and ISO-TP.

8.3Inside the ECU: Dcm and Dem

In a Classic AUTOSAR ECU, two basic-software modules implement diagnostics. The Diagnostic Communication Manager (Dcm) handles requests in three layers. The session layer (DSL) manages sessions and their timeouts, supervises P2, and sends 0x78 response-pending messages automatically when a service takes long. The dispatcher (DSD) checks whether the service is supported and allowed in the current session and security level, and answers with the right negative response if not. The processing layer (DSP) implements the standard services: it reads and writes DIDs by calling the software components through RTE ports or callbacks, starts routines, handles the jump to the bootloader, and for fault-memory services asks the Dem. The Diagnostic Event Manager (Dem) receives event reports from monitors in software components and basic software, debounces them, maintains the status bytes, snapshots and extended data of the DTCs, manages operation cycles and aging, decides which entries to displace when the memory is full, stores everything through NvM, and informs the Function Inhibition Manager (FiM), which switches off functions that depend on a failed input.

All of this is configured, not coded: which services exist in which session, the length and data type of each DID, which software component provides it, each DTC with its event, debounce algorithm, snapshot records and priority. The configuration is generated from the diagnostic description (next section), and that is why a DID added to the description but forgotten in the software component shows up as a missing port at generation time rather than in the vehicle. On an Adaptive machine, ara::diag plays the role of Dcm and Dem together (AUTOSAR 10.2); on a Linux or QNX SoC without Adaptive, a supplier's diagnostic server process does the same, usually reachable through the microcontroller or directly over DoIP.

Pitfall

Operation cycles decide when DTC statuses advance, and they are often wrong at first. If the Dem's power or ignition cycle is never started on the SoC side because the cycle signal comes from the microcontroller and the message was not integrated, pending DTCs never become confirmed, aging never happens, and the test-not-completed bits stay set forever. Check operation cycles explicitly in the integration tests.

8.4The diagnostic description: one source for ECU and tester

The ECU and every tester must agree on every byte: which DIDs exist, how their values are encoded, which routines take which parameters, which DTCs exist and what their snapshots contain. That agreement is the diagnostic description. The OEM specifies the vehicle-wide parts (sessions, security, identification DIDs, the flash sequence) and the supplier adds the ECU-specific parts. It is usually edited in a dedicated tool (Vector's CANdelaStudio with its CDD format is widespread) and exported as ODX for testers and as configuration for the ECU's diagnostic stack. Generating both from the same source is what keeps them consistent; describing a DID in a spreadsheet and coding it by hand in the ECU guarantees that they diverge.

The direction of travel is SOVD, service-oriented vehicle diagnostics: an HTTP and JSON API defined by ASAM and standardised as ISO 17978, where a tester (or a cloud service) reads data, faults and logs, runs operations and installs software through REST resources rather than byte-level services. SOVD fits central computers with many applications, where a UDS-style flat list of DIDs scales badly and diagnostic access over the internet is wanted; it coexists with UDS, which remains in microcontroller ECUs and is reached through an SOVD gateway. Adaptive AUTOSAR R25-11 supports SOVD natively in its diagnostic cluster.

8.5Reading a fault memory like an engineer

The DoIP capture above contains a fault memory read: 19 02 08 (ReadDTCInformation, reportDTCByStatusMask, mask 0x08 = confirmed DTCs) answered by 59 02 FF 9A 1F 29 28 C1 23 87 2F. Decoded: the status availability mask is 0xFF (all eight status bits are supported), followed by two records of a 3-byte DTC and a status byte. The first DTC, 0x9A1F29, is B1A1F-29 in SAE J2012 notation (the top two bits 10 mean "B", body; 0x29 is the failure type "signal invalid"); its status 0x28 means confirmedDTC and testFailedSinceLastClear set, testFailed clear: the fault happened, matured, and is not present now. The second, 0xC12387, is U0123-87 (U, network; lost communication with a sensor module, failure type "missing message"); its status 0x2F adds testFailed, testFailedThisOperationCycle and pendingDTC: it is failing right now.

That distinction drives workshop decisions. A historic, not current fault with an occurrence counter of 1 is often a one-off (a voltage dip during a jump start) and a reason to clear and observe, not to replace parts. A current fault with a high occurrence counter is a reason to measure. The snapshot (19 04, freeze frame) tells the conditions when the fault was first or last detected: supply voltage, temperature, vehicle speed, odometer, time since start; the extended data (19 06) give the occurrence counter, the aging counter and the fault detection counter. Designing those snapshot and extended data records well is one of the most valuable things a supplier can do for after-sales, because they are often the only facts the workshop and the warranty analysis will ever see (Section 14.4).

9Logging, tracing, monitoring and health

In the lab you attach a debugger; in a customer's car you cannot. Whatever the ECU recorded about itself before, during and after a failure is the only witness, so what to log, how to supervise, and how to keep crash data are design decisions made at integration time, not afterthoughts.

9.1Why the log is the only witness

Field problems share three properties that make them hard: they are rare (one car in ten thousand, once a month), they depend on conditions that are gone by the time anyone looks (temperature, a voltage dip, a particular sequence of events on the bus), and the people who see them are not engineers. Diagnostics (Chapter 8) records that something went wrong and a few facts about it. Logs, traces, health counters and crash dumps record how. The integration team decides the conventions for all of them, because only a consistent scheme across all components lets someone reconstruct a failure that crosses components, which most interesting failures do.

9.2DLT: the automotive log format

Automotive ECUs log in DLT, the AUTOSAR Log and Trace protocol, which started as a GENIVI (now COVESA) open-source project and is used by the Classic Dlt module, Adaptive ara::log and many Linux and QNX systems (AUTOSAR 10.3). Its design answers the specific needs of a vehicle: logs from many ECUs end up in one stream and must be told apart, bandwidth and CPU are scarce, and log levels must be changeable in the field without a new build. Every message therefore carries a four-character ECU identifier, an application identifier and a context identifier (a subsystem of the application), a message counter to detect losses, a timestamp from the ECU's clock, a log level (fatal, error, warn, info, debug, verbose), and a payload. A DLT daemon on each ECU collects messages from local applications and sends them to a client such as the open-source DLT Viewer over TCP, UDP or a serial line, or stores them in files; log levels per context can be changed at run time by a control message.

Two practical features matter at scale. In non-verbose mode an application sends only a message identifier and the raw argument values; the text and the argument types live in a description file (in AUTOSAR, part of the ECU's description) that the viewer uses to reconstruct the message. The warning in line 5 is 77 bytes in verbose form and 25 bytes as a non-verbose message with an identifier and the two numbers (experiments/out/dlt_sizes.txt), and the ECU no longer formats strings. The catch is that the description must be released together with the software (Section 4.1), or old logs become unreadable. The second feature is the timestamp: the ECU timestamp counts from the ECU's start, while the storage header records the logger's clock. Correlating logs from several ECUs therefore needs time synchronisation (gPTP on Ethernet) or a reference event visible in all logs.

Pitfall

Logging changes timing. A debug log level switched on in a test vehicle can add milliseconds per frame on the SoC and saturate the logging path, and the bug under investigation disappears. Keep the field log level at info or warn with rate limits per context, log events rather than per-frame data, and measure the cost of the logging configuration you ship, like any other load.

9.3Tracing: when the question is timing

Logs answer "what happened"; traces answer "when, and what else was running". On Linux, ftrace and the tools built on it record scheduler switches, interrupts, and markers written by applications, with microsecond timestamps and little overhead (Linux 10.5); LTTng and Perfetto do the same with more structure. QNX has its own kernel event trace. On a Classic AUTOSAR microcontroller, the OS can expose task and interrupt events through the ARTI interface (AUTOSAR Run-Time Interface, the successor of ORTI) to trace and timing analysis tools, and hardware trace records every executed instruction (Section 11.3). For a vision pipeline, the most useful trace is often the simplest: a marker with the frame number at each stage (capture, ISP done, inference done, displayed), which turns "sometimes laggy" into a latency histogram per stage. The worked example in Linux 10.8 shows such a hunt.

9.4Health supervision and watchdogs

Supervision is layered, and each layer covers the failure of the layer above. Applications report checkpoints: an alive checkpoint every cycle, deadline checkpoints at the start and end of a time-critical step, logical checkpoints that must occur in a defined order. A health manager (Adaptive Platform Health Management, the Classic Watchdog Manager, or a supplier's equivalent) evaluates them and decides on recovery through state or execution management: restart a process, switch a function group to a degraded mode (Section 3.3). The health manager in turn proves that it is alive by serving the SoC's hardware watchdog only while everything it supervises is fine; if the health manager or the operating system hangs, the watchdog resets the SoC.

A watchdog inside the SoC cannot catch every failure of the SoC (a power-management fault, a hang that also stops the watchdog's clock), so the safety microcontroller supervises the SoC from outside: the SoC sends a heartbeat over SPI with a counter and a status, and if the heartbeat stops or reports nonsense, the microcontroller puts the camera function into a safe state on the vehicle bus (for example "rear view unavailable", so that the driver gets a message instead of a frozen image), then power-cycles the SoC. The microcontroller is supervised by a window watchdog in the system basis chip, which must be served neither too early nor too late (a runaway loop that serves it constantly is caught too), often with a question-and-answer protocol where the correct answer depends on a challenge. This chain is part of the safety concept; the functional safety chapter explains why such independent monitors are needed (Functional safety 5.6).

Why it matters

Every reset should leave a trace: a reset reason (power-on, watchdog, software request, brown-out, exception) read from the chip's reset status register at the next start, logged, counted in a persistent counter and, if unexpected, stored as a DTC. "Sporadic reboots" in the field without a reset reason are almost undiagnosable; with one, half the investigation is done.

9.5Crash data from the field

When software crashes in a car, three kinds of data can survive. The reset reason and counters described above. A persistent log buffer: a region of RAM that is not cleared at reset (on Linux, pstore/ramoops), where the kernel and applications keep their last messages; after a watchdog reset the next boot copies it to storage. And a crash dump: on Linux and QNX a process core dump, cut down to a minidump with the stack and registers of each thread so that it fits the storage and upload budget, or for kernel crashes a kdump from a reserved crash kernel (Linux 10.2); on a microcontroller, the trap or fault handler writes the exception registers, the stack pointer and a part of the stack into a no-init RAM area before resetting, and the application copies it to NvM at the next start.

Crash data are only useful with the matching debug information, which is why release builds keep their symbol files archived by build ID (Section 4.4). They leave the car either through diagnostics (DIDs with crash counters and the last crash context, RequestUpload 0x35 or RequestFileTransfer 0x38 for files), through the telematics unit to the OEM's backend, or on a data logger in test vehicles. In the field, privacy rules (camera images, location) and data volumes limit what may be uploaded; that policy is agreed with the OEM, not decided by the developer who writes the crash handler.

Talk track

"In the field the ECU's own records are the only witness, so I design them: DLT logs with ECU, application and context identifiers, non-verbose in production with the catalogue released alongside, timestamps that can be correlated; frame markers for timing; layered supervision from application checkpoints through the health manager and hardware watchdog to the safety microcontroller and an external window watchdog; a reset reason for every reset; and crash data such as minidumps and persistent log buffers, decoded with archived symbols."

10Benches, CANoe and network simulation

An ECU cannot be tested alone, because it expects a vehicle around it: dozens of other ECUs sending messages, a gateway, power that varies, cameras that see something. Test benches simulate as much of that vehicle as the test needs, and the Vector tool chain is the most common way to do it.

10.1Recap: what CANoe does

The camera ECU chapter introduces CANoe and a bench for the camera ECU step by step (Camera ECU 12.1 to 12.4). In short: CANoe loads the network description (DBC, ARXML or FIBEX), simulates the ECUs that are not on the bench (the restbus), sends and receives through Vector hardware interfaces, decodes signals and diagnostic messages, runs test modules, and records everything. Its nodes and tests are programmed in CAPL, a C-like event-driven language, or in .NET and Python.

10.3From the desk bench to the HIL rack

Benches come in three levels, and a mature project uses all three with the same test cases. The desk bench has the ECU, a lab power supply, a bus interface, CANoe with the restbus, one to four real cameras or a video injection box, a debugger and a DLT viewer: one developer, results in minutes. The hardware-in-the-loop (HIL) rack replaces the vehicle with a real-time simulator: it computes vehicle dynamics and the restbus, controls a programmable power supply to reproduce cranking and voltage drops, injects synthetic or recorded camera images into the ECU's camera inputs synchronised with the simulated scene, and injects faults (open or shorted wires, bus errors, missing messages) through relays and the simulation. HIL racks run automated regressions every night. The vehicle provides what no rack can: real optics, real EMC, real temperatures and real drivers, at the cost of weeks of driving.

For a camera ECU, the hardest part of a HIL is the camera injection. The ECU expects serialised video over coax links (GMSL or FPD-Link) with the exact timing, register behaviour and embedded data of the real camera module, so injection boxes emulate the serialiser and the image sensor's control interface while streaming frames rendered by a simulator or replayed from recordings. Small deviations (a missing embedded statistics line, a different frame start timing) make the ECU's software behave differently than with real cameras, so the injection itself must be validated against the real camera.

10.4What a bench test looks like

A typical integration test checks a chain of behaviour, not a single function. The CAPL sketch below (simplified; real tests use the project's diagnostic description so that services are called by name) disconnects the left camera through a relay channel of the HIL, waits for the maturation time, and checks the fault code and the degraded mode on the bus.

testcase TC_CamLeftLinkLoss_StoresDtcAndDegrades()

Tests like this run in CANoe, organised and parameterised in vTESTstudio, and are started by the CI system on the HIL farm every night (Edge AI 10.4 shows the same infrastructure for model regression). Their weak point is flakiness: a test that fails once in fifty runs because a timeout is too tight erodes trust in the whole suite. Keeping a flakiness statistic per test, and fixing or quarantining flaky tests explicitly with an owner, keeps the nightly results meaningful.

11Debugging real hardware

Some bugs only exist on the target: an exception in a driver, a hang before the operating system starts, a timing problem that disappears when a log line is added, a core that locks up once a day. Finding them needs tools that look into the chip without the software's cooperation.

11.1The toolbox and when to reach for which tool

The software tools of the Linux chapter (gdb with gdbserver, strace, perf, ftrace, sanitizers; Linux 10.1) need a running operating system and a cooperative process. Below that level, and on microcontrollers, four hardware tools take over. A debug probe on the JTAG or SWD port gives run control: halt the cores, read and write registers and memory, set hardware breakpoints, program flash, even when no software runs. Hardware trace records what the cores execute, in real time and without stopping them. Memory dumps capture the state after a crash for analysis on a desk. Bus analysers, oscilloscopes and logic analysers show what actually happens on the wires. The art is choosing: a hang before the kernel starts needs the debugger; a once-a-day deadline miss needs trace; a crash in the field needs a dump; a "the other ECU does not answer" needs a bus analyser before anything else.

11.2JTAG, SWD and run control

JTAG (IEEE 1149.1) was designed for testing solder joints with a scan chain; its four signals (TCK, TMS, TDI, TDO) became the standard access to on-chip debug logic. Arm's SWD does the same over two wires. On an Arm system-on-chip the probe talks to the debug access port of the CoreSight debug architecture, which reaches each core's debug registers and the system bus; on Infineon's TriCore microcontrollers the equivalent is the DAP interface with the on-chip debug and MCDS trace logic. Debuggers such as Lauterbach TRACE32, iSYSTEM winIDEA or Segger's J-Link tools load the symbols of the release build and show source, variables and call stacks for a core halted on target.

A first session on a new board is often a script like the one below (TRACE32 syntax, shortened): select the chip, attach, load the symbols of the image that is already in flash, and look at the state of a core that is stuck.

SYStem.CPU TC397XP            ; select the device
SYStem.Up                     ; connect through the DAP and halt
Data.LOAD.Elf app_4.12.0.elf /NoCODE    ; symbols only, the code is already in flash
Register.view                 ; program counter, stack pointer, trap registers
Frame.view /Locals /Caller    ; call stack with local variables
Var.View %Hex Dem_EventStatus ; any global by name
Break.Set Cam_LinkRelock /Program /Onchip    ; hardware breakpoint
Go
Pitfall

Halting a core in a running system changes the system. The other cores keep running, the watchdog expires and resets the chip, the safety microcontroller decides the SoC is dead, peripherals overflow. Debugging live systems needs watchdogs suspended in debug mode (most chips have a "suspend on halt" option), the safety supervision relaxed on the bench, and an awareness that a breakpoint is a fault injection.

11.3Trace: seeing time without stopping it

Many embedded bugs are timing bugs: a race between two cores, an interrupt that arrives in a narrow window, a task that overruns once in a million cycles. Stopping the core destroys the timing that causes them. Hardware trace records instead: the embedded trace macrocell (ETM) of each Arm core emits a compressed stream of branch decisions and timestamps from which the tools reconstruct every executed instruction; data trace adds memory accesses on some cores; system trace macrocells (STM, ITM) carry messages that software writes with a single store instruction, a logging channel with almost no overhead. The trace goes into an on-chip buffer (seconds of history at most), into a reserved region of DDR, or out through a high-speed trace port to the probe, which can stream minutes. The tools then show a timeline of functions per core, interrupt latencies and the exact sequence that led to a failure, and can compute code coverage of a test run on the real target as a by-product.

Trigger conditions make trace practical: record continuously into a ring buffer and stop shortly after a specific event (a write to an error variable, the entry to a trap handler), so that the buffer holds the history leading up to the failure. The once-a-day bug then becomes a matter of waiting for one day with the trigger armed.

11.4Post-mortem: memory dumps and crash context

When a microcontroller traps, the trap handler is the last code that runs with full knowledge of the failure. A good one records the trap class and identification (on TriCore, classes such as memory protection, instruction errors and bus errors; on Arm Cortex-R and -M, the fault status and address registers), the program counter and return address, the stack pointer and a slice of the stack, the running task and the reset counter, into a no-init RAM region; then it resets. After the reset the application copies the record to non-volatile memory and offers it through a DID. With the release's ELF file the program counter becomes a function and line, and the stack slice becomes a call chain. On the SoC, process core dumps and kernel dumps play the same role (Section 9.5); vendor-specific RAM-dump modes can also capture the whole DDR after a fatal error for analysis with the probe or a host tool, which is invaluable for firmware crashes in DSPs or the ISP.

11.5Bus analysers, scopes and logic analysers

Before suspecting software, check the wire. A CAN or CAN FD interface with CANalyzer or a cheaper logger shows whether frames are on the bus, with which timing, and which error frames occur (Networks 13.6 lists the symptoms). An oscilloscope on CAN-H and CAN-L shows reflections, wrong termination, slow edges and ground offsets that a protocol tool only sees as errors. For automotive Ethernet, a TAP (a passive or active tap inserted into the 100BASE-T1 or 1000BASE-T1 link) or a switch port mirror feeds Wireshark, which decodes SOME/IP, DoIP and gPTP. A logic analyser on SPI, I²C or the camera control channel shows the conversations with the deserialiser and the image sensor during bring-up, and the serialiser and deserialiser chips themselves expose link-quality registers (lock status, CRC error counters, eye-margin measurements) that the camera service should log, as the story in Section 14.4 shows.

11.6Debugging a locked production ECU

Production ECUs have their debug ports locked by fuses, secure boot enabled and diagnostic write services protected (Section 6.4). Returned field units therefore cannot simply be attached to a debugger. Two paths remain. Many chips support debug authentication: the device presents a challenge, the debugger answers with a certificate signed by the OEM or supplier for this specific device (identified by its unique ID), and the debug port opens until the next reset; the certificates are issued by a controlled process and logged. The other path is the data the ECU recorded itself: DTCs with snapshots, persistent logs, crash records, readable through authenticated diagnostics. For deeper analysis, suppliers keep "golden" development units with the same hardware revision and unlocked debug, flash them with the field software, and try to reproduce the failure under the conditions the field data describe.

11.7A worked example: the reset once a day

A test fleet reports that the camera ECU's microcontroller resets about once per day of driving. The DTC memory shows a "watchdog reset" event with a snapshot: supply voltage normal, vehicle moving, about two hours after start. The reset reason register confirms the external window watchdog. The crash record in no-init RAM is empty, so the trap handler never ran: the core was not trapped but late. On a bench unit with trace, a trigger is set on the watchdog's pre-warning interrupt, and the ring buffer is captured after 26 hours. It shows the 10 ms task taking 9.8 ms instead of its usual 2 ms: an NvM write job, queued once the event memory reached a threshold, ran in the same task and erased a data-flash sector synchronously. The fix moves the NvM main function to its own lower-priority task and makes the erase asynchronous; the regression test adds a long run with a forced full event memory. None of the four tools alone would have found it: the DTC snapshot narrowed it to time and conditions, the reset reason excluded a crash, the empty trap record pointed to a timing problem, and trace showed the cause.

Talk track

"Below the operating system I use a JTAG or SWD probe for run control and post-mortem state, hardware trace with a trigger for timing bugs that disappear when stopped, crash records from the trap handler decoded with the release's ELF file, and bus tools before blaming software. 12Performance, stability and endurance testing

Functional tests ask "does it work". Performance and endurance tests ask "does it keep working, under load, for years, in the cold, after the ten-thousandth start". The failures they find are slow: a leak, a counter that overflows after 49 days, a flash sector that wears out, a thermal limit reached in July.

12.1What to measure

For a camera ECU the key performance indicators are: start-up time to the first frame and to full function (Section 3.2); end-to-end latency per pipeline stage and its worst-case percentile; frame drops per hour; CPU, GPU and accelerator load per core with headroom (often required to stay below 70 to 80 % at the worst case, so that a future update has room); memory usage per process and its trend; storage writes per day (flash wear); temperatures of the SoC and the throttling events they cause (Edge AI 9.3); bus load on CAN and Ethernet; and the counts of resets, restarts, DTCs and degraded-mode entries. Each has a target in the requirements, and each is logged by the ECU itself in a compact form (counters, histograms, maxima in DIDs), so that it can be compared between the bench, the fleet and the field.

12.2The test types

Load and stress tests push the inputs to their limits: all cameras at maximum frame rate, the busiest bus traffic the OEM specifies, maximum object counts in the scene, plus a background load such as a running update installation, and check that latency and frame-drop targets still hold. Soak (endurance) tests run the ECU continuously for days (24 to 72 hours is common per release, weeks for the final validation) and watch for trends: memory growth, increasing latencies, rising counts of warnings, files that grow. Power cycling tests start and stop the ECU thousands of times, including power cuts at random moments during start-up, shutdown and flash writes, and check that every start succeeds and no persistent data are corrupted (Section 3.4). Voltage profile tests apply the cranking pulses, slow ramps and dips of the vehicle electrical system standards (ISO 16750-2 and OEM specifications; Networks 12 explains the electrical side) and check the defined behaviour in each. Climate tests run the ECU in a chamber from −40 °C to its maximum ambient temperature, including cold starts and thermal cycling. Fault injection breaks inputs and links on purpose (Functional safety 5.6).

Numbers

A 32-bit millisecond counter overflows after 232 ms ≈ 49.7 days; a 32-bit counter of 10 µs ticks after about 11.9 hours. An ECU that is always powered (a telematics unit, a gateway with long post-run times, or a test bench) hits these within its life, which is why soak tests sometimes start with counters preset close to their limits. Flash wear: if logging writes 1 GB per day to a 64 GB partition with 3000 program/erase cycles per cell, the partition lasts about 500 years in theory with perfect wear levelling; at 100 GB per day it lasts about five, so write budgets are a requirement, not a detail.

12.3Finding slow leaks: why soak tests are long

A memory leak of 20 KB per hour is invisible in a one-hour test and fatal after a year in an always-on ECU. Detecting it in a soak test is a statistics problem: the process's memory usage fluctuates by megabytes as caches fill and buffers are allocated, and the leak is a small slope under that noise. Fitting a straight line to the samples and asking whether the slope is significantly above zero works, but the uncertainty of the slope shrinks only with the test duration to the power 1.5 (for a fixed sampling rate): doubling the test duration makes the smallest detectable leak almost three times smaller.

With 2 MB of fluctuation and one sample per minute, an 8-hour test can only reliably detect leaks above about 145 KB/h; at 24 hours the limit falls to about 28 KB/h, at 72 hours to about 5 KB/h (numbers from experiments/check_interactive.js). This is why per-release soak tests run over days, and why reducing the noise helps as much as running longer: measure a metric that fluctuates less (the heap allocator's statistics instead of resident memory, or memory after a forced cache flush), or test the leak suspects in isolation with leak checkers such as Valgrind or AddressSanitizer on the host (Linux 10.7), which find the allocation site directly.

12.4From measurements to release gates

Measurements become useful when they gate releases. Each release candidate gets a performance report with the same KPIs measured on the same setup, compared with the previous release and with the targets: start-up time percentile, latency percentile per stage, CPU and GPU headroom, memory trend from the soak test, reset and restart counts, frame drops. A regression beyond a threshold blocks the release or needs a documented waiver. The comparison over releases matters as much as the absolute targets, because performance usually erodes in small steps of a few milliseconds per release, each acceptable alone, until a vehicle-level requirement fails a year later.

Talk track

"Beyond functional tests I run load tests at the specified worst case, multi-day soak tests that look for trends such as memory growth, power-cycle tests with cuts at random moments, voltage-profile and climate tests, and fault injection. Each release gets the same KPI report, compared with targets and with the last release, so that slow erosion is visible. Leak detection is statistics: the detectable slope shrinks with duration to the 1.5 power, so soak tests are long, and noise reduction helps as much as more hours."

13From development build to production release

A release is the result of a calendar, a set of roles and a sequence of gates as much as of code. This chapter describes how integration is organised around the technical work of the previous chapters, and how a release enters production in the plant.

13.1The integration calendar

Integration runs on two rhythms. At project level, the supplier delivers software to the OEM in a release train, typically every four to six weeks, aligned with the OEM's vehicle integration steps and with the sample phases: B-sample software for the first vehicle prototypes with complete hardware, C-sample software on production-intent hardware and tools, then release candidates for production approval, and finally the SOP software, followed by maintenance releases (RFI to SOP 12.1). Freezes cut each phase: after a feature freeze only fixes and agreed changes enter, after the code freeze only fixes for blocking defects, each with a change request.

Inside each cycle the integration team runs a weekly heartbeat: component teams deliver their drops by a fixed deadline, integration merges and builds, smoke tests run the same day, the HIL regression runs overnight, findings are triaged and assigned, fixes come in by the end of the week, and a release candidate is tagged and tested on benches and in vehicles. In the release week, the candidate leaves on a fixed day with its release note and known-issue list.

Why it matters

A predictable heartbeat is what makes a large project manageable: everyone knows when a change will be integrated and tested, late drops wait for the next cycle instead of delaying everyone, and the time from a bug report to a tested fix is bounded. Projects that "integrate when ready" spend more time on integration and are later.

13.2Roles, ownership and interface contracts in practice

The roles differ in name between companies but not in substance. Component owners deliver drops that meet the interface contracts and fix the findings assigned to them. The integration team owns the build manifest, the integrated configuration, the start-up and memory budgets, and the triage of integration findings; it has the authority to reject a drop that breaks the build or an interface. A system or software architect owns the interfaces themselves and decides contract changes. The release manager owns the calendar, the release content (which change requests are in), the gates and the communication with the OEM. A change control board with the customer decides what may enter after a freeze. The test and validation teams own the test levels and their reports, and the safety and security managers sign off their parts.

Interface contracts work in practice when they are checked automatically: generated stubs and contract tests at component boundaries, ARXML consistency checks in the build, a diagnostic description that is generated into code and into the tester's ODX from one source, and a compatibility matrix that the update system enforces. Every change to a contract goes through the architect and is announced to all consumers before the drop that implements it. The process side of this, with traceability from requirements to tests and work products for assessments, belongs to the ASPICE world (ASPICE 8.2 shows an integration sequence); this section is about what makes it work technically.

13.3Release candidates, gates and sign-off

A release candidate passes a sequence of gates, each with defined evidence: the build is reproducible from the archive and signed; smoke and full regression on the HIL farm pass, with every failure analysed; the performance report is within targets (Section 12.4); the flash container is tested with the plant's and the workshop's sequence, from the previous release and the oldest field release; the update package is tested with A/B rollback and failure injection; the diagnostic description, the DLT catalogue and the other descriptions are consistent with the binaries; the software bill of materials and licence check are done; open defects are classified and accepted as known issues; and the safety and security impacts of the changes are assessed, including whether the RXSWIN changes. Only then do the responsible managers sign the release, and it is archived with everything needed to rebuild and support it.

Pitfall

The release gate is not the place to discover that the plant cannot flash the release or that the tester's description lacks a new DID. These checks belong into the nightly integration (Section 2.4), so that the gate only confirms what has been true for weeks.

13.4In the plant: end of line

The ECU is manufactured at the supplier's plant and installed in the vehicle at the OEM's plant, and software touches both. At the ECU plant, after assembly and electrical tests, the end-of-line station flashes the release (or a base software that the vehicle plant completes), provisions the security (fuses, HSM keys, device certificate), writes the serial number and manufacturing data, and runs a functional test, for a camera ECU often with test images injected into the camera inputs. Every step is logged against the serial number, which is what makes later traceability possible: which software, which keys, which test results, which component batches went into this unit.

At the vehicle plant, the end-of-line diagnostic system talks to all ECUs of the finished vehicle through the diagnostic connector: it checks software versions against the vehicle's order, flashes updates that appeared since the ECU was manufactured, writes the VIN and the variant coding for this vehicle's equipment, injects or synchronises keys between ECUs (for example SecOC keys and immobiliser data), runs calibration routines (for cameras, a static target calibration in a station or a dynamic calibration on a short drive; Camera ECU 13.2), clears the fault memory, and checks that no unexpected DTCs remain. All of it must fit the line's cycle time of about a minute per station, which is where the flash time of Section 5.3 and the reliability of the sequence become hard requirements.

Talk track

"Integration runs on a release train of four to six weeks aligned with the sample phases and freezes, and inside it on a weekly heartbeat of drops, builds, nightly HIL regression and a release candidate. Roles are clear: component owners, an integration team that owns the manifest and budgets, an architect who owns contracts, a release manager who owns content and gates, a change board after freezes. A candidate passes gates with evidence, including plant and workshop flashing and update rollback, before sign-off. In the plants, end of line flashes, provisions keys, writes serial numbers, VIN and coding, calibrates cameras and logs everything per serial number."

14After-sales: the workshop years later

For the customer, the ECU's life is the ten or fifteen years after SOP. For the supplier, that is when the quality of everything in this chapter is tested by people who were not involved: technicians, warranty analysts, and engineers who inherit the code.

14.1The after-sales loop

A field problem travels a loop. The customer notices a symptom and visits a workshop. The technician connects the OEM's tester, which reads all ECUs' fault memories and versions and runs a guided fault finding procedure for the symptom (written by the OEM from the diagnostic description, often in OTX): measure here, read this DID, run this routine. The repair is a reflash to the latest software, a recalibration, a cable, or the replacement of the ECU, which then goes back to the supplier. The supplier analyses the returned part; if it finds nothing wrong, it is recorded as "no fault found", a large share of returns for electronic units. Patterns in returns, warranty claims and fleet DTC statistics trigger a root-cause analysis (often in the 8D format), a fix, a release, and delivery by an over-the-air campaign or a workshop action. Field monitoring then shows whether the fix worked.

14.2In the workshop

The workshop sees the ECU only through its diagnostic interface and the OEM's tester. What the technician can do therefore depends on what the release supports and what the descriptions say. Reading versions shows whether the car runs the latest software; if not, the tester offers the update, downloaded from the OEM's backend for this VIN. Replacing an ECU means programming the new unit (spare parts are stored with a base software, and the tester flashes the version that matches the car), writing the vehicle's coding from the OEM's backend (online coding, using the record of the vehicle's equipment), pairing keys with the rest of the vehicle through an online authorisation, and calibrating: a camera ECU or a camera that was replaced, or a windscreen that was changed, requires a camera calibration with a target or a calibration drive (Calibration and fusion 3.5 explains online calibration). A workshop procedure that needs an engineer to interpret raw bytes is a failed design; every routine the workshop needs must be in the description with clear results.

Pitfall

Clearing DTCs is the workshop's reflex, and it erases the evidence. Fault codes that matter for analysis should have snapshots and extended data that tell the story on their own, and ECUs often keep a separate, non-clearable history (a "permanent" or development memory, or counters in DIDs) so that a returned part still carries its history after a workshop cleared the fault memory.

14.3Supporting a release for fifteen years

Spare parts and service must be available long after production ends; ten to fifteen years after the end of production is a common commitment, and regulations require access to repair information for independent workshops too. For software this means: the ability to build and sign the release again (archived sources, containers, tool licences and keys, Section 4.4); the ability to flash it with tools that still exist (flash containers in standard formats, testers maintained by the OEM); the symbols and descriptions to analyse field data; and the ability to fix security vulnerabilities for the period agreed with the OEM, which R155 and R156 turned from goodwill into an obligation (Functional safety 9.7). It also means the people: knowledge of a release must survive the team, which is a strong argument for the written contracts, descriptions and release evidence of this chapter.

14.4One story end to end: the black camera on cold mornings

Three winters after SOP, the OEM's warranty statistics show a cluster of complaints: "left side of the surround view black, sometimes, on cold mornings". Workshops find fault code B1A1F-29 (left camera video signal invalid) stored as confirmed but not present, with an occurrence counter between 1 and 5. Some technicians replace the camera; the returned cameras show no fault. The fault code's snapshot, designed years earlier, shows ambient temperatures below −15 °C and times between 10 and 20 seconds after start in every case.

The OEM requests logs from affected vehicles through a diagnostic upload of the persistent DLT buffer. They look like the listing in Section 9.2: at power-on the board temperature is −24 °C, all four links lock and the first frame appears at 1.54 s; 13 seconds later the deserialiser reports lost lock on port 1 with 37 CRC errors, three relock attempts fail, the fault matures, the surround view masks the left camera, and the camera service gives up until the next operation cycle. The logged CRC errors point to the link, not the camera. In a climate chamber with a golden unit and the vehicle's cable set, the engineers reproduce it: as the cable and connector warm up from −25 °C under the heat of the running ECU, the link's eye margin briefly collapses because the deserialiser's adaptive equaliser was tuned at start-up for the cold cable and is not re-adapted while locked. The fix has two parts: the camera service re-runs the equaliser adaptation when the CRC error counter rises, and the relock strategy keeps trying with back-off instead of giving up after three attempts.

Release 4.15 with the fix goes through the same gates as every release, including the R156 impact assessment (no type-approved function affected, RXSWIN unchanged), and is delivered over the air. The A/B update rolls back automatically on a few hundred vehicles where the update was activated while a camera was disconnected in a workshop, and the health check failed; the update criteria are refined. Within a month the fleet statistics for B1A1F-29 drop by 95 %. Every step of the story was possible because of decisions made years earlier at integration: the snapshot content, the logged CRC counters, the persistent log buffer and its upload path, the archived build and symbols, the A/B update with health check, and the version identification that let the backend select exactly the right vehicles.

Talk track

"After SOP the loop is: workshop diagnosis with the OEM tester and guided fault finding, repair or replacement with online coding and calibration, return analysis where no-fault-found is common, root cause, fix, OTA or workshop delivery, and fleet monitoring. Supporting a release for fifteen years needs reproducible builds, archived symbols and descriptions, keys, tools and security maintenance. Whether a field issue can be solved is decided years earlier by what the release records: DTC snapshots, link counters, persistent logs."

QSelf-check questions

Core questions with short model answers; the chapter sections hold the depth. The second group checks understanding with "why" and "what if" questions rather than definitions.

Q.1Core questions

What does a software integrator do on an ECU project?Basic

Combines deliveries from function teams, the platform team, silicon, OS and stack vendors and open source into one consistent, reproducible ECU build; owns the build manifest, the integrated configuration, start-up and resource budgets, and the triage of integration failures; makes interfaces explicit with versioned contracts and a compatibility matrix; and runs the integration heartbeat of drops, builds, smoke tests and nightly regression so that every build is releasable in principle.

Walk me through flashing an ECU over UDS.Basic

Pre-programming: extended session, check programming preconditions, ControlDTCSetting off and CommunicationControl off for all ECUs. Programming session (the application hands over to the bootloader), SecurityAccess seed and key or Authentication, write the fingerprint, erase with the 0xFF00 routine while the ECU sends response pending, RequestDownload, TransferData blocks with a sequence counter, RequestTransferExit, check memory (checksum or signature), check programming dependencies, ECU reset. Post-programming: communication and DTC setting on, clear DTCs, default session, read versions. The application is marked valid only after verification.

Why does the ECU need a separate flash bootloader?Basic

Code cannot safely erase and rewrite the flash it executes from, and an interrupted update must not leave the ECU without software that can talk to a tester. The bootloader runs after every reset, starts the application only if its valid marker and checksum or signature are correct, and otherwise stays active and accepts a new flash. It is not updated in normal field updates.

What is the response code 0x78 and when do you see it?Basic

Negative response code "request correctly received, response pending". The ECU sends 7F xx 78 when a service will take longer than P2 (about 50 ms), for example an erase or a long routine, and repeats it before P2* (about 5 s) expires until it sends the real response. The tester then waits with the P2* timeout instead of P2.

Explain DoIP.Basic

Diagnostics over IP, ISO 13400-2, port 13400. The tester finds the vehicle with a UDP vehicle identification request and gets the VIN and the gateway's logical address, opens a TCP connection and sends a routing activation with its own logical address, and then sends diagnostic messages with source and target logical addresses and UDS payload. The DoIP entity acknowledges each message and forwards it to Ethernet ECUs or translates it to ISO-TP for CAN ECUs. It makes flashing large images practical.

What are Dcm and Dem?Intermediate

Classic AUTOSAR basic-software modules. Dcm processes diagnostic requests: its session layer handles sessions, timing and response pending, its dispatcher checks that a service is allowed in the session and security level, its processing layer implements services and calls software components for DIDs and routines. Dem receives event reports from monitors, debounces them, keeps DTC status bytes, snapshots, extended data, operation cycles and aging, stores through NvM and informs FiM. Both are generated from the diagnostic description.

How does secure boot work?Intermediate

A chain of trust: immutable boot ROM verifies the first bootloader's signature with a public key whose hash is burned into fuses; each stage verifies the next with keys it carries in its signed image, through hypervisor and kernel; the kernel carries the root hash of a dm-verity file system checked block by block; applications and models are signed packages. On microcontrollers an HSM verifies the flash. Anti-rollback counters in fuses or RPMB reject older vulnerable images.

Describe an A/B update with rollback.Intermediate

The new image is written into the inactive slot while the active slot runs, then verified. The bootloader is told to boot the new slot on trial with a cleared counter. At each trial boot it increments the counter; above the limit it boots the old slot. After booting, a health check confirms that the function works; then the client commits by clearing the trial flag. If the health check fails, the client switches back and reboots. Persistent data must not be converted irreversibly before commit.

What does UN R156 require?Intermediate

A certified software update management system at the OEM: assessing each update's impact on type-approved and safety-relevant functions, RXSWIN identifiers for regulation-relevant software, records of software versions per vehicle, protection of updates against manipulation, safe conditions and driver information during installation, and handling of failed updates. Suppliers deliver their part of the evidence and the update mechanisms.

What is DLT and why is it used instead of plain text logs?Basic

The AUTOSAR Log and Trace protocol. Every message carries ECU, application and context identifiers, a counter, a timestamp and a level, so logs from many ECUs can be merged and filtered; levels can be changed at run time from a tester; and non-verbose mode sends only a message identifier and raw arguments, with the text in a description file, which saves bandwidth and CPU. Classic, Adaptive and Linux/QNX systems all produce it, so one viewer reads all.

How do you debug a crash that only happens on the target?Intermediate

First the recorded data: reset reason, DTC snapshot, crash record from the trap handler or core dump, decoded with the release's symbols. Then reproduce on a bench unit with a JTAG/SWD probe for run control and, for timing problems, hardware trace with a trigger on the failure so the ring buffer holds the history. Check the buses with an analyser before blaming software. Keep in mind that halting a core changes the system (watchdogs, other cores, supervision).

What is the difference between CANalyzer, CANoe and vTESTstudio?Basic

CANalyzer observes and analyses buses and can send single messages. CANoe adds simulation of the rest of the network, test execution and diagnostics with the ECU description, so it is the bench and HIL tool. vTESTstudio is an authoring environment for structured, parameterised test cases that run in CANoe. CANape is for measurement and calibration over XCP.

What is a HIL test and what does it add over a bench?Basic

Hardware-in-the-loop: the real ECU connected to a real-time simulator that computes the vehicle and the restbus, drives a programmable power supply, injects camera images synchronised to the simulated scene, and injects electrical and bus faults. It makes tests automated, repeatable and runnable every night, including faults that are dangerous or impossible to create in a vehicle.

What happens at end of line in the vehicle plant?Basic

The plant's diagnostic system checks software versions against the vehicle order and flashes updates, writes the VIN and the variant coding for the equipment, provisions or synchronises keys between ECUs, runs calibrations such as camera calibration with targets or a short drive, runs functional checks, clears the fault memory and checks that no unexpected DTCs remain, all within the station's cycle time and logged per vehicle.

How do you make sure a release can be supported for fifteen years?Advanced

Archive sources, the build container and toolchain, generator versions, tool licences and signing access so the build can be reproduced; keep symbols by build ID to decode field crashes; release the descriptions (ODX, DLT catalogue, A2L) with the binaries; use standard flash container formats; plan security maintenance for the agreed period; and keep the knowledge in written contracts and release evidence rather than in people's heads. Rebuilding an old release periodically proves it works.

What does a good DTC design include?Intermediate

A monitor with a clear fault condition and debouncing tuned between nuisance faults and reaction time, the right operation cycle and aging, a failure type that distinguishes causes, snapshot data that capture the conditions (voltage, temperature, time since start, mode) and extended data with occurrence and aging counters, an entry in the workshop's guided fault finding, and a decision on function inhibition. It is designed for the technician and the warranty analyst, not only for the developer.

Q.2Why and what if

Why is CommunicationControl switched off for all ECUs before flashing one?Why

While the target ECU is in the bootloader it stops sending its normal messages, so every other ECU would detect timeouts and store communication DTCs. Silencing normal communication on the bus also frees bandwidth for the flash transfer and removes load from the target. ControlDTCSetting off covers the remaining fault storage; both are switched back on, and DTCs cleared, after programming.

What if the power fails in the middle of a TransferData sequence?What if

The valid marker of the application was cleared before the erase and is written only after the check routines, so after power returns the bootloader finds no valid application and stays active. The ECU still answers on its diagnostic address with the programming services, and the tester repeats the flash from the start. Nothing is bricked, as long as the bootloader itself was not being updated.

Why does STmin = 1 ms make a CAN flash four times slower?Why

A classic CAN frame at 500 kbit/s takes about 0.23 ms and carries 7 bytes of a consecutive frame. With STmin 0 the frames follow back to back (about 29 KB/s); with STmin 1 ms the tester must wait 1 ms between frames, so throughput drops to 7 KB/s. The ECU requests STmin in its flow control frames, usually because its bootloader cannot process frames faster.

Over DoIP, why can small blocks make flashing slower than over CAN FD?Why

Each TransferData block waits for the previous positive response, so every block costs a round trip through the tester, the gateway and the ECU, about a millisecond, plus TCP effects such as Nagle's algorithm if not disabled. A 4 KB block moves in under half a millisecond at 100 Mbit/s, so round trips dominate. Blocks of tens of kilobytes or more amortise them.

Why does the A/B scheme use a boot counter instead of switching back after the first failed boot?Why

A boot can be interrupted for reasons unrelated to the new software, such as the driver switching off the ignition. A limit of a few attempts tolerates such interruptions while still catching software that never boots. The bootloader increments the counter before each trial boot, and only a positive commit clears it, so a hang anywhere before the commit counts as a failure.

What if version 4.12 converts the calibration format on its first start and is then rolled back?What if

Version 4.11 finds data it cannot read and either fails or falls back to defaults, so the rollback restores the code but not the function. Data migrations must therefore be reversible or deferred until commit: keep the old format until the update is committed, or write the new format alongside the old one, and delete the old one only with a later update.

Secure boot is enabled. Why is a locked JTAG port still needed?Why

Secure boot checks code at start-up only. A debugger attached to a running system can halt cores, read keys and memory, and modify code or data in RAM without touching flash, bypassing every signature. Debug interfaces are therefore disabled by fuses in production or opened only with device-specific, signed debug certificates.

Why should the anti-rollback minimum version not be raised with every release?Why

Raising it makes older versions permanently unbootable, which also removes the ability to roll back to the previous release if the new one fails. It should be raised only on commit and only when a release fixes a security vulnerability that makes older versions unacceptable; that is a security decision, not an automatic step of every update.

The rear-view application now waits for the logging daemon. Why does the first frame get 400 ms later, although no component became slower?Why

Start-up time is the critical path of the dependency graph. The logging daemon starts after the file system and takes about 650 ms, so it finishes later than the camera link that previously determined the application's start. The new dependency moves the critical path through storage and logging. Removing such accidental dependencies, or starting them asynchronously, recovers the time.

A DTC has status 0x28. Should the workshop replace the part?What if

Probably not yet. 0x28 means confirmed and failed since last clear, but testFailed and the this-cycle bits are clear: the fault occurred and matured in the past and is not present now. Check the snapshot (conditions) and the occurrence counter: a single occurrence during a voltage dip suggests a transient; repeated occurrences under the same conditions suggest a real but intermittent fault, for which the guided fault finding should test the link or the component specifically.

Why does a soak test need days to find a small memory leak?Why

The leak is a small slope under fluctuations of megabytes. The standard error of a fitted slope falls with test duration to the power 1.5 at a fixed sampling rate, so with 2 MB of noise an 8-hour test only detects leaks above about 145 KB/h, while 72 hours reach about 5 KB/h. Reducing the noise of the metric, or testing suspects with leak checkers on the host, helps as much as running longer.

What if the health manager itself hangs?What if

It stops serving the SoC's hardware watchdog, which resets the SoC. If the hang also affects the watchdog or the whole SoC, the safety microcontroller sees the heartbeat stop, puts the function into a safe state on the bus and power-cycles the SoC. The microcontroller itself is supervised by an external window watchdog. Each layer covers the failure of the one above.

Why can a log line make a bug disappear, and what do you do then?Why

Logging takes time and changes scheduling, cache state and memory layout, so a race or a narrow timing window may no longer occur. Use observation with less impact: hardware trace or system trace messages (a single store), trace markers in ftrace, counters updated in memory and read later, or a trigger-based ring buffer that is only written out after the failure.

A new release passes all HIL tests but the plant cannot flash it. What went wrong in the process?What if

The flash container and descriptions were not tested with the plant's sequence and fixture as part of the integration: perhaps a new logical block or DID is missing from the ODX, the block length or timing changed, or the container was signed with a development key. Plant and workshop flashing from the oldest supported version should be part of the nightly or at least every release candidate's checks, not of the release gate.

Why should the binary that is tested be the binary that is shipped?Why

Different compiler options, test hooks or debug features change timing, memory layout and code paths, so test results of one build do not prove the other. Integration and release builds should differ only in the signing key and features switched by a signed configuration, and the version and its signature should identify the exact tested image.

Why are microcontroller bootloaders almost never updated in the field?Why

The bootloader is the recovery path for every failed application flash. If its own update is interrupted, nothing remains that can program the ECU, and the unit must be replaced. When a bootloader must change, a dedicated updater is flashed as an application, which copies and verifies the new bootloader in a guarded procedure, accepting the residual risk only for that rare case.
