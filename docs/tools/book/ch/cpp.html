0Overview

C++ has a reputation for being a language you never finish learning. That is true of the rule book, but not of the ideas. Underneath the thousand-page standard sit perhaps a dozen mechanisms — objects with lifetimes, a precise notion of who owns what, a compiler that is allowed to assume you never break the rules, templates that generate code, and a handful of runtime structures such as vtables, control blocks and coroutine frames. Once you can picture those mechanisms in memory, almost every feature and every "gotcha" becomes a consequence rather than a fact to memorise.

That is the approach here. Each section starts with why the thing exists — the problem it solved, often visible in a short before/after refactoring — then shows how it works with a diagram of what the compiler and the machine actually do, then the practical details, pitfalls and a short talk track you can reuse in a design review or a customer meeting. The running examples come from camera software: a Frame that owns a pixel buffer, an Image<T> view, and small sensor messages flowing between pipeline stages.

1The map: what C and C++ really are

Why two fifty-year-old languages still run cameras, brakes and inference engines; the abstract machine the standard describes; the zero-overhead deal C++ makes with you; and the five ideas that carry the rest of this guide.

Open the software of almost any camera ECU and you will find the same layering. At the bottom, C: boot code, the board support package, drivers that program the CSI-2 receiver and the ISP, and much of the safety microcontroller. Above it, C++: the frame pipeline, the computer-vision and neural-network runtime glue, AUTOSAR Adaptive services, the rendering of the surround view. Python and other languages appear in tools, training and tests — rarely in the shipping binary. The reason is not tradition. It is that C and C++ give you two things at once that few other languages offer together: direct control over memory and the machine, and no mandatory runtime — no garbage collector, no interpreter, no hidden thread.

Why it exists

An ECU has a fixed amount of RAM, a deadline per camera frame (33 ms at 30 fps, often a fraction of that for one stage), and safety arguments that must be made about every allocation and every possible failure. A language whose costs are visible in the source code — and whose runtime is only what you link in — lets you make those arguments. C gives you that with very little abstraction; C++ adds abstraction that, when used well, compiles away.

The abstract machine

The single most useful idea for understanding C++ is that the standard does not describe your CPU. It describes an abstract machine: objects that occupy storage, have a type and a lifetime, and are read and written by expressions evaluated in a defined order. Your program's observable behaviour — volatile accesses, I/O, data written to files — must be what the abstract machine would produce. Everything else is negotiable. The compiler may keep a variable only in a register, delete a loop whose result nobody reads, merge two allocations, reorder independent stores or vectorise a loop, as long as the observable behaviour is unchanged. This is the as-if rule, and it is why optimised C++ is fast.

The deal has a price. The abstract machine only has defined behaviour for programs that follow its rules. If a program reads past the end of an array, overflows a signed integer, or uses an object after its lifetime ended, the standard says the behaviour is undefined — not "crashes", not "returns garbage", but "anything at all", including a program that seems to work in debug and fails in release. The optimiser is allowed to assume undefined behaviour never happens and to reason backwards from that assumption. Chapter 3 shows how that produces some of the most surprising bugs in the industry.

The zero-overhead principle

Bjarne Stroustrup's design rule for C++ has two halves: what you don't use, you don't pay for, and what you do use, you couldn't hand-code any better. A std::array<float, 9> is exactly nine floats; a std::unique_ptr is exactly one pointer; a range-for loop over a vector compiles to the same instructions as a pointer loop; a template sort can inline the comparison that C's qsort must call through a function pointer. Not every feature meets the principle — exceptions and RTTI carry space costs even when unused, std::shared_ptr pays for atomic reference counting whether or not you share across threads, and std::function may allocate — and those are precisely the features embedded coding rules restrict (Chapter 14).

C and C++: one family, two philosophies

C is a portable assembler with a type system: what you write is close to what executes, there are no constructors, destructors or hidden calls, and resources are managed by explicit calls you must not forget. C++ began as "C with classes" and kept C's machine model, but its central idea is different: let the type system manage resources and invariants for you. A Frame class that frees its buffer in its destructor cannot leak on an early return; a std::span<const uint8_t> carries its length so a function cannot forget it; a template generates a specialised kernel for each pixel type without a switch. Chapter 13 compares the two in detail and shows how they interoperate on the same ECU.

2Objects, values and references

What an "object" means to the compiler, why every expression has a value category, how references differ from pointers in memory, and what const really promises.

Why it exists

C++ needs to answer two questions about every expression, at compile time: what object is this, and may I steal its contents? The first decides aliasing, lifetime and layout; the second decides whether assigning a 12 MB frame costs a memcpy or three pointer writes. The vocabulary of objects and value categories exists to answer those questions precisely.

What an object is

In everyday speech an object is "an instance of a class". The standard means something more basic: an object is a region of storage with a type, a size, an alignment, a lifetime and a value. An int is an object; so is each element of a float[9] and the whole array; so is a Frame and each of its members. Storage and object are not the same thing — the bytes of a buffer can exist before any object lives in them and after the object has died. That distinction is what makes placement new, memory pools and unions possible, and it is the root of the lifetime rules in Chapter 3.

The type tells the compiler how to interpret the bytes and which operations are legal. It also lets the optimiser reason about aliasing: if a function receives a float* and an int*, the compiler may assume they do not point to the same storage, because an int object and a float object cannot occupy the same bytes at the same time. This is the "strict aliasing" rule, and it is one reason C++ can keep values in registers across stores.

struct SensorMsg {                 // a small, trivially copyable message

Initialisation: the first place C++ differs from C

A local int x; has an indeterminate value; reading it before writing is undefined behaviour in C++23 (C++26 relabels it "erroneous behaviour": still a bug, but no longer licence for the optimiser to do anything). Class types are always initialised by a constructor. The brace form T x{...} is the uniform choice in modern code because it works for aggregates, constructors and containers, and it forbids narrowing: int w{3.7}; does not compile, while int w = 3.7; silently truncates. T x{} value-initialises — zero for scalars and aggregates — which is the cheapest way to avoid a whole class of uninitialised-read bugs.

Pitfall

Braces prefer std::initializer_list constructors. std::vector<int> v{640, 480}; is a vector of two elements, while std::vector<int> v(640, 480); is 640 copies of 480. Image code with "width, height" constructors hits this regularly.

Value categories: may I steal from it?

Every expression has a type and a value category. Since C++11 there are three primary categories, and the names are less mysterious than they look once you ask two questions: does the expression have an identity (refers to an object you could take the address of), and can it be moved from?

  • lvalue — has identity, not movable by default. A named variable f, *p, v[i], a function returning T&. Historically "can appear on the left of =".
  • prvalue ("pure" rvalue) — no identity yet; it is a recipe for a value. 42, a + b, Frame(640, 480, 640), a function returning T by value. Since C++17 a prvalue is not even an object until it is materialised into one — which is why returning a prvalue never copies.
  • xvalue ("expiring") — has identity and is movable. The result of std::move(f), of a function returning T&&, or of a member access on an rvalue.

The two mixed categories group them: a glvalue (lvalue or xvalue) has identity; an rvalue (prvalue or xvalue) may be moved from. Overload resolution uses exactly this: an rvalue prefers a T&& parameter, an lvalue binds only to T& or const T&. That single rule is the switch that turns copies into moves (Chapter 6).

Interesting detail

std::move moves nothing. It is a static_cast<T&&> that turns an lvalue into an xvalue, so that overload resolution picks the move constructor. The actual stealing happens in that constructor. A std::move on a const object yields const T&&, which binds to the copy constructor — the code compiles and silently copies.

References versus pointers

A pointer is an object in its own right: eight bytes on a 64-bit target holding an address, which can be null, re-pointed, incremented and compared. A reference is an alias — another name for an existing object. It must be bound at initialisation, cannot be re-seated and cannot be null in a valid program. The standard deliberately does not say whether a reference occupies storage. In practice a reference that is a local alias usually vanishes entirely, while a reference parameter or member is implemented exactly like a pointer: the caller passes an address. So const Frame& and const Frame* cost the same; what differs is the contract the type expresses.

const correctness

const is a promise checked by the compiler: through this name, the object will not be modified. Read pointer declarations right to left: const uint8_t* p is a pointer to const bytes (the pixels are read-only, the pointer can move); uint8_t* const p is a const pointer to mutable bytes; const uint8_t* const p is both. A const member function is a function whose hidden this parameter has type const Frame*, which is why it can only call other const members and why the data() overload pair in the running example exists: a const frame hands out read-only pixels.

Two subtleties come up in reviews. First, const is shallow: in a const Frame, the member data_ becomes uint8_t* const — the pointer is frozen but the pixels it points to are not. Writing the const and non-const accessors by hand (or using std::experimental::propagate_const) is what makes constness "deep". Second, const is about the interface, not the bits: a cache filled lazily inside a const getter is marked mutable (and then must be thread-safe, because callers assume const members can run concurrently).

Pitfall

Returning const Frame by value (an old C++03 habit) disables moves from the result, because const Frame&& cannot bind to the move constructor. Return plain Frame.

Interesting detail

const rarely makes code faster. The compiler cannot assume a const T& parameter does not change during the call — another alias may modify it. What does help the optimiser is a local value copy or a constexpr constant. const is for correctness and readable intent; constexpr is for compile-time evaluation (Chapter 10).

Talk track

"Every expression is either something with an identity — an lvalue — or a temporary result that nobody else can see, an rvalue. The compiler uses that distinction to decide when it may steal an object's resources instead of copying them. std::move is just a cast that says 'treat this as expiring'."

3Object lifetime and undefined behaviour

When an object starts and stops existing, how temporaries die, the dangling-reference patterns that reach production, and how the optimiser turns undefined behaviour into deleted safety checks.

Why it exists

C++ gives you deterministic destruction — the exact line where a buffer is freed or a lock released — instead of a garbage collector that runs "sometime". Determinism is what makes RAII and real-time code possible. The price is that you, not a runtime, must make sure nobody uses an object after that line. Undefined behaviour is the standard's way of saying "the compiler will not check this for you, and will assume you got it right".

The lifetime of an object

An object's life has five steps. Storage is obtained (stack frame, heap, static area, or a buffer you provide). The constructor runs: first base classes, then members in declaration order — not in the order of the initialiser list, which is why compilers warn when the two differ. When the constructor body finishes, the lifetime begins. At the end, the destructor body runs, then members are destroyed in reverse declaration order, then bases. Finally the storage is released. Using the object outside the window between "constructor finished" and "destructor started" is undefined; so is reading a member before it has been constructed — the classic bug of a member initialiser that uses a member declared further down.

Temporaries and lifetime extension

A temporary — the materialised result of a prvalue such as make_frame() or a + b — is destroyed at the end of the full-expression, roughly "at the semicolon". There is one rescue: binding a temporary directly to a const T& or T&& local extends its lifetime to that of the reference. The extension does not pass through function calls, which produces the dangling patterns below. All of them compile, most pass tests, and they fail under a different optimisation level or allocator.

How the optimiser uses undefined behaviour

Undefined behaviour is not a bug in the standard; it is a contract that lets compilers generate fast code for valid programs. Because signed overflow is undefined, a loop for (int i = 0; i < n; ++i) can be assumed never to wrap, so the compiler can widen i to a 64-bit pointer offset and vectorise. Because dereferencing null is undefined, after *p the compiler may assume p != nullptr. The trouble starts when a program does contain UB: the optimiser's valid reasoning then removes code the author thought was protective.

Strict aliasing, the camera-byte example

Sensor metadata often arrives as raw bytes: an embedded-data line or a network payload. Reading a 32-bit field by casting the byte pointer is undefined twice over — the bytes may be misaligned, and there is no uint32_t object at that address. 4The memory of a program

Where objects live — stack, heap, static and thread storage — how virtual memory looks from C++, why alignment and padding change the size of your structs, and how allocators, pools and PMR make allocation deterministic.

Why it exists

The storage an object lives in decides what it costs to create, how long it lives, whether two threads can see it, and whether creating it can fail or take an unbounded amount of time. In a camera pipeline the difference between "this frame header lives on the stack" and "this frame header is allocated with new on every frame" is the difference between a deterministic 30 fps loop and occasional 2 ms stalls in the allocator.

Four storage durations, one address space

C++ names four storage durations. Automatic objects — locals and parameters — live in the current function's stack frame and die at the closing brace. Static objects — globals, namespace-scope variables, static locals and class statics — exist for the whole program. Thread storage (thread_local) gives each thread its own copy. Dynamic objects are created by new (or an allocator) and live until someone deletes them. On a Linux or QNX process these map onto regions of one virtual address space.

The stack is the cheapest storage there is: allocating a frame is one subtraction from the stack pointer, and the memory is almost always hot in L1 cache. It is also small and fixed — 8 MiB for the main thread on a typical Linux system, whatever pthread_attr_setstacksize gave a worker thread, and often only a few KiB for an RTOS task on the safety MCU. A 1920×1080 RGB frame (6.2 MB) on the stack is a crash waiting for a slightly bigger resolution; large or variable-sized data belongs in a buffer owned by an object that lives on the stack.

Static storage is laid out by the linker: zero-initialised objects in .bss (which costs no space in the binary), initialised ones in .data, and constants — string literals, constexpr lookup tables such as a gamma curve — in read-only .rodata, which on an MCU can stay in flash. Dynamic initialisation of globals across translation units happens in an unspecified order (the "static initialisation order fiasco"); a function-local static is initialised on first use and, since C++11, that initialisation is thread-safe — the compiler inserts a guard variable and a one-time lock.

Virtual memory as C++ sees it

Every pointer in a user-space process is a virtual address; the MMU translates it page by page (usually 4 KiB) to physical memory. Three consequences matter to C++ programmers. First, new of a large block often just reserves address space — physical pages are attached on first touch through a page fault, so the first pass over a fresh 12 MB buffer is much slower than the second, which matters for the first frame after start-up. Real-time code therefore pre-faults ("touches") buffers and locks them with mlockall during initialisation. Second, a hardware block such as the ISP or GPU needs physically contiguous or IOMMU-mapped memory, which is why camera buffers come from dma-buf / ION / PMEM allocators rather than new. Third, a null or wild pointer usually lands on an unmapped page and faults — the friendly case; a stale pointer into a still-mapped heap page silently corrupts data.

Alignment and padding

Every type has an alignment — alignof(T) — and objects of that type must start at an address that is a multiple of it: 1 for uint8_t, 4 for float, 8 for uint64_t and pointers on a 64-bit target. The hardware loads naturally aligned values in one access; some Arm cores fault on a misaligned load, others split it into two. To keep every member aligned, the compiler inserts padding between members and at the end of a struct, so that arrays of the struct stay aligned too. The size of a struct is therefore not the sum of its members, and member order changes it.

static_assert(sizeof(FrameHeader) == 24);   // document layout assumptions
static_assert(alignof(FrameHeader) == 8);
static_assert(std::is_trivially_copyable_v<FrameHeader>);   // safe to memcpy / DMA

struct alignas(64) PerCameraStats { std::uint64_t frames, drops; };  // one cache line each
alignas(32) float kernel[8];                  // AVX/NEON-friendly start address
Pitfall

#pragma pack(1) or __attribute__((packed)) removes padding so a struct matches a wire format, but every access to a misaligned member becomes slower or, through a pointer taken to that member, undefined. Bit-fields are worse for wire formats: their order within a byte and endianness are implementation-defined. For network or embedded-data headers, parse bytes explicitly with memcpy and byte-order conversion (Chapter 3), and keep in-memory structs naturally aligned.

What new actually does

A new Frame(640, 480, 640) expression does two separate things: it calls operator new(sizeof(Frame)) to obtain raw storage, then runs the constructor in it. delete runs the destructor and then operator delete. The default operator new calls malloc, and malloc is a general-purpose allocator: glibc keeps per-thread arenas with size-class bins, serves small requests from those, and hands requests above a threshold (128 KiB by default, adaptive) straight to mmap. That design is fast on average but not deterministic: a call can take a lock, walk free lists, split or coalesce blocks, or ask the kernel for more pages. Over hours of operation, mixed allocation sizes also fragment the heap, so a large request can fail even though enough total memory is free.

Custom allocators and PMR

The classic standard-library allocator model makes the allocator a template parameter: std::vector<float, PoolAlloc<float>>. It is zero-overhead but viral — the allocator becomes part of the type, so a function taking std::vector<float>& cannot accept the pooled vector. C++17 added polymorphic memory resources (<memory_resource>): containers in namespace std::pmr all use one allocator type, std::pmr::polymorphic_allocator, which holds a pointer to a std::pmr::memory_resource and calls it through a virtual function. The type stays the same; the strategy is chosen at run time.

A per-frame arena: allocate freely while processing a frame, free everything at once
alignas(std::max_align_t) static std::byte arena_buf[256 * 1024];

void process_frame(const Frame& f) {
    std::pmr::monotonic_buffer_resource arena{arena_buf, sizeof arena_buf,
                                              std::pmr::null_memory_resource()};
    std::pmr::vector<Detection> dets{&arena};     // no malloc on this path
    std::pmr::vector<Keypoint>  kps{&arena};
    detect(f, dets, kps);
}   // arena destroyed: all memory "freed" by resetting one pointer

The standard resources cover the common strategies: monotonic_buffer_resource is a bump-pointer arena that never frees individually; unsynchronized_pool_resource and synchronized_pool_resource keep pools of fixed-size blocks; new_delete_resource() forwards to the heap; and null_memory_resource() throws on any request. Using the null resource as the upstream turns "we never fall back to the heap" from a hope into a checked property.

Interesting detail

Placement new — new (ptr) Frame(...) — constructs an object in storage you already have and allocates nothing. It is how std::vector, std::optional and every pool are implemented. The matching destruction is an explicit destructor call, p->~Frame() (or std::destroy_at(p)), without freeing the storage.

Numbers worth knowing
  • A heap allocation with glibc: tens of nanoseconds when it hits a thread cache, microseconds or worse when it takes locks or calls the kernel.
  • Stack allocation: one instruction. Page fault on first touch: roughly 0.1–1 µs per 4 KiB page, i.e. ~3000 faults for a 12 MB buffer.
  • Default thread stack on Linux: 8 MiB (from ulimit -s); RTOS task stacks: often 1–16 KiB.

5RAII and ownership

The single most important C++ idiom: tie every resource to an object's lifetime. Destructors, exception safety, unique_ptr and shared_ptr in memory, custom deleters for C handles, and a frame pool that returns buffers automatically.

Why it exists

Every resource a camera stack touches — heap memory, DMA buffers, file descriptors for /dev/video0, EGL images, mutex locks, mapped registers — must be released exactly once, on every path out of a function, including error paths and exceptions. Humans are bad at "every path". The compiler is perfect at it: it already runs destructors at every scope exit. Resource Acquisition Is Initialisation simply puts the release into a destructor.

C style: release on every path by hand
int capture(const char* dev) {
    int fd = open(dev, O_RDWR);
    if (fd < 0) return -1;
    void* buf = malloc(FRAME_BYTES);
    if (!buf) { close(fd); return -1; }
    if (configure(fd) != 0) {
        free(buf); close(fd);   // easy to miss
        return -1;
    }
    int rc = read_frame(fd, buf);
    free(buf);
    close(fd);
    return rc;
}

How it works: scope exit is a hook

When control leaves a scope — by falling off the end, return, break, goto or an exception — the compiler calls the destructors of every fully constructed automatic object in that scope, in reverse order of construction. For normal exits it simply emits the calls; for exceptions it emits landing pads that the unwinder jumps to (Chapter 11). Objects that were never constructed are not destroyed, so a constructor that throws halfway through destroys exactly the members that were already built. That gives RAII its guarantee: if acquisition succeeded, release will happen.

The rule of zero, three and five

A class that manages a resource directly must decide what copying, moving and destruction mean. If you write any of destructor, copy constructor or copy assignment, you almost certainly need all three (the rule of three); with C++11 add move constructor and move assignment (the rule of five). The better rule is the rule of zero: write small RAII wrappers for raw resources once (UniqueFd, DmaBuf, EglImage), and build every other class from members that already manage themselves. The compiler-generated special members are then correct automatically.

Exception-safety guarantees

Functions are described by what they promise when something fails. The nothrow guarantee: it cannot fail (destructors, swaps, moves should be here). The strong guarantee: if it fails, state is unchanged — commit-or-rollback, usually by doing the work on a copy and swapping it in. The basic guarantee: if it fails, invariants hold and nothing leaks, but values may have changed. RAII gives the basic guarantee almost for free; the strong one costs a copy and is used where it matters, such as applying a new calibration set atomically. The same vocabulary applies with error codes instead of exceptions.

Smart pointers in memory

std::unique_ptr<T> is a single owning pointer whose destructor calls delete. It cannot be copied, only moved, so ownership is always unambiguous, and with the default or any stateless deleter it is exactly the size of a raw pointer with identical machine code. std::shared_ptr<T> implements shared ownership with a reference count, and that needs somewhere to live: the control block.

The control block holds the strong count (number of shared_ptrs), the weak count (number of weak_ptrs plus one while strong owners exist), and the deleter and allocator. The counts are updated with atomic instructions because owners may live on different threads — a copy of a shared_ptr costs an atomic increment and its destruction an atomic decrement, each a cache-line round trip when the count is contended. std::make_shared allocates the control block and the object in one allocation (better locality, one fewer malloc), at the price that the memory is only freed when the last weak_ptr is gone too. A weak_ptr observes without owning; lock() returns a shared_ptr or null, which is the standard way to break reference cycles such as a camera manager and its listeners pointing at each other.

Custom deleters: RAII for C APIs and pools

The deleter is where RAII meets the rest of the system. A stateless deleter type keeps unique_ptr pointer-sized; a function pointer or capturing lambda adds its own size.

Owners and borrowers

Good C++ code makes ownership readable from the types alone. Owners: values, std::vector, std::unique_ptr, std::shared_ptr, your RAII wrappers. Borrowers (non-owning, must not outlive the owner): T&, T*, std::span, std::string_view, iterators. A raw pointer in modern code should therefore mean "I look at it, someone else owns it". Pass shared_ptr by value only to a function that will keep a copy; to merely use the object, pass const T& and avoid two atomic operations.

Pitfall

"shared_ptr everywhere" is ownership by committee: nobody knows when a buffer dies, destruction happens on whichever thread drops the last reference (possibly a real-time thread, doing a 12 MB free), and cycles leak silently. Default to unique_ptr and values; use shared_ptr where lifetime genuinely is shared, such as a frame read by several consumers at once.

Interesting detail

The aliasing constructor std::shared_ptr<Roi>(frame_sp, &frame_sp->roi) creates a pointer to a sub-object that shares the frame's control block: the ROI keeps the whole frame alive. And a lambda that captures this in a callback registered with a longer-lived object is the most common dangling bug in event-driven C++; capture weak_from_this() instead.

Talk track

"In our code every resource has exactly one owner, and the owner's destructor releases it, so cleanup happens on every exit path without anyone writing it. unique_ptr costs nothing over a raw pointer; shared_ptr costs an atomic counter, so we use it only when ownership is really shared."

6Move semantics and copy elision

What a move really copies, why the moved-from object is still alive, why noexcept on a move constructor changes how std::vector grows, and how C++17 made returning big objects by value free.

Why it exists

Before C++11, returning a std::vector<Frame> from a function or inserting a frame into a container could duplicate megabytes of pixels — copying was the only way to transfer a value. Programmers worked around it with output parameters, swap tricks and the broken std::auto_ptr. Move semantics gave the language a second way to transfer a value: steal the resources of an object that is about to die instead of duplicating them.

What a move really copies

A move constructor is an ordinary constructor that takes T&&. Overload resolution calls it when the argument is an rvalue — a temporary or a std::moved name (Chapter 2). What it does is up to the class, and for a resource-owning class it is always the same pattern: copy the handle (the pointers and sizes), then reset the source so its destructor does not free what it no longer owns.

That picture explains the cost model. Moving a std::vector or a Frame copies 24–48 bytes regardless of how many pixels it owns. But a move is never cheaper than copying the object's own bytes, so for types that hold their data inline, move is copy: moving a std::array<float, 1024> copies 4 KiB, moving a SensorMsg copies 16 bytes, and moving a short std::string copies its inline buffer (libstdc++ stores up to 15 characters inside the 32-byte object — the small-string optimisation).

Rule of five for the Frame class
class Frame {
public:
    Frame(int w, int h, int stride)
        : data_{new std::uint8_t[std::size_t(stride) * h]}, w_{w}, h_{h}, stride_{stride} {}
    ~Frame() { delete[] data_; }

    Frame(Frame&& o) noexcept                       // steal
        : data_{std::exchange(o.data_, nullptr)},
          w_{std::exchange(o.w_, 0)}, h_{std::exchange(o.h_, 0)},
          stride_{std::exchange(o.stride_, 0)} {}
    Frame& operator=(Frame&& o) noexcept {
        if (this != &o) {
            delete[] data_;
            data_   = std::exchange(o.data_, nullptr);
            w_      = std::exchange(o.w_, 0);
            h_      = std::exchange(o.h_, 0);
            stride_ = std::exchange(o.stride_, 0);
        }
        return *this;
    }
    Frame(const Frame&) = delete;                   // frames are too big to copy by accident
    Frame& operator=(const Frame&) = delete;
private:
    std::uint8_t* data_; int w_, h_, stride_;
};

The moved-from object is still alive

A move does not end the source object's lifetime; its destructor still runs at the end of its scope. The standard library guarantees that moved-from library objects are in a valid but unspecified state: you may assign to them, destroy them, or call functions without preconditions such as clear() or size(), but you should not rely on their value. Your own types should give the same promise — which is why the move constructor above nulls the pointer instead of leaving it dangling. Reading a moved-from object is a logic bug that static analysers (clang-tidy's bugprone-use-after-move) catch well.

Why noexcept changes performance

When a std::vector outgrows its capacity it allocates a bigger block and transfers the elements. If transferring the fifth element throws, the strong guarantee of push_back requires the old vector to be intact — possible with copies (the originals are untouched) but not with moves (the first four are already gutted). So vector uses std::move_if_noexcept: it moves only if the move constructor is declared noexcept, and otherwise copies every element. A forgotten noexcept on a move constructor silently turns reallocation of a std::vector<Frame> into deep copies — or into a compile error if the type is move-only, which is the friendlier outcome. Compiler-generated moves are noexcept automatically when all members' moves are.

Copy elision: better than a move

Moving is cheap; not moving at all is cheaper. When a function returns an object by value, the caller reserves space for the result in its own frame and passes the address to the callee as a hidden parameter. If the callee constructs its result directly in that slot, there is neither copy nor move. This is return value optimisation. Since C++17 it is guaranteed when you return a prvalue (return Frame(w, h, s);) — the type does not even need a copy or move constructor. Returning a named local (NRVO) is permitted and done by every major compiler in simple cases but not guaranteed; if elision does not happen, the return is automatically treated as a move.

Pitfall

return std::move(local); is a pessimisation: it turns the returned expression into an xvalue, which disables NRVO and forces a move. Write return local;. GCC and Clang warn with -Wpessimizing-move. Equally, const Frame f = ...; return f; cannot be moved from if elision fails.

Sink parameters and forwarding

A function that stores its argument — a setter, a constructor, queue.push — should take the parameter by value and move it into place. The caller then decides: an lvalue argument is copied once into the parameter, an rvalue argument is moved, and the function body is one line. The alternative, two overloads for const T& and T&&, saves one move and doubles the code. Generic code that passes arguments through without knowing their category uses forwarding references and std::forward, explained with templates in Chapter 7; emplace_back(args...) is the canonical example — it forwards constructor arguments and builds the element directly in the vector's storage.

public:
    explicit Stage(std::string name) : name_{std::move(name)} {}   // sink by value
    void submit(Frame f) { queue_.push_back(std::move(f)); }       // caller moves in

    std::string name_;  std::deque<Frame> queue_;

7Templates and type deduction

How the compiler turns one generic algorithm into specialised machine code for every pixel type, what instantiation costs, how auto and template argument deduction decide types, and how perfect forwarding preserves value categories.

Why it exists

Image code is generic by nature: the same blur, resize or histogram runs on 8-bit grey, 16-bit RAW, packed RGB and float tensors. C offers two bad options — copy the function per type (blur_u8, blur_u16…) or erase the type with void*, an element size and function pointers, as qsort does, paying an indirect call per element and losing type checking. Templates give a third option: write the algorithm once and let the compiler generate a specialised copy for each type, with every operation inlined.

How it works: blueprints and instantiation

A template is not code; it is a blueprint the compiler keeps in memory. When you use box_blur<std::uint16_t>, the compiler instantiates it: it substitutes Pixel = std::uint16_t into the blueprint, type-checks the result and compiles it like a hand-written function. Each distinct set of template arguments produces a separate function with its own symbol — Image<uint8_t> and Image<float> are unrelated types that merely share source code. Because instantiation happens wherever the template is used, the full definition must be visible there, which is why templates live in headers; every translation unit that uses box_blur<uint8_t> compiles its own copy and the linker keeps one.

Name lookup inside a template happens in two phases. Names that do not depend on the template parameter are looked up and checked when the template is defined; names that depend on it (Pixel::channels, a call with a Pixel argument) are looked up at instantiation, including via argument-dependent lookup. This is why you sometimes must write typename T::value_type or this->member: the compiler cannot know, before instantiation, whether a dependent name is a type or a value.

The costs

Templates trade run time for build time and binary size. Every instantiation is compiled and optimised separately, so heavy template libraries (Eigen, ranges, fmt) can dominate build times, and a template instantiated for twenty pixel formats is twenty functions in flash. Two tools help: extern template class Image<std::uint8_t>; in a header tells other translation units not to instantiate it (one .cpp does it explicitly), and moving the type-independent part of a template into a non-template base or helper ("thin template" or hoisting) keeps the per-type part small. Modules (Chapter 10) reduce the parsing part of the cost.

Perfect forwarding

A wrapper such as make_unique, emplace_back or a logging decorator must pass its arguments on exactly as received: lvalues as lvalues (so they are copied or referenced), rvalues as rvalues (so they can be moved). Inside the wrapper every named parameter is an lvalue, so the category is lost — unless the parameter is a forwarding reference T&& and the call uses std::forward<T>(x). The mechanism is reference collapsing: substituting T = Frame& into T&& gives Frame& &&, which collapses to Frame&; only && + && stays an rvalue reference. std::forward<T> is then a conditional std::move: it casts to T&&, which is an rvalue only when T was deduced from an rvalue.

Compile-time values and specialisation

Template parameters can be values as well as types. std::array<float, 9> carries its size in the type; a Kernel<3, 3> lets the compiler fully unroll a convolution. A specialisation provides a different implementation for particular arguments — accumulator_t<std::uint8_t> is std::uint16_t, accumulator_t<float> is float — which is how type traits work. Variadic templates take any number of arguments, and C++17 fold expressions expand an operation over them: (sink << ... << fields). Interesting detail

8Polymorphism: vtables, lambdas and type erasure

How a virtual call is dispatched through a vtable and what it costs, the static alternatives (templates, CRTP, std::variant), what a lambda really is in memory, and how std::function hides any callable behind one type.

Why it exists

A pipeline must treat different things uniformly: several camera drivers behind one interface, stages that can be reordered from a configuration file, callbacks of any shape. Polymorphism means "one interface, many implementations". C++ offers it in several forms with different costs — the skill is choosing the one that matches whether the set of types is open or closed and whether the choice is made at run time or compile time.

Virtual dispatch: how a call finds its function

A class with at least one virtual function gets a vtable: one array of function pointers per class, generated by the compiler and stored in read-only data. Every object of such a class carries a hidden pointer to its class's vtable — the vptr, at offset 0 in the Itanium C++ ABI used by GCC and Clang on Linux and QNX. A call stage->process(frame) through a base pointer compiles to three steps: load the vptr from the object, load the function pointer from the slot assigned to process, call it indirectly with the object as this.

struct Stage {
    virtual ~Stage() = default;                       // slot 0/1: destructors
    virtual void process(Frame& f) = 0;               // slot 2
    virtual std::string_view name() const = 0;        // slot 3
};
struct Dewarp final : Stage {                         // final: no further overrides
    void process(Frame& f) override;
    std::string_view name() const override { return "dewarp"; }
    Lut lut_;
};

The cost. The indirect call itself is cheap when the branch predictor has seen it before — a nanosecond or two. The real costs are elsewhere: the call cannot be inlined, so the optimiser cannot fuse it with the caller's loop or vectorise across it; each object grows by 8 bytes of vptr, which matters for millions of small objects; and a mispredicted indirect call (many different dynamic types in one loop) costs a pipeline flush. The rule that follows: virtual functions at coarse granularity (per frame, per stage) are free in practice; virtual functions per pixel or per keypoint are not.

Compilers devirtualise when they can prove the dynamic type — the object is a local of known type, the class or function is final, or link-time optimisation sees every implementation. final is therefore both documentation and a performance hint.

Pitfall
  • Deleting through a base pointer without a virtual destructor is undefined: only the base part is destroyed. Any class meant to be used polymorphically needs virtual ~Base() (or a protected non-virtual one if deletion through the base is forbidden).
  • Virtual calls in constructors and destructors do not reach the derived class: while Stage's constructor runs, the vptr points to Stage's vtable, because the derived part does not exist yet. Calling a pure virtual function there is undefined.
  • Slicing: passing a Dewarp by value as a Stage copies only the base part. Polymorphic types are handled by reference or pointer and usually have copying disabled.
Interesting detail

The vtable holds more than function pointers: before slot 0 sit the offset-to-top (used for multiple inheritance) and a pointer to the class's std::type_info, which is what typeid and dynamic_cast read. With multiple inheritance an object has several vptrs, and calls through the second base go via small thunks that adjust this before jumping to the real function. Disabling RTTI (-fno-rtti) removes the type-info objects and with them dynamic_cast.

Static polymorphism: deciding at compile time

When the set of implementations is known at build time, the decision can move into the compiler. A template or concept-constrained function accepts any type with the right operations and is instantiated per type (Chapter 7). The curiously recurring template pattern (CRTP) lets a base class call into the derived class without virtual functions: struct Dewarp : StageBase<Dewarp>, where StageBase<D>::run() calls static_cast<D*>(this)->process(). C++23's "deducing this" (void run(this auto& self)) achieves the same with less ceremony. For a closed set of value types — the messages a fusion node accepts — std::variant stores one of N alternatives inline with a small index, and std::visit dispatches through a compiler-generated jump table, with no heap and no vptr per object.

Lambdas: classes the compiler writes for you

A lambda expression creates an object of a unique, unnamed closure type — a class whose data members are the captured variables and whose operator() is the lambda body. Capturing by value stores a copy, capturing by reference stores (in practice) a pointer, and the closure's size is just the size of its captures plus padding. A lambda with no captures has no state and converts to a plain function pointer, which is how lambdas are passed to C APIs. Because the closure type is unique and its call operator is visible, passing a lambda to a template like std::sort or std::transform inlines the body completely — the reason a lambda comparator beats qsort's function pointer.

Variations follow from the model. mutable makes operator() non-const so by-value captures can change. An init-capture [buf = std::move(frame)] creates a member initialised by any expression — the way to move a frame into a task. A generic lambda [](auto px) {...} has a template operator(). Capturing this stores the pointer, not the object: [this] in a callback that outlives the object dangles, while [*this] (C++17) copies the whole object.

Type erasure: one type for any callable

Every lambda has a different type, so a class that stores "a callback" needs one type that can hold any of them. Type erasure builds that type out of a fixed interface plus a hidden, per-type implementation. std::function<void(const Frame&)> does it with three ingredients: a small buffer inside the object for small callables (16 bytes in libstdc++; larger ones are heap-allocated), a pointer to an invoker function that knows how to call the stored type, and a pointer to a manager function that knows how to copy, move and destroy it — a hand-built vtable.

The costs are an indirect call per invocation (no inlining), a possible heap allocation when the closure exceeds the small buffer, and the requirement that the callable be copyable. C++23 adds std::move_only_function (accepts move-only closures, e.g. ones owning a unique_ptr<Frame>) and C++26 adds std::function_ref, a non-owning two-pointer view of a callable for parameters that are only called during the function — no allocation possible. Embedded code often uses a fixed-capacity alternative such as etl::delegate or inplace_function that refuses, at compile time, callables that do not fit its buffer.

Talk track

"For a few big components we use virtual interfaces — the indirect call per frame is irrelevant. For hot code we use templates so everything inlines. For a closed set of message types we use variant and visit, which gives us exhaustiveness checking and no heap. And std::function is our type-erased callback; in real-time paths we use a fixed-size version so it can never allocate."

9The evolution: C++11 to C++26 (and C along the way)

What each standard added, which problem it solved, what it still left open, and what that means for the compiler and standard version an automotive project should choose.

Why it exists

Most "modern C++" discussions are really discussions about versions: whether a team may use std::optional (C++17), concepts (C++20) or std::expected (C++23) depends on the toolchain the SoC vendor ships and on the coding standard the safety case cites. Knowing what each version brought — and why — lets you argue for an upgrade with concrete benefits rather than fashion.

Since 2011 the committee (ISO/IEC JTC1/SC22/WG21) has shipped a new standard every three years on a fixed train model: features that are ready board the train, the rest wait for the next one. Big features therefore often arrive in two steps — a usable core first, the library and polish one release later (lambdas in 11, generic lambdas in 14; coroutines in 20, std::generator in 23; modules in 20, import std; in 23).

C++98/03: the foundation

The first ISO standard fixed classes, templates, exceptions, RTTI, namespaces and the STL — containers, iterators and algorithms designed by Alexander Stepanov around the idea that algorithms should be written once over iterator ranges. What it lacked shaped the next decade: no move semantics (returning containers copied them), no standard smart pointer except the broken auto_ptr, no memory model for threads, verbose iterator types everywhere, and template error messages measured in pages. MISRA C++:2008 targets this version, which is one reason older automotive code looks the way it does.

C++11: the reboot

C++11 was large enough that Stroustrup called it "a new language". Move semantics and rvalue references (Chapter 6) made value semantics efficient. unique_ptr and shared_ptr made ownership expressible (Chapter 5). auto, range-for and lambdas removed most boilerplate. Variadic templates, constexpr, static_assert, nullptr, enum class, override/final, noexcept and brace initialisation arrived, as did a memory model with std::thread and atomics — the first time C++ formally knew threads existed. Limitations: constexpr functions were restricted to a single return statement, lambdas could not be generic or move-capture, and make_unique was simply forgotten.

C++14: finishing C++11

A deliberately small release: generic lambdas ([](auto x)), init-captures ([f = std::move(frame)]), relaxed constexpr with loops and local variables, return-type deduction for functions, std::make_unique, binary literals and digit separators (0b1111'0000). Its importance in automotive is out of proportion to its size: AUTOSAR C++14 guidelines, AUTOSAR Adaptive's ara:: APIs and many supplier toolchains standardised on it for years.

C++17: vocabulary types

C++17 gave everyday code better words. std::optional, std::variant, std::any, std::string_view express "maybe", "one of", "anything" and "a view of characters" without pointers or sentinel values. Structured bindings (auto [ok, frame] = try_grab();), if constexpr, fold expressions, CTAD, if/switch with initialisers, inline variables, [[nodiscard]] and [[maybe_unused]]. Guaranteed copy elision made returning by value a language rule. The library added <filesystem>, PMR allocators (Chapter 4), parallel algorithms and std::byte. Limitations: templates were still constrained with SFINAE, there was no span type, and parallel algorithms depend on a backend (TBB in libstdc++) that embedded targets rarely ship. MISRA C++:2023 targets C++17, which makes it the practical baseline for new safety-relevant code.

C++20: the second big one

C++20 brought four major language features at once. Concepts name the requirements of templates and give readable errors. Ranges make algorithms composable and lazy. Coroutines provide resumable functions as a language mechanism. Modules replace textual inclusion. Chapter 10 explains each. Smaller but daily: std::span, std::format, the three-way comparison operator <=> (one defaulted operator generates all six comparisons), consteval and constinit, designated initialisers (CamConfig{.width = 1920, .fps = 30}), std::bit_cast, std::jthread with stop tokens, [[likely]], and constexpr std::vector and std::string. Limitations: coroutines shipped with no library types (you write your own task type), modules needed years of compiler and build-system work, and std::format lacked print.

C++23: completing C++20

std::expected<T, E> gives value-or-error returns without exceptions — immediately useful in embedded code (Chapter 11). std::mdspan is a non-owning multi-dimensional view: exactly an image or tensor view with configurable layout and stride. std::print, std::generator (a coroutine type in the library), import std;, std::flat_map, std::move_only_function, std::stacktrace, std::to_underlying, std::unreachable, monadic optional operations (and_then, transform), ranges::to, and the language features deducing this, multidimensional operator[] (img[y, x]), if consteval and [[assume]]. The range-for temporary lifetime fix (Chapter 3) and std::start_lifetime_as also landed here.

C++26: reflection, contracts and safety

C++26 was declared feature-complete in June 2025 and finalised through 2025–26; compiler support is arriving feature by feature. It is arguably as significant as C++11. Static reflection lets code inspect types at compile time — iterate over the members of CamConfig to generate serialisation, logging or ARXML mappings without macros or code generators. Contracts (pre, post, contract_assert) put preconditions into function declarations, with a build-selected evaluation semantic. std::execution (senders/receivers) is a standard model for asynchronous and heterogeneous execution — owned by the Concurrency guide. The safety theme is strong: erroneous behaviour for uninitialised reads, a hardened standard library with checked preconditions, and removal of some UB. Also: std::inplace_vector (fixed-capacity, no heap — welcome in embedded), std::simd, std::linalg, #embed for binary resources such as LUTs, pack indexing, = delete("reason"), and std::hive.

Meanwhile in C

C evolves more slowly and more conservatively. C89/C90 is the ANSI baseline; C99 added <stdint.h>, // comments, designated initialisers, restrict, inline, bool and variable-length arrays; C11 added a memory model with _Atomic and <threads.h>, _Generic, _Static_assert and made VLAs optional; C17 was a bug-fix release; C23 (ISO/IEC 9899:2024) adopted several C++ ideas — nullptr, constexpr objects, auto, typeof, [[attributes]], bool/true/false as keywords — plus #embed, _BitInt(N) and checked integer arithmetic in <stdckdint.h>. MISRA C:2012 with its amendments (consolidated as MISRA C:2023/2025) covers C90 to C18.

10Modern language machinery: concepts, ranges, constexpr, coroutines, modules

The five big C++20-era mechanisms explained from the inside: how a concept is checked, why a range pipeline is lazy, what the compiler evaluates at compile time, how a coroutine frame is laid out, and what a module replaces.

Concepts: named requirements for templates

Why it exists

A template accepts any type until something inside it fails to compile — and then the error points deep inside the implementation, pages long. Restricting templates before C++20 needed SFINAE tricks that only experts could read. Concepts let you state the requirement in the signature, so misuse fails at the call with a message about the requirement.

C++17: SFINAE
template <typename P,
  std::enable_if_t<
    std::is_arithmetic_v<P> &&
    (sizeof(P) <= 4), int> = 0>
void box_blur(Image<P> img);
// error for Image<Rgb>: "no matching
// function ... enable_if ... type"
C++20: concept
template <typename P>
concept Pixel = std::is_arithmetic_v<P>
             && sizeof(P) <= 4;

template <Pixel P>
void box_blur(Image<P> img);
// error: "constraints not satisfied:
//   Pixel<Rgb> evaluated to false"

A concept is a named compile-time predicate on types. A requires expression can also check that operations exist: requires(T t, Frame& f) { { t.process(f) } -> std::same_as<void>; } describes a pipeline stage without any base class. During overload resolution the compiler evaluates the constraints of each candidate; candidates whose constraints are false simply drop out, and when two candidates both match, the one whose constraints subsume the other's (is strictly more specific) wins. That lets you write a generic resize and a faster overload for std::contiguous_iterator inputs with no tag dispatch. Concepts cost nothing at run time — they are checked and discarded by the compiler.

Ranges: composable, lazy algorithms

Classic STL algorithms take iterator pairs and produce results eagerly, so chaining three steps means three passes and two temporary containers. C++20 ranges add two things. First, algorithms accept a whole range (std::ranges::sort(dets)) and support projections (sort(dets, {}, &Detection::score)). Second, views: lightweight objects that describe a transformation without performing it. A pipeline of views is a nested iterator adapter; nothing happens until you iterate, and then each element flows through all stages one at a time — no intermediate storage.

auto confident = dets
    | std::views::filter([](const Detection& d) { return d.score > 0.6f; })
    | std::views::transform(&Detection::box)
    | std::views::take(16);                  // nothing computed yet
for (const Box& b : confident) draw(b);      // one pass, no temporary vectors
auto boxes = confident | std::ranges::to<std::vector>();   // C++23: materialise
Pitfall

Views are non-owning, so they inherit every dangling risk of string_view: a view over a temporary container dies with it. Some views cache state (filter caches its first element on begin()), so iterating a view on two threads, or after modifying the underlying container, surprises people. And deep pipelines are slow in unoptimised debug builds, which matters if your team develops on -O0.

constexpr, consteval, constinit: running code in the compiler

The compiler contains an interpreter for a large subset of C++. A constexpr function may be evaluated at compile time when its arguments are constants and the result is needed as a constant; a consteval function (C++20) must be. Since C++20 that subset includes loops, local variables, std::vector, std::string, virtual calls and even new/delete — as long as all allocations are freed before evaluation ends. constinit guarantees a global is initialised at compile time (no static-initialisation-order problems), without making it const.

consteval std::array<std::uint8_t, 4096> make_gamma_lut(double gamma) {
    std::array<std::uint8_t, 4096> lut{};          // 12-bit in, 8-bit out
    for (std::size_t i = 0; i < lut.size(); ++i)      // pow_ce: a constexpr pow helper
        lut[i] = static_cast<std::uint8_t>(255.0 * pow_ce(i / 4095.0, 1.0 / gamma) + 0.5);
    return lut;
}
constexpr auto kGamma22 = make_gamma_lut(2.2);   // computed by the compiler, stored in .rodata/flash

Two benefits follow. Tables, CRC polynomials, fixed-point coefficients and unit conversions cost nothing at start-up and can live in flash. And because UB is a compile error in constant evaluation (Chapter 3), static_assert tests of constexpr helpers are a free correctness check. The price is compile time and the restrictions of the interpreter (no I/O, no reinterpret_cast, limited floating-point math functions until C++26 made more of <cmath> constexpr).

Coroutines: functions that can pause

Why it exists

Some logic is naturally sequential but has to wait in the middle: "read the next tile, process it, wait for the DMA, continue". Without coroutines you either block a thread or cut the logic into callbacks and a hand-written state machine. A coroutine lets you write it sequentially while the compiler builds the state machine.

Any function containing co_await, co_yield or co_return is a coroutine. The compiler transforms it: its local state moves from the stack into a coroutine frame, normally allocated on the heap, and the body is split at each suspension point into a resumable state machine. The caller gets back an object (a task or generator type) holding a std::coroutine_handle — essentially a pointer to the frame — through which it can resume or destroy the coroutine.

The language provides only the mechanism; the behaviour is defined by library types through customisation points. The return type's promise_type decides whether the coroutine starts suspended, where co_yielded values go and what happens at the end. An awaiter — anything with await_ready, await_suspend and await_resume — decides what co_await x does: whether to suspend at all, and whom to hand the handle to (a thread pool, an I/O reactor, a DMA completion interrupt) so it can resume the coroutine later. C++23's std::generator is the first standard coroutine type:

std::generator<Tile> tiles(const Image<std::uint8_t>& img, int ts) {
    for (int y = 0; y < img.height(); y += ts)
        for (int x = 0; x < img.width(); x += ts)
            co_yield Tile{x, y, std::min(ts, img.width() - x), std::min(ts, img.height() - y)};
}
for (Tile t : tiles(frame_view, 64)) process(t);   // lazily produces one tile per resume
Pitfall
  • Reference parameters dangle. Parameters are copied into the frame — but copying a reference copies the reference. In the generator above, img must outlive the iteration; pass views of data that is guaranteed to stay alive, or take parameters by value.
  • The frame allocation. Compilers can elide it when the coroutine's lifetime is nested in the caller's (HALO), but that is not guaranteed. Real-time code supplies a custom operator new in the promise type that takes frames from a pool.
  • Using coroutines for asynchronous I/O, executors and cancellation is covered in the Concurrency guide.

Modules: compile once, import everywhere

#include is text substitution. A translation unit including <vector>, <string> and a few Eigen and OpenCV headers asks the compiler to parse hundreds of thousands of lines — and every other .cpp in the project parses the same lines again. Macros from one header leak into the next, include order matters, and the one-definition rule is easy to violate. A module is compiled once into a binary module interface (BMI), and import loads that compiled form. Only names marked export are visible, macros do not leak in or out, and import order does not matter.

// camera.cppm — module interface unit
export module camera;
import std;                                   // C++23: the whole standard library as one module
export class Frame { /* ... */ };
export Frame grab(int cam_id);
namespace detail { void program_csi(int); }   // not exported: invisible to importers

// main.cpp
import camera;
int main() { auto f = grab(0); }

The catch is tooling. The build system must know the dependency graph between modules before compiling, so modules required new support in compilers (usable in GCC 14, Clang 17+, MSVC 17.x) and build systems (CMake 3.28+), and BMIs are compiler-specific. Embedded toolchains lag behind. In 2026 modules are a good choice for new host-side code and a "watch" item for ECU code; header units and precompiled headers remain the pragmatic build-time fix elsewhere.

Talk track

"Concepts are compile-time requirements on template arguments, so errors appear at the call site. Ranges compose algorithms lazily. constexpr moves computation into the compiler, which also catches UB. Coroutines let the compiler build the state machine we used to write by hand — the frame lives on the heap unless we provide an allocator. And modules replace text inclusion with a compiled interface, mainly to cut build times."

11Errors, exceptions and the ABI

The ways C++ code can report failure, what really happens between throw and catch, why embedded projects often disable exceptions, std::expected as the alternative, and the binary contract — mangling, layout, vtables — that decides whether two separately compiled pieces still fit together.

Why it exists

A camera can be unplugged, a calibration file can be corrupt, a DMA can time out. Every function must have a defined way to say "I could not do it", and the caller must not be able to ignore it silently. C++ offers several mechanisms because the trade-offs differ: exceptions keep the happy path clean and cannot be ignored, but their failure path has unpredictable cost; return values are explicit and deterministic, but verbose.

A useful distinction from the safety world: expected failures (camera disconnected, frame dropped) are part of the function's contract and belong in the return type; programming errors (null where non-null is required, ROI outside the image) are bugs and belong in assertions or contracts that stop the system or bring it to a safe state, not in error codes that every caller has to handle.

What happens between throw and catch

GCC and Clang implement "zero-cost" exceptions, meaning zero cost when nothing is thrown: there are no checks on the happy path. Instead the compiler emits tables (.eh_frame and per-function language-specific data, the LSDA) that describe, for each range of instruction addresses, how to restore registers and which cleanup or catch code to run. A throw then performs a fairly expensive sequence:

Allocating the exception object (usually on the heap), walking the stack twice — the search phase finds a matching handler without changing anything, the cleanup phase unwinds frame by frame running destructors through landing pads — and comparing types with RTTI. Typical cost is several microseconds, growing with stack depth and number of frames to unwind; the first throw may be much slower if the tables must be paged in. If no handler is found, or an exception escapes a noexcept function or a destructor, std::terminate is called.

Why embedded projects disable them

Safety-relevant and hard-real-time code often builds with -fno-exceptions (and -fno-rtti): the worst-case execution time of a throw is hard to bound, the exception object usually needs heap memory, the unwind tables and type information add binary size, and every function becomes a potential exit point that reviews and tools must reason about. The consequence is a dialect: standard-library functions that would throw call abort instead, new cannot report failure except by terminating (use pools, or new (std::nothrow)), constructors cannot fail (use factory functions returning expected), and many third-party libraries need configuration or patches. MISRA C++:2023 does not ban exceptions but restricts how they are used; AUTOSAR C++14 also allowed them with rules. Chapter 14 covers the policies.

std::expected: deterministic errors that compose
enum class CamError { NotConnected, Timeout, BadFormat };

                 .and_then(to_float)                        // only runs on success
                 .transform([](Image<float> i) { return undistort(i); });

Interesting detail

noexcept is a promise to the caller and the optimiser, not a check: if an exception does escape, the program terminates. Its main practical effect is enabling the fast paths of the standard library — vector moves elements only through noexcept move constructors (Chapter 6). Destructors are noexcept by default.

The ABI: the contract between compiled pieces

An API is a source-level contract: names, types, signatures. An ABI (application binary interface) is the machine-level contract that lets separately compiled object files and libraries work together: how names are encoded as symbols, how objects are laid out in memory, how vtables are organised, how arguments are passed in registers, how exceptions unwind. On Linux, QNX and most non-Windows platforms the C++ part is the Itanium C++ ABI (named after the platform it was first written for), layered on the processor's C calling convention — System V AMD64 on x86-64, AAPCS64 on Arm64.

Name mangling

C has one function per name; C++ has overloads, namespaces, classes and templates, so the compiler encodes the full signature into the symbol. Seeing mangled names in linker errors is common enough that reading them is a useful skill (c++filt decodes them).

Layout, and why ABI stability is hard

Everything a client compiles against a header becomes baked into the client's binary: the sizeof of a class (for stack allocation), the offsets of members accessed by inline functions, the slot numbers of virtual functions. Add a private member to Frame or a virtual function before an existing one, ship a new libcamera.so without recompiling the clients, and they will read the wrong offsets or call the wrong slot — no linker error, just corruption. This is why OEM integration plans specify exact toolchain versions and why AUTOSAR Adaptive platform updates are delivered as matched sets.

The standard library carries the same burden. GCC 5 had to change std::string to meet C++11 (no copy-on-write), which broke its layout; libstdc++ therefore contains two ABIs side by side, selected by _GLIBCXX_USE_CXX11_ABI, and linking objects built with different settings gives undefined-symbol errors mentioning __cxx11. Fear of a repeat is why the committee rejects changes that would make std::unordered_map or std::regex faster but change their layout.

Why it matters

Techniques for a stable binary interface: the pimpl idiom (the public class holds only a pointer to a private implementation, so its size never changes); a C API with opaque handles at the library boundary (Chapter 13); inline namespaces to version symbols (namespace cam { inline namespace v2 { ... } }); and never exposing standard-library types across a boundary built with a different toolchain. Symbol visibility, versioning and shared-library mechanics are covered in the Build Systems & Toolchains guide.

Talk track

"For expected failures like a disconnected camera we return std::expected, so error handling is visible and deterministic. Exceptions are zero-cost until thrown, but a throw costs microseconds, needs the heap and complicates timing analysis, so our real-time code is built without them. At library boundaries we care about the ABI as much as the API: layout, mangling and vtable slots are baked into the clients, so we use pimpl or a C interface where binaries are delivered separately."

12Performance: writing code the machine likes

Why memory, not arithmetic, usually limits image code; cache lines and locality; array-of-structs versus struct-of-arrays; false sharing; branch prediction; loops the compiler can vectorise; zero-copy interfaces; and how to measure before optimising.

Why it exists

A modern core can execute several instructions per cycle, but a load that misses every cache waits around 100 ns — 300 or more cycles — for DRAM. A 1920×1080 frame does not fit in L1 or L2 cache. Most of the speed difference between a naïve and a good image kernel therefore comes from how data is laid out and traversed, not from clever arithmetic. C++ gives you full control of layout, which is exactly why it is used here.

Cache lines and locality

Memory moves between DRAM and caches in cache lines of 64 bytes on almost all current Arm and x86 cores (Apple's cores use 128). Reading one byte brings its 63 neighbours along. Code is fast when it uses those neighbours (spatial locality) and when it reuses data while it is still cached (temporal locality). Hardware prefetchers detect sequential and constant-stride access and fetch lines ahead of time, so a forward scan through a row runs at memory bandwidth, while random access or large strides defeat them.

For images the consequence is simple: images are stored row-major, so iterate y in the outer loop and x in the inner loop. A column-wise loop over a 1920-pixel-wide RGBA image touches a new cache line (and every 4 KiB, a new page and TLB entry) for every pixel. Operations that are inherently column-wise — a vertical filter, a transpose, a rotation — are done in tiles small enough that the rows of a tile stay in cache. Separately, a row stride that is a large power of two (e.g. 4096 bytes) can make every row of a column map to the same cache set and evict each other; padding the stride by one cache line is a classic fix.

Data layout: AoS versus SoA

The natural C++ way to store keypoints is an array of structs (AoS): std::vector<Keypoint>. If a hot loop only reads x and y, every cache line also carries the score, scale, angle and descriptor index it does not need. A struct of arrays (SoA) stores each field contiguously, so the loop reads only useful bytes and the compiler can load eight x values into one SIMD register.

Neither layout is always right: AoS is better when code uses most fields of one element at a time, SoA when loops stream over a few fields of many elements. A common compromise is hot/cold splitting — keep the fields the per-frame loop needs in a compact struct and move rarely used data (debug info, descriptors) to a parallel array — and AoSoA, small fixed-size blocks of SoA that match the SIMD width.

False sharing (the layout side)

Cache coherence works per line. When two cores write to different variables that happen to share a cache line, each write invalidates the other core's copy, and the line ping-pongs between cores even though no data is actually shared. Per-camera statistics counters placed next to each other in an array are the typical case: four capture threads, one line, and throughput that gets worse as you add cameras.

struct alignas(std::hardware_destructive_interference_size) CamStats {   // 64 on most targets
    std::uint64_t frames = 0, drops = 0, late = 0;
};
std::array<CamStats, 4> stats;     // each camera's counters on their own cache line
In your library

Atomics, memory ordering and lock-free structures — the synchronisation side of sharing — are covered in the Concurrency, Parallelism & Asynchronous Programming guide. Here the point is purely layout: data written by different threads belongs on different cache lines.

Branch prediction

A pipelined core guesses the outcome of each branch and keeps executing speculatively; a wrong guess discards that work and costs roughly 15–20 cycles. Predictors are excellent at regular patterns (loop exits, rarely-taken error checks) and bad at data-dependent random decisions — such as thresholding a noisy image pixel by pixel. For those, branchless code that computes both outcomes and selects one (out = v > t ? 255 : 0, which compilers turn into a conditional move or a SIMD compare-and-mask) is often several times faster and, importantly for real-time systems, has data-independent timing. [[likely]]/[[unlikely]] (C++20) only influence code placement; they do not train the predictor.

SIMD-friendly C++

Compilers vectorise loops automatically when they can prove it is safe and profitable. You help them by writing loops that are easy to prove: contiguous data accessed with a simple index; a trip count known before the loop starts; no function calls that cannot be inlined; no early exits; and no possible aliasing between input and output. The last one is the most common blocker in image code — if dst and src could overlap, the compiler must assume a store to dst[i] changes src[i+1]. C has restrict; C++ compilers support __restrict as an extension, and taking the inputs as std::span<const T> plus copying scalars into locals helps too. Use int or std::size_t loop counters consistently, keep data in SoA form, and align buffers to the vector width.

void scale_u8(const std::uint8_t* __restrict src, std::uint8_t* __restrict dst,
              std::size_t n, std::uint16_t gain_q8) {
    for (std::size_t i = 0; i < n; ++i)                         // vectorises to NEON/AVX2
        dst[i] = static_cast<std::uint8_t>(std::min<std::uint32_t>((src[i] * gain_q8) >> 8, 255));
}
// verify: GCC -O3 -fopt-info-vec-optimized, Clang -Rpass=loop-vectorize

C++26 adds std::simd, a portable vector type with explicit lanes, for code that should not depend on the auto-vectoriser's mood. Hand-written NEON intrinsics and the Arm/x86 vector units themselves are covered in Embedded Compute for Automotive Vision, chapters 10–11.

Zero-copy interfaces

At 8 MP and 30 fps, a single unnecessary copy of each frame is roughly 1 GB/s of memory bandwidth — a large slice of an ECU's DDR budget. The fastest copy is the one that never happens. In C++ that becomes an interface rule: stages receive views, not buffers. The capture driver owns the DMA buffers; stages are given an Image<T> or std::mdspan view (pointer, width, height, stride) or a ref-counted handle; the GPU imports the same buffer through its dma-buf file descriptor instead of uploading pixels. Ownership (who returns the buffer to the pool, and when) travels separately from the view, usually as the pool handle from Chapter 5.

Interesting detail

std::mdspan (C++23) is the standard version of the image view: std::mdspan<const std::uint8_t, std::dextents<int, 2>, std::layout_stride> describes a strided 2-D view with no ownership, and a sub-view for an ROI is created with std::submdspan (C++26) without touching pixels.

Measure first

Every rule in this chapter has exceptions, and intuition about performance is wrong often enough that measuring is the only reliable method. Use a sampling profiler on the target (perf on Linux, the QNX profiler, Arm Streamline, Intel VTune on the host), look at hardware counters for cache misses and branch mispredictions rather than only time, and benchmark micro-kernels with a framework (Google Benchmark, nanobench) that prevents the optimiser from deleting the work you are measuring. Optimise the hot loop that the profile shows, then measure again. Build flags, LTO and PGO, which often give 10–20 % for free, are covered in the Build Systems guide.

Numbers worth knowing
  • Latency, typical: register 0 · L1 ≈ 1 ns (4–5 cycles) · L2 ≈ 3–5 ns · L3/SLC ≈ 10–20 ns · DRAM ≈ 80–120 ns · mispredicted branch ≈ 15–20 cycles.
  • Cache line 64 B · page 4 KiB · NEON register 128 bit (16 × u8, 4 × float) · AVX2 256 bit.
  • One 8 MP RGBA frame = 32 MB; one extra copy at 30 fps ≈ 1 GB/s of DDR bandwidth.
Talk track

"For image code the CPU is mostly waiting for memory, so we design data layout first: row-major traversal and tiling for locality, struct-of-arrays for SIMD, separate cache lines for data written by different threads, and views instead of copies between stages. Then we let the profiler, not intuition, tell us where to spend effort."

13C versus C++, and making them work together

Two philosophies on one ECU: where C and C++ differ in intent and in detail, why C++ is not a superset of C, and how extern "C", opaque handles and RAII wrappers let the two cross a boundary safely in both directions.

Why it exists

A camera ECU is bilingual. Kernel drivers, V4L2, EGL, OpenCL, the QNX camera API, TI's OpenVX/TIOVX and most vendor SDKs expose C APIs, because C has a stable, simple ABI that every language can call. The safety MCU often runs pure C. Application code is C++. Every project therefore has boundaries where C++ calls C, and sometimes where C++ must offer a C interface to someone else. Getting those boundaries right is a daily skill.

Neither is "better". C's transparency is valuable where every instruction must be reviewed against timing and safety requirements, and where a toolchain must be qualified cheaply. C++'s abstractions remove whole classes of bugs — leaks, double frees, forgotten lengths, mismatched types — that C prevents only through discipline and static analysis. A useful way to put it to a customer: C makes the machine visible; C++ makes the intent visible.

C++ is not a superset of C

Most C compiles as C++, but not all, and some code compiles in both with different meaning. The differences that bite in practice:

  • void* conversion. C converts void* to any object pointer implicitly (Frame* f = malloc(n);); C++ requires a cast.
  • Type punning through unions. Writing one union member and reading another is a sanctioned reinterpretation in C; in C++ reading an inactive member is undefined. Use memcpy or std::bit_cast in C++.
  • Variable-length arrays (float tmp[n];) are C99 (optional since C11); not standard C++.
  • restrict exists only in C; C++ compilers offer __restrict.
  • Character literals: sizeof('a') is sizeof(int) in C and 1 in C++.
  • Empty parameter lists: before C23, int f(); in C means "unspecified parameters"; in C++ (and C23) it means no parameters.
  • const at namespace scope has internal linkage in C++, external in C — a const int kWidth = 1920; in a shared header behaves differently.
  • Designated initialisers: C allows any order, nesting and array designators ([3] = 1); C++20 requires declaration order and no array designators.
  • Implicit lifetime: C treats malloced memory as usable by any type; C++ needed rules (C++20 implicit-lifetime types, C++23 start_lifetime_as) to bless the same idiom.

Calling C from C++

extern "C" tells the C++ compiler to use the C linkage for a declaration: no name mangling (the symbol is just v4l2_open) and the platform's C calling convention. C headers designed for both languages wrap their declarations in a guard so C++ sees extern "C" and C sees nothing:

cam_api.h — a C API usable from both languages

extern "C" {
#endif

typedef struct cam_device cam_device;          /* opaque: layout hidden from users */
typedef void (*cam_frame_cb)(const uint8_t* px, size_t len, void* user);

int  cam_open(int id, cam_device** out);       /* 0 on success, negative errno */

#ifdef __cplusplus
}
#endif

On the C++ side the job is to convert the C contract into C++ types once, in a thin wrapper, so the rest of the code never sees raw handles: a unique_ptr with a deleter for ownership, expected for the error code, std::span for pointer-plus-length, and a trampoline to turn the C callback with a void* user pointer into a call on a C++ object.

The C++ wrapper
class Camera {
public:
    static std::expected<Camera, int> open(int id) {
        cam_device* d = nullptr;
        if (int rc = cam_open(id, &d); rc != 0) return std::unexpected(rc);
        return Camera{d};
    }
    template <class F> int start(F& on_frame) {      // F lives at least as long as streaming
        return cam_start(dev_.get(),
            [](const std::uint8_t* px, std::size_t n, void* user) {   // captureless lambda
                (*static_cast<F*>(user))(std::span{px, n});           //  = C function pointer
            }, &on_frame);
    }
private:
    struct Close { void operator()(cam_device* d) const noexcept { cam_close(d); } };
    explicit Camera(cam_device* d) : dev_{d} {}
    std::unique_ptr<cam_device, Close> dev_;          // move-only, closes exactly once
};

Offering C from C++

The reverse direction — a C++ library that customers or other suppliers integrate through a C interface — is common for perception libraries delivered as binaries, precisely because a C API sidesteps C++ ABI differences between toolchains (Chapter 11). The rules: functions are declared extern "C"; only C-compatible types cross (fixed-width integers, enums, standard-layout structs, opaque pointers); the library allocates and frees its own objects (never let the caller free() what C++ newed); and no exception may cross the boundary — a C caller cannot handle it, and unwinding through C frames is at best implementation-specific. Every exported function therefore catches everything and converts it to an error code.

extern "C" int det_run(det_handle* h, const uint8_t* px, int w, int h_px, det_box* out, int* n) noexcept {
    try {
        auto& d = *reinterpret_cast<Detector*>(h);
        auto boxes = d.run(ImageView<const std::uint8_t>{px, w, h_px});
        *n = static_cast<int>(std::min<std::size_t>(boxes.size(), *n));
        std::copy_n(boxes.begin(), *n, out);
        return 0;
    } catch (const std::bad_alloc&) { return -ENOMEM; }
      catch (...)                   { return -EIO; }
}
static_assert(std::is_standard_layout_v<det_box> && std::is_trivially_copyable_v<det_box>);
Pitfall

A struct shared between C and C++ must have the same layout in both: keep it standard-layout and trivially copyable, use fixed-width types, avoid bool and enum sizes you have not pinned down (C's enum is usually int; in C++ give it an explicit underlying type), and assert sizes and offsetof on both sides. Bit-fields and packing pragmas are the usual sources of silent mismatches.

Talk track

"We use C at the boundaries because its ABI is stable and every tool understands it, and C++ inside because it lets the type system manage resources and intent. Each C API gets one thin C++ wrapper that turns handles into RAII objects, error codes into expected, and pointer-length pairs into spans — so the rest of the code never touches the raw C contract."

14Embedded and safety-critical C++

Why safety projects use a restricted C++, how deterministic allocation is organised, the usual exception and RTTI policies, what MISRA C++:2023 and AUTOSAR C++14 actually contain, and what a restricted runtime looks like on an MCU.

Why it exists

ISO 26262-6 asks for software that is analysable: the coding guidelines must enforce a language subset, strong typing, defensive implementation and the absence of constructs whose behaviour is hard to predict, such as dynamic objects and unbounded recursion. Full C++ contains undefined behaviour, implicit conversions, heap allocation with unbounded timing, and exceptions whose worst-case cost is hard to bound. Embedded C++ is therefore C++ with rules: a subset chosen so that both reviewers and tools can reason about the code.

In your library

How coding guidelines fit into the development process — SWE.3/SWE.4 work products, deviation records, assessor questions — is covered in the ASPICE SWE Level 2 Study Guide. Running the checkers as CI quality gates belongs to the Software Quality & Engineering Workflow guide; ISO 26262 itself is summarised in the Automotive CV Standards guide. This chapter covers the content of the rules and the engineering patterns behind them.

Deterministic allocation

The core pattern is to split the program's life into phases. During initialisation the software may allocate: it reads configuration, creates every buffer, pool, queue and object it will ever need, pre-faults and locks memory, and verifies that everything fits. During the run phase — the part with timing requirements — it never calls the general-purpose allocator; all objects come from the pools and fixed-capacity containers created at start-up. Shutdown releases everything (on many ECUs, shutdown is simply power-off).

C++ supports this well once you know the tools: std::array and fixed-capacity containers (etl::vector<T, N>, C++26 std::inplace_vector<T, N>) keep storage inside the object; PMR containers draw from a pool or arena with null_memory_resource() as the upstream so a fallback to the heap fails loudly (Chapter 4); placement new and handles from object pools replace new/delete. A useful safety net is to replace the global operator new with a version that records or traps any allocation after the run phase has started — turning "we don't allocate at run time" into something a test can prove.

namespace rt { inline std::atomic<bool> running{false}; }
void* operator new(std::size_t n) {
    if (rt::running.load(std::memory_order_relaxed)) rt::fatal("heap allocation in run phase");
    if (void* p = std::malloc(n)) return p;
    rt::fatal("out of memory");
}
void operator delete(void* p) noexcept { std::free(p); }   // (plus the sized/aligned variants)

MISRA C++:2023

MISRA C++:2023, "Guidelines for the use of C++17 in critical systems", was published by the MISRA consortium in October 2023. It replaces MISRA C++:2008, which targeted C++03 and had become an obstacle to modern code, and it absorbs the AUTOSAR C++14 guidelines: AUTOSAR handed its rule set to MISRA so the industry would have one standard again. It contains 179 guidelines — a small number of directives (requirements that need judgement or process evidence) and rules (precise enough for tools to check). Each guideline has a category: mandatory (no deviation allowed), required (deviation only with a documented, approved rationale) or advisory (recommended; can be re-categorised by the project). Each is also classed as decidable or undecidable by a tool and as checkable within a single translation unit or only across the whole system — which tells you how much to trust "zero findings" from a checker.

Compared with the 2008 edition, the philosophy changed: instead of banning features, it permits modern C++ and targets the specific ways each feature goes wrong. Typical rule themes:

AUTOSAR C++14

The AUTOSAR "Guidelines for the use of the C++14 language in critical and safety-related systems" (first released 2017) were written because MISRA C++:2008 could not be applied to the C++14 code of AUTOSAR Adaptive. They contain roughly 350 rules with a recognisable naming scheme: rules starting with A (for example A5-1-1) were new AUTOSAR rules, rules starting with M were adopted from MISRA C++:2008. Many supplier code bases, tool configurations and customer contracts still cite them, so you will meet both rule sets; for new projects MISRA C++:2023 is the successor. For the C parts of a system, MISRA C:2012 (with amendments, consolidated in MISRA C:2023 and later editions) is the reference, and CERT C/C++ adds security-oriented rules often required by ISO/SAE 21434 work.

Restricted runtimes

On a microcontroller there may be no operating system at all. The C++ freestanding implementation guarantees only a small part of the library (type traits, <limits>, <cstdint>, <atomic>, <new>, and since C++23 more header-only pieces). Before main, startup code copies .data from flash, zeroes .bss and walks .init_array to run global constructors — which is why constructors of globals must not depend on hardware that is not initialised yet. Static stack-usage analysis (-fstack-usage, vendor tools) replaces "8 MiB is enough". Libraries such as the Embedded Template Library (ETL) provide fixed-capacity containers, delegates and state machines designed for this world; on the SoC side, QNX and Linux offer the full library but the real-time partitions often adopt the same restrictions by policy.

In the camera ECU

A typical split in a surround-view ECU: the safety MCU runs AUTOSAR Classic in MISRA C (generated RTE code plus hand-written SWCs); the SoC runs C++17 under MISRA C++:2023 for the safety-relevant camera monitoring path (no exceptions, no run-time allocation), and C++17/20 with fewer restrictions for QM visualisation and HMI code. The boundary between the partitions is a C-compatible message format with fixed-size structs — Chapter 13's rules applied across a hypervisor.

Talk track

"For safety code we use a C++17 subset defined by MISRA C++:2023, which also replaced AUTOSAR C++14. In practice that means: no undefined behaviour, no implicit narrowing, no naked new or delete, all memory allocated at start-up, and either no exceptions or very restricted ones. Deviations are documented and approved, so the safety case can show we know exactly where and why we left the subset."

15Putting it together: refactoring a camera frame class

One realistic piece of code taken from C-style to modern C++ in five steps — each step motivated by a bug it removes — ending in a design you can draw on a whiteboard in a design review.

The starting point is code that exists in many camera projects: a struct with a raw pointer, a handful of free functions, and comments telling the reader what not to do. Nothing in it is wrong if every caller is careful. The refactoring moves each "if every caller is careful" into the type system.

Step 0: C with classes

struct Frame {
    uint8_t* data;          // owned? borrowed? who frees it?
    int width, height, stride, format;
    uint64_t ts;
};
Frame* frame_create(int w, int h, int fmt);    // caller must call frame_destroy()
void   frame_destroy(Frame* f);
int    blur_u8(Frame* src, Frame* dst);        // -1 if formats differ, src must not equal dst

Problems: leaks on early returns; double frees when two structs are copied (the copy shares data); format checked at run time; aliasing rule in a comment; one blur per pixel type.

Step 1: an owning class, rule of zero

class Frame {
public:
    Frame(int w, int h, PixelFormat fmt)
        : w_{w}, h_{h}, stride_{row_bytes(w, fmt)}, fmt_{fmt},
          data_{std::make_unique_for_overwrite<std::uint8_t[]>(std::size_t(stride_) * h)} {}
    // no destructor, no copy/move declarations: unique_ptr makes Frame move-only and leak-free
private:
    int w_, h_, stride_; PixelFormat fmt_; std::uint64_t ts_{};
    std::unique_ptr<std::uint8_t[]> data_;           // declared last: initialised after stride_
};

Removed: leaks and double frees. Copying is now a compile error instead of a shared-buffer bug; moving is free (Chapter 6). make_unique_for_overwrite (C++20) skips zero-filling 6 MB that the camera will overwrite anyway. Note the member order: data_ uses stride_, so it is declared after it (Chapter 3).

Step 2: separate owning from viewing

Most functions do not care who owns the pixels; they need a typed window onto them. A non-owning view type, cheap to copy and passed by value, decouples algorithms from storage — a Frame, a DMA buffer from the pool, a sub-rectangle or a test fixture can all produce one.

template <class T>
class ImageView {                     // like std::mdspan<T, dextents<int,2>, layout_stride>
public:
    ImageView(T* p, int w, int h, std::ptrdiff_t stride_bytes);
    T* row(int y) const { return reinterpret_cast<T*>(base_ + y * stride_); }  // byte-typed base_
    ImageView sub(Roi r) const;                       // ROI without copying
    int width() const { return w_; }  int height() const { return h_; }
private:
    std::conditional_t<std::is_const_v<T>, const std::byte*, std::byte*> base_;
    int w_, h_; std::ptrdiff_t stride_;
};
ImageView<const std::uint8_t> Frame::view_u8() const;   // checks format once, here
ImageView<std::uint8_t>       Frame::view_u8();         // writable view of a non-const frame

Removed: repeated format checks and pointer arithmetic in every algorithm; const-correctness is now deep — a view of const pixels cannot write. The reinterpret_cast is confined to one audited place.

Step 3: one generic algorithm, constrained

template <class T> concept Pixel = std::is_arithmetic_v<T>;

template <Pixel T>
void box_blur(ImageView<const T> src, ImageView<T> dst) {
    assert(src.width() == dst.width() && src.height() == dst.height());   // C++26: pre(...)

Removed: per-type copies of the algorithm and run-time format dispatch. Passing an ImageView<Rgb> fails at compile time with "constraints not satisfied". Source and destination have different types (const T vs T), so passing the same view for both requires an explicit, visible conversion.

QSelf-check questions

Questions that check the core mechanisms of the chapter, each with a concise model answer and the section that explains it in depth.

Q.1Language fundamentals

What is undefined behaviour and why does C++ have it?Ch. 3

Behaviour for which the standard imposes no requirements, such as signed overflow, out-of-bounds access or use after free. It exists so compilers can generate fast code without checks and can optimise on the assumption that it never happens. The consequence is that UB can delete code elsewhere — for example a null check placed after a dereference — so it must be prevented by design, rules and sanitizers rather than found by testing.

Explain lvalues, prvalues and xvalues.Ch. 2

An lvalue has identity and is not implicitly movable (a named variable). A prvalue is a pure value without identity (a literal, a function returning by value); since C++17 it only becomes an object when materialised. An xvalue has identity but is expiring, typically the result of std::move. Rvalues — prvalues and xvalues — bind to T&&, which is how move constructors get selected.

What does std::move do?Ch. 2, 6

Nothing at run time: it is a static_cast to an rvalue reference. It allows overload resolution to pick a move constructor or assignment, which does the transfer. Moving from a const object silently copies, and the moved-from object stays alive in a valid but unspecified state.

What is the difference between a pointer and a reference?Ch. 2

A pointer is an object holding an address; it can be null, re-pointed and do arithmetic. A reference is an alias that must be bound at initialisation and cannot be re-seated or (validly) null. Reference parameters are implemented as addresses, so the cost is the same; the difference is the contract.

What happens to temporaries, and when does lifetime extension apply?Ch. 3

A temporary dies at the end of the full-expression. Binding it directly to a const T& or T&& local extends it to the reference's lifetime, but not through function returns, so a string_view of a returned std::string dangles. C++23 additionally extends temporaries in a range-for initialiser.

Q.2Memory and ownership

Explain RAII and why it matters.Ch. 5

Resource acquisition is initialisation: a resource is acquired in a constructor and released in the destructor. Because the compiler runs destructors on every scope exit — returns, breaks and exceptions — release cannot be forgotten. It gives the basic exception-safety guarantee almost for free and makes ownership visible in types.

How is shared_ptr implemented, and what does it cost?Ch. 5

Two pointers: to the object and to a control block holding atomic strong and weak counts plus deleter and allocator. Copies and destructions perform atomic increments/decrements. make_shared puts object and control block in one allocation. Costs: 16 bytes, atomics on copy, possible destruction on an unexpected thread, and leaks through cycles unless broken with weak_ptr.

Why might sizeof of a struct be larger than the sum of its members?Ch. 4

Padding: each member is placed at a multiple of its alignment and the struct size is rounded up to its largest alignment so arrays stay aligned. Ordering members from largest to smallest alignment minimises padding.

How would you avoid heap allocation in a real-time loop?Ch. 4, 14

Allocate everything during initialisation and use pools, per-frame monotonic arenas, rings and fixed-capacity containers at run time. PMR containers with a null upstream resource fail loudly on fallback, and replacing the global operator new with a trap after start-up proves the property in tests.

What does a move really copy in std::vector, std::string and std::array?Ch. 6

For vector, the three pointers (24 bytes) and then it nulls the source. For string, the pointer and sizes — or, for short strings in the small buffer, the characters themselves. For std::array, every element, because the data is inline: move equals copy.

Why should move constructors be noexcept?Ch. 6

vector reallocation must preserve the strong guarantee, so it uses move_if_noexcept: without noexcept it copies every element instead of moving them.

Q.3Polymorphism and generic code

How does a virtual function call work?Ch. 8

Each polymorphic object holds a vptr to its class's vtable, an array of function pointers. The call loads the vptr, loads the function pointer at a fixed slot and calls it indirectly. Cost: an indirect call (cheap if predicted), no inlining, 8 bytes per object. During construction the vptr points to the base vtable, so virtual calls from constructors do not reach derived overrides.

Why does a base class need a virtual destructor?Ch. 8

Deleting a derived object through a base pointer calls the destructor through the vtable only if it is virtual; otherwise only the base part is destroyed, which is undefined behaviour and leaks the derived resources.

Compare virtual functions, templates, std::variant and std::function.Ch. 8

Virtual functions: open set, run-time choice, indirect calls — good for coarse interfaces. Templates/concepts: compile-time choice, inlined — good for hot code. Variant: closed set of value types, no heap, exhaustive visit — good for messages and states. std::function: type erasure of any callable, indirect call and possible allocation — good for callbacks.

What is a lambda in memory?Ch. 8

An object of a unique compiler-generated class with the captures as data members and the body as a const operator(). Its size is the captures plus padding; a captureless lambda converts to a function pointer. Passed to a template it is fully inlined.

What is perfect forwarding?Ch. 7

Passing arguments through a generic function while preserving their value category, using a forwarding reference T&& and std::forward<T>. Reference collapsing makes T an lvalue reference for lvalue arguments, so forward casts to an rvalue only for rvalue arguments. emplace_back is the classic example.

What problem do concepts solve?Ch. 10

They name the requirements of template arguments so violations are reported at the call site in terms of the requirement, and they replace unreadable SFINAE. Constraint subsumption also lets the compiler pick the most specific overload. They cost nothing at run time.

Q.4Modern features, errors and the ABI

How are coroutines implemented?Ch. 10

The compiler turns the function into a state machine and moves state that lives across suspension points — parameters, locals, the promise and a resume index — into a coroutine frame, usually heap-allocated. The caller holds a coroutine_handle pointing at it. Behaviour is defined by the promise type and awaiters. Pitfalls: reference parameters dangle, and the allocation needs control in real-time code.

How do exceptions work, and why do embedded projects often disable them?Ch. 11

Table-based: no cost on the happy path; on throw the runtime allocates the exception, walks the stack once to find a handler and again to run destructors through landing pads. Throw time is hard to bound, needs heap and RTTI, and the tables add size — so hard-real-time and many safety components use -fno-exceptions and return expected or error codes.

What is an ABI and how can you break it without changing the API?Ch. 11

The binary contract: name mangling, object layout, vtable layout, calling convention, exception handling. Adding a private member or reordering virtual functions changes layout or slot numbers; clients compiled against the old header then use wrong offsets without a link error. Pimpl, C interfaces and versioned inline namespaces protect binary boundaries.

What changed in C++11, 17, 20 and 23 that you use daily?Ch. 9

C++11: move semantics, smart pointers, lambdas, auto, memory model. C++17: optional, variant, string_view, structured bindings, if constexpr, guaranteed elision. C++20: concepts, ranges, span, coroutines, modules, <=>. C++23: expected, mdspan, print. C++26 brings reflection, contracts and a hardened library.

Q.5Performance and embedded

What is false sharing and how do you fix it?Ch. 12

Two cores writing different variables on the same cache line force the line to bounce between their caches. Fix by placing data written by different threads on separate lines, e.g. alignas(std::hardware_destructive_interference_size), or by accumulating locally and combining later.

How do you make a loop vectorise?Ch. 12

Contiguous data with a simple index, known trip count, no non-inlinable calls or early exits, and no possible aliasing between inputs and outputs (__restrict, separate types or local copies). SoA layout and aligned buffers help; verify with the compiler's vectorisation report.

How do you design a zero-copy camera pipeline in C++?Ch. 12, 15

A pool owns DMA buffers allocated at start-up; ownership travels as a move-only handle that returns the buffer on destruction; stages receive non-owning typed views (pointer, size, stride); the GPU imports the same buffer by dma-buf fd. Pixels are written once and never copied.

How do you call a C library from C++ safely?Ch. 13

Declare it extern "C", then write one thin wrapper: handles in unique_ptr with a deleter, error codes into expected, pointer-length pairs into span, C callbacks via a captureless-lambda trampoline using the void* user pointer. When exposing C from C++, never let exceptions cross the boundary.

What are MISRA C++:2023 and AUTOSAR C++14, and how do they relate?Ch. 14

Coding standards defining a safe subset of C++ for critical systems. AUTOSAR C++14 (2017) covered C++14 for Adaptive AUTOSAR because MISRA C++:2008 only covered C++03. MISRA C++:2023 targets C++17, contains 179 guidelines classified mandatory, required or advisory, and absorbed AUTOSAR C++14, so it is the successor. Compliance means checked rules plus documented, approved deviations.

(Manager) How would you introduce a newer C++ standard in an automotive team?Ch. 9, 14

Start from the qualified toolchain and the coding standard: confirm compiler support on every target and its qualification status, check what the guideline set covers, and pick concrete wins (e.g. span, expected, concepts) that remove known bug classes. Pilot in QM components, update static-analysis configurations and the guideline re-categorisation plan, train reviewers, and only then move safety-relevant code.

(Manager) How do you keep a large C++ code base reviewable?Ch. 15

Agree a subset and enforce it with tools; make ownership and errors visible in types; keep algorithms generic and storage separate; require noexcept moves, no naked new, no run-time allocation in real-time paths; and use a short checklist in reviews (ownership, lifetime, UB, allocation, layout, errors).

Q.6Why and what if

What if a class that owns a raw buffer has a destructor but no copy constructor?What if

The compiler-generated copy copies the pointer, so two objects own the same buffer and both destructors free it: a double free, or a use-after-free when one copy outlives the other. Follow the rule of zero (let a std::unique_ptr or container own the buffer) or the rule of five (define or delete all special members together).

Why can adding a member to a class in a shared library break programs that were not recompiled?Why

Callers compiled against the old header have the old sizeof and member offsets baked into their code, and inline functions read fields at the old offsets. The new library then reads and writes beyond the caller's object. The API is unchanged, but the ABI is not; pimpl, versioned symbols or recompiling everything avoid it.

What if a move constructor is not noexcept?What if

std::vector must keep its strong exception guarantee when it reallocates, so it copies elements instead of moving them if the move could throw. A vector of frames then deep-copies every pixel buffer on growth. Mark move operations noexcept (the defaulted ones are, if all members' moves are).

Why may the compiler delete a null check after a dereference?Why

Dereferencing a null pointer is undefined behaviour, so the compiler may assume it never happens: after p->x it concludes p is not null and removes a later if (p == nullptr) as dead code. Undefined behaviour is not "whatever the hardware does" but a promise the optimiser builds on. Sanitizers and static analysis find such code.

What if a lambda captures a local by reference and is stored for later?What if

The closure object holds a reference to a stack variable that is destroyed when the function returns; calling the lambda later reads a dangling reference. Capture by value or move the needed objects into the closure ([buf = std::move(buf)]), especially for callbacks and tasks submitted to other threads.

Why can a std::shared_ptr copy in a hot loop be slow even on one thread?Why

Every copy and destruction atomically increments and decrements the reference count in the control block. Atomic read-modify-write operations cost far more than plain increments and, if other threads touch the same pointer, cause cache-line ping-pong. Pass const shared_ptr& or a raw reference when ownership does not change.

What if two counters updated by different threads sit next to each other in a struct?What if

They share a 64-byte cache line, so each write invalidates the line in the other core's cache and the threads serialise on coherence traffic even though they never touch the same variable: false sharing. Align each hot per-thread variable to its own cache line (alignas(64), or the standard constant for the destructive interference size).

Why does an array of structs often run slower than a struct of arrays in image code?Why

A loop that only needs one field still drags every other field of each element through the cache, wasting bandwidth, and interleaved fields are harder to vectorise. Storing each field contiguously lets the loop stream exactly the data it needs and map directly onto SIMD lanes, which is why planar image layouts suit per-channel processing.

What if exceptions are disabled in an embedded project?What if

Code that relies on them (the standard library's allocation failures, at(), many third-party libraries) terminates instead of reporting errors, so errors must travel as return values: error codes, std::optional or std::expected in C++23. Failure paths become explicit and analysable, which is why safety guidelines often prefer it, at the cost of more verbose code.

Why can a template-heavy design increase code size on a microcontroller?Why

Every distinct set of template arguments instantiates a separate copy of the code, so a generic container used with ten types exists ten times in flash. Techniques to contain it: a type-erased core with thin typed wrappers, explicit instantiation in one translation unit, and checking the map file and -Os builds before committing to a design.

The terms of the chapter in one or two lines each, alphabetically.

ABI
Application binary interface: mangling, layout, vtables, calling convention and unwinding that let separately compiled code interoperate.
Abstract machine
The idealised machine the C++ standard specifies; real code only has to reproduce its observable behaviour.
Aggregate
A class or array without user constructors or private members, initialisable with braces member by member.
Aliasing
Two names referring to the same storage; limits what the optimiser may assume.
Alignment
The address multiple an object of a type must start at (alignof).
AoS / SoA
Array of structs / struct of arrays: grouping data by element or by field.
As-if rule
The compiler may transform the program arbitrarily as long as observable behaviour is unchanged.
AUTOSAR C++14
2017 AUTOSAR coding guidelines for C++14 in safety-related systems; superseded by MISRA C++:2023.
Awaiter
Object with await_ready/await_suspend/await_resume that defines what co_await does.
BMI
Binary module interface: the compiled form of a C++20 module interface.
Cache line
Unit of transfer between memory and caches, usually 64 bytes.
Closure
The object created by a lambda expression; its members are the captures.
Concept
Named compile-time predicate constraining template arguments (C++20).
consteval / constexpr / constinit
Must run at compile time / may run at compile time / static initialisation guaranteed at compile time.
Contract (C++26)
Preconditions, postconditions and assertions declared with pre, post, contract_assert.
Control block
Heap structure of shared_ptr holding the strong/weak counts, deleter and allocator.
Copy elision / RVO / NRVO
Constructing a return value directly in the caller's storage; guaranteed for prvalues since C++17, optional for named locals.
Coroutine frame
Usually heap-allocated block holding a coroutine's parameters, surviving locals, promise and resume point.
CRTP
Curiously recurring template pattern: class D : Base<D>, for static polymorphism.
CTAD
Class template argument deduction from constructor arguments (C++17).
Devirtualisation
Compiler replacing a virtual call by a direct one when the dynamic type is known.
Erroneous behaviour
C++26 category: a well-defined but incorrect outcome (e.g. reading an uninitialised variable) that tools may diagnose.
extern "C"
C language linkage: no mangling, C calling convention.
False sharing
Performance loss when independent data written by different cores shares a cache line.
Forwarding reference
T&& with deduced T; binds to lvalues and rvalues alike.
Freestanding
C++ implementation without a hosted OS, guaranteeing only a minimal library.
Full-expression
An expression that is not part of a larger one; temporaries die at its end.
glvalue / rvalue
Expressions with identity (lvalue or xvalue) / expressions that can be moved from (prvalue or xvalue).
Implementation-defined
Behaviour chosen and documented by the compiler, such as sizeof(int).
Instantiation
Generating a concrete function or class from a template for given arguments.
Itanium C++ ABI
The C++ ABI used by GCC and Clang on Linux, QNX and most non-Windows systems.
Landing pad
Compiler-generated code the unwinder jumps to in order to run destructors or a catch block.
Lifetime
The period from completed construction to the start of destruction during which an object may be used.
Lifetime extension
A temporary bound directly to a local reference lives as long as the reference.
LSDA
Language-specific data area: per-function tables describing cleanups and handlers for unwinding.
lvalue
Expression with identity that is not implicitly movable, such as a named variable.
Mangling
Encoding of namespaces, classes and parameter types into linker symbol names.
mdspan
C++23 non-owning multidimensional view with configurable layout and strides.
MISRA C++:2023
Guidelines for C++17 in critical systems; 179 guidelines; successor to MISRA C++:2008 and AUTOSAR C++14.
Module
C++20 unit of code with explicit exports, imported instead of textually included.
Move semantics
Transferring resources from an expiring object instead of copying them.
noexcept
Promise that a function does not throw; violating it calls std::terminate.
ODR
One-definition rule: each entity must have exactly one (identical) definition across the program.
Padding
Unused bytes the compiler inserts to keep members and arrays aligned.
Pimpl
"Pointer to implementation": hides a class's data behind a pointer to keep its ABI stable.
Placement new
Constructing an object in already-allocated storage: new (p) T(...).
PMR
Polymorphic memory resources (C++17): allocator chosen at run time via memory_resource.
prvalue
"Pure" rvalue: a value computation without identity, materialised into an object only when needed.
Promise type
Type nested in a coroutine's return type that customises its behaviour.
RAII
Resource acquisition is initialisation: resources owned by objects, released in destructors.
Reference collapsing
Rules combining references in templates: only && + && stays an rvalue reference.
Reflection (C++26)
Compile-time inspection of types and members, enabling generated serialisation and mappings.
Rule of zero / three / five
Write no special members, or all three (dtor, copy ctor, copy assign), or all five including moves.
RTTI
Run-time type information used by typeid, dynamic_cast and exception matching.
SFINAE
"Substitution failure is not an error": pre-C++20 technique for constraining templates.
Slicing
Copying a derived object into a base object, losing the derived part.
Small-buffer optimisation
Storing small payloads inside the object (SSO for strings, SBO for std::function) to avoid allocation.
span
C++20 non-owning view of a contiguous sequence: pointer plus length.
Standard-layout
Class with C-compatible layout rules, usable across a C boundary.
Storage duration
Automatic, static, thread or dynamic: how long the storage of an object exists.
Strict aliasing
Rule that an object may only be accessed through its own type or char/std::byte.
Subsumption
One constraint implying another; the more constrained overload wins.
Thunk
Small adapter function adjusting this for calls through a secondary base's vtable.
Trivially copyable
Type that can be copied with memcpy (no user copy/move/destructor).
Type erasure
Hiding a concrete type behind a uniform interface and an internal function table.
Undefined behaviour
Behaviour with no requirements; the optimiser assumes it never occurs.
Unspecified behaviour
One of several valid outcomes, not documented, such as argument evaluation order.
Value category
Classification of an expression as lvalue, xvalue or prvalue.
Variant
std::variant: type-safe tagged union of a fixed set of types.
Vectorisation
Compiler turning scalar loops into SIMD instructions processing several elements at once.
vptr / vtable
Hidden per-object pointer / per-class array of virtual function pointers.
xvalue
"Expiring" value: has identity and may be moved from, e.g. std::move(x).
