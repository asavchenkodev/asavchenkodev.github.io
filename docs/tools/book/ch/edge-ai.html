Edge AI: inference engines and performance optimisation

How a trained network becomes a fast, validated binary on an automotive SoC: inference graphs and model formats, the runtimes and compilers of NVIDIA, TI and Qualcomm, quantization and graph optimisation, zero-copy preprocessing, honest latency and power measurement, and the parity tests that prove the deployed model still sees what the trained one saw.

1The big picture: from a checkpoint to a binary in the car

A perception team finishes training a detector and has a PyTorch checkpoint that scores well on the validation set. Getting from there to a car takes a second project of similar size. The network must be frozen into a graph, translated for a specific accelerator, squeezed from 32-bit floats into 8-bit integers, fed with camera frames without copies, measured under heat and full load, and then shown to detect the same pedestrians as the original. Each of these steps can lose accuracy or milliseconds, and most of the painful surprises of a vision project happen here.

1.1Why inference is its own engineering discipline

Training and inference run the same mathematics but optimise for opposite things. Training runs on data-centre GPUs with hundreds of gigabytes of memory, processes large batches, keeps every intermediate activation for the backward pass and cares about throughput over days. Inference in a car processes one frame at a time from each camera, must finish within a fixed budget every 33 ms, runs on a chip with a few watts and a few gigabytes shared with the ISP, the GPU and the display, and has to behave the same way in a cold garage and under a windscreen in desert sun. A network that needs 40 ms per frame is not "a bit slow"; it simply does not fit the function.

The gap is closed by a chain of tools that most engineers only meet as black boxes: an exporter that turns Python code into a graph, a graph compiler that rewrites and fuses that graph, a quantizer that chooses integer scales, a code generator or kernel library for the target engine, and a runtime that schedules the result next to everything else on the SoC. Understanding what each one does is what lets you answer the questions that come up in every project: why did accuracy drop by three points at night, why is the network 30% slower on the target than in the vendor's benchmark, why did a new compiler release change the outputs, and is the model now good enough to ship.

Why it matters

Deployment decides whether a model can be used at all. A network chosen without checking the target's operator support or memory bandwidth may need retraining months later, and a quantized model that was only checked on overall mAP can lose exactly the rare scenes a safety case cares about. The cheapest point to think about deployment is before the architecture is frozen.

1.2The running example: one detector, three SoCs

The chapter follows one network through all steps. It is a single-stage, anchor-free detector of the YOLO family (Deep learning 7.4): a convolutional backbone with residual blocks and SiLU activations, a feature pyramid neck that upsamples and concatenates feature maps, and decoupled heads that predict class scores and box offsets at strides 8, 16 and 32. The front camera delivers 1920 × 1080 NV12 frames at 30 fps; the network runs on a 960 × 544 input. It has about 7 million parameters and needs roughly 10 GMAC per frame, typical of a front-camera or parking detector.

The same checkpoint goes to three targets that between them cover most automotive vision hardware. On an NVIDIA DRIVE Orin it is compiled by TensorRT for the Ampere GPU or one of the two deep-learning accelerators (DLA). On a TI TDA4VM (Jacinto 7) it is compiled by TIDL for the C7x DSP and its matrix multiply accelerator (MMA), 8 INT8 TOPS in total. On a Qualcomm Snapdragon Ride SoC it is compiled with the QNN SDK for the Hexagon NPU (the HTP backend). The front half of the path is shared; from the ONNX file onwards each vendor takes over.

Read the figure as a list of hand-overs, each with its own failure mode. Export can fail on Python constructs that have no graph equivalent. The vendor compiler can reject an operator or run it on the CPU. Calibration can choose ranges that work for daylight and clip at night. The runtime integration can add copies and format conversions that cost more than the network itself. The rest of the chapter takes them one at a time, and Chapter 11 walks the whole path again for each target with everything in place.

Numbers

For a detector of this size: about 28 MB of FP32 weights, 7 MB in INT8. At 30 fps, 10 GMAC per frame is 0.6 TOPS of useful work (counting a multiply-accumulate as two operations), which looks small next to an 8 TOPS NPU. In practice such a network takes 8–20 ms on a TDA4VM-class accelerator, because utilisation is far below peak (Section 4.2), plus preprocessing and post-processing around it.

2From training graph to inference graph

A PyTorch model is a Python program that happens to compute a network. An inference engine needs the opposite: a fixed description of the computation with no Python, no gradients and, ideally, no surprises in tensor shapes. Freezing the program into such a graph is the first hand-over, and the format chosen for it decides which tools can read it next.

2.1What changes when a network stops learning

Several parts of a training graph exist only to make learning work, and they change meaning or disappear at inference time. Batch normalisation uses statistics of the current batch during training; in evaluation mode it uses the running mean and variance collected during training, which makes it a fixed per-channel scale and shift that can be folded into the preceding convolution (Section 6.1). Dropout and stochastic depth become identities. Auxiliary heads, deep-supervision outputs and the loss are removed. Data augmentation is gone, and with it any random operation. What remains is a pure function from an input tensor to output tensors.

Two decisions belong to the inference graph and are often made too late. The first is the input contract: resolution, colour format (RGB or the camera's NV12), value range, normalisation and memory layout. Each of these must match what the preprocessing on the target will deliver, bit for bit if possible. The second is where the graph ends. A detector's raw outputs are thousands of score and offset maps; turning them into boxes requires decoding, a threshold, a top-k selection and non-maximum suppression. Some toolchains can run that inside the accelerator, most run part of it on the CPU, and the export must stop at a point that every target supports.

Pitfall

Exporting while the model is still in training mode. Batch normalisation then uses batch statistics of a single image, dropout stays active, and the exported graph gives plausible but wrong results that no compiler will complain about. Always call model.eval() and compare the exported graph's outputs with PyTorch's on real images before going further.

2.2Export: turning Python into a graph

There are two ways to get a graph out of Python. Tracing runs the model once on an example input and records every tensor operation that happens. It is simple and robust, but it only sees the path taken for that input: an if on a tensor value is frozen to the branch taken, a loop is unrolled to the number of iterations seen, and Python-side values such as a list length become constants. Capturing the program symbolically (TorchScript in the past, torch.export and the Dynamo-based ONNX exporter today) analyses the Python bytecode, records control flow where it can and fails loudly where it cannot. The Dynamo-based exporter (dynamo=True, available since PyTorch 2.5 and the default in recent releases) is the recommended path; the older tracing exporter still works and is what many vendor examples use.

import torch

model = build_detector(num_classes=8)
model.load_state_dict(torch.load("det_ep300.pt", map_location="cpu"))
model.eval()                                    # BN uses running stats, dropout off
model.head.export_raw = True                    # stop before decode/NMS: every target supports this

x = torch.randn(1, 3, 544, 960)                 # fixed input shape: batch 1, 960 x 544
torch.onnx.export(model, (x,), "det.onnx",
                  input_names=["images"], output_names=["scores", "boxes"],
                  opset_version=17,             # the vendor compiler decides which opsets it accepts
                  dynamo=True)                  # torch.export-based exporter (PyTorch 2.5+)

# first parity check: the same input through PyTorch and ONNX Runtime
import onnxruntime as ort, numpy as np
sess = ort.InferenceSession("det.onnx", providers=["CPUExecutionProvider"])
ref = [t.detach().numpy() for t in model(x)]
out = sess.run(None, {"images": x.numpy()})
print([float(np.abs(a - b).max()) for a, b in zip(ref, out)])   # expect ~1e-5, not 1e-1

Fixed shapes are a deliberate choice. Most automotive accelerators compile a network for one input size; dynamic dimensions either are not supported or make the compiler fall back to conservative memory plans and slower kernels. If several resolutions are needed, compile several engines. A dynamic batch dimension is useful on a GPU serving several cameras, but even TensorRT asks for minimum, optimum and maximum shapes and optimises for the optimum.

The operators that cause trouble are predictable. Data-dependent shapes (NonZero, boolean masking, a variable number of boxes after NMS), GridSample as used by BEV lifting and deformable attention, unusual Resize modes, 5-D tensors, Einsum, scatter and gather with computed indices, and 64-bit integer arithmetic on shapes are the usual suspects. Some are not exported at all; more often they export fine and then fail in the vendor compiler or silently run on the CPU.

In practice

Run a "deployability check" in the first week of a new architecture: export a randomly initialised model, compile it with every target toolchain, and look at the placement report (which layers went to the accelerator) and the measured latency. A randomly initialised network has the same operators, shapes and speed as the trained one. The check takes a day; finding an unsupported operator after three months of training costs a retraining cycle.

2.3ONNX: the hand-over format

ONNX (Open Neural Network Exchange) is a vendor-neutral file format for computation graphs, defined as a protobuf schema. A model is a graph of nodes, each naming an operator type such as Conv or Resize with attributes; initializers holding the constant weights; and typed, shaped inputs and outputs. Every operator is defined in a versioned opset: Resize in opset 11 behaves differently from opset 10, and a compiler states which opsets it accepts. Quantized models are expressed either with explicit QuantizeLinear/DequantizeLinear pairs around float operators (the QDQ form, Section 5.6) or with integer operators such as QLinearConv.

ONNX is the de facto interchange point in automotive deployment because all three vendors of the running example import it, and because ONNX Runtime gives a reference implementation on a PC. That makes the ONNX file the natural place for the first quality gate: if the ONNX model in ONNX Runtime matches PyTorch, every later difference belongs to the vendor tool, the quantization or the integration.

Two tools are worth knowing by name. Netron displays an ONNX file as a graph and is the quickest way to see what the exporter really produced. onnx-simplifier (and the shape-inference pass in the onnx package) folds constant subgraphs, removes the shape arithmetic exporters love to emit, and often turns an unsupported pattern into a supported one before the vendor tool sees it.

Interesting detail

Exporters write shape calculations into the graph: Shape → Gather → Unsqueeze → Concat → Reshape chains that compute a reshape target at run time. With a fixed input size all of them are constants. Many "unsupported operator" errors on NPUs disappear after simplification because the offending Gather or Shape node was only ever computing the number 68.

2.4TFLite and the vendor formats

ONNX describes what to compute. The file that finally runs on the target describes how: which kernel implements each layer, where each tensor lives in memory, in which order layers execute and with which precomputed integer scales. That file is specific to a chip, a toolchain version and often an SDK release, which is the most important practical fact about it.

3Inference runtimes and graph compilers

Every vendor ships its own inference stack, and their manuals use different vocabularies, but they all do the same five jobs: read the graph, rewrite it, decide which engine runs which part, pick or generate an implementation for every operation, and plan memory. Once you see those jobs, TensorRT, TIDL and QNN look like dialects of one language.

3.1What every inference compiler does

The front end parses ONNX or TFLite into the tool's internal representation and checks that every operator is known. Graph optimisation then rewrites the graph without changing its mathematics: constant folding, removal of no-ops, folding batch normalisation into convolutions, fusing activations and element-wise operations into the preceding layer, and choosing a memory layout (Chapter 6). Partitioning assigns each node to an engine: the accelerator if it supports the operator with these parameters, otherwise a fallback such as the GPU or the CPU. Quantization, if requested, chooses integer scales from calibration data or reads them from a QAT model (Chapter 5).

Lowering turns each remaining operation into something the hardware executes. On a GPU this means choosing among many pre-written kernels (TensorRT times each candidate on the real device and keeps the fastest, a process it calls tactic selection). On an NPU it means mapping convolutions onto the MAC array, splitting feature maps into tiles that fit the on-chip SRAM and scheduling DMA transfers to overlap with compute. Finally, memory planning computes the lifetime of every intermediate tensor and packs them into a few buffers that are reused, so a network with 200 intermediate tensors needs only the memory of the few that are alive at the same time. The result is serialized into the engine or artefact file of Section 2.4.

The split between build time and run time matters for an embedded system. All of the above should happen once, offline or at the first start, and the result should be cached. At run time the engine is deserialized, buffers are bound, and each inference only submits pre-planned work. A runtime that re-optimises the graph at every start (ONNX Runtime does this by default, QNN without a context binary does it too) costs seconds of boot time, which a camera function that must be ready a few seconds after ignition cannot afford.

3.2ONNX Runtime and execution providers

ONNX Runtime (ORT) is Microsoft's open-source inference engine for ONNX. It has its own graph optimiser and CPU kernels, and it delegates subgraphs to execution providers (EPs): CUDA and TensorRT for NVIDIA GPUs, OpenVINO for Intel, QNN for Qualcomm, and TIDL for TI (TI's open-source edge AI tools ship ORT with a TIDL provider). The partitioner walks the graph, asks each provider in priority order which nodes it can take, and forms the largest supported subgraphs; whatever is left runs on ORT's CPU kernels.

That makes ORT both a convenient reference and a convenient deployment wrapper. On a PC it is the reference implementation for parity tests. On a target it gives one API across vendors, at the price of an extra layer and of partitions that you must check: a graph cut into seven pieces with CPU nodes between them can be several times slower than the same graph compiled in one piece. ORT reports the partitioning in its verbose log, and the TIDL and QNN flows print which layers went to the accelerator.

ORT's own graph optimiser has three levels, and what it does on the running example is real and instructive. On a small detector graph exported in training form (90 nodes: 23 convolutions, 19 batch norms, SiLU written as Sigmoid and Mul), the "basic" level folds all 19 batch norms into the convolution weights (71 nodes), and the "extended" level fuses each Sigmoid–Mul pair into one SiLU kernel and two convolution–activation pairs into fused convolutions (50 nodes). On four x86 cores the optimised FP32 graph runs in 10.3 ms against 22.0 ms unoptimised, the same arithmetic in half the time (the experiment is in tools/write/edge-ai/experiments/tinydet.py).

Interesting detail

ORT fuses SiLU into an operator it calls QuickGelu: the "quick" GELU approximation is \(x \cdot \sigma(1.702\,x)\), and with the constant set to 1 it is exactly SiLU, \(x \cdot \sigma(x)\). Fusion passes match patterns, not names, and one fused kernel often serves several activation functions.

3.3TensorRT

TensorRT is NVIDIA's inference compiler and runtime for its GPUs and, on Orin and Xavier, for the DLA. The builder parses ONNX, applies graph optimisations (folding, horizontal and vertical fusion, Q/DQ propagation), chooses precision per layer within what you allow (FP32, TF32, FP16, BF16, INT8, FP8 on newer GPUs), and then times candidate kernels for every fused layer on the actual GPU. The chosen kernels, the memory plan and the weights in their final layout are serialized into an engine. The runtime deserializes the engine, creates execution contexts (each with its own activation memory) and enqueues inferences on CUDA streams.

Three consequences follow from timing-based kernel selection. Building is slow, from tens of seconds to many minutes, so engines are built offline and cached. The engine is tied to the exact GPU and TensorRT version, and since timings vary slightly, two builds of the same ONNX file can choose different kernels and give results that differ in the last bits; a timing cache makes rebuilds reproducible. And reported layer timings refer to fused layers, so a profile shows names like conv12 + bn12 + silu12 + add3 rather than the ONNX nodes you know.

On Orin the DLA is a fixed-function convolution engine that supports FP16 and INT8 and a limited set of layers. TensorRT can build an engine for a DLA core with GPU fallback for the layers it cannot run. Each fallback is a transition between engines through memory, so a network that is 90% DLA-compatible may still be faster entirely on the GPU; the value of the DLA lies in freeing the GPU and in better performance per watt, not in raw speed.

INT8 in TensorRT historically worked by implicit quantization: you provide a calibrator with images, TensorRT computes activation ranges with an entropy method and picks INT8 kernels where they are faster. Since TensorRT 10 this path is deprecated in favour of explicit quantization: the ONNX file carries Q/DQ nodes, produced by QAT or by a PTQ tool such as NVIDIA's Model Optimizer, and TensorRT fuses them into integer kernels. The explicit form is better for deployment because the scales are part of the versioned model rather than a side effect of a build.

# build an FP16 engine on the target and save it; then benchmark it
trtexec --onnx=det.onnx --fp16 --saveEngine=det_fp16.engine \
        --timingCacheFile=det.cache --profilingVerbosity=detailed
trtexec --loadEngine=det_fp16.engine --useCudaGraph --noDataTransfers \
        --warmUp=2000 --duration=30 --percentile=99,99.9 \
        --dumpProfile --separateProfileRun --exportLayerInfo=layers.json
# the same network on DLA core 0, with GPU fallback for unsupported layers
trtexec --onnx=det_qdq.onnx --int8 --fp16 --useDLACore=0 --allowGPUFallback --saveEngine=det_dla.engine
Pitfall

Building the engine on a desktop RTX card and copying it to Orin. It will not load (different GPU architecture), and an engine built on a different TensorRT minor version may not either. Build on the target or on a matching cross-build setup with the same TensorRT release; containers on the build machine must match the target's JetPack or DriveOS version (Build and containers 10.3).

3.4TI TIDL

TIDL (TI Deep Learning) is the inference stack for the C7x DSP and MMA on Jacinto 7 and the AM6xA family. The front end is an import step that reads ONNX, TFLite or Caffe models, merges layers (batch norm into convolution, activations and element-wise operations into the producing layer), quantizes with calibration images and writes two binaries: the network, and a description of its input and output buffers. TI's open-source edgeai-tidl-tools wrap this in ONNX Runtime and TFLite: during a compile step the runtime partitions the graph, sends supported subgraphs to the TIDL importer, and at run time executes them on the C7x/MMA while unsupported nodes run on the Arm Cortex-A72.

Quantization is part of import, not a separate tool. You choose 8- or 16-bit tensors, the number of calibration images and iterations, and options such as per-channel weights and "advanced" bias calibration, which nudges biases so that the mean output of each quantized layer matches the float one on the calibration set. Mixed precision is set per layer: sensitive layers can be kept at 16 bits by name, at a cost in speed and memory. TIDL also has a host emulation mode that runs the quantized network on a PC with the same integer arithmetic, and TI designs it to match the target bit for bit, so most quantization debugging happens on a workstation.

Two TI-specific details shape the running example. The MMA multiplies a 64-element vector by a 64 × 64 weight block per cycle (Embedded compute 12.8), so channel counts that are multiples of 64 use it fully and a 48-channel layer wastes a quarter of it. And the detection post-processing can run inside TIDL: for supported detector families a "meta-architecture" description tells the importer how to decode boxes and run NMS on the C7x, which removes a costly hop to the Arm cores.

Numbers

TDA4VM: one C7x at 1 GHz with an MMA of 4096 INT8 MACs per cycle, 8 TOPS peak; 8 MB of on-chip MSMC SRAM shared with other cores; a single 32-bit LPDDR4 interface of roughly 15 GB/s shared by the ISP, GPU, display and the CPUs. With that bandwidth, a network that streams 100 MB of feature maps per frame through DDR is limited to about 150 fps before any compute, which is why on-chip reuse matters more than TOPS on this class of chip.

3.5Qualcomm QNN and SNPE

Qualcomm's inference stack has two generations that coexist in its current SDK (the Qualcomm AI Runtime, QAIRT). SNPE, the older Snapdragon Neural Processing Engine, converts models to a .dlc container and runs them on CPU, GPU or the Hexagon DSP through one API. QNN (Qualcomm AI Engine Direct) is the lower-level successor: a converter turns ONNX into a QNN graph (as C++ source and weights, compiled to a model library, or as a DLC), and the graph is executed by a backend library: CPU, GPU, or HTP, the Hexagon Tensor Processor that combines scalar cores, wide vector units (HVX), a matrix unit (HMX) and a tightly coupled on-chip memory (VTCM).

For the HTP the graph must be "prepared": tiled for VTCM, mapped onto HVX and HMX operations and scheduled. Doing this at every start takes seconds, so production flows prepare offline and store a context binary, which the runtime loads directly. Quantization uses a list of calibration inputs during conversion, or imports encodings computed elsewhere; Qualcomm's open-source AIMET toolkit provides cross-layer equalisation, AdaRound and QAT and exports exactly such encodings. The HTP is strong with 8-bit weights and 16-bit activations (often written A16W8), which is the usual first fix when 8-bit activations lose too much accuracy; newer HTP generations also run FP16.

# convert and quantize with calibration inputs (a text file listing raw input tensors)
qnn-onnx-converter --input_network det.onnx --input_list calib_list.txt \
                   --act_bw 8 --weight_bw 8 --output_path det.cpp
qnn-model-lib-generator -c det.cpp -b det.bin -o model_libs          # build libdet.so per target
# prepare offline for the HTP and serialize: the target then loads in milliseconds
qnn-context-binary-generator --model model_libs/aarch64-oe-linux-gcc11.2/libdet.so \
                   --backend libQnnHtp.so --binary_file det_htp.bin
qnn-net-run --retrieve_context det_htp.bin --backend libQnnHtp.so \
            --input_list test_list.txt --profiling_level detailed

Tool names and flags change between QAIRT releases; the sequence (convert, quantize, build the model, prepare a context binary, run with profiling) is stable.

3.6OpenVINO, TVM and LiteRT

Three more names come up in discussions. OpenVINO is Intel's toolkit: it converts models to its IR, quantizes them with its NNCF library and runs them on Intel CPUs, GPUs and NPUs. It rarely runs inside a car, but it is common on the x86 machines of simulation and validation farms, and it is a good example of a mature PTQ and QAT toolchain. Apache TVM is an open-source deep-learning compiler: instead of a fixed kernel library it generates code for each operator and searches automatically for fast schedules (tiling, loop order, vectorisation) by measuring on the target. Several NPU vendors have used TVM or its ideas inside their toolchains, and it is the standard reference for how a graph compiler is built. LiteRT, formerly TensorFlow Lite, is Google's runtime for .tflite models with delegates that hand subgraphs to accelerators, the same partitioning idea as ORT's execution providers.

3.7Choosing and living with a vendor toolchain

In practice the SoC decides the toolchain, so the real choices are how to use it and how to keep it replaceable. A few rules have proven themselves. Keep ONNX as the boundary and keep every model change upstream of it, so a second SoC or a new SDK only repeats the vendor half. Pin the toolchain version per release and treat an SDK update as a model change that reruns the full parity and performance suite. Read the operator support tables before training, including the parameter limits (kernel sizes, strides, dilation, channel counts, maximum tensor sizes), because "supports Conv" rarely means every convolution. And keep a small set of reference networks per target whose latency and outputs are tracked across SDK releases, so a regression in the tool is distinguishable from a regression in the model.

Talk track

"Every inference stack does the same five things: parse, optimise the graph, partition across engines, lower to kernels and plan memory. TensorRT picks kernels by timing them on the GPU, TIDL maps layers onto the C7x and MMA with quantization built into import, and QNN prepares a context binary for the Hexagon NPU. Our process is vendor-neutral up to ONNX and version-pinned after it."

4Hardware targets from the deployment point of view

The embedded compute chapter explains how CPUs, GPUs, DSPs and NPUs are built. The deployment engineer needs a narrower and more practical picture: which operations an engine runs well, where its data has to live, and what it costs to move work and data between engines. Those three facts predict most of the latency surprises of a port.

4.1What you need to know about each engine

The CPU runs everything, slowly. With NEON and multithreading an Arm Cortex-A cluster reaches tens to a few hundred GOPS on convolutions, two orders of magnitude below an NPU, but it is the universal fallback and it runs the code around the network: preprocessing glue, decoding, NMS, tracking. The GPU is flexible and fast in FP16; it runs unusual operators through CUDA or OpenCL kernels, but it is shared with rendering and its preemption is coarse (Concurrency 9.4). The NPU (DLA, MMA, HTP) is a fixed dataflow engine for convolutions and matrix multiplications in INT8 or INT16, very efficient for the operators and shapes it was designed for and unable to run anything else. DSPs such as the C7x and Hexagon's vector units are programmable and handle the layers the matrix engine cannot. Fixed-function blocks for scaling, lens-distortion correction and colour conversion sit next to them and matter for preprocessing (Chapter 7).

For each engine the deployment questions are the same. Which operators, with which parameters and data types, does it support? How much on-chip memory does it have, and does the compiler keep intermediate results there? What memory layout does it want: NCHW, NHWC or a blocked layout such as channels in groups of 32 or 64? How long does it take to hand a tensor to another engine, and can that be done without a copy? Can two networks share it, and with what preemption granularity? The answers are in the vendor documentation, but they are only reliable after you measure your own network.

4.2Compute-bound or memory-bound: the detector on a roofline

Whether a layer is limited by the MAC array or by memory depends on its arithmetic intensity: operations performed per byte moved. The roofline model turns this into a picture (Embedded compute 11.5). Attainable performance is the minimum of the peak compute rate and intensity × memory bandwidth; layers to the left of the ridge point wait for memory, layers to the right keep the MACs busy.

The figure explains several things people find puzzling. A 3 × 3 convolution with 256 channels on a small feature map does about 700 operations per byte and can use the full 8 TOPS. The same kind of layer early in the network, with 32 channels on a large map, does about 290 and is already limited by DDR. A 1 × 1 convolution does nine times less work per byte than a 3 × 3 one; a depthwise convolution does about 9 operations per byte; a residual add or an unfused activation does less than one. Resize and concatenation do no arithmetic at all; they are pure data movement. On a chip whose ridge point lies above 500 operations per byte, most of a detector is memory-bound if every tensor goes through DDR.

Two conclusions follow, and they shape the rest of the chapter. First, the compiler's main job on an NPU is to avoid DDR traffic: fuse element-wise layers into their producers (Section 6.2), keep tiles of feature maps in on-chip SRAM across several layers (Section 6.3), and reuse weights. Second, operators that are cheap in FLOPs, such as depthwise convolutions, are not necessarily cheap in time. MobileNet-style networks that look efficient on paper often run no faster than plain convolutions on an NPU, because they trade compute, which the NPU has plenty of, for memory traffic, which it does not.

Numbers

Ridge point = peak ops / bandwidth. For 8 TOPS and 15 GB/s it is about 530 operations per byte; for the GPU of a Jetson AGX Orin (about 85 dense INT8 TOPS, 205 GB/s of LPDDR5) it is around 400. Arithmetic intensity of a K × K convolution with C input and output channels, ignoring weights, is about \(K^2 C\) operations per byte in INT8 (two operations per MAC, each output byte written once and each input byte read once): 9·64 ≈ 580 for a 3 × 3, 64-channel layer.

4.3Partitioning and the cost of a fallback

When the compiler meets an operator the accelerator cannot run, it cuts the graph. The supported part before the cut runs on the accelerator, its output is written to DRAM (and possibly converted from the accelerator's internal layout and integer format to float), the unsupported operator runs on the CPU or GPU, and the result is converted back and handed to a second accelerator subgraph. Each cut adds a synchronisation, two layout conversions and two passes through memory, and the CPU kernel itself is often slow because it runs a large feature map on a few cores.

The fix is almost never to optimise the CPU kernel. It is to replace the operator with a supported equivalent before export (an approximation of a rare activation, a different upsampling mode, a reshape that avoids 5-D tensors), to move it to the end of the graph where it can join the post-processing, or to implement it as a custom layer on the accelerator's programmable part (TensorRT plugins, TIDL custom layers on the C7x, QNN op packages for the HTP). Read the placement report of every compile: a single line that says a layer runs on the CPU explains more latency than any profile.

Pitfall

Comparing platforms with the vendor's benchmark numbers for a "similar" model. The vendor model has been adapted to the hardware; yours may contain one operator that splits the graph. Ask for, or run, your own network or a close proxy, compiled with the shipped toolchain, at your resolution, with the placement report.

5Quantization in practice

Quantization replaces 32-bit floating-point numbers by 8-bit integers plus a scale. It makes networks about four times smaller, cuts memory traffic by the same factor and lets the NPU use integer MAC arrays that are many times cheaper in silicon and energy. The arithmetic is simple (Mathematics 11); the engineering lies in choosing the scales, finding the layers that cannot take it, and proving that nothing important was lost.

5.1The integer pipeline inside an INT8 layer

An affine quantizer maps a real value \(x\) to an integer \(q\) with a scale \(s\) and a zero point \(z\):

\[ q = \mathrm{clamp}\!\left(\mathrm{round}\!\left(\frac{x}{s}\right) + z,\; q_{\min},\, q_{\max}\right), \qquad \hat{x} = s\,(q - z). \]

The interesting part is what happens inside a quantized convolution, because it shows why integer inference is fast and where the errors come from. Weights are stored as INT8 with one scale per output channel and zero point 0; activations as UINT8 or INT8 with one scale per tensor. The layer multiplies 8-bit integers and accumulates the products in a 32-bit integer, which cannot overflow for realistic layer sizes. The bias is pre-converted to INT32 with scale \(s_x s_w\) so it can be added to the accumulator directly. Then the accumulator, whose real value is \(s_x s_w \cdot \mathrm{acc}\), is requantized to the output scale \(s_y\): multiplied by \(M = s_x s_w / s_y\), shifted, offset by the output zero point and clamped. Since \(M\) is a real number below 1, hardware stores it as a fixed-point multiplier and a right shift, and some engines restrict it to a power of two so that requantization is a plain shift.

Several practical facts follow from this pipeline. A fused ReLU costs nothing: it is the lower clamp at the zero point. A residual addition of two tensors with different scales needs both inputs rescaled to a common scale first, which adds a rounding step and is why compilers like to fuse the add into the convolution's requantization. A concatenation of tensors with different scales forces one shared output scale, so the branch with the smaller range loses resolution. And the sum over \(K^2 C\) products is exact; integer inference does not accumulate rounding error inside a layer the way people sometimes fear. The error is introduced at the boundaries, where values are rounded to the 8-bit grid.

Interesting detail

An INT8 multiplier needs roughly a tenth to a twentieth of the silicon area and energy of an FP32 multiplier, and the energy of fetching a byte from DRAM is two to three orders of magnitude larger than that of an 8-bit multiply-add. This is why NPUs are integer machines, and why the 4× smaller tensors matter more than the cheaper arithmetic.

5.2Range, step and the quantization error

For a fixed number of levels the quantizer has one free choice per tensor: the range it covers. A wider range covers rare large values but makes each step coarser, so every ordinary value is rounded more crudely (rounding error, at most half a step). A narrower range gives fine steps for the bulk of the values but saturates everything outside it (clipping error, which can be large for each clipped value). The best range balances the two, and where it lies depends on the shape of the distribution's tail.

The figure below quantizes one million samples of a typical post-SiLU activation: mostly small values, a cut-off negative side, and rare large outliers such as a headlight region would produce. Move the clipping point and watch the error split between the two kinds. The signal-to-quantization-noise ratio (SQNR) is the power of the signal divided by the power of the error, in decibels; each 6 dB is roughly one bit of effective resolution.

With rare outliers and 8 bits, min/max calibration (clip at the maximum, about 31) gives a step of about 0.12 and an SQNR of about 25 dB, almost all of it rounding error. Pull the clip in to the 99.99th percentile (about 4.4) and the step becomes almost seven times finer, yet the SQNR falls to about 16 dB: the few clipped outliers carry so much signal power that their error dominates. The best clip lies around 23 and gains less than 1 dB over min/max. Now set 4 bits: min/max collapses to about 3.5 dB, because the step is so coarse that the bulk of the values falls into one or two levels, and the best clip moves all the way down to about 3.3 (almost 14 dB). With few levels, giving up the outliers becomes the right trade. Switch to "no outliers" and min/max is already within about 1 dB of the optimum at 8 bits. The lesson is that no fixed rule ("clip at the 99.9th percentile") is right for all tensors and bit widths, which is why calibrators search for the range per tensor, and that the metric matters: SQNR weights large values heavily, while a detector may care more about the bulk of small activations.

Pitfall

The outliers may be exactly the important signal. Clipping activations of a sun glare or a headlight to improve average error can blind the network to the object next to it. Range choices must be validated on the scenarios where extreme values occur, not only on average metrics.

5.3Per-tensor versus per-channel, symmetric versus asymmetric

Granularity is the choice of how many values share one scale. Per-tensor scales use one scale for a whole weight tensor; per-channel scales use one per output channel. After batch normalisation has been folded into the convolution (Section 6.1), the weights of different output channels are multiplied by different factors \(\gamma_c / \sqrt{\sigma_c^2 + \varepsilon}\), so their ranges can differ by one to two orders of magnitude. With a single scale set by the largest channel, the small channels use only a handful of integer levels.

A seeded experiment on a 3 × 3, 64-channel convolution with BN folded in shows the effect clearly (experiments/quant_error.py). The largest absolute weight per output channel ranges from 0.03 to 1.68, a factor of 56. Per-tensor INT8 gives an SQNR of 30.0 dB over the whole tensor, per-channel 42.3 dB. For the eight smallest channels the difference is dramatic: 12.0 dB per-tensor against 42.5 dB per-channel; the smallest channel is represented with just five distinct integer values. Per-channel weight scales cost almost nothing in hardware, since each output channel's accumulator is requantized separately anyway, and all three toolchains of the running example support them. Activations are almost always quantized per tensor, because a per-channel activation scale would have to be applied inside the accumulation.

Symmetric quantization uses zero point 0 and a range \([-a, a]\); it is the norm for weights, whose distributions are centred, and it makes the arithmetic simpler. Asymmetric quantization shifts the range with a zero point, which wastes no levels on activations that are mostly positive, such as the outputs of ReLU or SiLU. With a symmetric INT8 grid, a ReLU output uses only the 128 non-negative levels, one bit lost. Some NPUs only support symmetric quantization, or power-of-two scales, and the toolchains compensate as far as they can; this is one of the target constraints a QAT setup must reproduce (Section 5.6).

Why it matters

Depthwise convolutions are the extreme case: each output channel has only nine weights, and their ranges vary wildly between channels. Per-tensor quantization of depthwise weights was the reason early MobileNets lost tens of points of accuracy in INT8. If an accuracy drop is concentrated in a network with depthwise layers, check the weight granularity first.

5.4Calibration methods and calibration data

Post-training quantization (PTQ) chooses activation ranges by running the float model on a calibration set and observing the values of every tensor. Weight ranges come directly from the weights. The calibrators differ in how they turn the observed values into a range. Min/max takes the extremes, which is robust for well-behaved tensors and wasteful for long tails. Percentile clips at, for example, the 99.99th percentile, which ignores rare outliers, with the risk shown in Figure 5.2. Entropy (the KL-divergence method TensorRT made popular) chooses the range whose quantized histogram loses the least information relative to the float histogram. MSE chooses the range with the smallest mean squared error, which is exactly the optimum in the figure. Modern tools combine them per tensor, and some optimise ranges for the error of the layer output rather than of the tensor itself.

The calibration set matters more than the method. A few hundred images are usually enough to estimate ranges, but they must cover the conditions where the network will be used: night, rain, low sun, tunnels, snow, every camera of the vehicle, both the production ISP tuning and the sensor variants. A calibration set of daytime highway frames produces ranges that clip at night and in glare. Treat the calibration set like training data: versioned, traceable and reviewed, because it is an input of the released model (Deep learning 14.2).

In practice

Use images processed exactly as they will be on the target: the same ISP output format, the same resize filter and normalisation. Calibrating with PNG files processed by OpenCV while the car feeds NV12 through a hardware scaler shifts the activation statistics before quantization even starts.

5.5Which layers hurt, and mixed precision

Quantization error is not spread evenly. A few kinds of layers cause most of it, and knowing them saves days. The last layers that regress box coordinates, depth or keypoints need fine resolution in their outputs; an error of half a step in an offset map is a pixel of box position. Score outputs through a sigmoid are compressed near 0 and 1, where the decision threshold often sits. Concatenations and additions of branches with different ranges force a shared scale. Depthwise convolutions suffer from per-tensor weights (Section 5.3). Attention, softmax and layer normalisation in transformer parts have large dynamic ranges and outlier channels. The first convolution is usually harmless in practice because its input is already 8-bit image data, but its output range can be very wide.

A sensitivity analysis finds these layers on your network. Quantize the whole model, then for each layer in turn keep only that layer in float (or quantize only that layer) and measure the task metric or the output SQNR on a validation subset. Sorting the layers by the improvement gives a short list of culprits. Mixed precision then keeps those layers at 16 bits: INT16 activations on TIDL and the Hexagon HTP (A16W8), FP16 on a GPU. A handful of 16-bit layers typically recovers most of the loss for a few percent of extra latency, because the sensitive layers are usually small ones at the end of the network.

Numbers

Typical outcomes for CNN detectors: PTQ with per-channel weights loses 0.5–2 mAP points; with a few 16-bit layers often below 0.5. Small networks, regression-heavy outputs (depth, 3D boxes) and transformer blocks lose more. FP16 on a GPU is usually indistinguishable from FP32 for CNNs. These are starting expectations, not acceptance criteria; the acceptance criteria are per scenario (Chapter 10).

5.6Better PTQ and quantization-aware training

Before retraining, several PTQ refinements are worth trying. Cross-layer equalisation rescales the channels of two consecutive layers in opposite directions (exact for ReLU and linear layers) so that their weight ranges become similar, which helps per-tensor targets. Bias correction shifts each layer's bias to cancel the mean error that quantization introduces in its output. AdaRound decides per weight whether to round up or down by minimising the layer's output error on calibration data, instead of rounding to nearest. These are available in AIMET, NVIDIA's Model Optimizer, OpenVINO's NNCF, and partly in the vendor importers themselves.

Quantization-aware training (QAT) goes further: it inserts fake-quantization operations into the training graph, which quantize and immediately dequantize tensors so that the forward pass sees the rounding and clipping of the target, and then fine-tunes the network for a few epochs. Rounding has zero gradient almost everywhere, so the backward pass uses the straight-through estimator: it treats the quantizer as the identity inside the range and as zero outside, which lets the weights move to positions that survive rounding. Ranges are either observed during training or learned as parameters. The result is exported as ONNX with explicit QuantizeLinear/DequantizeLinear pairs, the QDQ form, and the deployment tool must use exactly those scales.

QAT only helps if the fake quantization matches what the target will do: the same granularity, symmetric or asymmetric, the same placement of quantizers around fused operations (after conv+add+activation, not after each of them), the same treatment of concatenations, and power-of-two scales if the hardware requires them. A QAT model trained with per-channel asymmetric quantizers and deployed on a target that rounds the scales to powers of two loses most of what QAT gained. This is why vendors provide QAT recipes or toolkits matched to their compilers, and why explicit Q/DQ deployment, where the compiler must honour the given scales or refuse, is preferable to a compiler that silently recalibrates.

Talk track

"We start with post-training quantization: per-channel weights, a calibration set that covers the whole ODD, and a sensitivity analysis that keeps the few critical layers in 16 bits. If that loses more than our budget in any scenario, we fine-tune with quantization-aware training that mimics the target's exact arithmetic and deploy the explicit scales."

5.7FP16, BF16, FP8 and 4-bit formats

Floating-point formats with fewer bits are the alternative where the hardware supports them. FP16 (5 exponent bits, 10 mantissa bits) is the default on GPUs: for CNNs it is usually lossless, but its maximum value of 65504 can overflow in large activations or in sums inside normalisation layers. BF16 keeps FP32's 8 exponent bits with only 7 mantissa bits, trading precision for range; it is the training format of choice and is supported by newer inference hardware. FP8 (E4M3 or E5M2) is used on recent NVIDIA GPUs, including the Blackwell-based DRIVE Thor, and behaves like INT8 with a built-in logarithmic grid, which suits tensors with outliers. INT4 and FP4 are mostly used for weights of large language and vision-language models, where memory bandwidth for weights dominates; for CNN activations they are still a research topic. Each format has to be supported end to end by the engine you deploy on, and the TOPS figures of datasheets are quoted for the most favourable one.

6Making the graph cheaper: fusion, graph optimisation, pruning and distillation

Quantization changes the numbers; the techniques in this chapter change the graph. Some of them are free and automatic: the compiler rewrites the graph into a mathematically equivalent but cheaper one. Others, such as pruning and distillation, change the model and need retraining. Knowing which is which helps to set expectations: fusion saves what the export wasted, while real reductions in work come from the model itself.

6.1Graph optimisation passes, step by step

A compiler applies a sequence of rewriting passes, each of which matches a pattern in the graph and replaces it with an equivalent, cheaper one. The most important ones for vision networks are easiest to understand on a fragment of the running example's neck: two convolutions with batch norm and SiLU, a residual addition, an upsampling and a concatenation. Step through what the compiler does.

This is what the exporter writes for a model in evaluation mode: every module becomes its own node. Each arrow is a full feature map that one node writes to memory and the next one reads. For the whole experiment network that is 90 nodes: 23 convolutions, 19 batch norms, 21 sigmoids, 19 multiplications (SiLU is written as \(x \cdot \sigma(x)\)), 4 additions, 2 resizes and 2 concatenations.

In evaluation mode batch normalisation is a fixed affine map per channel, \(y = \gamma (z - \mu)/\sqrt{\sigma^2 + \varepsilon} + \beta\), applied to the convolution output \(z = w * x + b\). It can therefore be folded into the convolution once, offline: \(w' = w \cdot \gamma/\sqrt{\sigma^2 + \varepsilon}\) per output channel and \(b' = (b - \mu)\,\gamma/\sqrt{\sigma^2 + \varepsilon} + \beta\). Constant subgraphs (shape arithmetic, fixed scales) are evaluated at compile time. The network drops from 90 to 71 nodes with no change in arithmetic results beyond rounding.

Element-wise operations need no data from neighbouring pixels, so they can be applied to each output value while it is still in a register, in the convolution's epilogue. The sigmoid–multiply pair becomes one SiLU, the SiLU and the residual addition move into the second convolution: conv + bias + add + SiLU is one kernel that reads its inputs once and writes one output. ONNX Runtime's extended level brings the network to 50 nodes; GPU and NPU compilers fuse more aggressively, including the residual add.

In the INT8 graph the quantize and dequantize operations disappear into the integer kernels (Figure 5.3). Concatenation is removed entirely: the compiler allocates the concatenated tensor first and lets each producer write directly into its slice, so no data is copied. A nearest-neighbour upsampling can on many targets be folded into the consumer's addressing, reading each source pixel twice instead of materialising a four times larger tensor. What remains is a short chain of fused integer convolutions.

Further passes work across the whole graph. Layout selection chooses NCHW, NHWC or a blocked format for each tensor and removes the transposes between layers that agree. Horizontal fusion merges parallel convolutions on the same input, such as the class and box branches of a head, into one wider convolution. Dead-code elimination removes outputs that nobody uses, such as auxiliary heads left in the export. None of these change what the network computes; they change how often its data crosses the memory bus.

Pitfall

Folding batch norm with tiny running variances or huge gammas produces weights with extreme ranges in a few channels, which then quantize badly. If a model loses unexpected accuracy only after folding, inspect the per-channel weight ranges of the folded convolutions; per-channel quantization or re-training with weight decay on the BN parameters fixes it.

6.2Why fusion pays: counting bytes

Fusion does not reduce arithmetic; it reduces memory traffic, which Section 4.2 showed is what limits most layers. Count it for one feature map of the running example at stride 8: 120 × 68 pixels with 64 channels is 522 KB in INT8. Unfused, the convolution writes it, batch norm reads and writes it, the sigmoid reads and writes it, and the multiplication reads two tensors and writes one: about 4.2 MB of traffic. Fused, the convolution writes 522 KB once. At 15 GB/s of shared DDR bandwidth the difference is about 0.25 ms for this one layer, and a detector has twenty such layers; in FP32 everything is four times larger.

The same arithmetic explains why fusion matters even more on GPUs, where the cost of launching a kernel (a few microseconds) adds to the memory traffic for every unfused node, and why CUDA graphs, which record a whole sequence of kernel launches once and replay it, help small networks noticeably. On the experiment network the 90 → 50 node reduction halved the CPU latency (22.0 → 10.3 ms) without changing a single multiplication.

6.3Tiling and memory planning

An NPU's on-chip SRAM holds a few megabytes, while a high-resolution feature map can be larger. The compiler therefore splits feature maps into tiles, for example bands of rows with all channels, that fit into SRAM together with the weights of the layer. A DMA engine loads the next tile while the MAC array works on the current one (double buffering), so transfer and compute overlap. The best compilers go a step further and process a tile through several consecutive layers before writing anything back to DDR, which requires keeping a few extra rows of overlap for the 3 × 3 kernels; this layer grouping is how feature maps of the early, memory-bound layers avoid DDR almost entirely.

Memory planning handles what must go to DRAM. The compiler knows when each intermediate tensor is produced and when it is last read, and assigns tensors with non-overlapping lifetimes to the same memory. A detector whose intermediate tensors add up to 60 MB may need only 8–10 MB of activation memory at its peak, which is the figure that matters for the memory budget (Section 8.4). Skip connections are the enemy here: a feature map saved for the neck stays alive across many layers and blocks its memory the whole time.

6.4Pruning and sparsity

Pruning removes weights that contribute little and fine-tunes the network to recover. Whether it makes inference faster depends entirely on the structure of what is removed. Unstructured pruning zeroes individual weights anywhere; it can remove 80% of the weights with little accuracy loss, but a dense MAC array still multiplies by the zeros, so latency does not change unless the hardware has explicit sparsity support. Structured pruning removes whole output channels or blocks, which shrinks the tensors themselves and gives real speed-ups on every engine. Channels are usually ranked by the magnitude of their weights or of their batch-norm gamma, removed in steps, and the network is fine-tuned after each step.

Between the two lies semi-structured 2:4 sparsity, supported by NVIDIA's Ampere-generation tensor cores and therefore by the Orin GPU: in every group of four consecutive weights two must be zero. The hardware then stores only the non-zeros plus a small index and skips half of the multiplications, which is where the doubled "sparse TOPS" on datasheets come from. Networks are trained or fine-tuned with this pattern; the speed-up on a whole CNN is typically 1.1–1.5×, not 2×, because only some layers are compute-bound and the rest does not get faster.

Pitfall

Pruning to channel counts that do not fit the hardware. A layer pruned from 64 to 52 channels on an engine that processes channels in groups of 32 or 64 runs exactly as fast as before, and may even slow down if the compiler pads awkwardly. Prune in multiples of the array width and measure on the target.

6.5Distillation and architecture choices for the target

Knowledge distillation trains a small student network to reproduce the outputs, and sometimes the intermediate features, of a large teacher (Deep learning 14.3). From the deployment side it is the most effective way to make a network both smaller and accurate, because the student's capacity is spent on imitating a function that is already smooth and well-calibrated. It also changes what is deployed: the teacher can be a large model that will never run in the car.

The cheapest optimisation, however, is choosing operators the target runs well before training starts. Vendors publish "lite" variants of popular detectors for exactly this reason: TI's model zoo, for example, replaces SiLU with ReLU and large max-pooling kernels with chains of small ones, so that every layer runs on the MMA and quantizes well, at a small accuracy cost in float and often a gain after INT8. Input resolution is the biggest lever of all, since compute scales with the number of pixels: running the full field of view at reduced resolution plus a high-resolution crop around the horizon often beats a single large input. Hardware-aware neural architecture search automates such choices by measuring candidate networks on the chip.

Talk track

"The compiler's fusion and folding are free and remove what the training graph wasted, typically halving memory traffic. Real savings in work come from the model: target-friendly operators, the right input resolution, structured pruning in hardware-sized steps, and distillation from a bigger teacher."

7Preprocessing, memory transfers and zero-copy

Benchmarks measure the network. The car runs a pipeline: a frame arrives from the ISP in a YUV format at full resolution, must become a normalised tensor of the network's size and layout, and the outputs must become a list of objects. In a first port the code around the network regularly takes longer than the network, and almost all of it can be moved into hardware or removed.

7.1What preprocessing really is, and what it costs

Between the ISP output and the network input the running example needs five operations. Scale the 1920 × 1080 frame to 960 × 544 (with a crop or letterbox to keep the aspect ratio). Convert NV12, a full-resolution luma plane plus a half-resolution interleaved chroma plane (Camera, ISP, GPU and display 3), to three colour planes. Normalise every value with a per-channel mean and standard deviation. Rearrange the data into the layout the engine wants. And quantize it to the input's INT8 scale. Each step reads and writes the whole image.

Written naively in C++ on a Cortex-A72 core, these steps take on the order of 10 ms per frame; with NEON intrinsics and fused loops 2–3 ms. That is per camera, on the same CPU cores that run tracking, communication and diagnostics, and every pass costs DDR bandwidth that the accelerator also needs. Worse, a CPU implementation is rarely identical to the one used in training: OpenCV's bilinear resize, PIL's antialiased resize and a hardware scaler's polyphase filter produce visibly different images at the same nominal size, and the network notices.

Pitfall

Training on RGB images that were resized with one library and deploying with NV12 frames resized by a hardware scaler, then searching the quantizer for the two points of lost recall. Fix the preprocessing on the target first, then reproduce it bit-exactly in the training and evaluation data loaders, not the other way round.

7.2Moving preprocessing into hardware or into the network

Most of the work can disappear in one of two ways. The first is to let fixed-function hardware do it while the frame is being produced anyway. Most automotive ISPs can emit several outputs of one frame, for example a full-resolution stream for display and recording and a downscaled one for the network. Separate scaler and warp engines do resizing, cropping and lens-distortion correction from lookup tables: the VPAC multi-scaler and LDC on TI Jacinto, the VIC and the programmable vision accelerator on NVIDIA, the camera subsystem's scaling outputs on Qualcomm platforms. They work in the background, cost no CPU time and read the frame once.

The second is to fold the arithmetic into the network. Normalisation is an affine map per channel, \(x' = (x - m_c)/\sigma_c\), and the first layer is a convolution, so the normalisation can be absorbed into its weights and bias exactly like batch norm (Section 6.1): \(w' = w/\sigma_c\) per input channel and \(b' = b - \sum w\,m_c/\sigma_c\). The colour conversion from YUV to RGB is also linear (a 3 × 3 matrix after upsampling the chroma) and can be absorbed the same way, or the network can simply be trained on YUV input. TIDL and the QNN converter accept mean and scale as import parameters for this purpose; with TensorRT you fold them into the ONNX file.

Interesting detail

Folding the mean into the first convolution is exact except at the image border. The original network pads the normalised image with zeros, which corresponds to padding the raw image with the mean value; after folding, the raw image is padded with zeros. The difference touches one pixel ring and is usually negligible, but it is a reason why a folded model may not match its reference to the last bit at the edges.

7.3Zero-copy into the accelerator

Once preprocessing runs in hardware, what remains is moving buffers. In a naive integration each component allocates its own memory: the camera driver writes frames into one buffer, the application copies them into a CPU buffer, the inference runtime copies that into memory the accelerator can access, possibly converting the layout on the way. A 1920 × 1080 NV12 frame is 3.1 MB; every copy reads and writes it, about 0.6 ms of CPU time and 6.2 MB of DDR traffic. For six cameras at 30 fps, two extra copies cost over 2 GB/s of bandwidth, a seventh of what a TDA4VM-class chip has in total.

Zero-copy means that all engines work on the same physical buffers and only handles move between them. On Linux the common currency is the dma-buf, a file descriptor that represents a buffer which several devices can map (Camera, ISP, GPU and display 4.4). Each vendor adds its own layer: NvSciBuf and NvMedia surfaces on NVIDIA DRIVE (and CUDA external-memory import of dma-bufs), shared buffer pools from the CMA region used by TIOVX and TIDL on Jacinto, ION/dma-buf and the QNN memory registration API on Qualcomm platforms. The camera captures into a pool of such buffers, the scaler reads from it and writes the network input into another pooled buffer, and the inference runtime is given that buffer's handle as its input tensor.

Zero-copy has conditions, and integration time goes into meeting them. All engines must agree on the buffer's format and layout: plane order, row pitch alignment (often 64 or 128 bytes), and on NVIDIA whether the surface is pitch-linear or block-linear. The memory must be physically contiguous or behind an IOMMU every engine uses. Cache coherence must be handled: if the CPU touches a buffer that a device wrote, caches must be invalidated first, and the reverse needs a flush (Camera, ISP, GPU and display 4.3). And ownership must be explicit: the camera may not overwrite a buffer that the network still reads, which is what fences and buffer pools sized for the frames in flight are for (Concurrency 9.3).

Why it matters

Zero-copy is not only about the CPU time of a memcpy. Every copy is DDR traffic that competes with the accelerator, and every conversion is a place where formats can silently differ from training. The first integration milestone of a perception stack should be a frame travelling from the camera to the network input without a CPU touching its pixels.

7.4Post-processing: decoding and NMS

The detector's raw outputs are score and box maps at three scales: at 960 × 544 that is 8160 + 2040 + 510 = 10 710 locations, each with a score per class and four box offsets. Post-processing applies a sigmoid to the scores, keeps candidates above a threshold, decodes their boxes from offsets and grid positions, and runs non-maximum suppression to remove duplicates. NMS compares candidate boxes pairwise, so its cost grows roughly with the square of the number of candidates: negligible on an empty road and tens of milliseconds in a dense car park or a crowd, exactly when the function is needed most.

Three changes make it cheap and bounded. Compare the raw logits with the inverse sigmoid of the threshold instead of computing a sigmoid for every one of the 86 000 class scores; only survivors need the sigmoid. Keep only the top-k candidates (a few hundred) before NMS, which caps the worst case and makes it measurable. And run decode and NMS where the data already is: TIDL's detection meta-architectures run them on the C7x, TensorRT provides NMS layers and plugins, and on a GPU a parallel NMS kernel is cheap. If it stays on the CPU, it should at least work on compact candidate lists, not on full output maps copied out of the accelerator.

Talk track

"The network is only the middle of the pipeline. We scale and convert frames in the ISP and scaler hardware, fold normalisation into the first layer, share buffers by handle from the camera to the accelerator, and bound post-processing with a top-k before NMS. The first port spent more time around the network than in it; now the CPU only orchestrates."

8Measuring performance: latency, throughput, jitter and memory

"How fast is the network?" has no single answer. The time of one inference, the frames per second of the pipeline, the delay from photon to brake request, the worst case over an hour and the memory it all needs are different quantities, measured differently, and each matters to a different person. Being precise about which one you report is half of performance engineering.

8.1The quantities and how they relate

Inference latency is the time from submitting an input to the accelerator until its output is available. End-to-end latency runs from the exposure of the frame (the moment the scene was observed) to the moment the result leaves the ECU, and includes readout, ISP, preprocessing, queues, inference, post-processing and communication. Throughput is how many frames per second the pipeline completes. In a pipeline with several stages working on different frames, throughput is set by the slowest stage while latency is the sum of all stages plus queue waits, so pipelining raises throughput without making any single frame faster (Concurrency 8.1).

Jitter is the variation of latency from frame to frame. A function designed for an average latency fails on the frames that are slow, so latency must be reported as a distribution: the median (p50), high percentiles (p99, p99.9) and the maximum observed, together with how long the measurement ran. A p99.9 needs at least tens of thousands of samples to mean anything; at 30 fps that is ten minutes of running.

The experiment network shows how much the tail can differ from the median even in a trivial setup: on four cores of a shared cloud VM, 200 inferences of the optimised FP32 model had a median of 10.3 ms, a p99 of 19.8 ms and a maximum of 22.4 ms; the INT8 model 8.2, 19.9 and 22.5 ms. The median improved with INT8, the tail did not, because the tail came from the machine (other tenants, frequency changes, scheduler preemption), not from the network. On an embedded target the sources differ (DDR contention with the ISP and GPU, interrupts, thermal throttling), but the lesson is the same: the tail is a property of the system.

8.3Benchmarking without fooling yourself

Most wrong performance numbers come from a few mistakes. No warm-up: the first inferences allocate memory, load code, take page faults, fill caches and, on GPUs, wait for clocks to ramp up; discard them. Timing an asynchronous call: a CPU timer around an enqueue measures only the submission, while a timer around enqueue plus synchronise includes waiting that a pipelined system would hide; on GPUs use events recorded in the stream, and report what you measured. Unknown clocks: power modes and DVFS can change performance by a factor of two, so fix the frequency or at least record it. Synthetic inputs: random tensors give the same network time but empty post-processing, since nothing passes the threshold; use real frames, including dense scenes. And isolated measurement: the network alone on an idle SoC is the best case; the number that matters is with the ISP, the display, the other networks and the logging running.

The vendor tools help if you know what they report. trtexec separates host-to-device transfer, GPU compute and device-to-host transfer, reports percentiles and can run with CUDA graphs and without data transfers to isolate the engine. onnxruntime_perf_test reports P50 to P999 for any execution provider. TI's tools report inference time and DDR traffic per frame; QNN's qnn-net-run with profiling reports per-inference and per-operation timings. Treat their output as a component measurement, then measure the pipeline with your own timestamps.

Pitfall

Reporting throughput with batching as if it were latency. A GPU that processes 8 frames per batch in 40 ms has a throughput of 200 fps but a latency of at least 40 ms per frame plus the time to collect the batch. For a single camera stream batch size is 1; for several cameras, batching across cameras raises throughput and also the latency of the camera that arrived first.

8.4Memory: weights, activations, workspace and bandwidth

A deployed network needs memory for its weights (7 MB for the running example in INT8), its activations at their planned peak (Section 6.3, typically a few to a few tens of megabytes), the runtime's workspace for kernels that need scratch space, and the runtime itself. The last item is easy to forget: a CUDA context and the TensorRT and cuDNN libraries can take hundreds of megabytes on a Jetson or DRIVE system before the first weight is loaded. Each additional execution context, for example one per camera so that inferences can overlap, needs its own activation memory but shares the weights.

On an embedded SoC the more important memory figure is bandwidth. Multiply the DDR traffic per inference by the frame rate and the number of cameras and compare it with the share of the DDR budget the network may use. A network that moves 60 MB per frame at 30 fps uses 1.8 GB/s, about 12% of a 15 GB/s system, before the ISP, the GPU and the display take theirs. When two networks on the same SoC each meet their latency alone and miss it together, bandwidth is usually why (Concurrency 9.4).

9Profiling, thermal throttling and power

Measurement says how long something takes; profiling says why. On an inference target the "why" has three layers: which layers of the network take the time, what else on the SoC slows them down, and what the chip does to itself when it gets hot. The last one is specific to embedded systems and is the most common reason why a lab benchmark does not survive the vehicle.

9.1Reading a layer profile

Every toolchain can report time per layer: trtexec --dumpProfile and Nsight Systems for TensorRT, TIDL's per-layer cycle statistics and its import-time performance simulation, qnn-profile-viewer for QNN profiles. The first thing to do with such a profile is to sort it and look at the top ten layers, which usually account for most of the time. The second is to compute each layer's utilisation: its operation count divided by its time, divided by the engine's peak.

A worked example on a TDA4VM-class MMA (4096 INT8 MACs per cycle at 1 GHz): a 3 × 3 convolution with 64 input and 64 output channels on a 120 × 68 map has 120 · 68 · 64 · 64 · 9 ≈ 301 million MACs, which ideally takes 73 µs. If the profile reports 290 µs, the layer runs at 25% utilisation, and the reason is almost always one of four: it is memory-bound (check its intensity against Figure 4.1), its channel count does not fill the array, it is not fused with its neighbours, or the tiling spills to DDR. Layers with no arithmetic, such as reformatting, transposes, copies between engines and CPU fallbacks, show up as time with zero useful operations and are often the easiest wins.

Interesting detail

TensorRT profiles often contain layers called "Reformatting CopyNode" that the ONNX file never had. They convert tensors between layouts or precisions, for example from the FP16 NCHW layout of one kernel to the INT8 blocked layout of the next, or at the boundary between DLA and GPU. A profile with many of them points to mixed-precision boundaries or engine transitions that should be moved or removed.

9.2System-level profiling and contention

A layer profile is taken with the network alone. A system profile shows all engines on one time axis and reveals the interactions: the NPU waiting for a CPU thread that was preempted, the GPU rendering the surround view while the network's DLA fallback waits for it, inference time rising whenever the display composes a 3D view because both compete for DDR. Nsight Systems on NVIDIA platforms, Perfetto and the vendors' system profilers on Qualcomm, and TI's performance and DDR bandwidth statistics show such timelines; on Linux, ftrace and eBPF add CPU scheduling and driver events to the picture (Linux 10.5, 10.6). Hardware performance counters for DDR bandwidth per master are the decisive tool when "random" slowdowns correlate with other functions.

9.3Thermal throttling

Almost all electrical power a SoC uses becomes heat, and silicon has a maximum junction temperature, typically 105–125 °C for automotive parts. A front camera behind the windscreen sees cabin temperatures above 85 °C in summer sun, a central computer in the boot sees less sun but more neighbours, and both may have only passive cooling. When the junction temperature approaches its limit, the thermal management lowers clock frequencies and voltages (dynamic voltage and frequency scaling, DVFS) in steps, or, at a critical trip point, shuts functions down. Performance therefore depends on how long the chip has been working and in what environment.

There are two engineering answers, and automotive systems often combine them. The first is to budget for sustained performance: measure latency after a long soak at the maximum ambient temperature of the specification, in a thermal chamber, with the complete workload, and design the timing for that throttled state. The second is to avoid throttling by design: fixed clock frequencies chosen so that the thermal design can dissipate the worst-case power indefinitely, with throttling or shutdown only as a fault reaction that the function's safety concept handles as a degradation. Fixed clocks are popular in safety-related functions because they keep timing deterministic; the price is that the chip never runs at its datasheet peak.

Numbers

AEC-Q100 temperature grades for automotive ICs: grade 3 −40 to 85 °C ambient, grade 2 −40 to 105 °C, grade 1 −40 to 125 °C. Thermal time constants of an ECU housing are minutes to tens of minutes, so a thermal benchmark needs at least 30–60 minutes of continuous load before its numbers are representative. Leakage power roughly doubles for every 10–20 °C, so a hot chip also needs more power for the same work, which heats it further.

9.4Power budgets and power modes

Dynamic power of digital logic grows with capacitance, the square of the voltage and the frequency, \(P \approx C V^2 f\), plus leakage. Since lower frequencies also allow lower voltages, running an accelerator at 70% of its clock can save around half of its power, which is why power modes trade peak performance for efficiency. Jetson modules expose this as nvpmodel power modes (for example 15, 30 or 50 W on an AGX Orin) that cap clocks and active cores; automotive SoCs offer similar operating points configured by the platform. The relevant metric for an inference workload is energy per inference at the required frame rate, not TOPS per watt at peak: a faster engine that finishes early and idles can use less energy than a slower one that runs continuously.

Power budgets are set by the ECU's thermal design and the vehicle's electrical system. A windscreen camera module has a budget of a few watts up to around ten for everything inside it; a central ADAS computer has tens to a few hundred watts with active or liquid cooling. INT8 instead of FP16, fused graphs, fewer DDR transfers and lower input resolutions all reduce energy as well as latency, and DDR traffic is often the largest single contributor, because moving a byte off-chip costs far more energy than computing with it. Measure power on the board's current sensors (exposed by tegrastats on NVIDIA, by the PMIC or by external measurement on other platforms) with the real workload, and at the hot end of the temperature range.

10Deploying and validating on the SoC

The compiled binary is a different program from the PyTorch model: other arithmetic, other operator implementations, other preprocessing. Validation has to show that it is still the same function, that it gives the same answer every time, and that the next toolchain update has not quietly changed that. This is where deployment meets the safety case.

10.1The parity ladder: where accuracy goes

Accuracy parity is established in steps, each comparing a deployment stage with the one before it, so that a difference can be attributed to exactly one change. The reference is the float model in the training framework. The first rung is the ONNX model in ONNX Runtime, which should match to about 1e-5 relative error; anything larger is an export bug. The second is the target's compiled float or FP16 model, where differences come from kernel implementations and fused operations. The third is the quantized model in the vendor's host emulation, which isolates the quantization error. The fourth is the same quantized model on the target, which should match the emulation exactly or within a tiny tolerance. The fifth replaces the reference preprocessing with the target's real camera path: ISP output, hardware scaler, folded normalisation.

The ladder turns "the target is two points worse" into a diagnosis. If the loss appears between rungs 2 and 3, it is quantization, and sensitivity analysis, mixed precision or QAT are the tools (Chapter 5). If it appears between 3 and 4, the emulation does not reproduce the target, which is a toolchain issue to raise with the vendor. If it appears at rung 5, the training data does not look like what the camera delivers, and the fix is in the data pipeline, not in the compiler. Skipping rungs, for example comparing the PyTorch model on PNG files with the target running on live NV12 frames, mixes all of these into one number that nobody can act on.

10.2Comparing outputs: tensors, detections, KPIs

Three levels of comparison are needed, from the most sensitive to the most meaningful. Tensor level: for every output, and when localising a problem for intermediate tensors, compute the maximum absolute difference, the cosine similarity and the SQNR against the reference. Cosine similarity above 0.9999 is typical for FP16; for INT8 outputs 0.99 or better, with SQNR in the 20–35 dB range. Dumping intermediate tensors layer by layer and finding the first layer where the SQNR drops localises a quantization or compiler problem in minutes; NVIDIA's Polygraphy, TIDL's per-layer trace output and QNN's intermediate outputs all support such bisection.

Detection level: match the boxes of the reference and the deployed model on the same frames (same class, IoU above 0.5) and report how many are missing, how many are extra, and the distributions of score and box differences. Small numbers of flips for objects whose score is right at the threshold are expected; systematic misses of small or dark objects are not. Task level: compute the real KPIs (mAP, recall at the operating point, distance error) on a validation set split into slices of the operational design domain: day and night, rain, low sun, tunnels, object classes and distance bands. Acceptance criteria must be defined per slice before the measurement, for example "no slice loses more than one recall point and no safety-relevant class more than half a point", because an overall average hides exactly the slice that matters.

Pitfall

Marking intermediate tensors as outputs for debugging changes what the compiler can do: a tensor that must be written out cannot be fused away. The debug build may then be more accurate or slower than the release build. Compare the release engine's outputs as they are, and use intermediate dumps only to localise a difference you have already seen.

10.3Determinism and reproducibility

Two questions are easily confused. Run-to-run determinism asks whether the same binary gives the same output for the same input every time. Integer NPUs do: their arithmetic is exact and their schedule is fixed, so outputs are bit-identical, and TIDL's host emulation reproduces them bit for bit on a PC. GPUs mostly do for a given engine, but kernels that accumulate with atomic operations in parallel can change the summation order and with it the last bits of a float result. Build reproducibility asks whether compiling the same model again gives the same binary. Here TensorRT's timing-based kernel selection can choose different kernels in two builds, so outputs differ slightly; a stored timing cache, or simply treating the built engine as the versioned artefact, solves it.

Bit-exactness across platforms is not achievable for floating point: different summation orders, fused multiply-add and different math libraries change the last bits (Mathematics 11). Test strategy follows from this: bit-exact golden vectors for integer engines and a fixed SDK, tolerances based on SQNR or cosine similarity for float paths, and detection- and KPI-level comparisons for everything across platforms. Determinism also has system-level sources outside the network. Sorting candidates by score with an unstable sort makes NMS keep a different box when two scores are equal; multithreaded post-processing can emit objects in a different order; dropped frames change what a tracker sees. A replay test that feeds recorded frames with fixed timing is how the whole chain is checked for repeatability.

Why it matters

A safety argument needs to show that the binary in the vehicle behaves like the one that was validated. If outputs change with every build or every run, each change must be explained; if they are bit-exact against an emulator, most validation can be done on a server farm and the target only has to confirm the match.

10.4Regression testing in CI and on hardware

Deployment is not a one-time event. The model is retrained, the calibration set grows, the ISP tuning changes, the vendor SDK is updated twice a year, and each of these can change accuracy or latency. A regression pipeline makes every such change visible. On each change it exports the model, checks ONNX parity, compiles for every target with pinned toolchains in containers (Build and containers 11), runs the host-emulation parity suite, and then deploys to a farm of real boards for the on-target parity, the latency and memory suite and, periodically, a thermal soak. Gates compare the results with the previous release: KPI deltas per slice, p99 latency, peak memory and DDR traffic per frame, and bit-exactness where it is expected.

Two kinds of test data are needed. A small, fixed set of golden inputs with stored outputs gives fast and exact checks of the toolchain and the binary. A large, sliced set of recorded drives, replayed through the target, gives the KPI comparison. Re-simulation of recorded RAW data through the production ISP and the target network is the strongest form, because it tests rung 5 of the ladder as well.

10.5Release artefacts and the safety view

A deployed model is released as a bundle, not a file. It contains the ONNX model and the training checkpoint it came from, the identifiers of the calibration set and of the quantization encodings or QAT scales, the compiler and SDK versions with all options, the compiled binary and its hash, the preprocessing configuration including the ISP tuning version, the parity and performance reports, and the known limitations. With that bundle the binary can be rebuilt, explained and compared with its successor; without it, an SDK update becomes an archaeology project.

For safety-related functions this bundle is part of the evidence. ISO 21448 (SOTIF) and ISO/PAS 8800 for AI in road vehicles expect that the performance of the deployed model is demonstrated for its operational design domain and that changes are controlled; quantization, compilation and preprocessing are design decisions that need the same traceability as code (Standards 4). The practical consequence is that the KPIs used for release are measured on the target binary, or on an emulation proven bit-exact with it, never only on the float model.

11Worked example: one detector, three targets

This chapter walks the running example from checkpoint to released binary on each target, with the decisions a team would typically make and where accuracy and latency were lost on the way. The steps and tools are real; the numbers are typical outcomes for a network of this size, given to show proportions, not measurements of a specific product.

11.1The common front half

In the first week the team runs the deployability check of Section 2.2 on the untrained architecture. Two findings change the model before training starts. The neck used a bilinear Resize with align_corners, which one target only supported on the CPU; it becomes a nearest-neighbour upsample followed by the existing 3 × 3 convolution, which learns any smoothing it needs. The stem used a slicing "focus" layer that rearranges pixels into channels with strided slices; it becomes a plain strided convolution, which every NPU maps well. Channel counts in the neck are rounded to multiples of 64 for the MMA. Training then proceeds as usual, and the time spent is a day of compiling, not a retraining months later.

The trained checkpoint is exported once: evaluation mode, batch 1, fixed 960 × 544 input in the camera's planar RGB order with normalisation folded into the first convolution, raw score and box maps as outputs. The ONNX file is simplified, inspected in Netron, and compared with PyTorch on 200 real frames: maximum absolute difference about 1e-5. A calibration set of 500 frames is drawn from the validation drives, stratified over the ODD slices and both camera variants, processed by the production ISP tuning and the target's scaler model. These three items, the ONNX file, the calibration set and the preprocessing definition, are the common input to all three vendor flows.

11.2NVIDIA: TensorRT on DRIVE Orin

The first build is FP16 on the GPU with trtexec. TensorRT folds and fuses the graph into a few dozen layers, times kernels for each and writes an engine. FP16 parity is excellent (cosine similarity above 0.9999, no KPI change), and the engine runs in a few milliseconds on the GPU. The system budget, however, reserves the GPU for surround-view rendering, so the target is the DLA in INT8.

Quantization uses explicit Q/DQ: a PTQ pass with NVIDIA's Model Optimizer on the calibration set inserts quantizers with per-channel weight scales. On the GPU in INT8 the overall mAP drops by about one point, but the night slice loses three points of pedestrian recall. A sensitivity analysis points at the box-regression convolutions and the final neck concatenation; removing their quantizers keeps them in FP16, and the night loss falls to a few tenths of a point. The DLA build then reports that all layers run on the DLA except the final reshape of the outputs. The engine on the DLA is slower than on the GPU, but it leaves the GPU free and fits the budget. Frames arrive through NvSciBuf buffers from the camera stack, a small CUDA or VIC step produces the network input in place, and decode plus a top-k NMS run on the CPU on a compact candidate list.

Where it lost: accuracy at the quantization rung (fixed by mixed precision); latency at the FP16/INT8 boundaries, where TensorRT inserted reformatting layers, and at the DLA-to-GPU transition for the last layer. The engine is built on the target with the pinned DriveOS and TensorRT release and stored with its timing cache.

11.3TI: TIDL on TDA4VM

The model is compiled with TI's edge AI tools: ONNX Runtime with the TIDL execution provider partitions the graph, and the TIDL importer merges layers, calibrates with a subset of the calibration set over several iterations and writes the network and I/O binaries. With 8-bit tensors and per-channel weights the first result loses about two mAP points. Advanced bias calibration recovers part of it, and setting the two head convolutions and their inputs to 16 bits recovers most of the rest at a cost of about a millisecond. A detection meta-architecture file lets TIDL decode boxes and run NMS on the C7x, so the Arm cores receive a short object list.

Because the host emulation is bit-exact with the target, the whole quantization study runs on a server; the target only confirms the match on the golden vectors. On the board, the VPAC multi-scaler produces the 960 × 544 input directly from the ISP's NV12 output, the colour conversion is folded into the first layer, and buffers move between capture, scaler and C7x as shared memory handles through a TIOVX graph. The per-layer profile shows the early high-resolution layers as memory-bound and the deep layers near full MMA utilisation, as Figure 4.1 predicts; TI's DDR statistics confirm that the network's traffic per frame fits next to the ISP and display.

Where it lost: accuracy at the quantization rung, mostly in 8-bit activations of the heads; latency in the memory-bound early layers and, before the channel counts were rounded, in partially filled MMA passes.

11.4Qualcomm: QNN on the Hexagon NPU

The QNN converter turns the ONNX file into a QNN graph and quantizes it with the calibration list. With 8-bit activations and weights (A8W8) the result loses accuracy in the same head layers as on the other targets. Two routes are evaluated. Converting with 16-bit activations everywhere (A16W8) restores accuracy almost completely and costs noticeable extra latency and memory traffic. Using AIMET for AdaRound and a short QAT fine-tune, then importing its encodings and keeping only the heads in 16 bits, gives nearly the same accuracy at close to A8W8 speed; this is the chosen configuration.

The graph is prepared offline with the context-binary generator for the exact Hexagon version of the SoC, so that start-up only loads a binary instead of preparing the graph for several seconds. Input buffers come from the camera stack as shared memory registered with the QNN runtime, so the HTP reads them without a copy. The QNN profile shows per-operation cycles on the HTP and confirms that no operation falls back to the CPU.

Where it lost: accuracy at the quantization rung (activations); latency at start-up until the context binary was introduced, and in the 16-bit head layers.

Integer engines are bit-exact; float paths need tolerances; rebuilding can change kernels.

QSelf-check questions

Core questions with short model answers; the chapter sections hold the depth. The second group checks understanding with "why" and "what if" questions rather than definitions.

Q.1Core questions

What is the difference between a training graph and an inference graph?Basic

The inference graph is the network frozen in evaluation mode: batch norm uses running statistics and becomes a fixed affine map that can be folded into convolutions, dropout and auxiliary heads disappear, no gradients or activations are kept for a backward pass, shapes are usually fixed and batch is 1. It also fixes the input contract (format, normalisation, layout) and where the graph ends, typically before decoding and NMS.

Walk me through deploying a PyTorch detector to an automotive NPU.Basic

Check deployability on the target before training. Export in eval mode to ONNX with a fixed input size, stop before NMS, simplify, and check parity with PyTorch in ONNX Runtime. Compile with the vendor tool, read the placement report, quantize with a representative calibration set and per-channel weights, run a sensitivity analysis and keep critical layers at 16 bits or use QAT. Integrate with hardware preprocessing and zero-copy buffers, bound post-processing, measure end-to-end latency percentiles under full load and heat, and validate parity per ODD slice on the target binary before release.

What does an inference compiler like TensorRT do?Intermediate

It parses the ONNX graph, applies graph optimisations (constant folding, BN folding, vertical and horizontal fusion, Q/DQ fusion), chooses precision per layer within what is allowed, and selects for each fused layer the fastest kernel by timing candidates on the actual GPU. It plans activation memory and serializes everything into an engine tied to that GPU and TensorRT version. At run time the engine is only deserialized and enqueued on CUDA streams.

How does INT8 quantization work inside a convolution?Intermediate

Weights are INT8 with per-channel scales and zero point 0, activations UINT8 or INT8 with a per-tensor scale and zero point. The layer multiplies 8-bit values and accumulates in INT32, adds an INT32 bias pre-scaled by \(s_x s_w\), then requantizes with the fixed-point multiplier \(M = s_x s_w / s_y\), adds the output zero point and clamps, which also implements a fused ReLU. All arithmetic is integer; rounding happens only when values are put on the 8-bit grids.

PTQ versus QAT?Basic

Post-training quantization calibrates ranges on a few hundred representative images without retraining; it is fast and usually loses 0.5–2 mAP points on CNN detectors. Quantization-aware training fine-tunes with fake quantization in the forward pass and the straight-through estimator in the backward pass, so weights adapt to rounding; it recovers most of the loss but costs training time and must mimic the target's quantization scheme exactly.

What are the main calibration methods?Intermediate

Min/max uses the observed extremes; percentile clips at, say, the 99.99th percentile; entropy chooses the range that minimises the KL divergence between float and quantized histograms; MSE minimises the squared error. They differ in how they trade rounding error against clipping error on tensors with long tails. The representativeness of the calibration data matters more than the method.

Why per-channel quantization for weights but per-tensor for activations?Intermediate

Weight ranges differ strongly between output channels, especially after BN folding, and a per-channel scale costs nothing because each output channel's accumulator is requantized separately anyway. A per-channel activation scale would apply to the inputs of the accumulation, so the products could not simply be summed in integers; per-tensor activation scales keep the inner loop pure integer.

Which layers are most sensitive to quantization, and what do you do about them?Intermediate

Regression heads (box offsets, depth), score outputs near the threshold, concatenations and additions of tensors with different ranges, depthwise convolutions with per-tensor weights, and attention, softmax and layer norm. Find them with a per-layer sensitivity analysis, then keep them at 16 bits (mixed precision), improve PTQ with equalisation, bias correction or AdaRound, or use QAT.

What is operator fusion and why does it speed things up?Basic

Combining operations into one kernel, typically convolution plus bias, batch norm, activation and residual add, so element-wise work is done on values still in registers in the producer's epilogue. It removes intermediate tensors that would be written to and read from memory, plus kernel launches on GPUs. Since most layers on embedded accelerators are memory-bound, saving traffic saves time even though the arithmetic is the same.

What happens when a layer is not supported by the NPU?Basic

The compiler partitions the graph: the part before runs on the NPU, the tensor is written out and converted, the operator runs on the CPU or GPU, and the result is converted back for the next NPU subgraph. Each cut costs synchronisation, transfers and layout conversions, often more than the operator itself. Fix it by replacing the operator before export, moving it to the end of the graph, or implementing a custom layer on the accelerator.

What does zero-copy mean in a camera-to-inference pipeline?Intermediate

The camera, scaler and accelerator work on the same physical buffers, shared as dma-buf or vendor buffer handles, so no CPU copies pixels; only handles and fences move. It requires agreeing on format, pitch and layout, contiguous or IOMMU-mapped memory, correct cache maintenance for any CPU access, and buffer pools sized for the frames in flight so the camera never overwrites a buffer still being read.

How do you benchmark inference latency correctly?Intermediate

Warm up first, fix and record clocks and power mode, use real inputs including dense scenes, time asynchronous engines with device events, and report a distribution (p50, p99, p99.9, max) over enough samples. Then measure end to end from the exposure timestamp to output with the full system running, because contention and post-processing change the result; the isolated network time is only a component.

Why is TOPS a poor predictor of real performance?Basic

TOPS is the peak of all MAC units busy every cycle, often for INT8 with sparsity. Real layers are frequently memory-bound, their shapes do not fill the array, unsupported operators fall back, and pre- and post-processing run elsewhere. Utilisation ranges from over 50% for deep convolutions to single digits for awkward layers, so compare platforms by measured latency of your own network at your resolution with the system loaded.

What is thermal throttling and how do you account for it?Basic

When the junction temperature approaches its limit, the SoC lowers clocks and voltages, so latency rises after minutes of load in a hot environment. Either validate timing after a long soak at maximum ambient temperature with the full workload and budget for the throttled state, or run fixed clocks that the thermal design can sustain, treating throttling as a degraded mode.

How do you validate that the deployed model is as good as the trained one?Intermediate

Climb a parity ladder: PyTorch vs ONNX Runtime, compiled float vs ONNX, quantized emulation vs float, target vs emulation, and finally with the real camera preprocessing. At each rung compare tensors (cosine, SQNR), detections (matched, missing, extra boxes) and per-slice KPIs against criteria defined beforehand. Release KPIs are measured on the target binary or an emulation proven bit-exact with it.

What is in a release of a deployed model?Basic

The ONNX model and source checkpoint, calibration set and quantization encodings, compiler and SDK versions with options, the compiled binary and its hash, the preprocessing and ISP tuning configuration, parity and performance reports, and known limitations, enough to rebuild and explain the binary after the next SDK update.

When would you choose the DLA on Orin instead of the GPU?Advanced

When the GPU is needed for other work (rendering, other networks) or power efficiency matters, and the network's layers are DLA-compatible in INT8 or FP16. The DLA is usually slower than the GPU for the same network and any unsupported layer falls back to the GPU with a transition cost, so the decision rests on the system budget, measured with both engines loaded, not on the network alone.

Q.2Why and what if

Why does clipping activations at the 99.9th percentile sometimes make the error worse, not better?Intermediate

Clipping trades rounding error on all values for clipping error on the few above the range. If the outliers are large, each clipped value has a huge error, and they can carry a large share of the signal power, so total error rises. The optimum depends on the tail, which is why calibrators search per tensor (MSE, entropy) and why fewer bits push the optimum towards tighter clipping.

Why does INT8 make a network much faster on an NPU but only a little faster on a CPU with ONNX Runtime?Intermediate

The NPU is built around INT8 MAC arrays and on-chip memory, so integer layers run at many times the throughput of anything else. On a CPU, INT8 kernels with VNNI are faster but only for convolutions; quantize and dequantize nodes, resizes, activations and other float operations remain, and threads and caches limit the rest. In the chapter's experiment the CPU speed-up was about 1.25× at the median.

What if the calibration set contains only daytime images?Basic

Activation ranges are fitted to daytime statistics. At night, dark regions use few integer levels, and bright headlights or street lamps exceed the range and are clipped, so the network loses exactly the contrast it needs. Overall mAP on a mostly daytime validation set may hide this; only per-slice evaluation shows it. The calibration set must cover the ODD and be versioned like training data.

What if you fold normalisation into the first convolution and the target output differs at the image border?Advanced

That is expected. The original network pads the normalised image with zeros, which corresponds to the mean colour in raw values; the folded network pads the raw image with zeros. Only the outer ring of pixels is affected and it is usually harmless, but it means bit-exact comparisons must either use the folded model as the reference or tolerate the border.

Why can a MobileNet-style network be no faster than a plain CNN with three times the FLOPs on an NPU?Advanced

Depthwise and 1 × 1 convolutions have low arithmetic intensity, so they are memory-bound and leave the MAC array idle, and depthwise layers often map poorly to matrix engines. The plain CNN's 3 × 3 convolutions reuse data heavily and run near peak. Time on an accelerator follows memory traffic and utilisation, not FLOPs.

What if you prune 30% of the weights unstructured and see no speed-up?Basic

That is the expected outcome on dense hardware: the zeros are still multiplied and the tensor shapes are unchanged. Only structured pruning (whole channels, in multiples the hardware processes) or hardware-supported patterns such as 2:4 sparsity reduce work, and even then only compute-bound layers speed up.

Why does adding an intermediate output for debugging change the results or the speed of a TensorRT engine?Advanced

A tensor marked as an output must be materialised in memory and in a defined precision, so the builder cannot fuse across it and may choose different kernels and precisions around it. The debug engine is therefore a different engine. Use it to localise a difference already seen in the release engine, not as the reference.

Two TensorRT builds of the same ONNX file give slightly different outputs. Is that a bug?Intermediate

Usually not. The builder selects kernels by timing them, timings vary, and different kernels sum in different orders, which changes the last bits of float results. Keep the built engine as the versioned artefact or reuse a timing cache to make builds reproducible, and use tolerance-based parity for float paths.

What if two networks each meet their latency alone but miss it when running together?Intermediate

They compete for shared resources: DDR bandwidth above all, plus the engine itself if both use it, with coarse preemption. Measure DDR traffic per frame for each, look at a system timeline, and fix it with scheduling and budgets per engine, partitioning (separate NPU cores, DLA vs GPU), reducing traffic (fusion, tiling, resolution) or bandwidth regulation where the SoC offers it.

Why can the median latency improve with INT8 while the p99 does not change?Intermediate

The median reflects the network's compute; the tail is often caused by the system: preemption by other threads, interrupts, DDR contention, frequency changes or post-processing of dense scenes. A faster network does not remove those causes, so the tail must be investigated with timestamps and system traces separately.

Why does the bias need to be stored in INT32 with scale \(s_x s_w\) rather than in INT8?Advanced

The bias is added to the INT32 accumulator, whose real value has scale \(s_x s_w\), before requantization. Storing it at that scale in 32 bits lets it be added exactly with no extra rounding, and its relative precision matters because a bias error shifts every output of the channel.

What if the target and the vendor's host emulation disagree?Intermediate

The emulation is then not a valid stand-in, and all validation done on it is in question. Reproduce the difference on golden vectors, bisect layer by layer to find the first differing tensor, check SDK versions and import options on both sides, and raise it with the vendor. Until fixed, release KPIs must be measured on the target itself.

Why is energy per inference a better efficiency metric than TOPS per watt?Basic

TOPS per watt is a peak figure for ideal layers. Energy per inference at the required frame rate includes real utilisation, memory traffic, idle time and the operating point, so it compares what the product actually spends. A faster engine that finishes early and idles can use less energy than a slower, nominally more efficient one.
