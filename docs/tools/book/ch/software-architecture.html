Software architecture and system design

How a system is shaped before and while it is built, told by designing one multi-camera perception and visualisation ECU step by step: requirements, quality attributes and the drivers that decide the structure; views at several levels; architecture styles from the monolith to services; interface contracts, API design and versioning; modularity, SOLID and dependency management; design patterns in modern C++; messages, events and publish-subscribe; the basics of distributed systems; scheduling, memory and hardware in embedded architecture; latency and resource budgets; fault tolerance, degradation and observability; and how trade-offs, technical debt and evolution are handled. Each topic contrasts the embedded view with the cloud view.

1The big picture: what architecture is for

Every system has an architecture, whether anyone designed it or not. The question is whether its shape was chosen for the qualities the product needs, or whether it grew from the first prototype and now decides, by accident, how fast the system is, how it fails and how expensive every change becomes. This chapter is about choosing on purpose.

1.1Architecture is the set of decisions that are expensive to change

Most definitions of software architecture talk about "components, their relationships and their properties". That is true but not very useful when you have to decide what to do on Monday. A more practical definition is that the architecture is the set of decisions that are expensive to change later. Which processes exist and what runs in each of them; how data moves between them; which component owns which piece of state; where the boundary to the hardware vendor's software lies; which interfaces other teams and other companies depend on; how the system notices and survives a fault. A wrong variable name costs a minute to fix; a wrong decision about which process owns the camera buffers can cost a year, because by the time anyone notices, fifty other pieces of code depend on it.

This definition explains what an architect actually spends time on. Not on drawing boxes, but on finding the few decisions that will be expensive to reverse, making them deliberately with the information available, writing down why, and keeping everything else cheap to change. It also explains why architecture is not a phase at the start of a project. Expensive decisions keep appearing: a new sensor, a second hardware generation, a safety requirement that arrives late, a supplier who ships a library in a format nobody expected. Each of them is an architecture decision, and each is easier when the earlier ones left room.

Why it matters

The qualities that customers and regulators care about most, such as latency, availability, safety, security and the cost of the next variant, are properties of the whole system. No single function can deliver them, and no amount of good code inside a component can rescue a structure that works against them. A perception algorithm that is twice as fast does not help if the frame waits 30 ms in a queue in front of it, and a perfectly tested module does not help if a crash in an unrelated process takes the rear-view image down with it.

1.2The running example: a multi-camera perception and visualisation ECU

The whole chapter designs one system: the camera ECU that appears throughout this book, seen this time from the architect's desk. It receives four 3-megapixel fisheye cameras around the car (1920 × 1536 pixels each) and one 8-megapixel front camera (3840 × 2160), all at 30 frames per second, over serializer links. It does four jobs. It shows the driver a rear view and a stitched 360° surround view with a 3D model of the car and guidance lines when reversing or parking; it runs parking perception (free space, obstacles, parking slots) and sends an object list to the parking and braking functions; it runs front-camera detection for driver assistance; and it records short clips around interesting events for development and fleet learning. Around these it has the usual duties of an ECU: diagnostics, logging, updates, start-up within a deadline and a defined behaviour when something breaks.

The hardware is the typical pair (Camera ECU 1.2): a vision system-on-chip with application cores, an image signal processor (ISP), a GPU, a neural processing unit (NPU) and 8 GB of LPDDR5 memory, plus a safety microcontroller with Classic AUTOSAR that owns the vehicle buses, the power control and the supervision of the SoC. The display is either driven directly or through the head unit. That is the starting point; everything else in the system is to be designed in this chapter.

1.3What designing a system means, step by step

Designing a system is a loop, not a sequence, but it has a natural order that this chapter follows. First you find out what really drives the design: the few quality requirements and constraints that, if you get them wrong, make the product fail (Section 2). Then you choose a structure that serves those drivers, looking at it from several angles, because one diagram can never show both what runs where and what depends on what (3, 4). You define the contracts between the parts so that teams can work independently and the system can evolve (5, 6, 7), decide how the parts communicate and what happens when communication fails (8, 9), map everything onto the real hardware with budgets for time, memory and bandwidth (10, 11), design how the system detects and survives faults and how you will see what it is doing (12), and finally keep it healthy over years of change (13). Section 14 puts it all together as a method you can use in a design review or a system design discussion.

Along the way every topic is contrasted with the cloud view, because the vocabulary of software architecture (microservices, eventual consistency, retries, observability) mostly comes from large web systems, and senior engineers are expected to move between both worlds. The principles are the same; the weights are different. A web service buys reliability with redundancy and elastic capacity and can deploy fifty times a day; an ECU has fixed hardware, hard deadlines, a safety case and a software release that must work for fifteen years.

Talk track

"For me, architecture is the set of decisions that are expensive to change: process boundaries, data flow and ownership, interfaces other teams depend on, the hardware boundary and the fault behaviour. I start from the quality drivers, latency, safety, availability, and the cost of the next variant, choose a structure that serves them, write down the trade-offs, and then protect the decisions with budgets, contracts and automated checks so the design survives contact with fifty developers."

2Requirements, quality attributes and architecture drivers

Two systems with exactly the same functions can need completely different architectures. What separates them is not what they do but how well, how fast, how safely and under which constraints they must do it. Finding those qualities, making them measurable and ranking them is the first and most underrated step of design.

2.1Functions do not shape the architecture; qualities do

"Show a surround view when the driver selects reverse" is a functional requirement. It can be met by a single-threaded program on a laptop that reads four video files and draws them. What makes the real ECU hard is everything around that sentence: the image must appear within 2 seconds of power-on, it must lag reality by less than about a tenth of a second, it must keep running when the perception software crashes, it must detect when it freezes, it must run on hardware that costs a few hundred euros and is chosen two years before the software is finished, and the same code must work on the next SoC generation. These are quality attributes (also called non-functional requirements, a name that hides how central they are) and constraints. They decide how many processes there are, which CPU cores and accelerators do what, how much is checked at run time, and where the abstraction layers go.

This is why the first question in any design discussion, and in any system design exercise, is not "which components?" but "what matters most, and how much?". A good architect can name the three or four qualities that dominate a system and say what each costs. Everything else is details that a good team can handle locally.

2.2Quality attributes, and how to make them testable

Standards list the qualities a product can have. ISO/IEC 25010 (revised in 2023) names nine product characteristics: functional suitability, performance efficiency, compatibility, interaction capability (formerly usability), reliability, security, maintainability, flexibility (formerly portability) and safety, each with sub-characteristics such as availability, fault tolerance, modifiability or testability. The list is useful as a checklist so that nothing is forgotten, but a word such as "reliable" or "maintainable" in a specification decides nothing. Two people can agree that a system must be maintainable and mean opposite things.

The tool that turns a quality into something you can design and test against is the quality attribute scenario, from the architecture method of the Software Engineering Institute. It has six parts: a source (who or what causes the event), a stimulus (the event), the environment (the operating condition), the artifact (the part of the system that is stimulated), the response (what the system does) and the response measure (how you know it did it well enough). Written this way, each requirement contains its own test.

Pitfall

Requirements written as solutions ("the system shall use DDS", "perception shall run in a separate container") hide the real need and freeze a decision before anyone has analysed it. When you meet one, ask for the scenario behind it. Often the real requirement ("a crash of perception must not affect the view") can be met in a cheaper way, or the proposed solution does not even meet it.

2.3Constraints: what is already decided

A constraint is a decision that the architect does not get to make. In automotive projects there are many: the SoC and its vendor software (chosen in sourcing, often before the software team exists), the operating system and hypervisor that come with it, AUTOSAR on the microcontroller and often Adaptive AUTOSAR or another middleware on the SoC (AUTOSAR 2.1), the OEM's communication matrix and diagnostic specification, coding standards such as MISRA C++:2023, the ASIL assigned by the OEM's safety analysis, the cybersecurity and update regulations, the budget for hardware cost and power, and the supplier's existing code base. Organisational facts are constraints too: which team owns what, which supplier delivers which library, and how often the OEM integrates.

Constraints are not bad news. They remove options, which saves design effort, and they are usually there for good reasons such as cost, certification or supply. But they must be written down next to the quality scenarios, because a design that is perfect for the qualities and violates a constraint is not a design. Conway's law belongs here as well: a system tends to copy the communication structure of the organisation that builds it. If the front-camera team and the parking team are separate, sit in different countries and release on different cycles, their software will end up as separate components with an interface between them, whether the architect planned it or not. It is better to plan it.

2.4From many requirements to a few drivers: the utility tree

A real ECU has thousands of requirements, but only a handful decide its structure. Those are the architecture drivers: the quality scenarios that are both important to the customer and hard to achieve, plus the constraints. The utility tree of the SEI's Architecture Tradeoff Analysis Method (ATAM) is a simple way to find them. You write the qualities as the first level of a tree, refine each into concrete scenarios, and rate every scenario twice, on its business importance (high, medium, low) and on its architectural difficulty (high, medium, low). The scenarios rated high on both are the drivers. The rest still have to be met, but they do not need to shape the structure.

For the camera ECU, six drivers come out of the tree. The rear view's latency and start-up time (hard because they cross every layer from the sensor to the panel), fault containment between the rear view and the much larger perception software (hard because they share cameras, memory and the GPU), detection of a frozen or delayed image (safety, ASIL B in this example), the memory-bandwidth and accelerator budget with all five cameras running (hard because every function competes for the same DDR), portability to the next SoC (hard because vendor SDKs leak into everything), and bit-exact replay on a PC for testing (hard because it forbids hidden dependencies on the hardware and the clock). The rest of the chapter keeps returning to these six; each section shows which driver a decision serves.

In practice

The utility tree is most valuable as a conversation tool. Rating importance needs the customer, product owner or system engineer; rating difficulty needs the engineers who know the hardware and the code. Doing it together in two hours at the start of a project, and again when something big changes, aligns everyone on what the design is optimising for, and gives the architect a written reason when someone later asks why an "obvious" simplification was rejected.

2.5The same qualities in an ECU and in the cloud

Every quality attribute exists in both worlds, but the weights and the available tools differ so much that habits from one world can be harmful in the other. A cloud service scales by adding machines, so its performance problem is mostly cost; an ECU cannot add a chip after start of production, so its performance problem is a hard limit that must be budgeted from the first day. A cloud service is available if enough of its replicas are healthy; an ECU must keep a function available with the one SoC it has, so it relies on fault containment and fast restart inside the box. A cloud service deploys continuously and fixes forward; an ECU release is validated for months, flashed into hundreds of thousands of cars and must remain supportable for fifteen years.

3Seeing the architecture: views and levels

An architecture is a set of decisions, but people understand and review it through diagrams. No single diagram can show what runs where, what depends on what and what happens over time, so architects describe a system with several views, each answering one kind of question, at several levels of zoom.

3.1Why one diagram is never enough

A box labelled "Perception" can mean a C++ library, a process, a thread, a container image, a team or a feature, and an arrow can mean a function call, a message, a dependency at build time or a data flow. Most confusing architecture diagrams mix these meanings. The fix, known since Philippe Kruchten's "4+1" view model of 1995 and standardised in ISO/IEC/IEEE 42010, is to separate the questions. A logical or functional view shows the main functions and the data flowing between them. A development or module view shows the code units and their dependencies, which is what decides build times, ownership and how changes ripple. A process or runtime view shows processes, threads, queues and timing, which is what decides latency and fault containment. A deployment or physical view shows which software runs on which chip, core, partition and network. Scenarios (the "+1") walk through the views to check that they fit together.

The levels of zoom are a second dimension. The C4 model by Simon Brown names four of them: the context of the whole system with its users and neighbouring systems, the containers (separately running or deployed things: processes, applications, databases; in an ECU, also the chips and partitions), the components inside one container, and the code. Each level is a separate diagram for a separate audience: the context for customers and system engineers, containers for the integration and safety teams, components for the developers. 3.2The camera ECU at four levels

Context. At the top level the ECU is a black box. Five cameras deliver video over coaxial serializer links; the display receives the composed view either directly or through the head unit; the vehicle sends gear, speed, steering angle and HMI requests on CAN FD and Ethernet; the ECU sends the object list to the parking and braking functions and detections to the ADAS computer; diagnostic testers and the update master reach it through the gateway; the backend receives clips and logs through the telematics unit. This picture is for discussions with the OEM, and it fixes the external interfaces, which are the most expensive to change of all.

Deployment. One level down, the ECU is two chips with very different jobs. The safety microcontroller starts within milliseconds, owns the vehicle buses and the power control, supervises the SoC and hosts the small, safety-relevant monitors. The SoC runs a hypervisor or a single operating system with processes grouped by criticality: a small, simple and well-tested view partition that owns the rear view and surround view, a larger perception partition for the neural networks and tracking, and a platform partition for diagnostics, logging, recording and updates. The groups are separated by memory protection and resource limits, so that a crash or overload in one does not take down another. Section 4.5 shows how this split was chosen.

Components. Inside the vision pipeline, the components are arranged as a dataflow: capture, ISP control, frame distribution, the surround-view renderer, pre-processing, inference, post-processing and tracking. The domain logic in the middle does not know the vendor's SDK; it talks to ports (abstract interfaces for capture, image processing, inference and GPU import), and small adapters at the edge implement them for each SoC and for the PC replay environment (Section 6.3).

Runtime. The runtime view adds what the component view cannot show: which thread or engine runs each stage, at which priority, connected by which queue with which overflow policy, and how long each stage may take. This is the view that answers latency and fault-containment questions, and the one most often missing from real design documents.

Pitfall

The most common diagram error is mixing views in one picture: a box for a thread next to a box for a library next to a box for a chip, with arrows that mean "calls" in one place and "sends frames" in another. Such a diagram cannot be checked, because no question has a clear answer in it. Give every diagram a title that says which view and which level it is, a legend for the arrow types, and keep it to one kind of element per level.

3.3One model, many pictures

The views must agree with each other: every component in the component view must appear in some process of the runtime view and on some chip in the deployment view, and every arrow between components must be realised by some communication path. In AUTOSAR projects this consistency is partly enforced by tools, because the system description in ARXML is one model from which the views and much of the code are generated (AUTOSAR 7.1). Elsewhere it is enforced by discipline: a list of components with their owner, process, thread, interfaces and budgets, kept in the repository next to the code and checked automatically where possible (Section 13.4 shows such checks). How to draw and document these views in a specific notation such as C4, UML or SysML, and how to write the architecture decision records that explain them, is the subject of the planned software quality and documentation chapter.

Talk track

"I describe a system with a few views at different levels: a context diagram for the external interfaces, a deployment view of chips, partitions and processes, a component view with the dependencies, and a runtime view with threads, queues and timing. The runtime view is the one people forget, and it is the one that answers latency and fault-containment questions. Each diagram has one kind of box and a legend, and the views are kept consistent from one model rather than drawn by hand."

4Architecture styles

Architects rarely invent a structure from nothing. They reuse a small number of styles, each a proven way of arranging components and connectors with known strengths and weaknesses. Knowing the styles, and especially what each one costs, turns a vague discussion ("should we use microservices?") into a comparison of trade-offs against the drivers.

4.1Why styles exist, and the monolith

A style is a vocabulary plus a set of rules: which kinds of elements exist (layers, components, filters, services), how they may be connected (calls downwards only, data through pipes, messages over a network), and which properties follow from the rules. Choosing a style is a shortcut to a large set of consistent decisions. Real systems combine several styles at different levels, for example services between ECUs, a process split by criticality inside the SoC, a dataflow pipeline inside the vision process and layers inside each component.

The simplest style is the monolith: one deployable unit, usually one process, with all functions inside. It has real advantages: function calls instead of messages, one address space so that frames can be passed by pointer, one build and one start-up, simple debugging, and no network or serialisation cost. A modular monolith keeps these advantages and adds internal boundaries: modules with clear interfaces and enforced dependency rules, but still one process. Its weakness is that it is one failure domain and one release unit: a null-pointer dereference in the recorder takes down the rear view, a memory leak anywhere starves everything, a change to one function means re-validating and re-releasing all of them, and every team works in the same binary. For a small ECU these costs are acceptable. For the camera ECU, with a safety-relevant view next to a large, fast-changing perception stack, they are not, which is where the before and after in Section 4.5 starts.

4.2Layers, and ports and adapters

A layered architecture stacks components so that each layer offers services to the one above and uses only the one below. The AUTOSAR Classic stack is the textbook case: application components, the RTE, services, the ECU abstraction and the microcontroller abstraction (AUTOSAR 6.1); so is the network stack of an operating system. Layers buy portability and replaceability: you can swap the microcontroller by replacing the bottom layer. They cost some performance (each layer adds a call and often a copy), and they tend to accumulate "layer bypass" shortcuts when a higher layer needs a detail that the layer in between hides. A strict layering forbids bypasses; a relaxed layering allows calls to any lower layer, which is more practical and harder to keep tidy.

The hexagonal architecture, also called ports and adapters (Alistair Cockburn, 2005), turns the layers inside out. The domain logic (for the ECU: view selection, stitching geometry, tracking, the rules of the parking function) sits in the middle and defines the interfaces it needs, the ports: "give me the next frame of camera 2", "run this network on this tensor", "send this object list". Technology sits at the edge as adapters that implement those ports: a V4L2 or vendor capture adapter, an NPU runtime adapter, a SOME/IP publisher adapter, and also a file-replay adapter and a fake for unit tests. The important difference from layers is the direction of dependency: the domain does not depend on the platform, the platform adapters depend on the domain's interfaces. That is the dependency inversion principle applied to the whole system (Section 6.3), and it is what makes two of the ECU's drivers achievable: portability to the next SoC and bit-exact replay on a PC.

Interesting detail

Clean architecture, onion architecture and hexagonal architecture are essentially the same idea under different names: dependencies point inwards towards the domain, and the outer rings (frameworks, drivers, databases, user interfaces) are replaceable details. In embedded code the "framework" that must stay at the edge is usually the silicon vendor's SDK and the middleware, which change with every hardware generation, while the domain logic lives for many years.

4.3Components, and pipes and filters

A component-based architecture builds the system from components with explicitly declared provided and required interfaces, which are connected and deployed by configuration rather than by code. AUTOSAR software components with their ports, and the RTE that connects them according to the system description, are the automotive example (AUTOSAR 3.1). The style shifts work from programming to configuration and makes the system analysable by tools: you can check that every required port is connected, compute data flows and generate the glue. Its cost is tooling and the indirection between what the code says and what actually happens at run time.

A pipes-and-filters or dataflow architecture is the natural style for sensor processing. Each filter (capture, ISP, undistortion, pre-processing, inference, post-processing, tracking) reads items from its input, transforms them and writes them to its output; pipes connect the filters and buffer items between them. Filters do not know each other, which makes them easy to test, reorder, replace and distribute over threads, cores and accelerators. The style makes throughput and latency visible as properties of the graph: throughput is set by the slowest filter, latency by the sum of the filters plus the waiting in the pipes. The concurrency chapter shows such a pipeline for five cameras with its queues and policies (Concurrency 8.3). Two design rules from there are architectural rather than coding rules: frames never move, only references to pooled buffers travel through the pipes, and every pipe is bounded with an explicit policy for when it is full.

4.4Service-oriented architecture and microservices

In a service-oriented architecture, functions are offered as services with a defined interface (methods, events and fields), found at run time through service discovery, and used over a network or local transport without the client knowing where the provider runs. In vehicles this is SOME/IP or DDS between ECUs and ara::com on the Adaptive Platform (Networks 8.2, AUTOSAR 9.1). It decouples location: the object-list service can move from the camera ECU to a central computer without changing its clients. It also makes the in-vehicle network carry the interfaces that used to be hidden inside one ECU, so the versioning and compatibility of those interfaces become a system-wide concern (Section 5.4).

Microservices push the idea further: many small services, each owning its own data, each deployed, scaled and released independently by one team, communicating over the network. The term comes from large web companies (James Lewis and Martin Fowler described it in 2014), and its main benefit there is organisational: hundreds of teams can release independently. The costs are distribution itself (every call can fail, time out or arrive twice; Section 9), operational complexity (deployment pipelines, service meshes, tracing) and data consistency across services. A common lesson from the web world is that many organisations adopted microservices for problems that a well-structured modular monolith would have solved more cheaply.

Inside one ECU, microservices in the cloud sense rarely make sense. The hardware is fixed, so there is nothing to scale out; the data are large (a 3-megapixel frame is 4.4 MB), so serialising them between services is too expensive; and every process costs start-up time, memory and a share of the safety argument. What does make sense inside the ECU is a small number of processes split along failure domains and criticality, with zero-copy data paths between them, and services towards the rest of the vehicle. The question is never "monolith or microservices" but "where are the boundaries, and what does each boundary buy and cost".

Talk track

"A process boundary buys fault containment, independent release and resource limits; it costs a copy or a shared-memory protocol, a context switch, start-up time and an interface to version. Inside an ECU I draw process boundaries along failure domains and criticality, not along functions, and I keep frames zero-copy across them. Between ECUs I use services, because there the location of a function really does change between vehicle generations."

4.5Choosing for the camera ECU: before and after

The first prototype of the camera ECU was, like most prototypes, one process: a capture loop, the renderer and the neural networks in one binary, sharing global state, so that anything could reach anything. It worked on the bench and was fast. Measured against the drivers of Section 2.4 it fails three of them: a crash in perception kills the rear view (fault containment), the view cannot be certified to ASIL B without certifying the whole binary (safety), and the vendor SDK calls are spread across the code (portability). The redesign splits it along failure domains and criticality.

In the new design the view process owns capture, ISP control and the display path. It is small, has few dependencies, runs at high priority and is the only part that needs the highest integrity, so its safety argument stays manageable. It publishes every captured frame into a shared pool of buffers, which the perception process and the recorder read through read-only handles with reference counting (dma-buf file descriptors on Linux, the vendor's equivalent elsewhere). If perception crashes, the view keeps running and the platform supervisor restarts perception; if perception is too slow, it simply misses frames, because the view never waits for it. Perception publishes its object list over SOME/IP to the vehicle and, through a local channel, the guidance overlays back to the view. The platform services (diagnostics, logging, update, recording upload) run in a third group with strict CPU and memory limits. On the MCU, a small monitor checks that the displayed image is fresh (frame counters and timestamps embedded by the view, checked against the vehicle time) and that the SoC is alive.

Pitfall

A process boundary only contains faults that stay inside a process. Two processes that share a GPU, a camera driver or a buffer pool still interfere through those shared resources: a perception job that hangs the GPU also freezes the view. Fault containment therefore needs the runtime and deployment views together: who may submit work to which engine at which priority, who owns each buffer and what happens when a reader never returns it (Section 10.6), and what the MCU does when the view stops (Functional safety 6).

5Interfaces, API design and contracts

Interfaces are where architecture meets organisation. Every arrow between two components owned by different teams, or by different companies, is a contract that both sides depend on and neither can change alone. Good interfaces make independent work possible; bad ones make every change a negotiation.

5.1A contract is more than a signature

A function signature or a message definition says what can be called and which types travel. It says nothing about most of what goes wrong between components. The contract of an interface has several parts, and the ones that are not in the signature are the ones that break integrations (Production integration 2.2).

Hyrum's law (named after a Google engineer) is the reason to write all of this down: with enough users, every observable behaviour of an interface will be depended on by somebody, whether it was promised or not. If frames have always arrived in order, some consumer relies on it; if a call has always returned within 1 ms, some caller does not handle the slow case. The only defence is to specify what is promised, test it at the boundary with contract tests, and, where possible, make unpromised behaviour vary (for example by shuffling the order of independent callbacks in test builds) so that nobody can come to rely on it.

5.2Designing an API that is hard to misuse

A good API makes the correct use easy and the incorrect use impossible or at least obvious. The question to ask of every interface is: what is the most likely mistake a user will make, and does the interface prevent it? For a frame interface in C++, the likely mistakes are forgetting to release a frame (the pool runs dry and capture stalls), using a frame after releasing it (the buffer has been refilled with a newer image), confusing units or time bases, and writing into a buffer that other consumers are reading. The first version below allows all of them.

// Before: a C-style interface. Every mistake compiles.
struct FrameInfo { void* data; int w, h, stride; long ts; int buf_index; };
int  cam_get_frame(int camera, FrameInfo* out, int timeout);   // timeout in what unit? ts in what base?
void cam_release_frame(int camera, int buf_index);             // forget it and capture stalls
// After: ownership, units and mutability are in the types.
struct Nanos { std::int64_t v; };                              // vehicle time base (gPTP), not CLOCK_MONOTONIC

class FrameRef {                                               // move-only; releases the buffer in its destructor
public:
    FrameRef(FrameRef&&) noexcept;
    FrameRef& operator=(FrameRef&&) noexcept;
    FrameRef(const FrameRef&) = delete;
    ~FrameRef();                                               // returns the buffer to the pool
    std::span<const std::byte> luma() const;                   // read-only view: consumers cannot write
    ImageDesc desc() const;                                    // width, height, stride, format
    std::uint64_t sequence() const;
    Nanos exposure_mid() const;
};

class ICameraSource {                                          // a port owned by the domain (Section 6.3)
public:
    virtual ~ICameraSource() = default;
    virtual std::expected<FrameRef, CaptureError>
        next(CameraId cam, std::chrono::milliseconds timeout) = 0;
};

The second version uses the type system to carry the contract. A FrameRef cannot be copied, so there is exactly one owner; its destructor returns the buffer, so it cannot be forgotten (RAII, C++ 5); it hands out read-only views; time and timeouts have types with units; and errors are values (std::expected, C++23) rather than magic return codes or exceptions crossing a module boundary. The interface is also narrow: it offers what the consumers need and nothing that would expose the vendor's buffer structures. Narrow interfaces are easier to keep stable, easier to implement twice (for the SoC and for replay) and easier to test.

Pitfall

A "convenient" API that exposes the implementation (for example a getter that returns the vendor's native buffer handle "for performance") will be used by someone within weeks, and from then on the vendor's type is part of your public interface. If a consumer genuinely needs a native handle, for example to import a buffer into the GPU, give it a dedicated, narrow port for exactly that operation, implemented inside the platform adapter, rather than exposing the handle to everyone.

5.3Data interfaces: messages, schemas and zero-copy

Between processes and ECUs the interface is a message format rather than a function. Messages need a schema in a machine-readable form (ARXML service interfaces, Franca IDL, OMG IDL for DDS, protobuf or FlatBuffers), generated code on both sides, and explicit rules about byte order, alignment, optional fields and units. For small, frequent data such as the object list (64 objects of about 44 bytes, under 3 KB per message, 0.7 Mbit/s at 30 Hz), serialisation is cheap and the schema's job is compatibility. For frames, the data are too big to serialise: four surround cameras produce about 530 MB per second as NV12 images. Their interface splits into a small descriptor message (sequence number, timestamp, format, buffer identity) that travels by IPC, and the payload, which stays in shared, pre-allocated buffers. The contract then also covers how a consumer gets access to the buffer, how long it may hold it and how producer and consumer synchronise with the accelerators (fences) (GLES 6).

A design rule that pays off is to separate the data plane (frames, high rate, zero-copy, fixed format) from the control plane (start, stop, configuration, mode changes, low rate, flexible and versioned). Mixing them, for example by sending configuration inside frame descriptors or frames through the service middleware, makes both worse.

5.4Versioning and backward compatibility

Interfaces change, and in a vehicle the two sides of an interface are often updated at different times: the camera ECU gets an over-the-air update in March, the parking ECU in June, and some cars skip an update altogether. The architecture must therefore define which combinations work, and the rules that make most changes safe. The usual convention is semantic versioning (SemVer): a major version for incompatible changes, a minor version for compatible additions, a patch version for fixes that do not change the interface. SOME/IP carries a major interface version in every message and both major and minor versions in service discovery, so a client can find a provider with a compatible version (AUTOSAR 12.4).

What counts as compatible depends on which side is updated first. A change is backward compatible if new providers still serve old consumers, and forward compatible if old providers can serve new consumers (or old consumers can read data from new producers). The rules for message formats follow from that.

Two principles make evolution smoother. The tolerant reader accepts what it can understand and ignores the rest (unknown fields, extra enum values), while writers are strict about what they send, an idea usually traced to Jon Postel's robustness principle. And deprecation is a process with dates: announce, keep both versions running in parallel for a defined number of releases, measure who still uses the old one, then remove it. A compatibility matrix, checked by the update system before installing anything, records which versions of which ECUs work together (Production integration 7.5).

Numbers

Vehicles in the field run mixed versions for years: OTA campaigns reach most cars within weeks, but some cars are parked, offline or decline updates. A service interface between two ECUs must therefore usually support at least the previous major version for the life of a vehicle generation, which in practice means designing every message so that it can be extended without a major version change.

5.5API and ABI at library boundaries

Inside one ECU, interfaces between libraries delivered in binary form, such as a vendor's inference runtime or a supplier's perception library, add a second kind of compatibility: the ABI (application binary interface), meaning the layout of types, the calling convention, name mangling and the vtable layout. A change that is harmless in source code, such as adding a private member to a class, changes its size and breaks every binary compiled against the old header. The build chapter explains sonames, symbol versioning and how libraries signal ABI changes (Build 6.4); the C++ chapter explains why C++ ABIs are fragile (C++ 11). Architecturally there are three common answers: deliver source or rebuild everything together (the usual choice inside one ECU release), hide the implementation behind a pointer (the pimpl idiom) so that the class layout never changes, or put a plain C interface at the boundary, with opaque handles and functions, which is the most stable binary contract there is and the reason most plugin systems and vendor runtimes expose one (Build 4.5).

Talk track

"An interface contract has more than a signature: units and time bases, ownership and lifetime, threading, timing, errors, ordering and a version. I put as much of it as possible into the types, a move-only frame handle that releases itself, typed durations, errors as values, and test the rest with contract tests at the boundary. For evolution I use semantic versioning with tolerant readers: additions are minor versions, removals go through a dated deprecation, and identifiers are never reused."

6Modularity, SOLID and dependency management

Architecture at the level of processes and chips is only half of the job. The other half is the structure of the code itself: which modules exist, what each one knows about the others, and in which direction the dependencies point. That structure decides how far a change ripples, how long a build takes, and whether the system can be tested without the hardware.

6.1Coupling and cohesion

Two measures describe most of what makes code easy or hard to change. Cohesion is how strongly the parts inside a module belong together: a module that handles everything about camera calibration (loading, validating, applying, reporting) is cohesive; a "utils" module with string helpers, a CRC function and a thread pool is not. Coupling is how much a module depends on others: on their types, their behaviour, their timing, their data layout. The goal is high cohesion and low coupling, because then a change usually stays inside one module, and a module can be understood, tested and replaced on its own.

Coupling comes in degrees, and it helps to name them. Coupling to an abstract interface is the weakest; coupling to a concrete type is stronger; coupling to internal data (reaching into another module's structures) or to shared global state is strong; coupling to timing or order ("this must run after that has initialised") is the strongest and the hardest to see. Dependencies also have a direction, and that direction decides who must change when something changes. If the tracking module depends on the vendor's inference SDK, every SDK update can break tracking. If both depend on an interface owned by the tracking side, the SDK can change behind its adapter.

6.2SOLID in an embedded C++ code base

SOLID is the name Robert C. Martin's five design principles for object-oriented code became known by. They are not rules to apply mechanically but five ways of keeping coupling low and cohesion high, and each has a concrete meaning in a perception code base.

The single responsibility principle says that a module should have one reason to change, that is, serve one actor or one concern. A CameraManager class that configures the serializer, applies the ISP tuning, decides the view layout and writes diagnostic events changes whenever the hardware team, the image-quality team, the HMI team or the diagnostics team changes something. Split along those reasons, each part changes for one team only.

The open-closed principle says that a module should be open for extension but closed for modification: adding a new camera type, a new inference backend or a new view should mean adding code, not editing working code. In practice this means designing the variation points deliberately: an interface for inference backends registered in a factory (Section 7.2), a table of camera descriptions read from configuration rather than a switch statement in ten places.

The Liskov substitution principle (after Barbara Liskov) says that every implementation of an interface must be usable wherever the interface is expected, without the caller noticing. Formally, an implementation may weaken preconditions and strengthen postconditions, never the reverse. A replay camera source that returns frames faster than 30 Hz, or that never returns a timeout, violates the contract that real code was written against; tests pass on the PC and the real system fails. Substitutability is about behaviour, not about whether the code compiles.

The interface segregation principle says that clients should not depend on methods they do not use. A single IPlatform interface with forty methods for capture, display, power, temperature and storage forces every test fake to implement all forty and couples every user to every change. Small role interfaces (ICameraSource, IInference, IDisplaySink) keep dependencies precise.

The dependency inversion principle says that high-level policy should not depend on low-level detail; both should depend on abstractions, and the abstractions belong to the high-level side. It is the most important of the five for embedded architecture, because the low-level details (silicon SDKs, drivers, middleware) are the parts that change with every hardware generation, and the next section shows it in action.

Pitfall

SOLID applied without judgement produces the opposite of what it promises: an interface for every class, factories for objects that are only ever created once, and a call path through six indirections to add two numbers. Introduce an abstraction when there is a real second implementation (another SoC, a replay source, a test fake) or a real reason to change independently. In hot loops, prefer compile-time variation (templates, concepts) over virtual calls (Section 7.4).

6.3Dependency inversion: keeping the vendor SDK at the edge

In the prototype, the perception code calls the SoC vendor's SDK directly: it includes the vendor's camera header, allocates buffers with the vendor's allocator, passes the vendor's buffer type to the vendor's inference runtime and imports it into the GPU with vendor-specific extensions. It works, and it means that the vendor's types appear in hundreds of files. When the next programme chooses another SoC, every one of those files changes, and nothing can be tested on a PC because the SDK only exists for the target.

After the inversion, the domain modules (view logic, pre- and post-processing, tracking, the parking rules) depend only on ports that the domain itself defines: ICameraSource, IIspControl, IInference, IGpuImport, IObjectSink. The vendor-specific code is confined to adapter libraries, one per platform, and a replay adapter that reads recorded frames and a reference CPU inference backend form the "PC platform". Two drivers from Section 2.4 follow almost directly: porting to a new SoC means writing a new set of adapters, and bit-exact replay means running the same domain code against the replay adapters.

Inverting dependencies is not free. Every port is an interface that must be designed well enough to fit the next SoC, which you do not know yet. Design ports around what the domain needs, in the domain's vocabulary ("a frame with these properties", "run this model"), not around what the current SDK offers; and accept that the first port will need one revision when the second platform arrives. The GLES chapter gives the same advice for graphics: abstract the pieces that actually vary, not every API call (GLES 22).

Interesting detail

Bit-exact replay is a strong test of the architecture, because it fails on every hidden dependency: code that reads the system clock instead of the frame timestamp, a thread race that changes the order of detections, a random seed taken from the time, an uninitialised variable, a floating-point reduction whose order depends on the number of threads. Making replay deterministic forces those dependencies into the open, which is good for the real system too. Where the target accelerator computes differently from the PC (quantised arithmetic on the NPU, for example), the comparison is done at the level of the domain outputs against agreed tolerances (Edge AI 10.1).

6.4Dependencies between modules and packages

At the level of modules, libraries and packages, three principles keep the dependency graph healthy. The acyclic dependencies principle says that the graph of module dependencies must have no cycles. A cycle (tracking depends on calibration, calibration depends on diagnostics, diagnostics depends on tracking) turns the modules into one unit: they must be built, tested and released together, and nobody can understand one without the others. The stable dependencies principle says that dependencies should point towards modules that change less often, so that volatile modules depend on stable ones and not the reverse. The stable abstractions principle adds that stable modules should be abstract (mostly interfaces), so that being depended on does not prevent extension. Together they produce the shape of Figure 6.1: stable, abstract ports in the middle, volatile, concrete adapters and applications around them.

These rules only hold if the build enforces them. In CMake, each module is a target that declares its dependencies, and PRIVATE versus PUBLIC linkage controls whether a dependency leaks to the module's users (Build 5.5); in Bazel, visibility rules forbid unwanted dependencies outright. A small architecture test in CI that reads the dependency graph and fails on forbidden edges (no module outside platform/ may include a vendor header; no cycles; the view process may not link against perception libraries) costs an afternoon and protects the design for years. Such automated checks of architectural rules are called fitness functions (Section 13.4).

External dependencies, such as open-source libraries and vendor SDKs, need the same discipline at the package level: pinned versions with lockfiles, one version of each library in the image, an inventory (SBOM) for licences and security advisories, and an owner who decides on upgrades (Build 6.5, 11.5). Every external dependency is a long-term commitment in a product supported for fifteen years, so the question before adding one is not only "does it work?" but "who will maintain it for us in 2040?".

6.5Composition root and dependency injection without a framework

If modules depend only on interfaces, something must create the concrete objects and connect them. The answer is the composition root: one place, at the start of each process, where the configuration is read, the concrete adapters are created and passed into the domain objects through their constructors. This is dependency injection, and in C++ it needs no framework: constructors that take their dependencies as references or smart pointers are enough. A unit test does the same with fakes, the replay tool with replay adapters, and the ECU with the SoC adapters.

// main() of the perception process: the only place that knows concrete types.
int main(int argc, char** argv) {
    const Config cfg = load_config(argv[1]);                         // cameras, models, budgets
    auto clock    = make_vehicle_clock(cfg);                         // gPTP time base on the target, recording time in replay
    auto cameras  = platform::make_camera_source(cfg, *clock);       // SoC adapter or replay adapter, chosen at build time
    auto backend  = inference_registry().create(cfg.backend, cfg.model);  // factory (Section 7.2)
    auto sink     = platform::make_object_publisher(cfg);            // SOME/IP skeleton or a file writer

    ParkingPerception app{*cameras, *backend, *sink, *clock, cfg.perception};
    return run_until_shutdown(app, cfg.budgets);
}

Construction at start-up also suits embedded constraints: all objects, buffers and threads are created once, before the system reports "ready", and nothing is allocated in steady state (Section 10.3). The alternative, objects that find their dependencies themselves through global registries or singletons, hides the wiring and makes testing and replay much harder, as Section 7.6 shows.

Talk track

"I keep coupling low by pointing dependencies towards stable abstractions that the domain owns: the perception code knows ports like ICameraSource and IInference, and the vendor SDK lives only in adapters. Everything is wired in a composition root in main(), with constructor injection, no framework. The build enforces the rules: no cycles, no vendor headers outside the platform directory, checked in CI. That is what makes both a new SoC and bit-exact PC replay affordable."

7Design patterns in modern C++

Design patterns are named solutions to recurring design problems. Their real value is the name: "this is a strategy", "the registry is a factory" carries a whole design in two words. Modern C++ changes how most of the classic patterns are written, and in a few cases whether they are needed at all.

7.1Why patterns, and how modern C++ changes them

The 1994 book by Gamma, Helm, Johnson and Vlissides (the "Gang of Four") catalogued 23 patterns in three groups: creational (how objects are made), structural (how they are composed) and behavioural (how they interact). The book was written for C++ and Smalltalk of its time, where the only tool for variation was inheritance with virtual functions. Today's C++ offers more: lambdas and std::function for behaviour as a value, templates and concepts for variation at compile time, std::variant and std::visit for closed sets of alternatives, smart pointers for ownership, and RAII for every acquire-release pair (C++ 8). Several patterns shrink from a class hierarchy to a few lines, and the decision between run-time and compile-time variation becomes an explicit design choice.

Senior C++ discussions in automotive almost always come back to the five patterns in this section: factory, observer, strategy, state and singleton. The textbook diagram is the least interesting part. They want to hear what problem the pattern solves, what it costs, how you would write it in modern C++ and where it goes wrong. All code below is excerpted from one file that compiles and runs with g++ -std=c++20 -Wall -Wextra -fsanitize=address,undefined without warnings (tools/write/software-architecture/experiments/patterns.cpp).

7.2Factory: deciding what to create in one place

A factory separates the decision of which concrete type to create from the code that uses it. The perception process needs an inference backend: the NPU runtime on the target, a CPU reference implementation for PC replay, perhaps a GPU fallback. Code that writes new NpuDetector(...) is coupled to the NPU; code that asks a factory for "the configured backend" is not. In modern C++ a factory returns std::unique_ptr, which makes ownership explicit, and the most flexible form is a registry: a map from a name to a creation function, filled at start-up.

using DetectorFactory = std::function<std::unique_ptr<IDetector>(const std::string& model)>;

class DetectorRegistry {
public:
    void add(std::string key, DetectorFactory f) { f_.emplace(std::move(key), std::move(f)); }
    std::unique_ptr<IDetector> create(const std::string& key, const std::string& model) const {
        auto it = f_.find(key);
        if (it == f_.end()) throw std::invalid_argument("unknown backend: " + key);
        return it->second(model);
    }
private:
    std::map<std::string, DetectorFactory> f_;
};

// composition root
DetectorRegistry reg;
reg.add("npu",           [](const std::string& m) { return std::make_unique<NpuDetector>(m); });
reg.add("cpu-reference", [](const std::string&)   { return std::make_unique<CpuReferenceDetector>(); });

The registry makes the system open for extension (Section 6.2): a new backend registers itself without any change to the code that uses detectors. Two cautions apply. Self-registration through static objects in each backend's translation unit is tempting but depends on the linker keeping those objects and on the order of static initialisation, which is unspecified across translation units; registering explicitly in the composition root is boring and reliable. And a factory that throws on an unknown key should be called during start-up only, so that a configuration error stops the process before it reports "ready" rather than in the middle of a drive.

7.3Observer: notifying without knowing who listens

An observer (or publish-subscribe inside a process) lets a subject notify any number of listeners without knowing them: the capture component announces each new frame, and the renderer, perception, the recorder and a statistics module subscribe. It decouples the subject from its listeners, which is why it appears everywhere, from GUI toolkits to ara::com events. In C++ the classic implementation, a list of raw pointers to listener objects, has one notorious failure: a listener is destroyed while the subject still holds its pointer, and the next notification calls into freed memory. The modern implementation ties each subscription to an object whose lifetime the listener controls.

template <class T>
class Signal {
public:
    using Slot = std::function<void(const T&)>;
    class Connection {                          // RAII: the subscription ends when this object dies
    public:
        explicit Connection(std::shared_ptr<Slot> s) : slot_(std::move(s)) {}
    private:
        std::shared_ptr<Slot> slot_;            // the subscriber owns its slot ...
    };
    [[nodiscard]] Connection connect(Slot s) {
        auto sp = std::make_shared<Slot>(std::move(s));
        std::scoped_lock lk(m_);
        slots_.push_back(sp);                   // ... the signal only holds weak references
        return Connection(sp);
    }
    void emit(const T& v) {
        std::vector<std::shared_ptr<Slot>> live;
        {   std::scoped_lock lk(m_);
            std::erase_if(slots_, [](const auto& w) { return w.expired(); });
            for (auto& w : slots_) if (auto s = w.lock()) live.push_back(std::move(s)); }
        for (auto& s : live) (*s)(v);           // call outside the lock
    }
private:
    std::mutex m_;
    std::vector<std::weak_ptr<Slot>> slots_;
};
subscribers 2, hmi 1, recorder 1
after recorder left: subscribers 1, hmi 2, recorder 1

Three design questions matter more than the code. On which thread do listeners run? Here, on the thread that calls emit, so a slow listener delays the subject and every other listener; in a real-time pipeline the subject should only enqueue, and each listener should process on its own thread (Concurrency 6.4). Is it safe to call back while holding a lock? No: a listener that subscribes or emits again would deadlock, which is why the slots are copied under the lock and called outside it. What does the flow of control look like? Observers hide it: reading the subject's code does not tell you what happens when it emits. In small doses this is the point; in large doses, chains of events triggering events become impossible to follow (Section 8.5).

7.4Strategy: one interface, interchangeable behaviour

A strategy encapsulates one of several interchangeable algorithms behind a common interface, so that the user can be configured with any of them: the overflow policy of a queue, the exposure control algorithm, the seam-blending method of the surround view, the tracker's association method. Modern C++ offers three ways to write it, and choosing between them is a real design decision.

// (a) run-time: an interface, chosen by configuration, costs a virtual call
struct IOverflowPolicy {
    virtual ~IOverflowPolicy() = default;
    virtual void push(std::deque<Frame>& q, std::size_t cap, Frame f) = 0;
};
struct DropOldest final : IOverflowPolicy {
    void push(std::deque<Frame>& q, std::size_t cap, Frame f) override {
        if (q.size() == cap) q.pop_front();
        q.push_back(f);
    }
};

// (b) compile-time: a template parameter, no indirection, can be inlined
struct DropNewestPolicy {
    static void push(std::deque<Frame>& q, std::size_t cap, Frame f) { if (q.size() < cap) q.push_back(f); }
};
template <class Policy> class FrameQueue { /* ... */ void push(Frame f) { Policy::push(q_, cap_, f); } };

// (c) a callable: the lightest form when the strategy is a single function
using ExposureStrategy = std::function<double(double mean_luma)>;

The run-time form is right when the choice comes from configuration or must change while running, or when implementations live in different libraries. The compile-time form is right in hot paths (per pixel, per detection) and when the choice is fixed per build, and with C++20 concepts the requirements on the policy can be stated and checked. The callable is right when the strategy is one function without state of its own. A cost that is easy to miss is code size and build time: every template instantiation is new code, which matters on targets with limited flash and in large code bases.

7.5State: making the life cycle explicit

A component whose behaviour depends on its history is a state machine whether you write it as one or not. Without an explicit model, the state lives in a handful of booleans (started, locked, error, retrying) whose combinations nobody has enumerated, and the bug is always in the combination nobody thought of. The state pattern makes the states and transitions explicit. The camera channel of the ECU is a good example: it is off, starting (with a limited number of attempts to lock the serializer link), streaming, degraded (frames missing, but not yet given up) or failed.

The classic GoF implementation uses one class per state with virtual handlers. In modern C++, when the set of states is closed and known, std::variant is simpler and safer: each state is a small struct that carries exactly the data valid in that state (only Starting has an attempt counter, only Degraded has a count of missed frames), and the whole transition table is one function.

struct Off {};  struct Starting { int attempt; };  struct Streaming { std::uint64_t last_seq; };
struct Degraded { const char* reason; int missed; };  struct Failed { const char* reason; };
using State = std::variant<Off, Starting, Streaming, Degraded, Failed>;
using Event = std::variant<PowerOn, LinkLocked, FrameOk, Timeout>;

State on(const State& s, const Event& e) {
    return std::visit(overloaded{
        [](const Off&, const PowerOn&)          -> State { return Starting{1}; },
        [](const Starting&, const LinkLocked&)  -> State { return Streaming{0}; },
        [](const Starting& st, const Timeout&)  -> State {
            return st.attempt < kMaxStartAttempts ? State{Starting{st.attempt + 1}} : State{Failed{"link never locked"}}; },

7.6Singleton, and why it causes problems

A singleton guarantees that a class has exactly one instance and gives global access to it. It is the most used and most criticised pattern of the catalogue. The implementation is easy in modern C++: a function-local static is initialised exactly once, thread-safely, since C++11 (the "Meyers singleton").

class SystemClock {
public:
    static SystemClock& instance() { static SystemClock c; return c; }   // thread-safe initialisation since C++11

private:
    SystemClock() = default;

The problems are not in the implementation but in what global access does to the design. A singleton is a hidden dependency: nothing in the signature of is_stale_hidden says that it reads a clock, so a reader cannot see it and a test cannot replace it; the replay tool of Section 6.3 cannot make it use recording time, so replay stops being deterministic. It is global mutable state: any code anywhere can change it, so reasoning about one function requires knowing the whole program, and concurrent access needs locking that every caller pays for. It creates order problems: singletons that use other singletons in their constructors or destructors depend on initialisation and destruction order, the source of the "static initialisation order fiasco" across translation units, and of crashes at shutdown when one singleton's destructor uses another that is already gone. It leaks between tests: state from one test survives into the next. And it bakes in an assumption that may stop being true: "there is only one camera system", "there is only one clock", until the replay tool needs two.

The alternative is to create the one instance in the composition root and pass it to whoever needs it, as the StalenessMonitor does. There remain legitimate uses of global objects: a logger that every function may use and that never affects behaviour, or a hardware register block that physically exists once. Even those are better behind an interface that can be swapped in tests, and they should be immutable after start-up wherever possible.

8Communication: messages, events and publish-subscribe

How components talk decides how tightly they are coupled, in time as well as in code. A function call ties the caller to the callee's speed and failures; a message or an event loosens that tie and introduces queues, ordering questions and new ways to fail. Choosing the style of each connection is one of the most consequential decisions in a design.

8.1Calls, messages and events: three kinds of coupling

Three basic styles of interaction cover nearly every connection in a system. A call (a function call, a remote procedure call, a SOME/IP method) is a request that waits for an answer: the caller knows the callee, and both must be alive and responsive at the same time. A message (a command or a document sent to a queue) is addressed to a receiver but does not wait: the sender continues, and the receiver processes it when it can. An event is a statement that something has happened ("frame 4711 of camera 2 is ready", "reverse gear engaged"), published without knowing who, if anyone, listens.

The styles differ along two dimensions of coupling. Temporal coupling: must both sides be available at the same moment? A call needs that; a message or event through a queue does not. Knowledge coupling: does the sender know who receives? A call and a message do; an event does not. Less coupling means more independence and more flexibility, and also less visible control flow, more places where data waits and more failure modes to handle. A good design chooses per connection: a call where the caller genuinely needs the answer now (reading a calibration at start-up), a message where work is handed over (a clip to the uploader), an event where a fact is broadcast to whoever cares (a new frame, a mode change).

8.2Message passing and queues

Message passing between threads and processes, instead of shared state protected by locks, is the backbone of most robust embedded designs. Each component owns its state and is driven by the messages it receives, so there are no data races on that state and each component can be tested by feeding it messages. The queue between two components is where the architecture makes its timing decisions: how deep the queue is, what happens when it is full, and who owns the data while it waits. The concurrency chapter shows the four overflow policies (block the producer, drop the newest, drop the oldest, keep only the latest) with an interactive simulation (Concurrency 8.2); architecturally the rule is that every queue is bounded and every policy is chosen per data type. Frames for the display take the latest; frames for the recorder must not be lost while the clip is being written and get a deeper queue with an alarm when it fills; commands from the HMI are few and must all be processed in order.

For large data the message carries a reference, not the data: a buffer index or file descriptor, plus a reference count or a lease with a deadline, so that a consumer that hangs cannot hold a buffer forever. That makes the buffer pool a shared resource with a single owner (Section 10.6), and it makes the buffer handle part of the interface contract (Section 5.3).

8.3Publish-subscribe: topics, quality of service and discovery

Publish-subscribe generalises events across processes and ECUs. Publishers write to named topics (or offer services with events), subscribers declare interest, and a middleware connects them. Discovery lets them find each other at run time, so a new subscriber, such as a data logger in a test vehicle, can be added without touching the publisher. In vehicles, SOME/IP events with service discovery and DDS topics are the two main implementations, and the networks chapter compares them with signal-based communication (Networks 8.4); ara::com wraps them on the Adaptive Platform (AUTOSAR 9.2).

The architecturally important part of publish-subscribe is quality of service: the promises the middleware makes per topic. Is delivery reliable or best-effort? Does a late subscriber receive the last value (a "field" in SOME/IP, the TRANSIENT_LOCAL durability of DDS) or only future events? How many samples are kept per subscriber (history depth)? What deadline is expected between samples, and who is told when it is missed? A gear-position topic needs the last value for late joiners and a deadline monitor; an object list at 30 Hz needs best-effort delivery of the newest sample, because a retransmitted old list is worse than none; a diagnostic request needs reliable, ordered delivery. Choosing these per topic is a design decision that belongs in the interface contract, not a middleware default.

Pitfall

Publish-subscribe makes adding a subscriber free for the publisher's code, but not for the system. Every subscriber to the 30 Hz object list is another copy on the network or another reader on shared memory, and a subscriber that is slow or misconfigured (reliable delivery with a deep history on a high-rate topic) can create back-pressure that slows the publisher. Keep a list of who subscribes to what, and treat a new subscriber on a high-rate topic as a change that needs a budget.

8.4Event-triggered versus time-triggered

Embedded systems have a second choice that cloud systems rarely face: whether a component runs when data arrives (event-triggered) or at fixed times (time-triggered). Consider the chain from parking perception on the SoC (stage A, started by each camera frame) to the parking arbitration on the safety MCU (stage B), which decides whether to warn or brake. Event-triggered, B runs as soon as A's result arrives: minimum latency, but every variation of A's execution time passes straight into the timing of B's output. Time-triggered, B runs every few milliseconds on the MCU's static schedule and reads the newest result: the MCU's schedule stays predictable, but the result waits for B's next period, so latency grows and still varies. The third option, logical execution time (LET), fixes the timing completely: each task reads its inputs at the start of its period and publishes its outputs at the end, regardless of when it actually finished. LET comes from the Giotto research language of the early 2000s and is used in multi-core automotive control software because it makes data flow deterministic and independent of how the tasks happen to be scheduled.

With the default settings (A between 12 and 24 ms, MCU period 10 ms) the event-triggered chain has a mean latency of 20.5 ms and a jitter of 12.9 ms, which is exactly the spread of A plus B. Sampling adds an average of half a period: mean 25.5 ms, jitter 21 ms. LET is the slowest, with a mean of 46.7 ms, because A's result is held until the end of its 33 ms frame period and B's until the end of its own period; but its jitter of 6.7 ms comes only from how the 33.3 ms and 10 ms periods line up, and with a harmonic period of 8.33 ms it is exactly zero (a constant 41.7 ms). Making A slower changes nothing in the LET row as long as A still fits in its period.

Which one is right depends on the driver. For a display, low latency matters and some jitter is invisible, so event-triggered is natural. For a control loop or a safety monitor on the MCU, predictability is worth more than the last few milliseconds: a controller tuned for a fixed delay works badly with a varying one, a monitor with a fixed timing can be analysed and certified, and a test that reproduces a field issue needs the same data to reach the same task in the same cycle. The architecture can also mix them: event-triggered within the SoC pipeline, LET at the boundary to the MCU.

Why it matters

Jitter, not average latency, is what breaks downstream components. A tracker that predicts object positions forward to the current time needs to know how old its input is; a vehicle controller assumes a delay; a fusion step must pair data from the same moment. Every queue, every sampling step and every variable execution time adds jitter, and only an explicit triggering design, with timestamps on every datum, keeps it under control.

8.5The pitfalls of event-driven systems

Event-driven architectures are flexible and loosely coupled, and they fail in characteristic ways. The control flow becomes invisible: no single piece of code says what happens after reverse is engaged; the behaviour emerges from which components subscribe to which events. Document the important flows as sequence diagrams and test them end to end. Event storms appear when events trigger events: a mode change triggers a reconfiguration in three components, each of which publishes a state change that triggers further reactions, and a single input produces hundreds of messages or an oscillation. Make reactions idempotent, rate-limit, and prefer state (the current mode as a field) over events (a stream of "mode changed" messages) where consumers only need the current value. Ordering across topics is not guaranteed: "camera 2 failed" may arrive after the object list computed without camera 2. Put the information a consumer needs to interpret a message into the message itself (the set of cameras used, a configuration version), rather than relying on the order of separate messages. And a lost event is lost forever unless the design re-sends state periodically, which is why automotive interfaces often send cyclic messages with the full state even when nothing changed.

Talk track

"I choose the interaction style per connection: calls when the caller needs the answer now, messages to hand over work, events to broadcast facts. Every queue is bounded with a policy per data type, frames travel by reference, and every message carries its timestamp and the context needed to interpret it. Between the SoC and the safety MCU I'd use logical execution time or at least a fixed schedule, because a predictable delay is easier to control, test and certify than a fast but jittery one."

9Distributed systems: when parts fail independently

As soon as two parts of a system run on different processors and talk over a link, a new class of problems appears: one side can fail while the other keeps running, messages can be lost, delayed or duplicated, and there is no shared clock to say what happened first. These problems are the core of distributed systems, and a vehicle is one.

9.1Why the camera ECU is a distributed system

Even inside one housing, the camera ECU consists of two computers, the SoC and the safety MCU, connected by SPI or Ethernet, each of which can reset independently. Around it are the parking ECU, the ADAS computer, the gateway, the head unit, and through the telematics unit a backend in a data centre. Each of these has its own power state, start-up time, software version and failure modes. The defining property of a distributed system is partial failure: some parts work while others do not, and the parts that work cannot know for sure what happened to the others. A function call either returns or the whole program crashes; a request over a link can be lost on the way, processed but its reply lost, delayed beyond the timeout, or processed twice.

A classic list of mistakes that newcomers to distributed systems make is the "fallacies of distributed computing" (from L. Peter Deutsch and colleagues at Sun in the 1990s): assuming that the network is reliable, that latency is zero, that bandwidth is infinite, that the network is secure, that the topology does not change, that there is one administrator, that transport cost is zero and that the network is homogeneous. Every one of them has an automotive version: a connector that loses contact on cobblestones, a switch queue that adds milliseconds under load, an object list that does not fit on a CAN FD bus, a forged message from a compromised infotainment unit, an ECU that is missing in a variant, two suppliers with two configurations, a serialisation cost that eats the CPU budget, and big-endian and little-endian processors on the same network.

9.2Failure models and how failures are detected

Design starts by stating which failures the system must tolerate. The usual failure models, from mild to severe, are: crash-stop (a component stops and stays stopped), crash-recovery (it stops and comes back, possibly having lost its memory), omission (messages are lost), timing (responses arrive too late, which for a real-time system is as bad as not at all), and arbitrary or Byzantine faults (a component sends wrong, corrupted or inconsistent data). Cloud systems mostly design for crash and omission faults; automotive safety engineering also has to handle corrupted and delayed data, which is why safety-relevant messages carry end-to-end protection with a CRC, a sequence counter and a timeout (Functional safety 4.4).

The fundamental difficulty is that a remote failure cannot be observed directly. If the parking ECU receives no object list, the camera ECU might have crashed, be slow, be restarting, or the message might be lost on the way; from the receiver's side these look identical. All a component can do is suspect a failure after a timeout, using heartbeats, alive counters or the cyclic messages themselves. That makes every failure detector a trade-off between detection time and false alarms. A timeout of 50 ms on a 30 Hz object list detects a dead sender within two frames but raises a false alarm whenever a single message is delayed by a busy switch; a timeout of 500 ms rarely raises false alarms but leaves the parking function on stale data for half a second. The timeout should be derived from the measured latency distribution of the link plus the reaction time the safety goal allows, and the reaction to a suspected failure should be safe even if the suspicion is wrong.

9.3Timeouts, retries and idempotence

When a request gets no reply, the caller can give up or try again. Trying again is the right reaction to transient faults, but it raises a question that every distributed design must answer: what happens if the first request was processed and only the reply was lost? There are three possible delivery guarantees. At most once: never retry; a message may be lost but is never processed twice. At least once: retry until acknowledged; nothing is lost, but duplicates are possible. Exactly once delivery is impossible over an unreliable link in general, because the sender can never be sure whether a lost acknowledgement means "not processed" or "processed, reply lost". What systems actually implement is exactly-once processing: at-least-once delivery combined with a receiver that recognises and discards duplicates, or with operations that give the same result when applied twice.

An operation is idempotent if applying it twice has the same effect as applying it once. "Set the view to front" is idempotent; "toggle the view" is not. "Store clip 7f3a with this content" is idempotent; "append this clip to the upload list" is not. The design rule is to make commands state-setting rather than state-changing where possible, and where that is not possible to give each request a unique identifier that the receiver remembers for long enough to detect retries. The upload of recorded clips from the ECU to the backend uses both: each clip has a content hash as its identifier, and the upload is resumable in chunks, so a retry after a broken connection neither loses data nor creates duplicates.

Timeouts themselves need a design. A timeout that is too short creates retries for requests that were merely slow, adding load exactly when the system is busy. A timeout that is too long blocks the caller. A useful rule is to set it slightly above the 99th or 99.9th percentile of the measured response time, and to propagate a deadline rather than a timeout through a chain of calls: if the HMI must have an answer within 300 ms, the camera ECU should not start a 200 ms sub-request at 250 ms.

9.4Retry storms and how to avoid them

Retries help when failures are rare and independent. They do harm when failures are caused by overload, because then every retry adds load to the component that is already failing. The effect multiplies through layers: if an HMI application calls a vehicle service, which calls a camera service, which calls a calibration store, and each of the three layers makes up to three attempts, a dead calibration store receives 3 × 3 × 3 = 27 calls for every user action. The overloaded component never recovers, because the retries keep it overloaded; this is a retry storm, and it has taken down large web services many times.

The figure shows both faces of retrying. With a 1 % chance of failure per attempt, three attempts per layer cost 1 % extra load and almost eliminate failures. With the bottom service down, the same configuration sends 27 calls to it per user request, and the user still waits 5.4 s (27 attempts × 200 ms) before getting an error. Four layers with four attempts reach 256 calls and 51 s. The remedies are well known from large web systems and apply in vehicles just as well. Retry at one layer only, usually the one closest to the failing resource, and let the others fail fast: the load drops to × 3 and the wait to 600 ms. Use a retry budget: allow retries only while they are a small share of all calls (Google's SRE book describes 10 % per client); under a total outage the load stays at × 1.33 instead of × 27. Back off exponentially with jitter, so that clients that failed at the same moment do not retry at the same moment. Propagate deadlines and stop retrying when the caller can no longer use the answer. And use a circuit breaker: after a number of failures, stop calling the failing component for a while and fail immediately, then let a few trial calls through to see whether it has recovered.

Pitfall

The calculation in the figure assumes that attempts fail independently, which is the optimistic case. Real failures are correlated: if a service is overloaded or its storage is full, the second attempt fails for the same reason as the first. That is why retries rarely rescue a request from a sick component, and why the load amplification, not the success rate, is the number to design for.

9.5Ordering and time

Within one thread, "before" is obvious. Across processors it is not: each has its own clock, clocks drift, and messages take varying time. Two techniques make order explicit. Sequence numbers per producer let a receiver detect loss, duplication and reordering on one stream, which is why every frame carries one and why E2E-protected messages carry a counter. Logical clocks, introduced by Leslie Lamport in 1978, order events causally across processes: every process keeps a counter, increments it on each event and sends it with each message, and a receiver sets its counter beyond the received value. Lamport clocks guarantee that if one event caused another, it has a smaller timestamp; vector clocks extend this to detect events that are concurrent.

Vehicles add physical time, because sensor data must be fused by the moment it describes, not the moment it arrived. Automotive Ethernet synchronises clocks with gPTP (IEEE 802.1AS) to well below a microsecond between ECUs, and the camera ECU stamps each frame with the vehicle time of its exposure (Networks 7.6, Calibration and fusion). With good timestamps, consumers can reorder, align and compensate for delays; without them, processing delay is mistaken for scene time. The architectural rule is: every datum carries the time it describes, in a declared time base, from the point of measurement to the last consumer.

Ordering across different streams needs care. The perception process may publish "camera 2 unavailable" on a status topic and the object list on another; a subscriber may see the object list first. If the meaning of a message depends on another message, either put the dependency into the message (the object list states which cameras contributed and which calibration version was used), or send both through one ordered channel.

9.6State and consistency: who owns the truth?

When state exists in more than one place, the copies can disagree. The HMI believes the view is "front", the camera ECU shows "rear" because it restarted and came back in its default mode; the calibration service has stored a new extrinsic calibration while perception still uses the old one in memory. The first and most effective rule is single ownership: every piece of state has exactly one owner that may change it, and everyone else holds a copy that is explicitly a cache, refreshed from the owner. The view mode belongs to the view process; the HMI sends requests and displays the mode that the view process reports, not the mode it last asked for. Calibration belongs to the calibration service; consumers read a snapshot with a version number and log which version they used.

When copies are needed, the design must say how fresh they must be. Database theory gives the vocabulary. Strong consistency (linearisability) means every read sees the latest write, as if there were one copy; eventual consistency means copies converge if no new writes happen. The CAP theorem (Eric Brewer, 2000, proved by Gilbert and Lynch in 2002) states that when the network is partitioned, a replicated system must choose between consistency and availability; PACELC (Daniel Abadi) adds that even without a partition it must trade latency against consistency. In a cloud database this is a choice of product; in a vehicle the same trade-off appears in a smaller form. When the link between the camera ECU and the HMI is broken, should the HMI keep showing the last known view mode (available, possibly wrong) or show "unknown" (consistent, less available)? For anything safety-relevant the answer is to show that the information is stale, which is why automotive signals carry qualifiers and timeouts.

Crash-recovery makes consistency harder: a component that restarts has lost its volatile state and must resynchronise. Two patterns help. Publishers offer their current state as a field (SOME/IP) or with transient-local durability (DDS), so that a restarted subscriber receives the current value immediately. And persistent state is written atomically with a version (write a new file, then rename it; or two slots with a sequence number and CRC), so that a reset in the middle of a write never leaves a corrupted calibration behind (AUTOSAR 10.1).

Talk track

"A car is a distributed system: parts fail independently, messages get lost, delayed or duplicated, and there's no shared clock unless you build one. So I design for partial failure explicitly: timeouts derived from measured latency, idempotent state-setting commands or request IDs, retries at one layer with backoff and a budget, deadlines instead of independent timeouts, sequence numbers and exposure timestamps on everything, and one owner for every piece of state, with everyone else treating their copy as a cache that can be stale."

10Embedded architecture: scheduling, memory and hardware

Cloud architecture can assume that more hardware is a purchase order away. Embedded architecture starts from the opposite assumption: the chip, its memory and its accelerators were fixed before the software existed and will not change for the life of the product. Every function must fit into budgets of time, memory and bandwidth, at the worst case, on a chip that heats up.

10.1What changes when the hardware is fixed

Five properties make embedded architecture different. The worst case matters, not the average: a display that is late once per minute fails a requirement that an average would hide. Resources are shared and finite: the CPU cores, the GPU, the NPU, the ISP and above all the memory bandwidth are used by every function at once, so one function's optimisation can be another's slowdown. The hardware is heterogeneous: the same work can run on a CPU core, a DSP, the GPU or the NPU, at very different cost, and moving it between engines is an architecture decision with consequences for latency, power and portability (Embedded compute 8.5). The system must be certifiable: timing and resource use must be argued with evidence, which favours static designs over dynamic ones. And the product lives long: the hardware, operating system and toolchain of today must be supportable in fifteen years.

The consequence is a preference for static structure: threads, buffers and connections created at start-up; fixed priorities and schedules; budgets measured and enforced per component; and dynamic behaviour (allocation, thread creation, dynamic loading, discovery of new components) concentrated in the start-up phase or in the non-critical parts of the system.

10.2Execution architecture: from components to threads, cores and engines

The runtime view of Figure 3.1 is the result of a design step that is often skipped: mapping components onto threads, priorities, cores and accelerators. The usual approach groups work by rate and criticality. Work that runs at the same rate and must finish by the same deadline goes into one thread or rate group; work of different criticality goes into different processes or partitions; and each group gets a priority and a core set that match its deadline.

For periodic work with fixed priorities, rate-monotonic assignment (the shorter the period, the higher the priority) is optimal, and the Liu and Layland bound of 1973 gives a quick sufficient test: n periodic tasks always meet their deadlines if total utilisation is below n(21/n − 1), which is 78 % for three tasks and approaches 69 % for many. Real designs use response-time analysis, which is exact and also handles blocking (Embedded compute 7.3), and measure on the target, but the bound is a useful sanity check: a core planned at 90 % load for periodic real-time work is a risk.

Accelerators need their own scheduling design, because the operating system does not schedule them. Many embedded GPUs preempt only at coarse boundaries, so a long perception kernel can delay the view's render job by many milliseconds; the design must either give the view a higher-priority GPU context with preemption, split perception's GPU work into short jobs, or move pre-processing to another engine. The NPU is shared by the parking and front networks; an explicit scheduler inside the perception process that runs them in a fixed order per frame period is easier to analyse than two processes competing for the device (Concurrency 9.4). Partitioning by a hypervisor or by CPU limits (cgroups on Linux, adaptive partitioning on QNX) bounds what each group can take from the others, which is part of the freedom-from-interference argument (Functional safety 6.3).

10.5Hardware dependencies and the platform layer

Every vision SoC does the same things differently: capture, ISP control, buffer allocation and sharing, accelerator runtimes, GPU import, display, power and thermal management all have vendor-specific APIs, and the differences go beyond names (one vendor's ISP is inline, another's memory-to-memory; one NPU accepts NV12 directly, another needs planar RGB). The platform layer is where these differences are absorbed. Its design follows from Section 6.3: ports defined by what the domain needs, adapters per platform, and a capability query at start-up instead of compile-time assumptions ("can the ISP produce a second, downscaled output?", "can the NPU read NV12?"), so that the domain can choose the best path on each chip. The GLES chapter's advice for graphics applies to the whole platform: abstract what varies, not every call (GLES 22).

Some hardware decisions reach all the way up to the architecture, and the software architect should be in the room when they are made. Whether the cameras are frame-synchronised (a common trigger from the deserialiser) decides whether the surround view can render on frame arrival (Section 11.2) and whether the NPU can batch the four cameras. Whether the ISP can produce two outputs at once decides whether pre-processing for perception costs a GPU pass. Whether the safety MCU can receive the display's frame counter decides how the frozen-image monitor works. These are cheap to get right during hardware selection and expensive afterwards.

10.6Resource ownership

Shared resources are where fault containment quietly breaks down. If two processes both configure a camera sensor over I²C, the second overwrites the first; if any process may submit GPU work at any priority, a perception bug can starve the display; if a consumer may hold frame buffers indefinitely, a hung recorder starves capture. The rule that prevents most of this is the same as for state in Section 9.6: every resource has exactly one owner, the owner is the only one that touches it directly, and everyone else asks the owner through an interface that the owner can refuse, rate-limit or time out.

11Performance budgets and latency allocation

Performance is a property of the whole system, but it is built by many teams who each see only their part. A budget turns a system requirement into a number per part that each team can own, measure and defend, and it makes visible where the time actually goes.

11.1Why budgets

Without budgets, each team optimises its own component and reports that it is "fast": the ISP team's stage takes 6 ms, the renderer 8 ms, the display team's path is "one frame". Then the integrated system misses its latency requirement and nobody's component is at fault, because the problem is the sum and the waiting between the parts. A latency budget allocates the end-to-end requirement to the stages, including the waits, with a margin; a resource budget does the same for CPU, GPU, NPU, memory, bandwidth, flash, start-up time and power. Budgets are tracked continuously, like money: every change that spends from a budget is visible, and a team that needs more must get it from the reserve or from another team, through the architect.

11.2The glass-to-glass budget of the rear view

The rear view's latency is measured from the moment light hits the sensor ("glass") to the moment the pixel changes on the display ("glass"). It crosses every layer, from the sensor's exposure and readout through the ISP and the GPU to the display controller and the panel, and much of it is not processing at all but waiting for clock edges: the next render tick, the next vsync, the next frame of a compositor further down the chain.

The default design, which is what a first integration often looks like, has a typical latency of 89 ms and a worst case of 122 ms, missing a 100 ms target. Reading the budget shows why: the GPU work, which everyone suspects first, is 12 ms; the waits for the free-running render timer (up to 33 ms) and for vsync (up to 17 ms) are 50 ms, 41 % of the worst case. The cheapest fix is architectural, not an optimisation: if the cameras are frame-synchronised and the renderer starts when the frames arrive instead of on its own timer, the worst case drops to 91 ms. Running the ISP inline instead of memory-to-memory gains another 7 ms (84 ms). Routing the image through the head unit's compositor, a common request because it simplifies the display wiring, adds up to two more display frames: 156 ms with the default design, and still 124 ms with synchronised rendering and 117 ms with both improvements, which is why that decision belongs in the architecture review and not in a wiring discussion.

Why it matters

A budget written as a table, with waits as separate lines, changes the conversation. "The system is laggy" becomes "the render tick and vsync waits cost 50 ms because our clocks are not aligned", which points at a design change (synchronised cameras, render on arrival, latching the newest frame just before vsync) rather than at the team whose component happens to be the most visible.

11.3Allocating the perception budget to teams

The parking function needs the object list within 100 ms of exposure, at the 99th percentile. Allocation works top-down: start from the requirement, subtract a system reserve that the architect holds (here about 5 %), and give each stage a budget equal to its measured or estimated worst case plus a stage margin. Each line has an owner. When a stage exceeds its budget, the owner first optimises; if that fails, the request for more time goes to the architect, who either releases reserve or moves time from another stage. This makes trade-offs explicit: a larger network that gains accuracy must be paid for by someone.

11.4Measuring against the budget

A budget is only as good as its measurement. Three practices make it trustworthy. Measure distributions, not averages: record every frame's per-stage times and report percentiles and maxima over long runs, including the heaviest scenes, all cameras, recording active and the chip at its throttling temperature. Trace each frame end to end: every stage stamps the frame's sequence number with its start and end times into a lightweight trace, so that a late frame can be explained stage by stage (Section 12.4). And keep utilisation headroom on shared resources, because waiting time grows non-linearly with load. For a resource with random arrivals, the simple M/M/1 queueing model gives a mean time in the system of the service time divided by (1 − utilisation): 2 × at 50 % load, 3.3 × at 70 %, 10 × at 90 %. Periodic real-time work behaves better than random arrivals, but the direction is the same, and it is why budgets cap shared engines at 60 to 70 % rather than 95 %.

Numbers

Typical budget targets for an automotive vision SoC: CPU cores with real-time threads ≤ 70 % worst case; GPU ≤ 70 % of the frame period; NPU ≤ 80 % of the frame period (its work is periodic and scheduled); DRAM bandwidth ≤ 50–60 % of peak; memory ≤ 70–80 % of capacity with field monitoring of high-water marks; and 10 to 20 % of each latency budget held as system reserve at the start of a project, shrinking towards release.

12Fault tolerance, graceful degradation and observability

Every component will fail at some point: a camera cable loosens, a GPU job hangs, a rare input crashes a network's post-processing, memory slowly fragments. Fault tolerance is the part of the architecture that decides, in advance, how each failure is noticed, how far it is allowed to spread, and what the system still does afterwards. Observability is what lets you find out, later, what actually happened.

12.1Fault, error, failure, and where to break the chain

The dependability vocabulary distinguishes three things. A fault is the cause (a bug in the NMS code, a bit flip, a broken connector). An error is the wrong internal state it produces (a corrupted detection list, a buffer never returned). A failure is when the system's delivered service deviates from what it should do (the parking function receives a phantom obstacle, the display freezes). Faults are unavoidable; the architecture's job is to stop errors from becoming failures, or at least from becoming dangerous ones, by breaking the chain at three points. Detection notices the error close to where it appears. Containment keeps it from spreading to other components, through process and partition boundaries, resource limits and validation at interfaces. Recovery brings the system back to a correct state, or to a defined degraded one. Each of the patterns below serves one or more of these three steps.

The supervisor pattern deserves a note, because it changes how components are written. Erlang made famous the idea of "let it crash": instead of trying to handle every possible error inside a component, which multiplies the code paths that are hard to test, a component that meets an unexpected state stops, and a supervisor restarts it from a known good state. In an ECU this is attractive for complex, non-safety components such as perception post-processing, provided the restart is fast, the restart rate is limited, consumers are told that the data are unavailable meanwhile, and the restart does not lose state that cannot be recovered. A perception restart of 300 ms costs 9 frames at 30 fps, which the parking function can bridge with its own prediction; a restart loop that never ends must be detected and turned into a degradation.

12.3Degradation modes of the camera ECU

Switching everything off at the first fault is safe but makes the product unavailable much more than necessary. The better design is a small set of explicit degradation modes, each a well-defined, tested configuration that keeps as much function as the remaining resources can support, and that is reported to the driver and to the functions that depend on the ECU (Functional safety 4.7).

In Full mode everything runs. When a surround camera fails, the ECU goes to Reduced view: the stitched view shows the missing sector as unavailable rather than stretching neighbours into it, and perception reports reduced coverage so that the parking function can restrict itself. When perception fails or restarts too often, the ECU goes to View only: the driver still sees the cameras, and the parking function is told that the object list is unavailable. When the GPU path fails (a hung job, a lost context), the ECU falls back to Rear camera only, a minimal path that sends the rear camera's ISP output straight to a display overlay plane without the GPU, which is exactly the path also used for the early camera at start-up (Camera ECU 8.5); designing one minimal path for both cases means it is exercised at every start. When the SoC itself is lost, the MCU reports Camera functions unavailable to the vehicle, and the head unit shows a message instead of a frozen image.

The rules from functional safety apply to every mode, safety-relevant or not: downward transitions are fast and certain; upward transitions are slow and need the cause to be gone for a while, so that the system does not oscillate; every mode is tested deliberately, including the transitions, with fault injection on the bench; and the user is never left believing that a function works when it does not.

12.4Observability: designed in, not added later

A system is observable when you can answer questions about its behaviour from the data it produces, including questions you did not anticipate when you built it. Cloud systems speak of three kinds of telemetry: logs (discrete events with context), metrics (numbers aggregated over time, such as rates, percentiles and counters) and traces (the path of one request through many services), increasingly collected with a common standard such as OpenTelemetry and streamed continuously to a backend. An ECU has the same three needs and much tighter limits: logs go through DLT with limited bandwidth (Production integration 9.2), metrics live in RAM as counters and histograms read through diagnostic services or uploaded in small summaries, and traces must cost nearly nothing in the hot path. In the field, the data are usually read in a workshop or uploaded selectively, so what to keep must be decided in advance.

The design starts from the questions. For the camera ECU they include: Why was this frame late? Which camera dropped frames, how often, at what temperature? How old was the object list the parking ECU used when it braked? Which software, model and calibration version produced it? Did the view ever show a frozen image, and for how long? Each question implies data that must be recorded, and a cost in CPU, memory, bandwidth and storage that belongs in the budgets. For the frame pipeline, the cheapest answer is a fixed-size trace record per frame and stage, written into a lock-free ring buffer and dumped on demand or on an anomaly.

With such records, the end-to-end latency of any frame, the stage that made it late and the queue it waited in can be reconstructed after the fact, on the bench or from a dump taken when the frozen-image monitor fired. Combined with counters for drops, restarts and degradations, and with logs for state changes (not for every frame), they answer most field questions. Two further rules matter. Log versions and configuration at start-up and with every anomaly, because an answer is useless if you do not know which software produced it. And treat observability data as product data: it has a budget, it is tested, and it must respect privacy (a camera ECU's recordings contain people and licence plates) and security (logs must not leak keys or allow an attacker to fill the storage).

12.5Availability in numbers, and how the two worlds measure it

Cloud services express reliability as service level objectives (SLOs): for example, 99.9 % of requests succeed within 300 ms over 30 days. An SLO of 99.9 % allows 8.8 hours of failure per year (43 minutes per month); 99.99 % allows 53 minutes per year. The difference to 100 % is the error budget, which teams spend on releases and experiments, and when it is used up they slow down and fix reliability. Two simple rules of availability arithmetic are worth remembering: components in series multiply their availabilities (three at 99.9 % give 99.7 %), and independent redundant components multiply their unavailabilities (two at 99.9 % give 99.9999 %, if their failures are truly independent, which they rarely are).

Automotive functions are specified differently: per function and operating situation ("rear view available within 2 s of reverse in 99.99 % of activations"), with safety goals and hardware metrics that limit the rate of dangerous failures per hour of operation (Functional safety 5.4), and with field monitoring of degradations and restarts per thousand hours. The mindset of error budgets still transfers well: decide in advance how much unavailability is acceptable, measure it continuously in the fleet, and let the measurement steer how much risk the next release may take.

13Trade-offs, technical debt and evolution

Every architecture decision trades one quality for another, and every system changes over its life. The skill that separates senior from staff and principal engineers is less in finding a good design than in making trade-offs explicit, knowing which decisions can be reversed, managing debt deliberately and evolving a running system without stopping it.

13.1Making a trade-off explicit

The ATAM vocabulary helps to talk about trade-offs precisely. A sensitivity point is a design parameter to which a quality is sensitive (queue depth for latency, process boundaries for fault containment). A trade-off point is a parameter that affects several qualities in opposite directions (more buffering helps throughput and hurts latency). A risk is a decision whose consequences for a driver are unknown or bad. Naming them turns "I don't like this design" into "this queue depth is a trade-off point between recording completeness and view latency, and we have not measured it".

For a decision between a few options, a weighted decision matrix makes the reasoning visible. Consider how frames should travel from the view process to perception and the recorder (Section 4.5). Option A copies them over an ordinary IPC channel: simple, safe and portable, but it adds 2.1 GB/s of DRAM traffic for the four surround cameras and a few milliseconds of latency. Option B is a shared-memory ring with a home-grown protocol of indices and flags: as fast as possible, but every consumer can corrupt the ring's metadata, and a crashed consumer leaves buffers marked "in use". Option C passes kernel-managed buffer handles (dma-buf file descriptors on Linux, the vendor's equivalent elsewhere) behind the platform port: as fast as B, consumers get read-only mappings, and when a consumer crashes the kernel releases its references automatically; but it needs platform work for each operating system.

13.2Reversible and irreversible decisions

Decisions differ enormously in how expensive they are to undo. Choosing an internal data structure is cheap to reverse; choosing a message format that a hundred thousand cars will send to the backend, or a process boundary that the safety case depends on, is not. A useful habit, popularised by Amazon as "one-way and two-way doors", is to classify each decision before spending effort on it. Reversible decisions should be made quickly by the people closest to the work, because the cost of a wrong choice is small and the cost of delay is not. Irreversible decisions deserve analysis, prototypes and review, and they should be made at the last responsible moment: late enough to use the best information, early enough that not deciding does not block others. A large part of good architecture is turning irreversible decisions into reversible ones, for example by putting a port in front of a vendor runtime, or by versioning a message format from its first release.

When the information needed for an irreversible decision does not exist yet, buy it: a spike or prototype that measures the one thing in doubt (can the NPU run both networks within 24 ms? does the GPU preempt fast enough for the view?) is almost always cheaper than a wrong decision. Many architecture risks in embedded systems are answered by one day of measurement on the target.

13.3Technical debt

Ward Cunningham introduced the metaphor of technical debt in 1992: shipping code that is not quite right is like borrowing money; it lets you move faster now, and you pay interest on every later change until you repay the principal by fixing it. The metaphor is useful because it makes debt a business decision rather than a moral failing. Taking on debt deliberately to meet a sample deadline can be right; not knowing that you took it, or never paying it back, is not. Martin Fowler's debt quadrant separates debt that was deliberate from inadvertent, and prudent ("we ship now and refactor the view logic after the C-sample") from reckless ("we have no time for interfaces").

Not all debt costs the same. Debt in a module that nobody touches costs nothing; debt in the code that every feature passes through costs interest every week. Architectural debt, such as vendor types spread through the domain code or a cycle between modules, is the most expensive kind, because its interest is paid by every team and its principal grows with every line written against it. Making debt visible is the first step: a register with each item's location, the interest it costs (slower changes, bugs, blocked features) and an estimate for repayment; a measurement of where change and complexity coincide (files that are both large and frequently changed, found from version control history, are where debt hurts most); and a standing share of capacity, often 15 to 20 %, spent on repayment, prioritised by interest rather than by annoyance.

Pitfall

The "big rewrite" is the most tempting and most dangerous way to repay debt. It stops feature work for a long time, has to reproduce years of undocumented behaviour (all the fixes hidden in the old code), and often ships late with new debt of its own. Incremental replacement behind stable interfaces, as in the next section, is slower to start and much more likely to finish.

13.4Evolving a running system

Systems are rarely designed on a blank page; usually the task is to move an existing system towards a better structure while it keeps shipping. A small set of techniques makes that possible. The strangler fig pattern (named by Martin Fowler after a tree that grows around its host) builds the new structure next to the old one and moves functions over one at a time until the old one can be removed. Branch by abstraction does the same inside a code base: put an interface in front of the part to replace, switch callers to the interface, build the new implementation behind it, switch over, and delete the old implementation, all on the main branch with the system working at every step. Shadow mode (or a parallel run) runs the new implementation alongside the old one on the same inputs, compares the outputs without using the new ones, and switches only when the comparison is good; it is common in automotive perception, where a new network often runs in shadow in test fleets before it is allowed to act. Feature toggles and variant coding switch the new path on per build, per variant or per vehicle.

Inside the existing monolith, define the domain ports (ICameraSource, IInference, IGpuImport) and make the domain code call them. The first implementation simply forwards to the old vendor calls. Nothing changes in behaviour, so every test still passes; the change can be merged in small steps.

Move every vendor SDK call behind the ports into a platform adapter library, and add a CI rule that fails if any file outside the platform directory includes a vendor header. A replay adapter and a CPU reference backend are added next to the SoC adapter, and perception now runs on a PC against recordings.

Start a separate perception process that receives frames as buffer handles from the view process and runs the same domain code. The monolith's built-in perception still produces the object list that is sent to the vehicle; the new process's output is only logged and compared frame by frame on the bench and in test vehicles.

When the comparison shows identical object lists (bit-exact on the same backend) and the timing budget holds under worst-case load, a configuration switch makes the new process the producer. After one release with the old path still available as a fallback, the perception code is deleted from the view process, which becomes small enough for its safety argument.

Architecture tests run in CI on every change: no dependency cycles; no vendor headers outside the platform layer; the view process does not link any perception library; per-stage latency and memory high-water marks from a nightly target run stay within budget. Decay is now caught when it is one commit old, not one year.

The last step generalises. An architecture is a set of rules, and rules that are not checked erode, one reasonable-looking exception at a time. Fitness functions (from Building Evolutionary Architectures by Ford, Parsons and Kua) are automated checks of architectural properties: dependency rules on the module graph, budgets measured in nightly runs on the target, API compatibility checks against the previous release, start-up time in every build. They turn the architecture from a document that ages into a property of the build that stays true.

14Putting it together: designing a system step by step

The previous sections took the camera ECU apart one concern at a time. This section puts the pieces back together as a method you can follow in a design review, in a customer workshop or in a whiteboard discussion, and applies it once to the ECU and once to a cloud system, to show what changes and what stays the same.

14.1A method for system design

Good system design discussions follow roughly the same seven steps, whether they last forty-five minutes at a whiteboard or six weeks in a project. First, clarify the scope and the drivers. Ask what the system must do, for whom, and above all which qualities matter and how much: latency, throughput, availability, safety level, cost, start-up, lifetime, the constraints that are already fixed. Write down the three or four drivers and confirm them. Second, estimate the numbers. Data rates, compute, memory, storage, bandwidth, request rates; a few multiplications on the whiteboard, like those in Sections 10.3 and 10.4, reveal which resource will be the bottleneck and rule out designs before they are drawn. Third, sketch the whole system end to end at the context and container level, with the main data flow, so that every requirement has a path. Fourth, go deep on the hardest driver: the part where the design is most likely to fail, with alternatives and the reason for the choice. Fifth, design for failure: what breaks, how it is detected, how far it spreads, what the system still does. Sixth, make it operable: how it is tested, observed, updated and debugged. Seventh, summarise the trade-offs and the evolution: what you chose, what you gave up, what you would revisit as requirements change.

In practice

In a 45-minute discussion, a reasonable split is 5 to 8 minutes on requirements and numbers, 10 on the end-to-end sketch, 15 to 20 on one or two deep dives, and the rest on failure, operations and trade-offs. The most common mistake is to start drawing components in the first minute; the second is to spend the whole time on one box. Experienced reviewers listen mostly for the drivers, the numbers and the explicit trade-offs.

14.3The cloud counterpart: a fleet clip backend

The recorder on the ECU uploads short clips around interesting events (hard braking, a disagreement between the perception and the driver's action, a rare object) for development and fleet learning. Designing the backend that receives them with the same method shows how the same principles lead to a very different shape. Drivers: accept every clip a car is allowed to upload, never lose or duplicate one, keep cost per terabyte low, protect privacy (faces and licence plates), and let engineers find clips by metadata within minutes. Latency of minutes is acceptable; availability of the upload endpoint matters because cars have limited connectivity windows. Numbers: one million cars uploading five clips of 50 MB a day is 250 TB per day, 2.9 GB/s on average and about 9 GB/s at peak, but only 58 uploads per second; a year is 91 PB, so retention policy is a cost decision, not a detail. One clip takes about 80 s over a 5 Mbit/s mobile link, so uploads must be resumable.

The shape is a textbook cloud design, and each of its decisions maps back to a principle of this chapter. Bulk data bypass the services and go straight to object storage (the data plane is separated from the control plane, Section 5.3). The content hash as key makes uploads idempotent, so a car can retry after a lost connection without creating duplicates (Section 9.3). The upload service tells cars when to upload, which is back-pressure at fleet scale: when the backend is busy, cars wait instead of retrying (Section 9.4). Processing after the upload is event-driven through a durable log, so workers can be added, fail and restart independently, and the index is eventually consistent, which is acceptable because engineers can wait a minute for a new clip to appear (Section 9.6). Services scale horizontally because capacity is elastic, the opposite of the ECU's static budgets.

14.4What changes with the role

The same architectural knowledge is used differently at different levels. A senior engineer designs components and their interfaces well, owns a budget line and its measurement, and knows how their part fails and degrades. A staff or principal engineer works across teams: finds the drivers, owns the cross-cutting budgets and the platform boundaries, spots architectural debt before it compounds, and turns decisions into fitness functions so they survive without them. An architect adds the customer and the system level: negotiates scenarios and constraints with the OEM, aligns the software structure with the hardware and the safety concept, and keeps the decision record. An engineering manager applies Conway's law in reverse: shapes teams and ownership to match the architecture that is wanted (a platform team that owns the ports and adapters, function teams that own perception and the view), funds the platform and debt work that no feature team will ask for, and makes sure that decisions get made at the right level and speed. How to lead design reviews and build support for an architecture is the subject of the planned leadership chapter.

QSelf-check questions

Q.1Core questions

What is software architecture, in your own words?Basic

The set of decisions that are expensive to change later: how the system is split into processes and components, how data flows, who owns which state and resource, which interfaces others depend on, where the hardware boundary lies, and how faults are handled. It exists to deliver the system-wide qualities (latency, safety, availability, modifiability) that no single component can deliver. The architect's job is to find those few decisions, make them deliberately for the drivers, record why, and keep everything else cheap to change.

How do you specify a quality requirement such as "fast" or "reliable"?Basic

As a quality attribute scenario: source, stimulus, environment, artifact, response and a measurable response measure. "The rear camera captures a frame at night; it is on the display within 100 ms at the 99.9th percentile" is testable; "the system shall be fast" is not. Use distributions or worst cases, not averages, and state the environment (start-up from sleep versus cold start at −30 °C) because it changes the design.

What are architecture drivers and how do you find them?Intermediate

The quality scenarios and constraints that are both important to the business and hard to achieve; they decide the structure, the rest can be met inside components. A utility tree (ATAM) refines qualities into scenarios and rates each on importance and difficulty; the high-high ones are drivers. For a camera ECU: rear-view latency and start-up, fault containment between view and perception, frozen-image detection, the bandwidth budget and portability to the next SoC.

Monolith or microservices: how do you decide?Intermediate

By what each boundary buys and costs against the drivers. A process or service boundary buys fault containment, independent release, separate resource limits and team independence; it costs serialisation or shared-memory protocols, latency, start-up time, operational complexity and distributed-system failure modes. In the cloud, microservices mostly solve an organisational scaling problem; inside an ECU, with fixed hardware and large data, a few processes split by criticality and failure domain, with zero-copy data paths, usually beat both a single process and many small services. A well-structured modular monolith is often the right start.

Layered versus hexagonal architecture: what is the difference?Intermediate

In a layered architecture each layer depends on the one below, so the domain logic ultimately depends on the infrastructure (drivers, SDK, middleware). In a hexagonal (ports and adapters) architecture the domain is in the middle and defines the interfaces it needs; adapters for the platform, middleware and tests implement them, so dependencies point inwards. The hexagonal form makes the domain portable and testable without hardware, which is why it suits perception code that must outlive several SoC generations and run in PC replay.

Explain SOLID with embedded examples.Basic

Single responsibility: one reason to change, so a camera manager is split into link control, ISP tuning, view layout and diagnostics. Open-closed: add a new inference backend by registering it, not by editing callers. Liskov substitution: a replay camera source must honour the real contract (rate, timeouts), or tests lie. Interface segregation: small role interfaces such as ICameraSource instead of a 40-method IPlatform. Dependency inversion: the domain owns abstractions, the vendor SDK implements them in adapters. Apply them where there is real variation, not everywhere.

Why is dependency inversion especially important in automotive embedded software?Intermediate

Because the volatile parts are the low-level ones: silicon vendor SDKs, drivers, middleware and operating systems change with every hardware generation, while the domain logic (perception, view logic, tracking) lives for many years and across programmes. If the domain depends on the SDK, every port rewrites the domain and nothing runs on a PC. With the domain owning ports and the SDK confined to adapters, a new SoC means new adapters, and replay and unit tests run the real domain code.

What makes a good API?Intermediate

It is narrow, expressed in the domain's vocabulary, hard to misuse and documented as a full contract. In C++ that means putting the contract into types: move-only handles that release resources in their destructor, typed units and time bases, read-only views where callers must not write, errors as values (std::expected) rather than magic codes or exceptions across module boundaries. It hides implementation types (no vendor handles in the public interface) and states threading, timing, ownership and ordering, which signatures cannot express.

How do you version an interface and keep it backward compatible?Intermediate

Semantic versioning: major for incompatible, minor for compatible additions, patch for fixes. Compatible changes are additions of optional fields with defaults or new methods; removals, renames, type or unit changes and reused identifiers are breaking. Readers are tolerant (ignore unknown fields, handle unknown enum values), writers are strict. Removals go through a dated deprecation with both versions supported in parallel and usage measured. Across ECUs, a compatibility matrix checked by the update system protects against untested combinations, because cars run mixed versions for years.

What is the difference between API and ABI compatibility?Advanced

API compatibility means code that compiled against the old interface still compiles; ABI compatibility means binaries built against the old version still work with the new one without recompiling. In C++ the ABI includes class layout, vtable layout, name mangling and calling conventions, so adding a private member or a virtual function keeps the API but breaks the ABI. Remedies are rebuilding everything together, the pimpl idiom, or a C interface with opaque handles at binary boundaries.

How would you implement a factory in modern C++?Basic

A function or registry that returns std::unique_ptr to an interface, so ownership is explicit and callers do not name concrete types. A registry maps a configuration key to a creation function (std::function or a lambda) and is filled explicitly in the composition root; static self-registration depends on the linker and initialisation order and is best avoided. Create everything at start-up so that a bad configuration fails before the process reports ready.

What are the pitfalls of the observer pattern in C++?Intermediate

Lifetime: a destroyed listener still registered leads to a call into freed memory, solved with RAII connection objects and weak references. Threads: listeners run on the emitter's thread, so a slow one delays everyone; in real-time paths the subject should only enqueue. Locks: calling listeners while holding the subject's lock deadlocks when a listener subscribes or emits; copy the list under the lock and call outside it. And hidden control flow: chains of events triggering events become hard to follow.

When do you choose run-time versus compile-time strategies?Intermediate

Run-time (an interface with virtual functions) when the choice comes from configuration, changes at run time, or implementations live in different libraries; the cost is an indirect call and no inlining. Compile-time (a template parameter, constrained by a concept) for hot paths such as per-pixel or per-detection code and when the choice is fixed per build; the cost is code size and build time. A std::function or lambda when the strategy is a single function.

How do you implement a state machine in modern C++?Intermediate

For a closed, known set of states, a std::variant of small structs, each carrying only the data valid in that state, and one pure transition function using std::visit over (state, event). It is easy to test exhaustively, log and replay; the policy for unexpected events is explicit, or removed so the compiler flags unhandled pairs. Class-per-state with virtual handlers fits open sets; large hierarchical machines are better generated from a model or table-driven.

What is wrong with singletons?Basic

Not the single instance but the global access: it hides dependencies from function signatures, is shared mutable state that every caller must synchronise, creates initialisation and destruction order bugs across translation units, leaks state between tests and makes deterministic replay impossible (for example a singleton clock). The fix is to create one instance in the composition root and inject it. If you must, a function-local static is initialised thread-safely since C++11.

Publish-subscribe or request-response?Basic

Request-response when the caller needs an answer now and knows who provides it (reading a calibration, a diagnostic request). Publish-subscribe when a producer broadcasts facts or data to an open set of consumers (frames, object lists, gear state); it decouples knowledge and time, and needs explicit quality of service: reliability, durability for late joiners, history depth and deadlines per topic.

Explain at-least-once, at-most-once and exactly-once.Intermediate

At-most-once never retries and may lose messages; at-least-once retries until acknowledged and may duplicate them. Exactly-once delivery is impossible over an unreliable link because a lost acknowledgement is indistinguishable from a lost request; systems achieve exactly-once processing by combining at-least-once delivery with idempotent operations or deduplication by request identifier. Design commands to set state ("view = front") rather than change it ("toggle").

How do you prevent retry storms?Advanced

Retry at one layer only, close to the failing resource, and let the others fail fast; limit retries with a budget (for example 10 % of calls); use exponential backoff with jitter; propagate deadlines so nobody retries work whose caller has given up; and use circuit breakers to stop calling a failing dependency. With three layers of three attempts a dead service gets 27 × load; retrying at one layer gives 3 ×, a 10 % budget 1.33 ×.

What does the CAP theorem say, and does it matter in a car?Intermediate

A replicated system cannot be both consistent and available while the network is partitioned; PACELC adds that without a partition it trades latency against consistency. In a car the same trade-off appears whenever state is copied across ECUs: when a link is lost, a consumer can keep using the last value (available, possibly wrong) or declare it unknown (consistent). For safety-relevant data the answer is to mark it stale with a timeout and a qualifier, and to keep one owner per piece of state.

How do you order events that come from different ECUs?Intermediate

Per stream with sequence numbers, which reveal loss, duplicates and reordering. Across streams with timestamps in a synchronised time base (gPTP gives sub-microsecond sync on automotive Ethernet), taken at the moment of measurement such as mid-exposure, so consumers order and align by scene time, not arrival time. Where causality matters without physical time, logical (Lamport or vector) clocks. And if one message's meaning depends on another, put the dependency into the message.

How do you build a latency budget for a camera-to-display path?Advanced

List every stage from mid-exposure to the panel: exposure, rolling-shutter readout, link and capture, ISP, waits for the render trigger, GPU, wait for vsync, any compositor further down, scan-out, panel response, each with typical and worst values, and the waits as separate lines. Sum against the requirement with a reserve, give each line an owner and measure percentiles per stage with a per-frame trace under worst-case load. Usually the waits for unsynchronised clock edges are the biggest lever: synchronised cameras with render-on-arrival cut the example's worst case from 122 to 91 ms.

How do you manage memory in a real-time embedded system?Intermediate

Budget it per component from counted buffers, allocate everything at start-up from fixed-size pools, perform no heap allocation in steady state, enforce per-process limits through the OS so a leak hits only its owner, and monitor high-water marks in the field. The buffer count per pipeline stage is the main lever. DRAM bandwidth is budgeted too, because it usually runs out before capacity.

How do you design graceful degradation?Intermediate

Define a small set of explicit modes, each a tested configuration with a statement of what the user sees and what dependent functions are told: for the camera ECU full, reduced view, view only, rear camera only (GPU-free path, shared with the early camera), and unavailable. Downward transitions are immediate on detection; upward ones require the cause to be gone for a debounce time. Every mode and transition is exercised with fault injection, and the user is never left believing a function works when it does not.

What is observability and how does it look in a vehicle?Intermediate

The ability to answer questions about system behaviour, including unanticipated ones, from the data it emits: logs, metrics and traces. In a vehicle the same three exist under tight budgets: DLT logs for state changes, counters and histograms in RAM read via diagnostics or uploaded in summaries, and a cheap per-frame trace record (sequence, stage, timestamps, queue depth) in ring buffers dumped on anomalies. Design from the field questions, log versions and configuration with every anomaly, and give observability its own CPU, bandwidth, storage and privacy budget.

How do you manage technical debt?Intermediate

Treat it as a business decision: take it deliberately and prudently, record it in a register with its interest (slower changes, bugs, blocked features) and repayment cost, and reserve a standing share of capacity (often 15–20 %) for repayment, prioritised by interest. Debt hurts most where change frequency and complexity coincide, which version-control history reveals. Architectural debt such as vendor types in domain code is the most expensive because every team pays the interest.

How would you migrate a legacy monolith to a new structure?Advanced

Incrementally, never by a big rewrite: introduce interfaces in front of the parts to change (branch by abstraction), move implementations behind them, extract new components next to the old ones (strangler fig), run them in shadow mode comparing outputs, switch over with a fallback for one release, delete the old path, and add fitness functions in CI so the new rules hold. Every step keeps the system shippable.

Design a multi-camera surround-view and parking-perception ECU.Advanced

Clarify drivers: rear view within 2 s and ≤ 100 ms glass to glass, fault containment between view and perception, frozen-image detection at ASIL B, bandwidth with five cameras, portability. Estimate: 4 × 4.4 MB + 12.4 MB per frame set, about 15 GB/s of DRAM traffic. Structure: SoC plus safety MCU; view process owning capture and display, perception and platform processes; zero-copy buffer handles; ports and adapters around the vendor SDK; synchronised cameras with render on arrival; NPU batch of four with a fixed schedule; LET or a fixed schedule towards the MCU. Failure: MCU frozen-image monitor, supervised restarts, degradation modes with a GPU-free rear path. Operations: per-frame traces, replay on PC, OTA with versioned interfaces. Then name the trade-offs.

Design a backend that receives video clips from a million vehicles.Advanced

Drivers: no loss or duplicates, low cost per terabyte, privacy, findability, resilience to intermittent connectivity. Numbers: 250 TB/day, ≈ 3 GB/s mean, 9 GB/s peak, but only about 60 uploads per second, and 91 PB/year, so retention is a cost decision. Design: an upload service that admits cars and issues pre-signed URLs, resumable chunked uploads straight to object storage keyed by content hash (idempotent), completion events into a durable log, independent workers for anonymisation, metadata extraction and indexing (eventually consistent), back-pressure by telling cars when to upload, and horizontal scaling. Contrast with the ECU: elastic, asynchronous and eventually consistent because the drivers differ.

Q.2Why and what if

Why can the GPU take only 12 ms while the display lags by 120 ms?Why

Because most of the latency is not processing: half the exposure plus a 22 ms rolling-shutter readout come before the SoC sees anything, and the waits for an unsynchronised render tick (up to 33 ms) and for vsync (up to 17 ms), plus scan-out and panel response, come after. In the example's default design the waits alone are 50 ms. Only an end-to-end budget with waits as separate lines makes this visible.

What if the perception process keeps frame buffers and never releases them?What if

With a shared pool and no limits, capture runs out of buffers and the rear view freezes, so a perception bug breaks the view despite the process boundary. The design prevents it with a per-consumer hold limit (a reference beyond the limit is revoked or the frame is skipped and reported), kernel-managed handles that are released when a crashed process's descriptors close, and the capture side as the single owner of the pool.

Why not run one microservice per camera inside the ECU?Why

There is nothing to scale on fixed hardware, the cameras must be synchronised and batched for the NPU, every process costs start-up time, memory and a share of the safety argument, and frames are too large to serialise. The boundaries that pay off are along failure domains and criticality (view versus perception versus platform), not per function or per camera.

What if both the HMI and the camera ECU store the current view mode?What if

They will disagree after a restart, a lost message or a race, and the driver may see a view the HMI does not show as selected. One component, the view process, must own the mode; the HMI sends idempotent requests ("set front") and displays the mode the owner reports, which is published as a field so a restarted HMI receives the current value immediately.

Why is LET slower, and why would you still use it towards the safety MCU?Why

LET holds results until the end of each task's period, so latency is about one period per stage (46.7 ms mean in the example versus 20.5 ms event-triggered). In exchange, the delay no longer depends on execution times: jitter comes only from how periods align, and is zero for harmonic periods. A controller or monitor on the MCU works with a known, constant delay, timing can be analysed and certified, and replay produces the same data in the same cycle.

What if every layer of a call chain adds "just three retries"?What if

Load on the lowest component multiplies as attempts to the power of layers: 27 × for three layers. When it is overloaded, the retries keep it overloaded, and users wait for every attempt's timeout (5.4 s with 200 ms timeouts). Retries help with rare independent failures and hurt with correlated ones, which is what overload produces.

Why batch the four surround cameras on the NPU, and what does it cost?Why

The network's weights and activation spill are read from DRAM per inference; in one batch they are read once for four images, which saves about 5.9 GB/s in the example and improves NPU utilisation. The cost is that the first camera waits for the last, so the cameras must be frame-synchronised and a missing camera needs a deadline after which the batch runs without it.

What if someone adds a subscriber to the 30 Hz object list with reliable delivery and a deep history?What if

If that subscriber is slow, reliable delivery with a deep history makes the middleware buffer and retransmit old lists, which costs memory and bandwidth and can create back-pressure on the publisher; consumers receive stale data that is worse than none. High-rate state topics should use best-effort, keep-last-one semantics, and every new subscriber on a high-rate topic should be treated as a budgeted change.

Why is bit-exact PC replay such a strong test of the architecture?Why

It only works if every dependency of the domain code is explicit: time from frame timestamps instead of a global clock, no hardware calls outside adapters, deterministic ordering of results from parallel stages, seeded randomness, initialised memory. Any hidden singleton, race or platform call shows up as a mismatch, so achieving replay forces the decoupling that the architecture needs anyway.

What if two options in a decision matrix score almost the same?What if

Then the matrix has done its job by showing that the decision rests on the weights. Check which weight change flips it (in the example, valuing effort over fault containment flips C to A), discuss that assumption with the stakeholders, prefer the option that keeps future decisions reversible, and if needed run a spike to replace an estimated score with a measurement.

Why does adding a private data member to a class break binaries built against the old header?Why

Callers compiled against the old header allocate objects with the old size and access members at the old offsets, and inline functions use the old layout. The new library uses the new layout, so they disagree about memory. The source still compiles, so the API is compatible but the ABI is not; pimpl or a C interface keeps the layout fixed.

What if the fleet backend is down for a whole day?What if

Cars keep clips in a bounded on-board store and must never let the uploader affect their driving functions (it runs in the platform partition with strict limits). The upload service, or its absence, tells cars to back off rather than retry, so the backend is not stormed when it returns. When storage fills, cars drop the lowest-priority clips by policy. After recovery, uploads resume from the last chunk and content-hash keys prevent duplicates.

Why does an architect care whether the cameras are frame-synchronised, which sounds like a hardware detail?Why

Because it decides two drivers: the surround view can only render on frame arrival, saving up to a frame period of latency, if all four frames arrive together; and the NPU can only batch the four cameras efficiently if they belong to the same moment. It is cheap to provide during hardware selection (a trigger line from the deserialiser) and expensive to work around later.

Architecture driver
A quality scenario or constraint that is both important and hard, and therefore shapes the structure.
Error budget
The allowed unreliability under an SLO, spent on change and risk.
Fitness function
An automated check that an architectural property (dependency rule, budget, compatibility) still holds.
Hexagonal architecture
Ports and adapters: domain logic in the middle defines interfaces that technology adapters implement.
Idempotent
An operation whose repeated application has the same effect as a single one.
Logical execution time (LET)
Tasks read inputs at the start of their period and publish outputs at its end, decoupling timing from execution time.
Liskov substitution
Implementations must be usable wherever the interface is expected: weaker preconditions, stronger postconditions only.
Microservices
Small, independently deployable services that own their data and communicate over a network.
Monolith
A system deployed as one unit, usually one process; modular if it has enforced internal boundaries.
Observability
The ability to answer questions about a system's behaviour from its logs, metrics and traces.
PACELC
Extension of CAP: with a partition, availability or consistency; else, latency or consistency.
Partial failure
Some parts of a distributed system fail while others continue, often without knowing about it.
Pimpl
Pointer to implementation: hides a class's members in a separate object to keep its layout and ABI stable.
Port
An interface owned by the domain that describes what it needs from the outside world.
Quality attribute scenario
Source, stimulus, environment, artifact, response and response measure for one quality requirement.
Quality of service (QoS)
Per-topic promises of a publish-subscribe middleware: reliability, durability, history, deadline.
Retry budget
A limit on retries as a share of calls, which bounds load amplification during failures.
SemVer
Semantic versioning: major for breaking, minor for compatible additions, patch for fixes.
Shadow mode
Running a new implementation on live inputs without using its outputs, to compare it with the old one.
SLO
Service level objective: a target for a measured service level, such as 99.9 % of requests within 300 ms.
SOLID
Single responsibility, open-closed, Liskov substitution, interface segregation, dependency inversion.
Strangler fig
Replacing a system incrementally by building the new one around it and moving functions one at a time.
Tolerant reader
A consumer that ignores unknown fields and values, so producers can extend messages compatibly.
Utility tree
Qualities refined into scenarios rated by importance and difficulty, used to find architecture drivers.
View
A representation of the architecture from one perspective: logical, module, runtime or deployment.
