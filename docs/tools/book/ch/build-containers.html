Build systems, toolchains and containers

How a C++ source file becomes a running process on an Arm target: compiling, linking, ELF, libraries and the dynamic loader; CMake and its neighbours; packages, versions and reproducible builds; cross toolchains and sysroots; LTO, PGO and sanitizers; what a container really is and why it shares the kernel and the GPU; and the CI infrastructure that turns a commit into a signed artifact.

1The big picture: from source code to a product

Writing the code of a perception function is perhaps half of the work of shipping it. The other half is turning hundreds of thousands of lines of C++ into exactly the right binaries for an Arm SoC running QNX or Linux, for an x86 simulation PC and for a unit-test runner, every time in the same way, from versioned inputs that an auditor can trace years later. This chapter is about that second half: the toolchain, the build system, the packages, the containers and the CI machinery around them.

1.1Why building C++ for a car is a problem of its own

A Python script runs wherever there is an interpreter. A C++ program does not exist as a runnable thing until a compiler has translated it for one specific processor, one operating system and one set of libraries. The result runs only in an environment that matches all three. On a laptop this is invisible because the compiler, the libraries and the machine that will run the program are the same. In automotive work they almost never are: the code is edited and compiled on an x86 Linux workstation or CI server, but it runs on an Arm Cortex-A cluster under QNX or embedded Linux, against libraries that exist only in the customer's platform SDK.

Three further pressures make the build a first-class engineering topic. First, size: a camera ECU application with its middleware is easily a million lines and a few thousand translation units, so a clean build takes tens of minutes and incremental builds must be correct and fast. Second, variants: the same code is built for several targets, in debug and release, with and without sanitizers, sometimes with different feature sets for different customers. Third, traceability: functional safety (ISO 26262), Automotive SPICE configuration management and cybersecurity regulation (UN R155/R156) all ask the same question in different words, "exactly which inputs produced the binary in this vehicle, and can you produce it again?" A build that depends on whatever happened to be installed on a developer's machine cannot answer that.

Why it matters

Most "it works on my machine" problems, most mysterious crashes after an update and a surprising share of schedule slips come from the build and its environment rather than from the code: a different compiler version, a library found in the wrong place, a stale object file, an unpinned dependency. Knowing what each tool does is what turns those from mysteries into ten-minute diagnoses.

1.2The toolchain at a glance

The word toolchain is meant literally: a chain of separate programs, each consuming the previous one's output. The compiler driver (g++, clang++, qcc) hides the chain behind one command, but each stage still exists and each produces a file you can inspect.

The split is not historical accident. Compiling each source file separately means that changing one file recompiles one file, and that thousands of files can be compiled in parallel on many cores or machines. The price is that no compiler invocation ever sees the whole program: a call to a function defined in another file is just a name, a promise that someone will provide it. Resolving those promises is the linker's job, and doing the last part of it at run time, so that libraries can be shared and updated, is the dynamic loader's. Around that chain sit the tools that decide what to run: the build system, which knows which outputs are out of date, and the package manager, which brings in code built by somebody else.

Throughout the chapter one small example appears again and again: luma.cpp computes the mean brightness of a frame, main.cpp calls it, and both are built into a program cam_stats for a 64-bit Arm Linux target with the GNU cross toolchain aarch64-linux-gnu-g++ (GCC 13). All tool output shown is real output of that build.

// luma.h
double mean_luma(const std::uint8_t* px, std::size_t n);

// luma.cpp
#include "luma.h"
static int calls = 0;                       // internal linkage: local symbol
double mean_luma(const std::uint8_t* px, std::size_t n) {
    ++calls;
    std::uint64_t sum = 0;
    for (std::size_t i = 0; i < n; ++i) sum += px[i];
    return n ? double(sum) / n : 0.0;
}

// main.cpp
#include "luma.h"
#include <cstdio>
#include <vector>
int frame_count = 0;                        // global: exported data symbol
int main() {
    std::vector<std::uint8_t> frame(1920 * 1080, 128);
    ++frame_count;
    std::printf("mean luma %.1f\n", mean_luma(frame.data(), frame.size()));
}

2From source file to object file

The first three stages of the chain turn one .cpp file into one object file. They run once per translation unit and know nothing about the rest of the program, which is exactly what makes them parallel and incremental, and also what makes C++ builds slower than they need to be.

2.1Preprocessing: text in, translation unit out

The preprocessor is a text processor that predates C++ and knows nothing about types or functions. It executes the lines starting with #: #include pastes the whole content of another file in place, #define introduces macros that are substituted textually, and #if/#ifdef keep or drop blocks of text depending on macros, which is how one source supports several platforms (#ifdef __QNX__) or build variants (NDEBUG switching off assert). The output, a single long stream of C++ with no directives left, is called the translation unit. You can see it with g++ -E.

The numbers are humbling. Our nine-line main.cpp becomes a translation unit of 20 962 lines, because <vector> and <cstdio> pull in a large part of the standard library headers. Every .cpp file that includes <vector> parses those same twenty thousand lines again. In a project with 2 000 source files and a few heavy headers (Eigen, OpenCV, Boost, generated AUTOSAR bindings), the compiler spends most of its time re-reading headers, not compiling your code.

$ aarch64-linux-gnu-g++ -E main.cpp | wc -l      # the translation unit
20962
$ aarch64-linux-gnu-g++ -E -dM main.cpp | grep aarch64   # macros the compiler predefines
#define __aarch64__ 1

Include paths decide which file an #include finds: -I dir adds a directory, -isystem dir adds one whose warnings are suppressed, and the compiler has built-in directories for the standard library and the C library. When cross-compiling, those built-in directories must point into the target's file tree, not the host's, which is the whole point of a sysroot (Section 7.3). A header found in the wrong place still compiles more often than not, and then produces a program that disagrees with the library it links against.

2.2Compilation: front end, optimiser, back end

The compiler proper (cc1plus inside GCC, the Clang front end in LLVM) parses the translation unit, checks types, instantiates templates, and lowers everything into an intermediate representation: GIMPLE in GCC, LLVM IR in Clang. The optimiser then transforms that representation: inlining small functions, propagating constants, removing dead code, unrolling and vectorising loops. Only the last phase, the back end, is specific to a processor. It selects machine instructions, allocates registers and schedules instructions for the target pipeline.

This three-part structure is why one compiler supports many targets. The front end and optimiser are shared, and adding a processor means adding a back end. It is also why Clang is a cross compiler out of the box (--target=aarch64-linux-gnu), while a GCC binary is built for exactly one target and you install one GCC per target (aarch64-linux-gnu-gcc, arm-none-eabi-gcc, the GCC inside QNX's qcc). The output of compilation is assembly text, visible with -S. For our function, the vectorisable loop and the static counter are easy to recognise:

$ aarch64-linux-gnu-g++ -O2 -S luma.cpp -o -        (directives removed)
_Z9mean_lumaPKhm:                      ← the mangled name of mean_luma(const uint8_t*, size_t)
	adrp	x3, .LANCHOR0                  ← address of 'calls' (page part)
	ldr	w2, [x3, #:lo12:.LANCHOR0]     ← ++calls
	add	w2, w2, 1
	str	w2, [x3, #:lo12:.LANCHOR0]
	cbz	x1, .L4                        ← if (n == 0) return 0.0
	...
	ldrb	w2, [x0], 1                    ← load one pixel byte, post-increment pointer
	...
	fdiv	d0, d0, d1                     ← double(sum) / n
	ret

The name in the first line is the C++ mangled name: _Z9mean_lumaPKhm encodes the function name and its parameter types (PKh = pointer to const unsigned char, m = unsigned long). That is how overloads with the same name get different symbols, and why a C++ function cannot be called from C without extern "C". The rules of mangling are part of the C++ ABI; see C++ 11.3.

2.3Assembly and the object file

The assembler (as, part of GNU binutils, or LLVM's integrated assembler) turns the assembly text into machine code and wraps it into an object file. An object file is not runnable. It contains the machine code of the functions defined in this translation unit, the initial values of its global variables, a symbol table that lists what it defines and what it needs from elsewhere, and relocations: notes saying "at offset 0x48 in the code there is a call to mean_luma; patch in its address once you know it". On Linux and QNX the format of object files, libraries and executables is the same: ELF.

$ aarch64-linux-gnu-objdump -dr -C main.o          (excerpt)
  48:	bl	0 <mean_luma(unsigned char const*, unsigned long)>
			48: R_AARCH64_CALL26	mean_luma(unsigned char const*, unsigned long)

The call instruction at offset 0x48 currently jumps to address 0, a placeholder. The relocation entry below it, of type R_AARCH64_CALL26, tells the linker to fill in a 26-bit PC-relative offset to mean_luma later. That 26-bit field also explains a classic Arm link error: a direct bl can only reach ±128 MB, so in very large binaries the linker has to insert small trampolines (veneers) to reach distant functions.

In practice

Ask the driver to keep every intermediate file with -save-temps and to print every command it runs with -v. When an include, a macro or a flag behaves unexpectedly, the preprocessed .ii file and the exact command line answer the question faster than any amount of reasoning about the build scripts.

2.4Why C++ builds are slow, and what helps

The separate-compilation model has a structural cost: every translation unit re-parses every header it includes, and every template used in many files is instantiated in each of them and deduplicated by the linker afterwards. Build time is therefore roughly number of translation units × size of what they include, and the second factor dominates. The remedies attack it at different levels.

Inside the code, the cheapest fix is include hygiene: forward-declare instead of including, keep heavy headers (Eigen, OpenCV, generated service bindings) out of other headers, and use the pimpl idiom for classes whose private members drag in large dependencies. Precompiled headers parse a set of stable headers once and load the result as a binary snapshot; CMake supports them with target_precompile_headers. Unity (jumbo) builds concatenate several .cpp files into one translation unit so shared headers are parsed once, at the risk of name clashes between file-local symbols. C++20 modules are the language-level fix: a module interface is compiled once into a binary form and imported, not textually included; tool support became usable with CMake 3.28 and recent compilers, but most automotive toolchains do not support them yet (C++ 10.5). Explicit template instantiation (extern template) moves the instantiation of a heavy template into one file.

Outside the code, two infrastructure tools give the largest wins. A compiler cache (ccache, sccache) hashes the preprocessed input together with the compiler and its flags and returns the stored object file if it has seen that exact combination before; a CI build of an unchanged branch then takes minutes instead of an hour. Distributed or remote compilation (distcc, icecream, Bazel remote execution) spreads translation units over many machines. Both work only because each translation unit is compiled independently from inputs that can be hashed, an idea we meet again in Section 11.3.

Numbers

A translation unit including <vector> and <cstdio>: ~21 000 lines. With Eigen or OpenCV core: 60 000–150 000 lines. A ccache hit costs a few milliseconds instead of 0.5–5 s for compiling the file. Large automotive projects typically see 80–95 % cache hit rates in CI once the cache is shared.

3Linking: symbols, ELF and libraries

The linker is the first tool that sees the whole program. Its job sounds simple, connect every use of a name with its one definition and lay the result out in memory, but almost every confusing build error ("undefined reference", "multiple definition", a library that is ignored, a program that links but crashes) is about one of its rules.

3.1Symbols: what an object file offers and what it needs

Each object file carries a symbol table: one entry per named function or variable it defines or references. nm prints it. The letter in the second column is the symbol's kind: T a function defined in this file's code (text) section, B a zero-initialised global in .bss, D an initialised global in .data, U undefined, i.e. used here but defined elsewhere, W/V weak. Upper case means global (visible to other files), lower case means local.

$ aarch64-linux-gnu-nm -C luma.o
0000000000000000 T mean_luma(unsigned char const*, unsigned long)
0000000000000000 b calls                        ← 'static int calls': local, invisible to others

$ aarch64-linux-gnu-nm -C main.o
                 U mean_luma(unsigned char const*, unsigned long)   ← needed from elsewhere
                 U operator new(unsigned long)                      ← from libstdc++
                 U __printf_chk                                      ← from libc (printf, fortified)
                 U memset
0000000000000000 B frame_count                  ← global data, offered to others
0000000000000000 T main

Linking is bookkeeping over these two lists. Every U in any object must be matched by exactly one global definition somewhere in the inputs. The keyword static at namespace scope (and anonymous namespaces) produces a local symbol that never takes part in this matching, which is why two files can each have their own static int calls without conflict. __printf_chk instead of printf is a small surprise worth knowing: Ubuntu's compiler enables _FORTIFY_SOURCE by default whenever optimisation is on, which redirects some libc calls to bounds-checking variants (Section 8.6).

3.2ELF: one format, two views

ELF (Executable and Linkable Format) serves two readers with different needs. The linker thinks in sections: named pieces such as .text (code), .rodata (constants), .data (initialised globals), .bss (zero-initialised globals, which occupy no space in the file), .symtab and the relocation sections. The loader thinks in segments (program headers): a few contiguous ranges that are mapped into memory with one set of permissions each. The linker's main output decision is how to pack sections into segments.

$ aarch64-linux-gnu-readelf -h cam_stats         (excerpt)

  Data:                              2's complement, little endian
  Type:                              DYN (Position-Independent Executable file)
  Machine:                           AArch64
  Entry point address:               0x9c0

$ aarch64-linux-gnu-readelf -lW cam_stats        (excerpt)
  Type           Offset   VirtAddr           FileSiz  MemSiz   Flg Align
  INTERP         0x000238 0x0000000000000238 0x00001b 0x00001b R   0x1
      [Requesting program interpreter: /lib/ld-linux-aarch64.so.1]
  LOAD           0x000000 0x0000000000000000 0x000c35 0x000c35 R E 0x10000
  LOAD           0x00fd20 0x000000000001fd20 0x0002f8 0x000300 RW  0x10000
  DYNAMIC        0x00fd30 0x000000000001fd30 0x000230 0x000230 RW  0x8
  GNU_STACK      0x000000 0x0000000000000000 0x000000 0x000000 RW  0x10
  GNU_RELRO      0x00fd20 0x000000000001fd20 0x0002e0 0x0002e0 R   0x1

Several details in this output are worth reading slowly. The type is DYN, not EXEC: modern distributions build position-independent executables (PIE) by default so that the kernel can load them at a random address (ASLR). The INTERP segment names the dynamic loader that the kernel must start first. The second LOAD segment has a larger memory size than file size: the difference (8 bytes here) is .bss, which the loader zero-fills. GNU_STACK without E means the stack is not executable. GNU_RELRO marks a range that the loader makes read-only again after relocation, a hardening measure. The first bytes of every ELF file are 7f 45 4c 46, i.e. \x7fELF, followed by the class and byte order; the Machine field is what produces the error "cannot execute binary file: Exec format error" when an Arm binary is started on an x86 PC.

QNX uses ELF as well, with its own loader (ldqnx-64.so.2) and C library, so the same tools (ntoaarch64-readelf, ntoaarch64-nm from the QNX SDP) work on QNX binaries. Windows uses a different format (PE/COFF) and macOS another (Mach-O); the concepts carry over, the details and tools do not.

3.3Symbol resolution step by step

The GNU linker processes its inputs strictly from left to right on the command line and keeps two sets: symbols already defined and symbols still undefined. An object file (.o) is always included completely. A static library (.a) is different: it is an archive of object files with an index, and the linker pulls out only those members that define a symbol currently in the undefined set, then forgets the library and moves on. That one rule explains why library order matters and why a library placed before the objects that need it is silently ignored. Step through it.

Object files on the command line are taken whole. main.o defines main and frame_count, so they go into the defined set. It needs mean_luma, printf/memset (libc) and operator new (libstdc++), so those go into the undefined set.

The linker looks into the archive's index. Member luma.o defines mean_luma, which is undefined, so luma.o is pulled in completely. Its own needs (here none new) join the undefined set. Member stats.o defines nothing anybody needs yet, so it is not linked: unused code in static libraries costs nothing in the binary.

Suppose luma.o called clamp_u8, defined in another archive member: the linker rescans the same archive until no new member is pulled. But it never goes back to an archive it has already finished. If libfilters.a, which comes later, needed something from libluma.a, the link would fail with "undefined reference" even though the definition is right there in a library on the command line.

libstdc++.so and libc.so are shared libraries. The linker does not copy their code; it checks that they define operator new, printf and memset, records them as NEEDED in the output, and leaves the final binding to the dynamic loader at run time (Chapter 4). The undefined set is now empty, so the link succeeds.

Now write g++ -lluma main.o. When the linker reaches libluma.a, nothing is undefined yet, so no member is pulled. Then main.o adds mean_luma to the undefined set, and no later input defines it: main.cpp:(.text.startup+0x48): undefined reference to `mean_luma(unsigned char const*, unsigned long)'. That is the real error of our build with the order swapped.

Cyclic dependencies between static libraries are handled with -Wl,--start-group ... --end-group, which makes the linker rescan the group until nothing changes, or simply by listing a library twice. Better is not to have cycles. LLVM's linker lld and the newer mold remember all archives and do not have this order sensitivity, which is one reason builds sometimes behave differently with them. Build systems like CMake compute the order from the declared dependencies between targets (Section 5.5), which is the main reason to declare them correctly rather than adding libraries to a flat list.

Pitfall

"Undefined reference" errors are not always about order. The other common causes: the definition is in a file that is not compiled into any target; a C function is declared without extern "C", so the C++ side looks for a mangled name; the declaration and definition differ in a parameter type, so the mangled names differ (nm -C shows both); the library was built for a different architecture or with a different standard-library ABI (std::__cxx11::basic_string versus the old ABI).

3.4Relocation: patching the addresses

Once every symbol has a definition, the linker decides where everything lives. It concatenates the .text sections of all included objects into one output .text, the .data sections into one .data, and so on, assigns each a virtual address, and now knows the address of every function and variable. It then walks all relocation entries and patches the placeholder fields: the bl 0 at main.o+0x48 becomes a branch to the real offset of mean_luma. Relocations that cannot be completed at link time, because the target lives in a shared library whose load address is unknown, are converted into dynamic relocations for the loader (Section 4.3).

Two linker options matter in embedded work. -ffunction-sections -fdata-sections at compile time put every function and variable into its own section, and -Wl,--gc-sections at link time then drops every section that nothing references, often shrinking a binary by 10–30 %. A linker script describes the memory layout explicitly; desktop and Linux programs use the built-in default, but bare-metal firmware for a microcontroller or a DSP core needs one that places code in flash, data in RAM and the vector table at a fixed address. A map file (-Wl,-Map=out.map) lists where every section of every object ended up and why it was included, which is the tool for "why is my binary 4 MB bigger than last week?"

3.5Static and shared libraries

A static library (libluma.a) is nothing more than an archive of object files made by ar. Linking against it copies the needed members into the executable, which then has no run-time dependency on the library. A shared library (libluma.so, a shared object) is itself a linked ELF file, almost an executable without main. Linking against it copies nothing; the executable only records the library's name, and the code is mapped into the process at start-up.

The trade-off is real in both directions. Shared libraries save disk and RAM when many processes use the same library (every process on the system uses libc), and they allow fixing a bug or a security hole in one place without relinking every program. They cost start-up time for loading and relocation, a small run-time cost for calls through the PLT (Section 4.3), and they create the deployment problem of making sure the right version is found at run time. Static linking gives one self-contained file, slightly faster calls, better whole-program optimisation, and no surprises from the target's library versions, at the price of size and of relinking everything for every fix.

Automotive practice uses both. The platform's middleware and the C and C++ runtime are almost always shared, because many processes use them and the platform team updates them independently. An application's own internal libraries are often linked statically into its executable so that the delivered unit is one file with a known content. Fully static executables are common for tiny tools and in initramfs or early-boot images, where there may be no loader at all. Two cautions: glibc does not really support static linking for programs that use name resolution or dlopen, and LGPL-licensed libraries carry obligations when linked statically.

Pitfall: -lluma prefers the shared library

When a directory contains both libluma.so and libluma.a, -lluma silently picks the shared one. We hit exactly this while preparing the examples: a build meant to be static linked without complaint and then failed at start with libluma.so.1: cannot open shared object file. Write -l:libluma.a or wrap the library in -Wl,-Bstatic ... -Wl,-Bdynamic to force the archive; in CMake, link the target or the full path of the archive rather than a bare name.

Talk track

"A static library is a bag of object files copied into the executable at link time; a shared library is a separately linked file that the loader maps in at start. Shared saves memory and lets the platform update one copy; static gives us a self-contained binary with a fixed content. We use shared for the platform runtime and static for our own internal libraries."

3.6Visibility, the ODR and duplicate symbols

By default every non-static function in a shared library is exported, i.e. visible to and overridable by every other module in the process. For a large C++ library that means tens of thousands of exported symbols, a slower loader, no chance for the compiler to inline across the library boundary, and an accidental public API. The fix is to compile with -fvisibility=hidden and mark the intended API explicitly with __attribute__((visibility("default"))), usually through a macro such as LUMA_API; CMake generates that macro with generate_export_header. A version script (-Wl,--version-script) achieves the same at link time and can attach version tags to symbols (Section 4.4).

The one-definition rule says that every non-inline function and variable has exactly one definition in the whole program, and every inline function, class and template has identical definitions in every translation unit that uses it. The linker enforces only the first half: two strong definitions of the same symbol give "multiple definition of ...". The second half it cannot check, because inline functions and template instantiations are emitted as weak (COMDAT) symbols and the linker silently keeps one of the copies. If two libraries were compiled with different definitions of the same inline function or class, for instance with different #defines that change a struct layout, the program links fine and one library calls the other's version of the code. That is a classic source of crashes that appear only in the integrated build.

Pitfall: ODR violations across libraries

Typical cases: two libraries each embed a different version of the same third-party header-only library (Eigen, a JSON parser); a struct changes size depending on a macro (EIGEN_MAX_ALIGN_BYTES, _GLIBCXX_DEBUG) that is set in one library's build but not the other's; two shared libraries export the same symbol and the loader binds both callers to whichever was loaded first. Hidden visibility, consistent flags from one toolchain configuration, and AddressSanitizer's ODR checker (ASAN_OPTIONS=detect_odr_violation=2) and the gold linker's --detect-odr-violations catch many of them.

4Loading and running: the dynamic loader

A dynamically linked executable is not finished when the linker exits. Every time it starts, the kernel and the dynamic loader complete the link: they find the shared libraries, map them, patch the addresses that depend on where everything landed, and run initialisers, all before main. Understanding that step explains "library not found", "version GLIBC_2.34 not found" and slow start-up.

4.1From execve to main

When a shell or a launcher starts a program, it calls execve(). The kernel opens the file, checks the ELF header, and maps its LOAD segments into a fresh address space. Because the file has an INTERP segment, the kernel also maps the program interpreter named there, the dynamic loader (/lib/ld-linux-aarch64.so.1 on 64-bit Arm Linux), and starts execution in the loader rather than in the program. A statically linked executable has no INTERP, and the kernel jumps straight to its entry point.

The loader reads the executable's dynamic section, a table of tags such as NEEDED (a required library), RUNPATH (where to look), and pointers to the dynamic symbol table and relocations. It loads each needed library, recursively loads their needs, applies the dynamic relocations of every module, runs the initialisers of every library in dependency order (C++ global constructors of each library run here), and finally jumps to the program's entry point _start. That small piece of C runtime start-up code calls __libc_start_main, which runs the executable's own global constructors and then calls main. When main returns, the same machinery runs destructors and atexit handlers in reverse order.

$ aarch64-linux-gnu-readelf -d cam_stats          (excerpt)

 0x0000000000000001 (NEEDED)             Shared library: [libstdc++.so.6]
 0x0000000000000001 (NEEDED)             Shared library: [libgcc_s.so.1]
 0x0000000000000001 (NEEDED)             Shared library: [libc.so.6]

 0x000000000000001e (FLAGS)              BIND_NOW

Interesting detail

Global constructors running before main in an unspecified order across translation units is the "static initialisation order fiasco": a global in one file that uses a global from another file may see it unconstructed. In shared libraries the order also depends on the loader's dependency sort. Function-local statics (constructed on first use) avoid the problem, and they make start-up cheaper, which matters for an ECU where the rear camera must show an image within about two seconds of power-on.

4.2Finding libraries: NEEDED, RUNPATH and the soname

The name recorded in NEEDED is not the file name the linker opened but the library's soname, a name stored inside the library when it was built (-Wl,-soname,libluma.so.1). On disk a versioned library typically appears three times: the real file libluma.so.1.2.0, a symlink libluma.so.1 (the soname, used at run time) and a symlink libluma.so (used only by the linker when you write -lluma, shipped in the development package). The soname carries the ABI version: as long as libluma.so.1.3.0 stays binary compatible, the soname remains libluma.so.1 and existing programs pick up the new file automatically; an incompatible change bumps it to libluma.so.2, and old programs keep loading the old library.

The loader searches for each soname in a fixed order: the DT_RPATH of the requesting module (deprecated), then the environment variable LD_LIBRARY_PATH, then the module's DT_RUNPATH, then the cache /etc/ld.so.cache built by ldconfig from /etc/ld.so.conf, and finally the default directories /lib and /usr/lib. $ORIGIN in a run path means "the directory of the module itself", which lets an application ship its libraries in a relative lib/ directory and be installed anywhere. QNX's loader follows the same idea with LD_LIBRARY_PATH and its own default paths.

$ ldd ./cam_stats             (run on the target, or through the loader under QEMU)
	linux-vdso.so.1 (0x0000400000810000)
	libluma.so.1 => /opt/camstats/bin/./libluma.so.1 (0x0000400000850000)
	libstdc++.so.6 => /lib/libstdc++.so.6 (0x0000400000890000)
	libgcc_s.so.1 => /lib/libgcc_s.so.1 (0x0000400000bc0000)

ldd shows the result of the search, including indirect dependencies (libm is needed by libstdc++, not by us) and the vDSO, a tiny library the kernel maps into every process so that calls such as clock_gettime do not need a real system call. Be careful with ldd on untrusted binaries: on glibc it works by running the loader on the program. readelf -d or objdump -p only read the file and are safe; LD_DEBUG=libs ./prog prints every directory the loader tries.

Pitfall

LD_LIBRARY_PATH set in a developer's shell or in a CI script makes everything work on that machine and hides a wrong run path, which then fails on the target. The loader also ignores it for set-user-ID programs. Prefer correct RUNPATH or install locations, and test the deployed layout in a clean environment, ideally a container or the target itself.

4.3Position-independent code, the GOT and the PLT

A shared library is mapped at a different address in every process (and, with ASLR, on every start), yet its code pages should be shared in physical memory, so the loader must not patch them. The solution is position-independent code: compiled with -fPIC, the code reaches its own functions and data with PC-relative addressing, which works at any load address, and reaches everything that lives in other modules through a table of addresses in the writable data segment, the global offset table (GOT). The loader patches only the GOT, a few pages of private data per process, and the code stays read-only and shared.

Function calls go through the procedure linkage table (PLT): for each external function the linker generates a three-instruction stub that loads the address from the function's GOT slot and jumps there. With lazy binding the slot initially points back into the loader, which resolves the symbol on the first call and overwrites the slot; that speeds up start-up when a program uses only a few of thousands of imported functions. With immediate binding (-Wl,-z,now, visible above as BIND_NOW) everything is resolved at start, after which the loader can make the GOT read-only (full RELRO). Ubuntu and most hardened builds default to immediate binding because a writable GOT is a favourite target for exploits. For automotive start-up budgets the difference is measurable on programs with many symbols, which is one more reason for hidden visibility.

Position-independent executables (PIE, -fPIE -pie) apply the same technique to the main program so that it, too, can be loaded at a random address. The cost on 64-bit Arm and x86-64 is small, typically around 1 % or less, because both have efficient PC-relative addressing; on 32-bit x86 it was several percent, which is why PIE took a long time to become the default.

4.4The binary ABI and symbol versioning

Two separately compiled pieces of machine code can work together only if they agree on a long list of conventions: which registers carry arguments and return values, how the stack is laid out, how structs are passed, how big and how aligned each type is, how C++ names are mangled, how exceptions unwind and how virtual tables are laid out. Together these form the application binary interface. The processor part is defined by documents such as the Arm "Procedure Call Standard for the Arm 64-bit Architecture" (AAPCS64); the C++ part by the Itanium C++ ABI, which GCC and Clang use on Linux and QNX. The library part is whatever the headers of each library say about its types and functions, which is where most breakage happens: adding a member to a public struct, changing a parameter type or reordering virtual functions breaks binary compatibility even though every caller still compiles. The language-level rules are in C++ 11.3.

glibc and libstdc++ solve their own compatibility problem with symbol versioning. Every exported symbol carries a version tag, and a program records the version it was linked against:

$ aarch64-linux-gnu-nm -D --undefined-only cam_stats     (excerpt)
                 U __libc_start_main@GLIBC_2.34
                 U __printf_chk@GLIBC_2.17
                 U _Znwm@GLIBCXX_3.4                ← operator new
                 U _ZdlPvm@CXXABI_1.3.9             ← sized operator delete

When glibc changes the behaviour of a function, it keeps the old implementation under the old tag and adds the new one under a new tag, so programs built years ago still get the behaviour they were built for. The flip side is the most common deployment error in embedded Linux: a program built against a newer glibc than the target has fails at start with version `GLIBC_2.34' not found. Our binary needs GLIBC_2.34 only because it was linked on Ubuntu 24.04, whose glibc moved __libc_start_main to a new version. The rule that follows is simple: always compile and link against the target's libraries, never the build machine's, which is exactly what a sysroot guarantees (Section 7.3). The C++ runtime has the same rule: an executable built with a newer GCC needs a libstdc++ at least that new on the target.

Numbers

libstdc++'s soname has been libstdc++.so.6 since GCC 3.4 in 2004; compatibility is maintained through symbol versions (GLIBCXX_3.4.x, CXXABI_1.3.x). The one big break, the C++11 std::string and std::list, was handled with a second ABI inside the same library (_GLIBCXX_USE_CXX11_ABI) rather than a new soname.

4.5dlopen and plugins

A program can also load a shared library on demand with dlopen() and look up functions by name with dlsym(). This is how plugin architectures work: a perception framework that loads one shared object per camera driver or per neural-network backend, an inference engine loading a vendor's delegate library, or a GStreamer pipeline loading elements. Because dlsym looks up a plain string, plugin entry points are declared extern "C" to avoid mangled names, and they usually return a pointer to a C++ interface object so that the rest of the communication is ordinary virtual calls.

Plugins bring the ABI problem in its sharpest form: the host and the plugin must have been built with compatible compilers, standard libraries and versions of every shared header, and nothing checks that at load time. A stable C interface at the boundary, or a version handshake function that the host calls first, turns silent memory corruption into a clear error message. For safety-relevant software, dynamic loading after start-up is usually forbidden altogether because it makes the set of executing code depend on run-time conditions.

5Build systems: Make, Ninja, CMake, Meson and Bazel

Nobody types compiler commands for two thousand files. A build system knows which outputs depend on which inputs, runs only the commands whose inputs changed, runs independent commands in parallel, and computes the right flags for each file. The tools differ mainly in how they describe the graph, who writes that description, and how much they trust the environment.

5.1Why a build system: the dependency graph

Every build is a directed acyclic graph. Sources and headers are leaves, object files depend on one source and every header it includes, libraries depend on their objects, executables on objects and libraries. A correct incremental build rebuilds exactly the nodes downstream of a change, no fewer (or the binary contains stale code) and no more (or every edit costs a full rebuild). Click a file in the figure to see what its change costs.

The difficult part is not the graph between objects and libraries, which is declared, but the edges from headers to objects, which are implicit in the #include lines and change whenever someone edits an include. Modern compilers solve this by writing the dependencies as a side effect of compilation: -MD -MF file.d makes GCC and Clang emit the list of every header they actually opened. The build system reads those files after each compile and therefore always knows the true header dependencies for the next build. You saw these flags in the CMake-generated command lines above (-MD -MT ... -MF ...d).

A build system has to decide what "changed" means. Make compares modification times: an output is stale when any input is newer. That is cheap but fragile; touching a file, switching branches or restoring files from a cache with new timestamps triggers rebuilds, and a clock skew between machines can hide changes. Bazel, Buck and the compiler caches compare content hashes instead: an output is reused when the hash of all its inputs, including the command line and the tool versions, matches a previous run. Hash-based builds are the foundation of shared caches and remote execution (Section 11.3).

5.2Make

Make (1976) is the ancestor of all of them and is still everywhere: in the Linux kernel, in Yocto recipes, in vendor SDKs and in the files that CMake can generate. A Makefile is a list of rules, each saying "this target depends on these prerequisites and is made by these shell commands":

CXX      := aarch64-linux-gnu-g++
AR       := aarch64-linux-gnu-ar
# -MMD -MP: while compiling, also write main.d / luma.d listing every header read
CXXFLAGS := -O2 -Wall -MMD -MP

# target: prerequisites, then the recipe (lines must start with a TAB); $@ = target, $^ = all prerequisites
cam_stats: main.o libluma.a
	$(CXX) -o $@ main.o -L. -lluma

libluma.a: luma.o
	$(AR) rcs $@ $^

# pattern rule: any .o from its .cpp; $< = the first prerequisite
%.o: %.cpp
	$(CXX) $(CXXFLAGS) -c $< -o $@

# header dependencies recorded by the previous build (silently skipped on the first one)
-include main.d luma.d

Make's strengths are that it is universal and that it can run any command, not only compilers. Its weaknesses show at scale. It is a general language with shell commands inside, so every project's Makefiles look different and portability between Linux, QNX hosts and Windows is painful. Large projects split it into one Makefile per directory and call them recursively, which hides the dependencies between directories from every individual Make process; the classic paper "Recursive Make Considered Harmful" (1997) describes the resulting stale or over-eager builds. And Make re-evaluates its whole rule set on every invocation, which takes seconds in large projects before any work starts.

5.3Ninja

Ninja was written in 2010 for the Chromium browser, where Make needed about ten seconds just to decide that nothing had to be rebuilt. Its design idea is to be the opposite of Make: a deliberately minimal language with no conditionals, no functions and no shell logic, meant to be generated by a higher-level tool, never written by hand. All the decisions are made when the file is generated; Ninja itself only loads a precomputed graph, compares timestamps, stores the exact command line of every output (so a changed flag also triggers a rebuild) and keeps all cores busy. A no-op build of a large project takes well under a second.

rule cxx
  command = aarch64-linux-gnu-g++ $flags -MD -MF $out.d -c $in -o $out
  deps = gcc                     # Ninja parses the .d file and keeps it in its own database
  depfile = $out.d
build luma.o: cxx src/luma.cpp
  flags = -O2 -fPIC

In practice nobody writes this; CMake, Meson and GN generate it, and you only run ninja or, better, cmake --build. Ninja runs as many jobs as there are cores by default (plus two), which is also why its output is interleaved and why its -v option, printing every full command, is the first thing to use when a build behaves strangely.

5.4CMake: a build-system generator

CMake is not a build system in the strict sense. It is a generator: it reads a project description in its own language (CMakeLists.txt), inspects the toolchain and the machine, and writes the files for a real build tool, usually Ninja or Make, or project files for Visual Studio or Xcode. It became the de-facto standard for C and C++ because it abstracts over compilers and platforms, because almost every open-source C++ library ships CMake support, and because IDEs (CLion, Visual Studio, VS Code) understand it directly.

The configure step is where most of the confusion lives. It runs once per build directory and caches what it finds, the compiler path, the found packages, every option, in CMakeCache.txt. Changing the compiler or the toolchain file afterwards has no effect until the cache is deleted, which is why "delete the build directory and configure again" fixes a surprising number of problems. Build directories are always separate from the source (out-of-source builds), so one checkout can have build-x86-debug, build-aarch64-release and build-asan side by side. CMakePresets.json stores these configurations, generator, toolchain file, cache variables, in the repository, so that developers, IDEs and CI configure identically with cmake --preset aarch64-release.

Interesting detail

CMake's own defaults are worth knowing. CMAKE_BUILD_TYPE=Release means -O3 -DNDEBUG with GCC and Clang, not -O2; RelWithDebInfo means -O2 -g -DNDEBUG. In the build tree, executables get an absolute RPATH pointing at the build directories so they run without installation; cmake --install rewrites or removes it. Both details explain differences between "it ran from the build directory" and "it runs on the target".

5.5Modern CMake: targets and usage requirements

Older CMake code set global variables (include_directories, add_definitions, CMAKE_CXX_FLAGS) that applied to everything below them. "Modern CMake", the style since about version 3.0, is built around targets: every library and executable is an object with properties, and each property is marked with who needs it. PRIVATE requirements are needed only to build the target itself; INTERFACE requirements are needed only by those who use it; PUBLIC means both. When a target links another, it automatically inherits the other's PUBLIC and INTERFACE requirements, transitively.

cmake_minimum_required(VERSION 3.25)
project(cam_stats VERSION 1.2.0 LANGUAGES CXX)

add_library(luma src/luma.cpp)                       # STATIC or SHARED via BUILD_SHARED_LIBS
target_include_directories(luma PUBLIC src)          # users of luma get this include path
target_compile_features(luma PUBLIC cxx_std_17)      # ...and at least C++17
target_compile_options(luma PRIVATE -Wall -Wextra)   # only luma itself is built with these
set_target_properties(luma PROPERTIES VERSION ${PROJECT_VERSION} SOVERSION 1)

add_executable(cam_stats src/main.cpp)
target_link_libraries(cam_stats PRIVATE luma)        # inherits luma's PUBLIC requirements

install(TARGETS cam_stats luma)

The payoff is that each library describes itself once, and every consumer gets exactly the include paths, definitions, language level and link dependencies it needs, in the right order, without copying flags around. You can see it in the real generated commands of this project: luma.cpp is compiled with -Wall -Wextra -fPIC, main.cpp gets -I.../src but not the warnings, the link line names libluma.so.1.2.0, and CMake created the soname symlinks.

$ cmake --preset aarch64-release && cmake --build --preset aarch64-release -v     (paths shortened)
[1/5] aarch64-linux-gnu-g++ --sysroot=/opt/sysroots/aarch64 -Dluma_EXPORTS -I src -O3 -DNDEBUG -fPIC -Wall -Wextra -MD -MT ... -c src/luma.cpp
[2/5] aarch64-linux-gnu-g++ --sysroot=/opt/sysroots/aarch64 -fPIC -O3 -DNDEBUG -shared -Wl,-soname,libluma.so.1 -o libluma.so.1.2.0 ...
[3/5] cmake -E cmake_symlink_library libluma.so.1.2.0 libluma.so.1 libluma.so
[4/5] aarch64-linux-gnu-g++ --sysroot=/opt/sysroots/aarch64 -I src -O3 -DNDEBUG -MD -MT ... -c src/main.cpp
[5/5] aarch64-linux-gnu-g++ --sysroot=/opt/sysroots/aarch64 -O3 -DNDEBUG main.cpp.o -o cam_stats -Wl,-rpath,... libluma.so.1.2.0

Consuming external libraries works the same way. find_package(OpenCV REQUIRED) locates a package's config file (OpenCVConfig.cmake), which defines imported targets such as opencv_core carrying their own include paths and link dependencies, so linking them is one line. Package managers (Chapter 6) produce exactly these config files, Conan through its CMakeDeps generator, vcpkg through its toolchain file. FetchContent downloads and builds a dependency as part of your project, convenient for small libraries and tests, but it rebuilds them in every build directory and bypasses version locking and binary reuse.

Pitfall

The three most common CMake mistakes: setting flags globally through CMAKE_CXX_FLAGS or include_directories, which leaks them into every target and every consumer; using file(GLOB ...) to collect sources, so a newly added file is not built until someone re-runs configure; and linking with PUBLIC where PRIVATE suffices, which exposes implementation dependencies to every consumer and slows everybody's builds.

Talk track

"CMake doesn't build anything; it generates a Ninja build from a target graph. Each library declares what its users need as PUBLIC or INTERFACE properties and what only it needs as PRIVATE, and CMake propagates that through the link graph. The toolchain file says what we build for; presets make every developer and the CI configure the same way."

5.6Meson and Bazel

Meson (2013) has the same architecture as CMake, a generator in front of Ninja, but a cleaner, deliberately non-Turing-complete language that looks like Python, fast configuration, and built-in concepts that CMake added late: cross files describing the target, a dependency fallback system (WrapDB) and good pkg-config integration. It is strong in the Linux desktop and system world (GNOME, systemd, Mesa, GStreamer, PipeWire), so an embedded Linux engineer meets it in Yocto recipes even when the own project uses CMake.

# meson.build
project('cam_stats', 'cpp', version : '1.2.0', default_options : ['cpp_std=c++17'])
luma = library('luma', 'src/luma.cpp', version : '1.2.0', soversion : '1')
executable('cam_stats', 'src/main.cpp', link_with : luma, install : true)

Bazel, the open-source version of Google's internal build system Blaze, takes a different stance: it trusts nothing that is not declared. Every target lists all its inputs explicitly, each action runs in a sandbox that can see only those inputs, and toolchains are themselves declared and versioned inputs rather than whatever is installed. The result is hermetic builds: the same inputs give bit-identical outputs on any machine. Because every action is a pure function of hashed inputs, Bazel can store results in a shared remote cache and run actions on a remote execution cluster, so a developer's build downloads most outputs that CI already produced.

# BUILD.bazel
cc_library(
    name = "luma",
    srcs = ["src/luma.cpp"],
    hdrs = ["src/luma.h"],
    includes = ["src"],
)
cc_binary(
    name = "cam_stats",
    srcs = ["src/main.cpp"],
    deps = [":luma"],
)

The price is adoption cost. Every third-party library needs Bazel build rules (the Bazel Central Registry and the newer Bzlmod module system help), vendor toolchains such as QNX's need hand-written toolchain definitions, and engineers must learn a new model. Bazel pays off in large monorepos with many languages and a shared cache; several automotive software organisations use it for exactly that reason, while most supplier projects use CMake because customers deliver CMake packages.

6Dependencies, versions and reproducible builds

No product is built only from its own code. A camera application depends on the customer's platform SDK, on OpenCV or Eigen, on an inference runtime, on generated interface code and on the compiler's own runtime libraries. Getting the right version of each, built the right way, every time, and being able to prove it later, is a separate discipline.

6.1Why C++ needs package managers

Python has pip and Rust has cargo; C and C++ grew up without any standard way to distribute libraries, and their binaries are much harder to share because a compiled library is only usable with a compatible compiler, standard library, architecture, operating system, build type and set of options. Teams historically chose one of four approaches, each with a clear failure mode. System packages (apt install libopencv-dev) give whatever version the build machine's distribution has, for the build machine's architecture, which is wrong for cross-compiling and changes when the machine is upgraded. Vendoring, copying a library's source into the repository, pins the version but makes updates and security fixes manual. Git submodules pin a commit but still build everything from source in every build. Prebuilt binaries in a shared folder are fast but untraceable.

A C++ package manager combines the good parts: a recipe that knows how to build a library, versioned references, prebuilt binaries per configuration stored on a server, and a lockfile that freezes the whole resolved graph. The two widely used ones are Conan and vcpkg; in automotive Conan dominates because it handles binary-only customer packages and arbitrary toolchains well.

6.2Conan, briefly

Conan describes each package with a Python recipe (conanfile.py), identifies each binary by a package_id computed from the settings it was built with (OS, architecture, compiler and version, C++ standard, build type) and its options and dependencies, and selects settings through profiles: a host profile for the target and a build profile for tools that run on the build machine. Binaries live on a remote, usually a JFrog Artifactory or a Conan server, and are cached locally. Lockfiles pin every version and recipe revision. Conan 2 generates CMake config files (CMakeDeps) and a CMake toolchain file (CMakeToolchain), so the CMake side stays ordinary find_package and target_link_libraries.

How a customer platform team ships its SDK as Conan packages, what a drop contains, a consuming recipe and a QNX profile, and why "missing prebuilt package" is the most common error: Inside the camera ECU, Chapter 6.

6.3vcpkg

vcpkg, from Microsoft, takes the opposite default: it builds from source, from one curated registry of about 2 500 ports in a Git repository, and makes binaries reusable through binary caching. A project lists its dependencies in a manifest, and a baseline, a commit of the registry, fixes the version of every port at once, so the whole team and CI resolve the same versions:

{
  "name": "cam-stats",
  "version": "1.2.0",
  "dependencies": [ "eigen3", { "name": "opencv4", "default-features": false, "features": ["jpeg"] } ],
  "builtin-baseline": "<commit sha of the vcpkg registry>",
  "overrides": [ { "name": "eigen3", "version": "3.4.0" } ]
}

The target configuration is called a triplet (arm64-linux, x64-windows; custom triplets point to your own CMake toolchain file), and vcpkg integrates with CMake by being passed as the toolchain file (-DCMAKE_TOOLCHAIN_FILE=.../vcpkg.cmake, chaining your cross toolchain file through VCPKG_CHAINLOAD_TOOLCHAIN_FILE). vcpkg is excellent for open-source dependencies and Windows; Conan is stronger when binaries without sources must be distributed between companies, which is the normal OEM–supplier situation.

6.4Versions: API, ABI, SemVer and sonames

Semantic versioning (MAJOR.MINOR.PATCH) promises that a PATCH release only fixes bugs, a MINOR release adds features compatibly, and only a MAJOR release may break users. For C++ the promise has to be read twice, because there are two kinds of compatibility. Source (API) compatibility means existing code still compiles. Binary (ABI) compatibility means existing binaries still work against the new library without recompiling. Adding a data member to a public class, a new virtual function or a default argument keeps the API but breaks the ABI. For shared libraries, the soname should change with every ABI break (Section 4.2); for statically linked or source-built dependencies, only the API matters, because everything is rebuilt together.

Tools such as abi-compliance-checker and libabigail's abidiff compare two builds of a library and report ABI breaks, which is worth running in CI for any library delivered as a binary to other teams or customers. Within a product, the safest rule is the one from Section 4.4: all binaries that are linked or loaded together are built with one toolchain configuration from one consistent set of dependency versions.

6.5Lockfiles, version ranges and the diamond

Recipes can ask for a version range ("OpenCV 4.x, at least 4.8") so that compatible updates flow in automatically. That is convenient for libraries and dangerous for products, because the same recipe can resolve differently next month. A lockfile records the exact result of a resolution, every package, version and recipe revision, and later builds use it instead of resolving again. The rule of thumb: libraries declare ranges, products commit lockfiles, and lockfile updates are deliberate, reviewed changes.

The diamond is the conflict every package manager must handle: the application uses library A and library B, A wants zlib 1.2, B wants zlib 1.3. In one process there can be only one zlib (the ODR again, Section 3.6), so somebody has to decide. Package managers report the conflict and let the consumer override the version explicitly; the override then needs a justification and a test that both A and B work with it. In the worst case, a library built as a binary against one version and run against another, the problem appears only at run time.

6.6Reproducible builds

A build is reproducible when the same source, the same dependencies and the same toolchain produce bit-for-bit identical output, regardless of who builds it, when and where. That sounds automatic but is not, because compilers and tools quietly embed the environment into their output: __DATE__ and __TIME__ macros, timestamps in archives and packages, absolute paths of the build directory in debug information and assertion messages, file-system ordering of a directory listing, the user name, the locale, random seeds in some code generators, and parallel build output that depends on timing.

The fixes are well known and collected by the reproducible-builds.org project, which Debian, Yocto and others use. Set SOURCE_DATE_EPOCH to the commit time so every tool uses it instead of the clock. Map build paths with -ffile-prefix-map=$PWD=. so debug information and __FILE__ do not contain the CI runner's directory. Use deterministic archive mode (ar D, the default on most current distributions). Sort file lists, avoid timestamps in generated code, and pin the toolchain itself, typically by running the build in a container image identified by its digest (Section 9.8). Then verify by building twice in different directories and comparing hashes, a tool such as diffoscope shows exactly which bytes differ.

Why bother? Reproducibility is what makes a binary verifiable: anyone can rebuild from the tagged sources and confirm that the delivered binary contains nothing else, which is the strongest answer to supply-chain attacks (Section 11.6). It makes caching correct, because identical inputs really give identical outputs. And it is the practical meaning of the configuration management requirement in automotive processes: a field issue on software version 2.3.1 can be debugged with exactly the binary and symbols that are in the vehicle, rebuilt years later.

In practice

Full bit-for-bit reproducibility takes effort and is not always reached, especially with vendor toolchains that embed license information or timestamps. A useful intermediate goal is rebuildability: every released artifact records the commit, the lockfile, the toolchain image digest and the build command, and a rebuild from those produces a functionally identical binary. Keep the unstripped binary or a separate debug-info file for every release (Section 8.2), keyed by its build ID.

7Cross-compilation: toolchains, sysroots and Arm targets

An automotive camera ECU has a fast Arm SoC, but it is still far slower to compile on than a 64-core build server, it often has no compiler installed at all, and it may not even be running yet when the software is written. So code is compiled on one machine for another. That is easy in principle and full of small traps in practice, nearly all of them about the compiler finding the wrong headers or libraries.

7.1Vocabulary: build, host and target

The GNU convention uses three machines. The build machine runs the compiler (your x86-64 Linux workstation or CI runner). The host machine runs the program being built (the Arm ECU). The target machine matters only when the program being built is itself a compiler: it is the machine the compiler will generate code for. For ordinary application work, build ≠ host is all that matters, and a cross compiler is simply a compiler whose host is the build machine and whose target is the ECU. Confusingly, CMake and Conan call the ECU the "host" in exactly this GNU sense (Conan's -pr:h host profile), while everyday speech calls it "the target".

Each platform is named by a target triplet of the form architecture-vendor-OS-ABI, and the tools are prefixed with it: aarch64-linux-gnu-g++ (64-bit Arm, Linux, glibc), arm-linux-gnueabihf-gcc (32-bit Arm, Linux, hard-float ABI), aarch64-unknown-nto-qnx8.0.0 (64-bit Arm, QNX Neutrino 8; QNX's driver qcc -V gcc_ntoaarch64le wraps it), arm-none-eabi-gcc (bare-metal Cortex-M or Cortex-R, no OS). The triplet tells you which C library and calling conventions the code will assume, and two toolchains for the same CPU with different triplets produce incompatible binaries.

7.2What a toolchain contains

A cross toolchain is more than a compiler. It is a matched set of programs that run on the build machine and libraries and headers that belong to the target, and every piece must agree with the others and with the target's operating system.

The compiler (GCC or Clang) and binutils (assembler, linker, objdump, readelf, strip, ar) generate and handle target code. The compiler's own runtime support, libgcc or compiler-rt, provides helper functions for operations the CPU lacks in hardware. The C library (glibc, musl, or QNX's libc) and the C++ standard library (libstdc++, libc++) exist twice in a sense: their headers and link-time stubs in the sysroot on the build machine, and their run-time shared objects on the target. They must be the same version, or at least the target's must be newer, which is the GLIBC_2.34 story of Section 4.4. Toolchains come from three typical sources: the distribution's cross packages (as used for this chapter's examples), a vendor SDK (QNX Software Development Platform, an SoC vendor's Linux SDK, Arm GNU Toolchain), or a Yocto- or Buildroot-generated SDK that exactly matches the image built for the board.

7.3The sysroot

A sysroot is a directory on the build machine that mirrors the relevant part of the target's root file system: usr/include with the target's headers and lib and usr/lib with its libraries. The option --sysroot=dir tells the compiler and linker to look for headers and libraries only under that directory, exactly as if it were /. That is the single most important rule of cross-compilation: the compiler must never see the build machine's own /usr/include and /usr/lib. If it does, the build may succeed with x86 headers that differ in subtle ways (struct sizes, macros, versions) or fail with "file in wrong format" at link time.

The best sysroot is generated from the same build that produces the target image: Yocto's populate_sdk task or Buildroot's SDK create one that contains exactly the libraries and versions the board runs. Copying /usr from a running board also works and is a classic quick fix, with one trap we hit while preparing this chapter. Libraries such as libm.so are often small text files, linker scripts that name the real libraries by absolute path. Inside a sysroot the linker prefixes those paths with the sysroot, so a script written for a different layout fails with cannot find /usr/aarch64-linux-gnu/lib/libm.so.6 inside /usr/aarch64-linux-gnu. The fix is a sysroot with the standard layout, which is why generated SDKs are preferable to hand-assembled ones.

7.4CMake toolchain files and Conan profiles

CMake learns about the target from a toolchain file, a short CMake script passed once at the first configure (--toolchain file or -DCMAKE_TOOLCHAIN_FILE=file). It sets the target system, the compilers and the sysroot, and tells find_package, find_library and find_path where to search. This one was used for the real build in Section 5.5:

# cmake/aarch64-linux-gnu.cmake  -- describes the TARGET, read once at the first configure
set(CMAKE_SYSTEM_NAME      Linux)
set(CMAKE_SYSTEM_PROCESSOR aarch64)

set(CMAKE_C_COMPILER   aarch64-linux-gnu-gcc)
set(CMAKE_CXX_COMPILER aarch64-linux-gnu-g++)

set(CMAKE_SYSROOT /opt/sysroots/aarch64)               # target headers + libraries
set(CMAKE_FIND_ROOT_PATH ${CMAKE_SYSROOT})

# Programs (code generators) come from the build machine,
# libraries, headers and packages only from the sysroot.
set(CMAKE_FIND_ROOT_PATH_MODE_PROGRAM NEVER)
set(CMAKE_FIND_ROOT_PATH_MODE_LIBRARY ONLY)
set(CMAKE_FIND_ROOT_PATH_MODE_INCLUDE ONLY)
set(CMAKE_FIND_ROOT_PATH_MODE_PACKAGE ONLY)

The four FIND_ROOT_PATH_MODE lines encode the build/host split. Tools that run during the build, a protobuf compiler or an AUTOSAR code generator, must be build-machine executables, so programs are never searched in the sysroot; libraries and headers must be target files, so they are searched only there. Setting CMAKE_SYSTEM_NAME also switches CMake into cross-compiling mode, where it cannot run the test programs it compiles, so any try_run in a project needs a precomputed answer. A QNX toolchain file looks the same with CMAKE_SYSTEM_NAME QNX, the qcc driver and the SDP's target directory as the sysroot; QNX also requires the environment from the SDP's qnxsdp-env.sh to be sourced. With Conan, the host profile names the same toolchain and Conan's CMakeToolchain generator writes the toolchain file for you.

7.5Choosing the target CPU, and emulating it

The compiler needs to know not only the architecture but which variant of it may be assumed. -march=armv8.2-a allows instructions of that architecture level (for example half-precision floating point and dot-product instructions with the right extensions); -mcpu=cortex-a78ae additionally tunes instruction scheduling for that core and implies its architecture. Choosing too new a level produces illegal-instruction crashes on older cores; choosing too old leaves performance on the table, NEON is baseline on AArch64, but dot-product and SVE are not (Embedded compute 10 explains the SIMD side). On 32-bit Arm, the float ABI is part of the triplet: hf (hard-float) passes floating-point arguments in FPU registers, and soft-float objects cannot be linked with hard-float ones.

Without hardware, Arm binaries can still run on the build machine through QEMU user-mode emulation: qemu-aarch64 translates the program's instructions on the fly and forwards its system calls to the host kernel. Registered with the kernel's binfmt_misc mechanism, it makes Arm executables start transparently, and it is how unit tests of cross-compiled code run on x86 CI runners and how multi-architecture container images are built (Section 9.8). Every program output in this chapter came from qemu-aarch64. It is roughly 3–10 times slower than native code, does not emulate the target's GPU, ISP or NPU, and runs on Linux syscalls, so QNX binaries need a full-system QEMU or a QNX virtual machine instead. For timing and hardware access there is no substitute for the board or a hardware-in-the-loop rig.

7.6One source file all the way to a running process

Here is the whole chain of Chapters 2–4 and this chapter in one place: luma.cpp edited on an x86 workstation, ending as running code inside a process on a 64-bit Arm target. Step through it; each step names what is produced and which tool or component is responsible.

cmake --preset aarch64-release reads the toolchain file, detects aarch64-linux-gnu-g++, checks that it can compile and link a test program against the sysroot, resolves find_package through the Conan- or vcpkg-generated config files, and writes build.ninja. From now on every command line is fixed.

Ninja sees that luma.cpp.o is older than luma.cpp and runs the cross compiler. The preprocessor pastes in headers from the sysroot, the front end and optimiser turn it into IR, the AArch64 back end produces assembly with ldrb, fdiv and the mangled name _Z9mean_lumaPKhm.

The assembler writes luma.cpp.o: AArch64 machine code in .text, the counter in .bss, a symbol table offering mean_luma, and relocations for every address not yet known. A .d file records which headers were read, for the next incremental build.

The linker turns luma.cpp.o into libluma.so.1.2.0 with soname libluma.so.1, then links main.cpp.o against it and against libstdc++ and libc from the sysroot. It resolves every symbol it can, records NEEDED entries, a RUNPATH and versioned symbol references such as GLIBC_2.34, and writes PLT stubs and GOT slots for the rest.

cmake --install fixes the run path and installs into a staging directory; the binaries are stripped, the debug information is kept separately by build ID, and the result is packed (an IPK or RPM package, a Conan package, a file-system image, or an AUTOSAR Adaptive software package) and signed. On a development board it is simply copied with scp; on a production ECU it arrives through the flashing or update process.

A launcher (systemd, Adaptive's execution manager, QNX's slm) calls execve("/opt/camstats/bin/cam_stats"). The kernel checks the ELF header (AArch64: yes), maps the two LOAD segments at a random base address, maps /lib/ld-linux-aarch64.so.1 named in INTERP, sets up the stack with arguments and environment, and jumps into the loader.

The loader reads NEEDED, finds libluma.so.1 next to the program through $ORIGIN and the system libraries through ld.so.cache, maps each, checks the symbol versions, fills every GOT slot (BIND_NOW), makes RELRO pages read-only and runs library initialisers. A missing library or version stops the start right here, with a clear message.

The loader jumps to _start, which calls __libc_start_main; global constructors run, then main. The call to mean_luma goes through the PLT stub and the GOT slot into the library's code page, which is shared with every other process using libluma. The output is mean luma 128.0.

8Optimisation and checking as build options

The same source can become a slow binary full of debug checks, a fast binary tuned for one core, or an instrumented binary that catches memory errors. Those differences come entirely from flags. Knowing what the main ones do lets you pick the right build for each job and explain why the release build behaves differently from the debug build.

8.1Optimisation levels and target flags

-O0 translates each statement literally and keeps every variable in memory, ideal for debugging and useless for performance measurements. -O1 does cheap optimisations. -O2 enables nearly all optimisations that do not trade size for speed, and is the usual production level. -O3 adds more aggressive inlining, loop transformations and vectorisation; it is often a little faster and sometimes slower because the code grows and thrashes the instruction cache. -Os and -Oz optimise for size, which matters for microcontrollers and boot code. -Og optimises only as far as it does not disturb debugging.

Two other groups of flags change results more than people expect. Target flags (-mcpu, -march, Section 7.5) decide which instructions may be used at all. Floating-point flags decide which algebra the compiler may assume: -ffast-math allows reassociation, ignores NaN and infinity and flushes denormals, which can speed up image filters considerably and can also change results or break NaN checks, so it should be applied per file and only where tested. Optimisation never changes the meaning of a correct program, but it exposes undefined behaviour that happened to work at -O0, which is why "it works in debug" is not evidence that the code is correct (C++ 3.4).

8.2Debug information and build types

-g adds DWARF debug information, a description of source lines, types, variables and inlining that the debugger uses. It does not change the generated code, so a release build should always be compiled with -g and the debug information split off before deployment: objcopy --only-keep-debug extracts it into a separate file, strip removes it from the shipped binary, and the build ID, a hash note that the linker writes into every ELF file (visible in file output above), links the two. A core dump from the field can then be debugged with the exact symbols of the binary that crashed. Debug information is large, often several times the code size, which is why -gsplit-dwarf and compressed debug sections exist.

Projects usually define a small set of build types and keep them consistent across all components: Debug (-O0 -g, assertions on), Release with debug info (-O2 -g -DNDEBUG, the shipped configuration), and instrumented builds for sanitizers and coverage. Mixing build types across libraries that are linked together is allowed for most code but can break when headers change layout with NDEBUG or debug-mode macros such as _GLIBCXX_DEBUG, the ODR problem of Section 3.6.

8.3Link-time optimisation

Separate compilation has a performance cost: the compiler cannot inline a function from another translation unit, cannot see that a function is called with only one constant argument, and cannot remove a function that nobody calls. Link-time optimisation moves optimisation to the point where the whole program is visible. With -flto, the compiler writes its intermediate representation (GIMPLE or LLVM bitcode) into the object files instead of, or in addition to, machine code. At link time, the linker hands all of that IR to the compiler again, which optimises across file boundaries and only then generates machine code.

Typical gains are 5–15 % in speed and often 10–20 % in size, more for code with many small functions across files. The cost is link time and memory: a monolithic LTO link of a large program can take many minutes on one core. ThinLTO (Clang) and GCC's partitioned WHOPR mode keep most of the benefit while doing the expensive work in parallel and incrementally. LTO also makes ODR violations and undefined behaviour more visible, because more code is optimised together, and it requires that every object in the link was compiled by a compatible compiler version. In CMake it is one property, INTERPROCEDURAL_OPTIMIZATION, checked with the CheckIPOSupported module.

8.4Profile-guided optimisation

Even with the whole program visible, the compiler has to guess which branches are taken and which functions are hot. Profile-guided optimisation replaces guesses with measurements. First build with instrumentation (-fprofile-generate), then run the program on representative input, which writes counts of how often each branch and function executed, then rebuild with -fprofile-use. The compiler now inlines what is hot, keeps cold error handling out of the hot path, lays out code so that the common path falls through, and tunes loop unrolling. Gains of 10–20 % are common for branchy code; for tight numeric kernels that are already vectorised, much less.

The catch is the word "representative". A profile from a test that does not resemble production data optimises for the wrong case, and the profile must be regenerated when the code changes substantially. Sampling-based variants (AutoFDO, and BOLT, a post-link optimiser that rearranges a finished binary using perf samples) collect profiles from production-like runs without an instrumented build. For an embedded vision pipeline, PGO pays off mostly in control-heavy code such as tracking, post-processing and middleware, not in convolution kernels that run on the NPU anyway.

8.5Sanitizers

A sanitizer is compiler instrumentation plus a run-time library that detects a class of bugs as they happen. The compiler inserts a check before every relevant operation, and the run time keeps the metadata those checks need and prints a precise report on the first error. They find bugs that tests miss because the program happened not to crash, and they find them where they occur, not where the damage surfaces.

Pitfall

A sanitizer only reports bugs on code paths that actually execute, so its value is proportional to test coverage. Uninstrumented prebuilt libraries are blind spots (and for MSan a source of false reports). Sanitizer builds also change timing and memory layout so much that they are not suitable for timing tests or for shipping.

8.6Hardening flags and warnings

A second family of flags makes the shipped binary harder to exploit and some bugs fail loudly instead of silently. -D_FORTIFY_SOURCE=2 (or =3) replaces calls such as memcpy and printf with checking variants when sizes are known at compile time, the __printf_chk seen in Section 3.1. -fstack-protector-strong puts a canary value before the return address and aborts if it was overwritten. -fstack-clash-protection probes large stack allocations page by page. PIE plus -Wl,-z,relro,-z,now give full ASLR and a read-only GOT. On Armv8.3 and later, -mbranch-protection=standard enables pointer authentication of return addresses and branch target identification, which make return- and jump-oriented attacks much harder. -D_GLIBCXX_ASSERTIONS turns on cheap precondition checks in libstdc++ (bounds checks in operator[], non-empty checks in front()), and -fwrapv defines signed overflow as wrapping, removing one class of undefined behaviour at a small optimisation cost. The OpenSSF "Compiler Options Hardening Guide" keeps a current list.

Warnings are the cheapest checker of all. -Wall -Wextra plus a few targeted ones (-Wshadow, -Wconversion where practical, -Wnon-virtual-dtor) catch real bugs, and -Werror in CI keeps the count at zero. Which warnings and static-analysis rules are mandatory, and how they gate merges, is a quality policy question covered in the software quality chapter; the build's job is to apply the chosen set consistently to every target, which modern CMake does with a PRIVATE compile option or an interface target that carries the project's warning set.

9Containers: what they really are

A container feels like a small virtual machine: its own file system, its own process list, its own network. It is not. It is an ordinary process on the host's kernel that the kernel has been told to lie to: about which files exist, which other processes exist and which network it is on, plus limits on how much CPU and memory it may use. Everything useful and everything dangerous about containers follows from that one fact.

9.1Why containers exist

The problem containers solve is the one this whole chapter keeps running into: software depends on its environment. A build needs exactly this compiler, this CMake, this Conan, this sysroot and this Python; a service needs exactly these shared libraries. Installing those directly on developer laptops and CI machines leads to drift, where every machine is slightly different and nobody can reproduce last year's build. Virtual machines solve it by shipping a whole operating system, which is heavy: gigabytes per image, tens of seconds to boot, a full kernel's worth of memory each. Containers package only the user-space part, the files of a root file system, and run them on the host's existing kernel, so they start in milliseconds and cost little more than the processes inside.

For an automotive software team, containers are mainly a development and CI tool. The toolchain image, an image with the cross compilers, the QNX SDP or Yocto SDK, CMake, Conan and the analysis tools, is the single definition of "the build environment", versioned like code; developers use the same image locally or through VS Code dev containers, and CI runners use it for every job. Simulation and software-in-the-loop tests run in containers on servers. On the vehicle itself, containers are only beginning to appear on Linux-based high-performance computers (Section 10.5).

9.2A container is a process

When you run docker run ubuntu:24.04 bash, the Docker daemon asks containerd, which asks a small low-level runtime called runc, to start bash as a normal Linux process with a few extra properties. runc creates new namespaces for the process, puts it into a new cgroup, mounts the image's file system as its root, drops most of root's privileges, installs a seccomp filter, and then executes bash. On the host, ps shows that bash like any other process, with an ordinary PID; inside, it believes it is PID 1 on a machine with nothing else running. There is no guest kernel, no emulated hardware and no boot.

The layering of tools is standardised by the Open Container Initiative (OCI): an image format, a runtime specification (a JSON description of the namespaces, mounts, limits and process to start) and a distribution protocol for registries. Docker, Podman, containerd, CRI-O and Kubernetes all speak these, so an image built with one runs with the others. Podman runs without a central daemon and can run containers as an unprivileged user, which many CI setups prefer.

9.3Namespaces: a private view of the system

A namespace wraps one kind of global system resource so that processes inside it see their own instance. Linux has eight kinds, and a container normally gets a new one of most:

Note what is not on the list: there is no namespace for the kernel itself, for kernel modules, for the system clock, for devices in general or for the GPU. Those stay shared, which is the subject of Chapter 10. Namespaces and cgroups from the kernel's side: Linux 3.7.

9.4cgroups: limits on resources

Namespaces control what a process can see; control groups (cgroups) control how much it can use. A cgroup is a node in a hierarchy, exposed as a directory under /sys/fs/cgroup, and every process belongs to exactly one. Controllers attached to the hierarchy account and limit resources per group: cpu (a weight, and a hard quota such as "150 ms of CPU time every 100 ms" for 1.5 cores), cpuset (which cores and memory nodes), memory (a hard limit; exceeding it invokes the out-of-memory killer inside the group), io (block-device bandwidth), pids (a maximum number of processes, which stops fork bombs) and the device access rules. docker run --cpus 1.5 --memory 2g writes exactly these values. Current systems use cgroup v2, a single unified hierarchy; v1 had a separate hierarchy per controller.

The limits are about quantity, not interference. A memory limit caps how much RAM a container may allocate, but it does not stop the container from saturating the memory bus; a CPU quota caps CPU time, but two containers on neighbouring cores still share the last-level cache. A CPU quota can also introduce latency: a container that uses up its quota early in a period is throttled until the next period, which shows up as periodic stalls of tens of milliseconds in latency-sensitive services. For real-time or timing-critical work, cpuset pinning to dedicated cores is the better tool.

9.5Capabilities, seccomp and rootless containers

Root inside a container is still root on the shared kernel unless something restricts it, so runtimes add more layers. Linux splits root's power into about forty capabilities (CAP_NET_ADMIN, CAP_SYS_ADMIN, CAP_SYS_MODULE, ...), and Docker keeps only a small default set, so a container's root cannot load kernel modules, change the clock or mount file systems. A seccomp filter blocks dozens of rarely needed and historically dangerous system calls (Docker's default profile blocks around 40–50 of the more than 300 system calls). Mandatory access control (AppArmor or SELinux) adds file and operation rules. With user namespaces, root inside maps to an ordinary UID outside, so even an escape lands as an unprivileged user; this is how rootless Podman and rootless Docker work.

docker run --privileged removes almost all of these layers at once: all capabilities, no seccomp filter, all devices. It is often added to make hardware access or nested Docker "just work" in CI, and it effectively gives the container root on the host. A container that mounts the Docker socket (/var/run/docker.sock) can start a privileged container itself, so the socket is equivalent to root as well.

Pitfall

"It runs in a container, so it is isolated" is the most expensive misunderstanding about containers. A container is as isolated as its configuration: privileged mode, a mounted Docker socket, broad device access or host networking each remove a large part of the boundary, and even a perfect configuration shares one kernel with everything else on the machine.

9.6Images and layers: the overlay file system

A container image is a stack of read-only file-system layers plus a small JSON configuration (default command, environment, working directory, architecture). Each layer is a tar archive of the files added, changed or deleted relative to the layer below; each instruction in a Dockerfile that changes files produces one layer. Layers are identified by the SHA-256 hash of their content, so identical layers are stored and downloaded only once, no matter how many images share them: ten toolchain images based on the same Ubuntu layer store that layer once.

At run time, the storage driver, normally overlayfs in the Linux kernel, stacks the layers into one directory tree: the read-only layers as "lower" directories and an empty, container-private writable directory as the "upper" one. A read finds the file in the highest layer that contains it. The first write to a file from a lower layer copies the whole file up into the writable layer, and the write happens there (copy-up). Deleting a file creates a whiteout marker in the upper layer that hides the lower copy. When the container is removed, its upper layer disappears; anything worth keeping belongs in a volume or bind mount.

Two consequences are worth remembering. First, deleting a file in a later layer does not make the image smaller: the file is still stored in the earlier layer, only hidden. Downloading a 2 GB SDK, unpacking it and deleting the archive in three separate RUN steps leaves the archive in the image forever, so such work belongs in one step, or in a separate build stage. Second, copy-up of large files is slow, and write-heavy data (build directories, caches, databases) should live in volumes rather than in the overlay.

9.7Writing a good Dockerfile

A Dockerfile is a build script whose steps are cached by layer: a step is re-run only if the step itself or anything before it changed, including the files it copies. Ordering the steps from least to most frequently changing therefore decides whether a rebuild takes ten seconds or ten minutes. A toolchain-and-build image for the cross build of this chapter might look like this:

# syntax=docker/dockerfile:1
# ---- stage 1: the build environment (changes rarely) ----
# pinned by digest, not just by tag
FROM ubuntu:24.04@sha256:<digest> AS toolchain
ARG DEBIAN_FRONTEND=noninteractive
# install and clean up in the same RUN step, so the apt cache never lands in a layer
RUN apt-get update \
 && apt-get install -y --no-install-recommends \
        cmake ninja-build ccache python3-pip \
        g++-aarch64-linux-gnu qemu-user \
 && rm -rf /var/lib/apt/lists/*
RUN pip install --no-cache-dir --break-system-packages conan==2.9.2
COPY sysroots/aarch64 /opt/sysroots/aarch64

# ---- stage 2: the build (changes with every commit) ----
FROM toolchain AS build
WORKDIR /src
# dependencies first: this layer stays cached until the lockfile changes
COPY conanfile.py conan.lock profiles/ ./
RUN conan install . -pr:h ./aarch64-linux -pr:b default --lockfile=conan.lock --build=missing
# sources last
COPY . .
RUN --mount=type=cache,target=/root/.ccache \
    cmake --preset aarch64-release && cmake --build --preset aarch64-release \
 && cmake --install build/aarch64-release --prefix /out

# ---- stage 3: only the result ----
FROM scratch AS artifact
COPY --from=build /out/ /

The structure carries the important ideas. Multi-stage builds keep compilers and sources out of the final stage; docker build --target artifact --output type=local,dest=out . writes only the installed files to disk, and for a runtime image the last stage would start from a small base instead of scratch. Copying the lockfile before the sources means dependency installation is cached until the dependencies change. BuildKit's cache mount keeps the ccache directory between builds without putting it into any layer. Pinning the base image by digest makes the environment reproducible (Section 9.8). For the toolchain image itself, the same rules hold: one image per toolchain version, tagged with that version, rebuilt and rescanned regularly, and the digest of the image used recorded with every build. One syntax detail explains why the comments above sit on their own lines: a Dockerfile treats # as a comment only at the start of a line.

9.8Registries, tags, digests and multi-architecture images

Images are stored in registries (Docker Hub, GitHub Container Registry, Harbor, Artifactory, a cloud provider's registry) using the OCI distribution protocol. An image in a registry is described by a manifest: a small JSON document listing the configuration and the layers by their hashes. The hash of the manifest itself is the image's digest (sha256:...), which identifies that exact content forever. A tag such as ubuntu:24.04 or toolchain:latest is only a movable pointer to a digest: the same tag can mean different content tomorrow. Anything that must be reproducible or trusted references images by digest.

A tag can point to an image index (manifest list) instead of a single manifest, with one entry per platform: linux/amd64, linux/arm64, linux/arm/v7. When a client pulls, it chooses the entry matching its own architecture, so one name serves x86 servers and Arm boards. docker buildx build --platform linux/amd64,linux/arm64 builds both variants, either natively on runners of each architecture or by running the Arm build steps under QEMU through binfmt_misc (Section 7.5), which is simple but slow for compile-heavy images. For C++ projects the faster pattern is to cross-compile inside an amd64 container and only assemble the arm64 runtime image, or to use native Arm CI runners, which are now widely available.

Talk track

"A container is a normal Linux process with its own namespaces, so it sees its own files, processes and network, and a cgroup that limits its CPU and memory. The image is a stack of content-addressed read-only layers that overlayfs presents as one file system, with a thin writable layer on top. There is no guest kernel: every container on a machine shares the host's kernel, which is why containers are light and also why they are not a security boundary as strong as a VM."

10Containers and hardware: devices, GPUs and drivers

Perception development needs GPUs for training and inference, cameras and CAN interfaces on development rigs, and sometimes NPUs on evaluation boards. Containers make the software around them reproducible, but the hardware itself and the kernel drivers that operate it cannot be put into a container. Understanding exactly where that line runs explains every "works on the host, not in the container" problem with GPUs and devices.

10.1Devices in containers

On Linux, user space reaches hardware through device files in /dev: /dev/video0 for a V4L2 camera, /dev/dri/renderD128 for a GPU, /dev/ttyUSB0 for a serial adapter, CAN interfaces as network devices. A container sees none of them by default: its mount namespace has a minimal /dev, and the cgroup device controller (implemented as an eBPF program in cgroup v2) denies access to device numbers that were not allowed. docker run --device /dev/video0 does both things: it creates the device node inside the container and allows its major and minor number. The process inside then calls the very same kernel driver as a process on the host would, through open, ioctl and mmap.

That last point is the essence. Passing a device into a container does not virtualise it. The container gets direct access to the host's driver, with the driver's full attack surface, and shares the device with everything else on the host. Two containers opening the same camera compete exactly like two processes would. Network-type devices such as SocketCAN interfaces are different again: they belong to a network namespace and have to be moved into the container's namespace (or the container runs with host networking). Hot-plugged USB devices need extra rules, because the device node appears after the container started.

10.2GPUs: what is shared and what is injected

A GPU stack has two halves that must match. In the host kernel runs the kernel-mode driver (for NVIDIA nvidia.ko and friends; for Mali, Adreno or Intel GPUs a DRM driver) that owns the hardware, its memory and its scheduling. In each process runs a user-mode driver, shared libraries such as libcuda.so, libnvidia-ml.so, or the OpenGL ES, Vulkan and OpenCL libraries, that translates API calls into command buffers and submits them to the kernel driver through ioctls on the device files. The interface between the two halves is private and changes with every driver release, so the user-mode libraries must match the kernel driver version exactly.

That matching requirement is why GPU containers need help from the runtime. If an image shipped its own libcuda.so, it would work only on hosts with exactly that driver version. Instead, the NVIDIA Container Toolkit hooks into container creation: docker run --gpus all makes it add the GPU device nodes (/dev/nvidia0, /dev/nvidiactl, /dev/nvidia-uvm), bind-mount the host's user-mode driver libraries and tools such as nvidia-smi into the container, and allow the devices in the cgroup. The image contains everything above the driver: the CUDA runtime, cuDNN, TensorRT, PyTorch. The Container Device Interface (CDI) standardises the same idea for all vendors as a JSON description of which device nodes, mounts and environment a device needs, used by Docker, Podman and Kubernetes.

$ docker run --rm --gpus all nvidia/cuda:12.4.1-base-ubuntu22.04 nvidia-smi   # driver injected from the host
$ docker run --rm --device /dev/dri --group-add video my-gles-test             # Mesa/DRM GPU: device nodes only
$ docker run --rm --device /dev/video0 --group-add video my-capture-test       # a V4L2 camera

For GPUs driven by Mesa, open-source user-space drivers that support many kernel versions, passing /dev/dri is often enough, because the image's Mesa talks to the kernel's stable DRM interface. Embedded GPUs with proprietary user-space drivers (Mali, PowerVR, Adreno, NVIDIA Jetson) behave like the NVIDIA desktop case: the vendor libraries in the container must match the board's kernel driver and firmware. NVIDIA's Jetson images, for example, are tied to the L4T release of the host's JetPack, and an image for one L4T version generally does not work on another.

10.3Driver and runtime compatibility

The version rules for CUDA illustrate the general pattern. The driver (kernel module plus user-mode driver, installed on the host) supports a maximum CUDA version, which nvidia-smi prints. The CUDA runtime and toolkit inside the image must not be newer than that, because a newer runtime may call driver functions that do not exist yet; older runtimes keep working on newer drivers (backward compatibility). Since CUDA 11, an application built with a newer minor toolkit release (say 12.6) also runs on an older driver of the same major release (one that supports only 12.2), with some features unavailable (minor-version compatibility), and on data-centre GPUs a forward-compatibility package lets newer runtimes run on older drivers. Libraries above the runtime, such as cuDNN and TensorRT, are tied to specific CUDA versions, and TensorRT engine files are tied to the exact TensorRT version and GPU model they were built for.

The practical consequences for a team: the host driver is the slowest-moving piece and constrains everything else, so CI GPU runners and developer machines should standardise on a driver version that supports every image in use; images declare the CUDA version they need (NVIDIA's images do so with the NVIDIA_REQUIRE_CUDA variable, which the toolkit checks at start); and inference artifacts built for deployment are built on the target platform's exact software stack, not on the developer's workstation GPU.

Numbers

Container start overhead: tens to a few hundred milliseconds. Run-time CPU overhead of namespaces and cgroups: practically zero, the code runs natively. GPU compute inside a container: the same speed as on the host, because the same driver submits the same work. Typical CUDA base images: ~100–250 MB (base), several GB once cuDNN, TensorRT and a framework are added.

10.4What container isolation does not isolate

Containers isolate views and quantities. They do not isolate the things every container shares by construction, and that list is exactly where both security and timing arguments break.

The kernel. Every container makes system calls into the same kernel. A kernel vulnerability reachable through an allowed system call is a container escape: Dirty COW (2016) and Dirty Pipe (2022) let unprivileged code overwrite read-only files and were exploitable from containers. Runtime bugs matter too: in 2019 a flaw in runc (CVE-2019-5736) let a malicious container overwrite the host's runc binary, and in 2024 the "Leaky Vessels" flaw (CVE-2024-21626) leaked a host directory file descriptor into new containers. Seccomp and capabilities shrink the reachable surface, but the boundary is still one shared, very large kernel. A virtual machine's boundary is the much smaller hypervisor interface, and sandboxes such as gVisor (a user-space kernel) or Kata Containers (each container in a lightweight VM) exist precisely to get VM-strength isolation with a container workflow.

The GPU and other devices. All containers using a GPU go through one kernel driver and one device. The driver is a large, complex piece of kernel code reachable from inside the container. GPU memory is managed by that driver, and isolation between contexts depends on it; the "LeftoverLocals" disclosure (CVE-2023-4969) showed that on several vendors' GPUs one process could read another's leftover on-chip local memory. Unless the hardware partitions the GPU (NVIDIA MIG on data-centre GPUs, or SR-IOV virtual functions), containers also share its scheduler: a long kernel from one container delays every other one.

Timing. cgroups limit CPU time and memory size, but not shared caches, memory bandwidth, interconnect or GPU time slicing (unless platform features such as Intel RDT or Arm MPAM are configured). One container streaming through memory can slow another one down noticeably, the noisy-neighbour effect.

For the vehicle, this is why containers are not used to argue freedom from interference between functions of different ASIL in the sense of ISO 26262. Mixed criticality on an automotive SoC relies on hypervisors with separate kernels, separate cores and partitioned memory and devices, or on a safety-certified OS with its own partitioning (Embedded compute 6.6). Containers can separate QM applications from each other inside one Linux partition, which is useful but a different claim.

Why it matters

In a customer or safety discussion the precise sentence matters: "containers give us reproducible packaging and resource limits; they do not give us an independent kernel, and they do not partition the GPU. Our safety separation comes from the hypervisor and the OS partitioning."

10.5Containers on the target?

Classic camera ECUs do not run containers: they run QNX, an RTOS or a fixed embedded Linux image whose processes are defined at build time, and AUTOSAR Adaptive already provides its own deployment unit (software packages installed and started by the execution and update managers). Docker in particular, with its daemon and image management, is a poor fit for a constrained, safety-relevant device. QNX has no Docker at all; its isolation tools are processes, resource managers and adaptive partitioning.

The picture is changing on Linux-based high-performance computers for the "software-defined vehicle", where several suppliers' applications share one powerful SoC and should be updatable independently. There, lightweight OCI runtimes (containerd, crun, Podman, sometimes with a minimal orchestration layer) are used to package and start QM applications, with the same image format as in CI. The rules of this chapter apply unchanged: the images must match the target's architecture and kernel drivers, the GPU and NPU are shared, and safety separation still comes from the layers below. Development boards and test benches, on the other hand, use containers routinely to bring a known software environment onto the hardware.

11Development infrastructure: from commit to artifact

Everything so far, toolchains, build systems, packages, containers, comes together in continuous integration. CI is the machine that turns every commit into built, tested, traceable artifacts for every target, and continuous delivery is the part that promotes some of them towards a release. For an engineering manager it is also where most of the team's waiting time, infrastructure cost and supply-chain risk live.

11.1Why CI infrastructure

The core idea of continuous integration is simple: integrate small changes often, and let a machine check each one in a clean, defined environment before it is merged. The value comes from the clean environment as much as from the tests. A CI job starts from a fresh container built from a pinned image, checks out an exact commit, resolves dependencies from a lockfile and builds from scratch or from a verified cache, so its result does not depend on anybody's laptop. The record it leaves behind, which commit, which toolchain image, which dependencies, which tests passed, is the evidence that configuration management and release processes require.

A CI system has a few standard parts. A server or service (GitLab CI, GitHub Actions, Jenkins, Azure DevOps, Zuul) holds the pipeline definitions and decides what runs when. Runners (agents) execute jobs, usually inside containers, on pools of machines: large x86 servers for builds, Arm servers for native Arm work, machines with GPUs, and runners attached to hardware-in-the-loop benches with real ECUs. Caches make jobs fast, an artifact registry stores the results, and secrets management provides signing keys and credentials only to the jobs that need them. Which checks must pass before a merge, the quality gates, test levels and static analysis policy, is a process decision covered in the software quality chapter; this section is about the infrastructure that runs them.

11.2One CI job from commit to artifact

Follow one merge request through it. A developer pushes a branch; the CI service reads the pipeline definition from the repository at that commit, so pipeline changes are versioned and reviewed like code. The build stage fans out into a matrix: an x86-64 Linux build for host tests and simulation, an aarch64 Linux build with the GNU cross toolchain, and an aarch64 QNX build with the QNX SDP. Each job runs in its toolchain image, referenced by digest; it restores the dependency cache keyed by the lockfile's hash, installs Conan packages from the internal remote, configures with a preset and builds with ccache pointed at the shared cache. The same commit additionally builds sanitizer variants for the host.

The test stage runs each test where it can run: host unit and component tests natively, the same tests under ASan+UBSan and TSan, the aarch64 Linux test binaries under QEMU user mode, and a smoke test on a real board or hardware-in-the-loop bench for the QNX build, often only nightly or on merge, because hardware is scarce. Results are published as test reports attached to the pipeline. The package stage runs only if the earlier stages passed: it installs the outputs, creates packages (Conan packages, a deployable image or an Adaptive software package), generates an SBOM from the lockfile and the image, writes a provenance record and signs everything. The publish stage uploads the signed artifacts to a development repository in the artifact registry, tagged with the commit and pipeline ID. A release later promotes exactly those bits to a release repository after the required approvals.

# .gitlab-ci.yml (excerpt)

In practice

The pipeline is a product with users, and its speed shapes how the team works. A merge pipeline under about 15 minutes keeps changes small; one that takes two hours makes people batch changes and stop waiting for green. The levers are almost always the same: shared compiler and dependency caches, fewer and larger runners, running only affected targets and tests, moving the slow hardware tests to a nightly or merge-train stage, and keeping toolchain images pre-pulled on the runners.

11.3Build caches

Every cache in a build is built on the same idea: if a step is a pure function of its inputs, its output can be stored under a hash of those inputs and reused whenever the same inputs appear again. The difference between caches is the size of the step. ccache and sccache cache single compiler invocations: the key is a hash of the preprocessed source (or, in direct mode, of the source and all headers it included), the compiler binary, and the flags. Since ccache 4.4 its cache can be shared through a remote storage backend (HTTP, Redis), and sccache stores in cloud object stores, so all CI runners and developers share hits. Dependency caches (the Conan cache, vcpkg's binary cache) avoid rebuilding third-party packages. Docker layer caches avoid rebuilding unchanged image layers, and can be exported to the registry (--cache-to/--cache-from). Bazel's remote cache applies the idea to every action of the build graph, compile, link, code generation and test, which is the most general form.

A cache is only as correct as its key. If an input that affects the output is missing from the key, an environment variable read by a code generator, a header found outside the declared include paths, the absolute build path embedded in debug info, the cache can return a wrong result, and nobody notices because the build succeeds. Hermetic builds and reproducible-build discipline (Section 6.6) are what make caching safe. A shared cache is also an attack surface: whoever can write to it can inject object files into everybody's builds, so typically only trusted CI jobs on protected branches write to the shared cache, while merge request jobs and developers only read.

11.4Artifact registries, versioning and promotion

An artifact registry is the system of record for everything a build produces or consumes: Conan packages, container images, firmware and file-system images, test reports, debug symbols. JFrog Artifactory and Sonatype Nexus host many formats in one place; OCI registries (Harbor, GitLab's and GitHub's registries) are increasingly used for non-container artifacts as well, through the OCI artifact format. The registry also proxies external sources: builds pull open-source packages and base images through a caching mirror rather than directly from the internet, which makes them faster, independent of upstream outages and auditable.

Three rules make a registry trustworthy. Artifacts are immutable: a published version is never overwritten, a fix is a new version. Artifacts are traceable: each carries metadata linking it to its commit, pipeline, toolchain image, lockfile and test results. And releases are made by promotion, not rebuild: the binary that passed integration testing is moved or copied from a development repository to a staging and then a release repository; rebuilding "the same version" for release would produce a different, untested binary. Retention policies remove development builds after weeks while keeping released artifacts and their debug symbols for the vehicle's lifetime, which in automotive means fifteen years or more.

11.5SBOMs: knowing what is inside

A software bill of materials is a machine-readable list of every component in a delivered piece of software: name, version, supplier, license, a hash, and how the components depend on each other. Two formats dominate. SPDX, from the Linux Foundation, is an ISO standard (ISO/IEC 5962) with roots in license compliance; CycloneDX, from OWASP, is an Ecma standard (ECMA-424) with roots in security. Both are JSON or XML documents that tools can generate and consume.

SBOMs are generated, never written by hand. The best source is the build itself: the package manager's lockfile knows every dependency and version (Conan, vcpkg and Yocto can all emit SBOMs), and scanners such as Syft inspect container images and file systems for installed packages. The SBOM is then stored with the artifact and used continuously: vulnerability scanners (Grype, Trivy, Dependency-Track) match its components against vulnerability databases such as the NVD and OSV and raise an alert when a new CVE affects a version that is in a shipped product, years after release. Because many reported vulnerabilities are not exploitable in a given product, a VEX (vulnerability exploitability exchange) document records the assessment "affected / not affected, because ..." next to the SBOM.

In automotive, UN R155 requires a cybersecurity management system that monitors and responds to vulnerabilities over the vehicle's lifetime, and ISO/SAE 21434 describes the vulnerability monitoring activities; OEMs therefore increasingly require SBOMs from suppliers with every software delivery, along with license information for open-source compliance. The SBOM answers the first question after every new headline vulnerability: "which of our products and vehicles contain the affected version?"

The regulatory side, R155, R156 and ISO/SAE 21434, and threat analysis (TARA): Standards and regulations, Chapter 5.

11.6Supply-chain security

Attackers increasingly target the path from source to binary rather than the product itself, because one compromised build tool or dependency reaches every user. Three incidents frame the threat. In the SolarWinds attack (2020), malware on the vendor's build servers inserted a backdoor into a signed product during compilation; the source code in the repository was clean. In 2021 the "dependency confusion" research showed that many companies' build tools would fetch a public package with the same name as an internal one if its version number was higher. In 2024 a long-prepared backdoor was found in the xz compression library (CVE-2024-3094), inserted by a maintainer who had gained the project's trust over two years; the malicious code was hidden in test files and activated only by a modified build script in the release tarballs, which differed from the Git repository.

The defences map onto the topics of this chapter. Pin everything by version and hash: lockfiles for packages, digests for base and toolchain images, and fetch only through the internal registry mirror, with internal package names reserved so they cannot be shadowed. Build from verified source: tagged commits rather than release tarballs where possible, and reproducible builds so that independent rebuilds can detect tampering. Protect the build system: ephemeral, isolated runners, no long-lived credentials in jobs, and signing keys available only to the release pipeline. Sign and attest: sign artifacts and images (Sigstore's cosign, or the company's PKI), and produce a provenance attestation, a signed statement of which source, which builder and which inputs produced which artifact (the in-toto format). The SLSA framework ("Supply-chain Levels for Software Artifacts") grades this: at Build Level 1 provenance exists, at Level 2 it is signed by a hosted build platform, at Level 3 the build platform is hardened so that even the build's own steps cannot forge it. Know and watch what you ship: SBOMs and continuous vulnerability monitoring, with an update path (UN R156) to fix what is found.

Talk track

"Every artifact we deliver is built in CI from a tagged commit, in a toolchain container pinned by digest, from dependencies pinned in a lockfile and fetched through our registry. It is signed, comes with an SBOM and a provenance record, and is promoted to release without rebuilding. So for any binary in a vehicle we can say exactly what is in it, rebuild it, and tell within hours whether a new CVE affects it."

12.3One-sentence explanations

Toolchain

Preprocessor, compiler, assembler and linker as separate stages; the loader finishes the link on the target at every start.

Translation unit

One source file after all includes are pasted in; the unit of compilation, parallelism and caching.

Object file

Machine code plus a symbol table of what it offers and needs, plus relocations for addresses not yet known.

Linker

Matches every undefined symbol with one definition, lays out sections into segments and patches addresses.

Archive order

GNU ld pulls archive members only for symbols undefined at that moment, so libraries go after their users.

Static vs shared

Static copies code into the executable; shared is mapped once and shared, found and bound at run time.

Soname

The ABI name of a shared library recorded in NEEDED; it changes only when binary compatibility breaks.

PIC, GOT, PLT

Code reaches other modules through a patched table of addresses, so code pages stay read-only and shared.

Symbol versioning

glibc keeps old implementations under old tags; build against the target's libraries or fail with "GLIBC_x not found".

ODR

One definition per program; the linker catches duplicate strong symbols but not different inline definitions.

CMake

A generator: targets with PUBLIC/PRIVATE/INTERFACE usage requirements in, a Ninja build out.

Bazel

Hermetic, hash-based actions in sandboxes, so results can be cached and executed remotely.

Lockfile

The frozen result of dependency resolution; products commit it and update it deliberately.

Reproducible build

Same inputs, bit-identical output, by removing timestamps, paths and ordering from the result.

Sysroot

The target's headers and libraries on the build machine; the compiler must never see the host's own.

Toolchain file

Tells CMake the target system, compilers and sysroot, and to find programs on the host and libraries in the sysroot.

LTO / PGO

Optimise across files at link time / optimise with measured branch and call frequencies.

Sanitizers

Compiler instrumentation that stops at the first memory error, UB or data race, at the exact line.

Container

A host process with its own namespaces, limited by cgroups, on an overlay root file system, sharing the host kernel.

Image

Content-addressed read-only layers plus config; reference it by digest, a tag can move.

GPU in a container

The image brings the runtime; the host's kernel driver and matching user-mode driver are injected and shared.

Isolation limits

No separate kernel, no GPU partitioning, no cache or bandwidth isolation: not a safety separation.

CI artifact

Built once from pinned inputs, tested, signed, with SBOM and provenance, then promoted, never rebuilt.

Supply chain

Pin, mirror, build from verified source, sign, attest, and monitor what you shipped.

QSelf-check questions

Core questions with short model answers; the chapter sections hold the depth. The second group checks understanding with "why" and "what if" questions rather than definitions.

Core questions

What happens when you compile and link a C++ program?Basic

Each source file is preprocessed into a translation unit (includes pasted, macros expanded), compiled into IR, optimised, turned into assembly for the target CPU and assembled into an object file with a symbol table and relocations. The linker then combines all objects and libraries, resolves every undefined symbol to one definition, lays out sections into segments and patches addresses. For dynamic executables, the loader completes the link at run time by mapping shared libraries and filling the GOT.

Static versus shared libraries: differences and when to use which?Basic

A static library is an archive of object files; needed members are copied into the executable at link time. A shared library is a separately linked ELF file mapped in by the loader at start, shared between processes, replaceable without relinking. Shared saves memory and allows independent updates but adds load-time cost and deployment risk; static gives a self-contained binary and more optimisation. Typical split: platform runtime shared, internal application libraries static.

What does "undefined reference" mean and how do you debug it?Basic

The linker found a use of a symbol but no definition in any input. Check with nm -C whether some object or library defines exactly that symbol: missing source file in the target, wrong library order with GNU ld, missing extern "C", a signature mismatch that changes the mangled name, or a library built for another architecture or standard-library ABI.

Why does the order of libraries on the link line matter?Intermediate

GNU ld scans inputs left to right and pulls an archive member only if it defines a symbol that is undefined at that moment; it does not revisit earlier archives. So a library must come after the objects and libraries that use it, and cyclic dependencies need --start-group or repetition. lld and mold do not have this restriction, and CMake derives the order from target dependencies.

What are the GOT and the PLT?Intermediate

The global offset table is a table of addresses in the writable data segment that position-independent code uses to reach symbols in other modules; the loader fills it. The procedure linkage table holds small stubs that jump through GOT entries for function calls, optionally resolving them lazily on the first call. Together they keep code pages read-only and shareable while still allowing libraries to load at any address.

What is an ABI and how can you break it without breaking the API?Intermediate

The ABI is the binary contract between compiled pieces: calling convention, type sizes and alignment, struct layout, name mangling, vtable layout, exception handling, plus the library's exported symbols. Adding a data member to a public class, inserting a virtual function, changing a parameter from int to long or changing an inline function all keep source compatibility but break existing binaries. For shared libraries such changes require a new soname.

What is a sysroot and why do you need one for cross-compilation?Basic

A directory on the build machine containing the target's headers and libraries in the target's file-system layout. --sysroot makes the compiler and linker use only those, so the program is compiled against the same headers and linked against the same library versions that exist on the target, instead of the build machine's x86 files. Without it you get wrong-architecture link errors or, worse, version mismatches like "GLIBC_2.34 not found" at run time.

What goes into a CMake toolchain file?Intermediate

The target system name and processor, the C and C++ compilers, the sysroot, the find-root path, and the find modes: programs from the host, libraries, headers and packages only from the sysroot. Optionally default flags for the CPU. It is passed once at the first configure and cached; QNX and vendor SDKs ship their own.

Explain PUBLIC, PRIVATE and INTERFACE in CMake.Intermediate

They say who needs a usage requirement such as an include directory, definition, compile feature or linked library. PRIVATE: only to build this target. INTERFACE: only for targets that link this one. PUBLIC: both. Requirements marked PUBLIC or INTERFACE propagate transitively along target_link_libraries, so each library describes itself once and consumers get the right flags and link order.

What is LTO and what does it cost?Intermediate

Link-time optimisation stores compiler IR in object files and runs optimisation and code generation at link time across all of them, enabling cross-file inlining, constant propagation and dead-code removal; typical gains are 5–15 % speed and 10–20 % size. It costs link time and memory (mitigated by ThinLTO or partitioning), requires compatible compiler versions for all objects, and exposes latent ODR violations and UB.

Which sanitizers do you know and what does each find?Basic

AddressSanitizer: out-of-bounds, use-after-free, double free and leaks, using shadow memory and red zones, about 2× slowdown. UBSan: undefined behaviour such as signed overflow, bad shifts, misaligned or null access. ThreadSanitizer: data races, 5–15× slowdown. MemorySanitizer (Clang): reads of uninitialised memory. ASan, TSan and MSan cannot be combined, so CI runs separate jobs.

How does a Docker container work under the hood?Intermediate

It is an ordinary process on the host kernel started by a runtime such as runc with new namespaces (mount, PID, network, UTS, IPC, user) so it has its own view of the system, placed in a cgroup that limits CPU, memory and other resources, with an overlayfs root built from the image layers, a reduced capability set and a seccomp filter. No guest kernel, no hardware emulation.

Container versus virtual machine?Basic

A VM runs its own kernel on virtual hardware provided by a hypervisor; a container shares the host kernel and only isolates the view and resources of processes. Containers start in milliseconds and add almost no overhead but provide a weaker security boundary (the whole kernel syscall surface) and cannot run a different kernel or OS. VMs are heavier but give stronger isolation; gVisor and Kata Containers sit in between.

How do image layers and overlayfs work?Intermediate

An image is a stack of read-only tar layers identified by content hash plus a config. overlayfs merges them into one tree, adding a writable upper layer per container. Reads come from the highest layer containing a file; the first write copies the file up; deletes create whiteouts. Layers are shared between images and containers, and files deleted in later layers still occupy space in earlier ones.

How do you give a container access to an NVIDIA GPU, and why is the driver not in the image?Intermediate

Install the NVIDIA Container Toolkit on the host and run with --gpus (or CDI). It adds the device nodes, allows them in the cgroup and bind-mounts the host's user-mode driver libraries into the container. The user-mode driver must match the host's kernel module exactly, so shipping it in the image would tie the image to one driver version; the image carries only the CUDA runtime and libraries, which must not be newer than the driver supports.

What is an SBOM and why do OEMs ask for it?Basic

A machine-readable list of all components in delivered software, with versions, suppliers, licenses, hashes and dependencies, in SPDX or CycloneDX format, generated from the build. OEMs need it for vulnerability monitoring over the vehicle lifetime (UN R155, ISO/SAE 21434) and open-source license compliance: when a new CVE appears, they can find every affected product immediately.

What would a good CI pipeline for a multi-target C++ product look like?Advanced

Pipeline definition in the repository; jobs in toolchain containers pinned by digest; dependencies from a lockfile through an internal registry mirror; a build matrix per target and build type with presets; shared compiler and dependency caches written only by trusted jobs; host tests natively and under sanitizers, Arm tests under QEMU, hardware tests on HIL nightly or on merge; packaging, SBOM, provenance and signing; publish to immutable development repositories and promote to release without rebuilding; merge pipeline under about 15 minutes.

Understanding checks: why and what if

Why does C++ compile each file separately instead of the whole program at once?Basic

So that a change recompiles only the affected translation units, compilation parallelises across cores and machines, and each unit's result can be cached by hashing its inputs. The price is that the compiler never sees the whole program, which costs optimisation (recovered by LTO), forces headers to be re-parsed in every unit, and leaves cross-file consistency (ODR) to the linker and to discipline.

Your binary works on the development board but fails on the ECU with "version `GLIBC_2.34' not found". What happened?Intermediate

It was linked against a newer glibc than the ECU has, probably the build machine's or a newer board image's, and picked up a symbol version that the target's glibc lacks. Fix the build to use a sysroot generated from the ECU's image (or an older baseline), check with readelf -V which versions are required, and make the CI build use only that sysroot.

What if two shared libraries in one process export the same function name with different implementations?Advanced

With default ELF symbol interposition, the loader binds every reference, including the ones inside the second library, to the first definition found in load order. One library silently runs the other's code, which may assume different data layouts; the crash appears far away. Prevent it with hidden visibility, namespaces, version scripts or -Bsymbolic, and avoid embedding private copies of the same third-party library in several shared objects.

Why can a program crash when you change only a header of a shared library and rebuild the library?Intermediate

Executables compiled against the old header have the old struct layout, inline functions and vtable offsets baked into their machine code. If the change altered any of those, the old executables now read wrong offsets from objects created by the new library. That is an ABI break; it needs a soname bump or recompiling all consumers.

What if you build the release with -O3 instead of -O2?Basic

It may be slightly faster, the same, or slower: -O3 inlines and unrolls more and vectorises more loops, which grows the code and can hurt instruction-cache behaviour. It can also expose latent undefined behaviour. Measure on the target with real data; note that CMake's Release type already means -O3.

Why is a build that "succeeded from the cache" not necessarily correct?Advanced

A cache returns a stored output when the hash of the declared inputs matches. If some real input is missing from the key, an environment variable, an undeclared header, a tool version, a generated file, the cache can return an output built from different inputs. Correct caching needs hermetic, fully declared inputs, and a shared cache must be write-protected against untrusted jobs.

What if a container runs as root? Is that root on the host?Intermediate

Without user namespaces, UID 0 inside is UID 0 on the host kernel, restricted only by dropped capabilities, seccomp and AppArmor or SELinux. Any escape (kernel bug, runtime bug, misconfiguration such as privileged mode or a mounted Docker socket) gives real root. With rootless containers or user-namespace remapping, root inside maps to an unprivileged host UID, so an escape is much less damaging.

Why can't you run an Arm container image on an x86 server, and how do people do it anyway?Basic

The container's processes run directly on the host CPU, and the binaries contain Arm instructions. Containers do not emulate hardware. With QEMU user-mode emulation registered through binfmt_misc, the kernel runs Arm binaries through QEMU transparently, which works for building and testing but is several times slower. Native Arm runners avoid the emulation.

Why do containers not provide freedom from interference for ISO 26262?Advanced

All containers share one kernel, so a fault or overload in the kernel affects all of them; cgroups limit CPU time and memory size but not shared caches, memory bandwidth or GPU scheduling, so timing interference remains; devices and the GPU driver are shared. Spatial and temporal separation for mixed ASIL needs separate kernels with hardware partitioning (hypervisor) or a safety-certified partitioning OS.

What if you rebuild version 2.3.1 for a release instead of promoting the tested artifact?Intermediate

You ship a binary that was never tested. Even with the same source, a different cache state, toolchain image, dependency resolution or timestamp can change the output; without reproducible builds you cannot even prove it is identical. Promotion moves the exact tested bits and keeps the trace from test evidence to the delivered artifact.

What does the xz backdoor teach about supply-chain security?Advanced

That trust in a dependency is trust in its maintainers and release process, and that the release tarball is not necessarily the repository. The malicious code was activated only by a build script that existed in the tarball. Defences: build from tagged repository source where possible, reproducible builds that let others verify outputs, pinning and mirroring dependencies, SBOMs to find affected products quickly, and minimising dependencies in privileged components.

Why does deleting a big file in a later Dockerfile step not shrink the image?Basic

Each step produces an immutable layer; the deletion is only a whiteout entry in the new layer that hides the file, while the earlier layer still contains it and is still downloaded. Download, use and delete in the same RUN step, or do the work in a separate build stage and copy only the result.

GGlossary

ABI (application binary interface)
The binary contract between compiled code: calling convention, type layout, name mangling, exception handling and the exported symbols of libraries.
Artifact registry
A server that stores and versions build outputs and inputs (packages, images, symbols) immutably, proxies external sources and supports promotion.
ccache / sccache
Compiler caches that store object files under a hash of the preprocessed input, compiler and flags, and return them on a repeat.
CDI (Container Device Interface)
A vendor-neutral JSON description of the device nodes, mounts and environment a container needs to use a device such as a GPU.
Capability (Linux)
One of about forty pieces into which root's privileges are split; containers keep only a small default set.
cgroup (control group)
A kernel mechanism that groups processes and accounts and limits their CPU, memory, I/O, PIDs and device access.
Digest
The SHA-256 hash of an image manifest (or any content), identifying it immutably; tags are movable pointers to digests.
Dynamic loader
The program named in an executable's INTERP segment (ld-linux-aarch64.so.1) that maps shared libraries, applies relocations and runs initialisers before main.
ELF
Executable and Linkable Format: the file format of object files, shared libraries, executables and core dumps on Linux, QNX and most Unix systems.
GOT (global offset table)
A table of addresses in a module's data segment, filled by the loader, through which position-independent code reaches other modules' symbols.
Hermetic build
A build whose actions can see only their declared inputs, including the toolchain, so results do not depend on the machine.
Image (container)
A stack of read-only, content-addressed file-system layers plus a configuration, from which containers are started.
Linker script
A description of how input sections map to output sections and memory addresses; essential for bare-metal targets.
Lockfile
A file that freezes the result of dependency resolution (every package, version and revision) so later builds resolve identically.
LTO (link-time optimisation)
Keeping compiler IR in object files and optimising across all of them at link time.
Name mangling
Encoding a C++ name with its namespace and parameter types into a unique symbol, e.g. _Z9mean_lumaPKhm.
Namespace (Linux)
A kernel feature giving a group of processes its own instance of a global resource: mounts, PIDs, network, hostname, IPC, user IDs, cgroup view, time.
Object file
The compiled, not yet linked output for one translation unit: machine code, data, a symbol table and relocations.
OCI (Open Container Initiative)
The standards for container image format, runtime configuration and registry distribution, shared by Docker, Podman, containerd and Kubernetes.
ODR (one-definition rule)
Each function and variable has one definition per program, and inline entities have identical definitions everywhere; violations are often not diagnosed.
overlayfs
A Linux union file system that merges read-only lower directories with a writable upper one, using copy-up on write and whiteouts for deletion.
PGO (profile-guided optimisation)
Building with instrumentation, running representative workloads, and rebuilding with the measured profile to guide inlining and code layout.
PIC / PIE
Position-independent code / executable: machine code that runs at any load address, using PC-relative addressing and the GOT.
PLT (procedure linkage table)
Stubs through which calls to functions in other modules jump via GOT entries, optionally resolved lazily.
Provenance
A signed record of how an artifact was built: source revision, builder, inputs and parameters (e.g. in-toto/SLSA format).
Relocation
An entry telling the linker or loader to patch a location with the final address of a symbol.
Reproducible build
A build that produces bit-identical output from the same source, dependencies and toolchain, wherever and whenever it runs.
Sanitizer
Compiler instrumentation plus a run-time library that detects a class of bugs (memory errors, UB, races, uninitialised reads) at the moment they occur.
SBOM (software bill of materials)
A machine-readable inventory of all components in a piece of software with versions, licenses and hashes (SPDX, CycloneDX).
seccomp
A kernel filter that restricts which system calls a process may make; container runtimes install a default deny-list profile.
Section
A named part of an ELF file used by the linker: .text, .rodata, .data, .bss, symbol and relocation tables.
Segment
A program-header entry describing a range the loader maps into memory with one set of permissions (LOAD, INTERP, DYNAMIC, ...).
Semantic versioning
MAJOR.MINOR.PATCH, where only a major change may break users; for C++ it must cover both API and ABI compatibility.
Shared library
A separately linked ELF file (.so) mapped into processes at run time and shared in physical memory.
SLSA
"Supply-chain Levels for Software Artifacts": a framework grading build integrity by the existence, signing and unforgeability of provenance.
Soname
The ABI name stored in a shared library (libluma.so.1) and recorded in the NEEDED entries of its users.
Static library
An archive (.a) of object files from which the linker copies needed members into the executable.
Symbol
A named function or variable in an object file's symbol table, defined there or referenced as undefined.
Symbol versioning
Version tags attached to exported symbols (GLIBC_2.34) so a library can keep several implementations for old and new programs.
Sysroot
A directory on the build machine holding the target's headers and libraries in its file-system layout, used via --sysroot.
Toolchain
The matched set of compiler, assembler, linker, binary utilities, runtime libraries and headers that builds code for one target.
Toolchain file (CMake)
A CMake script naming the target system, compilers, sysroot and search rules, passed at the first configure.
Translation unit
A source file after preprocessing, with all included headers pasted in; the unit the compiler works on.
Target triplet
The name of a platform as architecture-vendor-OS-ABI, e.g. aarch64-linux-gnu, used to prefix cross tools.
vDSO
A small shared library the kernel maps into every process so that calls like clock_gettime avoid a real system call.
