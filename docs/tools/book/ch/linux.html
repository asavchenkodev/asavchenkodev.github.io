Linux and operating system fundamentals

What the kernel does between your code and the hardware: system calls, processes and the scheduler, virtual memory and DMA, files and IPC, interrupts and drivers, the network stack, how an embedded Linux system boots and is built, how PREEMPT_RT makes it predictable, and the tools that show you what is really happening.

1The big picture: what an operating system kernel does

A camera ECU runs a capture service, a perception process, a diagnostic stack, a logger and a dozen system daemons on a handful of cores, with one DRAM, one flash device and one Ethernet port. Every one of those programs believes it has the machine to itself: its own memory starting at address zero, its own files, its own CPU. The kernel is the program that makes this illusion true and safe. Almost every performance mystery and many field bugs in embedded Linux are explained by knowing which part of the kernel was involved and what it did.

1.1Why there is a kernel at all

Without an operating system, every program would have to drive the hardware itself: program the flash controller, the Ethernet MAC, the interrupt controller, and coordinate with every other program that wants the same devices. That works on a small microcontroller with one job and is exactly how bare-metal MCU firmware is written. It stops working as soon as several independent programs from different teams or suppliers share one processor, because one bug in any of them can corrupt the others or the hardware state.

The kernel solves three problems at once. It isolates programs from each other with the memory management unit, so a crash in one process stays in that process. It abstracts the hardware behind stable interfaces (files, sockets, video devices), so the same application runs on an eMMC or a UFS device, on a TI or a Qualcomm SoC. And it shares scarce resources fairly or by priority: CPU time, memory, bandwidth to devices. Everything in this chapter is one of these three jobs seen from a different angle.

1.2Privilege levels: user space, kernel, hypervisor, firmware

The isolation is enforced by the CPU itself. An Arm Cortex-A core has four exception levels. Applications run at EL0, where they cannot touch page tables, interrupt controllers or device registers. The kernel runs at EL1 and may do all of that. A hypervisor, if there is one, runs at EL2 and can host several kernels side by side; the secure monitor of Trusted Firmware-A runs at EL3 and switches between the normal world and a secure world (OP-TEE) that holds keys. x86 has the same idea with rings 0 and 3 plus a separate virtualisation mode.

The only ways from EL0 into EL1 are exceptions: a deliberate one (the system call instruction), a fault (touching an unmapped address, executing an illegal instruction) or an interrupt from a device. Each of them makes the CPU jump to an address the kernel registered in advance, so user code can never choose where the kernel starts running. That single hardware rule is what makes the whole protection scheme work.

Why it matters

"Kernel space" and "user space" are not just software layers; they are different CPU modes with different rights. A bug in a user-space camera service kills one process; the same bug in a kernel driver can corrupt any memory in the system and takes the whole ECU down. That is the most important argument when deciding whether a piece of code belongs in a driver or in a process.

1.3A map of the Linux kernel

Linux is one large program, close to 40 million lines of source of which a typical embedded build compiles a few million, that runs in one shared address space. Inside it, a handful of subsystems do almost all the work. Process management creates tasks and the scheduler decides which one runs on each core. Memory management owns the page tables, allocates physical pages and keeps file data cached in RAM. The virtual file system (VFS) gives one interface to every filesystem and, through the block layer, to every storage device. The networking stack implements sockets, TCP/IP, routing and packet filtering. Device drivers, most of them plugged into frameworks such as V4L2 for cameras, DRM for displays and netdev for network cards, talk to the hardware. Below them sits architecture code: exception vectors, the interrupt controller, timers, cache maintenance and the context switch.

1.4Monolithic Linux and microkernel QNX

Linux is a monolithic kernel: drivers, filesystems and the network stack all run in kernel space and call each other as ordinary functions. That is fast, because a read from a file is a chain of function calls rather than a chain of messages, and it is why Linux supports almost every device ever made. The price is that every driver has full privilege, so a bad pointer in a camera driver can overwrite the scheduler's data. Loadable kernel modules make the kernel extensible at run time but do not change that: a module runs with exactly the same rights as the rest of the kernel.

QNX Neutrino, the other operating system you meet on automotive application processors, is a microkernel. Its kernel only schedules threads, passes messages, manages memory protection, timers and interrupt dispatch. Drivers, filesystems and the network stack are ordinary processes ("resource managers") that receive messages. A crashing driver can be restarted without rebooting, and each component can be argued about separately in a safety case. Every read() becomes a synchronous message to another process, which costs a few microseconds more per call than a function call. The comparison comes back in several places below, because many design choices on Linux (drivers in the kernel, user-space drivers through UIO or VFIO, separate safety processes) are answers to the same trade-off.

2System calls: crossing the boundary

Every useful thing a program does beyond pure computation, opening a file, sending a packet, waiting for a camera frame, allocating memory, ends in a system call. It is the one door between user space and the kernel. Knowing what happens at that door explains why some calls cost 50 nanoseconds and others 50 milliseconds, and it is also where strace, seccomp filters and most security policies watch a program.

2.1What a system call is

A system call is a function call into the kernel that has to switch the CPU's privilege level on the way. Application code calls an ordinary C function such as read() in the C library. That wrapper puts the arguments into registers, puts the system call number into a fixed register (on arm64 the number of read is 63, in register x8) and executes a special instruction: svc #0 on Arm, syscall on x86-64. The instruction behaves like an exception that the program raised on purpose. Linux has around 450 system calls; their numbers are part of the kernel's stable interface and never change, which is why a binary built ten years ago still runs.

Your code calls read(fd, buf, 4096). In glibc or musl this is a few instructions: the three arguments go into x0, x1, x2, the number 63 into x8, then svc #0. Nothing has been checked yet; the library trusts nobody and the kernel will verify everything itself.

The svc instruction raises a synchronous exception. The CPU saves the return address in ELR_EL1 and the processor state in SPSR_EL1, switches to EL1 and to the kernel's stack pointer, and jumps to the vector table registered in VBAR_EL1, at the entry for "synchronous exception from a lower level". User code cannot pick this address, so it cannot jump into the middle of the kernel.

The entry code stores all user registers on the task's kernel stack (16 KB per thread on arm64 and x86-64) as a struct pt_regs, reads the reason for the exception, sees a system call, and calls the function at index 63 of sys_call_table: __arm64_sys_read, a thin wrapper that unpacks the registers and calls ksys_read().

ksys_read() looks up the file descriptor, checks that the buffer is a user address, and calls the read function of whatever the descriptor refers to: a file, a pipe, a socket, a V4L2 device. If no data is ready the thread goes to sleep inside the kernel and another task runs on this CPU (Chapter 3). When it is woken up it continues here, copies the data with copy_to_user() and returns.

The return value goes into x0: the number of bytes, or a negative error code such as -EAGAIN. Before leaving the kernel, the exit path checks whether a signal is pending or the scheduler wants to switch tasks (need_resched). Then it restores the user registers and executes eret, which drops back to EL0 at the instruction after svc. The library converts a negative value into -1 plus errno.

Two details are worth remembering. First, the kernel never trusts pointers from user space: copy_to_user() and copy_from_user() check that the address range belongs to user space and handle a fault in the middle of the copy, so a bad pointer gives EFAULT instead of a kernel crash. Second, the kernel runs "on behalf of" the calling thread: it uses that thread's kernel stack, is accounted as that thread's system time, and can sleep, which is impossible in an interrupt handler (Chapter 6).

2.2What a crossing costs, and the vDSO

The trap, saving and restoring registers and the extra checks on the way out cost roughly 50–150 ns on a modern core running natively. Security mitigations add to this: on CPUs affected by Meltdown, kernel page-table isolation (KPTI) switches page tables on every entry and exit, and Spectre mitigations flush or fence branch predictors. In a virtual machine the numbers are higher again. Measured on the 4-core x86 cloud VM used for the examples in this chapter:

$ ./syscost                        # 2 million calls each
getpid via syscall:         297.5 ns
clock_gettime via vDSO:      20.9 ns
clock_gettime via syscall:  315.6 ns

The middle line shows the trick that makes the most frequent call cheap. Reading the clock does not need privilege if the kernel publishes the clock data in a page that user space may read. The kernel maps a small shared library, the vDSO ("virtual dynamic shared object"), into every process, together with a read-only data page that it updates on every timer tick. clock_gettime() and gettimeofday() in the C library call the vDSO function, which reads the time base and the hardware counter (the Arm generic timer's CNTVCT_EL0, or the TSC on x86) without entering the kernel at all: about fifteen times cheaper here.

Numbers

A system call that does no work: 0.05–0.3 µs. A context switch: 1–5 µs. A minor page fault: 0.5–2 µs. A read from the page cache of a few KB: 1–5 µs. A read that goes to eMMC or UFS: 0.1–1 ms. The cost of a system call is rarely the crossing itself; it is the work behind it and whether the thread has to sleep.

Pitfall

Small I/O in a loop multiplies the crossing cost. Writing a log line with one write() per field, or reading a camera register file byte by byte through sysfs, can cost more CPU than the work itself. Batch the data in user space (a buffered stream, writev(), io_uring) and look at the call count with strace -c before optimising anything else.

2.3Errors, blocking and signals

Every system call returns either a result or a negative error number, and the convention is strict enough that the same handful of errors explains most surprises. EAGAIN means "would block": the descriptor is non-blocking and no data is ready. EINTR means the call was interrupted by a signal before it did anything, and should normally be retried. EFAULT means a bad pointer, EBADF a closed or wrong descriptor, ENOMEM no memory, EPERM and EACCES missing rights, EBUSY a device already in use, ETIMEDOUT what it says.

Blocking is the normal case for I/O. A thread that reads from a socket with no data is put on a wait queue that belongs to the socket and marked as sleeping; the scheduler runs something else. When data arrives, the network code wakes everything on that wait queue. The same mechanism serves pipes, V4L2 buffers, futexes and timers, which is why one thread can sleep on many of them at once with poll() or epoll: the kernel adds the thread to every wait queue and removes it from all of them when one fires.

Signals are the kernel's way to interrupt a thread asynchronously: SIGSEGV for a bad memory access, SIGTERM from systemd at shutdown, SIGCHLD when a child exits, SIGKILL which cannot be caught. A signal is delivered on the way back to user space; a thread sleeping interruptibly is woken, its system call returns EINTR (or is restarted automatically if the handler was installed with SA_RESTART). Signal handlers run in the middle of arbitrary code, so they may only call async-signal-safe functions; the robust pattern is to turn signals into events with signalfd or a self-pipe and handle them in the event loop.

3Processes, threads and the scheduler

The application view of threads and processes is covered in the concurrency chapter. Here we look at what they are inside the kernel: one data structure, a set of shared or copied resources, a state machine and a scheduler that picks, on every core and many times per second, which task runs next. That picture explains load averages, zombie processes, why one real-time thread can freeze a core, and how nice values translate into CPU time.

3.1One kernel object: the task

Linux does not have separate objects for processes and threads. Everything that can be scheduled is a task, described by a struct task_struct: its state, priority and scheduling policy, its accounting, its kernel stack and saved registers, and pointers to the resources it uses. The resources are separate objects with reference counts: the memory map (mm_struct: page tables and the list of mapped regions), the file descriptor table, the signal handlers, the current directory, and the namespaces it sees.

All tasks are created by the same system call, clone(), and its flags decide what is shared. pthread_create() passes CLONE_VM | CLONE_FILES | CLONE_SIGHAND | CLONE_THREAD and more: share the memory, the descriptors and the handlers, and join the creator's thread group. fork() passes almost none, so the child gets copies. What user space calls a process ID is the thread group ID (tgid); every thread also has its own task ID, which gettid() returns and which tools such as top -H, ps -L and the scheduler traces show. This is why you can set a different scheduling policy, CPU affinity or nice value per thread: the scheduler only sees tasks.

3.2fork, exec, exit and wait

New programs start in two steps that look strange at first. fork() duplicates the calling process, and execve() replaces the program inside a process with a new one. Splitting them lets the child adjust its environment between the two (redirect descriptors, drop privileges, change its cgroup) with ordinary system calls before the new program starts.

Copying a whole address space would be slow, so fork() copies only the page tables and marks every writable page read-only in both parent and child. As long as both only read, they share the physical pages. The first write by either side causes a page fault, and the kernel then copies just that one page: copy-on-write. execve() throws away the copied memory map, maps the segments of the new ELF file, sets up a fresh stack with the arguments and environment, and, for dynamically linked programs, starts the dynamic loader named in the file. The process keeps its PID, its credentials and its open descriptors, except those opened with O_CLOEXEC. That last detail leaks descriptors into child programs surprisingly often; open everything with O_CLOEXEC unless the child must inherit it. For starting another program from a large process, posix_spawn() or vfork() avoids even the page-table copy.

When a process exits, the kernel closes its descriptors and frees its memory immediately, but keeps the task structure with the exit status until the parent collects it with wait(). In that state the process is a zombie: it uses no memory and no CPU, only a PID. A parent that never calls wait() slowly fills the PID table; a parent that dies passes its children to init (PID 1, usually systemd), which reaps them. Service managers rely on exactly this: systemd learns that a service crashed because it is that service's parent and receives SIGCHLD.

3.3Task states

Every task is in one state at a time, and the one-letter codes in ps and top are worth knowing by heart. R is runnable: either running on a CPU or waiting on a runqueue for its turn. S is sleeping interruptibly: waiting for an event and wakeable by a signal, which is the normal state of an idle service. D is sleeping uninterruptibly: waiting for something that must complete, typically disk I/O or certain driver operations, and immune even to SIGKILL until it does. T is stopped by a signal or a debugger, Z is a zombie, and I marks idle kernel threads.

The Linux load average counts tasks in R and in D, averaged over 1, 5 and 15 minutes. A load of 8 on a 4-core machine with 80% idle CPU therefore does not mean "CPU overloaded"; it means tasks are waiting for I/O. vmstat 1 separates the two (columns r and b), and the pressure stall information in /proc/pressure/cpu, io and memory says directly what fraction of time tasks were delayed by each resource.

Pitfall

A process in state D that never leaves it points at a driver or a storage device that does not complete a request. cat /proc/<pid>/stack (as root) shows the kernel function it is stuck in, and echo w > /proc/sysrq-trigger dumps all blocked tasks to the kernel log. That is usually enough to know which driver to blame.

3.4How the scheduler picks the next task

Each CPU has its own runqueue, a structure with its own lock that holds the runnable tasks assigned to that CPU. Having one per CPU means that picking the next task never needs a global lock; tasks move between runqueues only when the load balancer decides to. Inside each runqueue, tasks are sorted into scheduling classes that are asked in a fixed order: the stop class (internal, for migrating tasks and CPU hot-plug), the deadline class (SCHED_DEADLINE), the real-time class (SCHED_FIFO and SCHED_RR), the fair class (normal tasks, SCHED_OTHER, plus SCHED_BATCH and SCHED_IDLE) and finally the idle task. Since Linux 6.12 there is also an extensible class (sched_ext) whose policy is loaded as a BPF program.

The real-time class is simple and fast: 99 priority levels, a list of tasks per level and a bitmap of non-empty levels, so finding the highest-priority runnable task is a single "find first set bit" instruction. A SCHED_FIFO task runs until it blocks, yields or is preempted by a higher priority; SCHED_RR adds a time slice (100 ms by default) among tasks of the same priority. The deadline class implements earliest-deadline-first with admission control: a task declares runtime, deadline and period, and the kernel refuses new tasks that would overload the CPU. Because a runaway real-time task would freeze its CPU forever, Linux by default lets real-time tasks use only 950 ms of every second (/proc/sys/kernel/sched_rt_runtime_us); the rest goes to normal tasks.

The load balancer runs periodically and whenever a CPU becomes idle. It looks at the hierarchy of scheduling domains (hardware threads of one core, cores sharing a cluster cache, clusters, sockets) and pulls tasks from busier runqueues, preferring nearby CPUs whose caches are warm. On big.LITTLE SoCs energy-aware scheduling adds an energy model and places tasks on the core that does the work for the least energy. For real-time work this flexibility is exactly what you want to switch off, with affinity and CPU isolation (Concurrency 7.2).

3.5The fair class: weights and EEVDF

Normal tasks share the CPU in proportion to a weight derived from their nice value (−20 to 19). Nice 0 has weight 1024 and each step changes the weight by a factor of about 1.25, which works out to roughly 10% more or less CPU time per step relative to a competing task. The scheduler tracks for each task a virtual runtime that grows with the real time it ran divided by its weight: a heavy task's clock runs slowly, a light task's runs fast. Picking the task that is furthest behind in virtual time gives each one its fair share.

From 2007 to 2023 this was the Completely Fair Scheduler (CFS), which always ran the task with the smallest virtual runtime from a red-black tree. Linux 6.6 replaced its pick rule with EEVDF, "earliest eligible virtual deadline first": a task is eligible if it has received less than its fair share so far, and each task gets a virtual deadline equal to its eligible time plus its requested slice divided by its weight. Among eligible tasks the one with the earliest virtual deadline runs. The shares are the same as with CFS, but latency-sensitive tasks that ask for short slices get the CPU sooner, without the heuristics CFS needed. The base slice is 0.75 ms scaled with the logarithm of the core count, which gives 3 ms on a system with eight or more cores.

Two practical consequences follow. Nice values only matter when threads compete for the same CPU; on an idle system a nice 19 task runs at full speed. And nice never gives a guarantee about latency: a nice −20 task can still wait behind other fair tasks for a slice or two. Anything with a deadline belongs in the real-time or deadline class, or should be protected with CPU isolation and cgroup limits on everything else.

3.6Preemption and the context switch

The scheduler rarely takes the CPU away from a task at an arbitrary instruction. Instead, events set a flag on the running task, need_resched, and the switch happens at the next safe point. The events are the periodic timer tick (100 to 1000 times per second depending on CONFIG_HZ, or not at all on idle or isolated CPUs with tickless operation) when the current task has used its slice, and a wake-up of a task that should run before the current one. The safe points are the return from an interrupt or system call to user space, and, in a preemptible kernel, the moment kernel code leaves a section where preemption was disabled. How many such sections there are and how long they last is the whole difference between the preemption models in Chapter 9.

The context switch itself has two halves. switch_mm() installs the next task's page tables if it belongs to another process; on arm64 that is a write to TTBR0_EL1 with an address-space ID, so the TLB entries of the old process do not have to be flushed. switch_to() saves the callee-saved registers and stack pointer of the old task and loads those of the new one, including floating-point and NEON state when needed. From that moment the CPU continues wherever the new task was stopped, usually inside schedule() in its own earlier call. The direct cost is 1–5 µs; the indirect cost of cold caches and TLBs can be larger.

Interesting detail

Every task that is not running is, from the CPU's point of view, sitting inside the function schedule(). A switch is therefore a function that is called by one task and returns in another. Kernel stack traces of sleeping tasks always end in schedule() or one of its wrappers, which is what you see in /proc/<pid>/stack.

3.7cgroups and namespaces

Two more kernel mechanisms act on groups of tasks rather than single ones. Control groups (cgroup v2 is current) put tasks into a hierarchy and attach resource controllers to each node: cpu for weights and hard quotas ("this group gets at most 2 CPUs' worth of time"), cpuset for the CPUs and memory nodes a group may use, memory for limits and reclaim, io for storage bandwidth and pids for the number of tasks. systemd places every service in its own cgroup, so CPUQuota=, MemoryMax= and AllowedCPUs= in a unit file are cgroup settings. On an ECU this is how you keep a logging or update service from stealing CPU or memory from the perception pipeline.

Namespaces give a group of tasks its own view of a global resource: its own mount table, PID numbering, network interfaces and routing tables, hostname, IPC objects, user IDs. A container is nothing more than a process tree with its own namespaces, cgroup limits, a different root filesystem and usually a seccomp filter. The kernel has no "container" object at all.

4Virtual memory

Every pointer in a Linux program is a virtual address. The hardware translates it on every access, and the kernel decides, lazily and page by page, which physical memory stands behind it. That indirection is what isolates processes, lets files and devices appear as memory, shares libraries between hundreds of processes and makes zero-copy camera pipelines possible. It is also behind first-frame latency spikes, out-of-memory kills and DMA buffers that suddenly contain stale data.

4.1Why virtual memory

The MMU gives each process the illusion of a large private memory, and the kernel uses that freedom for four things. Isolation: a process can only reach physical pages that its own page tables map, so it cannot read or corrupt anybody else. Flexibility: physical memory can be scattered, moved, shared or not yet allocated while the process sees one tidy contiguous range. Sharing: the code of libc.so exists once in RAM and is mapped into every process; two processes can map the same pages on purpose to exchange data without copying. Files and devices as memory: mapping a file makes its contents appear in the address space, and the kernel loads pages on first touch.

The hardware side of this (page sizes, the TLB, why accelerators need either contiguous memory or an IOMMU) is explained in the embedded compute chapter. Here we follow what the kernel does with it.

MMU, TLB, CMA and buffer sharing as hardware concepts: Embedded compute 4.7.

4.2Page tables and the TLB

Memory is managed in pages, usually 4 KB. The translation from a virtual page to a physical page frame is stored in a tree of page tables in ordinary RAM. On arm64 with 4 KB pages and 48-bit virtual addresses the tree has four levels: bits 47–39 of the address index the level-0 table, bits 38–30 the level-1 table, 29–21 level 2, 20–12 level 3, and the last 12 bits are the offset inside the page. Each table is itself one 4 KB page with 512 eight-byte entries, and each entry holds the physical address of the next table (or of the final page) plus permission bits: readable, writable, executable, user-accessible, cacheable. x86-64 uses the same four-level scheme with different names.

Walking four tables for every load and store would make every memory access five memory accesses. The TLB (translation lookaside buffer) caches recent translations; a hit costs nothing, a miss costs a hardware page walk of up to four dependent reads, most of which hit in the data cache. A core has some tens of L1 TLB entries and one to two thousand L2 entries, so with 4 KB pages it covers only a few megabytes. A pipeline that streams through 100 MB of frame buffers misses the TLB constantly. Huge pages help: a level-2 entry can map a 2 MB block directly (a level-1 entry even 1 GB), which covers 512 times more memory per TLB entry. Linux offers them explicitly (hugetlbfs, MAP_HUGETLB) and transparently: with transparent huge pages enabled, the kernel backs large anonymous regions with 2 MB pages when it can.

Each process has its own top-level table, installed in TTBR0_EL1 on a context switch. The kernel's half of the address space uses a second register, TTBR1_EL1, which never changes, so the kernel is mapped in every process at the same addresses but protected from EL0 by the permission bits.

4.3The address space of a process

The kernel does not describe a process's memory as pages but as a list of virtual memory areas (VMAs): contiguous ranges with the same permissions and the same backing, such as "these 1.5 MB are the code of libc, read-only and executable, backed by this file at that offset". Page tables are filled in lazily from the VMAs. You can read the VMA list of any process in /proc/<pid>/maps; this is the real one of cat printing its own:

$ cat /proc/self/maps

Interesting detail

Two numbers per process confuse many reviews. VSZ (virtual size) is the sum of all VMAs, including 8 MB per thread stack and every reserved but untouched region; it is often gigabytes and means little. RSS is the resident memory, but it counts shared library pages in every process that maps them. PSS ("proportional set size", in smaps_rollup) divides shared pages among their users and is the number that adds up across processes.

4.4Page faults and demand paging

Allocating memory in Linux mostly means creating a VMA. The physical page arrives only when the program touches the address the first time. That access finds no valid page-table entry, the MMU raises a page fault, and the kernel's fault handler decides what the address should contain and maps it. The program never notices, except in time.

malloc(64 MB) calls mmap(NULL, 64 MB, PROT_READ | PROT_WRITE, MAP_PRIVATE | MAP_ANONYMOUS, -1, 0). The kernel only adds a VMA to the process's memory map and returns an address. No physical page is allocated, no page-table entry is written, and the resident memory of the process does not change.

The first store to p[0] misses the TLB, the MMU walks the page table and finds the level-3 entry invalid (or even a missing level-2 table). It raises a data abort, a translation fault, and the CPU enters the kernel's exception handler with the faulting address in FAR_EL1.

The handler looks up the VMA containing the address. It exists and allows writing, so the fault is legitimate. Because the VMA is anonymous, do_anonymous_page() takes a free page from the page allocator, fills it with zeros (the kernel must never leak another process's data) and charges it to the process's memory cgroup.

The kernel writes the page-table entry, valid and writable, and returns from the exception. The CPU re-executes the same store, which now succeeds. The next 4 KB page will fault again: touching all 64 MB costs 16,384 faults, as the measurement below shows. Each fault on a typical Cortex-A system costs about 0.5–2 µs.

If no VMA contains the address, or the access violates its permissions, the kernel sends SIGSEGV: the segmentation fault. If the VMA maps a file and the page is not in the page cache, it is a major fault: the kernel starts disk I/O and the thread sleeps until it completes, often hundreds of microseconds. A write to a copy-on-write page after fork() copies the page first. All of them are invisible to the program except as time.

                 0      major-faults
$ perf stat -e page-faults,major-faults ./touch x    # malloc(64 MB), memset all of it
             16447      page-faults
                 0      major-faults
Pitfall: the first frame is slow

Demand paging moves the cost of allocation to the first use. A perception process that allocates its tensors and frame buffers at start-up but touches them only when the first frame arrives pays tens of thousands of faults inside its first cycle, and a real-time loop that touches a new stack page does the same at an unpredictable moment. Real-time code therefore touches (or memsets) everything during initialisation, uses MAP_POPULATE, and calls mlockall(MCL_CURRENT | MCL_FUTURE) so that pages are neither faulted in later nor reclaimed (Concurrency 7.4).

4.5mmap and shared memory

mmap() is the general tool behind all of this. With a file descriptor it maps a file: with MAP_SHARED the mapping is a window onto the file's pages in the page cache, so stores change the file and other processes mapping it see them; with MAP_PRIVATE stores create private copies. Without a file (MAP_ANONYMOUS) it gives zero-filled memory. Device drivers implement mmap too: mapping a V4L2 buffer, a dma-buf or a GPU buffer object maps the device's memory into the process, which is how frames reach user space without a copy.

Shared memory between processes is a mapping of the same pages by both. The modern way is an anonymous file: memfd_create() returns a descriptor for a file that lives only in RAM, both sides mmap() it, and the descriptor is passed to the other process over a Unix domain socket. shm_open() does the same with a name in /dev/shm. The memory is shared, but its synchronisation is not: the two sides still need a protocol, typically a lock-free ring of indices in the shared region plus an eventfd or a process-shared futex to wake the other side.

/* Producer: create a pool for frames that a separate perception process will map. */
int fd = memfd_create("frame-pool", MFD_CLOEXEC | MFD_ALLOW_SEALING);
ftruncate(fd, POOL_SIZE);
fcntl(fd, F_ADD_SEALS, F_SEAL_SHRINK | F_SEAL_GROW);   /* the size can no longer change */
void *pool = mmap(NULL, POOL_SIZE, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);

/* Hand the descriptor to the consumer over a Unix socket (SCM_RIGHTS, Section 5.6).
   The consumer calls mmap() on its copy of the fd and sees the same physical pages. */
send_fd(unix_sock, fd);

Zero-copy middleware used in automotive and robotics, such as Eclipse iceoryx underneath ROS 2 and some AUTOSAR Adaptive implementations, is built exactly like this: a shared memory pool mapped by all processes, with only small offsets travelling through queues. For camera frames the pages usually come from the capture or GPU driver as a dma-buf instead of a memfd, so that hardware engines can use them as well.

4.6When memory runs out: reclaim, swap and the OOM killer

Linux uses all free RAM as a cache for file data (the page cache, Section 5.3), so "free" memory on a healthy system is usually low and that is fine; MemAvailable in /proc/meminfo estimates what could be freed. When memory gets tight, the kernel reclaims pages: clean file pages are simply dropped (they can be read again), dirty ones are written back first, and anonymous pages can only go to swap, which most ECUs do not have. A background thread (kswapd) starts reclaiming when free memory falls below a watermark; an allocation that finds nothing must reclaim directly, which stalls the allocating thread for milliseconds.

Because allocation is lazy, Linux by default allows processes to reserve more virtual memory than exists (overcommit, vm.overcommit_memory = 0). If they then really touch it and reclaim cannot free enough, the OOM killer picks a victim, mainly by resident size adjusted by each process's oom_score_adj (−1000 to 1000), and kills it with SIGKILL. On an embedded product this must never be left to chance. Typical measures: no swap, memory cgroup limits per service (MemoryMax=) so a leaking logger is killed before anything important, oom_score_adj = -1000 for the processes that must survive, and in safety-relevant partitions strict accounting (vm.overcommit_memory = 2) so allocation fails visibly at malloc() time instead of later.

4.7DMA from the kernel's point of view

Devices that write frames into memory do not use the CPU's page tables. A DMA engine emits device addresses, which are either physical addresses or, if an IOMMU sits in front of the device, I/O virtual addresses (IOVA) translated by the IOMMU's own page tables. The same frame buffer therefore has three names: the CPU's virtual address in the process, the physical pages in DRAM, and the device address the capture engine writes to. The kernel's DMA API keeps them consistent, and drivers must never hand a CPU virtual address to hardware.

Drivers use two kinds of DMA memory. Coherent allocations (dma_alloc_coherent()) are mapped so that CPU and device always see the same data, by making the memory uncached for the CPU or by a hardware-coherent interconnect; they suit descriptor rings and small control structures. Streaming mappings (dma_map_single(), dma_map_sg()) take existing pages, such as frame buffers, and prepare them for one transfer: build the IOMMU mapping, and on a non-coherent system clean the CPU caches before the device reads and invalidate them before the CPU reads what the device wrote (dma_sync_*_for_cpu()). Getting that ownership hand-over wrong produces the classic symptom of a stripe of old pixels in an otherwise correct frame.

Where the pages come from matters too. Without an IOMMU a large frame needs physically contiguous memory, which after some uptime is hard to find; the contiguous memory allocator (CMA) reserves a region at boot, defined in the device tree, that the page allocator may lend to movable pages until a driver needs it. To share such buffers between drivers and processes, Linux wraps them in a dma-buf: a file descriptor that any other driver can import and map into its own IOMMU, with fences that say when the writer is done.

5Files, file descriptors, permissions and IPC

"Everything is a file" is the oldest Unix idea and still the most useful one for understanding Linux. Regular files, directories, pipes, sockets, cameras, timers, even process memory are reached through the same small set of calls on a file descriptor. This chapter follows that descriptor into the kernel, takes a read() all the way down to the flash chip and back, and then looks at who is allowed to open what and how processes talk to each other.

5.1Everything is a file descriptor

A file descriptor is a small integer that indexes a per-process table. The table entry points to an open file description (struct file), a kernel object created by open() that holds the current offset, the open flags (read-only, non-blocking, append) and a pointer to the operations of whatever is behind it. That in turn points to an inode, the kernel's object for the file itself: owner, permissions, size, where its data lives, and its cache of pages in RAM.

The three levels explain several behaviours that otherwise look random. Two processes writing to a log file they inherited from the same parent share an offset and do not overwrite each other; two processes that opened the file separately do, unless they use O_APPEND. dup2() makes two descriptors point to the same open file, which is how a shell redirects output. Closing a descriptor drops a reference; the open file is destroyed only when the last descriptor referring to it, in any process, is closed. And because descriptors are references to kernel objects, they can be sent to another process (Section 5.6), which then holds a reference to the same socket, dma-buf or memfd.

Numbers

Default limit of open descriptors per process: 1024 (soft, ulimit -n); systemd services usually get far more. Descriptors 0, 1, 2 are stdin, stdout, stderr. A new descriptor always gets the lowest free number, which is why closing 1 and opening a file makes that file the new stdout.

5.2The VFS and the filesystems you will meet

The virtual file system is the layer that turns a path and a system call into a call on a specific filesystem. It resolves paths component by component through a cache of directory entries (the dentry cache), checks permissions on every directory, crosses mount points, and then calls the filesystem's own functions through tables of operations. Every filesystem implements the same interface, so cat works on ext4, on a network share and on /proc.

On an embedded Linux system you meet three kinds. Disk filesystems store data on a block device: ext4 (journaling, the default), f2fs (designed for flash), XFS on larger systems, and for raw NAND without a controller, UBIFS on top of UBI. Read-only images are popular for the root filesystem because they cannot be corrupted at run time and can be verified block by block: squashfs and erofs, compressed, often combined with an overlay for writable parts or with a separate data partition. Pseudo filesystems have no storage at all: tmpfs keeps files in RAM (/tmp, /run, /dev/shm), procfs exposes processes and kernel state, sysfs exposes the device model (/sys/class/video4linux, /sys/bus/i2c/devices), devtmpfs holds the device nodes in /dev, and tracefs, debugfs, cgroup2 and configfs provide control interfaces.

Device nodes deserve one more sentence. /dev/video0 is an inode whose type is "character device" with a major and minor number. Opening it does not read any data from disk; the VFS looks up the driver registered for that number and from then on every read, ioctl and mmap on the descriptor goes to that driver. That is the whole mechanism by which "a camera is a file".

5.3From read() to the disk

Follow one read() of 256 KB from a calibration file that is not yet in memory. The request passes through the VFS, the filesystem, the page cache, the block layer, a driver and the storage device, and the thread sleeps while the hardware works. The trace below the figure is a real kernel trace of exactly this read, taken with the kernel's tracepoints after dropping the caches (fields shortened for width).

read(fd, buf, 262144) enters vfs_read(), which calls the file's read_iter operation, for ext4 ext4_file_read_iter(), which hands over to the generic filemap_read(). File data in Linux is always read through the page cache: each inode has a tree (an xarray) of the pages of that file that are in RAM, indexed by offset. The kernel looks up the 64 pages for offsets 0 to 256 KB.

If the pages are there and up to date, the kernel copies them into the user buffer with copy_to_user() and returns. No filesystem code, no device, no sleep: a few microseconds for 256 KB. This is the common case for configuration, libraries and anything read twice, and it is why the second start of a program is much faster than the first.

The pages are missing, so the readahead code allocates new pages, inserts them into the page cache locked and "not up to date" (the trace shows 64 mm_filemap_add_to_page_cache events) and asks ext4 to fill them. ext4 translates file offsets to disk block numbers through the inode's extent tree (reading metadata from disk first if it is not cached) and builds a bio, a request that says "read these sectors into these pages". Readahead also grows its window when it sees sequential reads, so later reads find their data already cached.

The block layer (blk-mq, with one queue per CPU and per hardware queue) merges adjacent bios into a request, optionally orders them with an I/O scheduler (mq-deadline or BFQ for slow devices, none for NVMe), and passes it to the driver, which writes a command descriptor and rings the device's doorbell register. The trace shows one request of 512 sectors (256 KB). The reading thread now waits for the first page to be unlocked; it goes to sleep in state D and the scheduler switches to another task.

The device's controller reads the flash (its flash translation layer maps logical blocks to physical NAND pages) and DMAs the data straight into the page-cache pages. Then it raises an interrupt. The handler acknowledges it and the completion runs in a softirq: the request is finished, every page is marked up to date and unlocked, and the waiting thread is woken.

The reader is scheduled again on its CPU, copies the 256 KB from the now-filled pages into buf and the system call returns 262144. The data stays in the page cache; the next reader of this file gets step 2. In the trace the whole miss took 0.71 ms, of which 0.27 ms was the device.

5.4Writes, the page cache and durability

Writes go through the page cache as well. write() copies the data into cache pages, marks them dirty and returns; the data reaches the device later, when the kernel's writeback threads flush pages that have been dirty for longer than 30 seconds (dirty_expire_centisecs), checking every 5 seconds, or earlier when dirty memory exceeds a threshold (10% of available memory starts background writeback, 20% makes writers wait). ext4 additionally commits its journal every 5 seconds. A returned write() therefore means "the kernel has the data", not "the data is on flash".

For data that must survive a power cut, and in a car the power can disappear at any moment during cranking or a crash, the application has to ask explicitly. fsync(fd) writes the file's dirty pages and metadata and waits until the device confirms, including a cache flush on the device. The robust pattern for replacing a file such as a calibration or a configuration is: write a temporary file, fsync it, rename() it over the old one (rename is atomic), then fsync the directory. A reader then sees either the complete old or the complete new file, never a half-written one. O_DIRECT bypasses the page cache entirely, which databases and some loggers use to control I/O themselves.

In practice

Flash wears out with writes, and eMMC and UFS devices report their remaining life (mmc extcsd read, UFS health descriptors). Keep high-rate logs in RAM (tmpfs or a ring buffer) and persist only what is needed, mount filesystems with noatime so reads do not cause writes, and budget the total bytes written over the vehicle lifetime against the device's endurance rating.

5.5Permissions, capabilities and mandatory access control

Every process runs with user and group IDs, and every inode has an owner, a group and nine permission bits: read, write and execute for owner, group and others. The VFS checks them on every open and on every directory along a path (execute on a directory means "may pass through"). Three special bits matter: setuid on an executable runs it with the file owner's user ID (that is how passwd can update a root-owned file), setgid does the same for the group, and the sticky bit on a directory such as /tmp lets only a file's owner delete it.

$ ls -ld /dev/null /dev/vda /tmp /usr/bin/passwd

Root (user ID 0) traditionally bypasses all checks, which is far too much power for a service that only needs one privileged operation. Linux therefore splits root's power into about 40 capabilities, each of which can be given to a process or attached to an executable on its own: CAP_SYS_NICE to use real-time priorities, CAP_IPC_LOCK to lock memory, CAP_NET_ADMIN to configure interfaces and routes, CAP_NET_RAW for raw sockets, CAP_SYS_RAWIO for direct hardware access. A camera service then runs as its own unprivileged user, in a group that may open /dev/video*, with only CAP_SYS_NICE, set in its systemd unit with User=, SupplementaryGroups= and AmbientCapabilities=.

On top of these discretionary rights, a Linux Security Module can enforce mandatory rules that even root cannot override: SELinux (labels on every process and file, used by Android and many automotive distributions), AppArmor (path-based profiles), SMACK (simple labels, used in AGL and Tizen) and Landlock (self-restriction by unprivileged programs). seccomp filters, finally, restrict which system calls a process may make at all, with a small BPF program checked on every call. Together they implement least privilege: a compromised infotainment browser should not be able to open the camera, send CAN frames or load kernel modules.

Interesting detail: IPC in QNX

QNX makes synchronous message passing the core of the whole system: MsgSend() blocks the client until the server has called MsgReceive() and MsgReply(), and the kernel copies the message directly between the two address spaces. Because the client is blocked while the server works on its behalf, the server can inherit the client's priority, which avoids priority inversion across processes, something Linux IPC does not do automatically.

6Interrupts, device drivers and kernel modules

Hardware does not wait for software. A camera finishes a frame, a network card receives a packet, a flash device completes a read, and each of them needs the CPU's attention within microseconds. Interrupts deliver that attention, drivers turn hardware registers into the generic interfaces of Chapter 5, and the way the two are split determines both how fast Linux reacts and how much a single device can disturb everything else. This chapter ends with the path of a camera frame from the frame-end interrupt to a buffer in your process.

6.1Why interrupts

The CPU could poll every device in a loop, and for a few very fast paths it does (NAPI networking under load, DPDK, some storage drivers). But polling burns a core even when nothing happens and reacts only as fast as the loop. An interrupt lets the device signal the CPU when something happened. On Arm SoCs a generic interrupt controller (GICv3 or later) collects hundreds of interrupt lines from the peripherals ("shared peripheral interrupts"), per-core interrupts such as the local timer, inter-processor interrupts that cores send each other, and message-signalled interrupts from PCIe devices, prioritises them and forwards each to a CPU. Which CPU is configurable per interrupt: /proc/irq/<n>/smp_affinity.

When an interrupt arrives the CPU finishes the current instruction, saves the minimal state, masks further interrupts on this core, and jumps to the IRQ vector. The kernel's generic interrupt code asks the GIC which interrupt it was, looks up the descriptor for that number and calls the handler that the driver registered with request_irq(). The handler runs on whatever task happened to be running, borrowing its time, which is why it must be short and may never sleep.

6.2Top half and bottom half

Linux splits interrupt work in two. The top half, the handler itself, runs with interrupts disabled on that CPU and does only what cannot wait: read and acknowledge the device's status register, take a completed buffer off the hardware, perhaps program the next one, and schedule the rest. The bottom half does the heavier processing later, with interrupts enabled, in one of several deferred contexts.

Softirqs are a fixed set of high-priority deferred handlers (network receive and transmit, block completion, timers, RCU, tasklets) that run right after the hardware interrupt returns, or in the per-CPU ksoftirqd thread when there is too much of it. They cannot sleep either. Workqueues run deferred work in kernel worker threads, so the work may sleep, take mutexes and call functions that wait. A threaded interrupt (request_threaded_irq()) gives a device its own kernel thread, with a scheduling priority, that runs the handler's second half. Under PREEMPT_RT almost all interrupt handlers are forced into such threads (Chapter 9), which is the main reason real-time Linux can prioritise a camera interrupt above a network flood.

Pitfall

A handler that does too much in the top half (a long loop over a FIFO, a udelay() waiting for hardware, a debug printk to a slow serial console) delays every other interrupt on that CPU and every task, including real-time ones. The kernel cannot preempt it. Move work out to a threaded handler or a workqueue, and never call anything that may sleep from interrupt context; the kernel will warn with "BUG: sleeping function called from invalid context".

6.3The driver model: buses, devices, drivers, probe

Linux describes all hardware as devices on buses: PCIe, USB, I²C, SPI, and the "platform" bus for blocks inside the SoC that cannot be discovered by probing. A driver registers with a bus and says which devices it supports: PCI vendor and device IDs, USB IDs, or for devices described in the device tree a compatible string such as "sony,imx219" (Chapter 8). Whenever a device and a driver match, the bus core calls the driver's probe function, which maps the registers, requests interrupts, clocks, regulators and GPIOs, initialises the hardware and registers it with a framework. Removing either side calls remove().

Most drivers do not create device files themselves. They plug into a subsystem framework that implements the user-space interface once for all devices of a class: V4L2 for cameras and video processing, DRM/KMS for GPUs and displays, ALSA for audio, netdev for network interfaces (including CAN), IIO for sensors, input for buttons and touch screens. The driver only fills in operations ("start streaming", "set this format", "transmit this packet"). That is why every camera driver supports the same ioctls, and why writing a new driver usually means implementing a framework's callbacks, not designing an interface.

Probing has dependencies. A camera sensor cannot probe before its I²C controller, clock and regulator exist. If a resource is not available yet, probe returns -EPROBE_DEFER and the core retries later. A device stuck in that state is the most common bring-up problem on a new board; /sys/kernel/debug/devices_deferred lists such devices with the reason, and dmesg shows probe errors.

Interesting detail

The devm_ functions (devm_ioremap_resource(), devm_request_irq(), devm_clk_get()) register each resource with the device, and the core releases them automatically, in reverse order, when probe fails or the device is removed. They removed a whole class of leaks and error-path bugs from drivers, which used to be the most frequent source of kernel bugs.

6.4A minimal kernel module

A kernel module is an object file linked into the running kernel at run time. It has full kernel privilege and uses kernel interfaces only: no C library, no floating point without special care, a small fixed stack (16 KB for the whole call chain), and every allocation can fail. The smallest useful example registers a character device. The misc framework assigns a minor number and udev creates /dev/hello; the module only provides open and read.

// SPDX-License-Identifier: GPL-2.0
#include <linux/module.h>
#include <linux/miscdevice.h>
#include <linux/fs.h>
#include <linux/atomic.h>

static char *greeting = "hello from the kernel";
module_param(greeting, charp, 0444);          /* shown in /sys/module/hello/parameters */
MODULE_PARM_DESC(greeting, "text returned by read()");

static atomic_t opens = ATOMIC_INIT(0);

static int hello_open(struct inode *inode, struct file *file)
{
	atomic_inc(&opens);
	return 0;
}

static ssize_t hello_read(struct file *file, char __user *buf,
			  size_t len, loff_t *ppos)
{
	char msg[128];
	int n = scnprintf(msg, sizeof(msg), "%s (open #%d)\n",
			  greeting, atomic_read(&opens));

	/* copy_to_user() with bounds checks; returns 0 once *ppos reaches n */
	return simple_read_from_buffer(buf, len, ppos, msg, n);
}

static const struct file_operations hello_fops = {
	.owner = THIS_MODULE,
	.open  = hello_open,
	.read  = hello_read,
};

static struct miscdevice hello_dev = {
	.minor = MISC_DYNAMIC_MINOR,
	.name  = "hello",                      /* udev creates /dev/hello */
	.fops  = &hello_fops,
	.mode  = 0444,
};

static int __init hello_init(void)
{
	int ret = misc_register(&hello_dev);

	if (!ret)
		pr_info("hello: registered /dev/%s\n", hello_dev.name);
	return ret;
}

static void __exit hello_exit(void)
{
	misc_deregister(&hello_dev);
	pr_info("hello: unloaded\n");
}

module_init(hello_init);
module_exit(hello_exit);
MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("Minimal character device");

The build uses the kernel's own build system (Kbuild) against the headers and configuration of the exact kernel it will be loaded into; a module built for another version or configuration is refused with an "invalid module format" error.

	$(MAKE) -C $(KDIR) M=$(CURDIR) modules
clean:
	$(MAKE) -C $(KDIR) M=$(CURDIR) clean

$ sudo insmod hello.ko greeting="camera ok"
$ sudo dmesg --notime | tail -1

$ cat /dev/hello
camera ok (open #1)

Notice what the kernel does for you in those few lines: the VFS routes open and read on /dev/hello to the two functions, simple_read_from_buffer() handles offsets and copies safely to user space, and the module parameter appears under /sys/module/hello/parameters/greeting. In a Yocto build, out-of-tree modules like this get a recipe that inherits the module class, so they are built against the same kernel as the image.

Pitfall

A module is not a sandbox. A null pointer in hello_read() causes a kernel oops, and depending on configuration a panic and reboot of the ECU. Production kernels also usually require modules to be signed (CONFIG_MODULE_SIG_FORCE) and load only from the read-only root filesystem, and out-of-tree or proprietary modules "taint" the kernel, which makes upstream developers ignore bug reports. Prefer upstream drivers, and keep custom logic in user space where you can.

6.5From a camera interrupt to a V4L2 buffer in user space

Now the whole path for one frame. A camera driver in V4L2 manages its buffers with the videobuf2 (vb2) framework, which keeps every buffer in one of a few places: queued to the driver and waiting, active (the DMA engine is writing into it), done (filled and waiting for the application), or owned by the application. The capture hardware and DMA were described in the camera chapters; here we follow the software.

The application opens /dev/video0, sets the format, and requests four buffers with VIDIOC_REQBUFS. vb2 allocates them through the DMA API (contiguous memory or IOMMU-mapped pages), the application maps each into its address space with mmap() or exports it as a dma-buf with VIDIOC_EXPBUF, queues all four with VIDIOC_QBUF and calls VIDIOC_STREAMON. The driver's start_streaming callback powers the sensor over I²C and gives the receiver the device address of buffer 0.

Frame 41 is exposed and streams over CSI-2. The receiver writes it line by line through the IOMMU into buffer 0 in DRAM. No CPU is involved and nothing is copied; the capture thread sleeps in poll(), waiting on the vb2 queue's wait queue.

At the end of the frame the receiver raises an interrupt. The handler reads and acknowledges the status, takes buffer 0 off the active slot, writes the device address of the next queued buffer (1) into the DMA registers so the next frame has somewhere to go, stamps buffer 0 with the time (ktime_get_ns(), CLOCK_MONOTONIC) and the frame sequence number, and calls vb2_buffer_done(). That moves the buffer to the done list and wakes everything sleeping on the queue.

The wake-up makes the capture thread runnable; when the scheduler runs it, poll() returns, and VIDIOC_DQBUF hands it index 0 together with the timestamp, the sequence number and flags. The pixels are already in the mapping the thread created in step 1. The time between interrupt and this moment is the scheduling latency of Chapter 9: some microseconds on an idle system, more under load, unless the thread has a real-time priority.

The application processes the frame, or passes the dma-buf descriptor to the ISP, GPU or NPU and waits for their fence, and then queues buffer 0 again with VIDIOC_QBUF. If it keeps buffers too long, the driver reaches a frame start with no queued buffer; that frame is dropped, and the next buffer's sequence number jumps by more than one.

The interrupt handler of such a driver is short. Simplified, with the hardware-specific parts reduced to two register accesses:

static irqreturn_t csi_rx_irq(int irq, void *priv)
{
	struct csi_rx *rx = priv;
	u32 status = readl(rx->regs + RX_IRQ_STATUS);
	struct rx_buf *done, *next;
	u32 seq;

	writel(status, rx->regs + RX_IRQ_STATUS);          /* acknowledge */
	if (!(status & RX_FRAME_END))
		return IRQ_HANDLED;

	spin_lock(&rx->lock);
	seq = rx->sequence++;                              /* counts every frame, even dropped ones */
	done = rx->active;
	next = list_first_entry_or_null(&rx->queued, struct rx_buf, list);
	if (next) {
		list_del(&next->list);
		writel(lower_32_bits(next->dma), rx->regs + RX_DMA_ADDR);  /* next frame goes here */
	}
	rx->active = next;                                 /* NULL: the next frame will be dropped */
	spin_unlock(&rx->lock);

	if (done) {
		done->vb.vb2_buf.timestamp = ktime_get_ns();
		done->vb.sequence = seq;
		vb2_buffer_done(&done->vb.vb2_buf, VB2_BUF_STATE_DONE);   /* wakes poll() / DQBUF */
	}
	return IRQ_HANDLED;
}

And the user-space side, the loop of a capture thread:

struct v4l2_buffer b = { .type = V4L2_BUF_TYPE_VIDEO_CAPTURE, .memory = V4L2_MEMORY_MMAP };
for (;;) {
	struct pollfd p = { .fd = vfd, .events = POLLIN };
	if (poll(&p, 1, 200) == 0) { report_timeout(); continue; }   /* no frame for 200 ms */

In practice

Real camera pipelines are a graph of sub-devices (sensor, serializer, deserializer, CSI-2 receiver, ISP), configured with the media controller API (media-ctl -p prints the graph), and multi-planar formats use V4L2_BUF_TYPE_VIDEO_CAPTURE_MPLANE. 6.6Drivers in Linux and in QNX

In QNX the same camera driver is a user-space process. The kernel delivers the interrupt as an event (a pulse) to a thread of the driver process, which runs at its own priority; the driver maps device registers into its address space and exports a path such as /dev/qcarcam as a resource manager. A crash restarts one process instead of the system, and the driver's priority is an ordinary thread priority. Linux can do user-space drivers too (UIO and VFIO map registers and forward interrupts to a process), and it is the right choice for simple custom FPGA blocks, but the mainstream drivers and frameworks live in the kernel.

Talk track

"A frame is written by DMA straight into a buffer we allocated at start-up. The frame-end interrupt only stamps the buffer, hands the hardware the next one and wakes our capture thread. The thread gets an index, not a copy. If we hold buffers too long, the driver has nothing to write into and drops the frame, and we see that as a gap in the sequence number, which we monitor."

7The networking stack

Cars are becoming Ethernet networks: cameras, radar, zone controllers and the central computer exchange SOME/IP services, diagnostics run over DoIP, time is synchronised with gPTP, and CAN is still everywhere. On a Linux ECU all of that goes through one kernel stack that was built for servers. Knowing where a packet waits, gets copied or gets dropped is what makes network latency predictable and network bugs debuggable.

7.1Why a layered stack, and sockets

The stack mirrors the protocol layers. A socket is the application's endpoint: a file descriptor with a send buffer and a receive queue. Below it, the transport protocol (TCP for reliable byte streams, UDP for datagrams) handles ports, ordering, acknowledgements and retransmission. IP handles addresses and routing: which interface and which next hop. The neighbour layer turns the next hop's IP address into a MAC address (ARP for IPv4, NDP for IPv6). A queueing discipline decides the order in which packets leave each interface. The driver moves packets to and from the network card through rings of DMA descriptors.

Inside the kernel every packet is a socket buffer (struct sk_buff): a descriptor pointing to the packet data, with room reserved in front so that each layer can prepend its header without copying, plus metadata such as the interface, timestamps, checksum state and the owning socket. Most of the stack's speed comes from passing these descriptors instead of data.

7.2From send() to the wire and back

The transmit and receive paths are not symmetric. Transmit runs mostly in the context of the sending thread, all the way to the driver. Receive starts with an interrupt, runs in softirq context on whatever CPU got the interrupt, and only at the end wakes the receiving thread.

send() copies the user data into socket buffers and accounts them to the socket's send buffer. For TCP the data stays there until it is acknowledged, because it may have to be retransmitted; TCP cuts it into segments no larger than the path's maximum segment size and sends as much as the congestion window and the receiver's advertised window allow. If the send buffer is full, a blocking socket sleeps and a non-blocking one returns EAGAIN. For UDP each send() becomes one datagram that goes down immediately.

The IP layer looks up the route for the destination (the forwarding information base, a longest-prefix-match tree), which yields the output interface and the gateway. Netfilter hooks run the firewall rules (nftables or iptables) for OUTPUT and POSTROUTING. The packet is fragmented if it is larger than the interface MTU and fragmentation is allowed. The neighbour table provides the next hop's MAC address; if it is unknown, the packet waits while an ARP request goes out.

The packet is enqueued to the interface's queueing discipline (qdisc): a simple FIFO, a fair queue such as fq_codel, or for time-sensitive networking mqprio and taprio, which map traffic classes to hardware queues and time slots. The qdisc dequeues to the driver's transmit function, which writes a descriptor into the TX ring and notifies the NIC. The NIC fetches the frame by DMA, computes checksums and, with segmentation offload, even cuts large TCP buffers into segments. A transmit-complete interrupt later lets the driver free the buffer. send() returned long before: it only queued.

On the receiving side the driver has pre-posted empty buffers in an RX ring. The NIC writes an arriving frame into the next one by DMA and raises an interrupt. The handler does almost nothing: it masks further receive interrupts from this queue and schedules NAPI polling. Under load, the interrupt stays masked and the softirq keeps polling, so a flood of packets does not become a flood of interrupts.

The NET_RX softirq calls the driver's poll function, which processes up to 64 frames per round: builds skbs, merges consecutive TCP segments of one flow (GRO), and passes them up. IP checks the destination; for a local address the INPUT firewall hooks run, then TCP or UDP looks up the socket by addresses and ports, queues the data on its receive queue, sends an acknowledgement for TCP, and wakes any thread waiting on the socket, directly or through epoll.

The woken thread's recv() copies data from the receive queue into the user buffer and frees the skbs. If the application does not read fast enough, the receive queue fills; TCP then advertises a smaller window and the sender slows down (flow control), while UDP simply drops datagrams that do not fit and counts them.

7.3TCP and UDP from the kernel's side

Several kernel behaviours explain most surprises with sockets. Buffers: each socket has a send and a receive buffer whose sizes TCP tunes automatically within net.ipv4.tcp_rmem and tcp_wmem; a UDP socket's receive buffer is fixed (about 200 KB by default) and silently drops datagrams when full, visible as RcvbufErrors in nstat. A burst of camera metadata or a SOME/IP event storm can overflow it while the receiver is descheduled for a few milliseconds.

Nagle's algorithm holds back small TCP segments while earlier data is unacknowledged, and the receiver's delayed acknowledgements hold back ACKs for up to about 40 ms on Linux. Together they produce the classic 40 ms stall in request-response protocols that write a header and a body in two calls. TCP_NODELAY switches Nagle off; writing a message in one call (or with writev()) avoids the problem entirely.

Readiness: epoll works because every socket has a wait queue. Adding a socket to an epoll instance installs a small callback on that queue; when data arrives, the callback puts the socket on the epoll instance's ready list and wakes the thread in epoll_wait(), which then returns only the ready descriptors. That is why epoll scales to thousands of sockets: the cost is proportional to the events, not to the number of descriptors watched. In level-triggered mode a descriptor stays ready as long as data is there; in edge-triggered mode (EPOLLET) it is reported once per new arrival, and the handler must read until EAGAIN.

Spreading the load: a busy NIC has several receive queues and spreads flows over them by hashing addresses and ports (RSS), each queue with its own interrupt that can be steered to a CPU. Software equivalents (RPS, RFS) do the same for single-queue NICs. On an ECU you use the same knobs in the opposite direction: keep network softirq work away from the cores that run real-time threads.

7.4Interfaces, routing, VLANs and filtering

Everything about the network configuration lives in kernel tables that the ip tool reads and writes over netlink. ip addr lists interfaces and addresses, ip route the routing table, ip neigh the ARP cache, and ip route get asks the kernel which route it would choose for a destination:

Automotive Ethernet adds structure on top. VLANs (IEEE 802.1Q) separate traffic classes and domains on the same cable; on Linux each VLAN is a virtual interface (ip link add link eth0 name eth0.20 type vlan id 20) with its own addresses and routes, and the VLAN priority bits map to hardware queues. Bridges and switch drivers (switchdev, DSA for switch chips on the board) make Linux a switch. Policy routing (several routing tables chosen by rules) separates, for example, diagnostic traffic from service traffic. Netfilter with nftables provides the firewall that a gateway or a central computer needs between the vehicle network and connectivity domains.

7.5Network debugging

Network problems are found layer by layer, starting at the bottom: is the link up and are frames being dropped, is the route right, is the socket's queue filling, is the peer answering. The tools map to those questions. ip -s link and ethtool -S eth0 show per-interface and per-queue counters, including drops in the driver's rings. ss lists sockets with their queues and TCP state; nstat shows protocol counters such as retransmissions and buffer overflows. tcpdump (or Wireshark on a capture file) shows the packets themselves. Pitfall: MTU

A connection that works for small requests and hangs for large ones is almost always an MTU problem: a VLAN, a tunnel or a switch on the path with a smaller MTU than the endpoints assume, and ICMP "fragmentation needed" messages blocked by a firewall. 7.6Automotive networking on Linux

CAN appears in Linux as a network interface too. SocketCAN drivers register can0 like an Ethernet card; applications open a PF_CAN socket of type raw, ISO-TP (transport protocol for diagnostic messages longer than one frame) or J1939, and bind it to an interface. Configuration uses the same tools: ip link set can0 type can bitrate 500000 dbitrate 2000000 fd on, then candump can0 and cansend from can-utils to watch and inject frames. Because the qdisc and driver path is shared with Ethernet, a CAN interface with a full TX queue returns ENOBUFS just like a congested network card.

SOME/IP services run over UDP and TCP sockets, with service discovery on UDP port 30490 by convention; DoIP diagnostics use TCP and UDP port 13400. Both are ordinary user-space protocols on top of the stack. Time-sensitive networking needs kernel support: hardware timestamps from the NIC's PTP hardware clock (SO_TIMESTAMPING), gPTP (IEEE 802.1AS) with linuxptp's ptp4l and phc2sys to synchronise the system clock to the network, and the taprio and etf qdiscs for time-aware shaping and launch-time transmission.

8Embedded Linux: boot, device tree, Yocto and Buildroot

On a PC, firmware discovers the hardware, a distribution provides a ready kernel and thousands of packages, and nobody counts seconds at boot. On an ECU none of that holds. Somebody has to bring up DRAM, describe every chip on the board to the kernel, build a root filesystem with exactly the software the product needs and nothing else, reproduce that build bit for bit years later, and show a camera image within two seconds of power-on. This chapter covers the pieces that make that possible.

8.1The boot chain

An Arm SoC boots in stages, each one small enough to fit where the previous one can load it, and each one setting up a bit more of the machine. The boot ROM inside the SoC runs first; it is fixed in silicon, reads boot pins or fuses to choose a boot device, and loads the first stage into on-chip SRAM, verifying its signature if secure boot is fused on. That first stage, U-Boot's SPL or Trusted Firmware-A's BL2, initialises clocks and the DRAM controller (DRAM training alone can take tens of milliseconds) and loads the next stages into DRAM. TF-A's BL31 stays resident at EL3 as the secure monitor and provides PSCI, the standard interface the kernel uses to start and stop cores; OP-TEE may be loaded as the trusted OS in the secure world. Then the normal-world bootloader, usually U-Boot, loads the kernel, the device tree and an optional initramfs and jumps to the kernel.

The kernel decompresses itself if needed, sets up memory management, starts the other cores through PSCI, initialises subsystems and probes the drivers for the devices described in the device tree, mounts the root filesystem and starts /sbin/init, on most systems systemd. systemd then starts services in dependency order, in parallel where possible, until the target the product defines (for example "camera function ready") is reached.

Why the early camera does not wait for Linux, and the staged boot on a camera ECU: Embedded compute 6.8 and Camera ECU 8.5. The QNX boot chain and image: Camera ECU 8.2–8.3. Secure boot, key handling and A/B updates belong to the production integration and ECU lifecycle chapter.

8.2U-Boot

U-Boot is the Swiss army knife between firmware and kernel. In production it does one job quickly: read the kernel Image, the board's .dtb and perhaps an initramfs from eMMC or UFS into RAM, set the kernel command line and jump. During development it is also the tool you use when nothing else works: a shell on the serial console, commands to read and write memory and flash, load images over TFTP or USB (fastboot, DFU), inspect I²C devices, and an environment of variables and scripts that defines the boot sequence.

=> printenv bootargs
bootargs=console=ttyS2,115200n8 root=/dev/mmcblk0p2 rootwait ro quiet
=> load mmc 0:1 ${kernel_addr_r} Image
=> load mmc 0:1 ${fdt_addr_r} board.dtb
=> booti ${kernel_addr_r} - ${fdt_addr_r}         # arm64 kernel, no initramfs, this DTB

The kernel command line (bootargs) is the main way to configure the kernel at boot: the console, the root device and whether to wait for it, quiet to avoid slow serial output, and for real-time systems parameters such as isolcpus=, nohz_full=, irqaffinity= and threadirqs. U-Boot can also patch the device tree before boot (memory size, MAC addresses, serial numbers). For the fastest boots, U-Boot's "falcon mode" lets the SPL load the kernel directly and skip the full bootloader.

8.3The device tree

A PC discovers its hardware: PCIe and USB devices identify themselves, and ACPI tables describe the rest. Most blocks in an Arm SoC and on an ECU board cannot be discovered at all; an I²C camera sensor at address 0x10 does not announce itself, and nothing tells the kernel which GPIO resets it or which CSI-2 port it is wired to. Before 2011 this was hard-coded in C "board files" in the kernel, one per board. The device tree replaced them with data: a tree of nodes describing the hardware, compiled from source (.dts, with shared parts in .dtsi includes) into a binary blob (.dtb) that the bootloader passes to the kernel. The same kernel binary then runs on any board, given the right DTB.

Each node has a name with a unit address, and properties. The essential ones are compatible (which driver should handle this, most specific first), reg (register addresses, or the address on a bus such as I²C), interrupts, clocks, *-supply regulators, *-gpios, and status = "okay" or "disabled". The SoC vendor's .dtsi describes everything on the chip, mostly disabled; the board's .dts enables what is used and adds what is soldered around it. Here is a camera sensor on the board's I²C bus 3, linked to the SoC's CSI-2 receiver through an OF graph (port and endpoint nodes that point at each other):

Device tree bindings, the documented set of properties for each compatible, live in the kernel source as YAML schemas, and make dtbs_check validates a board's tree against them. Overlays (.dtbo) let a bootloader add or change nodes for optional hardware, for example a camera variant, without a separate full tree per variant. The tree also reserves memory: CMA pools for camera buffers, carve-outs for firmware of the DSP or the real-time cores, regions shared with another OS on the same SoC.

Pitfall

A wrong device tree fails silently more often than loudly. A typo in compatible means no driver ever probes and nothing is logged; a missing regulator leaves the device in deferred probe forever; a wrong interrupt number gives a driver that probes fine and then times out. When a device is missing, check /sys/firmware/devicetree/base (what the kernel actually received), /sys/kernel/debug/devices_deferred and the probe messages in dmesg, in that order.

8.4Kernel start, initramfs and systemd

If the root filesystem needs work before it can be mounted, such as unlocking encrypted storage, setting up dm-verity, choosing the A or B slot or loading a storage driver module, the kernel first unpacks an initramfs: a small archive in RAM with just enough tools to do that, after which it switches to the real root. Many embedded systems skip it to save time and build the storage drivers into the kernel instead.

systemd then turns "start the product" into a dependency graph of units: services, mount points, devices, timers and targets. Units start in parallel as soon as their dependencies are met, and socket activation lets clients connect before a service has finished starting. For an ECU the important properties are the explicit ordering (the camera service needs the camera device and the calibration partition), the cgroup and resource settings per service (Section 3.7), the sandboxing options (ProtectSystem=, PrivateNetwork=, CapabilityBoundingSet=, SystemCallFilter=), restart policies and the hardware watchdog integration (RuntimeWatchdogSec=, and WatchdogSec= per service). systemd-analyze critical-chain and systemd-analyze plot show which units delay the target.

8.5Building the image: Yocto and Buildroot

An embedded Linux image is built from source: toolchain, bootloader, kernel, every library and application, configured for one board, with a manifest of every component and licence. Two build systems dominate. Buildroot is a set of Makefiles and Kconfig menus: choose a defconfig, make menuconfig, make, and it produces a toolchain, a kernel, a bootloader and a root filesystem image. It is simple, fast to learn and produces small systems, but it has no package management and every configuration change rebuilds from scratch.

The Yocto Project (with BitBake as the build engine and OpenEmbedded-Core as the base layer) is what most automotive Linux products use, including Automotive Grade Linux and most SoC vendors' BSPs. Its unit is the recipe: a .bb file that says where a component's source comes from and how to configure, compile and install it. Recipes are grouped into layers, git repositories stacked on each other: OpenEmbedded-Core, meta-openembedded for extra packages, the SoC vendor's BSP layer with its kernel, U-Boot, firmware and device trees, and your own product layer. Your layer changes the others only through .bbappend files, which keeps vendor updates mergeable.

# meta-myproduct/recipes-camera/camera-service/camera-service_1.4.bb
SUMMARY = "Front camera capture service"
LICENSE = "CLOSED"
SRC_URI = "git://git.example.com/camera-service.git;protocol=https;branch=main"
SRCREV = "<pinned commit hash>"                   # reproducible: never build a moving branch
S = "${WORKDIR}/git"                             # newer releases unpack into ${UNPACKDIR}
DEPENDS = "libdrm v4l-utils"
inherit cmake systemd
SYSTEMD_SERVICE:${PN} = "camera-service.service"

# meta-myproduct/recipes-kernel/linux/linux-vendor_%.bbappend
FILESEXTRAPATHS:prepend := "${THISDIR}/files:"
SRC_URI += "file://camera.cfg file://0001-board-add-imx219-camera.patch"   # config fragment + DT patch

The shared-state cache (sstate) is what makes Yocto practical: every task's output is stored under a hash of all its inputs (source, recipe, configuration, dependencies), and a later build, on the same machine or on any machine sharing the cache, reuses the output instead of rebuilding. A full image takes hours from scratch and minutes with a warm cache. The same hashes make builds reproducible and auditable, which matters for automotive release processes.

8.6Boot time

Boot time is a budget like latency, and it is spent in every stage. The usual levers, roughly in order of effect: start the critical function early on a separate core or as an early systemd unit rather than after everything else; remove what is not needed (drivers built as modules that probe late, unused services, a full initramfs); avoid slow output (quiet, no serial console at 115200 baud during boot); read less from flash (compressed images trade CPU for I/O, a smaller root filesystem helps both); defer non-critical probes and services; and use U-Boot's falcon mode or a minimal bootloader configuration. Measure with timestamps in every stage: U-Boot's bootstage, the kernel's initcall_debug and printk timestamps, and systemd-analyze.

9Real-time Linux and PREEMPT_RT

Real-time means a guaranteed worst case, not a good average. A stock Linux kernel reacts to most events within tens of microseconds, but once in a while it takes milliseconds, because some code path cannot be interrupted. For a display that is a dropped frame; for a control loop it is a missed deadline. PREEMPT_RT, fully part of mainline Linux since version 6.12 in 2024, removes most of those paths. This chapter explains where the latency comes from, what PREEMPT_RT changes, and how to measure the result honestly.

9.1Why stock Linux misses deadlines

Consider a real-time thread that sleeps until a timer fires every millisecond. Its wake-up latency, the time from the timer's expiry to the first instruction of the thread, has two parts. Interrupt latency is the time until the timer interrupt handler runs; it is long if the CPU currently has interrupts disabled, or is busy in another handler. Scheduling latency is the time from the handler waking the thread to the thread running; it is long if the kernel currently runs in a section where preemption is disabled, such as code holding a spinlock, a softirq processing a burst of network packets, or an RCU callback batch.

Other sources add to it: the CPU waking from a deep idle state (tens to hundreds of microseconds), frequency changes, a cache and TLB full of another task's data, page faults in the real-time code, and on x86 system-management interrupts handled by firmware where the OS cannot see them. A hypervisor below the OS is another source: on a virtual machine the whole virtual CPU can be descheduled by the host for milliseconds, as the measurements in Section 9.4 show.

9.2Preemption models and what PREEMPT_RT changes

The kernel can be built with several preemption models. PREEMPT_NONE never preempts kernel code (best throughput, servers). PREEMPT_VOLUNTARY adds explicit preemption points in long code paths (typical desktop). PREEMPT ("low-latency desktop") makes all kernel code preemptible except sections holding spinlocks or with interrupts disabled. With PREEMPT_DYNAMIC, distribution kernels choose among these at boot with preempt=. PREEMPT_RT goes further and attacks exactly the sections the others leave non-preemptible.

It does so with three main changes. Sleeping spinlocks: on RT, spinlock_t and rwlock_t become rt_mutex-based locks that a waiter sleeps on, with priority inheritance, so code holding them can be preempted by a higher-priority thread. Only a small set of truly low-level locks (raw_spinlock_t in the scheduler, interrupt controller and timer code) still spin with preemption disabled. Threaded interrupts: almost all interrupt handlers run in kernel threads (irq/37-virtio1) with a real-time priority (50 by default) that you can change with chrt, so a camera interrupt thread can outrank a network one, and a real-time application thread can outrank both. Preemptible softirqs: softirq work runs in thread context and can be preempted as well. Many smaller changes, such as making printk safe without blocking, were the reason the merge took almost twenty years.

Why it matters

PREEMPT_RT does not make code faster, and the average latency and throughput usually get slightly worse, because sleeping locks and threaded handlers cost a little more. What it gives is a bound: on a tuned system the worst case drops from milliseconds to tens of microseconds. Choose it when the tail matters, not to speed things up.

Pitfall

An RT kernel does not fix an application that is not real-time. A thread with normal priority, a lock shared with a best-effort thread, a malloc() or a page fault in the loop, a log write to flash: each of them reintroduces unbounded latency in user space, where the kernel cannot help (Concurrency 7.4). Out-of-tree drivers that disable interrupts or preemption for long stretches break the guarantee for everybody.

9.3Tuning beyond the kernel configuration

A real-time Linux system is a kernel configuration plus a set of system settings, and most of the gain often comes from the settings. Isolate CPUs for the real-time threads (isolcpus= or cpuset partitions), stop the periodic tick there (nohz_full=) and move RCU callbacks away (rcu_nocbs=). Steer interrupts to the housekeeping cores (irqaffinity= on the command line, /proc/irq/*/smp_affinity at run time) except those that the real-time thread itself needs. Control power management: a fixed CPU frequency or the performance governor, and limited idle states, either globally or by holding /dev/cpu_dma_latency open with a value of 0 (cyclictest does that automatically). Prioritise the interrupt threads that feed the real-time path. On SMT-capable CPUs, keep hyper-threads of real-time cores idle.

The application side completes the picture: SCHED_FIFO priorities chosen by rate, mlockall() and pre-faulted memory, priority-inheritance mutexes for anything shared, no blocking calls in the loop, and absolute-time sleeps. Those are described in the concurrency chapter.

Scheduling policies, affinity, priority inversion and rules for the inside of a real-time loop: Concurrency 7.1–7.4.

9.4Measuring latency with cyclictest

cyclictest from the rt-tests suite is the standard measurement. It starts one real-time thread per CPU, each of which sleeps until an absolute time with clock_nanosleep(), reads the clock as soon as it wakes, and records the difference: the wake-up latency of Figure 9.1, including the timer interrupt and the scheduler. The minimum, average and maximum per thread are printed; with -h it writes a histogram. A run on its own says little. What counts is the maximum over hours, with the system under worst-case load at the same time: network floods, storage I/O, GPU and NPU work, memory pressure (stress-ng, hackbench, or the real application).

Numbers

Typical maxima under load on current Arm SoCs, from published measurements and vendor data: stock PREEMPT kernel several hundred µs to a few ms; PREEMPT_RT without tuning 100–200 µs; PREEMPT_RT with isolated cores, steered interrupts and fixed frequency 20–80 µs. Well-tuned x86 systems reach below 20 µs. Treat these as orders of magnitude; your board, firmware and drivers decide.

9.5Finding the cause of a spike

A maximum says that something was late, not why. The kernel can tell you. cyclictest -b 500 stops tracing as soon as a latency above 500 µs occurs, so the end of the ftrace buffer holds the events just before the spike. The ftrace latency tracers record the longest section with interrupts disabled (irqsoff), with preemption disabled (preemptoff) and the longest wake-up of the highest-priority task (wakeup_rt), each with the function trace of that section. The newer timerlat and osnoise tracers, driven by the rtla tool (rtla timerlat top -a 100), measure latency like cyclictest but from inside the kernel and, when a threshold is exceeded, print an automatic analysis that splits the latency into IRQ delay, interference from other interrupts and threads, and names the task or handler that was running.

The answer is usually one of a short list: a driver with a long interrupts-off section, a softirq burst from the network, a thread of the same or higher priority that was not supposed to run on that core, the CPU waking from deep idle, or a page fault in the application. Each has its fix in Section 9.3 or in the driver.

10Debugging and tracing tools

On an embedded system you rarely get to attach an IDE and step through the problem. Bugs appear under load, after hours, on a target with a serial console and an SSH login. The good news is that Linux exposes an enormous amount of information about itself; the skill is choosing the tool that answers the current question with the least disturbance. Every example output in this chapter was produced on the example VM.

10.1Choosing the tool

Start with the question, then pick the layer. "Where does my program crash or hang?" is a debugger question. "What does it ask the kernel for?" is a system call trace. "Where does the CPU time go?" is a profiler. "Why was my thread late?" is a scheduler trace. "Who is leaking memory or writing out of bounds?" is a memory checker. And always start broad and cheap: top or htop per thread, vmstat 1, /proc/pressure/*, perf stat, before reaching for tracing.

10.2gdb

gdb shows the state of a program at one moment: the call stack of every thread, variables, registers, memory. Built with -g, a crash shows the exact line and the values that caused it:

$ gdb -q -batch -ex run -ex bt -ex 'print *f' ./crash

0x00005555555551ad in luma_sum (f=0x7fffffffb9d0) at crash.c:9
9	            s += f->data[y * f->width + x];
#0  0x00005555555551ad in luma_sum (f=0x7fffffffb9d0) at crash.c:9
#1  0x0000555555555219 in main () at crash.c:14
$1 = {width = 1920, height = 1080, data = 0x0}

On a target you usually do not run gdb itself. gdbserver on the target attaches to the process (gdbserver :2345 --attach <pid>), and gdb on the development machine connects over the network (target remote ecu:2345), using the unstripped binaries and the target's sysroot from the build (set sysroot), so the target image can stay stripped. For crashes in the field, enable core dumps: with ulimit -c unlimited or systemd-coredump, the kernel writes the memory of a crashing process to a file, and gdb opens it later with the matching debug symbols as if the crash had just happened. For hangs, thread apply all bt on the running process shows where each thread waits (Concurrency 10.3). Hardware watchpoints (watch frame->width) stop the program when a variable changes, which finds memory corruption that a backtrace cannot. Kernel code is debugged differently: from oops messages decoded with scripts/decode_stacktrace.sh, with kdump and the crash tool on a kernel dump, or with a JTAG debugger.

10.3strace, ltrace and perf trace

strace (Section 2.4) shows the system calls of a process and is the fastest way to answer "what file, device or socket does it use, and which call fails?". Useful options: -f to follow threads and children, -p <pid> to attach to a running process, -e trace=file,network to filter, -y to print the path behind each descriptor, -k to print the user stack of each call, -c for a summary. ltrace does the same for calls into shared libraries. Both stop the traced process on every event, which, as measured in Section 2.4, can slow it down a hundredfold. perf trace shows system calls from in-kernel tracepoints without stopping the process, at a fraction of the cost.

10.4perf

perf is the kernel's own performance tool, built on the perf_event_open() system call. It reads the CPU's hardware performance counters (cycles, instructions, cache misses, branch mispredictions, stalls), the kernel's software counters (context switches, page faults, migrations) and every tracepoint. perf stat counts events for a command:

Pitfall

These examples used the cpu-clock software event because the cloud VM exposes no hardware counters ("<not supported> cycles"). On an Arm target the PMU must be described in the device tree and the driver enabled, and non-root users need /proc/sys/kernel/perf_event_paranoid lowered. Check this early in a project; a target without working counters makes performance work much harder.

10.5ftrace and trace-cmd

ftrace is the tracing framework built into the kernel, controlled through files in /sys/kernel/tracing. It offers two kinds of data. Tracepoints are fixed probes at important events, about two thousand of them: sched_switch and sched_wakeup, irq_handler_entry, block request issue and completion, network transmit and receive, page faults, V4L2 buffer events. Tracers record more: the function and function_graph tracers record every kernel function call (filtered to the functions you name), the latency tracers of Section 9.5 record the worst sections. Events go into a per-CPU ring buffer in memory with nanosecond timestamps, cheaply enough to leave on during a test drive.

The traces in Sections 5.3 and 7.2 were taken by writing to these files directly. In practice trace-cmd is more convenient: trace-cmd record -e sched -e irq -e block -- ./app records events to a file, trace-cmd report prints them, and KernelShark or Perfetto show them as a timeline per CPU, which makes "my thread was runnable but did not run, and this other task ran instead" visible at a glance. Applications can add their own markers to the same timeline by writing to /sys/kernel/tracing/trace_marker ("frame 41 start"), which is the easiest way to correlate application phases with kernel events.

10.8A worked example: frames dropped every few minutes

A front camera service reports a gap in the V4L2 sequence numbers every few minutes, more often when the logger is busy. The investigation follows the layers. First the cheap counters: top -H shows the capture thread at normal priority on any CPU, /proc/interrupts shows the CSI-2 receiver and the Ethernet interrupts on the same CPU. A bpftrace histogram of the capture thread's run-queue latency has a tail at 30–40 ms. trace-cmd record -e sched -e irq -e v4l2 with a marker written at each frame, viewed in KernelShark, shows the moment: the capture thread is woken by the frame-end interrupt but stays runnable for 38 ms while a log-compression thread runs on that CPU, during which the driver ran out of queued buffers.

The fixes follow from the evidence and need no guessing: give the capture thread SCHED_FIFO priority and pin it, with its interrupt, to a CPU the logger may not use (cpuset for the logger's cgroup), and add one buffer to the ring as margin. A long test run with the same trace then shows run-queue latency below 100 µs and no gaps. The point of the story is the method: measure first, find the layer, then use the tool that observes that layer.

Talk track

"We never guess at timing problems. We look at counters first, then trace the scheduler and interrupts with ftrace or eBPF on the target under real load, find who ran when our thread should have, and fix priorities, affinity or buffering based on that trace. strace and Valgrind are for functional bugs on the bench; for timing we use tools that do not disturb timing."

11.3One sentence each

Kernel vs user space

Different CPU privilege levels; the only doors into the kernel are system calls, faults and interrupts.

System call

A trap into the kernel with a number and register arguments; returns a value or a negative errno.

vDSO

Kernel code mapped into every process so that reading the clock needs no system call.

Task

One kernel object for threads and processes; clone() flags decide what is shared.

fork / exec

Copy the process with copy-on-write pages, then replace its program; the PID and descriptors stay.

Zombie

An exited process whose parent has not called wait(); holds only a PID.

Scheduler

Per-CPU runqueues, classes asked in order stop, deadline, RT, fair, idle; RT always beats fair.

EEVDF

The fair class runs the eligible task with the earliest virtual deadline; shares follow nice weights.

Virtual memory

Per-process page tables translate every address; the TLB caches translations.

Page fault

First touch of a lazily allocated page; the kernel maps it, or sends SIGSEGV if no VMA allows it.

mmap

Map a file, a device buffer or anonymous memory; MAP_SHARED is how processes share pages.

OOM killer

When overcommitted memory is really used and reclaim fails, the kernel kills the biggest offender.

DMA API

Gives devices bus addresses through the IOMMU and keeps CPU caches consistent around transfers.

File descriptor

Index into a per-process table pointing at a shared open file that points at an inode.

Page cache

All file I/O goes through RAM copies of file pages; writes reach flash later unless you fsync.

Capabilities

Root's powers split into about forty pieces, so services get only what they need.

IPC

Copy small messages through sockets or pipes, share big data through memfd or dma-buf.

Interrupts

A short top half acknowledges the device; softirqs, workqueues or IRQ threads do the rest.

Driver model

Bus matches device and driver, probe acquires resources and registers with a framework.

V4L2 capture

A ring of DMA buffers; the frame-end IRQ stamps and completes one, the thread dequeues and requeues it.

Network stack

Transmit runs in the sender's context down to the driver; receive runs in softirq via NAPI.

Device tree

Data that describes non-discoverable hardware; compatible strings bind drivers.

Yocto

Layers of recipes built by BitBake into reproducible images, with an sstate cache.

PREEMPT_RT

Sleeping spinlocks with PI, threaded IRQs and softirqs: bounded worst case, not faster code.

cyclictest

Measures timer wake-up latency per CPU; only the maximum under load over hours counts.

Tracing

ftrace tracepoints and eBPF observe the kernel in production with little overhead; strace does not.

QSelf-check questions

Core questions with short model answers; the chapter sections hold the depth. The second group checks understanding with "why" and "what if" questions rather than definitions.

Q.1Core questions

What is the difference between kernel space and user space?Basic

They are different CPU privilege levels (EL1 and EL0 on Arm). Kernel code may change page tables, handle interrupts and access device registers; user code runs in its own virtual address space and can only ask the kernel through system calls. A bug in user space kills one process; a bug in the kernel can corrupt the whole system.

What happens when a program calls read() on a file?Intermediate

The C library puts the arguments and the system call number in registers and traps into the kernel. The kernel looks up the descriptor, goes through the VFS to the filesystem, and checks the page cache. On a hit it copies the data to the user buffer and returns. On a miss it allocates cache pages, maps file offsets to disk blocks, submits a block request, and the thread sleeps until the device has DMA'd the data and an interrupt completes the request; then it copies and returns.

How are processes and threads represented in the Linux kernel?Intermediate

Both are tasks (task_struct). clone() flags decide which resources a new task shares: threads share the memory map, descriptor table and signal handlers and form a thread group whose ID is the PID; a forked process gets copies. The scheduler only sees tasks, so policy, priority and affinity are per thread.

What does fork() do, and why is it cheap?Basic

It duplicates the calling process. Instead of copying memory it copies the page tables and marks writable pages read-only in both processes; the first write to a page faults and copies only that page (copy-on-write). Descriptors are duplicated and point to the same open files. It is usually followed by execve(), which replaces the program.

What is a zombie process and how do you get rid of it?Basic

A process that has exited but whose parent has not collected its exit status with wait(). It has released its memory and descriptors and only holds a PID and the status. The fix is in the parent: reap children (handle SIGCHLD, call waitpid). If the parent dies, init adopts and reaps the zombies.

Explain virtual memory, page tables and the TLB.Intermediate

Every address a program uses is virtual. The MMU translates it through a per-process tree of page tables (four levels for 48-bit addresses with 4 KB pages) into a physical page frame, checking permissions. Because a walk costs several memory reads, the TLB caches recent translations; huge pages make each TLB entry cover 2 MB instead of 4 KB. This gives isolation, lazy allocation, sharing and memory-mapped files.

What is a page fault? Minor versus major?Intermediate

An exception when an access finds no valid translation or violates permissions. The kernel checks whether a VMA allows the access: if not, the process gets SIGSEGV; if yes, it maps a page. A minor fault needs no I/O (a zeroed page, a page already in the page cache, a copy-on-write copy) and costs about a microsecond; a major fault must read from storage and the thread sleeps.

What is the page cache, and why does a Linux system show so little free memory?Basic

The page cache keeps file data in RAM; all normal reads and writes go through it. Linux fills otherwise unused memory with it because clean cached pages can be dropped instantly when memory is needed. MemAvailable, not MemFree, says how much memory is really available.

What is the OOM killer?Basic

Linux lets processes reserve more memory than exists (overcommit) because most reservations are never fully used. If they are used and reclaim cannot free enough, the out-of-memory killer selects a process, mainly by size adjusted by oom_score_adj, and kills it. On products you control it with memory cgroup limits per service, protected scores for critical processes, no surprise allocations, or strict overcommit.

Top half, bottom half: softirq, tasklet, workqueue, threaded IRQ?Intermediate

The top half is the interrupt handler: interrupts off on that CPU, acknowledge the device, grab status, schedule the rest, never sleep. Softirqs (and tasklets on top of them) run deferred work soon after with interrupts on but still cannot sleep; networking and block completion use them. Workqueues run work in kernel threads that may sleep. Threaded IRQs give a device its own prioritised kernel thread; PREEMPT_RT threads nearly all handlers.

What is a device tree and why does Arm Linux need it?Basic

A data structure, compiled from .dts source to a .dtb blob that the bootloader passes to the kernel, describing hardware that cannot be discovered: register addresses, interrupts, clocks, regulators, GPIOs, buses and the devices on them, and links such as sensor to CSI-2 receiver. It lets one generic kernel run on many boards; compatible strings select drivers.

How does a driver get attached to a device?Intermediate

Devices are registered on a bus (platform from the device tree, I²C, PCIe, USB) and drivers register with match tables. When a device's identity (for DT, the compatible string) matches a driver's table, the bus calls the driver's probe(), which gets its resources, initialises the hardware and registers with a framework such as V4L2. If a dependency is missing, probe returns -EPROBE_DEFER and is retried later.

Describe the boot sequence of an embedded Arm Linux system.Intermediate

Boot ROM loads and verifies the first-stage loader into SRAM; SPL or TF-A BL2 initialises DRAM and loads TF-A BL31 (EL3 monitor, PSCI), optionally OP-TEE, and U-Boot. U-Boot loads the kernel, DTB and initramfs and passes the command line. The kernel initialises, probes drivers from the device tree, mounts the root filesystem and starts init (systemd), which starts services by dependency. Safety-relevant early functions such as the rear camera run on a separate real-time core in parallel.

Yocto or Buildroot?Basic

Buildroot is simple: one Kconfig configuration produces a toolchain, kernel, bootloader and root filesystem, fast to learn, good for small or single-purpose systems. Yocto is layered recipes built by BitBake with a shared-state cache, package feeds, SDKs, licence manifests and vendor BSP layers; more complex but suited to products with many teams, variants and years of maintenance, which is why automotive projects mostly use it.

What does PREEMPT_RT change in the kernel?Intermediate

It makes almost all kernel code preemptible: normal spinlocks become sleeping rt_mutex locks with priority inheritance, interrupt handlers and softirqs run in prioritised kernel threads, and long non-preemptible sections are removed; only raw spinlocks in the core still disable preemption. The result is a bounded worst-case latency in the tens of microseconds, at a small cost in throughput. It has been in mainline since 6.12.

How do you measure and qualify real-time latency on Linux?Intermediate

With cyclictest on the target hardware: one high-priority thread per CPU waking periodically on absolute time, recording wake-up latency, run for hours while the system is under worst-case load (network, storage, GPU, memory stress, the real application). Report the maximum, not the average, and use the histogram. To find the cause of a spike, use cyclictest's break-trace option with ftrace, the irqsoff and wakeup tracers, or rtla timerlat.

A program is slow. How do you find out why?Intermediate

First classify: is it CPU-bound, waiting for I/O, waiting for locks or the scheduler? top -H, vmstat, /proc/pressure and perf stat say which. For CPU, perf record -g and a flame graph show the hot functions, hardware counters show cache misses or stalls. For waiting, off-CPU analysis with eBPF (offcputime), scheduler traces or strace -T show what it waits for. Only then change code.

What is eBPF and why is it useful?Intermediate

A way to load small, verified programs into the running kernel and attach them to tracepoints, kernel or user functions and perf events. They aggregate data in kernel maps (counts, histograms) and send only results to user space, so you can answer questions like "distribution of block I/O latency" or "who opens this file" in production with low overhead and without rebooting or recompiling. It is also used for networking (XDP, tc) and security policies.

How do you pass a camera frame between two processes without copying?Advanced

Allocate the frame in memory both can map, normally a dma-buf from the capture or GPU driver (or a memfd for CPU-only data), pass the file descriptor once over a Unix domain socket with SCM_RIGHTS, and let both mmap() it or import it into their drivers. Then only small messages (buffer index, sequence, timestamp) travel through a queue, plus fences or an eventfd for synchronisation; cache maintenance is handled by the dma-buf begin/end CPU access calls.

Q.2Why and what if

Why is clock_gettime() so much cheaper than getpid()?Basic

Because it usually does not enter the kernel. The kernel maps the vDSO, a small library plus a read-only data page with the current time base, into every process; clock_gettime() reads that page and the hardware counter in user space. getpid() through syscall() always traps (about 300 ns versus 20 ns on the example VM).

What happens if a SCHED_FIFO thread at priority 99 runs an endless loop?Intermediate

Nothing of lower priority runs on that CPU anymore, including normal kernel threads and per-CPU work. RT throttling (950 ms of every second by default) leaves 5% for normal tasks so the system can still be recovered, and newer kernels reserve time for fair tasks with a deadline server. If throttling has been disabled for real-time work, the CPU is effectively lost and watchdogs or stalls follow.

Why can't you kill a process in state D, even with SIGKILL?Intermediate

Uninterruptible sleep is used where the kernel cannot safely abandon an operation halfway, typically waiting for a device to complete I/O into memory it owns. Signals are only acted on when the task returns towards user space, which it cannot do until the wait ends. A task stuck there points to a device or driver that never completes the request; /proc/<pid>/stack shows where.

What happens if you malloc 10 GB on a machine with 4 GB of RAM?Intermediate

With the default heuristic overcommit, a single 10 GB request on a 4 GB machine without swap is normally refused, but many smaller ones that add up to more than RAM succeed, because allocation only creates VMAs. The trouble starts when the pages are touched: the kernel reclaims cache, then the OOM killer kills some process, not necessarily the one that allocated. With strict overcommit the allocation fails immediately with NULL.

Why is the first frame processed after start-up slower than the others?Basic

Everything is cold. Newly allocated buffers fault in page by page on first touch, code and model files are read from flash into the page cache, caches and TLBs are empty, libraries resolve symbols lazily, and lazy initialisation in drivers and frameworks runs. Pre-fault and lock memory, warm up with a dummy frame, and load files at start-up.

What if the application keeps all V4L2 buffers while it processes?Basic

At the next frame start the driver has no queued buffer to DMA into, so the frame is dropped; the sequence number of the next delivered frame jumps. Keep at least one or two buffers queued at all times: return buffers quickly, copy out only what must be kept, or allocate more buffers if processing legitimately holds several.

write() returned success. What if the power fails one second later?Intermediate

The data was probably only in the page cache and is lost; writeback happens after up to 30 seconds. A file being rewritten in place may be left truncated or mixed. For data that must survive, call fsync(); to replace a file atomically, write a temporary file, fsync it, rename it over the original and fsync the directory.

Why can UDP datagrams be lost on a receiver even over loopback?Intermediate

Every UDP socket has a fixed-size receive buffer. If the receiving thread is descheduled or slow while a burst arrives, the buffer fills and the kernel drops further datagrams, counting them as receive buffer errors. UDP has no flow control to slow the sender. Larger SO_RCVBUF, a higher-priority receiver, reading in batches with recvmmsg(), and an application-level sequence check help.

Why does a TCP request-response protocol sometimes take exactly 40 ms per request?Intermediate

The sender wrote the request in two small pieces. Nagle's algorithm holds the second piece until the first is acknowledged, and the receiver delays its ACK hoping to piggyback it on a reply, up to about 40 ms. Write each message in one call (or writev()), or set TCP_NODELAY.

What if the compatible string in the device tree has a typo?Basic

The kernel creates the device, but no driver's match table matches, so probe is never called and usually nothing is logged. The device exists in /sys/bus/.../devices without a driver link. Bindings validation (make dtbs_check) catches such mistakes at build time.

Why does PREEMPT_RT reduce throughput slightly?Advanced

Sleeping locks cost more than spinning ones when contended (a context switch instead of a short spin), priority inheritance adds bookkeeping, interrupt handlers and softirqs run in threads and therefore need wake-ups and context switches, and preemption in more places means more switches and colder caches. The kernel trades some average efficiency for a bounded worst case.

Why is a VM or a development PC useless for real-time qualification?Basic

Latency depends on the whole stack beneath the thread: hypervisor scheduling of virtual CPUs, firmware interrupts, power management, the specific interrupt controller and drivers. A VM can deschedule the whole guest for milliseconds, as the 20–53 ms maxima in Section 9.4 show. Only the target SoC, with its real kernel, drivers and load, gives meaningful numbers.

Two processes inherited the same log file descriptor from their parent. What happens when both write?Intermediate

They share one open file description and therefore one offset, so writes go one after another and do not overwrite each other (each write() updates the shared offset; with O_APPEND each write is atomically placed at the end). Two processes that opened the file independently have separate offsets and would overwrite each other's data without O_APPEND.

Why does a timing bug sometimes disappear when you run the program under strace or gdb?Basic

Both stop the program at every traced event and add context switches, which changes the interleaving of threads and the timing of I/O. Races and latency problems depend on exactly that. Use observation that does not stop the program: ftrace tracepoints, eBPF, perf trace, or logging into a lock-free ring.
