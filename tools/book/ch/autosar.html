AUTOSAR Classic and Adaptive

One level below the overview: what AUTOSAR standardises and why; how a Classic ECU is built from software components, ports and runnables, a generated RTE, an OSEK-based operating system, basic software and the MCAL; how a signal travels from the CAN controller into a runnable; how the ARXML methodology and the configuration tools produce the code; how an Adaptive application on a POSIX system is started, configured, supervised and connected to services through ara::com; the platform services from persistency to cryptography; manifests; interoperability between Classic, Adaptive and non-AUTOSAR software; and how all of it is arranged on the high-performance computers of current vehicles.

1The big picture: what AUTOSAR standardises

AUTOSAR is often described as "a software architecture for ECUs", but that undersells it. It is a contract between hundreds of companies about three things at once: how ECU software is layered, how the system is described in machine-readable files, and which interfaces the layers offer. Almost every problem you meet in an AUTOSAR project, from a signal that arrives with the wrong value to an application that is not started, is a problem with one of those three contracts. This chapter goes one level deeper than the overview in the camera ECU chapter: it shows the mechanisms, the generated code and the files, and what happens step by step.

1.1A one-page recap

The camera ECU chapter explains why AUTOSAR was founded in 2003 and what problem it solved (Camera ECU 2.1): before it, every supplier rewrote drivers, communication and diagnostics for every customer and every microcontroller, so reuse was rare and integration was slow. The answer was "cooperate on standards, compete on implementation": the plumbing became a standard that specialised vendors sell, and companies compete on the functions a driver notices. The same chapter introduces the two platforms (2.3): the Classic Platform for microcontrollers, where everything is configured before compilation and timing can be proven, and the Adaptive Platform for high-performance processors running a POSIX operating system, with C++ applications, service-oriented communication and software that is deployed and updated in parts. It also shows the Classic layer cake, one signal followed through the communication stack, the Adaptive building blocks, the manifests and SOME/IP with its service discovery (3.1 to 5.5).

This chapter assumes that picture and asks the next questions. What exactly is a software component, and what does the RTE generator write into C? How does the AUTOSAR operating system decide which runnable runs when, and why are there tasks, alarms and schedule tables? What does each layer do to a CAN frame and how long does it take? Which files does an OEM send, which does a supplier write, and which tool turns them into code? How does Execution Management start a process, what does FindService really do, and why does a service sometimes take two seconds to appear? And how do Classic, Adaptive, Linux, QNX and a hypervisor share one central computer?

1.2Three standards in one: architecture, methodology and interfaces

The first part of AUTOSAR is the architecture: the layers, the modules inside them and the rules about who may call whom. The Classic Platform specifies well over a hundred basic-software modules, of which a typical ECU uses several dozen, each with a specification (an SWS, software specification) that defines its API, its configuration parameters and its behaviour, down to the error codes. Because the specifications are precise, a CAN interface module from one vendor works with a CAN driver from another, and a test suite can check conformance.

The second part is the methodology: a single meta-model of everything that can be described about a vehicle's software and network, stored as ARXML. Software components, data types, interfaces, frames and signals, ECUs, the mapping of software to ECUs, the configuration of every basic-software module, the deployment of an Adaptive application: all are elements of the same model. Tools exchange these files and generators turn them into code. The methodology is what makes AUTOSAR scale to a vehicle with a hundred ECUs from twenty suppliers, and in practice it shapes daily work more than the layered architecture does (Chapter 7).

The third part is the interfaces: the APIs a layer offers (for example Rte_Read_… in Classic or the ara:: C++ APIs in Adaptive), the standard application interfaces for common vehicle functions, and the network protocols such as SOME/IP that let ECUs from different suppliers talk. A fourth, smaller part is the Foundation standard, which holds what both platforms share: SOME/IP and its service discovery, end-to-end protection profiles, the time synchronisation protocols, and the common parts of the meta-model.

Interesting detail

AUTOSAR releases were numbered 1.0 to 4.4 until 2019 (Classic 4.0 in 2009 introduced multi-core and started the 4.x line that most ECUs in the field are still based on). Since then all standards share one yearly release named after the year and month: R19-11, R20-11, …, R24-11, R25-11. A project usually freezes one release for the life of the ECU, because moving to a newer one changes the meta-model, the generators and sometimes the APIs. When someone says "we are on 4.3", they mean a Classic stack from around 2016 with years of vendor patches on top.

1.3The principles behind the design

Four principles explain most of the design decisions, and recognising them makes the details much easier to remember.

Separate the application from the infrastructure. Application code should express what the function does, not how data reaches it. A component that switches on the rear camera reads "gear" from a port; whether the gear arrives from a CAN frame, a FlexRay slot, an Ethernet PDU or another component on the same core is decided by configuration and implemented by generated code. This is the virtual function bus idea: design components as if they were all connected by one ideal bus, and decide the real distribution later.

Make the hardware replaceable. Each layer hides one kind of hardware dependency: the microcontroller abstraction layer hides the chip, the ECU abstraction layer hides the board, the services layer hides the vehicle network and the non-volatile memory technology. Moving software to another microcontroller should mean replacing the bottom layer and re-running the generators, not rewriting the application.

Configure instead of coding. The standard modules are generic; what makes them specific to an ECU is configuration (thousands of parameters per ECU) from which generators produce tables and code. That moves the work from writing code to writing and checking configuration, which is why AUTOSAR projects live and die by their tooling and by the quality of the ARXML they receive.

Decide as early as the use case allows. Classic decides almost everything before compilation, because a brake controller must be analysable: every task, buffer and message exists at build time, and nothing is allocated at run time. Adaptive deliberately defers decisions to deployment or run time (which service instance to use, which process to start in which state, which application to update) because a central computer's software changes during the vehicle's life. The difference between the platforms is mostly a difference in when things are bound, which is worth saying explicitly.

Talk track

"AUTOSAR is three contracts: a layered architecture with standard modules, a methodology where the whole system is described in ARXML and code is generated from it, and standard interfaces and protocols. Classic binds everything at build time for microcontrollers with hard real-time needs; Adaptive binds at deployment and run time for POSIX computers with services and updates. Both share the meta-model and protocols like SOME/IP, which is what lets them interoperate."

1.4The running example: rear view on reverse gear

One function runs through the chapter, because following it through every layer shows what each layer contributes. The driver selects reverse; within a few hundred milliseconds the display must show the rear camera image with guidelines. The gear position is measured by the transmission controller and sent as a CAN FD signal. A Classic ECU (here the safety microcontroller of the camera ECU, or a zone controller) receives it, a software component decides whether the rear view is requested, and the request is forwarded to a system-on-chip. There an Adaptive application, the rear-view service, is started by the platform, subscribes to camera frames and vehicle state, and offers a service to the display application. A third-party navigation application running on Linux in another virtual machine must also know that the rear view is active, so that it can pause its own route guidance pop-ups.

2Classic versus Adaptive: which one, where and why both

The two platforms are not an old and a new version of the same thing. They answer different questions, and a modern vehicle needs both answers. Knowing the criteria, rather than the comparison table alone, lets you place any ECU or function on the right platform and explain the choice.

2.1What drives the split

The camera ECU chapter compares the platforms in a table (Camera ECU 2.3). Behind the rows are five forces. The first is determinism: a brake or steering controller must react within a few milliseconds, every time, and its worst-case execution and response times must be shown by analysis. That is possible when the set of tasks, their priorities and their periods are fixed and known, which is what Classic provides. A POSIX system with virtual memory, caches shared by many cores, a dynamic loader and many processes can be made fast and reasonably predictable, but proving a worst case is much harder.

The second is memory and isolation. A microcontroller has hundreds of kilobytes to a few megabytes of RAM, a memory protection unit with a handful of regions and no virtual memory; software components share one address space and are separated, if at all, by OS-Applications and the MPU. A system-on-chip has gigabytes of DRAM and an MMU; each application can be a separate process with its own address space, which makes it possible to combine software of different origins and quality on one chip.

The third is communication. Signals in frames that are sent cyclically fit a CAN bus with a few hundred values. Ethernet, megabyte payloads, clients that come and go, and function placement that changes between vehicle variants need service orientation (Networks 8.4). The fourth is change: a Classic ECU is flashed as one image, while a central computer runs dozens of applications from different teams that should be updated independently and over the air. The fifth is the development ecosystem: Adaptive applications are C++ programs that can use POSIX threads, standard libraries and the tools of the wider software world, which matters when the application is a neural-network pipeline rather than a control loop.

Why it matters

Customer and architecture discussions often contain the sentence "let us move this function to the central computer". Whether that is a good idea depends on exactly these forces: the reaction time it needs, whether its worst case must be proven, the I/O it touches and how often it will change. A function that needs a 5 ms reflex on a local actuator usually stays on a Classic controller, even in a zonal car.

2.2Where each platform runs in a vehicle

Classic runs on almost every ECU with a microcontroller: engine and transmission controllers, brakes and steering, airbag, body and door modules, battery management, zone controllers, and the safety microcontrollers next to the systems-on-chip of ADAS and cockpit computers. It also runs on the real-time cores inside a system-on-chip (the Cortex-R "safety island" of many automotive SoCs) and, increasingly, as a virtual ECU in a hypervisor partition. Adaptive runs on the application cores of ADAS and automated-driving computers, central vehicle computers, and some telematics and gateway units. Infotainment is usually Android Automotive or Linux without Adaptive, sometimes with a small Adaptive or SOME/IP layer to talk to the rest of the car.

2.3Beyond AUTOSAR: the other software you will meet

A central computer rarely runs only AUTOSAR. Perception stacks are often built on vendor frameworks (NVIDIA DriveWorks, the Qualcomm and Mobileye SDKs) or on ROS 2 and DDS during development, and many OEMs build their own middleware on top of Linux or QNX instead of, or next to, Adaptive. Android Automotive runs the cockpit. Since 2024 the Eclipse Foundation hosts open-source efforts such as the Safe Open Vehicle Core (S-CORE), backed by several OEMs and suppliers, which aims at an open, safety-capable core stack for software-defined vehicles. These do not make AUTOSAR irrelevant: the vehicle network, the Classic ECUs and the service protocols around a central computer are still AUTOSAR, so any non-AUTOSAR stack must interoperate with it (Chapter 12). For a computer-vision engineer the practical consequence is that you should understand AUTOSAR's concepts even if your own process is a plain Linux program, because its inputs and outputs cross an AUTOSAR boundary.

3Classic: software components, ports and runnables

In a Classic ECU, application software is not "a program with a main function". It is a set of software components whose interface (ports), internal structure (runnables and the events that trigger them) and data are described in ARXML, and whose glue is generated. Understanding these four or five concepts is enough to read any Classic design and most generated code.

3.1Why components, and which kinds exist

A software component (SWC) is the unit of design, reuse and integration. Its description says what it needs and provides, so that an integrator can place it on an ECU and connect it without reading its code, and so that it can be reused in another vehicle where the data come from elsewhere. An SWC is a type; an ECU may contain several prototypes (instances) of the same type, for example one per wheel, if the type is declared multiple-instantiable.

The standard distinguishes component kinds by what they are allowed to touch. An application SWC contains pure function logic and may only communicate through the RTE. A sensor-actuator SWC turns raw electrical values into physical ones and back (volts into a pedal position, a torque request into a PWM duty cycle); it talks to the ECU abstraction through the RTE and is therefore specific to a sensor but not to a board. A service SWC is the RTE-side face of a basic-software module (the NVRAM manager, the diagnostic event manager, mode managers); application components reach BSW services through it. An ECU abstraction SWC and a complex device driver SWC are basic software that has ports, so the RTE can connect them to applications (Section 6.5). NV block and parameter components provide non-volatile data and calibration parameters. A composition contains other components and connectors and exists only at design time: it structures a large system into subsystems, and the generator flattens it.

3.2Ports and port interfaces

A port is a point of interaction, typed by a port interface. A provide port (P-port) offers what the interface describes, a require port (R-port) needs it, and a connector joins a P-port and an R-port with compatible interfaces. Six interface kinds cover the communication patterns of a control unit.

A sender-receiver interface carries data elements: values that one side writes and the other reads. By default a data element is last-is-best: the receiver sees the most recent value, and a value overwritten before anyone read it is simply lost, which is right for states such as speed or gear. Declared as queued, every value is kept in a FIFO and delivered in order, which is right for events such as a button press. The communication specification (ComSpec) of each port adds the details: the initial value before anything was received, an alive timeout after which the receiver is told the data is stale, whether the receiver can query an update flag, whether the value is protected end to end. A client-server interface carries operations with arguments and return codes, invoked synchronously (the caller waits) or asynchronously (the caller collects the result later). A mode-switch interface distributes the current mode of a mode machine (for example ECU state RUN, POST_RUN, SLEEP) and lets runnables be triggered or disabled by mode changes. Parameter interfaces provide calibration constants, NV data interfaces non-volatile data, and trigger interfaces fire runnables without data, for example once per crankshaft tooth.

Interesting detail

Sender-receiver connections may be 1:n (one sender, many receivers, the normal case) or n:1 (many senders, one receiver), but not n:m. Client-server connections are always n:1: many clients may call one server, never the reverse. If you find yourself wanting two servers for one client, the design really needs two ports or a mode-dependent selection.

3.3Runnables and the events that trigger them

The behaviour of a component is split into runnables: C functions without arguments (apart from an instance handle for multiple-instance components) that the RTE calls. A runnable does not loop or wait for time; it is triggered by an RTE event, does its work and returns. The important events are a timing event (every 10 ms), a data-received event (a new value arrived on a port), a data-receive-error event (the value timed out or is invalid), an operation-invoked event (a client called a server operation), a mode-switch event (entering or leaving a mode), an init event, and the completion events of asynchronous calls and sends. Events can be disabled in certain modes, so a runnable that only makes sense while driving is not triggered while the ECU is shutting down.

Runnables are classified by what they may do. A category 1A runnable has no wait points and uses only the implicit API, which means it works on copies of data that the RTE makes before it starts and writes back after it ends (Section 4.2). A category 1B runnable may also use the explicit API, calling the RTE during its execution, but still never waits. A category 2 runnable may contain wait points, for example a synchronous server call that blocks until the server answered; it needs an OS task that can wait (an extended task), which costs stack and makes timing analysis harder, so many projects forbid it.

Data that several runnables of the same component share is declared rather than written as globals: inter-runnable variables (with explicit or implicit consistency, like ports) and per-instance memory. Critical sections are declared as exclusive areas; the RTE implements them, depending on the task mapping, by disabling interrupts, taking an OS resource, or by nothing at all when the runnables involved can never preempt each other. The declaration matters because only the integrator knows which runnables end up in which tasks.

Pitfall

Two runnables of one component communicating through a static C variable "because it is the same file". It works until the integrator maps them to tasks of different priority, or to different cores, and the RTE, which knows nothing of the variable, provides no protection. Declare inter-runnable variables and exclusive areas; they cost nothing when protection is not needed, because the generator then emits plain accesses.

Three things are worth noticing. Everything is identified by short names and referenced by absolute paths through packages (/PortInterfaces/Gear_I/Gear), and every reference states the type it expects (DEST="…"); this is how tools merge files from different authors and detect dangling references. Instance references (DATA-IREF, AUTOSAR-VARIABLE-IREF) need a context, because "the element Gear" means nothing until you say through which port. And the description contains no addresses, frames or tasks: it is the component's view only, valid on any ECU.

The developer writes the runnable bodies against a header the RTE generator emits in its contract phase, before the rest of the system exists. The API names follow a fixed scheme from the RTE specification, Rte_Read_<port>_<element>, Rte_Write_…, Rte_Call_<port>_<operation>, Rte_IRead_<runnable>_<port>_<element>, so the code below compiles against any conforming RTE. The experiment compiles it with gcc -std=c99 -Wall -Wextra -Werror against such a header.

#include "Rte_RearViewManager.h"           /* contract-phase header from the RTE generator */

#define SPEED_OFF_RAW ((VehicleSpeed_T)(15u * 64u))   /* 1/64 km/h per bit */

static RearViewReq_T decide(Gear_T gear, VehicleSpeed_T speed, RearViewReq_T last)
{
    if (gear == Gear_R) { return RearView_On; }
    if ((last == RearView_On) && (speed < SPEED_OFF_RAW)) { return RearView_On; }
    return RearView_Off;
}

static RearViewReq_T g_last = RearView_Off;  /* better: per-instance memory */

void RearViewManager_Run(void)               /* TimingEvent, 20 ms */
{
    Gear_T gear;
    VehicleSpeed_T speed;
    Std_ReturnType r1 = Rte_Read_Gear_Gear(&gear);
    Std_ReturnType r2 = Rte_Read_VehicleSpeed_VehicleSpeed(&speed);
    if ((r1 == RTE_E_OK) && (r2 == RTE_E_OK)) {
        g_last = decide(gear, speed, g_last);
    } else {
        g_last = RearView_Off;               /* invalid or timed-out input: safe default */
    }
    (void)Rte_Write_RearViewReq_RearViewReq(g_last);
}
Pitfall

Units in ARXML are SI unless stated otherwise: periods and timeouts are in seconds (0.02 is 20 ms). A timeout entered as 100 "because the requirement says 100 ms" means 100 seconds, and the generated RTE will happily report fresh data for a signal that stopped 99 seconds ago. Our experiment shows exactly this mistake in the excerpt above; configuration tools display milliseconds, but scripts that write ARXML directly must convert.

Interesting detail

The return codes of Rte_Read carry information you should not throw away. RTE_E_OK means a value is available; RTE_E_NEVER_RECEIVED that only the initial value exists; RTE_E_MAX_AGE_EXCEEDED that the alive timeout expired; RTE_E_INVALID that the sender or COM marked it invalid. For safety-related inputs, a status bit can also come from end-to-end checks. Code that casts the return value to void silently turns a lost gearbox into "gear = last known value".

3.5From components to an ECU: compositions, the system and mapping

On the virtual function bus, components are connected without knowing where they run. The system description adds the physical side: the ECUs, the networks and their frames, and two mappings. The SWC-to-ECU mapping places each component prototype on an ECU (and, with multi-core ECUs, later on a partition and core). The data mapping assigns each data element that crosses an ECU boundary to a system signal, which in turn is packed into an I-PDU and a frame on a bus. A connector between two components on the same ECU becomes a buffer in the RTE; a connector across ECUs becomes a COM signal on each side; the components do not change.

From the system description, a tool cuts the ECU extract: the part of the system relevant to one ECU, with its components, its frames and its signals. The extract is what an OEM delivers to the supplier of that ECU, and it is the contract against which the ECU is configured and tested (Section 7.2).

Talk track

"A Classic SWC is described, not just coded: ports typed by interfaces define what it needs and provides, runnables triggered by RTE events define when its code runs, and the developer writes only runnable bodies against a generated header. Mapping components to ECUs and data elements to signals is a separate step, which is why the same component can run on different ECUs without code changes."

4The RTE: generated glue between components and the ECU

The Runtime Environment is the most misunderstood layer of Classic AUTOSAR, because there is no "RTE product" running on the ECU. It is code generated for one ECU from its configuration: buffers, accessor functions or macros, task bodies that call runnables in the right order, and callbacks from the communication stack. Knowing what it generates explains both its overhead and its typical bugs.

4.1What the RTE generator produces

The generator runs twice in a typical project. In the contract phase it reads only one component's description and emits its application header (Rte_<Swc>.h) with the API prototypes and data types, so that the component can be developed and unit-tested before the ECU is integrated. In the generation phase it reads the whole ECU configuration (components, connectors, the mapping of runnables to tasks, the COM signals, the OS configuration) and emits the implementation: Rte.c with the buffers and the API implementations, the task bodies, the callbacks that COM calls when a signal arrives, and the type header Rte_Type.h.

For each connector the generator chooses the cheapest implementation that is still correct. If the sender and receiver runnables run in the same task, Rte_Write can become a plain assignment to a global variable and Rte_Read a plain read; with optimisation, an RTE call costs nothing. If they run in tasks of different priority on one core, the write and read must be atomic, so for data wider than the CPU can copy in one instruction the generator adds a short critical section. If they run on different cores, it uses the inter-OS-application communicator (Section 5.5) or a spinlock-protected buffer. If the receiver is on another ECU, Rte_Write calls Com_SendSignal, possibly after a transformer serialised a complex data type or added end-to-end protection (Section 4.4).

The task bodies are where the RTE meets the operating system. The integrator maps every RTE event to an OS task with a position in that task: "TimingEvent 20 ms of RearViewManager_Run goes into Task_App_20ms at position 3". The generator then writes the task function. For a basic task activated cyclically by the OS, it is a sequence of runnable calls; for an extended task, it is an endless loop that waits for OS events and calls the runnables whose RTE events fired.

/* Typical shape of generated task bodies (names vary between RTE vendors) */
TASK(Task_App_20ms)                     /* basic task, activated every 20 ms by a schedule table */

    RearViewManager_Run();

        (void)GetEvent(Task_App_Event, &ev);
        (void)ClearEvent(ev);
        if ((ev & Rte_Ev_Gear_Received) != 0u) { RearViewManager_OnGear(); }
        if ((ev & Rte_Ev_Mode_Changed)  != 0u) { RearViewManager_OnMode(); }
    }
}
Why it matters

The order of runnables within a task and the mapping to tasks determine end-to-end latency. If the plausibility check that produces a value runs after the runnable that consumes it in the same 20 ms task, the consumer always sees last cycle's value: 20 ms of latency added by one line of configuration. Timing analysis of a Classic ECU is largely analysis of this mapping.

4.2Explicit and implicit communication, and data consistency

The RTE offers two ways to read and write sender-receiver data. With the explicit API (Rte_Read, Rte_Write), the runnable accesses the shared buffer at the moment of the call. With the implicit API (Rte_IRead, Rte_IWrite), the RTE copies all data the task's runnables read into task-local buffers before the first runnable starts, and publishes their writes after the last one ends; inside the task, the data cannot change. Why both? Because a runnable of a low-priority task can be preempted by a high-priority task or an interrupt that writes a new value. With the explicit API, two reads of the same port within one runnable can then return different values, and a calculation that uses both sees an inconsistent state. With the implicit API, every runnable in the task sees one consistent snapshot, at the cost of memory for the copies, copy time at task start and end, and data that may be up to one task runtime older.

Most projects use the implicit API for periodic control and signal-processing runnables (category 1A), because consistency within a calculation is what such code silently assumes, and the explicit API for event-driven runnables that react to one new value. Both are configuration choices of the component description, so a component's author decides, while the integrator only decides the task mapping that makes the difference matter.

Interesting detail

The same problem exists one level down, between COM and the RTE: a signal group (several signals that belong together, such as the four wheel speeds of one frame) must be read atomically, or a receiver may combine the front-left speed of one frame with the rear-right speed of the next. AUTOSAR solves it the same way: COM provides a shadow buffer, the RTE copies the whole group under protection, and the application reads a record.

4.3Client-server calls and modes

A client-server call between components on the same ECU usually becomes a direct function call: Rte_Call_Calib_GetState(&state) calls the server runnable in the caller's context, which is cheap but means the server's code runs at the caller's priority and on its stack. If the server must run in its own task (for example because it is on another core or must be serialised), the call becomes an activation of the server's task and the client either blocks on an OS event (synchronous, category 2) or receives the result later through Rte_Result (asynchronous). Calls to basic-software services, such as writing an NVRAM block or reporting a diagnostic event, are client-server calls to service components, which is why application code never includes BSW headers directly.

Modes are AUTOSAR's state machines. A mode manager (often BswM for ECU modes, or an application component for function modes) switches a mode-declaration group, for example EcuMode from RUN to POST_RUN. The RTE then fires mode-switch events on entry and exit, and disables RTE events that are configured not to run in the new mode, so a runnable that controls an actuator simply stops being triggered while the ECU prepares to sleep. Mode switches are synchronised with the tasks that run affected runnables, so no runnable sees half a transition.

4.4Across the ECU boundary: COM, transformers and end-to-end protection

When a data element is mapped to a system signal, the RTE no longer owns the buffer; COM does. On the sending side, Rte_Write calls Com_SendSignal, which packs the value into the I-PDU at its bit position, and COM transmits the I-PDU according to its transmission mode (cyclic, on change, or mixed) (Networks 8.1). On the receiving side, COM unpacks the signal when the frame arrives and calls an RTE callback, which updates the RTE buffer and fires any data-received event.

Simple signals map one-to-one to integers in a frame. Complex data, such as a record with an array of detected objects, cannot be described as bit positions; it must be serialised. Since release 4.2, the RTE can call a chain of transformers between the component and COM: the SOME/IP transformer serialises the data into SOME/IP format, the end-to-end transformer adds a counter, a data ID and a CRC using one of the E2E profiles (Functional safety 4.4), and the COM-based transformer packs signals. On the receiver, the chain runs in reverse and the E2E check result reaches the component as part of the read status. This is how a Classic ECU sends a service event to an Adaptive machine: the payload is SOME/IP serialised in the transformer and the SOME/IP header is added by the socket adaptor path (Section 12.1).

Pitfall

End-to-end protection must be configured identically on both ends: same profile, same data ID, same counter range, same position of the CRC. A mismatch does not fail loudly at build time; it shows up as a receiver that reports every value as "wrong CRC" and falls back to its default. When an E2E-protected signal is always invalid after an integration step, compare the data IDs in both ECUs' extracts before looking at the network.

Talk track

"The RTE is generated per ECU. For each connection it picks the cheapest correct implementation: a variable, a protected buffer, an inter-core channel or a COM signal. It also generates the task bodies that call runnables in the configured order, and it offers explicit access, which reads the live buffer, and implicit access, which gives a whole task one consistent snapshot."

5The Classic operating system

The AUTOSAR OS is a small, statically configured real-time kernel derived from the OSEK/VDX standard of the 1990s. It has no processes, no dynamic task creation and no memory allocation; everything it will ever schedule is listed in the configuration. That is precisely what makes its behaviour analysable, and why it fits into a few kilobytes of code.

5.1Tasks, their states and why there are two kinds

A task is the unit the OS schedules. Its priority is fixed at configuration time, and the scheduler always runs the ready task with the highest priority (fixed-priority preemptive scheduling, the same policy that a Linux SCHED_FIFO thread uses, Concurrency 7.1). A task is activated (by another task, an alarm, a schedule table or an interrupt), runs, and terminates.

OSEK defines two kinds of task, and the difference is about stack. A basic task has three states: suspended, ready, running. It runs to completion (possibly preempted by higher-priority work) and cannot wait. Basic tasks of the same priority that never run at the same time can share one stack, which on a microcontroller with 256 KB of RAM matters. An extended task adds a fourth state, waiting: it can call WaitEvent() and sleep until another task or an interrupt sets one of its events. That makes event-driven designs simpler, but every extended task needs its own stack for its whole life. Four conformance classes describe what an implementation supports: BCC1 and BCC2 (basic tasks only, without or with multiple activations and several tasks per priority) and ECC1 and ECC2 (also extended tasks).

Interrupts come in two categories. A category 1 ISR runs outside the OS: it is as fast as the hardware allows but may not call OS services, so it cannot activate a task. A category 2 ISR is managed by the OS: it has a small prologue and epilogue and may activate tasks and set events, and when it ends the scheduler runs if it made a higher-priority task ready. Almost all BSW interrupts (CAN receive, SPI end of transfer) are category 2.

5.2Resources and the priority ceiling protocol

When tasks of different priority share data that the RTE does not protect for them, they use an OS resource with GetResource() and ReleaseResource(). OSEK resources implement the immediate priority ceiling protocol: each resource has a ceiling priority, the highest priority of any task that uses it, and a task that takes the resource immediately runs at that ceiling until it releases it. No task that might want the same resource can preempt it in the meantime, so a task never blocks on a resource held by another. This eliminates unbounded priority inversion and deadlock by construction (Concurrency 7.3), at the price of briefly blocking unrelated tasks with priorities up to the ceiling. The special resource RES_SCHEDULER has the highest task priority and makes a section non-preemptable.

Because the OS knows all tasks and resources at build time, the generator computes every ceiling, and a worst-case response-time analysis can account for the longest critical section of each lower-priority task as blocking time. This is the same analysis as for CAN messages (Networks 4.6), applied to a CPU.

5.3Counters, alarms and schedule tables

Time in the OS is measured by counters, usually driven by a hardware timer tick (often 1 ms) or by other sources such as crank-angle teeth. An alarm is attached to a counter and fires once or cyclically when the counter reaches a value; its action is to activate a task, set an event or call a callback. Alarms are simple, but a set of independent alarms drifts relative to other timing sources and does not express "these five tasks have this fixed pattern".

A schedule table expresses exactly that. It is a sequence of expiry points at offsets within a period, each with one or more actions (activate these tasks, set these events). A 10 ms table might activate the 1 ms tasks at every point, the 5 ms task at offsets 0 and 5 and the 10 ms task at offset 2, deliberately shifted so that it does not start at the same moment as the 5 ms task. Schedule tables can be synchronised to an external time base, for example the FlexRay cycle or the global time distributed by the time-synchronisation module, so that a task runs a fixed time after a frame arrives on the bus. That makes it possible to design end-to-end latency across ECUs rather than just measure it.

5.4Scalability classes and protection

Not every ECU needs memory partitioning or execution-time budgets, so AUTOSAR OS defines four scalability classes. SC1 is OSEK plus schedule tables and stack monitoring. SC2 adds timing protection: execution-time budgets per task and ISR, limits on how often a task may be activated, and limits on how long resources may be held or interrupts disabled; a violation calls the protection hook, which can terminate the offending application. SC3 adds memory protection, using the MPU to restrict each OS-Application (a group of tasks, ISRs and data) to its own memory regions, and service protection, which rejects OS calls that the caller is not allowed to make. SC4 combines SC2 and SC3. An ECU that hosts software of different ASILs, or software from different suppliers, typically needs SC3 or SC4, because freedom from interference must be argued for memory and time (Functional safety 6.2, 6.3).

OS-Applications are either trusted, running in privileged mode with access to everything (the BSW usually is), or non-trusted, running in user mode under the MPU. A non-trusted application calls privileged functionality through trusted functions, the Classic equivalent of a system call. The integrator decides which components form which OS-Application; the RTE then has to generate communication across application boundaries that respects the protection.

Numbers

A Cortex-M or Cortex-R MPU has 8, 16 or 24 regions, which limits how finely memory can be partitioned; a context switch with MPU reprogramming costs on the order of a microsecond on a 300 MHz core. Typical tick rates are 1 ms; typical periodic tasks 1, 5, 10, 20, 50 and 100 ms. An AUTOSAR OS kernel needs roughly 5 to 30 KB of code, depending on the scalability class and number of cores.

5.5Multi-core: cores, spinlocks and the IOC

Since release 4.0 the OS supports multi-core microcontrollers (Infineon AURIX TC3xx with up to six cores, Renesas RH850 U2A/U2B, NXP S32 families). Each core runs its own scheduler with its own tasks, and every OS-Application is assigned to one core. Tasks on different cores truly run in parallel, so the ceiling protocol no longer protects shared data; AUTOSAR adds spinlocks for short cross-core critical sections, and the IOC (inter-OS-application communicator), generated code that provides communication channels between OS-Applications on different cores or in different memory partitions, with the necessary copying, locking and cache handling. The RTE uses the IOC whenever a connector crosses cores.

A typical distribution places the basic software and the communication stack on one core (often a lockstep core), safety-relevant application components on another lockstep core, and performance-hungry but less critical components on a non-lockstep core. Interrupts are routed to the core that owns the driver. Most BSW modules were not designed for parallel use; newer releases add concepts for distributing basic software across partitions and cores, but most stacks still keep the BSW on one core and pay for the cross-core calls.

Pitfall

Moving a runnable to another core "because it has spare capacity" without looking at its connectors. Every connector to a component on the original core becomes an IOC channel with copying and locking, and every data-received event becomes a cross-core activation with an inter-core interrupt. The load moves, but the latency of the chain can grow and its analysis gets harder. Partition by data flow, not by CPU load alone.

Talk track

"The Classic OS is OSEK with extensions: statically configured tasks with fixed priorities, basic tasks that run to completion and extended tasks that can wait for events, resources with the immediate ceiling protocol, alarms and schedule tables for timing, scalability classes that add timing and memory protection for mixed-criticality ECUs, and spinlocks and the IOC for multi-core."

6Below the RTE: basic software, MCAL and complex drivers

The basic software is everything between the RTE and the silicon: several dozen modules in three layers plus the OS, configured per ECU. The camera ECU chapter introduces the layer cake and the main stacks (Camera ECU 3.1, 3.4); here we look at the module map, at what the bottom layer really is, at one signal's path with its timing, at how an ECU starts, and at when to leave the standard with a complex device driver.

6.1The module map

The layers are cut horizontally by what they hide and vertically into stacks by function. Each stack has the same shape: a driver in the microcontroller abstraction layer that knows registers, an interface module in the ECU abstraction layer that makes the driver's hardware location irrelevant, and service modules on top that implement protocols and policies. Reading a module's name usually tells you where it sits: Can, Spi, Fls are drivers; CanIf, MemIf, EthIf are interfaces; Com, NvM, Dcm are services.

Two modules have no stack of their own but appear everywhere. The BSW scheduler (SchM) is to basic software what the RTE is to components: most BSW modules have cyclic main functions (Com_MainFunctionRx, CanNm_MainFunction, NvM_MainFunction) and exclusive areas, and SchM generates the code that calls the main functions from OS tasks and implements the exclusive areas. In practice the RTE and SchM are produced by the same generator. The default error tracer (Det) collects development errors (a null pointer passed to an API, a call before initialisation) during development and is usually switched off or reduced in production builds.

6.2The MCAL: the layer that knows the chip

The microcontroller abstraction layer is a set of drivers with standard APIs for the on-chip peripherals: Mcu (clocks, PLL, reset reason, RAM initialisation), Port (pin multiplexing and electrical properties), Dio (digital pins), Adc, Pwm, Icu (input capture), Gpt (general-purpose timers), Spi, Can, Lin, Fr, Eth, Fls (internal flash), Wdg (watchdog), and on newer chips crypto, CAN XL or Ethernet switch drivers. It is almost always delivered by the semiconductor vendor (Infineon, NXP, Renesas, ST, TI), because only they know the silicon errata and the hardware's safety mechanisms, and it is usually developed to ASIL D with a safety manual that lists the assumptions the integrator must fulfil.

MCAL drivers expose a deliberately boring API: initialise with a configuration structure (Can_Init(&CanConfigSet)), request an action (Can_Write(Hth, &PduInfo), Spi_AsyncTransmit(Sequence), Adc_StartGroupConversion(Group)), and report completion through callbacks into the layer above (CanIf_RxIndication, CanIf_TxConfirmation, a notification for an ADC group). Whether completion is detected by interrupt or by polling in a main function (Can_MainFunction_Read) is a configuration parameter per hardware object. Interrupts give lower latency; polling gives perfectly predictable CPU load, which is why some safety projects poll even CAN reception.

Pitfall

The Port and Mcu configurations are where hardware and software teams meet, and errors there look like software bugs elsewhere. A CAN receive pin configured without the right input filter, or a PLL configuration that gives 79.9 MHz instead of 80 MHz, produces a CAN bus that works on the bench and shows sporadic bit errors in the vehicle at temperature. Review MCAL configuration against the schematic and the clock tree, not only against the AUTOSAR checker.

6.3Following one signal from the CAN controller into a runnable

The camera ECU chapter follows the gear position through the stack in one paragraph (Camera ECU 3.3). Here is the same path with the functions that are called, the context they run in and where time is spent. Step through it.

The transmission controller sends the frame with the gear signal every 20 ms (and immediately on change). The CAN controller in our microcontroller samples the bits, checks CRC and form, acknowledges, and stores the frame in a receive message buffer whose acceptance filter matches the identifier. At the end of the frame it raises a receive interrupt. Nothing in software has happened yet; the frame took about 0.2 to 0.3 ms on the wire at 500 kbit/s nominal rate.

The category 2 ISR of the CAN driver reads the identifier, the length and the payload out of the message buffer, releases the buffer, and calls CanIf_RxIndication(Mailbox, &PduInfo). Mailbox identifies the hardware receive object; PduInfo points to the data and length. This takes a few microseconds; everything above still runs in the ISR context unless the driver is configured for polling.

The CAN interface looks up which L-PDU (link-layer protocol data unit) this hardware object and identifier belong to, possibly with a software filter if several identifiers share one hardware object, checks that the length is at least the configured length, and calls the upper layer configured for that PDU: PduR_CanIfRxIndication(RxPduId, &PduInfo). From now on nobody above knows it was CAN.

The PDU router forwards the I-PDU according to its static routing table: to COM for signal-based PDUs, to CanTp for diagnostic segments, to another bus interface for gatewayed PDUs, or to several destinations at once. For our gear PDU it calls Com_RxIndication(ComRxPduId, &PduInfo). The router itself is a table lookup.

COM copies the I-PDU into its buffer. If the PDU is configured for immediate processing, it unpacks now; with deferred processing (the default in many projects, to keep ISRs short) the work happens in the next Com_MainFunctionRx, typically every 5 or 10 ms in a BSW task. Unpacking extracts the bits of each signal, handles byte order and sign, checks update bits and invalid values, restarts the reception deadline monitor and, if configured, runs the E2E check through a transformer. Then COM calls the RTE's notification, for example Rte_COMCbk_GearPos().

The generated callback copies the signal into the RTE buffer (or the RTE reads it later with Com_ReceiveSignal), and, because RearViewManager_OnGear is triggered by a data-received event, sets the OS event of the extended task that runs it, or activates the basic task. If the new task has a higher priority than the BSW task, the OS switches to it when the callback returns.

The application task runs, the RTE calls RearViewManager_OnGear(), which calls Rte_Read_Gear_Gear(&gear) and gets the value with status OK. From the end of the frame to this point, the time is a few tens of microseconds with immediate processing, or up to one COM main-function period plus task switching with deferred processing. Add up to 20 ms of sender cycle and the sender's own task delay, and you have the real age of the gear when the rear view reacts. If the sender stops, the COM deadline monitor or the alive timeout makes the next read return a timeout status instead.

Numbers

Per received PDU, a Classic communication stack on a 300 MHz Cortex-R or TriCore core spends roughly 2 to 10 µs from interrupt to RTE buffer, depending on the number of signals and checks. The dominant latencies are the configured periods, not the code: sender cycle (10 to 100 ms), COM deferred processing (5 to 10 ms), and the receiving task period. That is why latency budgets are made from configuration tables, not from profiling.

6.4How a Classic ECU starts and goes to sleep

Start-up is orchestrated by the ECU state manager (EcuM) and the BSW mode manager (BswM). After reset, the start-up code initialises RAM and calls EcuM_Init(). EcuM initialises the drivers that are needed before the OS (Mcu, Port, sometimes Det and Dem in a pre-initialised mode), selects the post-build configuration set if there are several (Section 7.3), and starts the OS with StartOS(). The first task then completes the initialisation: the BSW scheduler, BswM, and through BswM's rules the remaining drivers, the communication stack, the NVRAM manager (which reads all configured blocks from flash, often the slowest step), and finally Rte_Start(), after which init runnables run and periodic events begin. A small ECU is fully up in 20 to 100 ms; OEM requirements that an ECU answers on the network within roughly 100 to 200 ms after a wake-up drive much of this ordering.

BswM is a rule engine: rules over mode requests and conditions ("ignition off and no communication request and NVRAM write-all done") trigger action lists ("release the communication channel, switch EcuM to sleep"). Network management keeps buses awake while any node requests communication (Networks 12.4); when all release, the ECU writes its NVRAM blocks, shuts down the stack in reverse order and either powers off or enters a sleep mode with selected wake-up sources. Much ECU-specific behaviour, such as what happens after a crash with an un-written block, lives in these rules.

6.5Complex device drivers: leaving the standard on purpose

Some things the standard stack cannot do, or cannot do fast enough: a protocol to a system-on-chip over SPI or a private UART, the control of a camera serializer over I²C, an injection timing that must be computed within microseconds of a crankshaft tooth, a hardware block the standard does not know. For these AUTOSAR provides the complex device driver: a module that may access the hardware and the MCAL directly, may have its own interrupts, and offers ports to the RTE and/or standard interfaces to other BSW modules. It is the official escape hatch.

Good CDDs are small and have a clean boundary. The usual design puts all time-critical and hardware-specific work into the CDD (an interrupt-driven SPI frame handler, a ring buffer, CRC checks, a state machine for the link) and offers the rest of the ECU a standard face: sender-receiver ports for data and a client-server port for commands, or an interface towards the PDU router so that its frames can be routed and gatewayed like any other PDU. The ASPICE chapter shows how a CDD's requirements, architecture and integration are documented and verified (ASPICE 8.3).

Pitfall

A CDD that grows into a second operating system: its own scheduler loop, its own timers, its own copy of signal handling, and direct calls into other BSW modules' internal functions. It works for one release and blocks every later update of the standard stack, and its timing is invisible to the OS configuration and to timing analysis. If a CDD needs periodic work, give it a main function scheduled by SchM; if it needs data from the rest of the ECU, give it ports.

Talk track

"Below the RTE the BSW is organised in stacks, each with a driver, an interface and services. A received CAN frame goes from the MCAL driver's ISR through CanIf and the PDU router to COM, which unpacks signals, monitors deadlines and notifies the RTE, which triggers the runnable. The MCAL comes from the chip vendor; anything the standard cannot do goes into a complex device driver with a standard-looking boundary."

7Methodology, ARXML and the Classic toolchain

In an AUTOSAR project most engineering effort goes into descriptions and configuration, and most integration problems are differences between descriptions. This chapter follows the files: who writes which, how they flow between companies and tools, and how they become a flashable image.

7.1One meta-model, many templates

AUTOSAR defines its concepts in a UML meta-model; ARXML is the XML serialisation of instances of that model, validated by an XML schema per release. The meta-model is organised into templates: the software component template (components, ports, interfaces, data types, internal behaviour), the system template (ECUs, networks, frames, signals, mappings), the ECU configuration template (parameter definitions and values for BSW modules), the BSW module description template, the diagnostic extract template, the timing extensions and, for Adaptive, the manifest specification. One ARXML file may contain elements from several templates, and a project typically consists of hundreds of files that together form one model.

ECU configuration deserves a closer look because it explains how tools work. Each BSW module's parameters are defined in a parameter definition (for example, /AUTOSAR/EcucDefs/Com/ComConfig/ComIPdu/ComIPduDirection, with its type, range and multiplicity), published by AUTOSAR and extended by each vendor in its module description. The project's ECU configuration values are containers and parameters that reference these definitions. A configuration tool is therefore generic: it reads the definitions, shows forms, checks values against ranges and dependencies, and calls each module's generator, which turns the values into C tables and macros.

Most of these values are not typed by anyone: they are derived from the ECU extract by the tool's "update from system description" step, and engineers only edit what the extract cannot know.

7.2The workflow from vehicle to flashable image

The flow runs from the vehicle level down to one ECU and then into code. The OEM's E/E architecture team models the networks, ECUs, frames and signals and the logical function architecture, usually in an architecture tool, and exports a system description. Function developers deliver component descriptions, often generated from Simulink models together with their code. The OEM cuts an ECU extract for each ECU, plus a diagnostic extract, and sends them to the supplier. The supplier imports them into the ECU configuration tool together with the BSW vendor's module descriptions, maps components and runnables to tasks and cores, completes the BSW configuration, runs the generators for the RTE, the OS and every BSW module, compiles the generated code with the static BSW code, the MCAL and the application code, links, and produces the image plus an A2L file for measurement and calibration tools.

In a well-run project this flow is automated: the extract and all configuration live in version control, a CI job runs the "update from extract", the generators and the build headlessly, and the generated code is either checked in (so reviews show what changed) or rebuilt reproducibly. Generated code is reviewed by diff, not by reading: a new OEM extract that changes one frame should produce a small, explainable diff in COM's tables.

Why it matters

When the OEM sends "ARXML drop 37", it is a contract change. Signal positions, periods, timeouts, E2E data IDs or even data types may have changed. The first job is a structured comparison with drop 36, the second is updating the configuration and regenerating, and the third is checking whether any component's assumptions changed. Teams that treat drops as "just regenerate" find the differences in the vehicle.

7.3When a parameter is bound: configuration classes and variants

Every BSW parameter has a configuration class that says when its value is fixed. Pre-compile parameters become macros and constants: the compiler can optimise them away, so they are the fastest and smallest, but changing one means recompiling. Link-time parameters are constant data in a separate object file: the module's code can be delivered as a binary library and linked with a project-specific configuration. Post-build parameters live in a separate configuration data structure that can be replaced after the code is built. Post-build loadable means the configuration sits in its own flash region and can be re-flashed without changing the code, for example to update a communication matrix late in the project. Post-build selectable means several configurations are linked into the image and one is selected at start-up, for example by a variant-coding value, so that one binary serves several vehicle variants.

The same idea applies above the BSW as variant handling: elements of the model (a port, a connector, a component) can carry conditions on system constants, resolved either before code generation (pre-build) or at start-up (post-build). It is how one ECU software supports left- and right-hand drive, or a camera ECU with four or five cameras, without separate code bases.

Pitfall

Post-build loadable configurations must match the code they are loaded with. The code checks a compatibility hash or version at start-up, and if the check is missing or ignored, a new communication matrix flashed onto old code silently reads its tables with the wrong layout. When a post-build update "breaks CAN", check the configuration and code versions before anything else.

7.4The tools and who makes them

The toolchain is a large part of a project's cost and of its daily friction. On the vehicle level, architecture tools such as Vector PREEvision or dSPACE SystemDesk model the E/E architecture and export system descriptions. On the component level, Simulink with Embedded Coder generates component code and descriptions; Vector DaVinci Developer, ETAS ISOLAR-A or dSPACE SystemDesk edit component descriptions directly. On the ECU level, the configuration tools come with the BSW stacks: Vector DaVinci Configurator with MICROSAR Classic, Elektrobit EB tresos Studio with EB tresos AutoCore, ETAS ISOLAR-B with RTA-CAR (RTA-OS, RTA-RTE), and others such as Siemens Capital VSTAR or KPIT KSAR. MCAL vendors usually deliver their drivers with plug-ins for EB tresos, which became a de facto MCAL configuration tool. The Eclipse-based Artop platform underlies several of these tools, and open-source libraries exist for reading and writing ARXML from scripts.

Two practical facts are worth knowing. First, projects rarely change BSW vendor mid-life, because configuration, scripts, generated-code reviews and the team's knowledge are tied to one tool. Second, every serious project automates its toolchain with scripts: the tools have command-line modes and scripting APIs, and the build server runs them without a GUI.

7.5What goes wrong in ARXML-driven development

Most AUTOSAR integration bugs are model bugs. A version skew between two sides of an interface is the classic: one ECU was configured from drop 36 and the other from drop 37, and a signal moved, changed its scaling or its enumeration (the camera ECU chapter shows the gear "R = 7 versus R = 2" case, Camera ECU 3.5). Unit and scaling errors arise because ARXML values are in SI units with compu-methods that convert raw values; a factor of 1000 is easy to lose. Silent defaults come from parameters left at the tool's default: a COM timeout of zero means "no deadline monitoring", an initial value of zero for a gear signal means "park". Hand edits to generated code are lost at the next generation. And merge conflicts in ARXML are hard, because the same element can be serialised in different orders by different tools; teams normalise files or merge with model-aware tools rather than with text diff.

Talk track

"Everything in AUTOSAR is a model instance stored as ARXML: components, system, ECU configuration and, for Adaptive, manifests. The OEM sends an ECU extract; the supplier configures the BSW against vendor module definitions, maps runnables to tasks, generates RTE, OS and BSW code and builds. Parameters are bound at pre-compile, link or post-build time, which decides how late a configuration can change. Most integration bugs are differences between models, so drops are diffed, not just regenerated."

8Adaptive: applications on a POSIX system

On the Adaptive Platform, an application is an ordinary POSIX process. What makes it "Adaptive" is that it is started, configured, supervised and connected by platform services, through standard C++ APIs and according to manifests. This chapter shows the platform as a whole, then follows one application from power-on to its first service offer.

8.1The platform and its functional clusters

The Adaptive Platform is specified as a set of functional clusters, each with a C++ namespace under ara:: (AUTOSAR Runtime for Adaptive applications), a specification and usually a daemon process that implements it. The AUTOSAR software architecture document of release R25-11 groups them as shown below. Most of the platform is therefore a set of cooperating processes, and an application uses a cluster through a library that talks to that cluster's daemon over inter-process communication.

Not every cluster is equally important day to day. For an application developer, Core (initialisation, Result and error types, instance specifiers), Execution Management, Communication Management, Log and Trace, Persistency and Platform Health Management are the ones you touch in every program. State Management is usually one project-specific process owned by the platform team. Diagnostics, Update and Configuration Management, Cryptography, the Intrusion Detection System Manager and the Firewall are mostly configured rather than called. Time Synchronization and Network Management run in the background. The newest clusters are worth recognising by name: the Raw Data Stream (R23-11) for streaming unstructured sensor data over TCP/UDP or IEEE 1722 without service serialisation, the Automotive API Gateway (R24-11) that gives non-AUTOSAR clients data-centric access to vehicle signals through the VISS protocol with the COVESA VSS catalogue, and Safe Hardware Acceleration and Remote Persistency (R25-11): a generic API for using hardware accelerators and a vehicle-wide store for configuration and coding data.

Beneath the clusters is the Operating System Interface. AUTOSAR does not specify its own OS for Adaptive; it requires a POSIX operating system (QNX, Linux, PikeOS, INTEGRITY and others are used) and restricts applications to the PSE51 profile of IEEE 1003.13 plus the C++ standard library, so that applications stay portable between operating systems. Platform implementations may use more of the OS. Since R25-11 the minimum language standard for the AUTOSAR code base is C++17.

Interesting detail

Clusters come and go, which tells you something about the standard. Signal-to-Service translation was a separate cluster until R19-11 and is now part of Communication Management's bindings; RESTful communication was dropped in R21-11; Identity and Access Management was removed as a cluster in R23-11, while access control remains a requirement that is now specified with the interfaces that need it (for example, State Management's interfaces are marked as access-controlled). When a document or a colleague lists "ara::iam", it predates R23-11.

8.2The application model: executables, processes, machines and clusters

Adaptive separates four things that a Linux developer would call "the program". An executable is the built binary, together with its description: which root software component it contains and therefore which ports it has. A process is a configured instance of an executable: with which arguments, environment, user and group, scheduling policy and priority, core affinity, resource group, start-up and termination timeouts, and in which function group states it should run. One executable can be configured as several processes, for example the same camera-preprocessing binary once per camera. A machine is one operating system instance, physical or virtual, with its network interfaces and its function groups. A software cluster is the unit of deployment and update: a set of executables, processes, manifests and data that are installed, updated and removed together by Update and Configuration Management (Section 10.5), and that can have its own diagnostic address.

The C++ side is deliberately small. Every application calls ara::core::Initialize() first and ara::core::Deinitialize() last; in between, platform objects are created with an ara::core::InstanceSpecifier, a path such as "RearViewApp/RootSwc/RearViewPPort" that names a port of the executable's root component and is resolved through the manifests at run time (Section 11.3). APIs return ara::core::Result<T> (a value or an error code, like std::expected) or ara::core::Future<T>, so applications can be written without exceptions, which many safety projects require; ValueOrThrow() exists for those who prefer exceptions.

8.3From power-on to the first service offer, step by step

The camera ECU chapter describes what Execution Management and State Management are for (Camera ECU 4.2). Here is what happens in time, from the moment the operating system is up to the moment the display application receives the first rear-view state. Step through the sequence.

After the boot chain (Linux 8.1) the kernel starts its init process, which launches Execution Management as the platform's initial process. EM reads the machine manifest and all execution manifests (in a vendor-specific, pre-processed form), and if authenticated start-up is configured, it checks the signatures of the executables it will start against a trust anchor, extending the chain of trust from secure boot into user space.

EM puts the machine function group (MachineFG) into its Startup state and starts every process configured for that state, in the order given by their execution dependencies: typically the logging daemon first, then the communication daemon with service discovery, persistency, PHM, time synchronisation, diagnostics and finally State Management. Each process is created with exactly the configured user, priority, affinity and resource limits.

A started process initialises and calls ReportExecutionState(kRunning) on its ara::exec::ExecutionClient. EM waits for this report within the configured start-up timeout; only then are processes that depend on it started. A process that does not report in time, or exits, makes the function-group transition fail, and EM reports the failure to whoever requested the transition.

State Management is itself a process started in the Startup state. Once running, it decides the target states of all function groups from its inputs (power mode from the safety MCU, vehicle state, diagnostic requests, errors reported by PHM), and requests the first transitions through EM's StateClient::SetState(): MachineFG to Running, and project function groups such as RearView to Standby.

For the transition, EM stops processes not configured for the new state (SIGTERM, then SIGKILL after the termination timeout) and starts those that are. The rear-view application's process starts, calls ara::core::Initialize(), creates its skeleton with its instance specifier (resolved through the service instance manifest), loads what it needs quickly, and reports kRunning. Heavy work, such as loading a neural network, should come after the report, with readiness published through a field.

The application's supervised entities begin reporting checkpoints to PHM: once per frame (alive supervision), from frame-in to result-out within a deadline (deadline supervision) and in the right order (logical supervision). PHM reports violations to SM, which can restart the process or move the function group to a degraded state, and PHM serves a hardware or external watchdog only while the platform is healthy (Functional safety 4.6).

The application calls OfferService(). The communication daemon registers the service instance and, for a SOME/IP deployment, starts the service-discovery phases on the network: an initial random wait, a few repetitions with doubling intervals, then cyclic offers (Section 9.4). Local clients on the same machine are informed through the local registry without waiting for the network.

The display application on another machine has been searching with StartFindService(). When the offer arrives, its handler creates a proxy and subscribes to the ViewState event group; the server acknowledges and sends the current value of fields immediately and events from then on. Only now does the display know whether the rear view is ready. In a well-tuned system this whole sequence, from EM start to first event, takes a few hundred milliseconds to a few seconds, dominated by process start-up and discovery timing.

Pitfall

Execution dependencies are not service dependencies. EM starts process B after process A reported kRunning, but that does not mean A's services are already offered or discoverable, and A may restart later while B keeps running. Applications must handle a service that appears late or disappears (with StartFindService and subscription-state handlers), rather than relying on start-up order. Start-up order is for platform processes, not for application logic.

8.4State Management and function groups

A function group is a named set of processes with a set of states; every process declares in which states of which function groups it runs. The machine function group exists on every machine with the states Off, Startup, Running, Shutdown and Restart; projects add groups for their functions, for example RearView with Off, Standby and Active, or Perception with Full and Degraded. Function-group states are what make a central computer change its behaviour: switching Perception to Degraded stops two processes and starts a reduced pipeline, without any application knowing about the others.

The split of roles is strict. EM is the mechanism: it knows how to start and stop processes for a state, but it never decides on its own to change a state (except at start-up). SM is the policy: it decides which state each group should be in, based on inputs it collects, and asks EM to perform transitions. AUTOSAR specifies SM's interfaces and some behaviour (for example how it reacts to PHM recovery requests, how it coordinates with network management and diagnostics, and since R25-11 how it suspends the machine to RAM and resumes it), but the actual state logic is project-specific code or configuration, and it is one of the most safety-relevant pieces of the platform because it decides what runs.

Why it matters

For a perception engineer, function groups are how degradation is implemented. If the front camera fails, the system does not "handle an exception"; SM receives the error, switches the perception function group to a state where the processes that need the front camera do not run, and the services they offered disappear. Downstream applications see services vanish and must react, which is why every client of a safety-relevant service needs a defined behaviour for "service not available".

8.5Platform Health Management in one paragraph

Platform Health Management is the Adaptive counterpart of the Classic watchdog manager, and its three supervision kinds are explained with an interactive figure in the functional-safety chapter (Functional safety 4.6). What is specific to Adaptive is the integration: applications create supervised entities and report checkpoints through ara::phm; PHM evaluates them against the timing and order configured in the manifest; failures are reported to State Management, which owns the recovery (restart a process, switch a function group, request a machine restart); and PHM triggers the watchdog only while supervision is healthy, so that a frozen platform, including a frozen PHM, leads to a reset by hardware. Health channels let applications report other conditions (a camera link down, a temperature limit) through the same path.

Talk track

"On Adaptive, EM is the first process: it reads manifests, starts the platform daemons and then State Management, and starts or stops application processes when SM requests a function-group state. Each process must report kRunning within its timeout. Applications offer and find services through ara::com, PHM supervises their checkpoints and reports violations to SM, which decides the recovery. EM is mechanism, SM is policy."

9ara::com and service-oriented communication

Communication Management is the cluster applications use most, and the one whose behaviour most often surprises them: services appear with a delay, subscriptions are lost after a server restart, callbacks run on threads nobody configured. This chapter shows what the generated C++ looks like, how discovery and subscription work in time, and which binding carries the data.

9.1Proxies and skeletons: what the generator writes

A service interface is described in ARXML with its events, methods and fields and their data types (the elements are explained in Camera ECU 5.2). From it, the ara::com generator of the platform vendor produces two C++ classes per interface. The proxy is the client's view: an object with one member per event (to subscribe and read samples), per method (to call it and get a future) and per field (get, set, notifications). The skeleton is the server's view: an abstract class whose methods the application implements, with members to send events and update fields. Underneath both, generated binding code serialises the data for the chosen transport and talks to the communication daemon.

The rear-view service skeleton, simplified (class and method names follow the ara::com specification; exact signatures differ slightly between releases and vendors):

#include "rearview/rearviewservice_skeleton.h"   // generated from the service interface

class RearViewService final : public rearview::skeleton::RearViewServiceSkeleton {
public:
    using RearViewServiceSkeleton::RearViewServiceSkeleton;

    // method: called by the binding when a client invokes SetViewMode
    ara::core::Future<SetViewModeOutput> SetViewMode(const ViewMode& mode) override {
        ara::core::Promise<SetViewModeOutput> p;
        p.set_value(SetViewModeOutput{ApplyMode(mode)});
        return p.get_future();
    }
};

int main() {
    ara::core::Initialize();
    RearViewService svc{ara::core::InstanceSpecifier{"RearViewApp/RootSwc/RearViewPPort"},
                        ara::com::MethodCallProcessingMode::kEventSingleThread};
    svc.ViewState.Update(ViewState{false, 0});      // field: initial value before offering
    svc.OfferService();
    ara::exec::ExecutionClient{}.ReportExecutionState(ara::exec::ExecutionState::kRunning);

    while (Running()) {
        auto sample = svc.ViewState.Allocate();     // event memory owned by the binding
        if (sample) { *sample.Value() = ComputeViewState(); svc.ViewState.Send(std::move(sample.Value())); }
        WaitForNextGearChange();
    }
    svc.StopOfferService();
    ara::core::Deinitialize();
}

Allocate() is worth noticing: the binding provides the memory for the sample, which lets a shared-memory binding write the event directly into memory the subscribers can read, without a copy. For small events it does not matter; for a few hundred kilobytes of object list it does. Camera frames themselves still do not go through events (Camera ECU 4.4, Section 13.4).

9.2Finding a service and subscribing

A client has two ways to find a service. FindService(spec) is a one-shot query: it returns the handles of all instances known at this moment, possibly none, because the offer may simply not have arrived yet. StartFindService(handler, spec) registers a continuous search: the handler is called whenever the set of matching instances changes, including when an instance disappears. Robust clients use StartFindService, create the proxy in the handler, and destroy or mark it unusable when the set becomes empty.

using rearview::proxy::RearViewServiceProxy;
std::optional<RearViewServiceProxy> proxy;

auto search = RearViewServiceProxy::StartFindService(
    [&](ara::com::ServiceHandleContainer<RearViewServiceProxy::HandleType> found,
        ara::com::FindServiceHandle) {
        if (found.empty()) { proxy.reset(); OnServiceLost(); return; }
        proxy.emplace(found.front());                       // or Create(handle) in newer releases
        proxy->ViewState.SetReceiveHandler([&] {               // runs on a binding thread
            proxy->ViewState.GetNewSamples([](auto s) { OnViewState(*s); });
        });
        proxy->ViewState.Subscribe(4);                     // cache at most 4 unread samples
    },
    ara::core::InstanceSpecifier{"DisplayApp/RootSwc/RearViewRPort"});

// a method call returns a future; never block in a receive handler on it
auto f = proxy->SetViewMode(ViewMode::kTopView);
if (f.wait_for(std::chrono::milliseconds(100)) == ara::core::future_status::ready) { auto r = f.GetResult(); }

Three details trip people up. The sample count passed to Subscribe is the size of the client-side cache: if the application reads more slowly than events arrive, the oldest unread samples are dropped, which is right for state and wrong for events that must not be lost. The receive handler runs on a thread of the binding, not on the application's thread, so it must be short and thread-safe. And subscription state is a separate thing from discovery: after a server restart the service is found again, but the subscription must be re-established, which the binding does automatically only if it notices the restart (Section 9.4). A subscription-state change handler tells the application when it is really receiving.

9.3Threads, processing modes and where your callback runs

On the server side, the skeleton's MethodCallProcessingMode decides how incoming method calls are executed. With kPoll, calls are queued and executed only when the application calls ProcessNextMethodCall(), so the application controls exactly when and on which thread its methods run; this is the deterministic choice for a cyclic processing loop. With kEvent, the binding calls the method implementation from its own threads as soon as a call arrives, possibly concurrently, so the implementation must be thread-safe. kEventSingleThread is the same but serialised, one call at a time. On the client side, events can be polled with GetNewSamples() from the application's own loop or pushed through receive handlers.

The choice matters for timing analysis and for safety: polling makes the application's timing independent of the network and of how many clients call, while event-driven processing gives lower latency but lets external load reach into the application's threads. Perception pipelines that run at the camera frame rate usually poll inputs at the start of each frame, which is the Adaptive equivalent of Classic's implicit communication: one consistent snapshot per cycle.

9.4Service discovery in time

The camera ECU chapter introduces SOME/IP service discovery and its messages (Camera ECU 5.3). The timing parameters deserve a closer look, because they decide how long a client waits for a service at start-up and how long it takes to notice that a server has gone. A server goes through three phases after OfferService(): an initial wait of a random time between a configured minimum and maximum (so that ECUs waking up together do not all transmit at once), a repetition phase in which it sends the offer a configured number of times with intervals that start at a base delay and double each time, and a main phase with an offer every cyclic offer delay. Each offer carries a TTL: clients consider the instance valid for that long after the last offer they received. A client that starts searching also has an initial wait and repetition phase in which it sends FindService messages; a server that receives one answers with a unicast offer after a short request-response delay. Each SD message also carries a reboot flag and a session counter; a restarted server starts with the flag set and the counter at one, which tells its partners that their subscriptions are lost.

Two lessons come out of the figure. First, a client that starts after the server's repetition phase and does not send FindService waits for the next cyclic offer: up to a full cyclic offer delay, typically one or two seconds. With FindService it learns of the service within the request-response delay, which is why clients should search actively at start-up. Second, the TTL is a slow failure detector: with a 1 s cyclic offer and a 3 s TTL, a crashed server is noticed between 2 and 3 seconds after the crash, depending on when the last offer was sent. That is far too slow for a safety function. Fast failure detection belongs at the application level, with alive counters and timeouts on the data itself (E2E, Functional safety 4.4), not with discovery parameters, and the server should send StopOfferService on an orderly shutdown so that clients learn at once.

Numbers

SOME/IP-SD uses UDP port 30490, usually with a multicast group per VLAN. TTLs are in seconds (24 bits; 0xFFFFFF means "until the next reboot"); a TTL of zero is a stop-offer or a negative acknowledgement. Typical vehicle configurations use an initial delay of 0 to 100 ms, a repetition base delay of 10 to 50 ms with 2 to 4 repetitions, and a cyclic offer delay of 1 to 2 s with a TTL of two to three cycles.

9.5Bindings: SOME/IP, DDS, IPC and signals

The application code above contains no protocol. The protocol is chosen per service instance in the service instance manifest, and the generated binding implements it. AUTOSAR specifies the SOME/IP binding (the default for communication between ECUs, interoperable with Classic and with non-AUTOSAR implementations such as vsomeip), a DDS binding (mapping events to DDS topics with QoS, which helps when the partner is a DDS or ROS 2 system, Networks 8.3), IPC for communication on the same machine (often shared memory with a notification channel, implemented by the platform vendor), and signal-based bindings that map a service to signal PDUs so that an Adaptive application can exchange data with a classic CAN or Ethernet PDU world directly (Section 12.2). End-to-end protection can be applied to events, methods and fields in the binding, configured in the manifest, and the E2E check result is delivered with each sample.

The Raw Data Stream cluster sits beside these bindings for data that has no structure worth describing as a service: a byte stream to or from a sensor, a radar's point data, or a recording interface. It provides a socket-like API with platform-managed configuration and security, rather than serialisation and discovery.

Pitfall

Serialisation is not self-describing (Camera ECU 5.4), and SOME/IP's interface version only protects you if someone increments it. A server whose event payload gained a field, deployed with the same major version, will be "compatible" according to discovery and will feed every older client shifted bytes. Change the major version for incompatible changes, use the minor version for compatible ones, and make interface versions part of the release checklist.

Talk track

"ara::com generates a proxy for clients and a skeleton for servers from the service interface. Clients should use StartFindService, because services appear late and disappear; subscriptions have a sample cache and a state; receive handlers run on binding threads. The transport is chosen in the manifest: SOME/IP between ECUs, IPC locally, DDS or signal-based bindings for other worlds. Discovery timing decides start-up delay and how slowly a crash is noticed, so safety-relevant liveness is checked on the data, not by service discovery."

10Platform services

Beyond execution and communication, the Adaptive Platform provides the services every application on a central computer would otherwise reinvent: storage, diagnostics, logging, cryptography, intrusion detection, updates, time and network management. Each is a daemon with a C++ API and a manifest-driven configuration. This chapter says what each does, how an application uses it, and where the deeper material lives.

10.1Persistency

Persistency gives an application two kinds of storage that survive power cycles: key-value storages for small typed values (calibration offsets, user settings, counters) and file storages for larger data (a map tile, a learned parameter set). Both are opened by instance specifier, so the application never knows the path or the file system: ara::per::OpenKeyValueStorage(spec) returns a handle with GetValue<T>(key), SetValue(key, value) and SyncToStorage(). The configuration in the manifest decides the location, the maximum size, and the protection: checksums, redundant copies (for example two-out-of-three) and what to do when corruption is detected. Persistency also handles updates: when Update and Configuration Management installs a new version of an application, the manifest says for each storage whether to keep, overwrite or migrate the old data, and the old state can be restored on rollback.

Remote Persistency (R25-11) extends the idea beyond one machine: a global store for configuration and coding data that applications on different ECUs can use through the same concepts, which matters when vehicle-level configuration (variant coding, feature activation) must be consistent across the car.

Pitfall

Writing to a key-value storage every frame. SetValue changes a cached copy; SyncToStorage writes flash, and flash wears out after a limited number of erase cycles per block. Persist on meaningful events (end of calibration, shutdown) and let Persistency's configuration bound the write rate.

10.2Diagnostics

The Diagnostic Manager (ara::diag) is the UDS server of an Adaptive machine, reachable over DoIP: it handles sessions and security access, routes data-identifier reads and writes and routine controls to the applications that implement them, keeps the event memory with diagnostic trouble codes and their snapshot data, and, since R25-11, handles SOVD (the HTTP/REST-based service-oriented vehicle diagnostics of ISO 17978) natively alongside UDS. Each software cluster can have its own diagnostic address and server instance, so an update of one cluster brings its own diagnostic description. How UDS, DTCs and diagnostic workflows work is the subject of the production integration and diagnostics chapter; the camera ECU chapter covers the camera-specific services (Camera ECU 10).

10.3Log and Trace

Applications log through ara::log: create a logger with a four-character context identifier, then stream values into it, logger.LogInfo() << "frame " << n << " latency " << ms;. The output follows the DLT protocol (originally from the GENIVI/COVESA community and the Classic Dlt module), so logs from Classic and Adaptive ECUs end up in the same tools with ECU, application and context identifiers. Log levels per context can be changed at run time from a tester. The cost of logging is mostly in formatting and transport; DLT supports non-verbose mode, where only a message identifier and raw arguments are sent and the text is added from a description file on the tester side, which reduces both bandwidth and CPU.

10.4Security: cryptography, intrusion detection, firewall and access control

Cryptography (ara::crypto) gives applications cryptographic primitives (hashing, MACs, signatures, encryption, random numbers), key management and X.509 certificate handling, without giving them the keys. Keys live in key slots managed by the crypto daemon, often backed by a hardware security module; an application refers to a key by slot and asks for an operation, so a compromised application cannot read key material. The API was reworked substantially in R25-11, so check which release your stack implements before copying examples.

The Intrusion Detection System Manager collects security events reported by platform clusters and applications (a failed authentication, a firewall drop, an unexpected diagnostic session), qualifies and rate-limits them, and forwards them to a reporter that sends them to the OEM's vehicle security operations centre, which is how the monitoring required by UN R155 is implemented on the vehicle side (Functional safety 9.7). The same concept exists in Classic as the IdsM module. The Firewall (R22-11) filters inbound traffic against configured rules, so that a machine accepts only the communication its manifests describe.

Access control answers "may this process use this service or platform interface?". The platform knows each process's identity because Execution Management started it, and the manifests state which ports and interfaces each process may use, so the communication daemon and the cluster daemons can enforce access. Until R22-11 this was the Identity and Access Management cluster; since R23-11 access control is specified with the interfaces themselves. In practice it is often implemented with operating-system mechanisms (separate user IDs, QNX abilities, Linux capabilities and mandatory access control) configured from the manifests.

10.5Update and Configuration Management

Update and Configuration Management (UCM) is the package manager of an Adaptive machine: it installs, updates and removes software packages, each containing one software cluster with its executables, data and manifests, and keeps a record of what is installed. A package is transferred over ara::com into UCM's local repository, authenticated, processed (unpacked and installed alongside the running version), then activated, which involves State Management restarting the affected function groups, verified, and finally either committed or rolled back. Vehicle UCM (V-UCM, separated from UCM in R23-11) coordinates a campaign across several machines and ECUs: it receives the vehicle package from the OTA client, checks vehicle state and driver consent, distributes packages to each machine's UCM and to flashing adapters for Classic ECUs, and activates them together. The process of over-the-air updates and its regulation (UN R156) belong to the production integration and lifecycle chapter.

10.6Time, network management and the newest clusters

Time Synchronization (ara::tsync) provides time bases synchronised across the vehicle, typically with gPTP over Ethernet (Calibration and fusion 4.4), and tells applications whether a time base is synchronised and how good it is. For sensor fusion this is not optional: a camera timestamp in one ECU's clock and a radar timestamp in another's must be compared in one time. Network Management (ara::nm) coordinates bus sleep and partial networks with the rest of the car, so the machine keeps the network awake only while it needs it (Networks 12.4). The Automotive API Gateway lets non-AUTOSAR clients, such as an app framework or a cloud connector, read and write vehicle signals named in the COVESA Vehicle Signal Specification through VISS v2 over HTTP, WebSocket or MQTT, while the gateway uses ara::com towards the vehicle internals (Section 12.3). Safe Hardware Acceleration standardises how applications use accelerators such as GPUs and NPUs through a generic API, a long-standing gap for perception software that so far used vendor APIs directly.

Talk track

"Platform services are daemons with ara:: APIs and manifest-driven configuration: persistency with redundancy and update handling, a diagnostic server with UDS and SOVD, DLT logging, crypto with keys kept in slots, an intrusion detection manager and firewall, UCM for installing and rolling back software clusters, plus time sync and network management. Applications use them by instance specifier and never see paths, keys or sockets."

11Manifests and the Adaptive toolchain

Adaptive replaces much of Classic's compile-time configuration with manifests: ARXML descriptions that are processed at integration time and read by the platform at run time. They are where an application's binary meets a particular machine, and they are where most "it compiled but it does not work" problems on Adaptive are found.

11.1Which manifest says what, and when it is bound

The camera ECU chapter lists the three manifest kinds (Camera ECU 4.3). The execution manifest describes executables and processes: how to start each process and in which function-group states. The service instance manifest describes how each port of each process is deployed: which service instance, over which binding, with which identifiers, endpoints, event groups and E2E settings. The machine manifest describes the machine: its function groups and states, network interfaces and VLANs, resource groups, time bases, and the platform's own configuration. Application design data (the component, its ports and the service interfaces) is described separately and is independent of any machine.

The separation follows the binding times. The interface is bound at compile time: the proxy and skeleton code is generated from it, and changing it means recompiling. The deployment is bound at integration time: the same binary can be deployed with SOME/IP between machines or IPC on one machine, with instance 1 in one vehicle and instance 2 in another, by changing manifests only. Some things are bound at run time: which of several offered instances a client uses, which processes run in the current state.

A simplified execution manifest for the rear-view process, using the element names of the AUTOSAR manifest specification (many mandatory elements are omitted for readability):

<PROCESS>

    <STATE-DEPENDENT-STARTUP-CONFIG>
      <FUNCTION-GROUP-STATE-IREFS>            <!-- runs in RearView.Standby and RearView.Active -->
        <FUNCTION-GROUP-STATE-IREF> … RearView … Standby </FUNCTION-GROUP-STATE-IREF>
        <FUNCTION-GROUP-STATE-IREF> … RearView … Active  </FUNCTION-GROUP-STATE-IREF>

</PROCESS>

11.2From ARXML to code, packages and a running machine

The Adaptive flow has two halves. At design and build time, application developers describe service interfaces, data types and their application component, the ara::com generator produces proxies, skeletons and binding code, and the application is compiled and linked with the platform libraries, usually with CMake or Bazel in a cross-compiling environment (Build and containers 7.6). At integration time, an integrator combines the applications' descriptions with the machine design: processes, function groups, deployments, network endpoints and SD parameters. The vendor's tooling validates the whole model (are all required ports mapped, do IDs collide, are the versions consistent?) and converts the manifests into the platform's run-time format, often JSON or a binary format, because parsing ARXML on the target at every start would be slow. Executables, run-time manifests and data are then packed into software packages for UCM or into the file-system image of the machine.

The commercial platform stacks come with their own tools: Vector MICROSAR Adaptive with DaVinci tooling, Elektrobit EB corbos AdaptiveCore with EB corbos Studio, ETAS RTA-VRTE with its tooling, and others. AUTOSAR also publishes a demonstrator implementation of the Adaptive Platform for its members, which is used to validate the specifications rather than in production.

11.3Following one instance specifier through the files

The single most useful debugging skill on Adaptive is to follow one port from the code to the network. In the code, the skeleton is constructed with the instance specifier "RearViewApp/RootSwc/RearViewPPort": executable, root component prototype, port. At run time the binding asks the platform which deployment belongs to that specifier for this process; the answer comes from the processed service-instance-to-port-prototype mapping, which points to the provided SOME/IP service instance (instance 1), which references the service interface deployment (service 0x4A10, event 0x8001, UDP), the SD server configuration (timing) and the network endpoint (IP address and VLAN of the machine). Only then can OfferService() put the right bytes on the right network.

Pitfall

The symptoms of a broken chain are indirect. A typo in the specifier string throws or aborts at start-up (good, at least visible). A missing mapping can make the skeleton fall back to nothing, so OfferService() succeeds and nothing appears on the network. A wrong instance ID or a minor-version mismatch makes client and server both healthy and never connected. When a service does not appear, check in this order: is the process running and did it report kRunning; is there a mapping for this process and port; what does Wireshark's SOME/IP-SD dissector show on the VLAN (offer present, with which service, instance, version and endpoint?).

Talk track

"Interfaces are bound at compile time through generated proxies and skeletons; deployment is bound at integration time through manifests; instance selection and which processes run are decided at run time. The code only knows an instance specifier; the service-instance-to-port mapping, the service instance and the interface deployment in the manifests turn it into service and instance IDs, endpoints and SD timing. Most Adaptive integration bugs are a broken link in that chain."

12Interoperability: Classic, Adaptive and everything else

No vehicle runs one platform. Classic ECUs speak signals, Adaptive machines speak services, a Linux application may speak plain SOME/IP or DDS, and an app in the cockpit wants vehicle data through yet another API. Interoperability is where these meet, and it works only when both sides were generated from one description of the interface.

12.1Classic and Adaptive over SOME/IP

SOME/IP and its service discovery are part of the Foundation standard, so both platforms implement the same protocol. On a Classic ECU, the role of the communication daemon is played by a set of BSW modules: the service discovery module (Sd) sends and receives offers, finds and subscriptions and opens or closes the routing paths for event groups; the SOME/IP transformer serialises and deserialises the payload in the RTE's transformer chain (Section 4.4); the socket adaptor (SoAd) maps PDUs to UDP and TCP sockets of the TCP/IP stack and adds or strips the SOME/IP header; the PDU router connects them to COM or directly to the RTE. A Classic server therefore offers a service whose events are, internally, PDUs sent through a socket connection, and an Adaptive client cannot tell the difference.

The precondition is that both sides agree byte for byte: service and instance IDs, method and event IDs, event-group membership, interface versions, serialisation settings (byte order, length-field sizes, alignment), transport protocol, and E2E profile and data ID. In practice this works when one model is the source of truth: the service interface and its SOME/IP deployment are described once in the vehicle model, exported into the Classic ECU extract and into the Adaptive machine's manifests, and both sides are generated from it. It breaks when one side is hand-configured from a spreadsheet.

Interesting detail

Classic ECUs are much more constrained in what they can offer: no dynamic memory, so a variable-length array in an event must have a maximum size known at build time, and large messages need SOME/IP-TP segmentation with buffers sized for the worst case. Interface designers who come from the Adaptive side often define payloads that a microcontroller can only receive after its buffers are increased by an order of magnitude. Design cross-platform interfaces with bounded sizes from the start.

12.2Translating signals into services and back

Most of the car still produces signals in CAN frames; the central computer's applications want services. A signal-to-service translation sits between: it receives signal PDUs, collects the relevant signals and publishes them as events or fields of a service, and in the other direction turns method calls or field setters into signal values in PDUs. It runs in a gateway: today usually a zone controller with Classic AUTOSAR, or the central computer itself, where Adaptive's communication management can bind a service to signal PDUs directly. The networks chapter follows such a signal through a zone controller (Networks 8.5); here is what the translation must decide.

First, timing semantics: signals arrive cyclically whether they change or not, while services usually notify on change. Publishing every cyclic update as an event wastes bandwidth and CPU on the clients; publishing only on change hides the fact that the source is still alive. A common rule is "on change, plus at least every n ms", with the field's getter always returning the latest value. Second, validity: a signal can be invalid (a reserved value), timed out (no frame) or fail its E2E check, and the service must express each of these, typically with a status member per value rather than by silently freezing the last value. Third, aggregation: signals from several PDUs with different periods end up in one record, so the record's members have different ages, and a timestamp per member or per source is needed for anything time-critical. Fourth, end-to-end protection: the gateway terminates the CAN-side E2E check and must add its own protection on the service side, which means the gateway's translation is now part of the safety chain and must be developed to the corresponding ASIL. And fifth, latency: translation adds a gateway cycle; a gear change that takes 20 ms on CAN can easily take 40 ms to reach a service client.

Pitfall

A translation that publishes "last valid value" when the source times out. Downstream, an application sees a perfectly fresh-looking event with gear = D while the transmission controller has been silent for a second. Every translated value needs a validity or age indication, and timeouts must propagate as states, not disappear.

12.3Non-AUTOSAR partners

Software that does not use an AUTOSAR stack can still be a first-class participant if it speaks the protocol. On Linux or QNX, the open-source vsomeip library from the COVESA community implements SOME/IP and its service discovery, and code generators such as CommonAPI produce proxies and stubs from interface descriptions (Franca IDL), which can be derived from the ARXML. A navigation application in a Linux virtual machine can thus subscribe to the rear-view service of our example. DDS-based software, including ROS 2 nodes used in development, connects through Adaptive's DDS binding or through a bridge that maps services to topics. Android Automotive exposes vehicle data to apps through the Vehicle HAL, whose vendor implementation is typically a SOME/IP client or a bridge to the vehicle's services. Cloud connectors and app frameworks can use the Automotive API Gateway, which offers vehicle signals under their VSS names over VISS (Section 10.6).

Two rules keep this manageable. The non-AUTOSAR side must be generated or configured from the same interface model (serialisation, IDs, versions, SD timing), so the interface model must be exportable to the formats the other side uses. And non-AUTOSAR software is usually of lower integrity, so it should consume services through a defined boundary (a separate VM, a firewall rule, access control) and never be on the path of a safety function without an argument for it.

12.4Owning interfaces across platforms

Interoperability is mostly an organisational problem. The vehicle needs a service catalogue: every interface with an owner, a version, its consumers and its deployment. Interface changes follow rules: compatible extensions (a new event, an added method) raise the minor version and old clients keep working; incompatible changes (a changed type, a removed element) raise the major version, and the server offers both versions for a transition period or all consumers change together. Signal-based interfaces follow the same logic with the communication matrix. Without this, the most common failure is not a crash but two ECUs from different software releases that silently do not talk to each other in one vehicle variant.

Talk track

"Classic and Adaptive interoperate over SOME/IP: on Classic the Sd module, the SOME/IP transformer and the socket adaptor do what the communication daemon does on Adaptive. Signal-to-service translation in a gateway turns cyclic signals into service events and fields and must handle timing, validity, aggregation, E2E and latency explicitly. Non-AUTOSAR software joins with vsomeip, DDS bridges, the Vehicle HAL or the VISS gateway, and everything works only if all sides are generated from one interface model with disciplined versioning."

13High-performance computers: where it all runs

ADAS computers and central vehicle computers combine everything in this chapter on one board: an Adaptive (or similar) platform on a powerful system-on-chip, Classic AUTOSAR on safety cores, other operating systems in virtual machines, and the vehicle network. How these are arranged is decided by safety, start-up time, isolation and cost, and the arrangement shapes what an application engineer can and cannot rely on.

13.1Three typical arrangements

The embedded-compute chapter describes the hardware (Embedded compute 6.6, 6.7); here are the software arrangements that sit on it. Switch between them.

In the SoC plus external MCU arrangement, the SoC runs one operating system (QNX or Linux) with the Adaptive Platform and the perception applications, and a separate microcontroller runs Classic AUTOSAR. The MCU starts within milliseconds, owns the CAN interfaces and power control, supervises the SoC with a watchdog and question-answer protocol, and talks to it over SPI or Ethernet (Camera ECU 1.2). It is simple, well understood and still the most common design for camera and ADAS ECUs.

In the hypervisor plus safety island arrangement, a type-1 hypervisor partitions the SoC's application cores, memory and devices into virtual machines: for example a QNX VM with Adaptive for safety-relevant ADAS functions, a Linux VM for less critical services, and in a cockpit domain an Android VM for infotainment. Classic AUTOSAR runs on the real-time cores of a safety island inside the SoC (the Cortex-R5F MCU island of TI's TDA4 family and the Cortex-R52 safety island of NVIDIA's Orin are examples), which has its own clock, power and memory and can supervise the rest of the chip. Some designs still add an external MCU for the vehicle interfaces and the highest ASIL.

The central vehicle computer scales the same pattern: two or more SoCs, a multi-core microcontroller, an Ethernet switch with TSN, links to the zone controllers, and partitions that host functions from several former domains, sometimes including virtualised Classic ECUs (vECUs) that run a Classic stack as a guest in a VM. Redundancy between the SoCs and a defined degradation when one fails are part of the architecture.

13.2Hypervisors and mixed criticality

A hypervisor's job in a car is static partitioning, not cloud-style elasticity. CPU cores are usually assigned to VMs exclusively; memory regions are fixed and enforced by the second-stage MMU; devices are either passed through to one VM (with the IOMMU or SMMU restricting their DMA to that VM's memory) or shared through virtual devices (VirtIO) served by a driver VM. VMs communicate through shared-memory channels and virtual Ethernet, over which SOME/IP runs exactly as between ECUs, so moving a function between VMs or ECUs changes deployment, not code. Hypervisors used in vehicles include QNX Hypervisor, SYSGO PikeOS, Green Hills INTEGRITY Multivisor, Elektrobit's EB corbos Hypervisor, and Xen-based solutions; several are certified for use in ISO 26262 systems up to ASIL D.

The safety argument is freedom from interference between partitions of different ASIL: spatial (memory and devices), temporal (CPU time, but also shared caches, DRAM bandwidth and interconnect, which a hypervisor alone cannot fully isolate) and exchange of information (the channels between VMs). The functional-safety chapter treats these mechanisms (Functional safety 6.2, 6.3, 6.4). For an application engineer the consequence is concrete: the latency of your perception process can depend on how much memory bandwidth the Android VM is using, unless the platform partitions caches and bandwidth (Arm MPAM, cache colouring, memory bandwidth regulation) and you budget for the worst case.

Pitfall

"The hypervisor isolates everything" is not true for shared hardware resources. A GPU shared between the cockpit VM and the ADAS VM is a classic example: unless the GPU supports hardware partitioning or preemption with bounded latency, a long cockpit render job delays a perception kernel, and no VM boundary helps. Shared accelerators need their own scheduling and isolation argument.

13.3Where Classic lives on a big computer

Classic does three jobs on an HPC. It is the vehicle interface: CAN FD, LIN, wake-up lines, power and reset control, where its millisecond start-up and deterministic timing are needed before the SoC has finished booting. It is the supervisor: it watches the SoC's health, implements the last-resort safe state (for example "request the driver to take over and stop requesting braking"), and resets the SoC if it stops responding. And it hosts small, highly critical functions that must keep running when the SoC is rebooting, such as the brake-light logic in a zone controller or the final arbitration of actuator requests. Whether Classic runs on a separate MCU, on an in-SoC safety island or as a vECU is a trade-off between independence (a separate chip shares no clock, power or silicon with the SoC, which helps the dependent-failure analysis), cost and board space.

13.4A camera pipeline on the Adaptive Platform

The camera ECU chapter makes the key point that images do not travel through ara::com events (Camera ECU 4.4). The resulting design has two planes. The data plane carries frames: the camera framework of the operating system or SoC vendor captures frames from the deserialiser into DMA-capable buffers, the ISP, GPU and NPU process them by handle, and processes share them through shared memory with fences or semaphores (Edge AI 7.3, Linux 4.5). The control plane uses Adaptive: State Management decides which pipeline configuration runs, Execution Management starts the pipeline processes, PHM supervises frame-level checkpoints with deadline supervision, ara::com carries results (objects, free space, parking slots, camera health) to other applications and ECUs, Persistency holds calibration data, and Log and Trace records what happened.

The end-to-end timing chain crosses both platforms: exposure and readout in the camera, transport over the SerDes link, ISP, network inference, tracking, an ara::com event to the planning process, a SOME/IP message to the safety MCU or another ECU, Classic COM and RTE, and finally a CAN FD frame to an actuator. Each AUTOSAR element contributes configured periods and queuing delays, and the timing analysis of a function adds them up from the configuration, as in Section 6.3 and 9.4.

13.5Where the architecture is heading

The direction of travel is the software-defined vehicle: fewer, more powerful computers; zone controllers for I/O and power; services as the main way functions interact; and software updated throughout the vehicle's life. For AUTOSAR this means more Adaptive on central computers, Classic concentrated on zone controllers, safety islands and actuators, and more emphasis on the parts that make software replaceable: interface catalogues, update management, and diagnostics through SOVD. At the same time, open-source stacks (Eclipse S-CORE and other Eclipse SDV projects), vendor middleware and container-based deployment (Build and containers 10.5) are being tried alongside or underneath Adaptive. Whatever wins on the central computer, the vehicle network, the Classic ECUs, SOME/IP and the methodology of describing interfaces once and generating everything from them will remain the context in which it has to work.

Talk track

"A typical ADAS computer runs Adaptive on QNX or Linux on the SoC and Classic on a safety MCU or a safety island; bigger computers add a type-1 hypervisor that statically partitions cores, memory and devices into VMs of different criticality, with SOME/IP over virtual Ethernet between them. Classic keeps the vehicle interface, supervision and the last-resort safe state. Camera frames stay in zero-copy buffers; Adaptive handles start-up, states, supervision and the exchange of results."

QSelf-check questions

Core questions with short model answers; the chapter sections hold the depth. The second group checks understanding with "why" and "what if" questions rather than definitions.

Q.1Core questions

What is AUTOSAR and why does the industry use it?Basic

A partnership standard, founded in 2003, with three parts: a layered ECU software architecture with standard basic-software modules, a methodology where the whole system is described in ARXML and code is generated, and standard interfaces and protocols. It separates applications from hardware and network, so software can be reused, the infrastructure bought from specialised vendors, and ECUs from many suppliers integrated with the same files and tools: cooperate on standards, compete on implementation.

What are the differences between Classic and Adaptive AUTOSAR?Basic

Classic targets microcontrollers: C, static configuration of everything at build time, an OSEK-based OS, signal-based communication, whole-image flashing, proven hard real-time up to ASIL D. Adaptive targets POSIX SoCs: C++ ara:: APIs, processes with memory protection, service-oriented communication with discovery, manifests bound at integration and run time, and updates of individual software clusters. They coexist; Adaptive does not replace Classic.

Describe the layers of the Classic architecture.Basic

From the bottom: the MCAL with standard drivers for on-chip peripherals, usually from the chip vendor; the ECU abstraction layer, which hides board details such as external transceivers or memories; the services layer with OS, communication, memory, diagnostics and mode management; the RTE, generated per ECU, which connects components to each other and to the BSW; and the application SWCs on top. Complex device drivers may cut through the layers for special hardware or timing.

What is the RTE and what does it generate?Basic

The Runtime Environment is generated code, specific to one ECU. It implements every port connection (a variable, a protected buffer, an inter-core channel or a COM signal), the Rte_Read/Write/Call APIs, the callbacks from COM, and the task bodies that call runnables in the configured order. In the contract phase it emits a header per component so components can be developed before integration.

What is a runnable and what triggers it?Basic

A runnable is a C function of a software component, called by the RTE, that runs to completion. It is triggered by RTE events: timing events, data received or receive errors, operation invoked, mode switches, init, and completion of asynchronous calls. The integrator maps each event to an OS task and a position in it, which decides priority, order and latency.

Explain sender-receiver versus client-server communication.Basic

Sender-receiver distributes data: one sender to many receivers (or many to one), last-is-best for states or queued for events, with initial values and timeouts in the ComSpec. Client-server is a request with arguments and a response: many clients to one server, synchronous (caller waits, needs a category 2 runnable unless it becomes a direct call) or asynchronous (result collected later).

How does the AUTOSAR OS schedule tasks?Intermediate

Fixed-priority preemptive scheduling of statically configured tasks. Basic tasks run to completion and can share stacks; extended tasks can wait for events and need their own stacks. Tasks are activated by alarms, schedule tables, other tasks or category 2 ISRs. Shared data is protected with resources using the immediate priority ceiling protocol. Scalability classes add timing protection (SC2), memory and service protection (SC3) or both (SC4).

What is a schedule table and why use one instead of alarms?Intermediate

A schedule table is a periodic sequence of expiry points with offsets, each activating tasks or setting events. It expresses a fixed pattern of activations with deliberate offsets to spread load, and it can be synchronised to a global time or bus cycle, so tasks run at a defined time after data arrive. Independent alarms cannot express the pattern and cannot be synchronised as a group.

Walk through what happens when a CAN frame with a signal is received.Intermediate

The CAN controller stores it in a message buffer and interrupts. The CAN driver's ISR reads it and calls CanIf_RxIndication; CanIf maps hardware object and ID to an L-PDU, checks length and calls the PDU router; PduR routes it to COM (or CanTp, or a gateway). COM copies the I-PDU and, immediately or in its next main function, unpacks signals, checks update bits and invalid values, resets deadline monitoring, runs E2E checks and notifies the RTE. The RTE updates its buffer and triggers the data-received event; the task runs the runnable, which reads the value with Rte_Read.

What is a complex device driver and when would you write one?Intermediate

A BSW module allowed to access hardware and MCAL directly, with its own interrupts, that offers ports to the RTE or standard interfaces to other BSW. Use it for things the standard stack cannot do or not fast enough: a private SoC link over SPI, serializer control, microsecond-level timing, unsupported hardware. Keep it small, give periodic work a SchM main function and expose data through ports, so it does not become a hidden second OS.

What is ARXML and what is an ECU extract?Basic

ARXML is the XML serialisation of the AUTOSAR meta-model: components, interfaces, data types, system and network descriptions, ECU configuration and Adaptive manifests are all ARXML elements referenced by package paths. The ECU extract is the part of the OEM's system description relevant to one ECU (its components, frames, signals), which the OEM sends to the supplier as the contract for configuration and test.

Explain pre-compile, link-time and post-build configuration.Intermediate

They say when a parameter's value is fixed. Pre-compile: macros and constants, optimised by the compiler, change requires recompilation. Link-time: constant data in a separate object, so a module can be delivered as a library. Post-build: a separate configuration structure; loadable means it can be re-flashed in its own region without changing code, selectable means several sets are in the image and one is chosen at start-up, for example by variant coding.

Name the Adaptive functional clusters you use most and what they do.Basic

Execution Management starts and stops processes according to manifests and function-group states; State Management decides those states; Communication Management (ara::com) provides service-oriented communication; Persistency stores key-value and file data; Platform Health Management supervises checkpoints; Log and Trace logs in DLT format; Diagnostics is the UDS/SOVD server; UCM installs and updates software clusters; Crypto, IDSM and Firewall provide security; Time Synchronization and Network Management run in the background.

How is an Adaptive application started?Intermediate

The OS starts Execution Management as the first process. EM reads the manifests, puts the machine function group into Startup and launches platform daemons and State Management in dependency order, each of which reports kRunning. SM then requests function-group states; EM starts the processes configured for them with their configured user, priority, affinity and limits. The application initialises ara, creates skeletons and proxies from instance specifiers, reports kRunning within its timeout, offers its services and starts looking for others.

What is the difference between FindService and StartFindService?Intermediate

FindService returns the instances known at this moment, which may be none because the offer has not arrived yet. StartFindService registers a handler that is called whenever the set of matching instances changes, including when one disappears. Robust clients use StartFindService, create proxies in the handler and handle loss of the service.

Explain events, methods and fields in ara::com.Basic

Events are data pushed from server to subscribed clients; clients subscribe with a cache size and read samples by polling or in a receive handler. Methods are calls from client to server returning a future, or fire-and-forget. Fields are state with an optional getter, setter and change notification, so a new subscriber gets the current value immediately. Each has an ID and is deployed to a transport in the manifest.

What are manifests, and which kinds exist?Basic

ARXML configuration that binds application binaries to a machine at integration time. The execution manifest describes processes: start-up configuration, function-group states, dependencies. The service instance manifest describes deployments of ports: binding, service and instance IDs, endpoints, SD and E2E settings. The machine manifest describes the machine: function groups, network interfaces, resource groups, time bases. Tools validate and convert them into a run-time format read by the platform daemons.

How do Classic and Adaptive ECUs communicate?Intermediate

Through SOME/IP and SOME/IP-SD, which both implement from the Foundation standard. On Classic, the Sd module handles discovery and subscriptions, the SOME/IP transformer serialises data in the RTE's transformer chain, and the socket adaptor maps PDUs to sockets. Both sides must be generated from one interface and deployment model so that IDs, versions, serialisation and E2E settings match. Alternatively, a gateway translates signals into services.

What is signal-to-service translation and what makes it hard?Intermediate

A gateway that turns cyclic signals from PDUs into service events and fields and back. The hard parts are semantic: when to publish (on change, cyclic or both), how to express invalid, timed-out or E2E-failed signals, how to aggregate signals with different ages, how to re-protect data end to end (which puts the gateway in the safety chain), and the added latency of a gateway cycle.

Describe a typical software architecture of an ADAS high-performance computer.Intermediate

An SoC with application cores, GPU, NPU and ISP runs QNX or Linux with Adaptive (or comparable middleware) and the perception and planning processes; a safety MCU or an in-SoC safety island runs Classic for the vehicle buses, power, supervision and the safe state. Larger computers add a type-1 hypervisor that statically partitions cores, memory and devices into VMs of different criticality, communicating over shared memory or virtual Ethernet with SOME/IP. Frames stay in zero-copy buffers; services carry results.

Q.2Why and what if

Why does Classic configure everything before compilation, when that makes every change expensive?Why

Because a static system is analysable. With all tasks, priorities, buffers and messages known at build time, worst-case response times and memory use can be computed and shown for ASIL D, nothing can fail at run time for lack of memory, and the code can be optimised to plain variable accesses. The cost, regenerating and retesting for every change, is acceptable for functions that rarely change and must be proven.

What if two runnables in tasks of different priority share data through a plain global variable?What if

The RTE does not know about it, so it adds no protection. If the low-priority runnable is preempted in the middle of reading or writing a multi-word value, it sees a torn or inconsistent value; if the runnables are later mapped to different cores, there is a real data race. Declaring an inter-runnable variable or exclusive area lets the RTE choose the right protection, which costs nothing when none is needed.

Why would you choose implicit over explicit communication, and what does it cost?Why

Implicit communication gives every runnable of a task one consistent snapshot of its inputs, so a calculation that reads the same value twice cannot see two different values when a higher-priority task writes in between. It costs RAM for task-local copies, copy time at task start and end, and data that can be up to a task runtime older than with explicit access.

A signal's alive timeout is configured as 100 in a script-generated ARXML. What happens?What if

ARXML time values are in seconds, so the receiver waits 100 s before reporting the data as stale. If the sender stops, the application keeps getting "OK" with the last value for well over a minute. Configuration tools display milliseconds, but scripts must convert; review generated timeouts after tool changes.

Why are COM signals often processed deferred rather than immediately in the interrupt?Why

Unpacking signals, checking them and notifying the RTE takes time; doing it in the receive ISR lengthens interrupt latency for everything else and makes the CPU load depend on bus traffic. Deferred processing in a periodic COM main function bounds and schedules this work, at the cost of up to one main-function period of extra latency. Time-critical PDUs can still be configured for immediate processing.

What if you move a runnable to another core to balance load?What if

Every connector to components on the old core becomes an IOC channel with copying and locking, data-received events become cross-core activations, and implicit snapshots no longer cover data written on the other core. CPU load balances, but latency and analysis effort for the chain can grow. Partition along data flow, and re-check end-to-end timing.

Why does Execution Management not decide which processes should run?Why

Separation of mechanism and policy. EM must be generic and simple, because it is safety-relevant platform code: it executes transitions exactly as configured. Which state the system should be in depends on vehicle state, errors, diagnostics and project-specific rules, so that policy lives in State Management, which can be changed and reviewed separately.

What if an application loads a large neural network before reporting kRunning?What if

It may exceed its start-up timeout, so EM treats the start as failed and the function-group transition fails, often visible as a feature that never becomes available or a restart loop. Report kRunning once the process is alive and responsive, then load heavy resources and publish readiness through a field or a service that is offered only when ready.

A client starts 1.5 s after the server and does not send FindService. How long does it wait, and how would you improve it?What if

The server is in its main phase, so the client waits for the next cyclic offer: up to one cyclic offer delay, typically 1–2 s. If the client sends FindService, the server answers with a unicast offer after its request-response delay, a few to tens of milliseconds. Shorter cyclic delays also help but cost bandwidth and CPU on every ECU.

Why is SOME/IP-SD's TTL not a good failure detector for a safety function?Why

Because it is slow and coarse: a client notices a crashed server only when the TTL of the last offer expires, between TTL minus the cyclic delay and TTL after the crash, typically 2–3 s, and TTLs are in whole seconds. Safety functions need detection within their fault-tolerant time interval, which requires alive counters, E2E protection and timeouts on the data itself.

What if a server restarts within the TTL? Do clients keep receiving events?What if

The restarted server has lost all subscriptions. Its first SD message carries the reboot flag with a reset session counter, which tells clients it rebooted; a correct client implementation then re-subscribes, and events flow again. Without reboot detection, a client would believe its subscription is still valid and wait for events that never come until the TTL logic catches up.

Why can the same Adaptive binary use SOME/IP in one vehicle and IPC in another without recompiling?Why

The application code only uses the generated proxy or skeleton and an instance specifier. The binding is selected through the service instance manifest, which maps the port to a deployment; the vendor's binding libraries for both transports are linked in (or loaded), and the platform resolves the specifier at run time. The interface is bound at compile time, the deployment at integration time.

An Adaptive service compiles, starts and reports kRunning, but no client ever finds it. Where do you look?What if

Follow the instance specifier chain: is there a service-instance-to-port mapping for this process and port; does it point to the intended service instance; are service ID, instance ID and major/minor version as the client expects; is the network endpoint on the right interface and VLAN; is the firewall allowing SD and data traffic. Then capture on the VLAN and check SOME/IP-SD offers in Wireshark: if there is no offer, the problem is on the server side; if the offer is there with other IDs, it is the model.

Why do Classic ECUs struggle with service interfaces designed on the Adaptive side?Why

Classic has no dynamic memory: every variable-length array, string and message must have a maximum size known at build time, and large messages need SOME/IP-TP buffers sized for the worst case. Interfaces with unbounded or very large payloads, or many methods, can exceed an MCU's RAM. Cross-platform interfaces must be designed with bounded sizes.

What if a gateway publishes the last valid value when a translated signal times out?What if

Downstream clients receive fresh-looking data that describes an old state, for example "gear D" while the transmission controller is silent. They cannot detect the fault, so a safety mechanism downstream is bypassed. Translated values need validity or age information, timeouts must propagate as states, and E2E protection must be re-applied at the gateway.

Why do vehicle HPCs still use a separate MCU or safety island when the SoC is so powerful?Why

Start-up time, independence and determinism. The MCU is running within milliseconds, long before the SoC has booted, so it can answer the vehicle network and control power. It has its own clock, power and silicon, which supports the dependent-failure argument when it supervises the SoC and implements the safe state. And it runs Classic with proven hard real-time behaviour for the vehicle interfaces.

What does a hypervisor not isolate, and why does it matter for perception?Why

Shared hardware resources: last-level cache, DRAM bandwidth, the interconnect, and shared accelerators such as a GPU. A VM can slow another down through these without touching its memory. A perception process's latency can therefore depend on what the cockpit VM is doing, unless the platform partitions caches and bandwidth and the GPU supports bounded preemption, and timing budgets account for the worst case.

Why was Identity and Access Management removed as a cluster if access control is still needed?Why

Access control is cross-cutting: each platform interface or service must decide whether a caller may use it, based on the caller's identity known from Execution Management and permissions from the manifests. Since R23-11 AUTOSAR specifies this with the interfaces that need it rather than as a separate cluster, and implementations often rely on OS mechanisms (user IDs, abilities, capabilities) configured from the manifests.

The part of the system description relevant to one ECU, delivered by the OEM as the configuration contract.

Counter, data ID and CRC added by the sender and checked by the receiver to detect corruption, loss, repetition and delay of data end to end.

The Adaptive cluster that starts and stops processes according to manifests and function-group states; the platform's first process.
Functional cluster
A unit of the Adaptive Platform with an ara:: API and specification, usually implemented by a daemon.

A named set of Adaptive processes with states; each process declares the states in which it runs.
IOC
Inter-OS-application communicator: generated Classic OS code for communication between OS-Applications on different cores or partitions.

A path naming a port of an executable's root component, resolved through the manifests to a concrete service instance and binding.
Machine
One operating-system instance running the Adaptive Platform, physical or virtual, described by a machine manifest.

Adaptive deployment configuration in ARXML: execution, service instance and machine manifests.
MCAL
Microcontroller abstraction layer: standard drivers for on-chip peripherals, usually from the chip vendor.

A group of tasks, ISRs and data that the Classic OS protects as a unit (memory, timing, services); trusted or non-trusted.

Platform Health Management: Adaptive supervision of checkpoints (alive, deadline, logical) with recovery through State Management.
Port
A point of interaction of a software component, typed by a port interface; provide (P) or require (R).

Generated ara::com classes: the client's view of a service (proxy) and the server's base class to implement it (skeleton).

Runtime environment: per-ECU generated code that connects Classic components to each other and to the BSW and calls runnables from OS tasks.
Runnable
A function of a software component, triggered by RTE events and run to completion (category 1) or with wait points (category 2).

A Classic OS object: a periodic sequence of expiry points that activate tasks or set events at fixed offsets, optionally synchronised to a global time.
SchM
BSW scheduler: generated code that calls BSW main functions from OS tasks and implements BSW exclusive areas.

Gateway logic that maps signals in PDUs to service events, fields and methods and back.

The Adaptive unit of deployment and update: executables, manifests and data installed and removed together by UCM.

Service discovery for SOME/IP: offers, finds and event-group subscriptions with TTLs, on UDP port 30490.

The Adaptive cluster, project-specific in logic, that decides function-group states and requests transitions from EM.

The Classic unit of application design: ports, internal behaviour with runnables and events, and implementation.
Task
The unit scheduled by the Classic OS: basic (run to completion) or extended (can wait for events), with a fixed priority.
Transformer
A Classic module in the RTE's data path that serialises (SOME/IP, COM-based) or protects (E2E) data before COM.
UCM, V-UCM
Update and Configuration Management (per machine) and Vehicle UCM (campaign coordination across the vehicle).
Virtual function bus
The design-time abstraction in which all components are connected by one ideal bus, before they are mapped to ECUs.

COVESA's Vehicle Information Service Specification (an access protocol) and Vehicle Signal Specification (a catalogue of signal names), used by the Automotive API Gateway.
