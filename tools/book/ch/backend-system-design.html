Backend and distributed system design

How large backend systems are built and operated, and how to design one step by step. One photo-sharing service grows from a single server to millions of users; every component (load balancers, caches, CDNs, replicas, shards, queues, consensus, rate limiters, service mesh, tracing) is added only when a number shows it is needed. The same method then solves the classic designs: URL shortener, rate limiter, chat, news feed and file storage.

1The big picture: why backends become distributed systems

A backend starts as one program on one machine, and for many products that is the right design for years. It becomes a distributed system for three reasons only: one machine cannot do the work fast enough, cannot hold the data, or must not be the single thing whose failure stops the business. Everything in this chapter is a tool against one of those three limits, and each tool has a price.

1.1The running example, and the three limits of one machine

Our running example is a photo-sharing service. People sign up, upload photos with a caption, follow other people, and scroll a feed of the photos posted by the people they follow; they like and comment. On day one it runs on one virtual machine: a web application in Python, Go or Java, a PostgreSQL database on the same box, and the photo files in a directory on its disk. This is not a toy architecture. A modern server with 32 cores, 256 GB of RAM and NVMe disks handles thousands of requests per second for a service like this, and a single PostgreSQL instance serves many businesses with millions of customers.

The first limit is throughput. Each request costs CPU time (parsing, business logic, rendering JSON), and each database query costs disk reads, locks and CPU. When the service gets popular, requests arrive faster than one machine can finish them; queues form, and latency grows without bound (Section 10.2 shows why it grows so sharply near full load). The second limit is data size. Photos are large: a million uploads a day at one megabyte each is a terabyte a day, and no single disk keeps up with that for long. Metadata is smaller but also grows; at some point indexes no longer fit in memory and every query starts reading from disk. The third limit is availability. A single machine fails: a disk dies, the kernel panics, the cloud provider retires the host, someone deploys a bug. If everything runs on one box, every one of these events is a full outage. Customers notice, and some do not come back.

A distributed system answers these limits with two basic moves. Replication keeps copies of the same thing on several machines: copies of the stateless application (for throughput and availability), copies of the data (for read throughput, availability and latency near the user). Partitioning splits the data or the work so that each machine holds and handles only a part (for write throughput and data size). Caches, CDNs and read replicas are forms of replication; shards and partitions are forms of partitioning; queues split the work in time rather than in space. The hard part is that every copy can be out of date and every machine can fail independently, while the network between them can delay, lose or reorder messages. Most of this chapter is about living with that.

Why it matters

In a design discussion the question is never "should we use Kafka" but "which of the three limits are we hitting, by how much, and what is the cheapest tool that removes it". Every distributed component adds failure modes, operational cost and consistency questions. A design that adds Redis, Kafka and sharding to a service with 50 requests per second is not advanced; it is expensive and fragile. The skill is to know the numbers well enough to add each piece at the right time.

1.2A method for system design

System design problems are open: "design a photo-sharing service" has no single right answer. What separates a good design from a pile of boxes is a method that moves from the problem to the numbers to the components, and states the trade-offs on the way. The same method works in a long design review and in a 45-minute whiteboard discussion, where the reasoning matters more than the final picture. The architecture-level version of this method, for embedded and automotive systems, is in Software architecture 14.1; here it is applied to web-scale backends.

Requirements come first because they decide everything else. Functional requirements are the features in scope ("upload a photo, follow users, see a feed of followed users' photos, like"); say explicitly what is out of scope (search, direct messages, ads). Non-functional requirements are the numbers: how many users, how many requests, how fast (for example "feed loads in under 200 ms at p99"), how available (99.9 % or 99.99 %), how consistent ("a like count can be a few seconds stale; a payment cannot"). The read-to-write ratio is the single most useful number, because it tells you whether to optimise the read path or the write path.

Estimates turn the requirements into load: requests per second on average and at peak, storage per year, bandwidth, and the size of the working set. They are rough on purpose; the goal is the order of magnitude, which decides whether you need one database or fifty. Section 1.3 shows how to do them quickly.

API and data model make the problem concrete: the handful of endpoints (POST /photos, GET /feed?cursor=…, POST /follow), the entities (user, photo, follow edge, like) and, most important, the access patterns ("get the 20 newest photos of the people user X follows"). Access patterns decide the keys, the indexes and later the partitioning. API design itself is in Software architecture chapter 5; this chapter uses it.

High-level design draws the boxes: clients, load balancer, services, databases, caches, queues. Walk through one read and one write end to end, so that every box has a reason to exist. Deep dives are where the design is decided: pick the component that the numbers say is the bottleneck (the feed read path, the hot celebrity account, the database that outgrows one machine) and design it properly, including what happens when parts fail. The wrap-up states the trade-offs you made, what you would change at ten times the load, and what you would monitor.

Talk track

"Before drawing anything, let me pin down scope and scale. I'll assume 10 million daily users, each uploading a photo every ten days and viewing about 50 photos a day, so roughly 500 reads per write. That makes this a read-heavy system, so I'll optimise the read path first: a CDN for the image bytes, a cache for the feed, and the database mostly for writes. Let me check those assumptions with a quick estimate."

Pitfall

Starting with technology names ("we'll use Kafka, Cassandra and Kubernetes") before requirements and numbers. Reviewers read it as pattern-matching without understanding, and in a real project it produces systems whose complexity is not paid for by any requirement. Name a technology only after you can say which limit it removes.

1.3Back-of-the-envelope estimates

Estimates exist because the components in this chapter differ by orders of magnitude in what they can do, and because the order of magnitude of the load decides which ones you need. You do not need precision; you need to know whether a number is 10, 1,000 or 100,000. Two tools make this fast: a few conversion tricks and a ladder of latencies.

The conversion tricks: a day has 86,400 seconds, call it 105. So one million events per day is about 12 per second, and 100 million per day about 1,200 per second. Traffic is not flat: consumer services have a daily peak about two to three times the average (evenings, one time zone), and events such as a product launch add short spikes on top, so design for the peak, not for the average. Storage is events per day times size times 365 times the number of copies. Bandwidth is requests per second times response size; multiply bytes by 8 for bits, and remember that a server network card carries 10 to 25 Gbit/s, sometimes 100.

The latency ladder explains most design decisions in this chapter. Reading from memory is about a thousand times faster than reading from an SSD, which is why caches exist. A round trip inside a datacenter costs about half a millisecond, so a request that makes 20 sequential calls to other services has spent 10 ms in the network alone, which is why chatty microservices are slow and why calls should be batched or made in parallel. A round trip between Europe and the US East coast costs about 90 ms, which no engineering can reduce because it is the speed of light in fibre; that is why CDNs and multi-region deployments exist. And an index turns a 56 ms scan into a 0.1 ms lookup, which is why the data model and its indexes matter more than the choice of database product.

Now the estimate for the photo service. Assume 10 million daily active users; each uploads 0.1 photos per day (one every ten days) and views 50 photos. Uploads: 1 million per day, about 12 per second on average and 35 per second at a 3× peak. Views: 500 million per day, about 5,800 per second on average and 17,000 at peak. The read-to-write ratio is 500:1. If a photo with its resized variants takes 1 MB, storage grows by 1 TB per day, 365 TB per year for one copy; metadata (a row of about 500 bytes per photo) is only 180 GB per year. If each view downloads a resized copy of about 250 KB, the peak egress is 17,000 × 250 KB ≈ 4.3 GB/s, about 35 Gbit/s.

These few numbers already sketch the architecture. 35 uploads per second is nothing for one database primary, so the write path does not need sharding yet. 17,000 photo views per second and 35 Gbit/s of egress are far too much for an origin server, so the image bytes must come from a CDN. 365 TB per year of photos belongs in object storage, never in the database. The metadata fits on one PostgreSQL node with replicas for years. The interesting work is on the read path: building feeds fast for 17,000 views per second.

Numbers

Useful capacity rules of thumb, all order-of-magnitude: one app server handles 1,000 to 10,000 simple requests per second depending on the work per request; one PostgreSQL or MySQL primary handles thousands to tens of thousands of simple reads per second and a few thousand to about ten thousand small write transactions per second (more with batching); one Redis instance does about 100,000 operations per second (measured here: 108,000 GETs/s with 50 clients over loopback, 1.4 million/s with 16-command pipelining); one Kafka partition takes on the order of 10 MB/s of writes, a cluster scales with partitions. Memory per server: 64 to 512 GB; one NVMe SSD: about 3 GB/s and hundreds of thousands of random reads per second.

In practice

In a design discussion, write the estimate on the board as three or four lines and round aggressively (86,400 ≈ 100,000; 17,361 ≈ 20,000). Then use it: "35 writes per second, so one primary is fine; 20,000 reads per second, so I need caching and a CDN". An estimate that is not used to make a decision was wasted time.

2Growing the photo service step by step

Large systems are not designed in one go; they grow, and each component is added because a specific limit was hit. Walking through that growth is the best way to understand why each component exists, and it is also the best structure for a system design answer: start simple, then scale the part that breaks.

2.1Six stages, each triggered by a number

Figure 2.1 shows the photo service at six stages. Step through it and read the trigger for each stage: the number that made the previous design insufficient. The chapters after this one explain each component in depth; this section is the map.

Everything on one machine: the application, PostgreSQL and the photo files. This is correct for a prototype and for many internal tools. It handles on the order of a hundred requests per second for this workload, it is easy to debug, and there is no network between the code and the data. Its limits: one disk for all photos, one CPU budget for everything, and any failure is a full outage. Backups and a restore you have tested are the only availability measure.

The database moves to its own machine (or a managed service such as Amazon RDS or Cloud SQL), and photo files move to object storage (S3, Google Cloud Storage, or MinIO on premises). The trigger is resource contention and growth: the database wants all the RAM for its cache, the photos want terabytes of cheap storage, and the app wants CPU. Object storage also gives durability (copies in several data centres) without any work on your side. The app server now stores only the object key in the database row and generates URLs to the photo.

One app server is no longer enough (CPU at 70 % at the evening peak), and a deploy or crash takes the site down. Several identical app servers go behind a load balancer, which spreads requests and stops sending traffic to servers that fail their health checks. The precondition is that the app servers are stateless: no user session or uploaded file lives only in one server's memory or disk. Sessions move into a signed token or into Redis; uploads go straight to object storage. Now you can add servers for capacity and lose one without an outage.

Reads dominate (500 photo views per upload). Three tools absorb them. A CDN serves the image bytes from edge servers near the users, so the origin sees only cache misses. A Redis cache keeps hot rows and precomputed feeds in memory, so most reads never reach the database. Read replicas, asynchronous copies of the database, take the reads that still need SQL. Each tool brings a consistency question: the CDN and cache can serve stale data, and replicas lag behind the primary (Chapter 6).

Some work does not need to finish before the user gets an answer: creating thumbnails, pushing the new photo into followers' feeds, sending notifications, updating search indexes. Doing it inside the request makes the upload slow and makes it fail when any of those systems is slow. A queue or log (Kafka, SQS, RabbitMQ) takes an event "photo uploaded"; workers consume it at their own pace and retry on failure. The upload returns as soon as the database row and the event are stored (Chapter 9 shows how to store both safely).

Writes and data finally outgrow one primary: hundreds of millions of users, terabytes of metadata, tens of thousands of writes per second. The database is partitioned by user id into shards, each with its own leader and replicas (Chapter 7). A second region serves users on another continent with lower latency and survives the loss of a whole region; data is replicated between regions asynchronously, and each user's data has a home region. This is the stage where consistency models and consensus (Chapter 8) stop being theory.

Why it matters

The order matters as much as the components. Splitting out the database and making the app stateless are cheap and remove whole classes of problems; sharding is expensive, hard to undo and makes many queries harder. A good design postpones the expensive steps until a number forces them, and prepares for them cheaply (for example by putting user_id into every table's key early, so that sharding by user later is possible).

Pitfall

Microservices are not on this list. Splitting the code into many services is an organisational decision (many teams deploying independently), not a scaling step; a stateless monolith behind a load balancer scales horizontally just as well. Chapter 11 and Software architecture 4.4 discuss when splitting pays off.

2.2Stateless services and where the state goes

The one idea that makes horizontal scaling possible is to separate the code that computes from the places that remember. A stateless service keeps nothing between requests that another instance would need: any request can go to any instance, so you can add instances, remove them, restart them and replace them without anybody noticing. All state lives in systems designed to hold state: databases, caches, object storage, queues. Those are few, carefully replicated and carefully operated, while the stateless tier is many cheap copies that are replaced rather than repaired.

State has a habit of sneaking back into services. An in-memory session map, a local file cache, a WebSocket connection, a rate-limit counter in a local variable, a scheduled job that runs "on the server": each makes one instance special. Some of these are fine as optimisations (a local cache that can be lost), but anything that must be correct has to live in a shared store or be routed explicitly. Long-lived connections are the hardest case: a chat server holds the socket for a user, so it is stateful by nature, and the design must know which server holds which user (Section 13.3).

The same separation shows in how data is chosen. Each kind of state goes to the store that fits its access pattern: relational rows with transactions and indexes go to PostgreSQL or MySQL; large immutable blobs go to object storage; hot, rebuildable data goes to Redis; streams of events go to Kafka; full-text search goes to Elasticsearch or OpenSearch; analytics goes to a column store such as ClickHouse or BigQuery. This is sometimes called polyglot persistence. Its cost is that the same fact now exists in several places, and keeping them in agreement is a design problem of its own (Section 9.4).

Interesting detail

The phrase "pets versus cattle" comes from operations: pets are servers with names that you nurse back to health, cattle are numbered and replaced when sick. Stateless services make the app tier cattle. Databases remain closer to pets even in the cloud, which is why managed databases are popular: someone else does the nursing.

3Traffic in: DNS, load balancers, proxies, gateways and CDNs

Before a request reaches any code, it passes through a chain of components whose job is to find the right machine, spread the load, terminate encryption, reject bad traffic and answer from a cache if possible. Each layer can stop the request, and the earlier it is stopped, the cheaper.

3.1The path of one request

When the phone app opens the feed, it first resolves the API host name with DNS. A plain DNS answer maps a name to fixed IP addresses; a GeoDNS or latency-based DNS (Route 53, Cloudflare, NS1) answers with the address of the edge location or region nearest to the user, which is the first layer of load balancing and the main tool for steering traffic between regions. DNS answers are cached by resolvers for their TTL, so changes take seconds to minutes to take effect; DNS is good for coarse steering, not for reacting to a server that died a second ago.

The connection then goes to an edge server of a CDN, which terminates TLS close to the user (saving round trips to a far origin) and answers from its cache if it can. Requests it cannot answer travel to the origin, where a layer-4 load balancer spreads TCP connections across a fleet of layer-7 proxies, which parse each HTTP request and route it to an instance of the right service. Inside, services call each other and the data stores, often again through load balancers or a service mesh (Chapter 11). A response retraces the path, and may be stored in caches on the way back.

Interesting detail

Many large providers use anycast at the edge: the same IP address is announced by many data centres via BGP, and the internet's routing sends each user to a nearby one. It makes the edge resilient (a failed site withdraws its announcement) and removes the DNS TTL delay for edge failover. Cloudflare and Google's front ends work this way.

3.2Load balancers: L4 and L7, and how to pick a server

A load balancer exists to make many servers look like one: clients know one address, and the balancer chooses a healthy server for each connection or request. It also enables zero-downtime deploys (drain a server, update it, put it back) and absorbs server failures through health checks. There are two kinds, named after the network layer they understand.

A layer-4 balancer works on TCP or UDP connections. It sees IP addresses and ports, picks a backend when a connection opens, and forwards the packets of that connection there; it never parses HTTP. That makes it very fast and able to carry millions of connections (AWS Network Load Balancer, Google's Maglev, Linux IPVS, or hardware appliances). A layer-7 balancer terminates the connection and reads each HTTP request: it can route /api/feed to one service and /api/upload to another, retry an idempotent request on another backend, add headers, compress, and balance individual requests over long-lived HTTP/2 or gRPC connections (Envoy, NGINX, HAProxy, AWS Application Load Balancer). The price is CPU per request and one more TLS termination. Large deployments use both: L4 in front for raw scale, a fleet of L7 proxies behind it for the smart work.

How the balancer picks a server matters more than it seems, because it decides how evenly the queues on the servers fill. Round robin sends requests in turn and is fair only if all requests cost the same. Random is simple and needs no shared state. Least connections (or least outstanding requests) sends to the least busy server, but needs an accurate global view. Power of two choices picks two servers at random and sends to the less busy one; it needs only local information and is surprisingly close to the best. Figure 3.2 shows a simulation of ten servers.

The result is worth understanding, because it reappears in Section 10.2. With random assignment, some servers get unlucky streaks and build long queues while others sit idle; the tail latency is dominated by those unlucky queues. Checking just two choices avoids the worst queues almost every time, which is why power of two choices is the default in Envoy, NGINX (random two least_conn) and many RPC libraries: it gets most of the benefit of least-loaded without needing an exact global view, which is impossible when many balancers share one fleet.

Health checks close the loop. An active check calls an endpoint such as /healthz every few seconds and removes a server after a few failures; a passive check (outlier detection) removes a server that returns errors on real traffic. A health endpoint should check what the server needs to serve requests, but not every dependency: if the health check fails whenever the database is slow, the balancer removes every server at once and turns a slowdown into an outage. When a server is removed for a deploy, connection draining lets in-flight requests finish before it stops.

Pitfall

Sticky sessions (always sending a user to the same server) are a sign that the app keeps state in memory. They make scaling and deploys uneven (a removed server logs out its users) and should be replaced by a shared session store. Stickiness is legitimate only as a performance optimisation for local caches, or for long-lived connections such as WebSockets, where it is a property of the connection anyway.

Interesting detail

gRPC and HTTP/2 multiplex many requests over one long-lived TCP connection. An L4 balancer picks a backend once per connection, so all requests of a client stick to one server for hours, and new servers added by autoscaling get no traffic. That is why gRPC needs L7 balancing (a proxy such as Envoy, or client-side balancing in the gRPC library) or periodic connection recycling.

3.3Reverse proxies and API gateways

A reverse proxy sits in front of servers and acts on their behalf; the client never talks to the servers directly. That position makes it the natural place for work that every service needs and none should implement: TLS termination with certificate management, HTTP/2 and HTTP/3 to clients while speaking simple HTTP/1.1 to the app, compression, buffering slow clients (so that a phone on a bad network does not hold an app worker for seconds), serving static files, and caching. NGINX in front of a Python or Ruby application is the classic example; the Python chapter 13.1 shows why a WSGI or ASGI server needs one.

An API gateway is a reverse proxy with API-level features: authentication (verify a JWT or OAuth token once at the edge, pass the user id inward), authorisation coarse checks, per-client rate limits and quotas, request validation, routing by path or version to different services, request and response transformation, and API keys and analytics for external developers. Products include Kong, Apigee, AWS API Gateway, and Envoy-based gateways. A backend for frontend (BFF) is a variant: one gateway per client type (mobile, web) that also aggregates calls, so the phone makes one request to load a screen instead of six.

Pitfall

The gateway attracts business logic ("just add this check here"), and after a year it is a monolith in disguise that every team must change and that nobody owns. Keep gateways to cross-cutting concerns; business rules belong in services.

3.4CDNs: serving bytes from near the user

A content delivery network is a large, shared fleet of caching reverse proxies in hundreds of locations (Cloudflare, Akamai, Fastly, CloudFront). It exists because of two numbers from Figure 1.2: the speed of light makes a far origin 100 to 300 ms away, and the photo service's 35 Gbit/s of image egress would need a large origin fleet and a large bandwidth bill. A CDN edge 10 to 20 ms from the user answers most requests itself and sends only misses to the origin; for static content such as photos, JavaScript and video segments, edge hit ratios above 90 % are normal.

The CDN decides what to cache from HTTP: the Cache-Control header gives the lifetime (public, max-age=31536000, immutable for content that never changes), and the cache key (by default the URL, optionally some headers or cookies) decides which requests share an entry. The best design for user content is immutable URLs: each photo variant gets a URL containing its id or content hash, so it can be cached forever and never needs invalidation; an edited photo gets a new URL. When content does change under the same URL, you either wait for the TTL or purge it through the CDN's API, which takes seconds to propagate. Many CDNs add an origin shield, a mid-tier cache that collapses the misses of all edges into one request to the origin, so that a new viral photo is fetched from the origin once rather than by 300 edges at the same time.

CDNs also accelerate dynamic, uncacheable requests: the TLS handshake happens at the near edge, and the edge keeps warm, long-lived connections to the origin over the provider's backbone. They are the first line of defence against DDoS attacks (absorbing traffic at the edge) and often host a web application firewall and bot detection.

In practice

Private photos still go through the CDN: the app returns a signed URL (with an expiry time and a signature the edge verifies), so the edge can serve and cache the bytes without the origin checking permissions on every request. Signed URLs and presigned upload URLs to object storage (Section 13.5) are how photo, video and file services keep the bytes off their app servers entirely.

Talk track

"Image bytes never touch our app servers. Uploads go directly to object storage with a presigned URL, and downloads come from the CDN with immutable, content-addressed URLs, so the cache never needs invalidation. The origin only serves the JSON for the feed, which is a few kilobytes per request."

4Caching

A cache keeps a copy of data in a faster place so that most reads do not have to go to the slower source. It is the single most effective tool for read-heavy systems, and also the source of a family of bugs that all have the same root: the copy and the original disagree.

4.1Why caches work: skew and the hit ratio

Caches work because access is skewed: a small part of the data gets most of the requests. Today's photos are viewed far more than last year's; a celebrity's profile far more than an average user's. This popularity often follows a Zipf distribution, where the k-th most popular item is requested in proportion to 1/kα. With strong skew, a cache holding a small fraction of the keys absorbs a large fraction of the reads. Figure 4.1 measures this with an LRU cache over one million keys.

Two simple formulas then tell you what a cache buys. The load that still reaches the database is (1 − h) times the read rate, where h is the hit ratio: at 17,000 reads per second, a 90 % hit ratio leaves 1,700 per second, and 99 % leaves 170. Going from 90 % to 99 % cuts the database load by ten. The average latency is h × tcache + (1 − h) × tdb, but the tail latency is set by the misses, so a cache improves p50 more than p99. Size the cache from the working set: the photo service's metadata for the last few days of photos, plus the precomputed feeds of active users, fits in tens of gigabytes, which is a small Redis cluster.

Why it matters

A cache in front of a database is also a load-bearing wall: once the database is sized for the 10 % of reads that miss, losing the cache sends ten times the load to a database that cannot take it. Cache failure modes (Section 4.5) are therefore availability problems, not just performance problems.

4.2Caching patterns: who fills and who updates the cache

The patterns differ in who is responsible for keeping the cache filled and up to date. In cache-aside (lazy loading), the most common, the application owns the logic: on a read it asks the cache, and on a miss it reads the database and puts the result in the cache with a TTL. On a write it updates the database and then deletes the cache entry, so that the next read loads the fresh value. The cache holds only what was actually requested, and a cache failure only makes things slower.

Deleting instead of setting on write is deliberate. If two writers update the same row and both set the cache, their cache writes can arrive in the opposite order of their database commits, leaving the older value cached. A delete is idempotent and order-insensitive: whatever happens, the next reader loads the current row. Even delete-on-write has a race, shown in Figure 4.3 (Section 4.3).

In read-through caching the cache itself loads missing entries from the database (a cache library or a product such as a caching proxy does it), which centralises the logic but couples the cache to the database schema. In write-through, every write goes to the cache and the database synchronously, so the cache is always warm for recently written data, at the cost of slower writes and caching data nobody reads. Write-behind (write-back) acknowledges the write once it is in the cache and writes to the database later, in batches: very fast writes, but data is lost if the cache dies before flushing, so it suits counters and metrics, not orders. Write-around writes only to the database and lets reads fill the cache, which avoids filling it with data that is written once and rarely read.

4.3Invalidation: the hard part

The quip that cache invalidation is one of the two hard things in computer science is accurate for a precise reason: the cache and the database are two systems without a shared transaction, so there is always an interleaving of operations in which the cache ends up with an old value. Figure 4.3 shows the classic one.

There are four ways to live with this. A TTL on every entry is the backstop: whatever goes wrong, the stale value disappears after at most the TTL, so choose the TTL as the longest staleness the product can accept (seconds for a like count, minutes for a profile). Leases, introduced by Facebook's memcache system, close the race: on a miss the cache hands the reader a lease token, a delete invalidates outstanding leases, and the cache rejects a SET that carries an invalidated token, so A's stale write in step 5 is refused. Versioned values store a version number (or the row's update timestamp) with the entry and only overwrite with a newer version. And change data capture moves invalidation out of the application: a process tails the database's replication log and deletes or updates the cache keys of every changed row, in commit order, so no code path can forget to invalidate.

Invalidation gets harder with derived data. The photo row is easy to invalidate; the cached feed of each of the photographer's 2,000 followers, which contains that photo, is not. Systems usually accept staleness there (a caption edit appears in feeds after the TTL) or store only ids in derived caches and fetch the current objects separately, so that only the object cache needs invalidation.

Talk track

"Cache-aside with delete on write, and a TTL on every key as a safety net. The race where a slow reader puts back an old value is real, so for data where staleness matters I'd use versioned writes or drive invalidation from the database's change stream; for like counts a 30-second TTL is enough."

4.4Eviction, and Redis as the standard cache

A cache is smaller than the data, so it must choose what to forget. LRU (least recently used) evicts the entry unused for longest and works well for recency-driven access; LFU keeps frequently used entries and resists one-off scans that would flush an LRU; TTL-based eviction removes expired entries first. Modern caches combine recency and frequency (Caffeine's W-TinyLFU). The data structures and the trade-offs are in Algorithms 9.3.

Redis is the default shared cache and much more. It is an in-memory data-structure server: besides strings it has hashes, lists, sets, sorted sets (used for leaderboards, timelines and sliding-window rate limits), streams, HyperLogLog for approximate counting and atomic Lua scripts. Commands run on one main thread, which makes each command atomic and avoids locking; I/O threads help with networking. One instance does around 100,000 simple operations per second without pipelining (Section 1.3), with sub-millisecond latency. For memory limits it evicts by an approximate LRU or LFU that samples a few keys instead of keeping a global order (maxmemory-policy allkeys-lru). Persistence (RDB snapshots, AOF log) exists but a cache usually does without it. Redis Cluster partitions keys into 16,384 hash slots spread over primaries, each with replicas; clients learn the slot map and talk to the right node directly. Memcached is the simpler alternative: multi-threaded, strings only, no persistence or replication, very fast for plain key-value caching.

Pitfall

Using Redis as a database by accident: storing data in it that exists nowhere else (sessions, carts, rate-limit state are fine if losing them is acceptable). Redis replication is asynchronous, so a failover can lose recent writes; if the data matters, it needs a real durable store behind it, or a deliberate decision that losing it is acceptable.

4.5When caches fail: stampedes, hot keys and cold starts

The dangerous cache problems are those where the cache stops absorbing load suddenly. A cache stampede (thundering herd, dog-piling) happens when a popular key expires: hundreds of requests miss at the same moment and all run the same expensive query, which slows the database, which makes more requests pile up. Three defences: request coalescing (single-flight), where only one request per key loads from the database and the others wait for its result; early or probabilistic refresh, where entries are refreshed in the background shortly before they expire (with a randomised probability that grows as expiry nears); and jittered TTLs, so that keys written together do not expire together. Serving the stale value while one request refreshes (stale-while-revalidate) is the same idea in HTTP.

A hot key is one key with so much traffic that the single cache node holding it saturates, for example the profile of a celebrity who just posted. Partitioning does not help because one key lives on one node. Fixes: a small in-process cache in each app server for the hottest keys (milliseconds of TTL are enough to cut traffic by orders of magnitude), or replicating the hot key under several names (profile:42#1…#8) and reading a random copy. Cache penetration is the opposite: requests for keys that do not exist (by a bug or an attacker) always miss and always hit the database. Cache the negative result with a short TTL, or keep a Bloom filter of existing keys in front. A cold start, after a cache cluster restart or a new region, means a 0 % hit ratio at full load; warm the cache from logs or let traffic in gradually.

Numbers

Effect of the hit ratio on the photo service's database at 17,000 reads per second: 90 % → 1,700 queries/s, 99 % → 170/s. A cache restart that drops the ratio to zero sends all 17,000 to a database sized for 1,700. This is why cache clusters are replicated and restarted one node at a time.

5Databases: data models, indexes and transactions

The database is where the truth lives, so its choice and its data model are the decisions that are most expensive to change later. Three questions matter more than the product name: how is the data shaped and accessed, how does the storage engine find and write it, and what does a transaction promise when many requests touch the same data at once.

5.1Relational or NoSQL: choose by access pattern

A relational database (PostgreSQL, MySQL, SQL Server, Oracle) stores rows in tables with a schema, links them with keys, answers arbitrary queries with SQL and joins, and wraps changes in ACID transactions. Its strength is flexibility: you do not have to know all questions in advance, because the query planner combines indexes and joins at query time. Its historical weakness is horizontal scaling: one primary takes all writes, and joins and transactions across machines are hard. For most products, including the photo service until stage 6, a relational database is the right default; it scales vertically further than people expect (hundreds of cores and terabytes of RAM are available) and read replicas take the read load.

"NoSQL" names several different models that gave up some relational features to gain scale or a better fit for one access pattern. Key-value stores (DynamoDB, Redis, Riak) look up a value by key and little else; they partition trivially. Document databases (MongoDB, Couchbase, Firestore) store JSON-like documents, good when an entity is read and written as a whole (a product with its variants). Wide-column stores (Cassandra, ScyllaDB, HBase, Bigtable) store rows under a partition key, sorted by a clustering key inside the partition; they are built for very high write rates and queries known in advance, such as "the last 50 messages of conversation X". Graph databases (Neo4j) make multi-hop relationship queries cheap. A newer family, distributed SQL or NewSQL (Google Spanner, CockroachDB, YugabyteDB, TiDB), keeps SQL and serializable transactions while partitioning and replicating automatically with consensus (Chapter 8), at the cost of higher write latency.

Pitfall

"Schemaless" means the schema moved into the application code. Every reader must handle every shape a document ever had. Document databases are a good fit when the data really is document-shaped, not as a way to avoid thinking about the schema.

5.2How indexes work: B-trees and LSM trees

Without an index, a query must read every row: a full scan. An index is a second data structure, sorted by the indexed columns, that leads straight to the matching rows. The measurement below is the photo service's most common query, "the 20 newest photos of one user", on a table of 2 million photos in PostgreSQL 16.

The index makes the query 580 times faster: three workers scanning 161 MB become a walk down a tree to the ten rows of that user. The index costs 60 MB of space (37 % of the table) and one more structure to update on every insert. The composite key (user_id, created_at desc) matters: it matches the query's filter and its order, so the database finds the user's rows already sorted. An index on created_at alone would not help this query.

A B-tree, used by PostgreSQL, MySQL InnoDB, SQL Server and most relational databases, keeps keys in pages of 4 to 16 KB arranged as a shallow, wide tree: with hundreds of keys per page, three or four levels cover billions of rows, and the upper levels stay in RAM, so a lookup costs one or two disk reads. A write first goes to the write-ahead log (sequential, for crash safety), then changes the right leaf page in memory; the page is written back later. When a page is full it splits. B-trees give fast, predictable reads and range scans; their writes are random (each insert touches a page somewhere in the tree), and a small change rewrites a whole page. The tree itself is explained in Algorithms 4.2.

An LSM tree (log-structured merge tree), used by RocksDB, LevelDB, Cassandra, ScyllaDB, HBase and Bigtable, never updates in place. A write goes to a log and to an in-memory sorted table (the memtable). When the memtable is full it is written to disk as an immutable sorted file (an SSTable) in one sequential write. Background compaction merges files into larger levels, dropping overwritten values and deleted keys (marked with tombstones). Writes are therefore sequential and cheap. Reads pay instead: a key may be in the memtable or in any of several files, so the engine checks them newest first and uses a Bloom filter per file to skip files that cannot contain the key. On the same container, one million random-key inserts took 20.1 s into SQLite's B-tree and 3.5 s into RocksDB; RocksDB wrote the data roughly three times overall (log, flush, compaction) to achieve that.

The trade-off is usually described with three amplifications: write amplification (bytes written to disk per byte of data), read amplification (disk reads per query) and space amplification (disk used per byte of live data). B-trees have low read amplification and moderate write amplification (whole pages for small changes); LSM trees have low write cost per insert and better compression but higher read and compaction cost, and compaction can cause latency spikes. Rule of thumb: write-heavy, append-like workloads (events, messages, metrics, time series) favour LSM; read-heavy workloads with point and range queries favour B-trees.

Pitfall

Adding an index for every query. Each secondary index is another tree to update on every write and more memory to keep hot; ten indexes on a busy table can make inserts several times slower. Index for the access patterns you actually have, check them with EXPLAIN ANALYZE, and drop unused ones (PostgreSQL's pg_stat_user_indexes shows scans per index).

5.3Transactions and isolation levels

A transaction groups several reads and writes into one unit. ACID names its promises: atomicity (all or nothing, even across a crash), consistency (the application's invariants hold, with help from constraints), isolation (concurrent transactions do not see each other's half-done work) and durability (once committed, it survives a crash). Atomicity and durability are mostly the write-ahead log's job. Isolation is where the subtle bugs are, because full isolation is expensive, so databases offer weaker isolation levels by default, and each level allows some anomalies.

A dirty read sees another transaction's uncommitted write. A non-repeatable read reads the same row twice and gets different values because someone committed in between. A phantom re-runs a query and finds new rows matching it. A lost update happens when two transactions read a value, both compute a new one and both write it: one increment disappears. Write skew is the subtlest: two transactions read the same data, make a decision based on it, and write different rows, so no row-level conflict is visible, but together they break an invariant. Talk track

"Most production databases default to read committed, which allows lost updates and write skew. For counters I'd use atomic updates; for 'check then act' logic such as booking the last seat or limiting a balance, I'd use SELECT FOR UPDATE, a version column, or run that transaction at SERIALIZABLE with a retry loop."

Interesting detail

The SQL standard defines isolation levels by which of three phenomena they forbid, and real databases interpret the names differently: Oracle's "serializable" is snapshot isolation and allows write skew; PostgreSQL's REPEATABLE READ is snapshot isolation and forbids phantoms, which the standard would allow; MySQL's REPEATABLE READ allows some lost updates for plain SELECTs. Know what your database means, not what the name suggests.

5.4MVCC and connection pools: two things that bite in production

Most databases implement isolation with multi-version concurrency control. An update does not overwrite a row; it writes a new version and marks the old one as superseded by the updating transaction. Each transaction reads with a snapshot that says which transactions' versions it may see. Readers never block writers and writers never block readers, which is why PostgreSQL and MySQL handle mixed read and write loads well. The cost is that old versions pile up and must be cleaned (PostgreSQL's VACUUM, InnoDB's purge of undo logs). A transaction left open for hours, for example a forgotten analytics session, keeps every version since its start alive, tables bloat and queries slow down.

The second production trap is connections. A PostgreSQL connection is a server process with several megabytes of memory, and performance degrades past a few hundred active connections. Fifty app servers with twenty threads each would open a thousand. A connection pool (in the app, and often a shared pooler such as PgBouncer in transaction mode) multiplexes many app requests over a small number of database connections. Pool size is a capacity decision: a pool much larger than the number of cores and disks the database has only adds queueing inside the database.

Numbers

From the experiments: index scan 0.097 ms versus full scan 56 ms on 2 M rows (580×); index size 60 MB for a 161 MB table; 1 M random inserts: SQLite B-tree 20.1 s, RocksDB LSM 3.5 s, RocksDB total writes ≈ 3× the ingested data. (Experiments: db_experiments.py index, anomalies, lsm.)

6Replication

Replication keeps copies of the same data on several machines. It exists for three reasons: to survive the loss of a machine without losing data or availability, to spread read load over several machines, and to put data close to users. The difficulty is that copies are updated at different times, and every design choice in replication is about how much disagreement between copies is acceptable and for how long.

6.1Leader and followers, synchronous and asynchronous

The most common scheme has one leader (primary) that accepts all writes, and followers (replicas, standbys) that receive a stream of changes and apply them in the same order. In PostgreSQL the stream is the write-ahead log itself (physical replication); MySQL ships its binary log; logical replication sends row changes, which allows different versions or a subset of tables on the follower. Clients send writes to the leader and may send reads to followers.

The key choice is when the leader confirms a commit to the client. With synchronous replication it waits until at least one follower has the change, so a confirmed write survives the loss of the leader; the price is a network round trip on every commit and a stall if the synchronous follower is slow or down. With asynchronous replication the leader confirms immediately and followers catch up when they can; commits are fast and followers can be far away, but if the leader dies, writes it confirmed but had not yet shipped are lost. Most production setups use asynchronous followers, or one synchronous follower plus asynchronous ones (semi-synchronous), so that one up-to-date copy always exists. Cross-region replicas are almost always asynchronous, because a synchronous round trip of 90 ms on every commit is too expensive.

Why it matters

"Replicated" does not mean "no data loss". With asynchronous replication, a failover loses the last moments of writes; with synchronous replication, the system stops accepting writes when it cannot reach a follower. You pick which failure you prefer; Chapter 8 shows that this choice cannot be avoided.

6.2Replication lag and the anomalies it causes

Followers lag behind the leader: milliseconds when all is well, seconds or minutes under load, during a long-running migration or after a network problem. Reading from followers is therefore reading the past, and three user-visible anomalies follow. Figure 6.1 shows the first.

Read-your-writes (read-after-write) consistency says a user always sees their own changes. Fixes: read data the user may have just changed from the leader (for example, the user's own profile, or everything for ten seconds after the user's last write); or remember the log position of the user's last write (a PostgreSQL LSN, a MySQL GTID) in the session and read from a follower only once it has replayed that far. Monotonic reads say a user never sees time go backwards: if one request hits an up-to-date follower and the next a lagging one, a comment appears and then disappears. Fix: route each user consistently to the same follower (by a hash of the user id). Consistent prefix reads say causally related writes are seen in order: nobody should see the answer before the question. This mainly arises with partitioned data, where different partitions replicate independently.

In practice

Monitor replication lag as a first-class metric (PostgreSQL: pg_stat_replication, replay_lag), alert on it, and have the routing layer stop sending reads to a follower that is too far behind. A follower that lags by minutes is worse than no follower, because it serves wrong answers confidently.

6.3Failover, split brain and fencing

When the leader fails, a follower must become the new leader: failover. It sounds simple and is one of the riskiest operations in distributed systems, because every step involves a judgement under uncertainty. First, detection: the leader is declared dead when it misses heartbeats for some timeout. Too short a timeout causes failovers during a garbage-collection pause or a brief network glitch; too long means minutes of unavailability. Second, election: the follower with the most recent data should win, and all nodes must agree on the winner, which is a consensus problem (Section 8.4). Third, reconfiguration: clients and other followers must switch to the new leader, and the old leader, if it comes back, must accept that it is no longer the leader.

That last point is the source of split brain: the old leader was not dead, only cut off, and now two nodes accept writes for the same data, which diverge and cannot be merged automatically. The defence is fencing: each new leadership term gets a monotonically increasing number (an epoch or fencing token), and storage or downstream systems reject writes carrying an older number. Production failover managers for PostgreSQL (Patroni) and MySQL (Orchestrator, Group Replication) keep the leader lease in a consensus store such as etcd or ZooKeeper; a leader that cannot renew its lease stops accepting writes on its own.

Interesting detail

Martin Kleppmann's Designing Data-Intensive Applications recounts a GitHub incident in 2012: an out-of-date MySQL follower was promoted, the writes it had missed were discarded, and auto-increment primary keys were handed out again. Those ids were also used as keys in a Redis store, so some private data was shown to the wrong users. Lost writes after failover rarely stay inside the database.

6.4Multi-leader and leaderless replication

With one leader, all writes go to one place, which is a bottleneck and, across regions, a latency problem: a user in Sydney writing to a leader in Frankfurt waits 280 ms per round trip. Multi-leader replication allows a leader in each region; each accepts local writes and replicates them to the others asynchronously. Writes are fast everywhere, but two regions can change the same record concurrently, and the conflict must be resolved. Last-write-wins by timestamp is simple and silently drops one of the writes (and depends on clocks, which drift; Software architecture 9.5 covers time in distributed systems). Better options are to avoid conflicts by giving each record a home region that alone writes it, to merge with application rules, or to use CRDTs, data types such as counters and sets whose concurrent updates merge deterministically (used in Riak, Redis Enterprise active-active, and collaborative editors).

Leaderless replication, popularised by Amazon's Dynamo paper and used by Cassandra and ScyllaDB, drops the leader altogether: the client (or a coordinator node) sends each write to several replicas and each read to several replicas, and uses quorums to make sure reads see recent writes. Section 8.3 explains how quorums work and what they do and do not guarantee.

Talk track

"I'd start with one leader per shard and asynchronous followers, with one synchronous follower for durability. Users get read-your-writes by reading their own data from the leader. For a second region, each user has a home region that owns their writes, so we avoid multi-leader conflicts; other regions get asynchronous copies for reads and disaster recovery."

7Partitioning and sharding

Replication copies all of the data to more machines; it does not help when the data or the write rate is too large for one machine. Partitioning (sharding) splits the data so that each machine owns a part. It is the only way to scale writes horizontally, and it changes the rest of the design: which queries are cheap, how transactions work and how the system grows.

7.1Range and hash partitioning

Every partitioning scheme answers one question: given a key, which partition owns it? Range partitioning gives each partition a contiguous range of keys (A to F, G to M, and so on), like the volumes of an encyclopaedia. Keys stay sorted, so a range query ("users whose names start with G", "events between 10:00 and 11:00") asks only the partitions that cover the range. The danger is skew: if keys arrive in order, such as timestamps or auto-increment ids, every new write lands in the last partition, which becomes a hot spot while the others idle. Bigtable, HBase and the key ranges of CockroachDB and TiDB use range partitioning and split ranges automatically as they grow.

Hash partitioning computes a hash of the key and assigns hash ranges to partitions. A good hash spreads any key pattern evenly, including timestamps and sequential ids, so hot spots from key order disappear. The price is that neighbouring keys end up on different partitions, so range queries must ask every partition and merge the answers (scatter-gather), which is slow and gets slower as partitions are added. The common compromise is a compound key: Cassandra's partition key is hashed to choose the node, and the clustering key sorts rows inside the partition. For the photo service, the key (user_id, created_at) puts all of one user's photos on one partition, sorted by time, so "newest photos of this user" is one partition read, while users spread evenly.

Partitioning by user also decides which queries become hard. Anything that crosses users, such as "photos by everyone with tag #sunset" or a global top-10, now touches every partition. Such queries are served by a separate system built for them (a search index, an analytics store) and fed asynchronously, rather than by scatter-gather over the primary data. Secondary indexes show the same tension: a local index (each partition indexes its own rows) is cheap to write but every query by the indexed column asks all partitions; a global index (partitioned by the indexed value) answers with one lookup but every write may touch another partition, so it is usually updated asynchronously.

Pitfall

Partitioning does not fix a hot key. If one celebrity account gets a thousand times the traffic of an average one, all of it lands on the partition that owns that key. Hot keys need their own treatment: caching, splitting the key (append a random suffix to spread writes, read all suffixes), or special handling in the application (Section 13.4).

7.2Consistent hashing

The obvious hash scheme, partition = hash(key) mod N, has a fatal flaw: when N changes, almost every key changes partition. Going from 10 to 11 nodes moved 90.8 % of the keys in the experiment, which for a cache means a near-total miss storm and for a database means copying almost all data. Consistent hashing avoids this. Nodes and keys are hashed onto the same ring of numbers (0 to 232 − 1, wrapping around); each key belongs to the first node clockwise from its position. When a node is added, it takes over only the keys between its position and its predecessor's, roughly 1/N of the data, from one neighbour; everything else stays put.

With one point per node, the arcs between points are very uneven, so some nodes own several times more keys than others. The fix is virtual nodes: each physical node is placed on the ring at many points (100 to 256 is common), so its share is the sum of many small arcs and evens out. Virtual nodes also let a bigger machine take more points, and when a node leaves, its load is spread over many others instead of falling onto one neighbour. Try it in Figure 7.2.

Interesting detail

Rendezvous hashing (highest random weight) is an alternative with no ring: for each key, compute hash(key, node) for every node and pick the highest. It moves the same minimal fraction of keys when nodes change and needs no virtual nodes, at the cost of O(N) work per lookup, which is fine for tens of nodes. Jump consistent hash (Google, 2014) maps a key to one of N buckets in a few lines of code with no memory, but only lets you add or remove the last bucket.

7.3Rebalancing and request routing in practice

Many production systems avoid moving individual keys at all by creating many more partitions than nodes from the start: a fixed number of partitions (for example 1,024), each a unit that can be moved whole. Redis Cluster has 16,384 hash slots, Kafka topics have a chosen number of partitions, Elasticsearch indexes a fixed number of shards. Adding a node means moving some whole partitions to it, which is simple to reason about and to throttle. Systems with range partitioning (Bigtable, HBase, CockroachDB, MongoDB) instead split a range in two when it grows too big or too hot, and move the halves independently.

Once data is partitioned, every request must find the right node. There are three places to put that knowledge: in a routing tier (a proxy such as Vitess's VTGate for MySQL, or mongos for MongoDB) that knows the partition map; in the client (Redis Cluster and Cassandra drivers learn the map and connect directly, with a redirect when the map changed); or in any node, which forwards to the right one. The partition map itself must be agreed on by everyone and changed safely, so it typically lives in a consensus-backed store such as ZooKeeper or etcd, or is gossiped between nodes.

In practice

Resharding a live relational database is a project of weeks: copy data to new shards, keep them in sync with change data capture, switch reads, then writes, then clean up, with verification and a rollback plan at each step. Tools such as Vitess automate it for MySQL; Citus does a similar job for PostgreSQL. This is why the decision to shard is postponed as long as vertical scaling and read replicas suffice, and why a good shard key (stable, high-cardinality, present in nearly every query, such as user_id or tenant_id) is chosen with care.

7.4Transactions across partitions

A transaction that touches one partition is as easy as on a single database. One that spans partitions, such as moving money between two accounts on different shards, needs all partitions to commit or none. Two-phase commit (2PC) does this with a coordinator: in phase one it asks every participant to prepare (make the change durable but not yet visible, and promise to commit if asked); if all say yes, in phase two it tells them to commit. The weakness is blocking: a participant that voted yes must wait for the coordinator's decision, holding its locks, and if the coordinator crashes at that moment, the participant cannot decide on its own. Distributed databases such as Spanner and CockroachDB make 2PC safe by replicating the coordinator's state and each participant with consensus, so a crash does not lose the decision.

Across services with separate databases, 2PC is usually avoided: it couples their availability and needs every system to support it. The alternative is a saga: a sequence of local transactions, each publishing an event that triggers the next, with a compensating action for each step (refund the payment, release the reservation) if a later step fails. Sagas give up isolation (others can see intermediate states) in exchange for loose coupling; they are built on reliable events, which is what the outbox pattern in Section 9.4 provides. The design rule that saves most of this pain is to choose partition keys so that most transactions stay inside one partition: all of one user's data on one shard, all of one order's lines with the order.

8Consistency, CAP, quorums and consensus

Once data has copies, "what does a read return?" no longer has an obvious answer. Consistency models are precise answers to that question, ordered by how much coordination they need. This chapter gives the vocabulary needed to compare databases honestly, and explains how consensus lets a group of machines agree on one value despite failures.

8.1Consistency models: a ladder of promises

The strongest useful model is linearizability: the system behaves as if there were a single copy of the data and every operation took effect at one instant between its start and its end. If a write has completed, every read that starts afterwards sees it, no matter which replica answers. It is what programmers intuitively expect, and it is what a leader lock, a unique username check or "only one worker may process this job" needs. It is also expensive: every operation must coordinate with a leader or a majority, so it costs a round trip and stops when a majority is unreachable.

Below it, sequential consistency keeps one global order that all clients agree on but may lag behind real time. Causal consistency only orders operations that depend on each other: a reply is never seen before the message it answers, but unrelated updates may appear in different orders on different replicas; it is the strongest model that remains available during network partitions. The session guarantees from Section 6.2 (read-your-writes, monotonic reads, consistent prefix) are promises to a single client, cheap to provide with sticky routing or log positions. Eventual consistency promises only that replicas converge if writes stop; any read may be stale until then. DNS, caches and asynchronous replicas are eventually consistent.

Note that the "C" in ACID (application invariants hold) and the "C" in CAP (linearizability) are different ideas that share a letter. "Strong consistency" in product documentation usually means linearizable reads of single keys, but check the fine print: some systems provide it only for reads that go to the leader, or only within one region.

8.2CAP and PACELC, stated precisely

The CAP theorem (Brewer's conjecture, proved by Gilbert and Lynch in 2002) says that when a network partition separates replicas, a system must choose between consistency (linearizability) and availability (every request to a non-failed node gets a non-error answer). If the two halves cannot talk, a replica asked to write either refuses (consistent, not available) or accepts (available, and the halves now disagree). It is often misquoted as "pick two of three", as if partition tolerance were optional. It is not: networks do partition, so the real choice is what to do when they do, CP or AP, and only during a partition. When the network is fine, a system can be both consistent and available.

PACELC (Daniel Abadi, 2010) adds the part that matters every day: if there is a Partition, choose Availability or Consistency; Else, even with a healthy network, choose Latency or Consistency. Stronger consistency needs coordination on every request, and coordination costs round trips, so even without failures you trade latency against consistency. This explains real systems better than CAP alone.

8.3Quorums

Leaderless systems keep N copies of each key and use quorums to make reads see writes. A write is sent to all N replicas and counts as successful when W of them acknowledge; a read asks R replicas and takes the newest version among the answers. If W + R > N, every read set overlaps every write set in at least one replica, so at least one answer has the latest acknowledged write. With N = 3, W = 2, R = 2, the system tolerates one replica being down for both reads and writes.

Stale replicas are repaired in two ways: read repair, where a read that sees an old version on some replica writes the newest one back, and anti-entropy, a background process that compares replicas (using Merkle trees, so only differing ranges are exchanged) and copies missing data. When some of the N home replicas are unreachable, a sloppy quorum lets the write land on other nodes temporarily, with a hint to hand it back later (hinted handoff); this keeps writes available during failures but breaks the overlap guarantee until the hints are delivered.

Quorums are often taken to give strong consistency, and they do not quite. Concurrent writes to the same key need a rule to pick a winner; last-write-wins by timestamp silently drops writes and relies on clocks. A write that reached fewer than W replicas reports failure but is not rolled back, so later reads may or may not see it. Without extra mechanisms, W + R > N gives "reads usually see the latest write", not linearizability. Cassandra adds lightweight transactions (Paxos) for compare-and-set when it matters.

Numbers

Quorum fault tolerance: a majority of N tolerates ⌊(N − 1) / 2⌋ failures: 1 of 3, 2 of 5, 3 of 7. Even N buys nothing: 4 replicas tolerate 1 failure, the same as 3. That is why consensus clusters have 3 or 5 members.

8.4Consensus and Raft

Many problems in this chapter reduce to getting several machines to agree on one thing despite failures: which node is the leader, whether a transaction committed, what the partition map is, which writes come in which order. That is the consensus problem, and it is subtle: the FLP result proved that no deterministic algorithm can guarantee agreement in a fully asynchronous network where even one node may crash. Practical algorithms stay always safe (never two different decisions) and make progress when the network is stable enough, using timeouts. Paxos (Leslie Lamport) was the first widely known solution; Raft (Ongaro and Ousterhout, 2014) was designed to be understandable and is now the most common. etcd (the store behind Kubernetes), Consul, CockroachDB, TiKV, and Kafka's KRaft mode use Raft; ZooKeeper uses a similar protocol, Zab.

Raft replicates a log: a sequence of commands that every member applies in the same order, so all members' state machines end in the same state. Time is divided into numbered terms, each with at most one leader. Step through Figure 8.3.

All servers start as followers. Each waits for heartbeats from a leader for a randomised election timeout (typically 150 to 300 ms). S3's timer fires first: it increments the term to 2, votes for itself and asks everyone else for a vote with RequestVote. Randomising the timeouts makes it likely that one candidate starts clearly before the others, so split votes are rare.

Each server grants at most one vote per term, and only to a candidate whose log is at least as up to date as its own (higher last term, or same term and at least as long). S1, S2 and S4 vote for S3; with its own vote, S3 has 4 of 5, a majority, and becomes leader of term 2. It immediately sends heartbeats so the others do not start elections. Two leaders in one term are impossible because two majorities of five always share a member, and that member votes once.

A client sends a write. Only the leader accepts writes: it appends the command as entry 7 in its log and sends AppendEntries to all followers. Each AppendEntries also carries the index and term of the previous entry, so a follower with a gap or a conflicting entry rejects it and the leader walks back until the logs match, then overwrites the follower's divergent tail.

S1 and S2 store entry 7 and acknowledge. Together with the leader, 3 of 5 servers have it, so it is committed: the leader applies it to its state machine and answers the client, and tells the followers the new commit index in the next message. S4 and S5 are slow or briefly disconnected; they catch up later from the leader. A write costs one round trip to the fastest majority, which is why consensus writes cost about one network round trip plus a disk sync.

S3 crashes. After their election timeouts, followers start an election for term 3. S5 cannot win: its log ends at entry 5, so S1, S2 and S4 refuse it. S1 has entry 7 and wins with votes from S2, S4 and S5. Because any majority of voters includes at least one server that stored entry 7, the new leader always has every committed entry: committed writes are never lost. Entries that were only appended on the old leader, never on a majority, may be discarded; their clients never got a success.

In system design, you rarely implement consensus; you use a system built on it. Leader election for your service, distributed locks with fencing tokens, configuration and service discovery are typically delegated to etcd, ZooKeeper or Consul, and consensus-replicated databases use it for every write. The cost model is what matters: each consensus write is a round trip to a majority, so a 5-node cluster spread over three regions pays cross-region latency on every write, and consensus clusters are kept small (3 or 5 members) because every member must confirm.

Pitfall

A distributed lock is only as good as its fencing. A process that took a lock with a 10-second lease, paused for 15 seconds in garbage collection and then wrote to storage believes it still holds the lock, while another process already does. The storage must check a fencing token (the lock's term number) and reject the stale writer; the lock alone cannot guarantee mutual exclusion.

9Queues and event streaming

A request-response call couples the caller to the callee in time: both must be up, and the caller waits for the slowest step. Putting a queue or a log between them breaks that coupling. The producer records that something happened and moves on; consumers process it when they can, at their own speed, and retry when they fail.

9.1Why asynchronous messaging, and queue versus log

The photo upload is the example. Inside the request, the service must store the photo and its row; everything else (three resized variants, pushing the photo into 2,000 followers' feeds, notifying the people tagged, updating the search index, scanning for abuse) can happen a few seconds later. Doing it synchronously makes the upload as slow as the sum of these steps and as fragile as the least reliable of them. With a message in between, the upload returns in tens of milliseconds, a spike of uploads becomes a temporary backlog instead of an overload, each consumer scales and fails independently, and adding a new consumer (say, a recommendation model that wants every upload) needs no change in the upload service.

Two kinds of systems carry such messages. A message queue (RabbitMQ, Amazon SQS, ActiveMQ) hands each message to one consumer and deletes it once acknowledged; it is a to-do list. It has per-message acknowledgement, redelivery after a visibility timeout, priorities and flexible routing, and it fits task distribution: "resize this photo". A log (Apache Kafka, Amazon Kinesis, Apache Pulsar, Redpanda) appends messages to a durable, ordered, partitioned log and keeps them for a retention period whether or not anyone has read them; each consumer tracks its own position. It fits event streaming: "photo 991 was uploaded" is a fact that many independent consumers read, some in real time, some hours later, and a new consumer can replay history.

Why it matters

Asynchronous does not mean free. You trade immediate consistency for eventual consistency (the follower's feed shows the photo a second later), and you add a system that must be operated, monitored for lag and sized. Use messaging where the work can be late, where load is spiky, or where many consumers want the same events; keep request-response where the caller needs the answer now.

9.2Kafka: topics, partitions, offsets and consumer groups

A Kafka topic is split into partitions; each partition is an append-only log on disk where every message gets a sequential offset. The producer chooses the partition by hashing the message key (here photo_id, or user_id if all of a user's events must stay in order), so all messages with the same key land in the same partition, in order. Order is guaranteed only within a partition; across partitions there is no global order. Partitions are the unit of parallelism and of scaling: more partitions, more consumers in parallel.

Consumers belong to consumer groups. Kafka assigns each partition of a topic to exactly one consumer in a group, so a group with three consumers on three partitions processes in parallel while each partition stays in order; a fourth consumer would sit idle. Different groups are independent: the thumbnailer and the feed fan-out both read every message, each at its own pace. A consumer periodically commits its offset ("I have processed up to here"); after a crash or a rebalance, the partition's new owner resumes from the last committed offset. The difference between the newest offset and the committed offset is the consumer lag, the key health metric of any streaming pipeline.

Durability comes from replication: each partition has a leader broker and followers (replication factor 3 is typical). The followers that are fully caught up form the in-sync replica set (ISR). With the producer setting acks=all and the topic setting min.insync.replicas=2, a write is acknowledged only when at least two replicas have it, so losing one broker loses nothing. Messages are kept for a retention time (seven days by default) or size, or, for compacted topics, the latest value per key is kept forever, which turns a topic into a changelog of a table. Since Kafka 4.0 the cluster's metadata is managed by its own Raft-based controller quorum (KRaft) instead of ZooKeeper.

Numbers

Kafka throughput comes from sequential disk writes, batching and zero-copy transfer: one broker handles hundreds of MB/s, and a partition on the order of 10 MB/s of writes. Plan partitions for the peak consumer parallelism you will need (adding partitions later changes which partition a key maps to, which breaks per-key order during the change).

9.3Delivery guarantees: at most once, at least once, exactly once

Messages can be lost or duplicated whenever a process crashes between two steps, so every pipeline has a delivery guarantee, whether it was chosen or not. The guarantee is decided by the order of two actions in the consumer: processing the message and recording that it was processed.

At most once (commit, then process) never repeats and may lose messages: acceptable for metrics or log sampling. At least once (process, then commit) never loses and may repeat: the right default for almost everything, provided processing is idempotent, meaning that doing it twice has the same effect as once. Inserting a thumbnail row keyed by photo id, setting a status, or upserting by a natural key are idempotent; incrementing a counter or sending an e-mail are not, and need a deduplication record ("event 41 already handled"), checked and written in the same transaction as the effect.

Exactly once is the most misunderstood term in messaging. Exactly-once delivery over an unreliable network is impossible: a sender that gets no acknowledgement cannot know whether the message arrived. What systems provide is exactly-once effect. Kafka's idempotent producer (on by default since Kafka 3.0) attaches a producer id and sequence number so the broker drops duplicate retries; Kafka transactions let a stream processor read from one topic, write to another and commit its offsets atomically, so a Kafka-to-Kafka pipeline (Kafka Streams, Flink) has exactly-once semantics. As soon as the effect leaves Kafka (a database write, an e-mail, a payment), you are back to at least once plus idempotent processing, or to storing the offset in the same database transaction as the effect.

Talk track

"I'd design for at-least-once delivery and make every consumer idempotent: the thumbnail job upserts by photo id, and the notification consumer records the event id in the same transaction as the notification row, so a redelivered event is skipped. Exactly-once delivery doesn't exist; exactly-once effect is at-least-once plus deduplication."

9.4The outbox pattern: publishing events reliably

The upload service must do two things: insert the photo row into PostgreSQL and publish "photo uploaded" to Kafka. These are two different systems without a shared transaction, a dual write. If the service commits the row and then crashes before publishing, the photo exists but no follower ever sees it in the feed. If it publishes first and the database insert then fails, consumers process a photo that does not exist. Retrying does not fix this, because the process may die at any point between the two writes.

The transactional outbox turns two writes into one. The service inserts the photo row and an event row into an outbox table in one database transaction. A separate relay reads new outbox rows and publishes them to Kafka, marking them as sent (or deleting them) afterwards. If the relay crashes after publishing but before marking, it publishes the same event again after restart, so consumers must deduplicate by event id; this is at-least-once delivery with a guarantee that no event is lost and none is invented. The relay is usually change data capture (CDC): Debezium reads PostgreSQL's logical replication stream or MySQL's binlog, which preserves commit order and adds no polling load. The mirror image on the consumer side is an inbox table that records processed event ids in the same transaction as the consumer's own change.

In practice

CDC is useful far beyond the outbox: it feeds search indexes, caches (Section 4.3) and analytics stores from the database's commit log, so every derived copy follows the source of truth in order. The database stays the single place where writes happen, and everything else is a projection of its log.

9.5Operating queues: ordering, poison messages and lag

Three issues come up in every real pipeline. Ordering: within a partition order is guaranteed, but a consumer that processes messages in parallel threads, or retries one message later while moving on, breaks it. If order matters per entity, key the messages by that entity and process each key sequentially. Poison messages: a message that always fails (bad data, a bug) blocks its partition forever if the consumer retries it endlessly. After a few retries with backoff, move it to a dead-letter queue for inspection and continue; alert when the dead-letter queue is not empty. Lag: if consumers fall behind, the lag grows; alert on lag in time ("feed updates are 5 minutes behind") rather than in messages, add consumers up to the partition count, and make sure the backlog after an outage can be drained faster than new messages arrive.

Pitfall

A queue hides overload instead of solving it. If consumers are permanently slower than producers, the queue grows until it hits a limit or the messages expire, and the system has turned "slow" into "silently dropping data". Queues absorb bursts; sustained overload needs more consumers or backpressure on producers (Section 10.2).

In automotive

A vehicle-fleet data backend has the same shape at a different scale: hundreds of thousands of cars upload diagnostic events and short sensor clips over cellular links that drop for minutes in tunnels. Vehicles buffer and resend, so ingestion must be idempotent (a per-vehicle sequence number as the dedup key), events arrive late and out of order (process by event time, not arrival time), and partitioning by vehicle id keeps each car's events ordered. Bulk clips go to object storage via presigned URLs, only the metadata to Kafka. The automotive side of such a system is in Software architecture 14.3.

10Protecting the system: rate limits, backpressure and idempotency

Every system has a capacity, and demand does not respect it: a client in a retry loop, a viral post, a crawler, a partner's batch job. A system that accepts all work slows down for everyone and then falls over. The tools in this chapter decide which work to accept, slow down the sources of excess work, and make retried work safe.

10.1Rate limiting algorithms

A rate limiter caps how many requests a client (identified by user id, API key or IP address) may make per unit of time, and rejects the rest, usually with HTTP 429 Too Many Requests and a Retry-After header. It protects the service from abuse and from buggy clients, and it divides capacity fairly among tenants. Four algorithms are common, and they differ in how they treat bursts.

The token bucket holds up to B tokens and refills at rate r per second; each request takes a token or is rejected. It allows bursts up to B and an average rate of r, which matches how real clients behave (a phone opening the app fires ten requests at once, then little). It needs two numbers per client (token count and last refill time), and it is what AWS API Gateway, Stripe and most gateways use. The leaky bucket is its mirror: requests enter a queue that drains at a fixed rate, which smooths output for a downstream that cannot take bursts, at the cost of added latency. The fixed window counter counts requests per calendar window (per minute) and resets at the boundary: one integer per client, but it lets through twice the limit around a boundary. The sliding window log stores the timestamp of every request and counts those in the last window: exact, but memory grows with the limit. The sliding window counter estimates the sliding count as the current window's count plus the previous window's count weighted by how much of it still overlaps; it is nearly exact with two integers per client. The underlying two-pointer technique is in Algorithms 7.3.

In a distributed service, many gateway instances must share each client's counter, otherwise a client gets the limit once per instance. The standard solution keeps the state in Redis and updates it atomically with a short Lua script (read tokens, refill by elapsed time, take one, write back), so one round trip per request decides it. To save that round trip on very hot paths, instances can take small batches of tokens locally and sync with the central store periodically, accepting a slight overshoot. Two decisions remain: what to do if the limiter's store is unreachable (fail open, accepting all, is usual for public APIs; fail closed protects fragile back ends), and where to limit (at the edge per client, and again in front of expensive internal services).

Pitfall

A rate limit is not a capacity plan. Per-client limits stop one client from hogging the service, but 100,000 clients each within their limit can still overload it. Capacity protection needs global load shedding and concurrency limits (Section 10.2) in addition to per-client fairness.

10.2Backpressure and load shedding: why systems fall over near 100 %

The reason systems fail abruptly under load, rather than gradually, is queueing. When requests arrive randomly, they sometimes bunch up, and a queue forms even when the server is on average not fully busy. The busier the server, the longer the queues: for a single server with random arrivals and service times, the mean waiting time grows like ρ / (1 − ρ), where ρ is the utilisation. Going from 50 % to 90 % utilisation multiplies the wait by nine, and from 90 % to 95 % doubles it again. Figure 10.2 shows the p99 response time from the M/M/c queueing model, servers with a shared queue.

Two lessons follow. First, run with headroom: services are sized to run at 50 to 70 % utilisation at peak, not 95 %, because the last 30 % of capacity costs a large multiple in tail latency. Second, pooling helps: one queue in front of many workers (one thread pool, least-loaded or power-of-two balancing) gives much better tails than many separate queues, because an idle worker never waits while another has a backlog.

When demand exceeds capacity anyway, the system must refuse work rather than accept it all slowly; otherwise every request times out, clients retry, and the load doubles (a retry storm, see Software architecture 9.4). Bounded queues are the foundation: a queue with a limit rejects new work when full instead of letting latency grow without bound (the in-process version is in Concurrency 8.2). Load shedding rejects requests early and cheaply when the server is overloaded, preferring to drop low-priority traffic (prefetches, analytics) before user-facing requests. Concurrency limits cap the number of in-flight requests per server; adaptive versions (Netflix's concurrency-limits library, inspired by TCP congestion control) adjust the cap from observed latency. Deadline propagation passes the client's remaining time budget along every call (gRPC deadlines), so a back end does not waste work on a request whose client has already given up. Circuit breakers stop calling a dependency that is failing and fail fast instead (Software architecture 12.2). Together, these are backpressure: the slow part of the system pushes back on the fast part, instead of drowning.

From the model (10 ms exponential service): one server, p99 = 92 ms at 50 %, 154 ms at 70 %, 230 ms at 80 %, 460 ms at 90 %, 921 ms at 95 %. Eight servers sharing a queue: 46, 48, 52, 71 and 124 ms. 10.3Idempotency keys: making retries safe

Clients must retry, because networks lose responses: a timeout does not tell the client whether the request failed or only the answer was lost. For reads and for naturally idempotent writes (PUT a resource, DELETE it) a retry is harmless. For creating things, such as a payment, an order or a post, a retry after a lost response creates a duplicate. The general argument is in Software architecture 9.3; the standard web mechanism is the idempotency key, popularised by Stripe's API.

The client generates a random key (a UUID) once per user intent ("pay this order"), not per attempt, and sends it in an Idempotency-Key header. The server, in order: inserts the key into a store with a unique constraint and state "started" (if the insert fails because the key exists, it is a retry); performs the operation; stores the response (status and body) with the key and marks it "done". A retry that finds "done" returns the stored response without acting. A retry that finds "started" means the first attempt is still running or crashed midway: return 409 Conflict and let the client retry later, and have a recovery job that finishes or rolls back stale "started" entries. The server should also store a hash of the request body and reject the same key with a different body (a client bug). Keys expire after a day or so.

The subtle part is atomicity between the key record and the effect. If the effect is in the same database as the key store, do both in one transaction. If the effect is external (charging a card through a payment provider), pass the idempotency key on to the provider too, so the provider deduplicates its side; this is why payment APIs accept idempotency keys. A worked decision record for this design is in Software quality 9.2.

Pitfall

Generating the key on the server, or per retry attempt on the client. Then every retry carries a new key and nothing is deduplicated. The key identifies the intent, so it must be created where the intent originates, before the first attempt, and survive app restarts if the retry can happen after one.

11Microservices in practice

Splitting a backend into services is mostly about people: it lets many teams build, deploy and scale their parts independently. The technical machinery in this chapter (protocols, service discovery, a mesh, Kubernetes) exists to make many small services behave like one reliable system, and it is a real cost that a small team should not pay too early.

11.1When to split, and where the boundaries go

A well-structured monolith scales horizontally behind a load balancer just like services do (Chapter 2), so scale alone is rarely the reason to split. The reasons are organisational and operational: teams blocking each other on one codebase and one release train; parts with very different resource profiles (a CPU-heavy image pipeline next to latency-sensitive APIs); parts with different reliability needs (payments versus recommendations); or a component that must be written in a different language. The architectural trade-offs, including modular monoliths, are in Software architecture 4.4.

Good service boundaries follow business capabilities (users, photos, feed, notifications, payments), not technical layers (a "database service" or a "validation service"). Each service owns its data: no other service reads its tables directly, because shared tables couple services more tightly than any API and make independent deployment impossible. Data that another service needs is either asked for through the API or copied into the other service through events (Chapter 9), accepting eventual consistency. The test of a boundary is how often a feature needs coordinated changes in several services; if it is often, the boundary is wrong.

Pitfall

The distributed monolith: services that must be deployed together, call each other synchronously in long chains, and share a database. It has all the costs of distribution (network latency, partial failures, harder debugging) and none of the independence. If a single user request fans out through eight synchronous hops, its availability is the product of eight availabilities and its latency the sum of eight latencies.

11.2REST, gRPC, GraphQL and asynchronous messages

Services talk in one of four styles. REST over HTTP with JSON is the lingua franca: resources and HTTP verbs, readable payloads, caching through HTTP semantics, and every tool in the world understands it, which makes it the default for public APIs and web clients. gRPC uses Protocol Buffers over HTTP/2: a schema compiled into typed client and server code, compact binary messages, multiplexed streams, built-in deadlines and cancellation, and streaming in both directions; it is the common choice between internal services, especially in polyglot environments. GraphQL lets the client ask for exactly the fields it needs across several resources in one request, which suits a BFF serving varied mobile and web screens, at the cost of harder caching and the risk of expensive queries. Asynchronous messages (Chapter 9) are not request-response at all and decouple services in time.

11.3Service discovery and the service mesh

In a fleet where instances start, stop and move every few minutes, a caller cannot be configured with IP addresses. Service discovery keeps a live registry of healthy instances per service. In server-side discovery the caller sends to a stable name or virtual IP and a load balancer resolves it (a Kubernetes Service, an AWS internal load balancer). In client-side discovery the caller's library reads the registry (Consul, etcd, Eureka, or the Kubernetes endpoints API) and picks an instance itself, saving a hop and allowing smarter balancing. DNS-based discovery is simple but suffers from caching and gives little control over balancing.

As the number of services grows, every one of them needs the same networking features: timeouts, retries with budgets, circuit breaking, load balancing, mutual TLS for encryption and service identity, and metrics and traces for every call. Implementing these in libraries for every language is costly and inconsistent. A service mesh moves them into a proxy next to each instance, the sidecar (usually Envoy), through which all traffic flows; a control plane (Istio, Linkerd, Consul Connect) configures all proxies and issues their certificates. The application makes a plain call to photo-service; the sidecar encrypts it, picks a healthy instance, retries if allowed and records the latency. The cost is an extra hop (typically well under a millisecond per proxy), CPU and memory for thousands of proxies, and a complex system to operate; newer "ambient" or sidecar-less designs move the proxy to a per-node component to reduce that cost.

Why it matters

A mesh makes the behaviour of the network uniform and observable across all services without code changes, which is valuable at dozens or hundreds of services. With five services, a good HTTP client library with timeouts and retries plus a load balancer is simpler and enough.

11.4Kubernetes as the runtime

Kubernetes has become the standard runtime for services, and its core idea is declarative reconciliation: you store the desired state ("three replicas of photo-service, image version 1.8, 500 millicores and 512 MiB each") in the API server, and controllers continuously compare it with the actual state and act to close the gap (Programming languages 10.2 explains the idea). The state lives in etcd, a Raft-replicated store (Section 8.4). Containers themselves, namespaces and cgroups are explained in Build systems 9.2.

The objects map onto the concepts of this chapter. A Pod is one instance: one or more containers sharing a network address, the unit of scheduling. A Deployment keeps N identical pods running and performs rolling updates, replacing a few pods at a time and waiting for each new pod to become ready, so a bad version can be stopped and rolled back. A Service is server-side discovery and L4 balancing: a stable DNS name and virtual IP that forward to the pods currently passing their readiness probe. An Ingress or the newer Gateway API is the L7 entry point. A HorizontalPodAutoscaler changes the replica count from CPU or custom metrics such as request rate. Probes encode health: a readiness probe decides whether a pod receives traffic (fail it while warming caches or when overloaded), a liveness probe decides whether the container is restarted (keep it simple, or a slow dependency makes Kubernetes restart healthy pods in a loop). Resource requests and limits tell the scheduler how much CPU and memory a pod needs, and the limits are enforced by cgroups: a pod over its memory limit is killed, one over its CPU limit is throttled, which shows up as latency spikes.

In practice

Stateless services fit Kubernetes perfectly. Databases and other stateful systems can run on it (StatefulSets, persistent volumes, operators such as CloudNativePG or Strimzi for Kafka), but many teams keep them on managed cloud services instead, because failover, backups and upgrades of stateful systems are where most of the operational risk lies.

Talk track

"Each service is a Deployment behind a Service, with readiness probes so new pods get traffic only when warmed up, and an autoscaler on request rate. Rolling updates with a canary step catch bad versions. Stateful systems, the database and Kafka, are managed services; Kubernetes runs only the stateless tier."

12Observability and reliability at scale

In a single process, a debugger and a log file explain most problems. In a system of fifty services and a hundred instances each, nobody can attach a debugger to "the request that was slow for some users in Brazil". Observability is the ability to answer such questions from the outside, from data the system emits, and it has to be designed in from the start.

12.1Metrics, logs and traces

Three kinds of telemetry answer different questions. Metrics are numbers aggregated over time: request rate, error rate, latency histograms, queue depth, CPU. They are cheap to store and fast to query, so they drive dashboards and alerts and answer "is something wrong, and since when?". Logs are records of individual events, ideally structured (JSON with fields such as request id, user id, route, status), and answer "what exactly happened to this request?". Traces follow one request across all the services it touches and answer "where did the time go?". The OpenTelemetry project standardises the APIs and the wire format for all three, so instrumentation is independent of the back end (Prometheus, Grafana, Jaeger, Tempo, Datadog, Honeycomb and others).

Two checklists help decide which metrics to collect. For every service, the RED method: Rate, Errors and Duration of requests. For every resource (CPU, disk, connection pool, queue), the USE method: Utilisation, Saturation (work waiting) and Errors. Latency must be recorded as a histogram, not an average: averages hide the tail, and percentiles cannot be averaged across instances (the mean of ten p99s is not the fleet's p99), whereas histogram buckets can be summed and the percentile computed afterwards.

Pitfall

Cardinality: every distinct combination of label values is a separate time series. A metric labelled with user id or full URL creates millions of series and can take down the metrics system. Put high-cardinality details into logs and traces; keep metric labels to bounded sets such as route template, status class and region.

12.2Distributed tracing

A trace is a tree of spans. Each span records one operation (an incoming request, an outgoing call, a database query) with a start time, a duration, a parent span and attributes. When the gateway receives a request, it starts a trace with a random trace id; every outgoing call carries the trace id and the current span id in a header (the W3C traceparent standard), and each service creates its spans as children. A tracing back end collects the spans and draws the waterfall.

Tracing every request is expensive at high volume, so traces are sampled. Head-based sampling decides at the start (keep 1 %), which is cheap but mostly keeps boring requests. Tail-based sampling buffers spans and decides after the request finishes, keeping all errors and slow requests plus a small share of the rest, which is what you want for debugging but needs a collector tier with memory. Logs become much more useful when every log line carries the trace id, so you can jump from a slow span to the logs of exactly that request.

12.3SLOs, error budgets and the arithmetic of availability

Reliability needs a target, otherwise every incident is a crisis and every risk is unacceptable. A service level indicator measures what users experience (the share of feed requests answered successfully within 300 ms); a service level objective sets the target for it (99.9 % over 30 days); the error budget is the remainder (0.1 %, about 43 minutes of full outage a month) that the team may spend on releases and experiments. How SLOs, burn-rate alerts and error-budget policies work as a process is in Software quality 11.1 and 11.2; this section adds the arithmetic that system design needs.

Availabilities of components that a request needs in series multiply: a request that passes through a gateway (99.99 %), a feed service (99.9 %) and a database (99.95 %) can be at most about 99.84 % available. Every synchronous dependency lowers the ceiling, which is a strong argument for fewer hops and for degrading gracefully (show the feed without like counts if the like service is down). Redundant components in parallel multiply their unavailabilities: two independent replicas at 99 % each give 1 − 0.01² = 99.99 %, provided failures are truly independent, which is why replicas go into different availability zones. Each additional nine costs roughly ten times more effort; the general numbers are in Software architecture 12.5.

Tail latency has its own arithmetic. If a request fans out to many back ends in parallel and must wait for all of them, its latency is the slowest one. With each back end slower than its own p99 in 1 % of calls, the probability that at least one of n is slow is 1 − 0.99n: 9.6 % for 10 back ends and 63.4 % for 100. A fan-out over 100 shards turns every back end's rare p99 into the typical case. Remedies from Dean and Barroso's The Tail at Scale: hedged requests (send a second copy to another replica if the first has not answered within the p95, and use whichever answers first), tied requests, smaller fan-out, and returning partial results when a few back ends are late.

Numbers

Downtime per year: 99 % = 3.65 days; 99.9 % = 8.8 hours; 99.95 % = 4.4 hours; 99.99 % = 53 minutes; 99.999 % = 5.3 minutes. Per 30 days, 99.9 % allows 43 minutes. Fan-out: P(at least one of n back ends beyond its p99) = 1 % for 1, 9.6 % for 10, 63.4 % for 100.

12.4Reliability patterns of large systems

Large systems fail all the time in small ways, so reliability comes from containing failures rather than avoiding them. Redundancy across failure domains: replicas in at least three availability zones (separate buildings, power and networks within a region), so that losing a zone loses a third of capacity, not the service; and capacity planned for N+1 or N+2, so that the remaining zones can carry the load. Bulkheads: separate pools of threads, connections or even whole cells of infrastructure, so that one overloaded tenant or feature cannot exhaust shared resources; cell-based architectures go furthest, serving each slice of customers from a complete, independent copy of the stack, so that a bad deploy or a poison request affects one cell. Graceful degradation: decide in advance what to switch off when a dependency fails (recommendations, like counts, image quality) and keep the core path working. Safe change: most outages are caused by changes, so roll out progressively (canaries, feature flags, one region or cell at a time) with automatic rollback on SLO burn (Software quality 10.4). Testing failure: inject faults deliberately (kill instances, add latency, block a zone) in a controlled way, as in chaos engineering, to verify that the redundancy actually works before a real failure tests it.

Talk track

"I'd define two SLIs for the feed, availability and p99 latency under 300 ms, with a 99.9 % objective. Every service exports RED metrics as histograms, logs are structured with the trace id, and traces are tail-sampled to keep all errors and slow requests. The fleet runs in three zones with enough headroom to lose one, changes roll out through canaries gated on the SLO, and the feed degrades to a cached version if the ranking service fails."

13Worked designs

The classic design exercises are small enough to discuss in 45 minutes and rich enough to need most of this chapter's tools. Each design below follows the method of Section 1.2: requirements and numbers first, then API and data, then the high-level design, then the one or two deep dives that decide the design, then the trade-offs.

13.1URL shortener

Requirements. Given a long URL, return a short one such as sho.rt/aZ3kQ9x; visiting the short URL redirects to the long one. Optional: custom aliases, expiry, click analytics. Non-functional: redirects must be fast (they sit in front of every click) and highly available; a short code must never point to the wrong URL. Numbers. 100 million new links per month is about 40 writes per second; with 10 redirects per link, about 400 reads per second on average and a few thousand at peak. Over five years, 6 billion links at about 500 bytes each is 3 TB. A 7-character code over 62 characters (a to z, A to Z, 0 to 9) gives 627 ≈ 3.5 trillion codes, far more than needed. So: tiny write load, moderate read load, small data; the design questions are code generation and read latency.

API and data. POST /links {url} returns the code; GET /{code} returns a redirect. One table, keyed by code: long URL, owner, creation time, expiry. This is a pure key-value access pattern, which fits any store; PostgreSQL is fine at this size, DynamoDB or Cassandra if it must grow without limit.

Deep dive: generating codes. Three approaches. Hash the long URL (for example the first 43 bits of a SHA-256, in base62): the same URL always gets the same code, but different URLs can collide, so every insert must check and handle collisions. Random codes: generate 7 random characters and insert with a uniqueness constraint, retrying on the rare collision; simple, unpredictable, and the collision probability stays tiny while the space is mostly empty. A counter in base62: every link gets the next integer, which is unique by construction and needs no check. A single counter is a bottleneck and a single point of failure, so each app server takes a block of 1,000 values from a central allocator (a database sequence or a ZooKeeper node) and hands them out locally; a crashed server just wastes the rest of its block. Sequential codes are guessable, which lets anyone enumerate all links; if that matters, permute the counter with a keyed bijection (a small block cipher) before encoding. Twitter's Snowflake ids (timestamp, machine id and sequence packed into 64 bits) are another way to generate unique ids without coordination.

Deep dive: the read path. Redirects are a cache-aside read of an immutable value: once created, a link never changes, so there is no invalidation problem, and a cache of the hottest 20 % of links absorbs most traffic. The redirect status code is a product decision: 301 Moved Permanently is cached by browsers, which removes repeat traffic but also hides repeat clicks from analytics; 302 Found sends every click through the service. Click events go to Kafka and into an analytics store, never into the redirect's own database write path.

Talk track

"Writes are only about 40 per second, so the interesting parts are unique code generation and fast redirects. I'd allocate counter blocks to each server and base62-encode them, permuted if guessability matters. Links are immutable, so redirects are cached aggressively with no invalidation. Analytics go through a queue so a slow analytics store can never slow a redirect."

13.2Distributed rate limiter

Requirements. Limit each API client by several rules (for example 100 requests per second and 100,000 per day), enforced across a fleet of 50 gateway instances; add under a millisecond to each request; return 429 with Retry-After; keep working if the limiter's store has problems. Numbers. At 1 million requests per second through the gateways, every request needs a limiter decision, so the limiter store must handle a million small atomic operations per second, with sub-millisecond latency: about ten to twenty Redis primaries at 50,000 to 100,000 operations each, partitioned by client id.

Design. Rules live in configuration, cached in every gateway. For each request, the gateway computes the key (client id plus rule) and runs one Lua script on the Redis shard that owns the key: it reads the token count and last refill time, adds tokens for the elapsed time up to the bucket size, takes one if available and writes back, all atomically because Redis executes a script without interleaving. The token bucket (Section 10.1) is the usual algorithm because it allows natural bursts; the sliding-window counter is the alternative when the limit must hold over any window. Expire the keys after inactivity so idle clients cost nothing.

Deep dives. Latency and load: one Redis round trip per request is about 0.2 to 0.5 ms within a zone; to cut it, each gateway can reserve a small batch of tokens per hot client locally and refill from Redis in the background, trading a little accuracy for no per-request round trip. Failure: if Redis is unreachable, fail open with a local, conservative in-memory limiter per instance, so a limiter outage never becomes an API outage. Multiple regions: global limits need cross-region coordination on every request, which costs 100 ms; usually each region enforces its share of the global limit (or limits are per region), with asynchronous reconciliation. Fairness under overload: per-client limits do not protect total capacity, so the gateway also sheds load globally (Section 10.2).

Pitfall

Implementing the check as two separate commands (GET the counter, then INCR it if below the limit). Between them, other gateways do the same, and the limit is exceeded under exactly the concurrent load it exists to stop. The check and the update must be one atomic operation: a Lua script, INCR with the comparison on its result, or a single Redis command designed for it.

13.3Chat system

Requirements. One-to-one and group chats (up to a few hundred members), messages delivered in real time to online users and by push notification to offline ones, history synchronised across a user's devices, sent/delivered/read receipts, online presence. Messages must not be lost or reordered within a conversation. Numbers. 50 million daily users sending 40 messages a day is 2 billion messages a day, about 23,000 per second on average and 70,000 at peak. At 200 bytes per message, history grows by 400 GB per day, about 150 TB per year before replication. If 20 million users are connected at the evening peak and a gateway server holds about 100,000 connections, the connection tier needs around 200 servers.

Connections. Real-time delivery needs the server to push, so clients hold a persistent connection, usually a WebSocket (long polling as a fallback). The gateway tier is stateful by nature: Bob's socket lives on gateway 7. A session registry (Redis, with a TTL refreshed by heartbeats) maps each online user's devices to their gateways. Gateways are kept thin: they authenticate, hold sockets and forward frames, and all logic lives in stateless chat services behind them, so a gateway restart only means clients reconnect to another gateway and resynchronise.

Sending a message. Alice's client gives each message a client-generated id and sends it over her socket. The chat service assigns a server-side id that orders the message within the conversation (a per-conversation sequence from the conversation's owner, or a time-ordered id such as Snowflake), stores it, and acknowledges to Alice, which turns her clock icon into one tick. It then looks up the recipients' gateways and pushes the message; Bob's client acknowledges receipt (two ticks). If Bob is offline, a push notification is sent through APNs or FCM, and his devices fetch everything since their last seen message id when they reconnect. Delivery is at-least-once (clients resend unacknowledged messages after reconnecting), and duplicates are removed with the client message id.

Storage. The access pattern is "write a message" and "read the latest messages of one conversation, page backwards", at 70,000 writes per second, a textbook wide-column workload: partition key conversation_id (often combined with a time bucket so a busy group's partition does not grow forever), clustering key the message id in descending order. Cassandra, ScyllaDB, HBase and Bigtable are typical choices. Groups are fan-out: a message to a 200-member group is stored once and pushed to each online member's gateway. Very large channels switch to pull (members fetch new messages when they open the channel) for the same reason as the news feed below. Presence is soft state: each client heartbeats every 30 seconds or so; a user is online if seen recently; presence changes are pushed only to contacts who are currently looking, because broadcasting every change to every contact would cost more than the messages themselves.

Interesting detail

With end-to-end encryption (the Signal protocol, used by Signal and WhatsApp), the server stores and forwards ciphertext it cannot read, and multi-device support becomes a key-distribution problem: a message is encrypted separately for each of the recipient's devices. The architecture above stays the same; search over history moves to the clients.

13.4News feed

Requirements. The home feed shows recent posts from the accounts a user follows, newest first or ranked, with infinite scrolling; it must load in under 300 ms at p99. A new post should appear in followers' feeds within seconds. Numbers. For the photo service: 1 million posts per day, users follow 200 accounts on average, and 10 million daily users open the feed 10 times a day, so 100 million feed reads per day, about 1,200 per second on average and 3,500 at peak. The key number is the fan-out: 1 million posts × 200 followers = 200 million feed insertions a day, about 2,300 per second on average, but one post by an account with 10 million followers is 10 million insertions on its own.

Fan-out on write (push) precomputes each user's feed: when Ana posts, a worker reads her followers from the social graph (from a Kafka event, so the post itself returns fast) and prepends the post id to each follower's feed list in Redis, capped at a few hundred ids. Reading the feed is one list read plus a batch lookup of the posts by id (from the post cache). Reads are fast and predictable, which matters because reads outnumber posts many times over. The costs: write amplification proportional to follower counts, wasted work for followers who never log in, and minutes of fan-out for an account with millions of followers. Fan-out on read (pull) stores only each author's own posts; at read time it fetches the latest posts of all 200 followees, merges and ranks them. Writes are cheap and there is no celebrity problem, but every feed load is 200 lookups and a merge, which is slow at p99 and expensive at 3,500 loads per second.

The hybrid used in practice: push for ordinary accounts, pull for accounts with very many followers. When Bob opens his feed, the service reads his precomputed list and merges in the recent posts of the few celebrities he follows, fetched at read time and cached heavily because many users need the same ones. Feeds are kept precomputed only for active users; a returning user's feed is rebuilt on demand by the pull path. Twitter described this hybrid for its home timeline publicly in the early 2010s. Ranking adds two stages on top: candidate generation (the merged list, plus suggested posts) and a ranking model that orders a few hundred candidates by predicted engagement. Pagination uses a cursor (the last post id seen), not an offset, so new posts at the top do not shift or duplicate the next page.

Talk track

"Reads outnumber posts by a large factor, so I precompute feeds by fanning out on write, asynchronously through Kafka, into capped Redis lists of post ids. The exception is celebrity accounts above a follower threshold: their posts are pulled and merged at read time, which bounds the fan-out cost. Inactive users get no precomputed feed; we rebuild it when they come back."

13.5File storage and sync

Requirements. Users store files of any size up to tens of gigabytes, and changes sync to all their devices within seconds; files have versions and can be shared. Data must never be lost. Numbers. 10 million users with 5 GB each is 50 PB of logical data; at three full replicas that would be 150 PB of disk, which is why storage efficiency is a first-order design concern. Metadata (file tree, versions, chunk lists, sharing) is small by comparison but has the hardest consistency requirements.

Chunking is the central idea. The client splits each file into blocks of a few megabytes (Dropbox has described 4 MB blocks) and identifies each block by its content hash (SHA-256). A file version is then just an ordered list of hashes. This gives three things at once: resumable uploads (a dropped connection loses one chunk, not the file), delta sync (editing a small part of a large file changes one or a few chunks, and only those are uploaded), and deduplication (a chunk that already exists, in this user's files or anyone's, is never stored twice). Content-defined chunking, which cuts at boundaries derived from the content itself, keeps chunks stable even when bytes are inserted at the start of a file.

Two separate stores. Chunk bytes go to object storage, uploaded and downloaded directly by the client with presigned URLs, so they never pass through the app servers. Durability there comes from erasure coding rather than full copies: a Reed-Solomon scheme with 6 data and 3 parity fragments survives the loss of any 3 fragments with 1.5× storage overhead instead of 3×, which at 50 PB saves 75 PB of disk. The metadata service owns the namespace (folders, files, versions, chunk lists, permissions) in a strongly consistent, transactional database sharded by user or shared-folder namespace; committing a new version is a transaction that checks the client based its change on the latest version. If not, two devices edited concurrently, and the usual resolution is to keep both and create a "conflicted copy" for the user to sort out, because merging arbitrary files automatically is impossible. A notification service holds a long poll or WebSocket per device and tells it that its namespace changed; the device then asks the metadata service what changed since its last cursor.

Why it matters

The split between bytes and metadata recurs in every storage-heavy design (photos, video, backups, ML datasets): put the large immutable bytes in cheap, durable object storage addressed by id or hash, and keep the small mutable metadata in a database with transactions. Each store then does what it is good at, and the hard consistency problems are confined to the small part of the data.

QSelf-check questions

Q.1Core questions

How do you approach a system design question?Basic

Clarify functional scope and non-functional requirements (scale, latency, availability, consistency), estimate load and storage, define the API and data model with the access patterns, draw a high-level design walking one read and one write end to end, then deep-dive into the bottleneck the numbers point to and its failure modes, and finish with trade-offs and what changes at ten times the load. Use the numbers to justify each component.

Estimate the load of a photo service with 10 million daily users.Basic

With 0.1 uploads and 50 views per user per day: 1 M uploads a day ≈ 12/s average, ~35/s at a 3× peak; 500 M views a day ≈ 5,800/s, ~17,000/s at peak; 1 TB of new photos per day at 1 MB each, 365 TB a year; metadata about 180 GB a year. Conclusion: writes fit one database, image bytes need object storage and a CDN, and the read path needs caching.

What is the difference between an L4 and an L7 load balancer?Basic

L4 forwards TCP or UDP connections by address and port without parsing the payload: very fast, millions of connections, but one backend choice per connection. L7 terminates the connection and reads each HTTP request: it routes by path or header, retries idempotent requests, terminates TLS, authenticates and balances individual requests on multiplexed HTTP/2 or gRPC connections, at a CPU cost per request. Large systems put L4 in front of a fleet of L7 proxies.

Why is power of two choices a good load-balancing policy?Intermediate

Random assignment leaves some servers with long queues by bad luck, which dominates the tail. Sampling two servers and taking the less loaded one avoids the worst queues almost always, while needing only local, possibly stale information. In the simulation at 90 % load, p99 fell from 45 to 11 service times, close to the 8 of a perfect least-loaded balancer.

Explain cache-aside and why writes delete the key instead of updating it.Basic

Reads check the cache, load from the database on a miss and store the result with a TTL; writes update the database and delete the cache key. Deleting is idempotent and independent of order: if two writers set new values in the cache, their sets can arrive in the opposite order of their commits and leave the older value cached, while a delete just forces the next reader to load the current row.

What is a cache stampede and how do you prevent it?Intermediate

When a popular key expires, many concurrent requests miss and all run the same expensive query, overloading the database. Prevent it with request coalescing (one loader per key, others wait), refreshing hot keys in the background before they expire (probabilistic early refresh, stale-while-revalidate), and jittered TTLs so related keys do not expire together.

SQL or NoSQL for a new service?Basic

Choose by access patterns and consistency needs, not fashion. A relational database is the default: flexible queries, transactions, constraints, and it scales further vertically and with read replicas than most products need. Choose a wide-column or key-value store when the access pattern is known, keyed and enormous (messages, events, time series), a document store for self-contained entities, and distributed SQL when you need both SQL transactions and horizontal write scale.

Compare B-tree and LSM-tree storage engines.Intermediate

B-trees keep sorted pages and update them in place after logging; reads take a few page visits and are predictable, writes are random and rewrite whole pages. LSM trees buffer writes in memory, flush sorted immutable files and merge them by compaction; writes are sequential and cheap, reads may check several files (helped by Bloom filters), and compaction costs I/O and can cause latency spikes. B-trees suit read-heavy OLTP; LSM suits write-heavy workloads. Measured: 1 M random inserts took 20 s in SQLite and 3.5 s in RocksDB.

Explain isolation levels and the anomalies they allow.Intermediate

Read committed (default in PostgreSQL, Oracle, SQL Server) prevents dirty reads but allows non-repeatable reads, lost updates and write skew. Snapshot isolation (PostgreSQL REPEATABLE READ) gives each transaction a consistent snapshot and in PostgreSQL detects lost updates, but allows write skew. Serializable prevents all anomalies, typically by aborting a transaction that must then be retried. Measured on PostgreSQL 16: a read-modify-write increment lost an update at read committed, and write skew left nobody on call under REPEATABLE READ but was aborted under SERIALIZABLE.

How do you prevent lost updates?Intermediate

Let the database do the change atomically (SET likes = likes + 1), lock the row while deciding (SELECT … FOR UPDATE), or use optimistic concurrency with a version column (UPDATE … WHERE version = 7 and retry if no row matched). Higher isolation levels detect it too, at the cost of retries.

Synchronous versus asynchronous replication?Basic

Synchronous: the leader waits for a follower before confirming a commit, so confirmed writes survive a leader loss, but every commit pays a round trip and stalls if the follower is unavailable. Asynchronous: the leader confirms immediately, so commits are fast and followers can be remote, but a failover can lose recently confirmed writes and followers serve stale reads. A common compromise is one synchronous follower plus asynchronous ones.

How do you give users read-your-writes consistency with read replicas?Intermediate

Read data the user may have just changed from the leader, for example the user's own profile, or all of their reads for a few seconds after a write; or store the log position of their last write in the session and read from a follower only after it has replayed that position. For monotonic reads, route each user consistently to the same follower.

How would you shard a users and photos database?Intermediate

Shard by user_id with hash partitioning, keeping each user's photos, follows and likes on the user's shard with compound keys such as (user_id, created_at), so the common queries hit one shard. Use many logical partitions mapped to fewer physical nodes so rebalancing moves whole partitions. Cross-user queries (search, global rankings) go to separate systems fed by events. Hot accounts get caching or special handling.

What is consistent hashing and why use virtual nodes?Intermediate

Nodes and keys are hashed onto a ring and each key belongs to the next node clockwise, so adding or removing a node moves only the keys in its arc, about 1/N, instead of nearly all keys as with hash mod N. With one point per node the arcs are uneven; placing each node at many points (virtual nodes) evens out the load (busiest node 2.3× fair share with 1 point, 1.2× with 100) and spreads a leaving node's keys over many others.

Explain the CAP theorem.Basic

When a network partition separates replicas, a system must either refuse some requests to stay linearizable (CP) or answer them and risk divergence (AP). Partitions are not optional, so the choice applies only during a partition; otherwise a system can be both consistent and available. PACELC adds that even without partitions there is a trade-off between latency and consistency.

How does Raft elect a leader and commit an entry?Advanced

A follower that hears no heartbeat within a randomised timeout becomes a candidate for a new term and requests votes; each node votes once per term and only for candidates whose log is at least as up to date as its own, so a candidate with a majority becomes leader. The leader appends client commands to its log and replicates them with AppendEntries; an entry is committed when a majority stores it. Because any electing majority contains a node with every committed entry, committed entries survive leader changes.

What do quorums W + R > N guarantee, and what not?Advanced

They guarantee that every read set overlaps every successful write set, so a read sees at least one copy of the latest acknowledged write. They do not by themselves give linearizability: concurrent writes need a conflict rule (last-write-wins loses data), failed partial writes are not rolled back, and sloppy quorums break the overlap temporarily. Read repair and anti-entropy make replicas converge.

Queue or log: RabbitMQ/SQS versus Kafka?Intermediate

A queue distributes tasks: each message goes to one consumer and is deleted on acknowledgement, with per-message redelivery and routing. A log stores an ordered, partitioned, retained stream that any number of consumer groups read independently and can replay, with order per partition. Use a queue for work distribution, a log for event streams with several consumers, replay or very high throughput.

How do you achieve exactly-once processing?Advanced

Exactly-once delivery is impossible over an unreliable network, so aim for exactly-once effect: at-least-once delivery (process, then commit the offset) plus idempotent processing, such as upserts by a natural key or a deduplication record of processed event ids written in the same transaction as the effect. Within Kafka, idempotent producers and transactions give exactly-once for Kafka-to-Kafka pipelines.

What problem does the outbox pattern solve?Intermediate

The dual write: a service that updates its database and publishes an event can crash between the two, losing the event or publishing one for a change that never committed. The outbox writes the event into a table in the same database transaction as the change; a relay (CDC such as Debezium, or a poller) publishes outbox rows afterwards. No event is lost or invented; duplicates are possible, so consumers deduplicate.

Design a rate limiter for an API.Intermediate

Token bucket per client and rule, state in a Redis cluster partitioned by client key, updated atomically with one Lua script per request; rules cached in the gateways; return 429 with Retry-After. Fail open with a local limiter if Redis is unavailable, optionally batch tokens locally for hot clients, and enforce global limits per region. Add global load shedding, because per-client limits do not protect total capacity.

Why does latency explode as utilisation approaches 100 %?Intermediate

Random arrivals bunch up, so queues form even below full load, and the mean wait grows like ρ/(1 − ρ). For one server with 10 ms service time, p99 is 92 ms at 50 % load, 460 ms at 90 % and 921 ms at 95 %. Hence services run at 50 to 70 % at peak and shed excess load rather than queueing it.

How do idempotency keys work?Intermediate

The client generates a unique key per intent and sends it with every attempt. The server records the key with state "started" under a uniqueness constraint, performs the operation, stores the response with the key and marks it done. A retry with a completed key returns the stored response; one with a key still in progress gets 409; the same key with a different body is rejected. External effects pass the key on (for example to the payment provider).

REST or gRPC between services?Basic

gRPC gives a typed schema with generated clients, compact binary messages, HTTP/2 multiplexing, streaming and built-in deadlines, which suits internal service-to-service calls. REST with JSON is universal, human-readable and cacheable, which suits public APIs and browsers. gRPC needs L7 or client-side load balancing because its connections are long-lived.

What does a service mesh do, and when is it worth it?Intermediate

A sidecar proxy next to every instance handles service-to-service traffic: discovery, load balancing, retries, timeouts, circuit breaking, mutual TLS and telemetry, configured centrally by a control plane. It makes networking behaviour uniform across languages without code changes, at the cost of extra hops, resources and operational complexity; it pays off with many services and teams, not with a handful.

What is the difference between readiness and liveness probes?Basic

Readiness decides whether a pod receives traffic; it should fail while the pod warms up or is overloaded. Liveness decides whether Kubernetes restarts the container; it should detect only a stuck process. Making liveness depend on downstream services causes restart loops of healthy pods during a dependency outage.

Metrics, logs and traces: what is each for?Basic

Metrics are cheap aggregated numbers for dashboards and alerts (is something wrong?). Logs record individual events in detail (what happened to this request?). Traces follow one request across services as a tree of timed spans (where did the time go?). Link them through a trace id in log lines and exemplars in metrics.

Design a URL shortener.Intermediate

About 40 writes/s and a few thousand reads/s at peak, 3 TB over five years. Codes from block-allocated counters encoded in base62 (7 characters give 3.5 trillion), optionally permuted against enumeration; a key-value table keyed by code; immutable links cached with no invalidation; 301 versus 302 depending on analytics; click events to a queue and an analytics store.

Design a news feed.Advanced

Precompute feeds with fan-out on write: a post event is consumed by workers that push the post id into capped per-user lists in Redis, so a feed read is one list read plus a batch post lookup. Celebrity accounts above a follower threshold are pulled and merged at read time to bound write amplification; inactive users' feeds are rebuilt on demand. Cursor pagination, a ranking stage over a few hundred candidates, and caches for posts and celebrity timelines.

Q.2Why and what if

Why make the app servers stateless before adding more of them?Why

Because otherwise requests must go to the server that holds their state: balancing becomes uneven, a crash or deploy loses sessions, and autoscaling cannot remove servers freely. With all state in shared stores, any instance can serve any request and instances are interchangeable.

What if the Redis cache cluster restarts at peak traffic?What if

The hit ratio drops to zero and the database, sized for the 1 to 10 % of reads that normally miss, receives all reads and likely collapses. Mitigations: replicated cache nodes restarted one at a time, request coalescing, load shedding in front of the database, warming the cache before taking traffic, and treating the cache as capacity in planning.

Why do immutable, content-addressed URLs make CDN caching easy?Why

Content at such a URL never changes, so it can be cached forever with no invalidation and no staleness; an edit produces a new URL. The hard problem of invalidation simply disappears for the bulk of the bytes.

What if two transactions both check "is this username free?" and then insert it?What if

At read committed or snapshot isolation both checks can succeed and both inserts happen, a write-skew or phantom problem. The robust fix is a unique constraint on the username, which the database enforces regardless of isolation level; the second insert fails and the application reports the name as taken.

Why can an index make writes slower?Why

Every insert or update of an indexed column must also update each index's tree, which means extra random page writes and log volume. A table with many secondary indexes pays that on every write; the measured index was also 37 % of the table's size.

What if the leader fails with asynchronous replication?What if

A follower is promoted, but writes the old leader confirmed and had not yet shipped are lost. If ids or other state derived from those writes were used elsewhere (caches, other systems), they can now conflict, as in the GitHub incident. Mitigate with a synchronous follower, fencing, and promoting only the most up-to-date follower.

Why does adding partitions not fix a hot key?Why

A single key always maps to a single partition, so all its traffic still lands on one node however many partitions exist. Hot keys need caching, local replicas, key splitting with random suffixes, or special application handling.

What if you use hash(key) mod N for a cache cluster and add a node?What if

About N/(N+1) of all keys change node (91 % from 10 to 11), so the cache becomes almost entirely cold at once and the database takes the full load: a self-inflicted stampede. Consistent hashing moves only about 1/(N+1).

Why are consensus clusters 3 or 5 nodes and not 4 or 10?Why

A majority must confirm every write, so an even number adds a member without adding fault tolerance (4 tolerates 1 failure like 3), and a larger cluster makes every write wait for more nodes. Five tolerates two failures, enough to survive one planned and one unplanned outage.

What if a network partition isolates the Raft leader with one follower out of five?What if

The old leader cannot reach a majority, so it cannot commit new entries; clients writing to it get no success. The other three elect a new leader in a higher term and continue. When the partition heals, the old leader sees the higher term, steps down, and its uncommitted entries are overwritten. No committed data is lost and there is never a committed split brain.

Why is last-write-wins dangerous for multi-leader replication?Why

It silently discards one of two concurrent writes, and "last" is decided by clocks that drift between machines, so even a write that happened later in real time can lose. Use single-home ownership, application merges or CRDTs when losing writes is not acceptable.

What if a Kafka consumer processes a message, writes to the database and crashes before committing the offset?What if

After restart or rebalance the message is delivered again and processed twice. That is at-least-once delivery working as designed; the processing must be idempotent or deduplicated, or the offset must be stored in the same database transaction as the result.

Why is order only guaranteed within a Kafka partition?Why

Partitions are independent logs on different brokers, consumed in parallel; a global order would require a single sequencer for all messages, which would cap throughput at one machine. Key messages by the entity whose events must stay ordered.

What if a fixed-window rate limiter is used for a login endpoint?What if

An attacker can send the full limit just before and again just after each window boundary, getting twice the allowed attempts in a short burst (200 instead of 100 in under two seconds in the simulation). A sliding-window counter or token bucket closes that gap.

Why do retries make an overload worse, and what limits the damage?Why

An overloaded service times out, clients retry, and the offered load multiplies exactly when capacity is short. Limit with exponential backoff and jitter, retry budgets (retries at most a small percentage of requests), retrying only idempotent calls, deadlines so abandoned requests are not processed, and circuit breakers.

Why does a fan-out over 100 shards have bad tail latency even if each shard is fast?Why

The request waits for the slowest shard, and with 100 shards the chance that at least one is beyond its own p99 is 63 %. The individual tail becomes the typical response time. Hedged requests, partial results and smaller fan-out help.

What if the idempotency key were generated on each retry attempt?What if

Each retry would look like a new request, the server could not recognise duplicates, and a lost response would still lead to a double charge. The key must identify the user's intent and be created once before the first attempt.

Why does the file storage design separate chunk bytes and metadata?Why

Bytes are large, immutable once written and need cheap durable storage that scales without coordination; metadata is small, mutable and needs transactions and strong consistency. Separate stores let each be optimised, keep bytes off the app servers, and confine the hard consistency problem to the small part.

Anycast

API gateway
A reverse proxy for APIs that adds authentication, rate limits, routing and request transformation.
Backpressure
Signalling from a slow component to its producers to slow down, through bounded queues, rejections or flow control.
Backend for frontend (BFF)
A gateway or aggregation service tailored to one client type, such as the mobile app.
Bloom filter
A compact probabilistic set that answers "definitely not present" or "possibly present"; used to skip files or avoid lookups.
CAP theorem
During a network partition a replicated system must choose between linearizability and availability.
Change data capture (CDC)
Reading a database's replication log to stream every committed change to other systems.
CDN
Content delivery network: a distributed fleet of caching proxies near users.
Circuit breaker
A client-side switch that stops calling a failing dependency for a while and fails fast instead.
Compaction
Merging LSM files to drop overwritten and deleted entries and keep reads efficient.
Consensus
Agreement of several nodes on one value or log order despite failures; Raft and Paxos are algorithms for it.
Consistent hashing
Hashing keys and nodes onto a ring so that membership changes move only about 1/N of keys.
Consumer group
A set of consumers sharing a topic's partitions, each partition read by one member; groups read independently.
Consumer lag
How far a consumer group's committed offset is behind the end of the log.
CRDT
Conflict-free replicated data type: a data structure whose concurrent updates merge deterministically.
Dead-letter queue
Where messages that repeatedly fail processing are moved for inspection.
Erasure coding
Splitting data into fragments plus parity so that any k of n fragments reconstruct it, with less overhead than replicas.
Error budget
The allowed unreliability implied by an SLO, spent on changes and risk.
Eventual consistency
Replicas converge if updates stop; reads may be stale meanwhile.
Failover
Promoting a follower to leader after the leader fails, and redirecting clients to it.
Fan-out on write / read
Building feeds by pushing new items to followers at write time, or by gathering them at read time.
Fencing token
A monotonically increasing number attached to a leadership or lock; storage rejects requests with older numbers.
Hedged request
A duplicate request sent to another replica when the first is slow; the first answer wins.
Hot key
A single key with disproportionate traffic that overloads the node owning it.
Idempotency key
A client-generated identifier per intent that lets a server recognise and safely answer retries.
Isolation level
How much concurrent transactions may observe of each other; read committed, snapshot, serializable.
Linearizability
The strongest single-object consistency: the system behaves like one copy with operations at single instants.
LSM tree
Log-structured merge tree: writes go to a memtable and immutable sorted files merged by compaction.
MVCC
Multi-version concurrency control: keeping several row versions so readers see snapshots without blocking writers.
Outbox pattern
Writing events to a table in the same transaction as the data, then relaying them to a broker.
Power of two choices
Load balancing by sampling two servers at random and choosing the less loaded.
PACELC
Extension of CAP: with a partition choose availability or consistency; else choose latency or consistency.
Partition (shard)
A subset of the data owned by one node or replica group.
Presigned URL
A time-limited signed URL that lets a client upload or download an object directly from object storage.
Quorum
The number of replicas that must acknowledge a write (W) or answer a read (R); W + R > N gives overlap.
Raft
A consensus algorithm based on leader election by terms and majority-replicated logs.
Read repair
Fixing stale replicas with the newest version seen during a quorum read.
Read-your-writes
A session guarantee that a client always sees its own previous writes.
Replication lag
The delay between a commit on the leader and its application on a follower.
Saga
A multi-step business transaction made of local transactions with compensating actions instead of 2PC.
Service mesh
Sidecar proxies plus a control plane that handle service-to-service networking uniformly.
SLO
Service level objective: a target for a measured indicator of user experience over a time window.
Split brain
Two nodes acting as leader for the same data at once, usually after a partition.
Cache stampede
Many simultaneous misses for one expired key overloading the source.
Token bucket
Rate-limiting algorithm with a bucket of B tokens refilled at rate r; allows bursts up to B.
Two-phase commit
Atomic commit across participants with a prepare phase and a commit phase; blocks if the coordinator fails.
Virtual node
One of many ring positions of a physical node in consistent hashing, used to even out load.
Write skew
An anomaly where concurrent transactions read overlapping data and write disjoint rows, breaking an invariant.
