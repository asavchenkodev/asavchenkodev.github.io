Computer networking and applied security

How a request really travels from a phone to a server and back, and how it is protected on the way: addressing, routing and names; TCP with its windows and congestion control; UDP, multicast and QUIC; sockets; HTTP/1.1 to HTTP/3 and gRPC on the wire; debugging and measuring; the cryptographic building blocks; TLS 1.3 and certificates; common attacks; and the engineering practice that keeps systems secure. The running example is one API call, GET https://api.example.com/photos/42, made by the photo-sharing app of the backend chapter. Every capture and number in the chapter was measured in a container on an emulated 20 Mbit/s link with 40 ms round-trip time.

1The big picture: layers, and what can go wrong between them

A network moves bytes between programs that do not share memory, over links that lose, reorder and delay packets, through equipment owned by other people. Networking is the set of protocols that turn that unreliable, shared, hostile medium into something a program can use; security is the part that makes it safe to use when someone on the path is an adversary.

1.1One API call, followed all the way down

When the photo app shows a picture, the code that asks for it is one line: an HTTP client is told to fetch https://api.example.com/photos/42. Everything this chapter is about happens underneath that line. The name api.example.com has to become an IP address, which needs a DNS query, which needs the phone to have an address and a default gateway in the first place. A TCP connection has to be opened to port 443 of that address, which costs one round trip before any data moves. A TLS handshake has to establish keys and prove that the server really is api.example.com, which costs another round trip and several kilobytes of certificates. Only then does the request leave, as an HTTP/2 frame inside a TLS record inside a TCP segment inside an IP packet inside a Wi-Fi or Ethernet frame. On the way it crosses a home router that rewrites its addresses, a dozen routers that each decide the next hop on their own, and perhaps a load balancer that reads the port numbers but not the content. The answer comes back the same way, paced by a congestion-control algorithm that is constantly guessing how much the path between the two machines can carry.

On the emulated link used in this chapter (Section 7.5), with a 40 ms round-trip time, that one line of code took 128 ms to get its first byte of response, of which only one round trip was the request itself; the rest was setup. That ratio, more than any bandwidth figure, is why networking knowledge matters to application developers: most slow requests are not slow because of bytes but because of round trips, and most broken ones break in one specific layer that can be identified if you know what each layer does.

Why it matters

Almost every system you build talks over a network, and almost every security incident involves one. The question "what happens when you type a URL into a browser" is a classic precisely because the answer shows whether you understand the layers or only the top one. The same knowledge decides practical things: whether to keep connections open, how to set timeouts, why a service is slow only for far-away users, why a firewall rule broke video calls, and what exactly a certificate error means.

1.2Layers and encapsulation: each layer adds a header and trusts the one below

Networking is layered because each layer solves one problem for the layer above and ignores the others. The link layer (Ethernet, Wi-Fi) moves a frame between two machines on the same physical network, identified by 48-bit MAC addresses. The network layer (IP) moves a packet between any two machines on the Internet by relaying it from link to link; it knows addresses and routes but promises nothing about delivery. The transport layer (TCP, UDP, QUIC) multiplexes many conversations onto one address with port numbers, and, in the case of TCP and QUIC, adds reliability, ordering and congestion control. Everything above, HTTP, gRPC, DNS, is the application layer. TLS sits between transport and application: it takes a reliable byte stream and makes it confidential and authenticated.

Each layer treats what it gets from above as an opaque payload and puts its own header in front (Ethernet also adds a trailer, the frame check sequence). That is encapsulation, and it explains a lot of behaviour. A switch only reads the Ethernet header, so it cannot route by IP address. A router reads the IP header and rewrites the Ethernet header at every hop, but leaves TCP alone. A NAT box or an L4 load balancer reads the port numbers in the TCP header, which is why they break when the transport header is encrypted, and why QUIC deliberately encrypts most of its own. Only the two endpoints see inside TLS.

The OSI model numbers seven layers; the Internet uses four or five, and engineers use the OSI numbers as names: "L2" for Ethernet and switches, "L3" for IP and routers, "L4" for TCP/UDP and load balancers that work on connections, "L7" for anything that understands HTTP. Session and presentation layers (OSI 5 and 6) have no separate protocols on the Internet; TLS is the closest thing to them.

Numbers

Ethernet MTU 1500 bytes of IP payload; IPv4 header 20 bytes, IPv6 40; TCP header 20 bytes plus options (Linux adds 12 bytes of timestamps to every segment), so a full-size segment carries 1448 bytes of data. On the wire each frame also costs 14 bytes of Ethernet header, 4 of FCS and 20 of preamble and inter-frame gap: 1538 bytes for 1448 bytes of payload, 94 % efficiency. TLS adds 5 bytes of record header and a 16-byte authentication tag per record of up to 16 kB.

1.3Security asks who can read, change or fake what

The original Internet protocols assumed cooperating parties: any machine on an Ethernet segment can read every broadcast and can claim any MAC or IP address; any router on the path can read and change any packet; DNS answers are believed if they arrive at the right port. Security engineering starts by stating which of these parties you do not trust and what you want to protect from them. For the photo app the honest answer is: the Wi-Fi in the café, every router between the phone and the data centre, and anyone who can send packets to the server are untrusted. The data needs confidentiality (nobody on the path reads the photos), integrity (nobody changes them), authenticity (the app talks to the real api.example.com, and the server knows which user is asking), freshness (an old request cannot be replayed) and availability (a flood of junk does not take the service down).

Cryptography provides the first four for data in transit, and TLS is how almost everything uses it. It does not help with availability, does not protect the endpoints themselves, and is only as good as the keys and the code around it. That is why this chapter has three security parts: the primitives and how they fail (Chapter 8), TLS and certificates (Chapter 9), and the attacks and engineering practice that matter once the cryptography is right (Chapters 10 and 11). The figure's right column is a reminder that there is a security protocol at almost every layer; which one you use depends on whom you trust. TLS protects one conversation end to end; IPsec and WireGuard protect everything between two networks; MACsec protects one Ethernet link, hop by hop.

Talk track

"I think about networking as layers that each fix one problem: Ethernet gets a frame across one link, IP gets a packet across the Internet hop by hop without any promise, TCP turns that into a reliable, ordered, congestion-controlled byte stream, and TLS makes the stream confidential and authenticated. Most performance problems are round trips during setup or congestion control reacting to loss; most security problems are about trusting something on the path, or the endpoint code itself, that should not be trusted."

2Getting a packet across: addresses, routing and names

Before any TCP or TLS, a machine has to know its own address, find the next hop, and turn a name into an address. These mechanisms are old, simple and almost entirely unauthenticated, which is why they are both robust and a favourite target.

2.1The link: MAC addresses, switches and broadcast domains

Ethernet frames carry a destination and a source MAC address. A switch learns which MAC address lives behind which port by watching source addresses, and forwards each frame only to the port where the destination lives; frames to unknown destinations and to the broadcast address ff:ff:ff:ff:ff:ff are flooded to every port. The set of machines a broadcast reaches is a broadcast domain, normally one IP subnet. VLANs split one physical switch into several broadcast domains by adding a 4-byte tag to the frame; they are the basic tool for keeping, say, office laptops away from building controllers (Automotive networks 7.4 shows the tag). Wi-Fi works the same way from IP's point of view: the access point is a switch with a radio port.

Nothing in Ethernet checks that a machine uses its own MAC address. Learning switches can be poisoned by forged source addresses, and any machine in the broadcast domain sees broadcasts and can answer them. That is the root of ARP spoofing (Section 10.1) and the reason that a shared network, a café Wi-Fi or a hotel LAN, is treated as hostile.

2.2IP: addresses, prefixes and routing by longest match

An IPv4 address is 32 bits, written as four bytes; a prefix such as 192.168.1.0/24 says that the first 24 bits name the network and the remaining 8 the host. A host compares the destination with its own prefix: if the destination is on the same subnet it sends the frame directly; otherwise it sends it to its default gateway, a router. Each router holds a routing table of prefixes and next hops and picks the longest matching prefix: with routes for 0.0.0.0/0 (default), 198.51.100.0/22 and 198.51.100.0/24, a packet to 198.51.100.10 follows the /24, because the more specific route wins. Routers on the Internet learn their tables from each other with BGP; inside a company or a data centre OSPF, IS-IS or static routes do the same job. Each router decrements the 8-bit TTL (hop limit in IPv6) and drops the packet at zero, which stops routing loops from circulating packets forever and is what traceroute uses: it sends packets with TTL 1, 2, 3, … and lists the routers that report the drop with an ICMP "time exceeded" message.

IP promises nothing beyond best effort. Packets may be dropped when a queue is full, duplicated, reordered when two paths have different delays, or delivered late. ICMP carries the network's error reports (destination unreachable, time exceeded, fragmentation needed) and the echo requests of ping. Blocking all ICMP in a firewall, a common over-reaction, breaks path MTU discovery (Section 2.6) and makes failures harder to diagnose.

2.4NAT and connection tracking: what they fix and what they break

IPv4 has about 3.7 billion usable addresses, far fewer than devices, so most devices sit behind network address translation. A NAT router keeps a table of active flows, keyed by the inside address and port, and rewrites outgoing packets to its single public address with a port it chooses; incoming packets are only accepted if they match an entry. Carrier-grade NAT does the same at the ISP, so a phone on mobile data is often behind two layers of it. The table entries time out: Linux's connection tracking keeps an established TCP flow for days, but a UDP flow for only 30–180 seconds without traffic, and many home and carrier NATs are far more aggressive.

NAT works because almost all traffic is a client connecting out. It breaks anything that expects to be reached from outside: a server at home, peer-to-peer calls and games, and protocols that write addresses into their payload. The workarounds are explicit port forwarding, protocols to ask the NAT for a mapping, and NAT traversal techniques (STUN, ICE, TURN relays) that WebRTC uses. Connection-tracking tables are also the reason long-lived idle connections die silently: a mobile app that keeps a TCP connection open for push messages must send keep-alives more often than the shortest NAT timeout on the path, typically every 30 seconds to a few minutes. IPv6, with its 128-bit addresses, does not need NAT, but most IPv6 networks still run a stateful firewall that behaves the same way for incoming connections.

Pitfall

NAT is not a firewall, although it acts like one by accident. It hides addresses, but the security comes from the connection-tracking rule "drop what you did not ask for". With IPv6 and no NAT, forgetting that rule exposes every device directly. Conversely, a "connection reset by peer" on an idle connection after exactly N minutes is almost always a NAT or load balancer timeout somewhere on the path, not a bug in either endpoint.

2.5DNS: a distributed, cached, mostly unauthenticated database

DNS maps names to records. The stub resolver in the operating system asks a recursive resolver (the ISP's, or a public one such as 1.1.1.1 or 8.8.8.8), which does the actual work: it asks a root server where .com is, asks a .com server where example.com is, and asks the authoritative server for example.com for the record. Each answer carries a TTL, and every resolver caches it for that long; the root and TLD answers have TTLs of days, so in practice only the last step happens for most queries. The common record types are A (IPv4 address), AAAA (IPv6), CNAME (alias to another name), MX (mail), TXT (free text, used for domain verification and email policies), NS (delegation) and SRV/HTTPS (service endpoints and parameters).

A query and its answer are small, which is why DNS uses UDP: the whole exchange is one datagram each way, one round trip. In the chapter's test network a query to a local authoritative server took 40 ms, exactly one RTT, and the answer was 49 bytes. Answers larger than about 1232 bytes (the safe size agreed for EDNS so that DNS never needs IP fragmentation) are truncated, and the client retries over TCP.

Classic DNS has no confidentiality and no authentication. Anyone on the path can see which names you look up, and an attacker who can guess the 16-bit query ID and the source port can inject a forged answer that the resolver caches for every user (cache poisoning; the Kaminsky attack of 2008 made this practical until resolvers randomised source ports). Two separate fixes exist. DNSSEC signs the records, so a resolver can verify that an answer came from the zone's owner; it protects integrity, not privacy, and is deployed unevenly. DNS over TLS and DNS over HTTPS (DoT, DoH) encrypt the path between the stub and the recursive resolver, which protects privacy from the local network but means trusting the resolver. TLS certificates (Chapter 9) are the reason a poisoned DNS answer usually leads to a certificate error rather than a silent compromise.

In practice

DNS is a common cause of "random" latency and outages. Low TTLs (30–60 s) let traffic move quickly during failover but multiply queries; high TTLs make changes slow to take effect (Backend 3.1 uses DNS for coarse traffic steering for that reason). Many runtimes cache DNS themselves, some forever (older JVMs with a security manager): a service that never re-resolves keeps calling the IP address of a load balancer that was replaced last week.

2.6MTU, fragmentation, path MTU discovery, and IPv6 in brief

Each link has a maximum transmission unit, 1500 bytes of IP packet on Ethernet. A path is limited by its smallest link, which is often smaller than 1500 because of tunnels: a VPN, a VXLAN overlay in a data centre or PPPoE on a DSL line each take some bytes for their own headers. IPv4 routers may fragment a too-large packet, but fragments are expensive, lost fragments lose the whole packet, and many firewalls drop them. Modern stacks therefore set the "don't fragment" bit and rely on path MTU discovery: a router that cannot forward the packet drops it and returns an ICMP "fragmentation needed" (IPv6: "packet too big") message with the size that fits, and the sender lowers its segment size. If a firewall drops those ICMP messages, small packets get through and large ones vanish: the connection opens, small requests work, and the first large response hangs. That "PMTU black hole" is the classic symptom of over-zealous ICMP filtering. TCP also announces its maximum segment size in the SYN (MSS 1460 in the capture of Section 3.1), and routers on tunnelled links often clamp it.

IPv6 changes the address size to 128 bits, removes fragmentation by routers (only the sender may fragment), replaces ARP with Neighbour Discovery, lets hosts configure their own addresses from the router's prefix (SLAAC), and makes the minimum MTU 1280 bytes. Most of the rest of this chapter is identical for IPv4 and IPv6; dual-stack clients try both and use whichever connects first ("happy eyeballs"), which is why an IPv6 misconfiguration often shows up as a 250-ms delay rather than an outright failure.

In automotive

In-vehicle Ethernet uses the same IP, ARP, UDP and TCP, but with static addresses and static ARP tables configured at build time instead of DHCP, VLANs per function domain, and switches configured not to learn. There is no DNS inside the vehicle; services find each other with SOME/IP Service Discovery over UDP multicast (Automotive networks 7.7, 8.2). The connected head unit and telematics unit, which do talk to the Internet, use the mainstream stack described here.

3TCP in depth

TCP turns IP's best-effort packets into a reliable, ordered byte stream, and it shares the network fairly with everyone else while doing so. The first job is bookkeeping; the second is guesswork, and most of TCP's interesting behaviour, good and bad, comes from how it guesses.

3.1What TCP promises, and the handshake that sets it up

TCP promises that the bytes written at one end arrive at the other end complete, in order and without duplicates, or that the connection fails with an error. It does not promise anything about timing, and it does not preserve message boundaries: two send() calls of 100 bytes may arrive as one read of 200 bytes or as reads of 37 and 163. To keep the promise, each byte has a 32-bit sequence number, the receiver acknowledges the highest in-order byte it holds, and the sender keeps every unacknowledged byte so it can retransmit.

The three-way handshake agrees on the starting sequence numbers in both directions and exchanges options. The client sends SYN with its initial sequence number (random, so that an off-path attacker cannot guess it and inject data), the server answers SYN-ACK with its own, and the client acknowledges. The SYN also carries the maximum segment size, the window-scale factor (Section 3.2), and whether selective acknowledgements and timestamps are supported. The client may send data immediately after its ACK, so the handshake costs exactly one round trip before the request leaves. The capture below is one plain HTTP request on the test link.

Closing is a four-way exchange because each direction is closed separately: FIN means "I will send no more", and the other side may still send. Abrupt termination uses RST, which tells the other side that the connection no longer exists; it is what a client gets when it connects to a port with no listener ("connection refused").

3.2Reliability and flow control: acknowledgements, retransmission and the receive window

Acknowledgements are cumulative: "ack 78" means "I have every byte before 78". The sender detects loss in two ways. If no acknowledgement arrives within the retransmission timeout (RTO), it retransmits; the RTO is computed from a smoothed RTT plus four times its variation, with a minimum of 200 ms on Linux and an initial value of 1 second before any RTT is measured, which is why a lost SYN costs a full second. Faster, if later segments keep arriving after a hole, the receiver keeps sending the same acknowledgement; three duplicate ACKs trigger a fast retransmit of the missing segment without waiting for the timer. Selective acknowledgements (SACK) let the receiver report exactly which blocks above the hole it holds, so the sender retransmits only what is missing. Linux's RACK-TLP adds time-based loss detection and a "tail loss probe" so that losing the last segment of a response does not have to wait for the RTO.

Flow control protects the receiver. Each acknowledgement carries the receive window, the free space in the receiver's buffer; the sender never has more unacknowledged bytes in flight than that. The original 16-bit field allows only 64 kB, so the window scale option in the SYN multiplies it (by 210 in the capture). A slow reader shrinks the window to zero, and the sender stops and probes until it reopens: that is backpressure from the application all the way to the sender, and it is visible in ss as a full receive queue on one side and a full send queue on the other (Linux 7.5 shows one).

That last sentence, throughput ≤ window / RTT, is the most useful formula in networking. To keep a path busy the window must hold a full bandwidth-delay product (BDP): on the test link, 20 Mbit/s × 40 ms = 100 kB, or 69 full segments. A 10 Gbit/s link to another continent with 150 ms RTT needs 187 MB in flight. A window of 64 kB on that path, the limit without window scaling, gives 3.5 Mbit/s no matter how fast the link is. Linux grows its socket buffers automatically up to net.ipv4.tcp_rmem/tcp_wmem maxima (6 MB and 4 MB by default), which is enough for most paths but not for long fat ones; setting SO_RCVBUF by hand switches the autotuning off and is usually a mistake.

3.3Congestion control: from Reno to CUBIC and BBR

Flow control protects the receiver; congestion control protects the network. In 1986 the early Internet suffered "congestion collapse": senders retransmitted into full queues, the retransmissions filled the queues further, and useful throughput fell by a factor of a thousand. Van Jacobson's fix, still the basis of TCP, is that each sender keeps a congestion window (cwnd), probes for more bandwidth while things go well, and backs off sharply when a packet is lost, because in a wired network a loss almost always means a queue somewhere overflowed.

Slow start begins with a small window (10 segments on Linux) and doubles it every round trip, so it finds the right order of magnitude quickly; it ends at the first loss or at a threshold. Congestion avoidance then grows the window by one segment per round trip and halves it on loss: additive increase, multiplicative decrease (AIMD). AIMD is what makes TCP fair: two flows sharing a link converge to equal shares, because the bigger one loses more when both halve. This algorithm is called Reno (NewReno with the improved recovery from several losses). Its weakness is speed: on a path whose BDP is 10 000 segments, regrowing from 5 000 after a loss takes 5 000 round trips, more than ten minutes at 150 ms.

CUBIC, the default in Linux since 2006 and in Windows and macOS since, replaces the linear growth with a cubic function of the time since the last loss: it grows quickly when far below the window at which the last loss happened, flattens as it approaches that value (where the loss is likely to recur), and accelerates again beyond it to probe for new capacity. It cuts the window by 30 % instead of 50 %. Its growth depends on time rather than on round trips, so flows with different RTTs share more fairly, and it fills fat pipes far faster than Reno. For small BDPs, as on the test link, CUBIC deliberately behaves like Reno ("TCP-friendly region").

Both are loss-based: they increase until a packet is dropped. That has two consequences. A random loss that has nothing to do with congestion, as on a lossy radio link, makes them back off anyway; the steady-state throughput of Reno follows the Mathis formula, throughput ≈ (MSS / RTT) × 1.22 / √p for loss rate p, so 1 % loss on a 40 ms path caps it at 3.5 Mbit/s regardless of link speed. And because they only back off when a queue overflows, they fill every buffer on the path first, which adds latency for everyone sharing it: bufferbloat.

BBR (Google, 2016) is model-based instead. It continuously estimates the bottleneck bandwidth (the maximum delivery rate seen over the last few round trips) and the minimum RTT (the propagation delay without queueing), paces packets at the estimated bandwidth, and limits the data in flight to about twice the estimated BDP. Every few round trips it paces 25 % faster for one RTT to see whether more bandwidth appeared, then 25 % slower to drain any queue it created; every 10 seconds it briefly drops to four packets in flight to re-measure the minimum RTT. The original BBR (v1, the one in mainline Linux and measured here) ignores loss entirely, which makes it robust to random loss and keeps queues short, but also makes it unfair to loss-based flows in shallow buffers and lets it cause heavy retransmissions; BBRv2 and v3, used inside Google, react to loss and ECN again.

Interesting detail

Explicit congestion notification (ECN) lets a router mark a packet instead of dropping it when its queue starts to grow, and the receiver echoes the mark back. The sender reacts as to a loss but without losing anything. Data centre algorithms such as DCTCP react proportionally to the fraction of marked packets and keep queues almost empty; L4S brings the same idea to the Internet. Active queue management in routers (CoDel, fq_codel, the Linux default qdisc on many distributions) attacks bufferbloat from the other side, by dropping or marking packets that have waited too long.

3.6Small messages: Nagle, delayed acknowledgements and the 40 ms stall

Congestion control is about bulk data; request-response protocols have a different problem. Nagle's algorithm holds back a small segment while earlier data is unacknowledged, so that a program writing one byte at a time does not send one packet per byte. The receiver's delayed acknowledgements wait up to about 40 ms on Linux for data to piggyback the ACK on. Together they produce a classic stall: a client writes a request header and body in two calls, the body waits for the ACK of the header, and the ACK waits for the delayed-ACK timer, adding 40 ms to every request (Linux 7.3 describes the mechanism from the kernel's side). The fixes are to write each message in one call (or with writev()), to set TCP_NODELAY, which every RPC library and most HTTP clients do, or, when building a large response from pieces, to set TCP_CORK and uncork when the message is complete.

3.7What TCP cannot fix: head-of-line blocking and ossification

Because TCP delivers one ordered byte stream, a single lost segment holds back every byte behind it until the retransmission arrives, at least one round trip later, even if those bytes belong to unrelated requests multiplexed on the same connection. That is head-of-line blocking, and it is the main reason HTTP/3 moved off TCP (Section 4.4). TCP has a second structural problem: it is implemented in operating system kernels and inspected by middleboxes all over the Internet, so changing it takes a decade. Extensions such as TCP Fast Open, which sends data in the SYN, were blocked or broken by middleboxes that did not recognise them. The answer of QUIC is to put the transport in user space and to encrypt almost all of its header so that middleboxes cannot ossify it again.

Talk track

"TCP gives a reliable ordered stream with sequence numbers, cumulative ACKs, SACK and retransmissions; flow control uses the receiver's window; congestion control uses cwnd, and throughput is bounded by min(cwnd, rwnd) divided by RTT, so a path needs a full bandwidth-delay product in flight. Reno and CUBIC back off on loss, which makes them sensitive to random loss, roughly 1/√p, and makes them fill buffers. BBR models bandwidth and minimum RTT instead and keeps queues short. The setup costs one RTT, plus one for TLS 1.3, and a lost segment blocks the whole stream."

4UDP, multicast and QUIC

UDP gives an application raw datagrams with port numbers and nothing else. That is exactly right for some jobs, a trap for others, and the foundation on which QUIC rebuilt a better TCP in user space.

4.1UDP: datagrams and nothing else

A UDP datagram has an 8-byte header: source port, destination port, length and checksum. It is delivered whole or not at all, possibly out of order, possibly twice, with no connection, no acknowledgement and no congestion control. Each send() becomes one datagram and each recv() returns exactly one, so message boundaries are preserved, unlike TCP. UDP is the right choice when an exchange fits in one datagram each way (DNS, NTP, DHCP), when late data is worthless and must not delay newer data (voice, video calls, game state, sensor streams: a retransmitted video frame that arrives after the next one is useless), when one sender talks to many receivers (multicast), and when an application wants to implement its own transport (QUIC, WebRTC's SCTP and media, many game protocols).

An application that uses UDP inherits the jobs TCP would have done. It must handle loss (forward error correction, retransmission of what still matters, or tolerance), keep datagrams below the path MTU (about 1200 bytes is the safe choice on the Internet), pace its sending and react to loss or delay, or it will damage other traffic and its own, and survive NAT timeouts with keep-alives. On the receiving side, the kernel's per-socket receive buffer (about 200 kB by default on Linux) silently drops datagrams when the application falls behind; the counter RcvbufErrors in nstat is the only trace (Linux 7.3). Because UDP has no handshake, the source address of a request is not verified, which makes UDP services usable for reflection and amplification attacks: a small request with a forged source address produces a large answer to the victim (Section 10.6).

4.2Multicast: one send, many receivers

Multicast sends one datagram to a group address (224.0.0.0/4 in IPv4); the network copies it to every member. Hosts join a group with IGMP (MLD in IPv6), switches that do "IGMP snooping" forward the group's traffic only to ports with members, and multicast routing protocols (PIM) extend the tree across routers. The sender does the work once, however many receivers there are, which is why multicast is used where many machines need the same stream at the same time: market data feeds in trading, IPTV inside an operator's network, service discovery (mDNS, SSDP, SOME/IP-SD) and DDS discovery in robotics and vehicles (Automotive networks 8.3). On the public Internet multicast is not routed, because inter-domain multicast routing never became manageable; streaming services use unicast through CDNs instead. Multicast inherits all of UDP's properties: no reliability, no congestion control and, without extra measures, no authentication of the sender.

4.3QUIC: a transport rebuilt on UDP

QUIC (RFC 9000, 2021) is a reliable, congestion-controlled, encrypted transport that runs in user space over UDP. It was designed to fix TCP's three practical problems for the web: setup latency, head-of-line blocking between multiplexed requests, and ossification. It does so with a few design decisions that are worth knowing individually.

TLS 1.3 is built in. The QUIC handshake carries the TLS handshake messages in its own CRYPTO frames, so transport and cryptographic setup happen in the same round trip: the client can send its request after one RTT instead of two (Figure 4.1). With a session ticket from an earlier connection it can even send data in its first flight (0-RTT), at the price that such early data can be replayed by an attacker and so must be limited to idempotent requests. Streams are part of the transport. A QUIC connection carries many independent streams, each ordered on its own; a lost packet only delays the streams whose data it carried. Everything is encrypted except a few header bits and the connection ID, including packet numbers and acknowledgements, so middleboxes cannot inspect or "help" with the transport and the protocol can evolve. Connections are identified by connection IDs, not by the address four-tuple, so a phone moving from Wi-Fi to mobile data keeps its connection (connection migration). And because it is a library rather than kernel code, it can ship new loss recovery and congestion control with the application; it also improves on TCP's details, for example by never reusing packet numbers, so that an acknowledgement is never ambiguous between an original and a retransmission.

The measurement in the test network agrees: a QUIC handshake with aioquic completed in 50 ms (one 40 ms RTT plus Python processing), and the first reply on a stream arrived after 92 ms, against 128 ms for TCP with TLS 1.3 and 169 ms for TLS 1.2 (Figure 7.1 shows the whole budget). The capture also shows a QUIC detail with a security purpose: the client's first packet is padded to 1200 bytes of UDP payload (1242 bytes on the wire). A server may send at most three times as many bytes as it received before the client's address is validated, so padding the first packet both proves the path carries 1200-byte datagrams and stops QUIC servers from being useful amplifiers.

QUIC's costs are real too. User-space processing and per-packet encryption make it use noticeably more CPU per byte than kernel TCP with hardware offloads; UDP is rate-limited or blocked on some enterprise networks, so every QUIC client keeps a TCP fallback; and debugging needs the TLS keys, because without them a capture shows almost nothing. HTTP/3 (Section 6.3) is the main user, carrying a large and growing share of traffic to the big content providers.

4.4Head-of-line blocking, made visible

The model below sends several streams of 20 packets interleaved over one connection, one packet per millisecond, and loses packets at random; a lost packet arrives one RTT late after its retransmission. Over TCP the receiver hands data to the application in one global order, so every packet after a hole waits for it, whatever stream it belongs to. Over QUIC each stream is ordered separately, so only the stream that lost the packet waits.

5Sockets programming

The socket API is the boundary between an application and the network stack. Most network bugs in application code come from three misunderstandings of it: that a read returns one message, that a write sends everything, and that one thread per connection scales.

5.1The socket lifecycle and the queues behind it

A server creates a socket, binds it to an address and port, and calls listen(), which tells the kernel to start completing handshakes on its behalf. Handshakes are completed by the kernel, not by the application: a SYN creates an entry in the SYN queue, and once the client's ACK arrives the connection moves to the accept queue, where it waits until the application calls accept() and receives a new file descriptor for it. A client creates a socket and calls connect(), which picks an ephemeral source port, sends the SYN and returns when the handshake is complete. After that both sides read and write through the per-connection socket's buffers and finally close().

The queues explain several production symptoms. If the application does not call accept() fast enough, the accept queue overflows and new connections are dropped or reset; ss -lnt shows the queue length in Recv-Q for a listening socket, and nstat counts ListenOverflows. The backlog argument is capped by net.core.somaxconn (4096 by default on recent kernels). A flood of SYNs that are never completed fills the SYN queue: that is the SYN flood attack, and SYN cookies defeat it by encoding the connection state into the server's initial sequence number instead of storing it, so the queue cannot fill (Section 10.6).

5.2Blocking and non-blocking I/O, partial transfers and framing

By default socket calls block: recv() waits until at least one byte is available, send() waits until all bytes fit into the send buffer, connect() waits for the handshake. That is simple, and one thread per connection is a perfectly good design for tens or hundreds of connections. In non-blocking mode (O_NONBLOCK) every call returns immediately; if it cannot make progress it fails with EAGAIN, and the program must wait for readiness some other way (Section 5.3).

Two rules apply in both modes. A recv() returns whatever bytes are there, which may be part of a message, several messages, or the end of one and the start of the next; TCP has no message boundaries, so the application must add its own framing, either a length prefix (gRPC uses 5 bytes, Section 6.4) or a delimiter (HTTP/1.1 uses blank lines and Content-Length). And send() on a non-blocking socket may accept only part of the buffer, so the rest must be kept and sent later. A recv() that returns 0 means the peer closed its sending direction; an error such as ECONNRESET means the connection is gone.

// Read exactly one length-prefixed message from a blocking TCP socket.
bool read_full(int fd, void* buf, size_t n) {
    auto* p = static_cast<char*>(buf);
    while (n > 0) {
        ssize_t r = recv(fd, p, n, 0);
        if (r == 0) return false;                 // peer closed
        if (r < 0) { if (errno == EINTR) continue; return false; }
        p += r; n -= static_cast<size_t>(r);       // a read may return fewer bytes than asked
    }
    return true;
}
std::optional<std::string> read_message(int fd) {
    uint32_t len_be;
    if (!read_full(fd, &len_be, 4)) return std::nullopt;
    uint32_t len = ntohl(len_be);
    if (len > 16 * 1024 * 1024) return std::nullopt;  // never trust a length from the network
    std::string msg(len, '\0');
    if (!read_full(fd, msg.data(), len)) return std::nullopt;
    return msg;
}
Pitfall

Every blocking call needs a timeout. A recv() on a connection whose peer vanished (power loss, a NAT entry that expired) waits forever, because no FIN or RST will ever come; TCP keep-alive only starts probing after two hours by default. Set SO_RCVTIMEO/SO_SNDTIMEO, use poll with a timeout, or, at the RPC level, deadlines (Section 6.4). The length check in the example matters too: a length field read from the network is attacker-controlled input.

5.3Many connections: select, poll, epoll and io_uring

A server with 10 000 mostly idle connections cannot afford 10 000 threads (each with a stack and scheduler cost), which was the "C10K problem" of the late 1990s. The answer is to put all sockets in non-blocking mode and ask the kernel which ones are ready. select() and poll() take the whole list on every call and scan it, which costs O(n) per call. epoll registers interest once, and the kernel keeps a ready list that epoll_wait() returns; the cost is proportional to the number of ready sockets, not the number of open ones. This is the reactor pattern underneath nginx, Node.js, Netty, Go's runtime and Python's asyncio (Concurrency 6.4 explains event loops in general).

epoll has two modes. In level-triggered mode (the default) epoll_wait() reports a socket as long as it has unread data. In edge-triggered mode it reports a socket only when new data arrives, so the handler must read until EAGAIN or it will never be told again about the bytes it left behind; edge-triggered saves wake-ups but is a common source of hangs. A typical loop looks like this:

int ep = epoll_create1(0);
add(ep, listen_fd, EPOLLIN);
for (;;) {
    epoll_event ev[64];
    int n = epoll_wait(ep, ev, 64, next_timer_ms());   // sleep until ready or a timer is due
    for (int i = 0; i < n; ++i) {
        int fd = ev[i].data.fd;
        if (fd == listen_fd) {                           // accept everything that is queued
            for (int c; (c = accept4(listen_fd, nullptr, nullptr, SOCK_NONBLOCK)) >= 0; )
                add(ep, c, EPOLLIN | EPOLLRDHUP);
        } else if (ev[i].events & (EPOLLIN | EPOLLRDHUP)) {
            on_readable(fd);                             // read until EAGAIN, parse frames, queue replies
        } else if (ev[i].events & EPOLLOUT) {
            flush_pending(fd);                           // only registered while a send was partial
        }
    }
    run_due_timers();
}

io_uring (Linux 5.1, 2019) changes the model from readiness to completion. The application places requests ("receive into this buffer", "send this", "accept") into a submission ring shared with the kernel and later collects results from a completion ring, without a system call per operation when the rings are polled. That removes most syscall overhead and allows real asynchronous file I/O, which epoll never did; it also has a history of security bugs, and several container platforms disable it by default. Windows' I/O completion ports follow the same completion model.

5.4Zero-copy and kernel bypass

Every byte that a server reads from a file and writes to a socket is normally copied twice by the CPU: from the page cache into the application's buffer by read(), and back into the socket buffer by write(). At a few hundred megabytes per second that is irrelevant; at tens of gigabits per second per server the copies and system calls become the bottleneck. The tools to avoid them form a ladder.

sendfile() and splice() move data from a file (or a pipe) to a socket inside the kernel; with a NIC that supports scatter-gather the data is never touched by the CPU. Web servers serving static files and Kafka serving log segments use this. With TLS, the encryption has to happen somewhere: kernel TLS (kTLS) lets the kernel, or a NIC with TLS offload, encrypt records on the way out, so sendfile still works. MSG_ZEROCOPY lets send() pin the application's pages instead of copying them, worthwhile for large buffers only, because the completion notification has its own cost. Receive-side offloads (GRO, LRO) merge segments so the stack processes fewer, larger packets, and segmentation offload (TSO, GSO) lets the NIC cut a 64 kB write into segments.

Kernel bypass goes further. DPDK maps the NIC's descriptor rings into a user-space process that polls them in a busy loop on dedicated cores, with its own (or no) TCP stack: millions of packets per second per core, at the price of 100 % CPU on those cores, no standard tools, and reimplementing whatever the kernel did. AF_XDP is a middle way inside Linux: an eBPF program at the driver decides which packets go to a user-space ring and which continue into the normal stack. RDMA (InfiniBand, RoCE) lets one machine's NIC read and write another machine's memory directly, without either CPU, and carries most traffic in machine-learning training clusters. These are specialist tools for packet processing, trading and storage; an ordinary service that is slow almost never needs them.

6HTTP/1.1, HTTP/2, HTTP/3 and gRPC on the wire

HTTP's meaning, methods, status codes and headers, has stayed the same since the 1990s; what changed is how those messages are put on the wire. Each version fixed the performance problem of the previous one, and each fix moved the remaining problem one layer down.

6.1HTTP semantics: the part that did not change

An HTTP request has a method, a target, headers and an optional body; the response has a status code, headers and a body (RFC 9110 defines these semantics independently of any version). Methods carry promises that infrastructure relies on. GET and HEAD are safe (no side effects) and so may be cached and prefetched; GET, PUT and DELETE are idempotent (doing them twice equals doing them once) and so may be retried automatically by clients and proxies; POST is neither, which is why a retried payment needs an idempotency key (Backend 10.3). Status classes say who should act: 2xx success, 3xx go elsewhere, 4xx the client's fault (do not retry unchanged), 5xx the server's fault (retry may help, with backoff). Headers carry everything else: content type and encoding, caching (Cache-Control, ETag), authentication (Authorization), cookies, and security policies such as Strict-Transport-Security (Section 10.1).

6.2HTTP/1.1 and HTTP/2

HTTP/1.1 is text. A request is a line such as GET /photos/42 HTTP/1.1, header lines, a blank line and a body whose length is given by Content-Length or by chunked encoding. Connections are kept alive and reused, but a connection carries one request at a time: the next request can only be sent after the previous response has been completely received. (Pipelining, sending several requests without waiting, was specified but never worked reliably through proxies.) Browsers therefore open about six connections per host, and sites used to split their content across hostnames to get more. Each connection pays its own TCP and TLS handshake and its own slow start, and each competes with the others for bandwidth.

HTTP/2 (2015, now RFC 9113) keeps the semantics and changes the encoding. Everything is a binary frame with a 9-byte header: 24-bit length, type, flags and a 31-bit stream identifier. Each request-response pair is a stream, and frames of many streams are interleaved on one TCP connection, so a slow response no longer blocks the others at the HTTP level. Headers are compressed with HPACK, which keeps a table of previously sent headers, so the repeated cookies and user agents of a page load shrink to a few bytes each. HTTP/2 has its own flow control per stream and per connection (WINDOW_UPDATE frames), PING frames for liveness, and SETTINGS frames to negotiate limits such as the maximum number of concurrent streams. Over TLS the version is negotiated in the handshake with ALPN (the h2 in the ClientHello of Section 9.2).

HTTP/2's multiplexing moved head-of-line blocking from HTTP into TCP. On a clean network one HTTP/2 connection beats six HTTP/1.1 connections; on a lossy one it can be worse, because a single loss stalls every stream, while with six connections it stalls only one sixth of the traffic (Figure 4.2 shows the effect). Fixing that required a transport with independent streams, which is what QUIC is.

6.3HTTP/3

HTTP/3 (RFC 9114, 2022) is HTTP/2's model mapped onto QUIC. Each request uses its own QUIC stream, so the stream identifiers and flow control of HTTP/2 move into the transport; header compression becomes QPACK, a variant of HPACK designed so that streams arriving out of order cannot deadlock on the shared table. A client usually learns that a server speaks HTTP/3 from an Alt-Svc header on an HTTP/2 response or from a DNS HTTPS record, then tries QUIC on UDP port 443 and falls back to TCP if UDP is blocked. The gains are largest where they were designed to be: first connections (one RTT saved, two with 0-RTT), mobile clients that change networks, and lossy or high-latency links. On a fast, clean data-centre network HTTP/2 over TCP is just as good and cheaper in CPU, which is why internal service traffic mostly stays on HTTP/2.

6.4gRPC on the wire

gRPC is a remote procedure call framework that uses HTTP/2 as its transport and Protocol Buffers as its default message encoding. Every call is an HTTP/2 POST to a path made of the service and method name, with content-type: application/grpc. Each message in the request or response body is prefixed with 5 bytes: one flag byte (compressed or not) and a 32-bit length. Because messages are length-prefixed, one stream can carry any number of them, which gives gRPC's four call types (unary, server streaming, client streaming and bidirectional) on the same mechanism. The outcome of the call is not the HTTP status, which is 200 whenever the call reached the server, but the grpc-status and grpc-message trailers, sent as a final HEADERS frame after the body. The capture of one unary call in the test network, with a 2-second deadline, shows all of this.

Three practical consequences follow from the wire format. Deadlines propagate: a server that calls other services passes on the remaining time, so a whole call tree gives up together instead of doing work nobody is waiting for. Load balancing needs an L7 balancer or client-side balancing, because one long-lived HTTP/2 connection carries all calls, and an L4 balancer that spreads connections would send everything from one client to one server (Backend 3.2). And browsers cannot speak gRPC directly, because their APIs do not expose trailers; gRPC-Web adds a proxy that converts.

6.5REST, gRPC or something else

The choice between REST with JSON, gRPC and asynchronous messaging is mostly about who the clients are and how tightly they are coupled, and Backend 11.2 discusses it from that angle. From the wire's point of view the differences are smaller than they seem: both usually run on HTTP/2 over TLS; protobuf is several times smaller and faster to parse than JSON, which matters for chatty internal services and little for a public API that sends a few requests per screen; and gRPC's streaming and deadlines come for free, while REST needs conventions for both. WebSockets, which upgrade an HTTP/1.1 connection into a bidirectional message channel, remain the standard for browser push; server-sent events are a simpler one-way alternative.

7.2Latency and throughput budgets

Two pieces of arithmetic answer most performance questions before any tool is run. The first is the round-trip count. A new HTTPS request costs one RTT for DNS (if not cached), one for TCP, one for TLS 1.3 (two for TLS 1.2) and one for the request itself, plus server time and transfer time. The RTT is set by distance: light in fibre covers about 200 km per millisecond, so Frankfurt to New York (about 6200 km, more along real cable routes) cannot be faster than about 70 ms round trip, and is typically 80–90. 7.3tcpdump and Wireshark

A packet capture is the ground truth: it shows what was actually sent, when, and what came back. tcpdump captures with a kernel filter (BPF) so that only matching packets are copied, and writes a pcap file that Wireshark or its command-line form tshark decodes with a dissector for almost every protocol. Captures contain whatever the traffic contained, credentials and personal data included, so treat pcap files and key logs as secrets.

7.4ss, nstat, ip, iperf3 and ping: what each one tells you

ss -tin shows every TCP socket with its state and internals: congestion algorithm, cwnd, smoothed RTT and variance, retransmissions, delivery rate, and the send and receive queues; it is the fastest way to see whether a slow transfer is limited by the network (small cwnd, retransmissions) or by an application (full receive queue at the reader, empty send queue at the writer). nstat prints the kernel's protocol counters since the last call: retransmissions, listen overflows, UDP buffer errors. ip -s link and ethtool -S show drops at the interface and in the NIC's rings; ip route get 198.51.100.10 shows which route and source address the kernel would use. ping measures RTT and loss with ICMP, mtr combines ping with traceroute to show where along a path loss or delay starts (with the caveat that routers rate-limit their own ICMP replies, so loss at one intermediate hop that does not continue to the destination is usually not real). iperf3 measures achievable TCP or UDP throughput between two hosts, with a choice of congestion control, parallel streams and duration, and reports retransmissions; it separates "the network cannot carry it" from "my application does not send it".

In practice

When someone says "the network is slow", ask for three numbers: the RTT (ping), the achievable throughput (iperf3 between the same hosts) and what the application actually gets. If iperf3 is fast and the application is slow, the problem is in the application: a small fixed buffer, one request at a time, a missing TCP_NODELAY, or a slow reader. If iperf3 is slow too, look at loss (ss retransmissions, nstat) and at the path.

7.5Building a test network on one machine

Every experiment in this chapter ran in one container. Linux network namespaces give each process group its own interfaces, addresses, routes and firewall, so three namespaces connected by veth pairs (virtual cables) form a client, a "network" and a server. Normally the middle would use tc qdisc add … netem delay 20ms loss 1% to impose delay and loss; the container kernel lacks netem, so experiments/linkemu.c (about 100 lines) does the same job in user space: it reads every frame from one veth end with a packet socket, drops it with the configured probability, queues it behind a 20 Mbit/s serialisation clock with a tail-drop buffer, and writes it to the other end after the configured delay. Offloads are switched off on the veths so that frames stay at MTU size. The result behaves like a real bottleneck: ping showed exactly 40.2–40.7 ms on the idle link, and TCP saw the expected drops when the buffer overflowed. The same technique, namespaces plus netem or an emulator, is the cheapest way to test how an application behaves on a bad mobile link before a customer does.

8Applied cryptography: the building blocks and how they fail

Engineers rarely implement cryptography, but they choose it, configure it and combine it every day, and nearly all real-world cryptographic failures happen there: the right primitive used for the wrong purpose, a nonce used twice, a key stored next to the data. This chapter explains what each building block guarantees, so that the combinations make sense.

8.1What each primitive gives, and what it does not

Modern cryptography is built from a handful of primitives, each with a precise promise. 8.2Hashes, MACs and why a hash is not a MAC

A cryptographic hash maps any input to a fixed-size digest (256 bits for SHA-256) such that it is infeasible to find two inputs with the same digest (collision resistance) or an input for a given digest (preimage resistance), and a one-bit change in the input changes about half of the output bits. In the experiment, "transfer 100 EUR" and "transfer 900 EUR" give digests that differ in 139 of 256 bits. Hashes identify content (Git objects, container image digests, the SBOM entries of Build and containers 11.5), check downloads against a published value, and are the inner part of signatures and MACs. MD5 and SHA-1 are broken for collisions and must not be used where an attacker chooses inputs.

A hash alone proves nothing about who produced the data, because anyone can compute it. To authenticate a message between two parties that share a key, use a MAC. The obvious construction, SHA-256(secret ‖ message), is broken for SHA-256 and SHA-512, and the reason teaches something about how hashes work inside. They process the input block by block, carrying a 256-bit internal state from one block to the next, and the final digest is that state. Given a valid tag for a message, an attacker can therefore set the state to the tag and keep hashing more blocks, producing a valid tag for the message plus padding plus anything they choose, without knowing the secret: a length-extension attack.

experiments/crypto_demos.py carries out the attack with a 70-line SHA-256 whose state can be set: given the tag of user=alice&role=viewer under an unknown 16-byte secret, it produces a tag that the server accepts for the same message followed by 26 bytes of padding and &role=admin. HMAC, which hashes twice with the key mixed in at both ends, is not affected, and the HMAC tags of the two messages are unrelated. The rule is simple: use HMAC (or the tag of an AEAD), never a hash of a key and data concatenated. SHA-3 and BLAKE3 happen not to have this weakness, but that is not a reason to build your own MAC from them.

Passwords need the opposite of a fast hash. A stolen database of SHA-256 password hashes can be attacked at billions of guesses per second on GPUs, because each guess costs one hash. Password hashing functions are deliberately slow and, in the case of Argon2id and scrypt, need a lot of memory, which GPUs and custom hardware have little of; each password gets its own random salt so that identical passwords give different hashes and precomputed tables are useless. In the experiment one SHA-256 of a password took 295 ns in Python, while PBKDF2-HMAC-SHA-256 with the 600 000 iterations OWASP recommends took 90 ms, about 300 000 times longer for the attacker and still unnoticeable at a login.

8.3Symmetric encryption and AEAD

Symmetric ciphers do the bulk work: AES, a 128-bit block cipher with 128- or 256-bit keys and dedicated instructions in every modern CPU, or ChaCha20, a stream cipher that is fast in software where AES instructions are missing. A block cipher alone only encrypts 16 bytes; a mode turns it into a cipher for messages. Old modes (CBC with a separate MAC, or worse, ECB) caused a long series of attacks, and modern protocols use only authenticated encryption with associated data (AEAD): one operation that encrypts the payload, authenticates the payload together with unencrypted associated data such as a header, and fails as a whole if anything was changed.

AES-GCM, the most common AEAD, works in counter mode: it encrypts the sequence nonce‖1, nonce‖2, … with AES to produce a keystream and XORs it with the plaintext; a polynomial hash (GHASH) over the associated data and the ciphertext, keyed with a value derived from the key, gives the 16-byte tag. ChaCha20-Poly1305 has the same structure with a different keystream generator and authenticator.

The whole security of the construction rests on the nonce. If two messages are encrypted under the same key and nonce they use the same keystream, and the XOR of the two ciphertexts is the XOR of the two plaintexts. The experiment encrypts a payment message and a PIN message with the same 96-bit nonce; an attacker who knows the first plaintext recovers {"pin": "4711", "user": "eve"} from the two ciphertexts alone. With two tags under one nonce, GCM's authentication key can be solved for as well, after which the attacker can forge messages. Nonce reuse happens in practice when nonces are random and too many messages are encrypted under one key, when a counter is reset after a reboot or a VM snapshot, or when two devices share a key and each counts from zero. Protocols such as TLS avoid it by construction, deriving the nonce from a record sequence number that never repeats within a connection; applications that encrypt data themselves should use a library API that manages nonces, or a nonce-misuse-resistant mode such as AES-GCM-SIV.

Numbers

Measured on one core of the container's Xeon (AES-NI, VAES, SHA-NI), 16 kB buffers: AES-128-GCM 13.6 GB/s, AES-256-GCM 12.8 GB/s, ChaCha20-Poly1305 3.4 GB/s, SHA-256 1.6 GB/s, SHA-512 0.65 GB/s. Encryption is not what makes TLS expensive; the handshake's public-key operations are (Section 8.6).

8.4Public-key cryptography: key exchange and signatures

Symmetric cryptography needs a shared key, and the hard problem is getting one to a stranger over a network that an attacker controls. Diffie-Hellman key exchange solves it: each side picks a random private value, sends a public value derived from it, and combines its own private value with the other side's public value; both arrive at the same secret, while an eavesdropper who sees only the public values cannot compute it. Today this is done on elliptic curves (ECDH): with X25519 each public value is 32 bytes and the shared secret is the private scalar times the other side's point. When the private values are generated fresh for each connection and deleted afterwards (ephemeral, the E in ECDHE), recorded traffic stays safe even if the server's long-term key is stolen later. That is forward secrecy, and TLS 1.3 requires it.

Key exchange alone is vulnerable to a man in the middle, who runs one exchange with each side. Signatures close that gap: the holder of a private key produces a signature over some data that anyone with the public key can verify. In TLS the server signs the handshake transcript, including both key-exchange values, with the key in its certificate. Signatures also authenticate software updates, container images and commits, where many verifiers need to check one signer. The main families are RSA (signatures of 256 bytes for RSA-2048, cheap to verify, expensive to sign), ECDSA on P-256 (64 bytes) and Ed25519 (64 bytes, deterministic, hard to misuse).

ECDSA has a sharp edge that is worth knowing, because it has broken real products. Each signature needs a fresh secret random value k. If the same k is used for two different messages, both signatures share the value r, and two equations in two unknowns give first k and then the private key. The experiment signs "firmware v1.2" and "firmware v1.3" with one P-256 key and a repeated k, and recovers the private key exactly from the two public signatures. A games console's code-signing key was extracted this way in 2010, and Android Bitcoin wallets lost funds in 2013 through a weak random generator that repeated k. Ed25519 and "deterministic ECDSA" (RFC 6979) derive k from the key and the message, so a bad random generator cannot leak the key this way.

RSA can also encrypt directly, and TLS 1.2 and earlier used "RSA key transport", where the client encrypted the session key with the server's public key. It had no forward secrecy and a long history of padding-oracle attacks (Bleichenbacher 1998, still found in products as ROBOT in 2017), and TLS 1.3 removed it.

8.5Randomness

Every key, nonce, salt, session identifier and password-reset token must be unpredictable, and a predictable random number generator silently breaks everything built on it. Use the operating system's cryptographically secure generator: getrandom() or /dev/urandom on Linux, BCryptGenRandom on Windows, secrets in Python, crypto.randomBytes in Node, SecureRandom in Java. Never use rand(), random, Math.random() or a time-seeded generator for anything security-relevant: they are designed for statistics and their output reveals their state. The dangerous moment is early boot on embedded devices and freshly cloned virtual machines, when the kernel has little entropy; a 2012 scan of the Internet found that tens of thousands of devices had generated RSA keys sharing a prime factor, because they all booted the same way and generated keys immediately. Modern Linux blocks getrandom() until the generator is seeded once, which solves this for software that uses it.

A large enough quantum computer would break RSA, Diffie-Hellman and elliptic curves (Shor's algorithm), though not AES or SHA-256 with adequate key sizes. Post-quantum signatures are much larger still (ML-DSA-44: 2420 bytes per signature), which makes certificate chains the harder part of the migration.

In automotive

Inside the vehicle, the bandwidth of CAN rules out signatures on messages. Signatures are used where bandwidth allows and many verifiers check one signer: software update packages, secure boot images, and V2X messages (Section 9.6). 9TLS 1.3, certificates and PKI

TLS combines the building blocks of Chapter 8 into a protocol that gives any two programs a confidential, authenticated channel. Its cryptography is now hard to get wrong; what goes wrong in practice is identity: certificates, names, trust stores, expiry and rotation.

9.1What TLS gives

TLS runs over a reliable byte stream (TCP, or QUIC's streams) and provides three things to the application above it: confidentiality and integrity of every byte, through AEAD-protected records of up to 16 kB each with a sequence-number-based nonce, so records cannot be read, changed, dropped, reordered or replayed without detection; authentication of the server, through a certificate chain that proves the server's key belongs to the name the client asked for; and optionally authentication of the client by the same mechanism (mutual TLS, Section 9.5). It does not hide the length and timing of messages, the IP addresses, or, in most deployments, the server name, which the client sends in clear in the SNI extension so that a server with many names can pick the right certificate (Encrypted Client Hello, ECH, is being deployed to close that gap).

9.3Certificates and chain validation

An X.509 certificate binds a public key to a name, signed by an issuer. The fields that matter are the subject and, more importantly, the subject alternative names (SAN), the DNS names or IP addresses the certificate is valid for (clients ignore the subject's common name nowadays); the validity period; the public key; key usage and extended key usage (server authentication, client authentication, code signing); basic constraints (whether it may sign other certificates); and the issuer's signature over all of it. Public CAs do not sign server certificates with their root keys: the root key stays offline in an HSM, signs a few intermediate certificates every few years, and the intermediates sign the leaves. The server must send its leaf and the intermediates; the client must already have the root in its trust store.

experiments/pki.sh builds such a chain and then breaks it in the ways that happen in production. Each failure has its own error, and recognising them saves hours:

$ openssl verify -CAfile root.crt -untrusted int.crt srv.crt

Pitfall

A missing intermediate is the most common certificate bug, and it hides well: browsers often work anyway, because they cache intermediates or fetch them from the URL in the certificate, while curl, Java, Python and mobile apps fail with "unable to get local issuer certificate". Always configure the server with the full chain (leaf first, then intermediates, never the root) and test with openssl s_client -connect host:443 -servername host, which prints the chain as sent.

9.4PKI in operation: CAs, transparency, revocation and lifetimes

The Web PKI rests on about a hundred certificate authorities whose roots are shipped in browsers and operating systems, each of which can issue a certificate for any name. Three mechanisms keep that manageable. Before issuing, a CA must verify that the requester controls the domain (domain validation, by placing a token in DNS or at a well-known HTTP path), and the ACME protocol, introduced by Let's Encrypt, automates that check and the whole issuance. Certificate Transparency requires every publicly trusted certificate to be logged in public append-only logs, and browsers reject certificates without proof of logging (SCTs); domain owners can monitor the logs and notice a certificate for their name that they did not request. CAs that misissue are removed from trust stores, which has happened to several, including large ones.

Revocation, telling clients that a certificate must no longer be trusted before it expires, never worked well. Certificate revocation lists grew large, OCSP online checks were slow, leaked browsing history to the CA, and were usually "soft-fail" (ignored when the responder did not answer), which is exactly what an attacker arranges. The industry's answer is short lifetimes instead: Let's Encrypt shut down its OCSP service in 2025 and has offered six-day certificates since January 2026, and the CA/Browser Forum's ballot SC-081 reduces the maximum lifetime of public TLS certificates from 398 days to 200 days from March 2026, 100 days from March 2027 and 47 days from March 2029. The practical consequence for every team: certificate issuance and renewal must be fully automated, monitored, and tested, because manual renewal every six weeks will fail.

Talk track

"TLS 1.3 does ECDHE in one round trip, so keys have forward secrecy, and the server proves its identity by signing the handshake transcript with the key in its certificate. The client checks that the chain leads to a root in its trust store, that every signature verifies, that the name is in the SAN and that the certificate is valid now. Certificate Transparency makes misissuance visible; revocation never worked well, so lifetimes are getting short, 47 days by 2029, which makes automated renewal mandatory."

9.5Mutual TLS and service identity

In ordinary TLS only the server has a certificate; the client is authenticated later, by a password or token inside the channel. In mutual TLS the server sends a CertificateRequest and the client presents its own certificate and signs the transcript with its key. That is the standard way for services to authenticate each other: the photo service accepts calls only from clients with a certificate issued by the company's internal CA for an approved service name. Service meshes (Istio, Linkerd) automate it with sidecar proxies that obtain short-lived certificates (often valid for hours) for each workload and rotate them continuously; the SPIFFE standard defines the identity format (spiffe://example.com/ns/prod/sa/billing) and how workloads obtain these certificates (Backend 11.3).

mTLS failures are confusing because in TLS 1.3 the client's certificate is checked after the client has already sent its Finished, so the error arrives as an alert on the first read rather than during connect. The experiment shows the three cases against a server that requires client certificates:

client sends no certificate           → tlsv13 alert certificate required

The second case is the client-side version of the missing-intermediate bug: the server trusts the internal root but was never given the intermediate, so the client must send it.

9.6Pinning, rotation and private PKIs

Certificate pinning means the client accepts only specific keys or CAs for a server, not anything the trust store would accept. It protects against a compromised or coerced CA and against corporate interception proxies, and it is a classic cause of outages: when the pinned key is rotated or the CA changes, every installed app that pinned the old one stops working until it is updated. Browsers abandoned dynamic pinning (HPKP) for that reason. If an app pins, it should pin the public key of the CA or intermediate rather than the leaf, include at least one backup key, and have a way to update the pins. For internal services a better tool is a private CA whose root only your own clients trust, which gives the same protection without depending on the public PKI.

Rotation is the routine that makes all of this safe: every key and certificate has an owner, an expiry that is monitored with alerts weeks ahead, and an automated renewal path that is exercised regularly, so that a rotation forced by a compromise is just a faster run of the normal process. The keys of a private CA root deserve the same care as a public CA's: offline or in an HSM, used only to sign intermediates.

In automotive

Diagnostics over IP can be protected with TLS: ISO 13400-2:2019 added a TLS port (3496) next to the plain DoIP port 13400, and testers authenticate with certificates issued by the vehicle manufacturer's PKI; UDS service 0x29 adds certificate-based authentication at the diagnostic level (Production integration 8.2). Vehicle-to-everything messages are signed with ECDSA under IEEE 1609.2 or the ETSI equivalents: each vehicle holds a pool of short-lived pseudonym certificates from a dedicated PKI (SCMS in the US, the EU's CCMS) and changes them regularly so that it cannot be tracked, and receivers must verify hundreds to thousands of signatures per second, which is why V2X units have hardware ECDSA accelerators. MACsec (IEEE 802.1AE) encrypts and authenticates in-vehicle Ethernet links hop by hop with AES-GCM in hardware, at line rate.

10Common attacks and their defences

Most successful attacks do not break cryptography. They go around it: through a protocol that trusts the network, a parser that trusts its input, a timing difference, a dependency nobody reviewed, or a token that proves less than the server assumes. The attacks below are the ones every engineer should be able to explain, together with the defence that actually works.

10.1On the network: man in the middle, spoofing and downgrades

A man in the middle (MITM) sits on the path and relays traffic between two parties who believe they talk directly. Getting onto the path is easy on a shared network: ARP spoofing (answering "192.168.1.1 is at my MAC" to everyone), a rogue DHCP server or Wi-Fi access point with an attractive name, or a poisoned DNS answer (Section 2.5) all redirect traffic. On the Internet, BGP hijacks, where a network announces someone else's prefix, have redirected traffic for whole services. None of these is preventable at the network layer in general, so the defence is to make the position useless: end-to-end TLS with certificate validation means the attacker sees only ciphertext and cannot impersonate the server without a valid certificate for its name.

The remaining gap is the first connection. A user who types example.com starts with plain HTTP, and an attacker can keep them on HTTP while talking HTTPS to the server ("SSL stripping"). HSTS (Strict-Transport-Security) tells the browser to use only HTTPS for the domain for a period, and the HSTS preload list builds that into browsers so that even the first visit is protected. Downgrade attacks try to make both sides agree on an older, weaker protocol version or cipher; TLS 1.3 prevents them by covering the offered versions in the Finished MAC and by placing a marker in the server random when it is forced to negotiate an older version. Interception proxies in companies and antivirus products, which install their own root certificate on clients, are MITM by design; they routinely weakened the security of the connections they inspected, and pinning or private trust stores are the way applications opt out.

10.2Replay and freshness

An authenticated message stays authentic forever, so an attacker who records "open the garage door" with its valid MAC can send it again tomorrow. Defences add freshness: a nonce chosen by the receiver (challenge-response), a counter the receiver checks is increasing, or a timestamp checked against a tolerance window, each covered by the MAC or signature. TLS handles this inside one connection with record sequence numbers; replay across connections is a problem only for 0-RTT data (Section 9.2) and for application-level tokens. A bearer token that is captured, by logging, a proxy or a malicious browser extension, can be replayed until it expires, which is why access tokens should be short-lived and why sensitive operations bind tokens to a client key (mTLS-bound or DPoP tokens) or ask for re-authentication. Replay is also the reason idempotency keys and request IDs are checked on the server side.

10.3Injection and the classic web attacks

Injection happens whenever data from an untrusted source is interpreted as code by some interpreter: a SQL engine, a shell, a browser, an XML parser, a log formatter. In SQL injection a query built by string concatenation, "SELECT * FROM photos WHERE id = " + id, lets 42 OR 1=1 return every row; the defence is parameterised queries, where the query and the data travel separately and the data can never become syntax. Command injection is the same with a shell; pass argument vectors to execve-style APIs instead of building command strings. Cross-site scripting (XSS) is injection into HTML: user-supplied text rendered without escaping becomes script running with the victim's session in the victim's browser. Context-aware output encoding (which template engines do by default), a Content Security Policy that forbids inline scripts, and HttpOnly cookies limit it. Cross-site request forgery (CSRF) makes a victim's browser send an authenticated request to another site, which SameSite cookies and anti-CSRF tokens prevent. Log4Shell (2021) was injection into a logging library that interpreted ${jndi:…} in logged strings and fetched and ran remote code: any string that reached a log line was a remote code execution.

Two attacks deserve special mention because they are the most common serious findings in modern APIs. Broken access control, in its simplest form an insecure direct object reference (IDOR): GET /photos/43 returns another user's photo because the server checks that the caller is logged in but not that the photo is theirs. Broken access control has topped the OWASP Top 10 since 2021; the defence is an authorisation check on every object access, in one central place, with tests. Server-side request forgery (SSRF): a feature that fetches a URL on the user's behalf (import a photo from a link, a webhook, a PDF renderer) is tricked into fetching an internal address, such as the cloud metadata service at 169.254.169.254, which returns credentials. The 2019 Capital One breach went that way. Defences are an egress allow-list for such fetchers, resolving and checking the address before connecting (and again after redirects), and metadata services that require a session token (IMDSv2).

10.4Memory-safety bugs

In C and C++, a parser that trusts a length field from the network can read or write past a buffer. About 70 % of the serious security bugs reported by Microsoft and by the Chrome team over many years were memory-safety bugs (Programming languages 3.7). The archetype is Heartbleed (2014): OpenSSL's TLS heartbeat handler copied as many bytes as the request's length field claimed, up to 64 kB, from a buffer that held only a few, and sent them back, leaking whatever was next in memory, including private keys and session cookies, from a large fraction of the Internet's HTTPS servers. The defences come in layers: memory-safe languages for new code that parses untrusted input (Rust, Go, Java, and the safer subsets of modern C++); bounds-checked containers and length validation in the rest (the 16 MB check in the example of Section 5.2); sanitizers and fuzzing in testing (Build and containers 8.5, Software quality 4.5), since a fuzzer finds exactly this class of bug within minutes; and exploit mitigations at run time, such as ASLR, stack canaries, non-executable memory and control-flow integrity, which make a bug harder to turn into code execution but do not remove it (Build and containers 8.6).

10.5Side channels: when timing tells the secret

A side channel leaks information through how a computation runs rather than what it returns: its timing, its power draw, its cache footprint. The simplest case is comparing a secret, an API key or a MAC, with an ordinary memcmp or ==, which stops at the first different byte. The comparison then takes slightly longer for each correct leading byte, and an attacker who can submit many guesses can find the secret one byte at a time: 32 × 256 guesses instead of 2256. The experiment measures it on one core: an early-exit comparison of a 32-byte token took 2.0 ns when the first byte was wrong and 11.1 ns when the first 28 were right, a steady 0.3 ns per correct byte, while a constant-time comparison that ORs together the XORs of all bytes took about 12.5 ns regardless.

The defence is to use the library's constant-time comparison for every secret (hmac.compare_digest in Python, crypto.timingSafeEqual in Node, CRYPTO_memcmp in OpenSSL, subtle.ConstantTimeCompare in Go) and to use cryptographic libraries whose primitives are written to run in constant time; table-based AES implementations leaked keys through cache timing, which is one reason hardware AES instructions matter. At the hardware level, Spectre and Meltdown (2018) showed that speculative execution leaves secret-dependent traces in the cache that another process, or JavaScript in a browser tab, can measure; mitigations in compilers, kernels and browsers (site isolation, reduced timer resolution) cost measurable performance and continue to be refined.

10.6Denial of service

Availability attacks exhaust some resource faster than the victim can add it: bandwidth, packet processing, connection state, or CPU per request. A SYN flood sends handshakes it never completes to fill the server's SYN queue; SYN cookies, enabled by default on Linux, make the attack ineffective by not storing state until the handshake completes. Reflection and amplification attacks send small UDP requests with the victim's forged source address to services whose answers are much larger: DNS (up to about 50×), NTP's old monlist command (over 500×), and memcached exposed to the Internet, which amplified by up to 51 000× and produced a 1.35 Tbit/s attack against GitHub in 2018. Defences are on several sides: operators filter forged source addresses at their network edge (BCP 38), services do not answer large responses to unverified addresses (QUIC's 3× limit, Section 4.3), and victims use scrubbing services and anycast CDNs whose capacity exceeds any single attack. Application-level attacks are cheaper for the attacker: the HTTP/2 rapid reset attack of 2023 opened and immediately cancelled streams, making servers do work for requests that cost the client almost nothing, and peaked at 398 million requests per second against Google. Per-client rate limits, limits on concurrent streams and work per connection, and load shedding are the defences (Backend 10.1, 10.2).

10.7Supply chain and authentication tokens

Modern software contains far more code from dependencies than from its own authors, and an attacker who compromises a dependency, a build system or a maintainer's account reaches every user. The xz backdoor (CVE-2024-3094) is the textbook case: over about two years a contributor gained the trust of the overworked maintainer of the xz compression library, became a co-maintainer, and shipped release tarballs (versions 5.6.0 and 5.6.1) whose build scripts injected a backdoor into the library; through a distribution patch that linked it into the SSH daemon, it would have let the attacker log in to affected servers. It was discovered in March 2024, just before reaching stable distributions, by an engineer who investigated a 500 ms slowdown of SSH logins. Earlier, the SolarWinds attack (2020) inserted a backdoor at build time into signed updates installed by thousands of organisations. The defences are reproducible builds, signed artefacts with verified provenance, pinned and reviewed dependencies, SBOMs to know what is affected when the next one happens, and least privilege for build systems (Build and containers 11.6).

Authentication tokens are the other place where APIs commonly fail. A JSON Web Token (JWT) is a signed set of claims (user, audience, expiry) that a service can verify without a database lookup. Its well-known pitfalls all come from trusting the token's own header: libraries that accepted "alg": "none" (no signature at all), or that verified an HS256 (HMAC) token using the server's RSA public key as the HMAC secret, so that anyone could forge tokens. The rules: fix the expected algorithm and key on the server, check expiry, audience and issuer, keep access tokens short-lived, and remember that a JWT cannot be revoked before it expires without extra state. OAuth 2.0 and OpenID Connect, the standard protocols for delegated login, are safe when used with the authorization-code flow and PKCE and dangerous when their redirect URIs and state parameters are validated loosely.

11Security engineering practice

Security is not a feature added at the end but a property of how a system is designed, built and operated. The practice consists of a few habits: think about attackers systematically before building, write code that does not trust its inputs, keep secrets out of reach, anchor trust in hardware where it matters, and assume that any single defence will fail.

11.1Threat modelling with STRIDE

Threat modelling answers four questions: what are we building, what can go wrong, what are we going to do about it, and did we do a good job. The usual tool for the first question is a data-flow diagram: external entities, processes, data stores and the flows between them, with trust boundaries drawn wherever data crosses from one level of trust to another. Threats concentrate at those boundaries. For the second question, Microsoft's STRIDE mnemonic walks each element through six threat types, each the violation of one security property: Spoofing (authenticity), Tampering (integrity), Repudiation (non-repudiation), Information disclosure (confidentiality), Denial of service (availability) and Elevation of privilege (authorisation).

The value is not the diagram but the conversation: walking the flows with the people who build them produces concrete threats ("can a user change the album ID in the upload request?") and concrete controls, which become backlog items and tests. A model should be updated whenever the architecture changes, kept small enough to be read, and ranked: a list of two hundred equally weighted threats is not used. Risk ranking can be qualitative, or follow a formal scheme where one is required; the automotive TARA of ISO 21434 is the same activity with a prescribed method for impact and feasibility ratings (Functional safety 9.2).

11.2Secure coding as a set of habits

Most of secure coding reduces to a few habits, applied everywhere rather than remembered occasionally. Validate input at the boundary against an allow-list of what is expected (type, length, range, format), and parse it into typed values once, so the rest of the code never handles raw strings from outside. Keep data and code apart: parameterised queries, argument vectors, template engines with automatic escaping. Fail closed: when an authorisation check errors, deny. Least privilege: each service, container and credential gets only the permissions it needs, so a compromise of one does not give the attacker everything (seccomp, capabilities and non-root containers in Build and containers 9.5). Use high-level, well-reviewed libraries for cryptography, authentication and parsing of complex formats. Handle errors without leaking: no stack traces or internal identifiers in responses, and no secrets in logs. And make the safe way the easy way: a shared HTTP client with sane timeouts and TLS verification on, a database layer that only offers parameterised queries, a lint rule that rejects verify=False. Static analysis, dependency scanning and fuzzing in CI catch what habits miss (Software quality 4.5).

11.3Secrets management and envelope encryption

Secrets, meaning database passwords, API keys, signing keys and TLS private keys, leak through a handful of predictable routes: committed to a Git repository (where deleting them later does not remove them from history), baked into container images, printed in logs or error messages, passed in environment variables that end up in crash dumps, or shared in chat. Scanners that check every commit for credentials catch the first route. The structural fix is a secrets manager (HashiCorp Vault, the cloud providers' secret stores, Kubernetes secrets backed by one of them): applications fetch secrets at run time using their own workload identity, every access is logged, and secrets can be rotated centrally. Better still are secrets that do not exist: short-lived credentials issued per workload (cloud IAM roles, SPIFFE certificates), and dynamic database credentials that expire after hours.

Data at rest is protected with envelope encryption. A key management service (KMS) holds a key-encryption key in an HSM, which never leaves it. For each object or file the service asks the KMS for a fresh data key, gets it back both in plaintext and wrapped (encrypted under the KEK), encrypts the data locally with the plaintext data key at full speed, stores the wrapped data key next to the data, and erases the plaintext copy. To read, it sends the wrapped data key to the KMS, which checks the caller's permissions, logs the request and unwraps it. The result: the bulk data never travels to the KMS, every decryption is authorised and audited, and rotating the master key means re-wrapping small data keys rather than re-encrypting terabytes.

11.4Hardware roots of trust: HSM, TPM, TEE and secure boot

Software can always be read by more privileged software, so keys that must survive a compromise of the operating system live in dedicated hardware that performs operations with the key and never releases it. A hardware security module (HSM) is a tamper-resistant device or network appliance that stores keys and signs, decrypts or derives inside; CAs keep their roots in HSMs, payment networks their PIN keys, and cloud KMSs their master keys. They are certified under FIPS 140-3 or Common Criteria. A TPM (Trusted Platform Module) is a small, cheap chip (or firmware equivalent) in almost every PC and server: it holds keys bound to the machine, and its platform configuration registers record hashes of every boot stage (measured boot). It can seal a secret, such as a disk encryption key, so that it is released only if the measurements match the expected boot chain, and it can attest to a remote party what software booted. Secure boot is the enforcing counterpart: each stage verifies the signature of the next before running it, starting from a key in ROM or fuses, so unsigned code never runs at all (Production integration 6 covers it in detail for ECUs). Trusted execution environments (Arm TrustZone, Intel SGX and TDX, AMD SEV-SNP) run code in an isolated world whose memory the main operating system or hypervisor cannot read; phones use TrustZone for fingerprint matching and key storage, cloud providers offer "confidential computing" VMs. Secure elements are smart-card chips (SIM, eSIM, payment cards, phone wallets) with the strongest physical protection of the group.

In automotive

Automotive microcontrollers include an HSM core, a separate small processor with its own memory and AES, ECC and random-number hardware, specified originally by the EVITA project in full, medium and light variants. It holds the SecOC keys, verifies the secure-boot chain, and protects diagnostic authentication; the application cores reach it only through a crypto driver interface (AUTOSAR's crypto stack, AUTOSAR 10.4). Central computers and gateways add intrusion detection that watches bus traffic for messages with wrong timing or content, and report to a vehicle security operations centre, as UN R155 requires (Functional safety 9.7).

11.5Defence in depth and zero trust

No single control survives every attack, so systems are built with several independent layers, each of which must fail for the attacker to succeed: TLS on every connection, authentication and authorisation in every service, least-privilege credentials, encrypted storage, monitoring that detects unusual behaviour, and the ability to rotate everything quickly after an incident. The older model, a hard perimeter firewall around a trusted internal network, failed because attackers who got inside, through a phishing email or a compromised laptop, could reach everything. Zero trust is the name for the replacement: no request is trusted because of where it comes from; every request is authenticated and authorised on the identity of the user and the workload and the state of the device, wherever it originates. Mutual TLS between services, short-lived credentials and per-request authorisation are its building blocks, and they are the same tools as in the rest of this chapter. The last layer is people and process: patching quickly, practising incident response, and making it easy for anyone to report something that looks wrong.

Why it matters

Practical security questions are rarely about cipher details. They are about judgement: given this system, where would you attack it, what would you protect first, and how would you know you had been breached. A short, concrete threat model of the system under discussion, with two or three ranked threats and their controls, answers that better than any list of acronyms.

QSelf-check questions

Q.1Core questions

What happens when you type a URL into a browser and press Enter?Basic

The browser parses the URL and checks its caches and HSTS list. It resolves the host name: browser cache, OS stub resolver, then a recursive resolver that walks root, TLD and authoritative servers, each answer cached for its TTL. It opens a TCP connection (SYN, SYN-ACK, ACK: one RTT), routed hop by hop by longest prefix match, through NAT at the edge; or QUIC over UDP if the server advertised HTTP/3. TLS 1.3 negotiates keys with ECDHE in one more RTT; the server proves its identity with a certificate chain and a signature over the handshake, and ALPN picks HTTP/2. The browser sends the GET as an HTTP/2 HEADERS frame; the response comes back through load balancers and maybe a CDN, paced by congestion control. The browser parses the HTML and repeats much of this for sub-resources over the same connection. On a 40 ms path the first byte arrives after about three RTTs.

What is the difference between TCP and UDP, and when would you use each?Basic

TCP is a connection-oriented, reliable, ordered byte stream with flow and congestion control; it costs a handshake and suffers head-of-line blocking, and it has no message boundaries. UDP sends independent datagrams with ports and a checksum only: no handshake, no reliability, no ordering, no congestion control, but message boundaries are kept. Use TCP for request-response, transfers and anything that must arrive complete; UDP when an exchange fits one datagram (DNS), when late data is useless (voice, video, game state), for multicast, or as the base of your own transport such as QUIC. With UDP the application owns loss handling, pacing, MTU and NAT keep-alives.

Explain the TCP three-way handshake and why it has three steps.Basic

The client sends SYN with a random initial sequence number and options (MSS, window scale, SACK, timestamps); the server replies SYN-ACK with its own ISN and acknowledges the client's; the client acknowledges the server's ISN. Each side must choose its own starting number and learn that the other received it, which needs at least three messages, since the middle one can carry the server's SYN and its ACK together. The random ISNs prevent off-path attackers from injecting data and stop old duplicates from being mistaken for a new connection. The handshake costs one RTT before data can flow.

Why does TIME_WAIT exist, and what problems does it cause?Intermediate

The side that closes first keeps the connection's four-tuple reserved for 60 seconds on Linux, so that delayed segments from this connection cannot be accepted by a new connection with the same addresses and ports, and so it can re-send the final ACK if the peer's FIN is retransmitted. A client that opens and closes many short connections to one server can exhaust its ephemeral ports (about 28 000), and a server that cannot restart because the port is "in use" lacks SO_REUSEADDR. The fix is connection reuse and pooling, not shortening TIME_WAIT.

What is the difference between flow control and congestion control?Basic

Flow control protects the receiver: the receive window advertised in every ACK says how much free buffer the receiver has, and the sender never exceeds it. Congestion control protects the network: the sender's congestion window is its estimate of how much the path can hold, raised while all goes well and cut on loss (or set from a bandwidth model in BBR). The sender may have min(cwnd, rwnd) bytes unacknowledged; throughput is at most that divided by the RTT.

Explain slow start, congestion avoidance, CUBIC and BBR.Intermediate

Slow start begins with a small window (10 segments) and doubles it each RTT until a loss or threshold, finding the order of magnitude fast. Congestion avoidance (Reno) adds one segment per RTT and halves on loss: AIMD, which converges to fair shares. CUBIC grows as a cubic function of time since the last loss, fast when far below the previous maximum and slow near it, and cuts by 30 %; it fills large BDPs much faster than Reno and is the default in Linux. Both are loss-based, so they fill buffers and are hurt by random loss. BBR estimates bottleneck bandwidth and minimum RTT, paces at the bandwidth with about two BDPs in flight, and probes periodically; v1 ignores loss, so it keeps queues short and tolerates random loss, but can be unfair and retransmit heavily.

What is the bandwidth-delay product and why does it matter?Intermediate

It is the amount of data in flight needed to keep a path busy: bandwidth times RTT, for example 20 Mbit/s × 40 ms = 100 kB, or 10 Gbit/s × 150 ms = 187 MB. If the window (receive buffer, congestion window, or an application's own limit such as one outstanding request) is smaller, throughput is window / RTT regardless of link speed. It explains why far-away transfers are slow, why window scaling and buffer autotuning exist, and how big router buffers should be.

What is Nagle's algorithm and when do you disable it?Intermediate

Nagle holds back a small segment while earlier data is unacknowledged, coalescing small writes. Combined with the receiver's delayed ACK (up to about 40 ms on Linux), a request written in two pieces waits for the ACK of the first piece, adding ~40 ms per request. Disable it with TCP_NODELAY for request-response and interactive protocols (all RPC libraries do), and in any case write each message in one call; use TCP_CORK when assembling a large message from pieces.

What is head-of-line blocking, and how do HTTP/2 and HTTP/3 deal with it?Intermediate

It is when a lost or slow item delays everything queued behind it. HTTP/1.1 had it at the HTTP level: one response at a time per connection. HTTP/2 multiplexes streams on one connection, fixing that, but TCP delivers one ordered byte stream, so one lost segment stalls all streams until it is retransmitted. HTTP/3 runs each stream on its own QUIC stream with independent ordering, so a loss stalls only the stream whose data was lost. With no loss there is no difference.

What is QUIC and why was it created?Intermediate

QUIC is a reliable, congestion-controlled, encrypted transport over UDP, implemented in user space. It integrates TLS 1.3 so transport and crypto setup take one RTT (0-RTT on resumption), carries independent streams to avoid cross-stream head-of-line blocking, encrypts packet numbers and most headers so middleboxes cannot ossify it, identifies connections by connection IDs so they survive address changes, and can evolve with the application. Costs: more CPU per byte, UDP blocked on some networks (TCP fallback needed), and harder debugging without keys.

How do epoll and io_uring differ from select and from thread-per-connection?Intermediate

Thread-per-connection is simple but each thread costs a stack and scheduling, which does not scale to tens of thousands of mostly idle connections. select and poll pass the whole descriptor list on every call and scan it, O(n). epoll registers interest once and returns only ready descriptors, so cost scales with activity; the application then does non-blocking reads and writes (readiness model). io_uring is a completion model: the application submits operations to a shared ring and collects results, avoiding a syscall per operation and supporting true async file I/O. Edge-triggered epoll requires reading until EAGAIN.

What does a TLS 1.3 handshake do, step by step?Intermediate

ClientHello carries supported versions and cipher suites, SNI, ALPN and a key share (for example X25519). ServerHello returns the server's key share; both derive handshake keys from the ECDHE secret with HKDF. The server sends, encrypted, EncryptedExtensions, its certificate chain, CertificateVerify (a signature over the transcript with the certificate key) and Finished (a MAC over the transcript). The client validates the chain and name, checks the signature and Finished, sends its Finished and its request with application keys. One RTT in total; session tickets allow resumption and 0-RTT.

How does a client validate a server certificate?Intermediate

It builds a chain from the leaf through the intermediates the server sent to a root in its own trust store, verifies each signature, checks that the current time is within each certificate's validity, that the requested host name matches a SAN entry, that key usage and extended key usage allow server authentication, that CA certificates have basicConstraints CA:TRUE and path length limits hold, and, depending on policy, Certificate Transparency proofs and revocation. Then, separately, the handshake's CertificateVerify proves the server holds the leaf's private key.

What is forward secrecy?Basic

The property that compromise of a long-term key does not expose past sessions. It comes from ephemeral key exchange: each connection uses fresh Diffie-Hellman keys that are deleted afterwards, and the long-term key only signs. With old RSA key transport, anyone who recorded traffic and later obtained the server's private key could decrypt everything. TLS 1.3 requires ephemeral key exchange.

Symmetric versus asymmetric cryptography: why use both?Basic

Symmetric ciphers (AES-GCM) are fast, gigabytes per second per core, but need a shared key. Asymmetric cryptography (ECDH, signatures) lets strangers agree on a key and authenticate each other over a public channel, but is thousands of times slower per operation and has larger outputs. Protocols therefore use asymmetric cryptography in the handshake to authenticate and agree a key, then symmetric AEAD for the data.

What is the difference between a hash, a MAC and a signature?Basic

A hash is a keyless fingerprint: anyone can compute it, so it detects accidental change or checks against a value obtained securely, but proves nothing about origin. A MAC uses a shared secret key: it proves integrity and origin to someone who shares the key, but that party could have produced it too. A signature uses a private key and is verified with the public key: anyone can verify, only the key holder can sign, which gives non-repudiation and suits one signer with many verifiers (updates, certificates).

What is mutual TLS and when would you use it?Intermediate

TLS in which the client also presents a certificate and signs the handshake, so both sides are authenticated cryptographically. It is the standard for service-to-service authentication inside a system, usually via a service mesh that issues short-lived workload certificates (SPIFFE identities) from an internal CA and rotates them automatically, and for devices talking to a backend with factory-provisioned certificates. The client must send its intermediates, and in TLS 1.3 a rejected client certificate shows up as an alert on the first read.

How would you store user passwords?Basic

Never in plaintext or with a fast hash. Use a password hashing function, Argon2id ideally (or scrypt, bcrypt, PBKDF2 with a high iteration count), with a unique random salt per password, stored with its parameters so they can be raised later; compare in constant time; rate-limit and monitor login attempts; and support multi-factor authentication. The goal is to make each guess against a stolen database expensive, since users reuse weak passwords.

Explain SQL injection, XSS, CSRF and SSRF and their defences.Intermediate

SQL injection: untrusted data concatenated into a query becomes SQL; use parameterised queries. XSS: untrusted data rendered into HTML becomes script in the victim's browser; use context-aware escaping, CSP and HttpOnly cookies. CSRF: another site makes the victim's browser send an authenticated request; use SameSite cookies and anti-CSRF tokens. SSRF: a server-side fetch is pointed at internal addresses such as the cloud metadata service; use egress allow-lists, validate resolved addresses, and require tokens for metadata. All except CSRF are cases of data being interpreted as code or as a trusted destination.

How would you threat-model a new service?Intermediate

Draw a data-flow diagram with external entities, processes, data stores and flows, and mark trust boundaries. Walk each element and boundary through STRIDE: spoofing, tampering, repudiation, information disclosure, denial of service, elevation of privilege. Write concrete threats ("can user A read user B's photo by changing the ID?"), rank them by impact and likelihood, assign controls that become backlog items and tests, and revisit when the architecture changes. Do it with the people building the system.

How do you manage secrets in a cloud service?Intermediate

Keep them out of code, images, logs and environment dumps; scan commits for leaks. Fetch them at run time from a secrets manager using the workload's own identity, with access logged and rotation automated. Prefer short-lived, automatically issued credentials (IAM roles, workload certificates, dynamic database users) so there is little to leak. Encrypt data at rest with envelope encryption: data keys wrapped by a KMS master key in an HSM, decryption authorised and audited per call.

How do you debug "the service is slow for some users"?Advanced

First quantify: which users, which percentile, since when. Break one request into a waterfall (DNS, connect, TLS, first byte, transfer) with client timings or tracing. Far-away users with slow setup point to round trips: reuse connections, terminate TLS near users, enable HTTP/3. Slow transfer points to window or loss: check ss for cwnd, RTT and retransmits, compare with iperf3 over the same path. If the network is fine, look at the server's queueing and dependencies. Change one thing at a time and measure again.

Q.2Why and what if

Why does a router not need to look at the TCP header, but a NAT box does?Why

Routing decides the next hop from the destination IP address only. NAT maps many inside hosts to one outside address, and the only way to tell their flows apart, and to route replies back, is the port numbers in the transport header, which it rewrites. That is why NAT breaks protocols that put addresses in their payload, and why encrypted transports keep their port numbers visible.

What if a firewall drops all ICMP?What if

Ping and traceroute stop working, which is the intended effect, but path MTU discovery also breaks: routers on a path with a smaller MTU drop large packets with the don't-fragment bit and their "fragmentation needed" or "packet too big" messages never arrive. Small requests work, large responses hang. In IPv6, blocking ICMPv6 also breaks neighbour discovery. Filter ICMP selectively instead.

Why is 1 % packet loss much worse on a 150 ms path than on a 10 ms path?Why

Loss-based TCP throughput is roughly (MSS / RTT) × 1.22 / √p. At 1 % loss that is about 14 Mbit/s at 10 ms but under 1 Mbit/s at 150 ms; the window regrows by one segment per round trip after each cut, and longer round trips mean slower regrowth. Recovery also waits at least one RTT per loss. The interactive Figure 3.4 shows the 1/RTT dependence.

What if a server's router buffer is ten times the BDP?What if

Loss-based senders fill it before backing off, so the queue adds up to ten RTTs of delay: bufferbloat. Throughput is unaffected, but every interactive flow sharing the link sees hundreds of milliseconds of extra latency; the measurement with 5 BDPs raised the median RTT from 40 to 199 ms with CUBIC. AQM (fq_codel, CoDel) in the router, ECN, or a delay-aware sender such as BBR keeps the queue short.

Why does BBR v1 keep almost full throughput at 5 % random loss when CUBIC collapses?Why

CUBIC treats every loss as congestion and cuts its window, so random losses keep the window far below the BDP. BBR v1 sets its rate from measured delivery rate and minimum RTT and does not react to loss at all, so random loss only costs the retransmissions (1453 in 15 s in the measurement). The same property makes it aggressive when loss really is congestion, which is why later BBR versions react to loss again.

What if two HTTP/2 requests share a connection and one response is very large?What if

HTTP/2 interleaves frames of both streams, so the small response is not stuck behind the large one at the HTTP level, unlike HTTP/1.1; the server's scheduler and stream priorities decide the interleaving, and per-stream flow control keeps one stream from taking the whole window. But any lost TCP segment, from either stream, stalls both until it is retransmitted.

Why does QUIC pad its first packet to 1200 bytes?Why

Two reasons. It proves that the path carries datagrams of at least 1200 bytes, the size QUIC assumes. And servers may send at most three times the bytes received from an unvalidated address, so a large first packet allows a full server flight while making the protocol useless as a reflection amplifier: an attacker spoofing a victim's address gets at most 3× amplification.

What if the same AES-GCM nonce is used twice with one key?What if

Both messages are XORed with the same keystream, so the XOR of the ciphertexts equals the XOR of the plaintexts, and knowing or guessing one plaintext reveals the other (the experiment recovers a PIN this way). In addition, two tags under one nonce let the attacker compute the GHASH key and forge valid tags for arbitrary messages. Confidentiality and integrity are both lost for that key.

Why is SHA-256(secret ‖ message) not a safe MAC, while HMAC is?Why

SHA-256's output is its internal state after the last block. An attacker with a valid tag can load that state and hash more blocks, producing a valid tag for the message plus padding plus an extension without knowing the secret (length extension; demonstrated in the experiment). HMAC hashes the message under an inner keyed hash and then hashes that result again with an outer key, so the published value is not a state that can be continued.

What if an ECDSA signer reuses its random nonce k?What if

The two signatures share r, and from s1 − s2 = k⁻¹(z1 − z2) the attacker computes k and then the private key from either signature. The experiment recovers a P-256 key from two firmware signatures this way; it has happened to a games console and to cryptocurrency wallets. Deterministic nonces (RFC 6979) or Ed25519 remove the dependency on a good random generator at signing time.

Why does the server's certificate alone not prove it is the real server?Why

A certificate is public; anyone can copy it and send it. What proves identity is possession of the matching private key, which the server shows in TLS 1.3 by signing the handshake transcript (CertificateVerify), including both key shares, so the signature cannot be reused in another handshake. A man in the middle with a copied certificate cannot produce it.

What if the server sends only its leaf certificate?What if

Clients that have the intermediate cached, or fetch it from the certificate's AIA URL (many browsers), succeed; curl, most language runtimes and mobile apps fail with "unable to get local issuer certificate". It looks like an intermittent, client-specific bug. The fix is to configure the server with the full chain, leaf then intermediates.

Why are certificate lifetimes being shortened to 47 days instead of fixing revocation?Why

Revocation checking never worked reliably: CRLs are large, OCSP is slow, leaks browsing data and is usually soft-fail, so an attacker who blocks the check wins. A short lifetime bounds how long a compromised or misissued certificate stays usable without any online check. The cost is that renewal must be automated, which ACME made easy, and that has been the push behind ballot SC-081.

What if an attacker can measure how long your API takes to reject a wrong API key?What if

If the key is compared with an early-exit comparison, each correct leading byte adds a little time (0.3 ns per byte in the experiment), and with enough repetitions and statistics the attacker recovers the key byte by byte. Use a constant-time comparison, or better, compare HMACs or hashes of the key, and rate-limit failed attempts.

Why is NAT not a security control, and what changes with IPv6?Why

NAT hides internal addresses, but the protection comes from the stateful rule that drops unsolicited inbound packets. With IPv6 every device has a global address and no NAT, so the stateful firewall must be configured explicitly; forgetting it exposes devices directly. NAT also does nothing against outbound connections, which is how most compromises talk to their operators.

What if a long-lived idle TCP connection silently stops working after a few minutes?What if

A NAT, firewall or load balancer on the path dropped its state for the idle flow; the endpoints still believe the connection exists, and the next send gets a reset or disappears into a retransmission timeout. Send application or TCP keep-alives more often than the shortest idle timeout on the path, and set read timeouts so a dead connection is detected.

Why does 0-RTT data need special handling?Why

The early data is encrypted with keys from an earlier session's ticket, before the server can contribute fresh randomness, so an attacker can record the first flight and replay it; the server cannot tell the copy from the original. Servers accept 0-RTT only for idempotent requests (GET without side effects), may keep replay caches, and many disable it.

What if your service fetches user-supplied URLs?What if

It is an SSRF candidate: attackers will point it at 127.0.0.1, internal service names, or 169.254.169.254 to steal cloud credentials, and use redirects or DNS rebinding to get around simple checks. Run the fetcher in an isolated network with an egress allow-list, resolve and validate the address before connecting and after each redirect, limit protocols and response size, and require IMDSv2-style tokens on metadata services.

An entity whose signature on a certificate is trusted to bind a key to a name; roots are in client trust stores.

Public, append-only logs of issued certificates; browsers require proof of logging.

Loss-based congestion control whose window grows as a cubic function of time since the last loss; Linux default.

Sender-side limit on unacknowledged data, set by congestion control.

Encrypting data with a data key that is itself encrypted (wrapped) by a key-encryption key held in a KMS or HSM.

Linux readiness-notification interface that scales with the number of ready descriptors.

Past sessions stay secret even if long-term keys are later compromised.

RPC framework over HTTP/2 with length-prefixed protobuf messages, deadlines and status in trailers.
