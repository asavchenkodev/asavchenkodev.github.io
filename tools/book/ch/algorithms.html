Data structures, algorithms and complexity

How the classic structures lie in memory, why each one exists, and how to recognise which algorithm a problem needs. The chapter starts with complexity analysis and the reasons cache behaviour can beat the textbook answer, walks through arrays, lists, ring buffers, hash tables, heaps, search trees, tries, union-find and graphs, then sorting, searching and the recurring algorithm patterns, bit manipulation, and a step-by-step method for unfamiliar problems with worked C++ solutions. The running example is the backend of an online shop: its request log, session cache, rate limiter, search box, job scheduler, build graph and delivery routing each need a different structure.

1Complexity: how cost grows with the input

A data structure is a decision about how data lies in memory, and an algorithm is a decision about the order in which you touch it. Complexity analysis is the vocabulary for comparing those decisions before you have measured anything: it says how the cost grows when the input grows, which is what decides whether a design survives contact with production data.

1.1Why this still matters when the library has everything

Every mainstream language ships a sorted map, a hash map, a priority queue and a sort routine, so it is fair to ask why an engineer should still know how they work. The answer is that the library gives you the parts but not the choice. The shop backend in this chapter keeps a log of every request, a cache of logged-in sessions, a rate limiter per client, a search box that suggests products as you type, a scheduler that runs delayed jobs, a build that compiles its services in dependency order, and a routing service that plans deliveries. Each of these has a natural structure, and picking the wrong one rarely fails a test. It fails later, when the input is a hundred times larger than on the developer's laptop: the session lookup that scanned a list was fine with 50 users and takes the site down with 50 000; the "find duplicates" job that compared every pair finished in a second on test data and runs for hours on the real export.

The second reason is that the structures teach a way of thinking that transfers. Almost every performance problem is one of a handful of shapes: work repeated that could be remembered, a search that scans when it could jump, data scattered when it could be contiguous, or a quadratic loop hiding inside a linear-looking one. Once you can see those shapes, you find them in code reviews, in system designs and in the profiles of slow programs.

Why it matters

The cost of a wrong structure grows with the data, so it shows up in production rather than in review. Knowing the structures in memory is what lets you predict that cost instead of discovering it.

1.2Big-O counts how work grows, not how long it takes

Measuring a program tells you how long it took on one machine with one input. Complexity analysis asks a different question: if the input doubles, what happens to the work? To answer it, we count the basic steps an algorithm performs (comparisons, memory reads, loop iterations) as a function of the input size n, and then keep only the term that dominates for large n. A loop that runs 3n + 20 steps and one that runs n/2 steps are both O(n): double the input and the work doubles. A loop nested inside another over the same data is O(n²): double the input and the work quadruples.

Formally, f(n) = O(g(n)) means that beyond some size, f is at most a constant times g. It is an upper bound. Its siblings are Ω (a lower bound: at least a constant times g) and Θ (both at once: the growth rate exactly). In everyday engineering speech "O" is used loosely to mean Θ, "this is O(n log n)", and that is fine as long as you know the difference when someone asks for a lower bound, as in the proof that comparison sorting needs Ω(n log n) comparisons (Section 6.1).

The constants we drop are not unimportant; they are just not what complexity is for. Complexity tells you which algorithms are even in the race at your input size; constants, memory layout and the hardware decide the winner among those that are. Figure 1.1 makes the first part concrete: move the slider and watch which classes stay inside a 100 ms budget at 10⁹ simple operations per second, roughly what one modern core manages.

Three refinements matter in practice. First, which case: an algorithm can have different best, average and worst cases. Quicksort averages O(n log n) but degrades to O(n²) on unlucky pivots; a hash table lookup averages O(1) but is O(n) when every key collides. When latency guarantees matter (a real-time loop, a request served under an SLA, a server facing hostile input) the worst case is the one you design for. Second, which n: graph algorithms have two sizes, nodes V and edges E, and "O(V + E)" is not the same as "O(V²)" for a sparse graph. String problems often have the text length n and the pattern length m. Third, what a step costs: Big-O silently assumes each basic step costs about the same. On real hardware a memory read costs anything from 1 ns to 100 ns depending on where the data is, which is the subject of Section 1.6.

Pitfall

Hidden loops. vector::erase at the front, string concatenation in a loop, list.size() in some older libraries, std::find inside a loop and in on a Python list are all linear. A loop that calls one of them is quadratic even though it looks like a single pass.

1.4Amortised cost: why push_back is O(1) even though it sometimes copies everything

A std::vector keeps its elements in one heap block with some spare capacity at the end. Appending writes into the spare slot, which is O(1). When the block is full, the vector allocates a larger one, moves every element across and frees the old block, which is O(n) for that one push. Saying "push_back is O(n) in the worst case" is true but misleading, because the expensive pushes are rare and get rarer as the vector grows.

Amortised analysis averages the cost over a whole sequence of operations instead of looking at one. If the capacity doubles each time it runs out, the copies happen at sizes 1, 2, 4, 8, …, and the total number of elements ever moved while pushing n elements is 1 + 2 + 4 + … + n/2 < n. Add the n writes of the new elements themselves and the total work is under 2n, or O(1) per push on average, with no probability involved. Figure 1.2 shows the pattern: most bars are a single unit of work, and the tall ones are spaced exponentially further apart.

The experiment for this chapter pushed 2²⁰ ints into an empty std::vector with GCC 13: 21 reallocations, 1 048 575 element moves in total, which is exactly one move per push on average. The growth factor is an implementation choice. libstdc++ and libc++ double; MSVC grows by 1.5×, which wastes less memory and lets a freed block be reused by a later allocation, at the price of a few more reallocations. Any constant factor greater than 1 gives amortised O(1); growing by a fixed amount (say 100 elements each time) does not, and makes n pushes cost O(n²).

Pitfall

Amortised O(1) is not real-time O(1). One push in a million still copies the whole vector, and in a latency-sensitive loop that single spike is what you see in the 99.99th percentile. Call reserve() when the size is known, or use a structure with a fixed capacity. Every reallocation also invalidates all pointers, references and iterators into the vector.

Talk track

"Amortised O(1) means a sequence of n operations costs O(n) in total, even if a single one is expensive. Vector doubling is the classic case: the copies form a geometric series that sums to less than n. It's a guarantee about throughput, not about the latency of any one call."

1.5Space complexity counts the extra memory, including the stack

Space complexity measures the memory an algorithm needs beyond its input. Merge sort needs an O(n) buffer; heapsort sorts in place with O(1) extra; a hash set used to detect duplicates costs O(n) memory to save O(n) time per query. The trade of memory for time is the most common optimisation in this chapter, and saying it out loud ("I'll spend O(n) memory on a hash set to get from O(n²) to O(n)") is what makes the choice reviewable.

Recursion uses memory that does not appear in the code: every call keeps a frame on the call stack until it returns. A recursive DFS on a path-shaped graph of a million nodes needs a million frames; at 50–100 bytes each that is 50–100 MB, while the default main-thread stack on Linux is 8 MB and a thread created by std::thread often has the same or less (on embedded RTOS tasks it can be a few kilobytes). That is why production code converts deep recursion into a loop with an explicit stack on the heap, and why "recursive solutions use O(depth) space" belongs in every complexity statement.

1.6When the cache beats the asymptotics

Big-O assumes every memory access costs the same. Hardware disagrees by two orders of magnitude. A core reads from its L1 cache in about 1 ns, from L2 in about 4 ns, from the shared L3 in 10–40 ns and from DRAM in roughly 80–120 ns. Data moves between those levels in cache lines of 64 bytes, and the hardware prefetcher watches the access pattern: if you walk memory sequentially it fetches the next lines before you ask for them, so a sequential scan runs at close to L1 speed even when the data lives in DRAM. Random access defeats the prefetcher and pays the full DRAM latency for every miss. The details of cache lines, prefetching and false sharing are in C++ 12, Cache lines and locality; here what matters is the consequence for choosing structures.

The measurements in Figure 1.3 come from experiments/bench.cpp (GCC 13, -O2, a 2.1 GHz cloud Xeon; absolute times vary, ratios are stable). Summing 2²⁰ ints from a std::vector took 0.25 ns per element, because the compiler vectorised the loop and the prefetcher kept it fed. The same values in a std::list whose nodes were allocated one after another took 2.8 ns per element: every step must load next before it knows where to go, so the loads cannot overlap. After shuffling the node order, each step became a DRAM miss and the loop took 139 ns per element. All three loops are O(n). Summing a 4096 × 4096 matrix row by row took 9.7 ms; column by column, touching one int per cache line before jumping 16 KB ahead, took 143 ms, 15 times slower for identical arithmetic.

The same effect moves the crossover points between algorithms. Searching a sorted array of 8 to 256 ints, a plain linear scan beat std::lower_bound in the experiment (8.8 vs 14.6 ns per query at 8 elements, 38 vs 46 ns at 256), because the scan is sequential and its branch is predictable while binary search jumps around and mispredicts half its branches; by 1024 elements binary search won clearly (58 vs 99 ns). For one million 64-bit keys, an unordered_map lookup took 54 ns, a sorted vector with lower_bound 355 ns and a std::map 1 315 ns: all three structures are "fast", and they differ by a factor of 24 because the tree pays one cache miss per level on 20 levels of scattered nodes.

In practice

Default to contiguous storage: std::vector, a sorted vector instead of a small std::map, an open-addressing hash table instead of a node-based one. Reach for node-based structures when you need what only they give (stable addresses, O(1) splicing, ordered iteration under constant insertion), and measure before believing either Big-O or intuition.

Talk track

"Big-O tells me which algorithms are viable at this size; the memory layout decides which one is fastest. A linked list and a vector are both O(n) to traverse, but the vector streams through cache lines and the list takes a cache miss per node, so in practice the difference can be two orders of magnitude."

2Linear structures: arrays, lists, stacks, queues and ring buffers

Linear structures keep elements in a sequence. They differ in where the elements live (one block, scattered nodes, fixed chunks) and therefore in which operations are cheap. Knowing the layout predicts every row of the cost table in Section 2.6.

2.1Arrays and std::vector: one block, index arithmetic

An array is the simplest possible structure: elements of the same size, one after another. Element i lives at base + i × sizeof(T), so access by index is a multiplication and an add, O(1), and walking the array visits consecutive addresses, which the cache rewards (Section 1.6). A C array or std::array has its size fixed at compile time; std::vector adds a heap block that can grow. In memory a vector is three pointers on the stack or inside its owner (begin, end of the used part, end of capacity), 24 bytes on a 64-bit system, pointing at one heap block (Figure 2.1, top).

The block layout explains the vector's cost table. Reading or writing by index is O(1). Appending is amortised O(1) (Section 1.4). Inserting or erasing in the middle is O(n), because every element after the position must shift by one, although that shift is a memmove of contiguous memory and runs at gigabytes per second, which is why a vector often beats a list even for middle insertions up to surprisingly large sizes. Erasing from the front is O(n) for the same reason; if the order does not matter, the "swap with the last and pop" idiom erases any element in O(1).

Pitfall

Any operation that may reallocate (push_back, insert, resize, reserve) invalidates every pointer, reference and iterator into the vector. Holding &v[0] across a push_back is a classic use-after-free. Store indices instead of pointers when the vector can grow.

2.2Linked lists: cheap splicing, expensive walking

A linked list stores each element in its own node together with a pointer to the next node (singly linked, std::forward_list) or to both neighbours (doubly linked, std::list). Because nodes are linked rather than adjacent, inserting or removing a node anywhere is O(1) once you hold a pointer to the position: rewrite two or four pointers and you are done, no other element moves. Nodes never move, so pointers and iterators to them stay valid for as long as the node exists, and a whole range of nodes can be moved from one list to another (splice) in O(1).

The price is everything else. There is no index: reaching the k-th element means following k pointers. Each node is a separate allocation with two pointers of overhead plus allocator bookkeeping, so a std::list<int> spends about 32 bytes per 4-byte int. And traversal is a chain of dependent loads that the CPU cannot overlap, which made the list 11 to 560 times slower than a vector in Figure 1.3. The famous line from Bjarne Stroustrup's talks is that you should use a vector unless you have measured a reason not to, and for most workloads that advice holds.

Lists still earn their place where their unique properties matter. An LRU cache (Section 9.3) needs to move an entry to the front in O(1) without invalidating the hash map that points at it. A kernel or allocator keeps free blocks or runnable tasks on intrusive lists, where the next/prev pointers live inside the object itself, so linking needs no allocation at all; the Linux kernel's list_head and Boost.Intrusive work this way. Lock-free queues and stacks are also built from linked nodes (Concurrency 5.3).

Interesting detail

The two-pointer techniques used on linked lists come from the lack of an index. To find the middle in one pass, move a slow pointer one step and a fast pointer two steps; when fast reaches the end, slow is in the middle. The same idea (Floyd's tortoise and hare) detects a cycle: if the fast pointer ever meets the slow one, the list loops.

2.3Stacks and queues are interfaces, not layouts

A stack allows access only at one end: push on top, pop from the top, last in, first out (LIFO). A queue pushes at the back and pops from the front, first in, first out (FIFO). Neither says anything about memory; they are restrictions of a sequence, and the restriction is the point, because it makes the intent clear and every operation O(1). In C++ they are adaptors: std::stack and std::queue wrap another container (a std::deque by default; a stack works well on a std::vector) and expose only push, pop and top/front.

Stacks appear wherever work must be undone in reverse order or resumed later: the call stack itself, undo histories, matching brackets in a parser, evaluating expressions, and iterative DFS (Section 5.2). Queues appear wherever work must be done in arrival order: request queues, BFS, message passing between threads, and print or job spoolers. In the shop backend, the HTTP server keeps a queue of accepted connections waiting for a worker thread, and the checkout service keeps a stack of compensating actions to undo a half-finished order.

A monotonic stack is a stack whose contents are kept sorted by popping everything that violates the order before each push. It answers "for each element, what is the next greater element to the right?" in one O(n) pass, because each element is pushed and popped at most once, and it turns up in problems about stock spans, daily temperatures and the largest rectangle in a histogram.

2.4Deques: chunks give O(1) at both ends

A double-ended queue supports push and pop at both the front and the back in O(1) and still offers indexing. std::deque achieves this with the layout in Figure 2.1 (bottom): a small array of pointers, the map, pointing to fixed-size chunks. libstdc++ uses 512-byte chunks (128 ints); pushing at either end fills the free part of the first or last chunk and allocates a new chunk when it runs out, and only the map, never the elements, is reallocated when it fills. Indexing costs two steps: find the chunk with a division, then the slot within it. Because elements never move, references to elements stay valid on push and pop at the ends (iterators do not, a subtle rule worth knowing).

Deque is the default container under std::queue and the natural structure for sliding-window maxima (Section 7.3) and 0-1 BFS. Its weakness is constant factors: indexing is slower than a vector's, iteration crosses chunk boundaries, and MSVC's implementation uses chunks of only 16 bytes, which makes it behave much like a list of tiny arrays. For a FIFO with a known maximum size, a ring buffer is faster and allocation-free.

2.5Ring buffers: a fixed array that behaves like an endless queue

A ring buffer (circular buffer) is a fixed-size array with two counters: head, the next element to read, and tail, the next slot to write. Pushing writes at tail and advances it; popping reads at head and advances it; when a counter passes the end of the array it wraps to slot 0. Nothing is ever allocated or moved after construction, every operation is O(1), and the memory footprint is exactly known. That combination is why ring buffers are everywhere that latency and memory must be predictable: the network card's receive and transmit descriptor rings, the kernel's io_uring submission and completion queues, audio and video buffers, log buffers that keep the last N events, and message queues between threads.

The cleanest implementation, shown in Figure 2.2, lets both counters increase forever and maps them to a slot with a mask. With a capacity N that is a power of two, slot = counter & (N − 1) replaces the expensive modulo with one AND, tail − head is the number of elements even after the counters wrap around the integer range (unsigned subtraction is modulo 2⁶⁴), and the buffer is full when that difference equals N. The alternative, wrapping the counters themselves at N, makes "full" and "empty" look identical (head == tail in both cases) and forces you to waste one slot or keep a separate count.

template <class T, std::size_t N>
class RingBuffer {
    static_assert((N & (N - 1)) == 0, "N must be a power of two");
    std::array<T, N> buf_{};
    std::uint64_t head_ = 0, tail_ = 0;      // free-running; slot = counter & (N-1)
public:
    bool push(const T& v) {
        if (tail_ - head_ == N) return false;  // full: caller decides (drop, wait, overwrite)
        buf_[tail_++ & (N - 1)] = v;
        return true;
    }
    std::optional<T> pop() {
        if (tail_ == head_) return std::nullopt;   // empty
        return buf_[head_++ & (N - 1)];
    }
    std::size_t size() const { return tail_ - head_; }
};

All operations are O(1) and allocation-free. This version is for one thread. The single-producer, single-consumer variant that two threads can share without a lock, with atomic counters on separate cache lines, is built in Concurrency 5.2.

In automotive and embedded

Safety-related embedded code usually forbids heap allocation after start-up, so ring buffers and fixed-capacity containers replace std::vector and std::queue. A CAN receive queue, a sensor sample history and a diagnostic event log are all ring buffers with a documented overflow policy.

3Hash tables: lookup by key in constant time

A hash table turns a key into an array index, so finding a value by key costs the same whether the table holds ten entries or ten million. It is the most used structure in backend code after the array, and its average-case speed rests on two assumptions that are worth understanding: a hash function that scatters keys well, and a table that is never allowed to get too full.

3.1Why hashing: from searching to computing the address

The shop's web servers receive a session cookie with every request and must find that session's data: who is logged in, what is in the basket. With a million active sessions, scanning a list costs a million comparisons per request; a sorted array or balanced tree brings that to about 20 comparisons. A hash table removes the search entirely. It computes a number from the key, the hash, reduces that number to an index into an array of buckets, and looks only there. If every key landed in its own bucket, every lookup would be one array access.

Keys do not land in their own buckets, of course: there are far more possible keys than buckets, so different keys sometimes map to the same index. That is a collision, and every hash table design is mostly a decision about how to handle collisions. As long as the hash spreads keys evenly and the table keeps a bounded number of entries per bucket, the expected work per operation stays constant: average O(1) for insert, lookup and erase. The worst case, every key in one bucket, is O(n), and Section 3.5 shows that this is not merely theoretical.

3.2Hash functions: deterministic, fast and well mixed

A hash function for a table must be deterministic (equal keys give equal hashes, or lookups fail), fast (it runs on every operation) and well mixed: changing any bit of the key should change about half the bits of the hash, so that structured keys (sequential ids, strings with a common prefix, prices ending in 0) still spread over all buckets. It does not need to be cryptographic: a table hash is not trying to resist someone inverting it, only to scatter keys. Typical choices are multiply-and-shift mixers for integers, and FNV-1a, MurmurHash, xxHash, wyhash or CityHash for byte strings.

Turning the hash into a bucket index is the second half. Taking the hash modulo the bucket count is the simplest method; libstdc++ uses a prime number of buckets so that a weak hash still spreads. Fast tables use a power-of-two bucket count and take the low bits with a mask (or the high bits after a multiplication), which is cheaper than a division but exposes any weakness in the low bits of the hash.

That interaction matters in C++, because std::hash for integers in libstdc++ and libc++ is the identity: std::hash<int>{}(1260) == 1260. Combined with prime bucket counts this is usually fine. Combined with a power-of-two mask in a hand-written or third-party table it is a disaster for keys that share low bits, such as ids that are all multiples of 16 or pointers aligned to 16 bytes. Figure 3.2 lets you try exactly that case.

Pitfall

A custom key type needs both a hash and an equality that agree: if a == b then hash(a) == hash(b). Hashing a struct by combining member hashes with plain XOR is weak ({x, y} and {y, x} collide, and equal members cancel to 0); use a proper combine (multiply, rotate, add) or hash the bytes of a tightly packed representation.

3.3Collisions: chaining versus open addressing

There are two families of collision handling, and they lead to different memory layouts (Figure 3.1). Separate chaining stores in each bucket a pointer to a linked list of the entries that hashed there. Inserting allocates a node and links it in; looking up hashes the key, goes to the bucket and walks its chain comparing keys. std::unordered_map is required by the standard to work this way in practice, because it guarantees that references to elements stay valid when the table grows, and only separately allocated nodes can give that guarantee. Open addressing stores the entries themselves in one flat array. If the home slot of a key is taken, the insert probes other slots in a fixed sequence (the next one in linear probing, quadratic jumps, or a second hash) until it finds an empty one; a lookup follows the same sequence until it finds the key or an empty slot.

The cost of a lookup depends on the load factor α, the number of entries divided by the number of slots. For chaining, a successful lookup visits on average 1 + α/2 nodes and an unsuccessful one α nodes, so chaining degrades gently and still works above α = 1. For linear probing the textbook result (Knuth) is ½(1 + 1/(1 − α)) probes for a hit and ½(1 + 1/(1 − α)²) for a miss, which stays small up to about 0.7 and then explodes, because occupied slots merge into long runs (primary clustering) that every key hashing into the run must walk. Probe counts alone make chaining look better, and that is the trap: a chaining probe is a pointer dereference to a node somewhere on the heap, probably a cache miss, while a linear-probing probe is the next slot in the same cache line. That is why the fastest modern tables, Google's Swiss table (absl::flat_hash_map), Facebook's F14, boost::unordered_flat_map and Rust's standard HashMap, all use open addressing at a maximum load of about 0.875, and add a trick: a separate array of one-byte tags holding 7 bits of each slot's hash, which SIMD instructions compare 16 at a time, so most probes never touch a non-matching key at all. In the experiment of Section 1.6 the node-based std::unordered_map took 54 ns per lookup in a million keys, already far better than std::map; flat tables typically halve that again.

Deletion is the awkward part of open addressing. Simply emptying a slot would break the probe sequence of every key that was pushed past it, so tables either mark deleted slots with a tombstone that lookups skip and inserts may reuse, or (in linear probing) shift later entries of the cluster back. Tombstones count towards the load when deciding to rehash, otherwise a table with many deletes fills with dead slots and every miss walks the whole array.

3.4Load factor and rehashing

To keep α bounded, a table grows when it passes a maximum load factor: it allocates a bucket array about twice as large and reinserts every entry, because each key's index depends on the bucket count. That rehash is O(n), but like vector growth (Section 1.4) it happens at geometrically spaced sizes, so inserts stay amortised O(1). std::unordered_map has a default max_load_factor of 1.0; after inserting 2²⁰ keys in the experiment it had 1 056 323 buckets (a prime) and a load of 0.99. Open-addressing tables use 0.5 to 0.875.

Rehashing has the same consequences as reallocation: a latency spike on the insert that triggers it, and, in open-addressing tables, invalidation of every iterator and pointer into the table. If you know the final size, call reserve(n) before inserting; it sizes the bucket array once, which in the experiment above avoided about 20 rehashes. Rehashing also does not shrink by itself: a table that once held ten million entries keeps its bucket array after they are erased, and iterating it walks all the empty buckets.

3.5The worst case is an attack surface

The O(1) average assumes keys behave as if random with respect to the hash. When an attacker chooses the keys, they can make them collide on purpose. In 2011 researchers showed that the web frameworks of PHP, Java, Python, Ruby and ASP.NET all parsed POST parameters into hash tables with predictable string hashes; a single request of a few megabytes of crafted colliding names turned each insert into a walk of a long chain and could keep a CPU core busy for a long time (hash flooding, CVE-2011-4885 and siblings). The fixes are a keyed hash with a random per-process seed, such as SipHash (now the default for strings in Python, Ruby and Rust), limits on the number of parameters, and, in Java 8's HashMap, converting a chain longer than eight entries into a balanced tree so the worst case becomes O(log n).

The same thinking applies to latency-critical code without an attacker. If a lookup must finish in bounded time (a packet classifier, a real-time control loop), the average case is not a specification. The options are a perfect hash computed offline for a fixed key set, a sorted array with binary search (O(log n) worst case), or a table with a bounded probe length such as cuckoo hashing, where every key lives in one of two possible slots and a lookup checks exactly two places.

Lookups are O(1) on average because the load factor is kept bounded by rehashing, which is amortised like vector growth. std::unordered_map uses chaining because the standard promises stable references; fast tables use open addressing for cache locality. The worst case is O(n) when keys collide, which is why servers use seeded hashes against hash flooding."

In practice

Choose a hash map when you need lookup by exact key and do not need order. Choose an ordered map or sorted vector when you need ranges, the smallest or largest key, or iteration in key order, or when you need a worst-case bound. In C++23, std::flat_map wraps two sorted vectors and is often the best ordered choice for read-mostly data.

4Trees and friends: heaps, search trees, tries and union-find

Trees appear whenever data has a hierarchy or an order that must be maintained under change. The four structures in this chapter each keep a different invariant cheaply: a heap keeps the minimum on top, a search tree keeps everything sorted, a trie shares prefixes, and union-find keeps track of which elements belong together.

4.1Binary heaps: the minimum on top, stored in an array

The shop's job scheduler holds thousands of delayed tasks (send the reminder e-mail in 24 hours, cancel the unpaid order in 30 minutes) and repeatedly needs the one that is due first. A sorted list would make "take the first" cheap but inserting expensive; an unsorted list the opposite. A priority queue needs both to be cheap, and the standard way to build one is a binary heap: a complete binary tree in which every parent is smaller than (or equal to) its children. The minimum is therefore always at the root, but the rest is only partially ordered, which is exactly what makes it cheap to maintain.

The clever part is the storage. A complete tree, filled level by level from the left, can be laid out in an array with no pointers at all: the root at index 0, the children of index i at 2i+1 and 2i+2, the parent at (i−1)/2. Push appends the new element at the end of the array (the next free leaf) and sifts it up: while it is smaller than its parent, swap the two. Pop takes the root, moves the last element into the root's place and sifts it down: while it is larger than its smaller child, swap with that child. Both walk one root-to-leaf path, so both are O(log n); reading the minimum is O(1).

In C++ the heap is std::priority_queue, a max-heap by default; for a min-heap pass std::greater<>. The algorithms std::make_heap, push_heap and pop_heap work on any random-access range. Building a heap from n unordered elements by sifting down from the last parent to the root costs only O(n), not O(n log n), because most nodes are near the bottom and sift down only a level or two.

The most common use in practice is top-K: to keep the K largest of a stream of n items, keep a min-heap of size K; for each new item larger than the heap's minimum, pop the minimum and push the item. That is O(n log K) time and O(K) memory, and it works on a stream that never fits in memory. Timer wheels and event schedulers, Dijkstra's algorithm (Section 5.4), merging K sorted files and the running median (two heaps, one for each half) all build on the same structure.

Interesting detail

std::priority_queue has no "decrease key" operation, which Dijkstra's algorithm nominally needs. The usual workaround is to push a duplicate entry with the new, smaller distance and skip stale entries when they are popped ("lazy deletion"). It costs a little memory and keeps the code simple.

4.2Search trees: sorted order under insertion

A binary search tree (BST) keeps, at every node, smaller keys in the left subtree and larger ones in the right. Searching starts at the root and goes left or right at each node, so it costs one comparison per level. Unlike a hash table, a BST knows the order of its keys: it can return the smallest key, the next key after a given one, or every key in a range, which is what "orders between 10:00 and 11:00" or "the next price above 50" needs.

The catch is the shape. A BST built by inserting keys in sorted order puts each new key to the right of the last and degenerates into a linked list of height n (Figure 4.2, left), and sorted input is common in practice (timestamps, auto-increment ids). Balanced search trees fix this by restructuring locally after each insert or erase with rotations, small pointer rewrites that change the shape without breaking the order. An AVL tree keeps the heights of every node's two subtrees within one of each other: very flat, height at most about 1.44 log₂ n, but more rotations on update. A red-black tree colours each node red or black and requires that no red node has a red child and that every root-to-leaf path has the same number of black nodes; that guarantees height at most 2 log₂(n+1) with at most two rotations per insert. std::map, std::set and their multi-variants are red-black trees in all three major standard libraries, and the Linux kernel uses red-black trees for its scheduler's run queue and for virtual memory areas.

The node layout in the middle of Figure 4.2 explains why std::map was 24 times slower than a hash table in Section 1.6: a million keys means 20 levels, and every level is a pointer to a node allocated somewhere else, so a lookup is up to 20 dependent cache misses. The B-tree on the right is the cache-aware answer. Each node holds many sorted keys and has many children (a fan-out of hundreds), sized to a disk page or a few cache lines; a lookup does a short binary search inside each node and descends only a few levels. A billion rows in a database index with a fan-out of 500 are four levels deep, and since the upper levels stay in memory, a lookup costs about one disk read. PostgreSQL, MySQL's InnoDB, SQLite and most file systems (ext4's directory index, Btrfs, APFS, NTFS) are built on B-trees or their B+ variant, where all values live in the leaves and the leaves are linked for fast range scans. In memory, absl::btree_map applies the same idea and is usually faster than std::map.

Talk track

"A balanced search tree gives O(log n) insert, erase and lookup with the keys in order, so it supports range queries and successor lookups that a hash table cannot. std::map is a red-black tree; it is cache-unfriendly because each level is a separate node, which is why databases use B-trees with hundreds of keys per node."

4.3Tries: keys that share prefixes share nodes

The shop's search box suggests products while the customer types. After "ma" it should offer "map", "mat", "math" and "max" instantly. A hash table cannot help, because it only answers exact-key questions, and a sorted array can (binary search for the first key ≥ "ma") but not as naturally. A trie (prefix tree, from retrieval) is built for this. Each edge is labelled with one character, each node represents the prefix spelled by the path from the root, and nodes where a complete word ends are marked (Figure 4.3). Looking up or inserting a word of length L takes O(L) steps no matter how many words are stored, and all words with a given prefix sit in one subtree.

The design decision is how a node stores its children. A fixed array of 26 or 256 pointers makes each step one index operation but costs 208 or 2 048 bytes per node, mostly null pointers. A sorted small vector or hash map of (character, child) pairs is compact but slower per step. A radix tree (Patricia trie) compresses chains of single-child nodes into one edge labelled with a whole string, which is how real implementations keep memory down. Tries and radix trees are behind IP routing tables (longest-prefix match on address bits), the Linux kernel's page cache index (the XArray), spell checkers, and the routers of web frameworks that match URL paths. For autocomplete at scale, the subtree is usually annotated with the most popular completions so that the suggestion does not have to walk thousands of descendants.

4.4Union-find: which things belong together

The shop's fraud team wants to group customer accounts that share a payment card, a phone number or a delivery address, directly or through a chain of other accounts. Each shared attribute merges two groups, and the question is always "are these two accounts in the same group?". Union-find (disjoint-set union, DSU) answers it in nearly constant time. Each element points to a parent; following parents leads to the root, which represents the set. find(x) follows the chain to the root; union(a, b) finds both roots and makes one the parent of the other (Figure 4.4).

Two small optimisations make it fast. Union by rank (or by size) always attaches the shorter tree under the taller one, which keeps the height at O(log n). Path compression makes every node visited by a find point directly at the root. Together they give an amortised cost per operation of O(α(n)), where α is the inverse Ackermann function, which is at most 4 for any input that fits in the universe; for engineering purposes it is constant.

struct DSU {
    std::vector<int> parent, rank_;
    explicit DSU(int n) : parent(n), rank_(n, 0) { std::iota(parent.begin(), parent.end(), 0); }
    int find(int x) {                              // iterative, with path halving
        while (parent[x] != x) { parent[x] = parent[parent[x]]; x = parent[x]; }
        return x;
    }
    bool unite(int a, int b) {                     // false if already in the same set
        a = find(a); b = find(b);
        if (a == b) return false;
        if (rank_[a] < rank_[b]) std::swap(a, b);
        parent[b] = a;
        if (rank_[a] == rank_[b]) ++rank_[a];
        return true;
    }
};

Union-find answers connectivity under additions only; it cannot split a set again. It is the engine of Kruskal's minimum spanning tree (Section 5.5), of grouping duplicate records, of percolation and image segmentation (connected regions of pixels), and of the classic "number of islands" and "accounts merge" problems, where it is an alternative to BFS that also works when the edges arrive one by one.

5Graphs: relationships, traversal and shortest paths

A graph is a set of nodes and the edges between them. Road networks, service dependencies, social connections, build targets, web links and state machines are all graphs, and a surprising number of problems are graph problems in disguise: a grid is a graph, a word ladder is a graph, a set of course prerequisites is a graph. A small toolbox of traversals covers most of them.

5.1Representations: matrix, lists or flat arrays

A graph has V nodes and E edges. Edges may be directed (a service calls another) or undirected (two accounts share a card), and weighted (a road's travel time) or not. How you store it determines the cost of every algorithm that runs on it, and the choice mostly comes down to density.

An adjacency matrix is a V × V table with a 1 (or the weight) where an edge exists. It is the right choice for small, dense graphs and for algorithms that need constant-time edge queries, such as Floyd–Warshall's all-pairs shortest paths. It is hopeless for large sparse graphs: a road network of a million junctions has a few million edges but would need a trillion matrix cells. Adjacency lists, in C++ usually std::vector<std::vector<int>> or a vector of (neighbour, weight) pairs, store only the edges that exist and give each node's neighbours as a contiguous run, which is what BFS, DFS and Dijkstra iterate over. CSR packs all the lists into two arrays, removing the per-list allocations; it is the standard format of graph libraries, sparse matrix code and GPU graph processing, and the fastest to traverse because it is fully sequential. For problems on grids, you usually do not build a graph at all: the neighbours of cell (r, c) are computed on the fly as the four (or eight) adjacent cells that are inside the grid and not walls.

5.2BFS and DFS: the two ways to explore

Every graph algorithm in this chapter is a traversal with a different rule for which node to visit next. Breadth-first search (BFS) visits nodes in order of their distance from the start, measured in edges: first the start, then all its neighbours, then all their unvisited neighbours, and so on. It uses a FIFO queue, and because a node is first reached by a shortest path, BFS finds shortest paths in unweighted graphs. Depth-first search (DFS) goes as deep as possible along one branch before backing up, using a stack (often the call stack, via recursion). It does not find shortest paths, but the order in which it enters and leaves nodes reveals structure: cycles, connected components, the order of dependencies (Section 5.3), and bridges and articulation points in a network.

// BFS on an adjacency list: distances in edges from src, -1 if unreachable. O(V + E).
std::vector<int> bfs(const std::vector<std::vector<int>>& adj, int src) {
    std::vector<int> dist(adj.size(), -1);
    std::queue<int> q;
    dist[src] = 0; q.push(src);
    while (!q.empty()) {
        int v = q.front(); q.pop();
        for (int u : adj[v])
            if (dist[u] == -1) { dist[u] = dist[v] + 1; q.push(u); }   // mark when discovered
    }
    return dist;
}

Both run in O(V + E): each node is enqueued once and each edge examined once (twice for undirected graphs). The detail that most often goes wrong is when to mark a node as visited. BFS must mark a node when it is discovered (pushed), not when it is popped; otherwise a node with many neighbours on the current level is pushed many times and the queue can grow far beyond V. A recursive DFS is the shortest code, but its depth is the length of the longest path it follows, so on a long chain or a large grid it overflows the stack (Section 1.5); production code uses an explicit stack instead.

The interactive Figure 5.2 in Section 5.4 lets you compare the traversals on the same map: BFS spreads in diamond-shaped rings, DFS dives along one direction and finds a long, winding path.

In practice

Crawlers, garbage collectors (mark phase), "people you may know" at distance two, finding everything affected by a change in a dependency graph, and flood fill in image editors are all BFS or DFS. Multi-source BFS, which starts with several nodes in the queue at distance 0, answers "distance from each cell to the nearest exit or server" in one pass.

5.3Topological sort: an order that respects dependencies

The shop's monorepo has a build graph: api needs net and db, net needs log, and so on. A build tool must compile every target after everything it depends on. Such an order exists exactly when the dependency graph is a directed acyclic graph (DAG), and finding it is a topological sort. The same problem appears in package managers, spreadsheet recalculation, task schedulers, database migration ordering and course prerequisites. How build systems use the graph beyond ordering (content hashes, caching, parallelism) is in Build systems 5.1.

Kahn's algorithm is the intuitive version. Count each node's incoming edges (its in-degree). Put every node with in-degree 0, which needs nothing, in a queue. Repeatedly pop a node, append it to the order, and decrement the in-degree of each node that depends on it; when one reaches 0, push it. If the order ends shorter than V, the remaining nodes are part of a cycle and no valid order exists, which is how build tools report circular dependencies. The DFS alternative appends each node to a list when DFS finishes it (after all its descendants) and reverses the list at the end. Both run in O(V + E).

// Kahn's algorithm. Returns an empty vector if the graph has a cycle.
std::vector<int> topo_sort(const std::vector<std::vector<int>>& adj) {   // edge v -> u: u needs v
    std::vector<int> indeg(adj.size(), 0), order;
    for (const auto& out : adj) for (int u : out) ++indeg[u];
    std::queue<int> q;
    for (int v = 0; v < (int)adj.size(); ++v) if (indeg[v] == 0) q.push(v);
    while (!q.empty()) {
        int v = q.front(); q.pop(); order.push_back(v);
        for (int u : adj[v]) if (--indeg[u] == 0) q.push(u);
    }
    if (order.size() != adj.size()) return {};    // leftover nodes sit on a cycle
    return order;
}

5.4Shortest paths: Dijkstra and A*

The delivery service needs the cheapest route through a road network where edges have travel times. BFS no longer works, because a path with fewer edges can take longer. Dijkstra's algorithm generalises BFS to non-negative weights by replacing the FIFO queue with a priority queue keyed by the best known distance. It repeatedly takes the unvisited node with the smallest tentative distance, declares that distance final, and relaxes each outgoing edge: if going through this node gives a neighbour a shorter distance than it had, update it and push the neighbour with its new distance. The node it takes is always final because, with non-negative weights, no later path can come back cheaper. With a binary heap the cost is O((V + E) log V).

// Dijkstra with a min-heap and lazy deletion of stale entries.
using Edge = std::pair<int, int>;                       // (neighbour, weight >= 0)
std::vector<long long> dijkstra(const std::vector<std::vector<Edge>>& adj, int src) {
    const long long INF = std::numeric_limits<long long>::max();
    std::vector<long long> dist(adj.size(), INF);
    std::priority_queue<std::pair<long long, int>, std::vector<std::pair<long long, int>>,
                        std::greater<>> pq;              // (distance, node), smallest first
    dist[src] = 0; pq.push({0, src});
    while (!pq.empty()) {
        auto [d, v] = pq.top(); pq.pop();
        if (d != dist[v]) continue;                    // stale entry: a shorter one was processed
        for (auto [u, w] : adj[v])
            if (dist[v] + w < dist[u]) { dist[u] = dist[v] + w; pq.push({dist[u], u}); }
    }
    return dist;
}

Dijkstra explores in rings of equal cost around the start, in every direction, even away from the goal. When there is a single goal and a way to estimate the remaining distance, A* focuses the search. It orders the priority queue by f = g + h, where g is the known cost from the start and h is a heuristic estimate of the cost to the goal, such as the straight-line distance on a map or the Manhattan distance on a grid. If h never overestimates (it is admissible), A* still returns an optimal path, and the better h approximates the true remaining cost, the fewer nodes it expands. With h = 0 it is exactly Dijkstra. The numbers in the caption come from the figure's own model (experiments/check_interactive.js): BFS expanded 355 cells, DFS 152, Dijkstra 381 and A* 231 of 407 open cells. Two limits are worth knowing. Dijkstra (and therefore A*) is wrong with negative edge weights, because a node declared final could later be reached more cheaply; Bellman–Ford handles negative weights in O(V·E) and detects negative cycles, which is how currency-arbitrage checks and distance-vector routing protocols work. And on graphs with only weights 0 and 1, a deque replaces the heap (0-1 BFS: push 0-edges to the front, 1-edges to the back) for O(V + E).

Interesting detail

Real route planners do not run plain Dijkstra on a continental road graph of tens of millions of nodes per query. They preprocess the graph once (contraction hierarchies, which add shortcut edges past unimportant junctions, or hub labels) and then answer queries in microseconds to milliseconds by searching only a few hundred nodes. Robot and vehicle motion planning uses A* on lattices and sampling planners such as RRT; that application belongs to the planning chapter of this book series.

Talk track

"BFS gives shortest paths when every edge costs the same. With non-negative weights I'd use Dijkstra with a binary heap, O((V+E) log V). If there's one target and an admissible heuristic, A* expands fewer nodes and is still optimal. Negative weights need Bellman–Ford."

5.5Minimum spanning trees: connect everything as cheaply as possible

Connecting a set of warehouses with fibre links, or a set of points with the least total cable, asks for a minimum spanning tree (MST): a subset of edges that connects all V nodes with no cycles (so exactly V − 1 edges) and minimum total weight. It is also a building block of clustering (remove the heaviest MST edges to split points into groups) and of approximations for harder problems such as the travelling salesman.

Two greedy algorithms solve it, and both rest on the same cut property: for any division of the nodes into two groups, the cheapest edge crossing between them belongs to some MST. Kruskal's algorithm sorts all edges by weight and takes each one unless it would close a cycle, which union-find detects in near-constant time (Section 4.4): an edge whose ends already have the same root is skipped. Cost: O(E log E) for the sort. Prim's algorithm grows one tree from a start node, always adding the cheapest edge leaving the tree, using a priority queue like Dijkstra; it suits dense graphs.

Pitfall

An MST minimises the total weight of the network, not the distance between any two nodes. The path between two warehouses in the MST can be much longer than their shortest path. Confusing the two (Prim versus Dijkstra) is a common slip: the code is almost identical, but Prim keys the queue by the weight of the single connecting edge, Dijkstra by the total distance from the source.

6Sorting and searching

Sorting is the most common preprocessing step in computing: once data is sorted, duplicates are adjacent, ranges are contiguous, the median is in the middle and any value can be found by binary search. The standard sorts are among the most carefully engineered code in any library, and knowing how they work explains their guarantees.

6.1Why n log n is the floor for comparison sorts

A comparison sort learns about the input only by comparing pairs of elements. Each comparison has two outcomes, so after k comparisons it can distinguish at most 2k different inputs. There are n! possible orderings of n distinct elements, and the algorithm must distinguish all of them to put each one right, so it needs at least log₂(n!) comparisons, which is about n log₂ n − 1.44n. That is the Ω(n log n) lower bound: merge sort and heapsort meet it in the worst case, quicksort on average.

The bound only applies to comparisons. If the keys are small integers or fixed-width strings, counting sort (count how many of each value, then write them out) runs in O(n + k) for k possible values, and radix sort sorts by one digit or byte at a time with a stable counting pass per digit, O(d · n) for d-digit keys. Radix sort is how GPUs sort millions of keys and how some databases sort integer columns.

6.2Quicksort, and how std::sort avoids its worst case

Quicksort picks a pivot, partitions the array so that smaller elements come before the pivot and larger ones after it, and recursively sorts the two parts. The pivot lands in its final position after the partition, and no merging is needed. Partitioning is a single sequential pass with swaps (Figure 6.1 shows the Lomuto scheme; the Hoare scheme, which scans from both ends, does fewer swaps), so quicksort is in-place, cache-friendly and has a small constant factor. That is why it is usually the fastest general-purpose comparison sort in practice.

The weakness is the pivot. If it is always the smallest or largest element, one side is empty, the recursion is n levels deep and the cost is O(n²). With the first element as pivot this happens on already-sorted input, the most common input of all: the chapter's experiment counted 24 247 comparisons for 2 000 shuffled numbers and 1 999 000 for the same numbers sorted, 82 times more. Production sorts defend themselves in three ways. They choose the pivot as the median of three (or nine) samples; they switch to insertion sort for small ranges (16 elements in libstdc++), where its simplicity wins; and std::sort uses introsort, which counts recursion depth and switches to heapsort if it exceeds about 2 log₂ n, guaranteeing O(n log n) in the worst case. Newer implementations such as pattern-defeating quicksort (pdqsort, in Boost and, until 2024, Rust's unstable sort) also detect already-sorted runs. In the benchmark, std::sort of 2²⁰ random ints took 74 ms and of the same ints already sorted 9 ms.

Pitfall

A comparator for std::sort must be a strict weak ordering: comp(a, a) must be false and the relation must be transitive. Using <=, or a comparator that is inconsistent for NaN floats, is undefined behaviour and can make libstdc++'s unguarded partition run off the end of the array and crash.

6.3Merge sort: guaranteed n log n and stability

Merge sort splits the array in halves, sorts each half recursively, and merges the two sorted halves by repeatedly taking the smaller front element (Figure 6.2). Every level of the recursion merges all n elements, and there are log₂ n levels, so the cost is O(n log n) in every case, not just on average. The merge needs an O(n) buffer, which is the price.

Merge sort's other property is stability: elements that compare equal keep their original relative order, because the merge takes from the left half on ties. Stability matters when you sort by one key after another. To list the shop's orders by customer and, within each customer, by date, sort by date first and then stable-sort by customer. std::stable_sort is a merge sort (falling back to an in-place O(n log² n) variant if it cannot allocate the buffer), and it took 93 ms against std::sort's 74 ms in the benchmark. Python's and Java's object sorts use Timsort, a merge sort that finds already-sorted runs in the input and merges them, which makes it very fast on the partially sorted data that real programs produce. Merge sort is also the basis of external sorting: sort chunks that fit in memory, write them to disk, then merge the sorted files with a heap of their front elements.

6.4Heapsort, insertion sort and the measured picture

Heapsort builds a max-heap in O(n) and repeatedly pops the maximum to the end of the array: O(n log n) worst case, in place, but not stable and with a poor cache pattern, because sifting jumps between distant indices. That is why it serves as introsort's safety net rather than as the main algorithm. Insertion sort, which inserts each element into the sorted prefix by shifting larger ones right, is O(n²) in general but O(n) on nearly sorted input and the fastest method for a few dozen elements, so every hybrid sort uses it at the leaves.

6.5Binary search, done right

Binary search finds a value in a sorted array by comparing with the middle element and discarding the half that cannot contain it, so it needs ⌈log₂(n+1)⌉ probes: 30 for a billion elements. The idea is trivial and the code is famously easy to get wrong; a 1988 study found that most textbook versions had bugs, and the overflow in (lo + hi) / 2 sat in the JDK's own binary search for nine years until 2006. The reliable way to write it is to state an invariant and keep it. std::lower_bound returns the first position whose element is not less than the target, using a half-open range [lo, hi) that always contains the answer:

// First index i with a[i] >= x, or a.size() if none. Invariant: answer is in [lo, hi].
std::size_t lower_bound_idx(const std::vector<int>& a, int x) {
    std::size_t lo = 0, hi = a.size();
    while (lo < hi) {
        std::size_t mid = lo + (hi - lo) / 2;   // no overflow
        if (a[mid] < x) lo = mid + 1;           // answer is right of mid
        else            hi = mid;               // mid itself may be the answer
    }
    return lo;
}

The general form of the idea is binary search on the answer: whenever a yes/no question is monotonic in a parameter (if capacity 50 is enough to ship all parcels in five days, so is 51), you can binary-search the smallest parameter for which the answer is yes, testing each candidate with a linear check. "Minimum capacity to ship within D days", "smallest maximum page load when splitting a book among k readers" and "earliest day the condition holds" are all this pattern, and git bisect is the same idea applied to commits.

In practice

Use std::lower_bound, upper_bound and equal_range rather than hand-written loops, and std::partition_point for binary search on a predicate. For small arrays, remember Section 1.6: below a few hundred elements a linear scan is often faster.

6.6Selection: you rarely need the whole array sorted

Many questions that look like sorting only need part of the order: the median response time, the 99th percentile latency, the ten best-selling products. Sorting answers them in O(n log n), but quickselect does better. It partitions like quicksort but recurses only into the side that contains the wanted position, so the expected work is n + n/2 + n/4 + … = O(n). std::nth_element implements it (with an introselect fallback against bad pivots) and found the median of 2²⁰ ints in 8.4 ms, nine times faster than sorting. For the top k in order, std::partial_sort keeps a heap of k elements and took 0.5 ms for the top 100. On a stream that does not fit in memory, the heap of Section 4.1 does the same job.

7.2Two pointers: let the order do the work

Two pointers move through the data in a coordinated way, each only forwards (or towards each other), so together they make O(n) steps where a nested loop would make O(n²). The classic case is finding a pair with a given sum in a sorted array. Start one pointer at each end. If the sum is too small, the only way to increase it is to advance the left pointer; if too large, retreat the right one. Each step discards a whole row of pairs that cannot work, which is why one pass suffices. The same idea removes duplicates from a sorted array in place (a slow write pointer and a fast read pointer), checks palindromes, merges two sorted arrays, and solves "three numbers that sum to zero" in O(n²) instead of O(n³) by fixing one number and running two pointers on the rest.

// Pair with sum == target in a sorted array. O(n) time, O(1) space.
std::optional<std::pair<int, int>> pair_sum(const std::vector<int>& a, int target) {
    int l = 0, r = (int)a.size() - 1;
    while (l < r) {
        long long s = (long long)a[l] + a[r];
        if (s == target) return std::pair{l, r};
        if (s < target) ++l; else --r;      // each move rules out a[l] or a[r] for good
    }
    return std::nullopt;
}

7.3Sliding window: a range that grows and shrinks

A sliding window is two pointers that bound a contiguous range: the right edge advances to include new elements, and the left edge advances when the range violates the constraint. The state of the window (a sum, a count per character, a set) is updated incrementally as elements enter and leave, never recomputed. Because each element enters once and leaves once, the whole scan is O(n). The shop's rate limiter is a sliding window over timestamps: "at most 100 requests in the last 60 seconds" keeps a queue of recent request times, pushes the new one, and pops from the front while the oldest is more than 60 seconds old.

Figure 7.1 shows the classic textbook version, the longest substring without repeated characters. The window state is the last index at which each character was seen; when the right edge meets a character that is already inside the window, the left edge jumps just past its previous occurrence.

int longest_unique(const std::string& s) {
    std::array<int, 256> last; last.fill(-1);   // last index of each byte value
    int best = 0, l = 0;
    for (int r = 0; r < (int)s.size(); ++r) {
        unsigned char c = s[r];
        if (last[c] >= l) l = last[c] + 1;      // repeat inside the window: shrink past it
        last[c] = r;
        best = std::max(best, r - l + 1);
    }
    return best;
}

A related tool is the prefix sum: store P[i] = the sum of the first i elements, and the sum of any range [i, j) is P[j] − P[i] in O(1). Combined with a hash map from prefix sum to count, it counts the subarrays summing to k in O(n) even with negative numbers, where a sliding window fails because the window sum is no longer monotonic.

7.4Recursion and backtracking: explore choices, undo, try the next

Some problems ask for every solution, or for a solution that can only be found by trying: all subsets of a set, all permutations, every way to place eight queens, a Sudoku. Backtracking builds a candidate one choice at a time, recurses, and then undoes the choice before trying the next one; if a partial candidate can already be seen to fail, it prunes that branch without exploring it. The structure is always the same: a function that takes the current partial solution, checks whether it is complete, and otherwise loops over the possible next choices with "choose, recurse, un-choose".

// All subsets of nums (the power set). 2^n subsets, O(n · 2^n) time.
void subsets(const std::vector<int>& nums, std::size_t i, std::vector<int>& cur,
             std::vector<std::vector<int>>& out) {
    if (i == nums.size()) { out.push_back(cur); return; }
    subsets(nums, i + 1, cur, out);              // choice 1: leave nums[i] out
    cur.push_back(nums[i]);                      // choice 2: take it ...
    subsets(nums, i + 1, cur, out);
    cur.pop_back();                              // ... and undo before returning
}

The cost is exponential by nature: 2n subsets, n! permutations. That is why the constraint in such problems is small (Section 1.3), and why pruning matters: a good bound can cut most of the tree. Backtracking is how SAT solvers, regular-expression engines with backreferences and constraint solvers work at their core, with much cleverer pruning.

7.5Divide and conquer: split, solve, combine

Divide and conquer splits a problem into independent subproblems of the same kind, solves them recursively, and combines the results. Merge sort (split in halves, merge), quicksort (partition, sort the parts), binary search (one half is discarded), fast multiplication of large numbers (Karatsuba) and the fast Fourier transform all have this shape. The cost follows from a recurrence: if a problem of size n makes a subproblems of size n/b and spends f(n) to split and combine, then T(n) = aT(n/b) + f(n). The master theorem solves the common cases: merge sort (a = 2, b = 2, f = n) gives O(n log n); binary search (a = 1, b = 2, f = 1) gives O(log n). The intuition is to look at the recursion tree: if every level does the same total work, multiply by the number of levels.

Because the subproblems are independent, divide and conquer parallelises naturally: the two halves of a merge sort can be sorted on different cores, which is how parallel sorts and map-reduce style computations split work (the threading side is in the concurrency chapter).

7.6Greedy: when the locally best choice is globally safe

A greedy algorithm makes the choice that looks best right now and never reconsiders it. When it works it is simple and fast, usually a sort followed by one pass. The shop's meeting-room booking is the classic example: to fit the most meetings into one room, sort them by end time and repeatedly take the next meeting that starts after the last one taken. Choosing the meeting that ends first leaves the most room for the rest, and an exchange argument proves it: take any optimal schedule; its first meeting can be swapped for the earliest-ending one without losing anything, and repeating the argument transforms it into the greedy schedule. Dijkstra, Kruskal, Prim and Huffman coding are all greedy algorithms with such a proof.

The danger is that greedy is easy to propose and often wrong. Making change with the fewest coins by always taking the largest coin works for euro coins but not for coins of 1, 3 and 4: for 6 it gives 4 + 1 + 1 (three coins) instead of 3 + 3. When a greedy idea comes to mind, try to break it with a small counterexample before coding it; if you cannot prove it with an exchange argument, the problem probably needs dynamic programming.

7.7Dynamic programming: remember the answers to subproblems

Dynamic programming (DP) applies when a problem can be split into subproblems whose answers are reused many times. The naive recursion for Fibonacci numbers, fib(n) = fib(n−1) + fib(n−2), computes fib(2) three times and fib(3) twice just for fib(5), and the number of calls grows like 1.618n (Figure 7.2). Storing each answer the first time it is computed makes the cost proportional to the number of distinct subproblems: O(n) for Fibonacci. Two conditions make DP work: optimal substructure (the best answer is built from best answers to subproblems) and overlapping subproblems (the same subproblems recur).

There are two ways to write it. Memoisation (top-down) keeps the natural recursion and caches results in a hash map or array; it computes only the subproblems that are actually needed. Tabulation (bottom-up) fills a table in an order where every entry's dependencies are already filled; it avoids recursion depth limits and often allows keeping only the last row or two of the table. The hard part is never the caching, it is defining the state: what exactly does dp[i][j] mean? A good definition is a sentence, such as "the minimum number of edits to turn the first i characters of a into the first j characters of b". From that sentence the recurrence usually follows by asking what the last step could have been.

// Fewest coins summing to amount (unbounded supply), or -1. O(amount · coins) time, O(amount) space.
int coin_change(const std::vector<int>& coins, int amount) {
    const int INF = amount + 1;
    std::vector<int> dp(amount + 1, INF);        // dp[x] = fewest coins that sum to x
    dp[0] = 0;
    for (int x = 1; x <= amount; ++x)
        for (int c : coins)
            if (c <= x) dp[x] = std::min(dp[x], dp[x - c] + 1);   // last coin was c
    return dp[amount] >= INF ? -1 : dp[amount];
}

For coins {1, 3, 4} and amount 6 this returns 2, where greedy returned 3. The common DP families are worth recognising by name: one-dimensional sequences (climbing stairs, house robber, longest increasing subsequence), two strings (edit distance, longest common subsequence), knapsack (choose items under a capacity), grids (paths with obstacles or costs), intervals (burst balloons, matrix-chain order) and DP over bitmasks of small sets (travelling salesman for n ≤ 20, Section 8.3). The cost is always the number of states times the work per state.

Talk track

"I'd define dp[x] as the fewest coins summing to x. The last coin is one of the denominations, so dp[x] = 1 + min over coins of dp[x − c]. That's amount × coins states and transitions, O(amount) memory. Greedy fails here, for example coins 1, 3, 4 and amount 6."

8Bit manipulation

At the bottom, every value is a pattern of bits, and a few operations on those patterns replace loops, save memory, and express hardware registers, flags and sets compactly. Embedded and systems engineers use them daily, because they are how software reasons at the level of the hardware.

8.1Why bits: flags, sets, packing and hardware

A 64-bit integer is a set of 64 yes/no values that the CPU can test, combine and count in one instruction each. That makes bits the natural representation for flags (a file's permission bits, a TCP header's SYN and ACK flags, the shop's feature toggles per customer), for small sets (bit i set means element i is in the set; union is OR, intersection is AND), for packing several small fields into one word (an RGB565 pixel, a timestamp and a sequence number in one 64-bit id), and for hardware registers, where each bit or bit field controls something physical. The operations are AND (&), OR (|), XOR (^), NOT (~) and the shifts (<<, >>). Setting bit k is x |= 1u << k, clearing it x &= ~(1u << k), toggling it x ^= 1u << k, and testing it (x >> k) & 1.

Negative integers are stored in two's complement: −x is ~x + 1. Its advantage is that addition and subtraction work the same for signed and unsigned numbers, so the hardware needs one adder. Its consequence is the set of tricks in Figure 8.1.

8.2The core tricks and why they work

Subtracting 1 from a number flips its lowest set bit to 0 and every 0 below it to 1. So x & (x − 1) clears the lowest set bit: it is 0 exactly when x is a power of two (or 0), and repeating it until x is 0 counts the set bits in as many steps as there are ones (Kernighan's method). Negation flips all bits and adds one, which leaves the lowest set bit and everything below it unchanged and flips everything above; so x & −x isolates the lowest set bit. That is the core step of a Fenwick tree (a structure for prefix sums with updates in O(log n)) and of iterating over the set bits of a mask.

XOR has its own family. It is its own inverse (a ^ b ^ b == a) and order does not matter, so XOR-ing all numbers in an array where every value appears twice except one leaves exactly the single one, in O(n) time and O(1) memory. The same property drives parity bits, RAID-5 recovery (the parity block is the XOR of the data blocks, so any one lost block is the XOR of the others) and simple checksums. C++20 added the <bit> header with portable names for what used to be compiler intrinsics: std::popcount, std::countr_zero (index of the lowest set bit), std::countl_zero, std::has_single_bit (power of two), std::bit_ceil (round up to a power of two, as the ring buffer of Section 2.5 needs) and std::rotl. Each compiles to a single instruction on current x86 and Arm cores.

8.3Bitsets, subset enumeration and the traps

A bitset stores one bit per element: std::bitset<N> for a size known at compile time, std::vector<bool> (a packed specialisation with proxy references, famously not a real container) or boost::dynamic_bitset otherwise. Set operations on bitsets process 64 elements per instruction, which makes them the tool for visited-sets in huge graphs, Bloom filters (a bit array plus k hash functions that answers "definitely not present" or "probably present" in a few bits per element), allocation bitmaps in file systems and memory allocators, and database bitmap indexes. For sets of at most about 20 elements, an integer is the set, and looping mask from 0 to 2ⁿ − 1 enumerates every subset; DP over these masks solves the travelling salesman problem for 20 cities in about 2²⁰ × 20² ≈ 4 × 10⁸ steps instead of 20! ≈ 2.4 × 10¹⁸.

Pitfall

In C and C++, shifting by a negative amount or by at least the width of the type is undefined behaviour (1 << 32 on a 32-bit int), and 1 << 31 on a 32-bit signed int is undefined in C (and was in C++ before C++14). Write 1u << k or uint64_t{1} << k. Right-shifting a negative signed value was implementation-defined before C++20 (now arithmetic). And bit order is not byte order: when bits are read from a network packet or a register map, the byte order (endianness) and the bit numbering of the specification must both be checked.

In embedded

Hardware registers are read and written with masks and shifts on volatile pointers; C bit-fields are avoided for them because their layout and access width are implementation-defined. Read-modify-write sequences on shared registers need care when an interrupt can change the same register in between.

9Solving an unfamiliar coding problem

The hard part of a new problem is turning a vague statement into a correct, efficient program. A repeatable method matters more than the number of problems memorised, because it keeps you moving when the problem is new and it makes your reasoning visible to whoever reviews the code.

9.1A method that works under pressure

The method in Figure 9.1 has seven steps, and the order is the point. Clarify first: the input types and sizes, whether the data can be empty, contain duplicates or negative numbers, whether it is sorted, what to return when there is no answer. The constraint on n tells you the target complexity (Section 1.3). Work an example by hand, including one tricky case; many solutions appear while doing this. State a brute force and its cost, even if it is obviously too slow: it proves you understand the problem and gives you a fallback. Then optimise by naming the waste in the brute force (repeated searches → hash map; repeated subproblems → DP; re-scanning a range → sliding window; sorting would make it easy → sort first) and choosing a pattern from Section 7.1.

Only then code, with meaningful names and small helper functions, talking through what each part does. Test by walking your example through the code line by line, then the edge cases: empty input, one element, all equal, the largest values (overflow), and the case where no answer exists. Finally state the complexity in time and space and mention a trade-off or extension. The trade-offs are what a reviewer asks about next: what if the data does not fit in memory, what if it arrives as a stream, what if several threads call this.

Pitfall

Starting to type before the approach is clear is the most common failure. The second is silence: a reviewer or pair partner can only help with reasoning they hear. If you are stuck, say what you are trying and why it does not work yet.

9.2Worked problems: recognising the pattern

The following problems are the classic representatives of the patterns in this chapter. For each, the useful part is the line of reasoning that leads to the pattern, not the code itself.

Two sum (unsorted). Find two indices whose values sum to a target. The brute force checks all pairs, O(n²). The waste: for each element we search the whole array for its complement. A hash map from value to index turns that search into O(1), so one pass suffices: for each x, check whether target − x was seen, then record x. O(n) time, O(n) memory. If the array were sorted, two pointers would do it in O(1) memory (Section 7.2), a trade-off worth mentioning.

std::optional<std::pair<int, int>> two_sum(const std::vector<int>& a, int target) {
    std::unordered_map<int, int> seen;               // value -> index
    seen.reserve(a.size());
    for (int i = 0; i < (int)a.size(); ++i) {
        if (auto it = seen.find(target - a[i]); it != seen.end()) return std::pair{it->second, i};
        seen.emplace(a[i], i);
    }
    return std::nullopt;                             // O(n) time, O(n) space
}

Merge overlapping intervals. Given booking intervals, merge the ones that overlap. Signal: intervals. Sorting by start makes every overlap adjacent, so one pass that extends the last merged interval or starts a new one suffices. O(n log n) for the sort, O(n) for the pass.

std::vector<std::pair<int, int>> merge(std::vector<std::pair<int, int>> v) {
    std::sort(v.begin(), v.end());                   // by start, then end
    std::vector<std::pair<int, int>> out;
    for (auto [s, e] : v) {
        if (!out.empty() && s <= out.back().second) out.back().second = std::max(out.back().second, e);
        else out.push_back({s, e});
    }
    return out;
}

Top-k frequent products. From a log of purchases, return the k most frequent product ids. Count with a hash map, O(n). Then the "top k" signal says heap: keep a min-heap of size k of (count, id) pairs, O(u log k) for u distinct ids. If k is close to u, nth_element on the counts or a bucket sort by frequency (counts are at most n) gives O(u). For a stream too large to count exactly, the Count-Min sketch approximates the counts in fixed memory, which is how real "trending" features work.

Number of islands. Count connected groups of land cells in a grid. Signal: grid, connected regions. Scan every cell; on each unvisited land cell, increment the count and flood the whole island with BFS or DFS, marking cells visited. Every cell is visited a constant number of times, O(rows × cols). Union-find (Section 4.4) is the alternative when land cells are added one at a time and the count must be updated after each.

Course schedule. Given prerequisites, can all courses be finished, and in what order? Signal: dependencies. This is a topological sort (Section 5.3): the order exists if and only if Kahn's algorithm emits every node; otherwise there is a cycle. O(V + E).

Kth largest element. Signal: k-th. Three answers at three levels: sort, O(n log n); min-heap of size k, O(n log k) and works on a stream; quickselect (std::nth_element), O(n) on average. Naming all three and when each fits is a strong answer.

Longest increasing subsequence. Signal: optimal value over choices, so DP: dp[i] = length of the longest increasing subsequence ending at i, O(n²). The known improvement keeps, for each length, the smallest possible tail value; those tails are sorted, so each element finds its place by binary search, O(n log n). It is a good example of a DP sped up by a data structure.

9.3Design an LRU cache

The shop caches product pages in memory. The cache has a fixed capacity, and when it is full the entry that was used least recently is evicted, on the theory that recently used pages will be used again. The textbook version asks for get(key) and put(key, value), both in O(1). It is the classic design exercise at the boundary between data structures and system design, because it needs two structures working together.

Two requirements pull in different directions. Lookup by key in O(1) says hash map. Knowing the least recently used entry and moving an entry to "most recent" in O(1) says an ordered list where any element can be unlinked and relinked at the front without searching, which is a doubly linked list. The combination: a list of (key, value) pairs ordered from most to least recently used, and a hash map from key to the list node (in C++, a list iterator, which stays valid when the node is moved). get finds the node through the map and splices it to the front. put updates and moves an existing node, or, if the key is new and the cache is full, evicts the node at the back (erasing its key from the map) and inserts the new node at the front.

template <class K, class V>
class LruCache {
    std::size_t cap_;
    std::list<std::pair<K, V>> items_;                                   // front = most recent
    std::unordered_map<K, typename std::list<std::pair<K, V>>::iterator> index_;
public:
    explicit LruCache(std::size_t cap) : cap_(cap) { index_.reserve(cap); }
    std::optional<V> get(const K& k) {
        auto it = index_.find(k);
        if (it == index_.end()) return std::nullopt;
        items_.splice(items_.begin(), items_, it->second);                // O(1), iterator stays valid
        return it->second->second;
    }
    void put(const K& k, V v) {
        if (auto it = index_.find(k); it != index_.end()) {
            it->second->second = std::move(v);
            items_.splice(items_.begin(), items_, it->second);
            return;
        }
        if (items_.size() == cap_) {                                     // evict least recent
            index_.erase(items_.back().first);
            items_.pop_back();
        }
        items_.emplace_front(k, std::move(v));
        index_[k] = items_.begin();
    }
};

Both operations are O(1) on average. The production questions come next. Thread safety: a single mutex around both structures is correct but serialises every get, because even a read moves a node; production caches shard by key hash (one lock per shard) or approximate LRU to avoid writes on reads. Memory: every entry costs a list node and a hash node, two allocations; an allocation-free version keeps the entries in a fixed array and links them by index, which is what embedded and kernel code does. Policy: LRU is fooled by one large scan that flushes the whole cache; LFU (least frequently used), the CLOCK algorithm used by operating-system page caches, and admission policies such as TinyLFU (in Java's Caffeine) handle that better. Redis, for example, approximates LRU by sampling a few keys and evicting the oldest of the sample, which needs no list at all.

Talk track

"I need O(1) lookup, so a hash map, and O(1) access to and reordering of the least recently used entry, so a doubly linked list. The map stores list iterators, so get is a lookup plus a splice, and put evicts from the back. For concurrency I'd shard it; for embedded I'd use a fixed array with index links."

9.4What production C++ and embedded code adds

In production code the algorithm is only the entry ticket; the real questions are about the constant factors and memory behaviour from Section 1.6 (why a vector of structs may beat a map, why a flat hash map beats std::unordered_map), about allocation (can this run without touching the heap after start-up, can it use a fixed-capacity container or a pool), about worst-case rather than average-case bounds where timing matters, about overflow in sums and midpoints, about recursion depth on small embedded stacks, and about what changes when the data is shared between threads (the concurrent versions of queues, maps and ring buffers are in Concurrency 5). Using the standard library fluently (std::sort with a lambda, lower_bound, priority_queue with greater<>, structured bindings, reserve) matters as much as the algorithm.

In automotive and embedded

Safety coding standards (MISRA C++ and AUTOSAR C++14 guidelines) restrict dynamic memory, recursion and unbounded loops, so the embedded form of these structures uses static arrays, explicit stacks, bounded queues and worst-case execution time arguments. The algorithms are the same; the containers and the analysis change.

QSelf-check questions

Q.1Core questions

What does O(n log n) mean, and why do we drop constants?Basic

It means that beyond some input size the work is at most a constant times n log n: doubling the input slightly more than doubles the work. Constants are dropped because they depend on the machine and implementation, while the growth rate decides which algorithms are viable at large n. Among algorithms of the same class, constants and memory layout decide the winner, so they still matter in practice.

Why is push_back on a vector O(1) if it sometimes copies the whole array?Basic

The capacity grows geometrically, so the copies happen at sizes 1, 2, 4, …, n/2 and sum to less than n over n pushes. The total work is O(n), O(1) per push amortised. A fixed increment instead of a factor would make it O(n) per push.

When would you use a linked list instead of a vector?Basic

When I need stable addresses or iterators while inserting and erasing, O(1) insertion or removal at a position I already hold, or O(1) splicing between lists, as in an LRU cache or an intrusive free list. For plain sequences a vector is almost always faster because it is contiguous and cache-friendly.

How does a hash table work, and what is its worst case?Basic

It hashes the key, reduces the hash to a bucket index and stores or looks up the entry there; collisions are handled by chaining or by probing other slots. The load factor is kept bounded by rehashing into a larger array, which keeps operations O(1) on average. The worst case is O(n) when many keys collide, through a bad hash or deliberately chosen keys.

What is the difference between std::map and std::unordered_map?Basic

std::map is a red-black tree: keys are ordered, operations are O(log n), and it supports range queries and successor lookups. std::unordered_map is a chained hash table: O(1) average, no order. The hash map is usually much faster for exact lookups (54 vs 1 315 ns per lookup in a million keys in the chapter's benchmark); the tree is needed for ordered queries or worst-case bounds.

How is a binary heap stored, and what do push and pop cost?Basic

As an array: children of i at 2i+1 and 2i+2, parent at (i−1)/2. Push appends and sifts up, pop moves the last element to the root and sifts down; both are O(log n). Reading the minimum is O(1), and building a heap from n elements is O(n).

BFS or DFS: which would you use for the shortest path in a maze?Basic

BFS, because it visits cells in order of distance in moves, so the first time it reaches the exit is via a shortest path. DFS finds a path but not necessarily the shortest. If moves have different costs, Dijkstra or A*.

Explain how binary search works and how to avoid the classic bugs.Basic

Keep a range that always contains the answer and halve it by comparing with the middle. Use a half-open range [lo, hi), compute mid as lo + (hi − lo)/2 to avoid overflow, and decide clearly whether mid can still be the answer (hi = mid) or not (lo = mid + 1), so the loop always shrinks the range.

Find two numbers in an array that sum to a target.Basic

One pass with a hash map from value to index: for each x, check whether target − x was seen, then insert x. O(n) time and space. If the array is sorted, two pointers from both ends give O(n) time and O(1) space.

Why is quicksort usually faster than merge sort, and why does std::sort not use plain quicksort?Intermediate

Quicksort partitions in place with sequential passes, so it has small constants and good cache behaviour, and needs no O(n) buffer. Its worst case is O(n²) on bad pivots, for example sorted input with a naive pivot. std::sort is introsort: median-of-three pivots, heapsort when recursion gets too deep (guaranteeing O(n log n)), and insertion sort for small ranges.

What does stable sorting mean and when do you need it?Intermediate

Equal elements keep their original relative order. It is needed when sorting by several keys in passes (sort by date, then stable-sort by customer) or when the input order carries meaning. std::stable_sort (merge sort) is stable; std::sort is not.

How would you find the k largest elements in a stream of a billion numbers?Intermediate

Keep a min-heap of size k. For each number larger than the heap's minimum, pop the minimum and push the number. O(n log k) time and O(k) memory, and it never needs the whole stream in memory. If all data is in memory and order does not matter, nth_element is O(n) on average.

How does Dijkstra's algorithm work, and when does it fail?Intermediate

It keeps tentative distances and a priority queue; it repeatedly takes the closest unfinished node, declares its distance final and relaxes its outgoing edges. With a binary heap it is O((V + E) log V). It fails with negative edge weights, because a finalised node could later be reached more cheaply; Bellman–Ford handles that case.

What makes A* faster than Dijkstra, and what must the heuristic satisfy?Intermediate

A* orders nodes by cost so far plus an estimate of the cost to the goal, so it expands nodes in the goal's direction first. The heuristic must be admissible (never overestimate) for the result to be optimal; consistent heuristics also guarantee each node is expanded once. In the chapter's grid example A* expanded 231 cells against Dijkstra's 381 for the same optimal path.

How do you detect a cycle in a directed graph?Intermediate

Either run Kahn's topological sort and check whether every node was emitted, or run DFS with three colours (unvisited, on the current path, finished) and report a cycle when an edge leads to a node on the current path. Both are O(V + E). For undirected graphs, union-find or DFS with a parent check works.

Explain union-find and its optimisations.Intermediate

Each element stores a parent; the root represents the set. find follows parents to the root, union links one root under the other. Union by rank keeps trees shallow, and path compression points visited nodes directly at the root; together the amortised cost per operation is the inverse Ackermann function, effectively constant.

Longest substring without repeating characters: approach and complexity?Intermediate

Sliding window with the last index of each character. Advance the right edge; if the new character was last seen inside the window, move the left edge just past that position. Track the maximum window length. Each index enters and leaves once: O(n) time, O(alphabet) space.

How do you recognise that a problem needs dynamic programming?Intermediate

It asks for an optimal value or a count over a sequence of choices, a natural recursion exists, and that recursion would solve the same subproblems repeatedly. Then I define the state in one sentence, write the recurrence from the possible last choices, and fill a table or memoise. The cost is states times transitions.

Design an LRU cache with O(1) get and put.Intermediate

A hash map from key to a node in a doubly linked list ordered by recency. get looks up the node and moves it to the front; put updates or inserts at the front and, when full, evicts the node at the back and erases its key from the map. In C++, std::list with splice and an unordered_map of list iterators.

How would you make an LRU cache thread-safe without a global bottleneck?Advanced

A single mutex works but serialises all calls, including reads, because every get reorders the list. Better: shard the cache by key hash with one lock per shard, or approximate LRU (sampling as Redis does, or CLOCK with a reference bit) so that reads only set a flag instead of moving nodes. The trade-off is exact LRU order for scalability.

Why can a sorted vector beat std::map even though both are O(log n)?Advanced

Binary search in a sorted vector touches a contiguous array whose upper levels stay in cache, and it has no per-element allocation. A red-black tree lookup follows pointers to nodes scattered on the heap, so each level can be a cache miss. Measured on a million keys: 355 ns against 1 315 ns. The vector loses when insertions in the middle are frequent.

Why do the fastest hash tables use open addressing rather than chaining?Advanced

Probes in an open-addressing table are adjacent slots in the same cache line, with no allocation per entry, while each chaining step follows a pointer to a separately allocated node. Swiss tables add a byte array of hash tags compared 16 at a time with SIMD, so most probes never touch a key. std::unordered_map uses chaining because the standard requires stable references across rehashing.

What is hash flooding and how is it prevented?Advanced

An attacker sends keys chosen to collide under a known hash function, turning O(1) operations into O(n) and a request into a CPU-bound denial of service. Defences: a keyed hash with a secret random seed (SipHash), limits on the number of keys per request, and tree-shaped buckets (Java 8 HashMap) that bound the worst case at O(log n).

How would you sort 100 GB of records on a machine with 8 GB of RAM?Advanced

External merge sort. Read chunks that fit in memory, sort each and write it as a sorted run; then merge the runs with a min-heap of their current front records, reading and writing sequentially with large buffers. With 8 GB chunks there are about 13 runs, so one merge pass suffices. Sequential I/O dominates the cost.

How would you implement a fixed-capacity queue for an interrupt handler and a task?Advanced

A single-producer, single-consumer ring buffer with a power-of-two capacity and free-running counters: the producer writes the slot and then publishes tail with release ordering, the consumer reads tail with acquire ordering. No locks, no allocation, O(1), and the full condition is tail − head == N with a documented overflow policy.

Count the set bits of an integer; check whether it is a power of two.Basic

std::popcount(x) compiles to one instruction; by hand, repeat x &= x − 1 until zero and count the steps. x is a power of two if x != 0 and (x & (x − 1)) == 0, or std::has_single_bit(x) in C++20.

Find the single number in an array where every other number appears twice.Basic

XOR all elements: pairs cancel because a ^ a = 0 and XOR is commutative and associative, so the result is the single number. O(n) time, O(1) memory.

Q.2Why and what if

Why can an O(n) linear scan beat an O(log n) binary search?Why

For small arrays the constants dominate. The scan reads consecutive memory and its loop branch is predictable; binary search jumps around and mispredicts about half its branches. In the chapter's benchmark the scan won up to 256 ints and lost at 1 024.

Why does a list traversal with nodes allocated in order run ten times faster than the same list after shuffling, when the code is identical?Why

Allocated in order, consecutive nodes sit in neighbouring memory, so most next pointers point into a cache line that is already loaded or being prefetched. Shuffled, every next pointer leads to a random address and each step waits for DRAM, about 100 ns. Measured: 2.8 vs 139 ns per element.

Why does std::unordered_map keep references valid across rehashing while an open-addressing table cannot?Why

In chaining, each element lives in its own heap node; rehashing only relinks nodes into a new bucket array, so the elements never move. In open addressing the elements live in the slot array itself, and rehashing copies them into a new array.

Why does BFS mark nodes when they are discovered rather than when they are dequeued?Why

If marking waited until dequeue, a node reachable from several nodes on the current level would be enqueued several times, wasting work and memory, and in dense graphs the queue could grow to O(E). Marking at discovery guarantees each node enters the queue once, with its correct shortest distance.

Why is building a heap O(n) while n pushes cost O(n log n)?Why

Bottom-up construction sifts down from the last parent to the root. Half the nodes are leaves and do no work, a quarter sift down at most one level, an eighth at most two, and the sum n/4·1 + n/8·2 + … is below n. Pushing one at a time sifts up from the bottom, and most elements may travel up to log n levels.

Why is the greedy coin algorithm right for euros and wrong for coins {1, 3, 4}?Why

For canonical coin systems like the euro, an exchange argument shows that taking the largest coin never prevents an optimal completion. For {1, 3, 4} and amount 6, taking 4 forces 1 + 1, while two 3s are better, so the locally best choice is not safe and DP is needed.

Why does Dijkstra not work with negative edge weights?Why

Dijkstra finalises the closest unfinished node on the assumption that any other path to it must be at least as long, because extending a path cannot make it cheaper. A negative edge breaks that: a longer detour through a negative edge can arrive cheaper after the node was already finalised.

What if your hash table's load factor is allowed to reach 0.95 with linear probing?What if

Clusters merge and probe sequences explode: about 10 probes for a hit and roughly 180–200 for a miss in the chapter's simulation, against 1.5 and 2.5 at α = 0.5. Inserts and misses slow down sharply, which is why open-addressing tables rehash at 0.5–0.875.

What if a hash table's hash is the identity and the bucket index takes the low bits?What if

Any keys that share their low bits, such as ids that are multiples of 16 or aligned pointers, land in a few buckets and the table degrades towards a list. Figure 3.2 shows this with ids ending in 0 and a modulo-20 table. A mixing step (multiply and shift) before masking fixes it.

What if a recursive DFS runs on a path graph of ten million nodes?What if

It recurses ten million levels deep. At 50–100 bytes per frame that is far beyond the default 8 MB stack and the program crashes with a stack overflow. Use an explicit stack on the heap, or BFS when the order does not matter.

What if quicksort always picks the first element as pivot and the input is already sorted?What if

Every partition puts all remaining elements on one side, the recursion depth becomes n and the cost O(n²): about 2 million comparisons for 2 000 sorted numbers against 24 000 for shuffled ones in the chapter's count. The recursion depth can also overflow the stack. Median-of-three pivots and introsort's depth limit prevent it.

What if A* uses a heuristic that sometimes overestimates?What if

It may expand fewer nodes and run faster, but it can return a path that is not the cheapest, because it can stop before exploring a better route that the inflated estimate made look worse. Weighted A* does this on purpose, trading bounded suboptimality for speed.

What if the data for a top-k query is spread across 100 servers?What if

Each server computes its local top k with a heap and sends only those k items; a coordinator merges the 100 lists with another heap. For exact global top-k of counts that are themselves split across servers, the local top k is not enough (an item could be just below k everywhere), so exact answers need the full counts or an iterative algorithm, while sketches give approximate answers cheaply.

What if the LRU cache must not allocate memory after start-up?What if

Preallocate an array of capacity entries and link them into the recency list by index (prev/next as integers). Use an open-addressing hash table of fixed size that stores entry indices, sized for a low load factor. Eviction reuses the tail entry's slot, so nothing is allocated or freed during operation.

What if you need a sorted map, but almost all operations are reads after an initial load?What if

Load into a vector, sort it once and use binary search (or C++23 std::flat_map). Lookups become cache-friendly, memory drops to the bare key-value pairs, and the O(n) cost of inserting into the middle no longer matters because inserts are rare.

Admissible heuristic
An estimate of the remaining cost that never exceeds the true cost; makes A* return optimal paths.
Amortised cost
The average cost per operation over a worst-case sequence of operations, as in vector growth or hash table rehashing.
B-tree
A balanced search tree with many keys and children per node, sized to disk pages or cache lines; the basis of database indexes and file systems.
Backtracking
Building candidates one choice at a time, recursing, and undoing each choice before trying the next, with pruning of hopeless branches.
Big-O
An upper bound on growth: f = O(g) if f is at most a constant times g for large inputs. Ω is the lower bound, Θ both.
BFS (breadth-first search)
Graph traversal in order of distance in edges, using a FIFO queue; finds shortest paths in unweighted graphs.
Bloom filter
A bit array with several hash functions that answers set membership with no false negatives and a tunable false-positive rate.
CSR (compressed sparse row)
A graph or sparse-matrix layout with an offset array and a flat target array; neighbours of node i are a contiguous slice.
DFS (depth-first search)
Graph traversal that follows one branch as deep as possible before backing up, using a stack or recursion.
Dijkstra's algorithm
Single-source shortest paths with non-negative weights, expanding nodes in order of distance from a priority queue.
Dynamic programming
Solving a problem by combining stored answers to overlapping subproblems, top-down (memoisation) or bottom-up (tabulation).
Hash table
An array indexed by a hash of the key; collisions handled by chaining or open addressing; O(1) average operations.
Heap (binary)
A complete binary tree stored in an array in which every parent is ordered before its children; implements a priority queue.
Introsort
Quicksort that switches to heapsort when recursion gets too deep and to insertion sort for small ranges; std::sort.
Load factor
Entries divided by slots or buckets in a hash table; kept below a maximum by rehashing.
LRU (least recently used)
A cache eviction policy that removes the entry unused for the longest time; implemented with a hash map and a doubly linked list.
Minimum spanning tree
A set of V − 1 edges connecting all nodes of a weighted graph with minimum total weight; found by Kruskal or Prim.
Open addressing
Hash table design storing entries in one flat array and resolving collisions by probing other slots.
Red-black tree
A balanced binary search tree with node colours and rules that keep its height at most 2 log₂(n + 1); std::map and std::set.
Ring buffer
A fixed array used as a FIFO with head and tail counters that wrap around; O(1) and allocation-free.
Sliding window
A contiguous range bounded by two indices that advance monotonically, with its state updated incrementally.
Stable sort
A sort that keeps equal elements in their original relative order.
Topological sort
An ordering of a directed acyclic graph's nodes in which every edge points forward; Kahn's algorithm or DFS finish order.
Trie
A tree whose edges are characters, so that keys with a common prefix share a path; supports prefix queries in O(key length).
Two pointers
A pattern in which two indices move monotonically through the data so that a pair search takes O(n) instead of O(n²).
Union-find
A forest in a parent array that tracks disjoint sets with near-constant find and union, using union by rank and path compression.
