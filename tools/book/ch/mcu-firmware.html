Bare-metal microcontroller firmware

What happens on a microcontroller below any operating system: reset and the vector table, startup code and the linker script, memory-mapped registers and volatile, interrupts and the NVIC, peripheral drivers from GPIO to the CAN controller, DMA with the Cortex-M7 cache and the MPU, HardFaults and stack depth, watchdogs, power and bootloaders, bytes on the wire and debugging with SWD, ITM and a logic analyser. One running example goes through the whole chapter: a Cortex-M7 sensor node that powers up, reads an IMU over SPI with DMA when the IMU raises an interrupt, sends a CAN frame, and then crashes in a way we debug from the stacked registers. The startup code, the interrupt behaviour and every fault in this chapter come from a real build of that firmware running on an emulated Cortex-M7.

1The big picture: a computer with nothing underneath

A microcontroller program is the only software on its chip. Nobody loads it, nobody gives it memory, nobody catches its mistakes. Everything an operating system would normally do, from setting up the stack to deciding what happens on a crash, is either done by the firmware itself or not done at all. This chapter is about those jobs.

1.1What "bare metal" means, and why it is still everywhere

On a Linux machine your program is a guest. The kernel loaded it from a file, mapped its pages, gave it a stack, and will kill it with a clean error message if it touches memory it does not own. Hardware is behind system calls and drivers; time is shared by a scheduler. On a microcontroller running bare-metal firmware there is none of this. When the supply voltage comes up, the processor core starts executing whatever instructions sit at a fixed place in its flash memory, and from then on that code owns everything: every byte of RAM, every peripheral register, every interrupt, every clock. "Bare metal" means exactly that: the program runs directly on the hardware, with at most a small library or a tiny real-time kernel linked into the same image.

This sounds primitive, and in a way it is, but it is also why microcontrollers are in every electronic control unit of a car, in every sensor module, motor controller, battery management system and airbag unit. A microcontroller boots in a millisecond, not in seconds. Its timing is predictable to the clock cycle, because there is no virtual memory, no page faults and no scheduler that might decide to run something else. It costs a few euros, draws milliamps, runs from −40 °C to 125 °C, and can be certified for functional safety because the entire software stack is small enough to be reviewed and tested. Even a camera ECU built around a large system-on-chip usually carries a separate microcontroller for power sequencing, CAN communication and supervision, because it is up before Linux has even started (Embedded compute 5.2).

The price is that the firmware engineer must understand what an operating system would have hidden. Which address the first instruction is fetched from. How global variables get their initial values when there is no loader. Why reading a register twice may give two different answers. What the processor does with your registers when an interrupt arrives, and how many bytes of stack that costs. Why the CPU and a DMA engine can disagree about what is in memory. These are the subjects of this chapter, and they are also what separates people who have written firmware from people who have written C.

Why it matters

Bugs below the operating system do not produce error messages. A wrong linker script gives a board that does nothing; a missing volatile gives a loop that works at -O0 and hangs at -O2; a stale cache line gives a filter that sometimes processes last millisecond's data. The only way to find them quickly is to know the mechanism well enough to predict the symptom.

1.2The running example: an IMU node on CAN

To keep the chapter concrete we follow one small product from power-on to crash. It is a sensor node: a microcontroller with an Arm Cortex-M7 core running at 300 MHz, 1 MB of flash, 128 KB of tightly coupled data RAM and 512 KB of ordinary SRAM. Connected to it is an inertial measurement unit, an IMU, with a three-axis gyroscope and a three-axis accelerometer. Once per millisecond the IMU has a new sample and pulls its interrupt pin high. The microcontroller reacts by reading a 16-byte burst from the IMU over SPI using DMA, converts and filters the yaw rate and the longitudinal acceleration, and every tenth sample, so at 100 Hz, sends them in an 8-byte CAN frame with identifier 0x1A0. A chassis or ADAS controller elsewhere in the car consumes that frame.

Almost every subject of the chapter shows up in this one product. Power-on runs the startup code and depends on the linker script. The IMU's data-ready pin is an interrupt with a priority. The SPI transfer is set up through memory-mapped registers and carried out by DMA, and because the Cortex-M7 has a data cache, the received bytes are only visible to the CPU if the cache is handled correctly. The CAN frame needs explicit byte packing and a CAN controller driver. A watchdog checks that the main loop is still alive, a brown-out detector resets the chip when the supply sags during engine cranking, and a bootloader lets the workshop update the firmware. And when a buffer is declared four bytes too small, the chip crashes into a HardFault that we can diagnose from eight stacked registers.

The experiments in this chapter use the same firmware structure, built with the GNU Arm toolchain and run on QEMU's emulation of an Arm MPS2 board with a Cortex-M7 (machine mps2-an500). QEMU has no SPI, DMA or CAN peripheral on that board, so those register blocks are stand-ins in RAM, but the core behaviour is real: the reset sequence, the vector table, exception entry and the stacked frames, the fault status registers and the MPU. QEMU does not model timing or caches, so cycle counts and cache effects in this chapter come from Arm's documentation, not from the emulator.

1.3The Cortex-M programmer's model in one page

Arm's Cortex-M family is the most common microcontroller core: the M0 and M0+ at the small end (Armv6-M), the M3, M4 and M7 in the middle and upper range (Armv7-M), and the M23, M33, M55 and M85 with the newer Armv8-M architecture, which adds TrustZone security and stack-limit registers. Automotive microcontrollers also use other cores, for example Infineon's TriCore, Renesas RH850 or Power Architecture parts, but the ideas in this chapter carry over; only the register names change. We use Cortex-M because its rules are public and identical across vendors.

The core has sixteen 32-bit registers. R0 to R12 are general purpose. R13 is the stack pointer, SP, and there are actually two of them: the main stack pointer MSP, used after reset and always used by exception handlers, and the process stack pointer PSP, which an RTOS gives to each task. R14 is the link register, LR, which holds the return address after a function call and a special "magic" value during an exception. R15 is the program counter. A program status register, xPSR, holds the condition flags, the Thumb state bit and, in its lowest bits, the number of the exception currently being handled. Cortex-M executes only the Thumb instruction set, a mix of 16- and 32-bit instructions, and marks Thumb addresses by setting bit 0: a function at address 0x6A8 is referred to as 0x6A9. You will see that odd bit in vector tables and in LR values, and forgetting it is a classic way to fault.

The core runs in one of two modes. Thread mode is normal code: main and everything it calls, or RTOS tasks. Handler mode is entered for every exception and interrupt. Independently, code is privileged or unprivileged; bare-metal firmware usually runs everything privileged, while an RTOS with memory protection runs tasks unprivileged so that the MPU can confine them (Functional safety 6.2). A special register called CONTROL selects which stack pointer thread mode uses and whether it is privileged, and on cores with a floating-point unit it also records whether floating-point state is live, which will matter for interrupt stack frames.

The second half of the programmer's model is the address map. There is no separate I/O space: memories and peripheral registers all live in one 4 GB address space, and the architecture fixes how it is divided. The lowest half gigabyte is for code, which is where flash memory sits and where the core looks for its vector table at reset. Then comes SRAM at 0x2000_0000, then peripherals at 0x4000_0000, then two regions for external memory and devices, and at 0xE000_0000 the private peripheral bus with the System Control Block (SCB), the Nested Vectored Interrupt Controller (NVIC), the SysTick timer, the MPU and the debug units. Each region has default attributes: code and SRAM are "Normal" memory that may be cached and from which instructions may be executed; peripheral regions are "Device" memory, never cached, never executed from, and accessed in program order. Those attributes are why a write to a peripheral register is not held in a cache, and why jumping into a peripheral region faults.

"A Cortex-M has two stack pointers, two modes and one flat address map. Thread mode runs main or the tasks; handler mode runs exceptions and always uses the main stack. Flash is at the bottom, SRAM at 0x2000_0000, peripherals at 0x4000_0000 and the core's own control registers, NVIC, SysTick, SCB and MPU, at 0xE000_0000, the same on every vendor's part. Everything is memory-mapped, so driving hardware is reading and writing addresses."

2From power-on to main()

C code assumes a world that does not exist at reset: a valid stack, global variables with their initial values, zeroed statics, working clocks. Startup code is the few dozen lines that build that world, and the vector table is how the hardware finds them.

2.1What reset does in hardware

A microcontroller is reset for many reasons: the supply has just come up (power-on reset), the supply dipped below a threshold (brown-out reset), someone pulled the reset pin, the watchdog expired, software asked for it, or the core locked up. In every case the chip's reset controller holds the core in reset until the supply and the internal oscillator are stable, records the cause in a reset-status register, puts every peripheral register back to its documented reset value, and releases the core. The clock at this point is a slow internal RC oscillator, typically 8 to 64 MHz, because the crystal oscillator and the PLL that multiplies its frequency are off until software turns them on. Memory contents are a different story: RAM is not cleared by reset. After power-on it holds random values; after a warm reset it still holds whatever the program left there, which is useful, as we will see with crash records.

When the core comes out of reset it does exactly two memory reads before executing anything. It reads the 32-bit word at the start of the vector table and loads it into the main stack pointer, and it reads the next word and loads it into the program counter. The vector table is at address 0x0000_0000 on most parts; some chips let boot pins or option bytes choose a different boot address, or map flash, system ROM or SRAM to address 0 at reset. Bit 0 of the second word must be 1, because it is a Thumb address; the core clears the bit to form the PC and uses it to set the Thumb state. If bit 0 were 0, the core would try to execute in a state Cortex-M does not support and would fault on the very first instruction. From that moment the core is running your code, in thread mode, privileged, on the main stack, with interrupts enabled in the core but none enabled in the NVIC.

Interesting detail

Loading the stack pointer from the vector table is a deliberate Cortex-M design choice. Older Arm cores started at a fixed address in assembly and had to set up each mode's stack before any C function could run. Because a Cortex-M has a valid SP before its first instruction and saves the caller-saved registers in hardware on exceptions, both the reset handler and every interrupt handler can be ordinary C functions. Nothing in the chapter's demo firmware is written in an assembly file.

2.2The vector table

The vector table is an array of 32-bit words. Entry 0 is the initial stack pointer; entries 1 to 15 are the system exceptions, Reset, NMI, HardFault, MemManage, BusFault, UsageFault, SVCall, DebugMonitor, PendSV and SysTick, with a few reserved slots; entries from 16 upward are the device's interrupt lines, IRQ 0, IRQ 1 and so on, as many as the vendor implemented (often 100 to 250). The exception number used throughout the architecture is the index into this table, so IRQ 21 is exception 37. When an interrupt or fault occurs, the hardware reads the handler's address from the table, which is why the NVIC is called vectored: there is no common entry point that has to work out who interrupted.

typedef void (*vector_t)(void);
extern uint32_t _estack;                      /* defined by the linker script */

__attribute__((section(".isr_vector"), used))
const vector_t vector_table[16 + 32] = {
  [0 ... 47]      = Default_Handler,          /* anything unexpected lands here */
  [0]             = (vector_t)&_estack,       /* initial MSP: loaded by hardware from address 0x0 */
  [1]             = Reset_Handler,            /* initial PC:  loaded by hardware from address 0x4 */
  [2]             = NMI_Handler,
  [3]             = HardFault_Handler,
  [4]             = MemManage_Handler,
  [5]             = BusFault_Handler,
  [6]             = UsageFault_Handler,
  [11]            = SVC_Handler,
  [14]            = PendSV_Handler,
  [15]            = SysTick_Handler,
  [16 + IRQ_DRDY] = DataReady_IRQHandler,     /* IMU data-ready, external interrupt */
  [16 + IRQ_CAN]  = Can_IRQHandler,
  [16 + IRQ_DMA]  = DmaDone_IRQHandler,
};

Three details in this table recur in every real project. The table has its own section, .isr_vector, so that the linker script can place it at the very start of flash, and it is marked used so that the linker's garbage collection does not throw it away (nothing in the program references it). The handlers are declared as weak aliases of Default_Handler: if the application defines Can_IRQHandler, the linker uses that; if not, the vector points to a default that stops loudly instead of jumping to address zero. And the table is const, so it lives in flash. A copy can be made in RAM later and the Vector Table Offset Register, SCB->VTOR, pointed at it, which is how a bootloader hands over to an application and how some systems change handlers at run time.

Pitfall

A misspelt handler name compiles and links without a warning: CAN1_RX0_IRQHandler instead of CAN1_RX0_IRQhandler simply defines a new function, and the vector keeps pointing at the weak default. The symptom is a board that hangs in Default_Handler the first time the interrupt fires. Check the map file, or make the default handler print the active exception number from IPSR.

2.3Startup code, step by step

The reset handler runs before any of the guarantees that C makes are true. Global variables that were initialised in the source, like uint32_t boot_count_init = 0x1234ABCD;, are in the .data section; their initial values are stored in flash, but the variables themselves must live in RAM so they can be modified. Variables without an initialiser, and those initialised to zero, are in .bss, and C promises they start at zero, but RAM after power-on contains noise. Nobody fixes this except the startup code. Its job, in order, is to make the hardware able to run C, copy .data from flash to RAM, zero .bss, run C++ constructors if there are any, and call main.

Here is the reset handler of the demo firmware. It is written in C, which works because the hardware has already loaded a valid stack pointer, but it must be careful not to use anything that the steps after it are about to create.

extern uint32_t _sidata, _sdata, _edata, _sbss, _ebss;   /* from the linker script */

__attribute__((noreturn)) void Reset_Handler(void)
{
  /* 1. FPU access before any code that may use floating point (CP10 and CP11, full access). */
  SCB_CPACR |= 0xFu << 20;
  dsb(); isb();                               /* make the change take effect before the next instruction */

  /* 2. Copy .data initial values from flash (LMA) to RAM (VMA). */
  uint32_t *src = &_sidata, *dst = &_sdata;
  while (dst < &_edata) *dst++ = *src++;

  /* 3. Zero .bss. */
  for (dst = &_sbss; dst < &_ebss; ) *dst++ = 0;

  /* 4. Vector table (a bootloader may have moved VTOR). */
  SCB_VTOR = (uint32_t)vector_table;
  dsb(); isb();

  main();
  for (;;) { }                                /* main must not return; if it does, stay here */
}

On QEMU the demo firmware prints what the hardware and the startup code produced. The core's ID register reads 0x411F_C272, which decodes as Arm, Cortex-M7, revision r1p2. Vector entry 0 is 0x2000_1000 and entry 1 is 0x0000_06A9. Inside main, SP is 0x2000_0FD0, 48 bytes below the top of the stack: the reset handler and main have pushed their own frames. The initialised global reads 0x1234_ABCD, so the copy worked; the uninitialised one reads zero. CONTROL is 0, meaning privileged thread mode on the main stack, with no floating-point context active yet.

Pitfall

An optimising compiler may recognise the copy and zero loops and replace them with calls to memcpy and memset. That is harmless if those functions exist and do not themselves depend on initialised data, but in a freestanding build without a C library it is an unresolved symbol, and with some libraries it is a call into code that expects .data to be ready. Startup files are therefore often compiled with -fno-tree-loop-distribute-patterns or written in assembly. The same trap catches anyone who adds a log message at the top of Reset_Handler: the logging code's state is in .bss, which has not been cleared yet.

2.4Clocks, the PLL and flash wait states

After reset the core runs from an internal RC oscillator, because it is the only clock guaranteed to be there. It is not accurate enough for CAN or a UART at high baud rates (its frequency varies by a percent or more with temperature) and not fast enough for the application. So one of the first things firmware does is start the external crystal oscillator, wait until the oscillator reports that it is stable, configure the phase-locked loop, PLL, to multiply the crystal frequency up (for example 25 MHz × 24 / 2 = 300 MHz), wait for the PLL to lock, and then switch the system clock over. Peripheral clocks are derived from the system clock through prescalers, and every peripheral has its own clock-enable bit, off by default to save power.

The order matters because of flash. Embedded flash needs a fixed time to deliver a word, on the order of 20 to 30 ns, independent of the CPU clock. At 24 MHz a clock cycle is 42 ns and flash keeps up; at 300 MHz a cycle is 3.3 ns, and the flash interface must insert wait states, about seven of them for a 25 ns flash. If firmware switches to 300 MHz before it has programmed the wait states, the very next instruction fetch reads garbage and the core faults or runs off into random code. So the rule is: raise wait states before raising the clock, lower them after lowering it. Seven wait states would make a 300 MHz core slower than a 50 MHz one, which is why fast microcontrollers have flash accelerators with prefetch buffers, instruction caches, and tightly coupled memory (TCM) that runs at full core speed with zero wait states.

Numbers

For a flash access time of 25 ns: 0 wait states at 24 MHz, 1 at 72 MHz, 4 at 168 MHz, 7 at 300 MHz. Interrupt latency on Cortex-M3, M4 and M7 is 12 cycles with zero-wait-state memory, 40 ns at 300 MHz; each wait state on the vector fetch and stacking adds to it.

2.5What C++ and the C library add

Bare-metal C++ works, but it adds three things the startup code and linker script must handle. Global objects with constructors need those constructors called before main: the compiler lists them in the .init_array section and the C library's __libc_init_array walks the list. Function-local statics with constructors are guarded by a lock that, in a hosted environment, comes from the threading library; bare metal either provides trivial versions or compiles with -fno-threadsafe-statics and accepts the consequence. And exceptions and run-time type information pull in unwinding tables and tens of kilobytes of library code, so most embedded projects build with -fno-exceptions -fno-rtti. The C library itself, usually newlib or its smaller newlib-nano variant on Arm toolchains, needs a handful of "system call" stubs such as _sbrk for malloc and _write for printf; the firmware provides them, typically mapping _write to a UART or to the debugger's trace channel.

Many safety-relevant projects avoid the heap entirely: no malloc after initialisation, all buffers statically sized. The reason is not that malloc is slow but that fragmentation and out-of-memory failures cannot be bounded by analysis. The same projects forbid recursion for the reason we will meet in Section 8.5: it makes the worst-case stack depth impossible to compute. The language rules behind this belong to C++ 14.

3Linker scripts and the memory map

On a PC the operating system decides where a program lives in memory. On a microcontroller nobody does, so the linker has to be told: which address ranges are flash and RAM, which sections go where, where the stack is, and which addresses the startup code needs to know. That description is the linker script.

3.1Why the linker must be told where things go

The compiler turns each source file into an object file whose code and data are in named sections, .text for instructions, .rodata for constants, .data for initialised variables and .bss for zero-initialised ones, with addresses still undecided. The linker collects the sections of all object files, decides final addresses, and patches every reference (Build systems 3 covers symbol resolution in general). For a Linux program the default placement is fine, because the kernel's loader maps the file wherever the ELF header says and virtual memory makes any address work. A microcontroller has physical memory only, with fixed ranges, and nothing that loads the program at run time: the image is written into flash once, and the CPU executes it in place. So the linker must place code at addresses inside flash, variables at addresses inside RAM, and the vector table at exactly the address where the core reads it at reset.

The subtle part is .data. Its initial values must be stored in flash, because flash is the only thing that survives power-off, but the variables must be used at RAM addresses, because flash cannot be written like RAM. A section therefore has two addresses: its load memory address, LMA, which is where its bytes are in the image, and its virtual memory address, VMA, where the code expects them at run time. (The name "virtual" is historical; there is no virtual memory here.) For .text both are the same flash address. For .data the LMA is in flash and the VMA in RAM, and the copy loop in the reset handler is what makes the two agree.

3.2Sections and the memory map

A typical microcontroller image has the vector table first, at the start of flash, followed by code and read-only data. In RAM it has .data and .bss, the stack, often a heap, and sometimes special sections. Two of those deserve explanation now because the rest of the chapter uses them. A .noinit section is RAM that the startup code neither copies nor zeroes, so its contents survive a warm reset: a fault handler can write a crash record there, reset the chip, and the next boot can read and report it. A DMA buffer section is RAM with special alignment, and on the Cortex-M7 often special cache attributes, for buffers that a DMA controller writes behind the CPU's back (Section 7.3).

Where to put the stack is a real design decision. The traditional choice is the top of RAM, growing down towards the heap and .bss. Then an overflow silently overwrites the highest global variables, and the symptom shows up later somewhere unrelated. The demo firmware puts the stack at the bottom of RAM instead: when it overflows, it runs off the start of RAM, or into an MPU guard region, and faults immediately at the instruction that overflowed. Armv8-M cores make this cheaper with dedicated stack-limit registers, MSPLIM and PSPLIM, which fault as soon as SP goes below a limit.

3.3A linker script, line by line

Here is the demo firmware's linker script for the GNU linker, shortened only by removing comments. Vendor scripts are longer, mostly because they handle C++ tables, several RAM banks and more special sections, but their structure is the same.

MEMORY
{
  FLASH (rx)  : ORIGIN = 0x00000000, LENGTH = 1024K
  RAM   (rwx) : ORIGIN = 0x20000000, LENGTH = 256K
}
ENTRY(Reset_Handler)
_stack_size = 0x1000;                       /* 4 KiB main stack */

SECTIONS
{
  .isr_vector : { KEEP(*(.isr_vector)) } > FLASH          /* first: the core reads SP and PC here */
  .text       : { *(.text .text.*) *(.rodata .rodata.*) . = ALIGN(4); } > FLASH

  .stack (NOLOAD) : { . = ALIGN(8); _sstack = .; . += _stack_size; _estack = .; } > RAM

  .data : { _sdata = .; *(.data .data.*) . = ALIGN(4); _edata = .; } > RAM AT > FLASH
  _sidata = LOADADDR(.data);                /* where the initial values are in flash */

  .bss (NOLOAD)    : { _sbss = .; *(.bss .bss.*) *(COMMON) . = ALIGN(4); _ebss = .; } > RAM
  .dma (NOLOAD)    : { . = ALIGN(32); *(.dma .dma.*) . = ALIGN(32); } > RAM
  .noinit (NOLOAD) : { *(.noinit .noinit.*) } > RAM
  _end = .;
}

The MEMORY block names the physical regions with their start and length; the linker refuses to place anything outside them and reports an overflow by how many bytes, which is the most common linker error in embedded work. Each output section in SECTIONS lists which input sections it collects, with wildcards so that .text.can_send, the section the compiler creates for one function under -ffunction-sections, lands in .text. The > RAM AT > FLASH on .data is the LMA/VMA split in one line: run at a RAM address, store in flash. Symbols assigned inside the script, such as _sdata or _estack, are not variables but addresses; C code declares them as extern uint32_t _sdata; and uses &_sdata, never their value. NOLOAD tells the linker that the section occupies addresses but has no bytes in the image. And KEEP protects the vector table from --gc-sections, which would otherwise remove it because no code refers to it.

Pitfall

Writing extern uint32_t *_sdata; and using _sdata instead of &_sdata reads the first word of RAM as a pointer. The copy loop then copies from a random place to another random place, and the board either crashes before main or runs with corrupted globals. When startup fails, check the map file and the symbol usage first.

3.4Reading the map file and the size report

The linker can write a map file (-Wl,-Map=fw.map) that lists every output section, every input section inside it with the object file it came from, every symbol's address and the load address of each section. It is the first thing to open when an image does not fit, when a function is in the wrong memory, or when two variables that should not be neighbours are. The size tool gives the summary. For the demo firmware it reports 2,856 bytes of text (the vector table, code and constants), 4 bytes of data and 4,220 bytes of bss, which in the tool's terminology includes the 4 KB stack because the stack is a NOLOAD section in RAM. Flash use is text plus data, because the initial values of .data are stored in flash too; RAM use is data plus bss.

The map file confirms the layout in Figure 3.1: .stack at 0x2000_0000 with length 0x1000, .data at 0x2000_1000 with "load address 0x0000_0B28", .bss at 0x2000_1004 with 0x24 bytes and the crash record in .noinit at 0x2000_1040. Asking the size tool for per-section numbers (arm-none-eabi-size -A) shows something easy to miss: the .dma section is 24 bytes even though the demo puts nothing in it. Those are the alignment bytes needed to start it on a 32-byte boundary, the cache-line size of the Cortex-M7.

In practice

Track flash and RAM use in continuous integration, per section, and fail the build when a budget is exceeded rather than when the linker finally refuses. A "how much stack and heap do we have left" report from the map file is cheap and catches the slow growth that otherwise surfaces as a stack overflow two weeks before a release.

3.5Placement decisions

Because the linker script decides physical placement, it is also where performance and robustness decisions are made. Interrupt handlers and time-critical loops can be placed in ITCM, the instruction tightly coupled memory, which has no wait states and no cache misses; the startup code then has to copy them there, exactly like .data, using a section with a flash LMA and an ITCM VMA. The stack and frequently used data can go into DTCM for the same reason. Code that must run while flash is being erased, such as the flash driver of a bootloader, must run from RAM because most single-bank flashes cannot be read while they are being written. DMA buffers go into a region that the DMA controller can reach, which is not every region (on some chips the DMA controllers cannot access DTCM at all), and, on a cached core, into a region whose cache attributes the driver handles correctly. Calibration data and identification blocks are placed at fixed addresses so that tools can find them in the image (Production integration 4.3).

In C these decisions show up as section attributes: __attribute__((section(".dma"))) on a buffer, __attribute__((section(".itcm_text"))) on a function. The linker script is where the section names get their meaning, so the two must be reviewed together.

Talk track

"The linker script is the memory map of the product in executable form. It says where flash and RAM are, puts the vector table first, keeps code in flash and variables in RAM, and gives initialised data a load address in flash and a run address in RAM so the startup code can copy it. It is also where we decide what goes into TCM, where the stack is and whether it can overflow silently, and where the DMA buffers live."

4Talking to hardware: registers, volatile and bits

Every peripheral is controlled through registers that appear at fixed memory addresses. Reading and writing them looks like ordinary memory access in C, which is convenient, and treacherous, because registers do not behave like memory and the compiler assumes they do unless told otherwise.

4.1A register is an address with side effects

A peripheral such as SPI1 occupies a small block of the peripheral address region, say 1 KB starting at 0x4001_3000. Inside it each 32-bit word is a register: a control register that turns the peripheral on and selects its mode, a status register whose bits report "transmit buffer empty" or "receive buffer not empty", a data register through which bytes go in and out. Writing to the data register does not store a value somewhere; it starts a transfer. Reading it does not return what was last written; it returns the byte that just arrived, and on many peripherals the read itself clears the "data available" flag. Some status bits are cleared by writing a 1 to them ("write 1 to clear", W1C) and are unaffected by writing 0, so that software can clear exactly one flag without touching the others. Some bits change on their own, at any moment, because hardware sets them.

So a register read is an event, not a lookup, and the compiler must perform every read and every write that the source code asks for, exactly once, in source order, with the access width the hardware expects. None of that is what a C compiler does for ordinary variables. For ordinary variables it may keep a value in a CPU register instead of reloading it, combine two writes into one, delete a write that is overwritten later, or move a read out of a loop. All of those are legal optimisations for memory and all of them break hardware access.

4.2What volatile does, and what it does not

volatile tells the compiler that an object can change, or be observed, by something outside the program. For every access to a volatile object in the source, the compiler must emit an access in the generated code, and it must not reorder volatile accesses relative to each other. That is exactly the guarantee registers need. The difference is easy to see in the generated code. Here are two loops that wait for the SPI receive flag, compiled with GCC for Cortex-M7 at -O2, the first through a pointer without volatile:

#define SPI1_SR_PLAIN (*(uint32_t *)0x40013008u)            /* wrong: not volatile */
#define SPI1_SR       (*(volatile uint32_t *)0x40013008u)

void wait_rx_plain(void) { while (!(SPI1_SR_PLAIN & SR_RXNE)) { } }
void wait_rx(void)       { while (!(SPI1_SR & SR_RXNE)) { } }

/* arm-none-eabi-gcc -mcpu=cortex-m7 -O2:
   wait_rx_plain:  ldr r3, =0x40013000      wait_rx:  ldr r2, =0x40013000
                   ldr r3, [r3, #8]   ; once         1: ldr r3, [r2, #8]   ; every time
                   lsls r3, r3, #31                    lsls r3, r3, #31
                   bmi done                            bpl 1b
               1:  b 1b               ; forever        bx lr
               done: bx lr                                                     */

Without volatile the compiler reads the status register once; if the flag is not set at that moment, it branches into an infinite loop that never reads the register again. That is not a compiler bug: nothing in the program can change an ordinary uint32_t while the loop runs, so re-reading it would be pointless. With volatile the load is inside the loop. The same thing happens with a flag variable that an interrupt handler sets and main polls: the demo's wait_flag_plain compiles to one load followed by b ., the classic "works in debug, hangs in release" bug.

What volatile does not do is just as important, and more often misunderstood. It does not make an operation atomic: counter++ on a volatile variable is still a load, an add and a store, and an interrupt between the load and the store loses an update (Section 4.3 and 5.5). It does not order ordinary, non-volatile accesses around the volatile one, so the compiler may still move a write to a normal buffer past a volatile write that starts a DMA transfer; that needs a compiler barrier or the buffer itself being accessed through volatile or through proper synchronisation. And it does not emit any hardware barrier instruction, so on a core with a write buffer or a cache, a volatile store is not guaranteed to have reached the peripheral when the next instruction executes (Section 4.5). In multi-threaded code on an operating system, volatile is the wrong tool altogether; atomics are the right one (Concurrency 2.3). On a single-core microcontroller it remains the correct tool for registers and for simple flags shared with interrupts, as long as every access is a single aligned load or store.

Talk track

"Volatile means: every access in the source is an access in the binary, in order. That is what memory-mapped registers need, because reads and writes have side effects. It does not mean atomic, it does not order the non-volatile accesses around it, and it does not insert memory barriers; for those you use critical sections, atomics and DSB or DMB."

4.3Register access patterns

Writing *(volatile uint32_t *)0x40013008u everywhere is unreadable. The standard approach, used by Arm's CMSIS headers and by every vendor's device header, is to describe each peripheral as a struct of volatile members laid out exactly like its registers, and to define a pointer constant to the peripheral's base address:

typedef struct {
  volatile uint32_t CR1;     /* 0x00 control 1 */
  volatile uint32_t CR2;     /* 0x04 control 2 */
  volatile uint32_t SR;      /* 0x08 status */
  volatile uint32_t DR;      /* 0x0C data */
  /* ... */
} SPI_TypeDef;
#define SPI1 ((SPI_TypeDef *)0x40013000u)

while (!(SPI1->SR & SPI_SR_TXE)) { }    /* wait until the transmit buffer is empty */
SPI1->DR = 0x80u | IMU_REG_GYRO_X;      /* send "read register" command */

The offsets in the comments are the documentation; the struct layout must match them exactly, which works because all members are naturally aligned 32-bit words and C does not insert padding between them. Reserved gaps are filled with explicit uint32_t RESERVED[n] members.

The most important pattern to understand is read-modify-write. To set one bit in a register without disturbing the others, C code writes GPIOA->ODR |= 1u << 5;, and the compiler generates three instructions: load the register, OR in the bit, store the result. If an interrupt arrives between the load and the store, and its handler modifies another bit of the same register, the main code's store writes back its stale copy and undoes the handler's change. This is the classic embedded race, and it cannot be fixed by volatile.

Hardware designers know this, and many peripherals offer registers that make the operation a single store. GPIO ports commonly have a bit set/reset register (BSRR on STM32 parts, PSOR and PCOR on NXP parts): writing a 1 to bit n sets output n, writing a 1 to bit n+16 clears it, and zeros are ignored. The compiler turns GPIOA->BSRR = 1u << 5; into a single str, which cannot be torn. W1C status bits follow the same idea for flags. Cortex-M3 and M4 also have bit-banding, an alias region in which each word maps to one bit of SRAM or of a peripheral, so that a single store sets or clears one bit; it was dropped in the Cortex-M7 and Armv8-M, so do not design around it. Where none of these exist, the read-modify-write must run inside a critical section, or the register must be owned by exactly one context.

Pitfall

Read-modify-write on a register with W1C bits clears flags by accident. TIM2->SR |= SOME_ENABLE_BIT; reads the status register, in which several flags may be 1, and writes them all back as 1, which clears all of them. For W1C registers, write the single bit you mean: TIM2->SR = TIM_SR_UIF; (or, for "write 0 to clear" designs, ~TIM_SR_UIF). The reference manual says per bit which convention applies: rc_w1, rc_w0, rs and so on.

4.4Bit manipulation without surprises

Firmware manipulates bit fields constantly: a 3-bit prescaler at bits 5 to 3 of a control register, a 4-bit priority in the top half of a byte. The safe idiom is a mask and a shift, defined once and used everywhere: clear the field, then OR in the new value, shifted and masked.

#define SPI_CR1_BR_Pos   3u
#define SPI_CR1_BR_Msk   (0x7u << SPI_CR1_BR_Pos)          /* bits 5:3, baud-rate divider */

uint32_t cr1 = SPI1->CR1;                                  /* one read */
cr1 &= ~SPI_CR1_BR_Msk;                                    /* clear the field */
cr1 |= (div_code << SPI_CR1_BR_Pos) & SPI_CR1_BR_Msk;      /* insert, masked */
SPI1->CR1 = cr1;                                           /* one write */

Four rules keep this correct. Use unsigned constants (1u << 31): shifting a 1 into the sign bit of a signed int is undefined behaviour in C, and shifting by 32 or more is undefined for any type. Read the register once into a local, modify the local, write once, so the hardware sees one well-defined new value instead of an intermediate state. Mask the inserted value, so a too-large argument cannot spill into the neighbouring field. And do not use C bit-fields for registers: their layout and access width are implementation-defined, and a compiler may access a 32-bit register with a byte load, which some peripherals ignore or fault on. Vendor headers use masks for exactly these reasons, and MISRA C restricts bit-fields for the same ones (C++ 14, MISRA).

Interesting detail

Cortex-M3 and above have instructions that do field operations in one go: BFI inserts a bit field, UBFX extracts one, CLZ counts leading zeros, which is how an RTOS finds the highest-priority ready task in one instruction. GCC emits them from the mask-and-shift idiom; you rarely need intrinsics.

4.5Ordering and barriers on Cortex-M

Cortex-M cores up to the M4 are simple in-order pipelines, and Device memory accesses happen in program order, so for many years firmware got away without thinking about memory ordering. The Cortex-M7 has a six-stage dual-issue pipeline, a write buffer, caches and an AXI bus on which accesses to different slaves can complete in a different order. Three barrier instructions control what may be outstanding. DMB, data memory barrier, ensures that memory accesses before it are observed before those after it; it is what you need between filling a DMA descriptor in Normal memory and writing the register that starts the DMA. DSB, data synchronisation barrier, waits until all outstanding memory accesses have completed; it is what you need before WFI, after changing the MPU, and after the last register write in an interrupt handler that clears the interrupt source. ISB, instruction synchronisation barrier, flushes the pipeline so that following instructions are fetched again with any new settings in effect; it follows writes to CONTROL, VTOR, the MPU and CPACR.

The interrupt case is the one that bites. An interrupt handler clears the timer's update flag as its last action and returns. The store to the timer's status register is buffered on its way through the bus bridge to the slower peripheral bus. The core performs the exception return, the NVIC still sees the timer's request line asserted because the clear has not arrived yet, and the handler runs a second time, finding no flag set. The fix is either to clear the flag at the start of the handler, so the store has many cycles to land, or to follow the clear with __DSB(). The codegen experiment shows the only difference between the two versions is the one dsb sy before bx lr, and that is the whole cost.

Pitfall

Hand-written inline assembly for barriers or special registers is easy to get subtly wrong. A first version of the chapter's BASEPRI critical section declared its output operand as "=r"; GCC legally assigned the same register to the output (the old BASEPRI) and the input (the new level), so the code read BASEPRI into r3 and then wrote r3 back: no masking at all. The fix is the early-clobber constraint "=&r". Use the CMSIS intrinsics (__get_BASEPRI, __set_BASEPRI_MAX, __DSB) instead of writing your own.

Not in this chapter: the memory models of multi-core application processors and C++ atomics belong to Concurrency 2.1 and 3.2; what undefined behaviour lets the optimiser do is in C++ 3.

5Interrupts and the NVIC

Interrupts are how a microcontroller reacts to the world on time without spending its life asking. They are also the only source of concurrency in bare-metal firmware, so every data race, every timing problem and most stack overflows in a bare-metal system involve an interrupt.

5.1Three ways to wait for hardware

The IMU in the running example has a new sample every millisecond. The firmware can find out in three ways. It can poll: read the IMU's status, or the data-ready pin, in a loop. Polling is simple and has the lowest possible latency, but it burns the CPU and couples everything else in the loop to the polling rate. It can use an interrupt: the data-ready pin is wired to an external-interrupt line, and when the pin rises the hardware stops whatever the CPU is doing, runs a handler, and returns. The CPU is free between samples, and can even sleep. Or it can use DMA: once a transfer is started, a DMA controller moves the 16 bytes from the SPI data register to RAM without the CPU, and raises a single interrupt when all of them have arrived. Real firmware combines them: an interrupt on data-ready starts a DMA transfer, and an interrupt on DMA completion tells the main loop that a sample is ready. Polling survives for things that happen within a few microseconds of starting them, where interrupt overhead would cost more than the wait.

On Cortex-M all of this is organised by the NVIC, the nested vectored interrupt controller that sits next to the core. Each interrupt line from a peripheral has an enable bit, a pending bit, an active bit and a priority in the NVIC. A peripheral event sets the line's pending bit; if the line is enabled and its priority is higher than whatever is running, the core takes the interrupt. "Nested" means that a higher-priority interrupt can interrupt a lower-priority handler; "vectored" means each line has its own handler address in the vector table.

5.2Exception entry and exit in hardware

When the core takes an exception, the hardware does what a compiler-generated function prologue would otherwise do. It pushes eight registers onto the current stack: R0 to R3, R12, LR, the return address and xPSR. Those are exactly the registers that the Arm procedure call standard allows a C function to destroy, so a handler written as an ordinary C function automatically preserves everything else. In parallel with the stacking, the core fetches the handler's address from the vector table. It then switches to handler mode and the main stack, writes the exception number into IPSR, and puts a special value called EXC_RETURN into LR. When the handler finishes with an ordinary bx lr, the core recognises the magic value (it starts with 0xFFFFFF, an address where no code can be), unstacks the eight registers, and resumes the interrupted code. The low bits of EXC_RETURN record where to return to: 0xFFFF_FFF9 means thread mode on the main stack, 0xFFFF_FFFD thread mode on the process stack, 0xFFFF_FFF1 another handler. On cores with an FPU there are matching values with bit 4 clear (0xFFFF_FFE9 and so on) when the frame includes floating-point registers.

The demo firmware measures this. main records its SP, 0x2000_0FC0, and triggers the CAN interrupt in software. Inside the handler, SP is 40 bytes lower: 32 bytes for the hardware frame and 8 for the two registers the compiled handler itself pushes. The handler sees EXC_RETURN 0xFFFF_FFF9. Then main executes one floating-point instruction, which sets CONTROL.FPCA to say that floating-point state is live, and triggers the interrupt again. Now the handler's SP is 112 bytes lower, and EXC_RETURN is 0xFFFF_FFE9: the frame has grown from 8 to 26 words, 104 bytes, to make room for S0 to S15 and the FP status register. The FP part is reserved but, by default, not actually written on entry; the core only saves the FP registers if the handler itself executes a floating-point instruction. This "lazy stacking" keeps latency at 12 cycles for handlers that do not use the FPU, at the price of 72 bytes of reserved stack per nesting level.

Two optimisations make back-to-back interrupts cheap. Tail-chaining: if another interrupt is pending when a handler returns, the core skips the unstacking and restacking, because the stacked frame is already correct, and starts the next handler about 6 cycles later. Late arrival: if a higher-priority interrupt arrives while the core is still stacking for a lower one, the core finishes the same stacking and runs the higher-priority handler first; the lower one then tail-chains. The demo firmware shows tail-chaining directly: an interrupt of equal priority triggered inside the CAN handler runs right after it, with exactly the same SP as the CAN handler, because no new frame was stacked.

Numbers

Interrupt latency: 12 cycles on Cortex-M3, M4, M7 and M33; 15 on M0+, 16 on M0. Basic frame 32 bytes, with FP context 104 bytes, plus 4 bytes of alignment padding when SP was not 8-byte aligned (xPSR bit 9 records it). Tail-chain about 6 cycles. At 300 MHz, 12 cycles are 40 ns; flash wait states, bus contention and a handler that saves more registers add to it.

5.3Priorities, preemption and grouping

Every interrupt line and most system exceptions have a configurable priority, an 8-bit field of which a chip implements only the top few bits: 2 bits on Cortex-M0 and M0+ (four levels), commonly 3 or 4 bits on M3, M4 and M7 (eight or sixteen levels). The rule that confuses everyone once: a lower number means a more urgent interrupt. Priority 0 beats priority 0x40, which beats 0xA0. Reset, NMI and HardFault have fixed negative priorities (−3, −2, −1) and beat everything. A pending interrupt preempts the running code only if its priority is strictly higher than the current execution priority; equal priority waits, and among several pending interrupts of equal priority the lowest exception number goes first.

Armv7-M can split the priority field into a group priority, which decides preemption, and a subpriority, which only decides the order in which pending interrupts of the same group are served. The split is set once in the SCB's AIRCR register (NVIC_SetPriorityGrouping). Most projects, and most RTOS ports, use all bits as group priority, because subpriorities add a dimension that is rarely needed and easily misread.

The interactive figure shows what priorities do to latency. With B at higher priority arriving during A's body, B starts 12 cycles after its request, whatever A is doing: that is what nesting buys. Switch B to equal priority and the same request waits until A finishes and then tail-chains; with A running 60 cycles, B's latency becomes 58 cycles. The lesson generalises: the worst-case latency of an interrupt is its own entry time plus the longest handler of equal or higher priority plus the longest critical section that masks it. That is why the data-ready interrupt in the running example gets a higher priority than the CAN handler, and why every handler and every critical section must be short.

Pitfall

Priority values in the NVIC are left-aligned in the byte. On a part with 4 implemented bits, priority level 5 is the byte 0x50, not 0x05; writing 0x05 sets only unimplemented bits and leaves the priority at 0, the highest. The CMSIS function NVIC_SetPriority(irq, 5) does the shift for you; writing the IPR register directly does not. RTOS ports add a second trap: interrupts that call RTOS functions must have a numerically higher (less urgent) priority than the RTOS's configured maximum, or they corrupt its data structures.

5.4Rules for writing an interrupt handler

Interrupt handlers run on borrowed time. While one runs, every interrupt of equal or lower priority waits, and the main loop waits. So a handler does the minimum that must happen at interrupt time and hands the rest to the main loop or a task. In the running example, the data-ready handler clears the external-interrupt flag, pulls the IMU's chip select low and starts the DMA transfer; the DMA-complete handler releases chip select, notes that a sample is ready and returns. Converting, filtering and packing the CAN frame happen in main.

From that principle follow the usual rules. Clear the interrupt source early, or the handler re-enters (Section 4.5), and clear only the flags you handle. Never block: no waiting for a UART to send a log line, no waiting on a flag another interrupt will set (if that interrupt has lower priority it can never run). Keep floating-point out of handlers on cores with lazy stacking, unless you have budgeted for the 72 extra bytes and the extra cycles. Do not call functions that are not reentrant, such as most printf implementations or malloc. Make everything that is shared with the main loop either volatile and accessed atomically or protected by a critical section. And measure the handler's execution time on the target: a handler that is fine at 1 kHz may break a 20 kHz motor-control loop that shares its priority.

static volatile uint32_t samples_ready;               /* written by the ISR, read by main */
__attribute__((aligned(32))) static uint8_t imu_rx[32];  /* one cache line, see Section 7.3 */

void DmaDone_IRQHandler(void)                         /* DMA stream for SPI1 RX finished */
{
  DMA2->LIFCR = DMA_LIFCR_CTCIF0;                     /* clear transfer-complete flag first (W1C) */
  GPIOA->BSRR = IMU_CS_PIN;                           /* chip select high: burst finished */
  samples_ready++;                                    /* single writer: one load, add, store */
  __DSB();                                            /* the clear must land before exception return */
}
Why it matters

In AUTOSAR terms, the handlers in this section are "category 1" ISRs: they do not call operating-system services and are invisible to the OS. Category 2 ISRs are wrapped by the OS and may activate tasks or set events (AUTOSAR 5.1). The rules above apply to both.

5.5Critical sections and sharing data with interrupts

The moment main and a handler share data that is bigger than one aligned word, or that is updated by a read-modify-write, there is a race. The demo firmware shows the textbook case. A 64-bit tick counter is kept as two 32-bit words, incremented by the SysTick handler: the low word, and the high word when the low one wraps. main reads the high word, then the low word. The demo starts the counter at 0x0000_0000_FFFF_FFFF and forces the SysTick interrupt to land exactly between the two reads. The naive read returns high 0 and low 0, so time appears to jump backwards by 232 ticks. In a real system the window is a few nanoseconds once every 232 ticks, which is why such bugs survive testing and show up after 49.7 days of uptime at 1 kHz.

There are three ways out, each with a cost. The first is a critical section that masks interrupts around the access. On Cortex-M the simplest is PRIMASK: cpsid i masks every interrupt with configurable priority, cpsie i or restoring the saved value unmasks them. It is one instruction each way, but it also delays the most urgent interrupts in the system. The more precise tool on Armv7-M and Armv8-M Mainline is BASEPRI: writing a priority value masks only interrupts of that priority or lower urgency, so a motor-control interrupt at priority 0x10 keeps running while the code protects data shared with handlers at 0x40 and below. RTOS kernels on Cortex-M3 and up use BASEPRI for exactly this reason. Either way the critical section must save and restore the previous state, not unconditionally re-enable, so that it can nest.

uint64_t ticks_read(void)
{
  uint32_t primask = __get_PRIMASK();      /* remember whether interrupts were already masked */
  __disable_irq();                         /* cpsid i */
  uint64_t t = ((uint64_t)ticks_hi << 32) | ticks_lo;
  __set_PRIMASK(primask);                  /* restore, do not blindly enable */
  return t;
}

uint64_t ticks_read_lockfree(void)         /* no masking: retry if the high word changed */
{
  uint32_t hi, lo;
  do { hi = ticks_hi; lo = ticks_lo; } while (hi != ticks_hi);
  return ((uint64_t)hi << 32) | lo;
}

The second way avoids masking by detecting the race and retrying: read the high word, the low word, and the high word again, and repeat if the high word changed. The demo firmware's version of this returns 0x0000_0001_0000_0000 after two tries, the correct value. It works because only one side writes and because the writer cannot be interrupted by the reader. The third way is a data structure designed for one producer and one consumer: a single-producer, single-consumer ring buffer where the handler only writes the head index and main only writes the tail index. Each index is one aligned word, written by exactly one side, so no locking is needed; the theory, and the memory-ordering details that matter on multi-core processors, are in Concurrency 5.2. On a single Cortex-M core, making the indices volatile and writing the data before publishing the index is enough, with a __DMB() before the index update if the buffer is in cacheable memory read by DMA.

Cortex-M3 and above also have exclusive-access instructions, LDREX and STREX, on which C11 atomics are built: a load marks the address, and the store succeeds only if nothing has interfered since, otherwise the code retries. Any exception entry or return clears the mark, so an interrupt between the two forces a retry. That makes atomic_fetch_add safe against interrupts without masking them. Cortex-M0 and M0+ have no exclusive instructions; on them atomic operations bigger than a single load or store are implemented by briefly masking interrupts.

Pitfall

Disabling interrupts in a function and re-enabling them at its end breaks the moment that function is called from inside another critical section: it re-enables interrupts in the middle of its caller's protected region. Always save and restore PRIMASK or BASEPRI. And never hold a critical section across anything slow, such as a flash erase or a blocking UART write; you have just added its duration to the latency of every masked interrupt.

Talk track

"If main and an ISR share data, I ask three things: is the access a single aligned load or store, is there one writer, and how much latency can I add? One writer and word-sized means volatile is enough. Multi-word data with one writer can use a retry loop or an SPSC ring buffer. Otherwise a short critical section, preferably BASEPRI so the urgent interrupts keep running, always saving and restoring the previous mask."

5.6The main loop: superloop, time-triggered or RTOS

With interrupts handling the urgent part, the rest of the firmware is organised in one of three ways. The superloop is a for (;;) in main that checks flags set by interrupts and does the corresponding work, and then sleeps with WFI until the next interrupt. It is easy to understand and has no overhead, but its worst-case response time is the sum of everything in the loop, and adding a slow job, such as writing to EEPROM, delays every other job. The time-triggered scheduler improves this: a timer interrupt every millisecond advances a tick, and a table says which job runs in which tick, so the timing of each job is designed rather than emergent. And an RTOS gives each activity its own task with its own stack and priority, and preempts between them, at the cost of RAM for each stack and a few microseconds per context switch (Embedded compute 7, and for OSEK and AUTOSAR OS AUTOSAR 5.1).

The running example is a superloop, and Figure 5.3 shows why that is enough: per millisecond the CPU works for tens of microseconds and sleeps for the rest. The structure is the same in every superloop: check the flags that interrupts set, take the data under a short critical section or from a ring buffer, process it, feed the watchdog if every job has checked in (Section 9.1), and sleep.

int main(void)
{
  clocks_init(); gpio_init(); imu_spi_dma_init(); can_init(500000); wdg_init(100 /* ms */);
  NVIC_SetPriority(EXTI0_IRQn, 2);  NVIC_EnableIRQ(EXTI0_IRQn);     /* data-ready: most urgent */
  NVIC_SetPriority(DMA2_S0_IRQn, 2); NVIC_EnableIRQ(DMA2_S0_IRQn);
  NVIC_SetPriority(CAN1_TX_IRQn, 5); NVIC_EnableIRQ(CAN1_TX_IRQn);

  uint32_t seen = 0;
  for (;;) {
    if (samples_ready != seen) {                    /* new burst in imu_rx */
      seen = samples_ready;
      SCB_InvalidateDCache_by_Addr(imu_rx, sizeof imu_rx);   /* see Section 7.3 */
      app_step(imu_rx, &filter, seen % 10 == 0);    /* convert, filter, maybe send CAN */
      wdg_checkin(JOB_IMU);
    }
    wdg_service();                                  /* kicks only if all jobs checked in */
    __DSB(); __WFI();                               /* sleep until the next interrupt */
  }
}
Interesting detail

The sleep at the end of the loop has a race: if an interrupt sets the flag after the check but before WFI, the core sleeps with work pending until the next interrupt. In the running example that costs at most one millisecond, which is acceptable. When it is not, mask interrupts with PRIMASK before the check and execute WFI with them masked: a pending interrupt still wakes the core even when PRIMASK masks it, and the handler runs as soon as the loop unmasks.

Not in this chapter: interrupts from the operating system's point of view (top and bottom halves, threaded handlers) are in Linux 6.1; priority ceiling and OS resources in AUTOSAR OS are in AUTOSAR 5.2.

6Peripheral drivers

A peripheral is a small piece of dedicated hardware that does one job, such as shifting bits out of a pin at a given rate, without the CPU. A driver is the code that configures it, feeds it and reacts to its events. The peripherals differ, but the pattern is always the same, and once you know it, a new reference manual chapter reads much faster.

6.1What every peripheral has in common

Before a peripheral can do anything, five things must be in place. Its clock must be enabled in the reset-and-clock controller, because peripheral clocks are off after reset to save power; register writes to an unclocked peripheral are ignored, and on some parts they cause a bus fault. Its pins must be routed to it: almost every pin can serve several functions, and a pin multiplexer selects GPIO, SPI clock, CAN transmit or something else. It must be configured through its control registers while it is disabled, and then enabled. Its interrupt must be enabled in two places, in the peripheral (which events raise a request) and in the NVIC (whether the request reaches the core). And if it moves data with DMA, a DMA channel must be connected to its request line. A surprising share of "the peripheral does nothing" bugs are one of these five steps missing.

Drivers come in layers. At the bottom is direct register access through the device header. Vendors provide a low-level layer of thin inline functions over the registers and a hardware abstraction layer (HAL) with functions like "transmit this buffer over SPI with DMA and call me back". In AUTOSAR Classic the same role is played by the microcontroller abstraction layer, MCAL, whose SPI, CAN and ADC drivers have standardised interfaces (AUTOSAR 6.2). The higher layers save time and make code portable across a vendor's family; the lower layers are what you read when the higher ones misbehave, and what you write when every microsecond counts. The professional expectation is that you can work at both levels and know what the HAL is doing underneath.

6.2GPIO and external interrupts

A general-purpose I/O pin can be an input, an output, an analogue pin or an alternate function. As an output it is either push-pull, driving actively high and low, or open-drain, only pulling low and relying on a pull-up resistor to go high, which is what shared lines like I2C and wired-OR interrupt lines need. Inputs have optional internal pull-up or pull-down resistors so that an unconnected pin does not float. Output speed settings choose how fast the driver switches: faster edges are needed for a 50 MHz SPI clock, slower ones reduce electromagnetic emissions everywhere else, which in automotive designs is not a detail but an approval criterion.

The IMU's data-ready output goes to a GPIO input that is also connected to an external-interrupt controller (EXTI on STM32 parts), which can raise an interrupt on a rising edge, a falling edge or both. The configuration is the five steps from Section 6.1 in miniature: enable the GPIO clock, set the pin to input with a pull-down, route the pin to an EXTI line, choose the rising edge, unmask the line and enable its NVIC interrupt. In the handler the first action is to clear the EXTI pending bit, which is write-1-to-clear. Edge-triggered inputs have one classic trap: if the edge comes while the interrupt is masked or the pending bit is being cleared, it may be missed, and with a level-oriented source like data-ready the sensor never produces another edge. Robust drivers therefore check the pin level after enabling the interrupt and at the end of the handler.

6.3Timers and PWM

A hardware timer is a counter clocked from a prescaled peripheral clock. The prescaler divides the input clock, the counter counts up to an auto-reload value and wraps, and every wrap can raise an update interrupt or trigger another peripheral, for example start an ADC conversion. That alone gives periodic interrupts with no drift, because the hardware reloads without software latency. Each timer also has several capture/compare channels. In compare mode a channel drives an output pin depending on whether the counter is below or above a compare value, which is pulse-width modulation: the period is set by the reload value, the duty cycle by the compare value. In capture mode a channel latches the counter value when an input edge arrives, which measures pulse widths and frequencies, for example of a wheel-speed sensor, to the timer's resolution.

PWM has a built-in trade-off between frequency and resolution, because the duty cycle can only change in steps of one count. With a 200 MHz timer clock, a 20 kHz PWM, above the audible range for motor drives, has 10,000 counts per period, about 13.3 bits of duty resolution; at 100 kHz it has 2,000 counts, 11 bits; at 1 MHz only 200, under 8 bits. Advanced timers add complementary outputs with dead time for half-bridges, so that the high-side and low-side transistors are never on at the same time, and a hardware break input that forces outputs into a safe state within nanoseconds of a fault signal, without waiting for software.

In practice

Write compare values through the preload (shadow) registers that take effect at the next update event, not directly. Otherwise a new duty cycle written in the middle of a period can produce one glitch pulse that is too long or too short, which in a motor drive is a current spike.

6.4The ADC

Most microcontroller analogue-to-digital converters are successive-approximation (SAR) converters with 10 to 16 bits. A conversion has two phases. In the sampling phase a small capacitor inside the ADC, a few picofarads, is connected to the pin and charges towards the input voltage through the source's impedance and the ADC's own switch resistance. In the conversion phase the capacitor is disconnected and the converter finds the digital value bit by bit. The sampling time is the part firmware chooses, and choosing it too short is the most common ADC error: the capacitor has not settled, and the result depends on what was converted before. For a 12-bit result accurate to a quarter of a least significant bit, the capacitor must settle to within 2−14, about nine time constants. With 5 pF and 1 kΩ of internal resistance that is about 100 ns from a 1 kΩ source, 0.5 µs from 10 kΩ and 2.5 µs from 50 kΩ, which is why voltage dividers that measure the battery are often buffered or given a capacitor at the pin.

The running example uses one ADC channel to monitor its own supply, triggered by a timer every millisecond, with results moved by DMA into a small buffer. That combination, timer trigger plus DMA, is the standard way to get equidistant samples without CPU jitter. Two more facts matter in practice. The result is relative to the reference voltage, so an ADC is only as accurate as its reference; and the effective number of bits after noise is usually one or two less than the nominal resolution, which oversampling and averaging can partly recover.

6.5The UART

A universal asynchronous receiver-transmitter sends bytes over one wire per direction without a clock wire. The line idles high; a byte starts with a low start bit, carries eight data bits, least significant first, optionally a parity bit, and ends with one or two high stop bits (Figure 6.1, third tab). The receiver detects the falling edge of the start bit and then samples each bit in its middle, timing itself with a clock that runs 16 (or 8) times faster than the baud rate. Because there is no clock wire, both sides must agree on the baud rate, and the error between them accumulates over the frame. By the middle of the stop bit, 9.5 bit times after the start edge, the receiver's sampling point must still be inside the bit, which allows a combined error of about 5 % in theory and is usually budgeted as about 2 % per side.

The baud rate comes from dividing the peripheral clock. At 80 MHz with 16× oversampling, 115,200 baud needs a divider of 43.4; using 43 gives +0.94 % error. 921,600 baud needs 5.4; using 5 gives +8.5 %, which does not work, but 8× oversampling with a divider of 11 gives −1.4 %, which does. From a 16 MHz clock, 115,200 baud with 16× oversampling is −3.6 % off, too much for comfort. Many UARTs have fractional dividers that reduce these errors; the point is to compute the error for your clock rather than assume it. For receiving, the efficient pattern is DMA into a circular buffer plus the UART's idle-line interrupt, which fires when the line has been quiet for one frame time and tells the driver that a message has probably ended.

6.6SPI: reading the IMU

SPI, the serial peripheral interface, is the simplest fast serial bus: a master drives a clock (SCK), sends on MOSI, receives on MISO, and selects one slave at a time with a dedicated chip-select line per slave. There is no addressing, no acknowledgement and no defined protocol on top; every sensor defines its own command format. Two settings must match the slave: clock polarity (CPOL, whether SCK idles low or high) and clock phase (CPHA, whether data is sampled on the first or second clock edge), which together give modes 0 to 3. Getting the mode wrong typically gives data shifted by one bit, which looks like plausible but wrong numbers.

SPI is full duplex: every byte shifted out is a byte shifted in. To read sixteen bytes from the IMU, the master sends a command byte, here 0x80 to mark a read OR'ed with the first register address, and then sixteen dummy bytes, receiving the sensor's data during those. The burst is 17 bytes, 136 clock cycles, 13.6 µs at 10 MHz. A CPU could do it by polling: write a byte to the data register, wait for "receive not empty", read the byte, repeat. At 300 MHz that is cheap in absolute terms, but it is 13.6 µs of busy waiting a thousand times per second, and the code must not be interrupted in the middle or the chip select timing stretches. With DMA the driver sets up two DMA streams, one feeding the transmit register from a buffer of dummy bytes and one draining the receive register into imu_rx, lowers chip select, enables the SPI's DMA requests, and returns. The CPU is free until the receive stream's completion interrupt.

void imu_start_burst(void)                       /* called from the data-ready ISR */
{
  static const uint8_t tx[17] = { 0x80u | IMU_REG_GYRO_X };  /* command, then 16 dummy bytes */
  DMA2_Stream0->M0AR = (uint32_t)imu_rx;  DMA2_Stream0->NDTR = 17;   /* RX: SPI1->DR to RAM */
  DMA2_Stream3->M0AR = (uint32_t)tx;      DMA2_Stream3->NDTR = 17;   /* TX: RAM to SPI1->DR */
  GPIOA->BSRR = IMU_CS_PIN << 16;                /* chip select low (reset half of BSRR) */
  DMA2_Stream0->CR |= DMA_SxCR_EN;               /* enable RX first so no byte is missed */
  DMA2_Stream3->CR |= DMA_SxCR_EN;
  SPI1->CR2 |= SPI_CR2_RXDMAEN | SPI_CR2_TXDMAEN;  /* let SPI1 raise DMA requests */
}

Note the order: the receive stream is armed before the transmit stream, because the first received byte arrives eight clocks after the first transmitted one, and a receive stream that is not ready yet leads to an overrun. Note also that the receive buffer is 17 bytes, one more than the data, because the byte received during the command is garbage; the conversion code starts at imu_rx[1]. Getting this count wrong is exactly the bug the running example will crash on in Chapter 8.

6.7I2C

I2C uses two wires, clock SCL and data SDA, shared by all devices on the bus, each with a 7-bit address. Both lines are open-drain: devices only pull low, and pull-up resistors pull high. That is what makes the protocol possible. A receiver acknowledges a byte by pulling SDA low during a ninth clock; two masters that start at once arbitrate bit by bit, because whoever sends a 1 and reads back a 0 knows someone else is transmitting; and a slow slave can hold SCL low after a byte to make the master wait, which is called clock stretching. A register read is a sequence of start condition, address with write bit, register number, repeated start, address with read bit, data bytes, a final not-acknowledge and a stop condition (Figure 6.1, second tab).

Open-drain has a physical cost: the rising edges are RC curves formed by the pull-up and the bus capacitance, and the specification limits their rise time, 1,000 ns at 100 kHz, 300 ns at 400 kHz, 120 ns at 1 MHz, measured from 30 % to 70 %, which takes 0.85 RC. With 100 pF of bus capacitance, 400 kHz needs pull-ups of at most about 3.5 kΩ; the lower limit comes from the 3 mA a device must be able to sink, about 1 kΩ at 3.3 V. And I2C has one notorious failure mode. If the master resets in the middle of a read while a slave is sending a 0 bit, the slave keeps SDA low, waiting for clocks that never come, and the bus is stuck: no start condition can be generated. The standard recovery, which every robust driver implements at start-up, is to switch SCL to a GPIO, clock it up to nine times until the slave releases SDA, and then send a stop condition.

Pitfall

I2C drivers that wait for a flag without a timeout hang the whole firmware when a slave misbehaves or the bus is stuck. Every wait in a bus driver needs a bound and an error path, and the error path needs bus recovery; the watchdog is not a substitute.

6.8The CAN controller

The CAN controller is the most complex peripheral in the running example, because it implements a whole protocol in hardware: framing, bit stuffing, CRC, acknowledgement, arbitration, error counting and automatic retransmission. The bus side, differential signalling, the frame format and arbitration on the wire, is covered in Automotive networks 4.2 to 4.4; here we look at the controller from the firmware side.

To send, the driver finds an empty transmit mailbox, writes the identifier, the data length and the data bytes into its registers, and sets a transmit-request bit. The controller then waits for the bus to be idle, transmits, and if it loses arbitration or detects an error, retries on its own. When several mailboxes are full, the controller sends the one with the lowest identifier first, which is the same rule the bus applies between nodes; some controllers can be switched to send in FIFO order instead. That gives a subtle problem called priority inversion inside the node: if all mailboxes are occupied by low-priority frames waiting to win arbitration on a busy bus, a newly urgent frame has nowhere to go. Drivers handle it by reserving a mailbox for high-priority traffic or by aborting a low-priority transmission. CAN FD controllers replace mailboxes with a message RAM shared between the CPU and the controller, with descriptors for transmit buffers, receive FIFOs and filter lists.

Receiving is filtered in hardware. A node on a busy bus sees thousands of frames per second and needs a handful, so the controller compares each identifier against acceptance filters, either an identifier and a mask or a list of exact identifiers, and stores only matching frames in a receive FIFO, typically three deep per FIFO in classic controllers. If software does not read a FIFO in time, new frames are lost and an overrun flag is set. Configure filters so the CPU only sees frames it handles, and size the interrupt priority and the FIFO depth so that a burst of frames cannot overrun it.

Before any of this works, the bit timing must be set. The controller divides its clock by a prescaler into time quanta, and a bit consists of a synchronisation segment of one quantum and two programmable segments, before and after the sample point. At 80 MHz and 500 kbit/s, a prescaler of 10 gives 125 ns quanta, sixteen per bit, and a split of 1 + 13 + 2 puts the sample point at 87.5 %, a value recommended for automotive networks so that all nodes sample at the same position. The controller also counts errors. A transmit error counter above 127 makes the node error-passive, so it stops destroying other nodes' frames with error flags; above 255 it goes bus-off and stops transmitting entirely, until software requests recovery and the controller has seen 128 occurrences of 11 recessive bits. The driver must report bus-off to the application and decide how fast to recover, because a node that recovers immediately and fails again can disturb the bus repeatedly.

int can_send(volatile can_regs_t *can, uint32_t id, const uint8_t *d, uint8_t len)
{
  if (!(can->TSR & CAN_TSR_TME0)) return -1;        /* mailbox 0 busy (a load from the peripheral) */
  can->TDTR = len;                                   /* data length code */
  can->TDLR = d[0] | d[1] << 8 | d[2] << 16 | (uint32_t)d[3] << 24;   /* bytes 0..3 */
  can->TDHR = d[4] | d[5] << 8 | d[6] << 16 | (uint32_t)d[7] << 24;   /* bytes 4..7 */
  can->TIR  = (id << 21) | CAN_TIR_TXRQ;              /* standard 11-bit id; request transmission last */
  return 0;
}
Numbers

An 8-byte classic CAN frame with a standard identifier is 111 bits including the interframe space, up to 135 with worst-case stuffing: 222 to 270 µs at 500 kbit/s. Sending it at 100 Hz uses at most 2.7 % of a 500 kbit/s bus. Bus-off after the transmit error counter passes 255; recovery after 128 × 11 recessive bits, at least 2.8 ms at 500 kbit/s.

7DMA, caches and the MPU

A DMA controller is a second bus master that copies data without the CPU. On small cores that is pure gain. On a Cortex-M7 with a data cache it creates a problem: two masters that see memory differently. And the MPU, the tool that solves part of that problem, is also the tool for catching stack overflows and wild pointers.

7.1Why DMA

Without DMA every byte a peripheral produces must be read by the CPU, usually in an interrupt handler: for a UART at 1 Mbit/s that is 100,000 interrupts per second, each costing a few dozen cycles of entry and exit for one byte of work. With DMA the peripheral raises a DMA request instead of an interrupt for each byte, the DMA controller performs the bus transfer, decrements a counter and advances an address, and the CPU hears about it once, when the whole block is done, or twice if it asked for a half-transfer interrupt too. The CPU's time is not the only gain. DMA transfers start within a few bus cycles of the request regardless of what the CPU is doing, so they do not suffer from interrupt latency or from critical sections, which means fewer overruns at high data rates. And the CPU can sleep while data moves.

The cost is a second bus master competing for memory and buses, a more complicated driver, and a new class of bugs: buffers that are reused before the DMA has finished with them, transfer counts that do not match buffer sizes, and on cached cores, coherence. In the running example DMA is used for the SPI burst, the ADC samples and the debug UART output.

7.2Setting up a transfer

A DMA channel or stream is configured with a source address, a destination address, a number of data items, an item width (byte, half-word or word), whether each address increments after every item, the direction, the request line it listens to, and what to do at the end: stop, or start again from the beginning in circular mode. For the SPI receive stream of the running example the source is the SPI data register, fixed; the destination is imu_rx, incrementing; the width is one byte; the count is 17. A circular buffer with half-transfer and transfer-complete interrupts gives double buffering: while the DMA fills the second half, the CPU processes the first. Some controllers have a hardware double-buffer mode with two memory addresses that alternate.

The driver contract is that a buffer belongs to the DMA from the moment the transfer is enabled until the completion interrupt, and to the CPU otherwise. Most DMA bugs break that contract: the CPU reads a buffer before completion, writes the next transmit frame into a buffer the DMA is still reading, or a local variable on the stack is used as a DMA buffer and the function returns while the DMA is still writing into what is now somebody else's stack frame.

Pitfall

Never use a stack variable as a DMA buffer unless the function waits for completion before returning. The DMA does not know the function has returned; it will keep writing into stack memory now used by other functions' frames, which is one of the hardest crashes to trace because the corruption appears in unrelated code.

7.3The Cortex-M7 cache and the coherence problem

The Cortex-M7 has optional instruction and data caches, typically 16 KB each in microcontrollers, with 32-byte lines; the data cache is four-way set-associative and, for normal SRAM, write-back with write-allocate. They exist because the core runs much faster than flash and the bus-attached SRAM. The data cache sits between the core and the bus. The DMA controller sits on the bus and talks to SRAM directly. So there are two views of a buffer, the cache's and the SRAM's, and nothing keeps them in sync: unlike application processors with a coherent interconnect, a Cortex-M7 microcontroller does not snoop DMA traffic.

For data the DMA writes and the CPU reads, the fix is to invalidate the buffer's cache lines after the DMA has finished and before the CPU reads: the next access misses and fetches from SRAM. For data the CPU writes and the DMA reads, the fix is to clean the lines, writing dirty data back to SRAM, before starting the DMA. CMSIS provides SCB_InvalidateDCache_by_Addr and SCB_CleanDCache_by_Addr, which operate on all lines that overlap the address range, followed internally by the barriers that make the operation complete. Many drivers also invalidate before starting a receive DMA, so that no dirty line can be evicted into the buffer while the DMA is writing it.

The trap is that maintenance works on whole lines. If a 17-byte receive buffer shares its 32-byte line with another variable that the CPU has just modified, invalidating the line discards that variable's new value, which only lived in the cache. Cleaning instead would write the CPU's old copy of the buffer bytes over what the DMA wrote. Neither is correct; the only correct layout gives each DMA buffer whole lines of its own: aligned to 32 bytes and with its size rounded up to a multiple of 32. That is why the running example declares __attribute__((aligned(32))) uint8_t imu_rx[32]; for a 17-byte burst, and why the linker script aligns the .dma section.

7.4Three ways to stay coherent

Cache maintenance is the first way, and the most efficient for large buffers, but every driver must get it right on every path. The second way is to make DMA buffers non-cacheable: use the MPU to give the .dma section the attribute "Normal memory, non-cacheable". The CPU then reads and writes those buffers directly in SRAM, coherence is automatic, and the cost is slower CPU access to that small region, which is usually negligible for buffers that are touched once per transfer. Many teams choose this as the default because it removes a whole class of bugs. The third way is to put buffers in memory the cache does not cover: TCM is never cached, so if the DMA controller can reach the DTCM, buffers there are coherent by construction. Whether it can is chip-specific; on some devices only certain DMA engines have a path to DTCM. Write-through caching, a fourth option, only solves the transmit direction.

Talk track

"On a Cortex-M7 the D-cache and DMA are not coherent. For receive I invalidate after the transfer, for transmit I clean before it, and every DMA buffer is 32-byte aligned and a multiple of 32 bytes long, because maintenance is per line. Often simpler: put DMA buffers in an MPU region marked non-cacheable, or in TCM if the DMA can reach it. 7.5The MPU

The memory protection unit checks every memory access against a small number of regions, 8 or 16 on Armv7-M cores. Each region has a base address, a size, access permissions for privileged and unprivileged code, an execute-never bit, and memory attributes: whether it is Normal memory or Device memory, cacheable or not, shareable or not. An access that violates its region's permissions raises a MemManage fault before it happens. There is no address translation; the MPU only answers "may this access proceed, and with which attributes". Where regions overlap, the region with the higher number wins, which is used to cut holes: region 2 covers all of SRAM as read-write, and region 7 makes the bottom 256 bytes of the stack no-access. A background setting, PRIVDEFENA, lets privileged code use the default memory map wherever no region matches, so the MPU only has to describe the exceptions.

A bare-metal system uses the MPU for three things. It sets memory attributes, as in the previous section: non-cacheable DMA buffers, and Device attributes for memory-mapped regions the default map would treat as Normal. It catches bugs early: an execute-never attribute on RAM stops a corrupted function pointer from executing data; a no-access region at address 0 traps null-pointer dereferences on parts where flash is not at 0; a no-access guard below the stack turns a silent stack overflow into an immediate fault. And with an RTOS it isolates tasks: each task runs unprivileged with regions that allow only its own stack and data, which is the basis of freedom from interference in safety systems (Functional safety 6.2).

static void mpu_guard(void)                      /* Armv7-M PMSA: region 7 = stack guard */
{
  MPU->RNR  = 7;
  MPU->RBAR = (uint32_t)&_sstack;                /* base aligned to the region size */
  MPU->RASR = (0u << MPU_RASR_AP_Pos)            /* AP = 000: no access, even privileged */
            | MPU_RASR_XN_Msk                    /* never execute */
            | ((8u - 1u) << MPU_RASR_SIZE_Pos)   /* SIZE field n means 2^(n+1) bytes: 256 B */
            | MPU_RASR_ENABLE_Msk;
  MPU->CTRL = MPU_CTRL_PRIVDEFENA_Msk | MPU_CTRL_ENABLE_Msk;   /* default map for privileged code */
  __DSB(); __ISB();                              /* new settings apply from the next instruction */
}

Armv7-M regions have awkward rules: the size is a power of two from 32 bytes, and the base must be aligned to the size, so a 96 KB buffer needs a 128 KB region or three regions, and eight subregion-disable bits help a little. Armv8-M replaced this with base and limit addresses at 32-byte granularity, but overlapping regions are no longer allowed: an address that matches two regions faults. Porting MPU code between the two is therefore a redesign, not a register rename.

Interesting detail

The guard region caught its own author. The demo firmware's first stack-measurement function scanned the stack from its lowest address upwards, looking for the paint pattern, and the first word it read was inside the no-access guard: a MemManage fault with MMFAR = 0x2000_0000, escalated to HardFault. The fix was to start scanning above the guard, but the lesson is general: once the MPU is on, every piece of code that walks memory, including debug helpers and memory tests, must respect it.

8When it breaks: faults and stack depth

When firmware does something the hardware refuses, the core raises a fault exception instead of continuing with garbage. There is no core dump and no error message, but there is something almost as good: the registers at the moment of the fault, stacked by hardware, and a set of status registers that say what went wrong. Reading them is a skill every embedded engineer is expected to have.

8.1The fault exceptions and how they escalate

Armv7-M has four fault exceptions. MemManage is raised by MPU violations and by attempts to execute from execute-never memory. BusFault is raised when the bus returns an error: an access to an address where nothing is mapped, to a peripheral whose clock is off, or a failed stacking. UsageFault covers instruction-level problems: an undefined instruction, an attempt to switch to Arm state (a branch to an even address), an invalid exception return, a coprocessor instruction while the FPU is disabled, and, if enabled, division by zero and unaligned accesses. HardFault is the catch-all. MemManage, BusFault and UsageFault are disabled after reset; while they are disabled, or if the fault happens at a priority where they cannot run, the fault escalates to HardFault. So in most firmware every fault arrives as a HardFault, and the real cause is recorded in the configurable fault status register.

The fault status registers are in the SCB. CFSR, at 0xE000_ED28, combines three byte-sized fields: the MemManage status in bits 7 to 0, the BusFault status in bits 15 to 8, and the UsageFault status in bits 31 to 16. MMFAR and BFAR hold the faulting data address when the corresponding "address valid" bit in CFSR is set. HFSR says why a HardFault happened: FORCED (bit 30) means escalation from a configurable fault, VECTTBL (bit 1) means the vector read itself failed. A fault inside the HardFault handler, or in NMI, cannot escalate further; the core enters lockup, stops executing, and most chips then reset.

BusFaults come in two kinds. A precise bus fault is reported by the instruction that caused it, so the stacked PC points at the guilty instruction and BFAR holds the address. An imprecise one arrives later, because a store went into the write buffer, the core carried on, and the bus error came back several instructions afterwards; the stacked PC is then somewhere after the culprit and BFAR is not valid. On Cortex-M3 and M4 an auxiliary control bit can disable the write buffer while debugging so that such faults become precise; on any core, making the region strongly-ordered with the MPU has a similar effect.

8.2A HardFault walkthrough

Here is the crash of the running example. A refactoring shortened the IMU receive buffer to twelve bytes, gyroscope and accelerometer only, because nobody used the temperature and the frame counter. The DMA count was not changed and still moves sixteen data bytes. The buffer sits in a driver state structure directly in front of the CAN driver's register pointer, so the four extra bytes land on that pointer. In the demo firmware a memcpy of the IMU burst stands in for the DMA transfer, and the result is a HardFault the moment the main loop tries to send the next CAN frame. The fault handler prints the stacked frame and the fault status registers; these are the real values.

The method is always the same. First, HFSR is 0x4000_0000, FORCED: a configurable fault was escalated, so look at CFSR. EXC_RETURN is 0xFFFF_FFF9, so the fault was in thread mode on the main stack, and the stacked xPSR has 0 in its exception-number field: not inside an interrupt handler. Second, CFSR is 0x0000_8200. The BusFault byte is 0x82: bit 9, PRECISERR, a precise data bus error, and bit 15, BFARVALID. BFAR is 0x3701_2A0C, an address where nothing exists. Third, the stacked PC is 0x0000_01F6; arm-none-eabi-addr2line -f -e fw.elf 0x1F6 answers can_send, app.c:54, and the disassembly at that address is ldr r0, [r0, #0], the read of the mailbox status register through the can pointer, which is in R0: 0x3701_2A0C. Fourth, the stacked LR is 0x0000_057B; clearing the Thumb bit gives 0x57A, the instruction after the call in main, at main.c:158, can_send(drv.can, 0x1A0, frame, 8). R1 holds 0x1A0 and R3 holds 8, matching the call, so the arguments arrived intact and drv.can itself was wrong.

The fifth step is the one that needs thinking. 0x3701_2A0C stored little-endian is the byte sequence 0C 2A 01 37. The IMU sends big-endian values, and its burst ends with the temperature 0x0C2A and the frame counter 0x0137: those are bytes 12 to 15 of the burst. Sixteen bytes were written into a twelve-byte buffer, and the last four replaced the pointer behind it. The fix is the buffer size, and the lasting fix is an assertion in the driver that the transfer count never exceeds the buffer it is given, ideally checked at compile time from sizeof.

Why it matters

This crash was easy because the fault was precise and the bad value was recognisable. That is not luck to hope for but something to design for: enable MemManage, BusFault and UsageFault so their handlers run instead of a generic HardFault, record the frame and the status registers in a .noinit crash record, and keep the ELF file with symbols for every released build, because a PC value is useless without it.

8.3Three more faults and what they look like

The demo firmware produces three more faults on purpose, each with a different signature. Knowing the signatures saves a lot of time.

A null callback. The DMA-complete handler calls a callback pointer that was never registered and is still zero. The result is a HardFault with CFSR 0x0002_0000, INVSTATE: the core was asked to execute at an address with bit 0 clear, which on Cortex-M means "switch to Arm state", which does not exist. The stacked PC is 0x0000_0000, which tells you the target was null but not who jumped there. Normally LR would, but here LR is 0xFFFF_FFF9: the compiler turned the call at the end of the handler into a tail call, a plain branch that leaves LR untouched, so LR still holds the handler's EXC_RETURN. The stacked xPSR answers the question instead: its low byte is 0x26, exception 38, IRQ 22, the DMA handler. And EXC_RETURN in the fault handler is 0xFFFF_FFF1: the fault happened in handler mode.

Division by zero. Integer division by zero on Cortex-M3 and above returns 0 by default, without any fault, which hides bugs. Setting CCR.DIV_0_TRP makes it a UsageFault; with UsageFault enabled in SHCSR, its own handler runs, HFSR stays 0, and CFSR is 0x0200_0000, DIVBYZERO, with the stacked PC exactly on the udiv instruction. Enabling this trap, and the unaligned-access trap where code should not need unaligned accesses, during development is cheap insurance.

Stack overflow into the guard. A recursive function using 48 bytes per call is called 200 levels deep with a 4 KB stack. When SP enters the MPU guard, the next push faults: CFSR is 0x0000_0092, DACCVIOL and MMARVALID, with MMFAR 0x2000_00F0 inside the guard, plus MSTKERR. That last bit says that the hardware's own stacking of the fault frame also hit the guard, and it has a consequence that surprises people: the stacked frame the handler reads is not a frame at all. Every "register" in it reads 0xC5C5_C5C5, the stack paint pattern, because the stacking writes were blocked. When MSTKERR or STKERR is set, ignore the frame and trust the status registers. The handler could run at all only because the MPU was configured with HFNMIENA clear, which disables the MPU while HardFault runs, so the handler could use the stack memory inside the guard. A more robust design runs thread code on the process stack, so that handlers always have a separate, healthy main stack.

8.4Writing a fault handler that helps

A useful fault handler does four things: finds the stacked frame, captures it together with the status registers, stores the capture where it survives a reset, and resets. Finding the frame needs a few instructions of assembly, because the frame is on whichever stack was active, and bit 2 of EXC_RETURN in LR says which. A naked function, one without a compiler-generated prologue that would move SP, tests the bit, puts the right stack pointer into R0 as the first argument and branches to a C function.

typedef struct { uint32_t r0, r1, r2, r3, r12, lr, pc, xpsr; } frame_t;
__attribute__((section(".noinit"))) struct crash_rec crash;   /* survives the reset below */

__attribute__((naked)) void HardFault_Handler(void)
{
  __asm volatile(
    "tst lr, #4      \n"     /* EXC_RETURN bit 2: 0 = frame on MSP, 1 = on PSP */
    "ite eq          \n"
    "mrseq r0, msp   \n"
    "mrsne r0, psp   \n"
    "mov r1, lr      \n"     /* pass EXC_RETURN as the second argument */
    "b fault_c       \n");
}

void fault_c(const frame_t *f, uint32_t exc_return)
{
  crash.magic = 0xDEADFA17u;  crash.exc_return = exc_return;  crash.frame = *f;
  crash.cfsr = SCB->CFSR;  crash.hfsr = SCB->HFSR;  crash.mmfar = SCB->MMFAR;  crash.bfar = SCB->BFAR;
  NVIC_SystemReset();                     /* next boot finds crash.magic and reports the record */
}

In development the handler can also halt with a breakpoint instruction if a debugger is attached (the DHCSR register says whether one is). In production it typically stores the record, maybe raises a diagnostic trouble code on the next boot, and resets, because a controlled reset is the safe state for most ECUs. A frame copied from a stack that failed stacking is still copied; the status registers tell later analysis whether to trust it. The diagnostic side, how crash records are read out in the field, is in Production integration 11.4.

8.5Worst-case stack depth

A stack overflow on a microcontroller does not produce an error unless something makes it: no guard page, no operating system. The stack simply grows into whatever lies below it. The two defences are to size the stack correctly and to detect overflow when sizing fails. Sizing means computing the worst-case stack depth, which, unlike the heap, can be done precisely, provided the program has no recursion and no calls through function pointers that analysis cannot resolve.

GCC reports each function's own stack use with -fstack-usage, one line per function in a .su file, and with -fcallgraph-info=su it also writes the call graph. A short script then finds the deepest path. For the demo firmware it is Reset_Handler (8 bytes), main (40), app_step (40) and log_frame (96, mostly its 64-byte line buffer): 184 bytes. The same firmware paints its stack with 0xC5C5_C5C5 at startup and, after running the application loop, scans for the deepest overwritten word: 184 bytes. Static analysis and measurement agree, which is the expected outcome for code without recursion; when they disagree, the analysis has missed a path (an indirect call, an inline assembly block, a library function compiled without -fstack-usage) or the test never executed the deepest path.

Interrupts come on top. Each level of preemption adds a hardware frame, 32 bytes or 104 with an active FP context, up to 4 bytes of alignment padding, and the deepest stack use of the handler that preempted. Handlers of the same priority never nest, so the number of levels is the number of distinct preemption priorities in use, not the number of interrupts. With three levels and 40 bytes per handler the demo needs 412 bytes in total, 628 bytes if every level carries FP state; its 4 KB stack has room to spare. Commercial tools such as AbsInt StackAnalyzer compute the same from the binary, including library code, and are what safety projects use as evidence.

In practice

Combine three things: a computed worst case with a margin, a guard (MPU region or Armv8-M stack-limit register) that faults on overflow, and a high-water measurement from paint in long-running tests, reported in diagnostics. Each catches what the others miss: the computation misses paths it cannot see, the measurement misses paths the test did not run, and the guard turns whatever both missed into a clean fault instead of corruption.

Talk track

"For a HardFault I read HFSR, CFSR and BFAR or MMFAR first, then the stacked PC and LR from the frame that EXC_RETURN points to, and map them with addr2line. If a stacking error bit is set I don't trust the frame. For stack sizing, I compute the deepest call path from -fstack-usage, add one exception frame plus handler depth per preemption level, put a guard under the stack and measure the high-water mark with paint."

9Staying alive: watchdogs, power and bootloaders

Firmware in a car runs for fifteen years, through cold starts, cranking dips and electrical noise, and it must recover by itself from anything it cannot prevent. Watchdogs, brown-out detection, controlled low-power modes and a bootloader that can always reprogram the application are the mechanisms for that.

9.1Watchdogs

A watchdog is a hardware timer that resets the chip unless software restarts it ("kicks" or "feeds" it) before it expires. It turns a hang, an endless loop after a corrupted variable, a deadlock between two flags, a stuck bus driver, into a reset and a fresh start, which for most ECUs is a safe state. Microcontrollers usually have two. The independent watchdog runs from its own low-speed oscillator, around 32 kHz, so it keeps working even if the main clock fails, and once started it often cannot be stopped by software. The window watchdog runs from the peripheral clock and adds a lower bound: a kick that comes too early also resets the chip. That catches a failure mode the simple watchdog cannot, a program stuck in a fast loop that happens to contain the kick. With a 32 kHz clock and a prescaler of 32 the watchdog counts in milliseconds, so a reload value of 100 gives a 100 ms timeout; a window of 75 to 100 ms then means "kick between 75 and 100 ms after the last kick".

Where the kick happens decides what the watchdog actually proves. Kicking from a timer interrupt proves only that the timer interrupt runs, which it will happily do while the main loop is stuck. The usual design is a checkpoint scheme: each job sets its bit in a check-in word when it completes a cycle, and the main loop kicks the watchdog only when all bits are set, then clears them. Safety systems go further with an external watchdog chip, often part of the power-supply IC, that asks questions the software must answer correctly in a time window, so that a hung or confused microcontroller cannot keep its own watchdog happy (Functional safety 4.6 and Production integration 9.4).

static volatile uint32_t checkins;                 /* one bit per job */
#define ALL_JOBS (JOB_IMU | JOB_CAN | JOB_ADC)

void wdg_checkin(uint32_t job) { __disable_irq(); checkins |= job; __enable_irq(); }  /* RMW: protected */

void wdg_service(void)                             /* called from the main loop only */
{
  if ((checkins & ALL_JOBS) == ALL_JOBS) {
    IWDG->KR = 0xAAAAu;                            /* reload key: restart the countdown */
    checkins = 0;
  }
}

After a reset, firmware should read the reset-cause register and record why it restarted: power-on, brown-out, pin, software, independent or window watchdog, lockup. A watchdog reset that nobody counts is a bug that nobody fixes. Many ECUs keep a counter of consecutive watchdog resets in .noinit RAM and fall back to a limp-home mode or stay in the bootloader after several in a row, so that a firmware fault cannot turn into an endless reset loop.

9.2Brown-out and power supervision

A 12 V car battery drops to 6 V or less while the starter motor cranks, and the regulators behind it may let the microcontroller's 3.3 V supply sag. Below its specified minimum voltage a microcontroller does not stop cleanly; it starts to misbehave: flash reads return wrong bits, the PLL loses lock, logic gates switch too slowly for the clock. Running in that state is worse than not running. A brown-out detector compares the supply against a threshold, typically selectable in a few steps, and holds the chip in reset while the supply is below it, with some hysteresis so that it does not oscillate around the threshold. An earlier warning, a programmable voltage detector, can raise an interrupt above the reset threshold, which gives firmware a few hundred microseconds to finish a flash write or store a state.

Flash writes are where brown-out matters most. Erasing or programming a flash page takes milliseconds; if the supply fails in between, the page may be half-erased with unpredictable content. Robust non-volatile storage therefore never overwrites data in place: it writes a new copy with a sequence number and a checksum, and only then marks the old one invalid, so that a power loss at any moment leaves at least one valid copy. The power path itself, reverse-polarity protection, load dumps and supervisors, is in Automotive networks 12.3.

9.3Low-power modes

A parked car allows its ECUs on the order of 100 µA each in total, and some ECUs must still wake up on a CAN message or a door handle. Microcontrollers offer a ladder of modes that trade wake-up time for current. In sleep mode only the core clock stops; peripherals and DMA keep running, and any interrupt wakes the core within a few cycles. The WFI at the end of the running example's main loop enters this mode. In stop or deep-sleep modes (the names vary by vendor) most clocks and the PLL stop, the voltage regulator goes into a low-power state and RAM and registers are retained; current falls from milliamps to microamps or tens of microamps, wake-up takes microseconds, and the clock tree must be restored after waking because the core restarts on its internal oscillator. In standby or shutdown modes almost everything is switched off, RAM is lost except a small backup domain, current is around a microamp, and wake-up is essentially a reset.

The core's part is small: WFI waits for an interrupt, WFE for an event, the SLEEPDEEP bit in the System Control Register selects whether a vendor's deep mode is entered, and SLEEPONEXIT makes the core go back to sleep automatically after an interrupt handler, for firmware that does everything in interrupts. The hard part is the system: every peripheral must be put into a defined state before sleeping, the wake-up sources (a CAN transceiver's wake pin, an RTC alarm, a GPIO edge) must be configured and tested, and the current must be measured on real hardware, because one forgotten pull-up or a floating input can draw more than the whole microcontroller. Sleep and wake from the network's point of view, with partial networking, is in Automotive networks 12.4.

Pitfall

Debuggers keep the debug logic powered and may keep clocks running, so measured sleep current with a probe attached is meaningless, and some parts cannot be halted by a debugger while in deep sleep. Measure power without the probe, and give the firmware a way to stay awake for a few seconds after reset so that a debugger can still connect.

9.4Bootloaders and the jump to the application

A bootloader is a small program that starts first after reset and decides whether to run the application or to stay and accept a new one, typically over CAN with the UDS diagnostic protocol in automotive ECUs. It exists because the application can be broken: an interrupted update, a bug that crashes at start-up, a corrupted flash page. As long as the bootloader is intact and never erased by itself, the ECU can always be reprogrammed in the workshop without opening it. The flashing protocol and the sequence of checks belong to Production integration 5.1; here we look at what happens on the chip.

The bootloader and the application are two separate programs, linked separately, each with its own vector table, startup code and linker script. The application is linked to start at its own flash address, here 0x0000_8000 for a header and 0x0000_8100 for its vector table. At reset the core always runs the bootloader. If it decides to start the application, it first checks that the application is valid: a header with a magic number, a length and a CRC, and in a secure-boot system a signature. Then it undoes everything it changed: stops SysTick and any DMA, disables and clears all NVIC interrupts and pending bits, and returns the clocks to the state the application's startup code expects. Then it points VTOR at the application's vector table, loads MSP with the application's initial stack pointer, and branches to the application's reset handler.

#define APP_VECTORS 0x00008100u

__attribute__((noreturn)) void jump_to_app(void)
{
  const uint32_t *v = (const uint32_t *)APP_VECTORS;
  __disable_irq();
  SysTick->CTRL = 0;                                   /* stop the bootloader's tick */
  for (int i = 0; i < 8; i++) {                        /* all external interrupts off, none pending */
    NVIC->ICER[i] = 0xFFFFFFFFu;
    NVIC->ICPR[i] = 0xFFFFFFFFu;
  }
  SCB->VTOR = APP_VECTORS;                             /* the application's table from now on */
  __DSB(); __ISB();
  __set_MSP(v[0]);                                     /* the application's initial stack pointer */
  __enable_irq();                                      /* PRIMASK as after reset */
  ((void (*)(void))v[1])();                            /* its Reset_Handler; v[1] has the Thumb bit */
  for (;;) { }
}

Two constraints are easy to miss. VTOR has alignment requirements: the table must be aligned to its size rounded up to a power of two, at least 128 bytes, so a table with 150 vectors (600 bytes) must sit on a 1,024-byte boundary and 0x8100 would not do. And the application must not assume reset values that the bootloader changed, or the bootloader must restore them, which is why the most common bootloader bug is an application that works when flashed alone and crashes behind the bootloader. Larger systems keep two application slots, A and B, so that an update is written to the inactive slot and the bootloader switches only after the new image has been verified; that, and how the image is authenticated, is part of the secure boot chain (Production integration 5.2).

Talk track

"The bootloader is a separate program at the reset address that is never erased by itself. It validates the application by header and CRC or signature, and to start it, it de-initialises everything it used, disables and clears all interrupts, sets VTOR to the application's vector table, loads MSP from the table's first word and jumps to the second. Most hand-over bugs are leftover interrupts or clocks, or a VTOR alignment problem."

10Bytes on the wire: endianness, packing and wire formats

Firmware constantly turns values into bytes and back: sensor registers, CAN payloads, flash records, protocol frames. The layout of those bytes is defined by a datasheet or a communication specification, not by the compiler, and treating a C struct as if it were that layout is one of the most common sources of portable-looking, wrong code.

10.1Endianness

A 32-bit value occupies four bytes, and the processor must decide which of them goes at the lowest address. Little-endian machines put the least significant byte first, so 0x1234_5678 is stored as 78 56 34 12; big-endian machines put the most significant first, 12 34 56 78. Cortex-M parts are little-endian in practice (the architecture allows big-endian data, but vendors almost never implement it), as are x86 and most Arm application processors. Wire formats are a different matter. Internet protocols use big-endian "network byte order". Many sensors, including the running example's IMU, send their registers high byte first. CAN signals are defined in a database with either "Intel" (little-endian) or "Motorola" (big-endian) byte order, often both in one vehicle.

Endianness only matters at the boundary where bytes become values. Inside the program a uint32_t is just a number, and shifts and masks work on numbers, not on memory, so code that assembles a value from bytes with shifts is correct on any machine. Code that copies bytes into a uint32_t with memcpy or a pointer cast gets the machine's byte order, which is correct on one kind of machine and wrong on the other. The codegen experiment shows that portability costs nothing: GCC compiles the shift-based big-endian decode, (p[0] << 24) | (p[1] << 16) | (p[2] << 8) | p[3], to one load and one REV byte-swap instruction on Cortex-M7. On Cortex-M0+, which cannot load unaligned words, it becomes four byte loads and shifts, which is exactly what is needed there.

10.2Struct layout, padding and packed

C requires each member of a struct to be at an address that is a multiple of its alignment, so the compiler inserts padding. A struct of a uint8_t type, a uint32_t value and a uint16_t CRC is 12 bytes on Arm: one byte, three bytes of padding, four bytes, two bytes, and two more bytes of padding so that arrays of the struct stay aligned (C++ 4, alignment and padding). A wire format with the same fields is 7 bytes with no gaps. The tempting fix is __attribute__((packed)), which removes the padding so that the struct matches the wire format byte for byte, and then memcpy the received bytes into it.

Packed structs are legal and widely used, but they carry three costs. The compiler must assume that every member may be misaligned. On Cortex-M7 it reads the packed 32-bit member with a single unaligned load, which the core supports for Normal memory, and that is fast, but on Cortex-M0+ the same function becomes four byte loads, four shifts and three ORs, because any unaligned access faults there. Even on M7, unaligned accesses fault if they are multiple-word instructions (LDRD, LDM), if they target Device memory, or if the unaligned trap is enabled. Taking the address of a packed member and passing it as an ordinary uint32_t * loses the "may be unaligned" information, and the callee may use an instruction that faults. And a packed struct still has the machine's byte order, so it solves padding but not endianness.

10.3Serialising explicitly: the running example's CAN payload

The robust approach is to treat the wire format as a sequence of bytes and write explicit encode and decode functions with shifts, one per message. They state the layout in code, work on any processor and compiler, and the compiler turns them into efficient instructions. The running example's frame 0x1A0 carries the yaw rate as a signed 16-bit value in units of 0.01 deg/s in bytes 0 and 1, the longitudinal acceleration in units of 0.001 g in bytes 2 and 3, both Intel byte order, a 4-bit alive counter in byte 6 and a CRC-8 (SAE J1850 polynomial 0x1D) over bytes 0 to 6 in byte 7. The alive counter and CRC let the receiver detect lost, repeated or corrupted frames, the end-to-end protection that safety-relevant signals need.

void can_pack(const filter_t *f, uint8_t alive, uint8_t out[8])
{
  int16_t yaw = (int16_t)(f->yaw_rate_dps * 100.0f);   /* 0.01 deg/s per bit */
  int16_t ax  = (int16_t)(f->accel_x_g * 1000.0f);     /* 0.001 g per bit */
  out[0] = (uint8_t)yaw;  out[1] = (uint8_t)((uint16_t)yaw >> 8);   /* Intel: low byte first */
  out[2] = (uint8_t)ax;   out[3] = (uint8_t)((uint16_t)ax >> 8);
  out[4] = 0;             out[5] = 0;                               /* reserved */
  out[6] = alive & 0x0Fu;
  out[7] = crc8_j1850(out, 7);
}

Run in QEMU with a constant IMU sample (yaw rate 20 deg/s, acceleration 0.2 g) through the first-order filter, the tenth sample produces F9 06 B2 00 00 00 01 60. Decoding those bytes with a DBC description of the message, using the Python cantools package, gives a yaw rate of 17.85 deg/s, an acceleration of 0.178 g, alive counter 1 and CRC 0x60, which matches a CRC-8 computed independently over the first seven bytes. The filter value is right too: after ten steps with a coefficient of 0.2 the output has reached 1 − 0.810, 89.3 % of the input, 17.853 deg/s, truncated to 17.85 by the 0.01 resolution. Cross-checking hand-written packing against the vehicle's communication database like this, in a unit test on the host, catches byte-order and scaling mistakes before they reach a bench.

Pitfall

Converting a float to a signed integer is undefined behaviour in C if the value does not fit. A yaw rate of 400 deg/s times 100 does not fit into int16_t; real code must clamp to the signal's range first, and should send the signal's defined "invalid" value when the input is not trustworthy, rather than whatever the conversion produced.

11Debugging below the OS

There is no terminal, no log file and no debugger process to attach. Debugging firmware relies on hardware built into the chip for exactly that purpose, on output channels that cost as little time as possible, and on instruments that watch the pins from outside.

11.1The debug port: SWD, JTAG, breakpoints and watchpoints

Every Cortex-M has a debug access port that an external probe connects to, either over JTAG, the older four- or five-wire boundary-scan interface, or over Serial Wire Debug, which needs only two pins, a bidirectional data line SWDIO and a clock SWCLK, and is what most microcontroller boards use. Through it the probe reaches two things. A memory access port lets it read and write any address through the bus matrix, including RAM, flash and peripheral registers, while the core keeps running; that is how a debugger shows live variables and how flash programming works. And the core's debug logic lets it halt the core, single-step, and read and write the core registers.

Breakpoints in code running from flash cannot be made by writing a breakpoint instruction into the code, as on a PC, because flash cannot be rewritten one instruction at a time. The flash patch and breakpoint unit (FPB) compares instruction fetch addresses against a small number of comparators, typically 4 to 8 depending on the core and the vendor's configuration, and halts the core on a match. When they are used up, some debug probes erase and reprogram flash pages to insert software breakpoints, which is slow and wears the flash. The data watchpoint and trace unit (DWT) has 2 to 4 comparators for data addresses, which halt the core when a variable is written or read: the fastest way to find who corrupts a variable, such as the CAN pointer in Chapter 8. DWT also contains a 32-bit cycle counter, CYCCNT, which is the most precise clock in the system for measuring code.

In practice

Halting the core does not halt the hardware around it. While you sit at a breakpoint, the timers count on, the CAN controller keeps acknowledging frames and goes into error states when its transmit mailboxes do not empty, the watchdog expires and resets the chip, and a motor stays in whatever state its PWM was in. Most microcontrollers have debug-freeze bits that stop chosen timers and watchdogs while the core is halted; set them in development builds, and never single-step through code that drives power stages on real hardware.

11.2Getting text out: semihosting, ITM and RAM buffers

The simplest output channel is a UART connected to a terminal, as in the demo firmware. It costs a pin pair and, at 115,200 baud, about 87 µs per character unless DMA sends it, which changes the timing of the code being observed. Semihosting routes C library calls like printf and exit to the host through the debugger: the firmware executes a BKPT 0xAB instruction with an operation code in R0, the debugger notices the halt, performs the operation on the host and resumes the core. The demo firmware uses it to exit QEMU. It is convenient and needs no pins, but each call halts the core for milliseconds, and without a debugger attached the breakpoint instruction raises a HardFault, so a semihosting build that leaves the lab hangs or resets at its first log message.

The instrumentation trace macrocell (ITM) is the efficient alternative. Writing a byte or word to one of its 32 stimulus port registers produces a small trace packet, sent out of the single SWO pin by the trace port unit without stopping the core; the probe captures it and the host shows it as text or as data. A write takes a few cycles as long as the trace FIFO has room. The DWT can add timestamped data-trace and periodic PC samples to the same stream, which gives a statistical profile of where the CPU spends its time with no instrumentation at all. A third technique needs no trace pin: the firmware writes log data into a ring buffer in RAM, and the probe reads that buffer through the memory access port while the core runs, which several debug probe vendors offer as a fast logging channel. On larger devices an embedded trace macrocell (ETM) records every executed branch, giving a complete instruction history, at the price of a wider trace port and a more expensive probe (Production integration 11.3).

11.3Measuring time: cycle counter, GPIO toggles and the logic analyser

Timing questions, how long does the handler take, how much jitter does the data-ready interrupt see, does the SPI burst finish before the next sample, need measurements, not estimates. The cycle counter answers the first kind: enable trace in the debug exception and monitor control register, enable CYCCNT, read it before and after the code. At 300 MHz it wraps after 14.3 seconds, more than enough for code paths. The answer includes cache misses and flash wait states, which is the point; run the measurement many times and report the maximum, not the average.

For everything involving the outside world, the reliable tool is a GPIO pin toggled by the firmware and watched by an oscilloscope or a logic analyser. Setting a pin at the start of the data-ready handler and clearing it at the end makes the handler's duration and its jitter relative to the IMU's interrupt line directly visible, alongside the SPI signals and the CAN bus, on one time axis. A logic analyser samples many digital lines at once and decodes protocols: it shows SPI bytes, I2C addresses and acknowledgements, UART characters and CAN frames with their identifiers and error frames. The rule for sample rates is at least four, better ten, samples per shortest bit or pulse you want to see, so a 10 MHz SPI clock needs 40 to 100 MS/s. A logic analyser shows logic levels; when the question is whether the levels are clean, ringing, too slow or crossing the threshold twice, use an oscilloscope (Production integration 11.5).

Why it matters

Many bugs in the running example's class of product are visible only on the wires: chip select released one clock too early, an I2C slave stretching the clock longer than the driver's timeout, a CAN node sending error frames during cranking. Firmware that reports "SPI timeout" points at a symptom; a logic-analyser capture of the same moment usually shows the cause.

11.4A debugging workflow for the running example

Putting the tools together for the kinds of problems this chapter has described gives a short, reliable sequence. If the board does nothing at all, connect the debugger and halt: is the PC in the reset handler, in Default_Handler, in a fault handler or in a lockup state? Check the vector table and the map file. If the board crashes, read the fault registers and the stacked frame, as in Section 8.2, or the crash record after reset. If a variable is corrupted, put a DWT watchpoint on it and let the debugger stop at the instruction that writes it. If the data is wrong but nothing crashes, suspect the cache (Section 7.3), the volatile qualifiers (Section 4.2) and the byte order (Chapter 10), and compare the bytes on the wire with a logic analyser against what the code thinks it sent. If the timing is wrong, toggle pins and measure; do not reason about interrupt latency without a measurement. And if it only fails after hours, suspect a counter wrap, a race whose window is a few nanoseconds wide, or a stack that slowly finds its deepest path; the stack high-water mark and the reset-cause register will tell you which.

Talk track

"My order is: halt and see where the PC is; for a fault, read CFSR, HFSR, the fault address and the stacked frame; for corruption, a hardware watchpoint; for timing, GPIO toggles or the cycle counter, never printf; for bus problems, a logic analyser on the pins. Semihosting only in the lab, ITM or a RAM log for anything timing-sensitive."

QSelf-check questions

Q.1Core questions

What happens on a Cortex-M between power-on and the first line of main?Basic

The reset controller holds the core until supply and clock are stable and records the reset cause. The core then reads the initial main stack pointer from the first word of the vector table and the reset handler's address from the second, and starts executing it in privileged thread mode. The startup code enables the FPU if present, sets up clocks and flash wait states, copies initialised data from its load address in flash to RAM, zeroes .bss, runs C++ constructors if any, and calls main.

What is the vector table and where is it?Basic

An array of 32-bit words: the initial stack pointer, then the addresses of the handlers for the system exceptions and every interrupt line, indexed by exception number. At reset it is at the boot address, usually 0x0; afterwards VTOR points at it and can move it, for example to RAM or to an application behind a bootloader. Handler addresses have bit 0 set because they are Thumb code.

What does the volatile keyword do, and what does it not do?Basic

It forces the compiler to perform every read and write of the object that the source contains, in order with respect to other volatile accesses, because something outside the program can change or observe it. It is needed for memory-mapped registers and simple flags shared with interrupts. It does not make read-modify-write atomic, does not order surrounding non-volatile accesses, and does not emit hardware memory barriers.

Why does this loop hang at -O2 but work at -O0: while (!flag) {} where flag is set in an ISR?Basic

Without volatile the compiler may assume nothing inside the loop changes flag, read it once and turn the loop into an endless branch; the demo's codegen shows exactly one load followed by a branch to itself. At -O0 the compiler happens to reload it. Declaring flag volatile, or using an atomic, makes the load happen on every iteration.

What is in a linker script for a microcontroller?Basic

A MEMORY block with the flash and RAM regions, and SECTIONS that place the vector table first in flash, code and constants in flash, .data with a RAM run address and a flash load address, .bss and the stack in RAM, plus special sections such as no-init RAM or DMA buffers. It also defines the symbols the startup code uses, such as the start and end of .data and .bss and the initial stack pointer.

What does the hardware do when an interrupt is taken on Cortex-M?Intermediate

It pushes R0–R3, R12, LR, the return address and xPSR on the current stack while fetching the handler address from the vector table, switches to handler mode on the main stack, sets IPSR to the exception number and loads LR with EXC_RETURN. The handler starts 12 cycles after the request on M3/M4/M7 with zero-wait-state memory. Returning with bx lr and that EXC_RETURN value unstacks the frame. With an active FP context the frame grows to 104 bytes.

How do interrupt priorities work on the NVIC?Intermediate

Each interrupt has a priority in an 8-bit field of which only the top few bits are implemented; a lower number is more urgent. A pending interrupt preempts only if its priority is strictly higher than the current execution priority; equal priorities wait and are then tail-chained, with the lower exception number first. The field can be split into group priority, which decides preemption, and subpriority, which only orders pending interrupts. Reset, NMI and HardFault have fixed negative priorities.

How do you protect data shared between main and an interrupt handler?Intermediate

If it is a single aligned word with one writer, volatile is enough. Multi-word data with one writer can use a retry loop (read high, low, high again) or a single-producer single-consumer ring buffer. Otherwise use a short critical section: PRIMASK masks all configurable interrupts, BASEPRI only those at or below a level, and the code must save and restore the previous mask. On M3 and above, LDREX/STREX-based atomics avoid masking for simple updates.

What is the difference between PRIMASK, FAULTMASK and BASEPRI?Intermediate

PRIMASK set to 1 masks every exception with configurable priority, leaving NMI and HardFault. FAULTMASK also masks HardFault by raising the execution priority to −1, which is used by fault handlers that must not be interrupted. BASEPRI masks only exceptions whose priority value is equal to or greater than the value written, so urgent interrupts keep running. BASEPRI and FAULTMASK do not exist on Armv6-M (M0, M0+).

How do you debug a HardFault?Intermediate

Read HFSR: FORCED means look in CFSR for the escalated fault. Read CFSR to see which fault and whether MMFAR or BFAR holds a valid address. Use bit 2 of EXC_RETURN to find the stack with the frame and read the stacked PC, which for a precise fault is the faulting instruction, and LR, the caller; map both with addr2line. The stacked xPSR's exception field shows whether it happened inside a handler. If a stacking error bit is set, do not trust the frame.

What is the difference between a precise and an imprecise bus fault?Intermediate

A precise fault is reported by the instruction that caused it, so the stacked PC points at it and BFAR holds the address. An imprecise one comes from a buffered write that failed later, after the core moved on, so the PC is somewhere after the culprit and BFAR is not valid. On M3/M4 disabling the write buffer while debugging makes them precise; marking the region strongly-ordered with the MPU has a similar effect.

Why are DMA and the Cortex-M7 data cache a problem, and how do you solve it?Intermediate

DMA writes and reads SRAM directly, while the CPU may see a cached copy, and the core does not snoop DMA traffic. After a receive DMA the CPU can read stale cached data; before a transmit DMA, the latest data may still be dirty in the cache. Invalidate after receive and clean before transmit, give each buffer whole 32-byte lines, or put DMA buffers in a non-cacheable MPU region or in TCM if the DMA can reach it.

How do you determine the stack size a firmware needs?Intermediate

Compute the deepest call path from per-function stack usage (GCC -fstack-usage with the call graph, or a binary analyser), with no recursion and resolved function pointers. Add, for each preemption level, an exception frame (32 or 104 bytes plus alignment) and the deepest path of the handlers at that level. Add a margin, put a guard under the stack and verify with a painted high-water mark on the target.

How does a watchdog work and where should it be kicked?Basic

It is a hardware timer that resets the chip if software does not restart it before it expires. Kick it from the main loop only when every monitored job has checked in, not from a timer interrupt, which keeps running when the main loop is stuck. A window watchdog also resets on a kick that is too early. After every reset, read and record the reset cause.

How does a bootloader start the application?Intermediate

It validates the application image (header, length, CRC or signature), de-initialises the peripherals and clocks it used, disables all interrupts and clears pending ones, sets VTOR to the application's vector table, loads MSP from the table's first word and branches to the address in the second. The VTOR address must meet the alignment rule for the table's size.

Little-endian versus big-endian: where does it matter in firmware?Basic

Only where bytes become values and back: sensor registers, protocol frames, CAN signals with Intel or Motorola order, files and flash records. Cortex-M is little-endian. Decoding with shifts is correct on any machine and compiles to efficient code (a load and REV on M7); casting a byte pointer to a wider type or memcpy into an integer takes the machine's order and is correct only by accident.

Should you use packed structs for protocol frames?Intermediate

They remove padding, but every member access then has to assume misalignment: fine on M7 for single loads from Normal memory, four byte loads on M0+, faults with LDRD/LDM, Device memory or the unaligned trap, and a pointer to a packed member loses that information. They also keep the machine's byte order. Explicit encode and decode functions are more portable and usually as fast.

What are SPI modes, and what goes wrong if the mode is wrong?Basic

CPOL chooses whether the clock idles low or high and CPHA whether data is sampled on the first or the second edge, giving modes 0 to 3. With the wrong mode the receiver samples while the data is changing, which typically shifts the data by one bit and gives plausible but wrong values rather than obvious garbage.

How do you recover a stuck I2C bus?Intermediate

A slave interrupted mid-byte can hold SDA low indefinitely. Switch SCL to a GPIO and toggle it up to nine times until the slave releases SDA, then generate a stop condition and re-initialise the peripheral. Do it at start-up and after timeouts, and give every wait in the driver a timeout.

What does a CAN controller do in hardware, and what is bus-off?Intermediate

It handles framing, bit stuffing, CRC, acknowledgement, arbitration, retransmission and error counting; software fills transmit mailboxes and reads filtered receive FIFOs. With the transmit error counter above 127 the node becomes error-passive; above 255 it goes bus-off and stops transmitting until software requests recovery and 128 sequences of 11 recessive bits have been seen. The driver must report bus-off and limit how fast it recovers.

How do you measure how long an interrupt handler takes?Basic

Read the DWT cycle counter at entry and exit and keep the maximum, or set a GPIO at entry and clear it at exit and watch it on a logic analyser or oscilloscope together with the interrupt source, which also shows latency and jitter. Not with printf, which changes the timing it measures.

What is semihosting, and why can it hang a device in the field?Intermediate

It routes C library calls such as printf to the host through the debugger: the firmware executes BKPT 0xAB and the debugger performs the operation. Each call halts the core for a long time, and without a debugger attached the breakpoint raises a HardFault. Use ITM/SWO or a RAM log buffer instead for anything outside the lab.

Q.2Why and what if

Why can Cortex-M interrupt handlers be plain C functions?Why

Because the hardware saves exactly the registers that the procedure call standard lets a C function destroy (R0–R3, R12, LR, PC, xPSR), and the return is triggered by a normal bx lr with the EXC_RETURN value. The handler's own prologue saves anything else it uses, as any function does. And SP is valid from reset because the core loads it from the vector table.

Why does .data need two addresses but .bss needs none in flash?Why

.data has non-zero initial values that must survive power-off, so they are stored in flash (load address) and copied to RAM (run address) at startup. .bss starts as all zeros, so storing it would waste flash; the startup code only needs its start and end to clear it.

What if the startup code calls a logging function before zeroing .bss?What if

The logger's state, such as a buffer index or an initialised flag, is random after power-on, so it may index outside its buffer, crash or skip initialisation. After a warm reset it holds the previous run's values, so the bug may appear only after power cycles. Nothing that depends on globals may run before .data and .bss are set up.

What if you raise the CPU clock before setting flash wait states?What if

The next instruction fetches from flash faster than flash can deliver data, so the core reads wrong instructions or constants and faults or runs wild. Raise wait states first, then the clock; lower the clock first, then the wait states.

Why can an ISR run twice when its flag is cleared as the last instruction?Why

The clearing store may still be in the write buffer or on its way through a bus bridge when the exception return happens, so the NVIC still sees the request asserted and re-enters the handler. Clear the flag early in the handler or add a DSB after the clear.

What if two interrupts have the same priority and one has been running for a long time?What if

The other waits; equal priorities never preempt each other. Its latency becomes the remaining duration of the running handler plus the tail-chain time. In the interactive figure, an equal-priority request 20 cycles after the request of a 60-cycle handler waits 58 cycles instead of 12. That is why urgent interrupts get a strictly higher priority and every handler is kept short.

Why did the null-callback fault have LR = 0xFFFFFFF9 instead of a return address?Why

The compiler turned the callback call at the end of the handler into a tail call, a plain branch that does not update LR, so LR still held the handler's EXC_RETURN. The stacked PC was 0, and the stacked xPSR's exception number (38, IRQ 22) identified the handler instead. Optimisations like this are why fault analysis uses all the registers, not just LR.

What if the stacked frame in your fault handler contains only the stack-paint pattern?What if

The hardware's stacking failed, which CFSR shows as MSTKERR or STKERR, usually because SP was already in a guard region or outside RAM: a stack overflow. The frame is not real; use the status registers and MMFAR, and fix the stack size or the recursion. Running thread code on PSP gives handlers a separate healthy stack.

Why does invalidating a DMA buffer sometimes corrupt an unrelated variable?Why

Cache maintenance works on whole 32-byte lines. If the buffer shares a line with another variable that the CPU has modified in the cache, invalidating the line discards that modification. Align DMA buffers to 32 bytes and round their size up to a multiple of 32, or place them in a non-cacheable region.

What if a DMA buffer is a local variable and the function returns before the transfer completes?What if

The DMA keeps writing into stack memory that now belongs to other functions' frames, corrupting return addresses and locals at unpredictable moments. The resulting crash appears in unrelated code. DMA buffers must be static or the function must wait for completion.

Why is kicking the watchdog from a SysTick interrupt a bad idea?Why

The SysTick interrupt keeps firing even when the main loop is stuck in an endless loop or a deadlock, so the watchdog never resets the chip. The kick must prove that the application's work is progressing: kick from the main loop when all jobs have checked in.

What if the bootloader leaves a timer interrupt enabled when it jumps to the application?What if

As soon as interrupts are enabled, possibly even inside the application's startup code, the timer interrupt fires and the core takes the vector from the application's table, which may point to a default handler, or worse, runs an application handler before the data it needs is initialised. The application seems to crash randomly at start-up only behind the bootloader. Disable and clear all interrupts before jumping.

Why does a 64-bit counter updated in an ISR need special care on a 32-bit core?Why

It is two separate 32-bit words, and reading them takes two loads. An interrupt between the loads can update both words, so the reader combines an old high word with a new low word. In the demo the forced race made 0x0000_0000_FFFF_FFFF read as 0. Use a critical section, a high-low-high retry loop, or LDREXD/STREXD where available.

What if you write NVIC priority 5 directly into the IPR byte on a part with 4 priority bits?What if

Only the upper four bits of the byte are implemented, so 0x05 becomes 0x00, the highest configurable priority. The interrupt then preempts everything, and if it calls RTOS functions it can corrupt the kernel. Write 5 shifted left by 4 (0x50), or use NVIC_SetPriority, which shifts for you.

Why does a logic analyser often find bus bugs faster than firmware logging?Why

It shows what actually happened on the wires, with real timing and without changing the firmware's timing: chip select edges, clock stretching, missing acknowledgements, error frames. Firmware logs show what the code believed happened, after the fact, and logging itself shifts the timing that may be causing the bug.

Bare metal
Firmware that runs directly on the hardware with no operating system, or only a small kernel linked into the same image.
Vector table
Array of the initial stack pointer and handler addresses, indexed by exception number, read by the core at reset and on every exception.
VTOR
Vector Table Offset Register in the SCB; holds the address of the active vector table.
Reset handler
The first code to run after reset; performs the startup sequence and calls main.
Startup code
Code before main that copies .data, zeroes .bss, enables the FPU and clocks and runs constructors.
LMA and VMA
Load memory address (where a section's bytes are in the image) and run address (where the code uses them).
.bss
Section of zero-initialised static variables; occupies RAM but no space in the image.
No-init section
RAM that the startup code does not touch, so its contents survive a warm reset; used for crash records and reset counters.
Map file
Linker output listing every section, symbol and address in the image.
MSP and PSP
Main and process stack pointers; handlers always use MSP, thread mode uses either.
Thumb bit
Bit 0 of a code address on Cortex-M, always 1; a branch to an address with bit 0 clear causes an INVSTATE UsageFault.
volatile
C qualifier that forces every source-level access to happen, in order with other volatile accesses.
W1C
Write-1-to-clear: a status bit that is cleared by writing 1 and unaffected by writing 0.
Set/reset register
GPIO register in which writing 1 to a bit sets or clears one output, making single-pin changes atomic.
NVIC
Nested Vectored Interrupt Controller: per-interrupt enable, pending, active and priority, next to the Cortex-M core.
EXC_RETURN
Value in LR inside a handler (0xFFFFFFxx) that triggers the exception return and encodes the mode, stack and frame type to return to.
Tail-chaining
Entering the next pending handler directly after the current one, without unstacking and restacking.
Late arrival
A higher-priority interrupt that arrives during stacking for a lower one is served first using the same stacking.
Lazy stacking
Reserving stack space for FP registers on exception entry but saving them only if the handler uses the FPU.
PRIMASK
Mask register that blocks all exceptions with configurable priority.
BASEPRI
Mask register that blocks exceptions at or below a priority level (Armv7-M and Armv8-M Mainline).
Critical section
Code during which interrupts that could touch the same data are masked.
LDREX/STREX
Exclusive load and store instructions; the store fails if the location may have been touched since the load, including by an exception.
DSB, DMB, ISB
Barriers: wait for memory accesses to complete, order memory accesses, and refetch instructions with new settings.
DMA controller
Bus master that moves data between peripherals and memory without the CPU, on peripheral requests.
Clean and invalidate
Cache maintenance: clean writes dirty lines back to memory; invalidate discards cached copies so the next read fetches from memory.
TCM
Tightly coupled memory: zero-wait-state RAM next to the core, never cached (ITCM for code, DTCM for data).
MPU
Memory protection unit: checks every access against a few regions with permissions, execute-never and memory attributes, without address translation.
HardFault
Catch-all fault exception with fixed priority −1; configurable faults escalate to it when they cannot run.
CFSR
Configurable Fault Status Register: MemManage, BusFault and UsageFault status bits in one word.
BFAR and MMFAR
Fault address registers for BusFaults and MemManage faults, valid when the matching CFSR bit is set.
Lockup
Core state after a fault in HardFault or NMI: execution stops; most chips then reset.
Stack painting
Filling unused stack with a pattern at startup and later scanning for the deepest overwritten word.
Watchdog
Timer that resets the chip unless software restarts it in time; a window watchdog also resets on early restarts.
Brown-out reset
Reset held while the supply is below a threshold, so the chip never runs at an unsafe voltage.
Bootloader
Separate program at the reset address that validates and starts the application or accepts a new one.
Endianness
Byte order of multi-byte values in memory or on a wire: little-endian (least significant first) or big-endian.
Packed struct
Struct without padding; members may be misaligned and the compiler must access them accordingly.
SWD
Serial Wire Debug: two-pin debug interface (SWDIO, SWCLK) to a Cortex-M's debug access port.
FPB and DWT
Debug units for hardware breakpoints (FPB) and data watchpoints, cycle counter and data trace (DWT).
ITM and SWO
Instrumentation trace macrocell (software writes trace packets to stimulus ports) and the single-wire output pin that carries them.
Semihosting
Running C library I/O on the host through the debugger via BKPT 0xAB; faults when no debugger is attached.
