GPU computing and CUDA programming

How a GPU runs thousands of threads at once and how to write code that keeps it busy: the SIMT execution model and warps, the memory hierarchy with coalescing and bank conflicts, occupancy and latency hiding, streams and memory types, kernels written and improved step by step on a camera frame, reductions and tiled matrix multiply, the libraries and TensorRT plugins, profiling with Nsight, and CUDA on embedded SoCs such as Orin, compared with OpenCL and Vulkan compute.

1Why GPUs: a machine built for throughput

A camera frame has two million pixels, and almost every one of them goes through the same arithmetic: convert the colour, scale, normalise, convolve. A processor that runs one instruction stream very fast is the wrong tool for that. A GPU runs tens of thousands of instruction streams slowly, and wins because there are so many of them. Programming it well means understanding how it keeps all of them fed with data, because that, not arithmetic, is almost always the limit.

1.1Latency machines and throughput machines

Every processor has the same basic problem: an arithmetic unit can do a multiply-add in a few cycles, but fetching its operands from DRAM takes hundreds. A CPU core answers this by avoiding the wait. It spends most of its silicon on large caches that keep data close, on branch predictors that guess where the program goes next, and on out-of-order logic that finds independent instructions to run while one is stuck. The result is a core that runs one thread, or two with hyper-threading, as fast as physics allows. A desktop CPU has 8 to 24 such cores.

A GPU answers the same problem by hiding the wait. It gives up on making a single thread fast: no branch prediction, no out-of-order execution, small caches per thread. Instead it keeps a large number of threads resident on the chip at the same time, with all their registers permanently allocated, so that switching from one to another costs nothing. When a group of threads waits for memory, the hardware simply issues instructions from another group that is ready. As long as there are enough groups, the arithmetic units never sit idle and the memory system is kept saturated with requests. The silicon saved on control logic goes into many more arithmetic lanes.

This trade-off decides what runs well on a GPU. Work that splits into thousands of independent pieces doing similar arithmetic, such as pixels, matrix elements, points of a point cloud or neurons of a layer, maps naturally. Work that is one long chain of dependent decisions, such as parsing a protocol, running a state machine or traversing a linked list, does not: it would run on a single slow lane while the rest of the chip waits. A practical engineer uses the GPU for the first kind and keeps the second on the CPU, and spends most effort on the boundary between them.

Why it matters

Almost every perception system runs its networks and much of its image processing on a GPU or a GPU-like accelerator. Knowing why the GPU is fast tells you why a port of CPU code is often slow on it: the code was written to make one thread fast, while the GPU needs it written so that many threads can run with simple, regular memory access. The rest of this chapter is about that rewrite.

Numbers

A desktop CPU core reaches DRAM in roughly 80–100 ns and a whole CPU streams a few tens of GB/s. The GPU in an NVIDIA Orin SoC has 16 streaming multiprocessors with 128 FP32 lanes each, 2048 lanes in total, runs up to 1.3 GHz for about 5.3 TFLOP/s in FP32 and 42.5 TFLOP/s in dense FP16 on its tensor cores, and shares 204.8 GB/s of LPDDR5 bandwidth with the rest of the SoC. Its DRAM latency is several hundred nanoseconds, so it needs on the order of 100 KB of requests in flight to keep that bandwidth busy (Section 4.1). A data-centre GPU such as an A100 has 108 SMs and 1.5–2 TB/s of HBM bandwidth; the principles are the same, the numbers about ten times larger.

1.2The running example: one camera frame into a detector

The chapter follows one task through all its parts. A front camera delivers 1920 × 1080 frames at 30 fps in NV12, the format most ISPs and video decoders produce: a full-resolution plane of 8-bit luma (Y) followed by a half-resolution plane of interleaved chroma pairs (U, V), 3.11 MB per frame. A detector of the YOLO family needs a 960 × 544 input in RGB, normalised per channel with a mean and standard deviation, stored as 16-bit floats in planar CHW layout (all red values, then all green, then all blue). The image is scaled by exactly one half to 960 × 540 and padded with two grey rows at the top and the bottom, a letterbox, because the network wants a height divisible by 32.

The preprocessing kernel that does this conversion is the first piece of CUDA code almost every perception engineer writes, and it is a perfect teaching example. It is short enough to understand completely, it touches every part of the memory system, and the difference between a naive and a good version is a factor of ten or more. Chapter 6 writes it four times, each version fixing one problem, and estimates what each one costs on an Orin. Around it the chapter adds the other kernels a perception stack needs (reductions, histograms, matrix multiplies) and the system-level parts: streams, memory types, zero-copy camera buffers and handing the result to a TensorRT engine without a copy.

How the numbers in this chapter were obtained

The chapter was written in a container without a GPU, so nothing in it was timed on real hardware. What is real: every kernel shown was compiled for the Orin GPU (compute capability 8.7) with NVRTC and ptxas from the CUDA 12.9 toolchain, and the register counts, shared-memory sizes and assembly (SASS) quoted come from that compiler output. The four preprocessing versions were also run instruction for instruction in a CPU emulator to check that they compute the same tensor. They are good to perhaps a factor of 1.5, which is enough to see which version wins and why. 2The SIMT execution model

CUDA lets you write a function for one thread and launch it for a million. The hardware groups those threads into warps of 32 that execute in lockstep, deals warps out to schedulers, and switches between them every cycle. Each of these layers explains a rule of GPU programming, from why block sizes are multiples of 32 to why an if can halve your speed.

2.1Grids, blocks and threads: the programming model

A CUDA program has two parts. The host code runs on the CPU, allocates memory, and launches work. The device code is a set of kernels: functions marked __global__ that run on the GPU. A kernel is written from the point of view of a single thread, and the launch says how many threads to start. The threads are organised in two levels. A block is a group of up to 1024 threads that run on the same SM, can share a fast on-chip memory and can wait for each other at a barrier. The grid is all the blocks of one launch; blocks are independent of each other and may run in any order, at the same time or one after another.

__global__ void scale(float* y, const float* x, float a, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;   // global index of this thread
    if (i < n) y[i] = a * x[i];                      // guard: the last block may be partly outside
}

// host: 1 million elements, 256 threads per block, enough blocks to cover n
int n = 1 << 20, threads = 256, blocks = (n + threads - 1) / threads;   // round up: 4096 blocks
scale<<<blocks, threads, 0, stream>>>(d_y, d_x, 2.0f, n);              // returns immediately

Inside the kernel each thread finds out who it is from built-in variables: threadIdx (its position in the block), blockIdx (the block's position in the grid), blockDim and gridDim (the sizes). All four are three-dimensional, which is only a convenience: a 2D image kernel can launch blocks of 32 × 8 threads in a grid of 30 × 68 blocks and compute a pixel's column and row directly. The <<<blocks, threads, sharedBytes, stream>>> syntax is the launch; it is asynchronous, so the CPU continues while the GPU works (Chapter 5).

Why two levels and not just "a million threads"? Because the hardware can only make cooperation cheap within a small group. Threads in a block are guaranteed to be on one SM at the same time, so they can share that SM's fast memory and synchronise with __syncthreads(), a barrier that costs a few cycles. Threads in different blocks may be on different SMs or may not even run at the same time, so the only safe way for them to communicate is through global memory with atomics, or by ending the kernel. This independence is what lets the same program run on a GPU with 16 SMs or with 132: the hardware just deals out blocks to whatever SMs exist.

Pitfall

Integer division in the grid size. Writing blocks = n / threads silently drops the last partial block, and the elements it should have handled keep whatever was in memory. The emulator used for Chapter 6 caught exactly this in a first draft of the vectorised kernel: 960 pixels per row are 240 groups of four, and 240 / 32 is 7, not 8, so 64 pixels at the right edge of every row were never written. Always round up and guard inside the kernel.

2.2Inside a streaming multiprocessor

The streaming multiprocessor (SM) is the GPU's equivalent of a core, and the unit you reason about when optimising. The Ampere SM in Orin (compute capability 8.7) is split into four partitions. Each partition has a warp scheduler that can issue one instruction per clock for one warp, a 64 KB slice of the register file, 32 FP32 lanes (16 that do only FP32 and 16 that do FP32 or INT32), a tensor core for matrix arithmetic, special-function units for reciprocal, square root, sine and exponential, and load/store units. The four partitions share a 192 KB block of SRAM that is split, by configuration, between the L1 data cache and the programmer-managed shared memory.

The important property is in the register file. 64 K 32-bit registers per SM sounds like a lot, but they are divided among all resident threads: 1536 threads would get about 42 registers each. Every thread's registers are reserved for as long as its block lives, so a warp scheduler can choose any ready warp every cycle without saving or restoring anything. This is the mechanism behind latency hiding, and also the reason register usage limits how many threads fit (Chapter 4).

Interesting detail

The "CUDA core" count in marketing is the number of FP32 lanes: 128 per Ampere SM, 2048 in the Orin GPU. Since Ampere, half of those lanes are shared with INT32 work, so a kernel that does a lot of integer index arithmetic gets less than the nominal FP32 rate. The tensor cores are separate: each does a small matrix multiply-accumulate per instruction, and they account for most of the headline TOPS.

In silicon, a GPU is that SM copied many times. SMs are grouped into GPCs (graphics processing clusters), which also hold the fixed-function graphics units; the L2 cache sits between the GPCs and the memory controllers, and a crossbar connects every SM to every L2 slice. Figure 2.2b is a photo of a desktop GPU die from 2016 with these blocks marked. Orin's GPU is a small member of the same family: 2 GPCs with 8 SMs each, a 4 MB L2, and no memory interfaces of its own, because it shares the SoC's LPDDR5 controllers (Chapter 11).

2.3Warps: 32 threads in lockstep

The hardware does not schedule single threads. It groups each block's threads, in order of their linear index, into warps of 32: threads 0–31 form warp 0, 32–63 warp 1 and so on (for a 2D block, the x index varies fastest). A warp shares one instruction stream. When the scheduler issues an instruction for a warp, all 32 lanes execute it at the same time on their own data, like a 32-wide SIMD instruction on a CPU. NVIDIA calls this SIMT, single instruction multiple threads, because the programmer writes scalar code per thread and the hardware does the grouping.

The difference from CPU SIMD matters in practice. With SSE or NEON, the programmer or compiler packs four or eight values into a vector register and every lane always does the same thing. With SIMT, each thread has its own registers and conceptually its own program counter, so threads of a warp may take different branches, load from unrelated addresses and even loop different numbers of times. The hardware makes that work, but not for free: while lanes disagree, the warp runs the paths one after another with some lanes switched off. The speed of a warp is therefore the speed of its slowest lane, and the speed of a memory instruction depends on how many different cache sectors its 32 addresses touch (Chapter 3).

Since the Volta generation each thread really does have its own program counter and call stack (independent thread scheduling). This makes it legal for threads in one warp to wait for each other through locks, which deadlocked on older GPUs, but it also removed an old assumption: the 32 threads of a warp are no longer guaranteed to be at the same instruction. Code that exchanges data inside a warp must say so explicitly with the _sync intrinsics and a mask of participating lanes, such as __shfl_down_sync(0xffffffff, v, 16), or with __syncwarp().

Talk track

"A kernel is written for one thread, but the GPU executes 32 threads at a time as a warp, one instruction for all of them. Thousands of warps are resident, and each SM's schedulers pick a ready warp every cycle, so memory latency is hidden by switching rather than avoided by caches. Two things follow: lanes of a warp should take the same branch, and neighbouring lanes should touch neighbouring memory."

2.4Divergence and reconvergence, step by step

Take a tiny kernel: each thread loads one value x; if it is positive the thread computes 2·sqrt(x), otherwise −x², and stores the result. Half the lanes take one branch and half the other. Below are the real instructions ptxas generated for Orin, and what the 32 lanes of one warp do on each of them. Step through it.

LDG.E loads x for all 32 lanes with one instruction. Every lane is active; their addresses are consecutive, so the warp's 128 bytes arrive as four 32-byte sectors.

BSSY B0 records the reconvergence point, the instruction after the if/else, in a convergence barrier register. FSETP.GT then sets a one-bit predicate P0 in each lane: true where x > 0. Nothing has diverged yet; this is ordinary lockstep arithmetic.

The compiler made the short else-branch branch-free: @!P0 FFMA computes −x·x only in lanes whose predicate is false. The 11 lanes with negative x do the work; the 21 others are masked and the instruction costs them a cycle anyway. Then @!P0 BRA sends exactly those 11 lanes to the reconvergence point. The warp has diverged.

The remaining 21 lanes run the square root: MUFU.RSQ on the special-function unit, a Newton step with three FFMAs, then FADD for the factor two. The 11 lanes that branched away wait, masked off. Both paths have now been executed by the same warp, one after the other.

BSYNC B0 waits until all lanes named in the barrier have arrived. From here on the warp runs all 32 lanes together again. Without this point, the two groups could stay apart for the rest of the kernel and every later instruction would be issued twice.

STG.E writes all 32 results with one coalesced store. The total cost of the divergent section is the sum of both paths, not the maximum: a warp is as slow as the union of what its lanes need.

Divergence costs only within a warp. If all 32 lanes of a warp take the same branch, the other path is skipped entirely, even if neighbouring warps go the other way. This is why the useful question is never "does my kernel have branches" but "do lanes of the same warp disagree, and on how much work". A bounds check at the edge of an image diverges in one warp per row and is irrelevant. A per-pixel branch on image content, such as "if this pixel is saturated, run an expensive repair", can diverge in every warp and double the cost. The usual remedies are to make short branches branch-free (the compiler already does this with predication, as in step 3), to sort or bin work so that similar items land in the same warp, or to move rare expensive cases into a second kernel that runs only on a compacted list of them (Section 7.4).

Pitfall

Divergence also hits loops. A kernel where each thread loops over a variable number of items, for example the points that fell into its voxel, runs every warp for as many iterations as its busiest lane needs. One dense voxel in a warp of empty ones makes 31 lanes wait. Balancing work across lanes, for instance by giving each warp a fixed number of points rather than each thread a voxel, is often the biggest optimisation for irregular data.

2.5From CUDA C++ to the machine: PTX, SASS and compute capability

The CUDA compiler nvcc splits a .cu file into host code, compiled by the normal C++ compiler, and device code, compiled in two stages. The front end produces PTX, a virtual instruction set with unlimited registers that is stable across GPU generations. The assembler ptxas then turns PTX into SASS, the real machine code of one GPU generation, allocating registers and scheduling instructions. Both can be embedded in the executable as a fatbinary: SASS for the GPUs you target, plus PTX that the driver can compile just in time for a GPU that did not exist when you built.

Every GPU has a compute capability that names its instruction set and limits: 7.2 for Xavier, 8.6 for desktop Ampere, 8.7 for Orin, 8.9 for Ada, 9.0 for Hopper. You choose targets with -gencode arch=compute_87,code=sm_87 (SASS for Orin) and -gencode arch=compute_87,code=compute_87 (PTX for later GPUs). In an automotive build you normally ship SASS only for the exact SoC, because JIT compilation at start-up costs time and makes the executed code depend on the installed driver.

$ ptxas -v  (via NVRTC, --gpu-architecture=sm_87)
ptxas info    : Compiling entry function '_Z15k2_fused_pixels...' for 'sm_87'
ptxas info    : Function properties for _Z15k2_fused_pixels...
ptxas         .     0 bytes stack frame, 0 bytes spill stores, 0 bytes spill loads
ptxas info    : Used 34 registers, used 0 barriers, 436 bytes cmem[0]

The -Xptxas -v report above, from the Chapter 6 kernel, is the first thing to look at for any kernel: registers per thread (they decide occupancy), shared memory, and spills, registers the compiler could not fit and moved to slow local memory. Reading SASS (with cuobjdump -sass or nvdisasm) is the second: it shows whether loads were vectorised, whether a loop was unrolled, whether a branch became predication, and whether an innocent-looking function call such as sqrtf or a double-precision constant pulled in a slow path. You do not need to write SASS, but recognising LDG.E.64, SHFL, BAR.SYNC or HMMA in a listing answers many performance questions faster than a profiler.

Interesting detail

Floating-point literals matter. Writing x * 0.5 instead of x * 0.5f promotes the expression to double precision, and on GPUs with few FP64 units, such as Orin and every consumer GPU, double arithmetic runs at 1/32 or 1/64 of the FP32 rate. The SASS shows it immediately as DMUL and conversions (F2F.F64.F32). Compiling with -Xptxas -warn-double-usage flags such code; --use_fast_math additionally replaces sqrtf, division and transcendental functions with faster, slightly less accurate hardware approximations, which is usually fine for image processing and rarely fine for geometry.

3The memory hierarchy

Most kernels in a perception stack do a few operations per byte they touch, so their speed is set by how fast data moves, not by how fast it is multiplied. The GPU has five kinds of memory with very different sizes, scopes and speeds, and a set of rules for how a warp's 32 accesses turn into memory transactions. Knowing those rules is the single most valuable piece of GPU knowledge.

3.1The levels and their numbers

Closest to the arithmetic are the registers: private to each thread, read every cycle, allocated by the compiler. Next is shared memory, a scratchpad on the SM that all threads of one block can read and write, explicitly managed by the program; it lives in the same SRAM as the L1 cache, which caches global memory automatically for one SM. The L2 cache is shared by all SMs and is the point where all memory traffic of the GPU meets; on Orin it is 4 MB. Finally there is global memory, the DRAM, which on Orin is the same LPDDR5 the CPU, the DLA, the ISP and the display use.

Two further names appear in CUDA code. Constant memory (64 KB, declared __constant__) is global memory with its own small cache that is optimised for all lanes reading the same address: kernel parameters and small coefficient tables live there, and a broadcast read costs one access. If lanes read different constant addresses, the accesses are serialised, so per-pixel lookup tables do not belong there. Local memory is the opposite trap: it is private to a thread like a register, but physically lives in DRAM (cached in L1 and L2). The compiler uses it for spilled registers and for per-thread arrays it cannot keep in registers, typically arrays indexed with a value only known at run time.

Numbers

Per SM per clock, roughly: registers deliver several kilobytes of operands, shared memory 128 bytes (32 banks of 4 bytes), L1 128 bytes. The whole Orin GPU at 1.3 GHz therefore has about 2.7 TB/s of shared-memory bandwidth across its 16 SMs, more than ten times its 204.8 GB/s of DRAM bandwidth. That ratio is why data that is used more than once should be staged in shared memory or registers.

3.2Global memory transactions and coalescing

When a warp executes a load, the load/store unit collects the 32 addresses and works out which memory blocks they fall into. The unit of transfer between L1, L2 and DRAM is a 32-byte sector; L1 cache lines are 128 bytes made of four sectors. A warp whose 32 lanes read 32 consecutive 4-byte floats touches exactly 128 bytes, four sectors in one line, and is served with the minimum possible traffic. This is a coalesced access. If the lanes read every second float, the same 32 values are spread over 256 bytes and eight sectors, half of each wasted. If each lane reads a value 128 bytes away from its neighbour, as when threads walk down a column of a row-major matrix, the warp touches 32 different sectors and uses 4 bytes of each: one eighth of the bandwidth does useful work.

The explorer below computes this for any access pattern. Pick an element size and a stride (in elements) and see which sectors the 32 lanes hit; switch to shared memory to see banks instead (next section).

Three practical rules follow. First, map consecutive threads to consecutive addresses: in a 2D image kernel, threadIdx.x must run along a row, never down a column. Second, prefer structure-of-arrays: an array of struct {float x, y, z, intensity;} points makes a kernel that reads only x load four times the bytes it needs, while four separate arrays let each read coalesce. Third, wider accesses help: a lane that loads a float4 or a uint2 moves 16 or 8 bytes with one instruction, so the warp needs fewer instructions for the same bytes, as long as the address is aligned to the access size.

Whether a wasted sector also costs DRAM bandwidth depends on the cache. If the neighbouring lane's data in the same sector is requested by the same warp a moment later, the sector may still be in L1 and the waste is only in transactions and L1 bandwidth. If it is requested much later, by another block, it may have been evicted and must be fetched again. Coalescing is the rule that avoids depending on that luck.

Pitfall

Pitched images. Camera buffers and cudaMallocPitch allocations pad each row to an alignment (often 256 or 512 bytes), so the row stride is not the width. Indexing with y * width + x instead of y * pitch + x produces an image that looks sheared, and only for resolutions whose width is not already a multiple of the alignment, which is why the bug often survives testing at 1920 and appears at 1280 × 960.

3.3Shared memory and bank conflicts

Shared memory exists for data that a block uses more than once or exchanges between its threads: a tile of an image for a convolution, tiles of two matrices for a multiply, partial sums for a reduction. It is declared in the kernel (__shared__ float tile[32][33];) or sized at launch, lives for the duration of the block, and is visible to all its threads. Because threads write and read each other's values, access must be ordered with __syncthreads(), the block-wide barrier: everything written before it is visible to every thread after it.

To deliver 128 bytes per clock, shared memory is split into 32 banks of 4-byte words, with consecutive words in consecutive banks: word w is in bank w mod 32. Each bank can serve one word per clock. If the 32 lanes of a warp access 32 different banks, the access takes one cycle. If several lanes access different words in the same bank, a bank conflict, the hardware splits the access into as many rounds as the worst bank needs. Lanes that read the same word share it (broadcast), which costs nothing extra.

The classic case is a matrix transpose. A block loads a 32 × 32 tile row by row (coalesced from global memory), then each warp reads it column by column so that its writes back to global memory are also coalesced. Reading a column of float tile[32][32] means lane i reads word 32·i + c, and every one of those words is in bank c: a 32-way conflict that makes the read 32 times slower. Declaring the tile as tile[32][33] shifts each row by one bank, so the column's words fall into 32 different banks and the conflict disappears at the cost of 128 bytes of padding.

template <int PAD>
__global__ void transpose_tiled(const float* in, float* out, int W, int H) {
    __shared__ float tile[32][32 + PAD];                       // PAD = 1 removes the bank conflicts
    int x = blockIdx.x * 32 + threadIdx.x, y = blockIdx.y * 32 + threadIdx.y;
    for (int j = 0; j < 32; j += blockDim.y)                   // block of 32 x 8 threads, 4 rows each
        if (x < W && y + j < H) tile[threadIdx.y + j][threadIdx.x] = in[(size_t)(y + j) * W + x];
    __syncthreads();                                           // the whole tile is loaded
    x = blockIdx.y * 32 + threadIdx.x; y = blockIdx.x * 32 + threadIdx.y;
    for (int j = 0; j < 32; j += blockDim.y)
        if (x < H && y + j < W) out[(size_t)(y + j) * H + x] = tile[threadIdx.x][threadIdx.y + j];
}
Interesting detail

On Ampere, shared memory and L1 are one 192 KB array per SM, and the split is chosen per kernel (cudaFuncAttributePreferredSharedMemoryCarveout). A kernel gets 48 KB of shared memory per block by default; up to 163 KB on Orin requires an explicit opt-in with cudaFuncSetAttribute(kernel, cudaFuncAttributeMaxDynamicSharedMemorySize, bytes). Since Ampere, cp.async (exposed as cuda::memcpy_async) can copy from global to shared memory without passing through registers, so a block can load the next tile while computing on the current one.

3.4Read-only data, textures and spills

Data a kernel only reads can take a faster path. Marking pointers const __restrict__ tells the compiler that nothing else writes through them during the kernel, which allows it to use the non-coherent read-only path (LDG.E.CONSTANT in the SASS of the Chapter 6 kernels) and to reorder loads more freely. The explicit intrinsic __ldg() does the same for one load.

Textures are the GPU's graphics heritage and still useful for images. A texture object wraps a 2D array or a pitched buffer and is read with tex2D<float4>(tex, x, y); the hardware then handles out-of-range coordinates (clamp, wrap, border), converts 8-bit values to normalised floats and, most usefully, performs bilinear interpolation in a dedicated unit. The cache behind it is tuned for 2D locality, so a warp reading a small square of pixels is served well even when the pattern is not a neat row. Remapping kernels such as fisheye undistortion or surround-view warps, whose reads follow a lookup table and are not coalesced, often run faster through textures than through plain loads.

Pitfall

Hardware bilinear filtering computes its weights in 9-bit fixed point with 8 fractional bits, so interpolated values can differ from a float computation by up to about 1/256 of the pixel difference. For display and most preprocessing that is invisible; for sub-pixel geometry, such as computing a disparity or refining a corner, interpolate in the kernel instead.

Register spills are the last trap. If a kernel needs more registers than the compiler is allowed to use, either because the code really needs them or because __launch_bounds__ or -maxrregcount capped them, ptxas stores some values in local memory and reports spill stores and spill loads. A few bytes of spills in a cold path are harmless; spills inside the inner loop turn register accesses into memory traffic. Per-thread arrays indexed by a runtime value land in local memory for the same reason, since registers cannot be indexed: fully unrolling the loop over such an array (so every index becomes a constant) usually moves it back into registers.

3.5Arithmetic intensity and the kernel roofline

Before optimising a kernel, decide which limit it is up against. The arithmetic intensity of a kernel is the number of floating-point operations it does per byte it moves to or from DRAM. Multiplying intensity by the memory bandwidth gives the best performance the memory system allows; the arithmetic peak caps it from above. Plotting both on log axes gives the roofline: a slanted line for memory-bound kernels and a flat line for compute-bound ones, meeting at the ridge point, peak FLOP/s divided by peak bandwidth.

For Orin the ridge is at 26 FLOP per byte for FP32 on the CUDA cores and about 200 for FP16 on the tensor cores. Almost every image-processing kernel lies far to the left: the preprocessing kernel of Chapter 6 does about 34 operations per output pixel while moving 12 bytes (6 read, 6 written), an intensity of 2.8. A reduction does one addition per 4-byte float, 0.25. For such kernels the only way to go faster is to move fewer bytes: fuse kernels so that intermediates stay on chip, use smaller data types, and make every byte fetched a useful one. Only dense linear algebra, convolutions and attention have enough reuse to reach the flat part, and only if the code stages data in shared memory and registers so that each byte fetched from DRAM is used many times (Chapter 8).

Talk track

"First I compute the bytes a kernel must move and the operations it must do. If the intensity is below the ridge, about 26 FLOP per byte in FP32 on Orin, the kernel is memory-bound and I measure it against the bandwidth: my preprocessing kernel moves 6.2 MB per frame, so 40 µs is the floor and anything near it is done. If it is above, I check how close it gets to the arithmetic peak, which usually means using tensor cores through a library."

4Occupancy and latency hiding

A GPU hides memory latency by always having another warp ready to run. How many warps it needs depends on how long the waits are and how much independent work each warp has between them; how many it can have depends on how much register and shared memory each one uses. Balancing the two is what "tuning occupancy" means.

4.1Why a GPU needs many warps

Each SM partition's scheduler can issue one instruction per clock. A warp that issues a load from DRAM cannot use the result for hundreds of cycles; in the meantime it can issue only instructions that do not depend on that load. If the scheduler has no other warp ready, the issue slot stays empty. The figure below simulates one scheduler with several warps, each of which runs a number of independent instructions, then issues a load and waits for it.

The rule is Little's law: the amount of work in flight must equal the throughput times the latency. For memory, the GPU needs bandwidth × latency bytes outstanding at all times. On Orin, 204.8 GB/s times a loaded latency of about 550 ns is roughly 110 KB in flight, about 7 KB per SM, or some 55 outstanding 128-byte warp loads per SM. A kernel gets there either with many warps that each have one load outstanding, or with fewer warps that each have several independent loads in flight. The second way is called instruction-level parallelism (ILP) and is often cheaper: a thread that processes four pixels issues four independent loads before it needs the first result.

Why it matters

This is the reason the one-thread-per-row version of the preprocessing kernel in Chapter 6 is slow even after fusion: 544 output rows are 17 warps for a GPU that can hold 768. Each SM gets about one warp, every load waits the full DRAM latency with nothing to hide it, and the GPU runs at a few per cent of its capability. A GPU kernel must expose tens of thousands of independent threads, or fewer threads each with plenty of independent work.

4.2What limits occupancy

Occupancy is the number of warps resident on an SM divided by the maximum, 48 on Orin. Blocks are placed on an SM whole, and a block fits only if all its resources do. Four limits apply at the same time. The warp slots: at most 48 warps, so a 256-thread block (8 warps) fits six times and a 1024-thread block (32 warps) only once, leaving 16 slots unused. The block slots: at most 16 blocks, which matters for tiny blocks. The registers: 65,536 per SM, allocated per warp in units of 256, so a kernel using 128 registers per thread can have at most 16 warps resident. And shared memory: 164 KB per SM, plus 1 KB the system reserves per block.

The calculator mirrors what the CUDA occupancy API (cudaOccupancyMaxActiveBlocksPerMultiprocessor) and the Nsight Compute "Occupancy" section compute. The register limit is the one that bites most often, because the compiler is free to use more registers to make a single thread faster. __launch_bounds__(maxThreads, minBlocks) on a kernel tells ptxas the block size you will launch and, optionally, how many blocks you want per SM, and it then limits registers accordingly; -maxrregcount does the same globally and bluntly. Both trade fewer registers per thread for more warps, and if the compiler has to spill to fit, the trade can make things worse.

Numbers

Orin (compute capability 8.7): 48 warps and 1536 threads per SM, 16 blocks per SM, 1024 threads per block, 65,536 registers per SM and at most 255 per thread, register allocation in units of 256 per warp, 164 KB shared memory per SM and 163 KB per block (48 KB without opt-in), 1 KB reserved per block. Data-centre Ampere (8.0) and Hopper (9.0) allow 64 warps and 2048 threads per SM; desktop Ampere and Ada (8.6, 8.9) have 48 warps and 100 KB of shared memory.

4.3Occupancy is a means, not a goal

High occupancy only matters as a way to hide latency. A kernel whose threads each keep several loads in flight and do enough independent arithmetic can saturate memory or the arithmetic units at 25 or 33 % occupancy, and many of the fastest kernels in cuBLAS and CUTLASS run exactly there. They give each thread a large register tile (Section 8.2), so it computes many outputs from data already in registers; that needs many registers per thread, which lowers occupancy, and it is the right trade. Vasily Volkov's talk "Better performance at lower occupancy" (2010) made this point with measurements and is still the reference.

The practical rule: look at occupancy when a kernel is latency-bound, which Nsight Compute shows as warps stalled on memory with neither memory nor arithmetic close to its peak. Then either raise occupancy (fewer registers, less shared memory per block, a better block size) or give each warp more independent work (process several elements per thread, unroll loops, issue loads earlier). If the kernel is already near the memory or compute roof, more occupancy will not help.

Pitfall

Tail effects. A grid runs in "waves" of as many blocks as fit on all SMs at once. Orin with six 256-thread blocks per SM holds 96 blocks per wave; a grid of 100 blocks runs one full wave and then a second wave with only 4 blocks, during which 92 % of the GPU idles. For short kernels, size the grid as a multiple of the wave or use a grid-stride loop (next section) so every block has similar work.

4.4Choosing a launch configuration

For most kernels, a block size of 128 or 256 threads is a good start: it is a multiple of 32, fits several blocks per SM, and leaves room for registers. For 2D images, 32 × 8 (one warp per row segment) or 32 × 4 keeps threadIdx.x along the row for coalescing. Use more threads per block only when they cooperate through shared memory and need a large tile.

The grid size has two common styles. One thread per element launches as many threads as there are outputs, rounded up, with a bounds check; it is simple and suits image kernels with a fixed size. A grid-stride loop launches a fixed number of blocks, typically a few waves' worth, and lets each thread loop over elements with a stride of the total number of threads. It handles any input size with one launch configuration, amortises per-thread setup, and is the natural form for reductions and histograms, where each thread should first accumulate many elements privately (Chapter 7).

__global__ void saxpy_gs(float* y, const float* x, float a, int n) {
    for (int i = blockIdx.x * blockDim.x + threadIdx.x; i < n; i += gridDim.x * blockDim.x)
        y[i] = a * x[i] + y[i];                      // consecutive threads still read consecutive elements
}
int sms; cudaDeviceGetAttribute(&sms, cudaDevAttrMultiProcessorCount, 0);
saxpy_gs<<<sms * 6, 256, 0, stream>>>(y, x, 2.f, n);   // six 256-thread blocks per SM = one full wave on Orin

cudaOccupancyMaxPotentialBlockSize suggests a block size that maximises occupancy for a given kernel, which is a reasonable default for a first version; the final choice should come from measuring two or three candidates, because the best configuration depends on cache behaviour that no formula captures.

5Host and device together: streams, events, copies and memory types

A kernel is only part of a GPU program. The CPU has to get data to the GPU, queue work in the right order, find out when it is done, and do all this without either side waiting for the other. CUDA's streams, events and memory types are the tools for that, and in a real-time system they decide latency at least as much as the kernels do.

5.1Launches are asynchronous: the stream as a queue

A kernel launch does not run the kernel. It writes a command into a queue that the GPU reads, and returns to the CPU after a few microseconds. That queue is a stream: commands in one stream run in order, each starting after the previous one has finished; commands in different streams have no ordering between them and may run concurrently if resources allow. Copies (cudaMemcpyAsync), memory sets and event records go into streams the same way.

The CPU learns about completion only by asking. cudaStreamSynchronize(s) blocks until everything queued in s has finished; cudaDeviceSynchronize() waits for all streams. Some calls synchronise implicitly: plain cudaMemcpy, cudaMalloc and cudaFree may wait for the whole device. Every synchronisation empties the queue and leaves the GPU idle until the CPU queues the next command, so a real-time pipeline should synchronise at most once per frame, and preferably not by spinning a CPU core.

There is a trap in the default stream. Work launched without a stream argument goes to the legacy default stream, which synchronises with every other blocking stream of the process: one forgotten stream argument in a library call serialises the whole application. Creating streams with cudaStreamNonBlocking, or compiling with --default-stream per-thread so that each CPU thread gets its own ordinary default stream, avoids it.

Numbers

A kernel launch costs the CPU roughly 2–5 µs, and back-to-back dependent kernels in one stream leave a gap of a microsecond or more on the GPU. A detector engine with 100–200 kernels therefore spends a measurable fraction of a millisecond just being launched, which is what CUDA Graphs remove (Section 5.6). An event's timestamp resolution is about half a microsecond.

5.2Pinned memory and asynchronous copies

On a discrete GPU, data crosses PCIe, and the transfer is done by DMA engines on the GPU (copy engines) that read host memory directly. DMA needs physical addresses that do not change, but ordinary malloc memory is pageable: the operating system may move or swap its pages. So a copy from pageable memory is done in two steps by the driver, first a CPU copy into an internal pinned staging buffer, then the DMA, and the call cannot return before the CPU part is done. Memory allocated with cudaMallocHost or cudaHostAlloc, or registered with cudaHostRegister, is pinned (page-locked): the DMA engine reads it directly, the copy runs at full PCIe speed, and cudaMemcpyAsync really returns immediately.

Pinned memory is a limited resource, since the OS cannot reclaim it, so it is allocated once at start-up for the buffers that are copied every frame, never per frame. On a PCIe 4.0 x16 link, a pinned copy reaches about 25 GB/s and a pageable one often half of that: the 3.11 MB NV12 frame of the running example takes about 125 µs pinned and 260 µs pageable, longer than a good preprocessing kernel.

5.3Streams and overlap

With pinned memory and more than one stream, three things can happen at the same time on a discrete GPU: a host-to-device copy of frame n+1, kernels on frame n, and a device-to-host copy of frame n−1. Each runs on a different engine. Splitting the work over two or three streams, one per frame in flight, lets the copy engines and the SMs work in parallel, so the per-frame cost drops from copy plus compute plus copy to roughly the largest of the three.

Kernels from different streams can also run concurrently, but only when the first does not fill the GPU: a small kernel on one camera and a small kernel on another may share the SMs, while two large ones simply follow each other. Stream priorities (cudaStreamCreateWithPriority) let the block scheduler prefer blocks of a high-priority stream when SMs become free, which helps a latency-critical network overtake a background task, though it does not preempt blocks already running.

5.4Events: timing and dependencies

An event is a marker placed into a stream with cudaEventRecord. It completes when the stream reaches it. Events have three uses. They time GPU work without disturbing it: record one before and one after, then cudaEventElapsedTime gives the GPU time between them. They express dependencies between streams: cudaStreamWaitEvent(s2, e) makes everything queued later in s2 wait until e completes, with no CPU involvement. And they let the CPU wait efficiently for one specific point: cudaEventSynchronize(e) with an event created with cudaEventBlockingSync puts the thread to sleep instead of spinning a core.

cudaEvent_t start, stop, ready;
cudaEventCreate(&start); cudaEventCreate(&stop);
cudaEventCreateWithFlags(&ready, cudaEventDisableTiming | cudaEventBlockingSync);

cudaEventRecord(start, pre);                       // timing around the preprocessing kernel
preprocess<<<grid, block, 0, pre>>>(frame, input_tensor);
cudaEventRecord(stop, pre);
cudaEventRecord(ready, pre);
cudaStreamWaitEvent(infer, ready);                 // inference stream waits on the GPU, not on the CPU
context->enqueueV3(infer);                         // TensorRT engine reads input_tensor

cudaEventSynchronize(stop);                        // only when the number is needed
float ms; cudaEventElapsedTime(&ms, start, stop);
Pitfall

Timing with CPU clocks around a kernel launch measures the launch, not the kernel, because the launch returns immediately. Adding cudaDeviceSynchronize() before reading the clock fixes the number but changes the program you are measuring. Use events for GPU time, measure the end-to-end frame latency separately, warm up first (the first launches pay for lazy module loading and clock ramp-up), and report a median or percentile over many runs, not one value.

5.5Unified, mapped and managed memory

CUDA offers several ways for the CPU and GPU to see the same data. Device memory from cudaMalloc is GPU-only; the CPU reaches it only through copies. Mapped (zero-copy) host memory, pinned memory allocated with cudaHostAllocMapped, can be accessed by kernels directly through a device pointer; on a discrete GPU every such access crosses PCIe, so it suits data read once, such as a small parameter block, not data a kernel reads repeatedly. Managed memory from cudaMallocManaged gives one pointer valid on both sides; on discrete GPUs since Pascal, pages migrate on demand when the other side touches them, through page faults, and cudaMemPrefetchAsync can move them ahead of time.

Managed memory makes code simpler and is excellent for prototypes, tools and data structures with pointers in them. In a real-time pipeline on a discrete GPU, its page faults happen at unpredictable moments and cost tens of microseconds each, so production code prefers explicit buffers and copies, or managed memory with explicit prefetches. On an integrated SoC the picture changes completely, because there is only one physical memory (Chapter 11).

5.6CUDA Graphs and multi-GPU basics

A frame of a perception pipeline launches the same sequence of kernels and copies every time. A CUDA graph records that sequence once, with its dependencies, and replays it with a single launch. The easiest way to build one is stream capture: cudaStreamBeginCapture(s), run the frame's work as usual (kernel launches, copies, even a TensorRT enqueueV3), cudaStreamEndCapture(s, &graph), then cudaGraphInstantiate once and cudaGraphLaunch every frame. The driver validates and prepares everything at instantiation, so per-frame CPU cost drops from microseconds per kernel to a few microseconds for the whole graph, and the GPU runs the kernels back to back without launch gaps. Parameters that change per frame, such as the input buffer address when buffers rotate, are updated with cudaGraphExecKernelNodeSetParams or by capturing one graph per buffer.

Multi-GPU work appears in cars only on the largest central computers, and in training all the time. Each GPU is selected with cudaSetDevice and has its own memory and streams; peer-to-peer access (cudaDeviceEnablePeerAccess) lets one GPU read another's memory over NVLink or PCIe, and collective libraries such as NCCL implement all-reduce and broadcast on top of it.

5.7Errors and debugging

Because launches are asynchronous, CUDA reports errors in two places. A wrong launch configuration (too many threads per block, too much shared memory) is detected at launch and returned by cudaGetLastError(). An error during execution, such as an out-of-bounds access, is detected only later and returned by whatever CUDA call comes next, often a synchronisation in an unrelated part of the code. Such execution errors are sticky: the CUDA context is corrupted, every following call fails, and the only recovery is to restart the process. In a production system that means a GPU fault must be handled by a supervisor that restarts the pipeline, not by retrying the call.

Every CUDA call should be checked with a macro that reports file and line, and every launch followed by cudaGetLastError() in debug builds. The tool for finding the actual bug is compute-sanitizer: its memcheck tool reports out-of-bounds and misaligned accesses with the thread and source line, racecheck finds shared-memory races (a missing __syncthreads), initcheck uninitialised device memory and synccheck illegal barrier use. cuda-gdb steps through kernels thread by thread. Setting CUDA_LAUNCH_BLOCKING=1 makes every launch synchronous, so the failing call is the one that reports the error, which is often all that is needed.

6Writing kernels: one camera frame, step by step

This chapter writes the preprocessing kernel four times. The first version is what a port from OpenCV calls looks like, the second fuses everything but parallelises like CPU code, the third maps threads to pixels, the fourth specialises for the exact scale and moves 64 bits per access. Then the system around it removes the last copy and the launch overhead. Each step fixes one problem from Chapters 2 to 5.

6.1The task and its byte budget

The input is an NV12 frame of 1920 × 1080: 2,073,600 bytes of luma and 1,036,800 bytes of interleaved chroma, 3.11 MB. The output is a 960 × 544 × 3 tensor of FP16 in CHW layout, 3.13 MB. For each output pixel the kernel must find its position in the input, interpolate luma and chroma there, convert YUV to RGB with the BT.709 video-range matrix, clamp to [0, 255], normalise each channel with (v / 255 − mean) / std (folded into one multiply-add per channel), round to FP16 and write three values to three planes. Two rows at the top and two at the bottom are letterbox padding with the grey value 114.

The minimum traffic is reading the input once and writing the output once: 6.24 MB. On Orin that takes 30.5 µs at the theoretical 204.8 GB/s and about 42 µs at 150 GB/s, a realistic sustained rate for a streaming kernel. The arithmetic, about 34 operations per output pixel, is 18 MFLOP per frame, under 4 µs of the FP32 peak. This kernel is memory-bound by a factor of ten, so the goal is clear before writing a line: every version should be judged by how close it gets to 42 µs.

Interesting detail

Where exactly chroma samples sit relative to luma (chroma siting) differs between standards. The kernels here assume each chroma sample sits at the centre of its 2 × 2 luma block; H.264 and HEVC streams default to left siting, horizontally aligned with the even luma column. Ignoring the difference shifts colour by a quarter of a chroma pixel, which is invisible to a detector but shows up as colour fringes in a pixel-exact comparison against a reference implementation. Whatever convention is chosen, training and deployment must use the same one.

6.2v0: three kernels with FP32 intermediates

The first port follows the CPU pipeline it replaces: cvtColor, resize, then normalise and reorder to planar. Each becomes a kernel. The first converts the full 1920 × 1080 frame to an interleaved RGB image of 32-bit floats, 24.9 MB; the second reads that and writes a 960 × 540 float image, 6.2 MB; the third reads that, pads, normalises and writes the FP16 planes.

__global__ void k0_nv12_to_rgb(const uint8_t* y, const uint8_t* uv, int pitch, float* rgb, int W, int H) {
    int x = blockIdx.x * blockDim.x + threadIdx.x, r = blockIdx.y * blockDim.y + threadIdx.y;
    if (x >= W || r >= H) return;
    const uint8_t* c = uv + (r / 2) * pitch + (x / 2) * 2;        // chroma pair of this 2x2 block
    float3 p = yuv2rgb(y[r * pitch + x], c[0], c[1]);
    float* o = rgb + ((size_t)r * W + x) * 3;                    // interleaved HWC, FP32
    o[0] = clamp255(p.x); o[1] = clamp255(p.y); o[2] = clamp255(p.z);
}
// k0_resize: bilinear on the float image; k0_normalize: pad, (v * s + b), FP16, three planes

Each kernel on its own is reasonable: threads map to pixels along rows, so accesses coalesce. The problem is between them. The intermediate images go to DRAM and come back, and they are stored in the widest possible type. The three kernels move 28.0, 31.1 and 9.4 MB, 68.5 MB in total, eleven times the minimum, so even running each at full bandwidth the chain needs about 460 µs, plus three launches. Nothing inside a kernel can fix that; the structure has to change.

6.3v1: fused, but parallelised like CPU code

Fusing the three steps into one kernel removes the intermediates: each output value is computed from the input bytes and written once. A natural first attempt parallelises the outer loop, as one would with OpenMP on a CPU: one thread per output row, looping over the 960 pixels of its row.

__global__ void k1_fused_rows(const uint8_t* y, const uint8_t* uv, int pitch, int W, int H,
                              __half* out, int OW, int OH, int top, int rows, float s, Norm n) {
    int r = blockIdx.x * blockDim.x + threadIdx.x;            // lanes of a warp = 32 different rows
    if (r >= OH) return;
    size_t plane = (size_t)OW * OH;                          // (helpers shortened; full code in experiments/kernels.cu)
    for (int x = 0; x < OW; ++x) {
        float3 p = grey_or_sample(y, uv, pitch, W, H, x, r - top, rows, s);   // bilinear luma + chroma
        size_t o = (size_t)r * OW + x;
        out[o] = to_half(p.x, n, 0); out[plane + o] = to_half(p.y, n, 1); out[2 * plane + o] = to_half(p.z, n, 2);
    }
}

It reads 3.11 MB and writes 3.13 MB, the minimum, and it is the slowest version of all. Two of the earlier chapters explain why. There are only 544 threads, 17 warps for a GPU with room for 768: each SM gets about one warp, and every load stalls for the full memory latency with nothing to switch to (Section 4.1). And the 32 lanes of each warp work on 32 different rows, so each load instruction touches 32 addresses about 3840 bytes apart, 32 separate sectors with one useful byte each (Section 3.2). The model puts it at roughly 2000 cycles per pixel per thread, about 1.5 ms per frame. Correct fusion, wrong mapping.

6.4v2: one thread per output pixel

Mapping one thread to each output pixel, with threadIdx.x along the row and blocks of 32 × 8 threads, fixes both problems at once: 522,240 threads, and lanes of a warp working on 32 neighbouring pixels, so their luma reads fall into two sectors and their FP16 writes into two sectors per plane.

__global__ void k2_fused_pixels(const uint8_t* __restrict__ y, const uint8_t* __restrict__ uv, int pitch,
                                int W, int H, __half* __restrict__ out, int OW, int OH, int top, int rows,
                                float s, Norm n) {
    int x = blockIdx.x * blockDim.x + threadIdx.x;            // lanes of a warp = 32 neighbouring pixels
    int r = blockIdx.y * blockDim.y + threadIdx.y;
    if (x >= OW || r >= OH) return;
    int ri = r - top;
    float3 p = make_float3(114.f, 114.f, 114.f);              // letterbox rows
    if (ri >= 0 && ri < rows)
        p = sample_nv12(y, uv, pitch, W, H, (x + 0.5f) * s - 0.5f, (ri + 0.5f) * s - 0.5f);
    size_t plane = (size_t)OW * OH, o = (size_t)r * OW + x;
    out[o]             = __float2half(clamp255(p.x) * n.s[0] + n.b[0]);
    out[plane + o]     = __float2half(clamp255(p.y) * n.s[1] + n.b[1]);
    out[2 * plane + o] = __float2half(clamp255(p.z) * n.s[2] + n.b[2]);
}

The compiler output shows what remains to improve. ptxas reports 34 registers and no spills, so occupancy is 100 % with 256-thread blocks (Figure 4.2). The SASS has 199 instructions per thread, of which 12 are single-byte loads (LDG.E.U8.CONSTANT: four luma bytes and eight chroma bytes for the generic bilinear) and three are 16-bit stores (STG.E.U16). In total the kernel issues about 3.2 million warp instructions per frame; Orin's 64 schedulers issue one each per clock, so instruction issue alone takes about 39 µs, almost exactly as long as the memory traffic. A kernel that is near two limits at once rarely reaches either, and the model puts v2 at about 55–60 µs.

6.5v3: specialise for 2:1 and move 64 bits per access

The generic bilinear code handles any scale factor, but this camera and this network always use exactly 2:1. At that scale, with pixel-centre sampling, every output pixel lies exactly between four luma pixels with weights of one quarter, a 2 × 2 box average, and exactly on one chroma sample. Specialising for it removes all weight computation and all clamping of coordinates, and makes the access pattern perfectly regular: output pixels 4q to 4q+3 need luma bytes 8q to 8q+7 of two rows and chroma bytes 8q to 8q+7 of one row. Each thread now handles four output pixels, loads its inputs with three 64-bit loads and writes its outputs with three 64-bit stores.

__global__ void __launch_bounds__(256) k3_fused_2to1_vec(const uint8_t* __restrict__ y,
        const uint8_t* __restrict__ uv, int pitch, __half* __restrict__ out, int OW, int OH, int top, int rows, Norm n) {
    int q = blockIdx.x * blockDim.x + threadIdx.x;            // quad of output pixels 4q .. 4q+3
    int r = blockIdx.y * blockDim.y + threadIdx.y;
    if (q * 4 >= OW || r >= OH) return;
    int ri = r - top;
    size_t plane = (size_t)OW * OH, o = (size_t)r * OW + q * 4;
    __half h[3][4];
    if (ri >= 0 && ri < rows) {
        uint2 l0 = __ldg(reinterpret_cast<const uint2*>(y + (2 * ri) * pitch) + q);       // 8 luma bytes, row 2ri
        uint2 l1 = __ldg(reinterpret_cast<const uint2*>(y + (2 * ri + 1) * pitch) + q);   // 8 luma bytes, row 2ri+1
        uint2 c  = __ldg(reinterpret_cast<const uint2*>(uv + ri * pitch) + q);            // 4 UV pairs
        const uint8_t *a = (const uint8_t*)&l0, *b = (const uint8_t*)&l1, *cc = (const uint8_t*)&c;
        #pragma unroll
        for (int k = 0; k < 4; ++k) {
            float Y = 0.25f * (a[2 * k] + a[2 * k + 1] + b[2 * k] + b[2 * k + 1]);
            float3 p = yuv2rgb(Y, cc[2 * k], cc[2 * k + 1]);
            h[0][k] = __float2half(clamp255(p.x) * n.s[0] + n.b[0]);
            h[1][k] = __float2half(clamp255(p.y) * n.s[1] + n.b[1]);
            h[2][k] = __float2half(clamp255(p.z) * n.s[2] + n.b[2]);
        }
    } else { /* letterbox rows: constant grey, same three stores */ }
    #pragma unroll
    for (int c = 0; c < 3; ++c)
        *reinterpret_cast<uint2*>(out + c * plane + o) = *reinterpret_cast<uint2*>(h[c]);   // 4 halves = 64 bits
}

The SASS confirms the intent: the loads became LDG.E.64.CONSTANT, the stores STG.E.64, three of each per thread. Per output pixel that is 1.5 memory instructions instead of 15, and about 54 instructions instead of 199. Registers dropped to 24. Issue time falls to about 11 µs, well under the 42 µs of memory traffic, so the kernel is now purely memory-bound and runs, in the model, at about 46 µs: within 10 % of the floor. The specialisation has a price that must be written down next to the code: pitch must be a multiple of 8 and the output width a multiple of 4, and a different camera resolution needs the generic kernel back.

Pitfall

Fusion changes numerics. v0 clamped every full-resolution RGB pixel before averaging, the fused kernels average luma first and clamp once. The CPU emulation of all four kernels on a test frame gives identical outputs for v1, v2 and v3 (bit for bit) but differences from v0 of up to 0.53 in normalised units, about 30 levels of an 8-bit channel, at edges where the colour conversion saturates; the mean difference is 0.0075. Which one is "right" depends on what the network was trained with. Preprocessing is part of the model, and a change to it needs the same parity check against the training pipeline as a change of weights.

6.6v4: the system around the kernel

At 46 µs the kernel is no longer the problem; the code around it is. Two costs remain in a typical integration. The first is a copy of the camera frame into a cudaMalloc buffer before the kernel runs. On a discrete GPU this is a real PCIe transfer of 3.11 MB, about 125 µs pinned. On Orin it is worse than useless: CPU and GPU share DRAM, so the copy reads 3.11 MB and writes 3.11 MB to the same memory for nothing, about 40 µs of GPU time plus the CPU-side call, and it takes bandwidth from every other engine. Importing the camera buffer into CUDA directly (Section 11.2) removes it.

The second is launch overhead and synchronisation. If the preprocessing kernel writes straight into the TensorRT engine's input binding (the engine's input tensor address is set to the kernel's output buffer with setTensorAddress), runs in the same stream as enqueueV3, and the whole frame (preprocessing, engine, decoding) is captured into a CUDA graph, the CPU does one launch per frame and one wait at the end, and the GPU runs from the first kernel to the last without gaps.

Numbers

The model, per 1920 × 1080 frame on Orin: v0 about 470 µs (68.5 MB); v1 about 1.5 ms (6.2 MB, 17 warps); v2 about 58 µs (issue and memory both at ~40 µs); v3 about 46 µs against a floor of 42 µs. Avoided by v4: a 40 µs DRAM-to-DRAM copy on Orin, or 125–260 µs of PCIe transfer on a discrete GPU, plus per-kernel launch gaps of the engine. At 30 fps and eight cameras, the difference between v0 and v3 is about 100 ms of GPU time per second, a tenth of the GPU.

7Reductions, atomics and warp-level programming

Image kernels where every output depends only on a few inputs are the easy case. Many useful operations combine everything into a little: a sum, a maximum, a histogram for auto-exposure, a list of the detections above a threshold. Doing that in parallel needs threads to cooperate, and the way they cooperate decides whether the kernel runs at memory speed or a hundred times slower.

7.1Tree reduction in shared memory

A sum over n values cannot be split into independent pieces like a pixel operation, but addition is associative, so it can be done as a tree: pairs are added in parallel, then pairs of pairs, and after log₂ n steps one value remains. On a GPU each block reduces its part of the input in shared memory and writes one partial sum, and a second pass, or one atomic per block, combines the partial sums.

The way threads are assigned to the additions matters a great deal. The first version most people write uses interleaved addressing: in step s = 1, 2, 4, …, thread t adds element t+s into element t if t is a multiple of 2s. It is correct, but the active threads are spread out: in the first step every warp has half its lanes active, in the second a quarter, and all warps keep issuing instructions for a handful of lanes. The modulo operation is also slow on a GPU. Sequential addressing turns it around: in step s = n/2, n/4, …, thread t adds element t+s if t < s. The active threads are now packed at the start, so whole warps become idle and stop issuing, and consecutive threads read consecutive shared-memory words, without bank conflicts.

Mark Harris's NVIDIA presentation "Optimizing parallel reduction in CUDA" walks through seven versions of this kernel and gains a factor of about 30 from the first to the last; the ideas generalise to every reduction-like kernel. The two biggest steps are not about the tree at all. One is to let each thread first add many elements sequentially, in a grid-stride loop, so that the tree only combines a few hundred partial sums per block instead of reducing every element. The other is to finish the last 32 values inside a warp without shared memory.

7.2Warp shuffles and cooperative groups

Since Kepler, threads of a warp can read each other's registers directly with shuffle instructions. __shfl_down_sync(mask, v, k) returns the value of v held by the lane k positions higher; five shuffles with offsets 16, 8, 4, 2 and 1 reduce 32 values to one in lane 0, with no shared memory and no barrier. Related intrinsics broadcast a value from one lane (__shfl_sync), exchange with a lane at a given XOR distance (__shfl_xor_sync, which leaves the total in every lane), collect one bit per lane (__ballot_sync) or test a condition across the warp (__any_sync, __all_sync).

__device__ float warp_sum(float v) {
    for (int o = 16; o > 0; o >>= 1) v += __shfl_down_sync(0xffffffffu, v, o);
    return v;                                             // complete only in lane 0
}
__global__ void reduce_shuffle(const float* __restrict__ in, float* out, int n) {
    float v = 0.f;                                        // 1. each thread sums many elements (grid-stride)
    for (int i = blockIdx.x * blockDim.x + threadIdx.x; i < n; i += gridDim.x * blockDim.x) v += in[i];
    v = warp_sum(v);                                      // 2. 32 -> 1 inside each warp
    __shared__ float part[32];
    int lane = threadIdx.x & 31, w = threadIdx.x >> 5;
    if (lane == 0) part[w] = v;
    __syncthreads();
    if (w == 0) {                                         // 3. first warp reduces the per-warp sums
        v = lane < (blockDim.x >> 5) ? part[lane] : 0.f;
        v = warp_sum(v);
        if (lane == 0) atomicAdd(out, v);                 // 4. one atomic per block
    }
}

Compiled for Orin, this kernel uses 12 registers and 128 bytes of shared memory; its SASS has ten SHFL.DOWN instructions (five per warp_sum), one barrier and a single RED.E.ADD.F32, the fire-and-forget form of an atomic add that the compiler uses when the return value is not needed. The kernel reads every input byte once and does almost nothing else, so it runs at memory speed: 8 Mi floats (32 MB) take about 220 µs at 150 GB/s.

Cooperative groups are the C++ face of the same features: cg::tiled_partition<32>(cg::this_thread_block()) gives an object for the warp with shfl_down, sync and cg::reduce(tile, v, cg::plus<float>()), and smaller tiles of 16, 8 or 4 threads for algorithms that work on groups narrower than a warp. CUB's cub::WarpReduce, cub::BlockReduce and cub::DeviceReduce package tuned versions for every level; in production code they are the default choice.

Pitfall

Floating-point addition is not associative, so a parallel sum depends on the order of the tree, and a version with one atomic per block depends on the order in which blocks finish. Two runs of the same kernel on the same data can differ in the last bits. For a loss or a mean that is harmless; for a test that compares outputs bit for bit, or for a safety argument that requires reproducible results, use a fixed-order two-pass reduction instead of atomics, or accumulate in higher precision.

7.3Atomics and the histogram

An auto-exposure or tone-mapping algorithm needs a histogram of the luma plane: 256 counters, one per grey level, incremented once per pixel. The obvious kernel has each thread read a pixel and do atomicAdd(&bins[value], 1) in global memory. Atomics are executed in the L2 cache, and atomics to the same address are serialised there. For a natural image that is spread over many grey levels this works reasonably; for an underexposed night frame where most pixels have values 16–20, millions of increments queue on five addresses, and the kernel slows down by an order of magnitude exactly when the algorithm that uses it matters most.

The fix is privatisation: each block keeps its own 256-bin histogram in shared memory, where atomics are executed on the SM and contention is limited to one block's threads, and at the end adds its bins to the global histogram with 256 global atomics. The data-dependent contention moves from the whole GPU to one block, and the global traffic drops from one atomic per pixel to 256 per block.

__global__ void hist_shared(const uint8_t* __restrict__ img, int n, unsigned* bins) {
    __shared__ unsigned h[256];
    for (int b = threadIdx.x; b < 256; b += blockDim.x) h[b] = 0;
    __syncthreads();
    for (int i = blockIdx.x * blockDim.x + threadIdx.x; i < n; i += gridDim.x * blockDim.x)
        atomicAdd(&h[img[i]], 1u);                        // on-chip, contention only within the block
    __syncthreads();
    for (int b = threadIdx.x; b < 256; b += blockDim.x)
        if (h[b]) atomicAdd(&bins[b], h[b]);              // 256 global atomics per block
}
Interesting detail

The SASS of this kernel for Orin does not contain a plain shared-memory atomic add at all. The compiler recognised that every lane adds the constant 1 and emitted ATOMS.POPC.INC.32: the hardware groups the lanes of the warp that target the same bin, counts them with a population count, and performs one increment by that count per distinct address. This warp-aggregated atomic is exactly the optimisation that hand-written histogram code used to do with __match_any_sync and __popc; on this generation the compiler does it for you, which is another reason to read the SASS before optimising by hand.

A 1920 × 1080 luma plane is 2 MB, so the histogram's floor is about 14 µs. If the histogram only feeds auto-exposure, computing it on every second row and column (a quarter of the pixels) is statistically just as good and four times cheaper, which is the kind of decision that matters more than any kernel optimisation.

7.4Scan and stream compaction

A detector head produces a score for every anchor point: for a 960 × 544 input at strides 8, 16 and 32 that is 120 × 68 + 60 × 34 + 30 × 17 = 10,710 points per class. Only a few dozen pass the confidence threshold, and only those should go to box decoding and non-maximum suppression. Turning "a flag per element" into "a dense list of the flagged elements" is stream compaction, and its core is a prefix sum (scan): if each element knows how many flagged elements come before it, it knows where to write itself.

Inside a warp this is cheap: __ballot_sync gives a 32-bit mask of which lanes passed, and each lane's output position is the population count of the mask bits below its own lane (__popc(mask & ((1u << lane) - 1))); lane 0 reserves space for the whole warp with one atomic on a global counter. Across a whole array, parallel scan algorithms (Blelloch's work-efficient scan, or the decoupled look-back scan that CUB uses) run in one pass at memory speed. cub::DeviceSelect::If and thrust::copy_if implement compaction directly. The same pattern serves point-cloud processing (keep the points inside the region of interest), sparse convolutions (list the active voxels) and moving rare expensive cases out of a divergent kernel (Section 2.4).

8Matrix multiply: tiling, register blocking and tensor cores

Matrix multiplication is the one operation with enough arithmetic per byte to make a GPU compute-bound, and almost every layer of a neural network is a matrix multiply in disguise. Writing a fast one by hand is an exercise in moving data up the memory hierarchy so that each value fetched from DRAM is used dozens of times. Nobody ships a hand-written one, but everyone who writes kernels should know how the fast ones work.

8.1The naive kernel and why it is memory-bound

Multiplying two N × N matrices takes 2N³ operations on 3N² values, so in principle each value is used about N times. The naive kernel gives each thread one element of C and lets it loop over a row of A and a column of B: 2N loads for 2N operations, an intensity of 0.25 FLOP per byte in FP32 if nothing is reused, a hundred times left of Orin's ridge. In practice L1 and L2 catch part of the reuse, because neighbouring threads read the same row of A and neighbouring columns of B, but the kernel still issues two load instructions per multiply-add and spends its time in the memory pipeline. Its SASS for Orin has 58 global load instructions, because the compiler unrolled the k loop, against a single store.

8.2Shared-memory tiling and register blocking

Tiling makes the reuse explicit. A block of T × T threads computes a T × T tile of C. It walks along the shared dimension in steps of T: in each step every thread loads one element of a T × T tile of A and one of B into shared memory, the block synchronises, and then every thread does T multiply-adds reading only shared memory. Each value loaded from global memory is used T times, and the intensity rises to T/4 FLOP per byte: 8 for T = 32.

constexpr int T = 32;
__global__ void mm_tiled(const float* __restrict__ A, const float* __restrict__ B, float* C, int N) {
    __shared__ float As[T][T], Bs[T][T];
    int tx = threadIdx.x, ty = threadIdx.y, col = blockIdx.x * T + tx, row = blockIdx.y * T + ty;
    float acc = 0.f;
    for (int k0 = 0; k0 < N; k0 += T) {
        As[ty][tx] = A[row * N + k0 + tx];                // coalesced: tx runs along a row of A
        Bs[ty][tx] = B[(k0 + ty) * N + col];              // coalesced: tx runs along a row of B
        __syncthreads();
        for (int k = 0; k < T; ++k) acc += As[ty][k] * Bs[k][tx];   // As: broadcast, Bs: conflict-free
        __syncthreads();                                  // before the tiles are overwritten
    }
    C[row * N + col] = acc;
}

The inner loop now reads shared memory twice per multiply-add, and shared memory, at 128 bytes per clock per SM, becomes the next bottleneck. Register blocking removes it: each thread computes a small tile of C, for example 4 × 4, keeping 16 accumulators in registers; per step of k it loads four values of A and four of B from shared memory into registers and does 16 multiply-adds, an outer product. The ratio of arithmetic to shared-memory loads goes from 1:2 to 2:1. The mm_regblock kernel in the experiments does this with a 64 × 64 block tile and 256 threads; ptxas gives it 40 registers, and its SASS shows the loads from shared memory as LDS.128, four floats per instruction. Production GEMMs go further: larger register tiles per thread, double-buffered shared memory loaded with cp.async while the previous tile is consumed, and a warp-level tile layout tuned per GPU.

Numbers

Intensity against DRAM for FP32 GEMM if each tile is fetched once: naive 0.25, 32 × 32 shared tiles 8, 64 × 64 block tiles 16 FLOP per byte. The Orin FP32 ridge is 26, so even the register-blocked kernel needs L2 reuse between blocks to become compute-bound; with FP16 tensor cores the ridge rises to about 200 and only large tiles get there. The 32 × 32 version launches 1024-thread blocks, which on Orin means one block and 67 % occupancy per SM (Figure 4.2).

8.3Tensor cores

A tensor core executes a small matrix multiply-accumulate as one instruction for a whole warp: the 32 lanes together hold fragments of an A tile, a B tile and an accumulator tile in their registers, and the instruction computes D = A·B + C. On Ampere one such instruction, mma.sync.m16n8k16 in PTX and HMMA.16816 in SASS, multiplies a 16 × 16 FP16 tile by a 16 × 8 tile with FP32 accumulation: 4096 operations. Supported input types on Ampere are FP16, BF16, TF32 (FP32 values rounded to a 10-bit mantissa), INT8 and INT4, and the hardware can skip half the multiplications of a 2:4 structured-sparse matrix.

using namespace nvcuda;
__global__ void mm_wmma(const __half* A, const __half* B, float* C, int N) {   // one warp per 16x16 tile of C
    int warp = (blockIdx.x * blockDim.x + threadIdx.x) / 32, tn = N / 16, tr = warp / tn, tc = warp % tn;
    wmma::fragment<wmma::matrix_a, 16, 16, 16, __half, wmma::row_major> a;
    wmma::fragment<wmma::matrix_b, 16, 16, 16, __half, wmma::row_major> b;
    wmma::fragment<wmma::accumulator, 16, 16, 16, float> c;
    wmma::fill_fragment(c, 0.f);
    for (int k = 0; k < N; k += 16) {
        wmma::load_matrix_sync(a, A + tr * 16 * N + k, N);
        wmma::load_matrix_sync(b, B + k * N + tc * 16, N);
        wmma::mma_sync(c, a, b, c);                       // SASS: two HMMA.16816.F32 per call
    }
    wmma::store_matrix_sync(C + tr * 16 * N + tc * 16, c, N, wmma::mem_row_major);
}

The WMMA API above is the simplest way in: it hides the fragment layout and compiles each 16 × 16 × 16 mma_sync into two HMMA.16816.F32 instructions, as the Orin SASS shows. This version still loads its fragments straight from global memory, so it is memory-bound like the naive kernel; a fast tensor-core GEMM combines it with everything in Section 8.2, staging tiles in shared memory with cp.async, loading fragments with ldmatrix, and keeping several accumulator tiles per warp. Hopper adds warp-group instructions (wgmma) that read operands directly from shared memory and a tensor memory accelerator (TMA) that copies whole tiles asynchronously; each generation changes the best structure, which is why this layer lives in libraries.

Pitfall

Tensor cores change numerics. FP16 inputs have an 11-bit mantissa, TF32 a 10-bit one, and accumulation order differs from a CPU loop. PyTorch and cuBLAS may use TF32 for FP32 matrix multiplies on Ampere and later depending on settings (torch.backends.cuda.matmul.allow_tf32, torch.set_float32_matmul_precision), which silently changes results in the fourth significant digit. When a comparison between GPU and reference fails at 1e-4, check the math mode before looking for a bug.

8.4Convolution as matrix multiply

A convolution layer with C input channels, K output channels and an R × S kernel can be written as a matrix multiply: unfold every R × S × C input patch into a row (im2col) and multiply the resulting matrix by the K × (RSC) weight matrix. Materialising the unfolded matrix multiplies memory by RS, nine times for 3 × 3 kernels, so fast libraries use implicit GEMM: the GEMM's tile loader computes the patch addresses on the fly and never writes the unfolded matrix. Other algorithms (Winograd for 3 × 3, FFT for large kernels, direct convolution for depthwise layers) win in some shapes, and cuDNN and TensorRT choose between them by timing candidates on the actual GPU during engine build, which is one reason an engine must be built on the hardware it runs on.

9.2TensorRT custom plugins

TensorRT compiles a network from ONNX into an engine of tuned kernels. When the network contains an operation TensorRT does not support, or supports badly, such as a deformable attention sampler for BEV networks, a voxel scatter for point-pillar networks or a custom NMS, the operation is implemented as a plugin: a C++ class whose kernels TensorRT calls at the right place in the engine. In TensorRT 10 the interface is IPluginV3, split into capability interfaces: the core part (name, version, clone), the build part, which tells the builder the output shapes and data types and which formats it supports, and the runtime part, whose enqueue does the work. The older IPluginV2DynamicExt still works but is deprecated.

class VoxelScatterPlugin : public IPluginV3, public IPluginV3OneCore,
                           public IPluginV3OneBuild, public IPluginV3OneRuntime {
  public:
    // build: which input/output formats can the kernel handle? The builder tries only those.
    bool supportsFormatCombination(int32_t pos, DynamicPluginTensorDesc const* io,
                                   int32_t nbIn, int32_t nbOut) noexcept override {
        return io[pos].desc.format == TensorFormat::kLINEAR &&
               (io[pos].desc.type == DataType::kHALF || io[pos].desc.type == DataType::kFLOAT);
    }
    // runtime: launch on TensorRT's stream, use only the provided workspace, never synchronise.
    int32_t enqueue(PluginTensorDesc const* inDesc, PluginTensorDesc const* outDesc,
                    void const* const* inputs, void* const* outputs, void* workspace,
                    cudaStream_t stream) noexcept override {
        int n = inDesc[0].dims.d[0];
        scatter_kernel<<<(n + 255) / 256, 256, 0, stream>>>(inputs[0], inputs[1], outputs[0], n, gridW_, gridH_);
        return cudaPeekAtLastError() == cudaSuccess ? 0 : -1;
    }
    // ... getOutputShapes, getOutputDataTypes, getFieldsToSerialize, clone, attachToContext ...
};

Four rules make a plugin behave inside an engine. Launch everything on the stream TensorRT passes in, so the plugin is ordered with the rest of the engine and can be captured in a CUDA graph. Never allocate memory or synchronise in enqueue; ask for scratch space through the workspace size instead. Declare only the formats and precisions the kernel really handles, and handle every one you declare, including FP16 inputs when the engine is built with FP16. And make the result deterministic and testable: a plugin is model code, and it needs the same parity test against the framework implementation as the rest of the network. A plugin creator class, registered with REGISTER_TENSORRT_PLUGIN or through a plugin library loaded at run time, lets the ONNX parser map a custom node of the same name to the plugin.

9.3Triton kernels

Triton is a Python-embedded language for GPU kernels in which the programmer writes code for a block of data rather than for one thread. A Triton program instance loads a vector or tile with tl.load, computes on whole tiles, and stores them; the compiler decides how to spread the tile over threads, vectorises and coalesces the accesses, uses shared memory and tensor cores for tl.dot, and generates PTX through MLIR. It is what torch.compile uses to generate fused kernels for PyTorch models, and it is a quick way to write a custom fused operation for training or research without writing CUDA C++.

import triton, triton.language as tl

@triton.jit
def scale_bias_relu(x_ptr, out_ptr, n, scale, bias, BLOCK: tl.constexpr):
    pid = tl.program_id(0)                       # one program instance per BLOCK elements
    offs = pid * BLOCK + tl.arange(0, BLOCK)     # a vector of offsets, not one index
    mask = offs < n
    x = tl.load(x_ptr + offs, mask=mask)
    tl.store(out_ptr + offs, tl.maximum(x * scale + bias, 0.0), mask=mask)

grid = (triton.cdiv(n, 1024),)
scale_bias_relu[grid](x, out, n, 0.5, 0.1, BLOCK=1024)

Triton covers element-wise fusion, reductions, softmax, layer norm and GEMM-like kernels very well, with performance close to hand-written CUDA after its autotuner tries a few block sizes. It gives less control over warp-level details, depends on a Python toolchain at build time, and its output is a PTX or cubin that must be loaded by something else in a product. In automotive deployment it therefore appears mostly indirectly, in training and in models exported after torch.compile, while production kernels on the target are CUDA C++ or TensorRT plugins.

9.4Choosing between a library, a custom kernel and Triton

The order of preference in practice: first check whether the operation can be expressed with layers TensorRT already handles, since anything inside the engine benefits from its fusion and tactic selection. Next, use a library for large standard operations. Write a custom CUDA kernel when the operation is a chain of cheap steps that should be fused (preprocessing, decoding), when its access pattern is irregular (scatter into a voxel grid, gather by a lookup table), or when it must be integrated as a plugin. Use Triton when the kernel is needed in PyTorch for training or experiments, and port it to CUDA C++ when it moves to the target. In every case, the first version should be the simplest correct one, measured, and compared against the bandwidth floor before anyone optimises it.

10Profiling and the optimisation method

Optimising GPU code without a profiler is guessing, and guessing is usually wrong because the expensive part of a pipeline is rarely where the code looks expensive. NVIDIA's tools split the job in two: Nsight Systems shows the whole timeline and where the GPU waits, Nsight Compute looks inside one kernel and tells you which limit it hits. Use them in that order.

10.1The method

Start from the number that matters to the product, usually the end-to-end latency of a frame at a percentile, measured on the target under realistic load. Then look at the timeline to see how that time divides between CPU work, copies, kernels and idle gaps; a frame that takes 8 ms of which the GPU is busy for 4 has 4 ms of system problems that no kernel optimisation will touch. Only when a kernel is clearly the largest block on the timeline, look inside it: compute its bytes and operations, see where it sits on the roofline, and let the profiler tell you which hardware unit is the limit and why warps stall. Change one thing, measure again, and keep the measurements; the order of magnitude of what each step bought is the knowledge you will reuse.

10.2Nsight Systems: the timeline

Nsight Systems records what every CPU thread, every CUDA API call, every kernel and copy and, on Jetson and DRIVE, the DLA and other engines do over time. It runs on the target with low overhead (nsys profile -t cuda,nvtx,osrt -o frame ./app) and is opened in the GUI on a workstation. Adding NVTX ranges to the application, one call to mark the start and end of "preprocess", "inference" or "frame 1234", makes the timeline readable and is worth doing in every production code base, since the ranges cost almost nothing when no profiler is attached.

#include <nvtx3/nvToolsExt.h>
void process(Frame& f) {
    nvtxRangePushA("frame");                     // shows up as a named bar on this thread's row
    nvtxRangePushA("preprocess"); launch_preprocess(f, stream); nvtxRangePop();
    nvtxRangePushA("infer");      context->enqueueV3(stream);   nvtxRangePop();
    nvtxRangePop();
}

The patterns to look for are few and recur in every project. Gaps on the GPU row while the CPU row shows API calls mean the GPU is starved by launch overhead or by the CPU doing work between launches. Long red cudaStreamSynchronize or cudaMemcpy blocks mean the CPU waits for the GPU and cannot prepare the next frame. Copies on a Jetson mean someone is moving data inside one DRAM. Kernels of different streams that should overlap but are serialised often point to the legacy default stream or an implicit synchronisation such as cudaMalloc in the frame loop.

10.3Nsight Compute: inside one kernel

Nsight Compute profiles individual kernels by replaying them several times with different hardware counters enabled, then presents the results in sections. A typical command profiles one launch of one kernel after a warm-up: ncu --set full -k regex:k3_fused --launch-skip 10 --launch-count 1 -o pre ./bench. The sections worth reading first are these.

The stall reasons are the most useful diagnostic once the obvious limits are understood. Long scoreboard means warps wait for data from L1TEX, that is global or local memory: more bytes in flight per warp (ILP, vector loads) or fewer bytes in total help. Short scoreboard means waiting for shared memory or the special-function unit, often bank conflicts. Barrier means threads wait at __syncthreads for slower threads of their block. MIO throttle and LG throttle mean the memory instruction queues are full, typically because there are too many small memory instructions, which vector accesses fix. Math pipe throttle means the arithmetic units are saturated, the good kind of limit. Not selected means warps were ready but another was chosen: the scheduler had enough work.

Pitfall

Nsight Compute changes what it measures. By default it locks the GPU clocks to base frequency for repeatable numbers, serialises kernels that would overlap, flushes caches between replay passes, and each pass reruns the kernel. Durations in Nsight Compute are therefore longer than in the application and must not be compared with Nsight Systems or event timings. Use Nsight Compute for ratios and reasons, and Nsight Systems or CUDA events for time.

Numbers

Metrics worth knowing by name, since they appear in reports and discussions: dram__throughput.avg.pct_of_peak_sustained_elapsed (DRAM bandwidth used), sm__throughput.avg.pct_of_peak_sustained_elapsed (busiest SM unit), sm__warps_active.avg.pct_of_peak_sustained_active (achieved occupancy), l1tex__t_sectors_pipe_lsu_mem_global_op_ld.sum divided by l1tex__t_requests_pipe_lsu_mem_global_op_ld.sum (sectors per load request: 4 for coalesced 32-bit loads, up to 32 for scattered ones), and l1tex__data_bank_conflicts_pipe_lsu_mem_shared.sum (shared-memory bank conflicts).

10.4The kernel roofline in practice

The roofline of Section 3.5 becomes a working tool once each kernel of a pipeline is placed on it with measured values: intensity from the bytes Nsight Compute counted at DRAM, performance from the operations and the measured time. Two numbers then describe every kernel: which roof it is under, and what fraction of that roof it reaches. A memory-bound kernel at 80 % of bandwidth is finished; one at 20 % has an access-pattern problem (coalescing, too few bytes in flight). A compute-bound kernel far below the arithmetic roof usually lacks instruction-level parallelism or uses the wrong units (FP32 lanes instead of tensor cores, or FP64 by accident). The same analysis at network level, layer by layer, explains why some layers of a detector are cheap in FLOPs but expensive in time.

10.5Common performance bugs

Most slow GPU code in practice has one of a dozen causes, and checking them in order is faster than general exploration. At system level: data copied that could be shared (on Jetson, any copy between CPU and GPU buffers), pageable memory in copies, synchronisation inside the frame loop, the legacy default stream serialising streams, allocations in the frame loop, and many tiny kernels whose launch cost exceeds their work (fuse them, or use a graph). Inside kernels: threads mapped across rows instead of along them, array-of-structures data where only one field is read, an intermediate image written to DRAM between two kernels that could be one, a shared-memory tile without padding, atomics on a few hot addresses, divergent branches on per-pixel data, too few threads to fill the GPU, accidental double precision, and register spills in the inner loop. On embedded targets, add clocks: a benchmark run while the GPU is still at a low power-mode frequency, or after it has throttled thermally, measures the power manager, not the kernel.

11CUDA on embedded SoCs

In a car, the GPU is not a card in a slot but one block of a system-on-chip that also contains CPUs, an ISP, deep-learning accelerators, a video encoder and a display controller, all sharing one DRAM and one power budget. CUDA code is the same, but the rules for memory, copies and timing change, and the GPU is one engine among several that must cooperate without copying data between them.

11.1What changes on an integrated GPU

Jetson modules and the DRIVE platforms use NVIDIA SoCs with an integrated GPU: Xavier (Volta, compute capability 7.2), Orin (Ampere, 8.7) and the Blackwell-based Thor generation. The GPU has no memory of its own. cudaMalloc allocates from the same LPDDR that the CPU's malloc uses, and the difference between memory types is only in how pages are mapped and cached, not where they are. Three consequences follow. A cudaMemcpy between host and device memory is a DRAM-to-DRAM copy that wastes bandwidth and time without moving data anywhere useful. Memory bandwidth, not PCIe, is the shared bottleneck: the GPU, CPU, DLA, ISP, encoder and display all draw from the same 204.8 GB/s on Orin. And the choice of memory type is about caching and coherence, which NVIDIA's "CUDA for Tegra" application note documents per SoC generation.

11.2Zero-copy camera buffers

On Jetson, camera frames from libargus or V4L2 land in NvBufSurface buffers, which are dma-buf file descriptors underneath; on DRIVE OS, frames from NvMedia and NvSIPL are NvSciBuf objects. In both cases the frame is already in DRAM and the task is to give CUDA a pointer to it. On Jetson the long-standing route goes through EGL: map the surface to an EGLImage, register it with CUDA's graphics interop, and get back either plane pointers (for pitch-linear buffers) or CUDA arrays (for block-linear ones). On DRIVE OS, cudaImportExternalMemory with an NvSciBuf handle maps the buffer, and cudaImportExternalSemaphore with an NvSciSync object lets CUDA wait for the camera's completion fence and signal its own, so the hand-over between engines happens without the CPU waiting at all.

// Jetson: NvBufSurface (dma-buf) -> EGLImage -> CUDA pointers, no copy
NvBufSurfaceMapEglImage(surf, 0);                                   // creates surf->surfaceList[0].mappedAddr.eglImage

CUgraphicsResource res;  CUeglFrame frame;

Two details decide whether this works in practice. First, buffers are registered once, at start-up, for each buffer of the camera's ring, not per frame: registration costs far more than the kernel. Second, the buffer's memory layout must match what the kernel expects. ISPs and video decoders often produce block-linear surfaces, a tiled layout that suits the hardware engines but cannot be indexed as y · pitch + x. Either the camera is configured to produce pitch-linear output, the VIC engine converts the layout in hardware (NvBufSurfTransform, which is a copy, but one done by a dedicated engine), or the kernel reads the block-linear surface through a CUDA array and a texture or surface object, which handles the tiling.

Pitfall

Zero-copy moves the synchronisation problem to you. The camera driver will reuse a buffer as soon as it gets it back, so the frame must not be returned to the capture queue until the kernel that reads it has finished, which means waiting on a CUDA event or fence, not on the kernel launch. Returning it too early produces frames that are half old and half new, an error that looks like a sensor fault and appears only under load.

11.3Sharing the SoC: engines, clocks and timing

An Orin also has two deep-learning accelerators (DLA), a programmable vision accelerator (PVA), the VIC for scaling and format conversion, and hardware video codecs. Good systems give each engine the work it does most efficiently, so the GPU is not spent on what another engine can do for less power: a detector compiled for the DLA, warps and layout conversions on VIC, feature tracking on PVA through VPI. TensorRT and cuDLA run networks on the DLA, and the hand-over between a GPU kernel and a DLA network uses the same imported buffers and fences as the camera path. The cost is more synchronisation points, and every engine still draws on the same DRAM bandwidth.

Timing on an SoC depends on power management. The power mode (nvpmodel on Jetson) sets maximum clocks and the number of active CPU cores; dynamic frequency scaling lowers clocks when the load is light; thermal management lowers them when the module is hot. For benchmarks, fix the clocks (jetson_clocks on Jetson) and say so in the report; for the product, measure at the clocks the vehicle's thermal design will allow in the worst case. GPU work from different processes is time-sliced between contexts, which adds jitter, so a latency-critical pipeline is best kept in one process with prioritised streams.

11.4OpenCL and Vulkan compute compared

CUDA runs only on NVIDIA GPUs. Two open standards cover the same ground on other hardware. OpenCL (Khronos, since 2009) is the closest relative: kernels in a C-based language (or C++ for OpenCL) are compiled at run time from source or loaded as SPIR-V, launched over an NDRange of work-items grouped into work-groups, with __local memory as the equivalent of shared memory. It is the main GPU compute API on Qualcomm Adreno and Arm Mali GPUs, which makes it relevant for automotive SoCs that do not come from NVIDIA; NVIDIA's discrete GPUs support it, but Jetson and DRIVE do not. Vulkan compute runs compute shaders (written in GLSL or HLSL and compiled to SPIR-V) through the same explicit API used for graphics: descriptor sets bind buffers, pipeline barriers order work, and synchronisation is entirely the application's job. It is verbose, but it shares memory and synchronisation with rendering, which suits surround-view and AR pipelines, and it runs everywhere a modern GPU does; Vulkan SC is a reduced variant for safety-critical systems.

QSelf-check questions

Core questions with short model answers; the chapter sections hold the depth. The second group checks understanding with "why" and "what if" questions rather than definitions.

Q.1Core questions

Explain the CUDA thread hierarchy and how it maps to the hardware.Basic

A kernel launch creates a grid of blocks; each block has up to 1024 threads. A block runs entirely on one SM and its threads can share shared memory and synchronise with __syncthreads; blocks are independent and may run in any order. Inside an SM, threads are grouped into warps of 32 consecutive threads, each warp assigned to one of the SM's schedulers, which issues one instruction per cycle for one ready warp. The independence of blocks is what lets the same code scale from 16 SMs to over a hundred.

What is a warp, and what is warp divergence?Basic

A warp is 32 threads that the hardware issues together, one instruction for all lanes. If lanes of a warp take different branches, the warp executes both paths one after the other with the inactive lanes masked, then reconverges, so the cost is the sum of the paths. Divergence between different warps costs nothing. Remedies: predication for short branches (the compiler does it), arranging data so lanes of a warp take the same path, or moving rare expensive cases to a separate kernel over a compacted list.

What is memory coalescing and why does it matter?Basic

The load/store unit turns a warp's 32 addresses into 32-byte sector transactions. If consecutive lanes access consecutive addresses, the warp's request is served with the minimum number of sectors (four for 32 floats); if the addresses are strided or scattered, each lane can need its own sector and most of the transferred bytes are wasted. Since most kernels are memory-bound, coalescing often decides performance by a factor of several. In practice: threadIdx.x along rows, structure-of-arrays layouts, aligned vector loads.

What is shared memory, and what is a bank conflict?Basic

Shared memory is fast on-chip memory, up to 164 KB per SM on Orin, shared by the threads of a block and managed explicitly; it is used for data reused by several threads, such as tiles in a convolution or matrix multiply, and for exchanging data between threads. It is split into 32 banks of 4-byte words. When lanes of a warp access different words in the same bank, the accesses are serialised: an n-way conflict costs n cycles. The classic fix is padding, such as tile[32][33] for a transpose, so that a column falls into different banks.

What is occupancy, and what limits it?Intermediate

Occupancy is the number of warps resident on an SM relative to the maximum (48 on Orin, 64 on A100). It is limited by the warp slots and block slots, by registers per thread (64 K registers per SM, allocated per warp), and by shared memory per block. It matters because resident warps are what the scheduler switches between to hide latency. But high occupancy is not a goal in itself: kernels with lots of instruction-level parallelism, such as register-blocked GEMMs, run fastest at 25–50 % occupancy.

How do you hide memory latency on a GPU?Intermediate

By having enough independent memory requests in flight: by Little's law, bandwidth times latency, about 110 KB on Orin. Two ways: many resident warps (occupancy), so the scheduler always has a ready warp while others wait; and more independent work per warp (instruction-level parallelism): process several elements per thread, use vector loads, unroll loops, issue loads early. Asynchronous copies into shared memory and double buffering overlap loading the next tile with computing the current one.

What are streams and how do you overlap copies with computation?Intermediate

A stream is an in-order queue of GPU work; work in different streams has no ordering and can run concurrently. To overlap, allocate host buffers as pinned memory, issue cudaMemcpyAsync and kernel launches for different frames or chunks in different streams, and express real dependencies with events (cudaStreamWaitEvent). The copy engines then transfer one chunk while the SMs process another. Avoid the legacy default stream, implicit synchronisations (cudaMalloc, synchronous copies) and synchronising inside the loop.

Pinned, mapped, managed memory: what is the difference?Intermediate

Pinned (page-locked) host memory cannot be moved by the OS, so DMA engines read it directly, enabling fast asynchronous copies. Mapped pinned memory is additionally given a device address so kernels access it directly over the bus, good for data read once. Managed memory gives one pointer valid on CPU and GPU, migrating pages on demand on discrete GPUs; convenient but with unpredictable page-fault costs unless prefetched. On an integrated GPU like Orin all of them live in the same DRAM and differ only in caching and coherence.

How would you write a fast parallel sum?Intermediate

Launch a grid that fills the GPU a few times over; each thread accumulates many elements in a grid-stride loop with coalesced loads; each warp reduces its 32 values with five __shfl_down_sync steps; warp results go to shared memory and the first warp reduces them; finally one atomic per block or a second small kernel combines blocks. The kernel is memory-bound and should reach most of the DRAM bandwidth. In production, cub::DeviceReduce. Mention that floating-point order makes results not bit-reproducible with atomics.

How do you optimise a matrix multiply in CUDA?Advanced

The naive kernel loads two values per multiply-add and is memory-bound. Tile it: each block loads tiles of A and B into shared memory, synchronises and reuses each value T times, raising intensity to T/4 FLOP per byte in FP32. Then register-block: each thread computes a small tile of C from values held in registers, so the inner loop does more multiply-adds than shared loads, with vector shared loads. Then double-buffer with asynchronous copies, avoid bank conflicts, and use tensor cores via mma.sync or WMMA with FP16/BF16/TF32. In practice use cuBLAS or CUTLASS, which do all of this per architecture.

What are tensor cores and how do you use them?Intermediate

Units that execute a small matrix multiply-accumulate per warp instruction, for example m16n8k16 with FP16 inputs and FP32 accumulation on Ampere, 4096 operations in one instruction; they provide most of a modern GPU's arithmetic throughput. You use them through cuBLAS, cuDNN and TensorRT (choosing FP16, BF16, TF32 or INT8), through CUTLASS templates, through Triton's tl.dot, or directly with the WMMA API or mma.sync PTX. Data must be in a supported precision and layout, and dimensions should be multiples of 8 or 16.

How do you profile a slow CUDA application?Intermediate

Measure end-to-end first. Then Nsight Systems for the timeline: GPU idle gaps, synchronisations, copies, launch overhead, CPU work in the critical path; NVTX ranges make it readable. Then Nsight Compute on the dominant kernel: Speed Of Light to see whether it is memory- or compute-bound, memory analysis for sectors per request and bank conflicts, occupancy, and warp stall reasons. Compare with the roofline estimate made beforehand. Remember Nsight Compute locks clocks and replays kernels, so its durations are not application timings.

What is a TensorRT plugin and what must its enqueue do?Intermediate

A C++ class (IPluginV3 in TensorRT 10) implementing an operation the engine does not support natively. The build interface reports output shapes, types and supported formats; the runtime interface's enqueue launches the kernels. It must use the stream it is given, not allocate memory or synchronise (scratch space comes from the workspace), handle every format and precision it declared, and be deterministic and tested against the framework's implementation. A creator registers it so the ONNX parser can map a custom node to it.

What changes when you program the GPU in a Jetson or DRIVE Orin instead of a discrete GPU?Intermediate

The GPU shares DRAM with the CPU and all other engines; there is no PCIe and no separate VRAM, so host-device copies are pointless DRAM-to-DRAM copies. Camera buffers are imported into CUDA (EGLImage on Jetson, NvSciBuf on DRIVE) and handed between engines with events or fences. Bandwidth is shared with the ISP, DLA, encoder and display, so total traffic matters more than kernel speed. Clocks depend on power modes and temperature, and the GPU is one engine among DLA, PVA and VIC that can take part of the work.

How do PTX and SASS differ, and what is a fatbinary?Basic

PTX is NVIDIA's virtual instruction set, stable across generations, with unlimited virtual registers. SASS is the real machine code of one architecture, produced by ptxas with register allocation and scheduling. A fatbinary bundles SASS for several targets and optionally PTX, which the driver can JIT-compile for GPUs newer than the build. For a fixed automotive target you ship SASS for its compute capability (8.7 for Orin) and avoid JIT at start-up.

How do you debug an illegal memory access in a kernel?Basic

Check every CUDA call and cudaGetLastError after launches; run with CUDA_LAUNCH_BLOCKING=1 so the failing launch reports the error; run compute-sanitizer --tool memcheck, which reports the thread, address and source line (compile with -lineinfo); use racecheck for shared-memory races and cuda-gdb to inspect a thread. Know that such errors are sticky: the context is unusable afterwards and the process must restart.

Compare CUDA, OpenCL and Vulkan compute.Basic

Same execution model under different names: thread, work-item, invocation; block, work-group, workgroup; warp, sub-group, subgroup; shared, local, workgroup memory. CUDA is NVIDIA-only with by far the richest libraries and tools. OpenCL is portable and the usual compute API on Qualcomm Adreno and Arm Mali; kernels are compiled at run time or from SPIR-V; it is not available on Jetson. Vulkan compute uses the explicit graphics API with SPIR-V shaders, suits work tied to rendering, and has a safety-critical variant, Vulkan SC. Optimisation rules carry over between all three.

Q.2Why and what if

Why can a GPU afford to switch warps every cycle when a CPU context switch costs microseconds?Basic

Because every resident warp's registers stay permanently allocated in the SM's large register file, so switching means only that the scheduler picks a different warp's instruction; nothing is saved or restored. A CPU thread switch saves and restores architectural state in memory and goes through the OS. The price on the GPU is that registers per thread limit how many warps can be resident.

What happens if you launch a 2D image kernel with threadIdx.x running down the columns?Basic

Lanes of a warp access pixels one row apart, thousands of bytes from each other, so each load touches up to 32 different sectors with one useful element each. Transactions per instruction rise up to 32-fold, and if the cache cannot keep the sectors until neighbouring columns are processed, DRAM traffic multiplies too. The fix is to swap the mapping so x runs along rows.

The fused one-thread-per-row kernel reads the minimum number of bytes. Why is it the slowest version?Intermediate

It creates only 544 threads, 17 warps for a GPU that can hold 768, so there is nothing to hide the memory latency behind: each SM runs about one warp that stalls on every load. In addition its lanes work on 32 different rows, so every load is uncoalesced. Minimum bytes is necessary, not sufficient; the bytes also have to move in parallel and in large, aligned transactions.

Why does v3 of the preprocessing kernel gain only about 20 % over v2 when it executes four times fewer instructions?Intermediate

Both read and write the same 6.24 MB, and the memory floor is about 42 µs. v2 was limited by instruction issue and memory at the same time, both near 40 µs, so removing instructions only lets it drop to the memory floor. Once a kernel is memory-bound, only fewer bytes make it faster, which is why fusion, not vectorisation, gave the factor of ten.

What if you raise occupancy from 50 % to 100 % by capping registers, and the kernel gets slower?Advanced

Likely the cap forced spills to local memory or removed the register tile that gave each thread its instruction-level parallelism. The kernel had already enough latency hiding at 50 %, so the extra warps did nothing while each thread got slower. Check ptxas spill reports and the stall reasons; occupancy is only worth raising when warps stall on latency with no unit near its limit.

Why does padding a shared tile by one column remove the conflicts of a column read?Basic

Without padding, row r starts at word 32r, which is always bank 0, so column c of every row is bank c: all 32 lanes hit the same bank. With 33 words per row, row r starts at bank r mod 32, so column c of row r is in bank (r + c) mod 32, different for each lane. The cost is 4 bytes per row of shared memory.

A histogram kernel is fast on daytime images and ten times slower at night. Why?Intermediate

At night most pixels fall into a few dark grey levels, so millions of atomic increments target the same few counters and are serialised at the L2. Privatising the histogram in shared memory per block confines contention to one block and reduces global atomics to 256 per block; warp-aggregated atomics, which the compiler may generate itself, further collapse lanes hitting the same bin.

What if the same reduction gives slightly different results on two runs?Basic

Floating-point addition is not associative, and with one atomic per block the order in which blocks add their partial sums depends on scheduling. The differences are in the last bits and expected. If bitwise reproducibility is required, use a fixed-order two-pass reduction, or accumulate in higher precision or integers.

Why is a cudaMemcpy of the camera frame harmful on Orin but necessary on a discrete GPU?Basic

On a discrete GPU the frame is in host memory and the GPU can only process it efficiently from its own VRAM, so the copy over PCIe is the transport. On Orin CPU and GPU use the same DRAM; the copy reads and writes 3.1 MB each for nothing, about 40 µs and bandwidth the ISP and DLA need. The right approach there is to import the camera buffer into CUDA and read it in place.

What if you return a camera buffer to the capture queue right after launching the kernel that reads it?Intermediate

The launch returns before the kernel runs, so the camera may write the next frame into the buffer while the kernel is still reading it, producing torn frames that mix two exposures. The buffer may be released only after a CUDA event or fence recorded after the kernel has completed. The bug appears under load, when the GPU lags behind.

Why are Nsight Compute kernel durations longer than the same kernel's time in Nsight Systems?Basic

Nsight Compute locks clocks to base frequency by default, flushes caches and replays the kernel several times to collect all counters, and serialises kernels. It is designed for repeatable ratios and stall analysis, not for wall-clock time. Timings come from Nsight Systems or CUDA events in the real application.

Why do fast GEMM libraries choose different kernels for different matrix shapes and GPUs?Intermediate

The best tile sizes depend on the shared memory, registers, tensor-core instructions and number of SMs of the GPU, and on the shape: a small or skinny matrix with large tiles leaves most SMs idle (a tail effect), while small tiles waste reuse on large matrices. Libraries and TensorRT therefore keep many variants and choose by heuristics or by timing on the actual device, which is also why a TensorRT engine is tied to the GPU it was built on.

What if a TensorRT plugin calls cudaMalloc and cudaStreamSynchronize inside enqueue?Intermediate

It works in a simple test and breaks the system: allocation may synchronise the device and adds unbounded latency per frame; synchronisation stalls the CPU and serialises the engine with everything else; neither can be captured in a CUDA graph. Scratch memory belongs in the workspace TensorRT provides, and ordering belongs to the stream it passes in.

When would you not use the GPU for an image-processing step on an Orin?Advanced

When another engine does it for less power and bandwidth or frees the GPU for networks: scaling and format conversion on VIC, a supported network on the DLA, some classical vision on PVA through VPI; when the step is a long serial dependency chain better done on a CPU core; or when the data is tiny and the launch and synchronisation would cost more than the work. The decision is made over the whole frame's timeline, not per step.

What would you check first if a kernel is 10× slower on the target than on your desktop GPU?Intermediate

Scale expectations first: Orin has a quarter or less of a desktop GPU's bandwidth and far fewer SMs, so a few times slower is normal. Then: clocks and power mode on the target, compiled architecture (SASS for 8.7 or JIT from PTX), copies that were cheap over PCIe but should be removed, contention with other engines for DRAM, and kernel launches or synchronisations that cost more on the slower embedded CPU. Profile with Nsight Systems on the target before changing code.

GGlossary

Arithmetic intensity
Floating-point operations per byte moved to or from DRAM; decides whether a kernel is memory- or compute-bound.
Atomic operation
Read-modify-write executed indivisibly, in L2 for global memory or on the SM for shared memory; serialised for the same address.
Bank
One of 32 independently addressable 4-byte-wide slices of shared memory; word w is in bank w mod 32.
Block-linear layout
Tiled surface layout used by NVIDIA's hardware engines; cannot be indexed as y · pitch + x.
Coalescing
Combining the addresses of a warp's memory instruction into as few 32-byte sector transactions as possible.
Stream compaction
Turning an array of elements with flags into a dense list of the flagged ones, using a scan for output positions.
Compute capability
Version number of a GPU's instruction set and limits, such as 8.7 for Orin; selects the SASS target.
Cooperative groups
CUDA C++ API for thread groups (block, warp tiles, grid) with sync, shuffle and reduce operations.
CUDA graph
A recorded set of kernels, copies and dependencies that is instantiated once and launched as a unit.
Divergence
Lanes of one warp taking different control paths, executed one after the other with masked lanes.
Event
Marker recorded in a stream, used for GPU timing, cross-stream dependencies and CPU waits.
Grid-stride loop
Kernel loop in which each thread processes elements i, i + total threads, …, so one launch handles any size.
Instruction-level parallelism
Independent instructions, especially loads, within one thread that can be in flight at the same time.
Kernel
A __global__ function launched on the GPU for a grid of threads.
__launch_bounds__
Kernel attribute giving the maximum block size and desired blocks per SM, so the compiler can limit registers.
Little's law
Work in flight = throughput × latency; for memory, bytes in flight = bandwidth × latency.
Local memory
Thread-private memory that physically lives in DRAM; used for spills and runtime-indexed arrays.
Managed memory
Allocation from cudaMallocManaged with one pointer valid on CPU and GPU; migrated or kept coherent by the driver.
Nsight Compute
NVIDIA's kernel profiler: replays a kernel with hardware counters and reports throughput, memory, occupancy and stall reasons.
Nsight Systems
NVIDIA's system profiler: timeline of CPU threads, CUDA API calls, kernels, copies and other engines.
NV12
YUV 4:2:0 format with a full-resolution luma plane followed by a half-resolution plane of interleaved U and V bytes.
NVTX
Annotation API for named ranges and markers that profilers show on the timeline.
Occupancy
Resident warps per SM divided by the maximum; limited by warp and block slots, registers and shared memory.
OpenCL
Khronos standard for heterogeneous compute with kernels compiled at run time; work-items, work-groups, local memory.
Pinned memory
Page-locked host memory that DMA engines can access directly; needed for asynchronous copies.
TensorRT plugin
User-implemented layer (IPluginV3) whose kernels TensorRT calls inside an engine.
PTX
NVIDIA's virtual instruction set, compiled to SASS by ptxas or JIT-compiled by the driver.
Register blocking
Each thread computes a small output tile held in registers, so loaded values are reused several times per load.
Roofline
Plot of attainable performance against arithmetic intensity with a memory-bandwidth slope and a compute ceiling.
SASS
The native machine code of an NVIDIA GPU architecture.
Scan (prefix sum)
Output element i is the sum of input elements before (exclusive) or up to (inclusive) i; computed in parallel in O(n) work.
Sector
32-byte unit of transfer between L1, L2 and DRAM; four sectors make a 128-byte L1 line.
Shared memory
Programmer-managed on-chip memory of an SM, shared by the threads of a block for the block's lifetime.
Shuffle
Warp instruction that reads another lane's register (__shfl_sync and variants) without shared memory.
SIMT
Single instruction, multiple threads: scalar per-thread code executed by warps in lockstep, with masking for divergence.
SM
Streaming multiprocessor: the GPU's core, with schedulers, register file, arithmetic units, tensor cores and L1/shared memory.
Spill
A value the compiler could not keep in registers and stored to local memory instead.
Stream
In-order queue of GPU commands; different streams may execute concurrently.
Tensor core
Unit executing a small matrix multiply-accumulate per warp instruction in reduced precision.
Texture
Read path with 2D-optimised cache, boundary modes, format conversion and hardware bilinear filtering.
Triton
Python-embedded language and compiler for block-level GPU kernels, used by torch.compile.
Vulkan compute
Compute shaders in SPIR-V dispatched through the explicit Vulkan API; Vulkan SC is its safety-critical profile.
Warp
Group of 32 threads that the hardware issues together.
Zero-copy
Accessing a buffer in place from another engine or processor instead of copying it into a separate allocation.
