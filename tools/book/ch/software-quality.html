Software quality, engineering workflow and technical documentation

How software teams keep changing a system quickly without breaking it: version control and release flow, code review, the kinds of tests and the tools that check the tests, refactoring, writing and diagrams, decision records, continuous delivery with feature flags, SRE practice and the metrics that tell a team whether it is getting better. The running example is the checkout service of a mid-sized online shop: the code that turns a cart into a paid order. Automotive practice appears only in short contrast boxes that point to the ASPICE and safety chapters.

1The big picture: quality is a property of the workflow

Software quality is not a phase at the end of a project and not a department. It is what you get when every change passes through a sequence of cheap, fast checks before it reaches users, and when every failure that slips through is turned into a better check. This chapter is about that sequence and the people practices around it.

1.1One change, many feedback loops

Follow a single change through a modern software team. An engineer on the checkout team wants to add promo codes. If the change is large or risky, she first writes a short design document so that colleagues can object to the idea before a line of code exists. Then she writes the code in small pieces; the compiler, the linters and the unit tests on her laptop answer within seconds. Each piece goes up as a pull request: CI builds it and runs the tests and analysers within minutes, and a colleague reviews it within hours. When both are happy, the change is merged into the one shared main line, the trunk. From there an automated pipeline builds one artifact, deploys it first to a small slice of production (a canary), compares its metrics with the old version and then rolls it out everywhere. The promo feature itself is still switched off by a feature flag; product and engineering turn it on for employees, then for 1 % of shoppers, then for everyone, while dashboards show the service-level indicators. If something goes wrong anyway, the on-call engineer is paged, mitigates, and the team writes a postmortem whose action items become new tests, new gates or better documentation.

Seen this way, "software quality" is a set of nested feedback loops with very different speeds. A type error caught by the compiler costs seconds. The same mistake caught in review costs a round trip of a few hours; caught by a canary it costs a rollback and some failed requests; caught by customers it costs an incident, money and trust. Almost every practice in this chapter does one of two things: it moves the detection of a class of problems into an earlier, faster loop, or it makes a later loop cheaper (smaller blast radius, faster rollback, better diagnosis). Keeping that in mind is the simplest way to judge any proposed process: which loop does it speed up, and what does it cost the loops it slows down?

Why it matters

A team that ships small changes through fast loops is not trading quality for speed. The DORA research programme (Section 10.5) has found for a decade that the teams that deploy most often also have the lowest change failure rates and the fastest recovery. Small changes are easier to review, easier to test, easier to roll back and easier to debug, so speed and stability come from the same habits.

1.2Why late feedback is expensive, and what the famous numbers really say

Almost every software-engineering talk shows a chart in which a defect costs 1 unit in requirements, 10 in coding, 100 in testing and 1000 in the field. The direction is right but the numbers are folklore: they go back to studies of large waterfall projects in the 1970s and 1980s (Boehm's work at TRW and IBM data), and later attempts to trace the exact multipliers found thin and mixed evidence (Laurent Bossavit's The Leprechauns of Software Engineering follows the citations). What is robust is the mechanism. A defect found late is expensive because the person who wrote the code has moved on and must reload the context; because more code has been built on top of it; because finding it needs a whole system and reproduction steps rather than one failing test; and because once users are affected there are costs outside engineering: support tickets, refunds, reputation.

The useful conclusion is therefore not "test more" but "shorten the distance between making a mistake and noticing it". That is why mainstream teams invest in fast unit tests, pre-merge CI, small pull requests, canaries and good alerting, and why they prefer one trunk that is integrated many times a day to long-lived branches that are integrated once a month.

Pitfall

Quoting "a bug in production costs 100× more" in a review or a budget discussion invites the question "according to whom?". Say instead that late defects are costlier because of context loss, dependent work, harder reproduction and user impact, and that the size of the factor varies widely between products. That answer is both correct and harder to argue with.

1.3The running example: a checkout service

The examples in this chapter come from one imaginary but realistic system. A mid-sized online shop sells to several European countries. Its checkout team has six engineers, a tech lead and an engineering manager, and owns two services: checkout (written in Go; turns a cart into an order, talks to the payment provider and publishes an OrderPaid event) and pricing (Kotlin; computes prices, discounts and shipping fees). They share a PostgreSQL order database and a Kafka event bus with other teams, run on Kubernetes in one cloud region with two availability zones, and deploy several times a day. At peak the checkout API handles about 200 requests per second, and its availability objective is that 99.9 % of checkout requests in a 30-day window succeed.

This is deliberately ordinary. The same practices apply to a mobile app, a data pipeline or an embedded product; what changes is mostly how expensive a release is and how much evidence a regulator wants, which is where the automotive contrast boxes come in.

In automotive

The car industry builds the same loops but with a much more expensive last stage: a vehicle release needs homologation evidence, and updates in the field go through a regulated software-update management system. That pushes more of the checking before release and makes traceable evidence (reviews, test reports, baselines) part of the product. The process view of this is in ASPICE SWE.4 and Project management 9.4.

1.4What changes as you become more senior

A junior engineer is judged on whether their own changes are correct. A senior engineer is expected to make other people's changes better too: reviewing well, writing tests that catch real bugs, keeping the build green. A staff or principal engineer, a tech lead or an architect owns the system of feedback loops: which gates exist and why, how releases flow, what goes into a design document, how incidents are analysed, and which few metrics tell the team whether it is improving. An engineering manager owns the conditions: time for maintenance, on-call load that people can sustain, and a culture in which incidents are discussed without blame. The chapter is written so that you can speak at each of these levels.

Talk track

"I think of quality as feedback loops. For every class of problem I ask where we find it today and whether we could find it earlier and cheaper. Types and linters in seconds, unit and contract tests in minutes, review in hours, canaries and SLO alerts in production. Then I make the late loops cheap: feature flags, automated rollback, good postmortems."

2Version control, branching and releases

Version control is the backbone of every other practice in this chapter: review happens on branches, CI runs on commits, releases are tags, and debugging often starts with "which commit changed this?". The choices a team makes here (how long branches live, how history is shaped, how releases are cut) decide how fast integration problems surface.

2.1What git actually stores

Git is easier to reason about once you know its data model, which is small. Every commit is an immutable snapshot of the whole tree plus metadata (author, message) and the hash of its parent commit or commits. Because each commit names its parents by hash, the history is a directed acyclic graph, and the hash of a commit covers its entire past: change anything in history and every later hash changes. A branch is nothing more than a movable name that points at one commit; a tag is a name that does not move. HEAD says which branch you are on. Merging, rebasing and cherry-picking are all ways of creating new commits in this graph; none of them edits an existing commit, which is why "rewriting history" really means creating new commits and moving a branch name to point at them.

Two consequences matter in practice. First, a commit you have pushed and others have fetched is shared state: if you replace it with a rewritten one and force-push, their copies still contain the old commit, and the next merge brings it back. Second, because a commit is a snapshot of the whole tree, every commit on the main line should build and pass tests; otherwise tools like git bisect (Section 2.5) stop working.

2.2Merge, rebase and squash: three ways to integrate a branch

Suppose a feature branch started from commit B and contains two commits, D and E, while main has moved on to C. There are three common ways to bring the work into main, and each leaves a different history.

A merge commit records that two lines of work were joined: commit M has two parents. Nothing is rewritten and the history is truthful, but in a busy repository the graph becomes a braid that is hard to read. Teams that use merge commits usually read history with git log --first-parent main, which shows only the merges into main, one per pull request.

A rebase replays D and E on top of C, producing new commits D′ and E′ with new hashes, and then main can simply move forward (a "fast-forward"). History is linear and every commit is kept, which is valuable when the individual commits tell a story ("extract interface", "add implementation", "switch callers"). The cost is that each rewritten commit must still build and pass tests, and that rebasing a branch someone else has based work on causes duplicate commits and confusion. The usual rule: rebase your own unpublished or private-review branches freely, never rebase shared history.

A squash merge combines all commits of the pull request into one new commit S on main. Main then has exactly one commit per reviewed change, which is easy to read, to revert and to bisect; the fine-grained commits survive only in the pull request. This is the default for many trunk-based teams on GitHub-style platforms, and it is a good default whenever pull requests are small. It is a bad fit for large changes whose internal steps matter, which is one more argument for keeping pull requests small.

In practice

Pick one integration style per repository and enforce it in the platform settings ("allow squash merging only", "require linear history"), so that nobody spends review time on it. Interactive rebase (git rebase -i) is still useful before opening a pull request, to turn a messy local sequence of "wip" and "fix typo" commits into a few meaningful ones.

2.3Branching models: from GitFlow to trunk-based development

A branching model answers one question: how long may work stay apart from everyone else's before it is integrated? The longer the answer, the larger and more surprising the integration.

GitFlow, published by Vincent Driessen in 2010, uses two long-lived branches (main for released code and develop for integration), a branch per feature, a release branch per release and hotfix branches from main. It fits software shipped as discrete versions on a slow cadence, such as installed desktop software or a library with several supported versions. Its weakness is late integration: features live for weeks on their own branch, and the merge into develop is where conflicts and interaction bugs appear all at once. In 2020 Driessen added a note to the original article recommending a simpler workflow such as GitHub flow for software that is delivered continuously.

GitHub flow keeps one long-lived branch: create a short branch, open a pull request, merge to main, deploy. Trunk-based development is the same idea taken further: everyone integrates into trunk at least daily, branches live hours rather than days, and work that is not finished is merged anyway but kept inactive behind a feature flag or behind an abstraction (Section 6.3). The State of DevOps research found trunk-based development, with three or fewer active branches and branches merged within a day, to be one of the practices that predict high delivery performance.

Trunk-based development only works with supporting practices: a fast and reliable pre-merge CI, small pull requests, feature flags for unfinished work, and the discipline that a red main is everyone's top priority. Without them, a shared trunk becomes a shared mess, and teams retreat to long branches for safety, which brings back the late integration they were trying to avoid.

Talk track

"Branching strategy is really integration frequency. Long-lived branches feel safe but they hide conflicts until the end. I prefer trunk-based development with short-lived branches, flags for unfinished work and a merge queue that keeps main green; release branches only where we must support a version in the field."

2.4Release management: versions, release branches and cherry-picks

For a web service like checkout, a "release" is simply a deployment of a particular commit of main, and the version is often just the commit hash or a build number. Release branches become necessary when you must keep an old version alive and patch it: mobile apps waiting for store review, on-premise software, SDKs and libraries, firmware. Then the rule that keeps things sane is fix on main first, then cherry-pick to the release branch. A cherry-pick copies the change of one commit onto another branch as a new commit. If the fix were made only on the release branch, the next release cut from main would silently bring the bug back, a classic regression.

Semantic versioning (SemVer 2.0.0) gives library and API versions a meaning: MAJOR.MINOR.PATCH, where a MAJOR increase signals an incompatible API change, MINOR adds functionality compatibly and PATCH fixes bugs compatibly. It is a promise to consumers, so it only works if "incompatible" is judged from the consumer's point of view, including behaviour they may rely on (Hyrum's law, Section 6.4). Services that are only called through versioned APIs version the API (for example /v2/orders) rather than the deployment.

A release in a mature team carries three things besides the code: a tag that marks exactly which commit was released, release notes generated from commit or pull-request titles, and the artifact itself, built once and promoted unchanged through environments (Build systems 11.4). Release trains, where a release is cut on a fixed schedule whatever is ready, keep a predictable cadence for products such as mobile apps; anything not finished simply waits behind its flag for the next train.

In automotive

Automotive projects keep release and maintenance branches for years, because a vehicle line must be patched long after the next one has started, and each release is a baseline with a configuration record that an assessor can audit. The mechanism is the same cherry-pick discipline, with more paperwork; see Project management 9.2 and Production integration 14.3.

2.5History as documentation, and finding the bad commit

The commit history is the only documentation that is guaranteed to be attached to the code it describes. A good commit message has a short summary line (about 50 characters, imperative mood: "Reject promo codes after their end date") and a body that explains why the change was made and what alternatives were considered; the diff already shows what. Conventions such as Conventional Commits (feat:, fix:, refactor:) make the history machine-readable for changelogs and version bumps. Six months later, when someone runs git blame on a strange line, the message is what tells them whether the strangeness was deliberate.

A linear, always-green history also makes git bisect work. You tell git one commit where the bug is absent and one where it is present; git checks out the commit halfway between, you (or a script) test it and report good or bad, and git halves the range again. Because each step halves the range, finding the culprit among 1,000 commits takes about log2(1000) ≈ 10 steps, and with git bisect run ./test.sh the whole search runs unattended. Bisect fails in exactly the situations a bad workflow creates: commits that do not build, huge squashed changes where "the culprit" is 3,000 lines, and flaky tests that give different answers for the same commit.

$ git bisect start
$ git bisect bad HEAD               # promo totals wrong today
$ git bisect good v2026.10.28       # correct last week
Bisecting: 61 revisions left to test after this (roughly 6 steps)
$ git bisect run go test ./pricing -run TestPromoTotals
...
3f9c2e1 is the first bad commit
    Round each discount share separately
$ git bisect reset
Numbers

Bisect needs about log2(N) test runs: 7 for 100 commits, 10 for 1,000, 17 for 100,000. That is why it pays to keep every commit on main buildable and to make the reproduction a script.

3Code review and pull-request design

Code review is the main human feedback loop before merge. It is worth understanding what it is actually good at, because teams that expect it to find most bugs end up with slow, painful reviews that still miss bugs, while teams that use it for what it does best get better code and better-informed engineers.

3.1What review is really for

Ask engineers why they review code and most say "to find defects". Studies of how review actually works tell a more nuanced story. A Microsoft study by Bacchelli and Bird (ICSE 2013) found that while finding defects was the top expectation, most review comments were about code improvements, readability and alternative solutions, and that knowledge transfer and team awareness were major outcomes. Google's case study (Sadowski et al., ICSE-SEIP 2018) describes review there as primarily about education, maintaining norms and readability, with gatekeeping and defect finding as secondary goals.

That does not mean review is useless for bugs; it is good at bugs that need understanding of intent: a wrong business rule, a missing case, a race that a test would only hit by luck, a security assumption that does not hold. It is bad at bugs a machine can find (formatting, type errors, null dereferences, most style issues), and asking humans to find those is a waste of the most expensive loop. So the division of labour is: tools check everything mechanical before a human looks (Section 13), and humans spend their attention on design, correctness of intent, tests and clarity.

Numbers

Google reported a median change of about two dozen modified lines, most changes reviewed by one reviewer, and a median time to complete review of under four hours for small changes (Sadowski et al., 2018). An older SmartBear study of about 2,500 reviews at Cisco found that defect detection drops sharply when a review covers more than about 400 lines or proceeds faster than about 500 lines per hour, and after about an hour of continuous reviewing.

3.2Designing a pull request: one reason to change

The quality of a review is mostly decided by the author before the reviewer opens it. The most important property is scope: a pull request should do one thing that can be described in one sentence. A PR that adds promo codes, renames a package and upgrades a library forces the reviewer to keep three unrelated questions in mind at once, and makes the eventual revert dangerous because it would undo all three. Refactorings and mechanical changes go in their own PRs, ideally before the behaviour change, so that the behaviour change becomes small and obvious.

The second property is size. A few hundred changed lines is a practical upper limit for a careful review; beyond that, reviewers skim. Large features are split into a sequence: first the interfaces, then the implementation behind a flag, then the callers, then the flag removal. When each step depends on the previous one and review is slow, stacked pull requests let the author keep working: PR 2 is based on PR 1's branch, PR 3 on PR 2's, and each is reviewed on its own diff. Tooling for stacks (Graphite, ghstack, Gerrit's relation chains, Phabricator's stacked diffs) automates the rebasing when an earlier PR changes.

The third property is evidence. The reviewer should not have to run the code to believe that it works. Tests in the same PR, a screenshot or recording for UI changes, a benchmark for performance claims, a sample log line for new observability, and a short note of what was tested by hand all turn "trust me" into "here is why". Finally, a PR should state its risk and rollout: what could break, who would notice, whether it is behind a flag and how to roll it back.

3.4The reviewer's job, in order

A good reviewer reads in a deliberate order, from the most expensive problems to the cheapest, so that time is not spent polishing names in code whose design is about to change. First, the problem and the design: is this the right change, in the right place, with the right interface? Does it fit the architecture, or does it create a second way of doing something the codebase already does? Second, correctness: does the code do what the description says, including edge cases, error paths, concurrency, and what happens on retry or partial failure? Third, tests: would these tests fail if the code were wrong? A test that only executes the code without checking results is decoration (Section 5.4). Fourth, operability: logs, metrics, alerts, configuration and the rollout plan. Only then readability: names, comments, structure. Formatting and style should never appear in a review, because a formatter and linter enforce them (Section 13.1).

Comments should be specific, explain why, and say how much they matter. Many teams prefix comments: nit: for optional polish, question: for understanding, and an explicit "blocking" for things that must change. Google's published reviewer guide sets the standard that a reviewer should approve a change once it definitely improves the overall health of the code, even if it is not perfect; perfection is not the bar, and "I would have written it differently" is not a reason to block. The same guide asks reviewers to respond within one business day at most, because slow reviews are the main reason authors batch work into large PRs.

Pitfall

Two failure modes are common. The rubber stamp: "LGTM" within a minute on a 900-line PR, which gives the team false confidence. And gatekeeping: one senior reviewer who blocks on personal taste, rewrites the author's design in comments and makes people avoid touching "their" code. Both are fixed by the same things: small PRs, explicit review guidelines, and comments that distinguish blocking from optional.

3.5Review culture, ownership and speed

Review needs owners. A CODEOWNERS file maps paths to people or teams who must approve changes there, which guarantees that someone who understands the payment client sees every change to it. Used too broadly it becomes a bottleneck: if one person owns half the repository, every PR waits for them. The usual compromise is that any team member can approve most code, and a small set of sensitive paths (authentication, payments, database migrations, CI configuration) needs a specific owner.

Speed matters more than most teams think. A review that takes two days does not just delay one change; it encourages authors to pile more into each PR to amortise the wait, which makes reviews slower still. Teams that keep review latency within a few hours usually do it with explicit norms: review requests are answered before starting new work, PRs are small enough to review in fifteen minutes, and when a discussion goes past two rounds of comments the people talk for five minutes instead.

Reviews of AI-generated code follow the same rules with one shift of emphasis: the author is still responsible for every line, and the reviewer should check that the author understood what they are submitting. Generated code tends to be plausible and verbose, so the checks for intent, tests that really assert behaviour, and duplication of existing utilities matter more; see GenAI 13.5.

In automotive

In an ASPICE or ISO 26262 project a review is also evidence: it must be recorded with reviewer, scope, checklist and findings, and its independence may be prescribed by the safety level. The mechanics of a good review are the same; the record is what differs. See ASPICE 10.2 and Functional safety 7.2.

Talk track

"Review is our main tool for shared understanding and design quality, not our main bug filter; machines catch the mechanical bugs before a human looks. I keep PRs to one purpose and a few hundred lines, write the why and the evidence in the description, and as a reviewer I go from design to correctness to tests to readability, approving when the change clearly improves the code."

4Testing: what to test, at which size, and how to generate inputs

Tests exist so that a team can change code with confidence. A test suite is an executable specification: it says what the code must do, and it says so every time anyone changes anything. The art is to get the most confidence per second of test time and per hour of maintenance, which is what the test pyramid, test doubles, contracts and generated inputs are all about.

4.1The test pyramid and test sizes

Mike Cohn's test pyramid (2009) says: write many small, fast tests at the bottom, fewer integration tests in the middle, and only a few end-to-end tests at the top. The reasoning is about feedback quality. A unit test runs in milliseconds, never flakes, and when it fails it points at one function. An end-to-end test that drives a browser through checkout against all services is the most realistic, but it takes minutes, fails for reasons unrelated to the change (a slow container, a test-data clash), and when it fails it only says that something, somewhere, is wrong. A Google Testing Blog post (Wacker, 2015) suggested roughly 70 % unit, 20 % integration and 10 % end-to-end as a starting split; the exact numbers matter less than the shape.

"Unit" and "integration" are fuzzy words; one team's unit test is another's integration test. Google sidesteps the argument by classifying tests by size, meaning the resources a test may use, which the test runner enforces. A small test runs in a single process, with no network, disk or sleep, and must finish in about a minute. A medium test may use several processes on one machine, including a real database on localhost, with a limit of about five minutes. A large test may span machines and runs for up to about fifteen minutes or longer. Size predicts speed and flakiness much better than the name of the level, and it is enforceable.

Two alternative shapes are worth knowing. The testing trophy (Kent C. Dodds) puts most effort into integration tests for front-end code, where units are thin and the interesting bugs are in how components fit together. The honeycomb (Spotify) does the same for microservices whose logic is mostly glue: test each service through its real API with real dependencies started locally, and keep unit tests for genuinely complex logic. Both are refinements, not contradictions: put the bulk of tests where the bugs are, at the smallest size that can catch them.

In automotive

The V-model names test levels by what they verify against: unit verification against the detailed design, integration verification against the architecture, qualification against the software requirements. That is a different axis from test size: an ASPICE "unit test" is usually small, but a software qualification test may also be automated and fast. See ASPICE SWE.5 and ASPICE 9.2.

4.2Unit tests and test doubles

A good unit test has three parts (arrange, act, assert), tests one behaviour, has a name that states that behaviour ("expired promo code is rejected"), and fails for exactly one reason. It tests through the public interface of the unit, not its private details, so that refactoring the inside does not break the test. A test that has to be changed every time the implementation changes, although the behaviour did not, is a cost without a benefit.

When the unit depends on something slow or uncontrollable (the payment provider, the clock, the database), the test replaces it with a test double. The vocabulary, from Gerard Meszaros, is useful because each kind has a different cost. A stub returns canned answers ("the provider always authorises"). A fake is a working but simplified implementation (an in-memory order repository). A spy records how it was called so the test can check afterwards. A mock is programmed with expectations ("expect Authorize(84.97) exactly once") and fails the test if they are not met.

Mocks are where test suites most often go wrong. A test that mocks every collaborator and asserts the exact sequence of calls tests the implementation, not the behaviour: rename a method or reorder two calls and dozens of tests fail although nothing is broken. Worse, the mock encodes the author's belief about how the dependency behaves, and if that belief is wrong, the test passes and production fails. Prefer real objects for cheap collaborators, fakes for stateful ones (repositories, queues), and mocks only at the boundary of your system, where you really do care that a call was made (an email was sent, a payment was authorised once). Then make sure the boundary itself is covered by a contract test, which is the subject of the next section.

In practice

Inject time and randomness. Code that calls time.Now() or a global random generator directly cannot be tested deterministically; code that receives a clock and a random source can. Most flaky unit tests in business code come from a hidden dependency on wall-clock time, time zones or ordering of a hash map.

4.3Integration and contract tests

Integration tests check that your code works with the real things it depends on: the SQL actually runs on PostgreSQL, the Kafka consumer really commits offsets, the HTTP client handles the provider's real error format. Containers made this cheap: a test can start a throwaway PostgreSQL in a few seconds (Testcontainers is the common library for this), run migrations, and test the repository against it. These are medium tests in Google's sense and belong in pre-merge CI.

Between services the hard question is: how do you know that checkout and payment still agree on the API, without deploying both into a shared test environment that is always broken by someone? Consumer-driven contract testing answers it. The consumer (checkout) writes ordinary unit tests against a mock of the provider; the testing library records each interaction (this request, this expected response shape) into a contract file. The contract is published to a broker. The provider (payment service) downloads the contracts of all its consumers and replays the requests against its real implementation in its own CI. Before either side deploys, a check asks the broker whether the version about to be deployed is compatible with the versions currently in production. Pact is the best-known implementation; the idea goes back to Ian Robinson's 2006 article on consumer-driven contracts.

The value is that each side is tested alone, in seconds, and the provider learns which fields its consumers actually use. A provider that wants to rename a field can see that two consumers still read it and must wait. What contracts do not test is behaviour across services under load or partial failure; that is the job of a few end-to-end tests and, in production, of canaries and SLOs.

4.4Property-based testing: let the computer find the example

An example-based test checks one input you thought of. A property-based test states a rule that must hold for all inputs and lets a library generate hundreds of inputs to try to break it. The idea comes from QuickCheck (Claessen and Hughes, 2000, for Haskell); Hypothesis (Python), jqwik (Java), fast-check (JavaScript), proptest (Rust) and rapid (Go) bring it to mainstream languages. When the library finds a failing input, it shrinks it: it tries smaller and simpler variants until it finds a minimal input that still fails, which is usually the clearest possible bug report.

Here is a real example from the pricing service. A cart-level discount must be split across the cart lines (for invoices and returns), in integer cents, and the shares must add up to the discount. The natural first implementation rounds each line's proportional share:

def allocate(prices, discount):           # cents
    total = sum(prices)
    return [round(discount * p / total) for p in prices]

@given(st.lists(st.integers(1, 100_000), min_size=1, max_size=20), st.integers(0, 10_000))
def test_shares_add_up(prices, discount):
    discount = min(discount, sum(prices))
    assert sum(allocate(prices, discount)) == discount

Hypothesis breaks it immediately and shrinks the failure to prices=[1, 1], discount=1: each line's share is 0.5 cent, both round to 0, and one cent of discount disappears. (Python rounds halves to even; with round-half-up both would round to 1 and a cent would appear from nowhere.) On 10,000 random carts in the chapter's experiment, 5,044 broke the property. The fix is the largest-remainder method: give every line the rounded-down share, then hand the leftover cents to the lines with the largest fractional parts. The same property, with the additional rule that no share exceeds its line's price, then passes 2,000 generated cases. No example-based test written by hand would have tried a two-line cart with a one-cent discount; the property did in milliseconds.

Good properties are rarely "compute the answer a second way". The productive patterns are: invariants (shares add up; output is sorted; balance never negative), round trips (decode(encode(x)) == x; parse(print(x)) == x), equivalence with a simple model (the optimised cache behaves like a dictionary), and metamorphic relations (adding an item never lowers the total; doubling every price doubles the tax). Stateful property testing goes one step further: the library generates sequences of operations (add to cart, apply code, remove item, checkout) and checks the system against a simple model after each step, which finds the interaction bugs that example tests miss.

Pitfall

Generators that are too narrow (only small positive numbers, only ASCII strings) give false comfort. Include empty lists, zero, negative numbers, very large values, Unicode and duplicates unless the domain truly forbids them, and keep failing examples as regression tests: Hypothesis stores them in a local database and replays them first.

4.5Fuzzing: coverage-guided input generation

Fuzzing is property-based testing's cousin for code that parses untrusted input: file formats, network protocols, URL and JSON parsers, image decoders. The property is usually just "does not crash, hang or trigger a sanitizer". What makes modern fuzzers effective is coverage guidance, introduced to the mainstream by AFL (Michał Zalewski, 2013) and built into LLVM as libFuzzer. The compiler instruments the target so that every run reports which code edges it executed. The fuzzer keeps a corpus of inputs, mutates one, runs it, and if the mutated input reached an edge never seen before, adds it to the corpus. Over millions of runs the corpus becomes a map of the program's behaviour, and inputs evolve deeper into it. Sanitizers (Section 5.2) act as the oracle: an out-of-bounds read that would silently return garbage in a normal build becomes an immediate, precise report.

The experiment shows how little it takes. The function below decodes %XX escapes in a URL query value. Its bounds check is off by one: it checks that one character follows the % but then reads two.

if (src[i] == '%') {
  if (i + 1 >= n) return -1;            /* BUG: should be i + 2 >= n */
  int hi = hexval(src[i + 1]), lo = hexval(src[i + 2]);
  ...
}

int LLVMFuzzerTestOneInput(const uint8_t *data, size_t size) {
  char *in = malloc(size), *out = malloc(size + 1);
  memcpy(in, data, size);                  /* exact-size copy: ASan sees any overread */
  volatile long n = url_decode(in, size, out);
  free(in); free(out);
  return 0;
}

Built with clang -g -O1 -fsanitize=fuzzer,address and started with ten different seeds, libFuzzer found the overflow every time within a few hundred executions, well under a second, on two- to four-byte inputs such as %! and %\n. A unit test written by a person who knows the format would test %41, %zz and perhaps a trailing %, and would miss exactly this case. One practical detail from the experiment: in the first version the decoder's result was unused, the optimiser was entitled to remove the call, and the fuzzer ran for minutes without finding anything. A fuzz target must keep the work observable.

At scale, Google's OSS-Fuzz service runs continuous fuzzing for open-source projects and reported (2023) having helped find and fix over 10,000 vulnerabilities and 36,000 bugs across about 1,000 projects. For a product team the practical setup is smaller: a fuzz target per parser or decoder, a short fuzzing run in CI on each change to it, a longer run nightly that keeps its corpus, and every crash turned into a regression test. Go (since 1.18), Rust (cargo-fuzz) and Python (Atheris) have native or standard fuzzing support, so this is no longer a C-only technique.

Why it matters

Parsers of untrusted input are where memory safety bugs become security vulnerabilities. Fuzzing is the only technique that explores such code with millions of adversarial inputs per minute at almost no human cost, which is why it is now an expected part of secure development for anything that parses data from outside.

4.6Flaky tests

A flaky test passes and fails on the same code. Flakiness is poisonous out of proportion to its frequency, because it teaches people to ignore red builds and to press "re-run" without reading the failure; at that point real failures are ignored too. Google reported in 2016 that about 1.5 % of all test runs gave a flaky result and that almost 16 % of its tests had shown some flakiness; with thousands of tests per change, nearly every large change hit at least one.

The causes are a short list: dependence on timing (sleeps, timeouts, races), on order (tests sharing state or depending on hash-map iteration order), on the environment (time zone, locale, free ports, network), on external services, and on resource limits on a busy CI machine. The response that works is systematic. Detect flakes automatically, for example by re-running failures and recording tests that pass on retry. Quarantine a flaky test quickly so that it stops blocking others, but give it an owner and a deadline, because a quarantined test protects nothing. Fix the cause rather than adding retries; a retry hides a race in the test today and lets the same race in the product through tomorrow.

Pitfall

"Increase the timeout" is the most common and least useful flake fix. If a test waits for something asynchronous, make it wait for the event (poll a condition, subscribe to a signal) with a generous upper bound, rather than sleeping for a guessed duration.

Talk track

"Most of our tests are small and fast, a layer of integration tests runs against real databases in containers, contracts keep services compatible without a shared test environment, and a handful of end-to-end tests cover the money paths. For logic with many input combinations I write property tests; for anything that parses untrusted input, a fuzz target with sanitizers. Flaky tests get quarantined with an owner the same day."

5Checking the code and checking the tests

Tests check the code; static analysis, sanitizers, coverage and mutation testing check things tests cannot see, or check the tests themselves. Each tool answers a different question, and each becomes harmful when it is used to answer a question it cannot.

5.1Static analysis: findings without running the code

Static analysis reasons about code without executing it. The spectrum runs from the compiler's own warnings, through linters that encode style and common mistakes (golangci-lint, ESLint, Ruff, clang-tidy), type checkers for dynamic languages (mypy, TypeScript), to deep analysers that track values across functions and files (the Clang Static Analyzer, Infer, CodeQL, Coverity, SonarQube's deeper rules). The deeper the analysis, the more real bugs it finds that tests miss (a null dereference on a rare error path, an unchecked SQL string reaching a query), and the more it struggles with false positives.

Two properties describe any analyser. A sound analysis reports every real problem of its kind, at the price of false alarms; a precise one reports only real problems, at the price of misses. Practical bug finders choose precision, because developer trust is the scarce resource. Google's experience, described by Sadowski and colleagues ("Lessons from building static analysis tools at Google", CACM 2018), is the standard reference: a check is only shown to developers if its effective false-positive rate, meaning findings developers do not act on, is low (they used a threshold of about 10 %), and findings are shown in code review on the lines the author just changed, when fixing them is cheapest, rather than in a separate dashboard nobody reads.

That gives the usual rollout recipe for an existing codebase with thousands of findings. Do not try to fix them all, and do not let them block anyone. Record a baseline of existing findings, then gate only on new findings in changed code (a "ratchet": the count may go down, never up), and fix old findings when the surrounding code is touched anyway. Turn on a new rule only after checking its false-positive rate on your own code. Security-focused analysis (SAST, such as CodeQL) follows the same rules, with the extra discipline that a finding marked "won't fix" needs a reason.

In automotive

In safety projects a coding standard such as MISRA C/C++ or AUTOSAR C++14 is enforced by a qualified static analyser, and every deviation needs a documented justification. Same tools, stricter use; see C++ 14: MISRA C++:2023 and Functional safety 7.2.

5.2Sanitizers: making silent bugs loud

Sanitizers are compiler instrumentation plus a runtime library that check, while the program runs, for whole classes of undefined behaviour that otherwise go unnoticed until they corrupt data far away. AddressSanitizer (ASan) catches out-of-bounds accesses, use-after-free and double free, with roughly a 2× slowdown; ThreadSanitizer (TSan) catches data races, typically at 5–15× slowdown and several times the memory; MemorySanitizer (MSan) catches reads of uninitialised memory; UndefinedBehaviorSanitizer (UBSan) catches signed overflow, invalid shifts and misaligned access at low cost. How they work and which flags to use is in Build systems 8.5, and the race detector's theory in Concurrency 10.2.

From the quality-workflow point of view, three rules matter. Sanitizers only find bugs on code paths that run, so they are multipliers for tests and fuzzers, not replacements. ASan and TSan cannot be combined in one binary, so CI needs separate sanitizer builds of the test suite, which usually run after merge or nightly because of their cost (Figure 13.1). And a sanitizer report is never a flake: it is a real bug, even if the test "usually passes". Go's -race flag and Rust's Miri bring the same ideas to memory-safe languages, where races and unsafe blocks are still possible.

5.3Code coverage: what it measures and what it cannot

Coverage tools record which parts of the code ran during the tests. Line (or statement) coverage counts executed lines; branch coverage counts whether each condition went both ways; MC/DC (modified condition/decision coverage) additionally demands that each sub-condition is shown to independently affect the decision, and is required for the highest safety levels (Functional safety 7.3). Branch coverage is the most useful default for ordinary software: line coverage can be 100 % for if (a) x = 1; without ever testing the case where a is false.

Coverage is good at one thing: showing code that no test executes. Uncovered code is certainly untested. The reverse does not hold. Coverage measures execution, not checking: a test that calls a function and asserts nothing produces exactly the same coverage as a test that checks every result. That is why a coverage target used as a goal goes bad (Goodhart's law: a measure that becomes a target stops being a good measure); teams under a "90 % or the build fails" rule learn to write tests that execute code without asserting much.

Google's published guidance (Ivanković et al., "Code coverage at Google", 2019, and the testing blog) gives a sensible frame: around 60 % is acceptable, 75 % commendable and 90 % exemplary for a project, but the more useful number is coverage of the changed lines in a pull request, shown in review next to the diff. A reviewer who sees that the new error branch is not covered can ask for a test for that specific branch, which is far more valuable than a project-wide percentage.

5.4Mutation testing: testing the tests

Mutation testing asks the question coverage cannot: if the code were wrong, would a test notice? The tool makes many small deliberate edits to the code, each called a mutant: >= becomes >, a constant changes, a condition is negated, a line is deleted. It runs the test suite against each mutant. If some test fails, the mutant is killed; if all tests still pass, the mutant survives, and a surviving mutant is a concrete, specific gap: here is a change to your code that your tests cannot tell apart from the original. The mutation score is the fraction of mutants killed. The idea dates from 1978 (DeMillo, Lipton and Sayward), resting on two observations: programmers mostly make small mistakes, and tests that catch small mistakes also tend to catch the larger mistakes built from them.

The figure below uses the real kill matrix from the chapter's experiment: a ten-line shipping-fee function (free shipping from 50.00, otherwise 4.99 to Germany and 9.99 elsewhere, plus 10.00 for express), eight mutants and six candidate tests. Try selecting tests and watch the two numbers.

Three results are worth stating in words. The smoke test alone executes every line, so line coverage is 100 %, and kills no mutant at all, because it asserts nothing: coverage says "fully tested", mutation testing says "not tested". The three sensible tests de_small, free and express also reach 100 % line coverage and kill seven of eight mutants; the survivor is >= becoming >, because no test uses an order of exactly 50.00. That is precisely the off-by-one at a business boundary that ends up as a customer complaint ("the site said free shipping from 50 euros"). Adding the boundary test kills it. In general, surviving mutants point at missing boundary values, unchecked return values and assertions that are too weak, which is exactly what a reviewer wants to know.

Mutation testing has a cost problem: every mutant is a test-suite run, and a real codebase has thousands of mutants. Tools reduce it by running only the tests that cover the mutated line, by mutating only changed code, and by skipping mutants that cannot matter (logging statements, equivalent mutants that do not change behaviour). Google runs mutation testing on the lines changed in each code review and shows a few surviving mutants as review comments (Petrović and Ivanković, "State of mutation testing at Google", ICSE-SEIP 2018), which turns an expensive batch metric into a cheap, targeted hint. Common tools are PIT (Java), Stryker (JavaScript, C#, Scala), mutmut and Cosmic Ray (Python), cargo-mutants (Rust) and Mull (C/C++).

Numbers

Chapter experiment: smoke test 8/8 lines, 0/8 mutants; three typical tests 8/8 lines, 7/8 mutants; with the boundary test 8/8 lines, 8/8 mutants. Two test suites with identical 100 % line coverage can have mutation scores of 0 % and 100 %.

Talk track

"Coverage tells me what is definitely untested; it can't tell me what is tested. For that I use mutation testing on changed code: a surviving mutant is a concrete edit my tests can't detect, usually a missing boundary case or a missing assertion. I gate on coverage of changed lines, not a project-wide number, and use mutants as review hints, not a hard gate."

6Refactoring, legacy code and clean interfaces

Most engineering time is spent changing code that already exists. Refactoring is the discipline of improving its structure without changing its behaviour, so that the next behaviour change is cheap. Legacy code is code where that discipline cannot start yet, because nothing tells you whether behaviour changed.

6.1Refactoring: small, behaviour-preserving steps

Martin Fowler defines refactoring as a change to the internal structure of software that makes it easier to understand and cheaper to modify without changing its observable behaviour. The important words are "without changing behaviour" and, implicitly, "small". A refactoring is a sequence of tiny transformations (extract a function, rename, move a method, replace a conditional with polymorphism, introduce a parameter object), each of which keeps the tests green. If the tests go red, you undo the last step rather than debug, because the step was small enough to redo carefully. Modern IDEs automate many of these transformations safely, which is one more reason to keep them small and mechanical.

Refactoring is not a separate project. The most productive habit is "make the change easy, then make the easy change" (Kent Beck): before adding promo codes to a pricing function that has grown to 300 lines, first extract the discount calculation into its own function with its own tests, in a separate pull request that changes no behaviour, and then add the feature in a small second PR. Reviewers can approve the first by checking that it is purely structural, and the second becomes obvious. The "boy-scout rule" (leave the code a little better than you found it) is the same idea in small: tidy what you touch, in a separate commit.

Pitfall

Mixing refactoring and behaviour change in one PR is the most common review problem in this area. The reviewer cannot tell which of 40 changed lines are supposed to change behaviour, and if the PR causes an incident, reverting it also reverts the cleanup.

6.2Legacy code: get it under test first

Michael Feathers' Working Effectively with Legacy Code (2004) gives the working definition: legacy code is code without tests. Age and language do not matter; what matters is that you cannot change it and know whether you broke something. The book's central move is to get such code under test with as little change as possible, and then refactor safely.

The first tool is the characterisation test (also called a golden-master or approval test): instead of writing down what the code should do, you record what it does. Run the old pricing function on a few hundred real or generated carts, store the outputs, and write a test that compares future outputs with the stored ones. The test does not judge whether the old behaviour is right, only whether it changed, which is exactly what a refactoring needs. If a characterisation test reveals a behaviour that looks like a bug, you note it and decide separately whether to fix it, because someone may depend on it.

The second tool is the seam: a place where you can change what the code does without editing it there, so that a test can substitute a dependency. A function that calls the payment provider directly through a global client has no seam; extract the call behind an interface passed into the constructor and the test can substitute a fake. When a change is needed in a function you cannot yet test, Feathers' sprout technique writes the new logic as a new, fully tested function and calls it from the old code with a one-line change; the wrap technique puts new behaviour before or after the old function in a wrapper. Both keep new code clean while the old code is gradually brought under test.

// Before: no seam. The only way to test is to call the real provider.
func Checkout(cart Cart) (Order, error) {
    total := price(cart)
    res, err := stripeClient.Charge(total)        // global client

}

// After: the dependency is a parameter, so a test can pass a fake.

6.3Large changes in small steps: expand, migrate, contract

Some changes cannot be made in one pull request: renaming a database column that five services read, replacing a library used in 400 files, changing an API that mobile apps already installed on phones call. The universal pattern is parallel change, also called expand and contract: first add the new thing alongside the old one (expand), then move every user over (migrate), then remove the old thing (contract). Each step is backward compatible with the one before it, so each can be deployed and, if necessary, rolled back on its own, and the system works at every point in between.

The database case shows why the steps must be separate. During a rolling deploy, old and new versions of the service run at the same time against the same database. If one migration dropped price_euros and added price_cents, the old pods would crash the moment it ran. Instead: add the new nullable column; deploy code that writes both; backfill old rows and verify the two columns agree; switch reads to the new column behind a flag; deploy code that writes only the new column; finally drop the old column. Six small steps over days or weeks replace one big risky one.

The same pattern at code level is branch by abstraction: put an interface in front of the old implementation, move all callers to the interface, build the new implementation behind it (switched by a flag), move traffic over, delete the old one. At service level it is the strangler fig, which routes requests one by one from an old system to a new one; both are covered in Software architecture 13.4. In very large codebases, changes that touch thousands of files are made by tools rather than people (Google calls them large-scale changes and splits them into thousands of small, independently reviewed and tested shards); the lesson for smaller teams is that codemods (automated source rewrites with tools such as OpenRewrite, jscodeshift, Comby or gofmt's rewrite rules) beat manual search-and-replace once a change touches more than a few dozen files.

6.4Clean interfaces and maintainable code

Most advice about "clean code" is about naming and small functions, which helps, but the decisions that matter most for maintainability are about interfaces: what a module promises and what it hides. John Ousterhout's A Philosophy of Software Design gives a useful test: a good module is deep, meaning a simple interface hides a lot of complexity (a file system's open/read/write/close hides block allocation, caching and journaling). A shallow module has an interface almost as complex as its implementation, so it adds a name without removing any complexity; a codebase full of thin wrappers, managers and pass-through layers is hard to change although every function is short.

A few principles carry most of the weight. Make illegal states unrepresentable: an order type whose status field and payment fields can disagree will eventually disagree; a type with one variant per state cannot. Put errors in the interface: the caller should see from the signature which failures can happen and must be handled (Go's error returns, Rust's Result, C++'s std::expected), and should not be able to ignore them silently. Prefer explicit dependencies (passed in) over hidden ones (globals, singletons, service locators), because hidden dependencies are both untestable and surprising. Keep data and its invariants together: Money as integer minor units plus a currency, never a float and a separate string.

Every published interface also meets Hyrum's law (named after Hyrum Wright at Google): with a sufficient number of users of an API, it does not matter what you promise in the contract; all observable behaviours of your system will be depended on by somebody. The order in which a list is returned, the exact text of an error message, the time an operation takes: if it can be observed, someone relies on it. This is why the smaller and more precise an interface is, the cheaper it is to change behind it, and why changes to widely used interfaces need the expand–contract discipline even when they look harmless.

6.5Managing technical debt as a team

Technical debt is the gap between the code as it is and the code as it would need to be for the next changes to be cheap; the metaphor, from Ward Cunningham, is that the "interest" is the extra effort every future change pays. What it is and how architecture accumulates it is covered in Software architecture 13.3. The workflow question is how a team decides which debt to pay. Debt is only worth paying where the code changes often: a messy module nobody touches costs nothing. Combining version-control history (how often each file changes, how many bug fixes touch it) with a complexity measure finds the "hotspots" where cleanup pays back fastest; Adam Tornhill's Your Code as a Crime Scene popularised this. Teams that manage debt well keep it visible (tickets with a stated cost, not a vague "refactor" backlog), pay it continuously in small pieces attached to feature work, and reserve a predictable share of capacity for it rather than negotiating each item.

Talk track

"With legacy code I first pin the current behaviour with characterisation tests, create seams so I can substitute dependencies, and then refactor in small behaviour-preserving steps, separate from feature changes. For anything that crosses a deploy boundary, like a schema or an API, I use expand, migrate, contract so that every step is backward compatible and reversible."

7Technical writing: design documents, requirements and API docs

Writing is how an engineer's thinking reaches people who were not in the room, including their future selves. The more senior the role, the more of the work is writing: a staff engineer's design document can steer the work of twenty people for a year, and a vague requirement can waste the same amount.

7.1Why writing scales, and the habits that make it readable

A meeting reaches the people in it once; a document reaches everyone who will ever need it, asynchronously, and it can be reviewed line by line. Writing is also a thinking tool: a design that cannot be explained in two clear pages is usually not understood yet. That is why many software companies put written proposals at the centre of decision making: Google's design docs, the RFC processes of Rust, Python (PEPs) and many product companies, and Amazon's narrative memos read silently at the start of a meeting.

The habits that make technical writing readable are few. Start with the conclusion: what is proposed, or what the reader must decide, in the first paragraph ("bottom line up front"). Write for a named reader and state what they already know. Prefer concrete examples to abstract descriptions: one sample request and response explains an API faster than a page of prose. Use numbers with units and sources. Separate facts, assumptions and opinions, and mark which is which. Keep one idea per paragraph, and cut every sentence that does not help the reader decide or act.

7.2Design documents and RFCs

A design document is written before significant work starts, when changing direction is still cheap. Its job is to get the right people to find the problems in an idea early: the security engineer who sees that the promo-code endpoint can be brute-forced, the data team who notice that the new event breaks their pipeline, the SRE who asks how it will be rolled back. Not every change needs one; a useful rule is to write one when the work takes more than a couple of engineer-weeks, crosses team boundaries, changes a public interface or data model, or is hard to reverse.

The sections that recur across companies are: context and problem; goals and, just as important, non-goals (what this deliberately does not solve, so reviewers do not ask for it); the proposed design, with diagrams at the right level (Section 8); alternatives considered and why they lost; cross-cutting concerns such as security, privacy, observability, cost, migration and rollout; and open questions. The alternatives section is what distinguishes a design document from a description: it shows that the problem was explored and gives reviewers something to argue with.

A design document has a lifecycle: draft, in review, approved, implemented, and eventually superseded. Mature teams keep that status at the top and link the document from the code and the ADR log (Section 9), because a design document that silently disagrees with the code is worse than none. Review happens in comments plus, for contentious designs, a short meeting whose outcome is written back into the document.

Pitfall

Design documents fail in two opposite ways: the 50-page document nobody reads, written to look thorough, and the "doc" that is a bullet list of the chosen solution with no problem statement and no alternatives. Two to six pages, with alternatives and non-goals, is the usual sweet spot.

7.3Requirements and specifications: vague versus testable

A requirement is useful if two people reading it would build the same thing and write the same test. Most bad requirements fail that test because they use words without a measurement ("fast", "user-friendly", "robust"), hide several requirements in one sentence, or describe a solution instead of a need.

The patterns in the right column follow the EARS templates (Easy Approach to Requirements Syntax, Mavin and colleagues at Rolls-Royce, 2009): ubiquitous ("The system shall…"), event-driven ("When <trigger>, the system shall…"), state-driven ("While <state>…"), unwanted behaviour ("If <condition>, then the system shall…") and optional feature ("Where <feature is included>…"). In agile product teams the same discipline appears as user stories with acceptance criteria, often written as Given/When/Then scenarios that double as automated tests (behaviour-driven development):

Scenario: Expired promo code is rejected
  Given a promo code "AUTUMN10" that ended on 2026-10-31

  And the response contains error "PROMO_EXPIRED"

Non-functional requirements (latency, availability, security, privacy, cost) deserve the same precision, and in services they usually become SLOs (Section 11.1), which turns a requirement into something measured continuously in production.

In automotive

Automotive requirements live in a requirements tool, each with an ID, attributes, verification criteria and trace links to the system requirement it refines and to the tests that verify it; reviewing and baselining them is an ASPICE base practice. The writing rules are the same. See ASPICE SWE.1.

7.4API documentation and the four kinds of docs

Developer documentation fails most often because one document tries to do four jobs. The Diátaxis framework (Daniele Procida) separates them. Tutorials teach a newcomer by doing ("build your first checkout integration in 15 minutes"). How-to guides solve a specific task for someone who already knows the basics ("how to issue a partial refund"). Reference describes every endpoint, field, error code and limit, precisely and completely, and is best generated from the source of truth (an OpenAPI or protobuf definition). Explanation gives background and reasoning ("why payments are asynchronous"). Readers arrive with one of these needs; mixing them makes every page worse for everyone.

For an API, the reference is the contract, so it should come from the same definition the code and the contract tests use. Each operation needs: what it does in one sentence, every parameter with type, unit and constraints, a complete example request and response, every error with its meaning and whether retrying is safe, idempotency and rate limits, and the versioning and deprecation policy. "Is it safe to retry?" is the question most often missing and most often needed during an incident.

7.5READMEs, runbooks and docs as code

Two short document types do a lot of work. A README at the root of each repository says what the component is, who owns it, how to build, test and run it locally, and where the real documentation lives. A runbook (or playbook) is written for the on-call engineer at 3 a.m.: for each alert, what it means, how to check whether it is real, the safe first mitigation (roll back, switch off the flag, scale up), how to escalate, and links to the dashboards. Every page-worthy alert should link to its runbook entry.

Keeping documentation true is the hard part. Docs as code treats documentation like source: Markdown in the same repository, reviewed in the same pull requests, built by CI (with link checking), and published automatically. A PR that changes behaviour and not the docs is then visible in review. Generated documentation (API reference from OpenAPI, configuration reference from the code's own flag definitions, diagrams from text, Section 8.6) removes whole classes of drift.

A diagram is worth drawing when it answers a question faster than prose. Notations exist so that the reader does not have to guess what a box or an arrow means. The rule of thumb for any diagram: give it a title that states the question, include a legend if shapes or colours carry meaning, label every arrow with what flows or what is called, and say what is deliberately left out. Architecture views and levels as a concept (why one diagram is never enough) are explained in Software architecture 3.1; this chapter is about the notations themselves.

8.2The C4 model: four zoom levels

Simon Brown's C4 model is the most widely used lightweight notation for software architecture because it fixes the meaning of a box by its zoom level rather than by a large symbol vocabulary. Level 1, system context, shows the system as one box with its users and the external systems it talks to. Level 2, containers, opens the box: each container is something separately deployed or run (a web app, a service, a database, a queue), labelled with its technology, with arrows labelled by purpose and protocol. Level 3, components, opens one container to show its main internal modules. Level 4, code, is class diagrams, and is rarely drawn by hand. Supplementary views include the deployment diagram and dynamic diagrams for one scenario.

In practice the context and container levels give most of the value. A good container diagram answers "if I change this service, who is affected?" and "where is the data?" at a glance. Component diagrams are worth drawing only for containers that are large or that several teams work in.

8.3Sequence diagrams: confusing versus clear

A UML sequence diagram shows the participants of one scenario as vertical lifelines and the messages between them as arrows in time order, top to bottom. Solid arrows are calls, dashed arrows replies; a narrow bar on a lifeline shows when that participant is active; boxed fragments mark alternatives (alt), optional parts (opt), loops (loop) and parallel parts (par). It is the best notation for flows where order, retries and failures matter, which is to say most interesting backend flows.

The clear version also reveals a design decision that the confusing one hides: the order is written as PENDING before the payment provider is called, with the idempotency key, so that if checkout crashes between steps 4 and 5, a recovery job can find the pending order and ask the provider what happened, and a client retry with the same key does not charge twice (the reasoning is in Software architecture 9.3). Good sequence diagrams make such decisions visible, which is why reviewers of a design document often ask for one for the main flow and one for the most important failure.

8.4State machine diagrams

A state machine diagram shows the states something can be in and the events that move it between them. Each transition is labelled event [guard] / action: the event that triggers it, an optional condition that must hold, and an optional action performed on the way. Its strength is completeness: once drawn, you can ask for every state and every event "what happens if this event arrives now?", and each missing arrow is either a deliberate rejection or a bug waiting to happen.

State machines are worth drawing for anything with a lifecycle that crosses requests: orders, subscriptions, payment attempts, connections, device modes. They also translate directly into code: an explicit transition table or a type per state (Section 6.4) is far less error-prone than a status string updated from ten places.

8.5Data-flow diagrams and trust boundaries

A data-flow diagram (DFD) shows where data comes from, which processes transform it, where it is stored and where it goes, without saying anything about the order of calls. Its classic symbols are rectangles for external entities, circles or rounded boxes for processes, open-ended rectangles for data stores, and labelled arrows for flows. Its main modern use is threat modelling: draw the trust boundaries (internet, internal network, third parties) as dashed lines, then examine every flow that crosses one, for example with Microsoft's STRIDE categories (spoofing, tampering, repudiation, information disclosure, denial of service, elevation of privilege).

Privacy reviews use the same picture: which flows carry personal data, which stores keep it, and for how long. The automotive counterpart, threat analysis and risk assessment under ISO/SAE 21434, starts from the same kind of diagram; see Standards 5.2.

8.6Diagrams as code and keeping them true

A diagram drawn in a drawing tool and pasted into a wiki starts to rot the day after it is drawn. Writing diagrams as text (Mermaid, which GitHub and GitLab render inline in Markdown; PlantUML; Structurizr DSL for C4 models) puts them in the repository next to the code, makes changes reviewable as diffs, and lets one model produce several views. The cost is less control over layout; for the few diagrams that need careful layout, keep the source file of the drawing tool in the repository too.

9Architecture decision records and design reviews

Code shows what was decided; it almost never shows why, or what was rejected. Architecture decision records keep the why next to the code, and design reviews are the meeting where a decision is tested before it becomes expensive to change.

9.1Why decisions need a record

Every long-lived codebase has decisions whose reasons have been forgotten. Why does checkout write the order before calling the payment provider? Why is pricing a separate service? A new engineer who does not know the reason faces two bad options: leave something strange alone forever, or "fix" it and rediscover the reason in production. Michael Nygard proposed the architecture decision record (ADR) in a 2011 blog post as the lightest possible fix: for each architecturally significant decision, a short text file in the repository, numbered, never edited after acceptance except for its status, and superseded by a new record when the decision changes. The log of ADRs becomes the history of the architecture.

"Architecturally significant" means the same thing as in Software architecture 13.2: expensive to reverse, or affecting many teams or quality attributes. The choice of a message broker, a consistency model, a public API style or a data retention rule qualifies; the choice of a logging library usually does not. The content of such decisions (how to weigh the trade-offs) belongs to the architecture chapter; this section is about writing them down.

9.2The format: context, options, decision, consequences

Nygard's original format has five parts: a title naming the decision, a status (proposed, accepted, deprecated, superseded by ADR-n), the context (the forces at play: requirements, constraints, what is known and what is not), the decision stated in active voice ("We will…"), and the consequences, all of them, not only the good ones. Later variants add an explicit list of considered options with pros and cons (MADR, Markdown Any Decision Records) or compress the whole thing into one sentence (Olaf Zimmermann's Y-statement: "In the context of…, facing…, we decided for… and against…, to achieve…, accepting…"). The format matters less than three properties: the record is short enough to be written, it lists the alternatives, and the consequences include the costs the team accepts.

# ADR-0017: Idempotency keys for payment authorisation

ADRs live in the repository (for example docs/adr/0017-idempotency-keys.md), are proposed and reviewed as pull requests like code, and are linked from the code they explain. When the decision changes, a new ADR supersedes the old one and both statuses are updated; the old text stays, because the reasoning of the time is exactly what a future reader needs. Tools such as adr-tools or Log4brains generate indexes, but a numbered folder and a README list are enough.

Pitfall

An ADR written after the fact to justify a decision already implemented tends to list only the chosen option and only its benefits. It is still better than nothing, but the value of an ADR comes from writing it while the alternatives are real, ideally as the conclusion of a design document.

9.3Design reviews: finding the risk while it is cheap

A design review is a structured critique of a proposal before it is built. Its purpose is not approval for its own sake but risk discovery: the reviewers' job is to find what will hurt (scaling limits, failure modes, security holes, operational burden, conflicts with other teams' plans) while changing the design costs a document edit rather than a rewrite.

Reviews that work have a few things in common. The design document is circulated in advance, or read silently in the first part of the meeting, so the time is spent on questions, not on a presentation. The right people are present: owners of the systems the design touches, someone from security and from operations, and at least one person not invested in the proposal. The author states which decisions are open and which are settled. Reviewers work through a short list of lenses: does it solve the stated problem; what are the failure modes and what happens to users in each; how does it scale and what does it cost; how is it observed, deployed and rolled back; what does it do to data (migration, retention, privacy); how will it be tested. The outcome is written into the document: approved, approved with changes (listed), or needs another round, and the significant decisions become ADRs.

Larger organisations add an architecture review board or a staff-engineer forum for cross-team decisions. The risk is that it becomes a gate that teams route around. The healthier pattern, common in product companies, is that review is mostly peer review by those affected, with the forum reserved for decisions that set standards for many teams, and with a published turnaround so that it never becomes the bottleneck.

Talk track

"For any decision that is expensive to reverse I write a short design doc with non-goals and alternatives and get it reviewed by the teams it affects, specifically looking for failure modes, rollout and operability. The decision itself goes into an ADR in the repo: context, options, decision and the consequences we accept, so the next person knows why."

10Delivery: trunk-based development, feature flags and continuous delivery

Continuous delivery is the ability to put any change into production safely, quickly and routinely. Its central trick is to separate two things that used to be one event: deploying code and releasing a feature. Once deployment is boring and release is a switch, both can happen many times a day.

10.1CI, continuous delivery and continuous deployment

The three terms are often blurred. Continuous integration means every engineer integrates into the shared main line at least daily, and every integration is verified by an automated build and test run; it is a practice of people, supported by a CI server, not the CI server itself. Continuous delivery means main is always in a releasable state and any version can be deployed to production by pressing a button. Continuous deployment goes one step further: every change that passes the pipeline is deployed to production automatically, with no human decision. Many teams practise continuous delivery for regulated or customer-facing changes and continuous deployment for internal services.

The deployment pipeline (Humble and Farley, Continuous Delivery, 2010) is the machinery. Its core rule is build once, promote many times: CI builds one immutable artifact (a container image identified by its digest), and the very same artifact moves through staging, canary and full production, configured by environment. Rebuilding for each environment would mean that what was tested is not what runs. The infrastructure behind it (runners, caches, registries, signing and SBOMs) is in Build systems 11.2–11.6.

10.2Trunk-based development in practice

Section 2.3 introduced trunk-based development as a branching model. In daily work it looks like this. An engineer pulls main, makes a change of a few hours' work, opens a pull request, gets it reviewed and merged the same day. Unfinished features are merged too, behind a flag or behind an interface whose new implementation is not yet wired in. A merge queue (Section 13.2) tests each PR against the latest main before it lands, so main stays green even when twenty PRs merge per hour. If main does break, the first response is to revert the offending commit, not to debug on main; the author fixes it on a branch and re-lands it.

The practice has prerequisites, and teams that adopt the branching model without them get the worst of both worlds: a pre-merge pipeline fast enough that waiting for it is not a reason to batch work (ten to fifteen minutes is a common target), tests reliable enough that red means broken, flags for incomplete work, and a culture in which keeping main green is everyone's job.

10.3Feature flags: deploy is not release

A feature flag (or toggle) is a runtime switch that chooses between code paths: if flags.Enabled("promo_codes", user) { … }. The flag's value comes from a flag service or configuration and can be changed without a deploy, often per user, per percentage of traffic, per country or per customer. Pete Hodgson's taxonomy (on martinfowler.com) is the standard way to think about them, because the four kinds have very different lifetimes. Release toggles hide unfinished or not-yet-launched features and should live days to weeks. Experiment toggles split users for A/B tests and live as long as the experiment. Ops toggles are kill switches for expensive or risky functionality (turn off recommendations under load) and may live for years. Permission toggles enable features for certain customers (beta programmes, paid tiers) and are really product configuration.

Flags give three things. They decouple deploy from release, so code can be merged and deployed continuously while the launch is a product decision. They make release reversible in seconds: switching a flag off is faster and safer than any rollback. And they allow progressive exposure: employees first, then 1 % of users, then more, watching the metrics at each step.

The cost is complexity. Every flag doubles the number of code paths that exist, and combinations of flags create states nobody tested. Stale release flags are technical debt with a particularly nasty failure mode: the 2012 Knight Capital incident, in which the firm lost more than 460 million dollars in about 45 minutes, involved a deployment that missed one of eight servers and a reused flag that reactivated old, dead trading code on that server. The discipline that keeps flags safe: each flag has an owner, a type and an expiry date; release flags are removed within weeks of full launch (the removal PR is part of the feature's definition of done); flag names are never reused; and both paths are tested while the flag exists.

In practice

Evaluate flags at the edge of a code path, not deep inside loops, and pass the decision down; log the flag variants a request saw, so that an incident timeline can show which users were on the new path. Hosted services (LaunchDarkly, Unleash, Flagsmith, cloud-provider configuration services) and the OpenFeature standard API make the mechanics easy; the discipline is the hard part.

10.4Progressive delivery: canaries and how big they should be

Progressive delivery exposes a new version to a growing share of traffic and checks it at each step. A rolling update replaces instances a few at a time; it limits capacity loss but not the blast radius of a bad version, because new instances serve real users immediately. Blue/green deployment runs the full new version beside the old one and switches traffic at once, with instant switch-back. A canary sends a small share of traffic to the new version and compares its metrics (error rate, latency, saturation, business metrics such as orders per minute) with the old version serving the rest; automated canary analysis (for example Kayenta in Spinnaker, Argo Rollouts or Flagger) fails the deployment and rolls back if the canary is statistically worse.

How large should the canary be? Intuition says "small, so fewer users are hurt". The interactive below shows why that is only half true. It models the checkout API at 200 requests per second with a normal error rate of 0.5 %; a canary analysis that needs at least one minute of data, fails the build when the canary's error rate is three standard errors above the baseline, and promotes the build after 60 minutes.

The model makes the trade-off precise. To tell a regression of size δ (new error rate minus baseline) from noise, the analysis needs a certain number of canary requests, roughly n ≈ z²·p(1−p)/δ²: about 1,800 for a build that fails 1 % instead of 0.5 %. The canary share only decides how fast those requests arrive. So for a subtle regression, the number of users hurt before detection is roughly n·δ, about 9 requests in this example, whatever the canary size, while a 1 % canary takes 15 minutes and a 5 % canary 3 minutes. If the regression is subtler still (0.75 %), a 0.5 % canary would need two hours and the build would be promoted to everyone undetected. For a build that fails every request, detection is limited by the one-minute minimum observation, and the damage is proportional to the canary share: about 120 failed requests at 1 %, about 6,000 at 50 %.

The practical conclusion matches what large operators do: start small for the first minutes to catch gross failures with little damage, then increase the share so that subtle regressions become statistically visible within the bake time, and make the analysis compare canary against a baseline of the old version running at the same time, not against yesterday. Business metrics need much more traffic than error rates, which is one reason to roll out over hours rather than minutes.

10.5DORA metrics: measuring delivery performance

The DevOps Research and Assessment programme (DORA, started by Nicole Forsgren, Jez Humble and Gene Kim, now part of Google Cloud) has surveyed tens of thousands of professionals since 2014 and published the yearly Accelerate State of DevOps reports and the book Accelerate (2018). Its lasting contribution is a small set of outcome metrics that predict organisational performance and that do not reward one dimension at the expense of another.

Two metrics measure throughput: deployment frequency (how often the team deploys to production) and lead time for changes (from commit to running in production). Two measure stability: change failure rate (the share of deployments that cause a failure needing remediation, such as a rollback, hotfix or incident) and time to restore service, renamed failed deployment recovery time in recent reports (how long it takes to recover from such a failure). The 2024 report added a fifth, rework rate (the share of deployments that are unplanned fixes). In recent reports the elite cluster deploys on demand (many times a day), has lead times under a day, a change failure rate around 5 % and recovers in under an hour; the clusters' exact boundaries move from year to year, so treat them as orientation, not targets.

The central finding is that throughput and stability correlate positively: teams that deploy most often also fail least and recover fastest, because the same practices (small batches, automation, trunk-based development, loosely coupled architecture, fast feedback) drive both. That is the empirical case for everything in this chapter.

Pitfall

DORA metrics describe a team's delivery system; they are not individual performance measures and not targets to be gamed. Counting deploys invites splitting one change into ten deploys; counting "failures" invites not declaring incidents. Use them as a team to find the bottleneck (long lead time usually means slow review or slow CI; high failure rate usually means weak tests or big batches), and pair them with measures of developer experience such as the SPACE framework (Section 13.3).

Talk track

"Deploy is technical, release is a product decision. We build one artifact, promote it through a canary with automated analysis, and keep features dark behind flags that have owners and expiry dates. We track the DORA metrics as a team: deployment frequency and lead time for speed, change failure rate and recovery time for stability; the research shows they improve together."

11Running in production: SRE practice

Site reliability engineering, as Google described it in 2016, applies software engineering to operations. Its most influential idea is to make reliability a number agreed between product and engineering, so that "should we ship features or fix reliability?" becomes a calculation instead of an argument.

11.1SLIs, SLOs and SLAs

A service level indicator (SLI) is a measurement of user-visible behaviour, best expressed as the ratio of good events to all events: the share of checkout requests that returned a non-5xx response within 300 ms, measured at the load balancer. A service level objective (SLO) is a target for an SLI over a window: 99.9 % of checkout requests are good, over a rolling 30 days. A service level agreement (SLA) is a contract with customers that says what happens (credits, penalties) if a level is missed; it is usually looser than the internal SLO, so that the team gets warned before the contract is breached.

Good SLIs measure what users experience, as close to the user as practical: availability and latency of the requests users make, freshness of data for a pipeline, correctness for a payment system. CPU usage and pod restarts are useful for diagnosis but are not SLIs, because users do not feel them directly. A small number of SLOs per service (two or three) is better than twenty, because each one should be something the team is willing to act on.

The choice of target is a business decision with an engineering cost. Every additional nine costs roughly ten times less permitted failure, and the dependencies set a ceiling: a service cannot be more available than the critical services it calls in series. 100 % is the wrong target for almost everything, because users cannot tell 99.99 % from 100 % through their own unreliable networks and devices, while the cost of the last fraction is enormous.

11.2Error budgets and burn-rate alerts

The error budget is the complement of the SLO: with 99.9 % over 30 days, 0.1 % of requests may fail, which at checkout's monthly average of about 100 requests per second is roughly 260,000 failed requests, or the equivalent of 43 minutes of total outage. The budget turns reliability into a resource. While budget remains, the team ships features, runs experiments and takes risks; when it is spent, an error budget policy, agreed in advance with product management, takes effect: typically a freeze on feature releases (except fixes) until the budget recovers, and reliability work moved to the top of the backlog. Agreeing the policy before it is needed is the point; negotiating it during a bad month never works.

The same idea gives better alerts. Alerting on every error, or on "error rate above 1 % for 5 minutes", pages people for blips that do not threaten the SLO and misses slow leaks that do. The burn rate is how fast the budget is being consumed relative to plan: a burn rate of 1 uses exactly the budget over the window, 14.4 uses it in about two days. The Google SRE Workbook recommends alerting on burn rate over two windows at once: page when 2 % of the 30-day budget is burnt within one hour (burn rate 14.4) or 5 % within six hours (burn rate 6), and open a ticket when 10 % is burnt within three days (burn rate 1). Each condition is also checked over a short window (one twelfth of the long one) so that the alert stops soon after the problem does.

Numbers

For a 30-day window: burn rate = (error rate) / (1 − SLO). With SLO 99.9 %, an error rate of 1.44 % is a burn rate of 14.4. Time to exhaust the budget = 30 days / burn rate: 50 h at 14.4, 5 days at 6, 30 days at 1.

11.3On-call that people can sustain

On-call is where reliability practice meets people's lives, and it fails when it is treated only as a rota. The SRE principles are concrete. Every page must be urgent, actionable and real: if the right response to an alert is "wait and see" or "nothing", it should be a ticket or a dashboard, not a page. Every page links to a runbook. The load is bounded: Google's SRE book suggests at most about two incidents per 12-hour shift, because a proper incident with follow-up takes hours, and that operational work ("toil": manual, repetitive, automatable work that scales with the service) should stay below half of an SRE's time, with the rest spent on engineering that reduces future toil.

Practical rotations have a primary and a secondary, at least six to eight people per rotation so that each person is on call one week in six or more, a handover at the end of each shift summarising open issues, and a regular review of all pages: which were noise, which runbooks were wrong, which alerts should be removed. Teams that own their services and carry their own pager ("you build it, you run it") have a strong incentive to make them reliable, which is the point; teams that are paged for others' services without the power to change them burn out.

11.4Incident response: mitigate first

An incident is an unplanned event that degrades service enough to need a coordinated response. Most companies define severity levels by user impact (for example SEV1: checkout unavailable for many users; SEV3: a minor feature degraded) so that the response scales with the impact. The structure of a response comes from emergency services' incident command systems, as adapted in the Google SRE book: an incident commander who coordinates and decides but does not debug, an operations lead who makes changes to the system, a communications lead who keeps stakeholders and status pages updated, and, for long incidents, a scribe who keeps the timeline. Separating these roles stops the most common failure, where the most senior person debugs and nobody coordinates or communicates.

The priority order is fixed: stop the bleeding, restore service, then find the cause. If the problem started with a deploy or a flag change, roll back or switch off first and investigate later; a rollback that turns out unnecessary costs minutes, an hour of debugging while users fail costs far more. The incident is declared early (declaring and downgrading is cheap) and closed with a clear statement that service is restored, followed by the postmortem.

Talk track

"We define two or three SLOs per service on user-visible behaviour, agree an error budget policy with product in advance, and alert on burn rate rather than raw errors. Pages must be urgent and actionable with a runbook. In an incident we separate command, operations and communications, and we mitigate first, usually with a rollback or a flag, before looking for the cause."

12Incident analysis, debugging reports and root-cause analysis

An incident that is mitigated but not understood will come back. The analysis afterwards, and the debugging report for a hard bug, are how a team turns one painful event into permanent improvements. The quality of that analysis depends less on templates than on two habits: reconstructing what actually happened before explaining it, and looking for all the conditions that allowed it rather than one culprit.

12.1Debugging as a method, and the debugging report

Hard bugs are found by method, not by staring. The loop is the scientific one: reproduce the failure reliably (if it cannot be reproduced, add the logging or tracing needed to catch it next time); reduce it to the smallest case (fewer requests, a smaller input, one service); form a hypothesis that explains all observations; design an experiment whose result would refute the hypothesis; repeat. Bisection is the most powerful general tool, and it applies to more than commits: bisect the input (half the cart lines), the configuration (half the flags), the environment (staging versus production) and the time window. Tools for observing a running system without changing it, such as tracing, profiling and system-call tracing, are in Linux 10.

A debugging report, written when a hard bug is solved, saves the next person days. It is short and factual:

## Symptom
What was observed, where, since when, how often (with links to graphs and tickets).
## Reproduction
Smallest known steps or input; environment; reliability (e.g. 3 of 10 runs).
## Investigation
Hypotheses tried, in order, and the evidence that ruled each in or out.
## Cause
The mechanism, explained so that someone else could have predicted the bug.
## Fix and verification
The change (PR link), the test that now covers it, how we verified in production.
## Why it escaped
Which test, review or gate could have caught it, and the follow-up for that.

The last section is what connects debugging to quality: every escaped bug is evidence about a missing or weak feedback loop.

12.2A worked incident: the promo-code slowdown

Here is an incident on the checkout service, reconstructed as a postmortem team would. The promo-code feature (Section 3.3) had been at 10 % of shoppers behind its flag for a day with no visible problem. At 14:02 a product manager raised it to 50 % ahead of a campaign. The new code path asked the pricing service for a quote once per cart line instead of once per cart, a pattern that had looked harmless in review and in tests with three-line carts. Campaign traffic brought large carts; pricing latency rose from 180 ms to 2.4 s at the 99th percentile; checkout requests began to time out; mobile clients retried immediately without backoff, tripling the load on an already slow pricing service.

The response went reasonably well. The fast-burn alert (Section 11.2) paged at 14:13; the on-call engineer declared an incident at 14:16, an incident commander took over coordination, and the operations lead, looking at the change log, noticed the flag ramp at 14:02 and switched the flag off at 14:21. Error rates returned to baseline by 14:24, and the queue of client retries drained by 14:31. The idempotency keys from ADR-0017 meant that no shopper was charged twice despite the retries. Up to 20 % of checkout requests failed for 17 minutes, about 30,000 requests in total. At the month's average of roughly 100 requests per second, the 99.9 % SLO allows about 260,000 failed requests in 30 days, so this one incident used more than a tenth of the budget.

12.3Beyond "the root cause": five whys, contributing factors and the Swiss cheese

The traditional tool is the five whys (from the Toyota Production System): ask why the failure happened, then why that happened, five times. Applied here: checkout failed because pricing was slow; pricing was slow because of one call per cart line; that was written because the author did not know about the batch endpoint; the author did not know because it is undocumented; it is undocumented because… The chain is useful for getting past the first symptom, but it has a known weakness: it produces one linear story and stops at whatever the asker finds satisfying, often a person ("the author should have known").

Complex systems rarely fail for one reason. Richard Cook's short paper How Complex Systems Fail (1998) puts it directly: catastrophe requires multiple failures, and "root cause" is a social construction that says more about when the analysis stopped than about the system. James Reason's Swiss cheese model gives the picture: each layer of defence has holes, and an incident happens when the holes in several layers line up. The useful analysis therefore lists contributing factors across all layers and asks, for each, how to make the hole smaller or the layer independent of the others.

Other tools exist for different needs. A fishbone (Ishikawa) diagram groups possible causes by category (people, process, tools, environment) and helps a group brainstorm. A fault tree works top-down from the failure through AND/OR gates and is used where probabilities matter, notably in safety analysis. For software incidents, a carefully reconstructed timeline plus a list of contributing factors per layer is usually the most productive combination.

Why it matters

"Human error" is never a useful conclusion. People made the decisions that seemed reasonable with the information and tools they had; the question is why the system made the bad decision easy and the consequences large. Analyses that blame people teach everyone to hide mistakes, and hidden mistakes cannot be learned from.

12.4Blameless postmortems and action items that get done

A blameless postmortem (a term popularised by John Allspaw at Etsy in 2012 and by the Google SRE book) is a written analysis that assumes everyone acted in good faith and focuses on the system. Blameless does not mean nameless or consequence-free for negligence; it means that the goal is learning, so people describe what they saw and did honestly. Postmortems are written for every incident above a severity threshold and for near misses that could have been severe, reviewed in a meeting, and shared widely, because other teams have the same holes.

13Coding standards, CI quality gates and engineering health

Every practice in this chapter can be left to good intentions or built into the workflow. The ones that last are automated: a formatter rather than a style debate, a gate on new findings rather than a quality campaign, a handful of measured signals rather than a feeling that things are getting worse.

13.1Coding standards as automation

A coding standard has two parts with different value. The formatting part (indentation, line length, brace placement) matters only in that it is consistent; it should be enforced by a formatter that rewrites code automatically (gofmt, rustfmt, Black or Ruff for Python, Prettier, clang-format), so that no human ever discusses it. Go's decision to ship one canonical formatter with the language removed an entire category of review comments across its ecosystem. The semantic part (avoid these constructs, handle errors this way, name things like this) carries real knowledge and is enforced, where possible, by linter rules, with a short written guide for what tools cannot check. Public guides such as Google's style guides for many languages and the C++ Core Guidelines are good starting points; a team's own guide should mostly say which of their rules apply and what is added.

The rule for introducing a standard into existing code follows the static-analysis recipe: format the whole codebase once in a single mechanical commit (and list it in .git-blame-ignore-revs so blame skips it), then enforce on every change. Lint rules with many existing violations are introduced with a baseline and enforced only on new code.

In automotive

MISRA C:2023, MISRA C++:2023 and AUTOSAR C++14 are coding standards whose rules are mandatory, required or advisory, with formal deviation records, and compliance is shown with a qualified analyser as part of the safety case. See C++ 14 and Functional safety 7.5 on tool confidence.

13.2Designing CI quality gates

A quality gate is an automated check that blocks a change from moving forward. Gates are powerful because they apply to every change without anyone remembering, and dangerous for the same reason: a slow, flaky or noisy gate blocks everyone and teaches people to work around it. Designing gates is therefore a balance of what to block on, where in the pipeline, and how fast.

The principles that hold up are these. Block only on what is new, reliable and actionable: new lint or analyser findings in changed lines, failing tests, coverage of changed lines below a threshold; old findings and trend metrics report but do not block. Put fast checks first: formatting and lint in seconds, build and unit tests in a few minutes, so that most failures are found early and cheaply. Keep the pre-merge path within a budget, commonly ten to fifteen minutes, with caching and test selection; move expensive checks (sanitizer builds, long fuzzing, full end-to-end suites, mutation analysis, performance benchmarks) after merge, where they run on main and either report or block the next release. Make the gate explain itself: a failure must say what is wrong and how to fix it, ideally with an autofix.

The merge queue closes a gap that per-PR checks leave open. Two PRs can each pass CI against the main of an hour ago and still break main when combined. A merge queue (GitHub merge queue, GitLab merge trains, Bors, Mergify) tests each PR, or a batch of PRs, on top of the current main plus everything ahead of it in the queue, and merges only if that combination passes. This implements what Graydon Hoare called the "not rocket science rule of software engineering": automatically maintain a repository of code that always passes all the tests.

Pitfall

A required check that sometimes fails for no reason is worse than no check. Track each gate's false-failure rate and duration as carefully as the code it checks, and treat a flaky gate as a production incident of the developer platform.

13.3Measuring engineering health

Managers and staff engineers are regularly asked "is our engineering getting better?". A small, balanced set of measures answers it far better than any single number. The DORA metrics (Section 10.5) cover delivery. A few workflow and quality signals locate problems: pull-request review latency and size; pre-merge CI duration and flaky-failure rate; escaped defects per release and their severity; incidents, error-budget consumption and pages per on-call shift; and the age of the oldest open postmortem action items. Developer experience matters as much as throughput: the SPACE framework (Forsgren and colleagues, 2021) recommends combining Satisfaction and well-being, Performance (outcomes), Activity, Communication and collaboration, and Efficiency and flow, and always using several of them together, because any single one is easy to game or misread.

Three rules keep metrics useful. Measure teams and systems, never individuals; lines of code, commit counts or story points per person reward the wrong behaviour immediately. Use metrics to ask questions, not to set targets (Goodhart's law again). And pair every number with a qualitative source, usually a short regular developer survey, because people know where the friction is before the dashboards do.

13.4Improving a team's practice: where to start

A tech lead or staff engineer joining a team with weak practice cannot introduce everything at once, and should not try. The approach that works is the one this chapter started with: find the feedback loop that hurts most and shorten it. If main is often broken, a merge queue and fast required checks come first. If reviews take days, smaller PRs and a response-time norm. If production surprises are frequent, flags and a canary. If the same incidents recur, postmortems with tracked action items. Introduce one change, measure whether it helped, and make it automatic before moving on. Practices imposed as rules without automation decay within months; practices built into the workflow outlive the person who introduced them.

QSelf-check questions

Q.1Core questions

What is the difference between merge, rebase and squash merge, and which would you choose?Basic

A merge commit joins the branch with two parents and keeps history truthful but braided. Rebase replays the branch's commits on top of main as new commits, giving a linear history with every commit kept; it must not be used on shared history. Squash merge puts the whole PR into one commit on main. With small PRs I default to squash merge (one revertable, bisectable commit per reviewed change) and use rebase locally to tidy commits before review; for larger changes whose individual commits tell a story, rebase-and-merge keeps them.

Why do many companies prefer trunk-based development over GitFlow?Basic

Because integration frequency decides how big and surprising conflicts are. Long-lived branches hide integration problems until a big merge; trunk-based development integrates at least daily, so conflicts are small and found early. The DORA research associates it with higher delivery performance. It needs fast reliable CI, small PRs and feature flags for unfinished work; GitFlow still fits products with discrete versions maintained in parallel.

What makes a good pull request?Basic

One purpose that fits in a sentence, a size a reviewer can read carefully (a few hundred lines at most), refactorings separate from behaviour changes, and a description with why, what, evidence (tests, screenshots, benchmarks), risk and rollout, and what is deliberately left out. Large work is split into a sequence or a stack of PRs, with unfinished parts behind a flag.

What do you look for when reviewing code?Basic

In order of cost: whether the change solves the right problem in the right place with a sensible interface; correctness including edge cases, errors, concurrency and retries; whether the tests would fail if the code were wrong; operability (logs, metrics, rollout, rollback); then readability. Formatting and style are for tools. I mark comments as blocking or optional and approve when the change clearly improves the code, not when it matches my taste.

Explain the test pyramid. When would you not follow it?Basic

Many fast, precise unit tests; fewer integration tests; few slow, flaky but realistic end-to-end tests, because feedback speed and precision fall as tests get bigger. When most of the logic is glue between components (thin front-ends, microservices that mainly call others), the bugs are in the integration, so a trophy or honeycomb shape with more integration tests against real dependencies gives more confidence per test. The principle is: test at the smallest size that can catch the bugs that actually occur.

Mock, stub, fake, spy: what is the difference and when do mocks hurt?Intermediate

A stub returns canned answers; a fake is a simplified working implementation (in-memory repository); a spy records calls; a mock has expectations about calls and fails if they are not met. Mocks hurt when they are used for internal collaborators: the tests then check the implementation's call sequence, break on every refactoring, and encode possibly wrong assumptions about the dependency. Use real objects or fakes inside, mocks at the system boundary, and contract tests to check that boundary.

What is contract testing and what problem does it solve?Intermediate

Consumer-driven contract testing lets a consumer record the requests it makes and the responses it relies on as a contract; the provider replays the contract against its real code in its own pipeline, and a broker answers "can I deploy this version?" against what runs in production. It replaces fragile shared integration environments for API compatibility, tells providers which fields are actually used, and runs in seconds. It does not test behaviour under load or partial failure.

What is property-based testing? Give an example of a good property.Intermediate

Instead of examples, you state a rule that must hold for all inputs, and a library generates many inputs, then shrinks any failure to a minimal counterexample. Good properties are invariants (discount shares sum to the discount), round trips (parse(print(x)) == x), equivalence with a simple model, and metamorphic relations (adding an item never lowers the total). In the chapter's experiment, the invariant found that rounding each share separately fails for two one-cent lines and a one-cent discount.

How does coverage-guided fuzzing work?Intermediate

The target is compiled with instrumentation that reports executed code edges. The fuzzer mutates inputs from a corpus, runs them in process at high rates, and keeps any input that reaches new coverage, so the corpus evolves into deeper parts of the program. Sanitizers turn silent memory errors into crashes, and each crashing input is saved as a reproducer. It is most valuable for parsers of untrusted input.

Why is 100 % code coverage not a good goal?Intermediate

Coverage measures execution, not checking: a test without assertions gives the same coverage as a good one. As a target it invites such tests and spends effort on trivial code. Coverage is good at showing untested code; gate on coverage of changed lines and review uncovered branches. To know whether tests check behaviour, use mutation testing; in the chapter's example two suites with 100 % line coverage had mutation scores of 0 % and 88 %.

What is mutation testing and how do you make it affordable?Advanced

The tool makes small edits (mutants) to the code and runs the tests; a mutant that no test detects is a concrete gap, usually a missing boundary case or a weak assertion. Mutation score is the share killed. It is expensive, so run it only on changed lines, only with tests that cover the mutated line, skip unproductive mutants, and show a few survivors as review comments, as Google does, rather than gating on a score.

How do you work with legacy code that has no tests?Intermediate

Pin current behaviour with characterisation (golden-master) tests, introduce seams so dependencies can be substituted, then refactor in small behaviour-preserving steps, separate from feature changes. New logic goes in sprouted, fully tested functions. For changes that cross deploy boundaries, use expand–migrate–contract. Prioritise cleanup where the code changes often.

How would you rename a database column used by several services without downtime?Intermediate

Expand and contract: add the new column; deploy code that writes both; backfill and verify; switch reads to the new column behind a flag; stop writing the old column; drop it. Each step is backward compatible with the previous code version, because old and new versions run side by side during a deploy, and each step can be rolled back on its own.

What goes into a design document?Basic

Context and problem; goals and non-goals; the proposal with diagrams at the right level; alternatives considered and why they lost; cross-cutting concerns (security, privacy, observability, cost, migration, rollout and rollback); open questions; status and reviewers. Two to six pages, written before significant work, reviewed by the teams affected.

Turn "the system must be fast" into a good requirement.Basic

Name the scope, condition, measure and window: "For carts of up to 50 lines, the checkout API shall respond within 300 ms for 99 % of requests, measured at the load balancer over 30 days." That can be tested and monitored as an SLO. EARS patterns (When / While / If… then / Where) and Given/When/Then scenarios are good templates.

What is an ADR and what makes a good one?Basic

A short record of one architecturally significant decision: title, status, context, options considered, the decision and its consequences, including the costs accepted. It lives in the repository, is reviewed like code, is never rewritten after acceptance and is superseded by a new ADR when the decision changes. Good ones are written while alternatives are still real and list the downsides honestly.

Which diagrams would you draw for a new service?Basic

A C4 context view (who uses it, which external systems), a container view (deployables, technologies, protocols, data stores), sequence diagrams for the main flow and the most important failure path, a state machine for any entity with a lifecycle, a deployment view showing failure domains, and a data-flow diagram with trust boundaries for the threat model. Each answers one question, with labelled arrows and the source in the repository.

What is the difference between continuous integration, continuous delivery and continuous deployment?Basic

CI: everyone integrates into main at least daily and each integration is built and tested automatically. Continuous delivery: main is always releasable and any version can be deployed by a button press. Continuous deployment: every change that passes the pipeline goes to production automatically.

What are feature flags for, and what are their risks?Intermediate

They separate deploy from release, allow progressive exposure and A/B tests, and give kill switches that act in seconds. Risks: combinatorial code paths, untested flag combinations, stale flags as debt, and reused flags reactivating old code, as in the Knight Capital loss. Mitigate with owners, types and expiry dates per flag, removal as part of done, no name reuse, and tests for both paths.

What are the DORA metrics and how should they be used?Basic

Deployment frequency and lead time for changes (throughput), change failure rate and failed deployment recovery time (stability), with rework rate added in 2024. The research shows throughput and stability improve together. Use them per team to find bottlenecks, never per person and never as targets, and pair them with developer-experience measures.

Explain SLI, SLO, SLA and error budget.Basic

An SLI measures user-visible behaviour as good events over all events; an SLO is a target for it over a window (99.9 % over 30 days); an SLA is a contract with consequences, usually looser than the SLO. The error budget is 1 − SLO, the failure allowed in the window (43.2 minutes for 99.9 % over 30 days); an agreed policy says what happens when it is spent, typically a feature freeze.

How do you alert on SLOs?Advanced

On burn rate, the speed of budget consumption relative to plan, over two windows: page if 2 % of the 30-day budget burns in 1 h (14.4×) or 5 % in 6 h (6×); ticket if 10 % burns in 3 days (1×); each with a short confirmation window of one twelfth so alerts reset quickly. This pages for threats to the objective and ignores harmless blips.

Walk me through how you handle a production incident.Intermediate

Declare early with a severity; assign an incident commander, an operations lead and a communications lead; check recent changes and mitigate first (rollback, flag off, scale, fail over) before root cause; communicate on a schedule; close when service is restored. Then a blameless postmortem: reconstructed timeline, impact, contributing factors across layers, what went well, a few owned and dated action items.

What does "blameless" mean in a postmortem, and why?Basic

The analysis assumes people acted reasonably with the information and tools they had and asks why the system made the failure easy and its impact large. It is not about hiding names or excusing negligence; it is about getting honest accounts, because people who fear blame hide mistakes and the organisation stops learning.

How would you design CI quality gates for a team?Intermediate

Before merge, fast blocking checks within about 10–15 minutes: format and lint, build and unit tests, static analysis and coverage on changed lines only, integration and contract tests, review with code owners, then a merge queue that tests on the latest main. After merge: sanitizer builds, continuous fuzzing, mutation on diffs, end-to-end and performance tests, gating the release. Block only on new, reliable, actionable findings; track each gate's flakiness and duration.

How do you introduce static analysis into a large existing codebase?Intermediate

Measure each rule's false-positive rate on your code first, enable only precise rules, record a baseline of existing findings, gate only new findings in changed lines (a ratchet), show findings in review where fixing is cheapest, and fix old findings when touching the code. Developer trust is the scarce resource, so noisy rules stay off.

How would you measure whether engineering is improving?Advanced

A balanced set at team level: DORA metrics; workflow signals such as PR size and review latency, CI duration and flakiness; quality signals such as escaped defects, incidents, error-budget consumption and pages per shift; and a regular developer survey (SPACE dimensions). Use them to find and test hypotheses about bottlenecks, never to rank individuals.

Q.2Why and what if

Why does squash merging work well only with small pull requests?Why

Because the squash commit is the unit of revert and bisect. With a 30-line PR it is precise; with a 3,000-line PR, bisect points at a commit that contains everything and the internal steps are lost from main.

What if a fix is made only on the release branch?What if

The next release cut from main does not contain it, and the bug returns as a regression. Fix on main first, then cherry-pick to the release branch.

Why does git bisect fail in a repository with many broken commits?Why

Bisect classifies each tested commit as good or bad; a commit that does not build or fails for an unrelated reason can be neither, so the search must skip it and may end with a range instead of a commit. Keeping every commit on main green is what makes bisect reliable.

Why does review find fewer defects than people expect, and is it still worth it?Why

Reviewers read diffs without running them, attention drops on large changes, and many bugs need execution to surface. Review is still worth it for design, intent, maintainability and knowledge spread, and for the subtle bugs that need understanding; the mechanical bugs belong to tools.

What if every collaborator in a unit test is mocked?What if

The test verifies the call sequence of the implementation rather than its behaviour. It breaks on harmless refactorings and passes when the mocked behaviour differs from reality, so it gives both false alarms and false confidence.

Why did the naive discount allocation fail for prices [1, 1] and discount 1?Why

Each exact share is 0.5 cent; rounding each one independently gives 0 and 0 (Python rounds halves to even), so a cent disappears; with round-half-up, both become 1 and a cent appears. Independent rounding cannot preserve a sum; the largest-remainder method distributes the leftover cents explicitly.

What if a fuzz target ignores the result of the function under test?What if

The optimiser may remove the call or parts of it as dead code, so the fuzzer explores nothing, as happened in the chapter's first run. A fuzz target must keep the work observable, for example by using the result.

Why are sanitizers usually run after merge rather than on every PR?Why

They need separate builds (ASan and TSan cannot be combined) and slow tests by 2–15×, which would blow the pre-merge time budget. Running them on main continuously or nightly still finds bugs within hours, and any report is a real bug.

What if a team sets a hard 90 % coverage gate on the whole project?What if

People write tests that execute code without asserting much, test trivial getters, and avoid touching poorly covered legacy code because any change risks dropping the number. Coverage of changed lines in review and mutation hints target the effort where it matters.

Why does a boundary mutant (>= to >) often survive?Why

Typical tests pick values comfortably inside each region (10.00, 60.00), and for those values both operators give the same result. Only a test exactly at the boundary (50.00) tells them apart, and such tests are the ones most often missing.

What if you rename a column and drop the old one in a single migration?What if

During the rolling deploy, pods running the old code still read and write the old column and fail immediately; rolling back the code does not help because the column is gone. Expand–contract avoids it by keeping both columns until no running version needs the old one.

Why does Hyrum's law matter for semantic versioning?Why

SemVer promises that minor and patch releases are compatible, but consumers depend on behaviour beyond the documented contract (ordering, error texts, timing). A change that is compatible by the documentation can still break them, so "breaking" has to be judged by observed use, and widely used interfaces need careful migration even for small changes.

Why does a design document need a non-goals section?Why

It bounds the scope so reviewers do not demand features the design deliberately excludes, and it records what was consciously left out, which prevents scope creep and helps later readers understand the boundaries.

Why do the confusing and clear sequence diagrams of the same flow differ in what they reveal?Why

The clear one names real participants, numbers messages, shows replies and the failure path, so it exposes decisions such as writing the order as PENDING with an idempotency key before calling the payment provider. The confusing one hides order, payloads and failures, which are exactly what a reviewer needs to judge correctness.

What if an ADR is edited every time the decision changes?What if

The history of why the architecture is the way it is gets lost, and the record can no longer explain code written under the old decision. Superseding with a new ADR keeps both reasonings and the date of the change.

Why does a smaller canary not reduce the number of users hurt by a subtle regression?Why

Detection needs a fixed number of canary requests to separate the higher error rate from noise, about z²·p(1−p)/δ². The excess failures among those requests are about n·δ regardless of how fast they arrive; a smaller canary only takes longer to collect them, and may not finish within the bake time at all.

What if a release flag is never removed?What if

The dead branch stays in the code, doubling paths and tests, and the flag can be flipped by mistake or reused, reactivating untested old code, which is part of what happened at Knight Capital. Flag removal belongs in the feature's definition of done.

Why do deployment frequency and change failure rate improve together in the DORA data?Why

Frequent deploys mean small batches, which are easier to review, test, roll back and diagnose, and teams that deploy often have automated their pipeline and rollback. The same practices drive both, so there is no trade-off between speed and stability at the level of the delivery system.

What if the SLO is set to 100 %?What if

There is no error budget, so every deploy and experiment is a violation risk, change slows to a crawl, and the target is still missed because dependencies and networks fail. Users cannot distinguish very high availability from 100 % anyway; the target should be what users need and the business will pay for.

Why alert on burn rate instead of on error rate above a threshold?Why

A fixed threshold pages for short blips that do not threaten the SLO and misses slow leaks that do. Burn rate ties the alert to the objective: fast burns page quickly, slow burns become tickets, and the long-plus-short window pair gives both precision and fast reset.

What if the incident commander is also the person debugging?What if

Nobody coordinates: parallel changes collide, stakeholders get no updates, and the debugging person tunnels on one hypothesis. Separating command, operations and communications keeps the response organised.

Why is "human error" not an acceptable root cause?Why

It explains nothing about why the error was easy to make or why its effect was large, and leads to "be more careful" actions that do not work. The analysis should find the conditions in tools, process and design that made the mistake likely and harmful, and change those.

What if the merge queue is removed and PRs are only tested against the main they branched from?What if

Two PRs that each pass alone can break main together (semantic conflicts without textual conflicts). With many merges per hour, main is red more often, everyone's PRs fail for unrelated reasons, and trust in CI erodes.

Why should engineering metrics never be used to rank individuals?Why

Individual activity counts are easy to game and reward the wrong behaviour (splitting PRs, avoiding reviews, not declaring incidents); delivery performance is a property of the team and its system, and using metrics against people destroys the honesty the metrics depend on.

GGlossary

ADR (architecture decision record)
A short, immutable record of one significant decision: context, options, decision, consequences; superseded rather than edited.
Bisect
Binary search over commits (or inputs, configurations) to find the first one where a failure appears; needs about log₂(N) steps.
Blameless postmortem
Written incident analysis that focuses on system conditions rather than individual fault, so people report honestly.
Burn rate
Speed of error-budget consumption relative to plan; 1 uses the budget exactly over the window.
C4 model
Architecture notation with four zoom levels: system context, containers, components, code.
Canary
A small share of production traffic served by a new version and compared automatically with the old version.
Characterisation test
A test that records what existing code currently does (golden master) so that refactoring can be checked for unchanged behaviour.
Cherry-pick
Copying the change of one commit onto another branch as a new commit.
CODEOWNERS
A file mapping repository paths to people or teams whose approval is required for changes there.
Contract test
A test that checks a consumer's recorded expectations of an API against the provider's real implementation.
Continuous delivery
Keeping main always releasable so any version can be deployed on demand; continuous deployment deploys every passing change automatically.
Coverage
The share of lines, branches or conditions executed by tests; MC/DC is the strictest common form.
Design document
A short proposal written before significant work: problem, goals, non-goals, design, alternatives, cross-cutting concerns.
Data-flow diagram
Diagram of external entities, processes, data stores and flows; with trust boundaries, the basis of threat modelling.
DORA metrics
Deployment frequency, lead time for changes, change failure rate and failed deployment recovery time (plus rework rate since 2024).
EARS
Easy Approach to Requirements Syntax: sentence templates for ubiquitous, event-driven, state-driven, unwanted-behaviour and optional requirements.
Error budget
The failure allowed by an SLO in its window (1 − SLO), spent on change and risk; an agreed policy applies when it runs out.
Expand and contract
Parallel change: add the new alongside the old, migrate users, remove the old; every step backward compatible.
Feature flag
A runtime switch between code paths that separates deploying code from releasing a feature.
Flaky test
A test that passes and fails on the same code, usually because of timing, ordering, environment or external dependencies.
Fuzzing
Automated generation of many, often malformed inputs; coverage-guided fuzzers keep inputs that reach new code.
Hyrum's law
With enough users, every observable behaviour of an API is depended on by someone.
Incident commander
The person who coordinates an incident response and makes decisions, without doing the hands-on debugging.
Merge queue
A system that tests each change on top of the latest main plus queued changes and merges only passing combinations.
Mutation testing
Making small deliberate code edits and checking that tests detect them; the share detected is the mutation score.
Property-based test
A test that states a rule for all inputs and lets a library generate and shrink counterexamples.
Rebase
Replaying commits on top of another base as new commits, producing linear history.
Sanitizer
Compiler instrumentation plus runtime that reports memory errors, data races or undefined behaviour while the program runs.
Seam
A place where behaviour can be changed without editing the code there, typically an injected dependency, used to get legacy code under test.
Semantic versioning
MAJOR.MINOR.PATCH, where major signals incompatible change, minor compatible additions, patch compatible fixes.
SLI
Service level indicator: a measure of user-visible behaviour, ideally good events divided by all events.
SLO
Service level objective: a target for an SLI over a time window, agreed between engineering and product.
Squash merge
Integrating a pull request as a single new commit on main.
Static analysis
Finding defects by reasoning about code without running it, from compiler warnings to inter-procedural analysers.
Test double
A stand-in for a real dependency in a test: stub, fake, spy or mock.
Toil
Manual, repetitive, automatable operational work that grows with the service and has no lasting value.
Trunk-based development
A workflow in which everyone integrates into one main branch at least daily through short-lived branches.
