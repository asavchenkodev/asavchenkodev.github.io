Concurrency, parallelism and asynchronous programming

What threads, cores and accelerators really do at the same time, why the hardware reorders memory, how locks, atomics and lock-free queues keep shared data correct, and how a multi-camera perception pipeline is cut into stages, queues and workers that meet a deadline.

1The big picture: why software does several things at once

A camera ECU has six cameras delivering frames, a neural accelerator waiting for tensors, a CAN bus expecting an object list every 33 ms, a diagnostic tester asking questions and a logger writing to flash. A single sequential loop cannot serve all of them on time. Concurrency is how one program is structured to make progress on many things; parallelism is how the hardware actually executes several of them at the same instant. Almost every hard bug in embedded vision software lives at the boundary between the two.

1.1Concurrency is structure, parallelism is execution

Concurrency means that the lifetimes of several tasks overlap: task B starts before task A has finished. That can happen on a single core, where the operating system switches between threads every few milliseconds, or because a thread starts an I/O request and does something else while the device works. Parallelism means that two instructions really execute at the same moment, on two cores, in two SIMD lanes or on a CPU and a GPU at once. Rob Pike's short version is: concurrency is about dealing with many things at once, parallelism is about doing many things at once.

The distinction matters because the two give you different things. Concurrency buys responsiveness and lets slow waits (a frame arriving, a network reply) overlap with useful work; it helps even on one core. Parallelism buys throughput, but only when there is independent work and the cores are not starved by memory bandwidth. A program can be concurrent without being parallel (an event loop on one thread), and parallel without being concurrent in its structure (one loop split across eight SIMD lanes).

On a single core the scheduler creates the illusion of simultaneity. Each switch saves the registers of one thread, loads those of another and switches stacks; the direct cost on a modern Linux system is about 1–5 µs, and the indirect cost of refilling caches and branch predictors can be larger. That is why "just add a thread per task" stops scaling: hundreds of busy threads on six cores spend a visible part of their time switching.

1.2Processes and threads

A process is a running program with its own virtual address space: its own page tables, heap, global variables and file descriptors. The memory management unit enforces the boundary, so a wild pointer in one process cannot corrupt another. A thread is a path of execution inside a process: its own registers, program counter and stack, but sharing everything else with the other threads of the same process.

The choice between them is a trade between isolation and cost. Threads communicate by simply reading and writing the same memory, which is as fast as it gets and is also the source of every data race in this chapter. Processes communicate through pipes, sockets, message queues or shared memory that both sides map on purpose, which costs copies or explicit setup but gives fault containment: a crashing logging process does not take the perception process with it, and a safety monitor in its own process can be restarted or can restart others. On an automotive platform the process boundary is also a safety boundary. AUTOSAR Adaptive applications, QNX resource managers and ROS 2 nodes are processes for exactly this reason, and ISO 26262 freedom from interference is argued much more easily between processes than between threads.

Numbers

Creating a thread on Linux costs roughly 10–50 µs (mostly allocating and mapping its stack, 8 MB of virtual address space by default with glibc). fork() plus exec() of a new process costs from a few hundred microseconds to milliseconds, depending on its size. A switch between threads of the same process skips the page-table switch; on CPUs without tagged TLBs a process switch also flushes the TLB, which is one reason threads exist at all.

Pitfall

Threads share the heap, so a thread that corrupts memory corrupts everybody. Mixing a safety-relevant function and a quality-managed (QM) component as two threads of one process gives you no isolation argument; they need separate processes, separate address spaces or separate cores with memory protection.

1.3Synchronous, asynchronous, blocking and non-blocking

These four words describe what happens to the caller while an operation completes. A blocking call does not return until the result is there: read() on a socket puts the thread to sleep in the kernel until data arrives. A non-blocking call returns immediately, either with the result or with "not yet" (EAGAIN), and the caller has to come back later. An asynchronous operation is started now and completes later on its own, signalling completion through a callback, a future, a fence or an event; the caller never polls it. Synchronous simply means "the result is available when the call returns", which blocking calls and successful non-blocking calls both satisfy.

Blocking code is the easiest to read and is perfectly fine when a thread has nothing else to do; a capture thread that blocks on VIDIOC_DQBUF until the next frame is a good design. It becomes a problem when one thread must serve many sources, because one blocking call freezes all the others. Non-blocking calls plus a readiness mechanism (poll, epoll) are the basis of event loops (Section 6.4). Truly asynchronous interfaces are how accelerators work: you submit a command buffer to a GPU or NPU and receive a fence that signals later (Chapter 9).

1.4How much faster can it get? Amdahl's law

If a fraction \(p\) of a program's work can be parallelised and the rest is serial, then on \(n\) cores the best possible speedup is

\[ S(n) = \frac{1}{(1-p) + p/n}, \qquad \lim_{n\to\infty} S(n) = \frac{1}{1-p}. \]

The serial part, however small, sets a ceiling. With 95% parallel work the speedup can never exceed 20, and eight cores give only 5.9. The serial part in practice is not only code that cannot be split; it is also the lock everyone queues on, the single thread that merges results, the memory bus shared by all cores and the time spent creating and synchronising tasks. Drag the slider to feel how quickly the curve flattens.

Gustafson's law is the optimistic counterpart: when more cores are available, people usually process more data (more cameras, higher resolution) rather than the same data faster, and then the parallel part grows with the machine. Both views are useful. Amdahl tells you why a single camera stream does not get faster on a bigger SoC; Gustafson tells you why the same SoC can handle eight cameras instead of four.

"Adding cores only helps the part of the work that is independent. Before we buy a bigger SoC, we measure how much of the frame time is serial: the merge step, the locks, the memory bandwidth. If that is 20%, no number of cores gets us more than five times faster."

2What the hardware and the compiler do to your code

You write statements in an order and naturally expect every other thread to see their effects in that order. Neither the compiler nor the CPU promises that. Both reorder memory operations because it makes single-threaded code much faster, and both are allowed to as long as a single thread cannot tell the difference. Another thread can.

2.1Why reordering exists

A store that misses the cache would stall the core for 100 ns or more if it had to wait until the cache line arrived. So every modern core puts stores into a store buffer and keeps executing; the buffer drains into the cache later. Loads, on the other hand, are executed as early as possible, often speculatively and out of program order, because a waiting load is what stalls a pipeline. The core makes sure its own loads see its own buffered stores (store-to-load forwarding), so single-threaded code behaves exactly as written. Other cores only see a store once it leaves the buffer.

The compiler does the same kind of thing at a higher level. It keeps values in registers instead of re-reading memory, moves loads out of loops, merges or removes stores that seem redundant and reorders independent statements to fill pipeline slots. All of this is legal under the "as-if" rule, which promises only that a single thread cannot observe the difference.

Step through the classic store-buffering test. Two threads each write one variable and then read the other one. In every interleaving of the four statements at least one thread must see a 1, yet real machines, x86 included, return 0 for both.

Both variables are 0 in memory and in both caches. Core 0 will run x = 1; r1 = y;, core 1 will run y = 1; r2 = x;. Intuitively the outcome r1 = 0, r2 = 0 is impossible: whichever store happens first, the other core's later load should see it.

Each core executes its store, but the value only lands in the core's private store buffer. The core does not wait for the cache line to be acquired in exclusive state; it simply continues with the next instruction. Nobody else can see x = 1 or y = 1 yet.

Each core now loads the other variable. Its own store buffer does not contain it, so the load reads the cache, where the value is still 0. Result: r1 = 0 and r2 = 0. From the outside it looks as if each load happened before the store above it, a store→load reordering.

Microseconds later the stores reach the cache and memory holds x = 1, y = 1. The damage is done: both threads have already decided based on 0. This is exactly the pattern of hand-written mutual exclusion ("set my flag, then check yours"), which is why Peterson's and Dekker's algorithms are broken on real hardware without fences.

x86 allows only this one kind of reordering (a later load may pass an earlier store to a different address); its model is called TSO, total store order. Arm, RISC-V and Power are weakly ordered: stores can become visible to other cores in a different order than they were written, and loads can be reordered with each other as well. Code with a hand-made "ready" flag that worked for years on an x86 simulation PC fails on the Arm target, rarely and under load.

2.2Coherence is not ordering

Caches are kept coherent by hardware: a protocol such as MESI makes sure that for any single memory location all cores agree on one sequence of values, and that a write eventually reaches every other core. Before a core may write a line it must own it exclusively, which invalidates the copies in other caches. Coherence is a per-location guarantee. It says nothing about the order in which writes to different locations become visible, and that is the order your algorithm depends on when it writes data and then sets a flag.

Coherence has a performance side too. A cache line moving from one core to another costs roughly 40–100 ns on a single chip, against about 1 ns for an L1 hit. A variable written by many cores (a shared counter, a lock word) makes its line travel constantly, which is why contended atomics and locks are expensive even when nobody waits. Section 5.4 shows the nastiest form of this, false sharing.

2.3Data races are undefined behaviour

C and C++ define a data race precisely: two threads access the same memory location, at least one access is a write, at least one is not atomic, and neither happens before the other (Chapter 3). A program with a data race has undefined behaviour, not merely an unpredictable value. That rule is what allows the compiler to optimise as if no other thread existed. The classic consequence is the spin loop that never ends:

bool ready = false;              // plain bool, written by another thread: a data race

void wait_for_camera() {
    while (!ready) { }           // the compiler may load ready once:
    start_processing();          //   if (!ready) for (;;) { }   — an endless loop
}

Because no other thread may legally change ready without synchronisation, the compiler is entitled to read it once and keep it in a register. With optimisation enabled the loop really becomes infinite. The data race on a simple counter is subtler: count++ is a load, an add and a store, and two threads can interleave them so that one increment disappears.

Wider types make it worse. A 64-bit timestamp written by one thread on a 32-bit core can be read half-updated by another (a torn read), and a struct of two fields copied while another thread writes it can mix old and new fields. The fix in all cases is the same: either make the access atomic or protect it with a lock, which is the subject of the next two chapters.

Pitfall: volatile is not for threads

volatile tells the compiler that every access must really happen, which is what memory-mapped device registers need. It does not make a read-modify-write atomic, does not emit any CPU barrier and does not create happens-before between threads. In C and C++ volatile is the wrong tool for sharing data between threads (Java and C# give the keyword a different, stronger meaning, which causes much confusion).

2.4The contract: sequential consistency for data-race-free programs

Language designers resolved this with one bargain, known as "SC for DRF". If your program has no data races, meaning every shared access is either atomic or ordered by synchronisation, then it behaves as if all operations of all threads were interleaved in one global order consistent with each thread's program order (sequential consistency). The compiler and hardware may still reorder whatever they like, as long as you cannot observe it. If the program has a race, all bets are off.

That moves the job from "understand every reordering of every CPU" to "mark every point where threads communicate". The C++ memory model in the next chapter is the vocabulary for marking those points, with the option of weaker, cheaper orderings when you know exactly what you need.

Why it matters

Most concurrency bugs on embedded targets are not exotic. They are plain data races that the x86 development PC hid because of TSO and a different timing. Running ThreadSanitizer on the host build (Section 10.2) finds most of them before the target ever sees the code.

3The C++ memory model and atomics

Since C++11 the language has its own memory model, so portable code no longer depends on whether it runs on x86 or Arm. You state which accesses communicate between threads and how strongly they must be ordered; the compiler then emits exactly the barriers that the target CPU needs, and nothing more.

3.1Happens-before: the one relation that matters

The model is built from three relations. Sequenced-before is program order within one thread. Synchronizes-with links two threads: a release operation on an atomic synchronizes with an acquire operation on the same atomic that reads the value it wrote (unlocking a mutex synchronizes with the next lock of it in the same way). Happens-before is the combination of the two, chained transitively. The guarantee is simple to state: if a write happens before a read of the same location, the read sees that write or a later one.

struct Frame { int width; const uint8_t* data; };
Frame frame;                                    // plain data
std::atomic<bool> ready{false};                 // the only atomic

void producer(const uint8_t* buffer) {
    frame.width = 1920;
    frame.data  = buffer;
    ready.store(true, std::memory_order_release);   // publish: everything above is visible
}

void consumer() {
    while (!ready.load(std::memory_order_acquire)) { }   // spin (or wait, Section 4.4)
    process(frame.width, frame.data);                    // guaranteed to see both writes
}

Notice that the data itself is not atomic. One atomic flag with release and acquire is enough to publish any amount of ordinary data, as long as the producer does not touch it again after publishing. This "publish with release, consume with acquire" pattern is the backbone of every queue, ring buffer and double-buffer hand-over in a camera pipeline.

3.3Read-modify-write and compare-and-swap

An atomic read-modify-write (RMW) such as fetch_add performs the load, the change and the store as one indivisible step, which is exactly what count++ lacked in Figure 2.2. For a counter that only reports statistics, relaxed is enough:

std::atomic<uint64_t> frames_dropped{0};
frames_dropped.fetch_add(1, std::memory_order_relaxed);   // only the total matters

Anything more complex than add, and, or or exchange is built from compare-and-swap: "if the value is still what I last saw, replace it with my new value; otherwise tell me the current value". You loop until the CAS succeeds. Keeping the maximum observed latency is a typical example:

std::atomic<int64_t> max_latency_us{0};

void record_latency(int64_t v) {
    int64_t cur = max_latency_us.load(std::memory_order_relaxed);
    while (v > cur &&
           !max_latency_us.compare_exchange_weak(cur, v, std::memory_order_relaxed)) {
        // on failure cur was refreshed with the current value: the loop re-checks v > cur
    }
}

compare_exchange_weak may fail even when the value matched. On CPUs that implement CAS with load-linked/store-conditional (Arm without LSE, RISC-V, Power) the conditional store fails whenever anything disturbs the reservation, such as an interrupt. Inside a retry loop that does not matter and the weak form is cheaper; use the strong form when a single attempt must be decisive.

3.4The rest of the atomic toolbox

Fences. std::atomic_thread_fence(order) orders surrounding relaxed operations without being attached to one variable. A release fence followed by a relaxed store behaves like a release store, which is useful when one fence can cover several stores. Fences are harder to reason about than ordered operations; prefer the latter.

Lock-freedom of the type. std::atomic<T> works for any trivially copyable T, but for large types the library silently uses a hidden lock. is_always_lock_free tells you at compile time. Atomics of 1, 2, 4 and 8 bytes are lock-free on all mainstream 64-bit targets; 16-byte atomics need cmpxchg16b on x86 or casp/LSE2 on Arm and are not always available.

Waiting on an atomic (C++20). wait(old) blocks until the value differs from old; notify_one/all wakes waiters. On Linux this maps to the futex system call (Section 4.1), so you get an efficient sleep without a mutex and condition variable:

std::atomic<uint32_t> frame_seq{0};

// consumer
uint32_t seen = frame_seq.load(std::memory_order_acquire);
frame_seq.wait(seen, std::memory_order_acquire);    // sleeps until frame_seq != seen

// producer, after writing the new frame
frame_seq.fetch_add(1, std::memory_order_release);
frame_seq.notify_all();

Shared pointers. Copying a std::shared_ptr from several threads is safe (the reference count is atomic), but assigning to the same shared_ptr object while others read it is a data race. C++20 adds std::atomic<std::shared_ptr<T>>, which is usually implemented with a small internal lock. It is a convenient way to publish an immutable configuration or calibration snapshot that readers grab and keep.

3.5Practical rules

Start with seq_cst (the default) and a lock. Move to acquire/release only for the few hot paths where measurements show a cost, and to relaxed only for values that do not publish anything. Write a comment next to every non-default order explaining which release pairs with which acquire; if you cannot write that sentence, the order is probably wrong. Test weak orders on the Arm target, never only on x86, because x86 hides most ordering mistakes.

Talk track

"The memory model is a contract: if the program is free of data races, it behaves as if threads simply took turns. Atomics with release and acquire are how we mark the hand-over points. A release store publishes everything written before it; the acquire load that reads it sees all of that. Relaxed atomics are only for counters."

4Locks and waiting: mutexes, condition variables, semaphores

Atomics protect one variable. Real invariants span several: a queue's buffer, its size and its head index must change together. A mutex turns a block of code into one indivisible step for everybody who uses the same mutex, and a condition variable lets a thread sleep until another thread has changed the state it needs. Most concurrent code should use these two and nothing cleverer.

4.1What a mutex really is

A mutex gives two guarantees. Mutual exclusion: only one thread at a time is between lock() and unlock(). Ordering: an unlock synchronizes with the next lock, so everything the previous owner wrote is visible to the next one. The second guarantee is why data protected by a mutex needs no atomics.

On Linux a mutex is built on a futex ("fast user-space mutex"), a design from 2002 that made uncontended locking nearly free. The lock word lives in ordinary user memory. Taking a free lock is a single atomic compare-and-swap with no system call. Only when the lock is taken does the thread ask the kernel to sleep on a wait queue keyed by the address of the lock word, and only an unlock that sees waiters asks the kernel to wake one.

The numbers explain the usual advice. An uncontended lock and unlock costs about 15–25 ns, a few cache hits and one atomic operation. A contended lock costs a system call, a sleep and a wake-up, typically 2–10 µs before the waiter runs again, plus the cache line bouncing between cores. So locks are cheap; contention is expensive. The cure for a slow lock is almost never a cleverer lock but a shorter critical section, finer-grained data or less sharing.

Interesting detail

Many mutex implementations spin briefly before sleeping (adaptive mutexes), because if the owner is running on another core it will probably unlock within a microsecond, far less than the cost of sleeping. Pure spinlocks in user space are a different matter: if the owner has been preempted, the spinner burns its entire time slice. In user space use them only for tiny critical sections on threads pinned to dedicated cores; in the kernel and on bare-metal they are normal because interrupts are disabled while held.

4.2Using mutexes well

Never call lock() and unlock() by hand; an early return or an exception leaves the mutex locked forever. The RAII wrappers do it for you. std::lock_guard locks for a scope; std::unique_lock can also unlock early, relock and be handed to a condition variable; std::scoped_lock (C++17) takes several mutexes at once with a built-in deadlock-avoidance algorithm.

class TrackList {
public:
    void update(const Detections& d) {
        std::lock_guard lk(m_);            // unlocked automatically at the end of scope
        merge(tracks_, d);
    }
    std::vector<Track> snapshot() const {
        std::lock_guard lk(m_);
        return tracks_;                    // copy out, then let the caller work unlocked
    }
private:
    mutable std::mutex m_;
    std::vector<Track> tracks_;            // protected by m_
};

Three habits prevent most trouble. Keep the mutex and the data it protects in the same class, so nobody can touch the data without the lock. Never call unknown code (callbacks, virtual functions, logging that may block) while holding a lock, because you cannot know which locks it takes. And keep critical sections short: copy what you need, unlock, then compute.

std::shared_mutex is a reader-writer lock: many readers or one writer. It sounds ideal for "read often, write rarely" data such as calibration, but the reader count itself is a shared cache line that every reader writes, so with short read sections it is often slower than a plain mutex. Publishing an immutable snapshot through an atomic shared pointer, or read-copy-update (Section 5.3), usually scales better.

4.3Condition variables, and the lost wakeup

A mutex protects state; a condition variable lets a thread sleep until that state becomes interesting. The rule that makes it correct is that the condition is always checked and waited for while holding the same mutex that the other side holds when it changes the state. cv.wait(lock, predicate) does the right thing: it checks the predicate, and if it is false it atomically releases the mutex and goes to sleep, then reacquires the mutex and checks again when woken. The loop around the predicate also absorbs spurious wakeups, which POSIX explicitly allows.

A bounded blocking queue, the workhorse between pipeline stages, shows the complete pattern with two condition variables, one for each direction:

template <class T>
class BoundedQueue {
public:
    explicit BoundedQueue(size_t capacity) : cap_(capacity) {}

    bool push(T v) {                              // blocks while full: backpressure
        std::unique_lock lk(m_);
        not_full_.wait(lk, [&] { return q_.size() < cap_ || closed_; });
        if (closed_) return false;
        q_.push_back(std::move(v));
        lk.unlock();                              // wake the consumer after unlocking
        not_empty_.notify_one();
        return true;
    }

    std::optional<T> pop() {                      // blocks while empty
        std::unique_lock lk(m_);
        not_empty_.wait(lk, [&] { return !q_.empty() || closed_; });
        if (q_.empty()) return std::nullopt;      // closed and fully drained
        T v = std::move(q_.front());
        q_.pop_front();
        lk.unlock();
        not_full_.notify_one();
        return v;
    }

    void close() {                                // lets both sides leave their waits
        { std::lock_guard lk(m_); closed_ = true; }
        not_empty_.notify_all();
        not_full_.notify_all();
    }

private:
    std::mutex m_;
    std::condition_variable not_empty_, not_full_;
    std::deque<T> q_;
    const size_t cap_;
    bool closed_ = false;
};

The bug this pattern prevents is the lost wakeup. A condition variable has no memory: a notify with nobody waiting is simply gone. If the consumer checks "is the queue empty?" and only afterwards starts waiting, the producer can push and notify in between, and the consumer then sleeps forever next to a full queue.

// BUG: check and wait are two separate steps
if (queue.empty()) {                        // (1) checked without the mutex
    std::unique_lock lk(m);
    cv.wait(lk);                            // (2) a notify between (1) and (2) is lost
}

// FIX: check the condition under the mutex, in the wait itself
std::unique_lock lk(m);
cv.wait(lk, [&] { return !queue.empty(); });
Pitfall

The producer must change the shared state while holding the mutex, even if that state is an atomic flag. Otherwise the flag can flip after the consumer checked it under the lock but before the consumer went to sleep, and the wakeup is lost again. Whether you call notify inside or after the locked section is only a performance question; notifying after unlocking avoids waking a thread that immediately blocks on the mutex.

4.4Semaphores, latches and barriers

A semaphore is a counter of available permits: acquire() takes one and blocks at zero, release() gives one back. C++20 has std::counting_semaphore and std::binary_semaphore. A counting semaphore models a pool of identical resources naturally, for example "at most four inference requests in flight", and a binary semaphore is a convenient one-shot signal from an interrupt handler or another thread.

A semaphore is not a mutex with a counter of one. A mutex has an owner: only the thread that locked it may unlock it, which lets the system detect errors and, crucially, apply priority inheritance (Section 7.3). A semaphore has no owner; any thread may release it. That is what makes it suitable for signalling and unsuitable for protecting data in real-time code, because the scheduler cannot know whom to boost.

std::latch (C++20) is a single-use countdown: "wait until all six camera threads have finished initialising". std::barrier is reusable: every participant waits at the barrier until all have arrived, then an optional completion function runs and the next phase starts, which suits lock-step algorithms such as processing tiles of one frame in phases.

4.5Deadlock, livelock and starvation

A deadlock needs four conditions at once (Coffman, 1971): resources are held exclusively, a thread holds one resource while waiting for another, nobody can take a resource away, and the waiting forms a cycle. Break any one and deadlock is impossible. In practice you break the cycle.

The story behind Figure 4.3 is typical. The capture code was written by one team and always locks the buffer pool first; the display code, written later by another team, holds its own lock while returning a buffer to the pool. Both orders are reasonable in isolation, the combination hangs perhaps once a week when both threads hit the window of a few microseconds. The remedies, in order of preference:

  1. Don't hold two locks. Copy what you need, release, then take the next lock. Most nested locking can be restructured this way.
  2. A global lock order. Give every mutex a level and only ever lock in increasing level. A debug wrapper can assert the order at run time (a lock hierarchy).
  3. Take them together. std::scoped_lock lk(pool_mtx, disp_mtx); acquires both with a try-and-back-off algorithm, whatever order the arguments come in.
  4. Time out and recover. try_lock_for turns a hang into an error you can log and handle, which is useful as a safety net, not as a design.

Livelock is the polite version of deadlock: threads keep backing off and retrying in step with each other, all busy, none progressing. Randomised back-off fixes it. Starvation means one thread never gets the resource because others always win, for example a writer behind a stream of readers on a reader-preferring lock, or a low-priority thread on a fully loaded real-time core.

5Lock-free structures

Lock-free code coordinates threads with atomics alone. It exists for two reasons: a thread that must never sleep (an interrupt handler, a real-time loop, an audio or control callback) cannot wait for a lock that a preempted thread holds, and at very high rates the cache traffic of a lock becomes the bottleneck. It is also the easiest place in all of software engineering to write code that is wrong in ways no test finds.

5.1Progress guarantees and when they matter

The terms describe what happens if threads are delayed or stopped at the worst moment. Blocking code (any lock) can stall everybody if the lock owner is preempted, crashes or is stuck. Lock-free code guarantees that some thread always makes progress: when a CAS fails, it failed because another thread succeeded. Wait-free code guarantees that every thread finishes its operation in a bounded number of its own steps, which is what hard real-time actually needs. A single-producer single-consumer ring buffer is wait-free; most multi-producer queues are only lock-free.

Lock-free does not mean faster. A contended CAS loop moves the same cache line between cores as a lock does, and retries waste work. The honest reasons to use lock-free structures in an automotive product are bounded latency for a high-priority thread and avoiding priority inversion entirely, not raw throughput. Use a well-tested library (Boost.Lockfree, folly, moodycamel's queues, the SPSC queues of the platform SDK) rather than writing your own, except for the SPSC ring, which is small enough to own.

5.2The bounded SPSC ring buffer

One producer, one consumer, a fixed array and two indices: the producer writes only head, the consumer writes only tail. Because each index has exactly one writer, no CAS is needed at all, only release stores and acquire loads. This is how frames are handed from a capture thread to a processing thread, how a driver hands messages to an application, and how two cores exchange data through shared memory.

template <class T, size_t N>
class SpscRing {
    static_assert(N >= 2 && (N & (N - 1)) == 0, "N must be a power of two");
public:
    bool try_push(const T& v) {                                    // producer thread only
        const size_t h = head_.load(std::memory_order_relaxed);    // our own index
        const size_t t = tail_.load(std::memory_order_acquire);    // consumer is done with slots < t
        if (h - t == N) return false;                              // full: caller decides
        slots_[h & (N - 1)] = v;
        head_.store(h + 1, std::memory_order_release);             // publish the slot
        return true;
    }

    bool try_pop(T& out) {                                         // consumer thread only
        const size_t t = tail_.load(std::memory_order_relaxed);
        const size_t h = head_.load(std::memory_order_acquire);    // makes the slot data visible
        if (h == t) return false;                                  // empty
        out = slots_[t & (N - 1)];
        tail_.store(t + 1, std::memory_order_release);             // give the slot back
        return true;
    }

private:
    alignas(64) std::atomic<size_t> head_{0};                     // written by the producer
    alignas(64) std::atomic<size_t> tail_{0};                     // written by the consumer
    alignas(64) std::array<T, N> slots_{};
};

Every memory order has a reason. The producer's release store of head pairs with the consumer's acquire load of it, so the consumer sees the slot contents. The consumer's release store of tail pairs with the producer's acquire load of it, so the producer never overwrites a slot the consumer is still copying. The indices grow without wrapping logic; unsigned subtraction h - t stays correct even when the 64-bit counters overflow, because N divides 264. The alignas(64) keeps the two indices on different cache lines (Section 5.4).

In practice

For frames, store a buffer index or pointer in the ring, never the pixels; the frames themselves live in a pre-allocated pool (Section 8.3). Production versions also cache the other side's index in a local variable and only reload it when the ring looks full or empty, which removes most cross-core traffic. And decide explicitly what "full" means for your data: for camera frames it usually means "drop", not "retry".

5.3CAS-based structures, ABA and memory reclamation

With several producers or consumers, indices have more than one writer and the structure needs compare-and-swap. The textbook example is a lock-free stack (Treiber stack): to pop, read top, read top->next, then CAS top from the old node to next. It looks obviously correct, and it has a famous bug, the ABA problem.

The stack is A → B → C. T1 starts a pop: it reads old = top = A and next = A->next = B. Before its CAS, T1 is preempted.

T2 pops A and B and frees both, then pushes a new node. The allocator happens to reuse A's memory, so the new top has the same address A. The stack is now A → C, and B no longer exists.

T1 resumes and executes CAS(top, A, B). The top is A, so the CAS succeeds and sets top to B, a freed node. C is lost from the stack, and the next pop reads freed memory. Nothing crashed at the moment of the bug; the crash happens later, somewhere else.

Either make the compared value change on every update (a version counter next to the pointer, compared with a double-width CAS), or make sure memory is not freed and reused while another thread may still hold a pointer to it (hazard pointers, epoch-based reclamation, RCU). Or avoid pointer CAS altogether, as the SPSC ring does.

ABA is a symptom of the real hard problem of lock-free programming: memory reclamation. When can a node removed from a lock-free structure be freed, if another thread might be about to read it? Garbage-collected languages get this for free, which is why lock-free structures are common in Java. In C++ there are three main answers. Hazard pointers: each thread publishes the pointers it is about to dereference, and a node is freed only when no hazard pointer names it. Epoch-based reclamation: threads announce which epoch they are in, and a node retired in epoch e is freed once every thread has moved past e. RCU (read-copy-update), heavily used in the Linux kernel: readers run without any writes at all, writers publish a new version with one pointer swap and free the old one after a grace period in which all readers have finished. C++26 standardises both hazard pointers and RCU in the library.

Why it matters

RCU is the right shape for data that is read on every frame and changed rarely: calibration parameters, a lookup table, the active configuration. Readers never block and never write a shared cache line; the writer builds a complete new version and swaps one pointer. The same idea at small scale is std::atomic<std::shared_ptr<const Config>>.

5.4False sharing

Caches move data in lines of 64 bytes (128 bytes on some Apple and Arm designs). Coherence works per line, not per variable. When two cores write two different variables that happen to sit in the same line, every write invalidates the other core's copy, and the line ping-pongs between them as if they shared a variable. Nothing is shared logically, hence false sharing.

The story is always similar. A team gives each camera thread its own statistics struct to avoid locks, stores the six structs in an array, and finds that the "lock-free" counters made the pipeline slower than the old mutex version. perf c2c on Linux shows the culprit directly: a cache line with heavy "HITM" traffic (hits on a line modified in another core's cache) and the offsets of the two fields being written. The fix is padding or alignment, so that data written by different threads lives on different lines:

struct alignas(64) PerCameraStats {          // one cache line per camera
    std::atomic<uint64_t> frames{0};
    std::atomic<uint64_t> drops{0};
};
std::array<PerCameraStats, 6> stats;          // camera i only writes stats[i]

C++17 offers std::hardware_destructive_interference_size as the portable constant, but its value is fixed at compile time and may not match the target CPU (GCC warns about this with -Winterference-size), so embedded code often hard-codes 64 for the known target. The opposite effect is useful too: data that one thread uses together should sit together, ideally in one line (hardware_constructive_interference_size).

The data-layout side of false sharing and cache-friendly structures: C++ 12, False sharing and cache lines and locality.

6Organising the work: threads, pools, futures, event loops and coroutines

Once the synchronisation primitives are clear, the bigger design question is how to map work onto threads. One thread per job is simple but does not scale; a pool of workers fed with tasks scales but hides ordering; an event loop serves thousands of sources on one thread but must never block. Each model has a natural home in an automotive system.

6.1Threads with a clean life cycle: std::jthread

A std::thread that is still joinable when it is destroyed calls std::terminate, which turns every forgotten join() on an error path into a crash. C++20's std::jthread fixes both halves of the problem: its destructor requests a stop and then joins, and the thread function can receive a std::stop_token to notice the request.

std::jthread capture([&cam](std::stop_token st) {
    while (!st.stop_requested()) {
        auto frame = cam.wait_frame(std::chrono::milliseconds(100));   // bounded wait
        if (frame) pipeline.submit(std::move(*frame));
    }
});
// leaving the scope: capture.request_stop(), then capture.join()

The stop request is cooperative: the thread has to look. That is why every blocking wait in a stoppable thread should either have a timeout or be interruptible. std::condition_variable_any::wait has an overload that takes the stop token and wakes up when a stop is requested, which the thread pool below uses.

Pitfall

Shutting down cleanly is where many pipelines hang: a consumer waits on an empty queue forever because nobody told it the producer is gone. Give every queue a close() (Section 4.3), stop producers first, then close the queues, then join the consumers, and test shutdown as seriously as start-up. Diagnostic sessions, suspend-to-RAM and software updates all restart the pipeline in the field.

6.2Thread pools

A thread pool keeps a fixed number of worker threads alive and feeds them small tasks through a queue. Creating a thread per task would cost tens of microseconds and an unbounded number of threads; a pool pays that once and caps concurrency at the number of cores you choose to give it.

class ThreadPool {
public:
    explicit ThreadPool(unsigned n) {
        for (unsigned i = 0; i < n; ++i)
            workers_.emplace_back([this](std::stop_token st) { run(st); });
    }
    ~ThreadPool() {
        for (auto& w : workers_) w.request_stop();   // workers drain the queue, then exit
    }                                               // members destroyed: jthreads join first

    template <class F>
    auto submit(F f) -> std::future<std::invoke_result_t<F>> {
        using R = std::invoke_result_t<F>;
        auto task = std::make_shared<std::packaged_task<R()>>(std::move(f));
        auto result = task->get_future();
        {
            std::lock_guard lk(m_);
            q_.emplace_back([task] { (*task)(); });
        }
        cv_.notify_one();
        return result;
    }

private:
    void run(std::stop_token st) {
        for (;;) {
            std::function<void()> job;
            {
                std::unique_lock lk(m_);
                cv_.wait(lk, st, [&] { return !q_.empty(); });   // also wakes on stop
                if (q_.empty()) return;                          // stop requested, nothing left
                job = std::move(q_.front());
                q_.pop_front();
            }
            job();                                               // run outside the lock
        }
    }

    std::mutex m_;
    std::condition_variable_any cv_;               // _any: can wait with a stop_token
    std::deque<std::function<void()>> q_;
    std::vector<std::jthread> workers_;            // declared last, so destroyed first
};

// usage: post-process five camera outputs in parallel
std::vector<std::future<Objects>> parts;
for (auto& out : npu_outputs) parts.push_back(pool.submit([&out] { return decode_and_nms(out); }));
for (auto& p : parts) merge(p.get());              // get() rethrows a task's exception

The packaged task wraps the callable together with a promise, so the caller receives a future for the result and exceptions travel back to whoever calls get(). The job is executed outside the lock; holding the queue lock while running a task would serialise the whole pool.

Sizing. For CPU-bound tasks use about as many workers as cores you give the pool, not more; extra threads only add switches. Tasks that block on I/O justify more threads, but in a real-time system the better answer is to keep blocking work out of the compute pool entirely. Granularity. Each task costs queue operations and a possible wake-up, about 1–5 µs in a mutex-based pool. Tasks of 50 µs and up amortise that easily; tasks of 1 µs are dominated by overhead, so split work into chunks (for example one tile row per task, not one pixel).

Work stealing, used by Intel oneTBB, Taskflow, folly and most parallel runtimes, also keeps recently created subtasks on the core that created them, where their data is still in the cache. It is the right model for recursive or irregular parallelism (splitting an image into regions that split further). For a fixed perception pipeline with predictable stages, a few dedicated threads plus bounded queues (Chapter 8) are easier to reason about and to analyse for timing.

6.3Futures, promises and executors

A future is a handle to a result that will exist later; the matching promise is the write end. std::async combines starting a task and getting its future in one call:

auto detections = std::async(std::launch::async, [&] { return detect(frame); });
auto lanes      = find_lanes(frame);            // runs meanwhile on this thread
fuse(detections.get(), lanes);                  // waits only if detect() is still running

Standard futures have well-known limits. get() blocks, and there is no way to say "when this is ready, run that" (no continuations), so chains of asynchronous steps end up blocking threads. Without an explicit launch policy, std::async may defer the task until get() and run it synchronously. And the future returned by std::async is special: its destructor waits for the task, so std::async(std::launch::async, log_stats); with the result discarded runs synchronously after all.

The standard's answer is std::execution (senders and receivers, adopted for C++26): a sender describes asynchronous work, algorithms such as then, when_all and let_value compose senders, and a scheduler decides where each piece runs (a thread pool, an event loop, a GPU stream). It brings structured concurrency, meaning every started operation has an owner that waits for its completion or cancellation, with no fire-and-forget. Until compilers and platforms ship it, libraries such as stdexec, libunifex, Asio and folly fill the same role.

6.4Event loops

An event loop serves many sources with one thread. The thread registers file descriptors (sockets, a CAN socket, timers, an eventfd that other threads write to) with the kernel, then repeatedly asks "which of these are ready?" and runs a short handler for each. On Linux the readiness mechanism is epoll; on QNX it is pulses and channels; Windows uses I/O completion ports.

Event loops are why a single process can handle SOME/IP service discovery, diagnostics over DoIP, a few dozen timers and a CAN interface without a thread per source and without locking. The one rule is absolute: a handler must not block. A 50 ms file write or a long computation in a handler delays every other event by 50 ms; such work is posted to a thread pool and its result comes back as another event (through an eventfd or a posted task). Linux's newer io_uring interface goes one step further from readiness to completion: the application queues complete I/O operations in a shared ring and collects their results later, the proactor pattern, with fewer system calls.

The kernel side of epoll and of interrupts: Linux 7.3 and Linux 6.

6.5Coroutines in use

Callback-based event-loop code fragments a simple sequence ("read a request, query the tracker, send a reply") into separate handlers with state passed by hand. C++20 coroutines let you write the sequence as one function that suspends at each co_await and is resumed by the event loop when the operation completes. Nothing blocks a thread: while the coroutine is suspended, the loop runs other work.

// Asio: one coroutine per client connection, all on the same event-loop thread
asio::awaitable<void> serve(asio::ip::tcp::socket s) {
    std::array<char, 4096> buf;
    for (;;) {
        std::size_t n = co_await s.async_read_some(asio::buffer(buf), asio::use_awaitable);
        auto reply = handle_request(std::span(buf.data(), n));        // short, non-blocking
        co_await asio::async_write(s, asio::buffer(reply), asio::use_awaitable);
    }
}

C++ coroutines are stackless: only the coroutine's own frame is saved (normally on the heap), not a whole stack, so a suspended coroutine costs a few hundred bytes and you can have thousands. The flip side is that only the coroutine itself can suspend, not functions it calls normally. Coroutines are a structuring tool for asynchronous I/O and pipelines; they add no parallelism by themselves, and running coroutine handlers on several threads brings back all the synchronisation questions of this chapter.

7Real-time threads from the application's side

"Real-time" does not mean fast; it means that a result is useful only if it arrives before a deadline, and that the system can show it will. For an application developer on Linux or QNX this comes down to a handful of decisions per thread: which scheduling policy and priority, which cores, what the thread is allowed to do inside its loop, and which locks it may share with whom.

7.1Priorities and scheduling policies

POSIX systems offer two families. The normal, time-sharing policy (SCHED_OTHER, on Linux the CFS/EEVDF scheduler) shares the CPU fairly according to nice values; a thread can be delayed by any number of others. The real-time policies SCHED_FIFO and SCHED_RR use fixed priorities (1–99 on Linux): the highest-priority runnable thread always runs, preempting everything below it, and a FIFO thread keeps the CPU until it blocks or yields. RR adds a time slice among threads of equal priority. Linux also has SCHED_DEADLINE, where a thread declares runtime, deadline and period and the kernel schedules by earliest deadline with admission control. QNX, the other common automotive OS, schedules by fixed priority throughout and offers FIFO, round-robin and sporadic scheduling per thread.

Fixed priorities are assigned by importance and rate, not by how much the developer cares. The classic rule is rate-monotonic: the shorter a task's period, the higher its priority, which is optimal among fixed-priority assignments for independent periodic tasks. A tracker that must run every 33 ms gets a higher priority than a 1 Hz diagnostics task, even though diagnostics may feel more "important".

Pitfall

A SCHED_FIFO thread in an endless loop starves everything below it on that core, including kernel threads. Linux protects itself with RT throttling: by default real-time threads may use at most 950 ms of every second (sched_rt_runtime_us), so a runaway thread shows up as an unexplained 50 ms gap in its timing rather than a frozen system. If you see periodic 50 ms stalls in an RT thread, look for a busy loop first.

How the scheduler decides, what real-time means formally, and schedulability analysis: Embedded compute 6.3–6.4 and 7.3. Kernel internals and PREEMPT_RT: Linux 9.

7.2CPU affinity and isolation

By default the scheduler may move a thread to any core. That balances load but costs a cold cache after each migration and makes timing depend on what else runs. CPU affinity pins a thread to a set of cores (pthread_setaffinity_np, taskset, cgroup cpusets); on QNX the equivalent is the runmask. For the most demanding threads the core is also isolated: the kernel is told not to schedule anything else there (isolcpus or cpuset partitions, nohz_full to stop the periodic tick) and device interrupts are steered to other cores through /proc/irq/*/smp_affinity.

Affinity is a tool for predictability, not for throughput. Pinning every thread by hand usually makes average performance worse, because the scheduler can no longer fill idle cores. A sensible split is a few dedicated cores for the threads with hard timing (the tracker, the control loop, the capture threads), and the rest left to the scheduler for best-effort work. Keep producer and consumer of a heavy data stream on cores that share a cache cluster where possible; on big.LITTLE SoCs make sure the real-time threads are not left on the small cores.

7.3Priority inversion

Priority inversion happens when a high-priority thread waits for a lock held by a low-priority thread, and a medium-priority thread, which needs no lock at all, preempts the low one. The high-priority thread is now effectively running at low priority, for as long as the medium thread keeps the CPU, with no bound.

The famous story is NASA's Mars Pathfinder in 1997. On Mars the lander began resetting itself every few days. A low-priority meteorological task held a mutex protecting the information bus; the high-priority bus management task blocked on it; medium-priority communication tasks ran in between; a watchdog noticed that the bus task had not completed its cycle and reset the computer. The engineers reproduced it on a ground replica with VxWorks tracing switched on, and fixed it from Earth by enabling priority inheritance on that mutex, which had been turned off.

The fixes are protocol-level. With priority inheritance the lock owner inherits the highest priority of any thread waiting for the lock, for as long as it holds it. With the priority ceiling protocol a lock has a fixed ceiling, the priority of its highest user, and whoever takes it immediately runs at that ceiling; this also prevents some deadlocks and is the AUTOSAR OS resource model. On POSIX systems both are mutex attributes; std::mutex does not expose them, so real-time code creates its mutexes through the native API or a small wrapper:

pthread_mutexattr_t attr;
pthread_mutexattr_init(&attr);
pthread_mutexattr_setprotocol(&attr, PTHREAD_PRIO_INHERIT);   // or PTHREAD_PRIO_PROTECT + ceiling
pthread_mutex_init(&tracks_mtx, &attr);
pthread_mutexattr_destroy(&attr);

Priority inheritance only works for locks with an owner. Semaphores, condition variables used as signals, and spin flags have no owner the system could boost, which is one more reason to keep a real-time thread's synchronisation to owned mutexes with short sections, or to lock-free hand-over such as an SPSC ring. QNX enables priority inheritance on its mutexes by default; Linux requires the attribute, which uses PI futexes in the kernel.

7.4Rules for the inside of a real-time loop

A real-time thread is only as predictable as the worst thing it does in its loop. Anything whose duration is unbounded or depends on other threads breaks the timing: allocating memory (the allocator takes a lock and may call the kernel), a page fault on first touch of memory, blocking I/O, logging that writes to a file, a lock shared with low-priority code, an exception being thrown. The standard recipe follows from that list.

  1. Prepare before the loop. Allocate and touch all buffers at start-up; lock the process memory with mlockall(MCL_CURRENT | MCL_FUTURE) so no page is ever swapped or faulted in later; pre-fault the stack.
  2. Wake on absolute time. Sleep until the next period with an absolute deadline, so jitter in one cycle does not accumulate into drift.
  3. Bound every operation. No allocation, no unbounded loops, no system calls with unbounded duration, no locks shared with non-real-time threads. Hand data to and from other threads through lock-free rings or PI mutexes with tiny sections.
  4. Log asynchronously. Write log records into a lock-free ring; a low-priority thread formats and stores them.
  5. Measure and supervise. Record the start time, duration and lateness of every cycle; a watchdog or the safety monitor checks the alive counter.
void tracker_loop() {
    sched_param sp{};
    sp.sched_priority = 80;
    pthread_setschedparam(pthread_self(), SCHED_FIFO, &sp);         // needs CAP_SYS_NICE or rtprio limit
    cpu_set_t cpus;
    CPU_ZERO(&cpus);
    CPU_SET(4, &cpus);
    pthread_setaffinity_np(pthread_self(), sizeof(cpus), &cpus);

    timespec next{};
    clock_gettime(CLOCK_MONOTONIC, &next);
    for (;;) {
        next.tv_nsec += 33'333'333;                                   // 30 Hz period
        if (next.tv_nsec >= 1'000'000'000) { next.tv_nsec -= 1'000'000'000; ++next.tv_sec; }
        clock_nanosleep(CLOCK_MONOTONIC, TIMER_ABSTIME, &next, nullptr);   // absolute: no drift
        step();                     // bounded: pre-allocated memory, no blocking, no file I/O
    }
}
Interesting detail

Normal Linux threads have a default timer slack of 50 µs: the kernel may wake them up to 50 µs late so it can batch timer interrupts and save power. Real-time threads get zero slack. A periodic loop that is mysteriously 50 µs late on every cycle is often a normal-priority thread that someone assumed was real-time.

7.5Measuring timing

Averages hide real-time failures; what matters is the distribution and its tail. Record per-cycle lateness and duration in the thread itself (cheaply, into a ring) and look at the 99.9th percentile and the maximum over hours of runtime under realistic load, including the logger, the network and the GPU busy at the same time. System-wide tracers show why a cycle was late: Linux ftrace/trace-cmd, perf sched, LTTng and Perfetto record every context switch and wake-up; QNX has the System Profiler. A trace that shows the high-priority thread runnable but not running, and who was running instead, finds priority problems in minutes.

Talk track

"Our real-time threads never allocate, never block on a lock shared with best-effort code and never do file I/O in the loop. They wake on absolute time, run on an isolated core with SCHED_FIFO, and we track the worst-case lateness in every long-run test, not the average."

8Pipelines: producer-consumer, queues and backpressure

A perception system is a stream processor. Frames arrive at a fixed rate whether or not the software is ready, every frame passes through the same sequence of steps, and the result is only useful if it is fresh. The design questions are how to cut the work into stages, how big the queues between stages are, and what happens when a stage is too slow.

8.1Stages, throughput and latency

Splitting the work into stages that run in parallel, each on its own thread or engine, is pipelining: while stage 2 works on frame n, stage 1 already works on frame n+1. Two numbers describe the result and they behave differently. Throughput (frames per second) is limited by the slowest stage. Latency (time from frame capture to result) is at least the sum of all stages plus all the time a frame spends waiting in queues.

That asymmetry is the core lesson. Pipelining and batching raise throughput; they never reduce the latency of one frame, and queues only add to it. A stage that takes longer than the frame period cannot be fixed by queueing: either it gets faster, or it is split further, or it runs on more workers in parallel (two inference contexts handling alternate frames), or frames are dropped.

Little's law connects the quantities for any stable system: the average number of items inside equals the arrival rate times the average time each spends inside, \(L = \lambda W\). At 30 fps with 100 ms end-to-end latency, three frames are in flight on average; if your buffer pool holds fewer than that plus the queue capacities, the pipeline will stall on buffers, not on compute.

8.2Bounded queues and backpressure

Every queue between stages must be bounded. An unbounded queue in front of a stage that is even slightly too slow grows without limit: latency rises minute by minute until memory runs out, and in the meantime the system acts on ever older data. A bounded queue forces a decision when it is full. That decision is called backpressure when the slow consumer pushes back on the producer, and load shedding when data is dropped.

The camera delivers 30 fps; the consumer needs the time you set per frame and has a queue of the chosen depth in front of it (not counting the frame it is working on). Look at the latency when the consumer is slower than the camera: with "drop newest" a deeper queue only makes every processed frame older, while "drop oldest" keeps the frames fresher at the same throughput.

The general lesson: when a consumer can be slower than its producer, queue depth buys tolerance for short bursts, not throughput, and the price is latency. Live pipelines therefore keep queues short (one to three frames), drop the oldest data, and count every drop as a monitored metric.

Pitfall

Dropping silently is as dangerous as never dropping. A perception stack that quietly processes 20 of 30 frames per second may still pass functional tests while its tracker, which assumes a constant 33 ms between updates, predicts badly. Every drop should be counted, timestamped and visible to whoever consumes the output, and downstream stages should use the frame timestamps, never the arrival rate.

8.3A multi-camera perception pipeline

Put together, a camera ECU running perception on five cameras looks like Figure 8.3. Each stage runs on the engine that suits it, every hand-over is a bounded queue with an explicit policy, and the frames themselves never move: they sit in a pre-allocated pool of DMA-able buffers and only references (buffer indices or dma-buf file descriptors) travel through the queues.

Walking one frame set through it shows where each concept of this chapter appears. The capture stage is driven by interrupts: the CSI-2 receiver writes the frame by DMA into a buffer from the pool and the driver timestamps it at the start of exposure, which is the time that matters for fusion. One short capture thread per camera dequeues the buffer and hands it on; if the downstream ring is full it returns the oldest buffer to the driver, so the camera never stalls. The ISP is a hardware engine that many SoCs time-share between cameras; its driver queues requests and signals completion. Pre-processing (undistortion, resize, colour conversion into the network's input tensor) runs on the GPU or a vision accelerator, submitted asynchronously with a fence on completion.

The sync and batch stage is where the five streams meet. It collects frames whose timestamps fall within a small window of each other into one frame set, waits for a missing camera only until a deadline and then proceeds without it, and hands the batch to the NPU, which runs one network for all five images at once because batching uses the accelerator better. Its queue holds only the latest set: if inference is still busy with the previous batch, a newer batch replaces the waiting one. Post-processing (decoding network outputs, non-maximum suppression) is data-parallel per camera and runs on a small thread pool. Finally a single tracker/fusion thread with a real-time priority on an isolated core consumes the detections strictly in timestamp order, updates the tracks and publishes the object list.

Numbers

At 30 fps the frame period is 33.3 ms. A typical split: capture and ISP 5–10 ms, pre-processing 3–6 ms, inference 15–25 ms for a batch, post-processing 3–6 ms, tracking 1–3 ms. Stage times sum to roughly 30–50 ms, and with one or two frames of queueing the end-to-end latency from exposure to object list lands around 50–100 ms. Each stage must fit within 33 ms at its worst case, not its average, or drops start.

Two design rules make such a pipeline debuggable. First, every frame carries its capture timestamp and a sequence number through every stage, and every stage records when it started and finished each frame; latency, drops and stalls are then visible per stage instead of guessed. Second, ownership of each buffer is always clear (pool, capture, ISP, GPU, NPU, back to pool), ideally enforced by the type system, for example a move-only handle that returns the buffer to the pool in its destructor.

The buffer life cycle, dma-buf, fences and buffer counts on the display side: Camera, ISP, GPU and display 9.4 and GPU programming 6.5. Timestamping across cameras and other sensors is part of the sensor fusion chapter (planned).

8.4Latency versus throughput as a design choice

Most performance tricks trade one for the other. Batching five cameras into one inference call raises NPU utilisation but makes the first camera wait for the last. Deeper pipelines with more stages raise the frame rate a system can sustain but add a hand-over to every frame. Larger queues absorb bursts but age the data. For offline workloads (training data processing, replaying recordings) throughput is the goal and all of these are good. For a function that steers, brakes or warns the driver, latency and its worst case are the goal, and every queue and batch must justify itself.

A useful habit is to write the latency budget down as a table, stage by stage, with worst-case times and queue waits, and to compare it with the requirement of the function (for example a 150 ms reaction budget for an emergency-braking chain, of which perception gets a part). It turns "the system feels laggy" into a concrete list of where the milliseconds go.

Talk track

"Throughput is set by our slowest stage, latency by the sum of all stages plus queueing. We keep queues one or two frames deep and drop the oldest data, because for perception a fresh answer beats a complete one. Every frame carries its exposure timestamp, so fusion never mistakes processing time for scene time."

9CPU, GPU and NPU: heterogeneous parallelism

A vision SoC has a few CPU cores and several engines that are each far more parallel than all of them together. Using it well is a scheduling problem: every engine should have work queued when it finishes the previous job, data should flow from engine to engine without the CPU copying or waiting, and the one thing that must never happen is a CPU thread sitting idle in glFinish() while three accelerators also wait.

9.1Kinds of parallelism

The CPU is latency-oriented: a few cores, each with deep out-of-order pipelines, branch predictors and large caches, built to finish one instruction stream as fast as possible. It handles control flow, irregular work and anything with little data parallelism. Inside each core, SIMD units (NEON on Arm) process 16 bytes at once, which is data parallelism on a small scale. The GPU is throughput-oriented: thousands of simple lanes grouped into warps or wavefronts (32 threads on NVIDIA) that execute the same instruction on different data, hiding memory latency by switching between many warps instead of caching. It suits pixel-parallel work: remapping, colour conversion, rendering. The NPU is more specialised still, a fixed dataflow array for matrix multiplications and convolutions with its own local memory, and DSPs and vision accelerators sit in between.

The categories map onto the concurrency vocabulary. CPU threads give task parallelism (different code on different cores). SIMD, GPU and NPU give data parallelism (the same operation on many elements). The pipeline of Chapter 8 gives pipeline parallelism (different stages on different frames). A well-used SoC exploits all three at once.

How each engine is built and which job suits which engine: Embedded compute 8.1–8.5; SIMD and NEON in Chapter 10 of that chapter.

9.2Accelerators are asynchronous by nature

Every accelerator API has the same shape. The CPU records commands into a buffer and submits it to a queue (an OpenGL ES context, a Vulkan queue, a CUDA stream, an OpenCL command queue, an NPU runtime's inference request); the call returns immediately; the engine executes later; completion is reported through a fence, event or semaphore. Within one queue commands execute in order, so dependent work on the same engine needs no extra synchronisation. Between queues and engines, fences express the dependencies: "the NPU job may start when the GPU's pre-processing fence has signalled".

The decisive point is who waits. If the CPU waits on each fence before submitting the next job, the engines run strictly one after another and the CPU thread is blocked most of the time. If the dependency is handed to the engines (a GPU-side wait on a sync object, a Vulkan semaphore between queues, a CUDA event recorded in one stream and waited on in another, a dma-fence attached to a dma-buf), the CPU only submits and moves on, and the engines start each job the moment its input is ready.

Fences, EGL sync objects and why glFinish() is the wrong fix: Camera, ISP, GPU and display 9.2–9.3 and GPU programming 6.3–6.4.

9.3Overlapping frames across engines

Put the asynchronous engines into the pipeline of Chapter 8 and each frame flows through ISP, GPU, NPU and CPU like an item on an assembly line. At any moment several frames are in flight, each on a different engine.

For this to work, every hand-over needs enough buffers: while the NPU reads frame n's tensor, the GPU writes frame n+1's tensor into a different buffer. That is double or triple buffering per edge of the pipeline, and it is why buffer pools are sized by the number of frames in flight (Little's law again). It also explains the classic overlap of data transfer and compute: with two buffers, the DMA engine copies the next input while the accelerator works on the current one.

9.4Scheduling shared engines

Engines are shared resources, and their scheduling is far cruder than a CPU's. Many GPUs and NPUs can only switch between jobs at the boundary of a draw call, a kernel or a layer, so a long low-priority job delays an urgent one by its full duration. When the surround-view rendering for the driver display and a perception network share one GPU, the display can stutter because a perception kernel holds the GPU for 15 ms. The countermeasures are splitting long jobs into shorter ones, using hardware queue priorities where the platform offers them, partitioning the engine (separate NPU cores per function, GPU partitioning on some automotive SoCs), and above all budgeting engine time per function the way CPU time is budgeted.

Memory bandwidth is the other shared resource, and the one that runs out first. The CPU, GPU, NPU, ISP and display all read and write the same DRAM. A memory-hungry job on one engine slows every other engine, which shows up as a "random" increase of NPU inference time whenever the GPU renders a 3D view. Measuring each stage alone is therefore not enough; worst-case timing has to be measured with all engines loaded at once.

Why it matters

Mixed criticality makes this a safety topic, not only a performance one. If a safety-relevant function and a QM function share a GPU, the safety argument must show that the QM work cannot delay the safety work beyond its budget, which is freedom from interference in the time domain. Accelerator preemption granularity and bandwidth regulation become requirements in the SoC selection.

10.2Tools that find races and deadlocks

ThreadSanitizer (-fsanitize=thread in GCC and Clang) instruments every memory access and synchronisation operation and reports two threads touching the same location without happens-before, with both stack traces. It finds races on any code path the test executes, even when they did not cause a failure in that run, which is why it beats stress testing for this class of bug. It also reports lock-order inversions ("potential deadlock") from the order in which locks were taken, again without needing the deadlock to happen. The cost is 5–15× slower execution and several times the memory, so it runs on host builds and in CI, not on the target. Valgrind's Helgrind and DRD are slower alternatives that need no recompilation.

Static checks. Clang's thread-safety analysis (-Wthread-safety) checks at compile time that data annotated GUARDED_BY(mu) is only accessed with mu held and that functions annotated REQUIRES or EXCLUDES are called correctly. It costs nothing at run time and turns locking conventions from comments into compiler errors. Commercial static analysers (Coverity, Polyspace, CodeSonar and others) add race and deadlock checks of varying depth across the whole code base.

Model checkers such as CDSChecker or Relacy explore all interleavings and all weak-memory behaviours of a small piece of code. They are the only practical way to gain confidence in a hand-written lock-free algorithm, because no test run explores the rare reorderings systematically.

Performance tools. perf c2c finds false sharing and contended lines; perf lock, mutex profiling in tracers and off-CPU flame graphs show where threads wait instead of work; system tracers (Section 7.5) show who preempted whom.

10.3When it hangs or corrupts anyway

For a hang, take a snapshot of every thread's stack before restarting anything: gdb -p <pid> and thread apply all bt, or a core dump with gcore; on QNX, pidin shows each thread's state and the object it is blocked on. Two threads each blocked in a mutex lock with the other's lock in their call stack is a deadlock; a thread blocked in a condition variable wait while its queue has data is a lost wakeup; all threads runnable but no progress suggests livelock or a busy loop. Record which mutex each thread waits for and who owns it (glibc stores the owner's thread id in the mutex, visible in the debugger); the wait-for graph of Figure 4.3 then draws itself.

For corruption, the questions are which data was wrong and which threads can write it. If the answer to the second question is "more than one" and there is no lock, you have probably found it. Reproduction improves dramatically with artificial pressure: run more threads than cores, add random short sleeps or yields at synchronisation points in a test build, pin producer and consumer on different cores (and then on the same core), run on the slowest and the fastest target variant, and keep the long-run test going for hours with the system under full load.

10.4Design rules that prevent most of it

The best concurrency bug is the one the design makes impossible. Share as little mutable data as possible: hand data over through queues so that at any moment exactly one thread owns it, and treat shared configuration as immutable snapshots. Keep each mutex together with the data it protects in one class, keep critical sections short and free of calls into unknown code, and define one lock order for the cases where nesting is unavoidable. Use the standard library and proven libraries for queues, pools and lock-free structures rather than inventing them. Bound every queue, give every blocking wait a way out (timeout, close, stop token), and give every thread an owner who stops and joins it. Annotate the locking for the compiler, run ThreadSanitizer in CI, and test on the target under load.

Talk track

"Most concurrency problems we have seen were plain data races or lock-order cycles, not exotic memory-model issues. So our rules are boring on purpose: ownership is handed over through bounded queues, locks live inside the class that owns the data, the compiler checks the lock annotations, ThreadSanitizer runs in CI, and the target runs long tests at full load."

11.3One sentence each

Concurrency vs parallelism

Concurrency is overlapping lifetimes (structure); parallelism is simultaneous execution (hardware).

Process vs thread

Processes have separate address spaces and fail independently; threads share memory and fail together.

Reordering

Store buffers, out-of-order loads and the compiler reorder memory accesses; only other threads can tell.

Data race

Unsynchronised conflicting access, undefined behaviour in C and C++, not just a random value.

Happens-before

Program order plus release→acquire synchronisation, chained; it decides what a read may see.

Memory orders

Relaxed for counters, release/acquire for hand-over, seq_cst when global order matters.

Mutex

Mutual exclusion plus ordering; cheap uncontended thanks to futexes, expensive under contention.

Condition variable

Always wait with a predicate under the same mutex the writer holds, or a wakeup gets lost.

Semaphore

A counter of permits without an owner: good for signalling and pools, no priority inheritance.

Deadlock

A cycle of threads each holding a lock the next one needs; prevent it with one lock order.

Lock-free

Some thread always progresses; chosen for bounded latency, not raw speed; reclamation is the hard part.

ABA

CAS sees the same value and assumes nothing changed; fix with tags or safe reclamation.

False sharing

Independent variables in one cache line make cores fight over it; align hot per-thread data to 64 B.

Thread pool

Fixed workers fed with tasks; size to the cores, keep tasks well above the scheduling overhead.

Event loop

One thread multiplexes many sources with epoll; handlers must never block.

Priority inversion

A medium thread delays a high one through a lock held by a low one; fix with inheritance or ceilings.

Backpressure

Bounded queues force a choice when full: block, drop newest, drop oldest or keep only the latest.

Heterogeneous

Submit asynchronously, chain engines with fences, double-buffer every hand-over, budget shared engines and bandwidth.

QSelf-check questions

Core questions with short model answers; the chapter sections hold the depth. The second group checks understanding with "why" and "what if" questions rather than definitions.

Q.1Core questions

What is the difference between concurrency and parallelism?Basic

Concurrency means several tasks are in progress at overlapping times; it is a property of the program's structure and works even on one core by interleaving. Parallelism means operations really execute at the same instant on several cores, SIMD lanes or engines. Concurrency gives responsiveness and overlaps waiting; parallelism gives throughput when there is independent work.

Process or thread: when do you use which?Basic

Threads share an address space, so communication is cheap but any thread can corrupt the others and they fail together. Processes are isolated by the MMU, communicate through IPC and can crash and restart independently. Use threads for tightly coupled work inside one component, processes for isolation between components, suppliers or safety levels.

What is a data race and why is it undefined behaviour in C++?Basic

Two threads access the same location, at least one writes, at least one access is not atomic, and no happens-before orders them. The language makes it undefined so the compiler may optimise as if no other thread existed: keeping values in registers, hoisting loads out of loops, splitting or merging stores. A racy spin loop on a plain bool can legally become an infinite loop.

Explain memory_order_acquire and memory_order_release.Intermediate

A release store keeps all earlier reads and writes of the thread before it; an acquire load keeps all later ones after it. When an acquire load reads the value written by a release store, the two synchronize: everything the writer did before the store is visible to the reader after the load. It is the pattern for publishing data through a flag or an index, and on x86 it costs nothing extra while on Arm it maps to stlr/ldar.

Why can't you use volatile for thread synchronisation in C++?Basic

volatile only forces the compiler to perform each access; it does not make read-modify-write atomic, does not emit CPU barriers and does not create happens-before. It is meant for memory-mapped hardware registers. Use std::atomic or a mutex.

How does a mutex work under the hood on Linux?Intermediate

It is a word in user memory manipulated with atomic operations. Locking a free mutex is one compare-and-swap, no system call. If it is taken, the thread marks it as contended and calls futex_wait, sleeping on a kernel wait queue keyed by the word's address. Unlock exchanges the word back to free and calls futex_wake only if there were waiters. So the uncontended path costs about 20 ns and only contention costs microseconds.

Why must a condition variable wait use a predicate, and what is a spurious wakeup?Intermediate

The predicate is the actual condition; the condition variable is only a sleeping mechanism with no memory. Checking the predicate under the mutex before sleeping prevents lost wakeups (the notify came before the wait), and re-checking after waking handles spurious wakeups, which POSIX allows, and the case where another consumer took the item first. cv.wait(lock, pred) does both.

What are the conditions for deadlock and how do you prevent it?Basic

Mutual exclusion, hold and wait, no preemption, and circular wait, all four at once. In practice you break circular wait: avoid holding two locks, define a global lock order, or acquire several locks at once with std::scoped_lock. Timeouts turn a hang into a reportable error but are a safety net, not a design.

Mutex versus semaphore?Basic

A mutex has an owner: only the locking thread unlocks it, which allows error checking and priority inheritance. A semaphore is a counter of permits with no owner; any thread can release it, so it suits signalling and resource pools. For protecting shared data, especially in real-time code, use a mutex.

What is priority inversion and how is it fixed?Intermediate

A high-priority thread blocks on a lock held by a low-priority thread, and a medium-priority thread preempts the low one, so the high one waits for an unbounded time. Mars Pathfinder's resets in 1997 are the classic case. Fixes: priority inheritance (the owner temporarily gets the waiter's priority) or priority ceiling (taking the lock raises the owner to a fixed ceiling, the AUTOSAR OS model), plus keeping critical sections short and not sharing locks between real-time and best-effort code.

How would you implement a single-producer single-consumer queue without locks?Advanced

A power-of-two ring buffer with two monotonically increasing indices. Only the producer writes head, only the consumer writes tail. The producer checks for space with an acquire load of tail, writes the slot, then stores head + 1 with release; the consumer acquires head, reads the slot, releases tail + 1. Put the indices on separate cache lines and store buffer handles, not frames, in the slots. It is wait-free and needs no CAS.

What is the ABA problem?Advanced

A CAS-based algorithm reads value A, gets delayed, and meanwhile the value changes to B and back to A (often because a node was freed and its memory reused). The CAS succeeds because it only compares bits, and the algorithm corrupts the structure. Fixes are a version tag next to the pointer with a double-width CAS, or safe memory reclamation (hazard pointers, epochs, RCU) so a node cannot be reused while someone may still hold it.

What is false sharing and how do you detect it?Intermediate

Two threads write different variables that sit in the same cache line, so the line bounces between their caches on every write although nothing is logically shared. It shows up as code that gets slower with more threads. perf c2c reports the contended lines and the offsets written; the fix is aligning or padding per-thread data to 64 bytes.

How do you size a thread pool?Intermediate

For CPU-bound tasks about one worker per core assigned to the pool; more only adds switching. Blocking tasks justify more threads, but it is better to keep blocking work out of a compute pool. Also size the tasks: overhead per task is microseconds, so each task should do tens of microseconds of work or more.

Latency versus throughput in a camera pipeline?Intermediate

Throughput is set by the slowest stage; latency is the sum of all stages plus queue waits. Pipelining and batching raise throughput but never lower the latency of one frame. For perception, keep queues short, drop old frames rather than queue them, and budget the worst-case latency per stage against the function's reaction-time requirement.

How would you split a six-camera perception system into threads?Advanced

As a pipeline of stages, each on the engine that suits it: interrupt-driven capture with a short thread per camera, ISP and GPU pre-processing submitted asynchronously with fences, a sync stage that groups frames by exposure timestamp with a deadline, batched NPU inference behind a latest-only queue, a small thread pool for post-processing, and one real-time tracker thread on an isolated core. Frames stay in a pre-allocated buffer pool; only handles move through bounded queues; every frame carries its timestamp and every drop is counted.

Q.2Why and what if

Why does the store-buffering test give r1 = r2 = 0 even on x86, which has a strong memory model?Intermediate

x86 TSO keeps stores in order and loads in order, but lets a load complete before an earlier store to a different address has left the store buffer. Both cores park their store and read the other variable from the cache, where it is still 0. Only a full barrier (mfence, a locked instruction, or seq_cst atomics) between the store and the load prevents it.

What if you replace the seq_cst operations in Dekker's algorithm with release/acquire?Advanced

It breaks. Release/acquire only orders a store with later operations of another thread that read that same store; it does not stop a thread's own later load from being performed before its earlier release store becomes visible. Both threads can again read the other flag as 0 and enter the critical section together. Dekker-style "set my flag, then read yours" needs a single total order, i.e. seq_cst or a full fence between store and load.

Why is lock-free code not automatically faster than a mutex?Intermediate

The cost of synchronisation is mostly the cache line moving between cores, and a contended CAS loop moves it just as a lock does, plus failed attempts waste work. An uncontended mutex is only an atomic or two. Lock-free pays off for bounded latency (no waiting for a preempted owner, no priority inversion) and in specific patterns such as SPSC rings, not as a general speed-up.

What happens if the producer sets an atomic flag without taking the mutex, but the consumer waits on the condition variable with a predicate under the mutex?Advanced

A lost wakeup becomes possible again. The consumer can check the flag (false) under the mutex, and before it is put to sleep the producer sets the flag and notifies; nobody is waiting yet, the notify is lost, and the consumer sleeps although the flag is true. The state change must happen under the same mutex (it can be released before notify) so it cannot fall between the check and the sleep.

What if you make the queue between camera and inference ten times larger to stop the drops?Intermediate

If inference is on average slower than the camera, nothing improves: the queue fills anyway, throughput stays the same, and every processed frame is now much older. A deeper queue only absorbs short bursts. The real choices are making inference faster, running more inference workers, reducing the input rate deliberately, or dropping the oldest frames and accounting for that downstream.

Why can adding a thread make a program slower?Basic

More threads than cores add context switches and cache pollution; shared locks become contended and each contention costs microseconds; shared counters or false sharing make cache lines bounce; and memory bandwidth may already be the limit, in which case more cores only queue at the memory controller. Amdahl's law adds that the serial part does not shrink at all.

Why does a real-time thread pre-allocate memory and call mlockall?Intermediate

Allocation takes allocator locks and may call into the kernel to map memory, with no bound on duration; a first touch of a page or a swapped page causes a page fault, which also takes unbounded time. Allocating and touching everything at start-up and locking it into RAM removes those sources of latency from the loop.

Why should the tracker use frame timestamps instead of assuming 33 ms between frames?Basic

Frames can be dropped, delayed by different amounts in different stages, and grouped across cameras whose exposures are not simultaneous. Prediction with a fixed 33 ms step then misplaces objects. The exposure timestamp from capture is the time the scene was observed, so motion models and fusion must use it.

What if the GPU is shared between surround-view rendering and a perception network?Advanced

Many GPUs switch jobs only at kernel or draw boundaries, so a long perception kernel can delay a display frame by its full duration, and both compete for memory bandwidth. You need hardware priorities or partitioning if available, splitting long kernels, explicit GPU time budgets per function, and worst-case measurements with both loads running. If one function is safety-relevant, the absence of timing interference must be argued, not assumed.

Priority inversion
A high-priority thread indirectly waiting for a lower-priority one, with medium-priority threads making the delay unbounded.
Process
A running program with its own virtual address space and resources, isolated from others by the MMU.
RCU (read-copy-update)
Readers access data without locks; writers publish a new copy by swapping a pointer and free the old one after all readers have finished.
Sequential consistency
All operations appear in one global interleaving consistent with each thread's program order; guaranteed for data-race-free C++ programs using seq_cst.
Semaphore
A counter of permits with blocking acquire and release and no owner.
Spinlock
A lock that busy-waits instead of sleeping; good only for tiny sections when the owner cannot be preempted.
Spurious wakeup
A return from a condition-variable wait without a matching notify, allowed by POSIX; handled by re-checking the predicate.
Store buffer
Per-core queue that holds stores until they can be written to the cache, letting the core continue; the main source of store→load reordering.
Thread
An independent flow of execution with its own stack and registers, sharing the address space of its process.
Throughput
Items completed per unit of time; for a pipeline, limited by its slowest stage.
Torn read / write
Observing a value that is half old and half new because it was accessed in more than one memory operation.
TSO (total store order)
x86's memory model: program order is kept except that a later load may complete before an earlier store to another address.
